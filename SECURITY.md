# Security policy

## In short

- Report a vulnerability through GitHub's private vulnerability reporting, never in a public issue ([Reporting a vulnerability](#reporting-a-vulnerability)).
- The design assumes you trust the repository and the source of the task: anyone who can push to it, launch a run, or is listed in `followup.trusted` can steer an agent that holds the credentials below, and this is not a sandbox for code you would not run on a developer's laptop ([The assumption](#the-assumption)).
- What limits the blast radius today: one container per run, per-repository identities, and narrow git credentials — a project-wide credential is not narrow ([What limits the blast radius today](#what-limits-the-blast-radius-today)).
- What is not on by default: the budget gateway, so with no `budget:` block the real model key sits in the agent's environment, and Vertex has no dollar cap in any mode ([What is not on by default](#what-is-not-on-by-default)).
- What no boundary stops: network egress is unrestricted, the agent shares the container with the runner and can read its `/proc`, and the caps are the gateway's — set a credit limit on every key you give Fugaro ([Known limits](#known-limits), [Money](#money)).
- Out of scope: an agent doing harmful things inside its own container with the credentials that job's service account is allowed to hold ([Scope](#scope)).

## Reporting a vulnerability

Please do not open a public issue for a vulnerability. Use GitHub's private vulnerability reporting: open the repository's **Security** tab, then **Report a vulnerability**. Include what you found, how to reproduce it, and the version (`fugaro version`) or commit.

We will acknowledge a report as soon as we can, work on a fix with you privately, and credit you in the advisory if you wish. This is a small project maintained by volunteers, so we cannot promise a fixed response time.

## Supported versions

Only the latest 0.x release is supported. Fugaro is pre-1.0; fixes land on `main` and ship in the next release.

## Trust model and known limits

Fugaro runs a coding agent with its permission prompts turned off, in a fresh cloud container per run, and ends every run with a pull request. This section says what that design protects, what it does not, and what you should do about the gaps. It describes the code as it is; the details, with file references, are in [docs/design/v1.md §6](docs/design/v1.md#6-security-model).

### Project scope is the default for a name that has one

`fugaro secrets set NAME` stores the value once for the whole installation — in the project's own Secret Manager, not a repository's — unless `--repo` is passed, which stores one repository's own copy instead. `--project-wide` is still accepted as a synonym of the default, so scripts written before the change keep working. This reverses the earlier rule, under which nothing was shared until the owner allow-listed a repository: storing at project scope now *is* the opt-in, and that is the point of the change — the default is the one an operator can see, rather than the one they have to remember. A name that has no project-wide meaning (a workflow's own `secrets:` entry, or the default Claude account's `claude-oauth-token`) keeps the repository scope it had. `bitbucket-token` is the other exception, and it is not a narrow case of the default but the absence of one: a Bitbucket credential is a repository access token, issued for one repository and usable for no other (Bitbucket's own scoping), so `fugaro secrets set bitbucket-token` always stores the repository's own copy — the project-wide store is refused for it unless the operator's local config allow-lists repositories in `project_secrets.bitbucket-token`, which the owner ruled on 2026-10-15 is only right for a credential that really does serve several repositories (see "Narrow git credentials" below).

**The reach is every enrolled repository.** Until a routing policy is published, that means every repository the local config knows; once one is published, every repository that policy admits. Either way this is the whole installation, not the repository whose job holds the value.

**Inside a shared job there is no IAM boundary between repositories — the profile is the boundary.** Today each repository still has its own job and its own service account, and a project secret is mounted on that job only for a name the repository may use (a reserved secret; a model provider's key per its own `allow_data_to`; a named Claude account's token per its own `allow_data_to`). Once shared project jobs exist, one job carries runs for several repositories: the boundary between them is then the profile the run is admitted under, not an IAM grant, and a project secret in that job's environment is readable by every one of those runs.

A repository's own copy of the same name always wins over the project copy, until the copy's last enabled version is disabled — so passing `--repo` is how a value stays this repository's.

**The data-policy gate is unchanged.** A model provider's `allow_data_to` still decides, at runtime and before any call, which repositories' code the gateway may send to that provider; a project-scope key mounted in a job is not permission to route another repository's code anywhere. A named Claude account's `allow_data_to` is likewise the only gate on its token until phase 5 replaces that fixture with person-owned secrets. And `workflows.<n>.secrets` cannot be shared this way at all: a workflow's own secret stays a repository copy.

### The assumption

**The design assumes you trust the repository and the source of the task.** Everyone who can push to the repository, everyone who can launch a run, and (for follow-up runs) the people listed in `followup.trusted` can steer an agent that holds the credentials below. Fugaro is built for a team running it on its own code. It is not a sandbox for code you would not run on a developer's laptop.

**A run may also be given files, and may also be asked for one.** An artifact run (`docs/design/artifact-runs.md`) has no git token and no pull request: it is handed files the launcher attached, and it leaves files in the runs bucket instead. Two consequences follow, and neither is a sandbox. **In:** an attached file is trusted exactly as much as the task text, since the agent reads it and can act on what is in it — a screenshot can contain a token, a customer's name or someone's face, and an operator who attaches a file they did not write has handed the agent that content as an instruction. **Out:** an artifact is output of the same unsandboxed agent, written to `runs/<slug>/<run>/artifacts/` under this repository's job account — the account a run of this repository runs as; there is no per-run account — so every launcher and every operator of the installation can read it (a launcher holds `objectViewer` on the whole bucket, an operator `objectAdmin`), every run of the same repository can read and overwrite it (the account is scoped to the repository's prefix, not to one run), and it is deleted with the rest of the run's record after 90 days by default. Nothing about an artifact is trusted: `fugaro artifacts get` verifies the sha256 recorded by the run, refuses a mismatch, never opens, executes or unpacks what it writes, and downloads into a **fresh directory it creates** (never `.`) — so a crafted name in a tampered record cannot land a `.git/hooks/` or `.claude/` file in a checkout you are working in. **And what produces it is repository text read once, which is not a boundary against the agent:** `commands.render` and `commands.probe` are the repository's own commands, kept in the runner's in-memory workflow configuration rather than re-read from a file the run itself can write, so the command string that ran is the string a reviewer read at the task's ref — but the plan stage and the render step are the same container, the same user and the same environment, so a render command that names a file in the checkout runs **that file's working-tree bytes**, which the plan stage could have rewritten, no more and no less than every other file in a checkout the agent controls.

That hash is **integrity in transit, not tamper evidence**: it and the artifact live in the same repository-scoped prefix, so anything that can rewrite one can rewrite the other — including another run of the same repository. Tampering is not detectable today; what is guaranteed is that the bytes you receive are the bytes the run uploaded.

**The render step runs with the run's own environment, secrets included.** `commands.render` executes as the agent's user with the agent's environment, so a workflow's secrets are visible to it — that is deliberate and is why an artifact recipe must not be handed to an untrusted repository. The runner builds the workflow's secret names into that environment only when `!r.review` (the `secretEnvs` block in `internal/runner/runner.go`), hands the result to `r.env` via `agent.BuildEnv`, and `runRender` in `internal/runner/artifact.go` starts the command with `Env: r.env`. It also means a render command can write a secret into a deliverable, and the deliverable is readable by everyone the paragraph above names.

**Today that "everyone" stops at this repository, and that boundary is a precondition, not a property of artifacts.** An artifact run's account is the repository's job account, so only runs *of this repository* can read or overwrite its deliverables. Project-centric phase 3's shared project jobs and the VM backend's accounts are **not** per-repository: on either of them the same run's inputs, artifacts and record would be readable and overwritable by **every run on the profile**. Because that blast radius has not been reviewed, **an artifact-producing run stays on the plain per-repository Cloud Run backend until a per-run prefix condition or a per-run account exists** (`docs/design/artifact-runs.md` §8.5, D11). **No code in this slice enforces that, and this document does not claim it does**: it is a decision about when artifact runs may be *enabled* on those backends, and the plan that does so must bring the per-run boundary with it. Until then an artifact run is only ever launched on the per-repository Cloud Run backend this installation uses today.

### What limits the blast radius today

- **One container per run, discarded at the end.** Nothing in the container itself persists between runs. What does persist is in the runs bucket by design: a cache a later run restores (`cache/<slug>/`) and a session a follow-up may resume (see below). The agent runs as an unprivileged user with no sudo and no setuid escape (the image self-test checks this on every build).
- **Per-repository identities.** Each repository's jobs and builds run as their own service accounts. A job can read only the secrets its own workflow declares (not every secret the repository has), and it can read and write only its own repository's prefixes in the runs bucket. That scoping is the job account's alone; it does not mean the bucket itself is isolated between repositories or between launchers — see "What is not on by default" below.
- **Cloud keys stay in the cloud.** No command copies a secret value back to your machine, and `fugaro secrets` never prints one.
- **With the budget gateway on, model keys stay out of the agent's environment.** With budget `observe` or `enforce` and `auth: api-key`, or `vertex` under `observe` (Vertex under `enforce` is refused outright, see "What is not on by default" below), the agent's calls go through a per-run gateway: with `api-key` it gets a gateway token instead of the real key, and on Vertex the gateway fetches the job's own token instead. Either way the gateway pins the models and charges every call against the caps. This is off by default.
- **Narrow git credentials.** On GitHub, a run gets an installation token for its one repository (contents and pull requests write, issues and metadata read) that expires within about an hour. The App has no `workflows` permission, so a run cannot change `.github/workflows/`. On Bitbucket, it is a repository access token, scoped to that one repository by Bitbucket's own design. **A project-wide git credential is not narrow.** `fugaro secrets set bitbucket-token --project-wide` (or `github-app-key`) stores one workspace token, or one App key, for the whole installation — and, since project scope became the default for the App key (see "Project scope is the default for a name that has one" above), `github-app-key` does so with no flag at all. `bitbucket-token` needs an explicit `project_secrets.bitbucket-token` allow-list to be stored that way, and its per-repository default is why: a repository access token serves the one repository it was issued for. Every enrolled repository mounts the project copy: the token reaches the repositories that workspace token covers, and the App key mints tokens for every repository the App is installed on — not only the repository whose job or build holds it. Use it only where that reach is what you mean.
- **Logs are isolated** in their own log bucket, readable by the people you made launchers, and redacted of every mounted secret, including common encodings. Redaction is best effort. Project Owners and Editors can still read every log, isolated or not. Cloud Build's own logs are never moved there: they carry a repository's build output, which by design never includes a secret value. `fugaro init --no-log-isolation` leaves Fugaro's own logs in `_Default` too.

### What is not on by default

Three gaps are easy to miss, because nothing warns you about them:

- **Budget mode defaults to off.** With no `budget:` block in the installation's own config (the project ceiling `fugaro init` writes), or an empty `mode`, there is no gateway and no per-call cap: the real model key sits in the agent's environment like any other secret, and the only limits are the provider account's own limit and the token cap, if you set one (0 is none). A repository's own `fugaro.yaml` can only tighten that ceiling, never loosen it.
- **Vertex has no dollar cap, in any mode.** `auth: vertex` with budget `enforce` is refused at `fugaro validate`/`init --repo`, and again by the runner before the agent starts, so a Vertex repository can only run `observe` or off in practice. There is also no key to put a credit limit on: the job's Vertex calls are authenticated by the job's own service account through the metadata server, not a key you hold.
- **Every launcher can write `runs/`, for every repository, even after the 0.7.0 bucket IAM hardening.** Before 0.7.0, or on an installation whose operator has not yet run 0.7.0's `fugaro init` to apply the migration, every launcher — not only operators — holds `roles/storage.objectAdmin` on the entire runs bucket, unconditioned, including the installation-wide project layer, recipes and shared config: a launcher can rewrite the project layer's commands or add an `image.setup` that runs in the next rebuild, replace a recipe or the shared config, or poison another repository's cache — all without launching a run, reaching that repository's secrets through its next build or job. Project Owners, Editors and anyone with a project-level storage role bypass the bucket's own policy regardless, hardened or not ([docs/design/bucket-iam.md](docs/design/bucket-iam.md) §9). Once the hardening is applied, a launcher's grant narrows to `roles/storage.objectViewer` (the whole bucket, unchanged) plus `roles/storage.objectUser` on `runs/` only — but `runs/` holds every repository's runs, not only the ones a launcher was onboarded to, so a launcher can still ([docs/design/bucket-iam.md](docs/design/bucket-iam.md) §10, item L3): overwrite another launcher's queued `task.json`, forge `result.json` or `launch.json`, set the `cancel` marker on anyone's run, or plant a `session/` file or `followup.md` that a later follow-up of that repository restores (see "A follow-up's protections are hygiene, not boundaries" below). What a launcher can no longer do, once the hardening is applied: write the project layer, the shared config, recipes or the marker; rewrite a build record, `check.json` or a layer copy; poison `cache/`; forge or steal `locks/`. The `fugaroLauncher` custom role, which every launcher also holds (a separate grant from the bucket one above), additionally lets any launcher list every secret in the project (names, labels and version counts; reading a value still needs `secretAccessor`, which only the job and build accounts hold).

### Known limits

These are real, current gaps. Each is a decision or a later hardening item, not an oversight.

- **What one run's agent can reach.** On a first run the agent's environment holds:
  - the repository's git token (as a credential helper, `FUGARO_GIT_TOKEN` and `GH_TOKEN`);
  - the per-run gateway token;
  - every secret the workflow declares.

  It shares the container and its user with the runner, so it can also read the runner's environment through `/proc`. That includes:
  - **the GitHub App's private key**, which can mint tokens for every repository the App is installed on (use one App per repository if that matters to you);
  - the real model and provider keys;
  - the job's service account, through the metadata server.

  Commands run through `fugaro verify` see the agent's full environment.
- **The managed settings file only guards against committed configuration, and only with the gateway on.** With the gateway on, the runner writes it before every stage, with the highest precedence, so a repository's own `.claude/settings.json` can't reroute the agent's model calls by itself, and the runner refuses to start a stage if anything still routes around it. With budget off there is no managed file and no routing check at all, so a committed `.claude/settings.json` can send the agent's calls, and the key, anywhere. Even with the gateway on, the file is writable by the agent's own user — the runner's — so a compromised agent can edit it mid-stage, or read the gateway token and the real key from the runner's `/proc` directly, same as above.
- **A follow-up's configuration can be stale, but its working tree isn't.** A follow-up reads `fugaro.yaml`, `agent.instructions` and the review prompt from the base branch, but Claude Code still loads `CLAUDE.md`, `.claude/` (skills, settings, subagents) and `.mcp.json` from the pull request's own branch, so a hook or MCP server planted there runs with the job's full environment and secrets. Review a PR's diff with that in mind before launching a follow-up on it.
- **Any launcher can mint a budget identity for any repository.** The signing account that mints a run's Firebase custom token holds no roles itself, but every launcher — not only the ones who onboarded that repository — holds `signJwt` on it, so a launcher credential is budget write access up to the caps for every repository, not only their own.
- **A launcher can override a job's environment, and the project's policy is read from it.** Anyone who may launch may pass environment overrides to `jobs.run` — Check 49 step 6 (added by Task 1.7, owner-run) sets `FUGARO_RUN` on a live job to show exactly what that reaches — so a launcher can also clear or redirect the two variables that decide whether a run reads the project's policy at all: `FUGARO_RTDB_URL`, the pointer to the database, and `FUGARO_FIREBASE_API_KEY`. Pointed at another database, or cleared, the run has no policy to read, and since project-centric mode *is* the published node, what it does next depends on the job it runs in: a **budget-on** job stops, because its launcher minted it a budget token — it mints whenever it can see a published policy or a shared budget, whatever the run's own mode — and a run launched with a token whose job carries no budget backend to read the policy with refuses rather than falling back (the same refusal a mode-on job meets when the token object has been removed from the bucket); a **budget-off** job of a project that has published nothing has no token and no marker to refuse on, and runs on the ceiling its job was deployed with, the same ceiling an installation that has never published a policy runs on. The budget token deliberately does not travel that way: it is a Firebase custom token minted per run and left in the runs bucket, never passed as an environment value, because the request that starts a job reaches audit logs. The `FUGARO_BUDGET_TOKEN` marker that makes a missing token a refusal is itself an environment value a launcher may set or clear, and a launcher who can write `runs/` can remove the token object that marker points at (see "Every launcher can write `runs/`" above). A launcher is also closer to choosing which repository a run is for than the run's own refusals suggest: it can set `FUGARO_RUN`, the run's storage slug, and anyone who can write `runs/` can write the `task.json` of any run (see above), so the slug-and-task pair an admission is computed from is not beyond a launcher. What stops that today, on a phase-1 job, is the per-repository job's bucket condition: the job's service account holds its own slug's prefixes, so a `FUGARO_RUN` override naming another slug fails at the task read, before the admission check runs, and for the bucket condition's reason rather than the binding's. Check 49 step 6 is what records which of the two refusals appeared; the binding's own live proof is the phase-3 check on a project job, Check 53 step 6 (added by Task 3.7), where the admission check is the only thing that can refuse. The run's own refusals are what a project job relies on: the slug must be the slug of the repository the task names, a remote on another provider's host is refused, and the project's allow-list is matched against the provider kind derived from that slug, never against `FUGARO_GIT_PROVIDER`, which may only refuse. `FUGARO_REMOTE` is not tied to the task's repository, though: it is where a job whose image has no checkout clones from, and everything the remote gives away is compared with the task before anything is cloned, in the admission check the run makes before any git credential is requested (`internal/runner`'s `admissionCheck`, reading the remote through `remoteHost`, `remoteEndpoint` and `repoNamedByRemote`). Refused there are: a remote on another provider's host; one on a host no provider kind owns — `github.com` and `bitbucket.org` are the two, so a self-hosted forge is refused — because the run scopes this repository's git credential to the remote's endpoint — scheme, host and port — with no allow-list of its own; one written over `http` (that credential in cleartext), or one naming a port on an `https` remote (that credential sent to an endpoint the provider does not serve); and one whose path names a repository other than this run's, a group or project path included — `task.CanonicalRepo` allows a nested path such as `acme/group/app`, so the path is compared with the task's own repository segment by segment and refused when it differs, rather than read as "no repository" — as is any path a repository name cannot hold (dot segments, an empty segment, an encoded separator, `acme/app.git;x`), which is a refusal rather than a skip because git may resolve such a path to a repository this run is not for. On a project job `FUGARO_REMOTE` is not read at all: the clone URL is computed from the task's repository, the job's provider and the policy (Task 3.3). On a per-repository job, what is not compared with the task at all is the remote that gives the comparison nothing to read: one naming no host — an empty `FUGARO_REMOTE`, a local path (`/srv/git/app.git`, `./app`, `file:///tmp/app`), a bare `github.com` with no scheme — and one naming a host but no repository path (`https://github.com/`). And with `FUGARO_GIT_PROVIDER` also unset and the remote naming no host, the provider the run opens is the one the cloned repository's own `fugaro.yaml` names, which is not compared with the provider derived from the slug either; where the remote does name a host, the provider is that host's kind, and a `git.provider` that disagrees with it is refused (the token is scoped to its own host). This is an accepted decision, not an oversight: the launcher holds the job's own credentials, and this list's first items already say what a launcher can reach. The launcher-side refusals `fugaro run` makes (a repository the policy does not admit, a policy newer than the binary) are advisory for the same reason — they are there to tell an operator before a job fails, and the run makes its own.
- **A follow-up's protections are hygiene, not boundaries.** Pull request comments sit inside a nonce-delimited block, but a model can still follow instructions inside it; the delimiter only keeps a legitimate review comment from being mistaken for one. A resumed session is replayed as the agent's own earlier turns, outside that block, so anyone who could write to a previous run's session file can plant context there: any run of the same repository (they share the job's service account and bucket prefix), and, since 0.7.0, any launcher of the installation at all — a launcher's `runs/` write reaches every repository's session files, not only the ones they were onboarded to (see "Every launcher can write `runs/`" above).
- **A proxied network's credentials reach the agent.** `HTTP_PROXY` and `HTTPS_PROXY` pass through verbatim so the agent works on proxied networks; `NO_PROXY` does too, except that with the gateway on the runner adds the loopback addresses to it. A proxy URL with `user:password@` embedded is as readable to the agent as any other variable. Authenticate your proxy by network or identity, not a URL credential.
- **Network egress is not restricted.** A run can reach any host. Prompt injection through the repository, a dependency, an issue or a PR comment could send source code or the credentials above anywhere. A VPC with egress rules is a later hardening option, not built.
- **The base branch is protected only by your branch protection.** The runner pushes only to `fugaro/<run-id>` branches, but the agent holds a token with contents write and can run `git push` itself. Require reviews and status checks on your default branch: Fugaro relies on it.
- **The agent can open or edit pull requests itself** with `gh`. Its instructions tell it not to; nothing technical stops it.
- **Money.** The gateway's caps bound a run that goes through the gateway. An agent that reads the real key from `/proc` can spend outside it. The backstop is the provider account's own limit: set a credit limit on every key you give Fugaro (Anthropic workspace limits, OpenRouter credit limits; Vertex has none to set, see "What is not on by default" above). With `auth: oauth` there is no gateway, only the token cap and the kill switches. A run's budget identity can reserve, up to the caps, until it expires (job timeout plus about an hour), even after the run ended.
- **An artifact run's compute is not capped.** The budget's caps count model dollars (`docs/design/m9-spec-v3-reconciliation.md` §7.4's reconciliation), and a render is compute: it is bounded by the run's own clock (`timeouts.total`, and a Cloud Run task timeout of `total + 2m`) and by the workflow's `resources`, never by `budget.per_run_usd`. `result.json`'s `cost.compute_usd` is an estimate, reported and never charged. If you give an artifact workflow 8 vCPU, a two-hour total, and a command that never finishes, you pay for two hours of 8 vCPU and the caps will not stop it.
- **Runs of one repository can see each other, and the 0.7.0 bucket IAM work does not change that.** They share a service account and its bucket prefixes, so a hostile run can read or overwrite another run's records and caches in the same repository. [docs/design/bucket-iam.md](docs/design/bucket-iam.md) is explicit that a compromised agent inside a run is unchanged by that work; it narrows what *launchers* can write (see "What is not on by default" above), not what a run's own job account can reach. **A shared project job widens that from one repository to every repository in the runs bucket, not to a profile, and that regression is stated here.** Phase 3's module (`deploy/terraform/gcp/modules/project/`, design [docs/design/project-centric.md §4.1](docs/design/project-centric.md)) creates one Cloud Run job and one job service account per (profile, provider, Claude account), and `fugaro init` creates one for every profile a local config names. Such an account serves every repository admitted to its profile, so its runs-bucket grant cannot name one slug: the condition covers the whole of `runs/`, `cache/` and `locks/` — **every** project job account gets that same condition, whatever its profile, and it reaches every repository's objects in the bucket, including repositories on other profiles and repositories that still run their own per-repository jobs. **That is a loss of a property this document credits 0.7.0 with gaining** (above: 0.7.0 removed "poison `cache/`" and "forge or steal `locks/`" from what a launcher can do). A run is an untrusted agent, unlike a launcher: a hostile one on a shared job can poison **another repository's cache** — cross-repository code execution on that repository's next run, since a cache it restores is code and configuration the run executes — **forge or steal a lock**, and **rewrite another repository's queued `task.json`**, which is what a run's task, ref and workflow are read from. Two more things the same prefixes reach, neither of which the design's accepted decision D4 listed on its own: **another queued run's budget token** (`runs/<slug>/<run>/budget-token`), which is that run's Realtime Database identity and not a cache entry — an accepted decision of its own, D13, ruled by the owner on 2026-10-15, with the design that replaces that channel, [docs/design/budget-token-channel.md](docs/design/budget-token-channel.md) — its open decisions D14 to D19 were answered by the owner on 2026-10-15 — still awaiting the owner's approval to implement: no code follows that document until the owner approves it — and **another run's `launch.json` and `result.json`**, which is why the runner checks the execution it was launched as (`CheckRunExecution`; plan Task 3.4). **A profile separates secrets, not bucket objects.** Different profiles are different job service accounts, so a profile decides which secrets a run can read; it does not keep one repository's run away from another repository's `runs/`, `cache/` or `locks/` objects, because the object layout is `<prefix>/<slug>/…` with no profile in it and so no per-profile condition can be written. Putting repositories that must stay apart — including repositories that must not share a budget identity — on different profiles therefore does **not** isolate them in the bucket. D4's and D13's rulings named separate profiles as the mitigation on the premise that a profile is a bucket boundary; that premise does not hold, so **the mitigation is an open question for the owner to re-rule** (narrow the object layout per profile, keep such repositories off shared jobs, or accept the installation-wide reach), and until then the only bucket isolation is not deploying a shared job: an installation that names no profile in its config gets no project job and keeps the per-repository grants. D4 and D13 are the owner's decisions in [docs/plans/2026-10-14-project-centric.md](docs/plans/2026-10-14-project-centric.md); an installation that names no profile in its config gets no project job and keeps the per-repository grants.
- **Follow-up runs act on pull request comments** from the people in `followup.trusted` on the base branch (and, on GitHub, only owners, members and collaborators among them). A trusted person who quotes an untrusted comment passes it on. A follow-up's agent gets no git credential and no `GH_TOKEN` in its own environment — the runner fetches and pushes the branch itself, and the comments arrive in the prompt — but it still shares the container and user with the runner, so it can read the token from the runner's `/proc`, the same residual as the model and provider keys above.
- **The managed deployer exists in every installation, and its fence has not been measured.** Every owner-run `fugaro init` plans a `fugaro-deployer` service account (`deploy/terraform/gcp/modules/installation/deployer.tf`), `belong` included, and grants each principal in the installation's `operators` list `roles/iam.serviceAccountTokenCreator` **on that account alone** — so an operator, and nobody else, may impersonate it. It holds one unconditioned custom role, `fugaroDeployer`, of create and read permissions (including `iam.serviceAccounts.create`, `run.jobs.create`, `storage.buckets.create` and `serviceusage.services.enable`), and nothing else unless the installation sets the module's `managed_deployer_scoped` — **which nothing sets**, so in 0.9.0 an installation gets the account and the unconditioned role and no conditioned role at all. **What the account is for is a feature that is gated off**: `internal/cli`'s `managedDeployerShipped` is false, so `fugaro init --create-project --managed`, `fugaro managed apply` and `fugaro restore` refuse before any cloud call, and no code path applies a plan as this account. **The fence, when it is turned on, is seven conditioned roles — one per service, each bound once — whose conditions admit only names carrying the reserved `fmgd-` prefix**, using `resource.name.startsWith` where the front of the name is fixed and `resource.name.extract("<template>").startsWith` where a middle segment is not knowable before apply (design [docs/design/managed-deployer-fence.md](docs/design/managed-deployer-fence.md), option 1). **Two things about it are unverified, and this document does not claim otherwise**: whether IAM honours `resource.name` at all for an IAM service account, a Cloud Run job, a Cloud Scheduler job, an Artifact Registry repository or an API key — **this is what Check 68 of [docs/gcp-live-checklist.md](docs/gcp-live-checklist.md), written, owner-run and not run, measures per service and in both directions** — and whether a name that does not match an `extract` template makes the condition false (fail closed) rather than true, which **no check in this tree can measure** (a name of a conditioned type that misses its own template cannot be created) and which therefore stands as accepted-unmeasured until the owner rules on the design's §8 point 2. Until Check 68 has run and passed, do not read the prefix condition as a boundary. A permission whose condition Google does not honour is **dropped** from the role rather than granted unconditioned, so an unsupported service costs the feature that type, not a hole. **And what the fence does not do**: it constrains the program's apply path, not an agent that goes around it — the agent's session holds the operator's credentials, which can impersonate the deployer (design §6 item 4).

### The VM backend, and the Docker daemon it gives a run

Fugaro can run a workflow on Cloud Batch instead: one VM per run, for workflows that ask for `docker: true`. Nothing selects that backend in this release — an installation's config refuses `backend: cloud-batch` until it is enabled deliberately — and this is the model that decision is made with. The details are in [docs/design/compute-backend.md §3](docs/design/compute-backend.md#3-security).

- **A run that asks for Docker is root on its VM.** The recipe mounts the VM's Docker socket into the container and adds the container's process to the socket's group ([§2.2](docs/design/compute-backend.md)). Access to that socket is root-equivalence on the VM: `docker run --privileged -v /:/host` is the VM's filesystem, its service-account token and its network. It is not a new *secret* exposure inside the run — the agent already shares the container and its user with the runner and can read the runner's `/proc` (see "What one run's agent can reach" above) — but it is root on the host the run stands on, which the Cloud Run path does not have: there a job is a container with no daemon and no root.
- **That root is not the agent's alone — it is every command the repository gets to run.** The socket is mounted for the whole run, so a `docker` call in the repository's own scripts, a test that starts a container, a Dockerfile's build steps, a Makefile target, a package's post-install step — anything the workflow or the repository causes to execute — reaches the same daemon with the same power as the agent's own commands. Fugaro makes no distinction between them: a run that asked for `docker: true` asked for the repository's code to have root on the VM, not only for the model to have it. Treat `docker: true` as a statement about the repository: enabling it for a repository whose code you do not review is enabling root-on-a-VM for that code, and the container boundary the "Out of scope" note below draws is the container, not the VM.
- **The VM is the isolation unit, and it is never reused.** One run, one VM, deleted on every exit path. Nothing at the OS level crosses from one run's VM to another's: separate VM, separate kernel, separate Docker store. That is stronger than Cloud Run's shared job against *other runs*, and weaker than it against *the host*, which on Cloud Run does not exist.
- **The IAM boundary is unchanged.** A VM runs as the job's own service account, at the same granularity project-centric D4 already accepted: by default the account of the (profile, account) pair, so every repository on that profile runs under one account, can read every object and secret that account reaches, and can poison another repository's cache and locks. A per-repository service account is expressible on this backend and would restore the per-repository boundary for the repositories that opt in; until an installation does that, the cross-repository loss is exactly what it is on Cloud Run's shared job.
- **The metadata server is reachable**, by the agent and by every container it starts, so the VM's service account is one request away.
- **Root can outlive its own runner.** Through the socket the agent can stop or kill the runner's process on the VM, and the VM keeps billing until the job's `maxRunDuration` or the sweeper's teardown ends it. It can also leave containers running that no Fugaro code knows about. That is why the VM, not the runner process, is the unit that gets reaped, and why a leaked VM is found by the sweeper and deleted.
- **The budget caps stay model-only, and bypassable.** The gateway's caps count model dollars and are enforced in-process by `fugaro exec`. An agent that holds the provider key — on this backend, every container it starts can read it from the host — can call the provider directly, off the gateway, and nothing halts it. The VM's compute also keeps billing after the runner is gone. The backstop is the provider account's own credit limit, the same one "Money" above names.
- **Who can launch, and what that reaches.** On Batch a launcher needs `roles/batch.jobsEditor` on the **project**, plus `roles/iam.serviceAccountUser` on the account a job names. A project-level `batch.jobsEditor` is not confined to Fugaro's repositories, images or commands: a launcher can create a job with any image, any command and any secret it can name, running as any account it holds `serviceAccountUser` on, and can cancel or delete any job in the project, including another launcher's. The Cloud Run path is narrower — a launcher runs one named job per (repository, workflow), so the image, the command and the environment are the job's. Enabling this backend trusts launchers further.
- **Egress is unchanged.** A run's VM has no external IP, but egress is still unrestricted: the agent can send whatever it can read anywhere the network allows, exactly as the Cloud Run path does ("Network egress is not restricted" above).

### Running Fugaro on repositories with external contributors

- Do not launch runs whose task text you copied from an untrusted issue or comment without reading it: the task is an instruction the agent follows.
- Keep `followup.trusted` to people with write access.
- **A first run or follow-up gives a fork's pull request no special handling at all.** If such a run checks out and executes a fork's code — a build script, a test command — that code runs with the workflow's secrets, the same as any other code a run touches. Treat a fork's pull request with the same caution as an untrusted task.
- **`mode: review` (`review-only`, `pick`) is trusted-author-only** (owner ruling 2026-10-13): it reviews a pull request only when the author's LIVE GitHub `author_association` is OWNER, MEMBER or COLLABORATOR, right now, or the author is Fugaro's own identity on a pull request it opened itself — fork or not. `followup.trusted`, the account-ID allow-list a follow-up's own comment trust also consults, plays NO part in this decision: unlike the live association, a list entry does not expire or re-check itself, so a person removed as a collaborator but left on the list would otherwise stay trusted here indefinitely. An outside contributor's pull request is refused outright, whether or not its head is in a fork; there is no flag to let one through. A **trusted** author's own fork is reviewed only when the fork repository's owner is that same trusted author, so a shared or organizational fork can't carry someone else's commits under a name the trust check never sees. Bitbucket has no `author_association` at all: review mode accepts only a same-repository branch there (pushing one already needs write access) and refuses every fork. None of this is a sandbox, though: the reviewing agent is still the same unsandboxed process, as the same user, in the same container, as every other run. A **trusted** author's own prompt injection (`CLAUDE.md`, a commit message, the diff itself) is still code execution under `--dangerously-skip-permissions`, and that code can still read the runner's own `/proc` environment (see "What one run's agent can reach" above) for every workflow secret, the GitHub App's private key, the real provider keys and the job's service account token, and send any of it out over the open network egress nothing here restricts — redaction of the posted comment and the logs only ever masks what Fugaro itself publishes, never a secret a running process exfiltrates on its own. Trusting a person this way also trusts what THEY trust: a collaborator who lets other people push to their own fork, or who enables "allow edits by maintainers" on their pull request, or who merges someone else's commits into their own branch, extends review mode's trust to all of it — the check is "whose fork, and whose association", not "whose commit". "Member" and "collaborator" are GitHub's own categories and can be broader than you expect: a MEMBER is any member of the organization, even one with no access to this particular repository, and a COLLABORATOR can be a read-only one. A stricter check (the collaborator's actual permission level) is possible future hardening whose required GitHub App permission is unverified; see [docs/recipes.md §3](docs/recipes.md) for the full account.
- Give Fugaro its own provider keys with credit limits, and its own GitHub App, installed only on the repositories it serves.
- Public repositories are refused for follow-ups unless `followup.allow_public` is set, for the same reason.

## Scope

In scope:

- The budget gateway, the Realtime Database rules and token handling that enforce the shared budget
- Credential handling: secrets in Secret Manager, `fugaro secrets`, redaction of logs and PRs, the runner's use of provider and model tokens
- The IAM and Terraform that `fugaro init` creates (per-repository isolation, custom roles, bucket conditions)
- The CLI and the runner (for example path or command injection from a task, a repository's `fugaro.yaml` or a PR comment)
- The release pipeline (checksums, signatures, the Homebrew cask)

Out of scope:

- An agent doing harmful things inside its own container with the credentials that job's service account is allowed to hold: the trust boundary is the container, and the design says so openly
- Problems that need an attacker who already holds your cloud project's owner credentials
- Vulnerabilities in Google Cloud, GitHub, Bitbucket or a model provider themselves; report those to the vendor
- Denial of service by spending your own budget

The trust boundary and what each credential can reach are described in [docs/design/v1.md](docs/design/v1.md#6-security-model) (section 6, Security model).
