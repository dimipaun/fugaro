# Credentials service

- Everything here is security-sensitive. Get an independent review before merging, and never merge on an in-loop `ship` alone.
- Once the caller's identity is verified, every refusal writes exactly one audit line (`internal/credsvc/audit.go`). No path may write zero lines or two.
- No credential value, token or key may appear in an audit line, a log line or an error. A refusal names the field, never its content. Test fixtures carry no secret-shaped literals either.
- The service is deployed for every installation: `fugaro update` deploys it — there is no flag and no separate command — and the deployment alone switches nothing on. A run reaches the service only where the switch is on: the repository's own root re-applied with it, the installation's bundle holding the credentials that repository's runs need — the one its `agent.auth` calls for, under EVERY account those runs may go out on, and the git credential its provider needs — and that repository's `agent.auth` being a cascade, or an `api-key` or `oauth` one on a project whose published budget mode is `observe` or `enforce` (D2071 — the gateway that reaches the service exists only there). `fugaro creds set` is the bundle's only writer and is refused inside an agent or a run. Never run it.
- `config.ServiceHeldSecretNames` stays empty. Flipping it (#907) takes the GitHub App key's mount and accessor off the job, and the owner gates it on live checks 94-96 and 99. A Terraform guard test (`modules/workflow`, `roots/repo/tests`) holds the module's mirror to it.
- `config.ProxiedGitSecretNames` holds `bitbucket-token`; **change it only with the owner's go**. It is the flip list that takes a **proxied** repository's Bitbucket token mount and accessor off its job (B1.13 part two, D500), and it fires only where the published node's block admits that repository with `proxy: true` and the installation's credentials service is deployed; every other Bitbucket repository keeps both. `modules/workflow/sa.tf` mirrors it, and only `deploy/terraform`'s `TestProxiedGitSecretNamesMatchTheModule` can hold the two spellings to each other — a `roots/repo/tests` run cannot read Go, so its runs pin the drop for the list the module spells. The flip **ships** in 0.26.0 — the release after the proxy chain's (whose own is the one `proxySince` names, 0.22.0, `internal/cli/recipes_skew.go`) and after 0.23.0, which went out without it; the owner released the hold on 2026-11-16, and the notes are `docs/releases/v0.26.0.md`. Removing the token from this list is the owner's go read backwards. The drop does not wait on the bundle by itself: `fugaro update` refuses to drop a proxied repository's mount until the bundle holds the token, the refusal naming the one command (the owner's O8 ruling of 2026-11-15), so there is no operator step for the order.
- `config.ServiceServedAuths` holds `api-key` and `oauth`; **change it only with the owner's go**. It is the flip list that takes a switched `api-key` or `oauth` repository's model mounts — the Anthropic key and the Claude OAuth token — and their `secretAccessor` off its job (B2.7, D2072, G17), and it fires only where that repository's own root has been re-applied with the switch on and the published mode is `observe` or `enforce`; every other repository keeps both, and a provider key (`FUGARO_PROVIDER_KEY_*`) stays mounted even on a switched one (R6, D1634). `modules/workflow/sa.tf` mirrors it in its `anthropic` arm and only `deploy/terraform`'s guard tests can hold the two spellings to each other; Go's half is `internal/infra`'s `ModelSecretsServed` and `dropModelMounts`. The flip **ships** in 0.26.0: the owner gave the go on 2026-11-18, moving Check 193's owner-run checks to after the flip (B2.8), and the notes are `docs/releases/v0.26.0.md`. Removing a name from this list is the owner's go read backwards. The order is what `serviceAuthSince` (`internal/cli/recipes_skew.go`) gates: a run of a switched `api-key` or `oauth` repository is refused on a job image below that release, whose runner reads the mounted key this list takes away. And `fugaro project policy publish` refuses to lower the budget mode to `off` while such a repository is switched (D2071 (a)): the mode is read at `update`, so a lowered one would leave switched jobs with no mount and every run halting until `update --repo`.
- `config.VaultFetchedSecretClasses` holds `workflow`; **change it only with the owner's go**. It is the flip list that names the class of secret the service FETCHES for a switched repository's run rather than letting its job mount it (B3.8, D2072's shape, G17): a class on the list means the job gives up the `secretAccessor` on and the mount of every secret of that class, and the runner reads each declared one from the service at bootstrap (B3.4). `config.VaultSecretClassWorkflow` is a workflow's own `secrets:`, the one class D1267's ruling puts on this path. `modules/workflow/sa.tf` mirrors the list in its `vault_fetched_secret_classes` local and only `deploy/terraform`'s `TestVaultFetchedClassesMatchTheModule` can hold the two spellings to each other. Go's half is `internal/infra`'s `dropVaultMounts`, whose answer (`WorkflowSpec.VaultSecretNames`, the tfvars' `workflow.vault_secret_names`) is what the module reads for the names of THIS workflow, so a repository whose own root was never re-applied with the switch on keeps every mount (G9, D147). Unlike the other three flips this one does NOT narrow the service's set: a workflow secret's value is read from the job's own container at fetch time, so `modules/workflow/sa.tf`'s `service_secret_names` keeps the container after its mount goes (D2074, B3.3). The flip **ships** in 0.27.0: the owner gave the go on 2026-11-18 with the other three flips of the chain, moving Check 194's owner-run checks to after the flip (B3.9). Removing the class from this list is the owner's go read backwards. The order is what `vaultSince` (`internal/cli/recipes_skew.go`) gates: a run of such a repository is refused on a job image below that release, whose runner mounts the value and cannot fetch it.
- `config.BuildServedSecretClasses` holds `git` and `build`; **change it only with the owner's go**. It is the flip list that names the classes of secret the service serves to a repository's BUILDS rather than letting them read their own (B4.9, D2076, D2077, G17): `git` is the git credential the daily image-check job mounts, and `build` is the build's own mounts — its `availableSecrets`, the build step's secrets and the build account's whole `secretAccessor` list (`modules/repo/build.tf`'s `google_secret_manager_secret_iam_member.build`), which empties because a request that named a secret would need the accessor the same class takes away, so the two leave together. `modules/repo/build.tf` mirrors the list in its `build_served_secret_classes` local, and the two clauses it feeds (`build_mounts_served` for the class `build` alone, `check_mount_served` for either) are what the module reads; only `deploy/terraform`'s `TestBuildServedClassesMatchTheModule` can hold the two spellings to each other. Go's half is `internal/infra`'s `buildMountsServed` (the tfvars' `build_secrets` empty, which is the address list the module's `for_each` agrees with) and `internal/backend/gcp`'s `BuildSpec.served()`, which drops `availableSecrets` and the build step's secret env from the request the same class drives. The flip's own accessor delete is admitted on the ordinary path (`internal/infra`'s `BuildAccessorAllowDelete`, given to `planRepo`'s guard), so one plain `fugaro update --repo` converges it. It does NOT reach a catalog entry's build: that build runs as the project's build identity, which the build-credentials route does not admit — that route serves one repository to the account bound to it (D2076) — so a catalog build keeps the `availableSecrets` its request mounts and the identity's own accessor (`modules/installation/build_identity.tf`) stays. The flip **ships** in 0.27.0: the owner gave the go on 2026-11-18 with the other three flips of the chain, moving Check 196's owner-run checks to after the flip (B4.10). Removing a class from this list is the owner's go read backwards. The order matters as it does for the other flips: a build of a switched repository is served by the service, so the installation's service must be deployed and the repository's root re-applied with the switch on, and a repository whose own root is never re-applied keeps every accessor and every mount (G9).
- `config.SharedJobServedClasses` holds `model`; **change it only with the owner's go**. It is the flip list that names the class of secret the service serves to a SHARED project job rather than letting the job read its own copy (B5.7, D505, D2078, G17): `model` is D145's first family — the Anthropic key, the Claude account token of the account the job's own name carries, and every provider key — and it is the WHOLE class here, with no per-`agent.auth` arm as the per-repository `ModelSecretsServed` has and no stage-account exception either, because a profile's repositories are served as a profile (B5.1, B5.2) and a shared job's stages all run on that one job's credential. The drop is not the whole class: `config.IsSharedJobServedModelEnv` names the two Claude variables alone (`config.ModelSecretEnvs`), because nothing serves a provider's key yet — the runner reads one from its own environment and the gateway routes with the job's own key — so a shared job keeps every `FUGARO_PROVIDER_KEY_*` it mounts, and that drop is the keys-through-service plan's KS16, whose red step is exactly that state (R6, D1634). It fires only for a profile whose own switch is on — `projectJobServesTheCredentialsService`, the `credentials_service` object on that job in the tfvars, granted one release earlier by B5.2 — and BOTH halves are needed, which is why a profile the switch holds off keeps every mount and every accessor before and after (G9, D147). `modules/project/sa.tf` mirrors the list in its `shared_job_served_secret_classes` local and reads its own two clauses through `local.is_shared_job_served_model`: the account's `secretAccessor` set (`local.job_secret_names`, the `for_each` of `google_secret_manager_secret_iam_member.job`) and the container's mounts (`local.job_mounts`, `modules/project/job.tf`) — the same local on both sides, because a mount the job's account keeps no accessor on is a job Cloud Run refuses to create (C2.3). Only `deploy/terraform`'s `TestSharedJobServedClassesMatchTheModule` can hold the two spellings to each other, and it also holds `model_secret_env_names` to `config.ModelSecretEnvs` and refuses a provider-key clause in this module. Go's half is `internal/infra`'s `projectJobMounts` and `projectAccountMount` (both read `config.IsSharedJobServedModelEnv` behind the switch), whose answer is the tfvars' `secret_env` and the job's own `FUGARO_SECRET_ENVS` redaction list — and `RefreshProjectJobCredentialsService`, which re-derives the mounts with the switch, because the switch can move inside a run and a job that kept an On record's drop after the record moved to Off would carry neither the credential nor an address to fetch one from (G17, D143). The GitHub App's key is deliberately NOT this list's: its drop is `config.ServiceHeldSecretNames`' own flip (#907, C2.3, G22), and `TestFilledSharedJobListKeepsTheAppKey` pins that filling this list moves no accessor and no mount of it. The flip **ships** in 0.27.0: the owner gave the go on 2026-11-18 with the other three flips of the chain, waiving B5.6's PASS and moving Check 197's owner-run checks to after the flip (B5.8). Removing the class from this list is the owner's go read backwards. The order matters as it does for the other flips: the profile's repositories are admitted to the service (B5.1) and its job's account may invoke it (B5.2), which is the release the address landed in, so no mount is lost before the service serves that credential to the image the job runs.
- The service account's only project-level grant is the custom database role `fugaroCredentialsDatabase`, with exactly `firebasedatabase.instances.get` and `.update`. It also holds one grant that is not project-level, taken knowingly by the owner (F7, F8 of `docs/launcher-does-not-mint/reconciliation.md`; D3121): `iam.serviceAccounts.signJwt`, through the `fugaroTokenMinter` role, on the runs' signer account — `deploy/terraform/gcp/modules/firebase/iam.tf`'s `google_service_account_iam_member.issuer_minter`, bound on the ACCOUNT and never on the project, planned only once `fugaro update` hands the account over (`var.issuer_account`, empty until then). What that row costs is stated and not softened: the service becomes the one identity that mints every run's and every launcher's token, and `iam.serviceAccounts.signJwt` signs any claim set for any uid as the account it is on, so the account that holds every model key is the account that signs every run's identity — the honest size of the amendment, taken knowingly by the owner (D3121). Never use a predefined role and never add the instance lifecycle permissions. The cover tables no longer refuse a grant they do not carry (D1545, `docs/no-prompt-policy/`): they warn, the plan applies and the finding goes into the step's audit record, so this rule and the review that checks it (`.claude/rules/terraform.md`) are the control.
- `website/content/security.md` is `SECURITY.md` byte for byte, below a generated header. Edit only `SECURITY.md`, then regenerate the page with `go run ./internal/clidoc` in the same PR. `internal/cli/docs_website_security_test.go` fails on any drift, and `website/test/security.mjs` holds the page's shape.
- Every reader of run dollars splits money from notional on `model_notional_usd`, never on `ModelBasis` (P12, D140). `internal/runstore/cost_readers_guard_test.go` enforces this.
- The owner runs every step in `docs/credentials-service/runbook.md`. If a task needs one, say which step is theirs and stop.
