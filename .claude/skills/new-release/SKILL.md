# /new-release X.Y.Z

Procedure for one Fugaro release. Detail lives in `docs/release.md` (read it first, whole); this file is the order of work and the stop rules.

## Rules

- Run only when the user asked for a release of a specific version, or you proposed one and they confirmed it. The tag push is outward-facing and permanent.
- Allowed before the user confirms the version: reading, preflight checks, proposing a version, drafting the Highlights text in the chat or in a local branch. Needs the user's go-ahead: merging the Highlights PR to main and running `scripts/release.sh` (step 4). Without it, stop before step 4. Step 7's two website dispatches are yours to run, under the owner's standing authorization (step 7): verify the preview before the promotion.
- Never move, delete or re-create a tag; never force-push; never bypass the release gate. Rolling back a published release is the USER's decision and the user runs it ([docs/release.md#rolling-back](../../../docs/release.md#rolling-back), which deletes the tag); you never run it. Your remedy for a bad release is to supersede it with the next patch release.
- `.claude/` may be locally excluded in a clone (`.git/info/exclude`), so a new file under `.claude/skills` needs `git add -f`.
- No secrets in the Highlights, PR text or your report. Read every check and every script output; do not assume green.
- When any step fails: stop, report the failing command and its output, and wait. Do not improvise a workaround.

## 1. Preflight

- `git switch main && git fetch --prune --tags`; `git status --porcelain` must be empty and `main` must equal `origin/main`. Untracked files count and make `scripts/release.sh` refuse (an untracked `.claude/` did once): list them in `.git/info/exclude`, never commit someone else's files.
- Main's checks (`test`, `terraform` and `rules`) green: `gh run list --branch main --limit 5`. The script waits for running ones. The CLI and mobile gate is those three only; the console checks are not part of it (the console releases on its own stream), and only a console release's gate adds them, via `GATE_REQUIRE_CONSOLE=1`.
- The version is the next semver after `git tag --list 'v*' --sort=-v:refname | head -1`. New features mean a minor bump (0.y.0), fixes only a patch; ask the user if unclear. Strict `X.Y.Z`, no `v`.
- `gcpProjectFieldSince` in `internal/cli/init_fugaroyaml.go` must equal the first release containing the `gcp_project:` field (today `"0.4.0"`). If this release is that one, or the value is wrong, fix it in a PR and merge it BEFORE continuing.
- **The owner's critical rule (2026-10-30): `fugaro update` is the whole upgrade.** Before tagging, check that an installation at the previous release reaches this one with `fugaro update` alone (migrations, rules, images and the plugin pin are done by it); if the release needs another command, a deletion or a hand repair, stop and report: the release does not ship until `update` does it, and `### For operators` must read "run `fugaro update`" plus what it will ask.
- Other checklist items of `docs/release.md` ("Before you tag"): the plugin tests on a bumped tree (next bullet), the price catalog regeneration with its `testdata/openrouter` snapshots refreshed in the same commit, `internal/pricing` `checkedAt`, tag protection and immutable releases (owner setting, only mention if unset).
- **The sandbox project must be named, and the pre-tag rehearsal is the OWNER's step — ask for it early.** `FUGARO_LIVE_GCP_PROJECT` names the sandbox GCP project the owner-run checks build in (`docs/gcp-live-checklist.md`, Preconditions; `scripts/release.sh` refuses without it in its preconditions, and refuses every name that is the owner's own installation — `belong`, `edge-devel-dimi`, `edgeappinc`, the rule `scripts/belong.sh` holds; the CLI does not refuse those names itself). Step 4 then builds this repository's own `go` catalog entry for real in it, which is one billable Cloud Build. `scripts/release.sh` no longer refuses a coding agent's session (the owner's order of 2026-11-21, "Remove the guard": "I didn't say you can't cut a release"), and the rehearsal refuses none either: `scripts/release-rehearsal.sh` builds in the sandbox project only and tags nothing, so you may run it by hand (the owner's ruling of 2026-11-19). A release cannot be cut until that build has run and passed, unless the owner says to skip it for that release, in their own words, and then `scripts/release.sh X.Y.Z --skip-rehearsal` is the command, and the rehearsal stays owed.
- **Run the plugin tests on a tree with the bump applied.** The bump rewrites two version stamps per skill file, so a version whose component gains a digit can push one over its byte budget by itself: 0.9.5 → 0.10.0 added two bytes and failed `TestPluginSkillsLintClean` on the bump commit, and 0.10.0's tag ended on the follow-up that shortened the file (#929). In a scratch worktree — `git worktree add /tmp/fugaro-bump HEAD`, then `scripts/bump-plugin-version.sh X.Y.Z && GOFLAGS=-p=2 go test ./plugin/ -count=1` in it, then `git worktree remove --force /tmp/fugaro-bump`. `--dry-run` (step 3) runs it too; this manual run is what catches it before the Highlights PR merges.

## 2. Highlights (required from 0.4.0)

- Collect the changes: `git log vPREV..main --oneline` and `gh pr list --state merged --search "merged:>=<date of vPREV>" --limit 100`. Read the PRs, not just titles.
- Write `docs/releases/vX.Y.Z.md` per `docs/releases/README.md`: 3 to 6 user-facing bullets, one sentence each, no commit-title echo, nothing internal-only (CI, tests, refactors). Add `### For operators` with ordered steps when a rollout order matters (shared config: upgrade CLIs and CI pins, rebuild images, then merge `gcp_project:`; `fugaro update --publish-config` is run by the user in their own terminal). Add `### Known limits` with what this release does not do, does not stop or leaves to a later one: a release ships with its known limits in its notes, so the section is written unless the release genuinely has none. Both sections are `###` and either may stand without the other; the website's changelog page renders them.
- Write the release's end-user summary, the `  vX.Y.Z: one sentence` line in `website/data/release-summaries.yaml`, **in this same PR** (`docs/releases/README.md`, "The end-user summary"). The website's changelog page prints it above the entry's Highlights of the three newest releases, and the site's build stops, naming the file, when a *released* file has no entry — for every released file, not only the three the page shows (a file ahead of the CLI stream's `current` version is the next release's notes, and the build asks it for no line yet) — so `scripts/release.sh` refuses to start without it. It is what the release gives a user, not what changed inside.
- Move the compatibility matrix's "as of" stamp in the same PR: `website/data/compatibility.yaml`'s `as_of.cli` to `X.Y.Z`, beside the notes file and the summary line. `website/test/compatibility.mjs` refuses a stamp behind the newest `docs/releases/vX.Y.Z.md`, and the site's compatibility page renders that file, so a release that wrote the notes and left the stamp alone publishes a page naming the release before this one (`docs/release.md`, "Before you tag"). The console's own notes commit moves `as_of.console` the same way, in its own release.
- Refresh the feature matrix in that same PR: `npm run features -- --as-of vX.Y.Z` in `website/`, then commit the root `FEATURES.md` it writes, beside the notes file, the summary line and the stamp. `scripts/release.sh` refuses, in its preconditions, an `origin/main` whose `FEATURES.md` does not carry the line `as_of: vX.Y.Z`, or one whose file has no commit since the previous release tag — the stamp alone does not prove a refresh, because the notes are written ahead of the release (D2447, D2449; `docs/feature-matrix/implementation-plan.md` task T5) — so the notes, the summary line, the compatibility stamp and this one go in together. The generator refuses to write while any name in `docs/status.md` is unmapped, and lists the names it could not place: map them in `docs/feature-matrix/mapping.yaml` in that PR (an excluded name needs its reason there), then re-run it. The matrix is not refreshed on a hotfix path (`docs/release.md`, "Hotfix releases").
- Branch, commit, push, open a PR; after the user's go-ahead, merge it (squash) once its checks pass; then `git switch main && git pull --ff-only`.

## 3. Dry run

`scripts/release.sh X.Y.Z --dry-run`: it must pass every precondition (including "docs/releases/vX.Y.Z.md exists and is not empty on main" and "website/data/release-summaries.yaml has a non-empty entry for vX.Y.Z"; both are its own messages, naming the file). It needs `FUGARO_LIVE_GCP_PROJECT` exported like the real run — it checks every precondition, and the sandbox project is one of them — but it builds nothing: the plan's line for the rehearsal is a line only, and no Cloud Build is submitted. It also applies the bump to a scratch worktree and runs `go test ./plugin/` there, then removes that worktree however it ends; it needs `go` on `PATH` and refuses without it (the check cannot run, so the plan would vouch for nothing). Read the plan line it prints: it says what the check did, and says so when the check did not run. Fix what it reports: when the plugin tests fail, a skill file is over its byte budget (`plugin/skills_lint_test.go`'s `maxSkillBytes`), so shorten it in a PR to `main` and re-run.

## 4. Release (needs the user's go-ahead)

`scripts/release.sh X.Y.Z` (no prompt). It waits for checks, opens the bump PR with auto-merge, waits for the merge and for the gate on the merge commit, then tags and pushes. Run it in the background and watch its output; a timeout or failure is reported, not retried blindly (the script is safe to re-run, per `docs/release.md`, but read why it stopped first). One of its stops has a written recovery there, a re-run of the same command once you have done a step by hand:

- Auto-merge refused (`Pull request is in clean status`, or auto-merge off): merge the bump PR yourself, then **re-run the same command**. It picks the merged PR up at step 4 and carries on; this is the one stop the command fixes, and it fixes it only because you merged what it could not.

**Lessons earlier releases paid for, each cheap to avoid:**

- **The tag waits on the pre-tag rehearsal, and that build is the owner's to run.** Once the release gate passes, `scripts/release.sh` runs `scripts/release-rehearsal.sh run <merge commit>` and then `check <merge commit>`: `run` builds this repository's own `go` catalog entry for real — the CLI's own catalog build, so the clone at the commit, the build, the leak scan, the smoke and the promotion all run — with a CLI built from the commit, in the sandbox project only, and writes a record (commit, Cloud Build id, verdict, the build's log). `check` is what the tag is cut on: a missing, red, or other-commit record refuses it and names the Cloud Build link, and the record is a local convention rather than proof (nothing reads the build id back from Cloud Build, so it is as trustworthy as the machine it sits on). It is one billable build per release, and the release runs in your session as in the owner's terminal (the owner's order of 2026-11-21 removed the refusal of an agent's session); you may also run `scripts/release-rehearsal.sh` by hand (the owner's ruling of 2026-11-19 — it builds in the sandbox project only and tags nothing). A red build is a stop too, and the log is the finding: 0.26.0's were a stale pinned branch, the leak scan's false positives on a real image and a layer-count refusal, none of which a hermetic test sees, and all three were found after the tag — by the owner's `fugaro update`, which is exactly what this step exists to prevent.

- **`main` need not be frozen.** The gate runs on the release merge commit and the tag goes on that commit, so merges that land meanwhile are not in the release. The gate wants `test`, `terraform` and `rules` green on it; the Go test job alone runs about twelve minutes.
- **The two doc lines that name the released CLI are the script's to rewrite.** `docs/project-named-oauth-tokens/spec.md`'s status line and `docs/project-claude-accounts.md`'s line 3 are pinned to `plugin/.claude-plugin/plugin.json`'s version (`TestDocsProjectNamedOAuthTokensStatusNamesTheReleasedCLI`, `TestDocsProjectClaudeAccountsOperatorGuide`), so they change in the bump commit and nowhere else. `scripts/release.sh` rewrites both in its release commit (the dry run's plan says "rewrite the two doc lines that name the released version"), and its preconditions refuse when either line no longer reads as the rewrite expects: then fix that line's wording on `main` in a PR and re-run. Make no release branch by hand for them.
- **A CI guard that reads `docs/release-streams.yaml`'s `current` runs on the bump's merge commit.** The bump moves the CLI stream's `current` to the new version in that commit, so the gate is the first run that shows a guard the new version. A console or CLI guard must therefore never hold more than mode ok: 0.14.0's console guard demanded skew "supported", failed the gate on the merge commit, and the release was recovered by tagging the fix commit (#1395) by hand, the second stop above.
- **The CLI's `vX.Y.Z` tag no longer starts a console release.** Since the console's own stream and the copy-in of 2026-10-23, the console releases from `console-vX.Y.Z` with its own version line, its own notes and its own workflow, and a `vX.Y.Z` push starts the CLI's two workflows and no console work. So a CLI release neither builds nor needs the console's notes, and the console's are not part of this procedure.

Then `git ls-remote https://github.com/dimipaun/fugaro 'refs/tags/vX.Y.Z^{}' 'refs/tags/vX.Y.Z'` must print the released commit.

**A hotfix — a patch of a line that has shipped — is the same command with `--hotfix`**: `scripts/release.sh X.Y.Z --hotfix --fix <sha>` cuts `release/X.Y` from the line's last tag, cherry-picks the fix and the plugin bump `main` already carries with `-x`, and refuses until the branch carries `docs/releases/vX.Y.Z.md`, its line in `website/data/release-summaries.yaml` and the CLI stream's `current`. It writes none of that text (it names what is missing and stops), it never moves your checkout — the branch is built in a scratch worktree — and it runs `gh workflow run ci --ref release/X.Y` itself, so there is no dispatch of yours. Two things have to be true before it runs: every `--fix` commit is on `main`, and `main`'s `plugin/.claude-plugin/plugin.json` already says `X.Y.Z` or newer, which means the bump PR merged to `main` first. The owner's ruleset step (restricting `release/[0-9]*` to the owner) is the owner's, not yours.

**A release cut at a given commit of `main` — `--at` — is the same command with the commit named**: `scripts/release.sh X.Y.Z --at <sha>` tags `<sha>` instead of the tip of `main`, the way a console release tags an exact commit. Use it when the tip is red with something that has nothing to do with the release and the last green commit already carries the bump: the tip refuses the release gate, and everything merged after that commit would otherwise ride along. That bump is the one step 2 above writes, and `--at` writes none of it — the plugin version and every skill header, `docs/releases/vX.Y.Z.md`, its line in `website/data/release-summaries.yaml`, the CLI stream's `current`, the two doc lines, `FEATURES.md`'s stamp with a commit to it since the previous tag, and `website/data/compatibility.yaml`'s `as_of.cli` — so it lands on `main` through an ordinary PR first (steps 1 to 3 above, done ahead of the release) and the sha of that merged commit is what you pass. There is no branch, pull request or dispatch of the run's own: the commit is tagged where it is, the rehearsal runs in a scratch worktree at it, and `scripts/verify-release.sh vX.Y.Z` verifies the release as usual. It relaxes no precondition — the release is still cut from a clean `main` equal to `origin/main`, and the checkout is never moved — and the commit must be an ancestor of `origin/main` and must already be green — the gate reads `test`, `terraform` and `rules` from that commit's own checks by sha, and a commit whose every `ci` run is a selected one is refused with the `gh workflow run ci --ref <a ref pointing at it> -f full=true` that puts a full run on it. `--at` refuses `--hotfix`.

## 5. Verify

Watch every workflow the tag starts: `gh run list --limit 6` and `gh run watch <id>` for `release`, `images` and `console-windows` (the console's Windows pack, which runs at release time only). The release is not done until every workflow on the tag is green, and `scripts/release.sh` ends by running `scripts/verify-release.sh vX.Y.Z` for exactly that: every run the tag push started has to conclude successfully, and the images the release published have to be pullable without a login. So the run's own output already carries that answer; when a workflow was red and its job has been re-run, `scripts/verify-release.sh vX.Y.Z` is the one command that reads it again. Then check, with commands, not by assumption:

- `gh release view vX.Y.Z --json isDraft,isPrerelease,assets,body`: not a draft; `isPrerelease` is false for 0.4.0 and later; assets are 4 archives (darwin/linux, amd64/arm64), an SBOM per archive, `checksums.txt` and `checksums.txt.sigstore.json`.
- The body: install header, then `## Highlights` (your file), then `## Changelog` (no SHAs), then the base-images footer.
- The "Verifying a release" commands of `docs/release.md`: the exact `cosign verify-blob` of `checksums.txt` and the archive checksum for this machine.
- Homebrew tap: `gh api repos/dimipaun/homebrew-tap/commits --jq '.[0].commit.message'` is "Brew cask update for fugaro version vX.Y.Z".
- `images` workflow succeeded, including `verify-public`; note each image digest from its summary.
- Ask the user to run `brew upgrade dimipaun/tap/fugaro && fugaro version` (prints `X.Y.Z`).

## 6. Post-release

- From a fresh build of the tag in a separate worktree (`git worktree add /tmp/fugaro-wt-vX.Y.Z vX.Y.Z`, build with `go build -o /tmp/fugaro-vX.Y.Z ./cmd/fugaro` from there, a path outside the worktree), so the main checkout stays on main (`go install github.com/dimipaun/fugaro/cmd/fugaro@vX.Y.Z` also works but reports `dev`). Run `/tmp/fugaro-vX.Y.Z doctor` against the dogfood project (`dimipaun/fugaro`), report each line, then `git worktree remove /tmp/fugaro-wt-vX.Y.Z`.
- If the release changes the operator order, update the rollout section of `docs/release.md` and the memory notes in the same PR or a follow-up.
- Tell the user what only they can do: `brew upgrade dimipaun/tap/fugaro && fugaro update` in each checkout, in their own terminal (it installs the plugin in Claude Code at user scope, deploys the rules generation and the policy node, and refreshes the job images; it asks nothing, each billable build leasing its cost against the project's budget caps instead). It writes no plugin pin — nothing in the tree does any more — so a checkout an earlier release wired is offered its removal as a diff, and the user commits it or does not. Its cloud step, `fugaro image refresh`, stops on a local config `base_images.<kind>` that is a dev or hand-pushed image until that entry is removed. Also `fugaro update --publish-config` in their own terminal, upgrading CI pins and teammates' CLIs before any repository merges `gcp_project:`, then `fugaro update --anchor` in each checkout to write that line (it refuses while an image was submitted by an older or dev CLI, was built FROM an older or dev base per its record's `base_ref`, or a configured base image is dev or older; plain `fugaro setup` also writes it, after the full converge), the owner-only repository settings still unset.

## 7. The website (the last step, and it is part of the release)

The site names the latest release, so the release is not done until the site shows it (the owner's standing rule of 2026-10-30, `docs/release.md`, "After each release, the website"). **Since 2026-11-07 the `website-live` environment requires no reviewer**, so nothing here waits on a GitHub approval: what holds the promotion to a reviewed commit is that environment's `main`-only deployment branch policy and the Workload Identity Federation provider's condition (`docs/release.md`, "What fences a release now"). **You run the two dispatches yourself.** The owner's standing authorization of 2026-10-18 reads "you are henceforth approved to run the website-preview and website-promote workflows", and since 2026-11-07 no reviewer click stands between them, so there is nothing to hand over. It covers those two workflows only: never approve an environment review by any route (should a reviewer be configured again, the owner clicks it), and never deploy by `scripts/deploy-website.sh` without its dry run and the owner's authorization for it. You do the website work, dispatch both, and verify both results.

- Do the website work: update downloads, checksums, versions and links, wherever the site names the latest release — **the changelog page excepted, which needs no edit**: it is built at build time from `docs/releases/vX.Y.Z.md` and `website/data/release-summaries.yaml`, renders the three newest CLI releases and links the rest to GitHub, so the notes and the summary line you wrote are all it shows for this release — and run the website's tests (`npm run check` in `website/`, and `go test ./internal/cli -run Docs`). Merge that to `main` before anything is dispatched: both workflows build a ref you name, and the promotion copies a preview channel's bytes.
- Dispatch the preview and wait for the run: `gh workflow run website-preview.yml --ref main -f ref=main -f channel=<name>`, then `gh run watch <id> --exit-status`. Only `main` can deploy, by design — the Workload Identity Federation provider both workflows authenticate through requires `assertion.ref == 'refs/heads/main'` **and** `assertion.event_name == 'workflow_dispatch'` — and the channel name follows the same pattern `scripts/deploy-website.sh --channel` validates.
- Verify the preview before anything is promoted, with commands rather than by assumption: read the run (`gh run view <id>`) for the URL it printed, fetch it, and check that the new version, the download links, the checksums and the changelog entry for this release are the ones you just wrote, and compare the home page's sha256 with the tree's own build when a build exists. A preview nobody read is the whole risk the two-workflow split was for, and the click that used to sit between the two is gone.
- Only then dispatch the promotion, and only for a channel whose preview was verified (by you or the owner): `gh workflow run website-promote.yml --ref main -f channel=<name>`, then `gh run watch <id> --exit-status`. Its job carries `if: github.actor == 'dimipaun'`; your `gh` runs under the owner's own account, so that holds. If the run is skipped by that condition, say so and give the owner the command. It copies that preview channel's version onto the live channel; there is no local equivalent, because the promotion has to be the one the workflow records. Read the run, then verify the live site serves what you verified on the preview.
- Final report: version, release URL, commit, **both website URLs** (the preview channel and the live site, and which release each shows), what was verified with the command, what was not, and the user's to-do list.

**If a dispatch cannot run or its verification fails, say so and stop.** The release is finished and this step is owed: the site names the previous release until both dispatches have run, and the two commands above are the whole of what is left. Hand the owner the exact command, and never route around it by another way of deploying.
