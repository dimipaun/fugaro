## 2. Findings

### A. CLI output

**F1. Exists (partly). The default `update` output is the converge loop's stage list, not a raw dump, and `doctor` already had its one-screen ruling applied.** The spec's "in the past `fugaro doctor`" is already done: `internal/cli/doctor_render.go` (`doctorDefaultMaxLines = 25`, the class table) is the owner's 2026-10-30 ruling and its default view holds verdict plus actionable items only. What is still noisy is what runs under a stage: Terraform's own progress is streamed through `infra/tf.(*TF).run` into `TF.Out` (stdout and stderr both), and `internal/cli/init.go` has about 59 direct prints. *Consequence:* part A is not a rewrite of `update`; it is putting a reporter between the stage loop and the Terraform stream, and teaching the other families the same shape. The doctor ruling stands as written; the reporter must not make `doctor` print more.

**F2. Gap. There is no shared reporter, and the seam it needs exists in three places.** `initflow.Options.Out` (`internal/initflow/loop.go`: the plan view is `view`, the closing account is `finish`; states are the `stateLabel` map: done, changed, will do, blocked, needs you, skipped, failed, billing pending, waiting for billing), `tf.TF.Out` (`internal/infra/tf/tf.go`, `run`), and the `watch` renderer's options. Everything else prints straight to `cmd.OutOrStdout()` or `cmd.ErrOrStderr()`: roughly **1,065 print sites in 119 files** under `internal/cli` and `ee` (a `git grep` count, UNVERIFIED as an exact figure). *Consequence:* "move every command onto it" is a very large mechanical change, and `internal/cli` tests and `internal/cli/docs_*_test.go` pin many printed sentences. A big-bang move is a review problem and a test-churn problem; see D1354.

**F3. Exists. Terminal detection and `NO_COLOR` exist in pieces; a spinner does not.** `stdinIsTerminal` (`internal/cli/init.go`) and `writerIsTerminal` (`internal/cli/initsecrets.go`) are package variables tests replace; `watch.UseNoColor` (`internal/watch/tui.go`) is the only `NO_COLOR` reader; `golang.org/x/term` is a direct dependency. There is no spinner. `charmbracelet/colorprofile`, `termenv` and `go-isatty` are indirect dependencies through `bubbletea`. There is no handling of Windows virtual-terminal mode (`git grep` for `ENABLE_VIRTUAL_TERMINAL_PROCESSING` and `SetConsoleMode` finds nothing), so colour and a carriage-return spinner on the legacy Windows console are UNVERIFIED (see UNVERIFIED). *Consequence:* the reporter should move `UseNoColor` into the shared package rather than copy it, and `CLAUDE.md` ("add no new framework or dependency without asking") means the spinner is a small writer of our own unless the owner says otherwise (D1355).

**F4. Wrong. `-v` is not free.** `internal/cli/root.go` `NormalizeVersionArgs` rewrites a **leading** `-v` or `--version` to `--version`, so `fugaro -v` prints the version. A non-leading `-v` (`fugaro update -v`) reaches the subcommand and is currently an unknown shorthand on every subcommand (the only one-letter flag in `internal/cli` is `logs`'s `-f`); `recipes` defines a `--verbose` that means "also print each recipe's use_when and steps" (`internal/cli/recipes.go`). *Consequence:* a persistent `--verbose` / `-v` on the root works for every subcommand, but `fugaro -v update` would print the version and stop, so the documented form is `fugaro update -v`; `recipes --verbose` must keep meaning what it means or be renamed (a field never changes meaning: it is a flag, but the same rule of thumb applies). See D1353.

**F5. Wrong. `~/.fugaro` and `%LOCALAPPDATA%\fugaro\logs` partly contradict the repo's directory convention, and the Windows half already agrees with it.** `internal/localcfg/platformdirs.go` `UserDir(getenv, goos, kind)` is the one rule: config is `$XDG_CONFIG_HOME` else `~/.config` (`%APPDATA%` on Windows), state is `$XDG_STATE_HOME` else `~/.local/state` (`%LOCALAPPDATA%` on Windows), cache is `$XDG_CACHE_HOME` else `~/.cache` (`%LOCALAPPDATA%` on Windows); `localcfg.configDir` adds `/fugaro`; `internal/infra/workdir.go` builds `stateDir` and `cacheDir` from it for the Terraform workdirs; the planned orchestrator cache is `$XDG_CACHE_HOME/fugaro/orchestrator/<id>.json` through the same call. `~/.fugaro` appears nowhere in code (verified: `git grep '"\.fugaro"'` finds only the repository-level `.fugaro/recipes` and `.fugaro/instructions.md` conventions). macOS uses the XDG paths too, not `~/Library`. *Consequence:* logs belong under the **state** directory, `<UserDir state>/fugaro/logs`: `~/.local/state/fugaro/logs` on macOS and Linux and `%LOCALAPPDATA%\fugaro\logs` on Windows, which is **exactly the spec's Windows path**. Only the macOS and Linux half differs from the spec. `internal/cli/tempxdg.go` and `doctor` already warn when `XDG_*` points at a temp directory, which matters for retention (an agent's session often sets one). See D1351.

**F6. Gap. The CLI keeps no log of its own runs, and the retention rule has a trap.** `internal/logtail` keeps the last lines of a stream (used for error context) and `fugaro logs` reads a cloud run's logs; neither is a command-run log. The spec writes a log for **every run, whatever the mode** and keeps 14 days or 50 runs. But the console polls: `plan status` about once a minute while the Graph is open (`PLAN_STATUS_MIN_INTERVAL_MS`), `budget show`, `runs ls` and `coordinator status` per view, and each is a CLI process. A global "50 runs" would be exhausted by polls in under an hour and would delete the log of the `fugaro update` the user wants to read after a failure. *Consequence:* retention must be per command name, or only step-based and mutating commands write a log at all, and a `--json` read must write none (D1352). A log is also **a new place for secrets**: it must be mode 0600 in a 0700 directory, pass through the same redaction the terminal gets (`initflow` redacts the stage detail; `safetext` is the console-facing sanitiser), and writing it can never fail the command (the planned orchestrator cache has the same rule, `TestCacheWriteFailureNeverFailsATick`); an agent's sandbox may have a read-only home.

**F7. Rule. A failure's tail and the log path are mostly already the repo's contract, in a different shape.** The loop prints `stopped at <stage>; fix: <fix>` and the caller returns the error; `ExitError` carries a code (`internal/cli`, `ExitCode`); `tf.ExitError` keeps the last stderr bytes (`tailBuffer`). Exit codes are documented in `docs/design/v1.md`: 0 ok or only planned, 1 a refusal or a step left for the user, 2 a cloud error. *Consequence:* "Exit with a non-zero code" is already the rule, and **a step left for you exits 1**: the reporter must keep three outcomes (done, failed, left for you) and not collapse the last into a green tick. The failure block adds the log path; it must not replace `fix:` and `left for you`, which the plugin skills and the website quote.

**F8. Rule. `--json` is a contract the console, the plugin and mobile read.** `CLAUDE.md` "A field never changes meaning" and `console/docs/json-contract.md` govern it; `internal/cli/docs_desktop_console_test.go` and `docs_console_boundary_test.go` pin it. The spec's own sentence ("never affected by the human-friendly formatting") is therefore already a rule and costs a test, not a decision: every command with `--json` prints no spinner, colour or log line on stdout, and the reporter writes its human lines to **stderr** in `--json` mode (or nothing). A coding agent reads default output too: the agent marker (`agentMarker`, `internal/agentenv`) already changes what the CLI offers; the default short output plus the log path serves an agent better than a wall, but an agent with a read-only home cannot read the log, so the failed-step context must be on the screen, not only in the file.

### B. The console graph

**F9. Wrong. The console already goes through the CLI for every read, and has no RTDB client.** `console/src/main/spawn.ts` `SPAWN_COMMANDS` and `console/src/main/ipc.ts` `CONSOLE_OPERATIONS` list the exact argv (including `live.watch`, `plan.status`, `coordinator.status`); `.claude/rules/console.md` makes a new command or flag security-sensitive (independent review, pinning tests in `console/test/unit/`, the section 5.1 table in `docs/design/desktop-console.md`). A search of `console/src` for Firebase or RTDB hosts finds only sanitiser patterns, no client. *Consequence:* the "principle" of spec section 2 is the current design. The work is a **new read**, not a re-plumbing.

**F10. Exists. The repo requirement is real, and it is one read, `plan.status`.** `console/src/renderer/screens/nocheckout.ts` says it: the Graph is "the console's only read with a precondition", `plan.status` reads the plan out of the installation's checkout, an installation with none throws `NO_PLAN_CHECKOUT` before the CLI is asked, and the card offers a chooser of the CLI-validated checkouts (`console/src/renderer/checkout.ts`). The CLI side is `internal/cli/plan_status.go` `newPlanStatusCmd`, which walks the checkout's `docs/` for `*.graph.json` artifacts and joins them to runs. *Consequence:* "remove the repo requirement and any code that reads docs directly" would remove the Graph's current source, which is what draws releases, the critical path and plan tasks (F18). It must be a new scope beside it, not a deletion (D1356).

**F11. Exists. A long-lived `--json` child, its limits and its shutdown.** `console/src/source/cli.ts` `subscribeLive` is idempotent per argv, bounded by `MAX_LIVE_FEEDS = 4` (it stops the oldest), restarts a feed that ended, and `close()` stops every child; `spawn.ts` holds `SHUTDOWN_GRACE_MS` (SIGTERM, then SIGKILL) and `READ_TIMEOUT_MS = 90000` for one-shot reads, which a stream does not use. The WSL route and `CHILD_ENV_KEYS` (11 keys, five `XDG_*`) apply. The `watch --json` guarantees a consumer can rely on are written in `console/docs/json-contract.md` section 10 (a slow reader blocks the child and never drops a document; a closed stdout ends the child on its next write and by signal). *Consequence:* `fugaro graph --watch` is a second feed class under the same ceiling: with `MAX_LIVE_FEEDS = 4`, a Graph stream competes with the Live tab's `watch` child. Zombie control exists for the Electron main process; a hard-killed console (SIGKILL, crash) leaves a CLI child that exits on its next stdout write (section 10.4), which for a quiet graph could be minutes. The stream therefore needs a periodic keep-alive line (see F20).

**F12. Exists. The CLI subscribes to RTDB with SSE already, and resumes by a full snapshot.** `internal/rtdb/stream.go` `Client.Stream` delivers `put`, `patch`, `keep-alive`, `cancel` and `auth_revoked`, restarts on its own, and on each connect starts with a `put` of `/` carrying the whole current value; `fugaro watch` opens four streams (`internal/cli/watch.go`). The console reads RTDB only by the person's own credential through the CLI (`roles/firebasedatabase.viewer`). *Consequence:* the spec's "reconnect with a fresh snapshot" is the transport's own behaviour. **Cost and quota:** each stream is a held connection against the Realtime Database's concurrent-connection limit (UNVERIFIED figure; the free tier is small); `watch` already holds four, so a graph stream must share the subtree it needs rather than add a fifth per window, and should run only while the Graph tab is visible.

**F13. Gap. There are no local orchestrators in the code.** `git grep -i orchestrator` over `internal`, `ee` and `cmd` finds comments only; no `internal/orchestrator`, no `fugaro orchestrator` command, no daemon, no registry, no listener for one (the only listeners in the tree are the runner's loopback gateway `internal/gateway/gateway.go` and the coordinator and credentials services' Cloud Run servers). What exists is a **plan**: `docs/stateless-orchestrator/` (plan only; nothing implemented; no task approved), whose tasks O0-O19 build a local single-user daemon (`fugaro orchestrator install|run|state|patch|uninstall`, a launchd or systemd user unit, macOS and Linux only, Windows out of v1 by D1232). *Consequence:* spec section 2's "none, one or several local orchestrators running on the laptop" has nothing to discover until that plan is built. Anything in part B that needs a local orchestrator is blocked on it.

**F14. Rule. The stateless-orchestrator design already answers where an orchestrator's state, single-instance fence and offline snapshot live, and the spec's registry-plus-endpoint duplicates all three.** From `docs/stateless-orchestrator/reconciliation.md` (D1220, D1232, D1241, D1243): state is one **RTDB** node per orchestrator under a new top-level `orchestrator/` subtree, written with `PutIfMatch` by the person's own credential; one instance by an RTDB heartbeat **lease** (the mailbox lease pattern, `internal/mailbox/lease.go`); the daemon writes a local **cache** each tick at `$XDG_CACHE_HOME/fugaro/orchestrator/<id>.json`, atomic (temp file then rename) and mode 0600, with a freshness stamp; and the state document **already carries the graph**: `tasks[]` with `id`, `title`, `status` (queued, running, review, done, failed, blocked), `repo`, `depends_on`, `last_update` (`docs/stateless-orchestrator/spec.md`, "State schema"). *Consequence, the design's central tension:* the spec's per-orchestrator registry file with PID, port and token, and a localhost SSE endpoint, are a **second** local data path for data that RTDB already carries and the cache file already stores offline. "Local orchestrators still work when offline" is served by the cache file. The one thing the endpoint adds is freshness without an RTDB round trip, and the lease gives one instance per project anyway, so "several local orchestrators" means several **projects** (D1358).

**F15. Gap. Central orchestrators are a spec, a branch and an amended store.** `docs/central-orchestrator/` (spec 2026-10-20) says an orchestrator is a role, "every orchestrator, local or central, reports to the coordinator in the same way"; its plan P0-P9 is on the `origin/central-orchestrator` branch, not on `main`. `docs/stateless-orchestrator/` (2026-11-04) amends its store and auto-compact text. *Consequence:* "central orchestrators known to the coordinator" has no data to list today.

**F16. Wrong. The coordinator is not a resident service that orchestrators report to; it is a scheduled aggregation over repositories.** `ee/coordinator/` is under the Subscription licence. `fugaro coordinator` is registered through `internal/cli/extend.go` `RegisterCommand` and `paidCommandNames`, so it exists only in a build with the `ee` tag (`ee/register/coordinator.go`). Its sweep (`ee/coordinator/sweep.go`, `newCoordinatorSweepCmd`, hidden) is a Cloud Run job a Scheduler job triggers **every 15 minutes** (`internal/cli/init.go` `--coordinator` help text); its writer is the coordinator's service account, and clients may read `coordinator/` but write nothing (`internal/budget/rules/coordinator_test.go`). `ee/coordinator/service.go` `Service` is a Cloud Run front door for the MCP work and mounts nothing orchestrator-shaped. `fugaro coordinator report` (`ee/coordinator/intent.go`, `Intent`) is how a caller declares branch, files and services; the record carries `DeclaredBy` as an unverified string and no orchestrator identity. *Consequence:* "every orchestrator reports to the coordinator" is not built, and what the coordinator would show is up to 15 minutes old (the `All` scope is the stalest in the dropdown, not the "overall source of truth").

**F17. Wrong. The coordinator's view has no tasks and no edges.** `ee/coordinator/state.go` `RepoView` and `StoredProjectView`, `ee/coordinator/view.go` (`PullRequest`, `Run`, `Record`, `Collision`, `View`) are per-repository pull-request and run records with release and collision data, read by the console as `coordinator.status` (`coordinator status --from-store --all --json`, contract section 6.13). A task-level graph with `depends_on` is in the orchestrator state schema (F14), not in the coordinator view, and the owner's 2026-10-22 ruling GD1 (`docs/console-dependency-graph/reconciliation.md` section 3, not the recommendation) said the graph's source should be the coordinator's project record. *Consequence:* the spec's "All, from the coordinator" gives a PR-and-run-level node set per repository with release grouping, and **task-level edges only when orchestrator state is ingested**: either the sweep ingests `orchestrator/` or the CLI reads it directly (D1357). The decision on who is allowed to read it is the same RTDB `viewer` role every launcher and operator has today; an orchestrator node under `orchestrator/` needs its own rules read grant (the stateless plan's O-task for the rules), and a hostile local process that reads the person's ADC could read it all anyway.

**F18. Exists. The console already draws a dependency graph, with releases, streams and a critical path, and an owner ruling says where it should get its data.** `console/src/renderer/screens/graph.ts` (SVG, an elkjs layout worker, motion with reduced-motion fallback), `renderer/graph/model.ts`, `layout.ts` and `layout-client.ts`; plans in `docs/console-dependency-graph/` (GV tasks; GD1-GD8 answered 2026-10-22); the redesign steps 6a and 6b (#1456, #1517) merged. Its model is plan tasks keyed `plan id + task id`, state from the run joined by the optional plan task in `launch.json`, and `docs/release-streams.yaml` for stream names. The spec's "one combined graph, nodes and edges, tagged by source, keyed by a stable task id, duplicates removed" is **a new node source feeding this model**, not a new screen. *Consequence:* the dropdown's scopes are additions to one existing screen; the spec's merge rule (stable task id, dedupe across sources) needs a definition of "stable task id" that does not exist across sources: a plan task id (`docs/**/*.graph.json`), an orchestrator task id (`t-042`, per orchestrator) and a pull request (per repository) are three namespaces (D1356).

**F19. Rule. `watch --json` is the template, and it is not NDJSON events.** `internal/watch/json.go` (`JSONDoc`) prints one complete document per change, at most one a second, with a first document within `watchFirstFrame` plus a tick, and `console/docs/json-contract.md` section 10 lists the guarantees. The spec's event stream (task added, status changed, edge added, orchestrator up or down), with sequence numbers and gap detection, is new vocabulary and a new consumer: gap handling, delta ordering, and a definition of "snapshot on reconnect" that races with events in flight. *Consequence:* a version-1 stream of **whole snapshots with a monotonically increasing `seq`** reuses the console's existing "latest document wins" reader and removes the gap problem (a lost document is repaired by the next one); event deltas can be added later as a new field (a field never changes meaning). D1360.

**F20. Gap. A snapshot stream needs a heartbeat and a sequence rule the spec does not give.** (1) A graph that does not change prints nothing, so a hard-killed console's orphaned child lives until its next write (F11): print a keep-alive document or line on a timer (for example every 30 seconds) so stdout closure is detected. (2) The sequence number is per child process and resets to 1 on every start; the console must compare `seq` only inside one child's life, and treat a new `stream_id` as a new snapshot. (3) A source going down is not an exit: `watch` already models a withdrawn stream as a state, not a termination (contract section 10.6); the graph's `source_state` per scope must do the same. (4) A reconnect inside the CLI sends a full snapshot **and** increments `seq`.

**F21. Gap. The scope argument is a renderer-supplied string.** The dropdown values (`local:<id>`, `orchestrator:<id>`) reach argv. `.claude/rules/console.md` requires exact argv rows; an arbitrary `<id>` is an injection surface into a CLI flag (a leading `-`, a path). The CLI must validate every id against a closed pattern and refuse the rest, and the console's argument kind must be a closed value set learned from `fugaro orchestrator ls --json`, never a free value (the `repo` argument of `live.watch` is the pattern to follow, and how it is validated needs reading by the plan's author). The names come from a person-controlled registry and RTDB documents: treat them as untrusted text and pass them through `src/shared/sanitize.ts` `TEXT_CLASSES` before the renderer.

**F22. Rule. The Graph is a view that "shows" cost-adjacent state.** `hidesView` (`src/shared/version.ts`, `REDUCED_VIEWS`) is the console's skew rule: a view that does not know a CLI shape withholds its figures. A new `fugaro graph` command a released console does not yet know simply does not exist (a refused read), and an older CLI has no `graph` at all. The repo's skew rule (adding a field is fine, removing or retyping bumps the format's version) governs the new document; the owner's memory ruling (assume no console users) means no compatibility work beyond a clear refusal sentence. The per-screen rule from the owner (2026-10-31, `.claude/rules/console.md`) applies: each scope's data paints when it arrives, independent reads in parallel, the sequence token covers each section, `runs ls` is never part of the first paint.

**F23. Gap (security: the local endpoint, the hard part of the spec).** If the spec's local orchestrator endpoint is built, these are the questions it leaves, with a proposed answer for each (D1359):

| Question | Spec | What the repo already does or implies |
| --- | --- | --- |
| Who can connect | Localhost, token in a 0600 registry file | The runner's loopback gateway binds `127.0.0.1:0` and mints a 32-byte `crypto/rand` token per start (`internal/gateway/gateway.go`). A **localhost bind is reachable by every process of every user on the machine** (and by a browser page through DNS rebinding or a form post): a bearer token in a 0600 file bounds this to the user, but the endpoint must also require the token on every request including SSE, refuse any `Host` that is not the literal loopback address and port, send no CORS headers, and use a constant-time compare |
| What a hostile local process of the same user can do | Not stated | Read the registry and so read the graph (data that user already reads through the CLI); the endpoint must be **read-only** (no state changes, no spawn): the daemon launches paid runs |
| Stale registry, PID reuse | "Removes files whose process has died" | A PID alone is not identity: after a crash and reboot the PID may belong to another process, and a SIGKILLed orchestrator never removes its file. Liveness must be a **handshake** (connect and read the orchestrator id and a start-time nonce it wrote in the file) plus an exclusively held lock file the live process holds (released by the kernel on death), and a file with neither is removed only by the CLI that read it |
| Port collisions | "port/endpoint" | Bind port 0 and record what the kernel gave; never a fixed port. Two orchestrators of one project are fenced by the lease (F14) |
| Where the registry sits | `~/.fugaro/run/<id>.json` | Not `~/.fugaro` (F5). A runtime directory is not a state directory: macOS has none, so `<state>/fugaro/run` at mode 0700 is the proposal |
| Windows | `%LOCALAPPDATA%` for logs, nothing for the registry | The daemon is macOS and Linux only in v1 (D1232), so the scope exists only there; whether a Windows console reaching a WSL-run CLI sees a WSL loopback endpoint is UNVERIFIED |
| Token in the console | CLI sends it | The console never holds the token (the CLI does, from the file). The token is in a file readable by the same user the CLI runs as; a CLI spawned with a different `HOME` (`CHILD_ENV_KEYS` passes `XDG_*`) reads a different registry, which is correct |

**F24. Gap. The first run of the whole graph has no data that is not already on screen.** With no orchestrator (F13), no central orchestrator (F15) and a coordinator that holds pull requests and runs (F17), a `fugaro graph` built literally today would list "All" (the coordinator's PR and run nodes for every repository, which the Coordinator tab shows already), "local orchestrators: none" and "central orchestrators: none". *Consequence:* the first slice of part B has to be something the existing data supports, and the dropdown can start with two scopes (D1356).

**F25. Gap. `fugaro orchestrators` collides with the planned command group.** The central-orchestrator plan (P3) names `fugaro orchestrator add|rm|ls` (project-level, singular), and the stateless-orchestrator plan names `fugaro orchestrator install|run|state|patch|uninstall`. The spec's `fugaro orchestrators --json` (plural, top level) would be a second spelling of `orchestrator ls`. D1361.

**F26. Rule. Licensing and placement.** The coordinator command is a paid command in `ee/`; core may not import `ee/` (`internal/eeboundary/boundary_test.go`); the console is under the business licence from 0.113.0 (`console/LICENSE.md`, `.claude/rules/console.md`). A `fugaro graph` whose `all` scope reads the coordinator view must either live in `ee/` and register through `RegisterCommand`, or be core with a seam; the orchestrator daemon the plan describes is **core** ("nothing in it needs `ee/`; it must not import it"). D1362.

**F27. Rule. The managed gate and the agent refusal do not apply to these reads and writes, but a new write does.** Both parts are local files and reads: no cloud write, so the managed project gate and the agent-session refusal for cloud writes (`agentMarker`, the `CLAUDE.md` "never works around the refusal of cloud writes") are not engaged by a log or a graph read. The orchestrator state writes are the stateless plan's, with its own rules (D1241 and the daemon never runs a gated converge command, D1238). The console's one approved write is launch; the Graph draws writes disabled (redesign ruling 2026-10-28), so a graph that offers an action is out of scope.

**F28. Rule. The HARD RULE on `fugaro update`.** Part A changes `update`'s output and part B may add a daemon registry; the registry or log directory must be created by the command that needs it, `update` must stay "the whole upgrade", and a release must not ship a step like "delete your old log directory" (`CLAUDE.md`). The planned daemon unit is re-rendered by `update` (T7), so any new local file the daemon writes (a registry or a port file) is migrated by the daemon's start, not by an operator.

**F29. Rule. Docs are tested.** `internal/cli/docs_*_test.go` and `website/test/*.mjs` pin sentences and counts in `docs/`, `README.md`, `SECURITY.md`, the website and `website/content/cli-reference.md` (generated from the cobra tree: a new persistent flag changes every command's table). Each task in the plan carries `go test ./internal/cli/ -run Docs` and `npm run check` in `website/`.

**F30. Open (the spec's own).** The spec says "Optional later: `-vv`", leaves "a command along the lines of" for the graph command, and leaves the dropdown order when several local orchestrators exist (sort key: project then start time is the proposal), the colour palette and marker glyph (ASCII fallback: the `watch` screen has `--ascii`), what "6 steps" counts (stages, not Terraform resources), and whether the summary includes time when a step is waiting for the user. None needs the owner; they are proposed answers in the plan.
