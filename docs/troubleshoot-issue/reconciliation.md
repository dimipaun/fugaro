## 1. Findings

**F1. Wrong (the command does not exist).** The spec starts from `fugaro troubleshoot`. It is the agent command of `docs/diagnose-agent/`, plan only apart from three parts; its verdict (`internal/diagnoseagent/prompt.go`) has three outcomes, `configuration`, `bug` and `fixed_in_newer_release`, given as an `outcome:` line inside a block fenced by a per-diagnosis random value, not as JSON. *Consequence:* the spec's three buckets map as `configuration` and `fixed_in_newer_release` to **Local** (a fix is printed; the second says to run `fugaro update`), `bug` to **Fugaro**, and a new fourth outcome `unclear` to **Unclear**. T-IS4 adds `unclear` and the signature to the prompt, the parser and the existing tests (`TestPromptStatesTheThreeOutcomes`, `TestGuideNamesTheOutcomeLabels`); T-IS3 maps outcomes to classes. The issue store and `fugaro issue` are built on their own (D1726) and one hook in T-DG8's output calls the recorder (T-IS8). No second troubleshoot is built.

**F2. Rule (the confirmation prompts; D1720 amended after review).** The spec's `submit` "asks for confirmation" and the no-number `submit` "asks before filing each one". `docs/no-prompt-policy/` says no command waits for input, and the owner ruled D1544 (2026-11-07): `--ask` is the one confirmation flag and `--yes` is removed (T11 tests that no doc, skill or console file says `--yes`). The first D1720 answer (`--yes`) rested on a premise the policy contradicts. *Consequence:* D1720 as amended: `submit` prints the preview and files nothing; `--ask` prompts on the owner's own terminal and files on a yes; never in an agent session.

**F3. Rule (D327: a learning is never filed by the command).** `runs digest --submit-draft` deliberately sends nothing; its comment says "a learning is never filed by the command, by a run or by an agent". The spec's `submit` runs `gh issue create` itself. *Consequence:* this is a different artifact (a bug report the user asks to file, typed by the user with `--ask`), so D327 stands for learnings and is cited in the README as untouched. It also contradicts the diagnose plan's D1605 ("is the issue report filed by a command? No", which declined a `gh` filing as an outbound post of user data): D1728 amends D1605. `troubleshoot` itself still never submits, and a coding agent's session does not file (F10; the marker is a mitigation, not a barrier, as `internal/agentenv` says).

**F4. Gap (the issue leaves a private project for a public repository).** The spec's header carries reporter, task ID and OS; the body carries log excerpts. The target is public. The digest's own rule (G1) is that a report that can leave the repository carries no repository name and no run ID. *Consequence:* D1722: the shared store keeps the whole issue; the GitHub post is built from a stricter projection and re-redacted at submit, and the preview shows exactly that text.

**F5. Gap (redaction is best-effort and the second reader is a different person).** `internal/agent/redact.go` states its output is "best-effort redacted, not guaranteed clean"; pattern redaction is new (`internal/redact`). In this spec a teammate's saved text is later posted by someone else. *Consequence:* redact on write (as the spec says), and again **at submit**, by the submitter's own binary, over the text it is about to post; plus emails, home-directory paths and the project and repository names (scrubbed always, not "if possible"). Tests with sample secrets built from fragments (rule: no secret-shaped literal).

**F6. Gap (a verdict from untrusted text).** The classification comes from an agent that read log text the user does not control (the diagnose plan's F5). A hostile log can try to steer the verdict to `bug` (noise) or to `configuration` (hide a real bug). *Consequence:* the agent is read-only (D1602 there) and the CLI, not the agent, writes the file from a strictly decoded verdict; `configuration` and `fixed_in_newer_release` have no saved class, so nothing can persist them (T-IS1's `Class` has no such value, T-IS3's mapping returns none); a steered `bug` costs one pending entry the user can dismiss, and nothing is ever filed without `submit --ask` on a terminal.

**F7. Gap ("task ID" and the file name).** A troubleshoot runs over a local command log whose ID is the log stem (`<command>-<14-digit UTC>-<pid>`, D1609 of the diagnose plan) or a cloud ref `<repo-slug>/<run-id>`; neither is a "task ID", and the project number exists only after upload. *Consequence:* D1723.

**F8. Gap (the duplicate test is undefined).** "If one matches" has no meaning without a key. A model comparing text would put teammates' issue text into a prompt. *Consequence:* D1724: a fingerprint.

**F9. Gap (numbering and the claim need atomic writes, and a claim can be stranded).** `blobx.Create` is create-if-absent and `ReplaceIf` is generation-matched, so a counter and a claim are expressible. A claim whose holder crashes before `gh` finishes would block the issue forever. *Consequence:* the claim carries a lease (15 minutes, a constant) after which anyone may take it; the number is taken with a counter `ReplaceIf` loop and a lost race retries; a submitted record is final (T-IS10). GitHub-side duplicate search before creating is not attempted (cost; the claim covers two teammates).

**F10. Rule (a coding agent's session must not write to the cloud).** `CLAUDE.md`: the update skill "never works around the refusal of cloud writes in a coding agent's session", and `recipes publish` refuses in such a session (`internal/cli/recipes.go`: `agentMarker` plus `initflow.AgentRefusal`); the managed gate is audit-only (D1545) and is not the guard. Upload, claim, counter and dismissal writes are cloud writes. *Consequence:* the guard is the one `recipes publish` uses (`agentMarker(os.Getenv, stdinIsTerminal(...))`, not `agentenv.Present`, which also fires in a person's own IDE terminal): in such a session the issue is saved locally, upload and `submit --ask` refuse with a line naming the command a person runs, and nothing retries. Pinned by T-IS11 and T-IS12.

**F11. Wrong (who can write the shared prefix; D1727).** The first draft said team members can write `fugaro/`. `docs/design/bucket-iam.md` ("only operators write `fugaro/`") and `iam.tf` (`runs_launcher`, pinned by `gcp.LauncherBucketCondition`) give an ordinary launcher objectViewer plus objectUser on `runs/` and `tokens/` only; job accounts reach `gcp.JobBucketPrefixes` (runs, cache, locks) only. So upload, claim and dismissal would fail for non-operators, and a job cannot forge an issue. *Consequence:* D1727 moves the store to its own prefix `issues/` with a launcher write grant (T-IS17, shipped by `fugaro update` with a converge test and the launcher condition updated); job accounts stay without it. Recipes keep `fugaro/` and are untouched.

**F12. Gap (sync "on the next command").** A cloud call on every command, offline and in an agent session. *Consequence:* D1725.

**F13. Gap (state is split between a local file and the shared store).** The spec's statuses live in both. *Consequence:* the shared store is the truth once uploaded (`pending`, `submitted`, `dismissed` plus the URL); the local copy refreshes on `issue list|show|sync`; a dismissal is shared too (it is a team's issue, spec 4b), and `list` shows the whole team's.

**F14. Gap (the daily report is the digest, and its rules forbid the section; D1721 amended after review).** The digest renders no free text of a record (G1), reads no clock (G3) and covers "this repository and no other" (G2/D322); a second writer, `internal/runner/digest.go`, must produce the same bytes as `fugaro runs digest` and a job cannot read the project-wide issues. The section hook has one slot reserved for `ee/register` (`internal/digest/section.go`). A committed section would put project issues in every repository's possibly public report and make the two writers differ. *Consequence:* D1729: the Issues section is **terminal-only**, printed by the CLI after `runs digest`'s own output and never written to the committed file, so G1, G2, G3 and the runner's parity are untouched; it may name a one-line summary through `internal/safetext`, because nothing is committed. Thresholds are a user-level setting (T-IS15); the nudge depends on whose machine prints it, which is acceptable for a terminal line.

**F15. Exists (the install hints).** No `brew install gh` or `winget` string exists in `internal/`. It is built here, with the platform and `/etc/os-release` read through an injected seam, and a link to `https://cli.github.com` for an unknown distro.

**F16. Gap (the new-issue URL has a length limit).** The fallback link carries title and body in the query; browsers and GitHub refuse long URLs. *Consequence:* the body is cut to a fixed byte budget (a constant, 6 KiB after encoding), ends with "full text: `fugaro issue show N`" (never a local path, D1722), and the preview says it was cut.

**F17. Rule (every command family touches docs, plugin and console).** `plugin/` tests check every command and flag a skill names against the CLI; many `internal/cli/docs_*_test.go` pin docs; the console reads `--json` output. *Consequence:* T-IS9 and a `--json` for `list` and `show` with the format's version (a field never changes meaning).

**F18. Gap (setup "recommends" `gh`).** `internal/cli/setup.go` is the admin's command and the no-prompt rule forbids a question. *Consequence:* one printed line at the end of `setup`, and a `doctor` line (T-IS13); never required.

**F19. Gap (preview and post can differ).** A preview followed by a later submit rebuilds the post from the shared record; a record changed in between is posted unseen under the submitter's account. *Consequence:* the post is built once, shown with a hash of its bytes, and `submit --ask` files only those bytes; the claim and the record of submission are conditioned on the record version previewed (T-IS7, T-IS12). With no number, `--ask` asks per issue after showing its preview.

**F20. Gap (path traversal from the shared store).** Local file names are built from shared data (`<NNNN>-<run-stem>.md`). *Consequence:* the number and stem are validated by shape (the D1609 stem shape, digits) before any path is built; a `../` value is refused (T-IS1, T-IS11).

**F21. Gap (duplicates can bury a bug).** A log steering the signature to an existing `dismissed` or `submitted` issue would attach an occurrence and hide a new bug; two uploaders with one fingerprint can also race. *Consequence:* an occurrence attached to a `dismissed` or `submitted` issue reopens nothing but is shown ("N new since dismissal") by `list` and counted by the terminal section; the fingerprint index entry is created before the number is taken, so one fingerprint gets one number (T-IS10).

**F24. Rule (these are conventions between honest clients, not a boundary).** A launcher with write access to `issues/` can rewrite or delete any record, counter, claim or index entry, so "a submitted record is final", "one fingerprint gets one number" and "two submitters file once" hold only among clients that follow the protocol; the boundary is that a post is rebuilt, previewed and re-redacted by the submitter's own binary (F4, F19). T-IS17 adds an L3-style "hygiene, not a boundary" entry for `issues/` to `SECURITY.md` and `website/content/security.md` (`.claude/rules/credentials-service.md` applies). Shared records are read with `ReadMax`, and `submit --ask` refuses without a terminal on stdin (the `initflow.AskRefusal` helper, not a new one). The claim and the record are one object, taken and finalized with `ReplaceIf`, so the previewed version is the generation matched; `gh` runs under a timeout shorter than the 15-minute lease.

**F22. Gap (claim and counter versions).** Taking over an expired lease is a `ReplaceIf` on the stale claim's version, and recording `submitted` is conditioned on still holding it (T-IS10, T-IS12). `gh` receives the body through `--body-file` and the repository as `-R github.com/dimipaun/fugaro`, so `GH_HOST` and `GH_REPO` cannot redirect the post (T-IS6).

**F23. Gap (arguments, dismissal, schemas).** Before numbers exist, `show`, `submit` and `dismiss` accept the local ID or the number; the saved line prints `Saved issue local-<stem>. Run 'fugaro issue submit local-<stem>' to file it on GitHub.` until upload and `#0007` after. `dismiss` writes the shared status once uploaded and refuses in an agent session (T-IS5, T-IS11). Unknown class or outcome values are refused (T-IS3). `list --json`, `show --json` and the shared record have JSON Schemas in `schemas/` (T-IS3, T-IS5). Short run IDs of `docs/short-run-ids` are UNVERIFIED (U6).

**F25. Gap ("resolved" and "the fix version" exist nowhere).** The regression rule needs an issue's resolved state and the release that fixed it. The shared record has neither, upload runs on any teammate's machine often without `gh`, and nothing records a GitHub close. *Consequence:* D1731: the record gains `resolved_in` (a release) and the original GitHub URL it already holds; a later spec on the `update` command fills it in (F27); upload compares the reporter's version with `resolved_in` offline. A reporter's version at or above `resolved_in` matching a resolved issue is a **regression**: the occurrence is flagged and linked to the original URL, and the issue's status is shown `regression` in `list` and counted by the terminal section. An unresolved or later-version match attaches as before (F21).

**F26. Gap (the failed command is a secret and data carrier; "troubleshoot never checks for duplicates").** Arguments can hold paths, URLs, project names and secret-shaped values; `fugaro update` must not prompt (D1544). *Consequence:* D1732: the header stores the command name and flags with values redacted (`internal/redact`, then values that look like a path, URL or identifier replaced by a placeholder); it is never part of the public post (D1722) and `update` only prints it. Duplicate matching runs only inside upload (T-IS10); T-IS8's `Record` and the troubleshoot path call no matcher and read no shared store (T-IS8 test with a spy).

**F27. Scope (clarified 2026-11-08).** The owner: `resolved_in` will be filled in by the `update` command in a separate spec, and this plan assumes the field is there. It builds no `issue resolve`; it stores `resolved_in` (empty until that spec writes it), compares it at upload (F25), and builds the `update` retry hint (D1733, T-IS19), which prints nothing while the field is empty. (An earlier edit wrongly moved the hint out of this plan; the owner said it stays.) After a successful update, for this reporter's issues whose `resolved_in` is at or below the version just installed and not yet notified, `update` prints `You can retry: <redacted command>` and marks them notified; it runs nothing, reads no stdin, prints without marking in an agent session, and never fails the update (the hard rule).
