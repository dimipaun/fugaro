# The project layer

Design: [design/layered-config.md](design/layered-config.md). Plan: [plans/2026-10-08-layered-config.md](plans/2026-10-08-layered-config.md). The runs-bucket write access this design assumes is narrowed in a later release: [design/bucket-iam.md](design/bucket-iam.md) (§8).

## 1. What it is

The project layer is one object per project, `fugaro/project-layer.yaml` in the runs bucket, holding project-wide `defaults:` and named workflow `profiles:` with a `default_profile`.

It applies to every repository whose `fugaro.yaml` names the project and its `gcp_project:`, and to no other. A project without one, and a repository without the line, behave as before 0.6.0.

## 2. The one rule

For each key, the narrowest layer that sets it wins: per-task flag, then repository, then the workflow's profile, then project defaults, then Fugaro default. The budget ceiling is the owner's, outside every layer, and only tightens. A project that has published a project policy ([design/project-centric.md](design/project-centric.md)) has no `budget.mode: off`: a run reads the policy from the project's database, so its jobs must carry the Firebase backend and the mode itself is policy.

The base branch resolves through four layers, narrowest first (`config.EffectiveBaseBranch`, the one function every layer resolves through): the checkout's committed `fugaro.yaml` when its text writes `git.base_branch`, then the installation config's `repos.<r>.base_branch`, then the project's default base branch — the installation config's top-level `base_branch`, which `fugaro project policy publish` writes into the policy node — then `main`. The file's key is judged on whether it is written, never against `main`: a file that sets nothing takes the project's default, while one that writes `main` means `main` even where the project runs on another branch.

A published policy is read by the run itself, not by the launcher: it lives at `config/policy/shared` in the project's Realtime Database, and the run reads it with its own Firebase identity before it starts. Each key in that node is then the ceiling **for that key**: a key the node does not set keeps the value the job's environment was deployed with, so a policy published only to set `budget.allowed_models` leaves the mode, the caps and the kill switches exactly as they were, and one that names a mode replaces it. `budget.*`, `model_prices`, `allow_repos` and `routing` take effect in this release. A run checks two things before any git credential exists and before anything is cloned: that the storage slug it was launched for (its `FUGARO_RUN`) is the slug of the repository its task names, and that a published `allow_repos` admits that repository. A slug that belongs to another repository stops the run, and so does a repository the list does not admit — a policy published with an empty `allow_repos` therefore admits nothing at all. That is not the same as an installation that has published no policy: with no node under the marker there is no allow-list, and only the slug binding is checked. Only a local invocation — a `fugaro exec --provider fake`, which the CLI resolves as local because no backend claims the process — is exempt from the two checks: it has no job identity to bind to, so neither applies to it. A missing Cloud Run execution name is not what makes a run that one: `Local`'s zero value means the cloud, and a job whose environment was edited after launch carries no execution name either, so a process in the cloud that no backend claims is not waved through: the run refuses it before any git credential, because it has no job name to place it in a job with (the git credential would otherwise be scoped to whatever remote that environment names). `fugaro run` makes the same two checks before it creates an execution. A repository the list does not admit is refused with the run's own message (`projectpolicy.NotAdmitted`'s, one step earlier), while the slug binding and the release skew — a policy whose `version` is newer than the binary, which only this side can see — are worded by the launcher itself, the skew refusal quoting, for a node ahead of the binary, the release that introduced the version on the node (the `projectpolicy.VersionSince` table beside `projectpolicy.Version`, one row per policy version, which every too-new refusal reads — the launcher's, `fugaro project policy`'s, `fugaro doctor`'s and the run's own — and none when the table has no row for that version), and the release the policy model ships in only for a node *behind* the binary. The launch-side checks are advisory, since a launcher may start a job directly, and the run's own check is the one that counts. `providers` is decoded, validated and accepted by a run, but never applied: a run routes by the copy in its own job's environment (§5). `routing` is **applied**: the run rewrites the Claude pins the published switch names from the canonical ID to the route's own ID, once, under the same gateway that routes and prices the call (`internal/runner/routing.go`, called from `resolvePolicy`) — so a policy published with `routing.claude` sends that project's Claude calls where the switch says, and `fugaro project policy publish` writes the block from the operator's own config (§7). §5's policy-key table says what each of them does in this release. The project layer's keys can only tighten whatever results. The node beside it, `config/limits/policyRules`, records which generation of the database's security rules is deployed, and that marker is what makes a refusal readable: before the owner runs `fugaro update --firebase-project` with a Fugaro that deploys the policy rules, the policy node is left unwritten — an administrator's IAM credentials can write it by hand, and `fugaro project policy publish` refuses until the marker is there, because a policy published before the rules is one the runs it is meant to bound cannot read — and a run whose job carries no backend behaves exactly as it did before the policy existed. Once the marker is deployed, a policy that cannot be read or decoded **stops the run** — it never falls back to the ceiling the job environment was deployed with, because that ceiling is the one the published policy was meant to replace. The halt names the one cause that is not tampering: an older CLI's `fugaro update --firebase-project` redeploys rules from before the policy nodes and leaves the marker in place, so a policy that was published becomes unreadable and the fix is to run `fugaro update --firebase-project` again with an up-to-date Fugaro.

The **rigor mode** has its own order inside that rule ([docs/rigor-modes/spec.md](rigor-modes/spec.md), D6, D20): for the mode, the narrowest layer that sets it wins — an `rigor.areas` rule the run's paths match, then the repository's `rigor.default`, then the project layer's `defaults.rigor.default`, then Fugaro's own default, which is `pro`. Unlike every other key, a narrower layer may set a **lower** mode than a wider one: this is a default and not a floor, so a project that wants a floor says so with a floor. The two `areas` lists are the one place the merge rule of §4 does not replace a list with a narrower layer's: a repository's own rules and the project's are both in effect (D20c), the strictest matched rule decides, and every rule that matched is named in the run's record (`result.json`'s `rigor.areas`) and on `fugaro diagnose`'s `Rigor:` line, while `fugaro runs ls`'s `MODE` column names the one that decided, and the pull request the run opens carries the same answer in its status line (`rigor: critical (area payments)`). The resolver also takes a run's own request, which may raise the mode and never lower it (D6): `fugaro run --mode` is that request, and so is the mode a `--pr` follow-up keeps from its pull request, with or without the flag (it may only raise it), `--path` declares the paths the run will touch so the area rules can be matched before it starts, and a run's record says `from: request` when the request is what decided. A mode a run has reached never falls within that run (D22).

A workflow takes a profile only when it names one (`workflows.<name>.profile`), or when the file has no `workflows:` at all (then one workflow, `default`, takes `profile:` or the project's `default_profile`). A workflow that names no profile takes nothing from any profile.

A workflow's **job profile** is a different selection on a different key: `workflows.<name>.job_profile` names a profile of the *published policy* (§5, phase 3 of [plans/2026-10-14-project-centric.md](plans/2026-10-14-project-centric.md)), which is the Cloud Run job's shape — its provider, cpu, memory, task timeout, secret mounts and admission list — and not the project layer's workflow template. It is `job_profile` and not `profile` because `profile` already names the layer's template above; a file may carry both. A workflow that names none runs on `standard`, which any policy carrying a `profiles` block must define; writing `job_profile: standard` says the same thing and is treated exactly like omitting the key, so it runs with no policy or a policy without profiles too. The selection is refused, never resolved to another profile: `policy publish` refuses a `profiles:` block that does not define `standard`, and a run refuses a workflow whose `job_profile` the published policy does not define (`internal/runner`'s checkJobProfile; a project that has published no policy at all refuses an explicit selection other than `standard` too, because nothing defines it). What a profile *holds* — its cpu, memory, task timeout, secrets and admission list — is applied where the job is built: `fugaro setup` deploys one Cloud Run job and one job service account per (profile, provider, Claude account) for every profile a local config names (§10), a `checkout: clone` workflow's launch of a repository on the profile's own provider runs on that job rather than on a per-repository one (a repository on another provider, and a repository whose profile is one no shared job serves — in this release every Bitbucket repository, either way, since no shared job serves Bitbucket — keeps its per-repository job, decided before the launch takes a claim), and a run in it holds the repository to the profile's own `allow_repos` as well as the project's (`internal/runner`'s `admissionCheck`). The Claude account is an axis of that job's name: a profile serves a Claude account by listing it in `profiles.<p>.claude_accounts` (the `default` account, or a name of the local config's `claude_accounts`), which deploys one job per (profile, provider, account) and mounts that account's token on it — the `default` account on the profile's no-account job. A profile that mounts a Claude OAuth token in its `secrets:` is still refused (`fugaro setup` refuses it: the field is how a profile states accounts, design [project-named-oauth-tokens.md](design/project-named-oauth-tokens.md) D4), and a launch that selects an account the profile serves no job for is refused (§5). Which runs actually work on a shared job today is [below](#which-runs-work-on-a-shared-job-today) — in short, every gate the tree carries is open, and the design's live end-to-end check has not been run. A launch that cannot read the repository's own workflows — `fugaro run --repo …` from a machine with no checkout of it — keeps the per-repository job, as it does today. A baked workflow keeps its per-repository job until phase 4 ends (design [project-centric.md §4.4](design/project-centric.md)), and a policy that carries no `profiles:` block changes nothing: the jobs stay per repository, and a workflow that names a `job_profile` other than `standard` there is refused at run start, because nothing defines it.

**The policy is version 4 from fugaro 0.14.0, the release that states the Bitbucket token's block in it**
(`projectpolicy.Version`, and the `projectpolicy.VersionSince` table beside it names the release
each version came in — 1 is the model, 0.8.0; 2 is the profile gate, 0.8.5; 3 is the account axis,
0.9.0; 4 is the Bitbucket token block, 0.14.0 — which is the release a refusal for a node *ahead*
of the binary quotes, never 0.8.0, the release the model ships in). Version 4 adds
`bitbucket_token.allow_repos` (the repositories the project's Bitbucket credential may reach),
`bitbucket_token.proxy` (the operator's per-installation switch for the credentials service) and
the owner-allow-listed `bitbucket_api_roots`, together with the rules that hold a profile mounting
`bitbucket-token` to that block: its own exact `allow_repos`, a subset of the block's, and no such
mount on a GitHub profile. The block is policy-wide and derived whether or not a profile mounts the
token, because a proxied run is launched in a job that does not hold the credential and reads the
block as its admission source. A version-3 reader would decode past `bitbucket_token` as a
top-level key it merely lists in its unknown keys, so the bump is what makes it refuse the node
("refresh the runner image") rather than run a Bitbucket profile whose own `allow_repos` is the
only gate — and the other direction refuses too: a version-3 node is refused by this release's
runs and by `fugaro project policy publish`, with the delete-then-publish remedy. Every
installation republishes its policy for version 4.

Version 3 (0.9.0) is the node that came before it: `profiles.<p>.claude_accounts` and the
`accounts` block that gates it say which account each job of a profile serves, and one job per
(profile, provider, account) is what `fugaro setup` deploys (§10). A reader from before that release
cannot run such a node at all — `claude_accounts` is a member *inside* a profile entry, which its
own profile decode refuses — so the version field is what turns that into the documented refusal,
with the upgrade as the remedy, rather than an unknown-field error naming a field and no move. What
a version-3 runner enforces beyond version 2's gate — the profile's exact `allow_repos`, every
account it lists covering every repository on that list, and no Anthropic API key mounted beside
them — is §10's subject.

Version 2 (0.8.5) is the gate that came before it, and this release keeps it: **a run in a project
job is admitted only when the profile its job's name pins admits its repository**. A
runner image from before that release decodes a `profiles` block and ignores it — project jobs run
the installation's base image, which can lag the CLI that publishes — so a launcher that pointed
such a run at another repository of the project's `allow_repos` would run it with that profile's
secrets. That bump closes it: a version-1 runner refuses a version-2 node ("refresh the runner
image") instead of running past a gate it does not know. The other direction refuses too: a node
older than the binary is refused by this release's runs, by `fugaro run` before the execution
exists and by `fugaro doctor` (`policy-older-than-binary`), and `fugaro project policy publish`
will not write over it; remove it with `fugaro project policy publish --delete`, then publish
again with this Fugaro — after reading the list you are about to lose with `fugaro project policy
show`, because a publish with no node seeds the list from your config: a repository you had added
by hand (`fugaro project repos add`) is dropped, and one you had removed (`fugaro project repos
rm`) comes back when the config still names it. The node's `clone_urls` block (no command of this
release writes one) and any `routing` block a person wrote go with it, since a publish carries
them only from a node it replaces. Repair the list from the diff the publish prints (`fugaro
project repos add` / `rm`), per installation; a shared job's runs halt in between.

### What ties a repository to a project

**Three things, all of them data** ([design/project-centric.md §4.3](design/project-centric.md#43-enrollment-open-question-2-an-allow-list-in-the-policy-checked-by-the-runner)): the repository's default-branch `fugaro.yaml` names the project (`project:`, which the runner enforces); the project's published **allow-list** (`allow_repos` in `config/policy/shared`, checked by the run before it mints a git token or takes a lease and, advisory, by `fugaro run` before launch); and provider-side access, the GitHub App installed on the repository — the thing a run needs to mint its own git token, so a repository the App is not installed on cannot run even when the list admits it. There is **no registration record**: the first draft proposed one written at first use, and no principal can write it — launchers are viewers, and a run's token writes only its own `runs/`, `spend/` and `agents/` nodes. What is durable about "which repositories have run here" is therefore read, not written: the runs bucket's `runs/<slug>/` prefixes and Firestore's `spendDaily` records (the credentials the CLI already holds read both), which is what `fugaro project repos ls` prints beside the allow-list, and the GitHub App's own installed-repositories list (read with the App key, behind `--github-app-key`), which is what `fugaro project sync` offers the missing ones from. Discovery stays **optional and explicit**: nothing enrolls a repository but an operator's command, and `sync` writes one confirmed batch.

### Which runs work on a shared job today

**Every gate in the tree is open; no run has been recorded on one.** The two gates this section used to name — the launch gate and the provider gate — are both open, and what remains is the live check: Check 53 of `docs/gcp-live-checklist.md` (the plan's Task 3.7, `docs/plans/2026-10-14-project-centric.md`), the design's phase 3 end-to-end check, is OWNER-RUN and **NOT RUN**. So this section states what the code does, read off the code rather than off a job, not that a run has completed on a shared job.

- **The launch gate is open.** `checkout: clone` shipped in 0.9.0: `cloneShipped` is true (`internal/cli/recipes_skew.go`), live Check 38 passed on 2026-10-17 (the owner's ruling: `docs/gcp-live-checklist.md`'s own Check 38 record has still to be written up), and a `checkout: clone` launch of a current base image reaches a shared job. (Before the flip this was a second gate: a launch was refused on every image a release could build, and only a dev build with that gate opened reached a shared job.) What a launch still checks is the job image's release — `cloneSince`, fugaro 0.7.5.
- **The provider gate is open (`projectJobGitHubAppID`).** A project job's environment carries `FUGARO_GITHUB_APP_ID` (`providers.EnvGitHubAppID`; owner ruling of 2026-10-17, plan task 3.5 step 4): `internal/infra` sets it for every GitHub job from the App ID the installation's own local config records (`internal/infra/projectjobs.go`; the environment otherwise holds the installation's identity, the bucket, Vertex's project and region and the budget backend's address and web key, `projectJobEnv`) — one App per project, and a config that records no App ID, or two different ones, is refused at `fugaro setup` before a plan exists — and `modules/project/job.tf` requires it, so a job deployed without it fails the plan rather than halting its runs. `TestProjectJobCarriesTheGitHubAppID` pins the ID in the golden plan, with no key material beside it. The App's **key** stays the `github-app-key` Secret Manager secret the profile mounts (`FUGARO_GITHUB_APP_PRIVATE_KEY`), read by the job's own account. Those are the two halves `internal/gitprov/providers`' github arm builds the provider from, and it refuses without either, so a GitHub run whose workflow the launch gates admit opens its provider rather than stopping there. The plan's Task 3.3 step 6 (the runner reading the ID from the policy) is not what a run depends on: a shared job carries the variable exactly as a per-repository job does. What the job does **not** carry is the table just below.
- **Bitbucket repositories never reach one.** No shared job serves Bitbucket in phase 3: `fugaro setup` deploys no job for a Bitbucket profile (it is not refused — the policy admits one, and a Bitbucket repository's workflow may select it — it simply gets no job), and a launch keeps a repository whose provider is not the profile's, or whose profile is one no shared job serves, on its per-repository job.

These still differ from a per-repository job, because the shared job's environment deliberately leaves out what the per-repository job takes from one repository's config:

| Missing from a shared job | Effect |
|---|---|
| `FUGARO_CHECKOUT` | the runner does not treat the job as a clone job: a full clone instead of a blobless one, and no mise provisioning or prefetch |
| `FUGARO_MODEL_PROVIDERS` | no owner-configured model provider (OpenRouter and the rest) is available: only the Anthropic API key a profile mounts, or Vertex, can serve the agent |
| `FUGARO_COMPUTE_PRICES` | the region's list prices are used, not the local config's override |
| `FUGARO_BUDGET_GRACE` | the default grace applies |
| `workflows.<n>.secrets` | a repository's own secrets are never mounted on a shared job; only the profile's project-wide `secrets` are |

**Claude OAuth tokens are no longer one of the missing pieces** — that row left the table above when phase 3 gave a shared account its own job. A profile serves a Claude account by listing it in `profiles.<p>.claude_accounts` in the project's local config, whose entries are the `default` account or a name of `claude_accounts`, each stored project-wide and covering the profile's own `allow_repos`. The deployer then builds one shared job per (profile, provider, account) — `gcp.ProjectJobName` puts the account in the job's own name, and the `default` account rides the profile's no-account job, the one job every profile keeps — and each of those jobs mounts that account's token (`claude-oauth-token`, or `claude-oauth-token-<name>` for a named account, as `CLAUDE_CODE_OAUTH_TOKEN`) from the platform. So an `agent.auth: oauth` launch onto a shared job is admitted when the profile lists the account the run's own credential selects **and** the repository is on that account's published `accounts.<n>.allow_repos`; it is refused, before the claim and before any budget token is minted, when the profile serves no job for that account, when the run selects another account, or when the account's list does not cover the repository (`internal/cli`'s `projectJobAccountFor`, with `checkProjectJobAccount` and `checkProjectJobAccountCovers`), and the runner re-decides the same question at run start (`internal/runner`'s `checkProjectJobAccount`) rather than trusting the launch. A **non-OAuth** run never targets an account job, and a repository that keeps a per-repository job of its own (a baked workflow, or an installation that has published no profiles) is not affected. `fugaro doctor` reports every account job, the token it mounts and the repositories that token may be used by.

**A profile that mounts secrets needs its own `allow_repos`.** A profile without one admits whatever the project's `allow_repos` admits on its provider, and any enrolled repository can select it with `job_profile:` in its own `fugaro.yaml` — so every enrolled repository's runs can read the profile's secrets. Give a secret-bearing profile an `allow_repos` naming exactly the repositories that should hold them; `fugaro project policy show` and `fugaro project show` print a warning beside such a profile until it has one.

## 3. The minimal fugaro.yaml

```yaml
version: 1
project: acme
gcp_project: acme-fugaro
```

Three cases need more:

- `git.base_branch:` when the branch is not the project's default;
- `profile: <name>` when the project has no `default_profile`, or the repository wants another profile;
- `git.provider:` when the project layer does not set it.

`fugaro config init --yes` writes this file for you, in a checkout whose project publishes a project layer (`--profile` and `--base-branch` cover the first two cases; it refuses to overwrite an existing `fugaro.yaml`).

## 4. Overriding a profile

```yaml
version: 1
project: acme
gcp_project: acme-fugaro
workflows:
  api:
    profile: java-service
    commands: { test: ./gradlew test -x integrationTest }
    secrets: [{ name: db-password, env: DB_PASSWORD }]
```

The merge rules (design §4):

| Value | Rule |
|---|---|
| map (`git`, `git.pr`, `agent`, `agent.models`, a workflow, `image`, `commands`, `rerun_failed`, `resources`, `timeouts`, `rebuild`) | merged key by key, recursively |
| scalar (string, number, bool, duration) | the narrower layer's value replaces the wider one when the key is present, even as `""`, `0` or `false` |
| list (`git.pr.labels`, `image.apt`, `image.setup`, `commands.reports`, `cache`, `rebuild.paths`, and any repo-only list) | replaced whole, **never appended**. To add to a profile's list, repeat it; `fugaro config show` prints the list that results |
| `null` or an empty value (`key:`) | "not set here": the wider layer's value stays. This is today's meaning of null |
| `[]` | an empty list replaces the wider one, which clears it |

Two exceptions: a workflow that sets `dockerfile:` drops its profile's `image:` block (a repository with bespoke needs writes its own Dockerfile, and `image` and `dockerfile` are mutually exclusive today); and top-level `profile:` applies only to a file with no `workflows:` — with `workflows:`, each workflow names its own profile.

`governance` is a top-level key of the layer file (§6) like `claude_models`, and it is the one block the layer may **loosen**: it is the guardrail the project sets for every repository of the project, not a default a repository replaces. Every governance key is a bound whose smaller value is the stricter one — a stage budget as a fraction of the per-run cap, a token ceiling, a stage timeout, the review ratio, the fan-out cap, and each tier of `governance.tiers` with its expected cost, expected duration and own fan-out — so a repository's own `governance:` block can only tighten it, and a looser value is dropped and recorded rather than applied. What the layer cannot do is move the cap itself: the deployed per-run cap stays the ceiling, and a stage budget is a fraction under it, never the cap (G6, D330). A tier is no exception and is the point of the rule: `governance.tiers.<tier>.expected_usd` says what a run of that tier is *expected* to cost, so an expectation above the deployed cap is a figure the run still stops at the cap for, and no tier key raises or replaces one (G6, D330). One key of the block is enforced today: a stage that runs past its `stage_timeout` stops the run, which records a checkpoint report and opens a draft pull request. The rest of the block is what the gateway reads in a later task.

Outside this table: secrets' values live in Secret Manager and are never in any layer — and a secret name is stored **project-wide by default**: `fugaro secrets set NAME` with no flag writes the project's own container, whose reach is decided per name rather than by enrolment — the repositories the name's own `project_secrets.<name>.allow_data_to` list names, a provider key's provider's `allow_data_to`, or a named Claude account's own list (`infra.ProjectSecretCandidate` and `AllowsData`; SECURITY.md's "the reach is…"), each of them still bounded by what a published policy admits — until phase 3 gives the mounts to a profile, `--repo` is what asks for one repository's own copy instead, and a repository copy with an enabled version wins over the project's for that repository ([design/project-centric.md §6.3](design/project-centric.md); `fugaro doctor` lists which copy each name resolves to, and warns when a repository copy shadows the project's). A project-scope secret is not a layer and cannot be set in one — `workflows.*.secrets` stays a repository's own application secret, and a name with a project-wide meaning cannot be shared through a workflow's block; per-person Claude tokens are a later project; the individual layer is flags and env only. `claude_models` (§6) has no row here on purpose: it is a top-level key of the layer file, not a `fugaro.yaml` key at all, so it exists in no repository's file to be scoped — a repository cannot write it even in principle, which is the whole point of the key (§8).

The published policy's own keys are outside this table too — they are set in the node (`config/policy/shared`) and in no layer, and the node *is* the ceiling for the keys it names (§2). What a run does with each of them in this release:

| Policy key | What the run does with it today |
|---|---|
| `version` | must be the version this Fugaro reads; anything else stops the run (release skew, P8). `fugaro run` refuses the launch before it creates an execution, naming the release that introduced the version on the node (a version above every release this binary knows is answered with the upgrade alone); a node older than the binary is refused with the release the model ships in |
| `budget.mode`, `budget.per_run_usd`, `budget.max_run_tokens`, `budget.allowed_models` | applied: the ceiling for the keys the node names, the environment's for the rest |
| `model_prices` | applied: the price table the run's caps are computed with. Its member names are **keyed by the model ID escaped** (RTDB refuses a key holding `.` or `/`, and the documented `deepseek/deepseek-v4-flash` carries one), and every reader decodes them back — the operator reads model IDs in `policy show`, the diff and `--json`, and a run prices the model it calls |
| `allow_repos` | applied: the run refuses a repository the list does not admit (and a slug that is not the task's own repository), before any git credential exists; `fugaro run` refuses an unadmitted repository earlier, with the run's own message |
| `providers` | decoded, validated and accepted, **not applied**: a run routes by the providers its own job carries (`FUGARO_MODEL_PROVIDERS`), which is what the switch resolution and the prices use — the node's block is what the switch is validated against when it is published and read, and what a later release will apply |
| `routing` | **applied**: with the gateway on, the run rewrites the Claude pins the switch names — `routing.claude.models` is the opt-in list (D1a) — from the canonical ID (`claude-sonnet-5-5`) to the route's own ID (`anthropic/claude-sonnet-5.5`), so the pin the agent is given, the route the gateway sends the call to and the row it is charged from all name one model. A switch this run cannot resolve (a model no job route claims, a route whose `allow_data_to` is not written, two routes claiming one model) **halts the run** rather than falling back to the direct path, and `via: auto` is skipped for a Vertex run, which serves Claude under the project's own credential. With the gateway off nothing changes: the pins keep Claude's IDs and the switch has nothing to act on |
| `profiles` | decoded, validated and **refused when unusable**: the block must define `standard` (the profile a workflow that names none runs on), every profile must pin a provider (`config.Providers`), cpu and memory must be a shape Cloud Run accepts, `timeout_class` must be a positive duration whose job task timeout — the class plus the backend's two-minute slack, the figure the job is deployed with — is within Cloud Run's 168h ceiling, every `secrets` entry must be a secret **name** (`config.CheckSecretName`: never a pasted key, and no value is ever echoed back), and every `allow_repos` pattern that names a provider must name the profile's own (a pattern that names none — `*`, `*/owner/*` — is accepted, because what keeps another provider's repository out is the provider gate in `projectpolicy.Admits`, not the pattern's spelling) — while an explicitly empty `allow_repos` is refused, because an absent key (the project's list applies) and an empty one (which the node could not carry anyway) are not the same statement. A profile's list can only narrow the project's enrollment, never widen it: `projectpolicy.Admits` requires the profile's provider, the project's `allow_repos` and the profile's own list, and `projectpolicy.ProfileFor` refuses a profile the policy does not define. `ProfileFor` is what a run applies: a workflow whose `job_profile` the published policy does not define halts at run start instead of running on another profile (`internal/runner`'s checkJobProfile), and the launcher resolves the job's own name with it. The other two are the profile's admission gates, and a run in a project job holds a repository to the project's `allow_repos` **and** the profile's own, before any git credential exists (`internal/runner`'s `admissionCheck`, through `AdmissionRefusal`); the launcher's advisory twin checks the project's list one step earlier, where the operator can still read the refusal. One job and one job service account per (profile, provider, account) is what `fugaro setup` deploys for every profile a local config names, and that job is where a profile's cpu, memory, timeout and secrets are applied. The job's name also carries a Claude-account axis, which the profile's own `claude_accounts` decides (one job per (profile, provider, account), the `default` account on the profile's no-account job; a named account must be stored project-wide and must cover the profile's `allow_repos`): a run whose `agent.oauth_token` (or `--token`) names an account the profile serves no job for is refused at launch rather than run on a job that holds no token of that account, and a Claude OAuth token written where it does not belong — in a profile's `secrets:` — is refused here. A run in a per-repository job — a baked workflow, or a policy that carries no profiles — is held to the project's list alone, which is what it was held to before. A profile's list is validated here and enforced there. `policy publish` writes the block from the operator's config (its `profiles:` key) and `project show` prints each profile with the job it maps to |

A key in the `providers` row is not an unknown key: the CLI knows it and does not refuse it the way it refuses a misspelt one (§2, [design/project-centric.md](design/project-centric.md)). The two rows differ for a reason worth stating: `providers` has no effect on a run, `routing` decides where that run's Claude calls go and what they cost, so publishing a switch is a live change to every repository of the project.

## 6. The project layer file

```yaml
# fugaro/project-layer.yaml, in gs://fugaro-runs-acme-fugaro
version: 1
project: acme
gcp_project: acme-fugaro
defaults:
  git:
    provider: github
    pr: { labels: [fugaro] }
  agent:
    auth: oauth
    review_rounds: 2
    recipe: standard
profiles:
  java-service:
    description: Gradle service with Postgres
    image: { tools: { java: "temurin-17" } }
    commands:
      build: ./gradlew assemble
      test: ./gradlew test
      reports: ["**/build/test-results/**/*.xml"]
    cache:
      - { key: [gradle/libs.versions.toml], paths: [~/.gradle/caches] }
    resources: { cpu: 4, memory: 16Gi }
    timeouts: { total: 2h }
  node-web:
    image: { tools: { node: "22" } }
    commands: { build: npm run build, test: npm test }
default_profile: java-service
# An explicit Claude model ID a route the installation config already
# defines also serves (mixed-credentials.md §4): provider name -> one
# "anthropic/<id>" per line, never a pattern.
claude_models:
  openrouter: ["anthropic/claude-sonnet-5.5"]
```

`claude_models` is the one top-level key (`version`, `project`, `gcp_project`, `defaults`, `profiles`, `default_profile`, `claude_models`, `governance`) that adds to the **local** config rather than to a repository's file: it names a route only the owner defines and says which Claude model that route also serves, so a senior review can be routed to it. It may only add an explicit `anthropic/<id>` to a provider the installation config already lists — never create a provider, never change its `base_url`, `auth`, `secret` or `allow_data_to`, never name a class of models. An entry is appended to that route's own `models`, so it is held to the route-entry rule as well: at most 100 characters, the same bound a route entry carries (`config.CheckModelPattern`), because the gateway applies that rule to the merged table and a longer ID would otherwise leave it refusing to start every run whose job carries the route. The refusal for a claim the installation config cannot take is at the surfaces that hold that whole config: `fugaro config publish` refuses to publish the object at all when a name is not defined, a list is empty, or an entry overlaps another route's pattern, and `fugaro validate` refuses the checkout for the same reasons. A run cannot make that check — its route table is the job's own `FUGARO_MODEL_PROVIDERS`, written per repository with only the providers that list that repository in `allow_data_to` — so a claim naming a provider this repository's job does not carry is a route **this repository does not have**: the claim is dropped for that run, and only a pin on the claimed ID is refused, as a model no provider serves. That is deliberate, because the layer is installation-wide: one claim naming a provider the owner did not list for every repository must not fail the bootstrap of repositories that never name the claimed model, let alone those that do not use a provider at all. The price is not the layer's to set: it comes from the operator's `model_prices`, and never from the built-in catalog — the catalog prices only the models a *route* lists, and the layer's claim is in no route the deployed job carries (below) — so a claimed ID with no `model_prices` row fails the run as unpriced, and the layer cannot make a call cheaper than the ceiling says. The claim reaches a run through the layer (it is never written into the deployed job's `FUGARO_MODEL_PROVIDERS`), so removing it from the layer puts the refusal back on the next launch.

Reserved keys, refused with a message: `environments` (the image catalog, Phase 2, blocked on the base image consolidation) and `extends` (profiles do not extend each other in this release). The object has a 64 KiB limit.

Its shape is checked strictly, with the shared config's trust rules: one document, holding a mapping; no anchors, aliases, merge keys, tags or repeated keys; no unknown or reserved keys; no key outside its scope (§5); no credential-shaped value (an Anthropic, OpenRouter, GitHub, Slack, Google API, Bitbucket or AWS key, a PEM private key, or a service-account key file — as a key or a value, anywhere, including inside a comment); and `project` and `gcp_project` equal to what it is read for.

halts: re-run `fugaro update --firebase-project` with a current Fugaro), **a rules marker below the generation that carries the policy nodes** (`projectpolicy.PolicyRulesVersion`: it records rules that predate the policy nodes while claiming a generation, so no run reads a policy and `fugaro project policy publish` refuses: the same `fugaro update --firebase-project`, which records this release's generation), **a rules marker below the generation this Fugaro deploys but at or above that one** (generation 1 or 2 while this release deploys generation 3: the rules carry the policy nodes, so the published policy is read and enforced and publishing another is not refused — what they predate is this release's own document, which adds the mobile app's mailbox **and binds the user claim to a device node** (`config/admin/devices/<uid>`, mobile plan P6.4/D166: an account with no node reads and writes nothing at all, and nothing mints one yet — the pairing command is plan task P6.6 and is not built, so the node has to be added by hand), so `fugaro update --firebase-project` from a Fugaro that deploys the current generation is the fix; the skew is reported as what is absent, not as a policy nothing reads), and the opposite skew, **deployed rules newer than this Fugaro** (the marker records a generation above this binary's, so a policy published under them **is** read — `projectpolicy.Read` takes a marker at or above its own generation as deployed — while the rules document itself is a shape this binary cannot verify and must not deploy its own over: `fugaro update --firebase-project` is the wrong move here and refuses the state itself rather than relying on the operator's reading — a marker above the binary's generation stops it before anything is planned, so an older binary cannot downgrade a newer installation's rules or rewrite the marker down — and the fix is `fugaro upgrade` first).

`fugaro runs ls` adds a LAYER column once any listed run carries a project layer: `gen N`, `gen N (not applied)` for a run that resolved without it (a launch from outside a checkout whose `fugaro.yaml` at the ref didn't name the layer's project and `gcp_project`), or `-` for a run with none. `fugaro diagnose` adds a `Config:` line: `project layer generation N (sha256 <short>)`, with `, not applied` and `; resolved sha256 <short>` appended when they apply; a run with no layer but a resolved sum shows `no project layer; resolved sha256 <short>` instead.

## 8. Publishing safely

**`--executable-changes` is a CLI check, not an access control.** It only gates `fugaro config publish`; whoever can write the bucket object directly (for example with `gcloud storage cp`) bypasses the guard below and the sha256 trail. Since the 0.7.0 bucket IAM hardening ([design/bucket-iam.md](design/bucket-iam.md)), that is operators only (and, for its own copy, a repository's own build account): a launcher's direct write is refused with a 403. An installation whose operator has not yet run `fugaro setup` to apply the 0.7.0 grants still has every launcher holding `roles/storage.objectAdmin`, with the old, wider bypass, until they do.

`fugaro config publish` refuses in a coding-agent session, before anything else. That is what "only from your own terminal" means here. Since 0.7.0 it is also operator-only in effect: a launcher's own terminal gets the operator-role refusal ([design/bucket-iam.md](design/bucket-iam.md)), the same as any other write to `fugaro/`.

**`--executable-changes`.** A profile may set the keys of `config.ExecutableKeys`:

<!-- executable-keys:start -->
- `workflows.*.commands.build`
- `workflows.*.commands.test`
- `workflows.*.commands.lint`
- `workflows.*.commands.fix`
- `workflows.*.commands.render`
- `workflows.*.commands.probe`
- `workflows.*.commands.rerun_failed`
- `workflows.*.image.apt`
- `workflows.*.image.setup`
- `workflows.*.image.tools`
- `workflows.*.image.skip_build_scripts`
<!-- executable-keys:end -->

— values that run as shell, or (`image.skip_build_scripts`) control whether shell a profile already describes runs, in the job or in the image build. `commands.render` and `commands.probe` are gated like `commands.build`: an artifact recipe's render and probe steps run the workflow's own text as shell in the job. `commands.reports` is not gated: it only lists paths to collect, and runs nothing. `inputs.*` is not gated either: the caps are numbers, and they bound what a launcher may attach, not anything a profile runs. `config publish` refuses a change to any of these keys, in either direction (`image.skip_build_scripts` going from `false` to `true` is reported too, not only the unsafe direction), unless `--executable-changes` is given, printing each one's before and after under an `EXECUTABLE CHANGES` banner first; changing `default_profile` itself is gated the same way, whenever either the old or the new default profile sets one of these keys.

**The write.** It is made under a generation precondition, so a concurrent publisher is refused rather than overwritten, and a diff against the previous object is shown first. The exact bytes are then copied to `builds/<slug>/project-layer.yaml` for each repository the installation config lists. `fugaro doctor` reports a repository whose copy differs from the published object.

**Residual caveats, now that Task 14 and Task 15 have both shipped.** Neither Cloud Build's render step nor the daily check job verifies this copy's sha256 against the canonical `fugaro/project-layer.yaml` — neither account can read that object at all. Cloud Build's render step only refuses a copy whose sha256 changed between submission and render (`_PROJECT_LAYER_SHA256`); the daily check job verifies nothing, trusting the copy as published, the same trust its neighboring build record already carries (design §8, §11's residual risk: a repository-controlled build step holding `objectUser` on its own `builds/<slug>/` could rewrite its own copy, confined to that one repository and the build secrets it already has access to).

**The threat model (design §11):**

- **Who can write.** Operators, since the 0.7.0 bucket IAM hardening. An installation whose operator has not yet run `fugaro setup` to apply the 0.7.0 grants still has every launcher holding `roles/storage.objectAdmin` too (see the lead note above).
- **What a hostile or careless layer could do.** Replace build or test commands for every repository that takes a profile: this already takes effect, through the embedded layer every launch carries, with no human reviewing the change first. Since Task 14 and Task 15 shipped, add `image.apt`, `image.setup` or `image.tools` (as dangerous as `image.setup`: it names tools installed into the image) or turn off `image.skip_build_scripts`, which then runs in Cloud Build, including on the nightly rebuild, with no human launching anything. `commands.lint` and `commands.fix` are executable keys too, like `commands.build` and `commands.test`, and so are `commands.render` and `commands.probe` since 0.8.0. Also: raise `resources` or `timeouts`; change `agent.model`, `recipe` or `auth`; point `base` at another shipped kind; loosen the guardrails for every repository of the project (`governance`, §5) — a larger stage budget or stage timeout, a higher review ratio or fan-out cap — up to the per-run cap, which is the one thing it cannot move; or hide any of this, since a plain bucket write leaves no review trail. And, since the claim shipped, add one explicit Claude model ID to a route the installation config already defines (`claude_models`, §6), which sends that route's model to the provider the owner set up under the owner's own terms — nothing more: the layer cannot create a route, change a route's `base_url`, `auth`, `secret` or `allow_data_to`, name a provider the operator did not define, claim a class of Claude models, or set a price.
- **What already bounds it.** The project layer cannot hold policy keys, `secrets`, `followup.*`, `base_branch`, `reviewers`, `dockerfile` or `instructions` (§5); the policy ceiling (dollars, tokens, allowed models) still comes from the owner and only tightens, and the governance the layer may loosen is bounded by that same ceiling: the per-run cap is what it may not move, and every stage budget is a fraction under it (G6); base images stay `config.Bases`; and every run records the layer's sha256 and generation, which `fugaro runs ls`, `diagnose` and `doctor` show. A `claude_models` claim (§6) is bounded by the route it names: the traffic still goes to a provider the owner defined, under that provider's `allow_data_to` (so a repository the owner did not list for it never gets that route in its job at all — the claim is dropped for that repository's run, and a pin on the claimed ID is refused as a model no provider serves, never sent), the claim is one explicit ID rather than a class, the run needs `agent.auth: api-key` and `budget.mode: enforce` like any other provider model, and the price is the owner's `model_prices`', never the layer's and never the built-in catalog's.
- **The fix, shipped in 0.7.0.** [design/bucket-iam.md](design/bucket-iam.md) narrows the bucket grant so only operators (and, for its own copy, a repository's own build account) can write `fugaro/` and `builds/<slug>/`. Each installation's operator applies it by running `fugaro setup`; until they do, the bucket stays writable by every launcher (see the lead note above).

**The readiness gate fires on what the planning config can see.** A project job is held back at
deploy time only where the config making the plan can read the policy node, which means the
readiness gate blocks a *deploy* only where the config making the plan can see a policy, because
that config is what it reads the node through. A config that names **no** `budget.rtdb_url` sees no
policy at all, so the gate never fires for it, whatever the project has published: nothing refuses
that deploy, and the job goes out unable to read a policy that may well exist. That is a gap in the
gate, accepted by the owner on purpose, not a rule a policy would close.

## 9. Rollout (0.6.0)

The order:

1. Release 0.6.0.
2. Every teammate's CLI, and every CI job or pin that runs `fugaro`, moves to 0.6.0.
3. Per repository, run `fugaro image refresh`. This moves its job images and its check job to a 0.6.0 base. Before a project layer is published there is nothing for it to copy: it writes no `builds/<slug>/project-layer.yaml` (decision L6, a build without a layer never touches a copy), so this step is safe to run against every repository regardless of whether its project has published one yet.
4. Only then publish the project layer with `fugaro config publish`. It warns, listing repositories whose build records predate 0.6.0.
5. Only then merge a minimal or profile-using `fugaro.yaml`.

What an older CLI does, in a repository with a project layer: a minimal or profile-using file is refused as invalid, so there is no silent misrun; a full file runs with today's behaviour, without the project defaults.

Step 5 is safe once Task 14 and Task 15 have shipped (§8): the project's `defaults:` and a profile's `commands.*`, `resources` and `timeouts` all take effect at once, through the layer every launch embeds, and a profile's `image.apt`, `image.setup` and `image.skip_build_scripts` reach every image a build produces — a human-triggered `image build`/`image refresh` and the unattended nightly rebuild alike.

## 10. Not yet

- **The 0.7.0 bucket IAM hardening** ([design/bucket-iam.md](design/bucket-iam.md)): narrows who can write `fugaro/project-layer.yaml` and `builds/<slug>/project-layer.yaml` from every launcher to operators only (§8). Until it ships, the residual risk in §8's "Residual caveats" stands: a repository-controlled build step can rewrite its own `builds/<slug>/` copy, and neither Cloud Build's render step nor the daily check job can tell it from a legitimate one.
- The image catalog (`environments:`): Phase 2, blocked on the base image consolidation — see [design/layered-config.md §9](design/layered-config.md#9-the-image-catalog-phase-2-blocked-on-the-base-image-consolidation).
- `extends` (a profile extending another).
- `fugaro config extract` (suggesting a project layer from several repositories' files).
- **`fugaro project show`'s running-now list is still the registry's** (phase 4's discovery surface, [plans/2026-10-14-project-centric.md](plans/2026-10-14-project-centric.md)): the commands that write and read `config/policy/shared` ship in 0.9.5 (§7), `fugaro doctor` reports the policy's state and `upgrade` says that a job's environment copy of the ceiling is inert for the keys a policy governs (§7), and the discovery answer has shipped too — `fugaro project repos ls` prints the enrolled against the seen from the runs bucket and `spendDaily`, and `fugaro project sync` offers the App's installed repositories (§7, [§2](#what-ties-a-repository-to-a-project)). What `project show` still prints for "running now" is the run registry's runs in flight, and it says so; the durable answer is one command away rather than in that output. What no command does yet is enroll a repository the App has dropped-and-reinstalled under a name the list names differently, or reconcile an enrollment against a repository that no longer exists: `repos rm` is the only way out, by hand.
- **The baked half of a published policy's profiles** (phase 3 of [plans/2026-10-14-project-centric.md](plans/2026-10-14-project-centric.md)): the clone half is live as of 0.9.0 (`cloneShipped` is true, `internal/cli/recipes_skew.go`; the flip landed after live Check 38 passed on 2026-10-17 (the owner's ruling: `docs/gcp-live-checklist.md`'s own Check 38 record has still to be written up)), and plan Task 3.5 (the retirement of a repository root) is not done. What is in the tree: the node carries the profiles, decodes and validates them (a profile that names a job Cloud Run cannot deploy is refused where it is published, §5), `policy publish`/`project show` write and print them, a run refuses a workflow whose `job_profile` the policy does not define (fail closed), `fugaro setup` deploys one Cloud Run job and one job service account per (profile, provider, Claude account) for every profile a local config names, a `checkout: clone` workflow's launch of a repository on the profile's provider runs on that job, and a run in it applies the profile's cpu, memory, timeout, secrets and admission list; a launch that selects a Claude account the profile's job does not run as is refused (a profile serves accounts by listing them in its own `claude_accounts`, and one job per account is deployed for it). What is not there is the baked half: a baked workflow still runs on its per-repository job, where the profile's shape, its own `allow_repos` and its account do not apply, which is phase 4's work. An older binary meets the selection as an unknown config key and refuses the file (its decoder knows no `job_profile:`), so the skew is a refusal at validation and never a run on a profile nobody selected.

(`routing` is no longer one of these: a run applies the published switch, §5. `allow_repos` stopped being one of these earlier: a run and `fugaro run` both apply it, §5.)
