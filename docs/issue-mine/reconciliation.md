# `fugaro issue mine`: reconciliation

Reconciliation of [spec.md](spec.md) against `origin/main` (commit `2232815b0`, 2026-11-08). Where the two disagree this file wins. The spec is the owner's (Dimi Paun). Nothing here is implemented and no task is approved. Every cited path and symbol was grepped on `origin/main`; what was not checked is in section 4.

**This spec is a read view over two plans that are themselves docs only:** [`docs/troubleshoot-issue/`](../troubleshoot-issue/README.md) (the issue record, the local and shared stores, `fugaro issue list|show|submit|dismiss|sync`; "troubleshoot-issue F25", "T-IS10") and [`docs/issues-resolved-on-update/`](../issues-resolved-on-update/README.md) (`resolved`, `resolved_in`, the installation record, the retry hint; "update-plan F11", "T-RU2"). **Numbers.** This work reserves **D1780–D1809** (D1780–D1784 used) and **Checks 470–479** (470–472 used). Verified on 2026-11-08 above every `D` and `Check` number on `origin/main` and in the open pull requests' docs: the highest reserved were D1779 and Check 469 (`docs/issues-resolved-on-update`).

## 1. Findings

**F1. Wrong (the command's whole data model is unbuilt).** The spec reads as if `fugaro issue`, a shared store and a `resolved` status exist. They are two docs-only plans. *Consequence:* every task here depends on named tasks of those plans (external prerequisites in the plan, none on `main`), and none can start before the one it names has merged. Where this spec needs a field or a key layout those plans have not built yet, T-IM2 and T-IM3 amend what those tasks build; they start only after the task they amend has merged, and the amendment must reach a release no later than the first one that ships the shared store (O2).

**F2. Rule (the spec's six statuses are four plus two derived views).** The shared record's status is `pending|submitted|dismissed|resolved`; `local` and `regression` are not values of it (update-plan F5; troubleshoot-issue F25). *Consequence:* the row's **display status** is derived, once, in one function (T-IM1): `local` when the issue has no project number and is not dismissed locally; `regression` when the user's own occurrence is flagged a regression against the issue's `resolved_in` and the issue is `resolved`; otherwise the record's status. A locally dismissed, not yet uploaded issue shows `dismissed`. The record's enum is not widened and no field changes meaning.

**F3. Gap ("the current user" is undefined, and the tree's verified identity needs the network; D1780).** The spec says the user is "identified the same way as the issue's reporter field", but neither plan says what that field holds (update-plan U3). The tree already has one verified answer to "who is asking": `access.Caller` returns the address of the Google credential the command will use, and says it is "never the local configuration's `user:` key and never `git config user.email`" because a person or a coding agent can set those. Its reader (`credentialEmail`) calls Google's userinfo endpoint with a 20-second bound, so it fails offline, while the spec's acceptance needs `mine` to work offline. *Consequence:* D1780: the reporter field holds `access.Caller`'s address (lower-cased, the `user:` prefix kept off the stored string), **set at upload by the uploading machine from the credential (`VerifiedOnly`), never copied from the local file's text, and an upload with no verified credential does not happen (the issue stays local)**; T-IM3 amends T-IS10's `Upload` and T-IS11's sync for it; `mine` matches on that. A verified lookup is cached after each success (T-IM4) so an offline run still knows who "me" is. The cache drives **display reads only**; no upload, claim or dismissal reads it (mutation check in T-IM4). An account switch is picked up on the next online run; until then offline rows are the previous account's (stated in the docs).

**F4. Gap (the record has no submit or resolve date; D1781).** The spec's three date columns need `submitted_at` and `resolved_at`, and the 30-day hiding needs the time an issue was resolved or dismissed. The planned record has only `created`; the claim's time is released after filing (troubleshoot-issue F9); update-plan D1754 deliberately avoided a timestamp for the **report window** and uses versions instead. *Consequence:* D1781: three additive record fields `submitted_at`, `resolved_at` and `dismissed_at` (strict RFC 3339 UTC), stamped by the writer that already makes the transition (T-IS12's `RecordSubmitted`, T-RU3's `SetResolved` and `SetClosed`, T-IS11's shared dismissal) under an injected clock (T-IM2). Adding a field is allowed; none changes meaning, and D1754's window logic stays version-based. Pre-release, so no compatibility shim is built (the release train is open item O2); a record that lacks one prints `-` and is never hidden. A local dismissal stamps `dismissed_at` in the local header too (T-IM2). The user's "hit" date is not a record field: it is the time in the user's own earliest occurrence (F7).

**F5. Gap ("already on that version" has two answers; D1782).** The fix can live in the CLI binary or in the cloud side that only `fugaro update` applies (job images, runner, policy). `CLAUDE.md`'s hard rule: `fugaro update` is the whole upgrade, and `brew upgrade` alone is not. A CLI-only comparison tells a user who has brewed but not updated to retry a command whose fix is not yet applied. *Consequence:* D1782: **covered** when the CLI version and the installation's recorded release (`installrec.Read` of `fugaro/installed.json`, T-RU2) are both at or above `resolved_in`; **behind** otherwise (the nudge is exactly "run `fugaro update`", the one command); when the record cannot be read (offline, no record yet, an agent session) the CLI alone decides, the row is `cli_only` and says "installation not checked", and **no retry suggestion is printed for it** (the suggestion needs both known; open item O4); a `dev` or unparseable CLI version is **unknown** (never covered, no nudge, because a dev build cannot be updated: troubleshoot-issue D1736).

**F6. Rule (the spec's GitHub lines are dropped; D1784, not the recommendation).** The spec says to show "whether the issue is open or closed on GitHub" and to refresh "the same way `fugaro update` does", with a last-checked time on failure. The owner ruled (2026-11-08, replying to the question whether `mine` should also mark issues resolved): no GitHub access at all, "go by the `resolved_in` field alone". *Consequence:* `mine` reads no GitHub **issue** state and never uses `internal/issueresolve`; its own network use is the shared store and the credential lookup (`access.Caller` calls Google's userinfo endpoint). The root command's once-a-day release check (`startUpdateCheck`, `internal/cli/updatewarn.go`, release builds on a terminal) is not issue state, runs for `mine` as for any command and is untouched; excluding `mine` from it would be new behaviour and is not proposed. A **submitted** row says what the shared record says (the URL, "filed, not marked fixed"); GitHub's open/closed state appears only through the record, so a closed-but-not-yet-resolved issue stays `submitted` until a `fugaro update` pass (T-RU4) marks it. The spec's "last checked" becomes "as of" the time of the shared read (or the snapshot's, F9). The cost is that latency, stated in the docs and in open item O1. Update-plan's resolver, cursor and the anonymous rate budget are untouched.

**F7. Gap (finding "my" issues without reading every issue; D1780; amended after review round 1).** The shared store keeps one record per issue and one occurrence object per duplicate (update-plan F10, T-RU3 `Reporters`). Finding a user's issues by reading everything is `N + M` reads, and one global names listing is capped by name order, which is issue-number order, so a project reaches the cap on its own and the newest issues are the ones dropped; any launcher could also fill the listing and empty everyone's view. *Consequence:* two small additions to what T-IS10 builds (T-IM3). (a) A **reporter index**: an empty object `issues/reporters/<digest>/<NNNN>` created (`blobx.Create`, idempotent) at upload for the issue's creator and for each duplicate's reporter; `<digest>` is the first 16 hex characters of the SHA-256 of the lower-cased reporter address (hygiene, not secrecy; the address stays in the record and occurrence bodies). `mine` lists only the user's own prefix (names only), capped at a constant 500 issues; a flood under a victim's digest can degrade only that victim's view, and the truncation line says so. (b) Occurrence objects are named `issues/occurrences/<NNNN>/<digest>/<time>`, where `<time>` is the issue's `created` time, the moment the user **hit** it (not the upload time), compact UTC; a retry of the same upload is a create-if-absent no-op. The original report is **not** an occurrence (the word keeps its meaning for T-IS14's Recurring count and `issues.nudge_recurrence`, T-RU3's `Reporters` and T-IS11's "new since dismissal"); the creator is the record's `reporter`. For each of the user's own issues `mine` makes one names-only listing of `issues/occurrences/<NNNN>/` (capped at 1000 names) and derives the user's hit time (the record's `created` if the user is the creator, else the earliest time under the user's digest) and the number of **other** people (distinct digests, the record reporter's included, the user's own excluded). It reads the user's issue records (`ReadMax`) and, for `resolved` issues only, the user's own occurrence objects (the regression flag). The same person on two machines is one digest, counted once.

**F8. Gap (the retry suggestion: whose command it is).** The spec wants the failed command as a try-again suggestion for a resolved issue the user is covered for. A merged duplicate's record holds the **original reporter's** command, and an occurrence holds no command (update-plan F11, troubleshoot-issue D1724). A launcher with write access can rewrite any shared record (troubleshoot-issue F24); update-plan O4 ruled that a command from the shared record is shown, never suggested for re-run. *Consequence:* `mine` suggests a retry **only from this machine's own issue file** (the command this machine wrote, redacted, through `safetext`, and only if it is a `fugaro` command in the CLI's command tree, the diagnose plan's D1614 check), and only for a **covered** row; it adds "commands can change things; nothing is run for you". It never prints a shared record's command, so an issue the user hit on another machine or whose file is gone prints no suggestion. The local file is matched to the shared row by number **and** fingerprint (a local issue file is global to the machine, so project A's `#0007` must not supply project B's command). It does not set the update hint's local notified flag (T-IS19): `mine` is a pull view and repeating it is harmless. In a coding agent's session the local command is still the only one printed, as update-plan F11 says.

**F9. Gap (offline, and issues hit on another machine).** The spec: "works offline, showing local issues and the last known statuses". Local issue files exist only on the machine that hit the problem; an issue the user hit elsewhere, or a duplicate merged into another reporter's issue, lives only in the shared store. *Consequence:* D1784 leaves nothing to refresh from GitHub, but the shared read still needs the network. T-IM5 keeps a **snapshot** of the last successful `mine` result (user cache directory, **one file per installation**, named by a digest of the runs bucket URL, mode 0600, a `format` field, strictly decoded, written atomically; it holds the display rows and never a command): offline, `mine` prints the snapshot's rows merged with the local files and says "offline: shared state as of <time>". With no snapshot it prints local rows only and says so. Coverage and the 30-day hiding are recomputed at print time against the current CLI version and clock, so a snapshot cannot keep a nudge or a hidden row stale.

**F10. Rule (agent sessions and writes; D1734 and D1725 of the first plan apply).** `list`/`show` in a coding agent's session use local data and skip sync (troubleshoot-issue D1734); `list` syncs in an interactive session (D1725). `mine` is a `list` view. *Consequence:* in a coding agent's session (the `agentMarker` guard of `recipes publish`, as every cloud rule here) `mine` reads local files and the snapshot only, makes no shared read, no upload and no credential lookup (the identity comes from the cache or is none), and says so; elsewhere it calls `SyncPending` as `list` does (a failed or refused upload is one line, never an error) and then reads the shared store. `mine` itself writes only two local caches (the snapshot, F9, and the identity, F3), never to the cloud.

**F11. Rule (hostile shared data, a new reader of an untrusted store).** The shared store is writable by every launcher ("hygiene, not a boundary", troubleshoot-issue F24); a teammate or a steered agent can write a record that this command prints on another person's terminal. *Consequence:* a summary and any text goes through `internal/safetext`; the GitHub link is printed only in the shape `https://github.com/dimipaun/fugaro/issues/<n>` (troubleshoot-issue F28); `resolved_in` only as a strict `X.Y.Z` (`updatecheck.CanonicalRelease`); times only strictly parsed; the issue number and the digest are validated by shape before any key or path is built (troubleshoot-issue F20); the counts are integers computed here, never read from a record; records are read with `ReadMax`. A false `resolved` record can show "fixed" for an issue that is not; the suggestion it can trigger is limited to the user's own local command (F8), so the worst effect is a wrong status line, stated in the hygiene entry for `issues/` that troubleshoot-issue T-IS17 and update-plan T-RU7 plan (neither is on `main`); T-IM7 adds this plan's effects to it: a launcher can forge who reported an issue or a regression through occurrence and index names, delete or inflate them, and so change what `mine` and the hit counts show.

**F12. Gap (the alias and `--all`).** `fugaro issue list --mine` must be the same code as `mine` or the two drift. `--all` means "include old resolved and dismissed rows", which `list` does not hide. *Consequence:* `mine` and `list --mine` call one function; `--all` and `--json` are accepted on both; `--all` without `--mine` on `list` is refused with one line (a flag never means two things). `list --json` (T-IS5, `schemas/issue-record.schema.json`) is untouched; `mine --json` is its own versioned shape (T-IM6, `schemas/issue-mine.schema.json`, `"format": 1`) whose field names are new, so no reader's field changes meaning (CLAUDE.md "a field never changes meaning"). The JSON carries the counts, never other reporters' names or digests.

**F13. Gap (ordering, hiding and the 30 days; D1783).** The spec orders four groups and does not place `regression` or `local`. *Consequence:* D1783: **1** `regression`; **2** resolved and the user is behind ("fixed, not updated"); **3** `local` and `pending` together; **4** `submitted`; **5** `resolved` (covered, unknown) and `dismissed`. Within groups 1, 2 and 5 the newest status change first; within groups 3 and 4 the oldest hit first (the longest wait is the loudest). Hiding applies only to group 5: a row whose `resolved_at` or `dismissed_at` is more than 30 days before now is hidden unless `--all`; a row in groups 1 to 4 is never hidden; a row with no such time is never hidden (F4). When rows are hidden a final line says how many and names `--all`.

**F14. Gap (regression is per user and is not cleared).** The regression flag is set on the occurrence at upload when the reporter's version is at or above the issue's `resolved_in` (troubleshoot-issue F25, T-IS10). Nothing reopens or re-resolves an issue (update-plan F14, O3: a GitHub reopen is not noticed). *Consequence:* a row is `regression` while the user's own flagged occurrence exists on a `resolved` record; it carries the link to the original issue (the record's URL, shape-checked) and nothing else. Another reporter's regression does not turn this user's row into one. If a later spec adds a re-resolve, this rule is revisited (it is named in the plan's review focus).

**F15. Gap (what "other reporters" may reveal).** The spec asks for a count ("also hit by 2 others"). The update plan lists names to the admin because the admin must tell the reporters; a reporter has no such need and the names are teammates' addresses. *Consequence:* `mine` prints and returns **counts only**; a count of zero prints no suffix; the user themself is never counted.

**F16. Rule (every command family touches docs, plugin, schemas).** `plugin/` tests check each command and flag a skill names against the CLI; many `internal/cli/docs_*_test.go` pin docs; the new `--json` shape needs a schema. *Consequence:* T-IM6 (schema) and T-IM7 (the issues page, the plugin paragraph, release notes). Release notes carry no `### For operators` step of their own: nothing here runs after deploy (the occurrence names and the three fields are written by the CLIs that ship the shared store), so the operator line stays "run `fugaro update`".

**F17. Gap (the shared-store listing needs read access).** `mine` reads `issues/` as an ordinary launcher; troubleshoot-issue D1727 and T-IS17 grant launchers read and write there. A prefix-conditioned objectUser grant does not carry listing (`docs/design/bucket-iam.md`); launchers can list because they hold objectViewer on the whole bucket, unconditioned. *Consequence:* no Terraform change; whether a non-operator launcher's login lists `issues/reporters/` and `issues/occurrences/` on the real bucket is UNVERIFIED and is Check 470.

**F18. Gap (release train).** The three date fields (F4) and the index and occurrence naming (F7) must be present in the **first** CLI that reads or writes shared issue records (T-IS10), or the record's `format` is bumped so an older teammate's CLI refuses rather than misreads (the same sequencing as update-plan F5/O2). *Consequence:* open item O2; the plan places T-IM2 and T-IM3 so they can land before or with T-IS10's release.
