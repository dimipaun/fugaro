## 0. What the spec is, and what it is not

The owner's second spec states the five rigor **levels** (`poc`, `startup`, `pro`, `critical`, `hotfix`) as **personas** (a short character each: what it cares about, ignores and hands back), how a level is **resolved** (built-in `pro` < project default < project area/repo overrides < the repo's own YAML < the task), a **promote** task that raises existing code to a higher level, **review matching** (a reviewer judges by the task's own level) and the **debt artefact** each level leaves. It is a behavioural layer. The 2026-10-20 work is the **mechanism**: scores on findings, thresholds per mode, a resolver, floors, a Markdown backlog. The two are complementary, which is the finding that shapes everything below.

## 2. Findings

**LF1 — Exists.** The five levels and the default `pro` are decisions already answered (D19: the built-in default is Pro, and Critical is what a repository pins to; D18: the security-sensitive tier stays Critical). The new spec restates them. *Consequence:* nothing to decide.

**LF2 — Wrong (vocabulary).** The spec says *level*, `level:`, `--rigor`; the approved plan, the Slice 1 code on the branch (`rigor.areas[].mode`, the `mode` front-matter field of a backlog item, D27) and the planned flag (T1.6's `--mode`, which D12's Hotfix gate also names) say *mode*. The config key's **name** `rigor:` already matches; its **shape** does not: the spec writes a repository's level as the scalar `rigor: critical` and the project's areas as a map keyed by name (`areas: {console: {repos, level}}`) beside a `repos:` map, while the tree has the block `rigor: {default, areas: [{name, match, mode}]}` in `fugaro.yaml` (`testdata/config/valid/rigor.yaml`) and `defaults.rigor` in the project layer (§4 item 8 asks which shape). Nothing of this is released: only Slice 0, T1.1–T1.4 and the backlog's T4.3/T4.4 exist, and only on the branch. *Consequence:* a rename, cheap now and expensive after Slice 3. → **LD2**.

**LF3 — Wrong (what an area is).** The spec's "area of interest" (`console`, `mobile`) was first read as a group of repos. The approved plan's area is a **path glob inside one repository** (D20; the code: `rigor.areas: [{name, match, mode}]`, and the project layer's `defaults.rigor.areas`, whose invalid fixture `rigor-area-outside-repo.yaml` refuses a glob that leaves the repo). The owner's answer to LD4: an area is **a named semantic part of the project**, not necessarily one repo; its members are whole repos or repos-with-paths. *Consequence:* the two notions unify into one: an area is a name plus members, defined at the project layer (and a repo's own YAML defines areas for its own paths as today). Because a member may be a repo-with-paths, **one repository can sit in two areas** (its `ui/` in `console`, its `mobile/` in `mobile`): that is the case semantic areas exist for, so it cannot be a validation error, and two areas whose members overlap on one path resolve by D23's strictest rule (§3b item 11). → **LD4**.

**LF4 — Rule (precedence).** D6 answered: area, then repository, then project, then the built-in default, one resolver, the mode never falls within a run. The spec: built-in < project default < project areas < project per-repo < repo's own YAML < per-task. With LD4's areas the layers become, weakest to strongest: **built-in `pro` < project default < project area (matched member) < project per-repo < the repo's own YAML (its default, then its own path areas) < the task**, floors excepted (LF5). *Corrected after review:* this is not one reversal against the 2026-10-20 answers but four. (a) area vs repo at the **project** layer (D6 had area strongest; the spec has the project's per-repo entry beating the project's area); (b) the task request, raise-only under D6, F14 and T5.2 (`internal/rigor/resolve.go` on the branch: "may raise and never lower"), may now lower a default (LF5); (c) the repo's whole YAML now beats every project area, where D20 and the shipped schema (`schemas/project-layer.schema.json` on the branch: "a repository's own rules never switch the project's off") make the two area lists a union a repo cannot switch off; (d) D23 needs "no order between a project area and a repository area", and this order puts one there. *Consequence:* D6, D20 and D23 are amended after review (§3a), each confirmed by the owner on 2026-10-22 (§3b items 4–6). → **LD3/LD4**.

**LF5 — Rule (floors).** D8, D18 and D21: a floor (the security-sensitive tier and any declared floor) is outside every layer; **no run, task request, follow-up, label or job variable lowers one**, only a merged change to the base branch's configuration. The spec's "per-task override: strongest of all" read literally lets a task go below a floor. *Consequence:* the owner's LD3: floors stay; "strongest" means strongest among **defaults**. A task may raise above a floor or lower a default, never go below a floor. *Amended after review:* "a task may lower a default" contradicts D6/F14 and T5.2's raise-only follow-up, which LD3's question did not show; §3a keeps the owner's intent for a **new** run and keeps a follow-up raise-only (§3b item 4). → **LD3**.

**LF6 — Exists (thresholds vs personas).** D1–D7: the reviewer scores each finding (1–5 on three axes), a mode is a set of thresholds, and the policy lives inside `runner.Decide`, so "may this pull request be ready" has one deterministic answer. The spec expresses the same five levels as characters, with no numbers. Two ways to read it: personas **replace** the thresholds (readiness then depends on model judgement) or **sit on top** of them. *Consequence:* the owner's LD1: both. The persona is the prompt that shapes how the coder and reviewer behave; the thresholds still decide what blocks. → **LD1**.

**LF7 — Gap (no persona layer).** The three prompt builders are level-blind. A persona needs an injection point: the system prompt of the implement stage (`SystemPrompt`), the reviewer's prompt (`ReviewPrompt`) and the fix prompt (`FixPrompt`). The text must live somewhere stable and tested. → **LD10** (embedded, one Markdown file per level, not overridable yet).

**LF8 — Exists (the debt artefacts are the backlog).** D9 and D30: one Markdown file per tolerated finding, filed in the run's own pull request; Startup and Pro file one per tolerated finding, POC none or one line, Critical none of its own, Hotfix one for what it deferred. The spec's "deferred list" is that set of items, the Hotfix "morning note" is the item Hotfix always files, POC's "run note and prototype warning" is PR-body text. *Corrected after review:* the spec's list is what the coder **consciously** skipped, and the runner files only **reviewer-tolerated** findings (T4.5); the coder's own deferrals, Critical's open risks, the morning note, the revert plan and OPEN QUESTIONS have no carrier today except the agent's free-text `pr.md` (`rawPRText`, `internal/runner/runner.go`). *Consequence:* no second format for the items, and one new agent→runner contract: fixed sections of the agent's `pr.md` that the runner parses (plan LV4.2). The fallback body that embeds the task text is never read for them. → **LD5**.

**LF9 — Gap (open risks).** The spec has Critical **never defer quietly**: anything it cannot fully cover is an explicit **open risk**. D30 had Critical file nothing of its own (it tolerates nothing). The backlog's front matter (D27) has eight fields (`id`, `title`, `mode`, `area`, `status`, `filed-by`, `filed-in`, `date`) and a closed three-word `status`. An open risk is a finding Critical could not close; it needs to be distinguishable from a tolerated finding. *Consequence:* a ninth required front-matter field `kind` (`deferred`, `open-risk`), and the `mode` field is renamed `level` (LF2). The generated index and its pins change with it. D27 (eight fields) and D30 (Critical files nothing of its own) are therefore amended by LD5 (§3a). → **LD5**.

**LF10 — Rule (Hotfix).** The persona says rollback ready before deploying and verify the fix restored service. D13: Fugaro opens pull requests and never deploys; `gitprov` has no merge call; D14: a deterministic diff rule gates and the agent's confidence number is recorded and never trusted; D12: an operator invokes Hotfix, gated on the base branch's configuration, never a PR comment. *Consequence:* the persona's text is adjusted to what Fugaro can do: rollback-ready means the PR body carries the exact revert (a `git revert` target or the flag to flip); "verify restored" is a line in the morning note for the human or CI. → **LD7**.

**LF11 — Gap (Pro asks for guidance).** A cloud run cannot ask mid-run. The existing "not ready" state is a draft PR. *Consequence:* a run that reaches a scope, cost or data-model call it should not make stops with the PR as a draft whose body **opens with an OPEN QUESTIONS section** and ends with a distinct reason, so a follow-up (or the orchestrator) can answer it. One new end reason, no new waiting state. *Corrected after review:* `runstore.Record.Reason` is free text and `outcome` already has `draft`, so the "reason" is a new closed record field (plan LV5.2), not an enum value; the answering follow-up is comment-sourced (F13) and so can carry no level (T5.2). → **LD8**.

**LF12 — Gap + Rule (recipes).** Recipes arrange the loop and name models; D16: modes lower the budget ceiling, never raise it; D10: the verify stage's gate is the recipe's `check`. The spec wants a recipe to read the level (cheap coder plus senior reviewer at `poc`/`startup`, stronger models at `critical`). *Consequence:* a recipe may branch on the resolved level; the cap is the level's own (D16 and T6.1 give each level its own per-run default below the deployed cap) and a recipe can never raise it, so a Critical recipe with stronger models reaches its cap sooner. `internal/recipe` has no conditional construct today (only `use_when` text and a `mode: implement|artifact` key), so the branch is a new construct. The shipped recipes stay level-agnostic until a per-level one is asked for. → **LD9**.

**LF13 — Gap (promote).** No task kind reads a backlog, audits code, or raises its level. The nearest thing is the follow-up run on a pull request. A promote task reads an area's code plus its backlog items (deferred, open-risk, morning notes) and works at the target level; from `poc` there is no list, so an **audit pass** comes first. It also closes the loop D15 left open ("the automatic follow-up: recorded now, scheduled later"): the Hotfix morning note is the promote task's input. Four points the spec leaves open are §3b item 12; the slice waits for them. → **LD6** (a later slice).

**LF14 — Exists, extended (review matching).** D7(a) already hands the reviewer the findings policy. The spec adds per-level review standards: no nitpicking POC for missing error handling, adversarial scrutiny at Critical, checking that skipped items appear on the deferred list (startup, pro) or as open risks (critical), checking minimality, the revert plan and the morning note (hotfix). *Consequence:* the persona text carries the standards (the reviewer's persona is the level's own, in a reviewer variant of the same file); the artefact-presence checks are deterministic checks in `Decide`, not model judgement, and they read only the agent's own `pr.md` sections. "Did the coder skip something it did not list" is judgement, not a presence check: the reviewer reports it as a scored finding and the level's thresholds act on it. The level can rise during a run (D22's three moments) after the reviewer has judged; §3b item 10. → **LD1**, **LD5**.
