# Messaging a running run: reconciliation

Checked against `origin/main` at `0db80aa40` on 2026-11-18. **Where this document disagrees with [spec.md](spec.md), this document wins.**
Decisions **D2940–D2947** are taken; **D2948–D2959** are reserved for this feature. Live check **Check 740** is taken; **741–744** are reserved.

## Assumptions

- **A1.** "A run that is going" means a run whose execution has started and has not reached finalize. A queued run (no execution yet) is out of scope: its task can still be changed by cancelling and launching again.
- **A2.** "The current stage" for `--now` means a **coder** stage (implement, fix, a follow-up's resumed implement). A review stage is never interrupted (D2942 keeps reviewers blind to messages).
- **A3.** The message's text is the person's own words, of the same standing as the launcher's instructions on a follow-up (`docs/design/v1.md` §4.4: "The launcher's own text is always trusted"), and reaches the agent fenced and marked as data from that person, never spliced into the system prompt.
- **A4.** The first slice is the CLI and the runner. The console, the mobile app and the orchestrator daemon send through the same objects later (spec "Later surfaces"), and nothing in this plan builds them.

## Findings

- **F1 (Rule → resolved by D2940).** The spec's "trusted senders: the launcher and `followup.trusted`" does not type-check. `followup.trusted` (`config.Followup.Trusted`, `internal/config/config.go`) lists **git-host account IDs**; a message is written to the bucket under a **GCP identity**, and the job has no way to learn which identity wrote an object (no per-object writer metadata; `LaunchedBy` is self-declared). Every launcher can already write every run's `task.json` and `cancel` marker (`docs/bucket-iam/spec.md` §2's writers table, and §4's H2: "Launchers write all of `runs/`"), and `SECURITY.md` states the model the system rests on: "Everyone who can push to the repository, everyone who can launch a run, and (for follow-up runs) the people listed in `followup.trusted` can steer an agent". A launcher sending a message adds no one to that list.
- **F2 (Gap → resolved by D2941). The spec's own "authenticated" requirement fails if messages live under `runs/`.** `SECURITY.md` ("The metadata server is reachable, by the agent and by every container it starts") means a run's agent can act as its job account, which holds `roles/storage.objectUser` on `runs/<slug>/` — and a project job account on the whole of `runs/` (`docs/bucket-iam/spec.md` §2.1). An inbox under `runs/` would let a hostile agent plant a "message from the person" into its own later stages or, on a shared project job, into **another repository's** running run. `tokens/` is read-only for every job account and writable by every launcher (and by the opt-in resident orchestrator's account, which holds the launchers' condition, `deploy/terraform/gcp/modules/installation/orchestrator.tf`); viewers and launchers read it through `runs_reader`. It is the one prefix that already has exactly this shape. **Its read side changes meaning, and the documents must say so.** A project job's read of the whole of `tokens/` was accepted because everything there is ciphertext (`deploy/terraform/gcp/modules/project/sa.tf`'s comment: "what it reads is ciphertext … so the reach is over bytes, not over tokens"; `token.PutObject`'s comment; `docs/bucket-iam/spec.md`: "The one object a launcher writes under `tokens/` is its own launch's sealed budget token"). Messages are plaintext, so on a shared project job every repository's agent can read every repository's messages. That is the reach it already has over `runs/` (`task.json`, the brief itself, is readable the same way: `SECURITY.md`'s D4 widening), so it is accepted, and RM6 (the `project/sa.tf` comment and `token.PutObject`'s comment) and RM7 (`bucket-iam.md`, and `budget-token-channel.md` §7.2 and §7.4's "plaintext object … is the exposure") rewrite those sentences rather than leave them false.
- **F3 (Wrong → resolved by D2942).** Spec item 6 assumes a reviewer judges the diff against the brief. It does not: `ReviewPrompt` and `reviewBrief` (`internal/runner/prompts.go`) take no task text, so a reviewer never sees the brief and cannot flag a change as "not what was asked". Showing it messages would add an injection path into the one stage whose independence the design protects.
- **F4 (Gap → resolved by D2943).** After implement ends, the only coder stage left is a fix, and `FixPrompt` ends "Touch nothing else: make only the changes these findings ask for" — `CLAUDE.md`'s "a fix round for review findings adds no functionality". A message saying "also do X" delivered there contradicts the prompt it rides in.
- **F5 (Gap → resolved by D2944).** A message can arrive when no coder stage remains (the last review shipped; finalize next), or during finalize itself. The spec says only "never delivered (the run ended first)".
- **F6 (Gap → resolved by D2945).** `agent.Claude.Run` writes the prompt to stdin once (`Stdin: strings.NewReader(req.Prompt)`) and closes it: there is no channel into a running `claude -p`. Interrupting a stage today is the cancel path (`WatchCancel` → context cancel → `procgroup`'s SIGTERM then SIGKILL), which ends the stage as a failure. `--now` therefore needs a new, non-failing stop and a `--resume` of the same session. Stopping in the middle of a tool call loses that call (a test run of many minutes).
- **F7 (Open → resolved by D2946).** "Wrap up" in the spec is open between a flag and ordinary text.
- **F8 (Open → resolved by D2947).** The command's name was left open. `fugaro cancel RUN` (`internal/cli/cancel.go`) is the one top-level command that acts on a running run; the `runs` family (`ls`, `show`, `watch`, `stats`, `summary`, and `digest` and `reports`, which write reports) never acts on a run that is going.
- **F9 (Gap, resolution).** **Version skew.** A CLI with this feature can send to a run whose runner predates it, and the run record carries no runner version (`runstore` writes `version` as the record's format only). Resolution: the runner writes an additive `messages` block into `result.json` at bootstrap with `accepting: true`; `fugaro tell` refuses, printing why, when the record has no such block ("this run's runner does not read messages; it started before Fugaro <release>"). No prompt, no wait (the no-prompt policy).
- **F10 (Gap, resolution).** **Listing.** A job account's conditional grant gives no `storage.objects.list` (`docs/bucket-iam/spec.md` §2.3: "a GET of a missing object answers 403"). So the runner never lists: messages are numbered, `tokens/<slug>/<run>/messages/0001.msg.json` onward, and the runner GETs the next number on each poll, treating 403 and 404 alike as "none yet". The CLI (a launcher holds `objectViewer` on the whole bucket, `runs_reader` in `deploy/terraform/gcp/modules/installation/iam.tf`) lists the prefix, takes the highest number plus one, and writes with create-if-absent, retrying on a collision, so two senders never overwrite each other. **A gap must not stall delivery.** Launchers hold `objectUser` on `tokens/`, so a number can go missing (a deletion, a hand-written object). When number N is missing, the runner also GETs N+1 to N+3; if one exists, N is recorded `missing` and reading goes on from there. The CLI refuses to write when its listing shows a gap below the highest number, saying which.
- **F11 (Gap, resolution).** **Retention.** The bucket's only age rule on `tokens/` matches the suffix `/budget-token` and exists only with the budget enabled (`deploy/terraform/gcp/modules/installation/bucket.tf`); message objects would stay for ever. Resolution: one unconditional lifecycle rule deleting objects under `tokens/` whose names end `.msg.json` at 7 days of age (GCS matches a prefix and a suffix, never a middle segment; the age comes from `var.bucket_lifecycle` like the bucket's other ages), shipped in the installation root that `fugaro update` already applies. **Amended after review:** the runs bucket is versioned (`bucket.tf`'s `versioning` block) and the existing noncurrent rule keeps a deleted object for `noncurrent_days` (7 by default) more, so a message's text stays readable as a noncurrent version — to anyone who can list versions — for about 14 days in all. The owner's 7-day answer (O1) is the live age, and the owner accepted about 14 days in all (O2). No operator step, no IAM change. The run's own record keeps its copy (F13).
- **F12 (Gap, resolution).** **Caps and hygiene.** A message is at most 4 KiB of text after cleaning, a run reads at most 20 messages (the CLI refuses the 21st; the runner never reads a number past 20, and `diagnose` lists one a launcher wrote by hand as "never read: over the cap"), and the text goes through the run's redactor (`agent.Redact`) and `safetext.MultiLine` cleaning, inside a fence drawn from a fresh nonce (the follow-up prompt's pattern), before the agent sees it.
- **F13 (Gap, resolution).** **The record.** `result.json` gains an additive `messages` block: `accepting`, and per message `seq`, `sent_at`, `sent_by` (the self-declared sender, display only), `flags` (`now`, `wrap_up`), `state` (`delivered` | `undelivered` | `refused` | `missing`), `stage`, `delivered_at` and `reason`. **No message text is in the record.** Additive, so `result.schema.json`'s version is unchanged (`CLAUDE.md`, "A field never changes meaning"). The copy is the runner's own write under `runs/`, which the agent could overwrite: it is an audit trail only. The runner's in-memory position is the only authority for delivery, and it never reads delivery state back from the record. `report.md` is posted from the runner's memory, and is the one place a message's text is quoted after the run.
- **F14 (Rule, resolution).** **The no-prompt policy.** `fugaro tell` never waits for delivery and never asks: it writes, prints the number and returns. With no text argument it fails at once; it does not read a terminal. It runs in a coding agent's session as `fugaro run` and `fugaro cancel` do: an agent that can launch a run can already steer one.
- **F15 (Gap, resolution).** **Halts.** A run whose last review is all `needs_owner` halts with `owner_decision` at once (v1.md §4.1). Messages do not change that path in this slice: a ruling sent by message before the halt reaches the next coder stage like any other; one pending at the halt is `undelivered` (D2944). The report is built in four places — the finalize path in `runner.go`, `storeUnposted` and `storeEnded` in `internal/runner/followup.go`, and the artifact path in `artifact.go` — and halted, cancelled and infra-error endings go through `storeEnded`, so RM4 wires the Messages section and the final read into `runner.go` and both `followup.go` sites. The artifact path never carries messages (F24).
- **F16 (Rule, resolution).** **Upgrade.** Nothing here needs an operator step: the runner and CLI ship in the release, `fugaro update` rebuilds the job images behind its own confirmation and applies the installation root that carries F11's rule. An installation at the previous version converges by that one command; a run started before the update keeps running without the `messages` block, and `fugaro tell` refuses it (F9).
- **F17 (Gap, resolution).** **Access.** `fugaro cancel` checks the caller's role before acting (`requireRunAccess(…, accesslib.ActionCancel, …)` in `internal/cli/cancel.go`; the closed table `actionRules` in `internal/access/resolve.go`). `fugaro tell` checks `ActionLaunch` (operator, per repository): sending a message steers the run as a launch does, so it needs the role a launch needs, and no new action is added. D2940's "any launcher" means any launcher whose role reaches that repository.
- **F18 (Gap, resolution).** **The last poll.** A message written after the runner's last poll would be lost silently. At finalize the runner makes one more read (rule 5). `fugaro diagnose` lists `tokens/<slug>/<run>/messages/` and shows any message the record never mentions as "never read", while it still exists (7 days, F11).
- **F19 (Gap, resolution).** **The undelivered line.** Everything under `runs/<slug>/<run>/` — `result.json` and the stored `report.md` alike (`(*run).storeReport` writes it through `Store.PutFile`) — is writable by the job account, so no copy-paste command may be built from it. The line has three parts, and each comes from somewhere a run cannot write:
  - **The text** comes from the runner's memory (for the comment it posts on the pull request) or from the message object under `tokens/` (for `diagnose`). It is quoted with `shellword.Quote` (`internal/shellword`, the existing quoter for printed commands) and put after `--`, so a text that starts with `-` is never read as a flag.
  - **The repository** is named with `--repo <owner/name>`, so the line does not follow up a pull request of whatever checkout it is pasted in.
  - **The pull-request number** comes from the runner's memory in the posted comment. In `diagnose` it comes from the git host, as the open pull request whose head is the run's branch `fugaro/<run-id>`, never from the record. When `diagnose` cannot ask the host, it prints the text and the line without a number, and says why.

  In the posted comment, the text sits in a code fence one backtick longer than its longest run of backticks, so it cannot close its own fence. A run that opened no pull request gets no `--pr` line: the text is shown on its own, to send in a new run.
- **F20 (Gap, resolution).** **What a hostile agent can still do.** It can rewrite its own run's `result.json` (or, on a shared project job, another run's) so that `fugaro tell` reads `accepting` as absent or the run as ended, and refuses. That is a denial of the channel, of the same class as the cancel marker it can already write under `runs/`. It can also rewrite the fates the record shows, so `diagnose` labels them "as the run recorded them" and cross-checks them against the message objects while those exist. It cannot forge or reorder a message, since it cannot write under `tokens/`. It **can** suppress delivery: `SECURITY.md` says the agent runs as the same user in the same container and can stop or kill the runner's process, so the runner's in-memory position and the report it posts are inside the agent's reach. What survives a hostile agent is the message objects themselves, which `diagnose` lists (F18). The plan accepts this and says so in `SECURITY.md`.
- **F21 (Gap, resolution).** **A repository with no token read grant.** A repository root that was never re-applied lacks the job's `tokens/` read (`infra.JobTokenGrantFindings`, `internal/infra/hardening.go`), and GCS answers that refusal as it answers a missing object: the runner would say `accepting: true` and read nothing. `fugaro doctor` already reports the missing grant, but only when it can read the bucket's IAM policy: launchers and operators lack `storage.buckets.getIamPolicy`, and `doctor` then reports the check as unchecked (`tokenGrantUnchecked`, `internal/cli/doctor_bucket.go`). `fugaro tell` runs the same check: when the policy is readable and the grant is missing, it refuses with the `fugaro update --repo` fix; when the policy cannot be read, it sends and prints one line saying the grant was not checked. It never refuses for want of access to the policy.
- **F22 (Gap, resolution).** **The role check is advisory.** `fugaro tell`'s `ActionLaunch` check (F17) is the CLI's, as `cancel`'s is: IAM gives every launcher write on `tokens/`, so a launcher without the repository's role can still write a message object by hand, and the runner delivers it. That is D2940's "any launcher" at the IAM layer; the role check stops the ordinary path and says why.
- **F23 (Gap, resolution).** **A yield stops the whole process group.** `procgroup` signals the group (`internal/procgroup/procgroup_unix.go`), so a background shell or a background sub-agent the agent started dies at the yield, even at a quiet point. The resumed turn is told so in its prompt ("background tasks you started were stopped; restart any you still need"). U2 and Check 740 cover it.
- **F24 (Gap, resolution).** **Which runs accept messages.** Only a run whose recipe has a coder stage (implement or fix) writes `messages.accepting: true`. A review-only job (`internal/runner/reviewmode.go`), an artifact run, a merge-judge run, an `evaluate` recipe and a rebase-only run write `accepting: false`, and `fugaro tell` refuses them with the reason.
- **F25 (Gap, resolution).** **Forward compatibility and flags.** A message carries a `version`; the runner writes `messages.format` (the highest version it reads) and `messages.flags` (the flags it honours) beside `accepting`. `fugaro tell` writes the version the run advertises, and refuses `--now` or `--wrap-up` when the run does not list them, so a release that carries RM1 before RM4 never sends a flag the runner would treat as a plain message.

### The rules the answers make

1. **Delivery points, by call site, deny by default.** A pending message is put only into the prompt built at three call sites: a first run's implement, a follow-up's implement (fresh or resumed), and a fix — plus the resumed turn of a `--now` yield inside one of them. Stage names cannot key it: the rebase conflict stage also calls itself `"implement"` (`internal/runner/rebase.go`) and the runner has no registry of names. So messages are taken only by an explicit call at those sites, and every other stage — review, first-line review, adversarial, triage, merge judge, pick, plan, checkpoint, digest, diagnose, the rebase conflict stage, or one added later — never makes that call. Tests pin the three sites and that the rebase stage's prompt carries none.
2. **`--now` (D2945).** On seeing a `now` message during a coder stage, the runner waits for a **quiet point** in the agent's `stream-json` output: every `tool_use` id of the main thread has its `tool_result` (parallel tool calls counted by id), and no sub-agent's events (those with a `parent_tool_use_id`) are counted. **Amended after review:** an earlier draft also required that the last assistant message not end in a `tool_use`, which is almost never true mid-stage, since the message before a `tool_result` is the one that asked for the tool; with it, nearly every `--now` would have reached the forced stop. A stop at this quiet point loses only the model's in-flight reply to the last tool result, never a running tool. It then stops the agent with a **yield** (the word is chosen so it cannot be confused with the runner's existing "interrupted (execution stopped)" reason): not a failure, not a cancel, not a halt. It starts the same stage again with `--resume <session>` and the message as the prompt. After 10 minutes with no quiet point, it stops at once and says so in the record (`reason: "no quiet point in 10m"`). A yielded segment emits no result event, so its spend and tokens are taken from the gateway's stage figure (or, with no gateway, from the last usage seen), and the resumed segment's `--max-budget-usd` is what remains of the stage's, not a fresh one. The stage keeps its original deadline: a resume does not reset the stage's or the run's clock, so twenty `--now` messages cannot stretch a stage. After a forced stop (no quiet point), the session may end on an unanswered `tool_use`; if `--resume` then fails, RM4 starts the stage again in a fresh session whose prompt carries the message and the instruction to read `git log` and the working tree first, and the record says `reason: "session lost at forced stop"`. **Amended after review:** an earlier draft named `fellBackFresh` as an existing fallback; it is follow-up-only (`internal/runner/followup.go`), and a fix stage has no `ErrNoSession` recovery at all. The yield and resume go through `r.stage`'s existing in-stage resume (the one it uses for transient and exhausted errors), so each segment is charged as those attempts are and the rule against resuming a session across accounts (A7b) holds. A cancel or halt during the wait wins. A `now` message seen during a review waits for the next coder stage. The flag means "at the next quiet point", unlike `fugaro cancel --now`, which stops at once; the documents say so (RM7, RM9).
3. **`--wrap-up` (D2946).** Delivered as rule 2, with the prompt telling the agent to commit what it has, write `pr.md`, and stop. When that resumed turn ends, or after **15 minutes** of it, whichever comes first, the runner ends the coder stage as succeeded (yielding at a quiet point, or stopping at once at the bound) and the run continues to its review rounds and finalize as usual. Further fix rounds run as configured. The 15 minutes is the owner's answer to O1.
4. **The fix prompt (D2943).** When a fix stage carries messages, or a `--now` message resumes a fix, `FixPrompt`'s closing line (or the resumed turn's prompt) is replaced by one that says the findings above and the person's messages below are both the round's work, and the messages may ask for more than the findings.
5. **Undelivered (D2944).** At every ending — finalize, a halt, a cancel, an infra error (F15's sites) — the runner reads once more (F18), then records every message still pending as `undelivered`; the comment posted on the pull request quotes it with the line `fugaro run --pr N --repo <owner/name> -- '…'`, built from the runner's memory (F19), and `diagnose` builds the same line from the message objects and the git host, never from anything under `runs/`.
6. **Refused.** A message the runner reads but cannot parse, or one over the size cap, is recorded `refused` with the reason and never reaches the agent. A number past 20 is never read (F12).

## Open items

- **O1 (answered 2026-11-18, all as recommended).** The 15-minute bound on a wrap-up (rule 3), the 10-minute wait for a quiet point (rule 2), the 4 KiB and 20-message caps (F12), and 7 days of retention (F11).

## UNVERIFIED

- **U1.** Whether Claude Code 2.1.283 accepts user messages on stdin mid-run under `-p --input-format stream-json`. Not used (D2945); it would make `--now` lossless. Settled by a probe against the pinned binary; anyone can run it.
- **U2.** That a session stopped by SIGINT/SIGTERM at a quiet point resumes cleanly with `--resume` on 2.1.283, keeping the turns before it. The quiet-point rule is designed so the session file ends on a complete turn. Also unverified: how a session resumes after a forced stop that left a `tool_use` unanswered (rule 2's fallback covers a failure), and what the resumed agent makes of background tasks the yield stopped (F23). RM3's tests against `fakeclaude` prove only the runner's side; **only Check 740** against the real binary settles it.
- **U3.** That the real binary's `stream-json` events mark a quiet point as rule 2 reads it. Today `agent.ParseStream` (`internal/agent/stream.go`) decodes only `system/init` and `result`; the `tool_use` and `tool_result` events are decoded by `agent.Relay` (`internal/agent/relay.go`), so RM3 adds its own decoding. Also unverified: how the real binary splits one assistant message into events (one event per content block, or one per message), which decides when the quiet point is first visible. Settled only by Check 740.
- **U4.** That a GCS lifecycle rule with `matches_prefix = ["tokens/"]` and `matches_suffix = [".msg.json"]` selects only the message objects and never a `budget-token`. Settled by RM6's `terraform test` and Check 740's last step.
