## 1. Findings

**F1. Wrong (the issues this spec loads do not exist yet).** The spec reads as if `fugaro issue` and its shared store were there. They are a docs-only plan with three parts in open pull requests. *Consequence:* every task here depends on named troubleshoot-issue tasks (external prerequisites in the plan) and none can start before T-IS1 is on `main`.

**F2. Wrong (no record of the old version X exists).** Step 1 says update "records the old version". The project marker has no release, and the only release evidence is a per-machine file that a second machine does not have (and that `installationServiceRelease` itself calls the desired, not the applied, state). *Consequence:* D1757: update writes the installation's `{release, previous_release}` to one new operator-written object in the runs bucket (the same place and kind as `fugaro/config.yaml`).

**F3. Wrong (release notes do not list the issues a release closes).** The spec's preferred route has no source, and building one means a hand step per release that can be forgotten. *Consequence:* D1751 and D1756: the route is GitHub's issue API, read through the milestone.

**F4. Gap (the fix release is the milestone, not Y).** "Recording the version that fixed them" is ambiguous between the version just installed (Y) and the release that first shipped the fix. troubleshoot-issue D1736 compares `resolved_in` with a reporter's version to detect a regression, which needs the release that *first* contains the fix: recording Y would hide a regression from a reporter on a release between the fix and Y (they would look unfixed) and withhold their retry hint. *Consequence:* `resolved_in` is the issue's milestone title (a strict `X.Y.Z`, D1756), accepted only when it is at or below Y.

**F5. Rule (the status enum: troubleshoot-issue F25 said it stays three values; the spec adds `resolved`).** F25 kept `pending|submitted|dismissed` and a separate regression flag; this spec, later and explicit, adds `resolved`. troubleshoot-issue T-IS10 also says "a submitted record is final" (`TestSubmittedIsFinal`), and the record codec refuses an unknown value (troubleshoot-issue F23, T-IS1), so a teammate's older CLI would refuse a record it cannot decode. *Consequence:* amended: the enum is `pending|submitted|dismissed|resolved`; "final" becomes "final except the one `submitted` → `resolved` transition the resolver makes, conditioned on the record's generation"; and the value must ship in the **same release as the first CLI that reads shared records** (T-IS10), or the record's version is bumped (the hard rule on formats). The sequencing is open item O2.

**F6. Gap (the acceptance "exactly after X and up to Y" cannot hold with a missed pass).** With GitHub unreachable the spec says "retry on the next update or the next daily report"; by then X is the last update's Y, so an issue fixed at or below it would never be listed. *Consequence:* D1757: the resolver considers every `submitted` issue whose fix release is at or below the installed version; the printed summary and the report window use the recorded `(previous, version]`. The acceptance is restated in section 2 ("Acceptance as built").

**F7. Rule (the hard rule: `fugaro update` must not fail, prompt or surprise).** `CLAUDE.md`: update is the whole upgrade and works perfectly; `docs/no-prompt-policy/` forbids a wait for input. The update door has `--plan-only` (`planOnly` in `internal/cli/init.go`), `--non-interactive`, `--json` (stdout is the JSON result, progress goes to stderr), and an agent-session refusal of cloud writes. *Consequence:* the resolver pass runs after the update's own success, never in `--plan-only`, under a total time bound (constant), swallows every error into at most one stderr line, writes nothing in a coding agent's session (it prints what it found: the `agentMarker` guard of `recipes publish`, as troubleshoot-issue F10), and with `--json` adds an additive field with a new name instead of text on stdout. A project at the previous version (no installation record) updates, writes the record, and prints no window.

**F8. Gap (the unauthenticated GitHub limit).** The API's anonymous limit is 60 requests an hour per IP, shared by a whole office. The milestone route costs one request per issue (`GET /repos/dimipaun/fugaro/issues/N`: `state`, `state_reason`, `milestone.title`). Reading the repository's closed-issue pages instead does not work: measured 2026-11-08, one anonymous page of 100 is about 1.1 MB and the first five pages were all pull requests, so an issue a week older than the newest number would never be reached. *Consequence:* the pass reads **single issues**, `GET /repos/dimipaun/fugaro/issues/<n>` (about 10 KB each), at most 20 per pass, **least recently checked first** (a local cursor file in the user cache directory records when each number was last asked, so an open, transferred or deleted issue cannot starve a newer one), stops on the first transport error (offline costs one timeout) and on a 403 or 429; every request is bounded in time and size, follows no redirect, and the URL is built from the `updatecheck.Repo` constant and the integer, never from a stored value (troubleshoot-issue F28 shape check on each record's URL first). The limit itself is UNVERIFIED (U1).

**F9. Gap (not planned and duplicate need a status).** The spec says they are "updated quietly" and names no status. *Consequence:* D1752: `dismissed` plus a new field `closed_as` (`not_planned` or `duplicate`), counted as nothing fixed and printed nowhere on update. Whether the API returns `duplicate` as a `state_reason` is UNVERIFIED (U2); an unknown reason is treated as no verdict and the issue stays `submitted`.

**F10. Gap ("who hit it" needs a list the shared store may not give).** The spec lists the reporter plus the reporters of merged duplicates. troubleshoot-issue T-IS10 keeps occurrences as separate objects and `ListShared` returns issue rows. *Consequence:* the resolver reads each fixed issue's occurrences through T-IS10's store (T-RU3 adds a reporters accessor); names are shared strings printed through `internal/safetext`, de-duplicated, capped at five plus "and N more". What the `reporter` field holds (a name, a handle, an email) is troubleshoot-issue T-IS1's and UNVERIFIED here (U3): an email is printed as its local part, never whole.

**F11. Rule (troubleshoot-issue F28 versus the retry command; D1755 not the recommendation).** F28 prints only a command this machine wrote and never one refreshed from shared data, because any launcher can rewrite a shared record (F24 there). The owner answered D1755 "local if available, if not from the shared record". *Consequence:* amended: print the local command, with the rerun suggestion, when this machine has the issue file; a command from the shared record is printed only as information (owner, O4: no suggestion to rerun) and only otherwise the record's command, accepted only if it is a `fugaro` command in the CLI's command tree (the diagnose plan's D1614 check), re-redacted, printed through `safetext`, labelled as taken from the shared record, never run. In a coding agent's session only the local command is printed (the shared record's text is never put in front of an agent as an instruction). The residual risk, stated for the owner: a launcher with write access can put any command that passes the tree check in front of an admin's eyes as a suggestion. Troubleshoot-issue T-IS19 and this spec's step 6 are one feature; T-RU5 replaces T-IS19's wording with the spec's (`#0007 is fixed. The command that failed was '…'. You may want to try it again.`) and adds the note that commands may change things.

**F12. Gap (update gains a cloud write; D1735 stands for the notified flag).** troubleshoot-issue D1735 keeps T-IS19's "notified" flag local so that update makes no cloud write. Step 5 of this spec makes update write `resolved` and the installation record. *Consequence:* D1735 is untouched (the notified flag stays a local file, so a second machine may repeat a hint once); the two new writes are the resolver's and the record's, both refused in an agent session and both tolerated failing. `TestUpdateRetryMakesNoCloudWrite` stays about the retry hint alone.

**F13. Rule (the daily report is the terminal-only section; its rules stand).** troubleshoot-issue D1729: the Issues section is printed after `runs digest`, never committed, so the digest's G1/G2/G3 and the in-job writer's byte parity (`internal/runner/digest.go`) are untouched. This spec adds to the section a **Resolved** list and a nudge, and lets the report path retry a skipped pass ("retry on the next daily report"). *Consequence:* the retry runs only where the section prints (a terminal, not an agent session, not the job), and the committed file's bytes are unchanged (the existing T-IS16 test is extended).

**F14. Gap (the regression path needs nothing new beyond the matcher seeing resolved issues).** Duplicate matching at upload already flags a match whose `resolved_in` is at or below the reporter's version (troubleshoot-issue T-IS10, F25). *Consequence:* T-RU3 adds a test that a `resolved` issue is found by the fingerprint index and its regression flag and original-issue link are set; nothing reopens the GitHub issue (the spec: "so it can be reopened", by a person). A GitHub reopen of an issue already marked `resolved` is not noticed (open item O3).

**F15. Gap (milestones are a maintainer's discipline).** Closed issues here mostly carry a milestone and some do not (an issue with none was seen in the repository's closed list on 2026-11-08); the `0.20.0` milestone is still open although 0.20.x shipped; patch releases (0.20.1 to 0.20.3) have no milestone of their own. *Consequence:* an issue closed as completed with no milestone, or one whose title is not a strict `X.Y.Z` (an optional `v` is accepted), has no verdict and stays `submitted`; a milestone **later** than the real release is safe (it names a release that contains the fix), one **earlier** than the real release names a release that does not: that failure is the maintainer's, listed as open item O1 and in the release notes' known limits. The milestone's open or closed state is not read.

**F16. Rule (new trust boundaries; threat model).** (a) GitHub's response is untrusted: a size bound, a strict decode, a state and reason whitelist, a strict milestone title, redirects refused, a number that is a pull request (the response carries `pull_request`) ignored; no GitHub text (title, body, comments) is ever printed, the summary is the local record's, through `safetext`. (b) Who can lie: a maintainer sets a milestone, but **the issue's author, the teammate whose `gh` filed it, can also close it as completed**, and the repository sets milestones at triage, so an author's "works for me" close can produce a false `resolved` (open item O1; checking who closed it is new behaviour the owner decides); a launcher with write access to `issues/` can write `resolved` or a false `resolved_in` into a record (hygiene, not a boundary, troubleshoot-issue F24 and its T-IS17 entry in `SECURITY.md`): the effects are a wrong "fixed" line, a suppressed regression flag for that issue, and a command suggestion (F11); nothing else reads these fields. (c) What leaves the machine: one anonymous GET per issue number (at most 20 a pass) to a public repository, the same kind of request `updatecheck` makes; it reveals that this IP is polling that issue. (d) Agent sessions never write; the guard is the one `recipes publish` uses, a mutation check in T-RU4 and T-RU5.

**F17. Gap (the installation record and who writes it).** `fugaro/` is operator-written (`docs/design/bucket-iam.md`); `update` already publishes `fugaro/config.yaml` there. `update --repo` is itself an operator step (`docs/design/bucket-iam.md`), so the non-operator case is a launcher's config-only `fugaro update`. The update door also reaches the post-success point in modes that apply nothing (`--plan-only`, a `--non-interactive` run without `--yes`, `--forget`, `--config-only`, `--publish-config`, `--anchor`, `--repo`). *Consequence:* the record is advanced only by a run that applied the installation root or found it with no changes, with nothing failed, on the update door and not in those modes (review round 1; a test per excluded mode); a refused write is skipped silently; the writer only ever raises the release (a second admin on an older CLI never lowers it), keeps `previous_release` unchanged when the release is unchanged (a re-run keeps the window stable), and writes with a generation-matched replace (`blobx.ReplaceIf`) after a create-if-absent (`blobx.Create`). The object is `{"format":1,"release":"0.22.0","previous_release":"0.21.1"}` (`format` because `fugaro/project.json`'s `version` is an integer format number, and a field never changes meaning), decoded strictly with a JSON Schema `schemas/installed.schema.json`; an unreadable or absent record means "no window": the report omits its Resolved list, the update prints the sweep result without a window. A bad high value has no automatic recovery: an operator deletes the object and the next update recreates it (stated in the docs).

**F18. Gap (two machines resolve at once).** Two admins running update, or an update and a report, can both find an issue fixed. *Consequence:* the transition is generation-matched and idempotent: the loser re-reads, sees `resolved`, and prints it as already resolved at most once per process; no number or status goes backwards.

**F19. Gap (the retry hint reaches the reporter only on their own update).** The admin's update marks the issue `resolved` first; the reporter's own later update lists local issues whose shared `resolved_in` is at or below their installed version and not yet notified (T-IS19's rule), so the hint is not lost by the admin having marked the record. The reporter sees it only after they update; the daily report's nudge (D1754 as amended) is what tells them to.

**F20. Gap (plugin and docs).** A documented command or its output changes the plugin skill and pinned docs (`plugin/` tests; `internal/cli/docs_*_test.go`). *Consequence:* T-RU7; a one-paragraph rule in `docs/release.md` that an issue closed as completed carries the milestone of the release that ships it (pinned wording, run the Docs tests).

**Acceptance as built** (replaces the spec's Acceptance where they differ):

- Updating to Y lists every `submitted` issue whose milestone (a strict `X.Y.Z`) is at or below Y and which GitHub shows closed as completed; the ones fixed in `(previous, Y]` are the new ones, any older ones a missed pass left are listed as "also fixed" in the same summary.
- Each listed issue is marked `resolved` with `resolved_in` set to its milestone, in shared storage, so every team member sees it after their next sync.
- Update succeeds, prints nothing about issues and exits as it would have when GitHub is unreachable, when the shared store cannot be read or written, in `--plan-only`, and in a coding agent's session (which prints the findings and writes nothing).

**Resolutions that were not questions (one defensible answer).** `resolved_in` is the milestone title, not Y (F4, the owner's note). Pass bounds are constants: 20 issues a pass, 3 seconds per request, 20 seconds in all, 256 KiB per response (F7, F8). The installation record is `fugaro/installed.json` in the runs bucket (F17). Step 6 and troubleshoot-issue T-IS19 are one feature (F11). `list`, `show` and `sync` of troubleshoot-issue show a `resolved` issue with `resolved_in` and the original link, and no-number `submit` skips `resolved` (T-RU8); no new command is added.

## 3. Open tensions and open items for the owner

**All four open items were answered by the owner on 2026-11-08, after the PR was opened:** O1 rule plus a known-limits line (recommended); O2 ship `resolved` and `closed_as` with the first shared-store CLI (recommended); O3 accept (recommended); **O4 not the recommendation: rerun is suggested only for this machine's own failed commands; a command that comes from the shared record is shown as the command that failed, with no suggestion to rerun it** (so F11's residual risk is a displayed line, not a suggestion; the tree check, redaction, label and agent-session exclusion stay).

- **O1 (milestone discipline).** The route depends on every issue closed as completed carrying the milestone of the release that ships it (F15). Nothing enforces it; `docs/release.md` gets a rule (T-RU7), and a check in `scripts/release.sh` that refuses a release with a closed, milestone-less issue was not asked for and is not planned. The author-close case (F16b) is the same discipline problem. Confirm that a rule and a known-limits line are enough, or ask for a `closed_by` check.
- **O2 (release train).** `resolved` and `closed_as` must ship with the first CLI that reads the shared records (troubleshoot-issue T-IS10), or the record's version is bumped (F5). The plan puts T-RU3 before T-IS10's release; the owner chooses the train.
- **O3 (a reopened issue).** A GitHub reopen of an issue already `resolved` is not noticed; a regression upload is what surfaces it (F14). Confirm that is enough.
- **O4 (D1755 residual).** F11's residual risk: a suggested command from the shared record. The tree check is a command-and-flags check, so a shared command such as `fugaro update --forget --yes` passes it; a launcher can also point a record's URL at any completed issue and make the suggestion fire on the next update. Confirm the tree check, redaction, label and the agent-session exclusion are enough, or return to local-only.
- **Tensions:** none left. T1 and T2 were ruled (D1756, D1757); D1750/D1754 and D1751/D1753 are reconciled in those rows.
