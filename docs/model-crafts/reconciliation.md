## 0. The word: **craft**

The spec calls the four model assignments "roles", which collides with the user roles (viewer, operator, admin: `docs/roles-scopes`, #1908). On 2026-11-07 the owner chose **craft** (his own word, not one of the four offered). This package uses *craft* for the spec's role: *coder craft, review craft (level 1), senior-review craft (level 2), security-review craft (level 3)*. `spec.md` keeps "role" because it is verbatim.

**Clash check (`git grep -iw craft` on `origin/main`, excluding this folder):** one hit, in `.agents/skills/golang-refactoring/references/safety-net.md`, unrelated English. No code identifier, doc term or website word is "craft". **A second clash the spec's word would have had and *craft* avoids:** the tree already has a code identifier `config.Role` (`RoleCoder`, `RoleReviewer`) and the struct `config.ModelRoles` (`coder`, `reviewer`, `background`) in `internal/config/config.go`, so even "role" for a model assignment is taken inside the tree (F2).

## 2. Findings

**F1 — Exists (most of it).** Credentials, per-stage access and ordered failover exist as `claude_accounts`, `stages.<stage>.claude_account` and `claude_account_auto`. The spec reads greenfield. *Consequence:* D1621 (generalise in place). The new things are: typed credentials beyond Claude OAuth, a **pool** as a first-class named object (today an implicit, global ordered list), **round-robin**, and the **effective-craft** view.

**F2 — Gap (vocabulary).** `config.Role`, `config.ModelRoles` and the plugin/skills' "reviewer role" already mean the model of a stage. Renaming the code identifiers is a **field-meaning** question: the CLAUDE.md rule "a field never changes meaning" forbids reusing `agent.models.reviewer` for a different thing; the new keys therefore get **new names** (`craft…`) and the old keys are migrated and removed (pre-1.0, no aliases). *Consequence:* D1621's migration.

**F3 — Wrong ("any role can use any supported provider and model").** The harness is Claude Code, which speaks the Anthropic Messages API, and the gateway never rewrites bodies. A non-Anthropic model works only through an **Anthropic-compatible route** (OpenRouter today). An OpenAI API key or a Codex OAuth credential cannot drive Claude Code. *Consequence:* D1623: the credential types that ship now are OpenRouter, Anthropic key, Vertex and Claude OAuth; OpenAI key and Codex OAuth are accepted only as a documented "not yet" with a clear refusal, and need a separate design (a translating gateway or a second harness). Acceptance criterion 1 is amended to "any craft can use any supported credential type with any model that credential's route serves".

**F4 — Wrong ("secrets in Secret Manager, config refers by name" as new).** It is how accounts work (`ClaudeAccountSecret`). The new part is that **Vertex has no secret**: see F8.

**F5 — Gap (quota and failure signal).** Failover needs a per-provider "this credential is exhausted" signal: HTTP 429 (rate limit), 402 (credits), 529 (overloaded) and Anthropic's subscription-quota text for OAuth. What the gateway sees and relays is `internal/gateway`'s forward path; what `internal/credsvc`'s cascade treats as a back-off and a probe is `cascade.go` and `probe.go`. **UNVERIFIED:** the exact set of statuses and bodies each provider returns on exhaustion, and which of them the cascade already maps to "backed off". *Consequence:* MC5/MC6 begin with a table of signals per credential type, each with a hermetic fake.

**F6 — Gap (round-robin state; amended after review).** Jobs are stateless; `creds.Selector` holds **no** state of its own and several instances select at once. What `credsvc` does keep is a per-run current credential and the leases, in its Store (`internal/credsvc`, `internal/creds`). A round-robin counter therefore needs a **compare-and-set** write in that Store and a concurrency test; and because a run is **sticky on the credential it was placed on** (D154, `creds/select.go`) and account failover is **never mid-stage** (D874), round-robin can only choose **per run (at its first selection) or per stage, never per call**. *Consequence:* D1625 (amended).

**F7 — Wrong (as first written; amended after review): a pool is *not* the cascade's candidate list.** `internal/creds/select.go` selects by **tier**: tier A (OAuth subscription) before tier B (API key), the order *within* a tier does not matter, and a run keeps the credential it was placed on (D154). `TierC` (the third-party route, OpenRouter) is **reserved and never selected**, and Vertex is **no tier at all**: `credsvc` cannot serve an OpenRouter or a Vertex member. *Consequence:* (a) a pool's listed order **cannot** be the credsvc candidate order; in the credsvc path "failover" means **tier order** (OAuth before key) and listed order only breaks ties; (b) **pools whose members are OpenRouter or Vertex run on the runner path** (the gateway's per-run upstream, `internal/runner/gateway.go`), not in `credsvc`; (c) the sentence "API-key, Vertex and OpenRouter pools work at once" in D1622 is amended to: **Anthropic-key and OpenRouter/Vertex pools work at once, each on the path that can serve it** (D1634). Pools reuse the cascade's back-off and probe; they do not change its selection rule except for round-robin within a tier (F6).

**F8 — Gap / Open (Vertex and "default").** The owner's question (2026-11-07): how is Vertex specified, since it needs no key? Facts on `main`: `agent.auth` defaults to `vertex` (`config.DefaultAgentAuth`); in a run the gateway's upstream is kind `vertex` built from `ANTHROPIC_VERTEX_PROJECT_ID` and the job account's token, no secret (`internal/runner/gateway.go`); `agent.auth` is **per run**, not per stage; a per-stage account is refused under `vertex` and `cascade` (`config.CheckStageAccountMix`); a run under `vertex` **refuses `budget.mode: enforce`** (`runner.VertexBudgetRefusal`: "Vertex budgets are not supported yet"). *Consequence (D1624):* a **built-in credential named `vertex`** (type vertex, no secret, always exists, carries project and region from the project config) referenced like any credential and usable as a pool's last fallback; and **"default" is a separate concept**: the project's fallback credential for an unset craft, which is `vertex` today, so a later change of the default never silently changes what `vertex` means. A pool member of type vertex makes the pool **un-enforceable** under budget enforce (D1626's rule).

**F9 — Gap (budget and leases).** A pool is a set of credentials with different cost structures (subscription: no per-token money; API key: dollars; Vertex: no budget enforcement). The budget lease (`internal/budget`, gateway lease/settle) is per call. *Consequence:* a pool's cost accounting is by the credential that served the call; a subscription credential records tokens at the metered price for observation, as OAuth runs do today. (**UNVERIFIED** in detail: how OAuth runs are priced in the record.)

**F10 — Rule (data egress).** Every credential serves a provider that receives the repository's code. `allow_data_to` lists the repositories a provider may be given (`internal/config/claims.go`, `runner.ProvidersEnv`) and the bmb account's list names only the repositories it may serve. *Consequence:* **allow_data_to is a property of each pool member, checked per member**; a pool is admitted for a repository only if every member admits it, or the non-admitting member is skipped and recorded (D1627).

**F11 — Rule (the dormant subscription switch).** The owner ruled earlier that ordered account failover stays dormant until the provider's terms allow one project to spread across several subscriptions (D875, `claude_account_auto`). D1622 keeps that: a pool of **two or more** Claude OAuth subscription credentials is inert until the owner turns on the same switch. A pool mixing one subscription with API keys: D1626.

**F12 — Rule (the layering; amended after review).** Project, repository and local layers merge with only tightening winning (`internal/policy`). For credentials and pools, *tighter* is: a repository may **select** among the credentials and pools the project allows and may **narrow** a pool. **Defined (amended after review):** *narrow* = a subsequence of the project's member list (members dropped, the relative order kept); a repository may **never** add a member, reorder, or change the strategy to a looser one. The direction of a strategy change: **failover (pinned order) is tighter than round-robin** (round-robin spreads spend and code egress across members), so a repository may keep or choose failover and may not choose round-robin when the project's pool is failover; the project layer may do either. It may never introduce a credential. Credentials and pools are created at the project/local layer only, because a secret reference is a spending and data-egress grant. (D1628.)

**F13 — Rule (fixed stage names).** The owner's ruling of 2026-11-02 (F1, recorded in his rulings of that date) fixed the stage names; a craft is a *mapping from stages to model+access*, not a new stage list: coder = `implement`, `fix`; review craft = `review_first`; senior = `review`; security = `adversarial`. **UNVERIFIED in this checkout:** the ruling's own file is in the owner's notes, not under `docs/`; the stage names themselves are in `internal/recipe` and `config.StageRole`.

**F14 — Gap (security review "optional" and level 3).** Today level 3 needs `stages.adversarial.claude_account: bmb` in the owner's local config and `--review-levels` (the owner's rule: security review is asked in the run). Under the spec the security-review craft inherits the senior's model and access when turned on without settings. The *switch* (level 3 on) stays the review levels' business (`internal/rigor`, `internal/recipe`); the craft only decides *model and access* when on. *Consequence:* no craft key turns level 3 on.

**F15 — Gap (who may change, and the apply steps).** A credential or pool change needs the project policy published and the job image or environment updated; per the composite-commands plan (#1907) these are named follow-up steps run by the command, and per the roles plan (#1908) only an admin of the scope may change them. A credential-**add** takes a secret value: the value entry stays a terminal (or env) input under the no-prompt plan (#1906 D1540). Audit: the managed gate's `AuditRecord` records the change; the run record gains an additive **`craft_credentials`** (stage → credential name served) beside `stage_accounts`, which keeps its meaning (CLAUDE.md "a field never changes meaning"). (D1629.)

**F16 — Gap (the effective-craft command; amended after review).** A read that shows, per craft, the model, the credential or pool, and for each setting its source (project, repository, local, or inherited from which craft) and whether the pool is inert. Console reads go through an exact-argv fence: `consoleReadPaths` in `internal/cli/project.go` is held equal to **`docs/design/desktop-console.md` §5.1's allow-list table** by a Go test (not to `spawn.ts`), so a new read needs a fence row and the test, in the same PR as the command. `--json` is a new document (versioned from the start).

**F17 — Gap (migration; amended after review).** Existing installations hold: `claude_accounts` (+ `default_claude_account`, `stages.<stage>.claude_account`, `claude_account_auto`), `agent.models.{coder,reviewer,background}`, `agent.auth`, route `secret`s, an Anthropic key secret, **and the committed/other keys the first draft omitted: `agent.oauth_token` (`config.Agent.OAuthToken`, the workflow's named account), `verifier_accounts` and `review_floor`** (both barred from the shared file by `sharedForbidden` in `internal/cli/sharedcfg.go`). Removing or renaming a key in a **JSON document a reader outside the binary consumes** (`models ls --json`, the policy node, the run record) **bumps that format's version** (CLAUDE.md). `fugaro update` converges them to credentials, pools and craft keys in place, with a test that an installation at the previous version converges and that a run before and after resolves the same model and credential. The spec's "Map the current behaviour: Coder = DeepSeek through OpenRouter, Senior review = Opus through Claude OAuth" describes **one** installation (this one's), not the general case; the migration must be derived from each installation's own keys, never from that example.

**F18 — Gap (diagnose).** The diagnose-agent plan (#1909, D1601) chooses credentials with a different order (the user's own first, the project's as a fallback). The craft model supplies *names and types*; the *selection order for diagnose* is that plan's decision, and a diagnose never changes a craft. No task here owns it.

**F19 — Gap (`background`).** `agent.models.background` (Claude Code's small background requests) is a model setting the spec has no craft for. It stays a model key under the coder craft's access; D1630.

**F20 — Missing (credential exfiltration through a pool; added after review).** Runner-path failover means every member's secret is in the **job's environment**, which the coding agent can read (SECURITY.md); and `gateway.go` never retries a call. *Consequence:* a **global constraint**: **a job receives only the secrets of the crafts it runs**; cross-secret failover happens **at a stage boundary** (the next stage's secret is re-fetched) or **inside `credsvc`**, never by putting the whole pool in one job's environment; and **a review-class credential never lands in a coder job**. (D1635.)

**F21 — Missing (review-class scope; added after review).** `internal/credsvc/cascade.go` `reviewCandidates`: "a review caller's list must never contain an entry the cascade could fall to", and D874's second rule. *Consequence:* the senior-review and security-review craft pools, and a repository's selection among them, keep that rule: a review craft's pool may only hold review-class credentials, pinned by `TestReviewCraftPoolOnlyReviewClass`.

**F22 — Missing (the D875 switch has a successor; added after review).** MC1/MC4 remove `claude_account_auto`, but D1622 depends on it. It is a **sensitive direction**: today it asks for the typed project name and is refused in a coding agent's session even with `--yes` (the reviewer cites D1107 and `docs/accounts-add` spec §11.4; **UNVERIFIED here** — the number D1107 was not found under `docs/`). *Consequence:* a named successor, a **project-level pool flag `subscription_spread`** (default off), keeps those refusals and pins them; every **write** (`accounts pool add/rm`, a strategy change, the flag) refuses under `agentMarker` as `accounts_add.go` does; D1622's inert rule is pinned **on the credsvc path too**, not only the runner (MC6). Tension with the no-prompt plan (#1906): the typed-name confirmation is removed there, so the refusal becomes an owner-session-only refusal in the D1542 style (T4). (D1636.)

**F23 — Missing (model ID versus pool member; added after review).** A craft names **one** model string, but routes claim models and are resolved **once per run** (`config.RoutingClaudeFor`), and Vertex and OpenRouter model IDs differ for the same model. *Consequence:* D1637: a pool is **admitted only if every member serves the model ID as written** (checked at config time); no per-member model mapping.

**F24 — Missing (credential-mixing rules; added after review).** `config.CheckStageAccountMix`, `agent.auth` per run, `docs/design/mixed-credentials.md` (Path A/B/C) and credsvc's fallback (auto versus oauth-only, D152 as the reviewer cites it) already govern what may mix. *Consequence (states what is retired or generalised):* `agent.auth` stays **per run** and picks the path (vertex, api-key, oauth, cascade); pools **generalise the account selection under `oauth` and `cascade`**; `CheckStageAccountMix` is generalised to refuse a pool the run's `agent.auth` cannot serve; the oauth-only-versus-auto fallback becomes a **pool property** (`fallback: none|api-key`); the mixed-credentials design's Path B (OAuth for the senior reviewer only) stays the shape a mixed pool builds on.

**F25 — Missing (which "project layer"; added after review).** D1628's "project layer" means the **owner-written project policy node** (`projectpolicy`), **never the runs-bucket shared file**, which `sharedForbidden` bars from carrying account keys.
