Its four inputs are 0.24.0's own `### Known limits` ([docs/releases/v0.24.0.md](../releases/v0.24.0.md)), read against the code each names:

1. **A craft's model half is written, validated and shown, and it is not yet what a run runs.** `fugaro craft ls` prints the model each craft resolves to, while a run still takes its models from `agent.models` and `agent.levels`; a craft's access is the half a run resolves today.
2. **A run is served from the published node's own craft blocks.** No command of 0.24.0 writes the crafts, credentials and pools from the owner's config into the published policy, so what a pool changes today is `fugaro craft ls` and the launch, rather than which member serves a call.
3. **A pool's members are served by the two halves of a run, and one pool cannot cross them.** An OpenRouter or Vertex member is served by the run's own gateway and a Claude OAuth or Anthropic-key member by the credentials service, so a pool that mixes the two can fail over only at a stage boundary.
4. **A credential whose type authenticates with a key is not declarable by a command yet.** `fugaro accounts add --type` serves `claude-oauth`; an OpenRouter or Anthropic-key credential is written in the config's own `credentials:` block.

The order the four are closed in is the owner's and it is the plan's slices: **A** the model half (MC11–MC17), **B** the publish (MC18–MC19), **C** the crossing (MC20–MC21), **D** the key credentials (MC22–MC25), and **E** the one task that makes the whole activation observable and safe (MC26, OWNER-RUN). ## Conventions

`CLAUDE.md` and [implementation-plan.md](implementation-plan.md)'s Conventions, every one of which this plan inherits: `.claude/rules/credentials-service.md` and `SECURITY.md` for anything touching `internal/creds`, `internal/credsvc` and the gateway (security-sensitive: independent review before merging); hermetic tests (`internal/gcpfake`, `internal/testutil`, `t.TempDir()`); **no secret-shaped literal** in tests, docs or fixtures; config and wire formats decode strictly and have JSON Schemas in `schemas/`; **a field never changes meaning** (new names, old keys migrated and removed, no aliases: pre-1.0); docs are tested (`go test ./internal/cli -run Docs`); plugin skills carry byte budgets and `plugin/skills_lint_test.go` checks every command and flag a skill names; `### For operators` is "run `fugaro update`" plus what it will ask (HARD RULE); no agent runs a live cloud action; in-run level 3 for a security task is asked with `fugaro run --review-levels`.

Two of that plan's conventions are load-bearing here and are restated rather than pointed at, because a reader of this file has to see them:

- **A config the release the owner already runs starts refusing is a broken installation** (the HARD RULE, CLAUDE.md). Every refusal this plan adds — MC20's cross-path pool above all — ships its convergence inside `fugaro update` **in the same release**, with a test that an installation at the previous version converges.
- **`fugaro update` is safe while runs are in flight, always** ([docs/design/update-in-flight.md](../design/update-in-flight.md)). No step here asks a run to finish first, refuses a policy write over one, or rewrites what one holds; the steps that can still reach one are named in the one line the update prints (`inFlightSteps`, `internal/cli/update_in_flight.go`) rather than denied, and `TestUpdateLeavesARunInFlightRunning` pins it.

**Boundaries.** *Always:* tests before a commit, `gofmt`/`go vet` clean, the folder's targeted test commands, a red step run and reported. *Ask first:* a schema change (MC16 owns the one here), a new dependency (none is proposed: every half reuses a package that exists), a change to `.github/workflows/` (none is proposed; an agent run may not make one at all). *Never:* a secret value in an argument, a flag or the environment; a live cloud action by an agent; editing `spec.md` (verbatim, the owner's); a widening write in a coding agent's session.

### MC11 — the model-half contract (contract)
- **Acceptance:** one file states, and one stub implements, the answer three later tasks build against: the rungs a stage's model is chosen by, in order; the craft each stage's model belongs to; where the resolved model is written so that every consumer of it agrees; and the verdict a craft's model carries when it cannot be served.
- **Files:** `internal/craft/model.go` (new: the stub and the doc comment), `internal/craft/model_test.go` (new), `docs/model-crafts/activation-contract.md` (new: the short contract document, what each side may rely on and what it may not).
- **Interfaces:** consumes `craft.Layer`, `craft.Resolve`, `craft.Effective` and `config.CraftNames`, `config.CraftParent`, `config.StageRole`. **F13's stage-to-craft map is part of the contract (D1663), and it exists twice today** — `stageCraft` in `internal/runner/routing.go` and `stageCraft` again in `internal/cli/init_craft_migrate.go`, written from the same sentence and kept in step by hand — so the contract names one copy (the runner's, which also has `stageLevel` and `stageRole` beside it) and the other task that needs it calls that one: CLAUDE.md's "after parallel runs create several files, do a final pass to remove duplicates" is the rule MC12 and MC21 both read it by. Produces `craft.ModelFor(stage string) (string, string)` (the model ID and the craft it came from) and `craft.ModelRungs()` — the rung list of **D1660**, most specific first: **the task's model grade**, **a review level's own model** (`agent.levels.l1/l2/l3.model`), **the craft's model**, **`agent.models.<role>`** (the role the stage's slot pins, `config.StageRole`), **`agent.model`**. The stub answers **the craft rung alone** — the craft's own resolved model and the craft each stage belongs to — and does nothing else: the two rungs above it (a task's grade, a level's own model) and the two below it (`agent.models.<role>`, `agent.model`) are the run's and not a package's, and half a rung list implemented in a stub is the drift the contract exists to prevent. **Where the write lands:** the contract fixes it as a bootstrap pass that writes each craft's resolved model into the slot the run already reads — the coder craft into `Agent.Models.Coder`, the review craft into `Agent.Levels.L1.Model` where the level wrote none, the senior-review craft into `Agent.Models.Reviewer` (and into `Agent.Levels.L2.Model` where the level wrote none), the security-review craft into `Agent.Levels.L3.Model` where the level wrote none. Two reasons, and they are why this half is a write and not a fifth rung read where the model is answered: **the write is `applyGrade`'s own pattern** (`a.Models.Coder = grade.Model`, `internal/runner/routing.go`), so the run already has one way for a narrower statement to reach every consumer; and **the consumers of a stage's model are more than `stageModel`** — `Agent.PinnedModels()` is what the gateway's allow-list pins, `config.CheckAllowed`/`CheckPins` are what the launch and `validate` judge, `cost.go` prices the stage row, and the record's `StageTiming.Model` reports it — so a fifth rung read in `stageModel` alone would leave the gateway refusing a model the run was told to run (D1661's own reason). The senior-review craft's model lands on the reviewer slot because L1's review does not: `reviewStages` gives level 1 the coder's slot and level 2 the reviewer's, and the security-review craft, which follows the senior review (`config.CraftParent`), resolves to the senior's model when it names none — so the write is a no-op for the craft that inherits and a real one for the craft that does not.
- **Tests:** `TestModelForAnswersTheCraftRung`, `TestTheRungOrderIsTheContracts`, `TestAnUnknownStageAnswersNoCraft`. **Command:** `go test ./internal/craft -run Model -count=1`.
- **Depends on:** nothing. A contract written from the tree's own types leaves nobody waiting through it. **Red step:** `TestModelForAnswersTheCraftRung` fails on the stub, which answers `""` for a craft whose model a layer set. **Tier:** standard. Its strictest consumer is MC12, which is standard, so the contract's rigor is the consumer's and not higher. **Commit:** `craft: the model half's contract, the rungs and the write (MC11)`.

## Rollout order

**Which half may ship alone, and which two may not (D1672).** This is a finding of this plan and not a slicing convenience: each of these four is a *release* decision, and the folder's own releases carry their migrations with them (the HARD RULE).

- **The model half (slice A) ships alone, first.** It reads the project layer, which `fugaro update` already publishes, and nothing else has to move with it. Its only installation-visible change is that a craft key the owner may already have written finally reaches a run — and a key nobody wrote changes nothing (D1662, MC17's converge test).
- **The crossing (slice C) ships alone.** It is a validation tightening: a pool that named members of both halves is refused by one sentence, and MC21 converges the pools the owner already has. It must ship **no later than the publish**, because the publish is what makes a pool's list the service's own input — a published cross-path pool is a pool whose listed order the owner reads one way and the service reads another.
- **The publish (slice B) and the key credentials (slice D) ship together.** A key credential is *declarable* on its own, but whether the service serves it is not the owner's to see: `poolOffering` narrows the bundle to the union of the **published** crafts' accesses and does not narrow at all when the node writes no crafts block — so a credential declared in the config and named by a craft is served, or not, depending on a node the owner's config does not show. That is exactly the state the known limit describes, and shipping the declarable credential without the publish would make it permanent: **half 4 is released with half 2 or not at all.** Half 2 alone is fine and may go first.
- **The order the owner gave is therefore also the release order, with one pairing:** A, then C, then **B+D** (B may precede D), then E's checks. Slice E is not a release of its own: each check is written by the release it measures — 620 with A, 622 with C, 621 and 623 with B+D, and 624 with the last of them, since it measures the convergence of all four at once — and the register's row carries the number free at that merge.
