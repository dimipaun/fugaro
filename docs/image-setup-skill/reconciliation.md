## 2. Findings

- **F1 Rule: the spec reverses a recorded ruling.** [docs/repo-image-removal/](../repo-image-removal/README.md) D1190–D1208 (owner 2026-11-04) remove the per-repo derived image, its check job and its refusals. The spec says "disabled, not removed". Resolved by **D1900**: the spec wins; R2–R10 are parked (see F2).
- **F2 Exists/Wrong: nothing today "disables" without removing.** `MayApply` returns false the moment `image:` or `dockerfile:` is set, so a repo with those keys still gets a per-repo image: the opposite of "always returns the project image". The disabled state needs a new resolver, not a flag on the old path.
- **F3 Gap: the "one function" does not exist.** The choice is spread over `catalog.Applies`, `catalogJobImage` and an `if` chain around `gcp.ImageName`. The plan adds one `jobImage`-style function that the `if` chain, the doctor checks and the image commands all call.
- **F4 Gap: "ignores any repo-level config" collides with a repo's `image: <name>`.** `image: <name>` and `needs:` are *catalog references*, not repo-level images, and the shipped path honours them. **Open tension T1** below.
- **F5 Gap: there is no repo-to-image map at project level.** Mapping lives in each repo's `fugaro.yaml`. **D1906** adds `image_map` to the published policy node (`internal/projectpolicy/policy.go`, beside `ImageCatalog`). An unknown top-level key is listed in `Policy.UnknownKeys`: an older **runner** logs it and goes on, but an older **CLI** refuses `fugaro run` (`launch_budget.go`) and publish (`project_cmd.go`). So once `image_map` or `bake_repos` is published, a teammate on an older CLI cannot launch until they upgrade; the release's operators line says to upgrade the CLI before `update` publishes them. A policy field also needs a `internal/localcfg` field (the published node derives from it, and its layering against the published value is stated by IS5), an `internal/settings` registry row and write-allowlist row, a command that writes it, and the managed-gate and agent-session rows for that write; `sharedcfg.go`'s `sharedForbidden` is a denylist the new keys must be checked against.
- **F6 Wrong: "Baked repos" is not a catalog setting.** The catalog has no bake list; `checkout: baked` is the *per-repo derived image* that holds a clone, and removal D1208 makes a catalog entry's own Dockerfile do the clone. **D1901**: a project policy boolean (default true) says the skill's generated Dockerfiles clone each mapped repo.
- **F7 Exists: the job logic "repo in image → use it; else clone" is already the runner's.** `internal/runner/runner.go` `openCheckout` opens a checkout already in `WorkDir` (`gitops.Open`), else `OpenOrClone` or `CloneBlobless`. The real gaps are two: a **shared** image cannot hold N repos at one `WorkDir`, and nothing checks that an opened baked checkout's origin is the job's own repository, so a project image could run repo A's task on repo B's source and push (security). IS8 fixes both.
- **F8 Wrong: "Remove the other harnesses".** The base image carries **seven** non-Claude harnesses, all listed with tier `harness` in `images/base/tools.tsv`: `codex`, `gemini`, `pi`, `qwen`, `opencode`, `goose`, `crush` (three through `images/base/harnesses/`, four through the Dockerfile's binary step with ARG pins), and the smoke contract lists them (`internal/image/tools.go`, `selftest.go`). Claude Code stays. `graphify` is also tier `harness` but is a Fugaro-side tool; it stays (UNVERIFIED, U5). Stated, not asked.
- **F9 Rule: "recipe" is already a Fugaro word.** `docs/recipes.md` is the task-loop recipe (`implement`, `review`, `fix`). The spec's "recipe" (the contract) is called **the runtime contract** everywhere in this folder; no document here uses "recipe" for it.
- **F10 Gap: validation covers builds, not prebuilt entries.** The smoke runs after a catalog **build**; a `source: image` entry is never built (`image_build_catalog.go` passes it over), so nothing validates it. (`NoSmoke` in `internal/backend/gcp/catalog.go` is the separate `--no-smoke` path.) The plan adds a Cloud Build smoke-only step for prebuilt entries.
- **F11 Rule: the spec's "never local" conflicts with the setup skill.** `plugin/skills/setup` validates with a local image build. The new skill uses only the cloud catalog build (`fugaro image build`), never the local one; the architecture rule is stated in the skill.
- **F12 Exists/Gap: the base already ships a services starter.** `images/common/fugaro-services` (`start|stop|status` for postgres, redis and the firebase emulator, selected by `FUGARO_SERVICES`) is part of the runtime contract, and a repo's `test:` already calls it. What is missing is the *project-level* declaration: which services an image provides and the repo's switch variable. **D1904** therefore builds on that script and its service names: the entry key feeds `FUGARO_SERVICES` through the launch env, the workflow's `env:` carries the switch, and a runner-side start is added only if the script is not already called before tests (U7).
- **F13 Gap: survey at 50+ repos needs file reads, not clones.** `gitprov.ContentsReader` exists (GitHub and Bitbucket); no command lists a project's repos with signals. **D1902**: a read-only `fugaro image survey` command.
- **F14 Exists: build-time secrets are done.** No plan work, except the generated Dockerfiles must use `RUN --mount=type=secret` and a skill test pins that no `ARG`/`COPY` carries a token.
- **F15 Rule: HARD RULE on `fugaro update`.** Changing the base image, adding policy fields and rebuilding baked images must all converge through `fugaro update` with a test that an installation at the previous version converges, and the run-in-flight safety stays (`TestUpdateLeavesARunInFlightRunning`). Every task touching policy or images carries that test.
- **F16 Gap: reruns need prior decisions to compare to.** They are the catalog (`image_catalog`), the map (`image_map`) and the bake boolean: all published and operator-owned. The skill reads them through the existing policy read and proposes only differences.
- **F17 Open: Cloud Batch for repos that truly need Docker.** Batch is not enabled (see §1), so today such a repo is refused on Cloud Run; the skill says so and flags the repo rather than promising VMs; the spec's "60–70 s vs 10 s, double cost" figures are the owner's and are used in skill text only as "about", UNVERIFIED (U2).

- **F18 Rule (security): baking N repos needs a cross-repo credential and makes every job on the image able to read every baked repo.** A catalog build's `credential` step holds one repository's `GIT_TOKEN` and runs as that entry's repository build account (`catalogcheck.tf`). **O3** below is the owner's.
- **F19 Rule: the resolver refuses where the old path fell back.** With no catalog default and repo keys ignored, an installation with no catalog would refuse on its next `update --repo` (today `Applies` falls back to the per-repo image). The spec says "no backwards compatibility"; CLAUDE.md's HARD RULE says `update` converges with no other step. **O4** below.
- **F20 Gap: an entry key breaks older readers.** The `image_catalog` block decodes strictly (`catalogEntryMembers`, `DisallowUnknownFields` in `policy.go`), so an entry `services` key makes an older runner or CLI fail to read the whole policy. IS9 lists the member and ships a converge test.
- **F21 Gap: the resolver's other callers.** `run.go` (the launcher's D1149 judgment), `doctor_layer.go` and `image_catalog.go` also call the selection; all must use the one function or they disagree with deploy about `image_map`.
- **F22 Rule (security): survey text is untrusted.** Versions, FROM lines and CI text enter the agent's context; they are pattern-validated and printed through `pluginwire.Printable`. `ContentsReader` reads fixed paths and lists nothing, so the survey reads a fixed signal list, and the repo list comes from the project's configured repositories (UNVERIFIED: the exact field, U6). The CLI opener uses the process environment's token (`api.go` `OpenProvider`), not the project credential service.

## 4. Open tensions and open items for the owner

T1, O3 and O4 were answered 2026-11-09 (each bullet below carries the answer); **O1 and O2 are still open**.

- **T1 (F4, D1900 against D1906).** D1900 says the resolver "ignores any repo-level config"; D1906's recommended text had a repo's own `image:` reference still win over the map. Choices: **(a)** the map is authoritative and a repo's `image: <name>`/`needs:` is also ignored with a warning, which keeps the spec literal and makes every existing catalog-referencing repo change behaviour; **(b)** only the repo-level *definition* keys (`image:` block, `dockerfile:`, `rebuild:`) are ignored, a catalog reference still beats the map, which keeps shipped repos working and makes "always the project image" true only for repos with no reference. The plan is written for **(b)** as the narrower change and **(a)** is a one-line change in IS1. **2026-11-09: reading (b).** Only a repository's *definition* keys (`image:` block, `dockerfile:`, `rebuild:`) are ignored, and a catalog reference still beats the map, so a shipped repository that pins an entry keeps running that entry's image and the project image reaches the repositories that name none.
- **O1.** Bake default yes means every `fugaro update` rebuilds all baked entries; the rebuild is behind its own confirmation (CLAUDE.md HARD RULE). Is a nightly baked rebuild (D1148's schedule) enough, or should `update` also rebuild? The plan does the schedule only.
- **O3 (F18).** Baking N repos into shared images: **(a)** a new cross-repo build credential and the new boundary that every job on a baked image can read every baked repo, **(b)** bake only the repos that share the image's own repository grant (typically none for a shared image), clone the rest at job start. The plan defers the bake step IS8b until the owner rules; **(b) is the recommendation**, and with it D1901's default yes means "bake what the build account may read". **2026-11-09: reading (b).** No new cross-repo credential: a catalog build bakes the checkout of the one repository whose build account it runs as, and every other repository the entry serves clones at job start, exactly as F7's logic already does. Two consequences are settled with the reading. First, D1901's default yes means "bake what the build account may read", which for a shared entry is normally the one repository that is the entry's own — a build says which repositories clone at start rather than leaving "bake your repos" to read like all of them. Second, F7's "a shared image cannot hold N repos at one `WorkDir`" no longer arises from the bake: since (b) bakes one repository per build, a definition bakes at the **per-slug** path IS8 names (`/work/baked/<slug>`) and never at `/work/repo`, so a job reads its own checkout there whatever the entry's own Dockerfile left behind (IS8's reader is what makes that path the one jobs use).
  **How the implemented bake reads (b)** (review of 2026-11-10, IS8b): a build bakes only the repository it runs for, and only when that repository runs the entry being built — a catalog reference in its own workflow beats the map, and the map answers for a repository that names none — and the switch `bake_repos` is not written false. An absent switch and a written true decide the same way, because that is what the switch means everywhere else it is read (`projectpolicy.Policy.BakesRepos`, `localcfg.BakeReposEffective`): one published node must not tell a settings reader "on" and a build "nothing is baked". Neither answer decides where a bake may land: (b) bakes the repositories that share the image's own repository grant, and for a shared image that is none of the others — so an entry the project's map puts another repository on is composed into by nobody, `bake_repos: true` included, and that is F18 answered rather than delegated. The map is also the build's only evidence about any repository but the checkout's own (one credential, one checkout, no second repository's config: (b)), so a repository the map does not put on the entry — one that runs it by its own workflow's reference — is refused as well: the build cannot name the repositories that pin the entry too, and the list it would print would be a guess. Which repository a rebuild runs as is resolved the same way a build resolves it — an entry with no repository of its own is assigned to the repository the project's `image_map` puts it on (`internal/infra` `catalogCheckRepos`) — and a definition whose marker names another repository is refused by the nightly check before a build is submitted, so a rebuild never runs as an account that does not reach the checkout the definition bakes.
- **O4 (F19).** An installation with no catalog default: **(a)** the resolver refuses with a message naming the skill (the spec's literal "no backwards compatibility"), **(b)** falls back to the per-repo image until a catalog default exists, so `update` converges. The plan is written for **(b)** to honour the HARD RULE; it contradicts "always the project image" only until a default exists. **2026-11-09: reading (b).** With no catalog default the resolver keeps the per-repo image, so an installation converges on `fugaro update` alone and never faces a project with no image to run.
- **O2.** What the owner's 50+-repo survey does for a repo with no readable lockfile (private submodule, monorepo): the plan maps it to the default image and flags it; confirm.
