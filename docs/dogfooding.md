# Dogfooding: Fugaro on its own repository

The repository's root `fugaro.yaml` points a Fugaro installation at this repository: project `fugaro`, one workflow `go` on the `go` base image. This page is the guide to running Fugaro on its own code, as it was done on the GCP project `fugaro-dev` from 2026-10-04: what to set up, what a run is and is not trusted with, what stays out of runs, and what the first weeks taught. The step-by-step behaviour of `fugaro setup` is in [gcp-setup.md](gcp-setup.md); this page says what is different here.

**Self-hosted runs and the one Fugaro base.** Since 0.7.0 this repository's own `fugaro.yaml` has no `base:` line (the `go` workflow runs on the one Fugaro base, with its runtimes from `mise.toml`), so `fugaro run --workflow go "<task>"` below works with a 0.7.0 CLI once `fugaro image refresh` has rebuilt the workflow's image on `fugaro-base` (docs/base-image-migration.md). Until that refresh has run, the old 0.6 job image refuses the new `fugaro.yaml` and a run fails at its first stage.

**What is recorded and what is not.** The layout, the first runs and the lessons below were observed on `fugaro-dev` by its maintainer; they are not a test. The simple setup this page leads with (`fugaro setup`, `/fugaro:setup`, `fugaro update`) is merged but has **not** been run from a clean project: the first install on `fugaro-dev` used the manual steps and hit the frictions that M11 removes. That clean run is the milestone's acceptance and is written up as Check 27 in [gcp-live-checklist.md](gcp-live-checklist.md), **NOT RUN**.

## The layout

- **One project holds everything.** The installation (runs bucket, registries, jobs, secrets, scheduler) and the Firebase budget backend are in the same GCP and Firebase project, `fugaro-dev`, Fugaro project name `fugaro` (the "same-project layout", design `m9-budget-and-dashboard.md` §6.0). The budget runs in `observe` mode; Firestore history is on, its location (`us-east5`) permanent.
- **Remove `roles/editor` from the default service accounts.** In this layout anything that runs as the default Compute Engine, Cloud Build or App Engine account and holds `roles/editor` can reach the budget backend, so on `fugaro-dev` the user removed it from the default Compute account by hand. `fugaro doctor` and `fugaro setup` flag it (`default-service-accounts`), and the fix is removing the role from that account.
- **The GitHub App** is created by the user in a browser and installed on `dimipaun/fugaro` ([git-providers.md](git-providers.md)). Its name is unique across GitHub, so the bare `Fugaro` was taken and the maintainer picked another; its ID is not a secret. It has Contents, Pull requests, Issues and Metadata, and **never the Workflows permission** (below).
- **The secrets are the user's.** The App's private key (`github-app-key`) and the model credential (`openrouter-api-key`, since `agent.auth` is `api-key` and both the coder and the in-loop reviewer are DeepSeek models through OpenRouter, `deepseek/deepseek-v4.1-flash` and `deepseek/deepseek-v4-pro`) are entered by the user in their own terminal, at the `secrets` stage's hidden prompts or with `fugaro secrets set`. **Both are stored once for the project** (project scope is the default: no flag, [design/project-centric.md](design/project-centric.md) §6.3), but being stored once is not the same as reaching every job: each name's reach is its own, and `openrouter-api-key`'s is the repositories its provider's `allow_data_to` lists (`edgeappinc/fugarosandbox` and `dimipaun/fugaro`, [multi-model.md](multi-model.md) §3) — not the third one. `github-app-key` is a reserved name, so it reaches every enrolled repository unless a `project_secrets` entry says otherwise ([design/project-secrets.md](design/project-secrets.md) §5). The enrolment list the reach is measured against is project `fugaro`'s three repositories, `dimipaun/fugaro`, `edgeappinc/fugarosandbox` and `dimipaun/fugarosandbox` ([design/project-centric.md](design/project-centric.md) §4.4). A repository that stores its own copy takes precedence over the project's, which `fugaro doctor` lists per name and warns about when it happens. No `anthropic-api-key` is asked for: with `api-key` the key is prompted for only when a pin goes direct to Anthropic, and every pin here is a provider's. No agent sees a value; `fugaro setup` refuses to prompt through one.
- **Reviewers.** `git.pr.reviewers` and `labels` in `fugaro.yaml` are empty, with a `TODO(user)` for a GitHub login; changing them is a normal PR to `main`.

## Setup

From a fresh clone of the real remote, as the person who owns the GCP project, in your own terminal (typed confirmations need a real one):

1. **Create the project and link billing**: the first run of `fugaro setup` creates a fresh project (`--link-billing` links billing; each its own typed confirmation; neither is covered by `--yes`; not run against a real organization yet, Check 27). Enable the Cloud Billing API on your credentials' quota project (`fugaro doctor` prints the line).
2. **`fugaro setup --firebase-project <gcp-project-id> --budget-mode observe`.** The first run asks, once, for the project's name (`fugaro`), the GCP project's ID and the region (`us-east5`). It converges the installation, the Firebase backend, the images, the history job, then the secrets (hidden prompts, in the checkout), the plugin wiring and, once `fugaro.yaml` is on the default branch, the repository. Each stage asks its own confirmation; a stage that needs you stops with one line, and a rerun resumes.
3. **The images.** `fugaro-base` and `fugaro-history` are published only from the first release tag that has them: 0.7.0 for `fugaro-base` (its build and publish jobs are in `.github/workflows/images.yml`), so a development build copies nothing and a release build before that tag has nothing to copy either. Build the base from this checkout and push it as [base-image.md](base-image.md) does (`images/build-base.sh base`), then `fugaro update --base-image <tag>`. Once a release has published it, `fugaro update --base base` pins it: the release's cosign signature is verified at its `-pinned` tag, the digest is read back through the installation's remote repository, and nothing is copied or pushed (`--expect-digest` only cross-checks the verified digest). The repository's runtimes are declared in its own `mise.toml`, not a base kind.
4. **`fugaro.yaml`.** This repository already has one. In another repository, run `/fugaro:setup` in your coding agent and merge its PR; Fugaro reads `fugaro.yaml` from the default branch.
5. **`fugaro update`** after the merge: the `repository` stage again. Step 2's `fugaro setup` enrolled the repository — `setup` is the door that enrols one, `update` converges what is enrolled — so the re-run that offers the first image build is `update`'s. The build is billable and has its own confirmation, then the job is deployed and the daily check unpaused. It asks once for the App's ID, or take `--github-app-id`.

Then `fugaro run --workflow go "<task>"`, `fugaro runs ls`, `fugaro watch`, `fugaro logs`, `fugaro diagnose`, or the plugin's `working` skill.

## What a run does, and what it doesn't

A run's verify step runs the workflow's `build` and `test` commands in the container: `go build`, `go vet`, a gofmt check, and `go test` without `-race`. It leaves out four package sets, on purpose:

- **`internal/runner` and `internal/e2e`**: about 12 and 6 minutes, and their tests need a Docker daemon or a git state the container lacks.
- **`internal/image` and `images`**: the base-image builds; their tests need Docker.

It targets about 20 minutes on 4 vCPU and 8 GiB (`timeouts.verify` is 25m). The in-run verify is a smoke check, not the gate.

**CI is the release gate, not the merge gate.** GitHub CI runs `go test -race ./...`, the docker-tests job, the Firebase rules emulator (`rules`) and the Terraform job on every push to `main`, and on demand for a branch (`gh workflow run ci --ref <branch>`); it no longer runs on pull requests and `main` has no required status checks (owner's ruling 2026-10-16: it took 7 to 8 minutes per pull request and the loop's own tests already ran). `test`, `terraform` and `rules` must be green on the commit a release is cut from (`scripts/release-gate.sh`), and a red `main` is fixed before anything else merges. A green run is not a green CI. The image has no Docker daemon (Cloud Run has none), no Java or Node (the rules emulator) and no tflint, so a run can't prove those: an agent changing `internal/runner`, `internal/image`, `images/` or the rules should say so in the PR, and you read the CI before merging. A run that ends as a failed draft only because the excluded or unrunnable parts failed can still be fine: check the PR's CI, mark it ready and merge (done for two PRs during M11). One package needs a bound of its own wherever it is run: `go test` kills any package still running after `-timeout`, which is 10 minutes per package by default and 20 in CI's `test` job, and `internal/runner`'s own suite takes about 25 minutes under `-p=2`, so it is run as `go test -race -timeout 40m ./internal/runner/...`; CI does not give that package the same bound yet — a workflow file is the owner's change (below) — so the two test steps to put in its place, and the job's own `timeout-minutes` that has to rise with them or the longer bound can never fire, are written out in `docs/pending-workflows/README.md`, `## ci.yml`. One `go test` invocation cannot do it: `-timeout` is a single value for every package it builds.

## What Fugaro can never change: `.github/workflows/*`

GitHub refuses a push from the App that creates or updates a workflow file unless the App holds the **Workflows** permission, and Fugaro's App never does, deliberately: a run able to edit CI could weaken the merge gates or reach the repository's secrets. A run that changes one anyway ends `infra_error` at finalize with its work saved but not pushed (git-providers.md, "A refused push"). Two parallel runs lost their work this way. **Rule: a task that touches `.github/` is done by a person or a local session, never by a run**, and no task text should ask for it (the agent is told not to). The same goes for `images.yml` and `release.yml`.

## Follow-ups and `followup.allow_public`

`fugaro run --pr N` continues a Fugaro PR and acts on the comments of `followup.trusted` accounts, with the workflow's secrets and the model credential in hand. On a **public** repository anyone can comment, so a follow-up is refused unless `followup.allow_public: true` is set, and even then only trusted accounts' comments are acted on. This repository is public and its `fugaro.yaml` sets both keys — `trusted: ["625256"]`, the maintainer's numeric ID, and `allow_public: true`, the owner's decision on 2026-10-04 (#111) — so a follow-up on its PRs acts on the maintainer's comments and ignores everyone else's. Widening `trusted` is a security decision: read the design's §6.1 first. The `setup` skill never sets `allow_public` without an explicit yes.

## Parallel runs and `--batch`

Each run has its own worker, branch and PR, so independent tasks run side by side: one `fugaro run` per piece, with a shared `--batch <name>` and a `--run-id` of its own so a repeated launch cannot start a piece twice; `fugaro runs ls --batch <name>` lists them and `--watch` follows them. What worked:

- **One owner per file.** Two runs that edit the same file give conflicting PRs. Settle shared names and interfaces first and put them in every task's text.
- **Merge in dependency order**, and launch a dependent task only after its base has merged.
- **Check headroom first**: `fugaro budget show`, and size the batch with `fugaro budget preview --recipe standard --runs N` (the ceiling `N` runs may cost, against today's remaining caps, and a `typical:` line saying what one run usually costs once the repository has 5 runs of the last 30 days that recorded a real-dollar cost per stage — subscription (`oauth`) runs are notional and are left out, as are runs whose `result.json` is unreadable or holds no per-stage cost); `max_parallel` (20) refuses beyond that. The budget gateway prices every call on `api-key`, so the bounds are the owner's per-run and project caps (`budget.per_run_usd` in the local config) and the day's headroom; the cloud loop costs cents per run.
- **Expect to read each PR's CI**, not just the run's verify.

## The cloud loop on provider models

This repository's own `fugaro.yaml` runs the whole cloud loop through OpenRouter on the `openrouter-api-key` credential — the coder on `deepseek/deepseek-v4.1-flash` and the in-loop senior review on the stronger, dearer `deepseek/deepseek-v4-pro` (`agent.auth: api-key`, so the budget gateway prices every call, and no `anthropic-api-key` is mounted) — with the independent review kept outside the loop. What a new user trips on, in the order it bites:

- **`agent.max_budget_usd` is not a cap on your real spend.** Claude Code applies `--max-budget-usd` against **its own** cost estimate, and for a non-Anthropic model that estimate is Sonnet-like — about 25 times what the gateway charges for DeepSeek ([mixed-credentials.md](design/mixed-credentials.md) §5 says the same, and so does the note this repository's own `fugaro.yaml` carries beside `agent.max_budget_usd`). So a per-stage limit that looks enormous in real dollars still buys very little: this repository's `agent.max_budget_usd: 500` ended two runs at **$0.13 and $0.22** of real spend when it was `5`. Set it high enough that it never cuts a stage short by accident, and let the gateway's caps be the real stop — a run's per-run cap and the project's per-run and daily caps, which `fugaro budget show` prints against the ledger that actually prices every call.
- **The per-run cap that binds is the one in the operator's local config, and it is frozen into the job at deploy time.** `budget.per_run_usd` (in `~/.config/fugaro/projects/<project>.yaml`) is written into every workflow job's environment as `FUGARO_MAX_RUN_USD` by `fugaro update --repo` (`internal/infra/spec.go`, `budgetEnv`), and a run's effective cap is the **lower** of that and the database's (`internal/runner/policy.go`, `internal/budget/lease.go`). A *higher* per-run cap set in the database with `fugaro budget set --repo <owner/name> --per-run <USD>` therefore changes nothing while the job still carries the older, lower value: the run halts with `run_cap: run cap $2.00 reached` until the job is re-applied. **After changing `budget.per_run_usd` in the local config, re-run `fugaro update --repo`** so the job carries the new value. To see the value a job actually carries, read its environment (read-only, nothing changes): `gcloud run jobs describe <job> --region <region> --format='value(spec.template.template.containers[0].env)'` and look for `FUGARO_MAX_RUN_USD`.
- **A stage is bounded by the workflow's `timeouts.stage`** — 60m in this repository's `go` workflow, and when a workflow sets none the defaults in `internal/config` fill in `min(40m, timeouts.total)` (`defaults.go`'s `applyDefaults`, run on every resolved config) — so a long implementation task is cut off mid-way and finalizes what it has. Split big work into tasks that each commit as they go, and continue the next step with `fugaro run --pr <N> --task-file <F>`, which acts on the PR's trusted comments with the workflow's secrets in hand.
- **The in-loop reviewer is a different, stronger model than the coder, but it is still not independent review.** Here `agent.models.reviewer` is `deepseek/deepseek-v4-pro`, a dearer OpenRouter model than the coder's `deepseek/deepseek-v4.1-flash`, so the run's own `ship` is worth more than a smoke check — but both are DeepSeek models of the same family, reading the code the other wrote, so it is still the loop judging itself: keep the real review **outside** the loop (a local session with your own eyes on the diff, plus the PR's CI), exactly as this repository does. A run's own `ship` never replaces it.
- **`fugaro cancel <RUN>` finalizes a draft PR.** Cancel does not throw the run away: it stops the current stage and lets the runner finalize, which opens a **draft PR** for the work done so far. A cancelled run therefore typically leaves an empty draft PR behind to close by hand (`fugaro cancel --now` is the exception: it stops the execution at once and skips that finalize).

## What went through runs, and what did not

Through runs: the first dogfood task (a small `diagnose` fix, merged after CI), M11's skills restructure, preflight and backend seam, and other ordinary features, fixes, refactors, tests and docs, plus PR follow-ups where permitted above. The two M11 tasks that touched `.github/workflows` (the release images and the skill lint) lost their runs' work to the refused push and were redone locally.

Through the **subagent review loop in a local session**, with your eyes on it: anything that handles money or security. That is the budget and policy code (`internal/budget`, `internal/policy`, `internal/gateway`, `internal/pricing`), the database rules and token minting, credential and secret handling (the whole `secrets` stage and the mirror), the runner's hardening and the image selftest, IAM and the Terraform that grants it, project creation and billing, the skills' security text, and `fugaro.yaml`, the workflows and `images/` themselves. For M11 the converge loop, mirror, secrets stage, plugin wiring, project creation and the two critical skills each got their own review. A run can open a PR for these, but then the review gate is you and the full CI, not the run's own two review rounds.

## Deferred work is a backlog item

There is one backlog and not two, and it is [`docs/backlog/`](backlog/FORMAT.md) — one Markdown file per item, with the generated [index](backlog/README.md) beside it (D32). A deferral is filed as an item rather than written into a plan file's follow-up list: an item outlives the plan and the pull request it was filed from, and the pull request that fixes one flips its `status` and regenerates the index in the same commit, so the flip travels in a reviewed diff (D31). Filing one is yours by hand: `fugaro backlog add` writes the file, which is what `filed-in: hand` and `mode: none` mean (D27, D30). No run files an item — a run's own record and its pull request's status section carry what it left open — so the folder holds the items a person filed and nothing else. Nothing new is written in the older shape: a `docs/plans` file's `## Known follow-ups` or `## Deferred review items` section was a second live list of the same deferred work, one that dies with the plan. The sections that predate the folder are history rather than a live list, and converting them to items is one mechanical pass — a person's, since it rewrites documents the owner wrote.

## Lessons

- **Time bombs in tests.** Three tests passed for days and then went red on `main` and on every PR, because they hard-coded a date against a wall clock that kept moving: a PR-flow test clock fixed at 2026-10-03 against stage deadlines on the real clock (`context deadline exceeded` after about 15:00 UTC that day, #73), a budget fixture's database clock fixed at 2026-10-02 against a token minted by the wall clock (writes refused about 36 hours later, #78), and a seeded run dated 2026-09-27 that `ls` stopped showing once it was more than 7 days old (#103). Rule: a test starts from the real time (or injects one clock everywhere), and a date that appears in a fixture must follow it.
- **Recommendation, not built: a scheduled CI run with the clock moved forward.** A nightly run of the suite with the wall clock set weeks ahead would have caught all three the day they were written. How to move the clock is open: Go reads the time through the vDSO, so LD_PRELOAD tools such as libfaketime are unreliable for Go binaries (unchecked here), and a container or VM with a shifted clock, or one injected test clock, are the options. A workflow file is a person's change (above).
- **Flaky is a hint.** `TestLedgerNeverExceedsGrantedWithLease` failed "sometimes" under `-race`; it was a real gateway bug (lease top-up starvation, #81), not a flake.
- **Output.** Go emits no JUnit reports, so verify says "0 tests: no JUnit reports"; it reports pass or fail from the exit status only. `gotestsum` would add per-test results and `rerun_failed`; it is a follow-up.
- **Login expiry.** `gcloud` and `gsutil` logins expire (reauth) while you are away; the `fugaro` CLI uses its own credentials and keeps working.
- **The frictions that became M11** (design `m11-setup-and-skills.md` §6): the first-install `setup --plan-only` failure, same-project refusal, the taken App name, the Cloud Billing API on the quota project, the default Compute account's `roles/editor`, the unpublished base and history images, wrapped multi-line commands, typed confirmations needing a real terminal, and the many manual rounds.

## Left out of the `go` image, on purpose

- **Docker.** There is no daemon on Cloud Run, so the docker-tests job can't be a verify step.
- **Node and npm, Java.** Only the Firebase rules emulator job needs them (Node 22, npm 11.19.0, Java 21 and a downloaded emulator jar); its tests skip without the emulator, and CI runs them.
- **tflint.** The Terraform lint is a CI job. Terraform itself is in the image (1.16.4, the CI version) for `go test -tags terraform ./internal/infra/...` and `terraform validate`, which need provider downloads at run time.
