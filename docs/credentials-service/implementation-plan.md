## Considered and declined: the in-runner cascade (the former Slice 1)

The plan's first version built the cascade inside the runner first (the existing gateway learning the OAuth upstream and the A→B switch, with the tier-A tokens mounted in the job), and moved it into the service second. **The owner declined it on 2026-10-17 (O1: "skip Slice 1; go straight to the service").** Why: in that slice the only writer of a shared mark was the run's own gateway, so the rules had to give every run token a **temporary write grant on shared marks** — and a hostile agent in one run could then mark an admitted account exhausted or broken for every run. That is worse than a denial of service: with `fallback: auto`, false tier-A marks push every run of the project onto paid tier B, a **cost shift bounded only by the caps** (review finding W3). The grant could not even be narrowed as written: the rules cannot check "its own repository's admitted set" (admissions live only in the operator's local config, `config.ClaudeAccount.AllowDataTo`, and nothing publishes them to the database), and marks are shared across runs by design and not monotonic (an exhausted mark is replaced by a later one), so no `.validate` expression can tell an honest mark from a false one (review finding M1). The slice also mounted several tier-A tokens in one job, readable through `/proc` (F6). **With the service first, no run token ever holds a write on `creds/`**: the service's own account is the only writer of the cascade's state (D136 exactly), and no job mounts a tier-A token at all.

## Conventions every task follows

1. **Owner-run live checks.** Every live step — a rules deploy, a Terraform apply, an init stage, a check — is the owner's, on installation `fugaro` and a sandbox repository only. **`belong` is never touched by any step of this work** (D147); it migrates only when the owner says so, by hand. `agentMarker` refuses live applies inside a coding agent; no task weakens it.
2. **No secret-shaped literals** in tests, fixtures, docs or skills. Fake credentials are built at run time (for example from a constant prefix and `t.Name()`), never a literal that looks like a key or token; the plugin lint (`TestLintRejectsSecretShaped`) and the image scan's `images/trivy-secret.yaml` already enforce this for their areas.
3. **Skills stay inside their budget.** Any edit under `plugin/skills/` passes `go test ./plugin/...` (`TestLintSizeBudget`, `TestLintByteBudget`, the command and flag lint).
4. **Docs guards.** Every task that edits a document runs `GOFLAGS=-p=2 go test ./internal/cli ./internal/config ./images -run 'Docs|Migration|BaseImageDoc|Design|SecurityMd|RecipesGuide|NoLegacy|Website|CliRef' -count=1` (the list CI's docs-only path names) — and updates the guard test in the same commit when the pinned text changes on purpose.
5. **Version skew.** A new `fugaro.yaml` value is a version-skew break in a strictly decoded config: it gets a `…Since` constant in `internal/cli/recipes_skew.go` and `fugaro init --repo` refuses it against a base image that predates it (the held plan's P9, carried over by D130). A policy change bumps `projectpolicy.Version` (and uses `SkewSentence`) **only when an older reader must refuse the node**; a new top-level member is tolerated by older readers (`projectpolicy.Decode` ignores unknown top-level keys) and does not bump it. A rules change bumps `projectpolicy.RulesVersion` **only when it changes the policy nodes** (`version.go`): `projectpolicy.Read` treats a marker below `RulesVersion` as "no policy here", so a bump drops every published policy (caps, `allow_repos`, routing, prices) on an installation until its owner redeploys the rules, and `requirePolicyRules` refuses to publish there. This work's rules change does not touch the policy nodes and does not bump it (C1.3).
6. **Strict decoding and schemas.** New config and wire formats decode strictly; `schemas/fugaro.schema.json` changes with the config.
7. **Rules changes** ship as template + regenerated golden + parity + emulator **denial** cases in one PR, and are deployed by the owner (`fugaro init --firebase <id>`).
8. **No agent edits `.github/workflows/`.** A workflow change (the service image's build) is staged under `docs/pending-workflows/` and copied in by the owner.
9. **Hermetic tests.** No network, no real cloud; use `internal/gcpfake`, `internal/testutil`, `internal/gateway/anthropicfake` and `t.TempDir()`. Runner and gateway changes run with `GOFLAGS=-p=2`. The one exception is C1.4's helper, which is built under the `live` tag, never runs in CI, and is run by the owner only.
10. **TIER A isolation (D132).** Every piece of code that exists only for subscription OAuth tokens through a proxy lives behind its own upstream kind and in its own files, and the task is marked **TIER A**. Removing tier A means deleting those files and one switch case, never unpicking shared code.
11. **The service is the only writer of cascade state (O1, D136).** No run token, runner or in-runner gateway writes under `creds/`; the runner side only calls the service and records what the service answers on its own run's nodes.

### Task C1.11: The service's forward and the cascade — SECURITY-SENSITIVE (TIER A parts marked)

**The bundle loader (Q6, ruled 2026-10-19).** The service's credentials are **one Secret Manager secret**, read as its own SA: **the bundle (latest version, short cache)**, one read for the whole credential set. The document is a **YAML** map of credential **names** to values, parsed with **`bundle.go`'s strict schema** (the shape `schemas/creds-bundle.schema.json` publishes): the top-level keys are exactly the known ones, the loader **refuses unknown keys** (never ignores them: a typo'd key that parsed would be a credential nobody meant to store), a document over the fixed **size bound is refused** before it is parsed (an oversize document is a mistake or an attack, and the bound is a constant, not a policy field), an empty document, a missing secret and an unparseable body are all **failures, not empty sets**. The loader **fails closed on a missing or unparseable bundle**: the service answers a typed refusal and issues nothing — never a fallback, never an empty credential list, never an in-job key (D143) — and the refusal names what is wrong (absent, too large, unknown key, unparseable) without ever carrying a value. **It never logs or echoes any value**: no credential value reaches a log line, an error, a header, a metric label or a panic message (`scrubToken`/`redactWriter`'s rule, F32, extended to the loader's own errors); the audit line (C1.13) carries names. The cache is short and bounded so a rotation by C1.25 is picked up quickly; a test pins that a cache hit and a cache miss parse to the same thing and that a bundle replaced between two calls is the one read after the cache expires. **This is the only place the service reads a credential**, and it is one grant on one secret (C1.18, Global Constraint 12).

- **`fugaro creds set NAME`** — read the bundle (`latest`), parse it with **C1.11's strict schema**, set or replace the entry `NAME`, and write it back as a new version (**read-modify-write**, one version, no per-entry secret). The value is read from a **hidden prompt** (the `readHidden` / `readSecret` path `fugaro secrets set` already uses) or stdin — **never from argv, never from an environment variable**, and the command registers no flag that could carry it (the `SetFlagErrorFunc` precedent in `internal/cli/secrets.go`, which exists because pflag quotes an unknown flag back). An unknown or reserved name, a document that fails the strict schema, and an oversize value are each refused with a named error before anything is written. **After a verified write the version it replaced is disabled** (`secretmanager.versions.disable` on the previous version, named in the command's output, best-effort with the failure reported rather than swallowed): a rotated-away bundle that stays **enabled** keeps every superseded credential readable by anyone who can read the container, which is the one thing a rotation is for (independent security review of the implementation, m4). Terraform cannot do this — it creates the container and manages no version (`version_destroy_ttl` on the resource would destroy *disabled* versions, not disable live ones, and a TTL is no substitute for the disable) — so the command that writes a version is the thing that retires the one before it. Nothing the command prints ever contains a value: names and metadata only, and no value in any error.
- **`fugaro creds ls`** — the bundle's **names and metadata only**: each entry's name, its presence, its last-changed time (the container's version metadata), and nothing else. **Never a value, never a prefix, never a length that narrows a guess**; `--json` carries the same shape. An unreadable or unparseable bundle is a named failure, not an empty list (`fugaro accounts ls`'s `Complete: false` precedent).

## Risks

- **D132 — accepted owner risk.** The owner chose to proceed without first confirming Anthropic's current terms for sharing individuals' subscription OAuth tokens across a project and sending their traffic through a Fugaro-operated proxy. This plan states no view on what those terms say. Tier-A-through-a-proxy work may later have to be removed, and the token holders' accounts are exposed in the meantime. Mitigation by construction: TIER A code is isolated (Convention 10), so removing it is deleting C1.7's files and the TIER A parts of C1.11 and C1.12.
- **The whole work waits for 0.9.0** (O1 + D134): no product value before the seal, both halves, has merged.
- **False marks are a cost shift, not only a denial of service** (review finding W3). With `fallback: auto`, a credential wrongly marked exhausted or broken pushes every run onto paid tier B, bounded only by the caps. Under O1 no run can write a mark, so this needs the service itself to misjudge a response; the classification of usage-limit responses (C1.11, Check 90's U3) is reviewed with that cost in mind.
- **Liveness is bounded by `fx` until an outcome is written** (W2): a run killed before its end and not yet swept keeps a valid identity until `fx`. The outcome's *day* is part of that bound and is not a run's to choose (review finding M1): the sweeper dates it from the run id's launch day, never earlier (a run's own heartbeat is run-written, and an outcome dated before the launch day sits on a day no liveness scan reads), and never ahead of the sweeper's today (a day the rules' `DAYOK` would not have accepted, and one no scan reads either). A run id dated ahead of the sweeper's clock has no reachable launch day, so its outcome is dated today and not the older heartbeat day — the two bounds would otherwise leave the outcome on a day neither the launch-day rule nor the scan covers. `TestSweepDatesTheOutcomeNoEarlierThanTheLaunchDay`, `TestSweepDoesNotDateTheOutcomeAheadOfToday` (a heartbeat days old, so the test fails without the clamp) and `TestSweepDoesNotDateTheOutcomeFromAStaleHeartbeat` (the plausibility window, which holds when the run id is not a launch id at all) pin all three.
- **The run identity and the calling job are not bound to each other (review finding m2).** C1.10 verifies each identity on its own: the account says which job called and the run identity says which run was minted, but nothing there checks that the run's repository is one the caller's job may act for. Any admitted job service account that holds a run identity can therefore present it. Bounded by the same launcher trust this plan already records (F29, SECURITY.md): a run identity is minted by the launcher, so the caller must already hold one — and under Global Constraint 6 each repository's job has its own account, so the account narrows *which job*, not *which repository's run*. The pairing is an admission question and is left to C1.11's O4 checks; it is recorded here rather than mitigated in C1.10.
- **The service is a single point** of compromise and availability (D143), accepted with its bounds. **Q6 makes the credential side of it literal**: one secret, one grant, so a read of the bundle is every service credential at once — the same set the service already holds — but the leak is one object rather than N, and the audit log's entry is the bundle's read, not a per-credential one (reconciliation.md §4, "Q6's consequences").
- **The service's per-run cap check is ADVISORY — accepted (owner's answer, 2026-10-19).** The binding cap is the in-job gateway's ledger (D143). A run's spend is therefore bounded by the gateway, not by the service; a wrong cap in the service is a refusal the run does not need, never an overrun it is allowed.
- **The launcher's reach and the replay bounds are accepted documented limits (owner's answer, 2026-10-19).** Any launcher can mint a budget identity for any repository (F29, SECURITY.md), and until a write-once outcome exists for a run `fx` is the only bound on a replayed token (W2). This plan records both and mitigates neither; the seal (D134, both halves) narrows the first for peer reads but does not close the launcher-trust caveat.
- **The bundle's write path is the owner's alone (Q6's accepted cost).** A teammate who may add a token without reading one loses that path: writing the bundle is reading it. Accepted as a single-owner setup; C1.25's commands refuse an agent's session and a run's process, and `fugaro creds ls` prints names and metadata only.
