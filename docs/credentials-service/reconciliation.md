## 0. What the spec is, in one paragraph, and what it really is in this repository

The spec asks for a per-project **credential proxy**: a Cloud Run service that alone holds every model key and OAuth token (and later every job secret), that jobs reach with a short-lived per-job token, and that picks the cheapest usable credential per call (A: shared subscription OAuth tokens, B: an Anthropic API key, C: an OpenRouter key), failing over transparently in the middle of a long Opus review. Read against the code, **most of its parts already exist under other names, in-process**: the budget gateway (`internal/gateway`) is already a loopback proxy that swaps a per-run token for the real key, streams SSE without buffering, and meters every call against caps; the per-run Firebase identity (`internal/budget/token`) is already a short-lived, launcher-minted, per-run credential bound to one repository and one run; "an external gateway" is already the recorded later hardening of M9's D2 (`docs/design/m9-budget-and-dashboard.md` §11); person-owned OAuth tokens with a project-level reference are already the design of project-centric phase 5 (`docs/design/project-centric.md` §7); and usage-limit account switching already exists, but only in a plugin skill and only as a whole-run relaunch. What is **genuinely new** is (1) moving the credential **out of the job** into a separately-deployed identity, (2) per-call credential switching inside one run (which breaks M10's "a run does not mix credentials" rule), (3) shared exhaustion/broken state, and (4) OAuth subscription traffic going through any proxy at all, which Fugaro has never done (`auth: oauth never goes through the gateway`).

### 2.2 Credential model and how a job gets secrets today

**F1 (Exists; the thing the spec moves).** Every secret a job uses is a Cloud Run **secret env mount** read as the **job's own service account**. `internal/infra/spec.go` `SecretMounts` mounts the git secret always; for `oauth` `ClaudeAccountSecret(token)` → `CLAUDE_CODE_OAUTH_TOKEN`; for `api-key` `anthropic-api-key` → `ANTHROPIC_API_KEY` (dropped when the secret has no version, `infra.OptionalSecret`) plus every provider key whose `allow_data_to` lists the repository; for `vertex` none (the SA gets `roles/aiplatform.user`); then the workflow's own `secrets`. Terraform binds `secretAccessor` per secret to the job SA (`deploy/terraform/gcp/modules/workflow/sa.tf`, `google_secret_manager_secret_iam_member "job"`) with `version = "latest"` in `modules/workflow/job.tf`. The runner reads its own environment (`runExec`, `internal/cli/exec.go`). **Consequence:** "the job's SA has no Secret Manager access" is a change to `sa.tf`, `SecretMounts`, `readiness.go` and every caller of the reserved names, not an addition; it is the inversion of today's model.

**F2 (Exists).** Secret IDs are `fugaro-<slug>-<logical>-<hash>` (`gcp.SecretID`) and `fugaro-project-<project>-<logical>-<hash>` (`gcp.ProjectSecretID`); reserved logical names are in `config.ReservedSecrets` (`bitbucket-token`, `github-app-key`, `claude-oauth-token`, `anthropic-api-key`). Operators hold `secretVersionAdder` + `viewer` (`modules/repo/secrets.tf`, `modules/installation/secrets.tf`), never `secretAccessor`. **Consequence:** the service's SA would be the new `secretAccessor` on the model and git secrets; the naming scheme can stay.

**F3 (Rule; spec's "only identity" claim is not achievable as stated).** Besides job SAs, the **build SA** holds `secretAccessor` on the git secret and workflow build secrets (`modules/repo/build.tf`, `google_secret_manager_secret_iam_member "build"`), and Project Owners/Editors bypass any secret-level policy (SECURITY.md, "What is not on by default"). **Consequence:** the service can be the only *Fugaro runtime* identity with access to model credentials; it cannot be the only identity with access to Secret Manager. SECURITY.md must say exactly that (D148).

**F4 (Exists; named OAuth accounts).** `claude-oauth-token-<name>` per repository (`config.ClaudeOAuthTokenPrefix`, `ClaudeAccountSecret`), accounts only in the owner's local config (`localcfg.Config.ClaudeAccounts`, `config.ClaudeAccount.AllowDataTo`), one Cloud Run job and SA per (repository, workflow, account) (`gcp.WorkflowVariant`, the variant loop over `config.AllowedClaudeAccounts` in `infra.Repo`), selected by `--token` / `agent.oauth_token` (`claudeAccountFor`). **Consequence:** tier A as the spec states it ("project-level named tokens, referencing individuals' tokens") is project-centric phase 5, not today's per-repository variants; the spec is the answer to *how* phase 5 mounts them (it does not: the service holds them) — see D131.

**F5 (Rule; M10 invariant).** `config.CheckProviderAuth` refuses `oauth` with any provider route: "an oauth token is a Claude subscription credential and is never sent to another provider", and one `agent.auth` per workflow means **a run does not mix credentials**. The spec's per-call cascade A→B→C inside one review mixes three credentials in one run. **Consequence:** the invariant must be lifted explicitly, in one place (a new auth mode), while its real content — an OAuth token is never sent to a non-Anthropic upstream — is kept (D133).

**F6 (Exists; what the agent can reach today).** SECURITY.md "Known limits / What one run's agent can reach": the git token, the per-run gateway token, every declared secret, and through `/proc` of the runner "**the GitHub App's private key**", "the real model and provider keys", "the job's service account, through the metadata server". This is M9's accepted D2 residual. **Consequence:** this is precisely what the spec fixes: with a service holding the keys and the App key, `/proc` yields only a short-lived per-run token. That is the strongest argument for the spec, and it holds whether or not tier A ever ships.

**F7 (Exists; GitHub auth).** `FUGARO_GITHUB_APP_ID` (`providers.EnvGitHubAppID`, per repository from `localcfg` `Repo.GitHubAppID`) and the App key `github-app-key` → `FUGARO_GITHUB_APP_PRIVATE_KEY` (project-scoped by default since D2). The runner mints an installation token itself (`apptoken.go` `tokenSource.Token`, `{"repositories":[repo]}`, `tokenPermissions`: contents write, pull requests write, issues read, metadata read; `buildTokenPermissions` for builds). On a first run the **agent holds the minted token** (`github.Provider.GitAuth` → `GH_TOKEN`, `gitops.CredentialVars`, `run.refreshGitAuth`); follow-up, review and artifact runs do not. Bitbucket uses a per-repository access token (`bitbucket-token`, `FUGARO_BITBUCKET_TOKEN`), which cannot be minted per job at all. **Consequence:** the spec's "service mints installation tokens per job" is a move of `tokenSource` into the service; it is the change that removes the App key from every job. Bitbucket gets no per-job token (D145).

**F8 (Wrong).** The spec scopes the GitHub token to "contents read/write **on the job branch**". An installation token's `contents` permission applies to the whole repository; it cannot be limited to one branch (branch limits are branch protection/rulesets, which SECURITY.md already relies on: "The base branch is protected only by your branch protection"). Today's token also needs `issues: read` and `metadata: read` (`tokenPermissions`). **Consequence:** "the agent never holds a GitHub token" is only achieved by the spec's *optional* proxied push/PR creation, not by scoping; the follow-up path already does this in-job (the runner pushes, the agent gets no `GH_TOKEN`). GitHub's branch-scoping limit is from GitHub's documentation, not verifiable here (UNVERIFIED U6).

**F9 (Exists; local runs).** `fugaro exec` (`runExec`) uses the caller's environment; there is no Secret Manager and no gateway requirement. **Consequence:** local runs keep the developer's own credentials and never use the service (D149).

**F10 (Exists; compute backend).** `internal/backend/batch` (`Options.Secrets` → Batch `secretVariables`, `checkSecrets`) resolves secret names as the VM's job SA; nothing selects the backend yet ("`backend: cloud-batch` is refused"), and `modules/compute/iam.tf` grants run accounts no secret access. **Consequence:** with the service, a Batch VM needs only invoker on the service plus the run identity — strictly simpler; the VM backend's "metadata server is reachable / Docker is root" (SECURITY.md) makes the in-job alternative worse there than on Cloud Run (D149).

### 2.4 Routing, the reviewer stage and the cascade

**F13 (Gap).** `routing.claude` (`run.applyRouting`) resolves **once per run** to one route; the gateway's route table (`internal/gateway/route.go`) is static for the run. The cascade is per call and depends on shared, changing state. **Consequence:** the cascade lives where the upstream is chosen per request — in the gateway's forward path (in-runner) or in the service — and `routing.claude` is the natural switch for it (D150). *(O3, 2026-10-17: the switch is spelled `routing.claude: {via: cascade}`, not `via: auto`, so `auto` keeps today's meaning.)*

**F14 (Gap).** Tier C serves Claude under a different model ID (`anthropic/claude-…` versus `claude-…`, project-centric §2.4 "nothing translates between them"); the gateway "never rewrites a body". **Consequence:** a mid-review switch from A/B to C needs body rewriting of the `model` field or a resume with a different pin; and C's cache behaviour is unmeasured (Check 50). Recommendation: C for a Claude reviewer only after Check 50 (D150).

### 2.5 Selection, exhaustion, broken and refresh

**F15 (Gap).** The runner does not detect usage or rate limits: no code under `internal/runner` or `internal/agent` matches "usage limit"; a Claude error fails the stage (`run.stage` → `r.fail`); the gateway never retries and passes a provider 429 through as `rate_limit_error` with `Retry-After` (`errorTypeForProviderStatus`). Claude Code's own usage-limit wording is **UNVERIFIED** (named-oauth-tokens U4). **Consequence:** reactive exhaustion detection must be done on the HTTP response (status, error type, reset headers) where the proxy sees it, not by parsing Claude Code's text. Which headers carry the reset time for subscription traffic is UNVERIFIED (U3).

**F16 (Gap).** Shared exhaustion/broken/lock state has no home. RTDB rules (`internal/budget/rules/rules.json.tmpl`, generated by `rules.Generate`) grant run tokens writes under `runs/$slug/$run/…`, `spend/…`, `agents/…`, `outcomes` and reads of `config/{caps,limits,mode,kill,policy}`; nothing about credentials. **Consequence:** a new subtree (for example `creds/`) is needed, a rules-template change with golden, parity and emulator tests and an **owner-run rules deploy** (D136).

**F17 (Open; RTDB as a lock/CAS store).** `internal/rtdb/client.go` is a REST client: `GetETag`, `PutIfMatch` (412 → `ErrPrecondition`) and multi-path `Patch`; **no transactions**; ETag CAS is used only by `budget.SetKill`. A service identity authenticating with its own SA's OAuth token is an **admin** and **bypasses the rules** (the launcher-as-viewer precedent in the rules doc). **Consequence:** rules cannot constrain the service's own writes; they can only deny every run token access to `creds/`. ETag CAS is enough for marks and per-token locks at this contention (tens of jobs). Firestore (used only for `spendDaily` by `budget` rollover) has real transactions and is the alternative (D136).

**F18 (Open; refresh races).** Fugaro's OAuth tokens come from `claude setup-token` ("the only way to mint one", `docs/design/named-oauth-tokens.md`) and are stored as a single env value; Fugaro has never refreshed one. Whether a setup-token is a long-lived token with no refresh flow is **UNVERIFIED** (U2). **Consequence:** if it is, the spec's refresh section (lock + CAS write-back to Secret Manager) has nothing to serialise in the first slices, and a 401 simply means `broken`. Defer refresh until a refreshable credential exists (D139).

**F19 (Gap; revoked vs exhausted).** No alert channel exists to "alert the token's owner and project admins"; Fugaro has no notification system, and the person behind an account is not recorded anywhere until phase 5's reference record. **Consequence:** `broken` is a visible state (watch, `accounts ls`, `doctor`) in the first slices; alerts wait for a notification channel (D141).

**F20 (Gap; owner headroom).** Nothing counts per-token use; `runstore/cost.go` notes OAuth spend is notional and "no per-person budget exists" (project-centric §7). **Consequence:** a usage share needs per-token counters (runs or sessions per window) in the same `creds/` subtree; recommend only "stop after one exhaustion per window" and a concurrency cap first (D142).

### 2.6 Stickiness, mid-review failover, wait-or-switch and durable sessions

**F21 (Wrong, in the design's favour).** The spec says failover means "resume the same session with the next credential (Claude Code session resume with different auth in the environment)". **With a proxy, no resume is needed to switch credential**: Claude Code holds the conversation and sends the whole context on every call; the credential is attached by the proxy, so the next call simply goes out under another credential, and only the prompt cache is lost. Resume is needed only (a) when the run must **wait** longer than one call can block, and (b) when the job dies. **Consequence:** the switch path is per request in the proxy; the session machinery is for waiting and for job death (D138). The one caveat is that subscription OAuth requests and API-key requests may differ in required headers or system prompt (the spec's own "to verify early"), UNVERIFIED (U1).

**F22 (Exists, partly).** `agent.Args` supports `--resume <id>`; `run.saveSession` uploads the latest **implement or fix** stage's session to `runs/<slug>/<run>/session/<id>.jsonl` (redacted) **at writeback or on a failed finalize**; `run.restoreSession` resumes only for a follow-up; stage transcripts go to `transcripts/<stage>-<n>.jsonl` at stage end. **Review-stage sessions are not saved**, nothing is saved periodically, and a killed container saves nothing. The job runs with `max_retries = 0` (`deploy/terraform/gcp/modules/workflow/job.tf`). **Consequence:** "resume after the Cloud Run job dies" needs periodic session upload during a stage, a resumable-run record, and a relauncher (a new execution that takes over the same run id and branch); none exists. Recommend this as its own later slice, independent of credentials (D138).

**F23 (Open; where the wait happens).** Waiting up to 15 minutes inside one HTTP call means the proxy holds a request open; Claude Code's client timeout and retry count are UNVERIFIED (U4), and Cloud Run's request timeout caps any wait (U5). **Consequence:** the wait belongs in the runner: the proxy answers a typed "exhausted until T" error, the stage ends, the runner sleeps within the job's own timeout and resumes the stage's session with `--resume`. That needs F22's review-stage session save (D138).

**F24 (Rule; cache-miss cost).** The gateway already prices calls from `internal/pricing` (cache read vs. input rates), so a switch's estimated cache-miss cost is computable: (cached input tokens of the last call) × (input rate − cache-read rate) on the new tier. For tier C with Claude the cache behaviour is unmeasured (Checks 46, 50). **Consequence:** the switch log can carry an estimate for A→B; for →C it says "unmeasured" until Check 50 runs.

### 2.7 Caps and accounting

**F25 (Exists; "only B and C count").** Today an `oauth` run has **no gateway**: its cost is recorded as notional (`reportNotional`, `AddNotional`, `BasisSubscription`), and caps never bind it except the token cap (`run.capReached`, `HaltTokenCap`) and kill switches. An `api-key` run's every call is reserved and settled. **Consequence:** the rule exists per run; the cascade needs it **per call**: the ledger must carry the call's tier and settle A calls as notional and B/C as real, in the same run (D140).

**F26 (Gap; which credential a run used).** `runstore.Record.OAuthAccount` (`oauth_account`) is declared but **no non-test code writes it**; `runview.Join` falls back to the task's requested account (`task.Spec.OAuthToken`), so `fugaro runs`' ACCOUNT column and `diagnose` show what was *asked for*, not what was used. RTDB `agents/<slug>/<run>/auth` (`budget.AgentEntry.Auth`) carries the auth mode only. **Consequence:** "dashboard shows which credential each job is on" needs a per-run current-credential field written on every switch, and a switch log; the existing field should be written by the runner first (D140).

**F27 (Exists; console).** `console/` holds only `README.md` and `docs/json-contract.md`; the console's rule is "the console holds none" (`desktop-console.md` §1, `desktop-console-v2.md` rule 7); project-centric §9 lists "a secrets and accounts inventory with owners, OAuth quota" as a missing view. `fugaro watch` shows `Auth` and NOTIONAL. **Consequence:** the console shows credential **names and states**, never values, through the CLI's JSON (`watch --json`, `accounts ls --json`); no console change is in scope here.

### 2.8 The service shape

**F28 (Exists as design; the out-of-job gateway).** M9 §11 "Later hardening (D2)" lists (1) a gateway sidecar and (2) an external gateway service; the spec **rejects the sidecar** for the right reason (same SA and metadata server; project-centric §4.1 says the same). **Consequence:** the spec is M9 D2's item 2; the decision record should say the sidecar is dropped.

**F29 (Open; the per-job token).** The spec does not say who mints it or what binds it. The run's budget identity already is a per-run credential: minted by the launcher with `signJwt` on a role-less signing account (`token.Mint`, `token.IAMSigner`), claims bind it to one repository slug (`fs`), one run (`fr`), one Fugaro project (`fp`) and the launcher (`rb`), expiry `fx` = launch + job timeout + slack (`token.ExpiryFX`), exchanged for a Firebase ID token the runner refreshes (`token.Session`). Its known weaknesses are recorded: any launcher can mint one for any repository (SECURITY.md "Any launcher can mint a budget identity for any repository"), and under phase 3 a peer run can read another run's token object until the seal ships (D13, budget-token-channel §7.1; PR #417, the runner half, merged into `next-0.9`; PR #523, the launcher half, an open draft). **Consequence:** reuse it as the proxy's job token, verified by the service against Firebase's public keys and against the run's liveness read from a node the run **cannot undo** — the write-once `outcomes/$day/$slug/$run` (rules `RUN && DAYOK && !data.exists()`; written at the run's end by `internal/budget/registry.go` and, for a run that died, by the sweeper in `internal/budget/sweep.go`), never `agents/<slug>/<run>`, which the rules let the run's own token rewrite or recreate (`.write: "RUN"`); until an outcome is written, `fx` is the only real bound. The seal — both halves — is a precondition of the service (D134). *(Corrected 2026-10-17 from "`agents/<slug>/<run>` present and not finalised", review finding W2.)*

**F30 (Open; the proxy's own authentication).** Cloud Run IAM invoker requires a Google ID token in `Authorization`, which Claude Code cannot add for itself, and subscription OAuth requests already use `Authorization`. **Consequence:** keep the in-runner gateway as the client: Claude Code → loopback gateway (gateway token, managed settings, metering) → service (job SA's ID token for IAM invoker + the run identity in its own header) → Anthropic/OpenRouter. This keeps `writeManagedSettings` / `checkSettingsRouting` and makes the service's ingress authenticated twice (D135).

**F31 (Open; streaming through Cloud Run).** Known in code: the gateway streams SSE unbuffered and never retries. Not verified here: Cloud Run service request timeout (configurable, believed up to 60 minutes), request-body limit (believed 32 MiB on HTTP/1, none on end-to-end HTTP/2), streaming of SSE responses through the front end, and the cold start (spec: "about a second"). **Consequence:** a 30-minute review is many calls, each typically well under the per-request timeout, so the 60-minute limit binds a call, not a review; one very large request (images, 1M-token contexts) is the size risk. All of it is UNVERIFIED (U5) and is an owner-run measurement (D151).

**F32 (Gap; logging that never holds a token).** The gateway already "never logs a header or a body" and scrubs (`scrubToken`, `redactWriter`); the runner redacts mounted secrets (`run.addMountedSecrets`). **Consequence:** the service inherits the gateway's forwarding code and its no-header logging rule; its audit log records names (job, repo, credential name, purpose, tier, status), never values.

**F33 (Rule; deploying the service).** Every live step is owner-run, on installation `fugaro` and a sandbox repository only, never `belong` (project-centric §11; `docs/plans/2026-10-16-managed-projects.md` global constraint 7); `agentMarker` (`internal/cli/initsecrets.go`) refuses live applies inside a coding agent; Terraform roots are installation, firebase, repo, compute. Managed projects' deployer SA (D75: `fugaroDeployer` and the conditioned half — `fugaroDeployerScoped` when this was written, seven roles, one per service, since the 0.10.0 redesign — bound only under the `fmgd-` name-prefix condition, "nothing at all on the runs bucket") is for agent-authored managed roots, **not** Fugaro's own infrastructure. **Consequence:** the service is a new resource set in the **installation** root (service, its SA, `secretAccessor` moved from job SAs, invoker for job SAs), deployed by an owner-run `fugaro init` stage; never by `fugaro managed apply`; checks numbered from this work's block **90–99** (D146).

**F34 (Rule; SECURITY.md claims the service changes).** "What one run's agent can reach" (F6), "With the budget gateway on, model keys stay out of the agent's environment", "Money … An agent that reads the real key from `/proc` can spend outside it", "A job can read only the secrets its own workflow declares", "Inside a shared job there is no IAM boundary … the profile is the boundary", and `docs/git-providers.md`'s "None of these variables reaches the agent" (true of the static variables only: the minted token does reach it, F7). **Consequence:** each changes in the PR that changes the behaviour; the guard tests `internal/cli/docs_security_test.go` and `docs_website_security_test.go` pin some of this text.

### 2.9 Scope: all job secrets

**F35 (Gap; workflow secrets cannot all be proxied).** A workflow's `secrets:` are put in the agent's environment deliberately (`secretEnvs` in `internal/runner/runner.go`, used by `commands.render`, verify commands and tests). A test-environment key the code under test reads cannot be "proxied so the raw secret never enters the job". **Consequence:** the service's first scope is model credentials and the GitHub App key; workflow secrets stay mounted (D145).

**F36 (Exists; boundary).** The spec keeps the service secrets-only with sibling services for other always-on features. The mobile work names a possible phase-2 service (`docs/mobile/reconciliation.md`, D115). **Consequence:** consistent; the boundary is recorded and no mobile function goes in this service.

### 2.10 Policy and terms

**F37 (Open; the owner's risk).** Tier A shares **individuals' subscription OAuth tokens** across a project and sends their traffic through a Fugaro-operated proxy that rewrites the authentication header. Whether that use is permitted is a question about Anthropic's current consumer and commercial terms and usage policies, which this document does not assess and does not characterise. **Consequence:** it is the owner's risk; **the owner accepted it on 2026-10-17** (D132's alternative, "proceed and record the risk as accepted") rather than confirming the terms before tier A is built or used. Tiers B and C do not raise it. This document states no view on the terms, and the plan keeps tier A isolated so it can be removed cheaply.

### Q6's consequences, stated plainly

- **A teammate who may add a token but not read one cannot use this path.** Today an operator holds `secretVersionAdder` and `viewer` and **never** `secretAccessor` (F2), so a teammate can add a model credential without being able to read one; a bundle is edited by **read-modify-write**, so writing it means reading every credential in it. That separation is gone. **Accepted: this is a single-owner setup**, and C1.25's commands are owner-run only, refused from an agent's session and from a run's process like the other owner-only commands.
- **Audit.** Secret Manager records one thing about this container, and the audit log shows access to one secret, not which credential was used: **which** credential inside it a call used is the service's own audit line, by name (C1.13), and the `creds/` state — not IAM.
