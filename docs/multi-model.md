# Running a non-Anthropic model (M10)

A run's coder can be a model served by OpenRouter (the first one is `deepseek/deepseek-v4-flash`) while Claude Code stays the harness and Claude reviews. Fugaro sends the model traffic through its own gateway, which picks the upstream by the request's model ID, attaches the provider's key (the agent never holds it) and prices every call. Nothing is translated: OpenRouter's Anthropic-compatible endpoint receives the same Messages request Claude Code sends (assumed until Check 25: that the endpoint exists at that path, accepts `Authorization: Bearer` and answers in the Anthropic stream format). The design and its open assumptions are in [design/m10-multi-model.md](design/m10-multi-model.md); the live check that settles them is Check 25 of [gcp-live-checklist.md](gcp-live-checklist.md).

This is an experiment, not a default: `agent.models` stays Claude unless a repository names a provider model, and a cheaper run is never "more ready" than a Claude one, because the Claude review alone decides readiness. The provider traffic goes through the same gateway as Claude's, so pinning, the dollar caps and the kill switches hold. The **owner** enables it, in the project's local config, because it sends a repository's code to a third party; a repository's `fugaro.yaml` cannot add a provider, a URL or a price, only name a model the owner has opened to it. Treat the first runs as measurements: the cost to reach a Claude-approved pull request is the number that matters.

**With `fugaro models`:** `fugaro models ls` prints the routes this project has, the models each one claims, what a run can name today and what it would cost, and `fugaro models search <text>` finds a model in the price catalog before you pin it. Both are offline reads — no bucket, no database, no host — so they run anywhere, a coding agent's session included.

## 1. On the OpenRouter account (before anything in Fugaro)

Fugaro never rewrites a request body, so what the gateway cannot ask for per request has to be set on the account.

- **A key per Fugaro project, with a credit limit.** Create it for this project only and set its credit limit at OpenRouter to what you are willing to lose. The key sits in the runner's process like the Anthropic key does, and a compromised agent in the same container could read it from `/proc`; the credit limit is the real backstop (the same stance as the workspace limit on an Anthropic key). Fugaro's dollar caps bound a well-behaved run, not a hostile one.
- **Provider preferences: no fallbacks.** In the account's settings pin the providers that may serve the model and turn **fallbacks off**. Otherwise OpenRouter may serve another model or provider than the one you priced (assumed until Check 25); Fugaro then charges the dearer rate and flags `priced_as: max`, but only the account setting prevents it.
- **Data policy.** Set the account's data-collection and zero-data-retention preferences (for example deny data collection) there. A repository's code is sent to whichever provider serves the request, so this is a decision about the code, made once, by the owner.
- **The route fee.** Note the fee your account pays on top of the model price; it goes into `route_fee_pct` below.
- **The real prices** of the model, from its OpenRouter page.

## 2. The project config (owner only)

In `~/.config/fugaro/projects/<project>.yaml` (the local config; a repository's `fugaro.yaml` cannot set any of this):

```yaml
providers:
  openrouter:
    kind: anthropic-compat            # the only kind
    base_url: https://openrouter.ai/api   # https; http only on a loopback host (tests)
    auth: bearer                      # bearer | x-api-key
    secret: openrouter-api-key        # the secret's NAME; never the key
    route_fee_pct: 5.5                # 0 to 50, added to every charge and reservation
    models: ["deepseek/*"]            # exact IDs or a prefix ending in *; providers may not overlap, and may not claim Claude models -- except one explicit anthropic/<id> per entry, the operator's opt-in (see "Direct to the vendor" below)
    allow_data_to: [edgeappinc/fugarosandbox, dimipaun/fugaro]   # repositories whose code may go here; every repository when absent or ["*"] (a list written with no repositories in it -- [], or the key with every entry commented out -- is refused)
model_prices:
  deepseek/deepseek-v4-flash:         # an override of the catalog's row: use the real numbers
    input_per_m: 0.14
    output_per_m: 0.28
    cache_read: 0.1                   # a multiplier of input_per_m (default 0.1), not a price
budget:
  mode: enforce                       # a provider model needs the gateway in enforce mode: observe never refuses a call
  per_run_usd: 2                      # enforce needs a per-run cap
```

**A provider's key is named after its entry: `<entry>-api-key`.** The entry `openrouter` stores its key as `openrouter-api-key`, `deepseek` as `deepseek-api-key`, and so on — `secret:` is the secret's *name*, never the key, and this is the name `fugaro secrets set` is given. `fugaro validate` warns about a `secret:` written differently (never fails: an existing key keeps working, and nothing is renamed or migrated), and `fugaro doctor` reports it as an informational line. **The conventional name is reserved for the provider it names**, whatever that provider's `secret:` says today: a workflow's own secret, or another provider's key, may not be stored under it, because the day that provider's key is renamed to the convention the value already stored there would become its credential. `fugaro secrets set` refuses it, and `fugaro validate` refuses a `providers` entry that claims another entry's conventional name. Two harness credential names are reserved the same way and for the same reason — `claude-oauth-token` (the Claude harness, with a `claude-oauth-token-<account>` name for each named account of `claude_accounts`) and `codex-oauth-token` (Codex, which Fugaro does not drive yet) — and a workflow may not declare one of any of these names. SECURITY.md, "Reserved secret names", states the whole rule.

Then run `fugaro update --repo` in each repository that is listed, so its job carries the provider list and mounts the key's variable. A repository not in a real, non-empty, non-`["*"]` `allow_data_to` gets neither, and a run on it that names a provider model is refused. An absent `allow_data_to` (or the explicit marker `["*"]`) is the deliberate exception: every repository of the project gets both the mount and the routing (design/project-secrets.md §3a, the owner's 2026-10-13 ruling); an `allow_data_to` written with no repositories in it (`[]`, or the key with every entry commented out, which YAML gives the same value as an absent key) is refused outright as ambiguous, so the only way to revoke everyone is to remove the provider's entry. Removing a repository from `allow_data_to` takes effect only after `fugaro update --repo` is run again for it (the list and the key's mount live in the job's configuration until then). **A version upgrade does not refresh this copy**: `fugaro upgrade`'s cloud step compares the deployed job's whole copy of the local project config (`providers`, `model_prices`, budget settings, the region's compute price override and the GitHub App ID) with what the local config would write now and, when they differ, prints a note naming the fields and this same command; it never runs `fugaro update --repo` itself, so its Terraform confirmations stay yours. `fugaro upgrade --check` makes no cloud call, so it cannot tell and says so instead. It checks each workflow's default-account job; a named-account job ([design/named-oauth-tokens.md](design/named-oauth-tokens.md)) is updated by the same `fugaro update --repo`, not checked separately.

**Provider models require `budget.mode: enforce`.** Provider calls are real dollars and `observe` never refuses a call, so a run (and `fugaro validate`) that names a provider model under `observe` or `off` is refused, naming the rule. Set `budget.mode: enforce` and `budget.per_run_usd` in the local project config and run `fugaro update --repo`; `fugaro budget set --global --mode enforce` (which needs the global `--daily` and `--per-run` caps, and asks you to type the project's name to lower it again) makes the shared database enforce too.

**`require_zdr` and `price_policy` price an OpenRouter route from Fugaro's built-in catalog** (the two paragraphs below describe the catalog itself: what it is built from, how to read its age, and your `model_prices` override). **Neither key is accepted by `fugaro update --repo` yet, so leave both out of the `providers` block**: no released fugaro reads them (they ship at 0.7.5), and a runner decodes the job's provider list strictly, so an older one would fail the job at bootstrap on a key nobody typed. `fugaro update --repo` refuses a route that sets either one — before it makes any cloud call, naming the release that lifts the refusal — and pricing the model under `model_prices` is the way round it (that entry replaces the catalog's row, and with it both switches). A route without the two keys already gets their defaults — `require_zdr: true`, `price_policy: cheapest` — which is what the rest of this paragraph describes. A model OpenRouter serves at several endpoints has a price *range*, not one price: `require_zdr: true` (the default) prices the endpoints that hold no data, `false` prices every endpoint the model is served by, and `price_policy` picks the end of that set's range — `cheapest` (the default) or `highest`. Neither switch chooses the endpoint OpenRouter serves the request from, so a call can still be billed at the other end of the range: the paragraphs below state how far off that can be, and the four things that bound it. `require_zdr` is a price, not an enforcement — Fugaro cannot read your account's data policy, which is where zero-data-retention is actually decided (§1), and `fugaro doctor` says so (OpenRouter's key endpoint, `GET /api/v1/key`, has no data-policy field to read). A model the catalog does not price, and every route that is not OpenRouter, is priced by `model_prices`; a `require_zdr: true` route on a model with no ZDR-eligible endpoint is refused rather than priced at the retaining endpoints — a pin or a call that names the model, not the whole route: the route's pattern claims a family, so the other models it claims stay priced, and `fugaro budget prices` lists the model it could not price with the reason. Once that refusal lifts, changing either takes effect on the next run only after `fugaro update --repo` is run again, like every other provider field.

**The prices come from the built-in catalog, not from you.** Fugaro's own provider price catalog prices every model a route claims **that the catalog carries**: a file generated from OpenRouter's public API by `scripts/gen-price-catalog.sh` and built into the binary (the one this release ships was read on 2026-10-23 and prices five models — each model's range over its endpoints, not one provider's quote). A model a route claims that the catalog does not carry — any `openai/gpt-5*` claim is one today — gets no row, and only a `model_prices` entry of yours can price it; the missing-price refusal comes at the model the run **names** (the pins, `agent.model`, a `budget.allowed_models` entry), never at the pattern that claims it, because a pattern claims a family and only the IDs you name have to be priced (`CheckProviderPolicy`, `internal/config/providers.go:559`; "The senior reviewer on a provider route" below says the same thing from the role's side). Nothing is fetched at run time, and **you do not need a `model_prices` entry to get a catalog-priced model priced**: `fugaro budget prices` shows such a row's `CATALOG` column (`zdr/cheapest`, `all/highest`, …), the tier's endpoint count and the day the catalog was checked, under its own `provider price catalog: …, checked … (N days ago)` line, and `fugaro doctor --all` prints the same age. Past the catalog's **30 days** the run stops trusting the cheap bound: every catalog-priced model is charged the **dearest end of its tier's range**, the log carries one `budget: price catalog stale` WARN and `result.json` sets `cost.catalog_stale: true` — the run over-counts on purpose rather than refusing, which keeps a stale catalog from silently under-pricing. `budget prices` and `doctor` warn at the same 30 days; the fix is to regenerate the file (the release checklist has that line) and commit it.

**Your `model_prices` still wins, whole.** An entry for a model the catalog prices replaces that row entirely — the price, and with it both switches: the route's `require_zdr` and `price_policy` choose the bound of the *catalog's* range, so they have nothing left to select once your own price is the row. That is the escape hatch for a model the catalog mis-prices or does not list at all, and it is the **only** way a non-OpenRouter route is priced (§1: the catalog covers OpenRouter's models). A model with neither a catalog row nor a `model_prices` entry is refused rather than guessed. The unverified-placeholder mechanism is still there for a future provider row — none ships now that the catalog prices these models — and such a row is accepted with a warning (`fugaro validate`, `diagnose`), the cap counting that guess, with `fugaro budget prices` marking it in its `VERIFIED` column. When you leave out the cache fields of an override, they default to the usual multiples of `input_per_m` (never to 0).

**In a project that publishes a policy, the prices, the ceiling and the routing come from the policy.** A run of a repository whose project has published `config/policy/shared` ([design/project-centric.md](design/project-centric.md)) takes `model_prices`, the budget mode, the per-run ceiling, `allowed_models`, `max_run_tokens` and `routing.claude` from that node, not from the copy in its job's environment: the job's environment is what the run reads when the project has published nothing. So the way to change a price or a routing switch in such a project is `fugaro project policy publish` — one edit for every repository — and `fugaro update --repo` no longer needs re-running for it (`fugaro upgrade`'s drift note says which keys that leaves). **`providers` is the exception, and it is the one that decides what a routed call costs and where it may go**: the node carries a `providers` block, `fugaro project policy publish` writes it and `fugaro validate` checks the switch against it, but a run routes by the copy in its **own job's environment** — the one cut down to that repository's `allow_data_to`, whose key name is the secret mounted on that job — so a change to a provider (its base URL, `models`, `allow_data_to`, `route_fee_pct`) still needs `fugaro update --repo` for every repository, and a `routing.claude` switch published in the policy resolves against the providers that job carries. Name a provider your jobs already have. The catalog below is unchanged by any of this: it fills the models the policy does not price, and the policy's own `model_prices` entries replace its rows exactly as the local config's do. A job that cannot reach the node — no `FUGARO_RTDB_URL`, or rules older than the marker `config/limits/policyRules` — is a run that halts rather than one that falls back to its environment copy, which is why `fugaro doctor` reports both states.

**`routing.claude` is the switch that sends a Claude model down a provider route, and only you can write it.** The object is `routing: {claude: {via: direct | openrouter | auto, models: [...]}}` in your local project config, and `fugaro project policy publish` copies it into `config/policy/shared`, which is where a run reads it; a repository's `fugaro.yaml` has no `routing` key and cannot write one. `models` is an **explicit list of canonical Claude IDs** — `claude-sonnet-5-5` as a pin spells it, one ID per entry, never a pattern and never a route's spelling — and that list *is* the opt-in: **an absent switch, and every model the list does not name, mean `direct`**, which is what every call does today. The two open vias are held to the safeguard in [design/project-centric.md](design/project-centric.md) §6.2: `openrouter` and `auto` resolve to a provider **only when that provider's `allow_data_to` is written** — a list, or the explicit `["*"]` — so "not decided yet" and "every repository" are never the same state on the one path that sends a Claude prompt to a third party; an empty list counts as not written, and a switch naming a model no route entry claims, or one two claim, is refused at load rather than resolved by an alphabetical accident. Routing needs the gateway, so like every provider call it happens under `budget.mode: enforce`. `fugaro validate` prints the resolution — `routing.claude: claude-sonnet-5-5 -> openrouter, sent as anthropic/claude-sonnet-5.5` — when it can read your config; it says `unresolved offline` when it cannot (a project config that is there and will not load is a problem of its own instead: the loader's reason, and a non-zero exit), and it notes a Claude pin the switch leaves on the direct route whose call would need the Anthropic key — whether the job holds one is not a fact this command reads offline, so the line names both states, the job with a stored key that sends the call to Anthropic as it stands and the job with none that halts — naming the line to write (`routing.claude: openrouter`, with the ID in `models`). `fugaro doctor --all`'s `routing-resolution` check prints the same resolution from the published policy, over this machine's own routes: each repository's `allow_data_to` filter, with the `claude_models` claims this checkout's project layer resolves merged in, which is exactly how a run merges them — and it names the layer as a reason it cannot be sure of, for a repository whose `fugaro.yaml` this machine has no checkout of. **What a routed Claude senior *costs* is a live question with a number attached**: whether a provider route reports `cache_read`/`cache_write` tokens at all is unmeasured, and a routed Claude that never reports a cache read is charged the full input rate instead of the cache rate — for a long senior review, the difference between list price and several times list price (design §6.2). The run that measures it is **Check 50** ([docs/gcp-live-checklist.md](gcp-live-checklist.md)) — **not run yet** — and until it is, `fugaro doctor --all`'s `routing-cache-markers` check says so.

**`cheapest` can undercharge, and this is the size of it (P11).** The switch prices a tier; it cannot choose the endpoint OpenRouter serves a request from, and OpenRouter's own routing picks among the endpoints your account allows, weighted by the inverse square of their price — so a dearer endpoint is served routinely, not as a rare fallback, and the cheapest one may be the unhealthy one (measured 2026-10-14, the cheapest `deepseek/deepseek-v4.1-flash` endpoint reported `status: -5` and 73.3% uptime over 30 minutes). The spread over that model's ZDR-eligible endpoints in the catalog this release ships is **8.6x on input and 13.3x on output** — the multiples `fugaro budget prices` and `fugaro validate` print from the row itself ($0.07–$0.60 input, $0.18–$2.40 output; the same row is regenerated each release, so the multiples move with it) — and 3.2x / 4.3x over the four providers the owner's own account allows, so a run charged the $5 cap can really cost about **$43–67**: the undercharge is dollars, not only accuracy, and the caps and the ledger are computed from the charge, which makes a cap bind later than the ledger claims. **Four things bound it:** (1) the dollar caps and `max_run_tokens` — they still stop the run, the reservation is still an upper bound on the reserved path, and the only hard bound on what leaves the account is the key's credit limit (§1); (2) the account's own provider allow-list, which *narrows* the set the weighting chooses from — OpenRouter documents that load balancing is disabled when `sort` or `order` is set, and whether an account setting **alone** pins the served endpoint is unverified (Check 44 step 5 records which provider serves), which is why §1 asks you to narrow it anyway; (3) the provider-reported cost (`usage.cost`), recorded beside the charge and never used to settle a call the table priced — it floors the conservative charge for an unpriced service tier (§6), and only that: `fugaro diagnose` compares the two and warns above a 10% gap, naming `price_policy: highest` and `model_prices` as the two answers — it is the one signal that sees a real undercharge *and* a price rise no age check can; (4) `price_policy: highest`, which charges the top of the selected tier and is the setting to use whenever the cap must be an upper bound — a first run against a new model, a costly batch. `cheapest` stays the default because it is what the marketplace's list price means and it matches OpenRouter's own default; `highest` over-charges every call for a bound most calls never reach.

## 3. The key

From a checkout of the repository (any listed repository), paste or pipe the key; it is read only from stdin, never an argument, and never printed:

```bash
fugaro secrets set openrouter-api-key
```

It is refused for a repository an explicit, non-empty, non-`["*"]` `allow_data_to` excludes; a provider with an absent list (or `["*"]`) is available to every repository, and one written with no repositories in it is refused by the local-config validator. The key is mounted into the runner's environment only (as `FUGARO_PROVIDER_KEY_OPENROUTER_API_KEY`) and, for workflows with `agent.auth: api-key`; the agent's own environment never has it, and it is registered with the log redactor. A workflow's own `secrets:` may not use the provider's secret name.

**One key for the whole project, and it is the default.** `fugaro secrets set openrouter-api-key` (stdin or the hidden prompt, never an argument) stores the key once for the installation, in the project's own container — no flag needed, and `--project-wide` is still accepted as a synonym so scripts written before this default keep working. `--repo <owner>/<name>` is what stores one repository's own copy instead. Since project scope is the default, `fugaro update --repo`'s own prompt stores the value it asks for project-wide too; the prompt has no `--repo` to pass, so the way to this repository's own copy is to press Ctrl-C at it, run the command it printed (`fugaro secrets set <name> --repo <owner>/<name>`) in your own terminal, and start `fugaro update --repo` again. A name the project's copy already covers is not asked for at all — `bitbucket-token` excepted: a repository access token serves one repository, so it is stored per repository by default; the prompt offers it project-wide only through an explicit `project_secrets` allow-list entry, which is what an operator holding one workspace or project access token for many repositories writes ([docs/git-providers.md](git-providers.md#one-workspace-or-project-token-for-many-repositories)) (`config.PerRepositorySecret`, `infra.ProjectSecretCandidate`; SECURITY.md, "Narrow git credentials"). The repositories that may mount the key are the ones this provider's `allow_data_to` already allows — the same list, not a second one — and a repository that has stored its own copy keeps using its own (a repository copy with an enabled version wins; disabling that version falls back to the project's only after the next `fugaro update --repo` for that repository, which replaces the job's IAM member and so needs `--allow-delete`). `fugaro doctor` lists which copy each name resolves to and warns when a repository copy shadows the project's, and `fugaro upgrade`'s drift note says that a project-scope copy created or deleted after a job's apply changes what that job mounts only on the next `fugaro update --repo`. Who may pin a model to the provider is unchanged. The owner's `project_secrets` block does the same for the four reserved names; see [design/project-secrets.md](design/project-secrets.md).

**The Anthropic key is needed only for the models that use it.** With `agent.auth: api-key`, `anthropic-api-key` is needed exactly when a call actually goes to Anthropic: a pin no provider allowed to see this repository serves (a Claude reviewer above all, and any other Claude or unclaimed model), or a budget mode other than `enforce` — without the gateway nothing routes a call to a provider, so every call is direct whatever the pins are. With `oauth` or `vertex` it is never needed. So a run whose coder, reviewer and background models are all served by a route that may see this repository needs no Anthropic key; the job still mounts the secret whenever it has a version, and a call that needs one without it is refused at run time with `fugaro secrets set anthropic-api-key`, never sent elsewhere. `config.AnthropicKeyNeeded` is that one rule, and both `fugaro update --repo` and `fugaro validate` ask it.

## 4. The repository's `fugaro.yaml`

```yaml
agent:
  auth: api-key
  models:
    coder: deepseek/deepseek-v4-flash
    reviewer: claude-sonnet-5-5
    background: claude-haiku-4-5      # optional: with a provider coder it defaults to the coder's model
  first_line_review: auto             # auto | on | off
  first_line_rounds: 1                # 1 to 3
  levels:                             # each review level's own settings
    l1: { model: claude-haiku-4-5 }   # the first line; without it, the coder's own model
    l2: { effort: high }              # the senior round
    l3: { model: claude-opus-5-5 }    # the adversarial round
  adversarial_rounds: 3               # review level 3's rounds, 1 to 10
```

`agent.levels` is the per-level block: `l1` is the first line of review, `l2` the senior round and `l3` the adversarial one, and each level takes the same four keys — `model`, `effort` (`low`, `medium`, `high`, `xhigh`, `max`), `focus` (what the reviewer is asked to look at, up to 500 bytes) and `none: true`, which turns the level off and is refused beside any other key, since a level that does not run has no settings. A level left out keeps what its layer already resolves — `l1` on the coder's model, `l2` and `l3` on `agent.models.reviewer` — and the project layer sets the same block under `defaults.agent.levels` for every repository of the project. The two layers merge **key by key**, not block by block: a repository that writes `l2: { model: ... }` keeps the project's `l1` and its `l3: { none: true }`. `none` is the one key that is not merged that way — a level that is off has no other keys — so `none: true` **replaces** the level the layer below set rather than merging into it, and a level that writes any other key turns the project's `none` back on: a repository can turn a project's level off, and one the project turned off back on. `agent.adversarial_rounds` is the one round knob of level 3 — 1 to 10, and unset means the resolved rigor mode's own senior row decides (poc and hotfix 1, startup 2, pro 3, critical 5), which is why no value is written into a config that does not name it. The block and the key both need Fugaro 0.16.0.

The catalog recipes `standard` (a first-line loop by the coder's model, then one senior round) and `solo` (the coder's model also reviews) package the common shapes; see [recipes.md](recipes.md).

`fugaro validate` checks the config-side rules above against the local config (a provider that claims the model, `allow_data_to`, `agent.auth`, the gateway being on, variants, prices); it cannot see whether the key is mounted or well formed, which only the runner refuses. **It is a check, not the gate**, and it is quieter than the runner in ways worth knowing before you read a clean report: it judges providers and pins only when the local config it finds is this repository's own project's (with none, or one for another project, it says nothing about either); an `oauth` workflow's pins are not judged at all (nothing is priced or pinned without a gateway), though its provider models still are; and if the project config's `model_prices` cannot be read, it reports that under `model_prices` when the budget is on and says nothing about it with the mode off — in both cases skipping the provider rules rather than judging against a table it does not have. The run refuses all of it on every launch (`checkProviderModels`), whatever validate printed. With a provider coder and a Claude reviewer, `first_line_review: auto` makes the coder's model review and fix its own work first (`review_first` stages, recorded with `tier: first`); the Claude `review` always runs afterwards and alone decides whether the pull request is ready. The first line is priced as the provider model, so it adds cents; it can only add cost, never replace the senior review.

## 5. What is refused, and why

Each is an `infra_error` before any model call, naming the pin and the rule (and `fugaro validate` reports the same):

- **No provider claims the model**, or the provider's `allow_data_to` is a real, non-empty, non-`["*"]` list that does not name this repository. Code only goes where the owner said it may; an absent list (or `["*"]`) means every repository, on purpose.
- **`agent.auth` is `oauth`, `vertex` or `cascade`.** An OAuth token is a Claude subscription credential and is never sent elsewhere — and a cascade run's own tier A is one of those tokens — so a run does not mix credentials. Use `api-key`.
- **The gateway is off or only observing** (`budget.mode: off` or `observe`). The gateway is what holds the key and prices the calls, and only `enforce` refuses a call that would go over a cap. A project that has published a project policy ([design/project-centric.md](design/project-centric.md)) has no `off` to offer here: a run reads that policy out of the project's own database, so its jobs must carry the Firebase backend, and an installation that wants the budget off stays on the per-repository path.
- **A variant suffix (`:free`, `:nitro`, `:online`) or an alias.** A variant is another price and routing; pins are exact upstream IDs.
- **No price** for the model (add it under `model_prices`), or an entry in `budget.allowed_models` or the pins that the owner's allow-list does not carry.
- **A provider key that is not mounted**, or has whitespace, a control character or non-ASCII, or fewer than 4 bytes.

At run time the gateway also refuses a request whose model is not pinned for the stage, and answers token counting for a provider model with a local 404 (Claude Code then estimates itself).

## 6. Reading the cost

Provider models are real dollars: the charge is the table price of the reported usage plus the route fee. **What is measured:** on a streamed call the gateway merges the usage every `message_start` and `message_delta` event reports (the largest each field ever claimed; cumulative counts never lower a call's charge) and decides whether the call settles from that usage only once the stream ends (`message_stop`, or a clean end of a non-streaming body) — not from `message_start` alone. A provider may report an all-zero usage at `message_start` and put the real, cumulative counts only in `message_delta` (OpenRouter routing to `deepseek/deepseek-v4.1-flash`, served by DeepInfra, did exactly this in a captured run: `message_start`'s `usage.input_tokens` was `0` with every cache field `null`, and `message_delta` carried `input_tokens:32`, `cache_read_input_tokens:0`, `output_tokens:47`); the gateway reads that as 32 input and 47 output tokens, not as a reply that said nothing. Zero input alongside a real cache read (heavy caching) is the same: priced from whatever was reported, never read as silence — **but only once `input_tokens` has been reported at all, even as an explicit `0`.** A usage object that never includes the `input_tokens` key in any event, OWNER RULING, has left input out entirely, not merely reported it as zero: that settles at the reservation regardless of a real cache read elsewhere in the same usage, the same as main did (a round of this PR briefly read a cache read alone as enough, with or without the key; that reading was reverted). Zero input (and no cache, or the key never reported) alongside a real output count is the general case: a real request always sends some input, so a provider whose usage never names one, cache included, simply left the field out, and the call settles at the reservation like any other missing field, whatever output it produced.

**What is estimated, and the fail-safe:** when the merged usage never names an input, cache read or cache write count at all — a real request always sends some input, so a provider whose usage is silent on all three left the field out, whatever output (or text) the response held — the call is charged its full reservation instead (`usage_unparsed` in the run's report, a WARN log line per call). So is any call whose usage the gateway could not read at all: a response with no usage event, one with a negative count (never trusted, whatever a later event claims), a `message_delta` whose usage didn't parse, or a stream that broke before it finished (partial settlement then charges the reported input and cache plus the reserved output — see `TestPartialSettlementCarriesFee`, `TestCutProviderStreamChargesPartial`). The WARN line (`budget: usage unparsed`) names one `reason`, from a closed set, and the event type names seen, never the provider's own text:

| reason | meaning |
|---|---|
| `no_usage_event` | no event (or body) ever carried a usage object |
| `input_zero_no_cache` | usage was read, but input and every cache field were zero or missing: a real request always sends some input, so the provider left it out |
| `negative_count` | a reported count was below zero |
| `malformed_usage` | a `message_start` or a `message_delta` carried a usage object the gateway could not parse |
| `stream_incomplete` | the stream never reached `message_stop` (and never said enough to partially settle either) |
| `no_output_count` | input (or cache) was real, but no `message_delta` ever named an output count |
| `not_readable` | the response body's encoding isn't one the gateway decodes |

**This also touches the Claude route, as a side effect, not a redesign of it.** The negative-count and malformed-usage guards above (and the `budget: usage unparsed` WARN line itself) live in code both routes share, so two Claude-route outcomes changed along with the provider-route fix: a `message_delta` the gateway can't parse, or one with a negative count, arriving *after* `message_stop` (the call already read as complete) now settles at the reservation on the Claude route too, where it previously settled at usage from whatever the stream said before that event — stricter for the malformed case, and a fix for an existing undercharge for the negative one (the negative count was floored to zero by `usage()`, the same bug the provider-route fix closes). "Can't parse" is the same unparseable-usage path whether the cause is a JSON type mismatch, a `message_delta` whose `usage` is `null` or missing the key entirely, or an event whose own name doesn't match `message_delta` at all (silently skipped, so nothing merges and the call is left exactly as it was before that event) — all three read the same way once the gateway can't trust what follows `message_stop`. `TestClaudeMalformedDeltaAfterStopChargesReservation` and `TestClaudeNegativeDeltaAfterStopChargesReservation` (`internal/gateway/ledger_test.go`) pin the two outcomes above. There is a third Claude-route difference: a negative count in ANY `message_start` (a duplicate or late one included) now marks the call broken on both routes, so it settles at the reservation (main let a later valid duplicate `message_start` overwrite the negative one and settled at usage). These three are the **only** Claude-route differences from main, and each is stricter: the call settles at the reservation where main settled at usage. The reservation is a strict upper bound on every allowed shape, so the only case where it is LOWER than what main charged is a report impossible for the request (a usage above the call's own worst case, e.g. output 1e11 with `max_tokens` 1000): the review's 259 such Claude-route probes and 691 such provider-route probes are all of that kind. An unreadable `message_start` is a provider-route-only fix (`TestClaudeMalformedMessageStartChargesReservation` pins that the Claude route is unaffected — `message_delta` is already gated on `started`, which an unreadable `message_start` never sets, so main's behavior holds either way), and the `input_tokens`-key ruling above applies to both routes identically (the Claude route never read a bare cache read as enough in the first place). Otherwise the Claude route is unchanged: same counts, same rates, same settlement for every shape it saw before. The one purely cosmetic change is that the WARN line can now fire for a Claude call too, whenever one settles unparsed (which could already happen, e.g. `TestIncompleteUsageChargesReservation`'s cases) — a new log line, never a new charge.

When a response carries no cache fields at all, all input is charged at the full input rate (never split into a cheaper cache rate it didn't report). Both this and the fail-safe above err high, never low, **relative to the true cost of the call** — not relative to what a more conservative earlier version of this code would have charged for the same response. Read naively, "never low" could look broken: reading usage from a shape the gateway used to fall back to the reservation for (zero input with a delta's real counts; a usage-bearing delta that arrives before `message_start`; input split across more than one delta; data-only SSE lines with no `event:` name; `message_start` with no `usage` object at all, followed by a delta that has one; `cache_creation_input_tokens` alone with input 0; a non-streaming body with `input_tokens` explicitly `0` and a real cache read; a stream with no `message_start` at all (text, then a delta carrying usage, then stop); a `message_start` whose usage lacks the `input_tokens` key or has it `null`, followed by a delta that carries the key; a `message_delta` after `message_stop` that names real input when the start had no usage (settles **partial**: reported input plus the reserved output); a stream cut after a delta that named real input, which settles **partial** — reported input plus the *reserved* output, not the full reservation) always charges *less* than the reservation fallback did, re-confirmed by running all eight (plus the two reverted shapes below) against both this branch and `main` directly. Every one of those is the fix working as intended: the reservation was never the true cost, only the safe upper bound the gateway fell back to when it could not read the usage; once it can, it charges what was actually reported (or, for a cut stream, the reported input and cache plus the output's own safe upper bound), which is always at or below the reservation, never below the true cost itself.

Two shapes a prior round of this fix also charged less than main for are reverted, by design, to match main exactly rather than charge less: a `message_start` whose usage object fails to unmarshal (a JSON type mismatch, not a missing field) now sets the same broken flag an unreadable `message_delta` already did, so a later delta can no longer settle the call from whatever it alone reported; and a usage object — in any event, stream or whole body — that never includes the `input_tokens` key at all, however real a cache read elsewhere in it, settles at the reservation, not from the cache read alone (the explicit `input_tokens: 0` case above is the one that still settles from usage; the key's total absence does not). Both are confirmed, probe by probe (a matrix of over 114,000 cases per run of the review), to charge at least what main did, except where main charged a usage above the reservation (an impossible report): there the reservation is charged instead, which is still at or above the true cost of any real call. Whether OpenRouter's responses carry usage and cache fields in the general case (beyond the one captured run above) is assumed until Check 25.

**A service tier the table does not price is charged, not fatal.** A provider may answer a call at a service tier for which the price table holds no multiplier — OpenRouter's DeepSeek answers `priority` — without the agent having asked for anything. Such a call is charged at `pricing.ConservativeTierMultiplier` (2) times **the rates it would otherwise be priced at** (the serving model's own, or the table's maximum for a model the table doesn't know), the dearest multiple the table knows: never the standard price, which under-charges a tier that costs more than it, and never free. It is deliberately not the table's maximum rates — a tier premium is a multiple of what the model costs, and charging a cheap model a dear one's rates would multiply the record and the shared day counters by tens and halt a run on a cap its own rates would have stayed under. The multiple is an assumed ceiling, not a published price, so on a provider route that reported what the call cost (`usage.cost`) the charge is the dearer of that multiple and the provider's own figure plus the route fee: the report floors the charge, and it can only raise it, never lower it. The floor stops at the reservation the call already made — the report is the one part of a charge the gateway cannot check against anything of its own, so it may raise a charge to the reservation and never past it — which is also why a report can never turn a call into an overrun; a charge above the reservation stays what the call's own usage made it. The charge is whole and counted against the run's and the day's caps like any other, so a call that would carry the run over its cap is still refused; a charge above its reservation counts as an overrun. It is recorded, not refused: `cost.service_tiers` in `result.json` (which `diagnose` prints as its `Tier:` line), the stage report's `ServiceTiers` (`usage.service_tier "priority"`), the `model call` line's `service_tier`, one `budget: service tier not priced` WARN per call, and one `budget: service tiers charged conservatively` WARN per stage — and the stage goes on. What is bounded is the **list**: `cost.service_tiers`, the stage report's list and the stage's WARN name at most eight distinct tiers, then one `+N more` entry counting the distinct tiers beyond them, so a provider that never repeats itself cannot grow the record with the call count. The per-call WARN and the `model call` line are not bounded that way — each names the one tier that call came back at. The table prices no tier other than `standard`, because no provider publishes a multiplier for another one; a documented multiplier belongs in the table as its own number, beside the rates it scales, with a source and a `checkedAt`.

`fugaro diagnose <run>` shows:

- `Cost:` the run's total, as for any run;
- `Route:` the spend by route (`openrouter`; `unattributed` may include late Claude spend);
- `Reported:` what the provider said the calls cost, beside what was charged (that the response carries a cost at all is assumed until Check 25). The table price settles, with one exception: an unpriced tier's charge is floored by the provider's report (clamped to the call's reservation), so there the charge may be the report rather than the table's figure. A large, lasting gap means a wrong `model_prices` entry, or a fallback you did not pin: fix the price, or the account's provider settings;
- `Warning:` the unverified-price warning, until you set the real price — or, on a catalog-priced model, the note naming the tier, the bound charged and the endpoint count behind it (§2);
- a `usage_unparsed` count above zero: some calls settled at their reservation instead of their usage; the run's log carries the reason and event types for each;
- a `Tier:` line when a call came back at a service tier the table has no multiplier for: it names the tier and says the charge is the conservative multiple of the rates the call was priced at — or, on a provider route that reported a cost, the dearer of that multiple and the provider's own reported cost with the route fee (the paragraph above), which is what explains a `Cost:` figure nothing else on the line accounts for. The clause is printed only when the record carries a provider-reported cost at all: a Claude call has no route, so it has no report to name.

`result.json` has `cost.model_by`, `cost.route_by`, `cost.reported_usd`, `cost.usage_unparsed`, `cost.catalog_stale` (see §2) and `cost.service_tiers` (the tiers above that the table has no multiplier for), and each entry of its `stages` array carries `model_usd` and `model` too: what that stage's calls cost (the gateway's figure when the gateway ran, else the result event's own `total_cost_usd`) and the model the stage was pinned to, so spend can be read per stage rather than only per run. `model_usd` is the stage's whole spend, the background model's calls included; `model` is what the config pinned, never what the upstream served, so it does not account for `model_usd` on its own — a stage that also called the background model, or one the upstream served under another name, is only fully explained by the run's own `cost.model_by` and the `model call` log lines below. The one precise relation, to the micro-dollar, is

```
sum(stages[].model_usd) + cost.model_by["unattributed"] == cost.model_usd
```

— a gateway call that settles after its stage's wait ran out is counted in `cost.model_usd` and in `cost.model_by`'s `unattributed` only, in no stage, which is the whole of the difference. Records written before 0.8.0 have neither field. The runner's `model call` log lines carry `route`, `serving_model`, `priced_as`, `settled` and `reported_micros`. `serving_model` different from the pin means OpenRouter served something else (that the response names the serving model is assumed until Check 25).

**On the next DeepSeek run, check `fugaro diagnose <run>` for two different things.** First, `usage_unparsed` should read `0`; if it is still above zero, the log's `reason` and `events` on the WARN line say why (the real SSE shape above was captured from one live run, not exhaustively, so it may be a shape the parser doesn't yet tolerate, not necessarily the one fixed here). Second, and separately, **check that the charge matches what the served model really costs.** The captured run's `message_start` named `deepseek/deepseek-v4.1-flash`, while the workflow pinned `deepseek/deepseek-v4-flash` — a different model ID, and until this change a model the table had no row for, which priced the call at the table's **maximum** rates (`priced_as: max` in the log, a warning naming both models, about 100x too high for a model this cheap). Both IDs are priced from the built-in catalog now (§2), each over its own endpoints, so that particular mismatch no longer over-charges by 100x — but the lesson stands, and it is the reason `diagnose` compares the provider's reported cost with the charge: prices are provider-specific even for one model, and the endpoint that serves a request is picked per request (the undercharge paragraph in §2). The `model call` line's `serving_model` says what OpenRouter actually served; if the run needs a number you trust more than the catalog's range, pin the model you mean and, when you know the provider that will serve it, set the price yourself under `model_prices` — that entry replaces the catalog's row (and both switches with it).

## 7. Known limits

- `fugaro report --by route` does not exist yet (the history has no route split); `--by model` works only with spend history on, and shows a subscription model's dollars under NOTIONAL~, never MODEL $.
- The provider key is in the runner's memory (the D2 residual of the gateway): use the per-project credit limit. Besides `/proc/<runner>/environ`, a prompt-injected agent can reach the job service account's metadata token, and that account has `secretAccessor` on the mounted provider secret, so it can read the key itself. The credit limit on the key is the real backstop; the gateway's pins and caps do not bound a key the agent holds.
- A provider route passes only these top-level body fields (`routedKeys` in `internal/gateway/forward.go`): `model`, `max_tokens`, `messages`, `system`, `stream`, `tools`, `tool_choice`, `temperature`, `top_p`, `top_k`, `stop_sequences`, `metadata`, `thinking`, `output_config`. `metadata` may hold only `user_id` (Claude Code sends `metadata.user_id`, a device-hash identifier, on every request and the gateway never rewrites a body, so the provider sees it; the impact is low). Any other field, or any other key inside `metadata`, is refused as a violation, because it could bill outside token pricing or override the account's data policy: OpenRouter's `plugins`, `provider`, `models`, `route`, `transforms`, `usage`, `web_search_options`, and also Messages API fields the budget doesn't price on this path (`context_management`, a top-level `cache_control`, `output_format`, `speed`, `service_tier`, `inference_geo`, `container`, `mcp_servers`). Whether a request that Claude Code builds for a provider model carries one of these is recorded by Check 25; the list is widened only on that live evidence.
- Claude Code features that a compatible endpoint may not support (extended thinking, beta headers, server tools) surface as the upstream's error and fail the stage; which of them break is assumed until Check 25 records it. The same holds for token counting: the local 404 for a provider model is a design choice, and how OpenRouter's `count_tokens` answers is assumed until Check 25.
- **`context_management` is refused before any provider ever saw a request (sandbox run `edgeappinc-fugarosandbox-27be4c45d773e3b9/20261013-013356-9966`, $0 cost).** Measured locally against the real Claude Code **2.1.296** pointed at a recording localhost server (a dummy key, a throwaway config dir, no cloud call): for a provider model, Claude Code's first request carries top-level `context_management` (`{"edits":[{"type":"clear_thinking_20251015","keep":"all"}]}`) whenever `thinking` (`{"type":"adaptive","display":"omitted"}`) is on, which it is by default; the session's first request also carries a top-level `safeguards` key. ### How the pinned Claude Code takes an effort setting (L0.1, U1)

Measured on 2026-10-30 against Claude Code **2.1.283** (the `images/base/Dockerfile` pin, installed from npm into a scratch directory), with the same method as the measurements above: each probe ran `claude -p hi --model <M> --max-turns 1` under `env -i` in an empty home directory, with a placeholder API key and `ANTHROPIC_BASE_URL` pointed at a loopback server that recorded the first request's `output_config`, `thinking` and `max_tokens` and answered 400. Nothing left the machine, so this is what the client sends; whether the API accepts each value per model was not measured live.

| Mechanism | Result |
|---|---|
| `--effort <level>` flag | Works. `--help` lists `low, medium, high, xhigh, max`; each is sent as `output_config.effort`. A bogus value prints `Warning: Unknown --effort value 'bogus' — ignoring it and using the default effort` on stderr and the model's default is sent. |
| `CLAUDE_CODE_EFFORT_LEVEL` environment variable | Works, same values. A bogus value is ignored silently (the default is sent). `unset` sends no `output_config` at all (the binary treats `auto` the same way; not probed). |
| `effortLevel` settings key (`--settings`) | Works for `low`, `medium`, `high`, `xhigh` only: its schema has no `max`, and `max` or a bogus value is dropped silently (the default is sent). |
| `maxEffortLevel` settings key | A cap, not a setting: `--effort xhigh` and `CLAUDE_CODE_EFFORT_LEVEL=xhigh` were both sent as `medium` under `{"maxEffortLevel":"medium"}`. Across settings files the lowest cap wins, so a managed settings file can lower any of the three mechanisms. |
| `CLAUDE_EFFORT` | Not an input: Claude Code sets it for hooks and Bash to read the active level. |
| Precedence | The environment variable beats both the flag and the settings key (`CLAUDE_CODE_EFFORT_LEVEL=low` with `--effort high`, or with `effortLevel: high`, sent `low`); the flag beats the settings key; `maxEffortLevel` clamps the result. |
| `claude-opus-5-5` | Sends `output_config.effort` for every level; default `medium`. |
| `claude-sonnet-5-5` | Sends `output_config.effort` for every level; default `high`. This version's model catalog does not know the model (it warns `isn't described by this version's model catalog`), so the default may change with the next pin. |
| `claude-haiku-4-5` | Never sends `output_config`, whichever mechanism or level, also with `CLAUDE_CODE_ALWAYS_ENABLE_EFFORT=1`; it sends `thinking: {"type":"enabled","budget_tokens":31999}` instead. An effort setting does nothing for it. |
| With `MAX_THINKING_TOKENS=0` | The effort survives: opus and sonnet drop `thinking` and still send `output_config.effort` (flag or environment variable). Haiku sends `thinking: {"type":"disabled"}` and still no effort. |
| `--output-format stream-json --verbose` | The level does not appear: the `init` event carries only `per_turn_effort_active: true`, and neither the `assistant` nor the `result` event names it (only an error result could be observed offline). A run record cannot read the effort from the stream; it has to record what it set. |

So a per-process mechanism exists, and L4.3 stands. It should set `CLAUDE_CODE_EFFORT_LEVEL` in the stage's environment: it wins over a `--effort` flag and an `effortLevel` in any settings file, and its closed set is `low, medium, high, xhigh, max`. It is still clamped by a `maxEffortLevel` in any settings file, the managed one included, and it is a no-op for Haiku 4.5. Because a bogus value is ignored silently rather than refused, Fugaro has to validate the value against that closed set before it reaches Claude Code.

## The senior reviewer on a provider route

The reviewer does not have to be Claude. Any model a route serves can be the senior — GPT, Gemini, a larger DeepSeek or Qwen — and that case needs no rule of its own: the route table and the prices are the ones §2 describes, the key §3's, and a different family reviewing a DeepSeek diff is a better second opinion than the same family reviewing itself. **This is Phase 1 of the senior-reviewer work, and it ships no product code** — this section, the two tests Phase 1 is for (PR #413) and one live check (Check 45). The design recommends the non-Claude senior as the first step, before any Claude senior ([design/mixed-credentials.md](design/mixed-credentials.md) §1), and the plan that carries the work is [plans/2026-10-14-openrouter-senior-reviewer.md](plans/2026-10-14-openrouter-senior-reviewer.md). The other half — a **claimed Claude** senior, one exact `anthropic/<id>` in a route's `models` — is a little further down, in "Direct to the vendor".

The recipe, in the two files it lives in:

```yaml
# ~/.config/fugaro/projects/<project>.yaml — the owner's local config (§2)
providers:
  openrouter:
    kind: anthropic-compat
    base_url: https://openrouter.ai/api
    auth: bearer
    secret: openrouter-api-key
    route_fee_pct: 5.5
    models: ["deepseek/*", "openai/gpt-5*"]   # the senior's ID, exact or as a pattern
    allow_data_to: [acme/app]                 # the repository whose code may go here
model_prices:
  openai/gpt-5.5:            # its list price, until the catalog prices it (§2)
    input_per_m: 1.25
    output_per_m: 10
budget:
  mode: enforce              # a provider model requires the gateway in enforce mode (§2)
  per_run_usd: 2
```

```yaml
# the repository's fugaro.yaml — the coder stays cheap, the reviewer is the senior
agent:
  auth: api-key
  models:
    coder: deepseek/deepseek-v4-flash
    reviewer: openai/gpt-5.5
```

Then `fugaro update --repo` in the repository, as for any provider change (§2), and `fugaro validate` before the run: the provider rule, `allow_data_to`, `agent.auth` and the price are §5's, and none of them is different because the model is the reviewer rather than the coder.

**A pattern is allowed for the senior's vendor, and never for a Claude model.** `models: ["openai/gpt-5*"]` claims every GPT-5 ID that provider serves and the pin names the one you want. The restricted spellings are the Claude patterns, `claude-*` and `anthropic/*` (`config.ClaudePatterns`, `internal/config/providers.go:411`; the rule is `CheckModelPattern`, `:447`): a bare `claude-*` or `claude-<id>` entry is refused like an `anthropic/*` one, with the one exception "Direct to the vendor" describes — a route may list **one exact** `anthropic/<id>`, never a wildcard, prefix or family spelling. Everything else about the route is §2's: no two providers may claim the same model, and `allow_data_to` decides which repositories may send code to it.

**It is the pin that has to be priced, not the whole pattern.** `CheckProviderPolicy` (`internal/config/providers.go:559`) asks for a price for the models a run can **name** — the three `agent.models` entries (coder, reviewer and background), `agent.model` and every `budget.allowed_models` entry — so `models: ["openai/gpt-5*"]` may claim a family while only the ID you pin is priced: the example above prices `openai/gpt-5.5` and nothing else that pattern covers, and a model the run names with no price is refused rather than guessed (§2). The price comes from the catalog's row if it carries one — the five models it prices today are the DeepSeek ones (three IDs), Moonshot's and Qwen's, so the example's coder and a DeepSeek senior need no entry while its `openai/gpt-5.5` does — and from your `model_prices` entry if not.

**`auto` is off here, and that is the whole of the first half.** `first_line_review: auto` is on only when a provider serves the coder **and none serves the reviewer** (`config.Agent.FirstLineOn`, `internal/config/config.go:173-181`): with the senior on a route, the derived recipe runs `implement` then `review`, with no `review_first` stage and no `tier: first` entry, so the work is reviewed once, by the senior. The one-line reason the default is what it is: the senior already reviews, and a first line by the coder's own model would add a round without adding a reviewer. `first_line_review: on` (with `first_line_rounds` bounding the rounds) turns it back on.

**The second half: a recipe that names its own first line keeps it.** `auto` only ever governed the **derived** recipe — the catalog's `default`, and nothing else (`derived := rrec.Name == recipe.DefaultName && rrec.Source == string(recipe.SourceCatalog)`, `internal/runner/runner.go:954`; the skip is `internal/runner/plan.go:35`) — so a recipe carrying its own `first_line` step still runs it whatever `auto` says. The catalog's `standard` carries both `first_line: {}` and `review: {bounce: first_line}` (`internal/recipe/catalog/standard.yaml`), so `--recipe standard` keeps the cheap loop **and** its bounce-back with a provider-served senior, while `--recipe default` does not. Name the recipe when you compare the two, or the difference looks like a bug in one of them.

**The background model is the coder's.** With `agent.models.background` unset, Claude Code's small background requests follow the **coder's** model (`config.EffectiveBackground`, `internal/config/providers.go:670`), which on this recipe is DeepSeek: the senior's stage makes its background calls on the coder's model through the same route, and only its review calls are the senior's own. Pin `agent.models.background` to change that. And every one of those background calls is charged at its own model's price rather than the senior's, so the stage's spend is the senior's review calls plus a small DeepSeek line (§6 reads both from `cost.model_by`).

**Thinking, and the one arrangement the background rule is really about.** The senior's stage gets the provider's thinking variables because its **own** role model is on a route — that is the whole of it here (`internal/runner/agentenv.go:54-66`, the decision at `:71-78`). The rule reads "the role model **or** the background", and the clause earns its keep in the other arrangement: a stage whose own model is Claude but whose background defaults to a provider coder still calls that route, which is exactly the claimed-Claude reviewer §7's owner ruling is about — it runs without thinking unless `agent.models.background` is pinned to a Claude model. On this recipe both are routed, so pinning the background does not change the thinking variables; it changes which model serves those calls and what they cost, and pinning a **Claude** model there puts a call back on Anthropic — which needs the key the next paragraph says this run does not have, because `config.AnthropicKeyNeeded` reads the background pin like any other.

**No Anthropic key is needed, asked for or mounted.** With `budget.mode: enforce` and every pin served by a provider the repository may send code to, no call of this run reaches Anthropic, so: the runtime **drops** the `anthropic-api-key` mount when the secret has no enabled version anywhere (`OptionalSecret` marks that one secret — and only it — optional, `internal/infra/readiness.go:74`; the branch at `:195`, `dropMount` at `:215`), the runner wants the variable only with the gateway **off** (`internal/agent/env.go:92-105`), and `fugaro update --repo` skips the prompt when `config.AnthropicKeyNeeded` (`internal/config/providers.go:657`, reached through `needsAnthropicKey`, `internal/cli/validate.go:50`) says no call goes to Anthropic (`internal/cli/initsecrets.go:311`). **Do not store a placeholder: nothing asks for one** (PR #371). Two things stay true. A key you *have* stored is never sent upstream while no Claude model is pinned — the gateway attaches a provider's key to a routed call and Anthropic's only to a direct one (`internal/gateway/forward.go:851,857-868`) — so the provider's own key (§3) is the only credential OpenRouter sees. And a key that is **present** and shorter than 4 bytes is still refused, because it cannot be redacted (`internal/agent/env.go:101-102`, gateway on) — a refusal a keyless installation never meets.

**What it costs.** One key, one route, one gateway. The senior is charged the table price of its reported usage plus the route's `route_fee_pct`, which is added to **every** charge on that provider (`internal/config/providers.go:51`) — the senior's calls included, so the fee is not a coder-only line. It reads the diff (and the coder's work) at the provider's list price per million tokens, so the ceiling is `agent.review_rounds` × that diff at those rates, bounded by the `per_run_usd` cap exactly as the coder's calls are (§6 reads the result). **The §2 undercharge warning is the senior's too, and it is a direction worth getting right**: `cheapest`, the default `price_policy`, prices the cheap end of a model's endpoint range, and OpenRouter may serve a dearer endpoint — so the charge, the ledger and the caps all sit **below** what the provider bills, by the spread §2 measures (it names a run charged $5 that really cost about $43–67). For a senior that reads a whole diff on every round, the gap is multiplied by `review_rounds`, which is why the two things §2 gives the owner matter here more than for the coder: set `price_policy: highest` when the senior's cost must be an upper bound (the cap then binds at the top of the range), and read `fugaro diagnose`'s **reported-gap warning** — the provider-reported cost beside the charge, warned above 10% — which is the one signal that sees a real undercharge after the fact, and names `price_policy: highest` and `model_prices` as its two answers. A call that reports no cache fields is charged at the full input rate (§6), so a senior that does not cache the diff it re-reads costs more than one that does — which is a price question here, not a correctness one. The account-side settings of §1 are the senior's too: with fallbacks off, the model you priced is the model that serves it, and the account's data policy is the decision about its code. Same account, same decision, one more model.

**The live check is Check 45, and it has not run.** What these docs cannot settle — whether a provider-served senior's reviews are better than the cheap loop's own, and what a real routed review costs with the fee — is what Check 45 of [gcp-live-checklist.md](gcp-live-checklist.md) measures by hand, on a sandbox project and a sandbox repository, and no agent runs it. Until it does, the non-Claude senior's live behaviour is unmeasured: everything above is the config's, and the assumptions Check 25 settles hold for the senior exactly as they hold for the coder: this page's opening one, that OpenRouter's compatible endpoint exists at that path and answers in the format the gateway reads (the unnumbered preamble, `:3`); §6's, that a routed response carries usage and cache fields at all (`:117`) and a cost at all (`:123`); and §1's, that no account-side fallback serves a model other than the one you priced (`:12`). Nothing in Phase 1 changes what is refused (§5), which is why it ships as documentation and two tests rather than as product code.

## Direct to the vendor

A model family does not have to go through OpenRouter. The same `providers:` block (§2) accepts a second entry pointed straight at the vendor's own Anthropic-compatible endpoint instead:

```yaml
providers:
  openrouter:
    kind: anthropic-compat
    base_url: https://openrouter.ai/api
    auth: bearer
    secret: openrouter-api-key
    models: ["qwen/*"]
    allow_data_to: [edgeappinc/fugarosandbox]
  deepseek:
    kind: anthropic-compat
    base_url: https://api.deepseek.com/anthropic   # the vendor's own endpoint, not openrouter.ai
    auth: bearer
    secret: deepseek-api-key
    models: ["deepseek/*"]
    allow_data_to: [edgeappinc/fugarosandbox]
```

There is no separate "direct" knob: the `providers:` map is the only knob there is. The provider entry that claims a model is its route: to switch a model family between OpenRouter and its vendor, move its pattern from one entry to the other and run `fugaro update --repo`. Providers may not overlap (`fugaro validate` refuses two entries claiming the same model), so a family belongs to exactly one route at a time.

**Claude goes direct by default.** No pattern claims Claude: a `models` entry that overlaps a Claude pattern — `claude-*`, `anthropic/*`, `anthropic/claude-*` — is refused, so no wildcard, prefix or family spelling can claim one, while patterns for other vendors (`deepseek/*`, `openai/gpt-5*`) are untouched, and an `anthropic/<id>` that no route names is refused wherever a pin is judged, with a message that says it is a Claude model and where the permission comes from. **One exact ID can be claimed**: a route may list `anthropic/claude-sonnet-5.5` — that literal model ID, nothing wider — and that entry is the operator's opt-in to serve that one Claude model through that provider. It is an operator decision in the project config **or** in the project layer's `claude_models` ([project-layer.md](project-layer.md) §6, shipped by the senior-reviewer plan's Task 7, PR #397 — the run merges the claim into its own route table on every launch), never something a repository's `fugaro.yaml` can set or ask for, and it relaxes nothing else. The repository still has to be inside that route's `allow_data_to` — code only goes where you said it may — the run still needs `agent.auth: api-key` (an OAuth token is a Claude subscription credential and is never sent to another provider) and `budget.mode: enforce`, and the claimed model still has to have a price. See [mixed-credentials.md](design/mixed-credentials.md) §4 for the ruling and its limits.

**The claimed stage is a provider stage, and the price is a provider price.** Everything §7 says about a stage whose role model is routed applies to it: its process gets the provider's thinking variables, its background calls follow `agent.models.background`, and it is inside the route's `allow_data_to` like any other routed stage. The background default is the **coder's** model and only when the coder is provider-served (`config.EffectiveBackground`): with a provider coder an unset background keeps a claimed Claude senior's background calls on the coder's route, while with a Claude coder it stays unset and those calls go direct to Anthropic instead — so a claimed Claude senior is not by itself a reason to expect the route to see every call its stage makes (§7 has the same rule from the thinking side). It is charged the table price of its reported usage plus `route_fee_pct`, and a call that reports no cache fields is charged at the full input rate (§6): a routed senior that never reports a `cache_read` costs several times a direct one reading the same diff at list rates, which is the difference Check 46 of [gcp-live-checklist.md](gcp-live-checklist.md) measures against the same task run direct — whether Claude Code's cache markers survive OpenRouter's Anthropic-compatible endpoint is unmeasured, not assumed. The price comes from the catalog's `anthropic/<id>` row once [provider-price-catalog.md](design/provider-price-catalog.md)'s Phase 2 adds it, and until then from your own `model_prices` entry; an override row leaves every field the catalog would carry at its zero value, so an image request on that model is refused and a PDF reserves the default context rather than the model's real one. **A claim the project layer holds is priced by `model_prices` alone, those rows included**: the catalog prices the models a *route* lists, and a run's route table is the job's own `FUGARO_MODEL_PROVIDERS`, which never carries a layer claim ([project-layer.md](project-layer.md) §6) — so the layer cannot give a claim a price, and the operator keeps the claimed ID's price under `model_prices` in the local operator config and runs `fugaro update --repo` once to put that row in the job's environment, or the claimed pin is refused as unpriced. **A price is not a permission, and neither is the allow-list**: a `model_prices` key of `anthropic/<id>` and a `budget.allowed_models` entry naming it are both accepted where they are written, and neither enables anything — the run refuses the pin at bootstrap on every launch, and `fugaro validate` reports it only under §4's caveat: it judges pins and providers only when the local config it finds is this repository's own project's, so with none, or one for another project, it says nothing here either — until a route's `models` names that exact ID. `fugaro budget prices` shows the row a claimed ID is charged from, and its source.


The account-side settings of §1 (no fallbacks, the data policy) are OpenRouter's own; a vendor's own endpoint has its own account-side settings to review, which are not enumerated here.

**Unverified until Check 33:** that a vendor's own Anthropic-compatible endpoint (DeepSeek's, Moonshot's) accepts the gateway's forwarded request bodies byte for byte and reports usage the way the gateway reads it. Check 25 (§1) settles this for OpenRouter only; Check 33 of [gcp-live-checklist.md](gcp-live-checklist.md) is the equivalent for a vendor's own endpoint, and is optional and user-run.

## The cascade, and the project policy switch

`agent.auth: cascade` is the fourth value of the auth list (§4, and the `agent.auth` refusal in §5), and it is not a route: it is a **credential switch**. A `cascade` workflow holds no model credential of its own; its calls go job → gateway → **the credentials service**, which picks a credential from its own tiers (tier A a Claude subscription token, tier B the project's Anthropic API key, tier C reserved) and attaches it to the call. **As of 0.10.1 the launch wires it**: `fugaro run` sets `FUGARO_CREDENTIALS_SERVICE_URL` on an opted-in installation's repository job, so a `cascade` run's calls are served by the service rather than refused at bootstrap; see the two paragraphs on the service below for what that does not reach. It routes nothing: it names no model of its own, and the pins are the ones the configuration already answers, exactly as they are for `api-key`.

**A repository asks for it, and only the operator turns it on.** A `cascade` workflow whose project policy does not carry the switch is **refused** at launch, before any model call and before a pin moves: the repository's `fugaro.yaml` is not where that decision lives. The operator writes `routing.claude: {via: cascade}` in the project policy and publishes it:

```yaml
routing:
  claude: {via: cascade}
```

`fugaro project policy publish` is that write. `fugaro validate` refuses the same file on the author's own machine, so a repository author meets the rule before a launch does. The spelling is deliberate: `via: auto` and `via: direct` keep the meanings they had, and a `cascade` workflow under a policy that carries neither is refused rather than guessed at.

**It needs the gateway.** The service is reached *through* the gateway, so a `cascade` workflow needs `budget.mode` `observe` or `enforce`, the same as a provider route (§5), and a `cascade` launch is refused for an installation with no database, for a budget whose mode leaves the gateway off, for a project policy that publishes no `budget.allowed_models` (the service refuses every call of a project that publishes none, so the run would be refused at its first call and halt), and for a database whose rules predate the credentials family.

**It needs the service, and the launch does not check for it.** The cascade's launch gate (`cascadeLaunchRefusal`, `internal/cli/run.go`) reads the project's published policy, the gateway's mode and the database's credentials rules marker; it reads neither the service nor its bundle. So the refusal is the **switch**'s and not the service's: a policy that carries no `routing.claude: {via: cascade}` refuses the run at launch, before any model call, and turning the service on is not what makes a `cascade` launch legal — publishing the switch is.

**And the address reaches a repository's own job, and no other.** The opt-in deploys the service; the launch is what tells a job where it is — `internal/cli/run.go`'s `credentialsServiceLaunchEnv` puts `FUGARO_CREDENTIALS_SERVICE_URL` on an opted-in installation's per-repository execution, which is the name `serviceUpstream` (`internal/runner/gateway.go`) reads, so a `cascade` run is served instead of refused at bootstrap. A `cascade` run whose job is **not** told the address is still refused while it bootstraps, and that is a **failed run, not a halt**: it ends as an `infra_error` with **no pull request opened**, where a halt would have pushed its work and left a draft. Two jobs are deliberately not told. A **shared project job** is not, because the service refuses a caller whose account belongs to one (Global Constraint 6, C3.9 moves it), and the same variable is what opens the git provider keyless — telling it would break every GitHub run on it. And an installation that has not opted in is **byte for byte what it was**: no variable is set on any of its jobs, and its `cascade` launches are refused by the switch exactly as §5 describes, before any model call. So do not opt in unless you mean it: with the service on, a `cascade` workflow is served, and the half this release does not carry is the **other `agent.auth` modes'** — the mount drop below is `agent.auth`-blind while only a `cascade` run's calls go through the service, so an `oauth` or `api-key` repository job of an opted-in installation has no model credential of its own and nothing yet to replace it. Run such a project's workflows with `agent.auth: cascade`. [SECURITY.md](../SECURITY.md#the-credentials-service) states both halves as limits of this release.

**What it changes for the repository is nothing else — but it reaches every workflow of it, not only the `cascade` one.** The pins, the roles, `first_line_review` and the budget rules are the ones §2–§6 already describe. What the opt-in changes is the *job*: `internal/infra/spec.go` calls `dropModelMounts` for every workflow of a per-repository job as soon as the installation has opted in, and that deletes every variable `config.IsModelSecretEnv` names — `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_API_KEY` and each provider key — so an `oauth` workflow of the same repository does **not** keep its own mount, and no per-repository job mounts a model credential at all on this release. It is `agent.auth`-blind by construction: an `oauth` or `api-key` workflow of a repository that has opted in, next to a `cascade` one, mounts none either — the service holds them, and its one bundle secret is [SECURITY.md's subject](../SECURITY.md#the-credentials-service). The one job the opt-in does not reach is a **shared project job**, which `internal/infra/projectjobs.go` never drops and which therefore keeps its mounts; a `cascade` workflow cannot be served there in this release, because the service refuses a shared job's account as a caller until the phase-3 shared-job rules are on `main` (C3.9). What it changes for a *halted* run is that the account switch of [the working skill's diagnose reference](../plugin/skills/working/reference/diagnose.md) §5 does not apply to it: the cascade picks the credential, not this machine's local config. An operator's side of an outage is [docs/credentials-service/runbook.md](credentials-service/runbook.md).
