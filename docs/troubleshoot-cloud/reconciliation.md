## 1. Findings

**F1. Rule (the command has no cloud tier at all).** `runTroubleshoot` (`internal/cli/troubleshoot.go:181`) reads the configuration, resolves a credential (`troubleshootCredential`, `:461`), collects the evidence (`diagnoseagent.Collect`), fetches the source tree (`srctree.Ensure`), and — when there is no credential — prints the evidence and exits non-zero (`troubleshootOffline`, `:550`). Nothing in the file calls `internal/backend`, mints a token, writes a task or reaches the runs bucket. *Consequence:* tier 3 is new code in this file plus one new package seam; no existing path is rerouted.

**F2. Exists (the tier boundary is already a branch).** `troubleshootCredential` (`internal/cli/troubleshoot.go:461`) resolves, in order, `CLAUDE_CODE_OAUTH_TOKEN`/`ANTHROPIC_API_KEY` in the environment (`diagnoseagent.Own`), then the `claude` login this machine already holds (`claudeplugin.Find`), then an error naming both fixes (`:467`). The third branch is exactly the condition tier 3 is reached under, and the refusal it prints today is what `cli/troubleshoot-fix` is rewriting. *Consequence:* the cloud tier hangs off the absence of a credential, not off a flag; and a person who has a login keeps the local answer (D2400).

**F3. Exists (the source is fetched before the credential is acted on).** The source tree is fetched at `internal/cli/troubleshoot.go:217`, and `credErr` is not consulted until `:233`. *Consequence:* when the cloud tier is reached, the CLI already holds the tree the bundle's source reference names (D2404) — the fetch is not repeated.

**F4. Rule (the egress line has three cases and needs a fourth).** `troubleshootEgress` (`internal/cli/troubleshoot.go:495`) prints one line before anything is sent: `Sending to Anthropic on <account>: the redacted log, fugaro doctor's output, the effective configuration and the Fugaro source at this version, read by the model <model>.` Its three cases are the environment's own token, this machine's login (`h.Local()`), and — for a handle that is neither (`!h.Own()`) — the project's account `h.Account()`. The cloud tier sends the evidence to the person's own project **first** and to Anthropic from there, on the project's credential. *Consequence:* the line gains a case, and it is the one sentence that must be right (D2410, T-TC7).

**F5. Exists (the redaction this tier inherits, and it is the local tier's).** `diagnoseagent.Collect` writes the four evidence files through the exact-value pass and the pattern pass (`internal/redact`), into a 0700 directory with 0600 files (the names and the two modes at `internal/diagnoseagent/evidence.go:37-49`, the collector at `:151`, the passes at `redact.Text`, `:254,283`), and `diagnoseagent.Prompt` fences the evidence as data with a per-run nonce (`diagnoseagent.NewNonce`). The cloud tier uploads **those** files, so it inherits both passes and adds no redaction of its own. The files are `<run ID>.log`, `doctor.txt`, `version.txt` and `config.yaml`; the CLI writes `changes.txt` beside them (`troubleshootChangesName`, `internal/cli/troubleshoot.go:272`). *Consequence:* D2404 uploads exactly what the local tier already sends, which is the whole argument of the spec's acceptance ("nothing leaves the machine that the local tier would not have sent").

**F6. Gap (no recipe mode fits a diagnosis, and the one it borrows demands two things).** `internal/recipe` holds two modes. `mode: review` needs `--pr` and reviews a diff (`docs/recipes.md:82`); `mode: artifact` runs the repository's own render command and uploads the files its `outputs` globs name (`docs/recipes.md`, section 6). Neither describes "read a bundle out of the run's own prefix and write a document". The mode a diagnosis borrows also demands two things of the workflow: an **`outputs` block**, required on that mode and legal only there (`docs/recipes.md:38`), and a non-empty **`commands.render`** — its render arm refuses *every* artifact recipe whose workflow leaves the command empty, whether or not the recipe has a render step (`internal/runner/gate.go:162-167`, `internal/config/config.go:1050-1053`; the launch's own arm is that same list, `checkArtifactLaunch` at `internal/cli/run.go:4161` calling `runner.RecipeGateProblems` at `:4242`, and the runner repeats it at bootstrap, `TestBlankRenderCommandRefusesTheRun`, `internal/runner/artifact_test.go:460`). *Consequence:* D2402 — one of the two formats is widened, and whichever it is, a job image must know it (F18); the `outputs` block is the recipe's to carry, and the render arm is a refusal the tier must not inherit, because a `diagnose` step renders nothing (T-TC11).

**F7. Exists (the artifact machinery is exactly what a diagnosis needs).** `runstore.ArtifactPrefix` and `runstore.ArtifactFile` (`internal/runstore/artifact.go:33,52`) are the upload-and-record path, `runstore.OutcomeArtifacts` (`:27`) is the outcome, `runstore.InputsDir`/`InputKey` (`:15,20`) are where a launcher writes what a run reads (used today by `--attach`, `attachUpload` at `internal/cli/run_attach.go:373`), and `fugaro artifacts get` / `readArtifactRecord` (`internal/cli/artifacts.go:253,385`) are the read-back. *Consequence:* the diagnosis needs no new storage contract — only a new producer for `artifacts/`.

**F8. Exists (the launch's gates are one callable block, and it has already been called without launching).** `freshLaunchGates` (`internal/cli/run.go:1629-2196`) is the one block `fugaro run` (`run.go:1063`) and the daemon both pass, and the daemon calls it **without launching**: `internal/cli/orchestrator_launcher.go:176` runs it and then writes the task itself. It is the launch's whole judgement, in this order: the credentials cascade (`cascadeLaunchRefusal`, `:1633`), the image-skew family — the recipe's own gate (`checkRecipeImage`, `:1903`; `checkCloneRecipeImage`, `:1724`), the feature gates judged from the workflow's config (`:1720-2053`: rigor, governance, jobs, security, planning, model grades, follow-up, task grades, security requests, review levels, none-model, stop fraction, triage, vision, titles, named tokens, plan tasks, launch limits, compression), the shared job's (`checkSharedImageSince`, `:2069`) and the mode's (`artifactsSince`, `:2084,2087`; `evaluateSince`, `:2102,2105`) —, the review variant's image and the installation's admission of it — `checkCloneReviewJobImage` (`:2120`) and `checkReviewJobImage` (`:2123`), then `checkReviewAdmission` (`:2133`), **all three of them inside `if spec.Mode == recipe.ModeReview` (`:2109-2136`), so a `mode: artifact` spec skips every one of them** —, `authorGates` (`:2142`), `sealGate` (`:2149`), `proxyGate` (`:2158`), `checkMaxParallel` (`:2161`), `checkArtifactLaunch` (`:2168`), `budgetPrecheck` (`:2172`) and `launchPolicyGates` (`:2192`). Three things follow, and all three were wrong in this document's first draft. **`checkReviewJobAdmitted` is not one of them**: its only caller is the review command's own path (`internal/cli/review.go:223`), so a launch of the review variant through `fugaro run` never runs it. **The review-variant gates are conditional on the mode** (above): the block carries them for a review and for nothing else, so the pre-flight must add them by name — and with them the two checks the block never carries at all, `checkReviewService` (`internal/cli/review.go:418`, the credentials service published) and `checkReviewAccountState` (`internal/cli/review.go:432`, the account's mark), which live only in `checkReviewLaunch` (`:219`) beside `checkReviewJobAdmitted`. `checkReviewHeadIsStill` (`:459`), the fourth of that function's calls, is not among them: it judges a pull request's head, and a diagnosis has no pull request. **And the feature gates are not the spec's alone**: each is judged from the workflow's own config, so a repository that declares a feature its image predates refuses *any* launch on that repository, a diagnosis among them. Nothing else composes these: `launchProjectJobFor` (`internal/cli/project_job.go:290`) decides and never refuses, and there is no readiness helper (`internal/infra/readiness.go` and `internal/preflight` are deploy-time and setup-time checks of a different set of facts). *Consequence:* the pre-flight (D2401) calls **this block**, not a list of gates copied out of it — a gate the launch gains is then met by the pre-flight without the pre-flight being revisited, which is the whole of F8's warning — and names the five review-variant checks the block does not carry for this spec.

**F9. Rule (the doctor's parallel reads are not the launch's).** `doctorPolicyVsJobs` (`internal/cli/doctor.go:2937`) compares the local config's recorded base image with this release's pin offline, `doctorBudgetMode` (`internal/cli/doctor_budget_mode.go:66`, the `budget-mode` check) reads the mode, and `doctorCredentialsServiceDeployed` (`internal/cli/doctor_brokering.go:209`, the `credentials-service-deployed` check) reads the service. They answer similar questions from local config, and none of them is the gate a launch passes. *Consequence:* D2401 declines the cheap alternative — a pre-flight built out of doctor's checks would be a second implementation of the launch's judgement, and the two would drift the first time a gate changed.

**F10. Exists (the review-only job variant, and its admission gate).** `fugaro review --pr N` runs the `review-only` catalog recipe on the review-only variant of the shared project job: the sibling `fugaro update` deploys beside each coding job, whose account segment carries `-review` (`internal/credsvc/review.go`'s `ReviewVariantSuffix`, `internal/infra/projectjobs.go`'s `ProjectReviewJobs`/`reviewVariant`, `implicitReviewVariant` for a profile-less installation), which **mounts no credential of its own** and whose verdict is signed by the installation's credentials service (`docs/recipes.md:80`). `reviewJobFor` (`internal/cli/review.go:269`) resolves it from the launch, and three gates admit it: `checkReviewJobImage` and `checkReviewAdmission` (`internal/cli/recipes_skew.go:2468,2507`) against `reviewJobSince` (0.20.0) and `reviewAdmissionSince` (0.21.0) (`internal/cli/recipes_skew.go:542,571`), and the binary's own `checkReviewJobAdmitted` (`internal/cli/review.go:241`) — the first two inside `freshLaunchGates`'s `if spec.Mode == recipe.ModeReview` (`run.go:2109-2136`), the third in no block at all. `checkReviewLaunch` (`internal/cli/review.go:219`) is the review command's own composition: those three, plus `checkReviewService` (`:418`, the service published) and `checkReviewAccountState` (`:432`, the account's mark), plus `checkReviewHeadIsStill` (`:459`, a pull request's head — the one a diagnosis has no analogue of). `launchProjectJobFor` (`internal/cli/project_job.go:295`) is the launch. *Consequence:* D2403 — the tier that must never spend the person's credential has a job that already spends the project's and holds no key.

**F11. Rule (a run is scoped to a repository).** `runstore.Open` builds `runs/<slug>/<run-id>/`, the slug comes from `task.Slug(provider, repo)` (`internal/task/task.go:1246`), and every job run clones a repository. A diagnosis of a failure that happened **outside** any checkout has no repository to scope to. *Consequence:* D2409 — the tier declines outside a checkout, and the alternative (a reserved scope under `runs/`) needs a slug no repository can collide with, which `task.Slug`'s own shape happens to give (`<readable>-<16 hex>`, `internal/task/task.go:1217,1254`) but which nothing else in the tree reserves today.

**F12. Rule (who may launch).** `internal/cli/access_run_gate.go:94` maps `accesslib.ActionLaunch` to `accesslib.RoleOperator`, and `requireAccess`/`requireRunAccess` (`:103`, `:127`) is the gate `fugaro run`, `cancel`, `logs` and `diagnose` ask, with the caller taken from the credential and never from config or git (F21 of `docs/roles-scopes`). *Consequence:* D2406 — the cloud tier asks the same action on the same scope, and a viewer is refused with the gate's own sentence.

**F13. Rule (the human-terminal rule is about a value, and this tier reads none).** The rule refuses a coding agent's session where a **credential value** would be typed or stored: `credsOwnerOnly` (`internal/cli/creds.go:120`), `accounts add --claude` (`internal/cli/accounts_add_login.go:171`, the gate its doc block at `accounts_add.go:98` describes), and the shared read refusal `refuseKeyReadAt` (`internal/cli/githubapp.go:107`). The cloud tier reads no value into the CLI and the job mounts none of its own (F10): the CLI holds a bucket object name, and the model call is signed inside the container. *Consequence:* D2406's second half — the rule does not apply to this tier, and saying so is what keeps it from being copied into a place it does not belong.

**F14. Rule (`fugaro run` carries no managed-project refusal, and one agent-session refusal).** `managedMutatingCommands` (`internal/cli/root.go:151`) holds `fugaro restore` alone, and `run.go` reads no managed fact: the managed mark decides whether a confirmation is asked, not whether a launch is refused. `fugaro run` does carry one agent-session refusal — a launch **without a checkout** in a coding agent's session, which would read the repository's `fugaro.yaml` with the person's own credential (`refuseKeyReadInAgent`, `internal/cli/project_job.go:823`; tests `internal/cli/run_test.go:2451,2483`). *Consequence:* D2406's third part — the tier adds no refusal of its own, and the one agent rule it does inherit cannot fire, because the tier runs where there is a checkout (F11).

**F15. Exists (the budget, and what a launch does with it).** `budget.Caps.PerRun()` (`internal/budget/model.go`) is min(the repository's or the default, the global); `budgetPrecheck` refuses a launch under `enforce` with the reason and names `--no-budget-check` (`internal/cli/launch_budget.go:604`), and an unreadable database is a fail-closed refusal (`:598`). A run's own spend is bounded by the lease the launcher takes. *Consequence:* D2407 — the diagnosis's cap is a number the launcher writes into its own lease and the task, and the gateway enforces it as it does for any run.

**F16. Rule (nothing in this command retries anything).** `troubleshootRun` is one call, and every failure path goes to `troubleshootOffline` (`internal/cli/troubleshoot.go:550`). *Consequence:* D2407's no-retry rule is a property to keep, not a behaviour to remove.

**F17. Exists (the live-check harness).** `docs/gcp-live-checklist.md` holds a register table (`:818`) and one `## Check NNN` section per check (`:12958` is Check 313), each naming a script under `scripts/live-checks/` with a hermetic sibling `checkNNN_test.sh` driven from `scripts/live_checks_test.go`. A check's block is `FACT <key>: PASS|FAIL|INFO — <detail>` rows ending `CHECK NNN RESULT END (exit N)`, exit 0 all held, 1 a criterion failed, 2 could not tell; the scripts refuse an installation whose name merely contains `belong` before the first call; the numbering ruling (`:183`) is that a reserved number is never reused. *Consequence:* Check 680 is one script and one register row (D2408).

**F18. Rule (a new step kind is gated by the job image).** `digest` (0.13.0) and `hand_over`/`rebase` (0.23.0) are the precedents: a step kind a job image must know is refused at the person's terminal, naming the release, before anything runs (`docs/recipes.md:36,74`), through the `*Since` family and `checkCatalogEntrySince` (`internal/cli/recipes_skew.go:1336`). A runner that knows the step kind but does not execute it refuses the recipe at bootstrap rather than skipping the step. *Consequence:* the recipe of D2402 carries a `since` gate of its own, and the pre-flight (D2401) is where the person meets it.

**F19. Gap (the docs and the skill do not name the tier).** `docs/troubleshooting-for-agents.md` and `plugin/skills/working/SKILL.md` are where the command is described to an agent, and the plugin's lint checks every command and flag a skill names against the CLI (`plugin/`). *Consequence:* the sentence arrives with the tier (T-TC10), and `docs/status.md` is **not** touched by this work — its row is the owner's status sweep's (the spec folder is new, so nothing is removed).

**F20. Contradiction (the mode the diagnosis borrows and the job it must run on disagree).** D2402 borrows `mode: artifact`; D2403 runs the tier on the review-only variant. The runner decides a run's **class** from the task's mode alone — `runClass` is `if r.spec.Mode == recipe.ModeReview { return classReview }; return classCoding` (`internal/runner/projectjob.go:95-100`), and the comment above it is explicit that the marker is the task's mode and never anything the container says — so a `mode: artifact` diagnosis is a `classCoding` run. Three doors then shut on it. `checkJobClass` (`:346`) halts it: it is in the review-only variant and is not a review, and the halt is deliberate ("a run in the wrong job has already been handed the wrong container, and the only safe answer is to stop"). `checkProjectReviewJobAccount` (`:884`), the second independent door on the same credential, halts it again, and it is asked **before the published policy is read at all** (`checkProjectJobAccount`, `:783`). And even a run admitted there would not get the model path D2403 promises: `reviewClassRun` (`internal/runner/gateway.go:335-337`) requires `runClass() == classReview` **and** the job's own class, so the credentials service's review class — the whole reason the variant holds no key — is not the path a diagnosis would take. *Consequence:* D2411 — the class marker must admit a diagnosis, and the two decisions above are otherwise incompatible: a launch that follows D2403 halts at bootstrap, with a sentence about a review, before a single model call. U3 is restated with it.
