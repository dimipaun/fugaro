# Who reads Secret Manager today (reconciliation §3, audited against the code)

**Status: the S0 audit, as a tested doc; it changes no behaviour** — built and merged as task B0.1,
with its guard in `deploy/terraform/secret_readers_test.go` (B0.2); [status-2026-11-07.md](status-2026-11-07.md)
is the census of 2026-11-07 and says which of these rows have since moved. One row per reader of a Secret
Manager value — an account class or a Go file — with the decision that keeps it reading and the slice
that ends it. The IDs are the key B0.2's guard uses: its exceptions table lists exactly these IDs, so
a hit with no row, and a row with no hit, both fail the build.

How to read a row:

- **Kind** is `runtime` (an identity a Fugaro component runs as) or `operator` (a human identity, or
  the CLI acting with the owner's own credentials). Every `operator` row exits `never`: nothing in
  this work takes the owner's own Secret Manager access away.
- **Exit slice** is the slice of the plan's Slices table that ends the read, or `never` when no slice
  of this plan does — the service's own grant, operator code, and the coordinator's App key read,
  which the coordinator plan owns. Where one row covers secret classes that leave in different
  slices, the row carries the earliest of them and the **what** cell names each class's slice.
- **Decision** is the decision that keeps the row a listed exception: D145 and D491 for the staged
  classes, D506 for the Bitbucket token living in the bundle, D499 for the rows the guard itself
  keeps listed.
- The rows are reconciliation §3, plus the build request built in Go, the managed
  projects' `fmgd-` secrets, and every non-test Go file under `internal/` and `cmd/` that imports the
  Secret Manager API or names its host — a file the guard would otherwise find with no row to map it
  to. A row's location — the module, the resource or the file it keys on — is in its **how** cell.
- E31 is the mobile plan's voice hop (P5.3.3's shell, P5.3.5's forwarding half): the one
  container holding every admitted provider's key, read by a process **anyone on the internet may
  call** — which is why the row says what it does not read as well as what it does.
- E25 and E26 are the dynamic-delivery class the design's D1931 added (DS2.2): the credentials
  service's per-secret reader and the intake's writer, each a row of its own because each is an
  identity that reaches the API, and the guard finds them where it finds every other grant — in the
  installation module's own `.tf`.

**The Batch backend's row has left this table (BR11, D3104; D3107).** E5 recorded a reader the compute
backend had only while an installation had selected it: the secrets the installation's `batch.secrets`
listed, mounted on the job as `secretVariables` and resolved by the VM's own account, which D2075
(2026-11-10) kept as a permanent listed exception because a Batch VM was not a job account the
credentials service admitted. **D3107 supersedes D2075** (owner, 2026-11-20, as recommended). D3104
rules that **a Batch run's credentials come from the credentials service and from nowhere else**:
nothing of a secret is put on a Batch job — not a value, and not a container's name either, because the
name alone is a standing grant of the job's account that the service's carriage makes unnecessary —
so there is nothing left on the VM for this table to audit, and the premise D2075 rested on (the cost
of a caller class in the service) is a cost this plan's release path pays elsewhere (D3101). What a
launch on `backend: cloud-batch` needs instead is the service, and one whose repository the service
does not serve is refused by the launcher before the run starts, with the fix that changes that
(`internal/cli/launch_batch.go`, BR11): a run whose model credential nothing mounts and no address
carries would otherwise fail at its first model call. The `batch.secrets` key outlives the mount as a
config fact alone — an installation whose block still carries it is read rather than refused until its
next `fugaro update` removes the key (R10) — and what is left of the map in the binary is
`checkSecrets`' shape check, which reads no Secret Manager value and is therefore not a reader either.

**The Bitbucket rows' state (B1.10, B1.13 part two).** The git proxy shipped (B1.5, B1.6, B1.7): on a
repository the published node admits with `proxy: true`, **a proxied job reads no token at all** — the
runner opens its provider tokenless, the forwarder holds no credential, and the service puts the
Bitbucket token on the wire (`internal/runner`'s `startProxiedGit`, `internal/gitproxy`). The flip
has landed with it: `config.ProxiedGitSecretNames` names `bitbucket-token`, so E1's token row is

An **Editor is deliberately not a row**, though this audit named it as one until 2026-10-29:
`roles/editor` carries `secretmanager.secrets.getIamPolicy` and delete but not
`secretmanager.versions.access`, so an Editor reads a container **directly** only through a
`secretAccessor` grant of its own — a grant of the kind every row above holds, and one the B0.3
sweep reports per container. Naming Editors as readers would be a claim `roles/editor` does not
support, and it would hide exactly those grants. An Editor also reads one **indirectly**: it carries
`iam.serviceAccounts.actAs` and `run.services.update`, so it can deploy code that runs as an account
holding a grant — a deploy rather than a read of its own, and the reason the
`credentials-service-deployers` line names it. The owner ruled the wording on 2026-10-29;
[reconciliation.md](reconciliation.md) F3 and `SECURITY.md` carry the same correction.
