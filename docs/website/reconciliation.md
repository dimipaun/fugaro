## 0. What this document is, and how its claims were checked

The owner's spec asks for a public site at **fugaro.dev**: Astro, a dark theme with one electric accent, an animated terminal and an animated architecture diagram, ten sections, per-OS install instructions, per-OS console downloads, a caps-and-costs guide built from *"real run history from existing projects"*, docs, a security page, an FAQ comparing Fugaro to other runners, a changelog *"generated from GitHub releases"*, and community links.

**Every claim about the code below was checked against `origin/main` at `76f6c59`**, the head this branch is based on; each finding cites a **file and a symbol** — a command constructor, a struct, a field, a test function, a workflow job — and never a bare line number, because line numbers drift with every merge. Where a fact lives in a file rather than in a symbol (a workflow's `on:` block, a directory's contents, a file that does not exist), the finding says so and names the file.

**Three things the spec assumes do not exist in this tree, and they are the reason most of §2 is a *Gap* rather than an *Exists*.** There is **no website, docs site, landing page or web asset of any kind** in the repository: no HTML, CSS, SVG or `.astro` source anywhere outside the console's two contract documents, no `firebase.json`, no `.firebaserc`, no `google_firebase_hosting_site`, and no mention of `fugaro.dev`, `fugaro.ai`, Cloudflare, Netlify, GitHub Pages, Plausible, Umami or any other analytics vendor outside the owner's own spec. There is **no generator for any of the text the site is asked to render**: no cobra documentation generator (`GenMarkdownTree` and the rest of `cobra/doc` appear nowhere in the tree), no changelog generator (GoReleaser's own `changelog` block at release time is the only changelog machinery that exists, and it runs inside a release, not for a site), and no CLI reference file. And there is **no page, script or test that renders security text, install text or release notes for a reader outside the repository**.

**Where the index rows went — nowhere, and that is the convention.** The repository keeps no index of `docs/design/` or `docs/plans/` (there is no `docs/README.md`, no `docs/design/README.md` and no `docs/plans/README.md`; `docs/SPEC.md` links nothing under `docs/` except the design tree), and the website work follows the same shape the managed-projects reconciliation records in its §1.1. The one index this work owes is its own, [README.md](README.md), because the owner asked for this directory to be a directory with an index — and it is written as a **directory index**, not as an entry in a registry the tree does not keep.

**This directory is not the shape the three precedents used, and the owner asked for it.** The precedents are a pair — the owner's text under `docs/design/` and the design + plan under `docs/design/` and `docs/plans/` — while this work is **four files under `docs/website/`**: the spec, this reconciliation, the plan, and the index. The reason is that the site is not a feature of the Go program: it is a second artifact, in its own language, with its own build and its own deploy step, which is what `console/` is. The directory is the artifact's documentation, and §4's D90 decides whether the artifact itself lives in this repository or in another one.

**Numbering, and where it comes from.** The owner allocates decision blocks to lines of work, and the allocation is written down where it was made: *"this one 62 and 63, voice 64–66, managed projects 67 onward"* (`docs/plans/2026-10-15-desktop-console-v2.md`, one sentence, merged on `main`). The gap is deliberate and is stated here rather than left to a reader to wonder about: numbers D79–D89 are in no document, and nothing in this work writes one.

**Check numbers.** The live checks live in [docs/gcp-live-checklist.md](../gcp-live-checklist.md). On `origin/main` its highest written `## Check N` section is **58** (the artifact-runs check), and everything above it is a reservation held by another line of work: **59** (as 59a/59b) by the console plan, **60** by `docs/design/budget-token-channel.md`, **61** by the project-centric plan's phase 6, **62–63** by the console v2 plan and **64–66** by the voice plan (the one allocation sentence above), and **67–68** by the managed-projects plan, which took 68 under the block clause the next paragraph examines. **This work takes 69 and up**, written as **69a–69c** in the sub-lettering convention the register already uses (43a–43f, 59a/59b, 67a/67b): the site's live checks are all owner-run, and 69 is the site's end-to-end one. ## 1. Summary and recommendation

The spec is a good brief for a marketing site and a poor brief for this repository, and the difference is one sentence long: **everything the site is asked to *show* is already in the tree, and everything the site is asked to *generate* is not.** The tagline is `README.md`'s own tagline line, the line under its `# Fugaro` title, verbatim — *"Fleeting cloud workers for coding agents: one task, one container, one PR, then gone."* The install instructions exist, tested and signed, in four places (the README, the release page's install header, the release guide's verification section and the design's artifact table — finding 21). The security model is `SECURITY.md`, 38 KB of it, already owner-facing. The release notes are `docs/releases/vX.Y.Z.md`, one file per release since 0.4.0, hand-written and gated by the release process. The caps are real, enumerable and each one has a command that sets it. The run record carries the cost fields the caps-and-costs guide wants to average. **What does not exist is any machinery that turns those facts into pages, and any test that would notice when they drift.** That is the whole of this work: a generated-content layer with drift tests, and a site that renders it.

The second thing the spec gets wrong is structural, and it is the load-bearing one. The spec lists **Firebase Hosting first** among its hosting options, because Fugaro already uses Firebase. **The Firebase project in this repository is an installation's, and an installation is a customer's** — the repository says so in as many words, three times, in three documents: *"one Firebase project serves one installation"* (`docs/gcp-setup.md`, `## Adoption`), *"one Firebase project serves one installation (design D3)"* (`docs/design/adopt-firebase-root.md`, `## Known limits`), and *"**Each Fugaro project has exactly one Firebase project (FP), shared by all its repositories and all its people**"* (`docs/design/m9-budget-and-dashboard.md`). In project-centric mode Firebase is **mandatory**, so every installation has one, and it is the installation's own. A public marketing site deployed into a Firebase project would therefore be deployed into **somebody's installation**, with a deploy credential against it — and the whole point of the installation model is that an installation's credentials are the operator's. **So the recommendation is a host that is not tied to any installation: Cloudflare Pages, or GitHub Pages as the zero-new-credential fallback** (§4, D91). **The owner answered D91 on 2026-10-16, against that recommendation and in a form that answers the objection it rests on: Firebase Hosting, in a *separate* Firebase project created for the website only** — never an installation's, never a customer's; the owner creates that project, the deploy credential is scoped to it alone and is neither an installation's nor a run's, and the deploy is an owner-run step from a workflow staged under `docs/pending-workflows/` for the owner to copy, because no run may hold that credential (D91, D109).

The third correction is smaller and it is the one that turns into a security task. **The spec's caps-and-costs guide is built from data about the owner's own installations** — *"computed by averaging real run history from existing projects"*. Those projects include `belong`'s production-adjacent repositories, and the rule that **no agent ever touches `belong`** is already written into the project-centric design and carried by every live check from 48 onward. The guide is worth having and the data is there (`internal/runstore/runstore.go`'s `Record` and `internal/runstore/cost.go`'s `Cost` carry exactly the fields it needs), but **it must be produced by an owner-run, read-only aggregation over run records that emits aggregates and nothing else** — counts, percentiles and per-recipe ranges, with no repository name, task text, branch name, run ID or person, from one named installation, refusing to publish a range drawn from fewer than N runs, and printing its own "not a promise" disclaimer. §4's D96–D98 state it, and the plan's Part 0 builds it with a test that asserts the output carries no identifiers. **The owner answered D96 on 2026-10-16: the command is `fugaro stats runs --project <name>`, it reads sandbox/dogfood (the `fugaro` installation) data only, `belong` is never aggregated unless the owner says so, and no range is published from fewer than 20 runs.**

**What this document refuses to accept from the spec, in three sentences.** It refuses *"Console downloads"* as a shipping section: the console is designed (its D11 makes it its own artifact published from the CLI's `vX.Y.Z` tag) but **not shipped** — `console/` holds two files, `console/README.md` and `console/docs/json-contract.md`, and `docs/releases/v0.8.0.md` lists the console under *"Not in this release"* — so the section ships as a placeholder whose links a test refuses to emit. It refuses *"tasks with review often run ~2 h, not 30 min"* as a publishable fact: **nothing in this tree measures a task's wall-clock time**, the closest numbers are the run's own *limits* rather than its durations (`internal/config/defaults.go`'s `applyDefaults` sets `total` to 90 minutes and `stage` to 40; this repository's own `fugaro.yaml` asks for `total: 2h, stage: 90m`), and a claim about how long work takes has to come out of the aggregation, not out of the spec. And it refuses the *"Windows via WSL"* install row as a support promise: `.goreleaser.yaml`'s `builds[0]` builds **darwin and linux on amd64 and arm64 and nothing else**, `README.md`'s `## Requirements` says *"Windows: untested"*, and the console design's own decision D10 puts Windows packaging **later** — so the site says what the repository says, and a test pins the OS list to `.goreleaser.yaml`.

**The recommendation, in the order that gets value first.** (1) Build the **generated-content layer and its drift tests before any site code**, because that layer is what makes every later page true — the install facts, the security text, the release notes and the CLI reference, each generated from one place and each pinned by a test that reads it (`internal/cli/docs_*.go`'s `readDoc` harness is the shape, and `TestDocsDesktopConsoleContractNamesEveryWatchField` is the precedent for a document derived from a struct rather than written beside it). (2) Put the site in **this repository, under a top-level `website/`**, beside `console/`, with the same boundary the console has (`internal/cli/docs_console_boundary_test.go`'s `TestConsoleIsOutsideTheGoModule`), so the drift tests are Go tests that read the site's own files from the repository they describe. (3) **Deploy it owner-run**, from a workflow staged under `docs/pending-workflows/` for the owner to copy, because **no Fugaro run may change `.github/workflows/*`** — the App is deliberately never granted GitHub's Workflows permission, so the push is refused (`docs/dogfooding.md`, `## What Fugaro can never change`; `docs/git-providers.md`; `docs/pending-workflows/README.md`) — and, under **D91's answer**, that step deploys to the **separate Firebase project created for the website only**, whose project id the owner supplies at deploy time through the workflow's variable rather than committing it. (4) **Add nothing to the release gate**: a `website` check would need `.github/workflows/ci.yml` and `scripts/release-gate.sh` edited, which is the one class of change a run cannot make, and the site is its own artifact with its own schedule (D109).

## 5. What the reconciliation refuses to accept from the spec

Four claims, and one right that the spec gives away.

1. **"Console downloads: per-OS download links."** There is nothing to download (finding 23). The section ships as a placeholder whose links a test refuses to render, and the data flag that turns it on belongs to the console's own release task (D95, and finding 25 for the rule it enforces). Publishing a download link for an unsigned or unreleased artifact is the one outcome here that has real consequences for a user.
2. **"Realistic expectations: tasks with review often run ~2 h, not 30 min."** Nothing in this repository measures how long a task takes; what it records is a run's *deadline* (finding 33). The claim is a **measurement to make, not a sentence to publish** (D97), and if the aggregation does not produce it, it is dropped rather than softened.
3. **"Ballpark time/cost ranges per task type, computed by averaging real run history from existing projects (agent to collect)."** The direction is right and the data exists, but "averaging" is the wrong statistic for a range — an average of a long-tailed distribution describes nobody — and *"from existing projects"* means **data about the owner's own installations**, one of which holds production-adjacent repositories no agent may touch (finding 32). It becomes an owner-run, read-only, installation-scoped aggregation emitting percentiles and no identifiers (D96), with a minimum sample and a disclaimer (D97).
4. **"Windows via WSL (no native promise yet)".** The parenthetical is the honest half and the row is a support claim: no Windows binary is built, `README.md` says "Windows: untested", and the console's own D10 deferred Windows (finding 20). The site mirrors the repository's wording and a test pins it to `.goreleaser.yaml` (D94).
5. **The one right the spec gives away, and the reason this document is cautious about generated text:** *"Changelog: generated from GitHub releases"* and *"computed by averaging … (agent to collect)"* both put a document's truth in a step nobody re-runs. In this repository the truth of a generated document is a **test**: every page in this plan that is derived from a file is derived by a task whose verification is that the page and the file agree (D98–D100). That is the difference between a changelog that is generated and a changelog that was generated once.
