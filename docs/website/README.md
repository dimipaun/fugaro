## The short version

The spec is a good brief for a marketing site and the repository can back most of it — but **everything the site is asked to *show* already exists here, and everything it is asked to *generate* does not**. The tagline is the line under `README.md`'s `# Fugaro` title, verbatim; the install paths are signed and tested; the security model is `SECURITY.md`; the release notes are `docs/releases/vX.Y.Z.md`; the caps and the run-record cost fields are real. What does not exist is any machinery that turns those facts into pages, or any test that would notice when they drift. That gap is the whole of this work, and it is why the plan puts the **generated facts and their drift tests before any site code**.

The corrections the reconciliation makes, in one line each:

- **Firebase Hosting is in — but in a *separate* Firebase project created for the website only** (D91, the owner's answer, **against** the recommendation). The reason the reconciliation recommended against it still holds and is why the projects are separated: **the repository's Firebase project is an installation's** — *"one Firebase project serves one installation"*, stated in three documents, and in project-centric mode every installation including a customer's has one — so a site deployed there would sit inside somebody's installation with a credential against it (F13). Under the answer, **the owner creates the site's project**, the deploy credential is scoped to that project and to nothing else (never an installation's and never a run's), and the deploy is an owner-run step from a workflow staged under `docs/pending-workflows/` for the owner to copy (D91, F14, D109).
- **The site carries analytics after all, and therefore a consent banner** (D93, the owner's answer, **against** the recommendation). Google Analytics loads **only after consent**; it sets identifiers, a banner is normally required in the EU/UK, and the page loads a Google script — the one named exception to "nothing third party" (D106), written into the plan's origins test and into its consent-banner task, whose tests are that no analytics request happens before consent, that consent is withdrawable, that no cookie is set before consent, and that the banner is accessible and keyboard-operable. **Switched on by W3.2 on 2026-10-18** (the owner's ruling recorded under that task in the plan): **Google Analytics 4**, measurement id `G-DZ4F35D3EH` in `website/data/site.yaml` and nowhere else, the gate and the bootstrap in the site's one first-party script (`website/public/scripts/site.js` — so the deployed policy needs no `'unsafe-inline'` and no nonce), the CSP widened by exactly the origins Google documents for GA4 without the Advertising features, and the privacy defaults in the one `config` call (no Google Signals, no ads personalisation, no user id, one page view). The state today is therefore the *post-consent request*: nothing is fetched before a visitor accepts, and **check 69b's pass condition is the one origin after consent**, not the absence of analytics.
- **The caps-and-costs guide's numbers are data about the owner's own installations**, one of which holds repositories no agent may touch. They come from an owner-run, read-only aggregation over one named installation that emits percentiles and **no repository name, run ID, branch, task text or person**, from a sample of at least N runs, with a "not a promise" line (D96–D97, W0.3).
- **Everything the site would say that the product cannot back today is held back**: no console download link (the console is designed and unshipped), no "~2 h" sentence (nothing measures task duration — the tree records deadlines, not durations), no Windows support claim (no Windows build exists), and no competitor comparison without a source and a date.

## What the owner has answered

Twenty rows, **D90–D109**, in the reconciliation's §4, each with this document's recommendation, the cost of the alternative and **the owner's answer**. **All twenty were answered on 2026-10-16** — seven of them the owner's alone (**D90** where the site lives, **D91** hosting, **D92** domain and redirects, **D93** analytics, **D96** the aggregation's data policy, **D102** the tagline, **D104** the palette) — and **two against the recommendation: D91** (Firebase Hosting, in a separate Firebase project created for the website only) **and D93** (Firebase Analytics, behind a consent banner). **D90's answer is the recommendation — this repository, under `website/` — so every path in the plan stands as written.**

**An answered decision is not an approved plan.** The plan's §7.1 states the one rule for what can start: **a wave starts as soon as the owner has given a go for it; nothing else blocks any more**, because no wave waits on an unanswered row — and §15 is that rule as the gate that turns the owner's *"start as soon as we can"* into a go, one wave at a time.

The plan takes **check 69 and up** (written as 69a–69c) for the site's live checks; the highest written section in [docs/gcp-live-checklist.md](../gcp-live-checklist.md) on `main` is 58, and 59–68 are reserved by the console, budget-token-channel, project-centric, console-v2, voice and managed-projects lines. **A reserved number is never reused or renumbered**; if 69 is taken before the plan's Part 2 lands, the owner reallocates and the plan follows.
