## 1. What exists

**F1: Exists. `fugaro runs digest` writes a closed period's report into the repository's own tree.**
`newRunsDigestCmd` (`internal/cli/runs_digest.go:98`) takes `--period day|week|month|year`, `--date`,
`--repo`, `--dir` (default `digest.Dir`), `--stdout`, `--json` and `--submit-draft` (`:156-165`);
`runRunsDigest` (`:167`) refuses an open period (`digestPeriod`, `:291`), reads this repository's
records, and writes `<dir>/<YYYY>/<key>.md` (`:262`) plus the regenerated index (`:269`). It is core
MIT code — it is in every build, tagged or not. *Consequence:* the owner's "each saved and committed
to the tree" is half done: **written** into the tree, never committed by the command (F15).

**F2: Exists. One layout, two writers, byte-identical.** `digest.Dir` is `docs/fugaro-reviews`
(`internal/digest/layout.go:23`), `IndexName` is `README.md` (`:25`), the index carries the
`generated by …; do not edit` header (`:30`), `reportShapes` fixes the four file names (`:46`) and
`IndexMarkdown` renders the table — period, runs, flagged, billed, notional (`:177`). The package
exists as its own package because a person's terminal and a report run both write these files and
must agree byte for byte (`:10`). *Consequence:* the trend view the owner asks for already has a
home: **the index's table** (F19).

**F3: Exists. The report's content and its flags.** `internal/digest/digest.go` builds the report:
the 8 KiB cap (`:49`, `capTo` `:565`) and six flags — `review_calls`, `subagents`, `halt`,
`fix_rounds`, `repeated_command`, `review_scope_drift` (`:79-97`, `FlagNames` `:97`). *Consequence:* the "watch patterns
over time and report them" half has a closed vocabulary to report in.

**F4: Exists. The pattern detector, with fixed rules and thresholds.** `Patterns`
(`internal/digest/patterns.go:91`) reads the summaries of the committed reports plus this one; the
four rules are named at `:22-37` and their thresholds are constants at `:39-56` (3 of 4 weekly
reports; 3 months of rises; +50% on last month's median; halts above a tenth for 2 weeks). Each
pattern carries the period keys it read and one figure per period. *Consequence:* the detector is
not something this design has to invent (F19, F20).

**F5: Exists. The report run, end to end.** The catalog recipe `run-digest` is `digest: {}` then one
`review` (`internal/recipe/catalog/run-digest.yaml`); the runner's step (`internal/runner/digest.go:101`)
writes every due period the tree does not hold (`writeDueReports`, `:301`), regenerates the index
(`:353`), commits under the runner's own identity (`:359`) and leaves the pull request to one senior
review; the finalize guard (`:168`) makes the run's diff against its base exactly the generated
files — and `stray.go` has since made that guard stronger, not weaker (§4, M7). `--retry` and `--pr` are refused for a report run, and a launch with no runs in the window is
refused before anything starts (`internal/cli/run_digest_manifest.go:86`). *Consequence:* a user who
wants the cadence automated has one command to schedule, and it is already documented
(`plugin/skills/working/reference/periodic-reviews.md` §2, §6).

**F6: Exists. The due computation**, in the runner: `digestDuePeriods` (`internal/runner/digest.go:425`)
is the seven closed days (`digestCatchUpDays = 7`, `:70`) plus the week on a Monday, the month on the
first and the year on the first of January. *Consequence:* the notion of "due" is already decided
once — and it is **unexported and unreachable from the CLI** (F17).

**F7: Exists. The learning draft, and it sends nothing.** `digestSubmit` prints a draft with no
repository name and no run ID — runs are renumbered `run-1`, `run-2`, … (`digestSubmitRuns`,
`internal/cli/runs_digest_submit.go:99`) — and ends with the one command that opens the issue form,
`gh issue create --web -R owner/fugaro` (`:57`), which the person runs (`internal/cli/runs_digest.go:142`).
*Consequence:* D327/D328's channel is real, and §7 of the spec keeps it unchanged.

**F8: Exists. The issue form and the contribution note.** `.github/ISSUE_TEMPLATE/skill_learning.yml`
is the "Skill learning" form with the `skill-learning` label, an MIT grant and a confidentiality
acknowledgement, both required; `internal/cli/docs_skill_learning_test.go:48` pins the form's name,
its label and the two grants. `CONTRIBUTING.md:67` states the rule: an issue is input, rewritten by a
maintainer into their own words and landed through a normal pull request, never pasted into a skill.
*Consequence:* "opt-in and human-approved" is not a proposal here, it is the shipped rule (F22).

**F9: Exists. The practice, in the skill every user has.** The `working` skill points at the review
(`plugin/skills/working/SKILL.md:29`), describes the command and the sweep (`:76-78`), and
`reference/periodic-reviews.md` holds the four periods, the scheduling section, how to read a report
and its patterns, where a lesson goes, the relaunch rules and the submission step.
`plugin/periodic_reviews_skill_test.go` pins the pointer (`:38`) and that the skill never submits on
its own (`:70`). *Consequence:* the "update the official skills" half of the request has shipped; what
it lacks is a signal that the cadence is being kept (F16, F18).

**F10: Exists. The retention the yearly report is built around.** The runs bucket's lifecycle is 90
days (`deploy/terraform/gcp/modules/installation/variables.tf:112`, `runs_days = 90`; the CLI states
it at `internal/cli/stats.go:40`), which is why a yearly report rolls the committed monthly reports
up instead of reading records (`internal/cli/runs_digest.go:109`, `:222`) and says how many of the
twelve it added up (`internal/digest/layout.go:201`). *Consequence:* the year period needs no new
design; it needs the monthly cadence to have been kept (F16).

**F11: Exists, and is a different surface. `fugaro report`.** `ee/report/cli/report.go:67` is the
spend report — `--by day|week|month|year|repo|model|person|mode` (`:108`), Firestore spend history
with a live fallback, `--csv`/`--json` — and it is a business-licensed command registered from
`ee/register/report.go:16`; its MIT half is `internal/cli/reportcore.go:1-13` (D444). It is not
committed anywhere and it is not a run review. *Consequence:* the two must not be merged, and the
spec says so (§9).

**F12: Exists. The decisions this design builds on are answered and cited.** D320–D328 are in
`docs/task-governance/reconciliation.md:297-303`: the report's own pull request (D320), the folder and
the index (D321), one repository per report (D322), IDs and numbers and no people (D323), Fugaro's
own reports in this public repository (D324), the selection and the flags (D325), the fixed pattern
rules (D326), the redacted draft and the issue form (D327), and the maintainer's rewrite (D328).
*Consequence:* this design does not reopen any of them; where it disagrees it says so and asks for a
new number (F21, F23).

**F13: Exists. The register's half of the live check.** Check 136 — a report run's pull request — has
its row (`docs/gcp-live-checklist.md:785`) and its section (`:10643`), pinned as a pair by
`internal/cli/docs_task_governance_checks_test.go:75`. The row and the section both say it is
**NOT RUN** and is the owner's, and no agent runs any step of it. *Consequence:* this design takes
**no check number** (README, "Numbers this work holds"); what it wants from the owner is that check,
run once (F14).

## 2. What is missing, and what conflicts

**F14: Missing. This repository carries no reports of its own.** D324 answered that Fugaro's own
reports go into this public repository under D323's rules, and `docs/fugaro-reviews/` does not exist
in the tree at all; the folder's absence is also why the product's flagship example of the feature
cannot be read by anyone evaluating it. **Conflicts** with `website/data/typical-costs.yaml:11`,
whose figures are the owner's hand measurements over a window that closed on 2026-10-19, two days
before the digest shipped: D324's stated rationale — that the reports' figures "already inform"
that file (`docs/task-governance/reconciliation.md:300`) — is not yet true. *Consequence:* spec §8 gap
5, and task R5, which is the owner's to run.

**F15: Missing. Nothing commits what the CLI writes.** `fugaro runs digest` writes the report and the
index with `os.WriteFile` and prints the two paths (`internal/cli/runs_digest.go:266-274`); it has no
commit, no push and no pull request. Only a report run commits (F5). *Consequence:* the owner's "each
saved and committed to the tree" holds only for the run path, and a cron or a person must add the
second half themselves; the spec fixes this as the CLI's deliberate boundary (§3), because a CLI that
commits decides the branch, the identity and the message for a user who may be on any branch.

**F16: Missing. Nothing tells a user a report is due, or that the cadence has lapsed.** A search for
a due, overdue or missing-report surface in `internal/cli` finds none: `digestPeriod` only refuses a
period that is still open (`internal/cli/runs_digest.go:291`), and no other command reads
`digest.Dir`. The runner computes what is due (F6) and nothing else does. *Consequence:* the skill's
cadence is honour-system prose; spec §6 adds `fugaro runs digest --due` (D962).

**F17: Missing, and a conflict of ownership. The due computation is unreachable from the CLI.**
`digestDuePeriods` and `digestCatchUpDays` are unexported in `internal/runner/digest.go:70`, `:425`,
and `internal/runner` is a package a CLI read must not import into (it would drag the whole runner
into the CLI's dependency graph). *Consequence:* the computation moves into `internal/digest` — one
implementation read by both — and the runner keeps only its own use of it (D962, task R0).

**F18: Missing. Nothing installs the cadence, and the setup path never mentions it.** The three ways
to schedule a report are in `plugin/skills/working/reference/periodic-reviews.md` §2, and nothing
carries them to a user at the one moment they are cheapest to decide — `fugaro setup`. The `setup`
skill mentions neither the digest nor the reviews. *Consequence:* spec §6, D965: the setup skill
prints the three ways and the exact command for each, and writes nothing without the user's word —
**answered by the owner on 2026-11-04: the user installs the cadence, and Fugaro writes no workflow
and no crontab.**

**F19: Missing. The pattern rules cannot see far.** The longest windows are four weekly reports and
three months (`internal/digest/patterns.go:39-56`); nothing reads the daily reports as a series and
nothing reads the yearly ones, which are the only documents that can survive the 90-day retention.
A user who reviews every day for a quarter gets no rule that spans that quarter. *Consequence:*
spec §5, D968 adds one rule with a longer window — **answered by the owner on 2026-11-04: yes, one
longer window, `cost_per_run_rising` over five months**; D966 refuses a separate trend file.

**F20: Missing, deliberately. The thresholds are not configurable — and there is a real tension.**
The thresholds are constants (F4). They are also the one part of a report a repository might want to
loosen, and this design keeps them fixed (D967): a `fugaro.yaml` key that lowers a threshold is a key
that silences a signal about the repository's own cost, and the policy merge's "only tightening wins"
does not apply to a threshold, because a bigger number here is not a wider permission anywhere else.
*Consequence:* a user who disagrees with a threshold gets a report that says so, not a key; if the
owner wants the key later, it takes a new decision — and there is now a command that would carry it,
`fugaro settings` (D1160–D1183, `docs/config-management/`), which writes only the rows its own
registry declares (§4, M2).

**F21: Missing. A learning that is not a wording change has no home between the issue and a
release.** The backlog's `filed-in` vocabulary is `run`, `pr` and `hand` (`internal/backlog/backlog.go:56`),
so an item filed from a learning is `hand` — which is already enough, and needs no new kind; what is
missing is the stated rule that a learning needing product work is filed at all, and that a learning
that is a wording change lands as a skill change in the same release. *Consequence:* spec §7, D970
and D971; task R6 writes the two sentences and touches no code.

**F22: Exists, and it is the strongest part of the request's shape. Nothing is automatic.** There is
no send seam in `--submit-draft` (F7), the form requires the person's own grants (F8), the skill's
own test refuses a skill that submits on its own (`plugin/periodic_reviews_skill_test.go:70`), and
the maintainer rewrites before anything ships (`CONTRIBUTING.md:67`). *Consequence:* the design's
decisions about the channel (D970, D971) are statements of what already holds plus the one thing
missing, not a new mechanism.

**F23: Conflicts, and it is left alone. `fugaro report` and `fugaro runs digest` both answer "what
did the period cost".** `report` is dollars by day, week, month, year, repository, model, person and
mode over the project's spend history, across repositories, business-licensed, never committed
(F11); `runs digest` is runs, flags, stages and dollars, for **one** repository, committed into it,
MIT. Merging them would put a cross-repository, person-carrying table into a file that a possibly
public repository commits, which D322 and D323 refuse. *Consequence:* neither changes; the plan
touches `ee/` and `internal/cli/reportcore.go` in no task, and the spec says so (§9).

**F24: Exists. A report carries no address and no task text, and a test holds it.** The closed
vocabulary is `internal/digest`'s own (`internal/digest/patterns.go:58-69` states the rule for a
pattern's fields), the folder's files are checked by the live check for addresses
(`docs/gcp-live-checklist.md:10710`), and the draft's renumbering is tested
(`internal/cli/runs_digest_submit_test.go`). *Consequence:* spec §4 is a statement of what holds, and
the one thing it decides is the opposite temptation — that the **committed** report keeps its run IDs
(D969, **answered by the owner on 2026-11-04 as recommended**), because the daily sweep needs them
and the report is the repository's own document. §4, M3: the person-class reads have since landed,
so this boundary now has live surfaces on the other side of it.

**The rulings of 2026-11-05 (§5) re-read six of these findings.** F2 gains a writer and keeps its
rule (the same layout writes every report: the job, a person's `--dir` write and the report run, and
the commit copies bytes rather than rendering them); F5 is unchanged in itself and is joined by the
job (E4); F10 gains the `reports/` prefix's own lifecycle (E3) while `runs/` keeps its 90 days; F14
is where the owner's own reports now arrive (the job writes them, the opt-in commit lands them, E5);
F15 is answered by the opt-in commit run rather than by a flag on the CLI, which keeps D964's answer
(E5); and F16's due signal keeps its command while its source is re-opened (E8, Open items).

## 3. Decisions D960–D971, and the owner's answers of 2026-11-04

**The owner answered the design on 2026-11-04.** Three decisions were named in words — **D965**,
**D968** and **D969** — and **each is as recommended, so no answer here is "not the
recommendation"**; the other nine were not singled out, and the recommendation in the table stands
for each of them, which is what the plan is written to. **The three answers, each with its why:**

- **D965 — the user installs the cadence; Fugaro writes no workflow and no crontab.** *Why:* a
  schedule Fugaro wrote would commit into a repository it does not own, under the user's identity,
  for a choice that is cheap for the user to make and expensive for Fugaro to get wrong.
- **D968 — yes, one longer window: `cost_per_run_rising`, over five months.** *Why:* the four rules
  read at most four weeks and one month against the month before, so a slow rise across a quarter and
  a half is invisible to every one of them.
- **D969 — the committed report keeps run IDs, stages, recipes and figures and carries no person,
  address, task text or log line; the outgoing draft renumbers the runs and drops the repository
  name.** *Why:* the report's reader is the repository's own agent and reviewer, who acts on a
  flagged row by running `fugaro diagnose RUN`, while the draft's reader is a public issue that needs
  the figures and none of the identifiers.

The recommendation comes first in the table, with the cost of the alternative. **Five rows are read
through §5 from 2026-11-05 on: D960, D961, D962, D964 and D966, each marked at its own row.** The
rows after them (D967–D971) are unchanged by the rulings; **D965 is unchanged too, and §5 says why
the one schedule the rulings add is not the one it refuses.**

## 4. What `main` has overtaken (2026-11-04)

The design was written against `3d6ed04d` on 2026-11-01. This section is the refresh: what landed
since, in the order it changes this design. **Nothing here overturns a finding or a decision** — the
loop still ships, the gaps are the same, and the three answers of 2026-11-04 confirm the plan — but
five of them change a sentence in the spec or the plan (**M1**, **M2**, **M6**, **M8**, **M9**) and
the rest are context the design now rests on.

**M1: The managed gate landed, and it is the same principle D965 states.** `readManagedGate`
(`internal/cli/managed_gate.go:181`) admits or refuses a cloud write in a coding agent's session,
and it now covers `update`, `config publish`, `image refresh`, `accounts add`,
`project policy publish` and `settings`. *Consequence:* the two surfaces this design adds write
nothing — the due signal reads a folder, the doctor line reports what it read — so **neither is gated
and neither needs a row**: spec §9 says so. D965's "Fugaro writes no workflow and no crontab" is the
same rule one level out: the tool does not write into a place it does not own.

**M2: `fugaro settings` is a command now, so the threshold question has a concrete home.**
D1160–D1183 built the one path that writes `fugaro.yaml` without a hand edit
(`docs/config-management/README.md:72`). *Consequence:* D967 still gives the patterns' thresholds no
key, and now the reason is sharper: `settings` writes the rows its registry declares, so a threshold
key is a row somebody adds deliberately, not a shape a report may invent. Spec §9 gains the sentence;
no task changes.

**M3: The person-class reads landed.** GitHub's arrived in #1646 and #1669, Bitbucket's is designed
in `docs/bitbucket-credentials/reconciliation.md:557`, and the spend history's own "person" is the
stored requester address (`ee/report/cli/report.go:88`). *Consequence:* F24's boundary — a committed
report carries no person and no address — now separates two live surfaces rather than stating a rule
with nothing on the other side. D969's answer is what keeps the boundary where it is.

**M4: The command set grew: `settings`, `rigor` and `accounts` are on `main`.** *Consequence:* none
of it changes a task. The due signal is a flag on an existing subcommand (`fugaro runs digest --due`)
and the doctor line is a check in an existing command, so `internal/cli/root.go` — the file another
work stream owns — is still not touched (R1, R2).

**M5: The project image catalog shipped.** `imageCatalogShipped` is `true` as of 0.18.0
(`docs/release.md:152`), the catalog's design folder is `docs/project-image-catalog/`, and the
launcher names **#1676** as the repo-image removal design. *Consequence:* the plan's "no new image"
still holds — a report run deploys whatever image a run deploys, and R5's report run needs no image
of its own. The release slot moves for other reasons (M8).

**M6: `fugaro upgrade` still exists, and it is what pins a checkout to a release.**

### E4. One project-level writer, and no per-orchestrator scheduler (ruling 3)

**The ruling.** There are many orchestrators and developers; the writer is **one project-level
scheduled Cloud Run job** in the project's GCP, **on the 0.18.0 catalog check job's pattern**
(`deploy/terraform/gcp/modules/installation/catalogcheck.tf`, `internal/infra/catalogcheck.go`): its

content or skips.

**What the owner settled about that account on 2026-11-05, after the review of the plan (answered
2026-11-05, as recommended).** Three things the ruling's own sentence left to the code, and each is
now decided:

- **The listing half, the full condition it needs, and the check that proves it.** Reading the run
  records is not one grant: a condition on `resource.name` **grants no listing**
  (`docs/design/bucket-iam.md` §2.3, live check 7's 403 on listing `runs/`;
  `docs/task-governance/reconciliation.md` already flags the same doubt), so the account needs
  `objectViewer` on `runs/` **through the prefix-limited listing mechanism**
  (`storage.googleapis.com/objectListPrefix`, unverified — bucket-iam §4, V7). **And the reverse
  holds too, which the plan states in full:** a condition carrying only `objectListPrefix` **cannot
  read an object**, so **both** grants carry **both** clause halves for their own prefix —
  `objectViewer` on `runs/` and `objectUser` on `reports/` — and **the halves are joined by `||`,
  never by `&&`**: the shape is the one `gcp.ProjectBucketCondition` already builds, per-prefix
  clauses joined with `" || "` (`internal/backend/gcp/names.go:537`), each grant reading

  ```
  resource.name.startsWith("projects/_/buckets/<b>/objects/<p>/") ||
  api.getAttribute('storage.googleapis.com/objectListPrefix', '').startsWith("<list prefix>")
  ```

  A conjunction is the shape a reader reaches for first and it matches nothing — a `get` carries no
  `objectListPrefix`, a `list` names no object — and a single half is a job that fails on its first
  run: the `resource.name` half grants no listing, and the listing half cannot read an object.
  **`<list prefix>` is left to the check, not decided here:** the attribute's value form — the
  request's own prefix (`runs/`) or the full `projects/_/buckets/<b>/objects/runs/` path — is
  unverified offline, and no code in this repo reads the attribute today. The listing half is not a
  `runs/` speciality either: R11's stored reader lists `reports/<slug>/<YYYY>/` the way today's reader
  lists a checkout's folder twice over, so `reports/`'s grant needs its listing clause as well. Its
  scope is the prefix and not one repository: the job summarises every repository, so it lists under
  `runs/` and `reports/` and no wider — the root listing is refused. The owner ruled that **an
  owner-run live check proves it before the job's Terraform lands**: a service account
  holding both conditioned grants lists `runs/<slug>/` and `reports/`, reads one object under `runs/`,
  and is refused the **root listing** (`gs://<bucket>/`), reading a `tokens/` object and listing
  `tokens/` or `cache/`. **If it fails, the plan stops and asks** — the bucket-wide viewer a listing
  otherwise needs is not planned as a fallback, because it would read `tokens/` and `cache/` too.
- **`reports/` has one writer, the job, and launchers read it.** The job holds
  `roles/storage.objectUser` on `reports/`; a person holds **read only** — which their existing
  unconditioned bucket-wide `objectViewer` already gives, so nothing new is granted to a person and
  **no launcher write grant on `reports/` is added** — the launcher's write condition
  (`gcp.LauncherBucketCondition`) covers `runs/` and `tokens/` as it is (`docs/design/bucket-iam.md`
  §4, H5), and `reports/` does not join it (a second writer is what this ruling refuses).
  **No other job account gets `reports/` either**: job accounts reach `runs/`, `cache/` and `locks/`,
  so the opt-in commit run (E5) reads the stored reports **under the starting person's launcher
  account**, not the run's.
- **Enabling it is a setting `fugaro update` writes, not a `gcloud` command.** The project layer gains
  `jobs.reports.paused` (and `jobs.catalog_check.paused`), each defaulting to `true`;
  `gcloud scheduler jobs resume` is undone by the next update, because the module always applies
  `paused`. **The 0.18.0 catalog check has the same gap from the other side** — its `paused` is a
  Terraform variable with no field in `CatalogCheckSpec` — and the task that adds the reports job's

  set` may write it is **Open item 6**, not decided here.

*Why:* a scheduler per orchestrator would write the same report many times, and each copy would need
a credential; one job holds one narrow account and one schedule.
