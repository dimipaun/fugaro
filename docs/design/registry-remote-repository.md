
# Serving `fugaro-base` through an Artifact Registry remote repository: retiring the copy

Status: design for review (2026-10-14), from the owner's question — *"why are we still mirroring?"* — after [retire-image-mirror.md](retire-image-mirror.md) (#318, verify-then-copy) kept the copy and deferred exactly this (`§8`, Option B). **Docs and a plan only: no Go, Terraform or workflow file in this change.** The plan is [docs/plans/2026-10-14-registry-remote-repository.md](../plans/2026-10-14-registry-remote-repository.md); the owner-run check is [docs/gcp-live-checklist.md](../gcp-live-checklist.md) Check 43.

**The one-paragraph answer to the owner.** The copy exists because Cloud Run Jobs and Cloud Build must pull through somewhere the installation controls, and at M11 design time (`docs/design/m11-setup-and-skills.md` §3.3, §14) `ghcr.io` was believed unreadable from them and the packages were private. Both premises are gone: the packages are public (every release's `verify-public` proves anonymous pulls, §2.3), and Artifact Registry **remote repositories support `ghcr.io` as a Docker upstream** (§2.1) — a documented, first-class feature, not a guess. So the installation does not need to *own bytes* to control them: it can own a **pull-through proxy** and reference a **digest** through it. This design deletes the base image's copy step, and with it 1.2 GB pushed through the operator's laptop, a per-installation artifact that only ever held "whatever the tag resolved to when someone last copied", and the whole class of "which copy of the base is this repository on" questions. What replaces it is narrower and stronger, and it arrives in two steps — because the first one is **planned, not shipped**. **#318's Task 1 and Task 2 are a plan**: `internal/cli/init_images.go:32-36` records cosign verification and a signed digest list in the release as *"the planned fix (plan, follow-up to T2), not in this change"* (the phrase is the `:35-36` sentence), and `internal/mirror/ref.go:22-27` states the same limitation in its own words — *"cosign verification and a signed digest list in the release are the planned fix."* — with no reference to T2 and no "not in this change"; `--expect-digest` (a digest obtained out of band) is the only pin the CLI has today. **With those two tasks shipped** — they stay required, unchanged (§9) — the CLI at `fugaro init --base`/`image refresh`/`upgrade` resolves the release's `-pinned` tag on ghcr.io, **verifies its cosign signature**, reads that digest back **through** the remote repository to prove the path works, and pins `base_images.base` to the remote-repository path **at that digest**; every job from then on pulls a content-addressed digest, not a mutable tag. Nothing here is on disk today: 43a-43c are the go/no-go and need no Fugaro change, and 43d-43f are unrunnable until such a release exists (§8).

## 1. What the owner asked, and what this document is

`docs/design/retire-image-mirror.md` §8 states the deferred option verbatim: *"whether Artifact Registry's remote-repository feature supports an arbitrary third-party upstream such as `ghcr.io` at all is UNVERIFIED and would need its own live check."* This document settles that from public documentation (§2), states which facts are still UNVERIFIED and which live check settles each (§2.12), designs the change (§3), compares the trust model with today's copy (§4), says exactly what is deleted, what stays and what Terraform adds (§5), covers the derived-image build (§6), the failure modes (§7), the owner's live check (§8), and how this relates to #318's tasks (§9).

**Corrections to #318's premise, stated up front, because they change its conclusion.** #318's plan says (its round-five note): *"the daily image check job is itself a Cloud Run Job running directly FROM the base image, and Cloud Run Jobs cannot deploy a bare `ghcr.io` reference (not verified live, assumed conservatively)"*. That assumption is **false as of the documentation read in §2.6**: Cloud Run today documents direct pulls of public GitHub Container Registry images, and recommends an Artifact Registry remote repository *specifically* for higher availability and for private GHCR images. The reason to use a remote repository is therefore no longer "Cloud Run cannot read ghcr.io" — it is §3.5's reason: **keeping exactly one, Artifact-Registry-shaped representation of "what base was this built from"**, which `internal/infra/tf/cover.go`, `submitRebuild`, `refreshVerdict` and `triggers()` all require.

## 2. Verified facts, each with its source

Everything in this section was read from public documentation on **2026-10-14**. Anything not verifiable this way is in §2.12 and marked **UNVERIFIED**, to be settled by Check 43.

### 2.1 Artifact Registry remote repositories support ghcr.io as a Docker upstream — VERIFIED

- *"Remote repositories store artifacts from the following upstream sources: Standard Artifact Registry repositories. External sources such as the following: CentOS, Debian, Docker Hub, **GitHub Container Registry (ghcr.io)**, Maven Central, The Python Package Index (PyPI)."* — [Create remote repositories](https://cloud.google.com/artifact-registry/docs/repositories/remote-repo), §intro.
- The Docker **preset** list holds exactly one entry — `https://registry-1.docker.io`, preset name `DOCKER-HUB` — so ghcr.io is not a preset: it is a **custom upstream**. Custom upstream URLs are supported for Docker, and the documentation's own "Custom URLs" table lists, verbatim: *"Docker | `https://ghcr.io` | GitHub Container Registry"* — [Remote repository overview](https://cloud.google.com/artifact-registry/docs/repositories/remote-overview), §"Custom URLs".
- Constraints that apply to a custom upstream: **HTTPS only** (*"Custom remote repository upstream URIs must use HTTPS. Unencrypted HTTP upstream URIs are not supported"*), **internet-accessible** (*"Remote repositories don't support on-premise or Virtual Private Cloud (VPC) network upstream sources without a public IP address"*), and the repository's *upstream source* is fixed at creation (*"you must configure the following settings, which can't be changed after the repository is created: … Remote repository upstream source"* — Create remote repositories).

### 2.2 The image path through a remote repository

- A remote repository is an ordinary Artifact Registry repository as far as an image reference goes. The documentation's own Docker example: `docker pull us-central1-docker.pkg.dev/PROJECT/quickstart-docker-hub-remote/busybox:latest` — *"us-central1-docker.pkg.dev is the hostname for the Docker repository you created. … quickstart-docker-hub-remote is the ID of the repository you created. busybox is the name of the image you want to pull from Docker Hub"* ([Create a Docker Hub remote repository](https://cloud.google.com/artifact-registry/docs/repositories/create-dockerhub-remote-repository)).
- So the shape is `<location>-docker.pkg.dev/<project>/<remote-repository-id>/<upstream path>[:tag|@digest]`. For Fugaro's upstream that means **`<region>-docker.pkg.dev/<project>/fugaro-ghcr/dimipaun/fugaro-base`** (§3.1). **UNVERIFIED as a whole** (§2.12 a): the documentation's only worked example is a preset upstream whose path happens to be a single segment; that the upstream path is appended verbatim is inferred from it, not stated.

### 2.3 Authentication to a public ghcr.io package — VERIFIED, and it requires nothing

- GitHub: *"You can … access public container images anonymously"* — [Working with the Container Registry](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry), §intro.
- Artifact Registry remote repositories take an *"Authenticated"* or *"Unauthenticated"* mode; credentials (a username plus a Secret Manager secret version) are optional and can be **added later** to an unauthenticated repository (*"You can add authentication to an unauthenticated repository after you create the repository, but you can't change an authenticated repository to an unauthenticated repository after you create it"* — Create remote repositories). Fugaro's packages are public (§1), so the repository is created **unauthenticated** — no secret, no rotation, nothing in the trust chain.
- *"If you want to authenticate to an upstream repository, then enable the Secret Manager API"* (Create remote repositories) — not needed for us, so `fugaro init` gains no new API and no new secret.
- The upstream is **validated at creation** unless told otherwise: the Terraform provider's `disable_upstream_validation` — *"If true, the remote repository upstream and upstream credentials will not be validated"* ([`google_artifact_registry_repository`](https://registry.terraform.io/providers/hashicorp/google/latest/docs/resources/artifact_registry_repository)). The design leaves validation **on** (the provider's default), so a typo'd upstream URI fails the apply rather than a job's first pull.

### 2.4 How tags and digests are resolved and cached — VERIFIED

- *"The first time that you request a version of a package, Artifact Registry downloads and caches the package in the remote repository. The next time you request the same package version, Artifact Registry serves the cached copy. If you request an artifact from an upstream source that doesn't exist, or doesn't contain the version you specified, then the request will fail."* — Remote repository overview, §"How remote repositories work".
- *"Cached artifacts are also still available if the external public repository is offline due to an outage or other issue."* — same page, §"Use cases and benefits". This is the answer to *"what happens if ghcr.io goes down after the first pull"* (§7).
- Mutable metadata is refreshed after a per-format age; for **Docker the row is *List/Get tags cache*, 1 hour** (*"Mutable files such as package indexes and metadata are updated from the upstream source when they become more than the default age"* — same page, §"Updates to package indexes and metadata"). **UNVERIFIED**: whether that 1-hour figure also governs a *manifest fetched by tag* (as opposed to a tag listing), i.e. how long a re-pushed tag stays invisible (§2.12 f).
- The wire protocol is one identifier, not two: *"`<tag-or-digest>` MUST be either (a) the digest of the manifest or (b) a tag. The `<tag-or-digest>` MUST NOT be in any other format."* — [OCI distribution specification](https://github.com/opencontainers/distribution-spec/blob/main/spec.md), §"Pulling manifests". A *client-side* reference may carry both — `referencePat = anchored(capture(namePat), optional(':', capture(tag)), optional('@', capture(digestPat)))` — [distribution/reference](https://github.com/distribution/reference/blob/main/regexp.go) `regexp.go`. That is why §3.1's pinned reference is a client-side string whose digest the client resolves before the request.

### 2.5 How a new tag or digest on ghcr becomes visible

- Through the remote repository, nothing is fetched until it is *requested* (§2.4), and a **digest** request is content-addressed: the only question is whether Artifact Registry will fetch an unknown digest directly. **UNVERIFIED** (§2.12 b, c). This design does not depend on it for correctness in the sense that matters — see the next bullet — but it does depend on it for the *first* pull, which is why Check 43b tests it against a fresh repository.
- **The tag is never resolved through the remote repository.** The CLI resolves `<ver>-pinned` at `ghcr.io` directly, exactly as `internal/mirror` already does for a tag (`mirror.go:165`, anonymous, digest-verified against the `Docker-Content-Digest` header, `mirror.go:688-712`), and the jobs reference a digest. So Artifact Registry's tag cache — 1 hour or otherwise — can never make Fugaro pin, or a job run, the wrong bytes. It can only make a *by-tag* request stale, and this design makes none.

### 2.6 Cloud Run Jobs and Cloud Build can pull through it — VERIFIED

- *"You can directly use container images stored in Artifact Registry, or public images from Docker Hub or GitHub Container Registry. Google recommends the use of Artifact Registry. Public images from GitHub Container Registry and Docker Hub images are cached for up to one hour. You can use container images from other public or private registries (like JFrog Artifactory or Nexus), or private images from GitHub Container Registry, by setting up an Artifact Registry remote repository."* and *"For higher availability, Google recommends deploying these Docker Hub or GitHub Container Registry images using an Artifact Registry remote repository."* — [Deploying container images](https://cloud.google.com/run/docs/deploying), §"Supported container registries and images"; the identical text appears in [Create jobs](https://cloud.google.com/run/docs/create-jobs).
- *"To deploy public or private container images that are not stored in Artifact Registry or Docker Hub, or are not public images in GitHub Container Registry, set up an Artifact Registry remote repository. Artifact Registry remote repositories allow you to: Deploy any public container image. …"* — Deploying container images, §"Deploy images from other registries".
- A remote-repository path is an Artifact Registry path, so it needs nothing new from Cloud Run or Cloud Build: Cloud Build already pulls step images and `FROM` images from Artifact Registry as the build account today, and the owner's 2026-10-12 live test (project `fugaro-dev`, build `c503576c-51d9-4f96-b9e7-debae7d0df39`) already proved `docker pull ghcr.io/dimipaun/fugaro-go:0.6.5` succeeds in Cloud Build in 21 s as the default compute service account (`docs/design/retire-image-mirror.md`, header) — i.e. the pull path this design routes through a proxy is not in question; what the proxy adds is the controlled path and the digest pin.
- Two constraints that touch this design: *"Cloud Run does not support container image layers larger than 9.9 GB when deploying from Docker Hub or an Artifact Registry remote repository with an external registry"* (Deploying container images) — the base image unpacks to about **3.8 GB** (measured: 3812 MB on amd64, `docs/design/base-image.md:267`) and no single layer is anywhere near the ceiling, but it is a limit worth knowing; and *"When you create a new job, the Cloud Run service agent needs to be able to access the container, which is the case by default"* (Create jobs) — the runtime pull is by the Cloud Run service agent, in-project here. **Two sizes, one image, and this document quotes both:** about **3.8 GB** is what the base *unpacks to* (measurement and the 4000 MB size budget: `docs/design/base-image.md:267`), and about **1.2 GB** is what it *moves over the wire as compressed layers* (`docs/design/base-image.md:272`: *"The copy: `fugaro init --base` and `image refresh` move the base through the operator's machine: about 1.2 GB instead of about 0.3 GB"*, the 0.3 GB being the old per-language images). Every 1.2 GB figure below — §2.8, §4, §7, §8/Check 43 — is the compressed one, and Check 43's "about 1.2 GB" of cached layers is the same number.
- Images may be named *"with a tag … or with an exact digest"* (Deploying container images) — which is what a pinned reference needs. Whether Cloud Run and Cloud Build accept the **combined** `:tag@digest` reference form (§3.1) is **UNVERIFIED** (§2.12 d).

### 2.7 IAM

- Creating a remote repository needs `roles/artifactregistry.admin` on the project (`artifactregistry.repositories.create`; *"Granting the artifactregistry.repositories.create permission to end users through the roles/artifactregistry.admin role is highly privileged"* — Create remote repositories, §"Required roles"), which the operator running `fugaro init` already has.
- Pulling needs *"Artifact Registry Reader (`roles/artifactregistry.reader`) on the Artifact Registry repository of the deployed container image"* (Deploying container images, §"Required roles") — grantable per repository ([Access control with IAM](https://cloud.google.com/artifact-registry/docs/access-control)). Cloud Build's pulls run as the repository's build account, so it needs that role **on the new repository**; see §5.3.

### 2.8 Cost — VERIFIED

- Remote repositories are billed like standard ones: *"The following types of repositories store artifacts: Standard repositories. Remote repositories. …"*, storage at *"$0.00 (Free) / 1 gibibyte hour, per 1 month / account"* for the first 0.5 GiB-month and *"$0.000136986 / 1 gibibyte hour"* above it, per billing account ([Artifact Registry pricing](https://cloud.google.com/artifact-registry/pricing)).
- *"Data transfer into Google Cloud is free."* — same page. The ghcr.io → Artifact Registry leg is therefore not billed. Delivery to a client in the same location is *"$0.00 (Free) / 1 gibibyte"* (same page), which is the case for Cloud Run Jobs, Cloud Build and the operator's own machine in the installation's region. Egress to the internet is Premium-tier priced (same page).
- Net effect for an installation (§3, §4): roughly the same registry storage as today's copy (only what the jobs actually pull is cached — the linux/amd64 layers), **minus** about 1.2 GB of compressed layers uploaded from the operator's machine per copy (`docs/gcp-setup.md` §3: *"About 1.2 GB is copied through your machine"*; the uncompressed image is ~3.8 GB, §2.6), and minus the copy's own storage when nothing pulls it.

### 2.9 Regions — VERIFIED

- A repository's location is *"regional or multi-regional"*; a remote repository's location is one of the settings *"which can't be changed after the repository is created"* (Create remote repositories), and `gcloud artifacts locations list` names the supported ones ([Repository locations](https://cloud.google.com/artifact-registry/docs/repositories/repo-locations), where `us-east5` — the installation's own region in `fugaro-dev` — is listed). Whether remote repositories are available in *every* listed location is **UNVERIFIED** (§2.12 k); Check 43a creates one in the installation's own region.

### 2.10 Limits — VERIFIED

- *"Public upstream host reads per organization, per region, per minute | Default | 600"* ([Artifact Registry quotas and limits](https://cloud.google.com/artifact-registry/quotas), §"Remote Repository Limits"); the same page: *"Requests to upstream hosts count against your organization's upstream host read request limit"*, *"Once the artifact has been cached to your remote, requests for that artifact only count against your project's request quota"*, and *"you might be subject to the upstream repositories' read and write quotas"*. Max *"data retrieval from upstream of remote repository per request | 9.9 GB"*. **The 600 is an inference for us, not a quotation that names our case:** the table row says *Default*, and the page does not say whether a *custom* upstream over ghcr.io is one upstream host, one per organization, or exempt. It is the number a burst would hit, and no item of Check 43 measures it (§7).
- Error shapes to expect, from [Troubleshoot remote repositories](https://cloud.google.com/artifact-registry/docs/troubleshoot-remote): **404** *"when the requested artifact doesn't exist in the upstream repository"*; **429** *"when the upstream read limit is exceeded"*; **502** *"when the upstream repository responds with an error code"*; **504** *"when the upstream repository is offline or cannot be contacted"*.

### 2.11 VPC Service Controls — VERIFIED, and it is a real constraint

- *"If Artifact Registry is in a VPC Service Controls service perimeter, Artifact Registry denies access to upstream sources outside the perimeter by default. To allow remote repositories in a specific location to access their configured external sources outside the perimeter, see the instructions for VPC Service Controls configuration."* (Remote repository overview.) The per-location switch is `gcloud artifacts vpcsc-config allow --project PROJECT_ID --location LOCATION` (or `deny`), read with `gcloud artifacts vpcsc-config describe`, and needs `roles/artifactregistry.admin` (Create remote repositories, §"Access to upstream sources in a service perimeter"). Denial blocks only upstream *fetches*: *"existing cached artifacts in remote repositories are still available."*
- This is the one case where this design asks more of an operator than today's copy does, and the documented switch is a single, idempotent command. Projects that cannot open that door keep `--base-image` (bring-your-own), unchanged (§5.2).

## 3. The design

### 3.1 One new installation singleton, one new shape for `base_images.base`

**Terraform adds one `google_artifact_registry_repository` per installation** (i.e. per project — an installation is a project in Fugaro's model, and the installation root already owns `fugaro-base`), in `deploy/terraform/gcp/modules/installation/registry.tf`:

```hcl
resource "google_artifact_registry_repository" "ghcr" {
  project       = var.project
  location      = var.region
  repository_id = var.names.ghcr_registry          # default "fugaro-ghcr" (§5.3)
  description   = "Public Fugaro images from ghcr.io, cached for this installation's builds and jobs"
  format        = "DOCKER"
  mode          = "REMOTE_REPOSITORY"
  labels        = { fugaro = "managed" }
  remote_repository_config {
    description = "ghcr.io"
    docker_repository {
      custom_repository { uri = "https://ghcr.io" }
    }
  }
  # No upstream_credentials: the packages are public (§2.3).
  # No cleanup_policies: the cache is the point (§7).
  lifecycle { prevent_destroy = true }             # required of every registry (§5.3)
}
```

The name must match `internal/infra/tf/cover.go`'s `repoID = ^fugaro(-[a-z0-9-]+)?$` (cover.go:154), which every `*_iam_member` on a registry is checked against (cover.go:628-632) — `fugaro-ghcr` does.

**The reference `base_images.base` holds** — and therefore what the check job's container image, `FUGARO_CHECK_SPEC`'s `base_images` map and Cloud Build's `FUGARO_BASE` substitution all carry — is:

```
<region>-docker.pkg.dev/<project>/fugaro-ghcr/<owner>/fugaro-<kind>:<ver>@sha256:<index-digest>
```

**That shape is closed, and the digest is part of it.** `<owner>` is the source owner this installation is configured to trust — `dimipaun` from `mirror.DefaultSources` (`internal/mirror/ref.go:56`, `[]string{"ghcr.io/dimipaun"}`), or a fork's own owner, as recorded in the local config's `image_source` by the run that pinned (`--image-source ghcr.io/<owner>`, an installation-only flag: §3.6's row on where the owner lives) — and `fugaro-<kind>` is the kind's own image name. A reference under `fugaro-ghcr` that does not have exactly that shape, **including a `@sha256:<64 hex>` digest**, is not this installation's pin and is treated as a foreign image everywhere (a custom base, refused rather than kept). §3.6 is why, and it is the reason the remote repository does not weaken the confinement the other validators enforce.

**Why the tag stays even though the digest pins.** The tag is the version marker, and three existing, load-bearing parsers read it:

- `managedVersion(ref, host, kind)` (`internal/cli/init_images.go:137-140`) cuts `"<host>/<repo>/fugaro-<kind>:"` and requires a release version — it answers *"is this entry a release base an earlier run pinned, or a custom/hand-pushed base this CLI must never touch?"*, which is also `isManaged`/`curVersion` and `refreshBase`'s refusal (`image_refresh_rules.go:26-46`). §3.6 gives it the owner and the digest it needs to answer that question about the remote path.
- `baseRefReleaseRE` (`internal/cli/init_fugaroyaml.go:369-375`), `\A[^\s@]+/fugaro-(base):v?([0-9]+\.[0-9]+\.[0-9]+)(?:@sha256:[0-9a-f]{64})?\z`, drives `imagePredates`/`recipes_skew.go` and `config_publish.go`'s layered-config gate. **It already accepts a digest suffix**, and it does not care which repository the path goes through — a happy coincidence of its `[^\s@]+` prefix, and the reason a digest-pinned release base was already anticipated here.
- `refreshVerdict`'s never-downgrade rule (`image_refresh_rules.go:51-67`) uses `managedVersion`'s version to keep a *newer* pin when an older CLI refreshes. A bare digest carries no order, and a CLI cannot resolve a digest back to a release (only ghcr.io's `-pinned` tags map version → digest, one-way). So the version must remain readable, or "never downgrade" becomes unanswerable — and the fallback (a new `base_versions` map in the local config plus its shared-config validation) is strictly more surface for the same information.

The digest, not the tag, is what the pull resolves (§2.4): the client asks the registry for the digest, so a moved tag cannot change what a job runs. §2.12 d is the one open question — if any of the three consumers rejects the combined form, the fallback is the digest-only reference plus a recorded version, and it is the owner's call (§10).

### 3.2 Where the digest and the signature are verified: the CLI, before it pins

The verification stays exactly where #318 put it — the **operator's machine**, at the one moment Fugaro writes the value that everything else reads — and the copy it used to precede is what disappears. **The symbols named below are #318's plan, not code on `main`** (`basepin.Resolve`, `basepin.OCIVerifier`, `mirror.ResolveDigest`): this design keeps them, and it is unrunnable until #318's Task 1 and Task 2 ship (§9). The four steps:

1. `fugaro init --base base` / `fugaro image refresh` (its base step, `internal/cli/image_refresh_steps.go:42-60`, routing through `internal/cli/init_images.go`'s `imagesStage`) / `fugaro upgrade` (whose cloud step *is* `fugaro image refresh`, `upgrade_cloud.go:433-489`) resolves `ghcr.io/dimipaun/fugaro-base:<releaseVersion()>-pinned` — the nightly-immune tag #318's Task 1 publishes and Task 2's `basepin.Resolve` reads — and gets the **index digest** (`mirror.ResolveDigest`, #318 Task 2's one new export, reusing `mirror.go:688-712`; no returning to the amd64 child, because nothing is being copied any more).
2. It verifies that specific digest's OCI-attached cosign signature against the `images.yml`-on-a-tag-push identity (`basepin.OCIVerifier`, #318 Task 2). No signature, or a wrong identity, refuses — nothing is pinned, nothing is written.
3. **It reads that digest back through the new remote repository** — `.../fugaro-ghcr/dimipaun/fugaro-base@sha256:<digest>`, a manifest GET with the operator's own Google credentials (the same authenticated client `internal/mirror` already uses for its destination side, `mirror.go:740-773`) — and **hashes the body it gets**, refusing unless the hash is exactly the requested digest. That is `getManifest`'s own rule, not a header read: *"the manifest ref names … returns its bytes, their digest (computed, and equal to the one a digest ref names and to the registry's header when it sends one)"* (`mirror.go:685-712`, which returns `ErrDigestMismatch` when the body hashes to something else, and again when the registry's `Docker-Content-Digest` disagrees with the body). A header-only check would prove reachability, not unchanged bytes. This one cheap request (no layers) does three things at once: it proves the upstream path shape (§2.12 a), it proves a cold digest fetch through the remote repository works (§2.12 b), and it proves the **bytes** survive the hop (§2.12 c). **It is this design's equivalent of #318's "verify before copy": verification moved from the bytes being copied to the path that will serve them.**
4. It writes `base_images.base` = the pinned reference (§3.1) into the local config (`init_images.go`'s `record()`, `:487-534`, which already re-reads the config, prints `base_images.<kind> = … (digest …)` and publishes the shared config) — and copies **nothing**.

Everything downstream is unchanged in structure: `fugaro image refresh`'s own later steps read the local config's value to move the check job and the clone jobs (`refreshCheckJob`, `refreshCloneJobs`) and to decide which workflows `refreshBuilds` rebuilds; `fugaro init --repo` renders it into the job, the spec and the build substitution.

### 3.3 What the job then references, and why nothing else had to move

- The check job's container image: `CheckSpec.Image = bases[kind]` (`internal/infra/spec.go:903-905`) → the pinned remote reference.
- `FUGARO_CHECK_SPEC`'s `base_images` (`spec.go:888-891`) → the same string, per kind.
- Cloud Build's `_FUGARO_BASE` substitution (`internal/backend/gcp/build.go:183`) → the same string, used as the derived build's step image and as `--build-arg FUGARO_BASE` (`images/derived/cloudbuild.yaml:75,104,144,159,210,237`).
- Clone workflows' job images (`spec.go:607-609`, `refreshCloneJobs`) → the same string.

**There is still exactly one representation of "what base was this built from", and it is Artifact-Registry-shaped**, which is why the fifth review's blocker in #318 does not reappear here (that review's two-representation problem was created by a ghcr.io-shaped value). Concretely, unchanged:

- `submitRebuild` (`internal/cli/imagecheck.go:695-700`, `s.BaseImages[kind]`), `refreshVerdict` (`image_refresh_rules.go:55`, `rec.BaseRef == want`) and `triggers()` (`internal/imagecheck/triggers.go:34`, `in.BaseRef != rec.BaseRef`) keep comparing like with like — exact string equality between the config, the deployed spec and the build record.
- The `refChars` guard the spec's refs pass through (`cover.go:727`, `^[A-Za-z0-9._:/@-]+$`) already allows `@` and `:`.
- `internal/infra/tf/cover.go` requires every registry-shaped value it sees to sit under `<registry>/<project>/` — the remote repository is in that project, so the pin passes the *prefix* half of that check as written. **Two separate tests do it, and they are not the same code:** `checkSpecs`'s `inRegistry` (`cover.go:749-754`, a closure) guards the `FUGARO_CHECK_SPEC`'s own `registry` (`:770`) and each of its `BaseImages` entries (`:779`), while a job **container's** `image` is a separate inline prefix test (`:650-651`) that never calls it. **But the prefix half is no longer a confinement on its own** once one repository in the project proxies all of ghcr.io: §3.6 is the change that keeps that promise, and it is a real code change to `cover.go` — **to both tests**, not "no change at all".

**What does need updating is every place that reads the shape of a base reference, not just the prefix.** That set is bounded and enumerated; §3.6 gives the rule, §5.5 lists the sites, and the plan's Task 4 carries a grep that finds them all rather than trusting the list.

### 3.4 What the check job's "copy dependency" becomes

Today the check job's image is the tag-shaped copy in `fugaro-base` (`docs/design/retire-image-mirror.md` §1: *"its container's `image = var.repo.check.image`"*). After this design it is the pinned remote reference; `RewriteCheckSpec`/`PlanCheckJob` (`internal/infra/checkjob.go:66-125,187`) move both the container image and the spec's map together, exactly as they do now — only the string changes. One consequence worth naming: a **digest-pinned** check job cannot be silently re-pointed by moving a tag, which today's tag-shaped copy can (`§4`).

### 3.5 Why a remote repository rather than pointing the jobs straight at ghcr.io

Cloud Run now documents direct public-GHCR pulls (§2.6), so "just use `ghcr.io/dimipaun/fugaro-base@sha256:…` everywhere" is a real alternative, and it is *rejected* here for reasons that are in the code, not in taste:

- `internal/infra/tf/cover.go`'s `inRegistry` would refuse it: a base image or a check job's image outside `<registry>/<project>/` fails the covered plan (`cover.go:650-651`, `:778-780`), so `fugaro init` could not create the resources this design would need.
- It would reintroduce #318's two-representation problem for `submitRebuild`/`refreshVerdict`/`triggers()` (exact string equality on `base_ref`), and a ghcr-shaped value cannot be compared against an Artifact-Registry-shaped one.
- Cloud Run's own direct-GHCR caching is *"up to one hour"* (§2.6) — an upstream outage with no warm cache would fail a job's pull where a remote repository's cache survives (§2.4).
- A remote repository gives the installation one place to see, audit and (later) credential the upstream, and one project-local path for every consumer, which is what a *per-installation* product wants.

The alternative is recorded, not hidden: if `cover.go`'s registry-confinement rule is ever relaxed *below* §3.6's shape test, this decision should be revisited.

### 3.6 A proxy over all of ghcr.io widens what is readable — so the confinement becomes the pin's shape

**The problem, stated plainly.** Today "an image under `<registry>/<project>/`" means something an operator or a build account put there: `fugaro-base` is writable only by people (`base_writer`, `modules/installation/iam.tf:137-145` — *"Only operators write the base images. Build accounts get reader"*) and each repo's registry only by its build account. Four validators lean on that prefix meaning *"vetted by us"*:

- `internal/infra/tf/cover.go` — **two tests, not one**. `checkSpecs`'s `inRegistry` (`:749-754`) gates the check spec's own `registry` (`:770`) and each `FUGARO_CHECK_SPEC` base image (`:779`); a job **container's** `image` is a separate inline prefix test (`:650-651`) that does not call `inRegistry` at all, and it is the one the task exists to close;
- `internal/cli/sharedcfg.go`'s `baseImageRE` (`:301-308`) — the published shared config's `base_images`;
- `internal/cli/init_images.go`'s `managedVersion`/`isManaged` (`:137-140`) — *"is this a release base an earlier run pinned, or a custom image the CLI must not touch?"*, which is also `curVersion` and `refreshVerdict`'s never-downgrade rule;
- `internal/infra/spec.go`'s `BaseImageWarnings` (`:846-856`).

A remote repository whose upstream is `https://ghcr.io` serves **every public image on ghcr.io**: `…/fugaro-ghcr/<anyone>/<anything>` sits inside the prefix, so all four would accept it. The digest pin protects *integrity*, not *provenance* — any digest that exists upstream is servable, including other owners', nightlies and old releases. Two concrete regressions follow if nothing changes:

- **The never-downgrade rule turns into a trap.** A shared- or local-config value `…/fugaro-ghcr/evil/fugaro-base:99.0.0@sha256:…` that parses as a managed release reads as *newer than this CLI*; `refreshVerdict` (`image_refresh_rules.go:51`; the never-downgrade branch is `:61-65`) then **keeps it forever**, and `fugaro image refresh` never replaces it.
- **The shared config stops needing write access to `fugaro-base` — for the same people, not for new ones.** The change is worth stating exactly, because an earlier draft of this section overstated it. Publishing the project's shared config is a write to the runs bucket's `fugaro/` prefix, and that prefix is `roles/storage.objectAdmin` to **`var.operators`** (`modules/installation/iam.tf:78-84`); the only role that can push a tag into `fugaro-base` is `base_writer`, granted to **the same `var.operators`** (`iam.tf:137-145`). So this is not "a teammate with bucket write gains a power they did not have": the *same* set of people, who could already put whatever they liked into `fugaro-base`, can now name any public ghcr.io image instead — a widening of the *class of value* that is accepted, which is why the rule below exists, but no new actor in the trust model, and this design must not claim it narrowed one. **What the rule does and does not close, stated exactly — against a writer of the shared config it is a *consistency* check, not a provenance one.** The trusted owner is the config's own `image_source`, and that record is **published in the same document as the entry it is checked against**, so whoever publishes the shared config sets both halves at once: `image_source: ghcr.io/evil` beside `base_images.base: …/fugaro-ghcr/evil/fugaro-base:99.0.0@sha256:…` passes `managedVersion`, `cover()` and `sharedcfg.go` alike — all three compare the entry against the record they are handed — and `refreshVerdict`'s never-downgrade rule (`image_refresh_rules.go:61-65`) then keeps it forever. That is the first regression above, and against that writer the rule does not close it. **What it does close is still real**: a foreign owner, a bare tag, a missing digest or any other shape in an entry whose config records *our* owner — a hand-edited or corrupted local config, a stale entry, an accidental paste, a checkout onboarded from elsewhere — and, on a machine with a local config, an `image_source` nobody there chose. **There is no new actor**: publishing the shared config is `roles/storage.objectAdmin` on the runs bucket's `fugaro/` prefix, granted to `var.operators` (`iam.tf:78-84`) — the same people `base_writer` lets push into `fugaro-base` (`iam.tf:137-145`) — so this is the same set of people with a wider *class of value*, not a privilege they lacked. **But the premise that makes this acceptable — that the owner is not the shared-config writer's to set — is false as designed**, which is why §10.7 asks the owner to rule on it (recommendation: refuse a published `image_source` that differs from the default unless the local config records the same one). What remains open beyond that is item 1 of "three things this rule does not do" below.

**The rule.** A reference under `<host>/<fugaro-ghcr>/` is the installation's base pin **only** in exactly this shape, and nowhere else:

```
<host>/<fugaro_ghcr>/<owner>/fugaro-<kind>:<version>@sha256:<64 hex>
```

- `<owner>` is the **recorded source owner** — the owner half of the local config's `image_source`, which is `ghcr.io/dimipaun` (`mirror.DefaultSources`, `internal/mirror/ref.go:56`) unless a run pinned with `--image-source` and recorded a fork's own — never "any segment", and never read back out of the reference being checked (the row below says why);
- the image name is `fugaro-<kind>`, the same name every other site already derives;
- the **digest is required**: a `fugaro-ghcr` reference without one is not this installation's pin.

**Where the rule lives, site by site.** The owner has to reach sites that currently receive only a host, and the call sites do **not** all have it: it is recorded once, in the local config, and read from there — threaded deliberately, not guessed from a flag or from the pin:

| Site | Change |
|---|---|
| `managedVersion(ref, host, kind, owner)` (`init_images.go:137-140`) | takes the owner; the remote path counts as managed only for that owner **and** with a digest. A foreign owner is "not managed" — which means `isManaged` says so, `image refresh` **refuses with `customBaseRefusal`'s existing escape hatch** instead of keeping it, and the never-downgrade trap above cannot fire. Failing closed, with the documented "remove the entry and rerun" fix |
| `isManaged`/`curVersion` (`init_images.go:173`, `:175` — one-line wrappers over `managedVersion`) and every caller that decides with them: `refreshBase` (`image_refresh_rules.go:26-46`), `refreshVerdict` (`:51-67`), `refreshPlan`'s kind loop (`image_refresh.go:250-255`, kept check at `:254`), `cloudCheck`'s kind loop (`upgrade_cloud.go:119-128`) | take the owner from **the local config's recorded source** (`image_source`, below) — **not** from `--image-source` at the call site, which an earlier draft wrongly assumed was reachable |
| **Where the owner lives, and why not the flag** (design decision, this row, not a code site) | **`--image-source` is an installation-only flag** (`init.go:1808-1824`'s `installationFlags`, whose map lists `"--image-source": o.imageSource != ""` at `:1812`; `init --repo` refuses it at `:1800-1802` — *"set(s) up the installation, not a repository"* — and `init_repo_gate.go:90-92` prints its note). **`--base` sits in that same map** — `"--base": len(o.baseKinds) > 0`, the same line `:1812` — so `fugaro init --repo` refuses it as well, and the reason is the same one: the pin and its owner are set on the **installation** run (`fugaro init --base`), and a `--repo` run can name neither. So `fugaro init --repo .` — the only command that renders job images — has **no owner in scope at all**: with the flag as the only source, the owner would be `""`, an empty owner refuses every remote path (§3.6, fail closed), and `fugaro init --repo` would refuse a **fork's own legitimate pin** on every run. **The owner is therefore recorded once, in the local config, and published in the shared config:** a new scalar `image_source` (`<host>/<owner>`, the same string `--image-source` takes, validated by `mirror.ValidSourcePrefix`, `ref.go:81-87`), written by the same `record()` call that writes `base_images.<kind>` (`init_images.go:487-534`, the write at `:522`) and carried to every machine and every repository's checkout by `Shared()`/`MergeShared` (`localcfg/shared.go:30-43`, `:75-107` — a scalar, so a `keep(&out.ImageSource, published.ImageSource)` line beside `Region`). Every reader in the row above, `cover()`, `BaseImageWarnings` and `sharedcfg.go`'s gate read it from there. `--image-source` keeps one job: it **sets** the record on the run that pins (`fugaro init --base` on a fork writes `ghcr.io/acme`), after which nothing needs the flag. **It is never derived from the pin**, deliberately: the pin is the value the rule is testing, so taking the trusted owner out of it would accept any owner and make the rule vacuous. **Absent means refuse**: a remote-shaped entry with no recorded `image_source` refuses, with the fix named (rerun `fugaro init --base base`, or remove the entry — `customBaseRefusal`'s existing escape hatch), the same failing-closed posture as an empty owner. And **a recorded source that is not on `ghcr.io` refuses too, naming the reason**: the remote repository's upstream is `https://ghcr.io` (§3.1), so a base pin can only name an owner *on ghcr.io* — `quay.io/acme` could never be served through the proxy. The refusal belongs on the **base-kind** path (where the pin is formed and where the record is read), not on the flag alone: `image refresh`'s history copy is a direct pull and keeps any registry `ValidSourcePrefix` accepts |
| `cover.go`, **both tests**: `inRegistry` (`:749-754`) *and* the job container image's inline check (`:650-651`) | each gains the shape test, and it is **the whole of §3.6's rule, version tag included**: a ref under the remote repository's ID must match `<host>/<project>/<fugaro_ghcr>/<owner>/fugaro-<kind>:<version>@sha256:<64 hex>` — owner, `fugaro-<kind>`, a **non-empty version tag**, and a **required digest** — with the same `refChars` and `..` guards; anything else under that ID is refused. (An earlier draft of this row dropped `:<version>`, which would have let a digest-only reference through the gate while §3.1 and the pin's own shape require the tag: the tag is the version marker `managedVersion`/`curVersion` read, so a shape test without it is not the same rule. §3.1's fallback — a digest-only reference with the version recorded separately — is therefore **not** accepted by this gate as written; it would be a change to this row, and the design should not imply otherwise.) The job-image check cannot delegate to `inRegistry` as written (different message, and it runs per container, not per check spec) — one shared predicate taking the ref is the way to keep them from drifting. `tf.Cover` gains the owner (`Owner`) and the repository ID, set where the cover is built (`internal/cli/init_review.go:269-283`, from the local config's recorded `image_source` — **not** `e.r.o.imageSource`, which is empty on every `init --repo` — and the installation's names). An empty owner refuses every remote path — fail closed |
| `sharedcfg.go`'s `baseImageRE` (`:301-308`) | syntax only, and it must keep `component` (so no path component can be `.` or `..`): `<host>/fugaro-base/<path>[:tag][@digest]` **or** `<host>/fugaro-ghcr/<component>/fugaro-<kind>:<tag>@sha256:<64 hex>`, the kind taken from the entry's own key. It is a *shape* gate as it always was (it accepts `<host>/fugaro-base/<anything>:1.2.3` today, which `managedVersion` then calls "not managed"); the semantic confinement is the `managedVersion` row above. The digest requirement is what stops a shared config from naming a *tag* through the proxy |
| `BaseImageWarnings` (`spec.go:846-856`) | accepts either registry — and it is deliberately **not** a security gate: its job is to warn that a build account cannot read an image (they can read both repositories now) and to point at the one place a base belongs. The confinement is the other four rows |

**Three things this rule does not do, named so nobody assumes them.**

1. **It does not bind the version tag to the digest.** The rule checks the *owner* and that a digest is *present*; it never checks that `<version>` has anything to do with `sha256:…`, and it cannot, offline — the digest is opaque. That gap is narrower than the one it closes but it is real. Today a fabricated `…/fugaro-base/fugaro-base:99.0.0` needs someone with `base_writer` to have pushed that tag; through the proxy the tag is free-form, and a `tag@digest` reference resolves by **digest**, so the tag need not exist upstream at all. Whoever can publish the shared config — whose `base_images` is unioned into every machine's config (`internal/localcfg/shared.go:81`) — can therefore pair a high version with **any digest that exists under our own owner's upstream path**, unsigned nightlies included, and `refreshVerdict`'s never-downgrade rule (`image_refresh_rules.go:61-65`) keeps it: a *new* pin is what the resolve-and-verify step examines, and this entry never becomes one. **What would close it, and what it would cost:** bind the two — resolve `<version>` through the proxy and require it to name the entry's digest — on the path that **already** reads both halves online: §3.2's resolve-and-verify step in `fugaro init --base`/`fugaro image refresh`, which fetches the release's manifest from ghcr.io and reads the digest back through the proxy. That is at most one extra comparison there, on a path that is already making network reads. It does **not** require the offline predicate to go online, and an earlier draft was wrong to price it that way: `refreshBase` (`image_refresh_rules.go:26-46`) makes no call at all, and `upgrade_cloud.go`'s `cloudCheck` (`:104-143`) is a read of the build record and the config, so binding at refresh time leaves `fugaro upgrade --check` exactly as offline as it is today. The honest limitation of that placement: an entry a *check* accepted would be refused at the next refresh rather than at the check. The alternative — record the resolved version beside the digest and refuse a reference whose version is not the release the CLI knows — has the same shape and the same cost. **This design does not close it, and says so** — it is listed for the owner in §10, and the sharp edge is bounded by the same thing that bounds the shared config today: publishing it is a bucket-write capability, and `fugaro doctor`/`fugaro validate` remain the place to look (design §4's trust model is about provenance, and §3.6 has narrowed — not eliminated — this particular forgery).
2. **It does not stop whoever can write the *local* or *shared* config, or update a job directly, from pointing a job at some other image — and for the shared config it is weaker than that sentence sounds.** For a *local* config the position is today's (anyone who can write it can already name an image in `fugaro-base` if someone with `base_writer` pushed one there), and the recovery is the same: `fugaro image refresh` refuses an entry that disagrees with the record and prints the fix. For the *shared* config the writer sets the record too, so there is nothing for the entry to disagree with: the pair is consistent by construction, `fugaro image refresh` has no reason to refuse it, and the never-downgrade rule keeps it. **The rule is therefore a consistency check against that writer, not a provenance bound** (§3.6 above, §4, §7, §10.7), and the honest bound on it is the one that has always applied to the shared config: it is a bucket write held by `var.operators` (§4's trust table).
3. **It does not make the proxy's own readable surface narrow**: if Artifact Registry accepted a **path-bearing Docker upstream URI** (`https://ghcr.io/dimipaun`), the registry itself could scope the proxy, which would be strictly better. Google's docs show a path-bearing custom upstream for **npm, Maven and Python** but not for Docker (§2.12 m: UNVERIFIED), Check 43a probes it, and this design does not depend on it.


## 4. The trust model, compared with today's copy

| | Today (the copy, **unverified**) | This design |
|---|---|---|
| What the job pulls | `<region>-docker.pkg.dev/<project>/fugaro-base/fugaro-base:<ver>` — a **tag** in the installation's own standard repository | `<region>-docker.pkg.dev/<project>/fugaro-ghcr/<owner>/fugaro-base:<ver>@sha256:<digest>` — a **digest** through a pull-through proxy |
| Who can change what the job runs, without touching a job | anyone who can write `fugaro-base` (operators: `base_writer`, `modules/installation/iam.tf:137-145`) — they can move that tag; and anyone who can write the config or update the job can point it elsewhere | the tag half is gone: the reference is a digest, and the proxy cannot serve different bytes for it (§2.12 c) — **but not "nobody"**, and the honest answer matters: whoever can write the local or shared config, or update a job directly, can still point it at another image (an ordinary path in the project's registry, or — new — any public ghcr.io image that matches §3.6's shape, which requires naming *this* installation's owner and a digest). Those writers are the **same `var.operators`** who hold `base_writer` (`iam.tf:78-84`), so what changed is the *class* of value that is accepted, not who can write one (§3.6) |
| What a `…/fugaro-ghcr/…` path admits | n/a — no such repository exists | exactly `<owner>/fugaro-<kind>:<version>@sha256:<digest>` for the owner **this installation's config records** (`image_source`) — the tag included, because it is the version marker the shape rule and `managedVersion` read; every other path under that repository id is a foreign image (§3.6). **The record and the entry are published in the same document**, so against whoever can write the shared config this is a consistency check, not a provenance bound — such a writer sets both halves and the never-downgrade rule keeps the result (§3.6, §10.7). Against every other source of an entry it is the confinement it claims to be. The prefix `<registry>/<project>/` is no longer a confinement by itself |
| What is verified, when, where | **nothing, today**: the copy checksums what it transfers against the registry's own header (`mirror.Plan`/`Copy`, `mirror.go:685-712`), and the tag it reads is whatever ghcr.io says it is. #318 would add: the digest *and* a cosign signature, at copy time, on the operator's machine — which is a precondition of the middle column below, not a description of today | the same digest and the same signature, at pin time, on the operator's machine (§3.2) — plus one read back **through** the new path, body-hashed, which today's copy has no equivalent of |
| What the operator's machine must reach | `ghcr.io` (1.2 GB of compressed layers down); then the same up to Artifact Registry | `ghcr.io` (a manifest, a few KB), sigstore's trust root, and the installation's registry (a manifest) |
| Bytes in the installation's registry | a full copy, ~1.2 GB, written by the operator | only what the jobs actually pull (the linux/amd64 layers), cached on first use |
| Why a wrong or tampered manifest cannot be served | not defended: the tag moves for everyone | **client-side digest verification**: docker, containerd and Cloud Build hash what they pull and refuse content that does not match the requested digest. That is what makes the proxy safe even though it sits in the middle — not the inference that Artifact Registry validates an upstream manifest (§2.12 c, g, both UNVERIFIED) |
| Where an attacker who controls a ghcr.io tag gets to | the *next* copy — with today's unverified copy, that is the next job, full stop; with #318, the signature check is the boundary | the same boundary #318 draws: the resolve step still reads a tag, and the signature check refuses a moved or unsigned digest. Nothing else changed |
| New dependency | — | the remote repository's availability on a **cold** pull (rate limits, §2.10; upstream outage, §7) — today's copy is warm by construction |
| New operator step | — | none for a plain project; a VPC-SC project needs one documented `gcloud artifacts vpcsc-config allow` per location (§2.11) |

**Stated plainly: this is a net strengthening, with one accepted new availability dependency.** The strengthening is digest pinning (a tag in a writable registry is no longer the thing jobs run) and the removal of the copy as a mutable artifact; the cost is that the *first* pull of a new digest happens in the job's environment rather than on the operator's machine — mitigated by §3.2's verification read, which warms the manifest (not the layers) and fails the refresh, loudly, if the path cannot serve the digest.

## 5. Exactly what is deleted, what stays, and what Terraform adds

### 5.1 Deleted

- **The base image's copy step**: the base-kind branch of `internal/cli/init_images.go`'s `imagesStage` — its `items()`/`read()`/`Apply()` path for base kinds, which today builds a `mirror.Ref` source at `ghcr.io/dimipaun/fugaro-base:<ver>` (`init_images.go:191-202, 214-227`), calls `mirror.Plan(ctx, it.src, it.dst, expect[it.key()])` (`:288`) and `m.Copy` (`:425`), and records the **destination tag** in `base_images` (`:522`). For base kinds this stage becomes resolve-verify-pin (§3.2) and copies nothing. `internal/mirror`'s copy engine (`Plan`/`Copy`) is **not** deleted: history still uses it (§5.2).

### 5.4 Migration: no backward compatibility, and the rule that makes it safe

**Nothing dual-shaped, no transition release, no `*Since` gate.** Fugaro is pre-release and exactly **two installations exist** — the owner's `fugaro` (project `fugaro-dev`, sandbox repository `edgeappinc/fugarosandbox`) and `belong` (EdgeWeb's and EdgeServer's) — which is the same ground `docs/design/project-secrets.md` §6 rules on (*"no backward compatibility needed before release"*) and `docs/design/m9-budget-and-dashboard.md` D18 before it. **Migrating an installation is: re-run `fugaro init` (installing the new remote repository and its grants), then `fugaro init --base base` / `fugaro image refresh` in each repository** — which rewrites `base_images.base` to the pinned remote reference. **No live step of this design's plan touches `belong` without the owner's explicit, separate word.**

What the migration costs, stated plainly for the two installations:

- The first `init` per project **creates** one repository resource and two IAM members — a normal plan, no replaces, no destroys, no `--allow-delete`.
- Rewriting `base_images.base` changes `base_ref`, so **every workflow's build record no longer matches**: `image refresh`'s build step rebuilds each workflow once (each build billable: about $0.21 for a 13-minute `E2_HIGHCPU_8` build — `docs/gcp-setup.md` §4, `:204`, and its §"What it costs", `:564` — not §3, which is the base-image section), and `triggers()` would also fire a rebuild in the daily check's own view. That is the one visible cost of the switch, and it is bounded by the number of workflows.
- The old copies in `fugaro-base` are **not** deleted by this change; the repository's existing cleanup policies (`registry.tf:24-73`: `keep-tagged` for `dev-`/`latest`, `keep-recent`, `delete-untagged`) prune them as they would any other version, and an operator may delete them by hand.
- A repository with a **custom** base (`--base-image`, a `dev-<sha>` tag) is untouched: `isManaged` still says "not a release base", and `customBaseRefusal` (`image_refresh_rules.go:106-117`) still refuses to replace it — now also for the reason that the CLI has nothing to pin over it.
- **What "already current" means after this change, and why the same version is not enough (B3).** Today `refreshBase` computes `want` from the version alone (`image_refresh_rules.go:26-46`): at the same version it returns the *copy's* path, so a run at 0.7.1 on a 0.7.1 CLI is a no-op. After this change the pinned value is a digest, which **cannot be computed offline** — so "current" has to be defined by **version *and* shape**, not by the version alone:
  - a kind is current when its entry is this release's **pin**: `managedVersion` == this release's version **and** the §3.6 shape (the remote path, this installation's owner, a `@sha256:` digest). Then the plan does nothing, verifies nothing and rebuilds nothing for that kind — a refresh does not re-verify an unchanged pin;
  - **anything else is stale, including a pre-migration `<host>/fugaro-base/fugaro-base:<same version>` entry.** That is the migration case: an installation already on 0.7.1 whose entry is the *copied* shape must move, and the string it moves to is produced only at apply time (resolve → verify → read back → pin, §3.2). **The absent-`image_source` refusal (§3.6) is not part of this leg, deliberately:** it fires only on an entry that is *already* in the remote shape — a `…/fugaro-ghcr/…` path, whose owner has to be checked before it can be pinned — whereas a copied entry is not remote-shaped at all and is simply stale, so it migrates. That is also the run that **writes** the record: `fugaro init --base` records `image_source` (the flag's value, else the default) in the same `record()` call that writes the pin (§3.6, `init_images.go:522`), so refusing a not-yet-recorded owner here would strand every installation on the one run that records it.
  So `refreshBase` becomes an *offline staleness question* (`(ref, pinned, err)` or equivalent): `pinned` when the config already holds this release's pin, `false` otherwise, with no digest invented offline. `refreshVerdict`'s comparison is then against the value the local config holds **after** step 2 (`refreshReload`, `image_refresh_steps.go:65`, re-reads it) — which is what `refreshBuilds` reads already (`image_refresh_steps.go:334`: `want := t.lc.BaseImage(kind)`) — so a *re-pin at the same version* (a re-released tag, a new digest) rebuilds, since the strings differ. **The plan preview is the one place that cannot print a value it does not have:** `refreshPlan` computes `p.want[k]` from `refreshBase` *before* step 2 runs (`image_refresh.go:250-255`) and prints it per workflow (`refreshPlan.print`, `:298-299`; each workflow's *reason* is computed by the `refreshVerdict` call at `:271`). For a stale kind, the printed reason is therefore "rebuilt: its base moves to this release's pinned image" and the *value* appears in step 2's own confirmation (which runs the resolve-verify-pin path), not in the preview. A `want` that is the old reference would print a plan that contradicts what step 2 does.
- **`fugaro upgrade` reads the same question, offline (B3).** `cloudCheck` (`upgrade_cloud.go:104-143`) calls `refreshBase(lc, k, ver)` and calls the repository stale when `cur != want` (`:128`); with the digest unavailable offline it must instead be **"is this entry this release's pin?"** — the same version-plus-shape predicate. Otherwise a 0.7.1 installation with a copied 0.7.1 entry would report "current: no base image to copy and no image to rebuild" (`upgrade_cloud.go:486`) and the migration would silently not happen on the path most users take. `upgrade_cloud_test.go`'s fixtures gain that case, and the stale reason names the shape (*"is <ref>; this release pins it by digest through <registry>"*) rather than printing a value it does not have.
- **One ordering trap, and the import kind is what removes it.** Check 43a creates `fugaro-ghcr` by hand before the implementation exists. With §5.3's `importGhcrRegistry` lookup, the first `fugaro init` after the implementation **adopts** that repository when it carries the `fugaro=managed` label (the check's create passes it) and **refuses with a named reason** when it does not — never the bare Terraform `already exists` an ordinary *create* would produce. Check 43's restore still deletes it in the pre-implementation run, so the two paths agree: delete it, or leave it labelled and let `init` adopt it.

## 6. The derived-image build

Images build **FROM the base**, through the same one value. `_FUGARO_BASE` (`internal/backend/gcp/build.go:183`) is `base_images.base`, and `images/derived/cloudbuild.yaml` uses it as the image of its own `fugaro`-running steps (`:75`, `:104`, `:210`, `:237`), as `FUGARO_BASE` in the environment (`:131`, `:239`), for `docker image inspect … RepoDigests` (`:144`) and as `--build-arg FUGARO_BASE=$$base` (`:159`).

So a derived build pulls the pinned remote reference **twice**: once as the step image and once as the `FROM` — both as the build account, through the remote repository, from the same cached manifest and the same cached layers, once warm.

**The template already expects exactly this shape, so nothing in it *should* change — and that is conditional on UNVERIFIED (d), not unconditional.** Its own comments say so: *"Render and build use one base image. Cloud Build pulls `_FUGARO_BASE` once … so a republished tag between the steps cannot give them different bases"* (`images/derived/cloudbuild.yaml:20-24`), and its `_FUGARO_BASE` substitution is documented as *"the base image; build pins the render step's image by digest"* (`:53`). What makes that true today is a `docker image inspect … RepoDigests` read that the render step writes to `/workspace/base-digest` and the build step turns into `--build-arg FUGARO_BASE=$$base` (`:144-159`) and a `dev.fugaro.base.digest` label (`:166`). With a digest-pinned `_FUGARO_BASE`, the same lines should produce the same answer for a stronger reason: the value is a digest before Docker ever sees it, so a moved tag cannot change what the render step, the build step or the label says. The label's digest is then the one the remote repository served, which §3.2's read-back already proved byte-equal to ghcr.io's.

**"Produce the same answer" is an assertion this document cannot make for the daemon, and it is the one place where a wrong answer is silent rather than loud.** `docker image inspect … RepoDigests` on a `tag@index-digest` reference returns whatever the daemon resolves the reference to: the index digest it was handed, or the **platform manifest** digest it selected. §2.12 n is that question, Check 43e's FACT line compares the digest the build recorded with the `$D` 43b read, and the failure it guards against is not a refusal — it is `triggers()` (`internal/imagecheck/triggers.go:36-38`) seeing `in.BaseDigest != rec.BaseDigest` on **every** daily check and rebuilding every workflow, once a day, forever, with nothing in any log saying why. Until 43e is recorded, treat the template as **conditionally** unchanged, not unchanged: if the daemon answers with the platform digest, the fix is at build time (`--base-digest-from` records the index digest the reference names, or the two are compared index-to-index), not in the check.

**But `$FUGARO_BASE` is also a substitution a *running* Cloud Build consumes** — as the step images (`:75`, `:104`, `:210`, `:237`) and inside the `docker image inspect` at `:144` — and whether Cloud Build's Docker accepts the combined `:tag@digest` form in all four places is exactly what §2.12 d leaves open. **Task 4 puts the template on the consumer list (§5.5) and Check 43e settles it live**; if any of those four refuses, the fallback is the digest-only reference (§10.1).

Further consequences:

- The build account needs `roles/artifactregistry.reader` on the **remote** repository (new, §5.3) in addition to `fugaro-base`'s reader grant, which stays for custom bases.
- Both pulls now resolve a **digest** where they used to resolve a tag in the project's own registry: an unchanged pinned base no longer means "whatever `fugaro-base:0.7.1` says today". `fugaro image build --repo … --workflow …` keeps working unchanged (`internal/cli/image.go:200-215`), because it reads the same config value.
- **A local build** (`fugaro image build --local`, `internal/image/local.go:212`) pulls the pinned reference with the operator's own Docker credentials — hence the operators' reader grant on the remote repository (§5.3). Only `BaseRef` (`local.go:61-67`) still names ghcr.io, and only for the *release* fallback when `base_images.base` and `--base` are both unset — unchanged by this design, and reachable only by not running `init --base` at all.
- `.fugaro/*.Dockerfile` files that hard-code `FROM ghcr.io/dimipaun/fugaro-base` keep the lint's allowance (`config.LintDockerfile`, `internal/cli/docs_base_test.go:271`) and keep bypassing the pin — unchanged, and out of scope: a user's own Dockerfile naming the upstream image directly is their own base, exactly as `--base-image` is (§5.2).
- **The pinned digest is the multi-platform *index*, and the consumer picks its platform** — as it already did when it pulled ghcr.io, and unlike the copy, which was amd64-only by construction (`docs/design/base-image.md` §12: *"The installation's copy stays amd64-only, and that is correct"*). Cloud Run and Cloud Build are amd64, so nothing they do changes; what changes is that the installation's own path now also serves the arm64 child, so a local `fugaro image build --local --platform linux/arm64` that reads `base_images.base` pulls through the remote repository instead of failing on an amd64-only copy. **UNVERIFIED** — not in §2.12's table because nothing here depends on it, and the fact is a bonus rather than a requirement: a proxy is content-addressed, so serving any child of the index should follow, but the documentation says nothing about per-platform behavior in a remote repository; Check 43b/43d are where it shows, incidentally. The cost, if the arm64 child is pulled, is its layers too, cached in the installation's registry.

## 7. Failure modes

| Failure | What happens | Why, and what to do |
|---|---|---|
| **ghcr.io is down, and the digest is already cached** | jobs keep pulling; builds keep building | Documented: *"Cached artifacts are also still available if the external public repository is offline"* (§2.4) |
| **ghcr.io is down, and the digest is *not* cached** (a cold pull, or after a cache eviction) | the pull fails; a Cloud Run Job execution fails at start, a Cloud Build fails at its first step | Documented error shapes: 502 (upstream error), 504 (upstream offline) (§2.10). Mitigation, and it is the reason §3.2's read-back exists: the refresh run *warms* the manifest at pin time, so what is left cold is the layers. **The layers are not pre-warmed by design** — downloading 1.2 GB on the operator's machine is exactly what this design removes; if the owner wants a warm cache at pin time (pull the image through the repository once, ~1.2 GB down on the operator's uplink and into registry storage), that is a one-line flag decision (§10) |
| **Artifact Registry's upstream read limit** (600 reads/org/region/minute, §2.10) | 429 *"Resource has been exhausted"* on a cold fetch; cached reads are unaffected (*"requests for that artifact only count against your project's request quota"*) | A burst is only plausible on the first pull of a new digest across many repositories at once; `fugaro image refresh` is an operator-driven, per-repository action, and jobs pull one manifest per cold node. Out of scope to measure (§2.12 l) |
| **A tag is mutated upstream** (the nightly re-pushing `fugaro-base:<v>`, or a compromise) | **nothing changes for an installation**: the reference is a digest, and the tag is only a version marker | The one place a tag still matters is the refresh run's resolve step, and that is where #318's signature check lives: a digest with no valid signature for the `images.yml` identity is refused (§3.2). The `-pinned` tag (nightly-immune) is what the resolve step reads |
| **A digest is deleted or retagged upstream** | the cached copy still serves; a cold pull 404s (*"when the requested artifact doesn't exist in the upstream repository"*, §2.10) | Fail-loud at the next refresh (no signature) and at the next cold pull. Deliberately not defended against by keeping a second copy — that is the design this one replaces |
| **The remote repository's cache is evicted** (a cleanup policy, or lifecycle) | the next pull re-fetches from upstream; if upstream is healthy, invisible | **Why this design configures no cleanup policies on the remote repository** (§3.1, §5.3): the cache is small (what the jobs pull), and an eviction that lands during an upstream outage turns a warm pull into a 504 |
| **A VPC-SC perimeter** denies upstream access | every cold pull fails; *"existing cached artifacts … are still available"* | One documented command per project+location: `gcloud artifacts vpcsc-config allow` (§2.11). A project that cannot open it keeps `--base-image` (unchanged, §5.2) |
| **The upstream path shape is not what §2.2 infers** | §3.2's verification read fails, loudly, at refresh time — before anything is pinned, and before any job is moved | This is precisely why the read-back exists instead of trusting the inference; Check 43b/43c settle it once, live |
| **A consumer rejects the combined `:tag@digest` form** | `fugaro validate`/`init` would fail at the first job or build; **and one consumer fails *silently* today**: the daily check's base-digest read (§5.5, `parseImageRef`) would log "its base trigger is skipped" on every run rather than failing the check | §2.12 d, Check 43d/43e; the parser fix is Task 4, and the fallback is the digest-only reference with the version recorded separately (§3.1, §10.1) |
| **The build records the platform digest while the check reads the index digest** (§2.12 n) | **nothing looks wrong, and the base trigger fires on every daily check**: one rebuild per workflow per day, silently, forever — no error, no warning, just the bill and the churn | `triggers()` compares `in.BaseDigest` (the reference's own index digest, `Registry.Digest` returning it with no call) against `rec.BaseDigest` (from `RepoDigests`, `images/derived/cloudbuild.yaml:144-146`). Whether they agree is UNVERIFIED and Check 43e's FACT line is where it is settled; the fix, if they do not, is at build time — record the index digest the reference names — not in the check, and not by accepting the rebuilds |
| **A `fugaro-ghcr` path that is not this installation's pin** (a foreign owner, no digest) | refused, not kept: it is "not managed", so `image refresh` stops with `customBaseRefusal`'s documented fix, `cover.go` refuses a plan that names it, and the shared config is rejected at publish time | §3.6. This is the failure mode the proxy *adds* — the prefix alone no longer confines — and the reason every validator got the shape rule |
| **A `fugaro-ghcr` entry that *is* consistent with the recorded `image_source`, when the same writer set both** (a shared-config publisher) | **not caught, by design as it stands**: the entry and the record it is checked against are published in the same document, so the pair agrees and the never-downgrade rule keeps it | §3.6, §10.7. The rule is a consistency check against a shared-config writer, not a provenance bound; the writer is the same `var.operators` who hold `base_writer` (§4), so it is a wider class of accepted value, not a new actor. The owner rules on whether to refuse a published `image_source` other than the default |

## 8. The live check for the owner (Check 43)

Written in full in [docs/gcp-live-checklist.md](../gcp-live-checklist.md) as **Check 43** — the number this design owns. Check 42 belongs to the config-transitions work (`docs/plans/2026-10-14-config-transitions.md` Task 7, *"Docs, the skills, Check 42 and the release bullet"*, and `docs/design/config-transitions.md` §5 item 5), so 43 is the next free number and the checklist's numbering ruling says so. It is scoped to **`fugaro-dev` and the sandbox repository only, never `belong`**, and run entirely by the owner — **no live apply by an agent**. Its commands are `gcloud`/`docker`/`fugaro` only; the plan's own tasks add no live step.

**It names its project rather than asking `gcloud`, and it re-checks with every step.** `P` is hard-coded to `fugaro-dev`; the setup and the guard are **one block** that every later step (43a, 43d, 43e, 43f, both restores) begins by re-running, because those steps run in later shells — 43d-43f are gated on a future release — where the variables are gone and an empty one is the same trap. The block ends in three **hard stops** (`exit 1`): the first asserts the block itself ran — `P` is exactly `fugaro-dev` **and** `L`, `R` and `U` are non-empty, so a skipped or partially pasted block stops there — the second that `fugaro doctor --project fugaro`'s `project:` line names `fugaro-dev` (on a foreign checkout `doctor` refuses that `--project` outright, so the `grep` after it fails either way), and the third that the checkout's origin is the sandbox; every `gcloud` command carries `--project="${P:?}"` (and `${L:?}`, `${R:?}`, `${R2:?}` where they are used), so an unset variable is a hard error rather than an empty argument `gcloud` resolves from its ambient `core/project`. Every `fugaro` command that takes it also carries `--project fugaro`: those commands otherwise pick their installation from the checkout's `fugaro.yaml` (`internal/cli/cloud.go:53`), and `--project` disagreeing with that checkout is **refused** (`internal/localcfg/select.go:163`), which is the hard stop that protects the `fugaro` half — `fugaro init --base`, `fugaro image refresh`, `fugaro init --repo .`, `fugaro image build` and `fugaro run` must run from the sandbox checkout and nowhere else. This is deliberate and was a defect in the first draft: `gcloud config get-value project` returns whatever the owner's ambient configuration points at (a `*-prod` project), and the check **writes** — it creates a repository and, in 43d, rewrites the local and shared configs and moves job images. `fugaro doctor`'s `project:` line (`internal/cli/doctor.go:748`, read from the local config, no cloud call) is the read-only cross-check. Checks 42 and 44 were audited for the same trap: 42's row and section are written by the config-transitions plan's own Task 7, 44 does not exist in this repository or on `main`, and no other step of this check reads a project from `gcloud`.

Its items, the UNVERIFIED fact each settles, and what each one needs to exist:

| Item | Settles | Needs |
|---|---|---|
| **43a** the create: `mode`, the custom upstream URI, the region, the `fugaro=managed` label | §2.12 k, e, m (the optional push probe and the optional path-bearing-upstream probe) | **nothing but `gcloud` and a Docker client** — this is the design's go/no-go, runnable before the implementation |
| **43b** a cold **digest** fetch through the fresh repository, and the bytes surviving the hop | §2.12 b, c, g | **nothing but `docker buildx imagetools`** — also go/no-go. Today the digest comes from the plain `:$V` tag; after #318 it is the `-pinned` tag's |
| **43c** the by-tag pull and `gcloud artifacts docker images list`: the path a **custom** upstream takes | §2.12 a (and, incidentally, the tag cache, f) | nothing but `docker` + `gcloud` — still pre-implementation |
| **43d** the CLI pins it (`base_images.base` is the remote path at the verified digest) and the check job runs from the pin | §2.12 d | **the implementation *and* #318's Task 1 merged, plus a tagged release that ran it** (there is no signed `-pinned` image before that) |
| **43e** the consumers accept `<tag>@<digest>`: `docker pull`, a real `fugaro init --repo` plan, a real `image build` whose Cloud Build uses it as step image and `FROM` — **and, in its FACT lines, the digest that build recorded against `$D`** | §2.12 d, **n** (the base-digest comparison: if the daemon answers with the platform digest while the check reads the index digest, the base trigger fires on every daily check forever) | same as 43d |
| **43f** the full sandbox `init --repo`/`image refresh` round trip, with the restore | end to end | same as 43d |

**Two things the check deliberately does not do.** It does not dispatch `images.yml` to move a tag: 43c's by-tag pull already shows the cache, nothing downstream reads a tag through the proxy (§2.5, §2.12 f), and a dispatch re-publishes the public `:$V` tag that `belong`'s copies read. The `-pinned` tag's immutability is #318's own check **39e**, which this design keeps (§9) — that one already dispatches the nightly for exactly that question. And it does not measure the upstream rate limits (§2.12 l).

The check is written to be runnable **before** the implementation, as a feasibility test of §2's inference: 43a, 43b and 43c alone need **no Fugaro change at all** — a handful of `gcloud`/`docker` commands against the sandbox project. That is deliberate: it is this design's equivalent of the 2026-10-12 Cloud Build pull test that #318 leaned on, and if 43a/43b/43c fail (the path shape, or the digest hop), the design stops there, with nothing shipped and nothing migrated.

## 10. Decisions for the owner to rule on

1. **The repository's name and the tag-in-reference form.** `fugaro-ghcr` (§3.1) versus a name that does not name the upstream (`fugaro-upstream`); and `<ver>@sha256:<digest>` (the version marker, §3.1) versus a digest-only reference with a new `base_versions` config map. **What each form costs, so the choice is made on the cost and not on taste:** the combined form keeps the version readable in `base_images.base` and in a `fugaro diagnose` dump, and pays for it with a reference shape that some parsers reject — `parseImageRef` is one and must be fixed (§5.5, the plan's Task 4), a Docker client and Cloud Build are the other two and are *not* known to reject it, which is exactly what Check 43e settles live. The digest-only form is accepted by every parser (nothing to verify in 43e, nothing to fix in `parseImageRef`), and pays for it by losing the version marker: the version then has to be recorded somewhere else, a new `base_versions` config map, and no config file or dump shows the version next to the reference any more. Neither form weakens the trust argument — the digest is the pin either way, and the version marker is only a label (§4). **Recommendation: `fugaro-ghcr` and the combined form**, with the digest-only fallback held in reserve for a bad §2.12 d result. This is the design's one structural choice that a live check (43e) could overrule, and the fallback is small.
2. **Whether the refresh run pre-warms the layers** (§7, cold pull). **Recommendation: no** — the removed 1.2 GB is the point; the manifest read-back is the compromise, and a first-execution pull is already what the check job does today for a fresh copy.
3. **Whether `fugaro-base`'s copy of the base image is deleted after the migration.** **Recommendation: no explicit deletion** — the existing cleanup policies prune it, and `prevent_destroy` is untouched.
4. **Whether history follows.** The remote repository makes `fugaro-history` copyable-free the same way (its jobs would reference a pinned remote digest, its `:latest` reference resolved and signed at refresh time). **Recommendation: a separate, later design** — this one is the base image's, and history's copy is the only remaining user of `internal/mirror`.
5. **The VPC-SC story for bring-your-own projects** (§2.11): document `gcloud artifacts vpcsc-config allow` in `docs/gcp-setup.md`, and keep `--base-image` as the answer for projects that cannot open the perimeter. **Recommendation: both.**
6. **Whether the version tag is bound to the digest** (§3.6, "three things this rule does not do", item 1). The shape rule requires the owner and a digest but never checks that `<version>` names that digest, so a shared-config writer can pair a high version with any digest under our own upstream path, and the never-downgrade rule keeps it. **The bound that writer is already under, stated so the options are priced honestly:** publishing the shared config is `roles/storage.objectAdmin` on the runs bucket's `fugaro/` prefix, granted to `var.operators` (`modules/installation/iam.tf:78-84`), and `base_writer` — the only way to put a tag into `fugaro-base` — is granted to the same `var.operators` (`iam.tf:137-145`), so the relaxation is in *what a config may name*, not in *who may write one*. **Options:** (a) leave it, documented here; (b) bind it — resolve `<version>` through the proxy and require it to name the digest — at §3.2's resolve-and-verify step, which is already online, leaving `upgrade_cloud.go`'s `cloudCheck` (`:104-143`) and `refreshBase` (`image_refresh_rules.go:26-46`) offline exactly as they are (an earlier draft wrongly priced this as making the check network-dependent); the cost is that a check accepts a forged entry until the next refresh refuses it; (c) record the resolved version beside the digest and refuse a mismatch, same shape and same cost as (b). **Recommendation: (a) for this change, with (b) named as the follow-up if the owner wants the shared config to be no stronger than it is today** — today it is bounded by `base_writer`. **This is one of two ways the proxy relaxes that bound, not the only one**: the other is the owner record itself, because `image_source` is published in the same document as the entry it validates, so the same writer sets both (§3.6, §4, §7). The two are independent — binding the version to the digest does not stop `ghcr.io/evil` at a matching version, and refusing a foreign published owner does not stop a high version over our own digest — so read this item together with §10.7, which is the other half.

7. **DECISION FOR THE OWNER — whether a published `image_source` may name an owner other than the default** (the second half of the relaxation §10.6 prices; §3.6's regressions, §4's trust table, §7's last row). **The question.** The trusted owner is recorded in `image_source` and **published in the shared config**, so whoever publishes that config sets the owner and the pin together: `image_source: ghcr.io/evil` beside `…/fugaro-ghcr/evil/fugaro-base:99.0.0@sha256:…` passes `managedVersion`, `cover()`, `sharedcfg.go` and `BaseImageWarnings`, and `refreshVerdict`'s never-downgrade rule then keeps it forever — the exact regression §3.6 says the shape rule closes. **There is no new actor**: a shared-config publisher is a member of `var.operators`, who already hold `base_writer` (`modules/installation/iam.tf:78-84`, `:137-145`), so this widens the *class of value* a config may name, not who may name one. The question is not "is this a vulnerability" but **"may the design rest on it"** — because §3.6's security argument, and this section's item 6, rest on the owner not being the writer's to set. **Options, with what each costs:**
   - **(i) Refuse a published `image_source` that is not the default unless the reading machine's local config records the same one.** `sharedcfg.go`'s validation (`:228-233`, where `base_images` is already checked) gains the check: the shared document's `image_source` must be either `mirror.DefaultSources[0]` (`ghcr.io/dimipaun`, `internal/mirror/ref.go:56`) or the value the local config records. A fork's operators set it locally, once, with the run that already records it (`fugaro init --base` / `--image-source`), and only then may it be published for others. Cost: a fork must record it on each machine before that machine may use a shared config naming it — the same local-config-first shape as everything else — and a genuine owner change is local-then-publish, two steps rather than one. **RECOMMENDED**: it restores the property the rule was written for (an entry a published config names must be our owner's *as this machine knows it*) at no cost to a plain installation, and it keeps §3.6's argument true instead of explaining why the confinement does not confine.
   - **(ii) Record the owner as an installation Terraform variable or output and read it back with `--config-only`.** Ties the owner to the installation's own apply and state rather than to a bucket write, and needs no new refusal. Cost: a new Terraform variable/output, a discovery path the rollback must keep, `--config-only` becomes the reader of a value the local config already has, and it does not help a teammate whose machine has no local config at all (the shared config is then their only source, and it is the thing being distrusted).
   - **(iii) Accept it as written, with the honest sentence.** Cost: nothing now, and the design must say in §3.6, §4 and §7 that against a shared-config writer the rule is a consistency check and not a provenance bound — which this revision states either way.
   **One consequence to price into (i) whichever option is taken: the published owner is last-writer-wins, so two operators recording different sources flip it on every publish.** `Shared()` (`internal/localcfg/shared.go:30-43`) builds the document out of the publishing machine's own config — `image_source` is a scalar it does not drop — and publishing merges with what is there through `MergeShared` (`:75-107`), whose scalars take the **local** value when it is non-empty (`keep(&out.ImageSource, published.ImageSource)`, beside `Region` at `:89`). So if operator A records `ghcr.io/acme` and operator B records `ghcr.io/other`, the document says whichever of them published last, and the next publish by the other flips it back. Nothing in the design today notices — a reader with no local config just adopts it — and under **(i)** every machine that records the other value **refuses the published config** until it records this one. That is the honest failure mode of (i): loud and local, on the machines that disagree, instead of the silent acceptance it replaces. Task 4's `TestMergeSharedKeepsTheOwnerInStep` is the unit test for the precedence itself (local wins, and the round trip through `Shared()` keeps the field), so the flip is at least *observable* rather than a surprise; nothing in this change makes the published value a majority or a tie-break.

   **The design's text is already the same under all three**: the old claim is gone and the limit is stated, so nothing here has to be rewritten for the owner to rule. **The plan's test for (i) is conditional on this ruling** and marked so — `TestSharedConfigRefusesAForeignPublishedOwner` in Task 4's step-1 list — so choosing (ii) or (iii) leaves no test asserting behaviour the design does not have.

## 11. Non-goals

- Any live cloud or network action by the agent: no repository is created, no image pulled, no project touched. Check 43 is the owner's.
- Retiring the history image's copy (§5.2, §10.4), `internal/mirror`'s copy engine, or `--base-image`.
- Changing `internal/mirror`'s trust model, or the base image's own content, size budget, monthly bump or secret scan. (`internal/infra/tf/cover.go` is no longer on this list: the proxy widens what is *readable*, so its job-image rule **is** changed, to the pin's closed shape — §3.6, §5.2.)
- Implementing Artifact Registry **virtual** repositories, CMEK, cleanup policies or upstream credentials for the new repository: none is needed for a public package, and each would add a trust input (§2.3).
- Any change to `.github/workflows/**` (Fugaro cannot push one; #318's Task 1 stages the workflow change under `docs/pending-workflows/`, and this design adds nothing there).
