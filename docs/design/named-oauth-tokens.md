# Named OAuth tokens (multiple Claude accounts)

Status: design for review (2026-10-10). Source: the owner's request (2026-10-09), "it would be nice to be able to store multiple oauth tokens (from multiple accounts) and pick one by name." Every fact below is cited to the code that was read for it; no cloud call was made. The verified/unverified split is explicit (§7). Plan: [../plans/2026-10-09-named-oauth-tokens.md](../plans/2026-10-09-named-oauth-tokens.md); its decisions T1 to T14 can be vetoed one by one.

## 1. What exists today (verified in the code)

The Claude OAuth credential is **one secret per repository**, reserved and fixed:

- `config.ReservedSecrets["claude-oauth-token"] = "CLAUDE_CODE_OAUTH_TOKEN"` (`internal/config/config.go:336`). The name is not configurable; it is the literal key of a map every repository shares.
- `agent.auth: oauth` in a repository's `fugaro.yaml` (`internal/config/config.go:123`) selects it. `infra.SecretMounts` (`internal/infra/spec.go:520-540`) is "the one place that decides" what a workflow's job mounts: for `auth: oauth` it appends exactly `{"claude-oauth-token", "CLAUDE_CODE_OAUTH_TOKEN"}`, nothing else, and nothing lets a workflow add a second one (a workflow's own `secrets:` may not name a reserved secret; `declares`/`ReservedSecrets` keep the two namespaces apart, `internal/cli/secrets.go:157-160`).
- The mount happens at the **job**, not the run. Terraform's `modules/workflow/job.tf` builds one `google_cloud_run_v2_job` per (repository, workflow), with `secret_env` as a static `dynamic "env"` block wired at `apply` time (`job.tf:45-66`), and a matching `google_secret_manager_secret_iam_member.job` grant per secret the job's env names (`job.tf:164-170`), scoped to that one secret. **Every execution of that job, whoever launches it and whenever, sees the same environment.** Cloud Run Jobs have no per-run secret selection; `fugaro run`'s only per-run lever is `RunJobRequest.Overrides` (`internal/backend/gcp/run.go:106-116`), which today overrides only `FUGARO_RUN` and the timeout, never a secret reference (§6 explains why that stays true).
- `fugaro secrets set claude-oauth-token --repo owner/name` is the only way to store a value (`internal/cli/initsecrets.go:426,515`; `internal/cli/secrets.go:82,89` for the standalone command). Storing never echoes a value; `claude setup-token` (run by the user, in their own terminal) is the only way to mint one.
- The runner's allow-list (`internal/agent/env.go:106-113`) puts exactly `CLAUDE_CODE_OAUTH_TOKEN` in the agent's environment for `auth: oauth`, nothing else credential-shaped beyond declared workflow secrets.
- Accounting has **no dollar cap for oauth**. `docs/design/v1.md` §6.1 "oauth" (`docs/design/v1.md:47,52`): the run only adds `total_cost_usd` to `notional` counters (global, repository, project), never billed, never capped by the gateway (there is no gateway for oauth — §6.1 "oauth has no gateway", line 52). Its only budget is the token cap (`agent.max_run_tokens`) and the kill switches. `fugaro budget show` prints `notional $X (subscription, not billed)` per repository and globally (`internal/cli/budget.go:607,621`); there is **no per-account dimension anywhere** in the budget schema (`internal/budget/model.go`'s `Counters.ByModel` is keyed by model, not by credential).
- **Layered config ruled per-person Claude tokens out of scope already** (`docs/design/layered-config.md:135`, decision area, and §13 non-goals): "They change how runs authenticate: a run would need to know who launched it and which secret to mount. That is a separate, later project." This design is that later project, scoped to *named accounts a repository may choose among*, not to *per-person* identity (no change to "every run of a repository's workflow runs as the same account," `docs/design/v1.md:72`).
- **A close, already-shipped precedent exists for almost this exact shape**: `internal/config/providers.go`'s `ModelProvider` (M10, multi-model). It lives only in the **local config** (never `fugaro.yaml`), is named (`providers.<name>`), carries its own `Secret` (a logical name, never a key), and gates use with `AllowsData(repo)`, an explicit per-provider allow-list of `owner/name` repositories (`providers.go:44-46,62-64`). `fugaro secrets set <provider-secret-name>` is validated against exactly that allow-list (`internal/cli/secrets.go:172-178`). This design reuses that shape for Claude accounts instead of inventing a new one.

## 2. The feature

Store several Claude OAuth tokens (different accounts/subscriptions), each under a name, and pick one:

- **by default**, per repository (unnamed today; named `default` from now on — fully backward compatible, see §5);
- **per run**, `fugaro run --token NAME`;
- **per workflow**, `agent.oauth_token: NAME` in the repository's `fugaro.yaml`.

## 3. Decision: where the named choice may live

**T1. Account definitions and the allow-list live only in the local config, never in `fugaro.yaml` or the project layer. Recommended.**

A new block, parallel to `providers:`:

```yaml
# ~/.config/fugaro/projects/<name>.yaml (operator-only file)
claude_accounts:
  acme-personal:
    secret: claude-oauth-token-acme-personal   # logical name, never a value
    allow_data_to: [acme/app, acme/sandbox]     # owner/name, case-insensitive
  acme-overflow:
    secret: claude-oauth-token-acme-overflow
    allow_data_to: [acme/app]
```

`default` is reserved and implicit: it always names the existing `claude-oauth-token` secret and needs no entry (so an installation that adds nothing here is byte-for-byte unchanged, §5). A repository's `fugaro.yaml` may set `agent.oauth_token: acme-overflow` (one name, the workflow's default) — but naming a token only *selects among* names the local config already allows that repository; it can never *define* one or widen the allow-list.

Why not the project layer or a profile: **both live in the same bucket object.** A profile is not a separate, more trusted file — `profiles:` is a sibling key of `defaults:` inside the one `fugaro/project-layer.yaml` object (`docs/design/layered-config.md` §6's own example shows both under one `version`/`project`/`gcp_project` document), and "who can write the project layer" (`layered-config.md:353`) is a single answer that covers every key in it, profiles included: any **launcher** holding `roles/storage.objectAdmin` on the runs bucket, not only operators. §11's own threat model already accepts that a bucket write can flip `agent.auth` or `agent.model` — but that is bounded today because *what* `agent.auth: oauth` reaches is fixed and singular. Letting a bucket object choose *which account's subscription* a run burns, with no PR review, would let any launcher silently redirect spend (and rate-limit exposure, see §6) to another account whose name they merely have to guess or enumerate — strictly worse than today, where the account is fixed per repository and only `fugaro secrets set` (an operator action, confirmed per secret, §7.2 IAM) can change what the one name resolves to. This holds exactly as much for a profile as for `defaults:`: a profile that sets `agent.oauth_token` would let any launcher redirect spend for every repository that profile templates, which is wider, not narrower, than a single repository's own `fugaro.yaml`. Keeping `claude_accounts:` in the **local config** (a file only an operator edits, never read from the bucket, exactly where `providers:` already lives) keeps the allow-list owner-controlled by construction, with no new IAM primitive.

*Veto alternative:* allow `claude_accounts` and `allow_data_to` in the **project layer**'s `defaults:` (so a project that already trusts its bucket for `agent.auth` trusts it for this too), with the stricter "commands in a bucket object" guard of `layered-config.md` §11 decision L7 applied here as well (diff shown, `--executable-changes`-style confirmation). Rejected for v1 because it is strictly more exposure for a feature whose whole point is **narrowing** which account a run can reach, and the local config costs the operator nothing extra (they already hold `providers:` there).

**T2. `agent.oauth_token` is a plain repo key, in neither the project layer nor a profile.** In the project-layer scope table (`layered-config.md` §5), it is added as: Project — no; Profile — no; Repo — yes; Override — yes (so `--token` beats everything, but the only committed place that can name a token is the repository's own, PR-reviewed `fugaro.yaml`). Note that this is *not* "scoped like `agent.model`" (an earlier draft of this decision said so, imprecisely): the existing table already has `agent.model`/`review_rounds`/`max_budget_usd`/`recipe` as Project — yes, Profile — **no**, Repo — yes, Override — yes (`layered-config.md:122`) — no `agent.*` key is profile-scoped today, so Profile — no needs no new argument here, only the Project column differs from `agent.model`'s, for the reason T1 already gives: **Profile must be no for the identical reason T1 argues Project must be no, not a weaker one** — a profile is a key inside the same launcher-writable `fugaro/project-layer.yaml` object T1 already distrusts (§1 above: `profiles:` sits beside `defaults:` in that one bucket object), so letting a profile set `agent.oauth_token` would reopen exactly the hole T1 closes, just spelled `profiles.<name>.agent.oauth_token` instead of `defaults.agent.oauth_token` — and it would be *wider*, since one profile templates every workflow of every repository that names it, so a single bucket write would redirect spend across a whole team at once rather than one repository. `agent.oauth_token` instead joins the company of `agent.instructions`, `agent.review`, `workflows.*.secrets` and `workflows.*.dockerfile` (`layered-config.md:123,130,129`): Repo-only keys, because each names something too sensitive, or too specific to one repository's review, for a bucket write to set.

## 4. Decision: selection at run time (the mounting problem)

Cloud Run mounts secrets at the **job**, not the execution (§1). Four shapes were weighed:

| Option | What it means | Verdict |
|---|---|---|
| **A. Mount every allowed name into every run** | Every named secret the repository may use becomes an env var in every execution | **Rejected.** A real security regression: the agent (which runs with permissions bypassed, sharing the container with the runner, §6.1 of v1.md) could read every allowed account's token from its own environment or `/proc`, not just the one a run chose. Quantified against `docs/design/v1.md` §6.1 "Service account... It can read only its own declared secrets" — this breaks that invariant outright, and against `SECURITY.md`'s own scope ("Credential handling... redaction of logs and PRs, the runner's use of provider and model tokens" is explicitly in scope; this would be a regression in exactly that area). |
| **B. One job (and job account) variant per (workflow, allowed name)** | Each variant is Terraform-managed exactly like a workflow is today: its own `google_cloud_run_v2_job`, its own dedicated service account, with `secretAccessor` granted on **one** secret only (the named one). `fugaro run --token NAME` resolves to the variant's job name, the same way `--workflow` already resolves to one. | **Recommended (T3).** No new IAM primitive: it is "each job has its own service account... it can read only its own declared secrets" (`v1.md` §6.1), applied once more. |
| **C. Runner-side fetch of only the chosen secret, via the job's own service account** | One job per workflow stays; the job account is granted `secretAccessor` on every allowed name (so it *can* fetch any one), and the runner (not Cloud Run) decides, at boot, which one to actually place in the agent's environment, based on the task's requested name. | **Rejected for v1 (bigger-version candidate, §9).** The task notes exactly the flaw: "per-run narrowing is impossible with static IAM." The job account's IAM grant must cover every name the repository may ever pick (since IAM is applied once, at `fugaro init --repo` / Terraform apply, not per run), so a compromised agent can still call the Secret Manager API directly, through the metadata server's token, and fetch an account it wasn't handed — the narrowing is then only in runner code, not in what the container's identity can reach. It also adds a new live GCP call to runner bootstrap that does not exist today (today every secret arrives pre-fetched, as an `env` the platform populated before the container started; `internal/agent/env.go`'s `BuildEnv` only ever reads `os.Environ()`, §1). |
| **D. Cloud Run execution overrides carrying a secret reference** | `fugaro run --token NAME` stays one job, and the execution's `RunJobRequest.Overrides` names which secret to mount for that one execution. | **Unverified, and the code gives no evidence it is possible; treated as not available** (§7, live-check item U1). `internal/backend/gcp/run.go:108-115` shows today's `Overrides` touching only `env` (a literal value, `FUGARO_RUN`) and `timeout`; there is no code path anywhere in the repository that sets a `secret_key_ref` through an execution override, and Cloud Run Jobs' override shape (`GoogleCloudRunV2ContainerOverride`) is modeled in this codebase as `{Env, ClearArgs, Args}`-only (`google.golang.org/api/run/v2` — no secret field is referenced by any Fugaro code). Even if the API allowed it, the override would still need to *name a secret the job's service account already holds `secretAccessor` on* (Cloud Run does not grant IAM per execution), so it would face exactly C's static-IAM problem, not solve it. |

**T3. Ship option B: one job variant per (workflow, allowed named account).** Concretely:

- A new pure helper, `gcp.WorkflowVariant(workflow, token string) string`: returns `workflow` unchanged when `token == "" || token == "default"` (so every existing repository's job name, service account ID and Terraform resource address are **byte-identical** to today — zero migration, confirmed by a golden test, §8 of the plan), else `workflow + "--" + token`.
- `infra`'s repository-spec builder (`internal/infra/spec.go:726-734`, the loop that fills `RepoSpec.Workflows`) iterates, for each `fugaro.yaml` workflow that has `agent.auth: oauth`, over `{"default"} ∪ {names the local config's `claude_accounts` allow for this repository}`, building one `WorkflowSpec` per pair through `c.workflow(logicalName, tokenName)`. Each variant's `Job`, `ServiceAccount.AccountID` and `SecretEnv["CLAUDE_CODE_OAUTH_TOKEN"]` are computed from the variant key; everything else (commands, base image, resources, timeouts) comes from the one `fugaro.yaml` workflow entry, unchanged. **No change to any `.tf` file is needed**: `modules/repo/workflows.tf`'s `for_each = var.repo.workflows` and `modules/workflow/job.tf`'s per-secret `google_secret_manager_secret_iam_member.job` are already generic over whatever map Go hands them (verified: `job.tf:165-170` loops `toset(values(var.workflow.secret_env))`, and `secrets.tf`'s container and operator grants already loop `var.repo.secrets`, itself filled by `maps.Copy(rs.Secrets, ws.SecretIDs)` at `spec.go:732` for every variant). The whole feature is additive Go computation over existing, already-reviewed Terraform.
- `fugaro run --token NAME` (default `""`, meaning the repo's/workflow's configured default, itself defaulting to `default`) resolves `NAME` against the local config's allow-list *before* calling `Launch`, exactly where `secrets set` already resolves a provider's name against `AllowsData` (`internal/cli/secrets.go:172-178`) — refused before any network call if `NAME` is not one the repository is listed for. It then passes the **variant key**, not `NAME`, as `backend.LaunchSpec.Workflow`, so `Launch` (`internal/backend/gcp/run.go:106`) and `CheckRunExecution` (`run.go:92-101`) need no change: `JobPath`/`JobName` already derive a distinct, correct job name from any string (`gcp.JobName`, `internal/backend/gcp/names.go:128-130`).
- **The clean workflow name is kept separate from the variant key everywhere a human or another consumer reads it.** `task.Spec` gains one field, `OAuthToken string` (`json:"oauth_token,omitempty"`), holding `NAME` (or empty for `default`); `task.Spec.Workflow` stays the `fugaro.yaml` key (`"build"`, not `"build--acme-personal"`), because the runner bootstrap and every other consumer look up `cfg.Workflows[task.Spec.Workflow]` by that exact name (`internal/config`'s `Workflows map[string]Workflow`) and must keep doing so unchanged. Only the narrow set of call sites that need the *Cloud Run job name* (the CLI's own `Launch` call, and nothing in the runner, which never needs its own job's name) compute the variant key from the two fields together.
- `runstore.Record` (`internal/runstore/runstore.go:106-129`, result.json) gains `OAuthAccount string` `json:"oauth_account,omitempty"`, so `fugaro ls`, `diagnose` and `fugaro logs` can show which account a run used (§6d); it is informational only, never read by anything that makes a security decision.

**Why a variant per name, not per name-and-workflow combinatorially out of control:** names are owner-chosen and expected to be few (a handful of accounts, not dozens); the plan's live-check task (§7) asks the owner to confirm Cloud Run's per-project job-count ceiling is comfortable at the scale they intend (no code in this repository reads or enforces such a ceiling today — it is a GCP account limit, unverified here).

## 5. Compatibility

- **An installation that adds no `claude_accounts` entry is unaffected, in full.** `gcp.WorkflowVariant` is the identity function for `"" | "default"`; the `infra` loop produces exactly the one `WorkflowSpec` per workflow it produces today; no new Terraform resource is created (the `for_each` set is unchanged); `task.Spec.OAuthToken` is omitted (`omitempty`); `runstore.Record.OAuthAccount` is omitted. A golden test (plan Task 2) diffs `BuildRepoSpec`'s JSON tfvars output, byte for byte, between the code before and after this feature, over the existing corpus of `fugaro.yaml` fixtures, with no `claude_accounts` configured.
- **`task.Spec` is strictly decoded** (`internal/task/task.go:181`, `dec.DisallowUnknownFields()`). `OAuthToken` is a new, `omitempty` field: a runner *older* than this feature refuses a task that sets it (the same "version-skew" pattern as `ProjectLayer` and `Recipe`, `docs/design/layered-config.md:326`). The CLI must therefore check the job's deployed image/build record names a runner that knows the field before it ever sets `OAuthToken` to a non-default value — mirroring `layeredSince` (`layered-config.md` §10) with a new `namedTokensSince = "0.8.0"` (or whatever version ships this, §8) gate: a launch that would set `OAuthToken` against an older build record is refused with a message naming `fugaro image refresh`.
- **Older `fugaro` CLIs** launching a repository whose local config *has* named accounts configured still work unmodified: they never set `--token`, so every launch resolves to the `default` variant, which is the same job as before. They simply cannot *select* another account; that is a feature gap, not a break.
- **`claude-oauth-token` keeps its exact name and behavior as the default.** `config.ReservedSecrets` is unchanged; `secretsSet`'s existing reserved-name branch (`internal/cli/secrets.go:157`) is untouched. A second, parallel check (mirroring the provider branch at line 172-178) validates a `claude-oauth-token-<name>` secret against the local config's `claude_accounts[<name>].AllowsData(repo)`.
- **The secret name pattern** is `claude-oauth-token-<name>`, where `<name>` matches a new `config.ClaudeAccountNameRE` (`^[a-z][a-z0-9-]{0,30}$`, deliberately excluding `default`, which is reserved and never has a `claude_accounts` entry of its own — a config that defines one is refused with a message saying so). This keeps every such secret matching `config.SecretNameRE` already (`^[a-z0-9][a-z0-9-]{0,62}$`, `internal/config/validate.go:27`), so no parser needs a new grammar, only a new *membership* check, exactly as providers' secrets already do.

## 6. Threat model

**(a) Which accounts can a given repository's runs consume?** Exactly the names whose `claude_accounts.<name>.allow_data_to` lists that repository (case-insensitive, `owner/name`), plus the always-available `default`. This list is **owner-controlled, local-config-only** (T1): neither `fugaro.yaml` nor the project layer can add a name, by construction — not merely by convention, since `infra`'s loop (§4) is the only place that decides which `WorkflowSpec` variants exist, and it reads the allow-list from the local config it was invoked with, never from the checkout.

**(b) How could a poisoned task/PR text or repo config pick another account's token?** Three independent backstops, mirroring providers exactly:
1. `agent.oauth_token` in `fugaro.yaml` is reviewed like any other repo key (§3 T2); a value naming an account the local config does not allow is a `fugaro validate` error before any run, exactly like `CheckProviderPolicy` already refuses a model a provider does not claim or allow (`internal/config/providers.go:324-364`).
2. `--token` is a launcher's own CLI flag. A **follow-up** run never re-derives it from a PR comment: it inherits the *original* run's resolved `OAuthToken` from that run's own `task.json`/`result.json` (the same lineage check that already keeps a follow-up's session, workdir and branch tied to the first run, `docs/design/v1.md` §6.1 "A restored session is replayed..."). A trusted commenter (`followup.trusted`) can steer *what the agent does*, never *which account's job it runs as* — there is no token-naming syntax inside the comment protocol (§4.4's nonce-delimited block carries review feedback text, never a flag).
3. Even if (1) or (2) were somehow bypassed, `infra`'s variant set (§4) is the hard backstop: a job for a disallowed name simply **does not exist** (no Terraform resource, no service account, no `secretAccessor` grant), so `Launch`'s own 404 path (`internal/backend/gcp/run.go:145-146`, "job %s does not exist; create it with fugaro init --repo") is what a bypass attempt actually hits.

**(c) Quota/ban blast radius of a leaked token.** Unchanged in kind from today's single-token model, narrowed in scope by B (§4): a compromised agent in one run can reach only the one account's token its own job variant mounts (never another allowed name's, unlike option A), through the same channels as any secret today — the variant's own environment and, as always, the job's own metadata-server identity (`v1.md` §6.1, "the agent can reach the tokens it works with"). A leaked token can be used for Claude Code calls as that Claude account until revoked; **Fugaro has no way to scope what a `claude setup-token` token can do** (it is Anthropic's own credential, unlike a GitHub App installation token or a Bitbucket repo-scoped token, §6.2) — this is already true of the single-account case and is unchanged by naming.

**(d) Rotation and audit.** `fugaro secrets set claude-oauth-token-<name> --repo R` stores a new version exactly like today's single secret (`internal/cli/secrets.go`'s existing versioning, labels and redaction all apply unmodified — it is the same command, a new valid `NAME`). `fugaro secrets ls` lists every named account's secret the repository holds, by its `fugaro_secret` label, metadata only (`internal/cli/secrets.go:337-382`), unchanged. Audit of *which account a run used* is `runstore.Record.OAuthAccount` (§4), shown by `fugaro ls`/`diagnose`/`fugaro logs`; it does not change who can read the log (§6.1's log isolation is untouched).

**(e) Accounting.** Subscription tokens have no dollar cap (§1); this design does **not** add a per-account dimension to the budget schema (`internal/budget/model.go`'s `Counters`, the Realtime Database rules, or the Firestore rollover) — that would touch security-critical, mutation-tested code (`m9-budget-and-dashboard.md`'s "leaf-only for writes" rules) for a feature whose only purpose today is "notional, never billed, never capped" display. For v1, `fugaro budget show`/`watch`/`ls` show **which account a run used** (via `OAuthAccount`, read from each run's own `result.json`, no backend change) but not a per-account *rollup total*; a `fugaro ls --token NAME` filter (client-side, over records already fetched) gives the closest thing to a per-account total without touching the budget backend. A true per-account dollar/token rollup is listed as a bigger-version item (§9); it would need a new dimension in `Counters.ByModel`-adjacent storage and a matching Realtime Database rule change, which is a security-sensitive change in its own right and deserves its own review, not a rider on this feature.

**(f) Expired or revoked token.** Unverified from code how Claude Code itself reports this (it is Anthropic's own CLI behavior, not Fugaro's — §7 lists it as a live-check item); Fugaro's existing behavior is almost certainly "the stage fails with whatever Claude Code printed," unchanged by naming. The new, offline-safe piece this design adds is **`fugaro doctor`**: a check that every `claude_accounts` name the local config defines has a stored secret version (reusing the existing `secrets ls`-style metadata read, no value ever read back) and that `agent.oauth_token` in every onboarded repository's `fugaro.yaml` names either `default` or an allowed, defined account — both are static, offline, no-GCP-call-needed checks in the `fugaroYAMLCheck`/`doctorCheck` family (`internal/cli/doctor.go:353-373` is the shape to extend). Doctor cannot and does not check whether a *value* is still valid for Claude (that needs a live call to Anthropic, out of scope, same as today's single-token case).

## 7. Verified vs. unverified

**Verified from code (cited inline above):** the single reserved secret and its env var; the job-level, static nature of Cloud Run Job secret mounts; `SecretMounts` as the one mounting decision point; the `ModelProvider`/`AllowsData` precedent and its `secrets set` validation; `task.Spec`'s strict decoding; `Launch`'s override shape (env and timeout only, no secret reference anywhere in this codebase); `runstore.Record`'s shape; the budget schema having no per-credential dimension.

**Unverified — live-check items, sandbox project only, for the owner to run (added to `docs/gcp-live-checklist.md` by the plan, §8):**
- **U1. Cloud Run Jobs execution overrides cannot carry a secret reference, only env/timeout/args.** This design is built as if that is true (option D rejected, §4); confirm against the live `run.googleapis.com` API (not just this repository's generated client bindings) that no `RunJobRequest.Overrides` field accepts a `secret_key_ref`, and that even if a future API version added one, Cloud Run still requires the secret to be in the job template (IAM is not grantable per execution). If this check finds otherwise, option D becomes viable and narrows the Terraform footprint of T3 — a reason to run it before, not after, implementation.
- **U2. `claude setup-token` and multi-account switching.** Confirm, by hand, what the *Claude Code* CLI does when a machine has already run `claude setup-token` for one account and the user wants a second token for a different account (log out and back in? A `--account`/profile flag? A separate browser session?). Fugaro's docs and the setup skill (`plugin/skills/setup/SKILL.md:108`) must tell the user the exact sequence, and this design cannot specify it without running it.
- **U3. Per-project Cloud Run job count comfort.** Confirm that an installation's intended number of (workflow × named account) variants stays well under any practical Cloud Run jobs-per-project/region guidance Google publishes or enforces; this repository's code does not read or enforce such a limit.
- **U4. The actual Claude Code error text for an expired/revoked oauth token**, so the runner's existing stage-failure path (unchanged by this design) can be checked to still produce something nameable in `fugaro diagnose`, and so the docs can quote the real message rather than a guess.

## 8. Release placement

**Recommended: release 0.8.0** (veto alternative: a dedicated 0.9.0, if the owner prefers not to grow 0.8.0's scope). Reasoning: 0.7.0 is already committed to bucket-IAM hardening and the base-image consolidation (`docs/design/bucket-iam.md`, `docs/design/base-image.md`), both touching `internal/infra` heavily; 0.8.0 already holds the Docker-capable backend (blocked on a live measurement check, `docs/design/generic-tool.md` §1) and the cost preview (`docs/design/generic-tool.md` §1.1) — neither of which this feature depends on or conflicts with. Sequencing this work to start only after 0.7.0 merges avoids `internal/infra` merge churn with the base-image consolidation (no functional dependency, a scheduling one). Sizing: medium — one PR group, no blocked sub-item, comparable to the `m10-multi-model.md` provider work it mirrors.

## 9. The minimal safe version, and what a bigger version adds

**Minimal (this design, v1):**
- `claude_accounts:` in the local config only, `allow_data_to`-gated like providers.
- `default` plus explicit named accounts, one job/service-account variant per allowed name (option B, §4).
- `agent.oauth_token` (repo scope only, never the project layer or a profile — T2) and `fugaro run --token NAME`, both checked against the allow-list before any launch.
- `fugaro secrets set/ls` extended to the new secret-name shape, never echoing a value.
- `fugaro doctor` offline checks (§6f); `OAuthAccount` shown in `fugaro ls`/`diagnose`/`fugaro logs`.
- No change to the budget/accounting backend.

**A bigger version would add:**
- A per-account dollar/token rollup in `fugaro budget show`/`watch` (needs new Realtime Database and Firestore schema, its own security review, §6e).
- Runner-side fetch (option C, §4) if a live check (U1/U3) shows the job-multiplication cost of option B is a real operational problem at the owner's scale — trading a static IAM guarantee for fewer Cloud Run resources, a decision that needs re-litigating with actual numbers, not assumed here.
- Cloud Run execution overrides carrying a secret selection (option D), if U1 turns out wrong.
- A `fugaro accounts` command to list configured names and which repositories may use each (today, `fugaro secrets ls` and reading the local config file cover this by hand).
- Extending the same `claude_accounts`/`AllowsData` shape to `anthropic-api-key` (today also a single reserved secret), which this design does not touch: API-key billing already goes through the gateway's dollar cap per repository, so "multiple named api-key accounts" is a different, lower-priority problem (budget accounting already works there) left for a separate design if ever requested.

## 10. Testing

- **Golden compatibility.** `BuildRepoSpec`'s tfvars JSON is unchanged, byte for byte, for every existing fixture with no `claude_accounts` configured (§5).
- **Allow-list enforcement.** A repository not listed in `allow_data_to` gets no job variant for that name (`infra` test), is refused at `fugaro validate`/`run --token` (CLI test), and a direct Terraform-level attempt is moot because the resource is never declared (no "apply refuses it" test needed — it is not generated).
- **`secrets set` validation.** Mirrors `TestAllowsDataIgnoresCase`-style cases already in `model_providers_test.go`, for `ClaudeAccountBySecret`.
- **Strict decoding.** A pre-feature runner (simulated by decoding with `DisallowUnknownFields` against a `task.json` carrying `oauth_token`) refuses, proving the version-skew gate is real, not just documented.
- **No live cloud, no live Anthropic call** anywhere in the automated suite; §7's items are the owner's own live-check task, run once in the sandbox project, their FACT lines pasted into `docs/gcp-live-checklist.md` and the PR.
