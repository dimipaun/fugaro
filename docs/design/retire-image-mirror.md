
# Retiring the image mirror: a digest-pinned `FROM` instead of a copy

Status: design for review (2026-10-13), from the owner's spec and the owner's gate (2026-10-12, PASSED) and live Cloud Build test (project `fugaro-dev`, build `c503576c-51d9-4f96-b9e7-debae7d0df39`, `docker pull ghcr.io/dimipaun/fugaro-go:0.6.5` succeeded in 21s as the default compute service account, digest `sha256:ba06760c...`). Docs and a plan only: no product code in this change. Delivery: **after** the base-image hard cut (`docs/design/base-image.md` §10, plan Tasks 17–21), a 0.7.x release — see "Release placement" below.

**A note on current repository state, checked while writing this (2026-10-13):** `.github/workflows/images.yml` already carries the real `fugaro-base`/`publish-base` jobs — commit `356f7b1` ("images workflow: publish the base image"), already an ancestor of this branch, copied them in from `docs/pending-workflows/images.yml` and `git rm`'d the pending copy, which now holds only `README.md`. That commit is **not yet in a released tag** (the latest release, v0.6.6, predates it), so no release has actually run the job yet and `ghcr.io/dimipaun/fugaro-base` has not been published by a release — but the workflow mechanism itself is live in the real file, not staged. `docs/release.md` and `docs/base-image.md` still describe it as staged; that is a separate, pre-existing staleness in those docs, not something this design introduces or relies on. Task 1 of the implementation plan accounts for this directly: it stages the *current* `.github/workflows/images.yml` plus its own addition into a fresh `docs/pending-workflows/images.yml`, rather than assuming a pending copy already exists.

## 1. Problem

`internal/mirror` exists because, at M11 design time (`docs/design/m11-setup-and-skills.md` §3.3), three things were true: Cloud Build and Cloud Run were believed (UNVERIFIED) unable to read `ghcr.io`; the packages were private; and there was no single project-local registry repository (`fugaro-base`) that only people, never a build account, could write — so copying the release's image into that people-only repository, once, as the operator, was the one guard against a leaked build token replacing the image every repository's `credential`, `render`, `gate`, `record` and check-job steps run.

Since then: the packages are public (every release's `verify-public` job proves anonymous pulls); the base-image consolidation cuts every installation to **one** base kind, `base`, built FROM one published image; Cloud Run never pulls the base at all — it only ever runs a repository's own derived image, from that repository's own registry, so the Cloud-Run leg of the original worry never applied to the base to begin with; and the owner has now directly confirmed, against a real Cloud Build in `fugaro-dev`, that `docker pull ghcr.io/dimipaun/fugaro-go:0.6.5` succeeds through the default compute service account in 21 seconds. What the mirror still does, then, is slower (every build now also pays for a 1.2 GB copy through the operator's own machine before a single derived image is built), bigger in code (internal/mirror's custom OCI-subset HTTP client, `fugaro init --base`, `--expect-digest`, `--replace-image`, the images stage, the base step of `image refresh`), and no stronger a guarantee than a digest pin plus a signature the operator can check before they ever submit a build — which it doesn't yet have (`--expect-digest` pins a digest, but there is no out-of-band source for one until cosign signing of the images exists, the plan's follow-up **F1**, not built; `docs/release.md`, `docs/design/base-image.md` §17 non-goals).

This design retires the mirror **for the base image** and replaces the copy with a digest-pinned `FROM ghcr.io/dimipaun/fugaro-base@sha256:…` that Cloud Build resolves directly, with the digest obtained and verified by the operator's own machine, not by whatever ghcr.io's tag resolves to at build-submission time.

**Explicitly out of scope: the history image.** `fugaro init --firebase` copies `fugaro-history` into the installation's registry today because the history job's Cloud Run Job resource (Terraform, `deploy/terraform/gcp/modules/installation/history.tf`) names that copy's path as its `image:`, and that is a different pull path from everything this design changes: Cloud Build never touches it, and whether a Terraform-managed Cloud Run Job can run an image directly off `ghcr.io` with no registry credential at all is not the thing the owner's live test checked (it checked a `docker pull` inside a Cloud Build step, not a Cloud Run Job's own image-resolution path). `internal/mirror`'s copy engine (`Plan`/`Copy`, the digest-by-digest verified transfer) stays, used only for `history` from here on; everything this design removes is the **base**-kind-specific glue around it. A follow-up design can retire the history copy too, once that pull path has its own live check.

## 2. The trust model after retiring it (item 1)

**Today's control point:** "only operators write `fugaro-base`; build accounts only read it" (`docs/gcp-setup.md` §"The base image"). A leaked build token can read the project's own copy but never replace it, so every repository's build is anchored to whatever the operator last confirmed and copied.

**The replacement control point: a digest the operator verified, baked into every build submission by code the build account cannot change.** Concretely:

- **Where the digest comes from.** `images.yml` (the real, merged file, §"A note on current repository state" above — no longer a pending copy) builds, smoke-tests, scans and will publish `fugaro-base` and `fugaro-history` once a release runs it, but today computes and publishes no signature of anything, images included: there is no out-of-band source for a digest yet, which is exactly the gap `docs/design/base-image.md` §17 lists as a non-goal and the plan's follow-up **F1** is meant to close. This design **is** that follow-up, scoped to what the mirror's retirement needs: after `publish-base` pushes `fugaro-base:<v>-amd64`, `:<v>-arm64` and the multi-platform index `:<v>`, a new step writes a small, line-oriented manifest (`image-digests.txt`, one `<tag> sha256:<hex>` line per architecture plus the index and `fugaro-history`), signs it **keyless** with `cosign sign-blob`, the same mechanism `release.yml` already uses for `checksums.txt` (`docs/release.md` "Verifying a release"), and uploads both the manifest and its `.sigstore.json` bundle as assets on the **same** GitHub Release (`gh release upload`, since the release itself was already created by `release.yml`). The certificate identity to verify against is `images.yml`'s own workflow ref (`https://github.com/dimipaun/fugaro/.github/workflows/images.yml@refs/tags/vX.Y.Z`), not `release.yml`'s — they are different workflows, so a verifier must check the one that actually signed it.
- **Who verifies it, and when.** The operator's own machine, at `fugaro upgrade` or `fugaro init`/`fugaro image refresh` time — never a build, never the daily check job, never a coding agent's session (the same `agentMarker` refusal `image refresh` already has). The CLI downloads `image-digests.txt` and its sigstore bundle from the GitHub Release of the binary's own running version (the same release API already consulted for update checks, `docs/release.md` "Update checks"), verifies the keyless signature against the `images.yml`-on-this-tag identity, and only then reads the `fugaro-base` index digest out of the verified manifest. This is a new piece of Go: verifying a sigstore bundle is not something this repository does anywhere today (only the shell-based `cosign verify-blob` in the docs). See "Open decisions" below for the Go-side approach.
- **Where it is recorded.** `base_images.base` in the local config keeps its name and its shape (a string value, union-ed into the shared config exactly as today, `localcfg.Shared()`), but its **content** changes meaning: instead of a path inside the installation's own Artifact Registry (`<region>-docker.pkg.dev/<project>/fugaro-base/fugaro-base:<v>`), it becomes the verified source reference directly: `ghcr.io/dimipaun/fugaro-base:<v>@sha256:<hex>` (a fork's `--image-source` changes only the host/owner prefix). Writing it is now "verify, then record" instead of "copy, then record" — no bytes move, no registry write, and the existing confirmation screen names the digest instead of the megabytes.
- **What the generated Dockerfile's `FROM` looks like.** `images/derived/Dockerfile.tmpl` needs **no change**: it already does `ARG FUGARO_BASE` / `FROM ${FUGARO_BASE}`, and the build-arg's value is just a string the CLI supplies. What matters is the **shape** of that string: it must always be `<host>/<path>/fugaro-base:<X.Y.Z>@sha256:<hex>` — tag **and** digest together, never a bare `@sha256:…` with no tag. This is not a style preference: `internal/cli/init_fugaroyaml.go`'s `baseRefReleaseRE` (`\A[^\s@]+/fugaro-(kind):v?(X.Y.Z)(?:@sha256:…)?\z`) is what every version-skew gate parses the build record's `base_ref` with — `gcpProjectFieldSince`, `recipesSince`, `layeredSince`, `namedTokensSince` (via `checkImageSince`) all depend on finding a release version in that string, and none of them care what host or path precedes `/fugaro-base:`. Keeping the tag alongside the digest means **every one of those gates keeps working unmodified**, across the migration, for both an old Artifact-Registry-hosted `base_ref` and a new `ghcr.io`-hosted one. Docker itself resolves a `tag@digest` reference purely by digest (the tag is informational once a digest is present), so this costs nothing at pull time and buys the CLI's own skew machinery for free. **This is a hard constraint on the implementation, not a preference the owner can relax without also reworking four unrelated gates.**
- **How a base bump happens.** Only ever an explicit operator step — `fugaro upgrade` (which already runs `image refresh` per repository, `docs/release.md` "Rolling out the shared installation config") or `fugaro init --base`/`fugaro image refresh` directly. Each re-verifies the running release's signed digest and rewrites `base_images.base` only when it differs (and never downgrades: the existing `newer()` comparison in `image_refresh_rules.go` is reused unchanged — the semantics "a newer managed copy than this release's is kept" transfer directly, the comparison just moves from an Artifact-Registry tag string to a ghcr.io one). There is no "latest" and no bare tag anywhere in this design: every write to `base_images.base` is a verified `tag@digest`.
- **What an attacker who controls ghcr.io's tag, or a fork of the repository, can and cannot do.** A digest pin means moving the `v*` tag in ghcr.io (or forking and publishing a lookalike under another owner) changes nothing for an installation that already resolved and pinned a digest: Cloud Build never re-resolves the tag, it pulls exactly the digest the Dockerfile names. The live question is upstream of the pull: can an attacker make the operator's own machine **record** a bad digest in the first place? That needs either (a) compromising the `images.yml` workflow's identity (the thing cosign's certificate-identity check is specifically built to catch — a forged signature would need GitHub's own OIDC issuer to vouch for a workflow ref it didn't run), or (b) compromising the GitHub Release itself before the operator downloads from it (mitigated, not eliminated, by `release.yml`'s own gate: a release only publishes from a commit that passed CI on `origin/main`, and tag protection/immutable releases are the repository owner's own GitHub setting per `docs/release.md`'s "Before you tag" checklist). This is strictly stronger than today's accepted risk (*"the trust anchor is the tag as the registry resolves it now … whoever can write `ghcr.io/dimipaun/fugaro-*:X.Y.Z` can make the user's cloud run their code"*, `internal/mirror/ref.go`'s doc comment) because today an attacker only needs to move the ghcr.io tag; after this change they additionally need to defeat the signature.
- **A narrow, deliberate consequence for `internal/infra/tf/cover.go`.** `Cover.checkSpecs` today refuses to silently fold a Terraform-managed check-job creation into the single project-name confirmation unless **every** `base_images` entry it would write is inside `<this run's registry>/<project>/…` (`inRegistry`, `cover.go:748-785`; `cover_test.go`'s `"base image of another project"` case already expects `false`). Once `base_images.base` legitimately points at `ghcr.io/dimipaun/fugaro-base:<v>@sha256:…`, every **new** repository's first `fugaro init --repo` would stop being silently covered — not a failure, just its own separate typed confirmation, every time, forever, which is friction without a matching safety gain (the value IS the thing the CLI itself just verified). `inRegistry` needs a second, narrower allowance: a base image reference is "covered" when it is inside the project's own registry **or** when it is byte-for-byte the pinned source reference this run's own verification produced (prefix-matched against the configured allowed source, **digest required**, never a bare tag) — never a looser pattern like "any `ghcr.io/dimipaun/*`" or "any ref with an `@sha256:`" (that would let a hand-edited `base_images.base` entry naming an attacker's own ghcr.io image sail through uncovered). **Flagged for opus review** (see the plan): this is the one place a mistake would silently widen what "nothing is applied unseen" means.

## 3. What the mirror bought, and whether to replace it (item 2)

Three things, each weighed against the owner's 21-second measurement:

- **Same-region pull speed for a 1.2 GB base, on every build.** The mirror pays this cost once, at `init`/`refresh` time (through the operator's own uplink: "about 3.5 minutes at 50 Mbit/s, about 16 at 10", `docs/design/base-image.md` §13), not per build — a derived build already pulls the base once per build whichever registry it lives in (no layer cache either way, `docs/design/base-image.md` §13). Direct-pull moves that pull to ghcr.io on *every* build instead of the operator's own copy once; the owner's test (21s) suggests this is not a material regression for Cloud Build specifically, but it has not been measured at the repository build account's own quota/network path (see Live checks), nor under sustained concurrent load across many repositories' builds on the same day.
- **Independence from ghcr.io's own availability and rate limits.** A real cost of removing the mirror: every installation's every build now depends on ghcr.io being reachable and not rate-limiting anonymous pulls, where before only the operator's own occasional `init`/`refresh` did. ghcr.io's documented anonymous rate limits are generous and scoped per IP, and Cloud Build's workers are Google's, not the user's, so the practical exposure is "many installations' builds, at volume, from Google's IP ranges" — this is a real open question, not analysed further here (flagged "out of scope" in Live checks below; GitHub Packages' current anonymous-pull limits are not republished here because they are not something this repository's tests or live checks can pin down, and they change without notice).
- **VPC-SC and egress-restricted projects.** The mirror is the only thing that currently lets such a project build at all (the install-time copy happens once, from the operator's own network, before any repository's build ever needs external egress). Direct-pull removes that option entirely for a project whose Cloud Build workers cannot reach the public internet.

**Options, in increasing complexity:**

- **(A) Direct pull by digest — recommended.** What this design does. Zero new infrastructure, matches what the owner already measured, and the loss (ghcr.io availability/rate limits, no VPC-SC support) is accepted as a known, documented limit rather than solved — exactly as today's SECURITY.md already documents other accepted limits rather than engineering around every one of them.
- **(B) An Artifact Registry *remote* repository over ghcr.io (a Google-managed pull-through cache, no upload).** This would keep same-region pull speed with none of the mirror's own code, if Artifact Registry's remote-repository feature actually supports an arbitrary upstream registry such as ghcr.io rather than only Docker Hub-shaped upstreams — **this is UNVERIFIED and this design does not assume it.** The owner would verify it with one `gcloud artifacts repositories create <name> --repository-format=docker --mode=remote-repository --remote-docker-repo=... --project <gcp-project>` against a real ghcr.io host (not a dry run — Artifact Registry remote repositories are created and billed for real) and one `docker pull <region>-docker.pkg.dev/<project>/<name>/dimipaun/fugaro-base:<v>` through it. If it works, (B) is strictly better than (A) for cost and availability and should be revisited as a fast follow-up; this design does not block on it because it adds a real, as-yet-unverified Terraform resource and this is meant to ship after the already-large base-image cut, not alongside a second unverified cloud primitive.
- **(C) Keep the mirror as an opt-in `base_images.base` escape hatch for locked-down projects.** Already true without any new code: `--base-image base=<image>` (bring-your-own, `docs/base-image.md` "Bring your own") already lets a VPC-SC project point `base_images.base` at an image of its own choosing, built and pushed however that project's network allows (`images/build-base.sh base`, by hand, as today's "Until you use a release build" path already documents). No separate `base_mirror: true` flag is needed: the existing bring-your-own path already covers this case, and adding a second mechanism that does almost the same thing would be exactly the kind of premature abstraction this design is trying to remove, not add.

**What each costs the daily check job and cold builds:** the daily check job never pulls the base directly — it pulls the repository's own already-built job image from that repository's own registry (`docs/gcp-setup.md` "What the daily image check reads"); it is unaffected either way. A cold build (the very first build of a new workflow, no warm layer cache) pays the full base pull under (A) exactly as it does today under the mirror, since Cloud Build never caches base layers across builds in either design (`docs/design/base-image.md` §13).

## 4. The build accounts (item 3)

**What is removed from Terraform:** `google_artifact_registry_repository_iam_member.build_base` (`deploy/terraform/gcp/modules/repo/build.tf:44-50`), the grant that lets a repository's own build account read the installation's `fugaro-base` registry. Nothing reads `fugaro-base` for the **base** kind once nothing is ever pulled from it; the repository's own `build_images` (writer on its own registry) and `build_tag_mover` grants are untouched (they serve the repository's own derived-image pushes, unrelated to the base).

**`tf.Guard` implications.** Removing an existing IAM-member resource is, in Terraform's plan, a `delete` action on that resource's address, and `tf.Guard` (`internal/infra/tf/guard.go`) refuses any plan containing a `delete` unless the exact address is named in `--allow-delete` — by design, so a plan never silently removes something. This means the **first** `fugaro init --repo` (or whole-installation `fugaro init`) a repository runs after upgrading past this change will show a `delete` of `google_artifact_registry_repository_iam_member.build_base["<repo>"]` and refuse until the operator passes `--allow-delete 'google_artifact_registry_repository_iam_member.build_base["<repo>"]'` once, explicitly, for each repository (or the installation names them all in one run, as `fugaro init --repo` already prints the exact guarded address to copy). This is not a workaround to design past — it is the guard doing exactly its job (a human confirms an intentional removal) and the migration doc should say so plainly, with the exact flag, rather than surprise an operator mid-rollout.

**Secrets and registries with `prevent_destroy` are never touched.** The `fugaro-base` Artifact Registry repository itself (`deploy/terraform/gcp/modules/installation/registry.tf:24-73`) carries `lifecycle { prevent_destroy = true }` already, and this design proposes no change to that resource at all — it is not in the delete set, only the per-repository *reader grant on it* is.

**What happens to the existing `fugaro-base` registry repository:** kept, untouched, forever — exactly like the already-existing `legacy_registry` pattern (`registry.tf:1-19`, kept for rollback, nothing writes it after migration). After this change nothing ever writes to it again (no operator copy, since there is nothing left to copy for the base kind; `history` still writes it, per the explicit out-of-scope call above). It becomes historical: an installation's already-copied base image versions stay there as an artifact of pre-migration builds, available for a manual rollback (`docker pull`/retag by hand) if an operator ever needs to rebuild from an old pinned copy instead of ghcr.io, but Fugaro itself never deletes it, never stops the cleanup-policy Terraform resource from existing (harmless once nothing is pushed there), and never automates a cleanup of the now-dead entries — that is the operator's own call, same as the legacy registry today.

## 5. Migration (item 4)

**Installations that already hold a mirrored copy.** The owner's two installations: `fugaro` (GCP project `fugaro-dev`, sandbox repository `edgeappinc/fugarosandbox`, the owner is its only launcher and operator) and `belong` (EdgeWeb's and EdgeServer's installation). **This design makes no live change to either, and no live step of its implementation plan may touch `belong` without the owner's explicit, separate word** — every live check below is scoped to `fugaro`/`fugaro-dev`, sandbox repository only, exactly as the existing `gcp-live-checklist.md` entries for that project already are.

**How a repository moves from the copied form to the pinned form.** No new mechanism: the **existing** `fugaro image refresh` step 2 ("the base step") is reused as-is in its surrounding flow (preflight, confirm, record, then steps 3 and 4 reload and rebuild what the new base disagrees with) — only *what step 2 does* changes, from "copy, then record the destination" to "resolve this release's signed digest, verify it, then record the verified source reference." A repository whose `base_images.base` still names `<region>-docker.pkg.dev/<project>/fugaro-base/fugaro-base:0.7.x` (the old, copied form) is treated exactly like one whose entry names an *older* release's copy today: `isManaged`/`managedVersion` (currently keyed to "is this ref inside the installation's own registry, under `BaseRepository`, naming this release's version") gain a second recognized shape — a ghcr.io-hosted `tag@digest` under the configured source prefix — and the `newer()` comparison and "never downgrade a newer managed copy" rule apply across both shapes identically, keyed purely on the parsed `X.Y.Z`. The **confirmation screen** changes in substance (it names a digest instead of megabytes and a destination path) but not in kind: it is still the same "type the project's name" step, still refused in a coding agent's session, still skippable with `--yes` from CI exactly as today.

**The strict-parser `*Since` gates.** As established in §2, `baseRefReleaseRE` (and therefore every gate built on it: `gcpProjectFieldSince`, `recipesSince`, `layeredSince`, `namedTokensSince` via `checkImageSince`) needs **no code change** across this migration, because the invariant "the base ref always carries `fugaro-<kind>:X.Y.Z[@sha256:…]`, host-and-path-agnostic" is preserved by construction (§2). A build record written before this change (`base_ref` an Artifact-Registry path) and one written after (`base_ref` a ghcr.io path) are judged identically by every existing gate — they differ only in which `fugaro` binary wrote them, which is exactly what those gates already exist to detect. **No migration task is needed for the skew gates themselves**; this is worth stating explicitly because it is the single easiest place to introduce a silent regression by "helpfully" tightening the regex to also require an Artifact-Registry-shaped host.

**`base_images` in the local and shared config.** No key changes (`base_images.base` is still the one key, post-cut); only the **value's shape** changes, and only for repositories an operator actually runs `image refresh`/`upgrade` against after upgrading. `Shared()`'s union behavior (`internal/localcfg/shared.go`) needs no change: it already treats `base_images` as an opaque string map, unioned by key, with the local value winning (`shared_test.go`'s existing coverage already exercises exactly this shape of change — a value changing under an existing key — so no new test category is needed there, only new fixture values).

**What the owner's existing job images do until rebuilt.** Nothing changes for them: an already-built derived image keeps running exactly as it is (it has its own `fugaro` binary baked in, from whatever base it was actually built FROM) until its workflow is next rebuilt — by a commit that changes something the image-config hash covers, by the daily check's own staleness rules, or by an explicit `fugaro image refresh`/`image build`. This design does not force a rebuild of anything; it only changes what a **new** build, from here on, resolves `FUGARO_BASE` to.

## 6. What is deleted, what stays (item 5)

**Deleted** (base-kind-specific; the package's history-kind use stays, §1):

- `fugaro init --base` and its `--base` flag's base-kind-copying meaning (history's own copy, via `--firebase`, is unaffected and unflagged here).
- The images stage's base-kind branch in `internal/cli/init_images.go` (`items()`'s base-kind loop, `managedVersion`/`isManaged`'s installation-registry-keyed form, `confirmReplace`'s base-kind path, `record()`'s "copied, so record the destination" write — replaced by "verified, so record the source").
- `image refresh`'s base step as a *copy* (`internal/cli/image_refresh_rules.go`'s `refreshBase` helper, which builds a `mirror.Dest` and nothing else) — replaced by the verify-and-pin step; the surrounding `image_refresh.go`/`image_refresh_steps.go` flow (preflight, the five numbered steps, `refreshStopped`, `askBuild`, `refreshVerdict`) stays, because none of it is specific to *how* step 2 gets a base ref, only to *what it does once it has one*.
- `--replace-image`'s `base`/`go`/`java-services`/`web-node` meanings (nothing is ever copied into the user's own registry for a base kind anymore, so there is nothing left to "replace a tag that names another image" about). `--replace-image history` is unaffected.
- `--expect-digest`'s role as the *only* source of an out-of-band pin for `base` — superseded by the signed digest list, which is checked by default now, not only when the operator remembers to pass a flag.
- Every base-kind-specific line of `docs/gcp-setup.md` §"The base image, in `fugaro-base`" that describes a copy (megabytes moved, storage cost, `--replace-image base`), and the matching lines of `docs/base-image.md`/`docs/base-image-migration.md`.
- `google_artifact_registry_repository_iam_member.build_base` (Terraform, §4).

**Stays, unchanged:**

- `internal/mirror`'s copy engine (`Plan`/`Copy`, the digest-verified HTTP client, the idle-guard, the anonymous-token flow), used for `history` only from here on.
- `--expect-digest` as a concept — it keeps meaning "pin a digest obtained out of band," now checked against (and able to *override*, for an operator who got a more specific pin some other way) the signed digest list's own resolution, exactly as `docs/plans/2026-10-08-base-image.md` Task 19 already documents the post-cut help text ("KIND is base or history").
- `verify-public` (release-time proof that the published images are anonymously readable) — if anything, this design leans on it *more*, since every build now depends on that property holding at build time too, not only at copy time.
- `--base-image` (bring-your-own, unrelated to the release's own trust chain entirely — the team names its own image and is responsible for it, as today).
- The base image's own content, the monthly bump, the size budget, the secret scan — none of this design's business.

## 8. Release placement

0.7.x, **after** the base-image hard cut lands (plan Tasks 17–21: the legacy kinds removed, `config.Bases == ["base"]`, the local/shared config and check-job rewrite for the one remaining kind, release 0.7.0 itself). ## 9. Decisions for the owner to rule on

1. **Go-side cosign verification.** This repository has never verified a sigstore bundle in Go (only shelled to `cosign verify-blob` in docs). Two paths: (i) vendor a Go sigstore-verification library (`github.com/sigstore/sigstore-go`'s `verify` package is the maintained, purpose-built one) compiled read-only into `fugaro` itself, so `fugaro upgrade`/`init` need no external binary; or (ii) shell out to a `cosign` binary if present on the operator's `PATH`, falling back to a loud warning (not a silent skip) when absent. **Recommendation: (i)** — an operator should not need `cosign` installed for a security control this design is making load-bearing; the plan's Task 2 (next document) flags this for opus review precisely because it is new, security-critical code.
2. **`cover.go`'s `inRegistry` allowance (§2).** Recommended: a narrow, exact-match exception (configured source prefix + mandatory digest), never a loose pattern. Flagged for opus review in the plan.
3. **Option (B), an Artifact Registry remote repository over ghcr.io**, as a possible fast follow-up once verified — not blocking this design.
4. **The Terraform `--allow-delete` migration step (§4)** — confirm the one-time, per-repository guarded delete is acceptable UX, versus, for example, a `fugaro image refresh`-driven removal that prints the exact flag for the operator to paste (recommended: the latter, so the operator never has to construct the Terraform address by hand).

## 10. Non-goals

- Retiring the history image's copy path (§1; a candidate follow-up once Cloud Run's own direct-pull path has a live check).
- Implementing an Artifact Registry remote-repository cache (option B).
- Signing anything beyond the base image's and history image's digests (no broader cosign rollout).
- Changing VPC-SC/egress-restricted projects' options beyond documenting that `--base-image` already covers them.
- Any live cloud or network action: this document and its plan are a design and a plan only.
