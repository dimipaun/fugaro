
# Retiring the image mirror: a digest-pinned `FROM` instead of a copy

Status: design for review (2026-10-13), from the owner's spec and the owner's gate (2026-10-12, PASSED) and live Cloud Build test (project `fugaro-dev`, build `c503576c-51d9-4f96-b9e7-debae7d0df39`, `docker pull ghcr.io/dimipaun/fugaro-go:0.6.5` succeeded in 21s as the default compute service account, digest `sha256:ba06760c...`). Docs and a plan only: no product code in this change. Delivery: **after** the base-image hard cut (`docs/design/base-image.md` §10, plan Tasks 17–21), a 0.7.x release — see "Release placement" below.

**A note on current repository state, checked while writing this (2026-10-13):** `.github/workflows/images.yml` already carries the real `fugaro-base`/`publish-base` jobs — commit `356f7b1` ("images workflow: publish the base image"), already an ancestor of this branch, copied them in from `docs/pending-workflows/images.yml` and `git rm`'d the pending copy, which now holds only `README.md`. That commit is **not yet in a released tag** (the latest release, v0.6.6, predates it), so no release has actually run the job yet and `ghcr.io/dimipaun/fugaro-base` has not been published by a release — but the workflow mechanism itself is live in the real file, not staged. `docs/release.md` and `docs/base-image.md` still describe it as staged; that is a separate, pre-existing staleness in those docs, not something this design introduces or relies on.

**A note on this revision (fourth review round — a genuine course correction, not a patch).** A fourth review found that §1's and §3's claim — "Cloud Run never pulls the base; the daily check job never pulls the base directly" — is **false**: the daily image check *is* a Cloud Run Job, and it runs **FROM the base image itself** (`deploy/terraform/gcp/modules/repo/check.tf`: *"a Cloud Run job that runs `fugaro image check --job` from the base image"*; its container's `image = var.repo.check.image`, set in `internal/infra/spec.go`'s `check()` directly from `lc.BaseImage(kind)` — the **same** config value this design's earlier drafts wanted to repoint at a bare `ghcr.io` reference). Cloud Run Jobs' container image must come from Artifact Registry, Container Registry (legacy) or Docker Hub — **not verified live, stated as an assumption** — and an arbitrary third-party registry such as `ghcr.io` needs an Artifact Registry *remote repository* to be deployable there at all (an unverified feature, §3 option B). Repointing `base_images.base` at a bare `ghcr.io` digest, as every earlier draft of this document did, would have made the check job's own container image field **undeployable**.

This revision keeps **what the mirror's retirement is actually for** — Cloud Build no longer depends on an operator-triggered copy to submit a build — while **keeping, and strengthening, the copy the check job genuinely cannot do without.** Concretely: **`base_images.base` keeps its exact meaning and shape from today** (an Artifact-Registry-hosted copy, written by the existing `fugaro init --base`/`image refresh` copy step, used by the check job's container image and `FUGARO_CHECK_SPEC` exactly as now); what's new is that the copy is preceded by a **cosign signature verification** (so it is a *verified* copy, not a blind one), and Cloud Build's own `FUGARO_BASE` substitution is now resolved **directly, fresh, at every build submission**, by the operator's own machine, against the signed `ghcr.io` digest — not read from `base_images.base` at all. This is a smaller, more surgical change than earlier drafts attempted, and it resolves two other findings (B2, B3 below) as a direct consequence, not as separate patches.

## 1. Problem

`internal/mirror` exists because, at M11 design time (`docs/design/m11-setup-and-skills.md` §3.3), three things were true: Cloud Build and Cloud Run were believed (UNVERIFIED) unable to read `ghcr.io`; the packages were private; and there was no single project-local registry repository (`fugaro-base`) that only people, never a build account, could write — so copying the release's image into that people-only repository, once, as the operator, was the one guard against a leaked build token replacing the image every repository's `credential`, `render`, `gate`, `record` and check-job steps run.

Since then: the packages are public (every release's `verify-public` job proves anonymous pulls); the base-image consolidation cuts every installation to **one** base kind, `base`, built FROM one published image; and the owner has directly confirmed, against a real Cloud Build in `fugaro-dev`, that `docker pull ghcr.io/dimipaun/fugaro-go:0.6.5` succeeds through the default compute service account in 21 seconds — so **Cloud Build** no longer needs the copy to pull a base. **Cloud Run is a different story, and this design does not change it**: the daily image check job *is* a Cloud Run Job, and it runs directly FROM the base image (not a repository's own derived image) — `check.tf`'s own comment says so, and `spec.go`'s `check()` sets the container's image straight from `lc.BaseImage(kind)`. Whether Cloud Run Jobs can deploy an arbitrary third-party registry reference such as `ghcr.io/...@sha256:...` directly is **not verified live here**; the documented, conservative assumption is that they cannot, without an Artifact Registry remote repository in front of it (an unverified feature, §3 option B). So the check job's container image stays an Artifact-Registry-hosted copy, exactly as today — what retires is **Cloud Build's own dependency on that copy**, which no longer needs to exist before a build can run.

What the mirror cost, for the part that *is* retiring: every build paid for a 1.2 GB copy through the operator's own machine before a single derived image was built, and the copy itself was no stronger a guarantee than "whatever the tag resolves to now" — `--expect-digest` pinned a digest, but there was no out-of-band source for one until cosign signing of the images existed (the plan's follow-up **F1**, not built; `docs/design/base-image.md` §17 non-goals).

This design retires the mirror's role **in Cloud Build submissions only**, replacing it with a digest-pinned `FROM ghcr.io/dimipaun/fugaro-base@sha256:…` that Cloud Build resolves directly, with the digest obtained and **cryptographically verified** by the operator's own machine at every submission — never trusting whatever ghcr.io's tag happens to resolve to. The check job's own image keeps coming from a copy, now a *verified* one.

**Explicitly out of scope: the history image.** `fugaro init --firebase` copies `fugaro-history` into the installation's registry today because the history job's own Cloud Run Job resource (Terraform, `deploy/terraform/gcp/modules/installation/history.tf`) names that copy's path as its `image:` — the same category of constraint as the check job's, for the same reason (a Cloud Run Job, not Cloud Build). `internal/mirror`'s copy engine (`Plan`/`Copy`, the digest-by-digest verified transfer) stays, used for `history` exactly as today, and now also for the check job's base-image copy (below) — nothing in this design removes or replaces it; it gains one new, optional pre-step (signature verification) ahead of its existing copy.

## 2. The trust model after retiring it, for builds (item 1)

**Today's control point:** "only operators write `fugaro-base`; build accounts only read it" (`docs/gcp-setup.md` §"The base image"). A leaked build token can read the project's own copy but never replace it, so every repository's build is anchored to whatever the operator last confirmed and copied.

**The replacement control point, for Cloud Build submissions specifically: a digest the operator's own machine resolves and verifies fresh, every time, never read from a static config value.** Concretely:

- **Where the digest comes from.** `images.yml`'s `publish-base` job (and `publish`'s `history` leg, for history's own, separate, unchanged copy-mirror use) signs the pushed image **by OCI digest** (`cosign sign`, not `cosign sign-blob`): right after pushing the multi-platform index, the **same job** runs `cosign sign --yes "ghcr.io/dimipaun/fugaro-base@sha256:<digest-just-pushed>"` keyless, attaching the signature as its own OCI artifact in the **same** ghcr.io repository — no GitHub Release asset, no cross-workflow coordination, no interaction with immutable releases (a container registry has no such concept; `docs/release.md`'s own "Before you tag" checklist tells the owner to enable them, which an earlier, GitHub-Release-asset draft of this design could not have survived). The signing step is gated to `github.event_name == 'push'` only (the version-job's own version-picking logic already treats `workflow_dispatch` identically to `schedule` — "the latest strict `vX.Y.Z` release tag," never the dispatched ref — so there is no legitimate manual-re-run-against-a-tag case this guard would wrongly skip).

  **The nightly's own run moves the plain tag; signing alone does not stop that, and a second, nightly-immune tag closes it.** `images.yml` also runs nightly and on `workflow_dispatch` (`images.yml:7-9`), rebuilding and re-pushing `fugaro-base:<v>` under the *latest* release's version tag with a **new, unsigned** digest, to pick up Debian security patches. If resolution read that plain tag, every fresh resolution (a build submission, a brand-new `fugaro init`/`upgrade`) of the then-latest release would hard-refuse for the entire window between the first nightly after a release and the next release tag — a window whose length tracks this project's own release cadence, not a fixed, small number of hours, and could be weeks. This is resolved, not merely disclosed: `publish-base`'s (and `publish`'s `history` leg's) tag-push step adds one more tag — `fugaro-base:<v>-pinned`/`fugaro-history:<v>-pinned` — to the **same** push/create call that already makes `:<v>`/`:<major>`, conditioned on `github.event_name == 'push'` so the nightly's own run of that same call never creates or moves it. Resolution (below) always reads the `-pinned` tag, never the plain one, so what it finds is the one digest the tag-push run itself signed, unaffected by how many nightlies have since moved the plain tag.

- **Who resolves and verifies it, and when — the part that changed with this revision.** Not the operator's `fugaro upgrade`/`init`/`image refresh`, recording a static value once. Instead: **every Cloud Build submission** (`fugaro image build`, the first-build path inside `fugaro init --repo`, and `fugaro image refresh`'s own build step) calls `basepin.Resolve` directly, fresh, immediately before submitting, to compute the `FUGARO_BASE` substitution it hands Cloud Build. `basepin.Resolve` resolves what `ghcr.io/dimipaun/fugaro-base:<version>-pinned` currently names (the same anonymous, digest-verified registry read `internal/mirror` already does today for a tag, reused via a new, small `mirror.ResolveDigest` export, not reimplemented), verifies **that specific digest's** OCI-attached cosign signature against the `images.yml`-on-this-tag identity, and returns the clean `ghcr.io/dimipaun/fugaro-base:<version>@sha256:<hex>` (without the `-pinned` suffix — that exists purely as a registry-side resolution anchor). Nothing is ever recorded into `base_images.base` by this path, and nothing reads `base_images.base` for this purpose: that config value keeps its **existing** job entirely (below). **Stated plainly: this depends on a new dependency, with no precedent anywhere in this repository** (today's only sigstore use is the shell-based `cosign verify-blob` a person runs by hand) — either `github.com/sigstore/sigstore-go` vendored read-only, if its library API supports OCI/registry-attached signature verification cleanly (**unverified at design time — the implementer confirms this first**), or shelling out to the real `cosign verify` binary, falling back loudly when absent. Either way this is a real, owner-level dependency decision; see "Decisions for the owner to rule on" below.

  **A real, new operational cost, stated plainly: every build submission now needs network access beyond GCP.** Before this design, submitting a build only ever needed `base_images.base` (a static local-config string) and GCP credentials. After it, the operator's own machine (or, for `fugaro image refresh --yes` from CI, that CI runner) needs to reach `ghcr.io` and the sigstore trust infrastructure (the TUF trusted root and Rekor, for keyless verification) **at every single build submission**, not only at an occasional `init`/`refresh`. This is a real, new dependency this design accepts in exchange for removing the operator-triggered-copy bottleneck; it is not analyzed further here beyond stating it (see Decisions).

- **Signing and publishing are not atomic.** `publish-base`/`publish` push the image, then sign it, in the same job but as a separate command. If the sign step fails, the job fails (`set -eu`, no `|| true`), so the two are *coupled* by CI's own pass/fail gate even though they are not a single atomic registry transaction. A build submission finding no valid signature for the resolved digest refuses cleanly — the same refusal covers a development build (`fugaro version` prints `dev`, unchanged from today) and a release tag whose `images.yml` run itself never published anything (`needs.version.outputs.publish` false — an off-main or backport tree, or a pull request).

- **`base_images.base` is unchanged by this design** — still an Artifact-Registry-hosted reference (`<region>-docker.pkg.dev/<project>/fugaro-base/fugaro-base:<v>`), still written by the **existing** `fugaro init --base`/`image refresh` copy step, still what the check job's container image and `FUGARO_CHECK_SPEC`'s `base_images` map read (`RewriteCheckSpec`'s own logic finds which kind an old container image belongs to by matching it against the spec's `base_images` value — splitting the container's image from the spec's recorded value, as every earlier draft of this document proposed, would break that matching entirely, refusing every check-job update; keeping them equal, exactly as today, is the simplest fix that needs no change to `RewriteCheckSpec`/`PlanCheckJob`/`internal/infra/tf/cover.go` at all). **What's new** is a verification step inserted immediately *before* the existing copy: the images stage (and `image refresh`'s base step) resolve-and-verify via `basepin.Resolve` first, then feed the **verified** digest as `mirror.Plan`'s `expect` parameter (the same field `--expect-digest` already populates), so the copy's own existing digest check is now anchored to a cryptographic signature rather than "whatever the tag said when the operator ran this."

- **What an attacker who controls ghcr.io's tag, or a fork of the repository, can and cannot do.** A digest pin means moving the `v*` tag in ghcr.io (or forking and publishing a lookalike under another owner) changes nothing for a build that has already resolved and verified a digest: Cloud Build never re-resolves the tag itself, it pulls exactly the digest the Dockerfile names. The live question is upstream of the pull: can an attacker make the operator's own machine resolve a bad digest in the first place? That needs compromising the `images.yml` workflow's own identity — the thing cosign's certificate-identity check exists to catch, since a forged signature would need GitHub's own OIDC issuer to vouch for a workflow ref it never ran. This is strictly stronger than today's accepted risk (*"the trust anchor is the tag as the registry resolves it now … whoever can write `ghcr.io/dimipaun/fugaro-*:X.Y.Z` can make the user's cloud run their code"*, `internal/mirror/ref.go`'s doc comment) because today an attacker only needs to move the ghcr.io tag; after this change they additionally need to defeat the signature.

- **`internal/infra/tf/cover.go` needs no change at all.** An earlier draft of this document (across two review rounds) proposed changing `Cover.checkSpecs`'s second allowance for `base_images`, first to a regex, then to an "exact match" that turned out to compare `lc.BaseImage("base")` against itself (always true, silently covering a hand-edited, unverified value — a real regression a third review round caught). Both drafts assumed `base_images.base` would hold a `ghcr.io` reference needing a new kind of allowance; since it does not (above), `cover.go`'s **existing, unmodified** `inRegistry` check — every `google_cloud_run_v2_job`'s container image, and every `FUGARO_CHECK_SPEC` base-image entry, must already be inside the project's own registry — stays exactly as correct as it is today, for exactly the same reason it is correct today. Nothing here weakens that guard; nothing here needed to touch it.

## 3. What the mirror bought, and whether to replace it, for builds (item 2)

Three things, weighed against the owner's 21-second measurement — and a fourth, discovered on the fourth review round, that is **not** retired:

- **Same-region pull speed for a 1.2 GB base, on every build.** The mirror paid this cost once, at `init`/`refresh` time, not per build. Direct-pull moves that pull to ghcr.io on *every* build instead; the owner's test (21s) suggests this is not a material regression for Cloud Build specifically, but it has not been measured at the repository build account's own quota/network path (see Live checks), nor under sustained concurrent load.
- **Independence from ghcr.io's own availability and rate limits.** A real cost: every installation's every build (not just an occasional `init`/`refresh`) now depends on ghcr.io being reachable and not rate-limiting anonymous pulls — and, newly, on reaching the sigstore trust infrastructure too (§2). Not analysed further here; flagged out of scope.
- **VPC-SC and egress-restricted projects.** The mirror was the only thing that let such a project build at all. Direct-pull removes that option for Cloud Build submissions specifically; `--base-image` bring-your-own (§6) is the documented path for such a project.
- **The daily check job's own image, which this design does *not* retire (the fourth-review-round finding).** The check job runs directly FROM the base image, as a Cloud Run Job, which (not verified live, assumed conservatively) cannot deploy a bare `ghcr.io` reference. This is why `base_images.base` and the copy mechanism stay, unchanged, strengthened with a verification pre-step (§2) — not a cost this design accepts in exchange for anything, simply a constraint it does not attempt to design around.

**Options, for the part that *is* retiring (Cloud Build's own FROM pin):**

- **(A) Direct pull by digest, resolved fresh at submission time — recommended.** What this design does.
- **(B) An Artifact Registry *remote* repository over ghcr.io.** Would also let the *check job* read a `ghcr.io`-sourced image without a continued copy — if Artifact Registry's remote-repository feature actually supports an arbitrary upstream registry such as `ghcr.io` (**UNVERIFIED**; the owner would verify with `gcloud artifacts repositories create <name> --repository-format=docker --mode=remote-repository --remote-docker-repo=... --project <gcp-project>` against a real `ghcr.io` host, not a dry run, and one `docker pull` through it). If verified, this is a candidate to retire the check job's own copy dependency too, in a later round — not proposed here.
- **(C) Keep the mirror as an opt-in escape hatch.** Already true without new code: `--base-image base=<image>` (bring-your-own) already lets a locked-down project point `base_images.base` at its own image.

**What each costs the daily check job and cold builds:** the daily check job is unaffected by anything in this design (it keeps reading the same, now-verified, Artifact-Registry copy it reads today). A cold build (the very first build of a new workflow) pays the full base pull from `ghcr.io` under (A), plus the network cost of resolving and verifying the signature — a real, if small, addition to every first build and every subsequent one, not just cold ones.

## 4. The build accounts (item 3) — unchanged, and here is why

**The build account's `fugaro-base` reader grant (`google_artifact_registry_repository_iam_member.build_base`, `deploy/terraform/gcp/modules/repo/build.tf:44-50`) stays exactly as it is today, with no Terraform change at all.** Earlier drafts of this document (across two review rounds) proposed deleting it outright, then making it conditional on whether `base_images.base` still pointed inside the installation's own registry. Both were built on the premise that nothing would read `fugaro-base` for the base kind once builds stopped needing it. That premise is false: **the check job runs as the same build account, and it still pulls its own container image from `fugaro-base`, unconditionally, for as long as the check job exists** — which is true for every repository with at least one workflow whose `rebuild.check` is not explicitly turned off (`check.tf`'s own comment: *"There is none when every workflow has `rebuild.check: off`"*), the common case. Retiring this grant was never actually possible without also retiring the check job's own dependency on the base image (option B above, unverified, not proposed here) — so there is nothing to condition, remove, or sequence a rollout around. The grant, and the registry it reads, are simply unaffected by this design.

## 5. Migration (item 4)

**Installations that already hold a mirrored copy.** The owner's two installations: `fugaro` (GCP project `fugaro-dev`, sandbox repository `edgeappinc/fugarosandbox`) and `belong` (EdgeWeb's and EdgeServer's installation). **This design makes no live change to either, and no live step of its implementation plan may touch `belong` without the owner's explicit, separate word.**

**What actually changes for an existing installation:** nothing about `base_images.base`'s shape, the check job, or the Terraform grant. What changes is purely **where Cloud Build's own `FUGARO_BASE` substitution comes from** — no longer `base_images.base`, now a fresh `basepin.Resolve` call at every submission. An existing installation's next build (via `fugaro image build`, `init --repo`, or `image refresh`) automatically uses the new, verified, `ghcr.io`-resolved value; nothing needs to be migrated, re-copied, or re-confirmed for this to take effect, beyond upgrading the CLI itself. The copy mechanism for the check job's own image keeps running exactly as before (strengthened by the new verification pre-step, which simply makes an existing copy fail loudly instead of succeeding blindly if the source were ever compromised).

**The strict-parser `*Since` gates, `managedVersion`/`isManaged`, and `internal/infra/tf/cover.go` need no code change for this migration at all** — none of them ever needed to recognize a new, `ghcr.io`-shaped `base_images.base` value, because that value never changes shape (§2). This is a direct, and large, simplification compared to earlier drafts of this document, which proposed changes to all three.

**Rollout order — a genuine precondition, not a detail (the fourth review round's B3 finding).** `docs/pending-workflows/images.yml` (the signing and `-pinned`-tag additions, plan Task 1) can only reach the real `.github/workflows/images.yml` by a human manually copying it in — Fugaro cannot push a commit touching `.github/workflows/**`. Plan Tasks 2–3 make **every Cloud Build submission** depend on a signed `-pinned` image existing; a release containing Tasks 2–3's code, tagged **before** a human has copied the workflow file in **and** a real tag push has run with it (producing the first signed image), would make every fresh build submission of that release hard-fail, with no signed image to find, until the *next* release. The precondition, stated explicitly: **the workflow file copy must land on `main`, and at least one real tag push must have run with it (producing a signed, `-pinned`-tagged image, verified live, plan Task 9 Check 38c), before the release that ships plan Tasks 2–3's code is tagged.** This can be the *same* release as the workflow copy (Task 1), as long as the copy lands on `main` before that release's own tag is cut — its own tag push would then produce the first signed image, which that same release's own fresh builds can immediately resolve and verify. It does **not** need to be an earlier, separate release, but it is a precondition the release process cannot enforce automatically and the owner must apply by hand (the same category of caveat `docs/pending-workflows/README.md` already carries for every staged workflow change).

## 6. What is deleted, what stays, for builds (item 5)

**Deleted:**

- Cloud Build's own reliance on `base_images.base` for its `FUGARO_BASE` substitution, at the three submission call sites (`internal/cli/image.go`, `init.go`, `image_refresh_steps.go`) — replaced by a fresh `basepin.Resolve` call at each.
- A GitHub-Release-asset design for the signature (an earlier draft of this document; §2 signs the pushed image directly in the registry instead).
- Two earlier drafts' own proposed changes to `base_images.base`'s shape, `managedVersion`/`isManaged`'s signature, `cover.go`'s second allowance, and the build account's Terraform grant — all withdrawn by this revision, because the premise they were built on (nothing reads `fugaro-base` for builds anymore, so nothing else does either) turned out to be incomplete: the check job does, unconditionally, forever.

**Stays, unchanged:**

- `internal/mirror`'s copy engine (`Plan`/`Copy`, the digest-verified HTTP client, the idle-guard, the anonymous-token flow), used for `history` exactly as today, and now also for the base image's copy for the check job's sake — with one new pre-step, a signature verification, feeding `mirror.Plan`'s existing `expect` parameter.
- `fugaro init --base`, `--expect-digest`, `--replace-image`, `managedVersion`/`isManaged` (today's two-parameter form, unchanged), `internal/infra/tf/cover.go` (unchanged), the Terraform `build_base` grant (unchanged) — the whole existing copy-and-record machinery for `base_images.base`, now preceded by verification.
- `verify-public` (release-time proof that the published images are anonymously readable).
- `--base-image` (bring-your-own). A custom base gets no signature verification at all, today or after this design — not a regression this design introduces.
- The base image's own content, the monthly bump, the size budget, the secret scan — none of this design's business.

## 8. Release placement

0.7.x, **after** the base-image hard cut lands (plan Tasks 17–21: the legacy kinds removed, `config.Bases == ["base"]`, release 0.7.0 itself). **Within this design's own release, the rollout-order precondition in §5 applies**: the workflow file copy (plan Task 1) must land on `main`, and its own tag push must have produced the first signed image (live-checked, Check 38c), before or in the same release that ships plan Tasks 2–3's code. It should not land in the same release as the base-image hard cut itself: that release is already large, and this design's own cosign-verification code is new, security-critical code that deserves its own, narrower review.

## 9. Decisions for the owner to rule on

1. **Go-side OCI-signature verification.** This repository has never verified a cosign signature in Go. Two paths: (i) vendor a Go sigstore-verification library (`github.com/sigstore/sigstore-go`'s `verify` package), **if its library API actually supports verifying an OCI-registry-attached signature cleanly — unverified at design time, the implementer confirms this first**; or (ii) shell out to the real `cosign verify` binary, falling back to a loud warning when it isn't on `PATH`. **Recommendation: (i), with (ii) as the fallback if sigstore-go's OCI-verification API proves awkward or incomplete.** The plan's Task 2 flags this for opus review.
2. **Option (B), an Artifact Registry remote repository over ghcr.io**, as a possible fast follow-up that could additionally retire the check job's own copy dependency, once verified — not blocking this design.
3. **The new, per-build-submission network dependency (§2)** — reaching `ghcr.io` and the sigstore trust infrastructure at every build, not only at an occasional `init`/`refresh`. Stated as a real, accepted cost; not mitigated further here.
4. **The nightly patch refresh vs. the pinned path (§2).** Resolved, not merely disclosed, by the `-pinned` tag. What the owner rules on is narrower: whether the extra published tag per release is an acceptable mechanism — **recommended, yes.**
5. **The rollout-order precondition (§5, §8).** The owner applies it by hand (copy the workflow file in, confirm a signed image exists, live-checked) before relying on any release containing plan Tasks 2–3's code.

## 10. Non-goals

- Retiring the history image's copy path, or the check job's own copy dependency (§1, §3; a candidate follow-up once Cloud Run's own direct-pull path, or an Artifact Registry remote repository, has a live check).
- Implementing an Artifact Registry remote-repository cache (option B).
- Signing anything beyond the base image's and history image's digests (no broader cosign rollout).
- Changing VPC-SC/egress-restricted projects' options beyond documenting that `--base-image` already covers them.
- Any live cloud or network action: this document and its plan are a design and a plan only.
