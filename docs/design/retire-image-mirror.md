
# Verifying the base image at copy time: a signed, pinned digest for `fugaro-base`

Status: design for review (2026-10-13), from the owner's spec and the owner's gate (2026-10-12, PASSED) and live Cloud Build test (project `fugaro-dev`, build `c503576c-51d9-4f96-b9e7-debae7d0df39`, `docker pull ghcr.io/dimipaun/fugaro-go:0.6.5` succeeded in 21s as the default compute service account, digest `sha256:ba06760c...`). That test is evidence a *future* change (§8, Option B) is plausible; this design does not act on it. Docs and a plan only: no product code in this change. Delivery: **after** the base-image hard cut (`docs/design/base-image.md` §10, plan Tasks 17–21), a 0.7.x release — see "Release placement" below.

**A note on current repository state, checked while writing this (2026-10-13):** `.github/workflows/images.yml` already carries the real `fugaro-base`/`publish-base` jobs — commit `356f7b1` ("images workflow: publish the base image"), already an ancestor of this branch, copied them in from `docs/pending-workflows/images.yml` and `git rm`'d the pending copy, which now holds only `README.md`. That commit is **not yet in a released tag** (the latest release, v0.6.6, predates it), so no release has actually run the job yet and `ghcr.io/dimipaun/fugaro-base` has not been published by a release — but the workflow mechanism itself is live in the real file, not staged. `docs/release.md` and `docs/base-image.md` still describe it as staged; that is a separate, pre-existing staleness in those docs, not something this design introduces or relies on.

**A note on this revision (fifth review round — a narrowing, not a patch).** A fourth review found that the daily image check job is itself a Cloud Run Job running directly FROM the base image (`check.tf`, `internal/infra/spec.go`'s `check()`), so `base_images.base` had to keep its Artifact-Registry shape for the check job regardless. That round's own course-correction, though, still had **Cloud Build** resolve and verify a `ghcr.io` digest fresh at every build submission while the check job kept reading the Artifact Registry copy — leaving two independently-maintained references for "what base was this built from." A fifth review found this breaks rebuild detection outright: `submitRebuild`, `refreshVerdict`, and `triggers()` all decide whether to rebuild by comparing `base_ref`/`base_images.base`-derived strings *exactly*, with no concept that a ghcr.io form and an Artifact-Registry form could name the same digest (§2 below). **This revision narrows the scope to "verify-then-copy": Cloud Build and the check job both keep reading the one `base_images.base` copy, unchanged, exactly as today.** What's new is narrower than either earlier draft: a cosign signature check inserted immediately before the *existing* copy step, and the copy's source switched from the plain release tag (which a nightly cron moves) to a nightly-immune `-pinned` tag. Retiring either consumer's dependency on the copy — what both earlier drafts of this document attempted — is deferred to a later, separate design (§8, Option B).

## 1. Problem

`internal/mirror`'s copy of `fugaro-base` into each installation's own Artifact Registry repository exists because, at M11 design time (`docs/design/m11-setup-and-skills.md` §3.3), three things were true: Cloud Build and Cloud Run were believed (UNVERIFIED) unable to read `ghcr.io`; the packages were private; and there was no single project-local registry repository that only people, never a build account, could write. Since then the packages are public (every release's `verify-public` job proves anonymous pulls), and the owner has directly confirmed, against a real Cloud Build in `fugaro-dev`, that `docker pull ghcr.io/dimipaun/fugaro-go:0.6.5` succeeds through the default compute service account in 21 seconds. That evidence makes a *future* design — retiring one or both consumers' dependency on the copy entirely — plausible (§8, Option B). It is not what this design does: Cloud Build and the daily check job (a Cloud Run Job that runs `fugaro image check --job` **FROM the base image itself**, `check.tf`'s own comment; its container's `image = var.repo.check.image`, set in `spec.go`'s `check()` directly from `lc.BaseImage(kind)`) both keep reading `base_images.base` exactly as today.

What the copy still costs, left as-is: it is no stronger a guarantee than "whatever the tag resolved to when the operator last ran `fugaro init --base`/`image refresh`" — `--expect-digest` pins a digest, but there was no out-of-band source for one until cosign signing of the images existed (the plan's follow-up **F1**, not built until now; `docs/design/base-image.md` §17 non-goals). A second, smaller problem, not previously documented: the copy's source today is the **plain** release tag (`fugaro-base:<v>`), which a nightly cron job re-pushes under a new, unsigned digest to pick up Debian security patches (`images.yml:7-9`). Once signing exists, verifying the plain tag's digest against a signature minted for an *earlier* digest the tag used to name would refuse — the copy needs a source the nightly never touches.

This design adds exactly two things to the existing, unchanged copy step (`fugaro init --base`/`image refresh`, the only place that writes `base_images.base`): a cosign signature check before the copy, and a source fixed to a nightly-immune tag so the signature actually matches what gets copied.

**Explicitly out of scope: the history image.** `fugaro init --firebase` copies `fugaro-history` into the installation's registry today because the history job's own Cloud Run Job resource (`deploy/terraform/gcp/modules/installation/history.tf`) names that copy's path as its `image:` — the same category of constraint as the check job's. `internal/mirror`'s copy engine (`Plan`/`Copy`, the digest-by-digest verified transfer) stays, used for `history` exactly as today: unsigned, unpinned, unverified, not this design's business (§6).

## 2. The trust model at copy time

**Today's control point, unchanged:** "only operators write `fugaro-base`; build accounts only read it" (`docs/gcp-setup.md` §"The base image"). A leaked build token can read the project's own copy but never replace it, so every repository's build (Cloud Build) and the check job (Cloud Run) are anchored to whatever the operator last confirmed and copied.

**What's added, narrowly: the copy step verifies a cryptographic signature before copying, and copies from a tag the nightly never moves.** Concretely:

- **Where the digest comes from.** `images.yml`'s `publish-base` job signs the pushed base image **by OCI digest** (`cosign sign`, not `cosign sign-blob`): right after pushing the multi-platform index, the **same job** runs `cosign sign --yes "ghcr.io/dimipaun/fugaro-base@sha256:<digest-just-pushed>"` keyless, attaching the signature as its own OCI artifact in the **same** ghcr.io repository — no GitHub Release asset, no cross-workflow coordination, no interaction with immutable releases (a container registry has no such concept). The signing step is gated to `github.event_name == 'push'` only (the version-job's own version-picking logic already treats `workflow_dispatch` identically to `schedule` — "the latest strict `vX.Y.Z` release tag," never the dispatched ref — so there is no legitimate manual-re-run-against-a-tag case this guard would wrongly skip). **Base only, not history** (§6): nothing ever verifies the history copy, so signing it would serve no purpose; an earlier draft of this document signed and tagged `fugaro-history` too, inconsistently with the plan's own scope — this revision aligns on base only.

- **The nightly's own run moves the plain tag; signing alone does not stop that, and a second, nightly-immune tag closes it.** `images.yml` also runs nightly and on `workflow_dispatch` (`images.yml:7-9`), rebuilding and re-pushing `fugaro-base:<v>` under the *latest* release's version tag with a **new, unsigned** digest, to pick up Debian security patches. `publish-base`'s tag-push step adds one more tag — `fugaro-base:<v>-pinned` — to the **same** push/create call that already makes `:<v>`/`:<major>`, conditioned on `github.event_name == 'push'` so the nightly's own run of that same call never creates or moves it.

- **The copy's source is the `-pinned` tag (or the verified digest), never the plain tag — fixing a bug an earlier draft of this document had.** That draft fed the resolved `-pinned` digest as `mirror.Plan`'s `expect` parameter (`internal/cli/init_images.go`, `s.read`, line 285: `m.Plan(ctx, it.src, it.dst, expect[it.key()])`), while leaving `it.src` built, unconditionally, from the **plain** tag (`init_images.go`'s `mk` closure, line 189: `mirror.ParseSource(allow, allow[0]+"/"+name+":"+ver)`). `mirror.Plan` (`mirror.go:169`) resolves `src.Tag` itself and refuses when it disagrees with `expect` (`ErrDigestMismatch`) — so from the first nightly after each release onward, the plain tag's digest would no longer be the one the `-pinned` tag (and the signature) names, and **every** copy attempt would refuse, not just a stale one. The fix: for the base kind specifically, the copy's source tag is `<ver>-pinned`, not `<ver>` — `mk`'s base-kind call site passes a distinct source tag from the destination tag it writes (the destination, `base_images.base`'s own value, keeps the plain `<ver>` shape it has today; only the *source* read for the copy changes). History's `mk` call is untouched (its source stays the plain `latest`/`<ver>` tag it uses today — no `-pinned` tag exists for history, §6).

- **Who calls `basepin.Resolve`, and when — the one call site, unlike an earlier draft's three.** Only the images stage's existing copy step (`fugaro init --base`, `fugaro image refresh`'s base step — both route through `internal/cli/init_images.go`'s `imagesStage`) calls `basepin.Resolve`, immediately before `mirror.Plan`, to compute the verified digest and switch the source tag. `basepin.Resolve` resolves what `ghcr.io/dimipaun/fugaro-base:<version>-pinned` currently names (the same anonymous, digest-verified registry read `internal/mirror` already does today for a tag, reused via a new, small `mirror.ResolveDigest` export, not reimplemented), verifies **that specific digest's** OCI-attached cosign signature against the `images.yml`-on-this-tag identity, and returns the clean `ghcr.io/dimipaun/fugaro-base:<version>@sha256:<hex>` (without the `-pinned` suffix). Nothing is recorded into `base_images.base` by `basepin.Resolve` itself — the existing copy step still writes `base_images.base` exactly as today, now from a verified source. **`fugaro image build`, `init --repo`'s first build, and `image refresh`'s own build step call nothing new at all: they keep reading `base_images.base` directly, exactly as today**, since Cloud Build's `FUGARO_BASE` substitution was never the thing this revision changes (§1 note).

  **Stated plainly: this depends on a new dependency, with no precedent anywhere in this repository** (today's only sigstore use is the shell-based `cosign verify-blob` a person runs by hand) — either `github.com/sigstore/sigstore-go` vendored read-only, if its library API supports OCI/registry-attached signature verification cleanly (**unverified at design time — the implementer confirms this first**), or shelling out to the real `cosign verify` binary, falling back loudly when absent. See "Decisions for the owner to rule on" below.

  **A real, new operational cost, stated plainly, but narrower than an earlier draft's: only `fugaro init --base`/`image refresh` now need network access beyond GCP, not every build.** The operator's own machine (or, for `fugaro image refresh --yes` from CI, that CI runner) needs to reach `ghcr.io` and the sigstore trust infrastructure (the TUF trusted root and Rekor, for keyless verification) at copy time — an occasional operation, not a per-build one.

- **Signing and publishing are not atomic.** `publish-base` pushes the image, then signs it, in the same job but as a separate command. If the sign step fails, the job fails (`set -eu`, no `|| true`), so the two are *coupled* by CI's own pass/fail gate even though they are not a single atomic registry transaction. A copy attempt finding no valid signature for the resolved digest refuses cleanly, naming the real reason, rather than falling back to an unverified copy.

- **`base_images.base`, and everything that reads it, is completely unchanged in shape and in every reader.** Still an Artifact-Registry-hosted reference (`<region>-docker.pkg.dev/<project>/fugaro-base/fugaro-base:<v>`), still written only by the existing `fugaro init --base`/`image refresh` copy step, still what Cloud Build's `FUGARO_BASE` substitution, the check job's container image, and `FUGARO_CHECK_SPEC`'s `base_images` map all read, exactly as today. In particular:
  - **`submitRebuild`** (`internal/cli/imagecheck.go:690-692`) reads `s.BaseImages[kind]` directly as the base to rebuild the check job from — unchanged.
  - **`refreshVerdict`** (`internal/cli/image_refresh_rules.go:51-66`) compares `rec.BaseRef == want` (line 55), where `want` is always an Artifact-Registry-shaped value computed from `base_images.base` — unchanged, and never fed anything else.
  - **`triggers()`** (`internal/imagecheck/triggers.go:34`) compares `in.BaseRef != rec.BaseRef` exactly — unchanged; both sides remain Artifact-Registry-shaped.
  
  There is only ever one shape of "what base was this built from" anywhere in the system, which is exactly why none of these needed, or get, any change under this narrowed design (unlike the two-representation problem an earlier draft introduced, §1 note).

- **Bring-your-own and development builds: nothing changes for them, because nothing in this revision touches their call sites at all.** `--base` (`internal/cli/image.go:200-208`: `o.base`, then `lc.BaseImage(kind)`, then `image.BaseRef(kind, Version)` as a further fallback) and `init.go`'s `buildImages` (`internal/cli/init.go:2413-2416`: `lc.BaseImage(kind)`, then the same `image.BaseRef` fallback) keep exactly today's behavior. `BaseRef` (`internal/image/local.go:61-67`) fires for a **release** build with neither `base_images.base` nor `--base` set, returning the bare, unsigned `ghcr.io/dimipaun/fugaro-<base>:<v>` ref — the version the fallback is named for. A **development** build (`fugaro version` printing `dev`) is the opposite case: `BaseRef` refuses outright (*"... is a development build with no published base image; pass --base ..."*), so a dev build must always name `--base` explicitly; there is no silent fallback for it. VPC-SC/egress-restricted projects keep using `--base-image` exactly as today. None of this is new or newly "unchanged" — it was never going to change, because the narrowed scope touches only the one copy step, not any build-submission call site.

- **What an attacker who controls ghcr.io's tag, or a fork of the repository, can and cannot do.** A signature check at copy time means moving the `v*`/`-pinned` tag in ghcr.io (or forking and publishing a lookalike under another owner) changes nothing for an installation that has already copied a verified image: the copy is a one-time, point-in-time action, not re-checked on every build. The live question is at the *next* copy: can an attacker make the operator's own machine verify a bad digest? That needs compromising the `images.yml` workflow's own identity — the thing cosign's certificate-identity check exists to catch, since a forged signature would need GitHub's own OIDC issuer to vouch for a workflow ref it never ran. This is strictly stronger than today's accepted risk (*"the trust anchor is the tag as the registry resolves it now … whoever can write `ghcr.io/dimipaun/fugaro-*:X.Y.Z` can make the user's cloud run their code"*, `internal/mirror/ref.go`'s doc comment) because today an attacker only needs to move the ghcr.io tag; after this change the next copy additionally needs to defeat the signature.

- **`internal/infra/tf/cover.go` needs no change at all.** `base_images.base` never changes shape under this revision (above), so `cover.go`'s **existing, unmodified** `inRegistry` check — every `google_cloud_run_v2_job`'s container image, and every `FUGARO_CHECK_SPEC` base-image entry, must already be inside the project's own registry — stays exactly as correct as it is today.

## 3. What verification buys, and the trade-off it carries

- **Gain:** the one copy both Cloud Build and the check job build/run from is now signature-verified at copy time, anchored to the `images.yml`-on-a-real-tag-push identity, rather than "whatever the registry's tag happened to resolve to when the operator last ran a copy."
- **Cost, stated plainly (not previously disclosed this directly, and corrected here — an earlier draft of this paragraph had the direction backwards).** `basepin.Resolve` always resolves the installed CLI's **own** version's `-pinned` tag (`releaseVersion()`, plan Task 3) — a tag the nightly never moves, by construction (§2). So a copy run at any time, for a given CLI version, reads the **same**, release-day, signed bytes every time: it does not refuse because the nightly has run since; it **succeeds**, copying those release-day bytes, even if the nightly has since rebuilt the plain tag with newer, unsigned ones. The actual cost is about freshness, not failure: before this design, a copy made between releases (after at least one nightly had already fired) would silently pick up the nightly's own newer, unsigned, patched bytes, because the copy's source was whatever the plain tag currently resolved to. After this design, that same copy — run with the same CLI, at the same point between releases — gets the **older**, release-day, signed bytes instead, because the source is now the tag the nightly can never move. A fresh install, or a kind newly added to an existing installation, set up between releases, is the concrete case this changes: today it gets the nightly's current patch level; after this design it gets the release's original bytes, verified. The only way to get newer, patched bytes into the copy is to upgrade to the CLI's **next** release (whose own tag push publishes and signs a new `-pinned` tag) and copy again. The trade a verified copy makes, explicitly: cryptographic assurance of provenance, in exchange for capping how fresh a copy can be at the release cadence instead of the nightly's own daily one. (A copy genuinely **refuses** only when no signed `-pinned` image exists yet for the installed CLI's own version at all — see §5's rollout precondition, a different situation from this one.)

## 4. The build accounts — unchanged, and here is why

**The build account's `fugaro-base` reader grant (`google_artifact_registry_repository_iam_member.build_base`, `deploy/terraform/gcp/modules/repo/build.tf:44-50`) stays exactly as it is today, with no Terraform change at all.** Both Cloud Build (every submission's `FUGARO_BASE` substitution) and the check job (its own container image, run as the same build account) read `fugaro-base` unconditionally, for as long as either exists for a repository — which is true for every repository with at least one workflow whose `rebuild.check` is not explicitly turned off, the common case. Nothing in this narrowed design removes a reader of `fugaro-base`, so there is nothing to condition, remove, or sequence a rollout around.

## 5. Migration

**Installations that already hold a mirrored copy.** The owner's two installations: `fugaro` (GCP project `fugaro-dev`, sandbox repository `edgeappinc/fugarosandbox`) and `belong` (EdgeWeb's and EdgeServer's installation). **This design makes no live change to either, and no live step of its implementation plan may touch `belong` without the owner's explicit, separate word.**

**What actually changes for an existing installation:** nothing about `base_images.base`'s shape, Cloud Build's reads of it, the check job, or the Terraform grant. What changes is purely **what the next `fugaro init --base`/`image refresh` run does before copying**: it resolves and verifies the `-pinned` tag's signature first, and copies from that tag/digest instead of the plain one. An installation that never runs that command again keeps its existing copy exactly as-is, verified or not — this design adds a gate to the copy action, not a background check of what's already there.

**The strict-parser `*Since` gates, `managedVersion`/`isManaged`, and `internal/infra/tf/cover.go` need no code change for this migration at all** — none of them ever needed to recognize a new, differently-shaped `base_images.base` value, because that value never changes shape.

**Rollout order — a genuine precondition, not a detail.** `docs/pending-workflows/images.yml` (the signing and `-pinned`-tag additions, plan Task 1) can only reach the real `.github/workflows/images.yml` by a human manually copying it in — Fugaro cannot push a commit touching `.github/workflows/**`. Once Task 3's code lands, **every** `fugaro init --base`/`image refresh` copy attempt depends on finding a signed `-pinned` image — not just a stale-after-nightly one, as an earlier draft's narrower framing had it, but literally any copy attempt, since there is nothing to verify before the first tag push with Task 1's workflow has run. The precondition, stated explicitly: **the workflow file copy must land on `main`, and at least one real tag push must have run with it (producing a signed, `-pinned`-tagged image, verified live, plan Task 7 Check 39c), before the release that ships plan Task 3's code is tagged.** This can be the *same* release as the workflow copy (Task 1), as long as the copy lands on `main` before that release's own tag is cut. It does **not** need to be an earlier, separate release, but it is a precondition the release process cannot enforce automatically and the owner must apply by hand.

## 6. What is deleted, what stays

**Deleted:**

- An earlier draft of this document's "Cloud Build resolves fresh at every submission" design, and its "the check job is unaffected"/"nothing needs to be migrated" claims — both false once rebuild-detection's exact-string comparisons are accounted for (§1 note, §2).
- A GitHub-Release-asset design for the signature (an even earlier draft; §2 signs the pushed image directly in the registry instead).
- Signing and `-pinned`-tagging `fugaro-history` (an earlier draft; §1, §2 — base only).
- The copy's source being the plain tag (a bug in an earlier draft of this revision itself, §2) — replaced by the `-pinned` tag.

**Stays, unchanged:**

- Cloud Build's `FUGARO_BASE` substitution, read from `base_images.base` at every submission, at all three call sites (`internal/cli/image.go`, `init.go`, `image_refresh_steps.go`) — no code change to any of them.
- `internal/mirror`'s copy engine (`Plan`/`Copy`, the digest-verified HTTP client, the idle-guard, the anonymous-token flow), used for `history` exactly as today, and for the base image's copy, now preceded by a signature verification feeding `mirror.Plan`'s existing `expect` parameter and a source-tag fix.
- `fugaro init --base`, `--expect-digest`, `--replace-image`, `managedVersion`/`isManaged` (today's two-parameter form, unchanged), `internal/infra/tf/cover.go` (unchanged), the Terraform `build_base` grant (unchanged).
- `verify-public` (release-time proof that the published images are anonymously readable).
- `--base-image` (bring-your-own). A custom base gets no signature verification at all, today or after this design — not a regression this design introduces.
- The base image's own content, the monthly bump, the size budget, the secret scan — none of this design's business.

## 8. Release placement, and what's deferred

0.7.x, **after** the base-image hard cut lands (plan Tasks 17–21: the legacy kinds removed, `config.Bases == ["base"]`, release 0.7.0 itself). **Within this design's own release, the rollout-order precondition in §5 applies**: the workflow file copy (plan Task 1) must land on `main`, and its own tag push must have produced the first signed image (live-checked, Check 39c), before or in the same release that ships plan Task 3's code.

**Deferred, an explicit later option, not proposed here: retiring Cloud Build's and/or the check job's dependency on the Artifact Registry copy (Option B, an Artifact Registry *remote* repository over ghcr.io).** The owner's 21-second pull test (above) suggests direct `ghcr.io` reads are plausible for Cloud Build; whether Artifact Registry's remote-repository feature supports an arbitrary third-party upstream such as `ghcr.io` at all is **UNVERIFIED** and would need its own live check (`gcloud artifacts repositories create <name> --repository-format=docker --mode=remote-repository --remote-docker-repo=... --project <gcp-project>` against a real `ghcr.io` host, not a dry run, and one `docker pull` through it). Retiring either consumer's dependency on the copy reopens the two-representation rebuild-detection problem this round's narrowing exists to avoid (§1 note) — any future design in this direction needs its own resolution for `submitRebuild`/`refreshVerdict`/`triggers()`, not just a verified pull path. Not designed here.

## 9. Decisions for the owner to rule on

1. **Go-side OCI-signature verification.** This repository has never verified a cosign signature in Go. Two paths: (i) vendor a Go sigstore-verification library (`github.com/sigstore/sigstore-go`'s `verify` package), **if its library API actually supports verifying an OCI-registry-attached signature cleanly — unverified at design time, the implementer confirms this first**; or (ii) shell out to the real `cosign verify` binary, falling back to a loud warning when it isn't on `PATH`. **Recommendation: (i), with (ii) as the fallback if sigstore-go's OCI-verification API proves awkward or incomplete.** The plan's Task 2 flags this for opus review.
2. **Option (B), an Artifact Registry remote repository over ghcr.io**, deferred to a later, separate design (§8) — not blocking this one.
3. **The new network dependency, at copy time only (§2)** — reaching `ghcr.io` and the sigstore trust infrastructure when `fugaro init --base`/`image refresh` runs, not at every build. Stated as a real, accepted cost; not mitigated further here.
4. **The nightly patch refresh vs. the pinned copy source (§2, §3).** Resolved, not merely disclosed, by the `-pinned` tag and the source fix. What the owner rules on is narrower: whether the extra published tag per release, and the lag until the next explicit copy picks up a newer release's patches, is an acceptable trade — **recommended, yes.**
5. **The rollout-order precondition (§5, §8).** The owner applies it by hand (copy the workflow file in, confirm a signed image exists, live-checked) before relying on any release containing plan Task 3's code.

## 10. Non-goals

- Retiring Cloud Build's or the check job's own dependency on the Artifact Registry copy (§1, §8; a candidate follow-up once Option B, or a resolution for rebuild detection's exact-string comparisons, has its own design and live check).
- Implementing an Artifact Registry remote-repository cache (option B).
- Signing anything beyond the base image's digest (history is explicitly out of scope, §1, §2, §6; no broader cosign rollout).
- Changing VPC-SC/egress-restricted projects' options beyond documenting that `--base-image` already covers them.
- Any live cloud or network action: this document and its plan are a design and a plan only.
