# Project-level secrets

Status: design, 2026-10-13, updated in two follow-up rounds the same day with the owner's ruling on provider-key availability, then finalized (§3a — **read this first**: an absent `allow_data_to`, or the explicit marker `["*"]`, now means "every repository" for both mounting and routing; no open question remains). Source: the owner's question, "Can we have project level API keys?", raised while moving the sandbox to a new project and re-entering `anthropic-api-key`, `openrouter-api-key` and `bitbucket-token` once per repository. Every fact below is cited to the code read for it; no cloud call was made (Section 7 lists what *would* need one, as owner-run live checks). Plan: [../plans/2026-10-13-project-secrets.md](../plans/2026-10-13-project-secrets.md); its decisions can be vetoed one by one. This PR is docs only.

## 1. What exists today (verified in the code)

A Fugaro project is one GCP project, one Firebase project, many repositories and many people (`docs/design/v1.md:27`, `docs/design/m9-budget-and-dashboard.md:453`; corrected citation — an earlier draft cited `docs/project-layer.md:1`, which is only that file's title and states no such thing). Two things already live at **project** scope, both operator-only, local-config:

- **`providers:`** (`internal/config/providers.go`), each with its own `allow_data_to: [owner/name, ...]` — the owner's single, centralized decision about which repositories may send code to a non-Anthropic model. `docs/multi-model.md` §2 is explicit that this list is the one place the decision lives.
- **`claude_accounts:`** (`internal/config/claude_accounts.go`, shipped 0.6.5, [named-oauth-tokens.md](named-oauth-tokens.md)), each with its own `allow_data_to`, the identical shape, for named Claude OAuth accounts.

**But storage of the value stays per repository for both.** `docs/multi-model.md` §2: "Then run `fugaro init --repo` in each repository that is listed" (`multi-model.md:41`), and §3: "From a checkout of the repository (any listed repository), paste or pipe the key" (`multi-model.md:49`), followed by a `fugaro secrets set openrouter-api-key` code block (`multi-model.md:52`) — corrected citation, not a verbatim quote as an earlier draft presented it: these are two sentences from two different sections, not one spliced quotation. The underlying claim (once per repository the provider lists) is unaffected. `named-oauth-tokens.md` §4a: "init --repo prints `fugaro secrets set claude-oauth-token-<name> --repo X`" — again, once per allowed repository. The reason is purely mechanical, not a policy choice: `gcp.SecretID(slug, logical)` (`internal/backend/gcp/names.go:143`) derives every secret's ID from the repository's own slug, and `internal/infra/spec.go:628` (`ws.SecretIDs[m.Logical] = gcp.SecretID(slug, m.Logical)`) is unconditional — **every logical secret name a workflow mounts gets its own Secret Manager secret, created by that one repository's Terraform module** (`deploy/terraform/gcp/modules/repo/secrets.tf`, `for_each = var.repo.secrets`, `prevent_destroy = true`), whether or not its definition (the provider, the account, or nothing at all for a reserved name) is centralized. `workflows.tf:14` feeds the workflow submodule's `var.secrets` exclusively from `google_secret_manager_secret.this`, the repo module's own resource — there is today no code path that lets a job mount a secret any other Terraform root created.

The four **reserved** secrets (`config.ReservedSecrets`, `internal/config/config.go:378`: `bitbucket-token`, `github-app-key`, `claude-oauth-token`, `anthropic-api-key`) have no centralized definition or allow-list at all — any repository may store its own, with no check, which is correct today (a repository's own key needs no permission from anyone). This is exactly why the owner hit the wall at these four names specifically.

What already exists at **project** (GCP-project) Terraform scope, for comparison: the `installation` module (`deploy/terraform/gcp/modules/installation/`, applied by plain `fugaro init`, no `--repo`) — the runs bucket (`bucket.tf`), the `launcher`/`operator`/`job_runner`/`build_submitter`/`tag_mover` custom roles and their project-level `google_project_iam_member` grants (`iam.tf`), the registries, the budget gateway's history account. Notably, the `fugaroLauncher` role already holds **project-wide** `secretmanager.secrets.list` and `secretmanager.versions.list` (`iam.tf:15-19`, comment: "metadata only: reading a value needs secretAccessor, which only the jobs and build accounts hold, per secret") — every launcher can already see the name of every secret in the project, repo-owned or not; only a value read is secret-scoped. This matters for §3: `fugaro secrets ls` needs no new IAM to list a project secret's metadata.

A secret's ID is a flat, project-level namespace in Secret Manager (`Projects.Secrets.Get`/`Create` take `projects/<p>/secrets/<id>`, `internal/backend/gcp/secrets.go:94-128`) — nothing about "which Terraform root created it" is visible to the API. A `secret_id = "some-string"` IAM grant (`google_secret_manager_secret_iam_member`, `deploy/terraform/gcp/modules/workflow/sa.tf:35-43`, `modules/repo/build.tf:13-20`) works identically whether that string names a secret the *same* Terraform state created or one a *different* root (the installation root) owns. This single fact is what makes the rest of this design a Go-and-IAM change, not a new Terraform resource type that crosses module boundaries.

`fugaro secrets set NAME` (`internal/cli/secrets.go:192`) already creates the secret itself if missing (`gcp.Secrets.Set`, `internal/backend/gcp/secrets.go:97-113`: a 404 on Get creates it with the given labels), with Terraform *adopting* a pre-existing, correctly-labelled secret rather than racing it (`secrets.tf`'s own comment: "they hold no value here... The adopted secrets are replicated automatically"). The value is always read from stdin only, never an argument, flag or environment variable (`secrets.go:278-305`, `readSecret` — corrected from `secrets.go:74-113`, which is `newSecretsSetCmd`'s own registration, not the stdin-reading function itself), and `secrets ls` has no `Access` call at all — only `List` (metadata).

## 2. The feature

Let a secret's value be stored **once per project** instead of once per repository, for the repositories the owner opts in, while a repository may still store its own value that overrides the project one.

## 3. Decision: the opt-in model (threat model)

**Must stay impossible, whatever is built:**
- a repository the owner has not allowed getting a project secret;
- a provider's key being *routed to* (a model pinned and run) by a repository outside that provider's own `allow_data_to`, **whenever a real, non-empty, non-`["*"]` list is actually written and excludes that repository** — `CheckProviderPolicy` (`providers.go:324`) is untouched **in code**, so this one case is unaffected by this design: a shared key never changes who may *pin a model* on it when the owner has actually named who may. **Corrected this round, MUST-FIX 1: this bullet is no longer true unconditionally.** §3a's **final** ruling means an absent or `["*"]` `allow_data_to` now opens routing too, not only the key's mount (an explicit empty list is refused outright, round 5's ruling — never a third meaning) — `CheckProviderPolicy`'s own call site is unedited, but its *behavior* changes the moment `AllowsData` itself does (Task 1), since it is the one function both read. The "must stay impossible" guarantee this bullet states is therefore scoped precisely to the listed case, not to every provider regardless of configuration — see §3a for the no-list/`["*"]` case's own, accepted consequence;
- `anthropic-api-key` or `claude-oauth-token` reaching a repository the owner did not opt in;
- a PR author's code reading more than a repo-level secret already lets it read today (the mount is still one env var in one job's environment; nothing changes about what the agent's own process can reach, SECURITY.md "What one run's agent can reach").

**Stated, not implied — a shared git credential's reach goes past the mount (plan follow-up 1, added 2026-10-14, and the same paragraph ships in SECURITY.md and the setup docs).** The bullet above is about the *mount*: one allowed repository's job or build reading the value, unchanged from before. What the *value* can then reach is a different, larger thing, and this design does not narrow it: a project-wide `bitbucket-token` is a workspace token, and a project-wide `github-app-key` is an App installation key that mints tokens for every repository the App is installed on, so code running in one allowed repository's job (a pull request's own code included) holds a credential that reaches repositories other than the one whose job it is. A repo-scoped token never did. That is the accepted cost of sharing a git credential at all; mount it project-wide only where that reach is the intent, and prefer a repo-scoped `fugaro secrets set bitbucket-token --repo owner/name` (or one App per repository) otherwise.

**Added 2026-10-27 (D462): the Bitbucket half of the paragraph above is now an option the operator may choose, not a mistake to avoid.** The owner ruled that an operator who holds one **workspace or project access token** may store it once for many repositories through `project_secrets.bitbucket-token.allow_data_to` — the allow-list decides only which jobs mount it, and the reach stated above is the accepted cost of opting in, with minimum scopes, an optional expiry and a rotation order documented in `docs/git-providers.md`. This reverses, for operators who opt in, the position the paragraph above and §6.3 of [project-centric.md](project-centric.md) were written to (`bitbucket-token` is a repository access token, so a project-wide copy hands every repository the first one's token). The default is unchanged and the allow-list is still the only way in: a repository access token serves one repository, `ProjectScopeByDefault("bitbucket-token")` stays false, and the pages an operator reads state the reach before they write the entry.

**Recommended: reuse what already exists, name-by-name, never widen it (option (c), an explicit allow-list per secret name).**

- **A provider's key or a named Claude account's token already has exactly the needed allow-list**: `providers.<name>.allow_data_to` / `claude_accounts.<name>.allow_data_to`. No new list is introduced for these — the *owner already made this decision once*, centrally, and duplicating it into a second list would only create two sources of truth that could drift. Storing the value with `--project-wide` (§4) makes that *existing* list also govern project-sharing; nothing about who may pin the model, or who may choose the account, changes. **For a provider's list specifically, "governs project-sharing" now has a different reading when the list is absent or `["*"]` than when it is a real, non-empty list — see §3a**, which the owner's final ruling adds: an absent or `["*"]` list means "available to every repository" for **both** the key's mount **and** `CheckProviderPolicy`'s routing check (corrected this round, MUST-FIX 1: an earlier draft of this sentence said routing "is untouched either way," which held only while §3a's gate question was still open — the owner's final ruling resolved it the other way; `claude_accounts`/`project_secrets` still read an absent *or explicit empty* list as "shared with nobody," unaffected by this ruling — an explicit empty list means something different, and is refused outright, for `providers:` only, round 5's own ruling).
- **The four reserved names have no existing per-name object to reuse**, so a new local-config block, parallel in shape to `providers:`/`claude_accounts:`:

  ```yaml
  # ~/.config/fugaro/projects/<name>.yaml (operator-only, never published — see §6)
  project_secrets:
    anthropic-api-key:  { allow_data_to: [acme/app, acme/sandbox] }
    bitbucket-token:    { allow_data_to: [myworkspace/*] }   # every repository of one workspace (D464 below)
    github-app-key:     { allow_data_to: [acme/app, acme/web] }
    claude-oauth-token: { allow_data_to: [acme/app] }   # the DEFAULT account only; a named one uses claude_accounts' own list
  ```

  `config.ProjectSecret{ AllowDataTo []string }`, `AllowsData`, `ValidateProjectSecrets`, `sortedKeys` — the exact shape of `config.ClaudeAccount` (`claude_accounts.go:63-73,117-143`), reusing `repoSlugRE`/`hasDotSegment`/`pluginwire.Printable`. **An entry may carry a segment wildcard (`myworkspace/*`) — see the D464 paragraph at the end of this section; `repoSlugRE` no longer describes an entry by itself.** **Default: no entry, nothing shared — true for `project_secrets:` itself in isolation, but not the whole story for an installation's Terraform plan (corrected this round, MUST-FIX 5): see §6's own note that an installation with ANY `providers:` entry at all, regardless of whether `project_secrets:` has anything in it, sees a new, empty project secret container the moment this feature's `installation` root code ships, since a provider's secret is added to `InstallationSpec.ProjectSecrets` unconditionally (§3a).** An installation with neither `project_secrets:` nor `providers:` configured at all is the only case that is genuinely byte-for-byte unchanged (§6).
- `project_secrets` may hold **only** a key of `config.ReservedSecrets` (4 names) — `ValidateProjectSecrets` refuses anything else. **An earlier draft of this bullet also proposed a `ValidateProjectSecrets` check refusing a key that collides with a provider's `.Secret` or a named claude account's derived secret; corrected after review, S1: both are dead code, structurally.** A provider's `.Secret` can never equal a `config.ReservedSecrets` key at all — `ValidateModelProviders` already refuses that unconditionally (`providers.go:127-129`, `case reservedSecretName(p.Secret): add(...)`) — so once `project_secrets`'s own keyspace is restricted to `ReservedSecrets`, no provider collision can ever reach it. A **named** claude account's derived secret (`claude-oauth-token-<name>`) is in the same position: no literal `ReservedSecrets` key has that shape, so it can never collide either. The one case worth a direct note, not a "collision" check: `config.ClaudeAccountBySecret(accounts, "claude-oauth-token")` **always** returns `(DefaultClaudeAccount, true)` for the bare, unsuffixed name — regardless of whether `accounts` has anything configured (`claude_accounts.go:91-93`) — so a naive collision check built on that function would incorrectly refuse `project_secrets.claude-oauth-token` itself, the exact, intended configuration this design's own §3 example shows as valid. `ValidateProjectSecrets` therefore does **not** call `ClaudeAccountBySecret` (or `ProviderBySecret`) at all: membership in `config.ReservedSecrets` is the only check needed, and it is both necessary and sufficient.
- **`workflows.*.secrets` (a workflow's own, `fugaro.yaml`-declared secrets) stay repo-only.** Recommended, no new mechanism: `layered-config.md`'s scope table already says why — "secrets belong to one repository's Secret Manager entries" (`layered-config.md:131`) — and a workflow secret is reviewed, per repository, in a pull request; two repositories happening to name a secret `db-password` is coincidence, never a shared credential. **An earlier draft proposed `SecretMounts` gaining a new refusal for a workflow secret colliding with a `project_secrets` name, mirroring its existing provider-collision check; corrected after review, S1: this one is also dead code, for a different reason than the `ValidateProjectSecrets` case above.** `config.Validate` (`internal/config/validate.go:204-209`) already, unconditionally, refuses *any* workflow secret named one of the 4 `ReservedSecrets` keys — the entire keyspace `project_secrets` is restricted to — regardless of whether `project_secrets` configures anything at all; a `fugaro.yaml` naming one never gets past `Validate` to reach `SecretMounts` in the first place. This differs from the EXISTING provider-collision check (`spec.go:540-542`), which is **not** redundant: a provider's `.Secret` is an operator-chosen, open-ended string `config.Validate` (which only ever sees the repository's own `fugaro.yaml`, never the local config) has no way to know about — only `SecretMounts`, which has both `w.Secrets` and `lc.Providers` in scope, can catch that one. No equivalent new check is added for `project_secrets`.
- **The project layer (`fugaro/project-layer.yaml`) is not the vehicle.** It is explicitly a non-secret file — its shape rules (`layered-config.md:213`) include "no credential-shaped value" among what its strict parser already refuses — and `agent.oauth_token` is already Repo/Override-only *in that table*, "it names a credential identity that only the repository's own, PR-reviewed `fugaro.yaml` may choose among names the local config (never the project layer) allow-lists" (`layered-config.md:123`). This design does not touch `fugaro.yaml` or the project layer at all: a repository's file and the project layer's `defaults:`/`profiles:` are completely unaware that a secret it mounts came from a project container instead of its own — exactly as a repository is unaware whether its `anthropic-api-key` secret came from `fugaro secrets set --repo` three months ago or was adopted from a bootstrap.

**D464, owner ruling 2026-10-27: an entry may use `*` inside a segment, and the rule stays narrower than the published policy's.** A project secret that serves a whole workspace — a Bitbucket workspace or project access token — needs one entry, not fifty: `project_secrets.bitbucket-token: { allow_data_to: [myworkspace/*] }`. The matcher is the policy's own segment matcher, shared rather than copied (`config.MatchSegment`, called by `projectpolicy.MatchRepo` and by `ProjectSecret.AllowsData`): `*` matches within a segment and never crosses `/`, matching is case-folded as every other `allow_data_to` entry already is, and `myworkspace/api-*` names a family. `myworkspace/a/b` (a nested repository path) is matched by no two-segment entry.

Three shapes are refused, all of them deliberately narrower than `allow_repos` (`projectpolicy.ValidPattern`), which admits a bare `*` and a wildcard provider segment and bounds a pattern by length instead:

- **the owner segment must be literal**, which refuses `*/*` and `*/api` with it, and the bare `*` (no owner at all) with them: one project secret is one owner's credential, and a wildcard owner would mount it in every workspace;
- **at most two `*` per entry** — a pattern with more is a typo rather than an intent, and the entry is what decides which repositories mount a value;
- **the entry still names exactly two segments** (`owner/name`), as it always has.

`ValidateProjectSecrets` reports each refusal at `project_secrets.<name>.allow_data_to` with the reason, and `AllowsData` refuses a wildcard owner by itself as well, so a config that somehow reached the matcher unvalidated mounts nothing rather than everything. **A wildcard means every current AND future repository it matches** — the entry is the only gate, and onboarding a repository that matches mounts the project copy on it with nothing else to do (SECURITY.md states this, and asks for minimum scopes for the same reason). No behaviour changes for an exact list.

**It reaches a published policy node in exactly one case, and is refused there.** The default Claude account's policy list is derived from `project_secrets.claude-oauth-token.allow_data_to` (`projectpolicy.DeriveAccounts`), and `accounts.<name>.allow_repos` is exact by D3 — the subset rule against a profile's own `allow_repos` is decided repository by repository — so `DeriveAccounts` refuses a wildcard entry with a message naming both blocks (`profiles.<name>.claude_accounts`, `accounts.default.allow_repos`), at publish and at `fugaro update`. A profile that names `default` therefore needs that one entry spelled repository by repository; the other three names' lists are never published. Nothing else about an entry leaves the operator's own machine: a job's environment holds a secret ID, never the list, and the mount is resolved to a concrete repository (`RepoSpec.ProjectSecretCandidates`, then `ProjectSecrets`) before any plan or apply, so an older runner reads nothing new and nothing degrades.

*Veto alternatives considered:*
- **(a) Per-repository opt-in via a `use_shared_secrets` list in each repo's local config entry.** Rejected: it inverts the existing, reviewed shape (allow-list *per secret name*, lived in `providers:`/`claude_accounts:` since 0.6.0/0.6.5) for no gain — the owner would still write exactly the same list of repository names, just keyed the other way, and now split across two kinds of block instead of one per-secret table `fugaro secrets ls`/`doctor` (§4) can show in one place.
- **(b) The project secret applies to every repository by default, with a per-repo opt-out.** Rejected outright for `project_secrets:` and `claude_accounts:` — both still fail the one non-negotiable rule the owner stated for them: "the DEFAULT must be safe (nothing shared until the owner says so)" — and would make onboarding a new, possibly-outside-contributor repository silently inherit every existing project key. **Reconciled with §3a's final ruling, not contradicted by it:** the owner's later, provider-specific decision — an absent `allow_data_to` (or an explicit `["*"]`) means every repository, for `providers:` only — is this same alternative (b), deliberately chosen for one pre-existing object the owner may already have configured list-less for other reasons (§3a), not a silent reversal of the rule above for `project_secrets:`/`claude_accounts:`, which this ruling never touches.

### 3a. Owner ruling on an absent `allow_data_to`, finalized this round (provider keys only)

**Final ruling (owner, 2026-10-13, superseding the open question a prior round of this design left unanswered): an ABSENT `allow_data_to` (the key not written at all) AND an explicit `allow_data_to: ["*"]` both mean "any repository of the project" — for BOTH the key's availability (mounting/storage, §4/§5) AND the data-policy gate (routing/pinning a model to it, `CheckProviderPolicy`).** Scope, unchanged from the first ruling: **project-level provider keys** (the secret of a model provider declared in the local config's `providers:` block, e.g. `openrouter-api-key`) — **not** `project_secrets:` (§3 above) and **not** `claude_accounts:`, both of which keep their existing, unchanged "empty/absent means nobody" meaning (confirmed below: `repoSlugRE` already refuses the literal `"*"`, so neither can accidentally inherit this ruling). `"*"` is the **only** wildcard for a provider's own list — an exact-match sentinel, never a glob (`acme/*` is not accepted there; a glob would need a different parser and a different kind of mistake to guard against) — matched case-insensitively, like every other `allow_data_to` entry. **D464 (owner ruling, 2026-10-27) adds a glob for `project_secrets` alone, and only inside a segment: see §3's own paragraph. A provider's list and a named account's list are unchanged by it.**

**RULING, round 5, corrected: an absent key and an EXPLICIT empty list (`allow_data_to: []`) are no longer treated identically.** A prior round of this ruling said the two "are not distinguished," reasoning that nothing else in this codebase tells a `nil` slice apart from a non-nil, zero-length one — but `gopkg.in/yaml.v3` (this codebase's YAML library) *does* preserve that distinction on decode (an absent key leaves the Go field `nil`; an explicit `[]` sets it to a non-nil, empty slice), so the two states are not actually indistinguishable, and conflating them left a real ambiguity unaddressed: an operator who writes `allow_data_to: []` by hand cannot tell, from the YAML alone, whether they meant "I haven't decided the list yet" or "I am revoking everyone, on purpose" — the exact ambiguity this design's own `["*"]` marker exists to resolve for the *absent* case. **Resolved: only an absent key or the explicit `["*"]` marker mean "any repository." An explicit, non-nil `allow_data_to: []` is refused outright by `ValidateModelProviders`**, with a message telling the operator to write `["*"]` for "any repository, on purpose" or remove the key entirely for "I haven't decided yet" — never silently accepted as either meaning.

**What changes — one function, not a second method and three call-site switches.** A prior round of this design added `ProviderKeyAvailable`, a second predicate read at three call sites so "available" (mounting) and "routable" (`CheckProviderPolicy`) could differ while the open question stood unanswered. **That mechanism is now deleted.** With the open question resolved — availability and routing are the identical question now — the fix collapses into `AllowsData` (`providers.go:62-64`) itself:

```go
// AllowsData reports whether repo (owner/name) may send code to p: true for
// EVERY repository when AllowDataTo is nil (the key is absent -- never
// written at all), OR contains the literal entry "*" (owner ruling,
// 2026-10-13, and its follow-ups, docs/design/project-secrets.md §3a).
// An explicit, non-nil, zero-length AllowDataTo ([] in the YAML) is refused
// by ValidateModelProviders before this method is ever called on valid
// config -- checking p.AllowDataTo == nil here, not len(...) == 0, is
// deliberate: it keeps this method correctly fail-closed (an empty-but-
// not-absent list matches nothing in the ContainsFunc below, same as
// before this ruling) even if that validation were ever bypassed.
// Otherwise, an exact, case-insensitive match against a listed repository,
// as before.
func (p ModelProvider) AllowsData(repo string) bool {
	if p.AllowDataTo == nil {
		return true
	}
	return slices.ContainsFunc(p.AllowDataTo, func(r string) bool { return r == "*" || strings.EqualFold(r, repo) })
}
```

`ValidateModelProviders` (`providers.go:147-151`, today's `for _, r := range p.AllowDataTo { if !repoSlugRE.MatchString(r) { ... } }`) accepts the literal entry `"*"` alongside a real repository slug — the owner's own explicit marker for "every repository, on purpose," which an earlier round of this design floated as a possible future mitigation and explicitly left as a non-goal (§9); it is built now, as part of this ruling, not deferred. **It also gains a new refusal, round 5's ruling: when `p.AllowDataTo != nil && len(p.AllowDataTo) == 0` (an explicit `[]`, not an absent key), refuse with a message naming the ambiguity directly** — e.g. `providers.<name>.allow_data_to: an explicit empty list is ambiguous: write ["*"] for any repository, or remove the key entirely` — checked once, before the per-entry `repoSlugRE` loop runs (an empty list has no entries to loop over anyway, so this is a separate, earlier check, not a change to that loop's own logic).

**Every existing caller of `AllowsData` inherits the new rule automatically, with zero call-site edits** — this is the simplification the deleted `ProviderKeyAvailable` indirection existed only to avoid needing while the question was open, and no longer needs now that it is closed: `CheckProviderPolicy` (`providers.go:334`, and its own two callers, `internal/runner/gateway.go:401` and `internal/cli/validate.go:180,182`), `runner.ProvidersEnv` (`internal/runner/providers.go:32`), `SecretMounts`'s per-provider mount condition (`spec.go:534`), and `secretsSet`'s repo-scope validation (`internal/cli/secrets.go:222`) **all already call `p.AllowsData(repo)` directly, today, unedited by this change** — once `AllowsData` itself is fixed, every one of them does the right thing without a single line of its own touched. `ModelProvider.ProviderKeyAvailable` and the three call-site switches the first draft of this ruling introduced are **deleted entirely**, not kept alongside the new rule: there is no longer a difference between "available" and "routable" for a no-list (or `["*"]`) provider for this second mechanism to answer differently, and keeping it anyway would only be a second place the two predicates could someday drift apart.

**`runner.ProvidersEnv` needs no change for a second, independent reason, not only "it already calls `AllowsData`": it already narrows every accepted provider's own `AllowDataTo` down to `[]string{repo}` before mounting it into the job's `FUGARO_MODEL_PROVIDERS` environment** (`providers.go:33-36`, `p.AllowDataTo = []string{repo}`, unchanged by this design) — so a provider configured with no list, or with `["*"]`, never leaks either spelling into any job's own environment; an older runner reading that variable sees an ordinary, single-repository list exactly as it always has, and needs no `*Since` gate (§7) to understand it.

**`claude_accounts:`/`project_secrets:` allow-lists are unchanged by this ruling**, in behavior and in code: neither inherits the no-list/`["*"]`-means-every-repository rule, which stays a provider's. `claude_accounts` keeps today's `repoSlugRE`-only validation (`claude_accounts.go:136-140`), which already refuses the literal string `"*"` — it is not a valid `owner/name` repository slug, by the same regex that refuses any other malformed entry — and a test pins that (`TestValidateClaudeAccountsRefusesWildcard`, plan Task 1), so a future change that extends `ValidateModelProviders`'s new `"*"` acceptance is never accidentally copied in by a careless shared-helper edit. **`project_secrets` is the one that moved, and only by D464 (owner ruling, 2026-10-27, §3): a segment wildcard is accepted there (`myworkspace/*`), a bare `"*"` and a wildcard owner segment are still refused, and `TestValidateProjectSecretsRefusesWildcard` pins that refusal.**

**The existing-job blast radius this ruling opens, not previously stated (B5(a)):** `Readiness`'s per-workflow loop sets `ws.DeployJob = true` **unconditionally** for a job that already exists (`readiness.go:121-122`, `case exists: ws.DeployJob = true`, regardless of `reasons`) — the `MissingSecret` gate (§5) only ever blocks a **brand-new** job from deploying for the first time; it was never designed to protect an *already-running* job from an update that adds a secret reference with no version anywhere, because before this feature, a workflow's set of mounted secrets never changed out from under an existing job on its own (only a `fugaro.yaml`/local-config edit the owner made on purpose could add one, and the owner would be adding a value for it in the same breath). This feature changes that: configuring a provider with no list, or the explicit `["*"]` marker (this round's extension), is enough, by itself, to add a brand-new mount to *every existing* `agent.auth: api-key` job's spec, the next time `fugaro init --repo` runs for it — with no guarantee a value exists anywhere yet. **The implementation must close this**, not merely document it — and the exact rule needs to be stated once, consistently, not left to drift between the design and the plan (an earlier round's drafts disagreed on this point, caught in review): **omission applies to *any* unresolvable secret_env entry on an existing job, not only one that is "new" (not already mounted before).** `Readiness` omits a secret_env entry with no version anywhere (repo or project) from `ws.SecretEnv`/`ws.SecretIDs` for *that* apply whenever the workflow's job already exists, reporting `Missing` as a diagnostic but leaving the job's other properties (image, env, resources) free to update — never setting `DeployJob` to `false` for an existing job over this (job.tf's `count = var.workflow.deploy_job ? 1 : 0` would **destroy** the job outright, a far worse outcome than a job merely missing one env var). Dropping "new" from the rule is deliberate, not a simplification for its own sake: `Existing` (`discover.go:511-514`) carries only the job's *current image*, nothing about which secrets it currently mounts, so "new vs already-mounted" cannot be told apart without a separate, larger discovery addition this design does not otherwise need — and the simpler rule is no less safe, since omitting an *already-mounted* secret this way plans an IAM-member **delete** for that logical name (`sa.tf`'s `for_each` shrinks), which `tf.Guard` refuses exactly like every other delete/replace this design introduces, requiring the identical owner `--allow-delete` confirmation before anything actually stops being mounted. **One more piece this omission must also do, not previously stated: recompute `ws.Env[runner.SecretEnvsVar]` (`FUGARO_SECRET_ENVS`, `spec.go:638`) from the *final*, post-omission `ws.SecretEnv`, not the value `SecretMounts` originally computed** — otherwise the runner's own redaction list would still name a variable the job's environment no longer has, a cosmetic but real inconsistency. This is new work for Task 3 (plan), not optional polish.

**The open question a prior round left here — whether the data-policy gate also opens on an absent list, and the "worst combination of the two decisions" a now-removed Option A/B table once analyzed (mounted everywhere, routable nowhere) — is now resolved, not merely defaulted (corrected this round, MUST-FIX 1: the table itself no longer exists in this document; an earlier draft of this sentence still pointed "below" at it).** The owner's final ruling (above) answers it directly: yes, the gate also opens, on the identical condition as the mount (absent, or `["*"]`). There is no longer a table of two options to weigh, because `AllowsData` is the single function both `SecretMounts`'s mount condition and `CheckProviderPolicy`'s routing check already call — fixing it once fixes both, and the two can no longer disagree with each other the way Option A's analysis worried about.

**The real-world consequence, stated plainly, once — the accepted cost of this decision, not a gap this design failed to close:** the moment the owner configures *any* provider with an absent or `["*"]` `allow_data_to`, every repository whose `agent.auth` is `api-key` — including one with outside contributors, or one the owner has simply not reviewed yet (a first run or a follow-up gives a fork's pull request no special handling at all, `SECURITY.md` §"Running Fugaro on repositories with external contributors") — can mount, route a model to, and therefore send its code to that provider. An operator who configures a provider and has simply not gotten around to writing `allow_data_to` yet (testing against one repository first, say) gets every repository's exposure by default, not a safe, inert placeholder — the opposite of today's fail-closed "absent = deny" for the one decision `docs/multi-model.md` §1 calls "a decision about the code, made once, by the owner." This is the owner's own final decision; the two mitigations a prior round of this design recommended for the open question (an explicit `["*"]` marker; coupling the mount to the gate) are no longer mitigations for a gap, since there is no in-between, mounted-but-unroutable state left for either one to fix — the marker is built (above), and "coupling the mount to the gate" is simply what `AllowsData` being the one function both paths call now guarantees by construction.

**MUST-FIX 2, stated once, plainly, here: the only way to revoke a provider's key from every repository, once it was ever configured with an absent/`["*"]` list, is to delete the provider's entry entirely** (`providers.<name>:` removed from the local config), **not to empty its `allow_data_to`.** Writing `allow_data_to: []` by hand to try to "revoke everyone" is now refused outright by `ValidateModelProviders` (round 5's ruling, above) — it was never a real revocation path in the first place, even before that refusal: `Installation()` (§6 step 3) and `SecretMounts` both key a provider's eligibility off whether the list is absent/`["*"]` vs. a real, non-empty list, never off "is the list literally empty right now" as a distinct third state — so emptying it would have silently done nothing a narrower list or a deleted entry does not already do, had it been allowed. Narrowing to a real, non-empty list revokes every repository *not* on it (§5's `ExtraSecrets`/N4 story, below) — revoking literally everyone needs the entry gone, not merely list-less.

`Readiness`'s existing `MissingSecret` gate (§5) is unaffected by any of this and still refuses to deploy a job whose secret has no version anywhere, repo or project — **no job ever runs with a dangling or absent credential**, same as before this ruling and its extension.

## 4. Decision: storage

**Where the container lives.** A new `secrets.tf` in the `installation` module (`deploy/terraform/gcp/modules/installation/`), parallel to the repo module's:

```hcl
# installation/secrets.tf (new)
resource "google_secret_manager_secret" "project" {
  for_each = var.project_secrets   # logical name -> secret ID, Go-derived

  project   = var.project
  secret_id = each.value
  labels = {
    fugaro         = "managed"
    fugaro_project = var.fugaro_project   # reuses the existing label (names.go:66), used today only on the runs bucket
    fugaro_secret  = each.key
  }
  replication { auto {} }
  lifecycle { prevent_destroy = true }
}
# operator grants: secretVersionAdder + viewer, the identical shape to
# deploy/terraform/gcp/modules/repo/secrets.tf's operator_secrets local.
```

`gcp.ProjectSecretID(fugaroProject, logical string) string`, the same `derive()` helper as `gcp.SecretID` (`names.go:101-112`), hashing `"project\x00" + fugaroProject + "\x00" + logical` — domain-separated (a nit fixed in review) so a Fugaro project name that happened to equal some repository's own slug could never make `ProjectSecretID` collide with `SecretID`'s hash of the identical (name, logical) pair.

**`var.project_secrets`'s key set must never shrink once a container exists (N3, a blocker — §6 has the full account).** It is tempting to read `for_each = var.project_secrets` and assume it behaves like `rs.Secrets` (§5: "unconditional, never pruned") just because both are Go-computed maps — but `rs.Secrets` earns that property because `workflow()` always includes every name a workflow *currently* mounts, and a scope move never removes a mount, only redirects it (§5). `var.project_secrets` has no equivalent guarantee on its own: it is populated purely from *current config eligibility* (§6), so a config edit that makes a name no longer eligible — emptying a list, deleting a provider/account — shrinks it directly, and `prevent_destroy` turns that into a hard `terraform plan` failure, not a `tf.Guard` prompt. The fix (§6): the same live-discovery pass that adopts a pre-existing project secret also **unions** every one it finds into the final map, so eligibility can only ever add a name, never remove one already created.

**Who writes a version.** `fugaro secrets set NAME --project-wide` (a new flag on the existing command, `internal/cli/secrets.go`), keeping every one of today's guarantees unmodified: stdin-only, hidden prompt on a terminal, never echoed, never an argument or flag value (§9.1's CLI contract). **Checked in this exact order, since `NAME` can match more than one branch's shape (S1: `claude-oauth-token`, the bare reserved name, is also what `ClaudeAccountBySecret` always matches to the implicit default account — the order below is what keeps that case unambiguous, not left to chance):**
1. `NAME` is a key of `config.ReservedSecrets` (checked first, so `claude-oauth-token` and the other three reserved names are always handled here, never falling through to point 2 below): refused unless `project_secrets[NAME]` exists with a non-empty `allow_data_to`.
2. Else, `NAME` is a provider's `.Secret`: accepted unconditionally, no condition on `allow_data_to` at all (§3a: an empty or absent list is now itself a valid, intentional "available to everyone" state for a provider, not a reason to refuse storage — it is the exact state this ruling exists to make useful).
3. Else, `NAME` is a **named** claude account's derived secret (`ClaudeAccountBySecret` resolves it to something other than `DefaultClaudeAccount` — point 1 already took the default case): refused unless that account's own `allow_data_to` is non-empty.
4. Else: refused — never a workflow's own secret, which has no project-wide meaning (§3).

**Who reads.** Never the operator (same as today: `secretVersionAdder`+`viewer`, no `Access` on the secret itself — `secrets.tf`'s own comment, unchanged in kind). Never the launcher/build-submitter roles beyond the metadata already granted project-wide (§1). Only a job's own service account, granted `secretAccessor` **per secret, per job**, exactly as today (`sa.tf:36-43`) — the grant is made from the *repository's own* Terraform root (the installation root does not, and should not, enumerate job service accounts: those are created per repository, in a separate state, §1's "flat namespace" fact is what makes this possible with no new resource type).

**Concretely, this needs one new, real Terraform-and-Go wire, not a no-op — corrected from an earlier draft of this design that wrongly assumed `internal/infra`'s Go code alone could redirect an existing, unmodified grant (caught in review; see §5 for the full mechanism and why the earlier draft's claim was wrong).** `sa.tf`'s `google_secret_manager_secret_iam_member.job` and `job.tf`'s `secret_key_ref` both already read `var.secrets[logical]` (a plain `map(string)`, logical name → secret ID) — the repo module's `workflows.tf` just has to feed that map a project ID for the names `Readiness` resolves to project scope (merged in, never replacing the repo-owned map `google_secret_manager_secret.this` already produces), and a NEW `repo.project_secrets` tfvars field is how that value actually reaches Terraform at all — **not** `ws.SecretIDs` (`internal/infra/spec.go:148`, tagged `json:"-"`, which `internal/infra/spec.go:762`'s `maps.Copy(rs.Secrets, ws.SecretIDs)` only ever folds into `rs.Secrets`/tfvars `repo.secrets`, itself consumed only by `secrets.tf`'s own `google_secret_manager_secret.this` resource, never by `workflows.tf`'s `module "workflow"` call, which reads the created resource's own `.secret_id` attribute back out — `workflows.tf:14`, unchanged by this design). **No new Terraform resource *type* for IAM, in either module** — the fix is entirely in what value `var.secrets`/`local.secrets` holds, never a new resource type. That value changing for an *existing* `google_secret_manager_secret_iam_member` instance is not free, though: `secret_id` forces replacement of that resource (a destroy-then-create of the same address, not an in-place update) — §6 spells out exactly which addresses this touches on a scope move and the exact `--allow-delete` command, since "no new resource type" does not mean "no replacement."

**`fugaro secrets ls`.** The existing per-repository command (`internal/cli/secrets.go:391-428`) gains a `SCOPE` column: `repo` (today, unchanged, for any secret with no project counterpart or no allow-listing), `project` (this repository mounts the project container), or `project, repo override stored` (a repo-level version exists and wins, §5) — names and version counts only, never a value, for both containers (the metadata call already needs no new IAM, §1). A new `fugaro secrets ls --project-wide` lists the project's own containers: name, versions, and the repositories currently allowed (from local config, not a live call) — an operator-only view in the same spirit as `fugaro accounts ls` (`named-oauth-tokens.md` §12).

**Versions and rotation.** Unchanged in kind: `fugaro secrets set NAME --project-wide` adds a new version the same way a repo-scoped `set` does; every allowed repository's job sees the new `latest` on its next execution (`secret_key_ref { version = "latest" }`, `job.tf:63-64` — unchanged).

**Precedence and deletion (repo overrides project; falls back once the override is gone).** See §5 — this is a live, Go-computed decision at `fugaro init --repo` apply time, not a Terraform-expressible conditional, and deliberately so: see §6's migration argument for why.

## 5. Decision: mounting and resolution

**At deploy time (`internal/infra`), nothing about `rs.Secrets` (the repo module's own, `prevent_destroy`'d containers) changes for a *scope move*.** `BuildRepoSpec`/`workflow()` still puts every logical name a workflow mounts into `rs.Secrets` **unconditionally**, exactly as today — this is the one choice that keeps a scope move from ever becoming a Terraform delete (§6).

**But `rs.Secrets` is still config-driven, and P2's "never pruned" claim has a second, independent hole §3a's own ruling opens (N4, a blocker, distinct from the installation-side N3 above): narrowing eligibility, not just a scope move, can shrink it too.** Once a provider has no list, or `["*"]` (§3a), `AllowsData`'s own widened behavior makes `SecretMounts`'s unedited mount condition eligible for **every** `agent.auth: api-key` repository — so `rs.Secrets["<provider-secret>"]` gets a repo-owned container created for every one of them, the first time each applies. If the owner later adds an explicit list that excludes some repository, `AllowsData` becomes false for it, `SecretMounts` stops including that provider's secret in its mounts at all, and `rs.Secrets` for **that one repository** loses the key — `prevent_destroy` on `google_secret_manager_secret.this["<provider-secret>"]` then fails that repository's next `fugaro init --repo` at `terraform plan`, the identical failure mode N3 describes for the installation module, just triggered by *narrowing* instead of a config change that removes an entry entirely. The job, meanwhile, keeps the key mounted (its spec update never ran) — revocation becomes impossible without `terraform state rm`, and live check 40g (below) cannot show what it claims to.

**The fix is the identical discover-then-union pattern as N3, applied to the repo module instead of the installation one.** `Existing` (`internal/infra/discover.go:511`, `Readiness`'s own live-state input, today carrying only `Jobs`/`DisplayNames`/`CheckJob`/`ProjectNumber`) gains `ExtraSecrets map[string]string` — every correctly-labelled secret `DiscoverRepo`'s new discovery step finds under `{LabelRepo: spec.Label}` (a `List` call) that is **not** already a key of `spec.Secrets` (i.e., one `SecretMounts`'s current, narrower config no longer computes, but that still physically exists and was once ours). `Readiness` unions `ex.ExtraSecrets` into `out.Secrets` before returning, so the **container** for such a name is kept in Terraform's `for_each` — only the **mount** is actually dropped (`SecretMounts`'s own, config-driven output no longer includes it, so `sa.tf`'s `google_secret_manager_secret_iam_member.job["<name>"]` *does* leave `values(var.workflow.secret_env)` and plans a `delete`, the same `tf.Guard`/`--allow-delete` pattern §6/B3 already established — a delete this time, not a replace, since the for_each key itself vanishes rather than changing value, but `tf.Guard` treats both identically). **Revocation of a no-list-widened provider is therefore possible, with an explicit `--allow-delete`, and never bricks the repository's own apply** — it was the missing union, not a missing `--allow-delete` story, that made 40g's claimed result unreachable.

**The mechanism, corrected (an earlier draft of this section described a redirect that was a no-op — caught in review, see §4's note):** `RepoSpec` gains **two** new fields, not one, because `Readiness` (`internal/infra/readiness.go`) never receives the local config — only the already-built `RepoSpec` and live GCP state (`func Readiness(ctx context.Context, c *Clients, spec RepoSpec, ex Existing) (RepoSpec, []Missing, error)`, no `*localcfg.Config` parameter) — so eligibility and resolution cannot be one step:

- **`RepoSpec.ProjectSecretCandidates map[string]string`** (`json:"-"`, never reaches tfvars): computed in `infra.Repo()`/`workflow()`, where the local config *is* in scope. One entry per logical name this repository is *eligible* to use project-wide — **uniform across all three name sources now, not split (corrected this round: `ProviderKeyAvailable` is deleted, §3a)** — `project_secrets`/`claude_accounts`-derived names via their own `AllowedForProjectSecret`/`AllowsData`, and a **provider's** `.Secret` via `ModelProvider.AllowsData` too, now that it itself absorbs the no-list/`["*"]`-means-any-repo rule — mapped to `gcp.ProjectSecretID(fugaroProject, name)`. This is candidate data only: being in this map says nothing about whether anything actually resolves there yet.
- **`RepoSpec.ProjectSecrets map[string]string`** (`json:"project_secrets"`, **this is the field that reaches tfvars**): computed by `Readiness`, which is the only place with both the candidates *and* a live Secret Manager connection. For each `logical` in `ProjectSecretCandidates` that a workflow (or the check job, below) also mounts: check (live) whether the repository's **own** container (`rs.Secrets[logical]`, already in the spec, via `hasEnabledVersion` — the same call `readiness.go:76-106` already makes for `DeployJob`'s missing-secret gate) has an enabled version.
  - **Yes → `ProjectSecrets` gets no entry for `logical`.** The repo-owned ID keeps being what `local.secrets[logical]` resolves to in Terraform (below) — unchanged from today. This *is* "repo overrides project," expressed as "nothing added to the output map," not a comparison Terraform itself has to make.
  - **No → `out.ProjectSecrets[logical] = ProjectSecretCandidates[logical]`.** If the project copy *also* has no version, `Missing{Kind: MissingSecret}` names the actual fix: `fugaro secrets set NAME --project-wide` instead of today's `--repo` message, and `logical` still gets no `ProjectSecrets` entry (there is nothing to resolve to yet).
  - **SF7, not previously stated, and corrected this round (small item 3): the original framing of this check as a defense against a squatting attacker was wrong.** `gcp.ProjectSecretID(fugaroProject, logical)` is deterministic and guessable from two public-ish inputs, but labels are not a trust boundary against a principal who can create secrets in the GCP project: `secretmanager.secrets.create` carries `secretmanager.secrets.update`-equivalent label-setting power too, so a principal able to pre-create a secret at that exact ID can set `{LabelManaged, LabelProject, LabelSecret}` on it just as correctly as `fugaro secrets set` itself would — the installation-side import then adopts it by those same labels, same as it would adopt a legitimate one. **The label check is therefore not a "squatting defense"**; it guards against **accidents and drift** — the repo-module's own equivalent check exists for the identical, narrower reason (`ForeignError`'s own doc comment, `discover.go:189-190`: "adopting it... would take over something that isn't ours," i.e. two different things sharing a name by coincidence, not an adversary forging marks). `hasEnabledVersion`'s version check above has no way to tell a correctly-labelled-but-wrong secret apart from the legitimate one, and this is worth closing for the same accident/drift reason `DiscoverRepo`'s per-secret loop (`discover.go:547-566`, the one this design's N4 extends for `ExtraSecrets`) already closes it for repo-scoped secrets (`hasMarks(s.Labels, want)`, refusing with a `*ForeignError` otherwise) — not because it stops an attacker, but because it is the same consistency check this design already makes everywhere else it reads a secret by a derived ID. **Fix (unchanged in mechanism, only in stated purpose):** extend `DiscoverRepo`'s new discovery step (N4, above) to also `Get` each `spec.ProjectSecretCandidates[logical]` ID and check it carries `{LabelManaged, LabelProject: <the installation's Fugaro project name>, LabelSecret: logical}` before adding it to a new `Existing.ProjectSecretsOK map[string]bool`; a secret that exists at that ID but fails the check is a hard refusal (`d.foreign(...)`, the same `*ForeignError` path as every other accidental-collision case this design finds, not a silent `Missing`-downgrade); one that doesn't exist at all is simply not in the map yet, same as today, no refusal. `Readiness` then only resolves `ProjectSecretCandidates[logical]` into `out.ProjectSecrets[logical]` when `ex.ProjectSecretsOK[logical]` is true, exactly mirroring how it already trusts `ex.Jobs`/`ex.ExtraSecrets` rather than re-deriving ownership itself.
- **Terraform**: `modules/repo/variables.tf` gains `repo.project_secrets map(string)` (already-existing secret IDs this module never creates a resource for). `modules/repo/workflows.tf:14`'s inline `secrets = { for k, s in google_secret_manager_secret.this : k => s.secret_id }` becomes a `locals` block, `local.secrets = merge({ for k, s in google_secret_manager_secret.this : k => s.secret_id }, var.repo.project_secrets)`, fed to `module "workflow"`'s `secrets = local.secrets` (job.tf and sa.tf are **unmodified**: both already read `var.secrets[logical]`, which now simply holds a different value for the names `Readiness` resolved). Because `ProjectSecrets` holds *only* the names that actually resolved to project scope (never "every eligible name" — the distinction the plan's P7/Task 3 must get right, see the review's own precedence-inversion finding, addressed next), a plain `merge()` is correct with no conditional Terraform logic needed: whichever map lists a key last would win, but only the resolved names are ever present in the second map at all.
- **This decision is re-evaluated only on the next `fugaro init --repo`**, the same way `DeployJob` and the job's image are (`readiness.go:55-72`'s own doc comment). Storing a repo override, or deleting its last version, takes effect at the operator's next apply — not at the next run, since Cloud Run Jobs mount secrets at the job, not the execution (the same fact [named-oauth-tokens.md](named-oauth-tokens.md) §1 already established for Claude accounts). This is stated as a limitation, not hidden: `fugaro doctor` warns when a repository's resolved scope (what `Readiness` would compute now) differs from what its deployed job currently mounts, the same shape `doctor` already uses for the project layer — "flags a run that launched without it or on an older generation" (`internal/cli/doctor.go:148-149`).

**Named Claude accounts.** Yes, project-level, with no special-casing: `claude-oauth-token-<name>` is just another `config.ReservedSecrets`-shaped name once `ClaudeAccountBySecret` resolves it, and the resolution above is keyed on the logical secret string, not on which object (`ReservedSecrets`, a provider, or a claude account) defined it.

**Workflow `secrets:`** stay repo-only (§3); no resolution logic applies to them.

**Build-time secrets (Cloud Build `--secret id=…,env=…`), and the daily check job — TWO places bypass `var.secrets`, not one (an earlier draft of this paragraph missed the second; caught in review, B4).** The git credential (`bitbucket-token`/`github-app-key`) is a `BuildSecret`, and `build.tf`'s `google_secret_manager_secret_iam_member.build` (`modules/repo/build.tf:13-20`) indexes `google_secret_manager_secret.this[each.value].secret_id` directly, the repo module's own resource, unlike `sa.tf`'s job grant. **`check.tf:71` does the identical thing, for the identical reason, and was missed in the design's first draft**: the daily image check's Cloud Run job sets its `secret_key_ref.secret` straight to `google_secret_manager_secret.this[env.value].secret_id` (`modules/repo/check.tf:65-76`), never through `var.secrets` either — and `internal/infra/readiness.go`'s own check-job gate (`readiness.go:139-151`) checks only the repo ID today, the same gap `SecretMounts`/`Readiness` had for workflows before this design's core fix (§5 above). **Effect if left unfixed:** a project-shared `bitbucket-token`/`github-app-key` with no repo-level version would leave the check job's spec pointing at a secret with zero versions — the exact "empty container" failure mode B5(a) describes for an existing job, just for the check job specifically.

**The fix is one Terraform change, shared by both sites, not two separate ones:** hoist `workflows.tf:14`'s inline map into a `locals.secrets` block in the repo module (§5's mechanism above already requires this for `workflows.tf` itself), and point **both** `build.tf:17` and `check.tf:71` at `local.secrets[each.value]`/`local.secrets[env.value]` instead of indexing `google_secret_manager_secret.this` directly. On the Go side, `Readiness`'s check-job branch (`readiness.go:139-151`) needs the identical repo-wins-else-project resolution as its per-workflow loop, writing into the same `RepoSpec.ProjectSecrets` output map (§5) — not a second map, since `local.secrets` is one, repo-wide Terraform local that every one of job.tf/sa.tf/build.tf/check.tf reads from.

**Flagged for Terraform-sensitive review (§8):** granting a *build* service account `secretAccessor` on a secret a *different* Terraform root created needs the same scrutiny as the job grant, with an explicit test that a build account never gets broader access than the one secret its own repository currently resolves to — and the check job, which runs as that same build account (`check.tf:42`), needs no separate grant of its own: `build.tf`'s existing `build_secrets` list already includes the git credential, so the same, single IAM-member replacement (B3) covers both the build step's and the check job's access.

**`fugaro doctor`/`diagnose`.** Two offline-ish, per-repository checks, in the existing `doctorCheck` family (`internal/cli/doctor.go`), mirroring named-oauth-tokens' two (`named-oauth-tokens.md` §6f): (1) a `project_secrets`/provider/account name with an allowed repository has no version anywhere reachable (neither its own nor the project's) — red; (2) a repository's last deployed job resolved a different scope than `Readiness` would compute today (the apply-time-only lag above) — a warning, not a failure. Both print the name and the scope, never a value.

**A third, project-wide check, not per-repository, for revocation lag (S3) — not previously in this design.** Removing a repository from an `allow_data_to` list, or deleting a provider/account entirely, does **not** retroactively revoke anything: the repository's job service account keeps its `secretAccessor` grant on the project secret, and the job keeps mounting it, until an operator re-runs `fugaro init --repo` for that one repository — and nothing today notices this lag, because it crosses a boundary no existing check looks across. `noteExtraAccessors` (`internal/infra/discover.go:813`) already does the *per-repository* version of this idea — it compares a repo-scoped secret's live IAM policy against what that one repository's own spec plans, so it can only ever see one repository's bindings at a time, never whether a binding on a *project* secret belongs to a repository the current config no longer allows. **A new check in plain `fugaro doctor`'s own output (corrected this round, MUST-FIX 4: an earlier draft of this sentence invented a `--project-wide` flag the plan never adds — Task 7's own `project-secret-extra-accessors` check is a normal doctor check, no flag) is needed**: for each project secret, list its live `secretAccessor` bindings (member service accounts), and for each one, resolve which repository it belongs to and check whether that repository is *currently* allowed (the same `AllowedForProjectSecret`/`AllowsData` check `Readiness` itself uses — uniform across all three name sources now that `ModelProvider.AllowsData` itself absorbs the no-list/`["*"]` rule, §3a; `ProviderKeyAvailable` no longer exists to name separately) — flagging any accessor that is not. **Resolving a member back to a repository cannot be a lookup: `gcp.ServiceAccountID` is a one-way hash (corrected this round, MUST-FIX 4 — an earlier draft said the SA name "encodes the repo slug," implying it could be read back out; it cannot), so this must be computed forward instead** — for every onboarded repository (`localcfg.Config.Repos`, which already enumerates all of them) and every one of its workflows, `gcp.ServiceAccountID(slug, workflow)` into a precomputed set to match each live member against. **Named-account job variants need their own entries in that set, not only the bare repository/workflow pairs**: a workflow with allowed `claude_accounts` gets one job (and one service account) *per account variant* (`gcp.WorkflowVariant(workflow, account)` as the "workflow" argument to `gcp.ServiceAccountID`, not the bare workflow name) — omitting the variants would leave every named account's own accessor unmatched against the precomputed set, either missing a real revocation-lag finding or misreporting one. This needs the local config's `repos:` map and, per repository, which claude accounts its own `fugaro.yaml`/local config currently allow — something no single repository's own `fugaro init --repo` run has reason to compute today. Names and scope only, metadata-level IAM-policy reads (`GetIamPolicy`), never a value.

**SF9, decided: this check stays a warning, not red — but names the fix explicitly, since "a warning nobody acts on" is the actual failure mode worth closing, not the severity level.** Red would be wrong on its own terms: the lag this check flags is the *expected*, transient state between an owner narrowing an `allow_data_to` list and the affected repository's next `fugaro init --repo` — exactly the same "not yet caught up" shape `doctor`'s own existing project-layer check already treats as a warning (`doctor.go:148-149`, quoted above), not a failure. Turning it red would make `doctor` fail for every installation mid-revocation, for however long that repository takes to get its own apply scheduled — a worse false-positive rate than the lag it is trying to surface. **What SF9 actually caught is a real gap: the warning's own message, as drafted, named the stale accessor but not the fix** — an operator reading it would not necessarily connect "repository X still has access" to "re-run `fugaro init --repo` for X, with `--allow-delete google_secret_manager_secret_iam_member.job[\"<secret>\"]` once `tf.Guard` names that address," since nothing else in this design states that connection in one place. **Fixed in the warning's own text, not in `tf.Guard`:** `tf.Guard`'s refusal message (`internal/infra/tf/guard.go`) stays feature-agnostic on purpose — it is the one safety primitive every root and every feature in this codebase shares, and hard-coding "revocation" into it would coincidentally help this one case while making its message less accurate for the many other reasons a delete/replace can appear. The doctor warning is the right, and only, place that already knows this is a revocation: its message is specified to end with the literal next step — "re-run `fugaro init --repo` for `<repo>` and pass `--allow-delete` for the address the plan's refusal names" — so the operator reading the warning needs no cross-referencing to act on it.

**Five places read a secret ID and were missed entirely by the first two drafts of this design (N1, a blocker; a fifth found this round, small item 5): image builds, the daily check's own rebuild, and two `doctor`/`init` checks all still name the REPO-scoped ID, unconditionally, with no awareness that `Readiness` may have resolved that logical name to the project copy instead.** Verified precisely:

This value becomes Cloud Build's `AvailableSecrets[0].VersionName` (`internal/backend/gcp/build.go:166-167`: `version(s.GitSecretID)`, a `projects/<p>/secrets/<id>/versions/latest` reference).
- `cloudBuildSpec` is called from **three** places (corrected this round, a nit: an earlier draft said "two," missing `runImageBuildCloud`), with two different fixes needed depending on which machine runs them: `submitAndWait` (`internal/cli/init.go`, `fugaro init`'s first build) and `runImageBuildCloud` (`internal/cli/image.go:156`, calling `cloudBuildSpec` at `image.go:232`, `fugaro image build`'s/`image refresh`'s own command handler) both run on the **operator's own machine**, with live GCP access and the local config both in scope — but they are not the identical case either, see the BLOCKING fix below; `submitRebuild` (`internal/cli/imagecheck.go:710`) runs **inside the deployed check job's own container**, which builds its own fresh `RepoSpec` by calling `infra.Repo()` directly (`imagecheck.go:484,765,788`) — **never `infra.Readiness`** — so it has no way to know what `Readiness` resolved at the last apply, even in principle, without a live Secret Manager connection of its own (which the check job is not designed to need, exactly the same constraint that shaped §5's `RepoSpec.ProjectSecrets` two-field split).
- `internal/cli/doctor.go:401`'s GitHub App health check reads `gcp.SecretID(slug, "github-app-key")` directly, hard-coded to the repo ID, and then **reads the value** (`appKeySource{Read: true, ...}`) to verify the App's permissions — a project-shared `github-app-key` with no repo-level version would make this check read a secret with no version at all, not the real key.
- **A fifth, not previously stated (small item 5): `internal/cli/init.go:2114`'s `appPreCheck` — `fugaro init --repo`'s own GitHub App pre-check, a distinct call site from `doctor.go:401`'s — builds `appKeySource{SecretID: spec.Secrets["github-app-key"], ...}`, the identical hard-coded repo ID, unconditionally.** Needs the identical fix as `doctor.go`'s. **Separately, and not a secret-ID-resolution bug at all: `checkGitHubApp`'s own "Fix" messages (`internal/cli/githubapp.go:134,143`) unconditionally suggest `fugaro secrets set github-app-key --repo <repo>` as the remediation — and a plain `fugaro secrets set NAME` with no `--project-wide` already defaults to repo scope (`resolveSecretRepo(cmd, env, "")`, the checkout's own origin). If `github-app-key` is currently resolving from the project copy for this repository, following either suggested command creates a brand-new repo-scoped override that then wins forever (§5, "repo overrides project" has no override-the-override) — a silent precedence flip, the exact footgun N2 closes for the secrets stage's own prompt, reachable here instead through a doctor/init-time Fix message.** Both Fix strings must warn explicitly when this repository is currently eligible for the project copy (`infra.ProjectSecretCandidate`, Task 2's helper — `checkGitHubApp` already has `lc` in scope to call it), naming `--project-wide` as the alternative, rather than silently suggesting the one command that would undo the sharing.

**The fix, in two parts, matching the operator-machine/in-job split above (both are new work, not covered by Tasks 1-7):**
1. **`cloudBuildSpec`'s signature changes to take `gitSecretID string` as a parameter**, computed by its two callers, never internally from `rs.Secrets[ws.GitSecret]`. A new, small, reusable helper — `internal/infra.ResolveSecretID(ctx, c *Clients, repoID, projectID string) (id string, err error)`, extracted from (and then reused by) `Readiness`'s own per-logical-name precedence check (§5), so the two never drift — is what `submitAndWait` (operator's machine, live access) and `doctor.go`'s GitHub App check (same machine) call before building their own request, passing the repository's own ID and (if a candidate exists) the project ID for the logical name in question.
2. **For the in-job path**, there is no live call to make from inside the check job (by design, §5): the resolved ID must already be sitting in the job's own environment when it starts, the same way every other piece of apply-time-resolved data already reaches it. `CheckJobSpec` (`internal/infra/spec.go:183`, the struct `FUGARO_CHECK_SPEC`'s JSON already carries, `CheckSpecEnv`/`spec.go:850`) gains a `GitSecretID string` field; `Readiness`'s check-job branch (§5) computes it the same way it already resolves `out.Check.SecretEnv`'s precedence, and **re-marshals** `out.Check.Env[CheckSpecEnv]` with the resolved value before returning (the one new piece of logic `Readiness` did not previously need, since nothing else it resolves is also embedded as JSON inside another env var). `submitRebuild`/`imagecheck.go`'s own `rs, err := infra.Repo(...)` call (which still only ever produces the repo ID, unchanged) is **not** what feeds `cloudBuildSpec` any more for this field: the check job reads `s.GitSecretID` (`s infra.CheckJobSpec`, already a parameter `submitRebuild` has) instead.

**BLOCKING (B1), corrected this round — a live resolve at build time can itself disagree with the apply-time choice the build account's own IAM grant was made for, but the fix drafted in the previous round (comparing against a *deployed job's* `secret_key_ref`) cannot be built as written: it breaks the most common case, a first build.** `fugaro init`'s own flow is `planRepo` (discovers, resolves via `Readiness` into a local `ready`, writes tfvars, **applies**, and returns only `missing` — `ready` itself never leaves the function) followed, once `planRepo` returns, by `offerBuilds`/`buildFirst`/`submitAndWait`, called with the **original**, pre-`Readiness` `spec` (`infra.Repo()`'s own output, never `ready`). For a workflow whose job does **not exist yet** — exactly the first-build case `buildFirst` exists for — reading "the deployed job's `secret_key_ref`" finds no job at all (`(*discovery).job`/`Jobs.Get` returns nil on a 404, `discover.go:723-732`): the previous draft's comparison would have nothing to compare against on every single first build, not only a rare drift window. `fugaro image build --repo X --workflow W` run for that same new workflow has the identical problem, independent of `init` entirely.

**Fix, in two parts, because the two call shapes are not the same case:**
1. **Inside `init`'s own flow, no live comparison is needed at all — thread the apply-time `ready` out of `planRepo`, don't discard it.** `planRepo`'s own apply (`t.Apply`) already made the grant match `ready`'s choice by the time it returns; the caller just needs that value. `planRepo`'s signature gains a return (or `r.initRun` gains a field `planRepo` sets, the implementer's choice) for the resolved `RepoSpec`, and `buildFirst`'s own call to `submitAndWait` uses `ready.ProjectSecrets[ws.GitSecret]` if present, else `ready.Secrets[ws.GitSecret]` (today's repo ID) — the exact precedence `Readiness` already decided, read back rather than re-derived, with **no live Secret Manager read of its own** for this purpose.
2. **For a standalone invocation with no just-completed apply to read back** (`fugaro image build --repo X --workflow W`/`fugaro image refresh`, run independently, and `doctor`'s GitHub App check) — the thing that actually decides whether the build succeeds is not a deployed job at all, it is **the build account's own IAM grant on the secret**. For each candidate ID (the repo-scoped one, and the project-scoped one when a candidate exists), `Get` it first and skip it (not an error) on a 404/absent response **— corrected this round, should-fix: an earlier draft called the `GetIamPolicy` read "the identical call `DiscoverRepo`'s own `secretPolicies` population already makes," which glossed over that `DiscoverRepo`'s own loop only ever calls `GetIamPolicy` *after* a successful `Get` (`discover.go:555-568`); a project candidate nobody has stored `--project-wide` yet does not exist as a secret at all, and `GetIamPolicy` on it 404s the same way `Get` does** — then read `GetIamPolicy` on whichever ones exist and find which one's bindings grant `roles/secretmanager.secretAccessor` to `rs.BuildServiceAccountEmail` (`spec.go:245`): that is the **granted** choice, independent of whether any job happens to be deployed yet. Resolve live via `ResolveSecretID`, and compare: **three outcomes, not two (corrected this round, should-fix: an earlier draft's "agreement proceeds, disagreement refuses" had no third case, so a repository that has never had anything granted yet — a genuinely first build — would have been wrongly refused)** — agreement with the granted ID proceeds; **no existing ID is granted at all (the pre-first-apply state: nothing has ever been applied for this repository, so there is nothing yet to disagree with) proceeds too, using the live-resolved ID**, the identical treatment as agreement; only an actual, non-empty mismatch refuses (not a bare error — name both IDs and tell the operator plainly to run `fugaro init --repo` first, so the grant catches up before anything calls Cloud Build with a secret ID the build account cannot yet read). This is the one piece of the original BLOCKING fix that survives unchanged: compare before trusting a live resolve, just against the real ground truth (the grant), not a job that may not exist yet.

**This is additive to Tasks 3 (`Readiness`) and 5 (Terraform) but large and separable enough to need its own task — Task 8 in the plan, inserted before the docs task**, since it touches files (`internal/cli/image.go`, `internal/backend/gcp/build.go`, `internal/cli/imagecheck.go`, `internal/cli/doctor.go`) none of Tasks 1-7 otherwise touch.

## 6. Decision: migration (no backward compatibility needed before release)

Two installs exist today: `dimipaun/fugaro` on project `fugaro`, and the sandbox. **Never `belong`** (the live-checklist's own installation, retired — `docs/gcp-live-checklist.md`'s "Numbering ruling" and its results sections name it; it is explicitly off-limits for any live step, repeated in this task's own instructions).

**The *secret container* is never destroyed, by construction — but "0 destroys" for the whole plan is false, and the earlier draft of this section was wrong to say so (caught in review, B3).** Because `rs.Secrets` keeps including a logical name unconditionally even after it becomes project-shared (§5), Terraform's `for_each` over `google_secret_manager_secret.this` **never shrinks** as a side effect of this feature: nothing a plan produces is ever a `delete` of the repo-owned **secret resource itself**, so `prevent_destroy` on `google_secret_manager_secret.this` is never tripped by an `init --repo` that follows a `project_secrets`/`allow_data_to` edit. This was an explicit, considered trade-off against the alternative (drop the logical name from `rs.Secrets` once it is project-shared, which plans a `delete` that `prevent_destroy` then refuses outright — not merely a `tf.Guard` refusal requiring `--allow-delete`, but a Terraform provider-level plan error that blocks the apply from doing *anything* until the operator runs `terraform state rm` by hand).

**But the IAM-member grants that point *at* a secret are a separate story, and they do get replaced.** `google_secret_manager_secret_iam_member`'s `secret_id` forces replacement (a destroy-then-create of the same resource address) when its value changes — and on a scope move, `local.secrets[logical]` (§5) changes value for exactly the names that just started resolving to the project ID. Concretely, for a logical name that moves from repo-scope to project-scope:

- `module.repo.module.workflow["<workflow-or-account-variant>"].google_secret_manager_secret_iam_member.job["<logical>"]` is replaced, **once per workflow (and once per named-Claude-account job variant, `sa.tf`'s `for_each` is keyed by logical name, `sa.tf:36-43`) that mounts that logical name** — not one address, potentially several, all for the same repository.
- If the logical name is also a `BuildSecret` (the git credential, `bitbucket-token`/`github-app-key`): `module.repo.google_secret_manager_secret_iam_member.build["<logical>"]` is replaced too (`build.tf:13-20`; the check job runs as the same build account and needs no separate grant, §5's "Build-time secrets" paragraph, B4).
- `tf.Guard` (`internal/infra/tf/guard.go:15-38`) refuses **every** such replacement by default — its own doc comment already says a replace ("`[\"delete\",\"create\"]` or `[\"create\",\"delete\"]`") is treated exactly like a delete — so the apply does nothing at all unless each exact address above is named with `--allow-delete` (repeatable, `internal/cli/init.go:370`). The same happens **in reverse** when a repository later adds its own override (moving a name back from project-scope to repo-scope) or a repository is removed from an `allow_data_to` list: the same addresses replace again, needing `--allow-delete` again. **A `moved` block cannot avoid this**: the resource *address* does not change, only its `secret_id` attribute does, and `moved` only ever relocates an address, never papers over an in-place attribute forcing a replacement. **A replacement is a delete followed by a create, so a run launched in that window — seconds at most — finds no accessor for the secret its job mounts and fails at its first read of it; launch it again.** Access never widens at any point during the apply: the two grants are never held at once, which is exactly why this design does not use `create_before_destroy` (it would briefly leave both the repository's and the project's grant in place, and the apply would still need `--allow-delete`).
- The exact owner command, for one workflow and the git credential (repeat `--allow-delete` once per address the plan actually lists — the implementer's commit for Task 6 prints the real set from a fixture, this is the shape):
  ```
  fugaro init --repo acme/app \
    --allow-delete 'module.repo.module.workflow["build"].google_secret_manager_secret_iam_member.job["anthropic-api-key"]' \
    --allow-delete 'module.repo.google_secret_manager_secret_iam_member.build["bitbucket-token"]'
  ```

**The exact owner sequence, for an existing name (e.g. `anthropic-api-key`) moving from repo-scope to project-scope:**
1. Add `project_secrets.anthropic-api-key.allow_data_to: [...]` to the local config.
2. `fugaro init` (the installation root, no `--repo`): plans **1 create** (`google_secret_manager_secret.project["anthropic-api-key"]`), 0 destroys, 0 replacements — the installation root's own first apply touches nothing that already exists. Apply it.
3. `fugaro secrets set anthropic-api-key --project-wide`: stores the value once. **This step's ordering (after step 2, never before) matters, and an earlier draft of this design wrongly assumed it did not (S2, caught in review):** `gcp.Secrets.Set` creates the Secret Manager secret directly via the API if it doesn't exist yet (§4), exactly the same as a repo-scoped `set` — but a repo-scoped `set` run *before* `fugaro init --repo` is safely adopted later because `DiscoverRepo` (`internal/infra/discover.go:540-570`) reads every name in `spec.Secrets` from GCP, checks its labels, and imports it into Terraform state (`d.add(importSecret, ...)`, the template `module.repo.google_secret_manager_secret.this[{key}]`, `imports.go:87`) **before** `terraform apply` ever runs — so the resource is already in state by the time `google_secret_manager_secret.this`'s `for_each` would otherwise try to create it again. `DiscoverInstallation` (`internal/infra/discover.go:401`) has **no equivalent step for `var.project_secrets`**: it imports the runs bucket, the registries and the installation's own singletons, never a secret. Run step 3 before step 2's apply, and that apply's `google_secret_manager_secret.project["anthropic-api-key"]` creation hits a 409 (the secret already exists, created directly by `Set`) and the apply **fails** outright — not a graceful adoption, an error. **The fix this design commits to, not left open:** `InstallationSpec` gains a `ProjectSecrets map[string]string` field (`gcp.ProjectSecretID(fugaroProject, name)` per entry — populated by `internal/infra/tfvars.go:150`'s `Installation(lc, o)`, the Go function that already builds every other `InstallationSpec` field from the local config, for **every** key of `lc.ProjectSecrets` with a non-empty `allow_data_to`, **every** `lc.Providers[*].Secret` unconditionally (§3a: a provider's secret is eligible for project storage regardless of its list), and **every** `lc.ClaudeAccounts[*]` with a non-empty `allow_data_to`, keyed by `config.ClaudeAccountSecret(name)`), and `DiscoverInstallation` gains the symmetric import step `DiscoverRepo` already has: for each name in `spec.ProjectSecrets`, read it from GCP, check it carries `{LabelManaged, LabelProject: fugaroProject, LabelSecret: logical}`, and import it (a new import-kind template, `module.installation.google_secret_manager_secret.project[{key}]`, mirroring `imports.go:87`'s repo-module one) before the apply. With this fix, step 3 may run before *or* after step 2, exactly like a repo-scoped `set` already can.
4. For each allowed repository whose own copy currently has no version: `fugaro init --repo` plans **0 deletes of any `google_secret_manager_secret.*` resource**, but **replacements of the `google_secret_manager_secret_iam_member.*` addresses above**, refused by `tf.Guard` until named with `--allow-delete` (see the command above), plus an ordinary `update` of the workflow's (and, if applicable, the check job's) Cloud Run job spec (a new revision, not a replace — Cloud Run Jobs accept template changes in place). **A repository that already has its own stored value plans no change at all (it keeps mounting its own, §5) — this is not a hypothetical caveat, it is both existing installs' actual starting state (S4, below), so step 4 alone does nothing for them until step 4a also runs.**
4a. **S4, not previously stated: a repository whose own copy already has a version (both existing installs, for the names the owner's original complaint names) must have that version disabled before it will ever use the project copy at all**, since §5's precedence is unconditional — "repo overrides project" has no override-the-override. Per repository, per name: disable (never delete — keeping history, consistent with how `fugaro secrets set` already only ever adds versions) the repo-scoped secret's current enabled version (`gcloud secrets versions disable <version> --secret=<the repo-scoped secret ID, from `fugaro secrets ls`>`, since no `fugaro` command disables a version directly today), then re-run `fugaro init --repo` for that repository — which now plans exactly step 4's replacements (`--allow-delete` required, same as above). **Skipping this step is not a safety net — it is the state in which this feature is a no-op for every repository that already has its own copy, which today is every repository of both existing installs for the names the owner cares about.**

**SF5, not previously stated: this step is project-owner-only, not something an operator can run.** `secrets.tf:26-35`'s operator grant is exactly two roles, `secretVersionAdder` (`secretmanager.versions.add`) and `viewer` (metadata/`list`, no `Access`) — neither carries `secretmanager.versions.disable`. An operator running the `gcloud secrets versions disable` command above gets a permission-denied error, not a successful disable; only a principal with broader Secret Manager admin on the project (today: the project owner, the same principal who already runs `fugaro init` itself for the installation root, §1) can complete this step. State this plainly in the migration instructions so an operator does not spend time chasing a permission error during the exact migration window step 4a describes.

**Step 4's `fugaro init --repo` is two stages, not one, and the first was wrong in the design's first two drafts (N2, a blocker).** Before the Terraform-applying repository stage that step 4 describes, `init --repo`'s **secrets stage** (`internal/cli/initsecrets.go`) runs first and decides which of a repository's secrets need a value at all, by checking only the repo-scoped ID's own version state (`find()`, `initsecrets.go:361-371`) — with no idea a project copy might already cover the name. Left unfixed, this stage would call **every** project-shareable name "missing" for **every** repository that has not yet had a value entered into its own repo copy — prompting the operator for a value they do not need to re-enter at a real terminal (and then storing it into the repo copy, silently flipping precedence back to repo-scope, the exact re-entry this feature exists to remove) or, worse, blocking an unattended `--yes`/CI run outright (`NeedsYou`). Under §3a this also means `init --repo` would prompt **every** `agent.auth: api-key` repository for a no-list provider's key the moment that provider's key is stored project-wide, even though nothing about that repository needed a new value. Fixed in the plan's Task 9: the secrets stage's `find()` also checks the project copy (reusing Task 2's `infra.ProjectSecretCandidate` helper) before ever calling a name missing.
5. **Optional, separate, owner-initiated cleanup**: once satisfied the project copy is in use, `fugaro secrets set`'s sibling has no "delete the now-redundant repo container" command in this design (deliberately — see §9's non-goals); the operator may `terraform state rm`/delete it by hand, at their own pace, outside any automated flow.

`fugaro init`'s plan output, for both the installation and the repo root, already distinguishes creates, updates, replacements and destroys (the live checklist's own "plan 1 create, 2 updates, 0 destroys" lines, `gcp-live-checklist.md:1253`) — this design adds no new plan-summary code, only new resources/fields that summary already knows how to print; it is step 4's **replacements**, not destroys, that are new and need `--allow-delete`.

**Existing providers with an explicit `allow_data_to` today: their mounting/routing *behavior* does not change — but their installation root's Terraform plan does, the first time it applies after this feature ships, and that is a real, stated consequence, not "nothing" (corrected this round, MUST-FIX 5: an earlier draft of this bullet said "nothing changes" without this qualifier).** Both installs that exist, `dimipaun/fugaro` and the sandbox, configure their providers (for example `openrouter`) with a non-empty `allow_data_to` today (`docs/multi-model.md` §2's own example lists specific repositories, never an empty list) — their own local configs are operator-local, never checked into this repository, so this is not independently verified by reading a file here; it follows directly from the ruling's own wording, which this design implements unedited: "when `allow_data_to` lists repositories, the key is available **only** to the listed ones" is byte-for-byte today's `AllowsData` behavior (§3a), unaffected by whether the list is empty or not. **But `InstallationSpec.ProjectSecrets` includes every `lc.Providers[*].Secret` unconditionally (§6 step 3, Task 4), regardless of the list's own state — so both existing installs' `openrouter` entry gets `google_secret_manager_secret.project["openrouter-api-key"]` (an empty container, no version ever stored unless `--project-wide` is actually run) plus its operator grants created the very next time plain `fugaro init` applies the installation root, a real, new resource in the plan.** Neither install's *behavior* is affected by this release unless the operator deliberately removes its provider's list — but their next plain `fugaro init`'s plan is not a no-op either, and the release note/migration instructions should say so plainly rather than let an operator be surprised by an unexpected creation they did not ask for.

**A provider the operator configures with no list at all, from this release onward, is a new state neither install has used before** (§3a's consequence): every `agent.auth: api-key` repository's `fugaro init --repo` plan gains a mount slot for it, whether or not that repository was ever meant to use it, and whether or not `--project-wide` storage is ever run. This is worth the owner's attention specifically *because* it is new, not because either existing install's current configuration triggers it today.

## 7. Compatibility and gates

- **Three edits, as with every new config key**: `localcfg.Config.ProjectSecrets map[string]config.ProjectSecret` (Go struct), `Validate` wiring `ValidateProjectSecrets` (mirroring `ValidateClaudeAccounts`'s call site), and — since `project_secrets` lives in the **local config**, never `fugaro.yaml` — **no JSON Schema edit** (`schemas/fugaro.schema.json` validates `fugaro.yaml` only; the local config has no published schema, matching `providers:`/`claude_accounts:` today).
- **`localcfg.Config.Shared()` strips it**, alongside `Providers`/`ClaudeAccounts` (`internal/localcfg/shared.go:37-38`) — never published to the runs bucket, operator-only (the precedent two tests already pin this shape: `TestMergeSharedNeverCarriesProviders`/`...ClaudeAccounts`, `internal/localcfg/shared_test.go:217,245` — this design adds a third).
- **Strict parsers refuse an unknown key.** `task.Spec` is unaffected — this feature adds no new task field (the resolved secret ID is a Terraform/job-spec concern only, never a per-run choice the runner sees, unlike `OAuthToken`). The `*Since` gate pattern (`recipesSince`/`layeredSince`/`namedTokensSince`, `internal/cli/recipes_skew.go`) does **not** apply to a **workflow's own** mount: an older runner's environment simply has the variable name it already expects (`ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`, …), pointed at a different secret ID — nothing about the runner's own code needs to know the difference, since Cloud Run's `secret_key_ref` resolves the mount, not the runner's own code. The gate that *does* matter for a workflow's mount is a plain Terraform-version one: a repository whose deployed job predates this feature's `infra`/Terraform code needs `fugaro init --repo` re-run before project-sharing takes effect for it (§5) — already true of every `infra` change, with no new constant needed. **BLOCKING, not previously stated: this reasoning is false for exactly one case, the daily check job's own rebuild — see below, a genuine exception, not an oversight to paper over with "in the same way" wording.**
- **`docs/release.md`'s checklist** gains one bullet, in the same family as the `gcpProjectFieldSince`/`recipesSince` bullets (`docs/release.md:55-58`): confirm the release note names the sequence in §6, and that an installation applying the installation root for the first time after this feature ships sees the new `secrets.tf` resources as **creates**, never **updates to an unrelated resource** (a regression in `installation`'s other resources would show as an unexpected diff there).
- **The job-image version gate does not change for a workflow's own mount — but it does for the daily check job's rebuild, and an earlier draft of this bullet was wrong to claim otherwise uniformly (BLOCKING, B2, caught in review — and the previous round's own gate mechanism was wrong too, corrected again this round).** The runner's own code and `task.Spec` are untouched (previous bullet) for every mount Cloud Run's own `secret_key_ref` resolves. **But the daily check job's image is always the *base* image (`spec.go:857`, `Image: bases[...]`), never a repository-specific build — so the `fugaro image check --job` process that reads `FUGARO_CHECK_SPEC` and resolves the git credential (N1, §5) is whatever `fugaro` binary was baked into that base image the last time it was built, completely independent of which `fugaro` binary last ran `fugaro init --repo` for this repository.** Two version-skew failure modes follow directly, neither covered by Tasks 1-7 or by Task 8's first draft: (1) an **older** base image's `fugaro` has no `CheckJobSpec.GitSecretID` field at all — `imagecheck.go`'s lenient decode (`imagecheck.go:442`, `json.Unmarshal` into that binary's own, older struct) simply drops the unknown JSON key, and that binary's own, unmodified code still calls `cloudBuildSpec` with `rs.Secrets[ws.GitSecret]` (the repo ID) — which fails, silently (a build failure the operator must separately notice and diagnose, not a crash with an obvious cause), the moment the git credential's repo-level version is disabled per §6 step 4a; (2) a **newer** base image's `fugaro` (with the field) decoding a spec a **stale, pre-this-feature `fugaro init --repo`** wrote has `s.GitSecretID == ""` (JSON simply lacks the key) — and nothing in Task 8's first draft says what the new binary should do with an empty value, which, read literally, would resolve to no secret at all. **Fix, part (a) — the `""` fallback:** when `GitSecretID` is empty, `submitRebuild` falls back to `rs.Secrets[ws.GitSecret]` exactly as it would have before this feature, recovering case (2) cleanly, since `infra.Repo()` always still computes that value regardless of version.

  **Fix, part (b), case (1) — corrected this round: the previous draft's gate was wrong in three ways and could not be built as written.** It compared `imagecheck.Record.FugaroVersion` — the version of the `fugaro` **CLI that submitted a repository's own derived-image build** (`internal/cli/image.go:541`, `FugaroVersion: Version`), an entirely different thing from the `fugaro` binary baked into the **base** image the check job actually runs. It placed the check inside `internal/infra.Readiness`, which cannot import `internal/cli` (`imagePredates`/`gitSecretIDSince` live there, and `internal/cli` already imports `internal/infra` — a cycle). And it described gating "a `fugaro secrets set` operation that would disable the repo version" — no such operation exists; §6 step 4a's disable is a raw `gcloud` command outside fugaro's control (SF5), so there is nothing in this codebase for a gate to intercept at that moment. **The real fix needs none of that: the check job's own base image reference is a plain string already in `ready.Check.Image`, parseable the same way an existing, shipped mechanism already parses a base ref string to judge its age** (`baseRefReleaseRE`/`imagePredates`, `internal/cli/init_fugaroyaml.go:369-392`, the pattern `baseRefReason` already uses for a *different* `*Since` constant, `gcpProjectFieldSince` — judging whether a build record's own base ref is new enough). No live call, no build record, no import cycle: in `internal/cli`'s own `planRepo`, **after** `Readiness` returns `ready` but **before** the apply, when `ready.ProjectSecrets[gitSecret] != ""` (the repo copy has no version, resolution already fell through to the project copy) and `ready.Check.Image`'s parsed release predates a new `gitSecretIDSince` constant, **refuse the apply outright** — naming both fixes (update the base image, `fugaro image refresh`/`base_images`, or re-enable the repo-scoped version so resolution falls back to it). When the ref does not parse as a release at all (a custom or dev base, `baseRefReleaseRE` finds no match) the version is genuinely unknown — **warn**, don't refuse, the same distinction `baseRefReason`'s own `reasonBaseRefDev` vs. `reasonBaseRefOld` already draws for its own `*Since` constant.

  **Why this could not instead be "omit the git credential from the check branch only, keep the repo ID there":** `local.secrets` (§5) is **one** repo-wide Terraform local that `job.tf`/`sa.tf`/`build.tf`/`check.tf` all read from — there is no way for the check branch to resolve a *different* value for the same logical name than the workflow jobs do. And the gate's own precondition is that the repo copy **has no version at all**: keeping `check.tf`'s mount on the repo ID in that state does not "fail safe," it points `secret_key_ref` at a secret with zero versions, which `Readiness`'s own `MissingSecret`/P7a logic already treats as unresolvable for every *other* reader of the same name — refusing the whole apply, with a clear fix, is the only option that does not leave something half-updated.
- **Shared config publication**: non-secret only, as already true of everything in `fugaro/config.yaml` — `project_secrets`' *names and allow-lists* are never published (they are local-config, operator-only, same as `providers:`/`claude_accounts:`, previous bullet); only the *fact* that a repository resolves a given scope could in principle be surfaced through `doctor`/`ls` (§5), never through the shared config object.
- **The trust boundary this implies, stated plainly (S5, not previously in the threat model): `project_secrets`/`providers`/`claude_accounts` policy lives only in each operator's own local config file, never synchronized or centrally enforced.** Any operator (there can be more than one per installation, `installation.operators`, `iam.tf`) can grant any repository access to the owner's shared key by adding that repository to an `allow_data_to` list in their own copy of the local config and running `fugaro init --repo` — **without ever holding, reading, or being able to read, the secret's value**. This is the same trust `providers:`/`claude_accounts:` already place in every operator (unchanged by this design, not a new exposure it introduces) and is **acceptable**, not a gap: operators are the people the installation's own IAM already trusts to onboard repositories, adopt Terraform state and run applies against production infrastructure — granting access to a name is a strictly smaller power than everything an operator can already do. Stated here so it is not mistaken for an oversight: there is no secondary approval step, and this design does not add one.

## 8. Live checks (owner tasks, `fugaro`/sandbox installations only — never `belong`)

- **40a.** A project secret, stored once with `--project-wide`, reaches an opted-in repository's job (the variable is set, from the project ID, confirmed via `jobs.get`'s `secret_key_ref`, never by reading the value).
- **40b (corrected, SF6 — `--project-wide` takes no repository argument, so a check worded as "a repository is refused at `fugaro secrets set --project-wide`" described a command this feature cannot issue).** For a `project_secrets`/`claude_accounts`-backed name (reserved secrets, named Claude accounts — unaffected by §3a): `fugaro secrets set NAME --project-wide` itself is refused outright, with no repository involved, whenever that name's `allow_data_to` is empty or absent — a store-time refusal, not a per-repository one. ## 9. Release placement and non-goals

**0.7.x**, after the base-image hard cut already on `main`/`next` (the current line, per this PR's own target).
