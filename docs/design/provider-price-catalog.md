# A built-in catalog of provider-model prices

*Status: 2026-10-14, draft for the owner's review. Nothing here is built. Related: [m10-multi-model.md](m10-multi-model.md) (§5 pricing and budget accounting, §13 assumptions), [mixed-credentials.md](mixed-credentials.md) (the Claude-through-OpenRouter opt-in), [shared-config.md](shared-config.md), [layered-config.md](layered-config.md), [../multi-model.md](../multi-model.md) (the user doc). The plan is [../plans/2026-10-14-provider-price-catalog.md](../plans/2026-10-14-provider-price-catalog.md).*

**What is verified, and what is not.** Every claim below about *Fugaro's existing behavior* was read from this branch's code, with the file and line named. Every claim about *OpenRouter* was read from its public documentation or its public APIs on **2026-10-14** (no credentials were used; the API responses quoted here were fetched from `openrouter.ai` directly), and the URLs are named. Claims that could not be checked either way are marked **UNVERIFIED** and are items in §10, with Check 44 of [../gcp-live-checklist.md](../gcp-live-checklist.md) as the live check that settles them. A number quoted from the owner's ruling is marked as the owner's; a number quoted from an API response is marked as measured on 2026-10-14 and will drift as OpenRouter's lists change.

## 0. Summary and recommendation

1. **Fugaro ships a price catalog for the models OpenRouter serves.** A generated, embedded data file (`internal/pricing/catalog/catalog.json`) records, per model, the price range over the endpoints OpenRouter may route to. A project needs no hand-typed `model_prices` for those models. `fugaro budget prices` still shows every price the budget will use, where it came from and when it was checked; an owner's `model_prices` entry still wins (§3 D4). One builder hands that table to every consumer — the run, `validate`, `diagnose`, `budget prices` and the local config's own override check — so no surface prices differently from the run (§3 D5).
2. **The catalog records a range, not a price, because OpenRouter's public price is the cheapest endpoint's.** `/api/v1/models` lists `deepseek/deepseek-v4.1-flash` at $0.01584 input / $0.891 output per million tokens, which is the cheapest of the 33 endpoints `/api/v1/models/deepseek/deepseek-v4.1-flash/endpoints` returns; the dearest ZDR-eligible one is $0.60 / $2.40 (measured 2026-10-14, §1). Per model the catalog stores the minimum and the maximum over the zero-data-retention (ZDR) eligible endpoints and the minimum and the maximum over **all** endpoints, for each of input, output, cache read and the two cache writes, plus web search where the endpoints price it (owner ruling 1, 2026-10-14 names the first three; D7 adds the rest because the same API row carries them). A dimension an endpoint does not price counts, for **both** bounds, as that endpoint's input price times a fixed factor (1.0 for a cache read, 1.25/2 for the cache writes, which is the table's existing assumption for a route that reports no cache fields) — so the high end can never fall below what any eligible endpoint would really charge (§3 D1, D7).
3. **Two switches on the provider route select which point the gateway charges**, both in the owner's local config (`providers.<name>`): `require_zdr` (default **true**) selects the ZDR set, and `price_policy: cheapest | highest` (default **cheapest**, matching OpenRouter's own default routing, which chooses among the stable providers' lowest-cost candidates — D6 quotes it) selects the end of the range.
4. **`cheapest` can undercharge, and this design says so plainly rather than hiding it.** OpenRouter may serve an endpoint dearer than the one priced. The bill for a run can exceed the charge by up to the cap times the spread between the cheapest eligible endpoint and the dearest: for the model above the measured spread is 37.9x on input and 13.3x on output over the ZDR set (3.2x / 4.3x over the four providers the owner's account allows), so a run that charges $5 may really cost up to about $189 (measured 2026-10-14, §1). This is the common case, not a corner: OpenRouter's default routing picks among the stable providers weighted by the **inverse square** of the price, so a dearer endpoint is served routinely — with three candidates at $1, $2 and $3 the $1 one is only 9x likelier than the $3 one — and the cheapest endpoint may be the unhealthy one: the cheapest `deepseek/deepseek-v4.1-flash` endpoint, `open-inference/fp4`, reported `status: -5` and 73.3% uptime over 30 minutes when measured. What bounds it: the per-run and daily dollar caps (which are the reason a cheap charge is not free money); the account's own provider allow-list, which narrows the set the weighting chooses from — an account-side preference is **not** documented as disabling the weighting itself: the routing guide says only that "if you have `sort` or `order` set in your provider preferences, load balancing will be disabled", and its fallbacks section guards its guarantee with "this is combined with the `order` field", so whether an account setting alone pins the served endpoint is **UNVERIFIED** (Check 44 step 5 records which provider served over several runs); `docs/multi-model.md` §1 asks the owner for that narrowing anyway; the provider-reported cost (`usage.cost`), which is **recorded and never settles** and which `diagnose` already compares against the charge — a gap above 10% is the observable signature of this undercharge, and `diagnose` names `price_policy: highest` when it fires (§3 D12); and `price_policy: highest` itself, which charges the top of the range and is the safe setting. §6 states all of them.
5. **A stale catalog can never silently under-price.** The file carries a `checked_at` date; past the catalog's own staleness threshold the run charges the **highest** bound of the selected tier instead of the policy's bound, logs a WARN and records `catalog_stale` in `result.json` (§7). The threshold is 30 days, shorter than the existing 90-day one (`internal/cli/budget.go:41`), because a marketplace price moves for reasons no age check can see: the generator is re-run on the release checklist's own line (§5), and a *rise* in a provider's price is invisible until it is. `highest` is what covers the gap between regenerations, and §6 treats the provider-reported cost as the bound that observes the rise first.
6. **`require_zdr` prices a tier; it does not enforce routing.** Fugaro cannot add OpenRouter's per-request `provider` object (the gateway never rewrites a body, and `provider` is a refused key on a routed call — `docs/multi-model.md` §7), so ZDR routing is enforced account-side only, and Fugaro cannot read the account's privacy setting: `GET /api/v1/key`'s documented response has no data-policy field (§8), so `fugaro doctor` says exactly that and names what to check. This is the honest limit of the switch; it is not a gap this design can close.
7. **Provider pinning is out of the first slice.** Sending OpenRouter's `provider` routing object (so the price is exactly one provider's) needs a body rewrite, which M10 forbids; it is named in §9 as a later option only.
8. **Nothing in the money path changes shape, and every surface gets the same table.** The catalog is compiled into the existing `pricing.Table` by one builder, `config.PriceTable` (§3 D5), which every consumer calls: the run (`internal/runner/gateway.go:399`, `internal/runner/policy.go:112`, `internal/runner/spend.go:122`), `fugaro validate` (`internal/cli/validate.go:133` and `:168`), `fugaro diagnose` (`internal/cli/diagnose.go:277`), `fugaro budget prices` (`internal/cli/budget.go:1193`) and the local config's own override check (`internal/localcfg/localcfg.go:241`) — the first seven call the builder; `Overrides()` produces the overrides the builder consumes, so its own check stays a check of the override set and does not consume them through the builder (see D5). All eight call `pricing.Embedded()` today; after this change the seven that price something call the builder, so a model the catalog prices is never refused by one surface and charged by another. The gateway's lookup, reservation, settlement, fee and `reported` bookkeeping are untouched, and the only new failure is the one that already exists (a model with no price on a provider route is refused, `internal/gateway/forward.go:543`).

## 1. The problem, with numbers

`/api/v1/models` (public, no key) returns one price per model:

```json
{"id": "deepseek/deepseek-v4.1-flash", "canonical_slug": "deepseek/deepseek-v4.1-flash-20260910",
 "pricing": {"prompt": "0.00000001584", "completion": "0.000000891", "input_cache_read": "0.0000000054"}}
```

Those are dollars **per token**, as strings; per million tokens that is $0.01584 / $0.891 / $0.0054. `/api/v1/models/deepseek/deepseek-v4.1-flash/endpoints` returns 33 endpoint rows, one per `tag`, and the cheapest of them, `open-inference/fp4`, is exactly what the models list quoted. So the list price is the **cheapest endpoint across all providers**, which is what the models list is for and is not what a given account will pay.

`/api/v1/endpoints/zdr` returns every endpoint with a zero-data-retention policy (946 endpoint rows over 356 models when read on 2026-10-14); each row carries `model_id`, `provider_name`, `tag` and its own `pricing`. Matching the two by `(model_id, tag)` gives this model's price range (USD per million tokens, measured 2026-10-14):

| tier | endpoints | input | output | cache read |
|---|---|---|---|---|
| ZDR-eligible | 26 | 0.01584 – 0.60 (37.9x) | 0.18 – 2.40 (13.3x) | 0.0039 – 0.06 |
| all | 33 | 0.01584 – 0.60 (37.9x) | 0.18 – 2.40 (13.3x) | 0.00294 – 0.06 |
| the owner's account's four providers (DeepInfra, Fireworks, Parasail, Together) | 5 | 0.14 – 0.45 (3.2x) | 0.42 – 1.80 (4.3x) | 0.0042 – 0.009 |

(The owner's ruling quotes "up to about 2.4x" for this model; that is the owner's figure for a smaller provider set. The measured rows above are what the public APIs say, corrected on **2026-10-15** to the snapshots the generated file is made from (`internal/pricing/catalog/testdata/openrouter/`): the first reading of the endpoints list here had it at 32 distinct tags with one duplicate and a cache-read maximum of 0.034, and the models list at 0.02016 input — the file built from the same responses carried 33 tags, 0.06 and 0.01584, which is what these rows and every figure below said at the time. The generation is reproducible from those snapshots. **The ranges are the numbers the file carried when this was written, not a promise about the file that ships**: the release checklist regenerates it (`scripts/gen-price-catalog.sh`), so `internal/pricing/catalog/catalog.json`'s own `checked_at` is the date its numbers are from, and the snapshots under `testdata/openrouter/` are refreshed with it — the file was last regenerated on **2026-10-23**, when this model's `all` tier read 40 endpoints at 0.07 – 0.6 input / 0.18 – 2.4 output and its `zdr` tier 35. Read the rows above as the measurement that motivated the design, and the file for what is charged. The account's own provider preference — the four named providers, or an account-side allow-list — is **not readable** from the API key, §8, so the catalog cannot record it.)

So today an owner who wants a correct cap for this model must hand-type one `model_prices` entry that is **too high for every call** or **right for one endpoint nobody pinned** — the "the real prices, and that OpenRouter reports usage the way the gateway reads it, are assumed until Check 25" caveat in `docs/multi-model.md` §2. The built-in table does not help: its one provider row (`providerRows()`, `internal/pricing/table.go:79-87`) is stamped `Unverified` with the note that no provider price was read, and it prices `deepseek/deepseek-v4-flash` at $1/$4 where the models API lists that same ID at $0.091/$0.182 — 11x and 22x too high — while the model the M10 documents route to is `deepseek/deepseek-v4.1-flash`, a different ID a pin would compare against at `priced_as: max`. The catalog replaces that invented row and the hand-typing with a generated, reviewable, per-tier range, and the two switches choose what to charge from it.

**And the endpoint that serves a call is not the endpoint the list price names.** OpenRouter's provider-routing guide (read 2026-10-14) states how a request picks a provider, verbatim: "Prioritize providers that have not seen significant outages in the last 30 seconds. For the stable providers, look at the lowest-cost candidates and select one weighted by inverse square of the price (example below). Use the remaining providers as fallbacks." Its worked example: with candidates at $1, $2 and $3 and the $2 one unstable, the $1 one is only **9x** likelier than the $3 one; and `allow_fallbacks` defaults to **true**. So the cheapest endpoint is one of several an account may be served by, and it need not be a healthy one — on 2026-10-14 the cheapest endpoint of the model above, `open-inference/fp4`, carried `status: -5` and 73.3% uptime over the last 30 minutes, and a router that deprioritizes providers with recent outages would not pick it first. A price the owner cannot see, served by a router the owner cannot read, is the problem; a range is the honest answer to it, and the two switches below choose which end of the range to charge.

## 2. What exists today (verified in the code)

- **The price table.** `pricing.Embedded()` (`internal/pricing/table.go:47-70`) builds a `*Table` from hand-written Go rows: `Source` = the Anthropic pricing page and `CheckedAt` = `"2026-10-20"` (`table.go:4-7`), plus one provider placeholder row (`providerRows()`, `table.go:79-87`) marked `Unverified` with its own `PriceSource`/`PriceCheckedAt`. There is **no** `go:embed` price data file anywhere in the repo. The seven embeds that do exist are all non-price artifacts, which is the idiom this design follows: `deploy/terraform/terraform.go:15` (`all:gcp`), `images/images.go:13,50,56` (`derived/Dockerfile.tmpl`, `derived/cloudbuild.yaml`, `base/tools.tsv`), `internal/budget/rules/rules.go:46` (`rules.json.tmpl`, the closest precedent: a generated artifact with a golden test), `internal/config/example.go:11` (`example.yaml`) and `internal/recipe/catalog.go:9` (`catalog/*.yaml`).
- **Owner prices.** `model_prices` → `pricing.Overrides` (`internal/pricing/overrides.go`), carried to a job as `FUGARO_MODEL_PRICES` (≤ 32 KiB, `overrides.go:51`); `Table.With` (`pricing.go:212-250`) replaces a model's rates whole and clears `Unverified`. `Rates.CacheRead` is a **multiplier of `InputPerM`**, not a price (`pricing.go:36-41`); `fugaro budget prices` already multiplies it back out for display (`internal/cli/budget.go:1230`).
- **The embedded table's staleness.** `priceStaleAfter = 90 * 24 * time.Hour` (`internal/cli/budget.go:41`); `budget prices` prints the source, the check date, the age and a warning past it (`budget.go:1238-1241`). `fugaro validate` and `diagnose` show pin warnings (`config.PinWarnings`, `internal/config/pins.go:44`).
- **Provider routes are local-config only.** `config.ModelProvider` (`internal/config/providers.go:28-47`: `kind`, `base_url`, `auth`, `secret`, `route_fee_pct`, `models`, `allow_data_to`) lives on the local config's `providers` map (`internal/localcfg/localcfg.go:78-80`). A repository's `fugaro.yaml` cannot set it (`TestRepoCannotAddProvider`, `internal/config/model_providers_test.go:183`), the project layer has no `providers` field (`internal/config/layer.go:49-94`), and the shared installation config refuses the section outright (`sharedForbidden`, `internal/cli/sharedcfg.go:155`; `localcfg.Config.Shared()` strips it, `internal/localcfg/shared.go:30-43`). A provider's fields reach a **job** only through `FUGARO_MODEL_PROVIDERS`, compact JSON written by `fugaro init --repo` (`runner.ProvidersEnv`, `internal/runner/providers.go:29-51`) and decoded strictly (`DisallowUnknownFields`, `providers.go:64-66`; ≤ 16 KiB). `docs/multi-model.md` §2 already states the consequence: a provider-list change takes effect only after `fugaro init --repo` is re-run.
- **The gateway's money path.** A request's model resolves to a route by pattern (`internal/gateway/route.go:144-151`); the fee is added to the reservation (`forward.go:557`) and the settlement (`forward.go:770`). An unpriced **pinned** model is priced at the table maximum and flagged `priced_as: max` (`forward.go:531-535`), but if it is routed to a provider the call is **refused**: `model %s is routed to %s but has no price: set model_prices` (`forward.go:543-554`); `config.CheckPins` refuses the same pin at bootstrap with `%s has no price: add it under model_prices in the project config` (`internal/config/pins.go:29-32`). A serving model dearer than the pin charges the dearer of the two rates, also `priced_as: max` (`forward.go:748-751`).
- **Reported vs charged.** The provider's `usage.cost` is parsed into `usageAcc.reported` (`internal/gateway/sse.go:176-182`), recorded on the charge (`ledger.go:103`) and in `result.json` as `cost.reported_usd`, and **never** prices a call the table priced (`forward.go:1017`, comment: "a record for comparison: it prices the call only where it floors a tier charge") — the one exception being a service tier no one prices, whose conservative charge it floors (`docs/multi-model.md` §6, `forward.go`'s `fromUsage`). `diagnose` sums the charge per route, strips the fee with `pricing.WithoutFee` and warns when reported exceeds the fee-stripped charge by more than 10% (`internal/cli/diagnose.go:245-293`); the runner logs the same gap once (`reported_gap`, `internal/runner/gateway.go:370-383`).
- **The runner builds the one table.** `spendFromEnv` reads `FUGARO_MODEL_PRICES` and does `pricing.Embedded().With(o)` (`internal/runner/spend.go:116-125`); with the budget on and no overrides it falls back to the plain embedded table (`internal/runner/policy.go:108-113`); the gateway is started with `Prices: s.Prices` (`internal/runner/gateway.go:57`) and the same table answers `CheckPins` (`gateway.go:346`).
- **`fugaro doctor` checks** are `doctorCheck{ID, OK, Problem, Fix, Severity}` (`internal/cli/doctor.go:39-45`) where `""` fails doctor, `"warning"` fails only with `--strict` and `"info"` never fails; the provider-adjacent checks today are `fugaro-yaml`, `claude-accounts-stored` and `oauth-token-allowed`.

## 3. Decisions

**D1. The catalog records a per-model range over endpoint sets, not a single price.** Per model: `zdr` (min, max) and `all` (min, max), each with every dimension D7 names in USD per million tokens as decimal **strings** (`input_per_m`, `output_per_m`, `cache_read_per_m`, `cache_write_5m_per_m`, `cache_write_1h_per_m`, `web_search_per_1k`), plus the endpoint count and, for each extreme, the `tag` that holds it. The values are **per-dimension extremes** (the lowest input over the set, the lowest output over the set, the lowest cache read over the set, ...), not one endpoint's numbers: that is what "the price range over the endpoints" means, it is what the owner's ruling asks for, and it compiles exactly (see D7). *Veto alternative:* record the cheapest and dearest **endpoint** (three numbers from one row each). It reads better but bounds nothing: Decart's $0.18 output and OpenInference's $0.01584 input are on different endpoints, and a per-endpoint record would price output at $0.891 while the true worst case in the set is $2.40. A dimension the set does not price is not a hole in the bound: each endpoint contributes its **own** input price for a dimension it does not price, and the extreme is then taken over those contributions, so the maximum is never below what an eligible endpoint would really charge (that is D7's one fold rule; the multiplier it compiles to can exceed the ratio of the two extremes, which is the safe direction, and it is refused if it passes `MaxMultiplier`).

**D2. The catalog is a generated JSON file embedded in the binary.** `internal/pricing/catalog/catalog.json`, written by `internal/pricing/catalog/gencatalog` (a `main` package) through `scripts/gen-price-catalog.sh`, read at runtime by `internal/pricing/catalog/catalog.go` via `//go:embed`, decoded strictly, and validated by a test that runs on every build. Reasons: it carries hundreds of numbers (up to twelve per model, six dimensions over two tiers, each a min/max pair with the endpoint tags) — a Go literal set would be unreadable in review, and the repo already has a generated-artifact idiom (`internal/budget/rules/rules.json.tmpl` + a golden test, `internal/recipe/catalog/*.yaml`). A price in the job's environment is not an option: `FUGARO_MODEL_PROVIDERS` is capped at 16 KiB and `FUGARO_MODEL_PRICES` at 32 KiB, and a per-project calibration of every model is exactly the hand-typing this design removes.

**D3. Two switches, on the provider route, in the owner's local config.** `require_zdr` (bool, default **true**) and `price_policy` (`cheapest` | `highest`, default **cheapest**). They sit on `config.ModelProvider` beside `route_fee_pct`, so they reach a job the same way every other provider field does (§2), and they are the owner's alone: a repository cannot set them. The default-true spelling follows the repo's existing idiom (`*bool` + an `On()` accessor: `PRSettings.EarlyDraft`/`EarlyDraftOn`, `internal/config/config.go:99-115`). The **scoping answer** the owner asked for: `providers.<name>` exists **only** in the local operator config today, so "the shared project layer" is not an option in this slice — the project layer has no provider fields and the shared bucket config refuses the section by name (`internal/cli/sharedcfg.go:155`). If the config-transitions work (Check 42) later lets the shared project layer carry a provider route, these two switches follow it with the same ceiling semantics as `allow_data_to`, and nothing in this design depends on which layer spells them.

**D4. Resolution order: owner override, then the catalog by tier, else the existing refusal.** `model_prices` for a model still replaces the whole row (owner ruling 4) and still clears provenance flags, **rates and nothing else**: the owner's price replaces a model's `Rates` and clears the flags that say where a price came from, while the row's limits — the context window and the maximum output the catalog carries — stay (`Table.With` keeps them; `pricing.go:212-250`). A model the owner prices that a catalog-covered route claims therefore still gets its catalog row, carrying limits and no rates until the override lands on it: a row the override would otherwise have created from nothing has neither, so the gateway would fall back to `DefaultMaxOutputTokens` (1,000,000) and stop refusing a `max_tokens` above the model's real maximum (`forward.go:463-468`), and a PDF would reserve the default context window. The switches still decide nothing there — an owner's number is the second way out of a route the catalog cannot price (D9) — so such a model is exempt from the `require_zdr` refusal and from the `MaxMultiplier` bound, and its row is materialized from the file for its limits alone. With no override, a model claimed by a route the catalog covers is priced from the catalog's selected tier; a model with no entry in either is refused exactly as today (bootstrap `CheckPins`, gateway backstop). The catalog entry is keyed by the **exact** upstream ID (no aliases, no `:` variants), which is also what a pin must name (`pricing.IsAlias`, `alias.go:30-44`).

**D5. The catalog compiles into the `pricing.Table` in one place, and every surface uses that place; the gateway is not touched.** `config.PriceTable(providers, overrides, catalog, now)` in `internal/config` returns the table the whole program prices with: the embedded rows, then one catalog row per (route, model the route claims) with the rates that route's switches select, then the owner's `model_prices` applied **last**, so an override still wins. Every one of the eight sites that calls `pricing.Embedded()` today calls it instead — `internal/cli/budget.go:1193`, `internal/cli/diagnose.go:277`, `internal/cli/validate.go:133` and `:168`, `internal/localcfg/localcfg.go:241`, `internal/runner/gateway.go:399`, `internal/runner/policy.go:112` and `internal/runner/spend.go:122` — so a model the catalog prices is never refused by one surface and charged by another, and `validate` cannot refuse a pin the gateway would price. `localcfg.Config.Overrides()` keeps its own job (decoding `model_prices` and rejecting a malformed one, `localcfg.go:241`) and the builder takes its result; its last two lines are a `pricing.Embedded().With(o)` that only proves the set applies (no two keys naming one model), and that call does **not** become a `PriceTable` call — the builder consumes overrides, so routing this one through it would make `Overrides` its own caller. It **stays as it is** (`pricing.Embedded().With(o)`): the catalog has nothing to say about whether an owner's override set is well-formed, and `Overrides()` needs no table of its own to say it. The builder needs the route table, so `validate` passes the routes of the config it is validating and `diagnose`/`budget prices` the local config's. On a machine with no provider route the builder adds no catalog row and the result is today's behavior exactly — including today's refusal of a pinned model with no price, since with no route nothing says the model goes to OpenRouter.

Why not teach the gateway to look the catalog up live: the money path would grow a second lookup branch, a second provenance state and a second way for `validate`/`budget prices`/`CheckPins`/the gateway to disagree; compiling once means one code path prices every call, and the existing gateway tests (reservation, settlement, fee, partial, `reported`) keep testing the code that charges.

**One model ID belongs to one route, so it has exactly one price — there is no per-route price split.** The table is keyed by model ID, and at most one route can claim a given ID: `ValidateModelProviders` refuses overlapping provider `models` patterns ("a model must belong to one provider", `internal/config/providers.go:158`; `ProviderFor` picks the single match, `providers.go:91`), and `CheckModelPattern` refuses a pattern overlapping `ClaudePatterns` (`providers.go:212-220`). So the case "catalog-priced on one route and owner-priced on another" cannot arise, and this design does not claim it. What can arise is narrower: (a) a model **no** route claims gets no catalog row and is priced by `model_prices` only, exactly as today; (b) a model claimed by a route whose `base_url` is not OpenRouter — a direct vendor route such as `base_url: https://api.deepseek.com/anthropic` (`docs/multi-model.md`, "Direct to the vendor") — also gets no catalog row, because OpenRouter's marketplace prices say nothing about what the vendor charges. The catalog covers a route only when its `base_url` host is `openrouter.ai` (or a loopback host, so the hermetic fake is testable) — an inference, stated here, not a knob; *veto alternative:* an explicit third field (`price_catalog: auto | openrouter | off`), rejected for the first slice as a knob whose only other setting is a wrong answer.

**D6. `cheapest` undercharges, by design, and the design states the size of it in the units the caps use.** OpenRouter's provider-routing guide (read 2026-10-14): "Prioritize providers that have not seen significant outages in the last 30 seconds. For the stable providers, look at the lowest-cost candidates and select one weighted by inverse square of the price (example below). Use the remaining providers as fallbacks." Its example: candidates at $1, $2 and $3, the $2 one unstable — the $1 one is 9x likelier than the $3 one. `allow_fallbacks` defaults to **true**, and "if you have `sort` or `order` set in your provider preferences, load balancing will be disabled." Two consequences the review asked to be written down: a dearer endpoint is served **routinely**, not as a rare fallback, and the cheapest endpoint may be the one an account avoids — measured 2026-10-14, the cheapest `deepseek/deepseek-v4.1-flash` endpoint (`open-inference/fp4`) carried `status: -5` with 73.3% uptime over 30 minutes. The size of the undercharge, stated properly: **the charge is at most the cap, and the bill can be up to the cap times the price spread across the eligible endpoints** — 37.9x on input and 13.3x on output for the measured model's ZDR set (3.2x/4.3x over the four providers the owner's own account allows), so a run charged the $5 cap can cost up to about $189. Four things bound it (§6): (1) the caps, which bind later rather than never; (2) the account's own provider allow-list, which **narrows** the set the weighting chooses from — the guide says "if you have `sort` or `order` set in your provider preferences, load balancing will be disabled", and its fallbacks section guards its guarantee ("to guarantee that your request is only served by the top (lowest-cost) provider, you can disable fallbacks") with "this is combined with the `order` field", so whether an **account** setting alone stops the weighting is **UNVERIFIED**; `docs/multi-model.md` §1 asks the owner to narrow the set anyway; (3) the provider-reported cost, recorded beside the charge, which is the observable bound: it is the only signal that sees a real undercharge, and it also catches a price **rise** that no age check can; (4) `price_policy: highest`, the top of the selected tier. The reported cost is what `fugaro diagnose` compares at a 10% gap (`reportedGapPct`, `internal/cli/diagnose.go:240`), and its warning text names `price_policy: highest` beside `model_prices` as the two answers (§7). `cheapest` stays the default (owner ruling 3): it matches OpenRouter's own default and it is what the marketplace list price means, and the alternative over-charges every call for a bound most calls never reach. The user docs and `fugaro doctor` say which to pick and when.

**D7. Cache read and cache write are prices in the file and multipliers in the engine, and the file carries the write prices too.** `Rates` expresses every cache price as a *multiple of the input price* (`internal/pricing/pricing.go:36-41`), so each cache dimension the tier prices is recorded as a **price** (min and max over the tier, in the same unit as the other dimensions) and compiled into `Rates{X: bound.X_per_m / bound.input_per_m}` — making the effective price charged for a cache token exactly the recorded bound (for `zdr`/`cheapest` on the DeepSeek example, $0.0039 / $0.01584 = 0.246 of input). The pair is an envelope, not a real endpoint; D1 chose that on purpose, and it is coherent because what is charged for a cache token is the tier's own extreme, never a product of two independent ones.

**The endpoints API reports the write prices too, so the catalog reads them rather than inventing the multipliers.** Each endpoint's `pricing` carries `input_cache_write` (5-minute) and, where the provider distinguishes it, `input_cache_write_1h`; on the measured Claude rows these are exactly the 1.25x and 2x the table already assumes (0.0000025 / 0.000002 = 1.25x, 0.000004 / 0.000002 = 2x, `anthropic/claude-sonnet-5.5`, 2026-10-14), but they are not universal: `moonshotai/kimi-k3`'s 25 endpoints price a write on exactly one of them ($3.75/M against a cheapest input of $0.49/M), so pricing it at the 1.25x default would under-count writes by about 6.1x. The first slice therefore records `cache_write_5m_per_m` and `cache_write_1h_per_m` per tier alongside the other four. The existing `overrides.go` defaults (`DefaultCacheWrite5m 1.25`, `DefaultCacheWrite1h 2`, `overrides.go:20-25`) remain what applies to a **tier where no endpoint prices the dimension** (every DeepSeek endpoint, measured: none of its 33 rows carries either field) and to an owner's override that leaves them out.

**Three rules keep the compiled row expressible and safe, and the first of them is one rule stated once, in this design, in the plan and in Check 44.** (a) **A dimension the tier does not price is omitted from the file and folded at compile time, never written as a price.** For **both** bounds — the minimum and the maximum — each endpoint of the tier that does not price the dimension contributes a stand-in, and the extreme is then taken over the stand-ins and the real prices together. The stand-in is the endpoint's **own input price times a fixed factor**: 1.0 for a cache read, `DefaultCacheWrite5m` 1.25 for a cache write 5m and `DefaultCacheWrite1h` 2 for a write 1h (`overrides.go:20-25`). It is the same factor whether the tier prices the dimension on *some* endpoints or on none, so a partially priced dimension cannot fold lower than an unpriced one; every measured model that prices a write prices it **above** its input (1.25x and 2x on `anthropic/claude-sonnet-5.5`, 1.33x on `qwen/qwen3.8-flash`, 7.7x on `moonshotai/kimi-k3`, measured 2026-10-14), which is why the write factor is above 1 rather than 1.0. It is a stand-in for an endpoint that publishes nothing, not a claim about what it charges: the maximum is therefore never below what any eligible endpoint would really charge, and the minimum is never below zero. The compile then writes the bound as a **multiplier of the tier's input price**, and for an unpriced dimension it sets that multiplier **explicitly** — 1.0 for a read, 1.25/2 for the writes — rather than leaving it 0 for someone else to raise: `defaultCacheRates` (`pricing.go:252-266`) raises a 0 multiplier to 1 **only inside `Table.With`**, on the override path, and a catalog row never passes through it (so "leave it 0 and let the default raise it" would price cache reads at 0 on a catalog row, i.e. free). Web search is the one dimension with no stand-in: it is omitted when the tier prices it nowhere and compiles to 0, because a per-search price has no input-price equivalent (it is a per-search price, not a token price) and is therefore stated as an assumption rather than a bound: **an endpoint that prices no search is taken to charge none**, which U7/Check 44 step 3 settles. A tier that prices a dimension is unaffected by the fold: what is charged is the recorded extreme, never a product of two independent ones. (b) If a tier prices a cache dimension but the tier's own input price makes the ratio exceed `pricing.MaxMultiplier` (10, `pricing.go:110`), the compile **refuses** the row with a message naming the model, the dimension and both prices, rather than clamping: clamping down would under-price, and clamping up would hide a model the table cannot express. (c) Nothing here prices an unpriced dimension: a response that reports a cache write on a row that priced none is the existing unpriced-dimension case, and `SurpriseMultiplier` (`pricing.go:104`) is unchanged.

**Web search is the one non-token dimension the table can express, so the file carries it.** The measured `anthropic/*` rows (the Phase-2 additions, D8) price `web_search` at $0.01 per search — the same $10 per 1,000 the Anthropic table already assumes (`table.go:26`), and the same value the deleted placeholder row got from `rates()` — so a row for a model that prices a search has to carry it, or a web search would be free. The tier records `web_search_per_1k` when any of its endpoints prices it (exact decimal, the API's per-search value shifted by three places) and **omits** it when none does, exactly like the cache dimensions — so no dimension in the file is ever the string `0`, and the loader's "every price present is more than 0" rule holds for every dimension without an exception. The compiled row's `Rates.WebSearchPer1k` is the recorded value, or 0 when the tier omitted it (0 is valid there: a route that prices no search charges none). Whether the Anthropic-compatible endpoint reports web searches to a provider route at all is **UNVERIFIED** (`Usage.WebSearches` is read from the response's `server_tool_use.web_search_requests`, `internal/gateway/sse.go:229`) and is Check 44's step 3, so the field is carried and not relied upon.

**A model with a long-context price tier is refused, not approximated.** 80 of the measured models carry a `pricing.overrides` array — a threshold above which every rate changes (e.g. `anthropic/claude-haiku-5.5`: above 100,000 prompt tokens, input $0.10 → $0.50 and output $0.50 → $2.50, 5x). That is exactly `pricing.Tier`, but the file's shape carries one price *range* per dimension and `Tier` is a single point, so pricing it correctly needs a shape this slice does not have, and pricing it at the base rate would under-count a long-context call by 5x. The generator therefore **hard-errors** on an allowlisted model that carries a long-context tier (or an `image`, `audio` or `internal_reasoning` dimension), naming the model and the field, so the allowlist cannot silently grow past what the file expresses; `model_prices` with a `long_context` block is how such a model is priced today. None of the five non-Claude allowlist models has one, and neither do the three Claude rows (measured 2026-10-14).

**D8. What the generator includes, and what it refuses.** The generator takes an **explicit allowlist** of model IDs (in the script, so growing it is a reviewable diff), not all 462 models the models API lists on 2026-10-14: for the first slice the DeepSeek family (`deepseek/deepseek-v4.1-flash`, `deepseek/deepseek-v4-flash`, `deepseek/deepseek-v4-pro`), one Qwen and one Moonshot row (`qwen/qwen3.8-flash`, `moonshotai/kimi-k3`) for the families the owner might use — `qwen/qwen3.8-flash` is on that list although **neither** of its two endpoints is ZDR-eligible (measured 2026-10-14), so a `require_zdr` route (the default) refuses it: the generator writes it an `all` tier and no `zdr` tier (D9), and the row is useful only on a route that sets `require_zdr: false`. It is kept rather than dropped because it is the case that makes D9's refusal visible in the shipped file, and because the alternative — silently leaving the family out — is what a reader would otherwise have to guess; the plan's Task 7 says which row to try first, **no Claude ID is on it, and that is not an oversight.** A row keyed `anthropic/<id>` was unusable in two independent ways when this was written: `ClaudePatterns` (`claude-*`, `anthropic/*`, `internal/config/providers.go:205`) makes `CheckModelPattern` refuse any provider `models` pattern overlapping them (`providers.go:212-220`), so no route could claim the row; and `IsAlias` refused the `anthropic/` prefix outright, so `CheckPins` (`internal/config/pins.go:27`) could never price a pin with that ID. Both relax **only** with the explicit opt-in designed in [mixed-credentials.md](mixed-credentials.md) §2, and the three measured Claude rows (`anthropic/claude-sonnet-5.5`, `anthropic/claude-opus-5.5`, `anthropic/claude-fable-5.1`) arrive in the same change as that opt-in, in a later slice (§11). *(**Amended 2026-10-15:** both refusals are now relaxed — `IsAlias` accepts a well-formed `anthropic/<id>` (`internal/pricing/alias.go`), so a pin and a `model_prices` key may name one, and one route entry may claim that same exact ID while every pattern overlapping `ClaudePatterns` is still refused. What keeps the three rows out of the shipped file today is the allowlist itself — no Claude ID is on it — and the shared-installation ceiling below.)* The opt-in has a second ceiling to lift before such a row is usable anywhere but one machine: the route it would be priced on is a `providers.<name>` entry, and the shared installation config refuses that section outright (`sharedForbidden`, `internal/cli/sharedcfg.go:155`), so a Claude catalog row is priced by an operator's local config only until that ceiling moves as well — the same limit D3 records for the two switches, and the reason no part of this design depends on which layer ends up carrying a provider route. The five non-Claude IDs all exist and were measured on 2026-10-14; the generator refuses an allowlisted ID the API no longer serves, so a rename cannot quietly shrink the file.

It **never includes** a spelling `pricing.IsAlias` would refuse as a pin, and this is enforced rather than intended: an allowlisted ID `pricing.IsAlias` returns true for is a **hard error** in the generator, so the file can never contain a key no route could claim and no pin could name. That is what keeps out `~vendor/model-latest` alias rows (19 of 462, identifiable by `alias_target`), every `:` variant (`:batch` — 77 rows with their own prices — and `:free` — 14), and an `anthropic/<id>` that is not a single explicit claimable ID. *(2026-10-15: the one shape the opt-in claims is no longer an `IsAlias` refusal, so this screening no longer catches it; the allowlist does — no Claude ID is on it.)* The generator may import `pricing` for that check even though the loader may not (Task 2 of the plan's layering rule): `internal/pricing/catalog/gencatalog` is a `main` package nothing imports, so it creates no cycle. It **refuses** (hard error naming the model and the field) a model whose pricing carries a dimension the file does not express: a long-context tier (`pricing.overrides`, 80 models), `image`/`image_output` (32 models), `audio`/`audio_output`/`input_audio_cache`, or `internal_reasoning` (D7). It **skips** a model with no ZDR-eligible endpoint — no `zdr` tier is written, and a `require_zdr` route refuses that pin rather than pricing an empty set (D9).

The endpoints' `discount` field is **UNVERIFIED**: no public documentation for it was found on 2026-10-14, it appears **nested inside each endpoint's own `pricing` object** (not beside it, and not in the models list — DeepInfra's showed `0.3`, its siblings `0`), and the obvious reading — a discount the published price does not yet include — would mean the catalog over-prices rather than under-prices, which is the safe direction. The generator records the price the API published, ignores the field, and Check 44's step 5 settles it by comparing the settled charge with the catalog's price for the usage observed; if `discount` turns out to be applied at billing time the generator must apply it first, which is a small change plus a regenerated file.

**D9. A tier the model has no endpoints for refuses the pin, loudly.** `require_zdr: true` on a model the catalog knows with zero ZDR endpoints, or a model with no catalog row at all and no override, fails at bootstrap with a message naming the switch, the model and both ways out (`require_zdr: false`, or `model_prices`), and keeps the gateway's existing refuse as the backstop. No path prices an empty set, and no path silently falls back to "all". **The refusal is per model, and lands where the model is named.** A route's pattern claims a whole family, so a model of that family the catalog cannot price is refused when a pin or a call names it, and never by failing the table for the models the run does use: the row is simply absent (so no path prices it), and the reason is recorded on the table for the pin rules, `budget prices` and the gateway's backstop to report. Failing the table instead would refuse a run pinned to a priceable model of the same family, and one new non-ZDR model at OpenRouter would break every default route on the next regeneration.

**D10. Staleness charges the safe end, and age is not the only thing that makes a catalog stale.** `checked_at` in the file; past a catalog-specific threshold — **30 days**, shorter than the existing `priceStaleAfter` (90 days, `internal/cli/budget.go:41`) because a marketplace price moves for reasons the Anthropic table's slow-moving list does not — the compiled bound is forced to the selected tier's **maximum** regardless of `price_policy`, with a WARN per run (`budget: price catalog stale`) and `cost.catalog_stale: true` in `result.json`. A stale catalog therefore can never under-price, and it never refuses a run for a reason that has nothing to do with the repository. What age covers and what it does not, stated plainly: it covers an *unobserved* change to the file's inputs, and it cannot see a price **rise** that happened yesterday — which is why D6's bound 3 (the provider-reported cost, compared by `diagnose`) is the check that observes a rise, why a shipped catalog is regenerated on the release checklist's own line (§5), and why the file's other staleness signals are checked at load time as well: a `version` other than 1, an unparseable `checked_at`, or a key `pricing.IsAlias` would refuse is a load error, never a silent fresh read (§4). `fugaro validate`, `fugaro budget prices` and `fugaro doctor` say the same thing before any run.

**D11. The two switches must survive version skew in the job's environment.** `FUGARO_MODEL_PROVIDERS` is decoded with `DisallowUnknownFields`, so a value written by a newer CLI and read by an older runner is a **hard bootstrap failure**, not a silent default. Two rules: `ProvidersEnv` **omits** both keys when they hold their defaults (a `*bool` nil for `require_zdr`, `""` for `price_policy`), so a job written by the new CLI and run by an older image is byte-identical to today and keeps today's behavior (owner prices, or the placeholder row — the placeholder `providerRows()` is deleted in the same change, in the plan's P6 and its Task 4 step 3; §5 is the generator, which does not touch it); and a **non-default** value is refused by `fugaro init --repo` when the workflow's base image predates the release that reads the field, naming the release — the same gate shape `cloneSince`/`imagePredates` already use in `internal/cli/recipes_skew.go`. The runner must also treat an absent key as the default, which falls out of the same rule and is pinned by a test. This is the one place this feature touches the wire between CLI and runner, and it is why it is written down here rather than discovered in a failed run.

**D12. `fugaro doctor` is honest about what it cannot check, and `diagnose` names the way out.** Two checks (§8): `provider-price-catalog` (OK, with the age, the source and the exact regeneration command; a `warning` finding — which fails `doctor` only under `--strict`, `internal/cli/doctor.go:39-45` — when the catalog is older than the same 30-day threshold D10 uses) and `provider-zdr-unverified` (info, fired when any provider sets `require_zdr` true, saying that Fugaro prices the ZDR tier, that ZDR routing is enforced by the account's privacy setting only, and that Fugaro cannot read that setting — `GET /api/v1/key`'s documented response carries no data-policy field — so this is the owner's own check; Check 44 records the answer). `fugaro diagnose` carries the other half: its existing reported-vs-charge warning (`internal/cli/diagnose.go:273`, fired above `reportedGapPct` = 10%) gains the two things the review asked for — it keeps `model_prices` as one answer and names **`price_policy: highest`** as the other, because a gap on a catalog-priced route is as likely to be OpenRouter serving a dearer endpoint as it is a wrong `model_prices`, and the fix the owner wants is the policy, not a hand-typed row.

Every number above is measured (2026-10-14), including the two `min_of`/`max_of` pairs and the endpoint-derived limits. **The Claude row is the Phase-2 shape, not a Phase-1 key** (D8: no `anthropic/<id>` row exists until the mixed-credentials opt-in relaxes `CheckModelPattern` and `IsAlias`); it is shown because it is the only measured model that prices all six dimensions, and it is what that row will look like. A tier object with fewer than six dimensions is normal, not a defect; a dimension that is present is always a `{min, max, min_of, max_of}` object.

Rules that make it reviewable and safe to parse:

- **Keys sorted**, models sorted by ID, `json.MarshalIndent` with two spaces and a trailing newline. Generation from the same inputs and the same `-date` is byte-identical (pinned by a test).
- **Prices are decimal strings**, produced by shifting the API's per-token decimal string six places (exact decimal arithmetic, never `float64`), so a diff shows a price change and never a float-formatting wobble. The loader parses them with `strconv.ParseFloat`.
- `min`/`max` are the per-dimension extremes over the set; `min_of`/`max_of` name the endpoint `tag` holding each extreme (ties broken by the lexicographically smallest tag, so a tie cannot make the file flap between runs). A `:` variant or alias can never appear as a key.
- `context_tokens` and `max_output_tokens` are the **minimum** over all endpoints (`context_length`, `max_completion_tokens`), so nothing is reserved or allowed above what every eligible endpoint accepts; `0` means the model reports none, and `pricing`'s `DefaultContextTokens`/`DefaultMaxOutputTokens` apply (a larger reservation, never a smaller one). An endpoint whose `context_length` or `max_completion_tokens` is **null** is left out of the minimum (it advertises no limit, so it cannot constrain the others); a tier where every endpoint's is null records `0`, which means the same thing as today — the model reports none, and `pricing`'s defaults apply. Leaving a null out can only make the recorded minimum larger, i.e. allow a longer call than that endpoint may accept, which is the one direction this rule is not conservative; measured 2026-10-14, neither field is null on any of the 91 endpoint rows of the five allowlist models (33 + 16 + 15 + 2 + 25) nor on the 8 rows of `anthropic/claude-sonnet-5.5` (the Phase-2 example), while 8 of the 462 models in the models list carry a null `top_provider.max_completion_tokens` (so the field can be null on a model, and the generator reads the endpoints, not the list). `image_tokens` is not recorded: a catalog-priced row has none, so images are refused on it (`pricing.Model.ImageTokens` 0 means refuse, `pricing.go:56`), any model that prices an image is refused by the generator (D8), and per-image pricing is a later refinement.
- The file is **not** authoritative by itself: the loader (`catalog.Load()`) validates it and returns an error, and the runner refuses the run with `the built-in price catalog is malformed: …` rather than pricing from a half-read catalog. The compile-time test makes that unreachable in a released binary.
- A `checked_at` that does not parse, or a `version` other than 1, is a load error (never a silent "fresh" or "stale").

## 5. The generator

`scripts/gen-price-catalog.sh` → `go run ./internal/pricing/catalog/gencatalog`. No credentials of any kind; three public GETs per model (`/api/v1/models` once, `/api/v1/endpoints/zdr` once, `/api/v1/models/<id>/endpoints` per allowlisted model — using the `links.details` value when the API gives one, since that names the canonical slug).

- **Inputs:** `-models <json> -zdr <json> -from <dir>` read saved snapshots instead of the network (the test path), `-allow <file>` the model allowlist (default: the list in the script), `-date YYYY-MM-DD` the `checked_at` to write (required when fetching: the generator never reads the wall clock, so a run is reproducible), `-o <path>` the output.
- **Spellings:** every key is a model ID a route can claim and a pin can name — the generator refuses an allowlisted ID `pricing.IsAlias` refuses (D8), so no key is dead weight a reviewer has to reason about.
- **Dimensions:** for each tier and each of the six dimensions the file expresses (input, output, cache read, cache write 5m, cache write 1h, web search per 1k), the minimum and maximum over the tier's endpoints, with the tag at each extreme; a dimension no endpoint of the tier prices is omitted, never written as `0` (D7(a)) — for **both** bounds, an endpoint that does not price a dimension stands in with its own input price times the fixed factor D7(a) names (1.0 read, 1.25/2 writes) before the extreme is taken, and that stand-in is computed, never written to the file. A model whose pricing carries a dimension the file does not express — a long-context tier, an image, audio, internal reasoning — is a hard error naming the model and the field (D8).
- **Determinism:** no map iteration in the output path; the ZDR match is `(model_id, tag)` (verified: every ZDR row's tag is present in that model's endpoints, and provider names alone are ambiguous — BaseTen serves three tags and one of them appears twice); duplicate `tag`s with identical prices collapse into one endpoint, whose limits are the smaller of the two rows' (the model above had 33 endpoint rows over 33 tags and its ZDR set 26 over 26 when this was written, and 40 over 40 and 35 over 35 in the 2026-10-23 file, so nothing collapses in the shipped file; the rule is there because the API does return one tag twice, and `TestGeneratorDuplicateTagTakesTheLowerLimits` covers it — the fold is a minimum, so the file does not depend on the order the response listed the rows in), duplicate `tag`s with *different* prices are a hard error naming the model and tag rather than a silent pick (`TestGeneratorRefusesDuplicateTagWithDifferentPrices`); a model on the allowlist that the API no longer serves is a hard error naming it, so a rename can never quietly shrink the file.
- **Review workflow:** the script prints a summary diff (models added/removed, per-dimension min/max deltas, the endpoint counts, the old and new `checked_at`) and writes the file; the PR shows both. `internal/pricing/catalog/testdata/openrouter/*.json` holds the snapshots the checked-in file was generated from, so a reviewer can re-run the generation offline (`scripts/gen-price-catalog.sh -from internal/pricing/catalog/testdata/openrouter -date 2026-10-23` — the path is the repo root's, and the date is the checked-in file's `checked_at`, so the command as written reproduces the checked-in bytes) and get the identical bytes.
- **When it runs:** by hand, at the owner's discretion, and as the release checklist's own line (design D2's sibling: `docs/release.md` gains "regenerate the provider price catalog and read the diff", the same shape as its `cloneSince` lines). Nothing regenerates it in CI: a price must never change because a workflow ran.

## 6. Money: what is charged, and how the undercharge is bounded

**The charge.** For a routed call whose model the catalog prices at the selected tier and bound, `Rates` are `{InputPerM: bound.input_per_m, OutputPerM: bound.output_per_m, CacheRead: bound.cache_read_per_m / bound.input_per_m, CacheWrite5m: bound.cache_write_5m_per_m / bound.input_per_m, CacheWrite1h: bound.cache_write_1h_per_m / bound.input_per_m, WebSearchPer1k: bound.web_search_per_1k or 0}` — each cache multiplier as the ratio D7 describes, with D7(a)'s fold when the tier has no such dimension (read 1.0, writes 1.25/2) and the search price 0 when the tier omitted it — and everything downstream is unchanged: `Model.WorstCase` bounds the reservation, `check` enforces `max_output_tokens`, `Rates.Cost` prices the reported usage and rounds to µ$, `pricing.WithFee` adds `route_fee_pct` to the reservation **and** the charge, and the ledger records `used`, `ByModel`, `ByRoute`, `Reported`, `overruns`. The catalog's prices are the **model** prices; the route fee is the owner's, added on top, exactly as `docs/multi-model.md` §1 asks the owner to discover from their account. `route_fee_pct` has no implicit value: it is a plain percentage that defaults to **0** — "0 is none" (`internal/config/providers.go:39-40`) — bounded by `MaxRouteFeePct` 50 (`providers.go:25-26`), so a route with no fee charges exactly what the catalog lists, and any markup the account pays on top of the model price has to be declared here to be counted. A fallback to a dearer **model** (not endpoint) is still caught by the existing `priced_as: max` (`MaxOf(pin, serving)`), which is a different and already-handled case.

**The four bounds on `cheapest`.**

1. **The caps.** `budget.per_run_usd`, the daily caps and `max_run_tokens` are all computed from the charge; an under-charge makes a cap bind later than the ledger says, never sooner. The reservation is an upper bound on any call the request allows, so a run cannot exceed a cap on the reserved path (the reason `route_fee_pct` multiplies the reservation too). What an under-charge costs is therefore **dollars**, not only accuracy: the provider can bill up to the spread times the cap while Fugaro's ledger records the cap (the cap-times-spread statement in §0 item 4 and D6), and a cap still stops the run — it stops it later than the ledger claims, and the dollars billed over the cap are the account's. The only hard bound on what leaves the account is the account-side credit limit on the OpenRouter key (`docs/multi-model.md` §7), which is why the design recommends it there for any run whose spend matters.
2. **The provider's own number.** `usage.cost` is parsed, recorded per stage (`StageReport.Reported`) and in `result.json` as `cost.reported_usd`, and shown by `fugaro diagnose <run>` beside the charge with the fee stripped (`WithoutFee`) — and it **never settles** a call the table priced, the one exception being the floor it puts under an unpriced service tier's conservative charge (`forward.go`'s `fromUsage`, `docs/multi-model.md` §6). With `cheapest`, a persistent `Reported:` above `Cost:` is the undercharge showing up in the data the owner already reads; `fugaro diagnose` warns above a 10% gap, names `price_policy: highest` and `model_prices` as the two answers, and the runner logs `reported_gap` once per run. This is the bound that also covers a price **rise** between catalog regenerations — the case age cannot see (D10) — because it compares what the provider charged with what the table charged, whatever the reason for the gap. What that measurement needs is exactly what M10 left unverified: whether the Anthropic-compatible endpoint returns a `usage.cost` at all — Check 25's question, carried into Check 44 (§10, U3).
3. **`price_policy: highest`.** The safe setting: every call is charged the top of the selected tier. For the measured example that is $0.60 / $2.40 rather than $0.01584 / $0.891; the docs say to use it whenever the cap must be an upper bound (a costly batch, a first run against a new model) and `cheapest` when the charge is a close estimate and the caps are the guard.
4. **The reported-vs-charged discipline in the docs.** `docs/multi-model.md` §6 already tells the owner to read `Reported:` beside `Cost:`; this design adds the one sentence that makes it actionable: with `cheapest`, a lasting gap means either the routing picked a dearer endpoint or the price moved, and the answers are `price_policy: highest`, a regenerated catalog, or `model_prices` for the endpoint actually served.

**The account-side setting is a narrowing, not a documented switch.** The routing guide documents that `sort` or `order` in the *request's* `provider` preferences disables load balancing, and describes disabling fallbacks as "combined with the `order` field"; no account-level provider preference is documented at all, and Fugaro cannot send one (§9). So the honest reading is the one above: an account allow-list narrows the set the inverse-square weighting chooses among, and whether it also pins the choice is **UNVERIFIED** — Check 44 step 5 records which provider served over several runs, with the same settings, so the answer is measured rather than assumed.

**What the catalog does not do.** It does not raise a charge after the fact (the table settles, always), does not adopt `reported` (M10's decision, unchanged, and phase 3's question), and does not know the account's provider preferences (§8), so a `cheapest` row can be below even the ZDR set's minimum when the account allows only four providers — the owner's "about 2.4x" case is a *narrower* range than the catalog's, and the catalog is therefore conservative in the wrong direction for exactly those accounts. That is the strongest argument for `highest` on an account with a narrow provider allow-list, and it is stated in the user doc.

## 7. Staleness, and never under-pricing silently

| Surface | What it says / does |
|---|---|
| `fugaro budget prices` | New `CATALOG` column; a catalog-priced row prints its tier, bound, endpoint count and the catalog's `checked_at`; a stale catalog prints the same warning shape as the Anthropic table's but measured against the catalog's own 30-day threshold, naming the **catalog** source and date (distinct from the Anthropic table's) and the regeneration command |
| `fugaro validate` | A warning per catalog-priced pin naming the tier and bound, and (for a `cheapest` row) one note: the charge is the cheapest of N eligible endpoints; `price_policy: highest` charges the range's top |
| `fugaro diagnose <run>` | The pin-warning line gains the tier/bound; `Reported:` beside `Cost:` as today, with the fee stripped, and the reported-vs-charge warning names `price_policy: highest` beside `model_prices` (D12); a stale catalog is named when `cost.catalog_stale` is set |
| The run | `checked_at` older than the catalog's own 30-day threshold (not `priceStaleAfter`, which stays the Claude table's 90 days — D10) ⇒ the compiled bound is the selected tier's **maximum**, a WARN `budget: price catalog stale` per run, and `cost.catalog_stale: true` in `result.json` |
| `fugaro doctor` | `provider-price-catalog`: OK with the age and the source; `warning` past 30 days, naming `scripts/gen-price-catalog.sh` as the fix |

**What the user documentation says.** `docs/multi-model.md` is the page an owner reads before configuring a provider, so it carries the whole story: that the prices now come from a catalog built into the binary rather than a `model_prices` block, the two switches with their defaults, the `cheapest`-undercharge paragraph with the four bounds above, the "`require_zdr` prices a tier, it does not enforce routing" paragraph, how a single model is still overridden with `model_prices`, and how to read the catalog's age from `fugaro budget prices` and `fugaro doctor`. `docs/design/m10-multi-model.md` §5's placeholder row and its "a price check command is out of scope (a later nicety)" line are marked superseded there, pointing at this design, so a reader of M10 is not left with two answers.

The invariant: **no path prices a provider-model call lower because the catalog is old.** The stale case over-counts (the tier maximum) and says so in three places; the fresh case charges what the owner asked for (the policy's bound) and annotates it. A price the catalog has no row for is still the existing refusal, never a silent maximum (`forward.go:543`).

## 8. `require_zdr` is a price tier, not a routing policy

This is the design's most important honesty point, and it is the one a user will otherwise get wrong.

- **What Fugaro can do.** Price the call against the ZDR-eligible set (the owner's switch, default true), and warn when that is not the set the account actually allows.
- **What Fugaro cannot do.** Make OpenRouter route ZDR-only. ZDR enforcement is the per-request `provider.zdr` field or the account's privacy settings — `zdr` is documented as a boolean in the `provider` object, enforced per model group at account and guardrail level, "OR"-ed with the request setting, so the request field can only ever *add* enforcement (ZDR guide and provider-routing guide, both read 2026-10-14). Fugaro's gateway never rewrites a body and refuses `provider` as a routed key (`docs/multi-model.md` §7, `routedKeys` in `internal/gateway/forward.go`), so the account setting is the only enforcement it can rely on.
- **What Fugaro cannot read.** The account's ZDR / data-collection setting. `GET /api/v1/key`'s documented response is `label`, `limit`, `limit_reset`, `limit_remaining`, `include_byok_in_limit`, `budgets`, `effective_budget`, `usage*`, `byok_usage*`, `is_free_tier`, `free_model_daily_requests` and a deprecated `rate_limit` (limits reference, read 2026-10-14). There is **no** data-policy field, and guardrail-level ZDR is set on guardrails, which the key response does not enumerate. **UNVERIFIED:** whether an undocumented field or a second endpoint exposes it. Check 44 step 2 records the answer from the owner's own key; if one exists, doctor's check becomes a real check and this section is corrected.
- **Consequence, stated plainly to the user.** `require_zdr: true` (the default) means "price this route as if only ZDR-eligible endpoints can serve it". It is the right default because it is the conservative price and matches the account policy the owner intends; it is not a data-policy guarantee, and the docs must not imply one. The doctor check says exactly this, at `info`, whenever a provider sets it.

## 9. Out of the first slice

- **Provider pinning.** OpenRouter's `provider` object (`order`, `only`, `ignore`, `sort`, `max_price`, `zdr`) would make the price exactly one provider's (or bound it with `max_price`, which "will prevent your request from running if the price is not available"). It needs the gateway to rewrite or add a body field, which M10 forbids for a money-relevant reason (the body is the agent's; a rewritten body is a new correctness surface), so it is named here and nothing more. If it is ever wanted, the honest shape is a per-route constant body fragment rather than a general rewrite, and it must be priced by the same catalog.
- **Reading the account's provider preferences** (to narrow `zdr` to the four providers the owner actually allows). Nothing documented exposes them (§8). If Check 44 finds an endpoint, narrowing the catalog's ZDR set per account becomes possible and makes `cheapest` much tighter.
- **Applying `discount`** (D8): one line, once its semantics are known.
- **Image and per-request pricing** in `Rates`; the catalog skips such models rather than guessing.
- **Adopting `reported` as the settled charge**; M10's phase 3 question, untouched.
- **Catalog rows for every OpenRouter model** (462 today); the allowlist grows by reviewable diff.

## 10. Open, and what the live check settles

- **U1. Whether the account's ZDR setting can be read from an inference key** (§8). Doctor's wording depends on it; Check 44 step 2.
- **U2. Whether `require_zdr: false` still routes ZDR-only when the account enforces ZDR** (the "OR" rule read from the docs, not observed). Check 44 step 5 records the serving provider with the switch off.
- **U3. Whether the Anthropic-compatible endpoint returns `usage.cost`** (M10 §13 item 1, restated). Without it, bound 2 of §6 is unavailable and `highest` is the only safe setting; Check 44 records whether `reported_micros` is nonzero in the `model call` log lines.
- **U4. What `discount` means** (D8). Check 44 compares the settled charge with the catalog's price for the usage it observes.
- **U5. Whether the prices the generator reads are the prices charged** (including whether a chosen endpoint's price is the one billed, and whether `input_cache_read` appears in a billed response). Check 44 steps 3-4.
- **U6. Whether a stale catalog's forced maximum is ever wrong in the other direction** — a price drop that makes the tier's recorded maximum exceed the true cost. It over-counts by construction; nothing to verify except that the warning fires. The mirror case — a price **rise** while the file is still inside its threshold — is not something age can see (D10); the reported cost is what observes it (§6 bound 3).
- **U7. Whether a provider route ever reports web searches** (`Usage.WebSearches` comes from the response's `server_tool_use.web_search_requests`, `internal/gateway/sse.go:229`). The file carries `web_search_per_1k` for the models that price it, so nothing is refused over it; if the Anthropic-compatible endpoint never reports one, the field is inert on a provider route and the row should say so rather than imply the charge exists. Check 44 step 3's token counts would show it.
- **U8. Whether the fold D7(a) assumes is what an endpoint that prices no dimension really charges** — that an endpoint publishing no `input_cache_read` bills those tokens at its input price, that one publishing no write bills at 1x–2x of input, and that one publishing no `web_search` charges nothing for a search. The bounds are the safe direction by construction; the fold is an assumption about billing, and Check 44 step 3's token counts (and step 5's settled charge) are what turn it into a measurement.
- **U9. What `status` and the uptime fields in an endpoint row mean.** Measured values are quoted in §1 and D6 (`open-inference/fp4`: `status: -5`, `uptime_last_30m: 73.33`), but no public documentation of the scale was found on 2026-10-14 — the field is read as "a non-zero status means the endpoint is degraded", which is an **UNVERIFIED** reading. Nothing in the design acts on it: the generator records prices only, and no row is dropped for a status.
- **U10. Whether an account-side provider allow-list narrows the routing choice or pins it** (D6's point 2, §6). The provider-selection guide documents that `sort` or `order` in a request's `provider` preferences disables load balancing, and guards its fallbacks guarantee ("to guarantee that your request is only served by the top (lowest-cost) provider, you can disable fallbacks") with "this is combined with the `order` field"; no account-level preference is documented, and Fugaro cannot send one. Check 44 step 5 records which provider served over several runs, so the design's bound 2 is a measurement rather than a guess.

## 11. Phases

**Phase 1 (this design's slice):** the catalog file for the five non-Claude IDs, the generator, the compile-into-table step, the two provider switches, staging/doctor/`budget prices` surfaces, the user docs, and Check 44. Phase 1 never changes what a call is charged for a model the owner priced by hand, and it adds no Claude row, because until [mixed-credentials.md](mixed-credentials.md) §2's opt-in relaxes `CheckModelPattern` and `IsAlias` such a row could be neither claimed nor pinned (D8).

**Phase 2:** add the three `anthropic/<id>` rows in the same change as the mixed-credentials opt-in; carry a long-context tier, so the 80 measured models with a `pricing.overrides` array become eligible (D8's refusal becomes a row shape: `pricing.Tier` already exists, `Tier.AboveInputTokens`/`InputPerM`/`OutputPerM`, `pricing.go:44-48`, and `Rates.LongContext` is a single point, not a range — the one real new piece is deciding what the min/max of an overridden price means); per-image pricing; apply `discount` if U4 says so; grow the allowlist; narrow the ZDR set per account if U1 finds a readable setting.

**Phase 3 (needs the owner's decision):** provider pinning via a per-route body fragment; `reported` as the settled charge; image pricing.
