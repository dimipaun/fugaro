# Fugaro spec: autonomous cloud ops for managed projects

Oct 15, 2026 · @Dimi

## Summary

In a Fugaro-managed project, the agent runs Terraform and other cloud operations end to end with no human confirmation. It reviews each plan itself before applying it.

Today every cloud command stops for confirmation: typing yes, confirming the project, and more. The `--yes` flag skips these, but needing it everywhere is a pain. The prompts also protect little, because humans rarely read Terraform plan output. An agent that checks every resource change is the better reviewer.

This is safe because a managed project is disposable. It holds only Fugaro resources, and it can be rebuilt from the project Git repo. Even deleting the whole project loses almost nothing.

**Goals**

- No confirmation prompts for cloud operations in managed projects.
- The agent reviews every plan, and both the plan and its review are kept for audit.
- Cost surprises are caught within days, not at month end.
- A lost project can be rebuilt quickly from the project repo.

**Non-goals**

- Projects not managed by Fugaro, such as shared or customer-owned GCP projects. They keep today's confirmations.
- Encrypted backup of third-party secrets.

## Fugaro-managed projects

A managed project is a Firebase project, and its GCP project, that Fugaro creates and owns, holding only Fugaro resources.

- **Created by Fugaro.** Only projects Fugaro itself provisioned can be managed. An existing project can't be flagged after the fact.
- **Marked in two places.** A GCP project label (for example `fugaro-managed=true`) and the project config in the project Git repo. Fugaro treats a project as managed only when both agree.
- **Single purpose.** Nothing outside Fugaro should run there. If Fugaro finds resources it didn't create, it warns and falls back to confirmations.
- **Rebuildable.** The project repo must hold everything needed to recreate it (see Disaster recovery).

## Behavior

In a managed project, every cloud operation runs without prompts, and the agent replaces the human as plan reviewer.

1. Run `terraform plan` and save the plan file.
2. The agent reads the full plan: every create, update, replace and destroy.
3. Scope check: each resource must be in the managed project. Anything outside it, such as another project, org-level IAM or the billing account, stops the run.
4. Cost check: the agent flags new or upsized resources that bill continuously, such as Cloud Run min instances, Cloud SQL tiers, GPUs and large VMs.
5. The agent writes a short review: what changes, why, and any concerns.
6. Apply the saved plan with no confirmation.
7. Store the plan and the review in the project repo for audit.

In projects that aren't managed, today's confirmations and the `--yes` flag stay as they are.

## Cost safeguards

The real risk is a valid plan that creates something expensive, not a deletion. So every managed project gets a GCP budget on its billing account when it is created.

- **Budget alerts** at set fractions of a monthly amount (for example 50%, 90% and 100%), sent to the project owner.
- **Hard stop (optional).** On 100%, a small function disables billing or scales services down. This is safe because the project is disposable.
- The budget is separate from Fugaro's model-spend caps in RTDB. It covers all GCP spend, including resources the agent creates.

The budget amount is set at project creation and stored in the project repo.

## Disaster recovery

If a managed project is lost, Fugaro rebuilds it from the project Git repo into a new project.

- **Fresh project ID.** A deleted GCP project ID stays reserved for about 30 days, so restore always creates a new ID and updates the repo config to point at it.
- **What the repo must hold:** Terraform, project settings, spending caps, spending history, and recipes.
- **GCS state.** Recipes and anything else in GCS must also be saved to the repo, or be re-creatable, so a rebuild gets them back.
- **Live state is lost.** In-flight jobs and RTDB counters aren't restored. Running jobs are simply re-run.

## Secrets

Secrets aren't backed up. They're reissued.

- **Keys Fugaro issues itself** (service account keys, Firebase config) are regenerated automatically during restore.
- **Third-party keys** (OpenRouter, Anthropic, Claude OAuth tokens) are regenerated by hand. There are only a few, so this takes minutes.
- The project repo keeps a list of required secrets, where each comes from, and the Secret Manager name it goes into. It never stores the values.
- **Later, optional:** encrypt secrets into the repo, with the encryption key kept outside the managed project.

## CLI and config

Proposed names; final names are open.

| Command / setting | What it does |
| --- | --- |
| `fugaro init project --managed` | Creates a new managed Firebase/GCP project, applies the label, sets the budget, and writes the config to the project repo |
| `managed: true` in project config | Turns off confirmations for that project, if the GCP label matches |
| `budget.monthly` in project config | Monthly budget amount used for alerts and the optional hard stop |
| `fugaro restore` | Rebuilds a lost managed project from the repo into a new project ID |
| `fugaro secrets status` | Shows which required secrets are missing after a restore |
| `--yes` | Still supported for projects that aren't managed |
