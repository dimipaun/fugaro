## 0. What this document is, and how its claims were checked

The owner's second console spec asks for six things the first one did not: **project discovery** over every project in the home config, including projects owned by others; a task **dependency graph**; a **command channel** to orchestrating agents through the realtime database; **overlap detection** over the files jobs changed; a **version roadmap** with drag-and-drop; and an **independence-maximizing planning skill** that feeds the graph. The rest of it — the review inbox, desktop notifications, per-job controls, spending cap alerts, spending graphs and live tasks — is the v1 spec restated, and is reconciled as such.

The shape of this document is this tree's own. A spec is committed **verbatim** as a source ([project-centric-spec-source.md](project-centric-spec-source.md), [m9-spec-source-v3.md](m9-spec-source-v3.md), [setup-and-skills-spec-source.md](setup-and-skills-spec-source.md)); a **reconciliation** reads it against the tree and rules on every difference ([m9-spec-v3-reconciliation.md](m9-spec-v3-reconciliation.md) is the precedent, and its **"Rulings (binding)"** table — the unnumbered section that opens it, ahead of "What v3 adds and where it lands" — is the shape this document's **§1** (a ruling on every difference, classified) and **§2** (what those rulings leave open) copy); the **plan** carries the tasks that follow from the rulings. This document is the middle one.

**Every claim about the code was checked against `origin/main` at `a573870`.** Each finding cites a **file and a symbol**, never a bare line number: a line number is a fact about one commit, a symbol is a fact about the code, and this tree's review convention asks for the second. Every path cited below exists on `origin/main` at that commit.

**The same rule applies to a cited rule number, and this document learned it the hard way.** §5.1's rules were renumbered once already, and the v1 plan's Task 1.1 records it in as many words: "the numbering in the design as it now stands, after this revision inserted the `app://` scheme rule (3) and the Electron Fuses rule (4) and moved the rest down". **Two rules were inserted, not one** — so the spawn allow-list went from **old rule 4 to rule 6**, old rule 3 was the IPC allow-list (today's rule 5), and old rule 5 (job-written text) is today's rule 7. An earlier revision of this document cited the allow-list as §5.1 rule 3, which is today's CSP rule; a first correction of that sentence said the allow-list had moved "from rule 3 to rule 6", which was wrong for the same reason one level up — it had read the plan's note as inserting a single rule. Both corrections are recorded rather than silently applied, and together they produce the rule this document follows from here on: **a rule is cited by number *and* by its subject**, so a reader can tell which one moved.

**Where the owner's brief and this tree disagree about a number, the tree is quoted and the disagreement is recorded** rather than resolved silently — §5.2 does that for the release train and §5.3 for the live-check numbers — **and where the tree carried no number at all, §5.3 names the owner's allocation rather than inventing one.** Each is a correction to the *brief*, not to the spec.

**Where the index rows went.** This repository keeps **no index file**: there is no `docs/README.md`, no `docs/design/README.md` and no `docs/plans/README.md`, and `docs/SPEC.md` is not one either — it is the original product specification, and it links exactly one design ([design/v1.md](v1.md), from its own header) and no list of designs. What the tree has instead is a convention, applied in both directions: **a design document carries a `Related:` line** (see the head of [desktop-console.md](desktop-console.md), [artifact-runs.md](artifact-runs.md), [compute-backend.md](compute-backend.md)) and **a plan carries a `Spec:` line**. So the rows this work owes are the tree's own: this document and the plan carry theirs above, and the two merged documents that this spec amends — the v1 design and the v1 plan — each got **one new sentence** pointing forward at this pair, in their own style and without a word of their existing text changed. That is the whole of the index work, and saying so is more useful than adding a file this tree does not keep.

**The verdict, in one paragraph.** All six of the new features need something this tree does not have, and the largest of them is a write path that D2 and D14 forbid. The **dependency graph** needs a machine-readable task graph, and the only planner artifact that exists is `.fugaro/render-plan.json`, written by a `mode: artifact` run's plan step and read by nobody (`internal/runner/artifact.go`'s `renderPlanPath`); **overlap detection** needs the set of files a branch changed, and no document the console can read carries it (`internal/runview/runview.go`'s `Row` has `pr_url` and no paths); the **sessions registry** needs an identity for an orchestrating agent, and the registry that exists — `/agents/<slug>/<run>` — is written by a *running job about itself* and dies with the run (`internal/budget/model.go`'s `AgentEntry`, `internal/budget/registry.go`'s `Session`); the **version roadmap** needs a project record to write to, and the owner's own end state for that record is the project-centric plan's phase 6, which is reserved and **not built**; and the **command channel** is a write to a realtime-database queue that does not exist and that nothing consumes, in an app whose whole safety argument is that it spawns a read-only allow-list of exact argument vectors. What *does* exist is what the spec itself names as the alternative path: `fugaro run`, `fugaro run --retry` and `fugaro cancel` — **none of which asks a question** (the CLI's write commands carry a **confirmation — typed, or `--yes`** — on `budget set`'s raise, `budget kill` and `budget resume` (`confirmTyped`, which needs a real terminal), on `image build` (`confirmBuild`, which reads the project's name), and on `init`, `config init` and `upgrade`, whose steps are confirmed by `--yes` or at the terminal; none of that is on these three commands — F8), so a spawn of one of them is confirmed by the app or by nobody — and the two launches already carry the claim semantics that make "two agents can't start the same task twice" true at the level that actually protects anyone — **a launch**, not a task. **Project discovery** is the one feature whose substrate is already here (F1): the config enumerates the installations today and the missing piece is the read the v1 design's own D13 names, `fugaro config list --json`.

## 1. Findings

Each finding is classified **Exists** (the tree has it, and the spec should be read as naming it), **Wrong** (the spec, or a document in this tree, says something the code contradicts), **Gap** (nothing in the tree does it), **Rule** (not a fact but a constraint the tree's existing decisions impose on how the feature may be built), or **Open** (a question this document cannot answer from the tree alone).

### Project discovery and layout

**F1 — the config enumerates the installations, no command prints them, and the app may not read it itself. (Exists / Gap / Rule)**

The spec's "reads the global Fugaro config in the home directory and lists every project the user has set up" is true in Go, unreachable from a command, and — read literally — **forbidden to the app**. The Go half is real: `internal/localcfg/localcfg.go` has `ProjectsDir` (`$XDG_CONFIG_HOME/fugaro/projects`, else under `~/.config`), `ProjectPath`, `Projects(getenv)` (an `os.ReadDir` of `projects/*.yaml` returning the names) and `LoadProject`. Two commands already call it, and **neither prints the list**. `internal/cli/init.go` uses it in `noteSecondProject`, which counts the configs to print one note — "two project configs now exist; commands outside a checkout need `FUGARO_PROJECT=<name>` or `--project <name>`" — so a bare `fugaro init` does *not* offer the installations it found; and `internal/cli/doctor.go` uses it for the **empty** case (`len(names) == 0`), to tell an operator who has no installation at all to run `fugaro init` (its own comment says why it needs the raw list rather than `localcfg.Select`'s wrapped error). `internal/localcfg/select.go`'s `SelectError` carries a `Projects` field, so a refusal to pick a project lists them too — in an error, which is not a document.

The command half is the gap, and the v1 design's D13 already names it and its shape. **`fugaro config` has exactly `example`, `show`, `layer`, `init` and `publish`** (`internal/cli/configcmd.go`, `config_show.go`, `config_init.go`, `config_publish.go`); `config show` describes *one checkout's* resolved `fugaro.yaml` rather than the set of installations; and there is **no `fugaro project` command on `main`** at all — D13 says it arrives with project-centric phase 1 (PR #390), and `internal/cli/root.go`'s `AddCommand` list confirms it is not there yet. D13's own answer calls the missing read **`fugaro config list --json`** and files it as **gap 5 of §4.3, "not v1's problem"**. So the sidebar is waiting on a read the v1 design already scoped and named, not on a design question — and the spawn allow-list (§5.1 **rule 6**, "the spawn allow-list is exact argv, not a command name") is what will have to admit it.

The part of the spec's sentence that is **ruled out** rather than merely unbuilt is the reading itself: §3.4 **rule 7** says "The console never stores a credential, never reads `~/.config/fugaro` itself, and never passes a flag the renderer chose", and rule 7 continues that **"the installation list is the operator's, typed and picked, not discovered"**. What the spec wants — projects added with the CLI appearing automatically — is reachable as D13's own alternative: the CLI prints the list, the operator **picks** from it, and the app still stores only the tuple it was given. See **D31**.

**F2 — the v1 design's gap 5 and §3.4 rule 7 are imprecise about what exists. (Wrong, narrowly)**

D13 says "nothing on this tree enumerates installations", and rule 7's imperative rests on the same reading. Taken literally both are false: `localcfg.Projects` enumerates the configs, `doctor` and `init` call it — to **count** them, not to print them — and `SelectError.Projects` lists the names in a refusal (all three in F1). What is true — and what both passages mean, since D13 goes straight on to name `fugaro config list --json` as the missing thing — is that **no command exposes them as a document**. The correction is recorded here rather than edited into v1: v1 is merged, its decisions are answered, and the sentence that needs changing is changed by the task that implements the read (V2.1.1), beside the old one.

**F3 — "including projects owned by others" is a credential question, not a listing question. (Gap / Rule)**

The list of projects in the home config is the list of projects *this operator has been set up for*. It is not a directory of projects that exist, and there is no such directory: a Fugaro installation is a GCP project with a runs bucket and a realtime database, and finding one you have never been told about would mean enumerating someone else's GCP projects, which no credential on the machine permits and no part of this design wants.

A project owned by someone else reaches this operator the way it reaches the CLI today: **by name**, through the config that project *publishes* to its own runs bucket. `internal/localcfg/shared.go` has `(*Config).Shared()` (the local config's view of the published one), `MergeShared` (published values filling in what the local config does not set) and `SameInstallation` (whether the published config is the same installation the local config thinks it is); `internal/localcfg/sharedcache.go` caches the fetched copy for `SharedFreshFor` (24 h) and lets it stand in for an unreachable bucket for `SharedOfflineFor` (7 days). The fetch is authorised by whatever the operator already holds on that project's bucket — `internal/cli/cloud.go`'s `cloudOptions`/`addCloudFlags` add `--gcp-project` for exactly the case where the project name is not enough to find the installation.

So the spec's sentence is achievable, but only as D13's tuple: an installation is (project name, config path, binary path, optionally a checkout), **added by hand and verified rather than discovered** — D13's pairing check runs one allow-listed read with the typed `--project` and the chosen checkout, and refuses to store an installation the CLI would refuse later. Nothing about that tuple is owner-specific, which is the whole answer to "including projects owned by others": a project owned by someone else is added exactly like any other, and what the operator can then *read* is what their own credentials allow, through the published shared config. A console that invented a wider list would be inventing access. See **D31**.

**F4 — the three states exist, in three different places, and none of them is a field. (Exists / Gap / Rule)**

`running` exists and is well documented: the live registry is `/agents/<slug>/<run>` (`internal/budget/model.go`'s `AgentEntry`, `PathAgent`), the feed is `internal/watch/json.go`'s `BuildJSON` with `JSONRun` and `JSONFinished`, and the row type behind `fugaro runs ls` is `internal/runview/runview.go`'s `Row`.

**`needs attention` is a real concept in this tree, and it is a *skill's grouping* rather than a field.** `plugin/skills/working/reference/status.md` groups runs under "**Needs attention:** `failed`, `infra_error`, `error`, `halted`, `cancelled`, `unlaunched`", and every one of those is a state the CLI computes: `internal/runview/runview.go` carries the status constants (`StatusUnlaunched` among them) and `fugaro runs ls --json` prints them (`internal/cli/runs.go`'s `lsDoc`).

**`blocked` exists too, as something else entirely.** It is an `init` *stage* state: `docs/gcp-setup.md` lists what a stage prints as `done`, `changed`, `will-do`, `blocked`, `needs-you`, `skipped`, `failed` — a statement about an installation's converge, not about a task. The third meaning, a task whose dependency is unfinished, is the one the spec means, and that one needs the graph (F6). The other live signal in the tree is a *rate*: `internal/localcfg/localcfg.go`'s `(*Config).BurnAlert()` (from `watch.burn_alert_usd_per_hour`) feeding `internal/cli/watch.go`'s `watch.Config{BurnAlertPerHour: …}`.

**Rule:** a status dot may only colour a field a document carries — and the corollary is what makes this a finding rather than a quibble. `needs attention` **is** defined, but its definition lives in a *skill's prose*: the app may not read a skill file as data (F33's boundary), and it must not re-implement the grouping, because a console-side classification of run states is exactly the drift the "computed where it is read" argument forbids (F7). So the v2 answer is that the grouping **moves from `plugin/skills/working/reference/status.md` into the CLI's own document**, printed once, after which the dot is a colouring of it; a task-blocked state waits for the graph; an `init` stage's `blocked` is a different screen's word and should not be borrowed. The rate alert stays what it is.

**F5 — "total spend across projects" is a sum no single installation can back. (Gap / Rule)**

Spend lives per installation: `internal/budget/model.go` has `PathSpendGlobal`, `PathSpendRepo` and `PathSpendRun` under the installation's realtime database, `PathCapsRepo` for the caps, and the history job writes Firestore's `spendDaily` for the same installation. `fugaro budget show` prints one installation's figures (`internal/cli/budget.go`'s `budgetShowDoc`, whose `Project` and `GCPProject` fields say *which* installation they are about), and `fugaro report` reads the same installation's history (`internal/report/report.go`'s `Build`).

There is no cross-installation total anywhere, and the reason is not laziness: two installations' figures are two different currencies of trust — one is read live from a database this operator can read, the other may be a cached copy of a config fetched up to 7 days ago (`SharedOfflineFor`) with spend figures that are not in the shared config at all. **Rule:** the Overview shows one figure **per installation**, labelled with the installation it came from, and a summed total appears only where one installation's own documents back it. See **D32**.

### Dependency graph

**F6 — there is no planner artifact with task dependencies. (Gap)**

Nothing in this tree produces, stores or reads a task dependency graph. The plans under `docs/plans/` are prose task lists: `2026-10-15-desktop-console.md` ends with a hand-written "cross-task dependencies" list, and `2026-10-14-project-centric.md` orders its phases by hand in the same way. That is a real dependency graph, written by a person, in a format only a person reads.

The one machine-readable planner artifact is `mode: artifact`'s: `internal/runner/artifact.go`'s `renderPlanPath` is the constant `.fugaro/render-plan.json`, written by a run's plan step (`runArtifactMode`, `runRender`) and read by nobody: the comment on the constant says so in as many words — "a file in the checkout, read by nobody but a person (the render the runner runs is commands.render, never a plan the model wrote)" — while the prompt the plan stage gets (`artifactPlanPrompt`) says only that the plan "is not the deliverable" and asks the model to write it to that path. The plan document is about *render* steps, not tasks, and it carries no dependencies and no footprints. `internal/runstore/artifact.go`'s `RenderRecord` records what the render did; `internal/runstore/runstore.go` carries it as `Render *RenderRecord`. None of that is a task graph.

So the graph is **new work with no precedent to extend**, and it needs three decisions rather than one: where the artifact lives, who writes it, and what reads it. See **D25**.

**F7 — two of the four colours are computable today and two are not. (Gap)**

`done` and `running` come from documents that exist (`JSONFinished`, `JSONRun`, `AgentEntry`). `ready` and `blocked` are properties *of the graph* — a node with no unfinished dependency is ready — and since the graph does not exist (F6), neither does either colour. This is not a UI detail: "ready" is also what the launch action (F8) is allowed to act on, so a console that guesses "ready" is a console that can launch a task whose dependency is half-built.

**F8 — "launch selected ready tasks" is a write, and "fan out everything ready" is an unbounded one. (Gap / Rule)**

Launching exists: `fugaro run` (`internal/cli/run.go`'s `launchResult`, whose `status` is `launched` or `already-launched`), with `--task-file` for a task handed over as a file and `--retry` for "the stored task of RUN … that never started". But every launch is a **write** and a **claim**: `internal/runstore/launch.go`'s `(*Store).Claim` writes the `launching` object (`ClaimKey`) holding `{holder, at}` with `ClaimTTL` of 10 minutes, so that a second launcher of the same run gets `already-launched` instead of a second container. The console is read-only in v1 (D2), and D14 says read-only is enforced by the exact-argument allow-list **alone** — which means the allow-list is the whole fence, and a launch cannot be added to it without deciding that the fence has moved.

**Rule:** "fan out everything ready" is not a bigger button, it is a different risk class from "launch this one": it multiplies a write by a number the app computes, so the *app* decides how many containers run. If any fan-out exists in v2 it must be a single CLI command that takes the plan, applies the caps and the kill switch itself, and reports what it refused — never a loop of launches in the app. See **D22**.

### Command channel to orchestrators

**F9 — the queue contradicts D2 and D14 outright. (Wrong)**

"Console writes commands (e.g. start tasks 4 and 7) to a command queue in the realtime database" is a **write to a project's database by the desktop app**. That is exactly what D2 ruled out — its answer is *"**Yes, strictly read-only.** The three commands are shown copyable. When they arrive (v1.1), the app invokes the CLI's own command so the typed confirmation, the admin check and the ETag compare-and-set stay in the CLI."* (That second sentence is true of the budget writes the row is mostly about — whose confirmation is the typed one, `confirmTyped` — and **not** of `fugaro cancel`, which has no confirmation of any kind; the other writes D2 has in mind are confirmed by `--yes` or at a terminal rather than by typing. See F8.) And it is what D14's recommendation makes structural — *"Treat every identity as a possible admin, and give the read-only guarantee to the allow-list alone."*, which the owner accepted as recommended. An allow-list over argument vectors can express "this app may run `fugaro runs ls --json` and nothing else"; it cannot express "this app may write this one path in your database", because the app would hold a credential that can write all of them. Both answers are recorded in `desktop-console.md` §10 (D2, D14) and both are restated as Global Constraints in `2026-10-15-desktop-console.md`.

**F10 — there is no command queue, and nothing that would read one. (Gap)**

The queue the spec names does not exist in any form. The realtime database's paths in this tree are the budget and registry ones (`internal/budget/model.go`: `PathCapsRepo`, `PathSpendGlobal`, `PathSpendRepo`, `PathSpendRun`, `PathAgent`) plus the config and outcome paths the design's §2 table lists; no prefix holds commands, and no Go code polls one. What plays the queue's role today is the **runs bucket**, and it is a different design: `runs/<slug>/<run>/task.json` is written by the launcher and consumed by the Cloud Run job, `launching` is the claim, and the reader is `internal/backend/gcp`'s job path, not a poller.

The difference matters for the spec's own sentence: "orchestrating agents listen via a hook or a Fugaro command polled between turns". There is **no hook mechanism** in `plugin/` (the plugin is skills, not callbacks) and **no `fugaro` command that polls anything** — the command list in `internal/cli/root.go` is `version`, `validate`, `config`, `verify`, `exec`, `image`, `run`, `recipes`, `runs`, `logs`, `diagnose`, `cancel`, `secrets`, `accounts`, `init`, `budget`, `watch`, `report`, `update-skills`, `upgrade`, `doctor`. The nearest long-lived reader in the tree is `fugaro watch --json` (`internal/cli/watch.go`'s `--json` help: "print one JSON document per change instead of a screen"), which the console already owns — but it *reads*, and a queue needs a reader that *acts*.

**F11 — what a queue would cost, said plainly. (Rule)**

The v1 design's whole safety story is that the app is a spawner of read-only commands. A queue changes five things at once, and each is a decision the owner has to make rather than an implementation detail:

- **Who may write it.** The runs-bucket grant this tree settled on is per-prefix and shared by every run of a profile ([bucket-iam.md](bucket-iam.md)'s end-state table and its H2 alternative). A queue path in the same installation inherits that shape: whoever may write a command may write *any* command, including one addressed to a repository they do not own.
- **What runs it.** Nothing today. A queue needs a consumer that is always on, holds the project's credentials, and is not a Cloud Run job launched by a claim — that is a new service, in a tree whose every job is launched with a claim and dies.
- **Replay.** The launch path has a claim, a TTL and an `already-launched` answer (`Claim`, `ClaimTTL`, `ClaimKey`). A realtime-database command has none of the three: no ack, no expiry, no dedupe, and a consumer that reconnects re-reads. The claim is not a detail that can be added later — it is the only reason "two agents can't start the same task twice" is true today.
- **Authorization.** D14's recommendation — *"Treat every identity as a possible admin, and give the read-only guarantee to the allow-list alone."* — is the whole of the app's read-only posture. A write path makes the app an identity with a *project* credential, and there is then no fence left to describe.
- **The budget kill switch.** `internal/budget/kill.go`'s `SetKill` is the operator's stop — it *writes* the switch — and `internal/budget/evaluate.go` is what enforces it against spend: `Evaluate` returns `deny(ReasonKillSwitch, ScopeGlobal, …)` for the global switch and `deny(ReasonKillSwitch, ScopeRepo, …)` for the repository's, before it looks at a lease. The sweeper is not in that chain: its own doc comment says it "writes no counter, no cap, no switch, no mode, nothing under /config" (`internal/budget/sweep.go`). A launcher must consult the evaluation **before** launching, and `fugaro run` already has `--no-budget-check` as the explicit way to say "I know". A queue that launches jobs has to answer the same question in the same place, or the kill switch becomes advisory for exactly the path the console controls.

**F12 — the alternative the spec itself names is the thing that exists. (Exists)**

"Alternative path: console launches ready jobs directly via the Fugaro CLI; the agent sees them appear in the graph." Every part of that sentence has a counterpart in this tree: the launch is `fugaro run` (with `--task-file`, `--retry`, `--pr`, `--recipe`, `--json`), the outcome semantics are `fugaro cancel`'s (`internal/cli/cancel.go`'s `cancelResult`, whose constants distinguish the outcomes a cancel can have, and whose `marker` and `hard` fields say which of the two things cancel did), and "the agent sees them appear in the graph" is the run registry the agent's own budget session writes (`internal/budget/registry.go`'s `Session.Start`/`Update`, `AgentEntry`). What is missing is only the graph itself (F6) and the console's permission to write (F9).

**F13 — "polled between turns" has no command behind it. (Gap)**

There is no `fugaro` command that a long-running agent can poll for instructions, and adding one is not a small thing: it is the read half of the queue in F11, and it needs the same answer about who may write what it reads. The honest interim is that an agent between turns can run `fugaro runs ls --json` (`internal/cli/runs.go`'s `lsDoc`, `--json` at the same file) and see what is running — a **read**, which is what the console can do too. See **D21**.

### Sessions and orchestrators

**F14 — nothing registers an orchestrating session, and the registry that exists is a different thing. (Gap)**

The spec asks each orchestrator to "register a session with an ID, label, and project". The registry in this tree is `/agents/<slug>/<run>`: `internal/budget/model.go`'s `PathAgent` and `AgentEntry`, written through `internal/budget/registry.go`'s `Session` (`Start`, `Update`, `Finish`, with `goSafely` around the fire-and-forget writes) and leased in `internal/budget/lease.go` (whose `AddNotional` is what feeds the repository's and project's notional counters). It is **written by a running job about itself**, keyed by run, and it stops when the run stops.

An orchestrating agent is not a run: it has no container, no Cloud Run job, no slug binding and no budget token. The per-run identity this tree mints — `internal/budget/token`'s object at `runs/<slug>/<run>/budget-token` with claims `{fs, fr, fx, fp, rb}` — is exactly what a session would need and exactly what a session does not have. So a sessions registry is **new identity work**, not a new view over an existing table, and it is the single most expensive thing in this spec after the queue.

**F15 — the claim the spec wants exists, at the level of a launch rather than a task. (Exists / Gap)**

"Tasks are claimed before starting, so two agents (or an agent and the user) can't start the same task twice." Two claims exist and both are about runs, not tasks:

- the launcher's: `internal/runstore/launch.go`'s `(*Store).Claim` writing `launching` (`ClaimKey`) with `ClaimTTL`, read back by `ReadClaim`, so a second launcher sees `already-launched` in `launchResult.status`;
- the runner's: `internal/runner/lockcache.go`'s `ErrDuplicateExecution` ("another execution already owns this run"), with `internal/lock`'s branch lock beneath it so that two executions cannot push the same branch.

Both are the *right* answer to the question they answer. Neither prevents two agents from starting **the same task** in two sessions, because a task is prose in a plan file (F6) — there is no object to claim. Task-level claiming therefore arrives with the graph, not before it, and it should be built as a **claim on the graph's node**, with the same shape as `launching`: a holder, a timestamp, a TTL. See **D24**.

**F16 — "one graph per session" needs a per-session artifact that has no home. (Open)**

If sessions exist, each has its own view of the work, which means the graph is per-session rather than per-project — and then the question "where does a per-session graph live" has three possible answers (a file in the orchestrator's checkout, a path in the project's realtime database, a local file the console reads) with different trust properties, and the tree does not pick one for the owner. It is recorded as Open and folded into **D24**.

### Overlap detection

**F17 — no document the console can read carries the files a branch changed. (Gap, and the hard one)**

This is the finding most likely to be underestimated. `internal/runview/runview.go`'s `Row` — the row behind `fugaro runs ls` — carries `repo`, `branch`, `base_branch`, `pushed`, `pushed_head`, `pr`, `pr_url`, `requested_by` and `oauth_account`, and **no changed-files field**. `internal/watch/json.go`'s `JSONRun` and `JSONFinished` likewise. `internal/runstore/runstore.go`'s record carries the outcome, the render record and the artifacts, not paths. The files a run changed are known exactly once, transiently, and are then thrown away: `internal/followup/prompt.go`'s `PromptData.DiffStat` (clipped to `maxDiffStatBytes`, 4 KiB) is filled by the runner for the follow-up prompt — `internal/runner/followup.go` runs `sessionGit(ctx, r.repo, "diff", "--stat", "origin/"+base+"...HEAD")`, with `sessionGit` defined in `internal/runner/session.go` — and is never stored. (`internal/gitops/rejected.go` is the *other* thing a push produces: `ClassifyPush`, `PushRejected` and `WorkflowFiles`, which classify a rejected push and name the workflow files it touched. It builds no diff stat, and citing it for one is the kind of near-miss this section exists to avoid.)

So overlap detection cannot be a console-side computation over existing reads. It needs a **new recorded fact** — the set of paths a run's branch touched — written by the run (which knows) into the run's own record (which is read). That is a CLI change with a schema, a size bound and a rules/deploy consequence, and it is v2's second-largest piece of work after the graph. See **D27**.

**F18 — "expected footprint per task" has nothing to attach to. (Gap)**

The planner cannot add a footprint to a task that is not an object (F6), and the planning skill has no such output today (F31). The footprint is therefore part of the graph artifact's schema, not a separate feature — and it is **advisory by construction**, because a predicted path set is a prediction. See **D28**.

**F19 — "sessions grouped by repo" depends on sessions. (Gap)**

Follows from F14. What exists today is the repo grouping in the feed itself: `JSONRun`/`Row` carry `repo`, and the runs bucket is keyed `runs/<slug>/<run>`.

**F20 — the console gets changed files from the CLI or not at all. (Rule)**

The tempting shortcut is a GitHub token in the app: read the PR's files list and be done. It is the wrong answer for three independent reasons, and the third is the one that would bite. First, a token in the app is a **second credential** with a second trust boundary, in a design whose §3.4 **rule 7** says the console never stores a credential and whose §7.4 says nothing leaves the machine. Second, **the provider is not knowable** from any document the console reads — the v1 design's rule 2 spells this out: `pr_url` is a hostile field written by the run's own container, `internal/task/task.go`'s `Slug` hashes provider and repository together one way, and no JSON shape carries the provider, so the console cannot even tell whether a given run is on GitHub or Bitbucket Cloud. Third, the app would be **reading a third party's API about the operator's own repositories**, which is a new egress path in an app whose CSP is `connect-src 'none'` and which has no network client at all.

**F21 — "soft warnings, not locks" is the existing model. (Rule)**

`internal/lock` is a branch lock held *by a run* to stop two executions pushing the same branch, and it is not the console's to take: a console that locked branches would be a second writer to the same lock space. Overlap detection is a *report*, and the design's rule that the app writes nothing (except the opt-in spawn log, D20) means the report is a view, not a state.

### Version roadmap

**F22 — the project record the spec calls the source of truth does not exist yet. (Gap / Open)**

"Source of truth is the Fugaro project (stored with project state, e.g. in the project Git repo)." That is the owner's own end state, and this tree has it as a **planned** thing: `docs/plans/2026-10-14-project-centric.md`'s phase 6 is the backing-repository export — the `fugaro project export` command, whose owner-run check is **Check 56** in the same plan's reservations — and it is reserved and **not built**. Until it lands there is no project Git repository to hold a task's target version, and no document anywhere carries one: nothing in `internal/` has a version field per task, and the only versions in the tree are the CLI's own (`internal/cli`'s `Version`, `docs/releases/`, and the plugin's `fugaro-version` markers, e.g. `plugin/skills/parallelism/SKILL.md`'s `fugaro-version=0.7.5`).

Two interim options exist and both are cheap; the choice is the owner's (**D29**): the version lives in the plan artifact beside the task (works today, no new infrastructure, dies with the plan file), or the roadmap view waits for phase 6 (one source of truth, nothing to migrate, and the view cannot ship until then).

**F23 — a drag is a write. (Rule)**

"Drag tasks between versions" edits the project record. Under D2/D14 that is the same class of thing as the queue (F9): the app would hold a credential that writes the operator's project state. The shape that fits this tree is the one the v1 design already uses for its deferred write actions — the console shows the **exact command** that would make the change, the operator runs it in their own terminal, and whatever guard that command carries is the fence. See **D30**, and see **F8**: the CLI's existing writes are guarded by **a confirmation — typed, or `--yes`** (a typed one on `budget set`'s raise, `budget kill` and `budget resume` and on `image build`; `--yes` or a per-step terminal prompt on `init`'s stages, `config init` and `upgrade`), while `fugaro run`, `fugaro run --retry` and `fugaro cancel` are not guarded by one at all — so for a roadmap write that does not exist yet, the guard is a thing to specify with the command, not to assume.

**F24 — "dependency-aware: flags a task scheduled earlier than something it depends on" needs the graph. (Gap)**

Follows from F6. It is a pure function of the graph and the version column, so it is cheap *once* the graph exists and impossible before.

**F25 — "no GitHub milestones or Jira sync" is already this tree's position. (Exists / Rule)**

Nothing in this tree reads GitHub milestones or Jira; the provider story is [git-providers.md](../git-providers.md) and the provider clients are `internal/gitprov`'s `github` and `bitbucket` implementations of `gitprov.Provider`, whose whole surface is pull requests and their comments — `EnsurePR`, `Comment`, `UpdatePR`, `PullRequest`, `Comments`, `ApplyReady`, `GitAuth`, `Repository`, `FetchPRHead` — with **no commit-status method at all** (and `internal/gitprov/status.go` is not one: it is the `"### Fugaro status"` section the runner keeps current *inside the PR description* — `StatusHeader`, `StripStatus`, `ReplaceStatus`/`ReplaceStatusWith` (`internal/gitprov/status.go`); an earlier revision of this sentence wrote `Replace`/`Strip`, which are not functions in that file, and this document's rule is that a cited symbol exists). Nothing in it reads a milestone. (`internal/gitops` is not a provider client either — it wraps the `git` CLI a run needs; it has no provider API and no milestone read.) Worth recording as a rule the console inherits rather than as a thing to build: the roadmap's source of truth is Fugaro's own record, and the absence of a sync is a design decision, not an unfinished feature.

### Additional features (all wanted)

**F26 — the review inbox exists as data, and its links are governed by rule 2. (Exists / Rule)**

Finished jobs with their numbers and their `pr_url` are in the feed (`JSONFinished`, `Row`). The link is the governed part: the v1 design's rule 2 says the console **opens no PR link at all** until a document carries the repository's provider (its gap 7), because a GitHub-shaped guess is wrong on Bitbucket Cloud and dangerous where the name is someone else's. So the inbox ships as rows with copyable text, and it starts opening links the day gap 7 lands — no new decision here, only the note that "PR links" in the spec means "the PR number and URL as text" in the first version.

**F27 — desktop notifications are a new mechanism, with a new surface. (Gap)**

Nothing in this tree notifies a user about a job. The one thing that ever speaks up is `internal/updatecheck/updatecheck.go` — a daily `GET` against the releases endpoint, cached under `$XDG_CACHE_HOME/fugaro`, at most one nag a day (`WarnTTL`, `CheckTTL`, `FetchTimeout`) — and it is a version nag, not an event feed. **The two switches that silence it live on either side of it rather than in it**: the environment variable is the CLI's (`internal/cli/updatewarn.go`'s `noUpdateCheckEnv`, whose value is `FUGARO_NO_UPDATE_CHECK`), and the config key is the local config's (`internal/localcfg/localcfg.go`'s `Config.UpdateCheck` — the `update_check: false` field — read through `(*Config).UpdateCheckEnabled`); the check is in addition disabled automatically in several contexts. The nearest *live* signal is the burn alert the watch already computes (`BurnAlert()` into `watch.Config{BurnAlertPerHour: …}`).

A desktop notification needs three things this tree does not have: a long-lived reader (the console has one), a rule about **what may appear in a notification** (an OS notification renders outside the app's window, outside its CSP, and may be shown on a locked screen — so the content must be a fact from a document and never a string from a hostile field, which is the `pr_url` rule again), and the state the spec calls "needs input", which is not one of the states the CLI prints — the nearest is the "needs attention" grouping that lives in a skill's prose today (F4). See **D33**.

**F28 — per-job controls map cleanly: one read, two writes. (Exists / Rule)**

- **live logs** — a read: `fugaro logs` (`internal/cli/logs.go`'s `logLine`), or the watch feed's log lines.
- **cancel** — a write, and it exists: `fugaro cancel RUN` (`internal/cli/cancel.go`'s `cancelResult`), with its grace semantics and **no prompt at all** (no `--yes`, nothing read from stdin; the write is the run's cancel marker, `cancelResult.marker`).
- **retry** — a write, and it exists: `fugaro run --retry RUN`, "launch the stored task of RUN … that never started" (`internal/cli/run.go`).

So the mapping is complete and there is nothing to invent — which is exactly why D2 deferred these three to the CLI's own commands. **Rule — and this is the one place where this design corrects the merged v1 document rather than quoting it:** D2's answer, and this design's own first draft, said the app inherits *the typed confirmation* along with the command. **It does not inherit one, because there is none to inherit.** `fugaro run` has no `--yes` and reads stdin only for `--task-file -`; `fugaro run --retry` is the same; `fugaro cancel` has no confirmation of any kind. The CLI's writes carry **a confirmation — typed, or `--yes`** — and it is on the writes that loosen or halt a project and on the billable ones: **typed** on `budget set`'s raise, `budget kill` and `budget resume` (`internal/cli/budget.go`'s `confirmTyped`, which needs a real terminal and refuses a pipe or a coding-agent session — `--yes` confirms those too, but the typed path is the one that needs a terminal) and on `image build` (`internal/cli/image.go`'s `confirmBuild`, which reads the project's name, with `buildNotConfirmable` refusing the case where there is no terminal to ask); **not typed** on `init`'s stages (`internal/cli/init.go`'s `initRun.confirm`, which takes `--yes` or the project's name typed at a terminal — some of init's steps are typed-only), on `config init` (whose `--yes` flag is the whole confirmation: without it the command prints the file and exits 1, a dry run that writes nothing) and on `upgrade` (`--yes`, or a prompt at each step at a real terminal). A launch is deliberately not among them: anyone who may launch may launch non-interactively, which is the property that makes a console spawn possible at all. So when the console spawns one of these three, **the app's own confirmation is the only confirmation in the chain**; what the CLI adds is the budget pre-check, the claim and the command's own rules, and no question. That makes the app's confirmation a security-relevant surface rather than a UI nicety, and what it shows is the owner's decision, not the app's. This design recommends a confirmation on every one of the three, showing **the exact argv the app built, field by field, and the run id (or the task file) it is about to hand over**; the alternative — no dialog at all, which is defensible because the mechanical guards stay in the CLI either way — is the owner's to take, and it is the one the two SECURITY-SENSITIVE tasks are written to make visible rather than to assume. See **D22** and **D34**. If the console gets them, it gets them as *spawns of those commands*, shown with the argv it built (the opt-in spawn log, D20, is what makes that auditable), never as a console-side re-implementation. A console-side cancel would have to write the run's `cancel` marker itself, which is the write surface D2 keeps out.

**F29 — cap alerts have data and no threshold. (Exists / Gap)**

Caps and spend are readable: `fugaro budget show`'s `budgetShowDoc` (`internal/cli/budget.go`), the realtime-database paths in `internal/budget/model.go` (`PathCapsRepo`, `PathSpendGlobal`, `PathSpendRepo`, `PathSpendRun`), and Firestore's `spendDaily` for history. What does not exist is any notion of "approaching": the tree's one alert is a **rate** — `watch.burn_alert_usd_per_hour`, read by `(*Config).BurnAlert()` and passed into `watch.Config` — not a fraction of a cap. So "warn as a project approaches its cap" needs a threshold, and the question is where the threshold lives: a local setting of the app (a read-side computation over figures the CLI already prints) or a new field in the project record (a rules change, a deploy, and a version skew, for a display). See **D35**.

**F30 — spending graphs and live tasks exist. (Exists)**

`fugaro report` (`internal/report/report.go`'s `Build`, and the documents in `internal/report/render.go`: `JSONDoc`, `JSONLine`, `JSONTokens`) is the history; `fugaro runs ls --json` (`lsDoc`) and the watch feed are the live tasks. Both are reads the console's allow-list can already name, and both are already in the v1 design's data-source table.

### The independence-maximizing planning skill

**F31 — the skill exists and its budget is the constraint. (Exists / Gap)**

The planning and routing skills under `plugin/skills/` are `parallelism`, `routing`, `setup`, `upgrade` and `working`. The one that owns fan-out is **`parallelism`** (`plugin/skills/parallelism/SKILL.md`, whose description is "Plan work that could be split across several Fugaro runs: wide for independent work, narrow for coupled work, redundant attempts for one hard task. The lint budgets are in `plugin/skills_lint_test.go`: `maxSkillLines` 400 and `maxSkillBytes` 24576 for a `SKILL.md`, `maxReferenceLines` 300 and `maxReferenceBytes` 16384 for any other skill file, plus frontmatter rules (`name`, a `description` with "use when", 40–1024 characters). So a new skill costs a new directory, a new frontmatter, and a second place where fan-out advice lives and drifts. See **D36**.

**F32 — "cut dependencies with small interfaces/contracts" is already how this repo plans, by hand. (Exists)**

The console plan's own "cross-task dependencies" section and the project-centric plan's phase ordering are exactly this technique, performed by a person writing prose. The skill's contribution is to make the *output* machine-readable, not to invent the technique.

**F33 — "feeding the console directly" must not become a file the app reads. (Rule)**

Two fences stand in the way and both are load-bearing. The v1 design's data-plane rule is that **the CLI is the only data plane** — the console reads documents a `fugaro` command printed, never a file it found. And `console/README.md`'s Go/console boundary, enforced by `internal/cli/docs_console_boundary_test.go`'s allow-list, keeps the Go module and the console from importing each other. A planner artifact the console opened directly would be the first exception to both. So the skill writes the graph **where the plan lives**, and the CLI grows a command that prints it — see **D25**.

### The graph artifact's schema, written down (V2.2.1, V2.2.2)

**V2.2.1's task says the schema is written down in the design before it is written in Go, and this is that writing-down: version 1 of the graph artifact, the document a plan carries beside it.** D25 puts the graph on the plan's side rather than in a database and D28 gives a task's footprint its shape, but neither can hold a field list — and the field list is the one thing all three parties have to agree on, because the planning skill writes this document (V2.8.1), the CLI validates it and prints it (V2.2.1), and the console reads the printed form and never opens the file (D1, §3.4 rule 7). A schema that lived only in `internal/plan/document.go` would be one the skill's reference file copies out of Go source, which is how two spellings of one format start.

**The file, and how a read finds it.** The artifact is `docs/plans/<plan>.graph.json` — the plan `docs/plans/2026-10-15-desktop-console-v2.md` is described by `docs/plans/2026-10-15-desktop-console-v2.graph.json` — so a plan moved to another directory takes its graph with it, and a checkout may hold a plan whose graph has not been written yet. `fugaro plan graph --plan <path>` reads the artifact named after that plan; with no `--plan` it looks for `docs/plans/*.graph.json` **in the directory the command is run in**, and the three answers are three different things: exactly one artifact is read, none is a refusal that says to pass `--plan`, and more than one is a refusal that lists them. It never picks, because a guess here is the first thing a console would draw (F6: the graph is new work with no precedent to extend).

**The document, in full.**

```json
{
  "schema_version": 1,
  "plan": "docs/plans/2026-10-15-desktop-console-v2.md",
  "nodes": [
    {"id": "V2.2.1",
     "title": "the graph document, its schema, and the read that prints it",
     "run": "console-graph-1",
     "version": "0.9.0",
     "footprint": {"prediction": true, "paths": ["internal/plan/**", "internal/cli/plan.go"]}},
    {"id": "V2.2.2",
     "title": "the footprint",
     "run": null,
     "version": null,
     "footprint": {"prediction": true, "paths": []}}
  ],
  "edges": [
    {"task": "V2.2.2", "needs": "V2.2.1",
     "reason": "the footprint is a field of the document V2.2.1 defines"}
  ]
}
```

**Every field, and what its empty form says.**

| Field | Type | What it carries, and what an empty one means |
|---|---|---|
| `schema_version` | integer | The schema the document is written in. **1** is the only version this design defines, and a document carrying no version, or another one, is refused with **both numbers named** ("this graph is schema version 9 and this build reads version 1") — so "your CLI is older than your plan" is a different message from "this document is broken". |
| `plan` | string | The plan the graph describes, as a path, so a document found in the wrong checkout can be seen to be about another plan. Required and non-empty: a graph that does not say which plan it is about cannot be checked against one. |
| `nodes` | array of node | The tasks. **Always an array, `[]` when the plan has no tasks** — an empty array is a fact and a null is not (the availability rule the console's contract states, §1 of [json-contract.md](../../console/docs/json-contract.md)). |
| `edges` | array of edge | The dependencies. Same rule: `[]`, never null. |
| `nodes[].id` | string | The planner's own name for the task (`V2.2.1`): non-empty, unique in the document, and what the edges refer to. |
| `nodes[].title` | string | What a person reads on the node. Required — a node with no title is a node nobody can identify. |
| `nodes[].run` | string or null | **The state source D25's prose means**: the run this task belongs to, whose documents carry its state (`JSONRun`, `AgentEntry`), or `null` when it belongs to no run — the honest state of a task that has not been launched, which is not the empty string. |
| `nodes[].version` | string or null | The target version this task ships in (D29's "the plan artifact now"): the roadmap's source of truth until the project record carries one, and `null` when the plan does not say. |
| `nodes[].footprint` | object | The planner's expected set of paths (D28, below). Present on every node, so a renderer never has to ask whether the field is there. |
| `nodes[].footprint.prediction` | boolean | **`true`, always.** The label is a field of the document rather than a convention of the reader, so no screen can print a footprint as if it were a measurement. A document that says `false` is refused rather than corrected: a prediction is what this field is. |
| `nodes[].footprint.paths` | array of string | Glob-shaped paths in **doublestar** semantics — the ones this repository already uses (`doublestar.Match` in `internal/imagecheck`, `doublestar.Glob` in `internal/cache/key.go`, `doublestar.ValidatePattern` in `internal/config/validate.go` and `internal/verify/reports.go`), not a second implementation of globbing. Each pattern is validated when the document is read, so a malformed one is a refusal at the read rather than a pattern that silently matches nothing. `[]` means "this task predicts no path", which is not the same as a footprint that is absent. |
| `edges[].task` | string | The dependent: the node that waits. |
| `edges[].needs` | string | The dependency: the node it waits for. Both must name nodes the document carries — an edge to a node that is not there is refused, not dropped. |
| `edges[].reason` | string | **Why the edge exists, and it is required.** An edge with no reason is an edge nobody can check, and the field costs the planner one sentence. |

**What the read refuses, and why a refusal is the right answer.** A document from another schema version; one that is not JSON at all; one carrying a field this version does not define (refused by name rather than ignored, because an ignored field is a planner's work disappearing silently); a node with an empty or duplicated `id` or no `title`; an empty string where `run` or `version` may be null (the two are different claims and the empty string is the third, wrong one); a footprint that does not claim to be a prediction; a malformed glob; an edge naming a node the document does not carry, or carrying no reason. **And a cycle is refused, not drawn** — every "ready" and "blocked" answer is a function of the graph (F7), so a cyclic graph has no answers to give and a view that rendered one would be inventing them; the refusal names the cycle (`a -> b -> c -> a`) so the planner can fix it without hunting.

**What version 1 does not carry, said here so it is not added by accident.** No state field: `done` and `running` come from the run `nodes[].run` names, and `ready`/`blocked` are computed where the graph is read (V2.2.3, F7) rather than written by the planner — the planner cannot know them, and a document that guessed them would be a second answer to a question the CLI already answers. No bottleneck ranking (V2.2.3) and no overlap warnings (V2.4.1, which compares these footprints against the changed-file record of V2.1.2). **V2.2.3 and V2.4.1 both add fields to the document a read prints**, and the artifact's `schema_version` is what a console refuses on, so each of them states whether it bumps the version or adds fields a console may ignore; that decision is theirs to take and this section records that it is not taken here.

**Built, 2026-10-18 (V2.2.1, V2.2.2).** `internal/plan/` carries the document type, the parser and the validation, and `fugaro plan graph [--plan P] [--json]` is the read; it takes no cloud flag of any kind, which is what makes it safe to spawn with no installation selected. The same field list is stated for the console in §6.9 of [json-contract.md](../../console/docs/json-contract.md), and the key sets of the document, a node, an edge and a footprint are pinned by golden files under `internal/cli/testdata/`, so a field added to any of them fails a named test rather than reaching a screen.

### The installations document, and the fields it may not carry (V2.1.1)

**D31's read shipped on 2026-10-18 as `fugaro config list --json`, and its shape is deliberately narrower than any struct the tree already has.** The document names one entry per installation — the project name, the GCP project, the region, whether a shared config was merged, and when the shared copy was last checked — and nothing else. **It is not a marshalled `localcfg.Config`**, and that is the security property rather than a stylistic one: the config struct carries more than the console needs, so marshalling it would make every field added to it later join a document the app is allowed to read, silently, in a pull request about something else. The fields are named one by one in the document type, a test asserts that the type is not the config type, and a second test asserts that no field outside the named set reaches the output. The console's contract states the same list in §6.8, and the app still reads nothing itself (§3.4 rule 7): the operator picks from what the CLI printed, and D13's stored tuple and pairing check are unchanged. **A sixth field landed on 2026-10-20 (V2.1.1) and joins that list rather than changing it: `checkouts`.** It is the other half of D13's question — not only which installations this machine has but where the checkout of each one's repositories is — and it arrives in this document rather than through a second command, because a second command would answer the same question twice. One entry per remembered path: the repository identity, the path, whether it is still a checkout of that project and that repository, and a reason code when it is not (`internal/cli/config_list.go`'s `validateCheckoutPath`, over the state file in `internal/localcfg/checkouts.go`), re-validated on the read and never written by it. It is local state — never published to the runs bucket, never merged into the shared config — and absent, not empty, in the document an older CLI prints. §6.8 of the contract carries its row, so "the same list" there is now these six. **A seventh field landed on 2026-10-20, from the same read's security review, and it is the one the verdict turns on: `enrolled`.** A checkout's own `fugaro.yaml` saying `project: aurora` is a claim the checkout makes — a fork, a third-party repository or a hostile pull request can copy the line — so a path is `valid: true` only when the project's own config enrolls its repository as well, and the two facts are reported separately: `enrolled` is the local `repos:` map read (`(*localcfg.Config).Enrolls`), false when that config cannot be read, and an un-enrolled repository is `not_enrolled` rather than valid. The recorder holds the same rule on the write (`recordCheckout`), so an un-enrolled clone is never remembered and cannot spend the 20-repository bound. **And the review settled what a reader may do with a valid path, in one rule that rule 7 of v1 and §6.8 now both carry**: a `valid: true` row may be the child's working directory for an allow-listed read-only command and nothing else — never opened, joined, executed or passed as a flag by the app, and a `valid: false` row is never used for anything, including one whose path printing had to escape or truncate (a new reason code, `not_representable`, because the printed string names a directory the machine does not have).

### The changed-file record, and what it may not carry (V2.1.2)

**D27's record shipped on 2026-10-18: the runner reads the paths its own commits changed and writes them into the run's own `result.json`.** The range is the run's own work — `origin/<base>...HEAD` for a first run, the commit it started from for a follow-up (`gitops.ChangedFiles`, the same `workBase` the workflow guard and the work bundle use) — so a person's earlier commits on the branch are not this run's. A rename is recorded as the delete and the add it is: a path that moved is a path two runs can collide on, which is the whole point of the set. **It is read at the top of finalize and again once the run's own commits are final**, which is two reads for two cases rather than belt and braces: the first is what covers the runs that return early — an artifact run, a run the check gate ended — and the second is what covers a file the agent left uncommitted until finalize, which is committed just above it.

**What the record holds, and what it does not.** Paths, and nothing else: no contents, no diff, no commit message, no line counts, and no file sizes. This is the first time this repository stores a path outside a prompt, and the reason the omission is a rule rather than a preference is F17's own: **a path can name a client, a person or a project**, and the console is the one reader of this repository that runs on a machine the operator does not control the cloud side of. The record is bounded, and the bound is stated rather than implied — at most 200 paths, or 16 KiB of path, whichever comes first — and **a truncated set says so**: the record carries `total` (how many paths the run really changed) and `truncated`, so "this run changed 200 paths" and "this run changed 200 of 10,000" are different documents. A reader that showed a truncated set as a whole one would be showing a number the record does not support, which is why the console's contract spells the pair out (§5 of [json-contract.md](../../console/docs/json-contract.md)) and the human listing prints a truncated record as `N/M`.

**Absence is not emptiness.** The field is absent — never an empty object, never `paths: null` — for a run that recorded none: one that died before finalize, or one whose git read failed. Absence means "no record of what this run changed"; an empty `paths` means "this run changed no path". A view that collapsed the two would report an unknown as a fact, and V2.4.1's overlap comparison must not read a truncated or absent record as "no overlap" (that task's verification says so in as many words). What is read today: `changed_files` on every row of `fugaro runs ls --json`, and the `FILES` column the human listing grows **only when some listed run has a record** — a listing of runs from before the field looks exactly as it did.

**It is a schema change, and it is additive.** The field is `omitempty`, so a record written by this build is the record an older reader saw, and a console that does not know the key ignores it; the version handshake the v1 plan builds in phase 3 is what keeps an older console honest about a field it does not know rather than guessing at one it does. Nothing else about `result.json` changed, no new credential or egress path exists for it, and the record lives where the run's other facts live — the runs bucket, with the same trust as the rest of `result.json`.
