# Config transitions that retire cloud resources

Status: **implemented in 0.7.5** (plan Tasks 1–7; this paragraph was "docs only" when the design was written on 2026-10-14). Source: a real transition the owner performed on 2026-10-14, converting the `dimipaun/fugaro` repository from `agent.auth: oauth` to `api-key` with DeepSeek models. Every fact below is cited to the code or the doc read for it; no cloud call was made (Section 6 says which facts only a live run can settle, as owner-run checks — Check 42 in [../gcp-live-checklist.md](../gcp-live-checklist.md) is the one that remains). Plan: [../plans/2026-10-14-config-transitions.md](../plans/2026-10-14-config-transitions.md); its decisions can be vetoed one by one.

**What shipped, and which of §8's questions the owner answered.** The recommended answers were taken: 0.7.5 with everything (§8.1, not detection only), the orphaned job deleted through the Cloud Run API after the typed confirmation (§8.2, behind the ownership, label, terminal and agent checks of §4.2(c)), the Go-side address inventory kept as the consent list with the guard still running on the real plan (§8.4), no state access in `fugaro validate` (§8.5), and `docs/gcp-setup.md` restructured — one new section, "Changing auth, or removing a workflow, secret or provider", with the two manual sections pointing at it (§8.6), whose stale hand-written `removed { … }` advice is corrected rather than cross-referenced. On §8.3 the ordering pre-step stays documentation: `fugaro init --repo --allow-job-delete` is named in that section and in `docs/gcp-setup.md`, and the run's narrow gate (§3.3) still lets that path through unchanged; the retirement flow's own first choice is `--retire`, which is the one path the summary names. One thing the design did not foresee, found while implementing: `Readiness` unions every correctly-labelled live container back into `RepoSpec.Secrets` (its N4 rule), so §3.1a's convergence note would have been unreachable had it tested that map rather than the workflows' own mounts; the note asks the mounts.

Related: [project-secrets.md](project-secrets.md) (#329) shares this design's hazards — a scope move replaces IAM members and never destroys a container, and a narrowed `allow_data_to` can shrink a secret map — and this document keeps its vocabulary and cross-references it throughout. [v1.md](v1.md) §8.2 is the authority on `fugaro init`'s flow; this design changes nothing there that it does not name.

## 1. The origin (2026-10-14, verified against the code)

The owner changed `agent.auth` from `oauth` to `api-key` (DeepSeek through OpenRouter) in the `dimipaun/fugaro` checkout's `fugaro.yaml`, and ran `fugaro init --repo .`. What they got was raw Terraform text, before any plan list:

```
Error: Instance cannot be destroyed
  on secrets.tf line 4, in resource "google_secret_manager_secret" "this":
   4: resource "google_secret_manager_secret" "this" {
Resource module.repo.google_secret_manager_secret.this["claude-oauth-token"] has
lifecycle.prevent_destroy set, but the plan calls for this resource to be destroyed.
```

The `line 4` is real and checkable: `resource "google_secret_manager_secret" "this"` is declared at line 4 of `deploy/terraform/gcp/modules/repo/secrets.tf` (its `prevent_destroy` is at line 22). It is quoted here for the wrap, not the line; the plan turns this text into a literal fixture and regenerates it with a build-tagged test that really runs Terraform, so a module edit that moves the resource moves the line with it.

and the same for `claude-oauth-token-bmb`. **The user could not see what else the plan wanted to do**, because Terraform aborts a plan on `prevent_destroy` before it prints the resource list.

What the plan actually wanted — visible only after the owner had removed the protected addresses from the state by hand (`terraform state rm`) — was **2 imports, 6 creates, 3 updates and 11 deletes**, on top of the job deleted by hand through the API.

**The numbers this design uses, defined once, because four different counts are in play and every later section must mean the same thing by them:**

| Count, in the origin | Meaning |
|---|---|
| **14 retired addresses** | What the retirement set returns (§3.1a): every address the state manages that the new spec no longer produces. In the origin all 14 come from the state; after a failed run, the labels return the same set for the addresses the state no longer holds. |
| **12 going away** | The retired addresses whose resources are deleted from the cloud: 11 by the apply, 1 (the orphaned job) through the Cloud Run API. |
| **2 removed from state and kept** | The two OAuth secret containers: `prevent_destroy`, so they are state-removed and never destroyed. Their **values stay in Secret Manager** (§4.2a). |
| **3 state-removed before the plan** | 2 containers + the orphaned job. This is the step that makes a plan exist at all. |
| **11 deleted by the apply** | 12 going away − the 1 job deleted through the API. |
| **1 deleted through the API** | The orphaned job, after the apply. |

14 = 12 + 2, and 12 = 11 + 1. The counts are per-installation (the operator and launcher lists decide several of them), which is why the plan computes the list rather than printing a fixed one — 14 is this origin's number, with one operator and one launcher, not a constant.

**These are the numbers of the state alone, and the state is not the whole answer any more.** The incident happened before #329's N4 union was on `main`. `Readiness` now puts every live, correctly-labelled container back into `RepoSpec.Secrets` (`Existing.ExtraSecrets`), so **today's code re-adopts the two OAuth containers instead of retiring them**: the plan produces their addresses again, the repository module keeps making the four per-secret operator grants, and the retirement set is the other eight addresses — **8 retired = 7 going away (6 the apply deletes + 1 through the API) + 0 kept, and 1 state-removed before the plan** (the protected job; the containers are not removed from anything). The `14/12/2/3/11` set is still exactly what §1's narrative, §3.2's second shape and the fixtures of `internal/infra/retire_test.go` describe, and it is what a retirement sees when the label list does not find the containers — unlabelled, or a refused `secrets.list` (§3.1a) — which was the owner's case: the labels could not vouch for them, so nothing adopted them and Terraform refused to destroy them. Both sets are pinned: `TestRetirementsOriginTransition` for the 14, `TestRetirementsOriginTransitionWithTheUnion` for the 8.

Consequence for the two sections that quote counts: **§3.2 prints today's shape first and this one second**, and every later count of `14`/`12`/`3`/`11` in this document is this set's, not today's default.

- **2 imports**: the new api-key secrets (`anthropic-api-key`, and the provider key), created by `fugaro secrets set` through the Secret Manager API and adopted by label.
- **6 creates**: operator and job-accessor IAM members.
- **3 updates**: the surviving jobs' specs.
- **12 going away**, and here they are, because this set is the fixture the plan's tests pin. Seven are the old named-account variant `module.repo.module.workflow["go_bmb"]`: `google_cloud_run_v2_job.this[0]`, `google_service_account.job`, `google_service_account_iam_member.operator[<the one operator>]` (one per operator, `modules/workflow/sa.tf:12`), `google_cloud_run_v2_job_iam_member.launcher[<launcher>]`, `google_secret_manager_secret_iam_member.job["claude-oauth-token-bmb"]`, `google_secret_manager_secret_iam_member.job["<the git credential>"]` and `google_storage_bucket_iam_member.job`. The other five are the bindings tied to the two OAuth secrets: one accessor on the *surviving* default-account variant, `module.repo.module.workflow["go"].google_secret_manager_secret_iam_member.job["claude-oauth-token"]` (the default variant keeps existing but stops mounting the OAuth token), and, for each of the two containers, the two operator grants the repository module makes per secret — `google_secret_manager_secret_iam_member.operator[…]` with roles `roles/secretmanager.secretVersionAdder` and `roles/secretmanager.viewer` — four addresses with the one operator this installation had. Seven plus one plus four is twelve going away. The **two secret containers** are the thirteenth and fourteenth retired addresses: they are state-removed, never deleted, and their values stay in Secret Manager. So in the origin the retirement set returns 14, 3 of those addresses are state-removed before the plan, the apply deletes 11, and the API deletes 1 — the job. That is also what the owner's own run says: they passed **11** addresses to `--allow-delete`, with the job already out of the state, so the apply deleted 11.

The owner resolved it by hand, in this order:

1. `terraform state rm` of the two OAuth secret containers and of `module.repo.module.workflow["go_bmb"].google_cloud_run_v2_job.this[0]`, in the repository's workdir (`$XDG_STATE_HOME/fugaro/terraform/<gcp-project>/repos/<slug>/gcp/roots/repo`, after `terraform init -backend-config=backend.hcl` with `TF_CLI_CONFIG_FILE=<workdir>/terraformrc`). Two different hazards forced this: a secret has `prevent_destroy`, and **a job whose workflow has left the configuration keeps `deletion_protection = true` in the state**, so `--allow-job-delete` can no longer lower it (`--allow-job-delete` is a *variable* of an apply that still contains the job; once the job is gone from the configuration there is no resource left to carry the variable).
2. `gcloud run jobs delete` of the orphaned job.
3. `fugaro init --repo . --allow-delete <the 11 addresses the plan then wanted to delete, from the 12 going away>`.

The OAuth tokens stayed in Secret Manager: never destroyed, and now unmanaged. Nothing in the product told the user any of this. The only documentation is the manual outline in [gcp-setup.md](../gcp-setup.md) ("Turning checks off, or removing a workflow", "Offboarding a repository"), which says the order matters — lower deletion protection **before** changing `fugaro.yaml` — and which a user who has already changed the file, as this one had, cannot follow.

**The three failures this design closes.** (1) The failure is surfaced as Terraform's own text, which names a lifecycle attribute rather than the config change that caused it. (2) The failure comes *before* the resource list, so the user cannot see the blast radius, and cannot decide. (3) There is no supported path at all: the only way through is `terraform state rm` by hand in a workdir that `PrepareWorkdir` overwrites on the next run (`internal/infra/workdir.go`, which `RemoveAll`s `dir/gcp` and rewrites the embedded tree afresh).

## 2. Inventory: which config changes retire resources

Read from `deploy/terraform/gcp/modules/{repo,workflow,installation}` and `internal/infra/spec.go`, not guessed. The address prefix `module.repo` is the repository root; `module.repo.module.workflow["<variant>"]` is one workflow variant.

**What one workflow variant owns** (`modules/workflow`): `google_service_account.job`; `google_service_account_iam_member.operator[<operator>]` (one per operator); `google_storage_bucket_iam_member.job` (the runs-bucket condition); `google_secret_manager_secret_iam_member.job[<logical>]` (one per mounted secret); `google_project_iam_member.vertex[0]` (only when `agent.auth: vertex`); `google_cloud_run_v2_job.this[0]` (`deletion_protection = !var.allow_job_delete`, `job.tf:15`); `google_cloud_run_v2_job_iam_member.launcher[<launcher>]` (one per launcher).

**What the repository root owns besides those** (`modules/repo`): `google_secret_manager_secret.this[<logical>]` for every logical name in `rs.Secrets` (**`prevent_destroy = true`**, `secrets.tf:22`); `google_secret_manager_secret_iam_member.operator[…]` (two per secret × operator: `secretVersionAdder` and `viewer`); `google_artifact_registry_repository.images` (**`prevent_destroy = true`**, `registry.tf:59`); `google_artifact_registry_repository_iam_member.operator_images[<operator>]`; the build account and its grants (`google_service_account.build`, `…_secret_iam_member.build[…]`, `…_registry_repository_iam_member.{build_images,build_tag_mover,build_base}`, `google_project_iam_member.build{log_writer,build_submitter}`, `google_service_account_iam_member.{build_self,operator_build[…]}`); and, when any workflow is checked, `google_cloud_run_v2_job.check[0]` (**`deletion_protection = !var.allow_job_delete`**, `check.tf:27`), `google_cloud_run_v2_job_iam_member.check_invoker[0]` and `google_cloud_scheduler_job.check[0]`.

The rows below use these two abbreviations: **PD** = a `prevent_destroy` container (Terraform refuses the plan outright, before `tf.Guard` ever sees it), **DP** = a `deletion_protection` job (the *provider* refuses the delete at apply time unless the protection was lowered by an earlier apply, while the resource was still in the configuration).

**What this inventory settles.** Only two protections are in play, and they fail at different times and in different ways: `prevent_destroy` fails **at plan time, before anything is listed**, and `deletion_protection` fails **at apply time, after the plan was shown and confirmed**. Every retirement in rows A–F has one or both. That asymmetry is why §3 must compute the list itself rather than read it off Terraform's output, and why §4(b) needs its own mechanic for jobs.

## 3. Detection and explanation

### 3.1 Detect from the state and the spec, before Terraform runs

`fugaro init --repo` already computes, in Go, the complete spec and therefore the complete set of addresses Terraform will manage: the tfvars come from `infra.Repo` (`spec.go:747`) and the imports from discovery (`internal/infra/imports.go`, whose `importTable` is a per-kind address template). It already reads the state (`TF.ShowState`, `internal/infra/tf/tf.go:246`, giving `State.Addresses()`, `tf.go:219`).

So the retirement set is a set difference, computed with no Terraform run at all:

```go
// package infra
// Retirement is one resource the new configuration no longer produces.
type Retirement struct {
    Address string
    Kind    string // "secret container", "workflow job", "check job", …
    Cause   string // the config change, in the user's words
    Kept    string // what survives: "the secret and its value stay in Secret Manager"

    // The fields the later steps need, which a state address alone cannot
    // give. A retired secret's logical name is no longer a key of
    // rs.Secrets, so its Secret Manager ID cannot be looked up there; a
    // retired job's name and region are the job's, not the address's.
    Logical  string // the logical secret name, for a container ("" otherwise)
    SecretID string // its Secret Manager ID, for a container
    Job      string // the Cloud Run job name, for a job
    Region   string // the job's region, for a job

    // Protected is whether an ordinary apply can delete this address at all,
    // which is what tells Removals (§4.2a) which addresses it must take out
    // of the state. It is true for a secret container, whose module carries
    // prevent_destroy, and for a job whose state says
    // deletion_protection = true. It is read from the state like the fields
    // above, and never guessed from the address alone: a job whose protection
    // is already false is one the apply deletes, and state-removing it would
    // leave it alive in GCP with nothing managing it (§3.3's documented flow,
    // where the user lowered the protection before editing fugaro.yaml).
    Protected bool

    // ProtectedRead is whether that protection was actually read, and it is
    // what lets §3.1's refusal rule be expressed at all: an unread
    // deletion_protection is Protected (the conservative default the removal
    // set needs) *and* not read, so the gate below can refuse on a value the
    // state carries without refusing on one it does not.
    ProtectedRead bool
}

// Retirements is the addresses the state manages that spec no longer
// produces. Both sides are computed by fugaro; the user types neither.
func Retirements(state []string, spec RepoSpec) []Retirement
```

`SecretID` and `Logical` come from the **state's own attribute values**, not from `spec`: `TF.ShowState` (`tf.go:246`) returns a `*State` whose modules keep each resource as raw JSON (`StateModule.Resources []json.RawMessage`, `tf.go:199`), so `address` and `values` are both there to decode — the retired container's `secret_id` attribute is right there. `Job` and `Region` come from the job's state attributes (`name`, `location`) the same way, which is also what makes the label check in §4.2(c) possible without a name the spec can no longer produce. **`Protected` comes from the state too, and from a different kind of attribute:** a container's is implied by its address kind (its module declares `prevent_destroy`), while a job's is the job's own **`deletion_protection`** attribute in `values` — the same attribute §3.3's gate reads, so the gate and the removal set cannot disagree about which jobs the ordinary path can finish. A job address whose `values` cannot be read at all counts as **protected** (the conservative direction: it is state-removed and then handled by the §4.2(c) API delete, which works whatever the flag says, so nothing is ever left alive); the *gate* refuses only on a value it actually read as `true`, which is what the struct's **`ProtectedRead`** carries — `Protected` alone cannot tell a state that said `true` from one that said nothing, and the gate's refusal quotes the state. **The decode has a named home and needs no change to `internal/infra/tf`:** `infra.FillFromState(st *tf.State, rets []Retirement)` lives in `internal/infra/retire.go` (`internal/infra` already imports `internal/infra/tf` for `RetireAllowDelete`'s `*tf.Plan`), walks the exported `Resources` of `st.Values.RootModule` and its children, and fills those fields — so `State.Addresses()`'s narrower decode stays as it is. Where a state is unreadable, a resource is not in the state, or an attribute is missing (a provider version that renames it), the field stays empty and the summary prints the address alone — degraded, never guessed. The attribute names are the provider schema's, and Check 42's live run is what confirms them against a real state (§6).

### 3.1a The second source of truth: label discovery, which is what makes a delete resumable

**The state alone cannot answer the question a rerun asks.** `Retirements` is `state − spec`, and the retirement's first step *removes addresses from the state* (§4.2a). So if the apply, the guard or the API delete then fails or is refused, a rerun computes `Retirements` again, the job is no longer in the state, and nothing mentions the orphan — the exact "state and cloud disagree silently" case §6 forbids, for the origin's own job. The state cannot be the record of a thing the flow deletes *from the state*.

So there is a second, cheaper source, and it is the cloud's own: **the labels**. Discovery owns the rule (`v1.md` §8.2: a resource under one of our names that exists **and** carries our mark is ours), and the orphan set applies it to the resources that can outlive the configuration. Both are new API calls, not an existing path — this section's first draft claimed `DiscoverRepo` "already lists" labelled secrets, and it does not: `DiscoverRepo` **`Get`s each logical name in `rs.Secrets`** (`discover.go:546-572`), so it can only see the containers the new spec still produces, which is exactly the ones an orphan is not.

- **Cloud Run jobs, two rules, because the two kinds of job carry different labels.** Both start from a `jobs.list` in the repository root's project/region, keeping `fugaro=managed` and `fugaro_repo=<this repository's label>` (`modules/workflow/job.tf:11-14`, `modules/repo/check.tf:22-26`):
  - a **workflow job** carries **`fugaro_workflow=<variant>`** and is an orphan when that value is **not a key of `spec.Workflows`** — the variant has left the configuration.
  - the **check job** carries **`fugaro_role=check`** and **no `fugaro_workflow` at all** (`check.tf:22-26`), so it must be excluded from the workflow rule and given its own: it is an orphan **iff `spec.Check == nil`** (no workflow is checked any more: `rs.Check` is set only when `checked` is non-empty, `spec.go:816-823`). Without that split, a live check job would read as an orphan on **every** run, because "no `fugaro_workflow`" is not a key of `spec.Workflows`.
  The job's name and region come from the list call itself, which is why `Job`/`Region` no longer depend on the state at all.
- **Secret Manager secrets**: a **new `secrets.list` with a label filter** (`fugaro=managed`, `fugaro_repo=<label>`, and one `secrets.get` per listed container for its `fugaro_secret` label), keeping the containers **no job of the configuration mounts any more** — `rs.Workflows`' and `rs.Check`'s own `SecretEnv`, not the `rs.Secrets` map. The map cannot answer this question: Readiness has already unioned every live, correctly-labelled container back into it (N4, the note rule below), so every container this list can return is a key of it, and a test against the map would skip all of them and leave the note unreachable in the real flow. The mounts are the pre-union answer — "does anything of fugaro.yaml still mount this name?" — which is exactly what the note is about. **This call does not have the permission story the job calls have, and the design says so rather than assuming it.** `secretmanager.secrets.list` and `secretmanager.versions.list` are in the installation's launcher custom role (`modules/installation/iam.tf:8-20`, alongside `run.jobs.get`/`list`, `run.executions.*` and `run.operations.get`), but that role is granted to `var.launchers` only (`iam.tf:58-62`) — it is the launcher's role, not the operator's. The run uses the **operator's own ADC** (`infra.NewClients`, `discover.go:100`), the same credentials the apply uses, so whether that ADC holds `secretmanager.secrets.list`, and whether it holds `run.jobs.list` on the project, is **not verified offline and is not assumed**: Check 42's live run is what settles it (§6), and the degradation path below is what happens if it does not. **A kept container that is no longer in the state is an informational note, not a retirement** — it is a secret an earlier retirement (or a hand `state rm`) already released, there is nothing left to do about it, and §3.1a's whole purpose is that the user is told their value is safe. **Only a state-held address or an orphan job makes the retirement set non-empty and prints the summary; a kept container alone does neither** — and a non-empty set prints a summary and names the next command, it does **not** by itself open the *refusal* gate, which is §3.3's and is narrower than the set. Otherwise every later `fugaro init --repo` would re-report the two OAuth tokens forever. The containers the *current* retirement releases are still named in the summary's `KEPT` block, because their addresses are in the state or in the orphan list when the run starts.

```go
// package infra
// Orphans are the cloud resources the labels say are ours that spec no longer
// produces, in two groups:
//   - Retirements: a workflow job whose fugaro_workflow is no longer a
//     variant key, or the check job (fugaro_role=check) when spec.Check is
//     nil.
//   - Notes: a labelled secret container whose logical name is no longer
//     mounted, and which the state no longer holds. Informational only:
//     RetireSet never counts one as a retirement, so it cannot make the
//     summary, the gate or --retire fire on their own.
func Orphans(ctx context.Context, c *Clients, spec RepoSpec) (retirements []Retirement, notes []Retirement, err error)
```

**A label call that is refused degrades loudly, and never silently.** `Orphans` runs on every `fugaro init --repo` and under `--plan-only`, so a `PERMISSION_DENIED` from `run.jobs.list` or from `secrets.list` is a normal outcome to be handled, not an exceptional one, and it may not be treated like the *delete*'s 403 (§4.2c): the delete is a mutation that must not be guessed at, while these two calls are reads whose failure only narrows what the run can see. So a refused or failed label call prints a warning line naming the call, the permission, the `gcloud` equivalent and the consequence — "orphaned jobs/secrets cannot be checked; anything the state no longer holds will not be named" — and the run **continues with the state-derived retirement set**. A refusal is a **false-negative** risk, never a false positive and never a silent one; the two halves are reported separately, so "nothing to retire" and "could not look" are different sentences. If the state half is empty and a label half failed, the summary says the check could not be made rather than claiming there is nothing to retire — and because the same call runs under `--plan-only`, a user who sees no orphans there learns why.

**The same rule covers the label list discovery already makes.** `DiscoverRepo` lists the repository's secrets by label to union the live containers back into the plan (N4, `discover.go`'s `extraSecrets`), and that is the *same call* — same filter, same permission — as `Orphans`'s: in the origin case both are refused together or neither is. So a refusal there degrades the same way rather than ending the run: a note names the call, the permission, the `gcloud` equivalent and what is lost (the union), and the ordinary `fugaro init --repo` goes on. The consequence is narrower than silence: a container the configuration no longer computes is left out of the plan's `for_each` instead of being adopted back into it, so the plan meets the module's `prevent_destroy` and §3.3's abort is what the user reads — the retirement path's own explanation for exactly that state. (Before this round the refusal was a hard error, which contradicted this section's rule and made Check 42's recorded warning unreachable for `secrets.list`.)

**The retirement set is the union** — `Orphans`'s retirements ∪ `Retirements(state, spec)` — deduplicated by address, with `Orphans` winning on the fields it fills (`Job`, `Region`, `SecretID`, `Logical`) because it read them from the live resource. `Orphans`'s notes are printed beside the summary and are **not** part of the set, so a run with nothing to retire says so in one line and does nothing else. Both sides print the same summary, and the union is what the allow-list is intersected with, so a rerun's allow-list covers exactly what the rerun plans.

**A journal was the other candidate, and it is rejected.** A file outside `dir/gcp` recording "removed from state, not yet deleted" would work, but it needs its own location, its own lifecycle and its own garbage collection, it must survive `PrepareWorkdir`'s `RemoveAll` (§1's third failure) without becoming a second state store fugaro has to trust, and it would still be wrong if the user deleted the job by hand or ran `gcloud` — the labels are simply the record of what exists, kept up to date by the cloud itself. `Orphans` is also *read-only*: a `jobs.list` and a `secrets.list`, no new credential and no new scope — the same `infra.Clients` the repository root already builds (`discover.go:100`), under the operator's own ADC, which Terraform already runs as — and it runs in `--plan-only` too, because listing changes nothing.

`spec` needs one new method — the addresses it will produce — which is the same shape `importTable` already uses:

```go
func (rs RepoSpec) Addresses() []string
```

**Its completeness is the design's one unguarded assumption, so §6 pins it with a golden test rather than trusting the mirror.** `Addresses()` duplicates what the Terraform modules declare, and a module change that adds a resource without a matching line here would show up as a *false retirement* — the safest possible direction for the error, but still an error. The test compares `Addresses()` against a real `terraform plan`'s `resource_changes` for a fixture spec (the repository already keeps such fixtures: `internal/infra/tf/testdata/plan_*.json` and `real_terraform_test.go`), so a new resource in a module fails CI until its address is added. A miss is never silent and never retires anything for real, because §4(d) intersects the allow-list with the *plan's* addresses: an address `Addresses()` failed to predict is not in the summary, so the guard still refuses it.

**Why this and not Terraform's plan.** Terraform's plan is authoritative for what is *applied*, but it is exactly what is unavailable in the origin case: the plan aborts on `prevent_destroy` before listing anything. The Go-side set is available earlier, is deterministic, and is what the consent is about. It is a **prediction used for explanation and consent**, never a substitute for the guard: §4(d) still runs `tf.Guard` on the real plan, and §4(e) still refuses anything the prediction did not name.

Printed **instead of** Terraform's text, **before the plan**, whenever the retirement set is non-empty — a state-held address or a label-discovered orphan job, never a kept container alone (§3.1a). Shape (this is the origin case, with #329's union on `main`, which is the code of the day: the numbers are the ones §1's note derives):

That is the shape §1's unlabelled case produces — **14 retired, 12 going away, 2 kept, 3 state-removed before the plan** (§1's note has the two number sets side by side, and says which is which) — and it is what a state-only retirement sees before discovery has run in front of it. The `KEPT` list is still built from the same label discovery as the orphan set (§3.1a), so **a rerun after a failed delete still names the kept secret** even though its container is no longer in the state. Its addresses come from `Orphans` for exactly that reason.

**The summary shows no imports, creates or updates, and no deletes other than the retirement's own.** It is printed *before* the plan, so those numbers do not exist yet — this section's first draft printed `2 imports, 6 creates, 3 updates, 11 deletes` in a summary that runs before any plan can (§3.3's own argument: no plan exists until the protected addresses have left the state). The plan's own counts, and the *real* delete list, are shown **after** the plan, at the second confirmation of §4.2. Step 1's count is the state removal's own: every address step 1 takes out, the API-deleted jobs included, which is why it can exceed the rows of the `Removed from Terraform's state` list (that list is the narrower one: what leaves the state and is then never deleted).

The three `<…>` tokens in the first line are **placeholders**: the origin's real project name, GCP project ID and repository are the owner's, and this document does not reproduce them.

Every line is required by the origin's three failures: *what* is going (the address list, which Terraform never printed), *why* (the config change, which Terraform's text never named), *what is kept* (so the user does not fear for their tokens), and *the exact next command*.

### 3.3 When Terraform aborts early anyway

Three guards, all cheap:

- **The summary is computed before `t.Plan`**, so in the normal path the raw text is never shown.
- **If `t.Plan` fails**, `fugaro init --repo` matches the failure against the `prevent_destroy` signature (`has lifecycle.prevent_destroy set, but the plan calls for this resource to be destroyed`) and, when it matches, prints the retirement summary and the next command **instead of** Terraform's stderr, and exits 1. This is the fallback for the case where the Go-side prediction and the real plan disagree — for example a hand-edited workdir, or a `prevent_destroy` trip this design's inventory does not model. Terraform's own text stays in the `--json` result's `failed[].error` and in the workdir's logs, so nothing is hidden, only re-framed. **The match is whitespace-normalized, and that is a requirement, not an implementation detail:** Terraform wraps this message to the terminal width, and §1's own quoted output is the proof — it breaks after `has`, so a literal substring match on the signature never fires on the real text. Both the haystack and the needle are collapsed (every run of whitespace, newlines included, to a single space) before the substring test, and the resource address is read from the same normalized text. §6 pins it with the real wrapped output as a literal fixture, and the build-tagged `internal/infra/tf` test that really runs Terraform generates that output so the fixture cannot go stale (Task 6).
- **`--plan-only` stays read-only, and `--retire` and `--plan-only` exclude one another.** `--plan-only`'s documented contract is that it "creates and changes nothing" and never takes `--yes` (`init.go:364`, `:476`, `:709`), and `terraform state rm` **is** a change to the state — so the first draft of this section was wrong to let `--retire --plan-only` do the §4.2(a) removals "because it changes nothing". The two flags join the existing mutual-exclusion rule (`init.go:709`), and a plain `fugaro init --repo --plan-only` reads the state, prints `printRetirements` first, and then **continues into the ordinary read-only path**: it shows the ordinary plan (its counts and its delete list) whenever one can be produced, and exits, having removed nothing, deleted nothing and applied nothing. It is not "print the summary and stop" — a run whose plan can be produced must still show it. **In the origin case no plan can be produced**, because the protected addresses are still in the state and Terraform aborts before listing anything, so the summary *is* the whole of what it can show, and it says so; that is §3.3's own argument for removing them before the plan, and it is why the real delete list is available only from `--retire` itself. Task 5's tests pin both halves (`TestInitRepoPlanOnlyRemovesNothing`, and the plan-shown assertion in `TestInitRepoPlanOnlyStillShowsThePlanWhenItCanBeProduced`).
- **The refusal gate is narrow: it fires only where today's path already dies, so it does not replace the documented flows.** The summary is printed whenever the retirement set is non-empty — that alone is a warning, not a refusal. The run refuses (exit 1, naming `fugaro init --repo . --retire`) only when the retirement contains an address the ordinary path cannot finish:
  - a **`prevent_destroy` container**, and this one is detected *lazily*: the plan is attempted, and the refusal happens on the §3.3 signature above, not on a guess. A false positive from the hand-maintained `Addresses()` mirror (§3.1) therefore cannot turn every `fugaro init --repo` into a hard block; it shows up as a summary line and the plan decides.
  - a **DP orphan** — a job address the retirement set holds **whose state says `deletion_protection = true`**, i.e. the job still carries the protection *and* has left the configuration, so no apply can lower it. **The gate reads the attribute, and it must:** `FillFromState` (`§3.1`) already decodes the same `values` map, and `deletion_protection` is one of the job's own attributes in the state. A job address whose protection is **already false** — the user who followed `gcp-setup.md`, lowered the protection with `--allow-job-delete` *before* editing `fugaro.yaml`, and is now running `init --repo --allow-delete <addresses>` — is **not** refused: that is the documented flow §3.3 promises to keep working, and refusing it on the address alone would break exactly the user who did the right thing. Protection `true` in the state plus a variant that has left the configuration is the only combination that cannot finish, because the provider refuses the delete at apply time.
- **Everything else keeps working exactly as `gcp-setup.md` documents it today, and "non-empty" is not a refusal.** Removing a workflow, dropping a secret from a workflow, turning checks off: the summary prints, **the run continues into the ordinary path** — the plan runs, `tf.Guard` refuses the deletes as it always has, and `--allow-delete <addresses>` does what it has always done. The summary names `--retire` as the one-command alternative, but nothing stops the user who prefers the manual route, and **no exit status changes for them**: the refusal is the two blocking cases above (the `prevent_destroy` plan abort, and a state-held job whose state says `deletion_protection = true` after its variant left the configuration), and a job whose protection is already false is exactly this bullet's case, not a refusal. `--retire` is added *at the point where that flow stops working*, not in place of it.
- **`--retire` accepts `--allow-delete`, and the two are intersected.** The effective allow-list is `RetireAllowDelete(plan, rets) ∩ --allow-delete` when the flag is given, so adding `--allow-delete` to a retirement can only *narrow* what may be destroyed, never widen it; and `--allow-delete` alone can never permit a `prevent_destroy` container, because no plan exists to name it in. **Owner question Q3 covers the reverse case** (a user who has not yet edited `fugaro.yaml` being offered `--allow-job-delete` first).

## 4. A supported, guarded path

**Every command, flag and file name this section proposes is proposed, not shipped: `fugaro init --repo --retire`, its `⚠ RETIRE` banner, `Retirement`, `Retirements`, `RepoSpec.Addresses()` and the orphaned-job delete do not exist in any released fugaro.** The mechanisms they are built from — `(*TF).StateRm`, `tf.Guard`, `--allow-delete`, `--allow-job-delete`, the typed confirmation, the agent-session refusal, `ForgetAllowDelete` and `HardeningAllowDelete` — all do exist, and this section says which is which each time.

### 4.1 Command shape: three options

- **Option A — a mode of `fugaro init --repo` (`--retire`).** *Recommended.* The state, the workdir, the spec, the plan file, the guard and the confirmation all already live in `init --repo`; the user is already in that flow; and the config change that caused the retirement is the same checkout's `fugaro.yaml`, so the two cannot drift apart. The cost is one more flag on a command that already has many, and a mode inside a flow whose existing confirmations must not be weakened.
- **Option B — a dedicated `fugaro repo retire`.** Cleaner separation and its own banner, and it reads better in documentation. But it duplicates the workdir, spec, discovery and plan plumbing (all of which are `init --repo`'s, not a subcommand's), and it splits one intention — "my config changed, make the cloud match" — into two commands a user must sequence correctly, with the risk that it is run without the config change, or that the config change is applied by a later plain `init --repo` that the user never associated with it.
- **Option C — document it only.** *Rejected.* The origin is the evidence: the documentation exists (gcp-setup.md), the user had already passed the point where it could be followed, and the only feedback the product gave was a Terraform lifecycle error. Documentation is not a supported path.

### 4.2 Mechanics

**(a) Removing a retired address from the state — `terraform state rm`, which fugaro already has.** The addresses come from the retirement set of §3.1/§3.1a (state-minus-spec **plus** the label-discovered orphans), and are then narrowed by `Removals` to **the ones Terraform cannot remove for us**: still in the state, **and `Protected`**. **Both halves of that test are per-address facts, not a property of the retirement set:** "still in the state" is read from `State.Addresses()`, and `Protected` is §3.1's own field — `true` for a container (its module's `prevent_destroy`) and for a job whose state says `deletion_protection = true`. A job whose protection is already **false** is therefore *not* returned, even though it is retired and still in the state: the apply can and must delete it, and state-removing it would leave it alive in GCP with nothing managing it. This is the same distinction §3.3's gate makes, read from the same attribute, so the two can never disagree. That narrowing is not an optimisation, it is the correctness condition of the whole step. The retirement set's other addresses — a retired variant's service account, its IAM members, its bucket grant — are **not** protected, so the apply must delete them: state-removing them here would take them out of the plan, take them out of the allow-list, and leave them **alive in GCP with nothing managing them**. A run that state-removed the whole retirement set would plan **zero** deletes and leave eleven resources alive in GCP with nothing managing them, which is the precise opposite of §1's 11 deletes.

Two classes are protected, and both are the modules' own doing:

- **`google_secret_manager_secret.this[*]`** carries `prevent_destroy = true` (`deploy/terraform/gcp/modules/repo/secrets.tf:22`), which aborts the plan *before* it prints a resource list — §1's failure (2). These are retired from state and **never deleted**: they are §3.1's `Kept` rows.
- **A Cloud Run job carries `deletion_protection = !var.allow_job_delete`** (`deploy/terraform/gcp/modules/workflow/job.tf:15`; the check job, `deploy/terraform/gcp/modules/repo/check.tf:27`) — **and only a job whose state says `true` is protected**. `--allow-job-delete` is a tfvars **variable of an apply that still contains the job**, so once the resource has left the configuration there is nothing left to carry it and the provider refuses the delete at apply time: those jobs are retired from state and then deleted through the Cloud Run API (§4.2c). A job whose state says `false` was already lowered by an earlier apply, the ordinary path deletes it, and `Removals` leaves it in state for exactly that (the `Protected` field of §3.1).

**So in the origin's unlabelled set `Removals` returns 3 of the 14 retired addresses** — the 2 containers and the 1 job — and the other 11 stay in the state for the apply to delete, which is exactly the plan §1 quotes and the counts §1's table defines (3 state-removed before the plan, 11 deleted by the apply). With #329's union on `main` the same transition returns **1** (the protected job): the two containers are adopted back into the plan rather than retired (§1's note), so nothing about them is removed, and the apply deletes the 6 remaining addresses while the API deletes the job. §6 pins the narrow rule with a test, because the failure mode is silent: a too-wide `Removals` produces a clean plan and a GCP project with leftovers — so the pair is asserted from both sides, `TestRemovalsReturnsEveryProtectedAddressStillInState` and `TestRemovalsKeepsAnUnprotectedJobForTheApply` (two retirements differing only in `Protected` must give different answers), since the rule is per-address and not a property of the set. The primary mechanic is the runner's existing `(*TF).StateRm` (`internal/infra/tf/tf.go:302`), which fugaro already uses for `--forget` (`internal/cli/init.go:1751` and `:2588`) and which is **exactly what the owner ran by hand** in the origin:

```go
// package infra/tf — already exists, unedited by this design.
func (t *TF) StateRm(ctx context.Context, addrs ...string) error
```

It takes exact instance addresses — `module.repo.google_secret_manager_secret.this["claude-oauth-token"]`, `module.repo.module.workflow["go_bmb"].google_cloud_run_v2_job.this[0]` — which is precisely the shape the retirement set produces and the shape the owner typed. The addresses are **computed by fugaro, never typed**. It destroys nothing, and it is per-address: fugaro passes only **the protected addresses still in the state** (`Removals`, above), so an address an earlier run already removed is never passed again — `terraform state rm` of an address no longer in the state fails, so that filtering is what makes a rerun safe — and it leaves the live container or job untouched in the cloud, which is what makes the secret survive and the reverse transition re-adoptable.

**A `removed { from = … lifecycle { destroy = false } }` block was the first draft's mechanic and is now an alternative, gated on Check 42 proving it.** The reason is a real, unresolved question the first draft did not raise: the repository's own verified fixture for this (`internal/infra/tf/real_terraform_test.go:58-63`, which really runs Terraform and asserts the plan action `forget` against `testdata/plan_forget.json`) uses a **bare, whole-resource address with no instance key and no surrounding `for_each`** — `removed { from = terraform_data.d }`. Every address this design needs has an instance key (`this["claude-oauth-token"]`) or a module instance key (`module.workflow["go_bmb"]`), and in both cases the resource or module **is still declared in the configuration** with other keys remaining. Whether `removed.from` accepts an instance key at all, and whether it is refused when the block it belongs to is still declared, could not be verified offline and must not be assumed. So: **the `forget` plan action is real and already golden-tested in this repository (that is what `plan_forget.json` is); the instance-key form of the block is not.** `StateRm` needs neither fact and is the mechanism the design commits to. Check 42 carries the removed-block question as a hard precondition (§6), and if it proves out, a later release may prefer the block — it keeps the removal inside the plan, so the plan file alone describes the whole transition.

Either way, the confirmation names every secret that will be left in Secret Manager, by logical name and by Secret Manager ID (§3.1's `Logical`/`SecretID`), so the user consents to what stays behind, not merely to what goes.

**There are two typed confirmations in a retirement, and they confirm different things.** The first is the pre-plan one: the user has read the retirement summary (§3.2), which is a *prediction* derived from the state and the labels and therefore cannot contain the plan's counts, and types the project name to let the run remove the protected addresses from the state. The second comes **after the real plan exists**, at the point the ordinary path confirms — `confirmOrdinary` is called at `init.go:2357`, immediately before `t.Apply` at `:2360`, and it is defined in `init_review.go:163` — but it is **not** `confirmOrdinary` that the retirement calls. **`confirmOrdinary` may not be used for this, and the reason is the `--yes` guarantee:** it goes through `askOrdinary` (`init_review.go:142`), which returns `true` without any prompt when `runCovers()` says the plan is covered by the run's one review confirmation (`init_review.go:152-155`), and otherwise falls back to `r.ask` (`init.go:983`), which `--yes` satisfies outright ("confirmed by --yes"). Either path makes the second confirmation yes-able or skippable, which this design forbids for a retirement. So the retirement's second confirmation **calls `askTyped` (`init.go:1023`) explicitly**, at that same point in the flow, with the same project-name answer and the same "never `--yes`, never `--non-interactive`, never `--json`, never a pipe, never an agent session" rule as the first — it is a second use of the same primitive, not a reuse of the ordinary confirmation. The run shows the plan's own counts and its **full delete list** — the real deletes, not the predicted ones — plus anything else the plan contains, and asks again. The first confirmation cannot stand in for the second: it is asked before the addresses leave the state, when no plan can be produced at all. A plan that carries changes beyond the retirement's own deletes is shown and confirmed the same way, so a retirement never becomes a way to apply an unread plan. **Note what that means for the `--yes` guarantee overall:** it rests on the typed prompts alone — both of them — and `TestInitRepoRetireConfirmsTwice` pins the two prompts while `TestInitRepoRetireShowsThePlanBeforeTheSecondConfirmation` pins that a plan with non-retirement changes (the origin's 2 imports, 6 creates and 3 updates) is displayed, and confirmed, before the apply.

**It is the typed confirmation, and that is the primitive that must be used: `askTyped` (`init.go:1023`) and `canConfirmTyped(initflow.Typed, …)` (`init.go:938`), never `ask` (`init.go:983`).** `ask` is the "yes" prompt and is covered by `--yes` (`ask` returns true when `r.o.yes` is set and only checks the agent marker), which is exactly what this design forbids for a retirement; `askTyped` is the `initflow.Typed` confirmation the repo already uses for money-and-permanent steps, it never takes `--yes`, `--non-interactive`, `--json`, a pipe or an agent session, and `reachable` tells the caller whether it could be asked at all (when it could not, the step is left for the user — nothing is state-removed and nothing is deleted). **What the user types is the project's name**, which is what `typed` accepts (`init.go:1000`): the naming of every kept secret is the **banner** `askTyped` prints before the prompt, not a different expected answer. A retirement that cannot be asked that way is refused, not confirmed by a weaker prompt.

**(b) A job whose workflow has already left the configuration.** Three options, all considered:

- *(i) An ordering pre-step.* `fugaro init --repo --allow-job-delete` before editing `fugaro.yaml` — an apply whose only change is `deletion_protection = false`. This is what gcp-setup.md already prescribes, and it is the **cheapest and least invasive** path. But it is usable **only if the user has not yet changed the file**, which is precisely the case the origin is not. Keep it as the recommended order for anyone who reads ahead; it cannot be the only path.
- *(ii) State-remove the job, then delete it through the API.* `StateRm` the job address (which destroys nothing), apply, then delete the live job. *Recommended as the fallback, and the one that covers the origin.* It is the hand procedure the owner ran (`state rm` + `gcloud run jobs delete`), made supported, and it reuses (a)'s mechanic rather than adding a second one.
- *(iii) Keep the resource in the configuration for one apply.* Impossible: the workflow has left `fugaro.yaml`, so `Repo()` cannot produce it, so there is no resource for the variable to act on. Rejected as unbuildable, not as unsafe.

**Order matters inside (ii), and the design is explicit about it:** the state removal must happen **before** the plan, because the job's `deletion_protection = true` in state is what makes the provider refuse the delete; and the API delete must happen **after** the apply, because until then the job is still the state's and Terraform owns it. That gives the two-phase shape §6's failure injection tests.

**(c) The unmanaged leftovers after the state removal.** Two options: Fugaro deletes the orphaned job through the Cloud Run Admin API after a typed confirmation, or it prints the exact `gcloud` command. **Recommended: Fugaro deletes it**, because the whole point of this design is a guided path and because the job is unambiguously ours — it carries `fugaro=managed`, `fugaro_repo=<label>` and `fugaro_workflow=<name>` (`modules/workflow/job.tf:11-14`).

**What the run is allowed to delete is decided by labels and re-checked before each delete, not remembered from a previous run** (§3.1a): the orphan set is `Orphans`'s **retirements** — the jobs in this project/region carrying our `fugaro_repo` label that are either a workflow job whose `fugaro_workflow` is not a variant the new spec produces, **or the check job (`fugaro_role=check`) when `spec.Check` is nil** (its own rule, §3.1a; the two kinds carry different labels and neither rule may be applied to the other's job). That is what makes this step **resumable**: the state removal took the job out of the state, so a rerun's `Retirements` does not mention it, but the label list does, and the rerun re-attempts exactly the delete the failed run reported (plan Task 5's `TestInitRepoRetireResumeFindsTheOrphanWithoutTheState`). A journal file would have had to be cleaned up and could disagree with the cloud; the labels *are* the cloud.

The safety rules, spelled out, because this is the one new *cloud* mutation the design introduces:

- **Ownership is checked before anything is deleted, and the check must match the job's kind — the two kinds carry different labels.** Fugaro reads the job's labels and refuses unless `fugaro=managed` and `fugaro_repo` equals this repository's label, **and then**:
  - for a **workflow job** (`modules/workflow/job.tf:11-14`) the third label is `fugaro_workflow`, and it must equal the workflow this retirement names — not merely "carries our mark". A job with our mark but another workflow's variant is refused, not deleted. This is discovery's own rule (`v1.md` §8.2: a resource under one of our names that exists **and** carries our mark is adopted; one without the mark is refused), narrowed for a delete.
  - for the **check job** (`modules/repo/check.tf:22-26`) the third label is `fugaro_role=check` and there is **no `fugaro_workflow` at all** — the job belongs to the repository, not to a variant. A rule that required `fugaro_workflow` here would refuse every legitimate check-job delete, which is why §3.1a gives the check job its own retirement rule (`spec.Check == nil`) and this one its own ownership rule: `fugaro=managed`, `fugaro_repo=<this repository>`, `fugaro_role=check`. The `deleteOrphanedJob` contract therefore takes the expected label set, not a workflow name: `func deleteOrphanedJob(ctx context.Context, c *infra.Clients, project, region, job string, want map[string]string) error`, with `want` holding `fugaro`, `fugaro_repo` and either `fugaro_workflow` or `fugaro_role` according to the retirement's kind. A check job with `fugaro_role=check` is deleted; one with any other role is refused.
- **It never runs under `--plan-only` (which excludes `--retire` outright, §3.3), `--json`, `--non-interactive` or `--yes`**, and never in a coding agent's session, for the same reason and through the same marker as the apply (§4e).
- **404 is success.** A job that is already gone (a resumed run, a hand delete) is reported as done, not as a failure — the same treatment discovery gives a 404 for every resource it looks up (`v1.md` §8.2).
- **The delete is a long-running operation, and Fugaro waits for it.** `jobs.delete` returns an operation, not a finished delete, so the caller polls it to its terminal state, exactly as the fake's job-start path already models operations. Without that, "the delete failed" and "the delete is still running" are the same observation and a rerun would start a second delete on a job that is already going away. The wait is bounded: a timeout reports **"still deleting"** as a third outcome, distinct from success and from failure, and the run's output names it.
- **`deletion_protection` does not block the API delete, and this design does not claim it does.** It is a *provider-side* flag: the owner's own `gcloud run jobs delete` succeeded on the protected job, and that is the evidence. What the state removal buys is not permission from Cloud Run but permission from **Terraform** — with the job still in the state and gone from the configuration, it is the plan's delete that the provider refuses. Check 42's step 4 therefore checks that the delete's **operation completes**, not any claim about Cloud Run enforcing the flag.
- **The client and scope are the repository root's own**: the same `infra.Clients` the `Run` discovery calls already use (`infra.NewClients`, `discover.go:100`, over the operator's own ADC — the same credentials `terraform apply` uses, not the installation's launcher role), with the same `project` — no new credential, no new scope, no gcloud shell-out. **This is also why the delete is not a launcher-permission operation:** the launcher custom role holds `run.jobs.get`, `run.jobs.list`, the `run.executions.*` pair, `run.operations.get` and the two secret-list permissions and **no `run.jobs.delete`** (`modules/installation/iam.tf:8-20`), so the call runs as the operator, exactly as the apply does. A `PERMISSION_DENIED` is therefore a specified outcome, not an unexpected one: the run reports it, prints the `gcloud run jobs delete` command and the missing permission, and exits 1 (§4.2c's refusal rule). **The region is the job's own `location`** — read live by `Orphans` (§3.1a), or from the state's `location` attribute (the `Region` field of §3.1) when the row came from the state — and not the spec's `region`: that is where the job actually is, and it is what the delete must name. When the state does not carry it, the spec's `region` is used and the summary says which one it used.
- **A refusal has a defined exit status, and it is 1, like a failed delete.** An ownership refusal after the state removal leaves exactly the condition §6 forbids to be silent: the job is out of state, alive in the cloud, and still protected. So the run reports it, prints the `gcloud` command, and **exits 1** — it is not "success with a note". The apply has already succeeded, so a rerun is safe: `Removals` filters the state removal, the plan is clean, and the delete is re-attempted from the label list (§3.1a), which still names the orphan after the state has forgotten it. This is the same exit status as the delete-failed case below, for the same reason.
- **An apply that succeeded with a delete that then failed is a named, resumable state, not a silent one.** The run prints exactly which jobs it removed from state, which it deleted, and which it could not, exits 1, and a rerun picks up at the delete — because the state removal is already done and idempotent, and because the orphan is found by **label** rather than by state (§3.1a), so it is still found once the state no longer mentions it. That is the "state and cloud never disagree silently" invariant (§6).
- **The `gcloud` command is printed in the summary and in the failure path**, as the manual fallback and as the record of what happened.

*This is one of §8's open questions: an owner may prefer printing the command only.*

**(d) The `--allow-delete` list, derived automatically.** The retirement mode computes the guard's allow-list from the real plan's deletes and replaces **intersected with the retirement set (§3.1a's union of `Retirements` and `Orphans`' retirements — never its notes)** — so an address the summary did not name is never allowed, and the guard still refuses it. When the user also passes `--allow-delete`, the two are intersected again (§3.3), so the flag can only narrow the list. This is the same shape as two existing, shipped precedents: `infra.ForgetAllowDelete` (the rollback's allow-list, `internal/infra/forget.go:44`) and `infra.HardeningAllowDelete` (0.7.0's bucket hardening, `internal/infra/hardening.go:160`), the latter of which also prints its own banner naming what the deletes mean (`HardeningBanner`). The user never pastes the addresses; they read one list and type one confirmation.

**(e) The guard stays.** Nothing in this design weakens an existing guard:

- `tf.Guard` is untouched. `--allow-delete` keeps its exact meaning; retirement only *computes* it, from a list the user confirmed.
- Retirement is an **explicit consent mode with its own banner** (`⚠ RETIRE`, not `⚠ CONFIRM`), in the family of the 0.7.0 hardening banner and `--forget`'s two-step confirmation.
- It follows the covered/uncovered rules like every other step: `--yes` **never** covers it, `--non-interactive` never covers it, `--json` never covers it, and it needs the user's own terminal — the same rule `canConfirmRepo`/`confirmRepo` already implement for onboarding a repository (`init_repo_gate.go`) and the secrets stage implements for values.
- **It is refused from a coding agent's session exactly like applies are today**, through the same `agentEnv(os.Getenv)` marker (`initsecrets.go:146`), and for the same stated reason (`init.go:371`): the marker is a mitigation, not a barrier, and the real control is the typed confirmation.
- `--allow-job-delete` keeps its meaning and its own `--repo`-only guard (`init.go:685`); retirement does not set it behind the user's back. Where a job must be state-removed rather than unprotected (§4b(ii)), the summary says why.

## 5. Where users learn

1. **Error and warning texts** — the retirement summary (§3.2) and the `prevent_destroy` re-framing (§3.3). Neither shows raw Terraform text; both name the cause and the command. The `--json` document gains `retire` (the `[]Retirement` list) so a scripted user sees the same facts, and keeps `failed[].error` as the raw Terraform text.
2. **A docs section** in `docs/gcp-setup.md`: "Changing auth, or removing a workflow, secret or provider", with the ordered steps and a worked example — a small transcript of the run's own output, three addresses of which one is a secret kept in Secret Manager (the 2026-10-14 origin's own numbers are §1's, and §1's note says how the union moves them today). The existing "Turning checks off, or removing a workflow" and "Offboarding a repository" sections are **edited to point at it** rather than kept as a second, divergent outline; the "do it in this order" advice stays, restated as "the order matters, and `fugaro init --repo` now tells you when you have passed it".
3. **The setup and upgrade skills** (`plugin/skills/setup`, `plugin/skills/upgrade`): each gains the refusal text an agent will see, with the instruction not to attempt the transition from an agent session and to hand the user the `--retire` command instead. The skills lint (`plugin/skills_lint_test.go`, `internal/cli/skills_test.go`) is updated with them.
4. **`fugaro init --repo --plan-only`** warns when the checkout's configuration, compared against what the project's state holds, would retire resources: it reads the state, the label-discovered orphans and the spec, and prints the **full predicted retirement summary** — `printRetirements` (§3.2), the same text and the same address list, kept secrets and next command that the `--retire` path prints — **first**, and then continues into the ordinary read-only path: it shows the ordinary plan and its delete list whenever one can be produced, and exits, having removed nothing, deleted nothing and applied nothing (§3.3). It is a prediction rather than the retirement's own delete list, because in the case that matters — the protected addresses still in the state — no plan can exist at all, and the summary is then all `--plan-only` can show; the real list comes from `--retire` itself. The plan pins both with `TestInitRepoPlanOnlyRemovesNothing`, which asserts the summary is printed in full and that no `state rm` was recorded, and with the assertion that a `. --plan-only` run which *can* produce a plan still shows it. **`fugaro validate` is deliberately not in this list, and the first draft of this design was wrong to include it:** `internal/cli/validate.go` has no Terraform and no state access at all, so it cannot make this comparison, and giving it one would turn a documented offline command into a live, state-reading one. `fugaro doctor` is in the same position and is likewise **not changed by this design**: it reads no state, and the plan's tasks contain no doctor edit (if the owner wants doctor to point at `fugaro init --plan-only`, that is a one-line change with its own plan entry, not an orphan of this one). *This is §8's open question 5: whether a read-only state access in `validate` is worth the change to what that command is.*
5. **`docs/gcp-live-checklist.md` Check 42** (owner-run, sandbox): the oauth → api-key → oauth round trip with the secrets retained and re-adopted (§6).

## 6. Safety and testing

**Safety invariants.**

- **Fugaro never deletes a secret or a secret version.** No new code path calls `secrets.delete`, `versions.destroy` or `versions.delete`; the state removals of §4.2(a) destroy nothing and the containers keep `prevent_destroy`. A state-removed secret stays in Secret Manager with its value.
- **A state-removed secret must be re-adoptable by label.** `DiscoverRepo`'s existing labelled-secret discovery is what makes the reverse transition clean; this design adds no new label, no new mark and no registry of its own, so re-adoption is the *existing* path, unchanged.
- **Nothing weakens a guard** (§4e).
- **State and cloud never disagree silently.** §6's failure injection is the test of this, not an aspiration.
- **The one new cloud mutation is the orphaned-job delete (§4.2c)**, and it is bounded by the ownership, label, terminal and agent checks spelled out there. It covers both job kinds: a workflow job is matched on `fugaro_workflow`, the check job on `fugaro_role=check`, and each is deleted only under its own rule. Everything else this design reads from the cloud is read-only: `Orphans` (§3.1a) is one `jobs.list` and one labelled-secret list, with the same client and the same `cloud-platform` scope the repository root already uses.

**Tests, in the repository's existing patterns.** The fakes are the ones that already exist: `internal/cli/init_test.go`'s `fakeTerraform` (a real binary the tests build once, `init_test.go:42`) and the `gcpfake` clients, plus the golden plan fixtures under `internal/infra/tf/testdata/` and the CLI's `internal/cli/testdata/` (`init_commands.golden`, `init_review.golden` are the precedent for a printed-output golden).

**Three of them cannot carry these tests as they stand, and the plan makes extending them a task of its own** (plan Task 4) rather than an assumption buried in a step:
- `internal/infra/tf/faketerraform` is **stateless and keyed by subcommand alone**: one scripted response per key, so `show -json` (the state) and `show <plan>` are indistinguishable, `state rm` is all-or-nothing, and there is no sequencing across invocations. The tests that need it — state before vs after a removal, a half-failed `state rm`, a plan that fails and then succeeds on the rerun, "the removal was recorded before the plan" — need a fake that can answer differently on the second call and tell the two `show` forms apart.
- `internal/gcpfake/run.go` has **no job DELETE handler** and does not render job **labels** in `jobs.list` (`listJobs` returns names only), so neither the delete, nor the 404, nor the label-ownership refusal, nor `Orphans`' discovery by label can be tested against it.
- `internal/gcpfake/secrets.go` has a delete handler but **no call recording**, so "Fugaro never deletes a secret or a secret version" cannot be asserted; it needs per-method counters the test can read (the same shape as `Run.RunRequests`/`Run.Patches`, which already record calls).

- **The origin transcript as a fixture**, with its 14 addresses listed once in §1 (12 going away, 2 removed from state and kept — the state-only set of §1's note, which the union narrows to 8): the `prevent_destroy` failure text, the two secret addresses, the `go_bmb` variant and the 11-delete plan, asserting that `init --repo` prints the retirement summary and never the raw text. The new golden lives beside the existing ones as `internal/cli/testdata/init_retire.golden`.
- **`RepoSpec.Addresses()` completeness**: a test diffing `Addresses()` against the `resource_changes` of a **real** `terraform plan` of the real `repo` root, planned from a fixture spec that turns everything on. The plan output is committed as a golden (`internal/infra/testdata/repo_root_addresses.golden`) and regenerated by a build-tagged test gated on a **`-update` flag** — the one step that reaches outside the repository, run at build time on the owner's machine and never applying anything (it plans a temp copy of the root with the provider's credential checks skipped; whether that override suffices is a build-time question, and the fallback is read-only credentials for a sandbox project). **The gate matters because CI does reach this file:** `.github/workflows/ci.yml:115` runs `go test -tags terraform ./internal/infra/...`, so a `//go:build terraform` test in this package is compiled and executed there. It must therefore **skip unless `-update` is set**, and its body — `terraform init`, the provider download, the credentials question — must be behind that skip, so CI compiles and vets it (which is what keeps the generator from rotting) but never downloads a provider or touches a network. Global Constraints' "no live cloud or network call in any automated test" is upheld by the skip, not by the file's location. The CI-visible assertion is the **untagged** test in `spec_test.go`, which diffs `Addresses()` against the committed golden, so a resource added to a module without an address here fails the build. This is the guard against the mirror drifting (see §3.1).
- **The user-changed-the-file-first order**, which is the origin: the workflow has already left `fugaro.yaml` and the job still carries `deletion_protection = true` in state. Asserts the state-remove-then-delete-by-API path is chosen, that the removal happens before the plan and the API delete after the apply, and that the `--allow-job-delete` pre-step is *not* offered as if it were still available.
- **A baked/clone transition** (row E), asserting the check job, its invoker grant and its Scheduler job appear in the retirement set exactly when the last checked workflow leaves. **The check job is a job of its own kind**, and the tests pin both directions of the rule §3.1a gives it: `TestOrphansNeverReturnsTheCheckJobItStillNeeds` (with `spec.Check != nil` the check job — which carries `fugaro_role=check` and no `fugaro_workflow`, `modules/repo/check.tf:22-26` — is **not** an orphan, so it is never deleted while it is still wanted) and `TestOrphansCheckJobIsAnOrphanWhenSpecCheckIsNil` (with `spec.Check == nil` it is, and `deleteOrphanedJob` deletes it under the role label rather than refusing it for a missing `fugaro_workflow`). Without the pair, a check job reads as an orphan on every run, and a genuinely retired one is state-removed but never deleted — state and cloud disagreeing silently, which §6 forbids.
- **A reverse transition** (row A in reverse), asserting the labelled containers are re-imported and the named variants come back as creates, with **zero** deletes of any `google_secret_manager_secret.*` resource.
- **The state removal is narrow, and never eats what the apply must delete**: a test over the origin's 14 retired addresses (the state-only set again) asserts `Removals` returns exactly the **protected** ones still in the state — the 2 containers and the 1 job — and that a retired variant's service account and IAM members are **not** returned, because the plan has to delete them. The companion assertion is on the plan itself: the retirement-mode plan still contains those 11 deletes, so a `Removals` that widened by accident fails the test instead of quietly planning a clean run over a project full of leftovers.
- **Failure injection, in both phases**: a `state rm` that fails half-way (some addresses removed, some not), and an apply that succeeds while the API delete fails. The rule to pin: the run reports exactly which addresses were removed from state, which were deleted in the cloud and which were not, writes nothing else, and a rerun resumes — `Removals` returns only **protected** addresses still in state, so an already-removed address is never passed to `state rm` again (`terraform state rm` of an address no longer in state fails, so this filtering is what makes the rerun safe), and a delete of an already-deleted job is a 404 treated as done. Never leaving state and cloud disagreeing without saying so.
- **The orphaned-job delete's own cases** (§4.2c): a job whose labels are not ours is refused; a job with our marks but another workflow's `fugaro_workflow` is refused; a job already gone (404) is reported done; a check job is deleted under `fugaro_role=check` while a workflow job under `fugaro_workflow=<variant>`, and each is refused when its own third label is the other kind's; and `--plan-only`, `--json`, `--non-interactive`, `--yes` and an agent session each never reach the call. **Every refusal exits 1** and reports the job as out of state, alive and still protected — the exit status is part of the contract, not left to the implementation.
- **A kept container alone never keeps the retirement alive** (§3.1a, the convergence rule): with the two OAuth containers already released and out of the state, a later `fugaro init --repo` returns them as **notes**, prints no summary, opens no gate and never suggests `--retire`; the same run with one state-held address does print it. This is the test that stops the summary, the gate and the next command from recurring forever on a project that has nothing left to retire.
- **The orphan set is read from labels, and the rerun finds the orphan without the state** (§3.1a): a job carrying `fugaro_repo=<label>` whose `fugaro_workflow` is not a spec variant is returned by `Orphans`; with the state already not holding the job (a simulated failed earlier run), the run still reports it and still attempts the delete. A second test asserts a job whose `fugaro_workflow` **is** still a spec variant is not an orphan and is never deleted, whatever the state says. Both need the fake's label rendering (plan Task 4).
- **A refused label call degrades loudly and the run goes on** (§3.1a): with `gcpfake` answering `PERMISSION_DENIED` on `run.jobs.list`, on `secrets.list`, and on both, `Orphans` prints the warning naming the call, the permission, the `gcloud` equivalent and the consequence; the run continues with the **state-derived** set rather than an empty one; and with the state half also empty the summary says the check could not be made rather than that there is nothing to retire. This runs in `--plan-only` too, because the same call does. The permission itself is not testable here — no fake can prove what an operator's ADC holds, which is why Check 42 carries it as a FACT.
- **The delete waits for its operation**: a delete whose operation is still running at the timeout is reported as **"still deleting"**, distinct from a failure and from success, and a rerun does not start a second delete on it.
- **The `prevent_destroy` match, against the real wrapped text**: the fixture is §1's own quoted output, which Terraform breaks after `has`, and the test asserts the summary is printed and Terraform's text is not. A second test asserts the *unnormalized* match does **not** fire on that same fixture, so the normalization cannot be removed without failing a test. The build-tagged test in `internal/infra/tf` that really runs Terraform (a `prevent_destroy` resource, `real_terraform_test.go`'s pattern) generates the real text and asserts the matcher fires on it, so the fixture cannot go stale unnoticed.
- **`--plan-only` is read-only and excludes `--retire`**: `TestInitRepoRetireAndPlanOnlyExcludeOneAnother` (the existing mutual-exclusion rule, `init.go:709`) and `TestInitRepoPlanOnlyRemovesNothing`, which asserts the recorded `fakeTerraform` invocations contain no `state rm` and that `gcpfake`'s job delete was never called, with the predicted summary still printed **first**; and, beside it, the assertion that a `--plan-only` run which *can* produce an ordinary plan still shows it, so "print the summary and stop" cannot creep back in.
- **A retirement confirms twice, and the second confirmation has the real plan in front of it** (§4.2): `TestInitRepoRetireConfirmsTwice` records two `askTyped` prompts — the pre-plan prediction and, after the plan exists, the plan's own counts and its full delete list — and `TestInitRepoRetireShowsThePlanBeforeTheSecondConfirmation` runs the origin transition (2 imports, 6 creates, 3 updates, 11 deletes) and asserts the plan's counts and its delete list are printed before the second prompt, that neither prompt is reachable from `--yes`/`--non-interactive`/`--json`/an agent session, and that the state removal happens between them.
- **The guard's own behaviour when the plan aborts early** is pinned by a test, not merely documented: a plan that cannot be produced prints the summary, exits 1, and leaves the workdir's state untouched.

**What only a live run can settle** (owner-run, Check 42): that a real `prevent_destroy` plan failure is matched by the normalized signature this design parses (the live run is also what keeps the fixture honest); that the state's own attributes are the ones §3.1 names — the confirmation's Secret Manager IDs match `gcloud secrets describe` and its job name and region match `gcloud run jobs describe`; that `terraform state rm` on these exact instance addresses leaves the containers in Secret Manager and lets the plan proceed; **whether `removed.from` accepts an instance key at all, and whether it is refused while its block is still declared** — the hard precondition for ever preferring the `removed`-block variant over `StateRm` (§4.2a), and not something this document assumes; that the Cloud Run API delete's **operation completes** on a job the state no longer holds (the flag is provider-side, so the fact is the operation finishing, not Cloud Run enforcing anything — §4.2c); and that the oauth→api-key→oauth round trip leaves both secrets in Secret Manager with their values and re-adopts them.

## 7. Release placement and compatibility

**Placement: 0.7.5, as one release.** The plan's first draft claimed a clean split — detection and explanation as 0.7.1, the retirement mechanics as 0.7.5 — and that split does not survive contact with the summary: the summary's whole point is the *next command*, and in the design as it stands that command is `fugaro init --repo --retire`, which does not exist until the mechanics ship. A 0.7.1 that printed a flag its own binary rejects would be worse than no warning. So the honest options are:

- **0.7.5, everything together** (*recommended*): detection, the summary, the reframing, the guard-preserving retirement flow and the orphaned-job delete, in one release. This is what the plan's tasks now describe, and it is what makes the split statement and the "one PR" statement agree.
- **0.7.1, detection only, with a different next command**: the summary ships alone and its last line names the *documented manual steps* — `fugaro init --repo --plan-only` prints the predicted list (§3.3), and the docs section's `terraform state rm` and `--allow-delete` sequence does the rest — instead of `--retire`. That is a real, shippable half, and it is the smaller change; it costs the user the copy-paste the design exists to remove, and it hands them a *predicted* list rather than the plan's own, because without the mechanics nothing can remove the protected addresses to make a plan exist. *This is §8's open question 1.*

Its one real dependency, either way, is the project-secrets work ([#329](project-secrets.md), plan `2026-10-13-project-secrets.md`). Row F of the inventory is the same hazard that design's N3/N4 fix closes, and its `Existing.ExtraSecrets` union is what makes "a secret leaves `rs.Secrets`" impossible for a config-driven reason. Shipping this design **before** that one would mean two mechanisms for one invariant, which is exactly what this design's §2 refuses to do.

**Compatibility.** No new `fugaro.yaml` key, so the three-edit rule (schema, docs, examples) is not triggered and no `*Since` gate is needed for a repository's own file. `--retire` is a CLI flag, not a configuration key, so an older binary simply does not know it — and an older binary keeps failing the way it does today, which is the status quo, not a regression. **The new refusal gate is not a behaviour change to any documented flow either (§3.3):** it fires only on a `prevent_destroy` plan abort, or on a job the state still holds with `deletion_protection = true` after its workflow has left the configuration — the two cases where today's path (lower the protection first, then `--allow-delete`) cannot be completed at all — a user following `gcp-setup.md`'s existing sections sees a new summary line and, otherwise, the same run. If a `*Since` constant turns out to be needed (for example if the retirement flow must be gated on a repository's last `init --repo` having been run by a binary that knows it), it follows `docs/release.md`'s existing format, and the plan says where.

## 8. Open questions for the owner

1. **§7 — 0.7.5 with everything, or 0.7.1 with detection only and a documented next command?** The recommended answer is 0.7.5; the 0.7.1 half is real but weaker, because it hands the user back the copy-paste the design exists to remove.
2. **§4.2(c) — does Fugaro delete the orphaned job through the Cloud Run API after the typed confirmation, or only print the exact `gcloud` command?** The recommendation is to delete it, behind the ownership, label, terminal and agent checks §4.2(c) spells out; printing only is the more conservative alternative and costs the user one copy-paste.
3. **§4.2(b) — should the ordering pre-step (`--allow-job-delete` before editing `fugaro.yaml`) be actively *offered* when the file has not yet changed**, or left to the documentation? Offering it is friendlier and cheaper (no state removal, no API delete); leaving it out keeps one path rather than two.
4. **§3.1 — is a Go-side address inventory (`RepoSpec.Addresses`) acceptable as the source of the consent list**, given it is a prediction, it is a hand-maintained mirror of the modules (§6 pins it with a golden test), and the guard still runs on the real plan? The alternative is to always run the two-phase plan (state-remove, plan, read the real list), which is authoritative but touches the state on every run — and is unavailable in the origin case anyway, where no plan can be produced until the removals have happened.
5. **§5.4 — should `fugaro validate` gain a read-only state access so it can warn about a retirement?** The recommendation is **no**: `validate` is a documented offline command today, and the warning is already available one flag away, on `fugaro init --plan-only`, which is where the state is read anyway.
6. **§5.2 — the `docs/gcp-setup.md` restructuring**: this design proposes rewriting the two existing manual sections to point at one new section. The owner may prefer to keep them as they are and add the new section alongside.
