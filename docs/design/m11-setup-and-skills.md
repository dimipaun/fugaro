## 0. Summary and recommendations

The brief's target README is two lines: `fugaro init`, then `/fugaro:setup` in the coding agent. Most of the machinery exists already, but split into three commands you must run in a precise order with flags you must know (§2). M11 makes it one command and one skill.

1. **One re-runnable `fugaro init`, built as a converge loop over stages**, not a rewrite. The three commands we have (`init`, `init --firebase`, `init --repo`) stay as the engines of the stages; the new top level decides the order, runs what is needed, stops at the first thing only the user can do, and ends with "what is left for you". Re-running continues from there. (§3)
2. **Stay "adopt" by default; add project creation behind its own flags, later.** Today `init` never creates a project or links billing. Recommend: creation (`--create-project`) and billing linkage (`--link-billing ACCOUNT`) each need their own explicit flag *and* their own typed confirmation (`--yes` alone never does either); without the flag, init prints the exact one-line command and the console URL. This is slice C, after the adopt-only converge (slice B). (§3.1)
3. **The base images are mirrored into the project's own registry by init, from the CLI's own credentials, in Go, with no Docker daemon.** The published ghcr images cannot be pulled by Cloud Build or Cloud Run, and build accounts must not be able to write the base registry (a security property), so the copy runs as the user. Digest-verified, idempotent, lazy per base kind (a repository's workflows say which kinds it needs), and the history image goes the same way. (§3.3)
4. **Secrets: values only ever from the user's terminal.** Init prompts for the provider credential and the Claude credential at a hidden prompt, refuses to read them from a non-terminal, skips what is already stored. The agent (the skill) only lists names and tells the user what to type. (§3.5, §9)
5. **Repo onboarding after `/fugaro:setup`:** `init` never writes `fugaro.yaml`. The skill ends by running `fugaro init --repo --plan-only` (read-only) and tells the user to run **`fugaro init`** again in their terminal once the setup PR is merged: run in a checkout whose default branch has a valid `fugaro.yaml`, `init` adds the repo stage (job, first image build, schedule) to the same converge. The README therefore stays two lines and the skill carries the "then run it again" step. (§3.6)
6. **The skills stay in the Claude Code plugin (`plugin/skills`, single source), and `fugaro init` wires the plugin into the repository's project `.claude/settings.json`** so the plugin installs by itself for every teammate who opens and trusts the project (verified live, no install prompt, §14 item 1): it merges (never overwrites) the Fugaro marketplace under `extraKnownMarketplaces` and `"fugaro@fugaro": true` under `enabledPlugins`. The marketplace source is **pinned to the release tag of the binary that ran init** (the release gate already forces plugin version equal to tag), so binary, plugin and pin agree. Updating is `fugaro init` or `fugaro update-skills`, which bumps the pin: one diff in `settings.json`. `fugaro doctor` and a one-line warning on regular commands compare the pin (and, if readable, the installed plugin version) with the running binary. (§4)
7. **`/fugaro:setup` keeps the `image:` block as the default and a `.fugaro/<workflow>.Dockerfile` as the escape hatch.** The brief's "agent authors a Dockerfile and fugaro.yaml together" is satisfied by the existing contract (a Dockerfile built `FROM` a Fugaro base), not by letting the agent replace the security-critical template. Every line the agent adds that executes in Cloud Build is shown to the user before it is committed. (§5)
8. **The pluggable backend seam: keep what exists, add only a name, a stage grouping and a conformance test.** The interface covers the run lifecycle only; secrets, image builds and provisioning are GCP-direct. M11 does not widen it; it makes init's stages the per-backend unit and adds the contributor docs and a conformance suite. No AWS work. (§7)
9. **Skills are instructions executed with the user's credentials.** They are Fugaro-owned and travel in a release-tagged plugin, pinned from the repository, which helps, but a skill is still a prompt-injection target, a skill can tell an agent to do something expensive, and a plugin is code that runs with the user's rights. §9 lists what a skill must never tell an agent to do, what the plugin may contain, and the tests that enforce it.
10. **First slice, shippable alone (A): the skills restructure and the wiring** (the four skills in the plugin, the do-not-edit header and version in each, the settings merge and pin, `update-skills`, `doctor --plugin`, the lint tests). It touches no cloud, fixes none of the cloud friction, and is what the brief calls the reason to dogfood. Before any of it is built, four **verification spikes** (V1 to V4, plan) check the assumptions the wiring rests on; two are already checked (§14). Slice B (converge init with the image mirror and secrets prompts) is a parallel lane. The milestone is done only when B has been dogfooded (§11).

## 2. What the three commands do today

All from `internal/cli/init.go`, `init_firebase.go` and `internal/infra`.

- **`fugaro init --name N --gcp-project P --region R`** (installation). Environment checks (no impersonation, no overriding project variables, `terraform` on PATH, no `http2debug`); enables Cloud Resource Manager (own confirmation); creates the Terraform state bucket (own confirmation); plans, shows the plan, asks for the project name typed (`--yes` skips); applies the saved plan; offers to remove project Viewers' read access to the runs bucket; writes `~/.config/fugaro/projects/<N>.yaml` from the outputs (diff shown, backup kept). Refuses deletes unless `--allow-delete`. Modes `--plan-only`, `--print-vars`, `--config-only` (this is the teammate path: the config is written from the state), `--forget`.
- **`fugaro init --firebase FP`**. Checks the Firebase project exists and has billing, refuses a database that holds data without a Fugaro mark; three applies (installation for the history account; the Firebase root: database, restricted sign-in key, token signer, budget admins; installation again for the history job once its image exists), each with its plan and confirmation; between them deploys rules, mark, name, mode, largest lease, Firestore (location `us-east5` is permanent: typed confirmation), Identity Platform checks.
- **`fugaro init --repo [PATH]`**. Reads the checkout's committed `fugaro.yaml` (`project:` must match), plans the repository's registry, build account, per-workflow jobs, secret containers, the daily check job and a paused Scheduler job; GitHub needs `--github-app-id`; offers each workflow's first image build (billable, own confirmation) once the secrets are stored; a second apply deploys the job and unpauses the check.
- **Not in `init`:** the base image (built by hand or published ghcr, `init --base-image` records it), the history image (built by hand), secret values (`fugaro secrets set`), the GitHub App and Bitbucket token (made by the user in a browser), billing, project creation.

## 3. `fugaro init`, the whole of phase 1

### 3.1 What it does end to end for a new team

Stages, in order. Each stage has a **check** (read-only: is it done?), a **plan**, an **apply**, and reports `done`, `changed`, `blocked` (on another stage) or `needs-you` (with the exact one-line command or prompt).

| # | Stage | Reuses | New |
|---|---|---|---|
| 0 | **Preflight** | `checkEnv`, ADC and quota checks, readiness | Shared with `fugaro doctor`: Cloud Billing API on the quota project, the default Compute SA's `roles/editor` warning (friction log), Terraform version, Docker (only if a local base build is needed), plugin wiring state |
| 1 | **Project** | adopt: the project exists, has billing | `--create-project`, `--link-billing` (flagged, slice C) |
| 2 | **Services** | `resourceManager`, the installation's API list | enable the rest in one place (Service Usage), Firebase Management for the Firebase side |
| 3 | **Installation** | `install` (state bucket, runs bucket, base registry, roles, scheduler account, logs) | none |
| 4 | **Firebase backend** | `initFirebase` (RTDB, rules, mark, mode, Firestore, Identity Platform, budget admins, history account) | default: same project; `--budget-mode observe` is the default |
| 5 | **Images** | history job's image existence check | mirror the history image; mirror base kinds on demand (§3.3) |
| 6 | **Installation, second pass** | the history job and its scheduler | run automatically when stage 5 has made the image exist (today a manual `init --firebase` again) |
| 7 | **Secrets** | `secrets set`, `secrets ls` | prompts and skip-if-present (§3.5) |
| 8 | **Plugin wiring** | none | merge the marketplace and `enabledPlugins` into `.claude/settings.json` at the binary's tag (§4.3); outside a checkout, print the snippet |
| 9 | **Repository** (only inside a checkout whose default branch has a valid `fugaro.yaml`) | `runInitRepo` | wired as a stage; first build waits for stage 7's secrets |

Order is the dependency order the dogfooding run discovered by hand: installation, Firebase, images, history job, secrets, repository.

**The converge loop.** `fugaro init` evaluates each stage's check in order and applies the first one that is not done and not blocked, then re-evaluates, until every stage is `done` or the next is `needs-you`. It never skips a confirmation: each stage keeps its own existing confirmation text. Re-running it is the resume. A failed stage stops the loop with exit 2 and a stage name; nothing after it runs.

**The single plan view.** Planning cannot be complete up front (the Firebase root needs the installation's outputs), so the view is honest about it:

```
fugaro init: project aurora (GCP aurora-prod, us-east5)
  [done]       preflight
  [will do]    installation        14 to create, 0 to change, 0 to delete   (Terraform plan below)
  [will do]    firebase backend    plans after the installation exists
  [will do]    images              history (about 20 MB); base images on demand
  [needs you]  secrets             github-app-key, claude-oauth-token (hidden prompts)
  [skipped]    repository          no fugaro.yaml on the default branch yet
Type the project name to apply the installation: 
```

`--plan-only` prints this view plus each reachable stage's real Terraform plan and changes nothing (as today, it can still create the state bucket behind its confirmation). `--json` prints the same as data, with `left_for_you` as an array of `{stage, kind: command|prompt|console, text}`.

**Confirmations.** Unchanged in spirit: typed project name for applies, extra typed confirmations for what is permanent or irreversible (Firestore location, project creation, billing linkage), separate confirmations for billable builds. `--yes` keeps its meaning ("confirm every step without asking, only after reading what it will do") but **never** covers project creation or billing linkage (those need their own flags) and **never** supplies a secret.

**Non-interactive mode.** `--non-interactive` means: no prompt is ever shown; a missing input is an error that lists every missing flag in one message; an apply needs `--yes`, else the run is `--plan-only`. Without a terminal, `init` refuses to prompt and says so (the friction log: typed confirmations need a real TTY; the message must tell the user to run the command in their own terminal, and the skill says the same). The converge loop's `--json` output makes it scriptable for CI and for a team lead provisioning another team.

**Inputs and defaults.** In a terminal, a first run asks for the three inputs it needs, each with a default it *suggests* and the user confirms: the Fugaro project's name (default: the repository's owner or directory, sanitised), the GCP project ID (suggest from `GOOGLE_CLOUD_PROJECT` or the ADC quota project; **never silently from `gcloud config`'s default project**, the standing rule: a default project is how a command lands in the wrong project), and the region (suggest `us-east5`). It then writes the local config, so later runs ask nothing. The GitHub App's ID (not a secret) is asked here when the checkout's origin is GitHub, and stored in the local config (friction: `init --repo --plan-only` needed `--github-app-id` the first time).

**A new team member (adopt mode).** `fugaro init --gcp-project P` where the installation exists and the local config does not: the existing `--config-only` path writes the config from the state, the converge sees every stage `done`, installs skills, and prints what the caller lacks (an IAM role, `--launcher` on the owner's side). Needing Owner is only true for the first person; the check for "may I apply?" is the plan's first permission failure, reported as "ask an owner to run `fugaro init`" with the roles named. This is how "the team already shares the Firebase project, so they share the infra" becomes true in practice.

### 3.2 Creating or adopting the project (slice C)

User rule so far: init never creates projects or links billing. Recommendation on how far to go, because a new team's first hour is spent here:

- **Create: yes, flagged.** `fugaro init --create-project --gcp-project <id> [--parent organizations/N|folders/N]` calls Cloud Resource Manager `projects.create`, waits for the operation, adds Firebase (`firebase.googleapis.com` `projects:addFirebase`), after a typed confirmation that shows the project ID, the parent, and "this project will be used for everything Fugaro runs". The ID is global and permanent (6 to 30 characters); a collision is a clear message with a suggested `<name>-<suffix>`. It is idempotent: if the project exists and is ours (a Fugaro mark) or empty, it adopts.
- **Billing: guided by default, flagged to act.** Linking a billing account commits the user's money, so by default init lists the billing accounts the caller may use (`cloudbilling.googleapis.com` `billingAccounts.list`) and prints the console URL and the single-line `gcloud billing projects link` command. With `--link-billing <ACCOUNT_ID>` it calls `projects.updateBillingInfo` after its own typed confirmation naming the account. Needs `billing.resourceAssociations.create` on the account; absent that, the message says to ask the billing admin.
  *Implemented (T16) with deliberate differences:* init does not list the caller's billing accounts (that would reveal every account the user can reach); it prints the `gcloud billing projects link` line with a placeholder and the user names the account. Billing is linked only to a project this run created, or to an existing one that has no billing link at all (an unreadable, suspended or closed link is never replaced). "Adopt" means a project the caller can read, not one proven ours or empty (no cheap read-only mark or emptiness check exists before the installation does); every change to a pre-existing project says so in its own typed confirmation. `--create-project` excludes a different `--firebase`.
- **The chicken-and-egg:** the Cloud Billing API must be enabled on the credentials' **quota project** (friction log), and a project that does not exist cannot be the quota project. Preflight checks it and either enables it on the quota project (own confirmation) or prints the one-line command; for a creation run the quota project is an existing project of the user's, said plainly.
- **Org policy, quotas and `roles/editor` on default accounts** are the user's organisation's business: errors are surfaced verbatim with the likely cause, never worked around. For a project init created, Compute is not enabled so no default Compute SA exists yet; init does not enable it. For an adopted project, the existing warning stays and the one-line fix is printed (never applied to a project init did not create).

### 3.3 The base images: mirrored by init

The problem: `ghcr.io/dimipaun/fugaro-<kind>:<version>` cannot be read by Cloud Build or Cloud Run in the user's project (the packages were private, and Cloud Run does not pull ghcr in any case: **unverified**, §14), `fugaro-go` is only published from the next release, and `fugaro-base` is writable by operators only on purpose (a leaked build token must not be able to replace the image every repository's credential step runs).

Recommendation: **init copies the image into `<region>-docker.pkg.dev/<gcp-project>/fugaro-base/` as the user**, from the CLI, in Go (a registry client library such as `google/go-containerregistry`, a new dependency, to be reviewed; no Docker daemon, no shell-out), authenticating to Artifact Registry with the user's ADC token.

- **Which images.** The history image at stage 5, always. Base kinds lazily: the repository stage knows its workflows' kinds from `fugaro.yaml`, mirrors those first, and records them in the local config's `base_images`. `fugaro init --base web-node,go` pre-mirrors; the "all three up front" alternative costs about 5 GB of registry storage (about $0.5 a month) and several minutes of upload for kinds the team may never use (open question Q3, default lazy).
- **Which version.** The CLI's own version (`fugaro version`): the matching base is the one with the matching runner (the `credential`, `gate`, `record` and `check` commands live in the base's `fugaro`). The tag copied is the immutable version tag; the copy is verified by manifest digest, and when the destination already has the same digest the stage is `done` (idempotent, free). The destination tag is what `base_images` records.
- **What it checks first (all read-only):** the source is readable anonymously (else the message says the release's packages are not public, which is a release bug, §12); the manifest has a `linux/amd64` entry; the user can write `fugaro-base` (`roles/artifactregistry.writer`, which the operator role gives). It shows the size and the storage cost and asks for a confirmation of its own (billable: about 1.5 GB per base, 2.1 GB for `java-services`).
- **A development build** (`fugaro version` is `dev`) has no published image. The stage says so and prints the single line that builds from a checkout (`sh images/build-base.sh go <tag> && docker push <tag>`, then `fugaro init --base-image <tag>`), as today; there is no silent fallback to a different version. A contributor flag `--base-from-source <checkout>` runs those two steps (needs Docker), for dogfooding.
- **Not Cloud Build.** A mirror run on Cloud Build would run as a service account, which would need write access to `fugaro-base`: the exact grant the design withholds from build accounts. Rejected. (Alternatives to verify later: an Artifact Registry remote repository over ghcr, §14.)
- **The history image** (a distroless image holding the `fugaro` binary) joins the release's published images (`fugaro-history`, one line in `images.yml`, plus the public-visibility step) and is mirrored as `fugaro-base/history:latest`, which is what the history job references today.

### 3.4 Services, schedulers and the rest of the backend

No new resources: Terraform already creates the registries, the schedulers (the daily image check, paused until a record exists; the history scheduler) and the history job. What M11 changes is only that the converge loop applies them in the right order without the user re-running `--firebase`. The Firebase side seeds the RTDB budget nodes (mark, project name, mode `observe`, largest lease) exactly as today; Identity Platform and Firestore keep their existing confirmations (the Firestore location stays permanent and typed).

### 3.5 Secrets

Phase 1 cannot store every secret: today's containers are per repository, created by `init --repo`'s Terraform or on demand by `secrets set` (which creates a labelled secret if needed), and phase 1 has no `fugaro.yaml`, so it does not know whether the repository authenticates with oauth, an API key or Vertex. Recommendation:

- **Keep the per-repository scoping** (a job's account reads only its repository's secrets; changing that is an IAM redesign and out of scope; see Q4 for a later project-level variant).
- **Init stores, for the checkout it runs in, what it can know without `fugaro.yaml`:** the provider credential (the checkout's origin says GitHub or Bitbucket: `github-app-key` as a hidden multi-line paste or a file path the user names, or `bitbucket-token`) and one Claude credential, chosen by a prompt with `claude-oauth-token` as the default (the user's stated direction; `claude setup-token` is run by the user in their own terminal, and init says so), `anthropic-api-key` as the alternative. It does not ask for Vertex.
- **Detect and skip:** `secrets ls` shows what exists for the repository; a present secret is `done` and is never overwritten by init (rotating is `secrets set`).
- **Hidden prompts only.** The value is read with `golang.org/x/term` from a terminal. If stdin is not a terminal, init does not read secret values from it (a pipe could be an agent holding a value it should not have); it prints the one-line `fugaro secrets set <name> --repo <slug>` command to run in a terminal. The existing `secrets set` keeps its pipe and file forms for the user's own scripts. No value is ever echoed, logged, written to `result` JSON, put in an error, or kept in the local config. (The existing minimum-length and size rules apply.)
- **`/fugaro:setup` closes the loop:** once it knows `agent.auth` and the workflows' own `secrets:`, it compares them with `fugaro secrets ls --json` and tells the user which one-liners to run. It never handles a value (§9).
- **Not a Fugaro job:** creating the GitHub App or a Bitbucket repository access token happens in a browser. Init prints the steps and the facts that bit the dogfooding run: **GitHub App names are globally unique** (the example name `Fugaro` is taken: the docs example must say so and suggest `<yourname>-fugaro`), the name is shown as the author of every PR, and it cannot be changed later. (Docs fix in T20; the same for Bitbucket token names.)

### 3.6 How a repository gets onboarded

The brief says init does not create `fugaro.yaml`, yet today `init --repo` needs it. The ordering, resolved:

1. `fugaro init` (phase 1): installation, backend, images, secrets, skills. Stage 9 reports "skipped: no fugaro.yaml on the default branch".
2. `/fugaro:setup` (phase 2): the agent writes `fugaro.yaml`, optionally `.fugaro/<workflow>.Dockerfile`, validates, builds locally, and shows `fugaro init --repo --plan-only` (a read-only command the skill may run) to the user. The skill puts `fugaro.yaml`, the Dockerfile and the `.claude/settings.json` change that init made in stage 8 in one pull request and **tells the user to merge it**: `fugaro.yaml` is read from the default branch at every run and the Cloud Build image build clones the default branch, so neither can be provisioned from an unmerged file (§5.5 names a pre-merge build as slice D). A teammate gets the plugin only once `settings.json` is merged and they trust the folder (§4.7).
3. After the merge, the user runs **`fugaro init`** again in the checkout. The converge sees stage 9 applicable and onboards the repository: registry, build account, jobs, first image build (billable, own confirmation), second apply, check unpaused. `fugaro init --repo` stays as the explicit form for scripts and for onboarding a repository from another directory.
4. `fugaro doctor` (and the skill's last step) confirm: validate, image status, a smoke `fugaro run` suggestion the user decides on.

README "Getting started" is then: 1. `fugaro init`, 2. `/fugaro:setup` in your coding agent (it will tell you when to run `fugaro init` once more). Because the plugin installs only once the folder is trusted (§4.7), `fugaro init` ends by saying so: it installs by itself, silently (the trust dialog does not mention it), and its skills are there in the first session, no restart. That keeps the brief's two lines and puts the third in the skill, where an agent can explain it. Alternative considered and rejected: the skill running `init --repo` itself with `--yes` (cloud resources and a billable build applied by an agent, which §9 forbids).

## 4. The skills system

*Amended 2026-10-04 (user ruling, binding): the plugin is kept. The earlier design of this section (skills embedded in the binary, installed as `.claude/skills/fugaro-*` files, per-file version and hash stamps, a six-state machine) is withdrawn.*

### 4.1 The set

The skills live **only** in `plugin/skills/<name>/` (single source), as markdown with `reference/` files. Plugin skills are namespaced by the plugin name, so the directory `setup` is invoked as `/fugaro:setup` (the brief's `/fugaro-setup`, today's `fugaro:onboard`).

| Skill (`plugin/skills/<dir>`) | Trigger | Content |
|---|---|---|
| `setup` (`/fugaro:setup`) | the user runs it, or asks to set Fugaro up for this repository | §5 |
| `working` (`/fugaro:working`) | the user wants to hand a task to Fugaro, check on runs, read logs, understand a result, continue a PR | `SKILL.md` is the decision tree and the rules of a good task; `reference/launch.md`, `status.md`, `logs.md`, `diagnose.md`, `followup.md` carry what the five plugin skills say today (migrated, trimmed), plus the dashboard (`fugaro watch`, `budget show`), cancel and retry, draft PR versus ready |
| `routing` | the agent is about to decide where a piece of work should run | the judgment table of §4.2 |
| `parallelism` | the agent plans work that could be split | wide for independent work, narrow for coupled, optionally redundant attempts for a hard single task; short (about 60 lines) |

The five operational skills (`launch`, `status`, `logs`, `diagnose`, `followup`) merge into `working`; `onboard` becomes `setup`. Recommendation on the brief's "may be folded into #2 if short": **keep parallelism separate.** Its trigger is planning, not operating, and the description (what Claude Code matches on) differs. Everything operational is one skill with reference files so the agent loads the manual only when it is working with runs.

### 4.2 Cloud versus local (the routing judgment)

Self-contained coding tasks with clear acceptance criteria, that build and test inside the repository's image: cloud. Local: anything needing credentials or state that exist only on the developer's machine (investigating live cloud resources, a database with local data, VPN-only services, a task reading a private path), anything interactive or exploratory ("look at this and tell me"), anything that touches money or security (`docs/dogfooding.md` already says which parts of Fugaro itself go through a local review loop), and anything the image cannot run (Docker-in-Docker, Testcontainers, Android builds; Cloud Run has no Docker daemon). Cloud jobs' credentials deliberately do not grant machine access, so a task that "needs" them is the wrong task for the cloud. When unsure: split, with the self-contained part to the cloud.

### 4.3 How the plugin reaches the team: project settings, pinned to the tag

`fugaro init` (stage 8) and `fugaro update-skills` merge two entries into the checkout's `.claude/settings.json`:

```json
{
  "extraKnownMarketplaces": {
    "fugaro": { "source": { "source": "github", "repo": "dimipaun/fugaro", "ref": "v0.2.0" } }
  },
  "enabledPlugins": { "fugaro@fugaro": true }
}
```

(The shape, including `ref`, is what `claude plugin marketplace add dimipaun/fugaro#<tag> --scope project` and `claude plugin install fugaro@fugaro --scope project` wrote with Claude Code 2.1.289; see §14.) The plugin installs by itself, with no install prompt, when a teammate opens and trusts the project (Claude Code 2.1.289, verified live 2026-10-04; the trust dialog lists only pre-approved permissions and does not mention the plugin). **A repository's settings can therefore install a plugin from whatever marketplace they name: only trust folders you trust** (the notices flag other marketplaces and plugins). The marketplace lists the plugin by a relative path (`./plugin`), so the plugin loads from the marketplace copy at the pinned ref, with no second install source.

- **The pin is the binary's release tag** (`fugaro version` is `0.2.0`, the ref is `v0.2.0`). The release gate already forces `plugin/.claude-plugin/plugin.json` version equal to the tag (`scripts/release-gate.sh`, `scripts/bump-plugin-version.sh --check`), so the binary, the plugin and the pin agree by construction. A `dev` binary has no tag: init writes no pin, says so, and prints the snippet with a placeholder.
- **Merge, never overwrite.** The file is parsed as JSON; every other key, and every other marketplace or plugin entry, is kept. Only `extraKnownMarketplaces.fugaro` and `enabledPlugins["fugaro@fugaro"]` are set. The diff is shown and written after the stage's confirmation; a file that does not parse is never rewritten (init prints the snippet and the parse error). `settings.local.json` and user settings are never touched. A `fugaro` marketplace entry that names a different repository (a private fork hosting its own marketplace) keeps its repository and only its `ref` is moved, with a note. Init never commits; the user reviews `git diff`.
- **Updating** is `fugaro init` or `fugaro update-skills` after upgrading the binary: it bumps the `ref`, one line in `settings.json`, reviewed in a PR like any other. `update-skills [--check] [--dir D] [--json]` needs no credentials, no network and no Terraform; `--check` prints the state and exits 1 when it is not `ok`. Whether an existing install moves to the new ref on its own, and how a teammate refreshes it, is §14 item 1d.
- **Outside a checkout** there is nothing to install: init prints the settings snippet and says where it belongs (Q5, decided).
- **Skills stay agent-neutral** (plain markdown, no Claude-specific tool names), but the wiring is Claude Code's; other coding agents are not wired by init.

### 4.4 Header, version and the staleness states

Each skill file keeps a visible header and the version it ships with:

```
<!-- fugaro-skill name=setup fugaro-version=0.2.0 -->
> **Fugaro-owned skill (Fugaro 0.2.0). Do not edit this file.** It comes from the Fugaro plugin and is replaced when the plugin updates. To change how your agent behaves, write your own skill in a separate directory.
```

The version in the header is rewritten by `scripts/bump-plugin-version.sh` with `plugin.json`, and checked by `--check` (so the release gate fails on a header that disagrees with the tag) and by a test. There is no hash and no per-file state machine: the skills are not copied into repositories, so they cannot be edited in place there.

What the CLI compares is the **pin** in `.claude/settings.json` (and, where readable, the installed plugin version) with the running binary:

| State | Meaning | Severity |
|---|---|---|
| `ok` | the pin equals the binary's tag | none |
| `outdated` | the pin is older than the binary (semver) | warning: run `fugaro update-skills` |
| `newer` | the pin is newer than the binary | warning: upgrade the CLI (the pin is never moved down) |
| `unpinned` | the `fugaro` marketplace entry has no `ref` (it tracks the default branch, so skills can be ahead of or behind any binary) | warning |
| `foreign` | the marketplace entry names a repository other than the expected one | warning (a private fork is legitimate; an unexpected change in a PR is not): named, never rewritten |
| `not wired` | no marketplace entry or the plugin is not enabled in the project settings | warning: run `fugaro init` or `fugaro update-skills` |
| `installed differs` | the installed plugin version differs from the pin | warning: in Claude Code run `/plugin marketplace update fugaro` (verified live: after a changed `ref` the plugin shows "not cached" and its skills disappear until that command is run; it works in the same session, no restart) |
| `not installed` | wired, but this person has not installed or has declined the plugin | **informational**, never a failure |
| `cannot compare` | a `dev` binary, or the installed version is unreadable | informational |

The installed version is read from `~/.claude/plugins/installed_plugins.json` (the `fugaro@fugaro` entry's `version`, `scope` and `projectPath`, observed with Claude Code 2.1.289; the file's format is not a documented contract, so an unreadable or unexpected file means `cannot compare`, silently).

### 4.5 Staleness detection in the CLI

- **Regular commands** (`run`, `ls` without `--watch`, `validate`, status-like commands, `init`): one stderr line at most per process, `warning: the Fugaro plugin pinned in .claude/settings.json is 0.1.0, this is 0.2.0: run fugaro update-skills`. Stdout and `--json` are untouched, no network, never an error, silenced by `FUGARO_NO_SKILL_WARNING=1`, nothing inside a Cloud Run job (`backend.OnCloudRun`). Cost: reading one small JSON file found by walking up from the working directory (and the installed-plugins file).
- **`fugaro doctor`** (new, read-only, `--json`, exit 1 when any check fails): the shared preflight checks (§3.1 stage 0), the local config and the installation it names, whether the base images and the history image are mirrored, the stored secrets by name (never values), `fugaro.yaml` validity, and the plugin table above. Every failing check prints the one-line fix.
- **`fugaro doctor --plugin --strict`** is the one a repository puts in CI: offline (no credentials), only the plugin checks, and **every warning state fails it** (`outdated`, `newer`, `unpinned`, `foreign`, `not wired`); the informational states (`not installed`, `cannot compare`) never do, and `installed differs` is not evaluated there (a CI runner has no install). This is the supply-chain control of §9.

### 4.6 Authoring and testing in this repository

- **Source:** `plugin/skills/<skill>/**` only. A contributor tries a change with `claude --plugin-dir plugin` (a documented flag). The repository's own `.claude/settings.json` is wired by `fugaro init` like any other (pinned to the last tag); nothing is generated or committed per skill.
- **Tests that make the skills a checked artifact** (all offline, in CI):
  1. every skill has frontmatter (`name` equals the directory, a description of bounded length that contains a trigger phrase), the visible header, and a header version equal to `plugin.json`'s; no unresolved placeholder;
  2. **every `fugaro` command and flag a skill names exists** (the existing `TestSkillCommandsExist` pattern, extended to flags and to reference files);
  3. **every fenced `yaml` example labelled `fugaro.yaml` in a skill validates** against the real schema (`config.Load`);
  4. **JSON field claims are real:** a table in the test lists each field a skill reads from `--json` output (`valid`, `problems`, `smoke.checks[].ok`, ...) and checks it against the structs;
  5. **forbidden-instruction lint** (§9): no skill contains `--yes` next to `init`, a secret value pattern, `secrets set` with an inline value, `print-access-token`, `curl | sh`, `--allow-delete`, `--forget`, `budget set`/`resume` as an instruction (a skill may *describe* them and say the user runs them; the lint allows them only inside a block marked `user-runs`);
  6. a size budget per skill file: `SKILL.md` at most 400 lines, reference files at most 300;
  7. **the plugin carries skills only:** no hooks, MCP servers, commands, agents or `bin/` (a plugin is code that runs with the user's rights; §9), and the marketplace entry carries no version (existing test);
  8. the settings merge (§4.3) and the pin states (§4.4) as table tests: merge into an empty file, into a file with other keys and other marketplaces, into an invalid file (refused), a fork entry, idempotent re-run, `dev` binary.
- **Staying truthful as the CLI changes:** tests 2 to 4 fail when a flag or field is renamed, and a CLI change that touches a command a skill documents shows up as a skill diff in the same PR (the PR template gets a checkbox). The version is the release's, so a release always ships skills that match its commands; the pin check handles installs that lag.

### 4.7 Limits, stated honestly

- **The marketplace repository must be readable by the user's Claude Code.** Fine while `dimipaun/fugaro` is public. A private fork hosts its own marketplace and plugin at its own tags; init then keeps the fork's repository in the entry (§4.3) and every teammate needs git access to it.
- **First-run experience.** The marketplace entry applies only after the user trusts the folder, so the plugin appears when the folder is trusted, not immediately after `fugaro init`. It installs by itself, silently, and its skills are usable in the first session (verified live, §14 item 1d). Init says so and prints the command for the person who ran it and wants it now (`claude plugin install fugaro@fugaro --scope project`). After a pin change, `update-skills` and `doctor` say to run `/plugin marketplace update fugaro` in Claude Code.
- **Teammates can decline the prompt.** Then there are no Fugaro skills for them; `fugaro doctor` reports `not installed` as informational, and the CLI works as before.
- **Other agents** are not wired.
- **Pre-0.1 pins.** Until a binary has a tag the pin cannot be written (`dev`).

## 5. `/fugaro:setup`

It is today's `fugaro:onboard` grown in four directions: services, the human decisions, the handoff to init, and being wired into the project by init.

### 5.1 What it must discover

For each candidate workflow: language(s) and toolchain versions (the existing evidence table: `.nvmrc`, `.tool-versions`, `engines`, CI `setup-*` actions, CI container images, `go.mod`, Gradle wrapper and toolchain blocks); the build tool and the test commands exactly as CI runs them; JUnit report paths; resource sizing from the CI machine size; the repository's secrets that the build or tests read (names only); the git provider and default branch; services the tests need (docker-compose files, Testcontainers, `services:` in CI, emulator configs, `DATABASE_URL`-style test variables). Evidence is cited with file and line, as today, and nothing is invented.

### 5.2 Services

| Need | How it is provided |
|---|---|
| Postgres, Redis, Firebase emulators | `java-services` base: `fugaro-services start` as the first step of `commands.test` (exists) |
| Postgres or Redis on another base | `image.apt` plus a start line in `commands.test`, or a Dockerfile for the vendor package |
| Other servers (MySQL, Mongo, Kafka, Elasticsearch, a browser) | `image.apt` or `image.setup`; a Dockerfile when a vendor installer is needed; started in the test command; memory counted against the job (Cloud Run `/tmp` is memory) |
| Docker daemon, docker-compose, Testcontainers | **Not available on Cloud Run.** The skill stops and tells the user: a test command that covers the suites that do not need it, or wait for the Docker backend (M8). It never works around it |

### 5.3 The Dockerfile question

Today an image is a Fugaro **base kind** (`web-node`, `go`, `java-services`) plus a **derived image** rendered from the template with the workflow's `image:` block (`node`, `apt`, `setup`, `skip_build_scripts`), or from a repository Dockerfile `.fugaro/<workflow>.Dockerfile` (`dockerfile:`, exclusive with `image:`) that must build `FROM ${FUGARO_BASE}`, clone into `/work/repo`, keep `finalize-checkout`, end as `USER fugaro`, not replace `ENTRYPOINT`; `fugaro validate` checks this and `fugaro image build --local` smoke-tests the result (no root, no sudo, tini, no setuid, claude present, checkout at the built commit, build command passes).

The brief wants the agent to author "Dockerfile and `fugaro.yaml` together". Recommendation: **keep the declarative block as the default and the repository Dockerfile as the escape hatch, and make the skill good at choosing.** Reasons: the template carries the parts that are security-critical and easy to get wrong (the git credential as a BuildKit secret that no layer keeps, secrets as mounts, removal of the sudo rule and setuid bits, `finalize-checkout`); an agent that writes the whole Dockerfile will get one of them wrong sooner or later, and `validate` and the smoke test catch only the contract, not every leak. So:

- The decision rule in the skill: use `image:` unless the evidence needs something it cannot express (a vendor installer, a toolchain that is not a Node version or an apt package, build arguments, a multi-stage tool build). Then `fugaro image render --workflow W > .fugaro/W.Dockerfile`, remove `image:`, set `dockerfile:`, and edit the rendered file **minimally**, keeping the contract. The agent never starts from a blank Dockerfile and never writes one at the repository root (that is the application's, if it has one).
- **Together:** the skill treats `fugaro.yaml` and the Dockerfile as one decision: `commands.build/test`, `resources`, `image:` or `dockerfile:`, secrets and the service start line are written in one pass and validated in one loop (`fugaro validate --json`, then `fugaro image build --local --json`, both until clean).
- **Human review of executed text.** Every `image.setup` line and every added Dockerfile instruction is shown to the user in the conversation before the setup PR (§9): these run in Cloud Build with the build account and the declared secrets mounted.
- **How it builds on Cloud Build:** unchanged: the render step reads the default branch, the build step builds `FROM` the base pinned by digest in the project's registry (§3.3), then the smoke test runs without network and promotion happens only on a pass. The Dockerfile is therefore only testable in the cloud after it is merged; locally, `--local` is the gate, and the first Cloud Build is the real test (slice D proposes `fugaro image build --ref BRANCH`, a non-promoting build of a pushed branch, to close that).
- Without Docker locally, the skill says so, finishes with `validate`, and leaves the first cloud build as the test, telling the user to run `fugaro image build` in their own terminal (a billable build is typed, never `--json`, never in an agent session) and how to read a failed one (`fugaro diagnose`).

### 5.4 The human decisions it must ask (never default silently)

`agent.auth` (`oauth`, `api-key`, `vertex`; the choice decides which secrets exist, and `oauth` runs have no gateway cap); `agent.models.coder` and `reviewer` (explicit IDs; the skill reads the current allowed and priced IDs from the CLI, never from memory; with a budget on, aliases are refused); the budget (`budget:` block with `mode`, `per_run_usd`, `per_day_usd`: offered, numbers only from the user; project-wide caps and kill switches are `fugaro budget set`, which the user runs); `git.pr.reviewers` (Bitbucket needs UUIDs) and `labels`; `followup.trusted` (**security**: whose PR comments a follow-up run acts on; empty by default, ids only from the user); `review_rounds`; workflow names when there are several; `rebuild.check`; whether anything marked money or security should be kept off Fugaro. It uses the agent's question facility one topic at a time, with the evidence and a recommended answer.

### 5.5 Validation and the end of the skill

`fugaro validate --json` clean; `fugaro image build --local --json` with `smoke.passed`; `fugaro init --repo --plan-only` shown to the user (read-only); `fugaro secrets ls --json` compared with what the config needs (§3.5); one PR with `fugaro.yaml`, the Dockerfile if any, and the `.claude/settings.json` change init made, never committed or merged by the agent unless the user says to; then the instruction to run `fugaro init` after the merge and a suggested first `fugaro run`.

## 7. The pluggable backend seam

**What exists.** `internal/backend.Backend`: `Launch`, `Execution`, `List`, `Logs`, `Cancel`, `LongestTaskTimeout`, `TaskTimeout`, with `backend/gcp` implementing it on Cloud Run (and `Prices` for compute cost). Storage is `gocloud.dev/blob`. **What is not behind it:** Secret Manager (`gcp.Secrets`, imported by `cli/secrets.go`), image builds (`backend/gcp/build.go`, Cloud Build), the registry, logs isolation, and provisioning (init is Terraform for GCP). Eleven files in `internal/cli` import `backend/gcp` directly. Firebase is the control plane (budget, dashboard, stats) regardless of compute, as the brief says, and so stays GCP-bound even with another compute backend: an AWS team still needs a Firebase project. That is the brief's intent and should be said in the contributor doc.

**Small changes that keep the door open** (no AWS work):

1. **A name:** local config `backend: cloud-run` (default) and a constructor registry `backend.Open(name, ...)`, so the CLI asks for a backend by name instead of importing `gcp` in eleven places. Do the two or three call sites init is already touching; leave the rest.
2. **Init stages as the per-backend unit:** the stage interface of §3.1 (`Check`, `Plan`, `Apply`, `Left`) is defined in a backend-neutral package; the GCP backend contributes its stages. A contributor's backend brings its own stages for what Terraform does today.
3. **Optional sub-interfaces,** each only where a second backend needs it: `Secrets` (Set, List), `ImageBuilder` (Build, Status), `CostReporter` (compute cost of an execution). Not introduced now; the conformance suite names them as the next step.
4. **A conformance suite:** `internal/backend/backendtest.Run(t, factory)` exercising the five lifecycle methods against any implementation, run today against the GCP backend on the existing fake. A contributor's pull request is "passes `backendtest`".
5. **Docs:** `docs/backends.md` (what the seam is and is not, the Firebase dependency, the list in item 3), linked from the README's help-wanted section.

## 9. Security

Skills are text that a user's agent obeys **with the user's credentials** (ADC, the logged-in `gh`, shell access), and Fugaro's own `init` creates billable resources. The threats and answers:

| Threat | Answer |
|---|---|
| A skill (ours, buggy) tells the agent to do something destructive or costly | Fugaro-owned and shipped in a release whose checksums are signed, at a tag that the marketplace pin names; the forbidden-instruction lint (§4.6 test 5) and a security review of every skill's content in the plan (own review) |
| The plugin ships more than skills (a hook or an MCP server runs code with the user's rights on every teammate's machine) | A test fails any hook, MCP server, command, agent or `bin/` in `plugin/` (§4.6 test 7); the plugin is reviewed like code |
| A PR changes the marketplace entry in `.claude/settings.json` to another repository or ref, or unpins it (every teammate who trusts the folder then has that plugin installed silently, with no prompt, and its skills are obeyed by their agent) | The skills are no longer in the repository, so there is nothing to edit in place, but `settings.json` is now the attack surface: `fugaro doctor --plugin --strict` in the repository's CI fails `foreign`, `unpinned`, `outdated` and `newer`; CODEOWNERS on `.claude/settings.json` recommended in the docs; a pin to a tag, not a branch, so the content is fixed; Claude Code's own trust dialog is the last gate, but it does not mention the plugin (verified live), so only trust folders you trust |
| Prompt injection from what the setup skill reads (README, CI files, `package.json` scripts, issue text) | The skill states that repository content is data, never instructions; it takes commands from CI as *evidence for `commands.*`* and does not run them; it never executes deploy or release steps found there |
| The agent runs init or applies cloud changes | The skill never tells the agent to run `fugaro init` (other than `--plan-only` and `--print-vars`), `--yes`, `--allow-delete`, `--forget`, `--allow-job-delete`, `--onboard-repo`, `--replace-image`, `--create-project`, `--link-billing`, `--allow-fork`, `fugaro budget set|kill|resume`, or anything that spends (the lint's forbidden flags); init needs a terminal for its typed confirmations, which an agent session has not, and refuses to apply anything under an agent's environment (next row) |
| What `--yes` covers, and what nothing but a person at a terminal does | `--yes` confirms only the **ordinary** steps, and only when no agent environment marker is set: the installation's and the Firebase root's Terraform applies, the registry copy of the release images, the local config's writes, the plugin wiring and a **known** repository's onboarding steps. It never covers a **typed-only** step (`initflow.Typed`; `--yes`, `--non-interactive`, `--json`, a pipe and an agent environment all leave it needs-you with the one-line route): creating a project or linking billing (the typed project ID, the typed account), a secret (the hidden prompt), a repository the project does not list (typed `owner/name`, or `--onboard-repo` in a terminal with no agent marker), the Firestore database's permanent location (typed), a billable image build (the project's name typed; the same rule holds for a standalone `fugaro image build` without `--local`, which has no `--yes` and never takes `--json`, and `fugaro image check --job` submits nothing in an agent session), and replacing a release tag or `history:latest` in the registry (`--replace-image KIND`, repeatable, names the intent and is itself never enough: the project's name is typed at a real terminal). Under an agent environment (`CLAUDECODE`, `CLAUDE_CODE_ENTRYPOINT`, `CLAUDE_CODE_SSE_PORT`, `CLAUDE_CODE_REMOTE`, `CURSOR_AGENT`, `AI_AGENT`) **every applying stage is needs-you** ("run this in your own terminal window, not through a coding agent") and no "pass `--yes`" hint is printed; read-only checks and `--plan-only` still run. A run that adopted an existing installation changes nothing more in the cloud in the same run (the notes say an owner applies); the plugin wiring, a local `.claude/settings.json` edit with its own confirmation, is the one stage still run. **This is a mitigation, not a barrier:** an agent can unset its own environment, `CLAUDE_CODE_SSE_PORT` is also set in a person's own IDE terminal (only that marker's refusal tells the person they can unset it; no other refusal carries an unset hint), and a person can always run the commands themselves. What actually bounds an agent is the skills' lint (it may not be told to pass these flags), the typed confirmations at a real terminal, and the user reading what they confirm. Tested by a matrix over every stage and mode (`TestApplyMatrix`) |
| The agent handles a secret | A skill never asks for, reads, prints, echoes, writes into a file or pipes a secret value; never runs `fugaro secrets set` itself; lists names with `secrets ls` and gives the user the one-line command to run in their own terminal; tells the user not to paste a value into the conversation; never runs `gcloud auth print-access-token`, `gcloud auth print-identity-token`, reads credential files (`~/.config/gcloud`, `~/.config/fugaro`, `.env`), or sets `GOOGLE_IMPERSONATE_SERVICE_ACCOUNT` |
| The agent adds executed text from an untrusted source to the build | `image.setup` and Dockerfile lines are shown to the user before the PR; downloads are pinned by version and checksum; `curl | sh` and unpinned `latest` are refused by the skill (and warned on by `validate`, to add) |
| The agent widens trust | The skill never writes `followup.trusted`, `git.pr.reviewers`, `budget` numbers or `allowed_models` the user did not state; never loosens a ceiling; never commits, force-pushes or merges unless the user says so |
| The skill sends the agent to the wrong place (cloud versus local) | Routing judgment is explicit; cloud jobs' keys do not reach local resources by design |
| The mirror copies a tampered image, or a release tag moves | **Accepted risk (T2).** **A git tag is mutable.** Whoever can move the `v*` tag changes what the plugin pin (`ref: vX.Y.Z` in `.claude/settings.json`) and the image tags (`ghcr.io/dimipaun/fugaro-*:X.Y.Z`) resolve to: both are anchored to the tag, not to content. The copy is verified against the digests the registry serves now, which proves it equals what ghcr.io served, not that ghcr.io served the release. Whether Claude Code verifies a plugin it installs from the pin is **unverified** (§14). **Recommended, and the repository owner's setting (Fugaro does not change repository settings):** a GitHub ruleset restricting updates and deletions of `v*` tags, and immutable releases; both are on the pre-tag checklist in `docs/release.md`. **Decision (2026-10-04, live Check 27): one confirmation per run for the ordinary steps in a project Fugaro owns.** A first `fugaro init` in a project Fugaro had just created asked the user to type the project's name about nine times (installation apply, Viewer-read removal, Firebase apply, Firestore write, image copy, history-job apply, repository confirmation, repository apply, first build), most of them guarding free, reversible resources in a project nobody else uses. In a **Fugaro-owned** project (created by this run, or the runs bucket's `fugaro/project.json` names this project and this GCP project, a read-only check that fails closed) the ordinary steps share one review screen and one typed project name, asked when the first of them has something to change (not up front: a rerun with nothing to do must not ask), held in memory for the run only. Still separate, each its own typed confirmation: project creation, the billing link, the Firestore database's creation, every Cloud Build, replacing a registry tag, an unlisted repository (typed owner/name) and secrets; none of their code can reach the run confirmation (`TestRunConfirmationCallSites`). The first covered steps are the state bucket and the Cloud Resource Manager API, which need no plan because they are fixed, announced, free and listed on the screen; **every later Terraform plan is classified against an allowlist, not a denylist** (`tf.Cover`): covered only if every resource type is one our modules declare (pinned by `TestAllowedTypesCoverTheModules`), the actions are creates and in-place updates only, each IAM member is a listed launcher/operator/budget admin or a fugaro service account of this run, each role is one the modules use or a fugaro custom role of the project, nothing is an IAM binding, policy, audit config, service account key or a custom role whose permissions change, and **the attributes are the modules'** (a job's image is in this project's registry and its command is the modules' or none; a scheduler calls a job of this project and region on run.googleapis.com as a fugaro account; a log sink goes to this project; a bucket is private; `project`, `bucket` and `repository` are this run's; a budget names only the billing account the review showed; the web key has its two API targets; an import's ID is in this run's projects, **and the import is one that this root's own discovery wrote** (exactly its address and ID, for all three roots: the installation's, the repository's and the Firebase root's; a stale `imports.tf.json` or a hand edit is not covered and its stage asks its own typed name; see [adopt-firebase-root.md](adopt-firebase-root.md) §4.5); a computed member or role is trusted only when the same module creates the account or role; account and role names are the modules' exact ones, pinned by tests against the code); **the Firebase project is verified separately**: with `--firebase` naming a project other than the installation's, its root and its database writes are covered only if that project's own runs bucket carries this project's mark (in practice they ask their own typed names), and the screen says which project each root applies to and whether it is verified; a plan that cannot be read is not covered; such a plan stops its stage, which asks its own typed name. The trade: an attacker who can plant a marker in the runs bucket of a project the user adopts saves the user some typing there, in steps that are free and reversible by design; the typed-only steps are untouched. Follow-up, not built: a per-type map of which member classes may hold which role (today any module role goes to any accepted member). Not built: a pre-plan of the Terraform roots for the review screen (a fresh project has no state bucket to plan against, so the screen says "planned when applied" and each stage still prints its exact plan before it applies), and the standalone `init --repo`, which keeps per-step prompts.

**Decision (2026-10-04, live Check 27): a new project config defaults `launchers` and `operators` to the authenticated user.** The first `init` applied an installation with both lists empty, so nobody held the launcher or token-minter role and `fugaro run` failed with "not allowed to sign as the token signer". ## 10. Risks

- **Init is the largest file in the CLI (1,943 lines in `init.go`) and creates billable resources.** The converge loop wraps the existing step functions rather than rewriting them; each stage keeps its confirmations and tests; the orchestrator is the only new control flow. Mitigation: the orchestrator and the mirror and secrets stages are reviewed on their own (plan).
- **Project creation and billing linkage depend on Google behaviours and permissions that vary by organisation** (policies, quotas, who may link billing). Mitigation: slice C last, flagged, errors verbatim, a printed fallback; live-tested on a throwaway project.
- **A new dependency for the registry copy.** Reviewed like any other (licence, size, maintenance); the alternative is a thin client of the registry HTTP API that we would then own.
- **The skill is the product's second UI** and an agent may follow it loosely. The tests pin commands, flags and fields, not behaviour; the live check (§11) runs the skill end to end on real repositories, and a skill revision is cheap to ship.
- **The plugin or its fetch reached from a cloud run** (§9, §14 item 1c).
- **Scope creep into AWS:** only the seam of §7.
- **Unverified API facts** (§14): each is checked before its stage ships.

## 12. Release and docs changes this implies

**Accepted risk: the trust anchor is the registry's current tag.** Digest verification proves the copy equals what ghcr.io served, not that ghcr.io served the release: whoever can write `ghcr.io/dimipaun/fugaro-*:X.Y.Z` can make the user's cloud run their code. `--expect-digest KIND=sha256:<hex>` pins a digest obtained out of band (the tag's index digest, from the release notes); the CLI prints the full digest of everything it copies. Cosign verification of the image digest and a signed digest list in the release are the planned fix (plan, follow-up task F1). A tag in the project's registry that names another image (a release tag, or a hand-pushed `history:latest`) is never replaced without `--replace-image` and a confirmation naming both digests. Known limits of the copy: the destination tag is re-read just before the manifest PUT, but there is no conditional manifest PUT, so a small window remains; abandoned upload sessions are not deleted by init, Artifact Registry expires them; a finalize call has its own 30-minute silence limit.

The images workflow publishes `fugaro-history` and fails when an image is not anonymously pullable (a `docker manifest inspect` without login); `fugaro-go` is published from the first tag after it exists (already true of the workflow); the release notes carry the base digests. README: "Getting started" is the two lines, and the long Quickstart moves under a "Manual setup" heading in `docs/gcp-setup.md` (the deep reference stays: it is what `init`'s stages are). `docs/design/v1.md` §5.2, §8 and §9.2 are updated (the onboard skill becomes `fugaro:setup`; `init`'s converge and the mirror; the plugin is kept and wired through project settings, pinned to the tag). `docs/dogfooding.md` becomes the two-command flow. `docs/release.md` gains one paragraph: the plugin version, its skills' header versions and the tag the pin names must agree (§4.3), and a tag is never moved.

What was merged (the plan's status line has the PRs) against what the sections above propose. The decisions are the implementers' ledger entries and the reviews' rulings; the CLI's `--help` is the reference for flags.

**Not built.** T18 (`image build --ref`, optional), F1 (cosign signing and verification of the images; `--expect-digest` is the only pin), the `services` stage of §3.1 (the installation's Terraform keeps enabling the APIs), `--base-from-source` (§3.3).

**T12 merged (#106).** Every printed command is one line (`TestPrintedNextStepsAreOneLine`, `TestPrintedCommandsGolden`, the skills' `TestSkillCommandsAreOneLine`), and the no-terminal refusal is one sentence (`TestNoTerminalMessageUniform`).

**The final-fixes wave (after the two final reviews).** Decided differently from the text above, and §9 states the result: `--yes` is split into an ordinary class and a typed-only class (`initflow.Typed`: project, billing, secrets, an unlisted repository, the Firestore location, a billable build, replacing a registry tag); an agent environment applies nothing; `--replace-image` takes a kind and is never enough alone; `init --repo` on its own and the secrets stage sit behind the hostile-checkout gate; `fugaro.yaml` is read as a bounded regular file; a run that adopted an installation applies nothing more; `--json` prints one object on every outcome; the binary prints its release commit; and the plugin stage and `doctor` list what else the settings file carries.

**§3.1 stages.** The stages are `preflight`, `project` (registered only with `--create-project`), `installation`, `firebase` (only with `--firebase`: it is not the default, so a first `init` builds no Firebase backend and a user who wants one passes the flag), `images`, `installation-2`, `secrets`, `plugin`, `repository`; gating is linear over the registered ones, not the dependency graph (the graph is documented and tested against the order). `--yes` never covers `project` or `secrets`, and `--json` never prompts. The engine's own typed confirmation still prompts under `--json` (unchanged; the rule applies to the secrets stage). The exit code is 1 for a stage that needs the user, 2 only for an engine's coded remote failure. Engine stages cannot check read-only (they plan when applied), so the plan view is the loop's, and each engine prints its own Terraform plan.

**§3.1 inputs.** Name, GCP project and region are gathered before the loop (the config must exist before any stage). The repository stage collects the GitHub App's ID and it is validated and refused when it conflicts with `--config-only`, `--forget`, `--print-vars` or a `--repo` mismatch, and warned about when unused. A checkout's `fugaro.yaml` project never names a new installation silently.

**§3.2 project and billing.** The flags are `--create-project` (a boolean) with `--gcp-project <id>`, plus `--parent` and `--display-name`; `--link-billing <account>` is valid only together with `--create-project` (it links a project this run created, or an existing one that has no billing link at all, on a rerun). Billing accounts are not listed (§3.2's note). Unverified against the real APIs: propagation, `addFirebase` polling, organization policies, billing quotas, restricted project-ID words.

**§3.3 the mirror.** No `go-containerregistry`: `internal/mirror` is about 600 lines of `net/http` against the OCI distribution API (the allowlist, the credential never sent to the source, the host-pinned token and push-last are simpler to enforce and test that way). Only the `linux/amd64` image of an index is copied and the destination tag names that manifest. A development build skips the stage (it does not block `init --firebase`); the history image is mirrored only with `--firebase`. The flags are `--base`, `--image-source`, `--expect-digest` and `--replace-image`. There is no read-only writer-role check: the first upload POST's 403 message is it. **Unverified live:** the ghcr anonymous token and blob redirect, Artifact Registry's OAuth2 Bearer for upload, and that its `Location` stays on its host.

**§3.5 secrets.** The stage covers more than the git credential and one Claude credential: also the allowed model providers' keys (with `agent.auth: api-key`) and the workflows' own `secrets:`, from the checkout's `fugaro.yaml` when it has one. PEM paste only: no file-path prompt (the printed command redirects a file). At most 120 lines per PEM, fail closed. It refuses in an IDE terminal that sets `CLAUDE_CODE_SSE_PORT` and says to unset it or use `secrets set`. The stage creates the secret's labelled container itself, which `init --repo`'s Terraform then adopts. It is a mitigation, not a barrier, against an agent that holds a value.

**§3.6 and §12 onboarding.** A repository not in the local config needs a typed `owner/name` or `--onboard-repo` (the hostile-checkout gate of §9), and the plugin stage is scoped the same way and to a `fugaro.yaml` of this project or none (a checkout with no `fugaro.yaml` is wireable after the typed opt-in, the first-run flow, since wiring precedes `/fugaro:setup`). A first image build keeps its own typed confirmation. The long Quickstart stayed in the README under "Manual setup" (the design said `gcp-setup.md`); `gcp-setup.md` is the deep reference.

**§3.1 adopt mode.** The installation stage writes the config from the outputs when state exists and the config file does not. Launchers and operators are copied from the outputs so a later plan does not undo them; registry cleanup, log isolation and the budget backend go into new `terraform.*` keys of the local config; a message lists what the outputs lack; an existing config is never overwritten (mode 0600). It cannot tell who the caller is, so the role note lists the members.

**§4 the plugin.** `--check` exits 1 on warning states only. A branch (non-tag) ref is `unpinned`. There is no per-command warning for `not wired`, `unpinned` or `foreign` (those are `doctor`'s). `Locate` stops at the git top, never the home directory, and needs a `.git` at or above the settings file. A non-github `fugaro` source is `foreign` and untouched; a fork is never blessed silently (a warning, state `foreign`, `--allow-fork` moves its ref only); an `enabledPlugins` value `false` is kept. A changed file is re-indented to two spaces, an already-wired one is untouched. `--check` outside a checkout exits 1. `doctor --plugin --strict` fails on warning states except `installed differs`. `doctor` reports `base_images` as recorded in the local config, not whether the registry still holds them, and the secrets' names best-effort inside a checkout.
