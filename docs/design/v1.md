# Fugaro v1 — Design

*Status: proposed · 2026-09-26 · Implements the product spec in [SPEC.md](../SPEC.md).*

This document turns the product spec into a concrete v1 design: language, distribution, components, the in-container lifecycle, schemas, security model, and test strategy. Where it deviates from SPEC.md, it says so and why.

## 1. Decisions at a glance

| Topic | Decision |
|---|---|
| Agent inside the container | **Claude Code headless** (`claude -p`), driven stage-by-stage by the engine, using the target repo's own `CLAUDE.md`, skills and subagents. |
| Model auth | All three supported, chosen per repo: **Vertex AI (default)** via the job's service account, Anthropic **API key**, or subscription **OAuth token**. |
| Engine language | **Go.** One static binary serves as both the local CLI and the in-container runner. |
| Images | Engine publishes **base images** (`server-jvm`, `web-node`); each consuming repo builds a **derived image** with its checkout and dependencies baked in, rebuilt by Cloud Build when a daily check finds it stale or wrong (§7.2). GCS caches layer on top at startup. |
| Git providers | **GitHub and Bitbucket Cloud**, behind one `Provider` interface. |
| Infrastructure | **Terraform modules** are the source of truth; **`fugaro init`** is a thin wrapper that writes variables and applies them. |
| Multi-cloud | **Seams only.** A `Backend` interface and `gocloud.dev/blob` storage; GCP is the only implementation. Repo config holds no cloud resource paths. |
| Build/test | **The agent runs and interprets them** through a recording wrapper (`fugaro verify`). The engine never re-runs tests; it only reads the record. |
| PR follow-up runs | **In v1.** A run can resume an existing Fugaro PR and address its review comments. |
| Status view | `fugaro ls --watch` in v1; web dashboard deferred. |

## 2. Goals and non-goals

**Goals (v1)**

- Run a self-contained task end-to-end in a Cloud Run job and always end with a PR (ready or draft).
- Server (JVM/Gradle) and web (Node/pnpm/npm) workflows.
- Many concurrent runs with no local resource use beyond the CLI.
- Follow-up runs that address review comments on an existing Fugaro PR.
- Launchable and inspectable by a local Claude Code agent through a plugin.
- No company- or repo-specific assumptions in the engine.

**Non-goals (v1)**

- Android workflow.
- A second cloud backend (the seams exist; the implementation does not).
- A hosted web dashboard or a long-running control-plane service.
- Bitbucket Data Center / Server.
- Auto-merge. Fugaro never merges.

## 3. Architecture

### 3.1 Components

```
                 ┌───────────────────────── local machine ─────────────────────────┐
                 │  Claude Code + fugaro plugin (skills)  ──►  fugaro CLI (Go)    │
                 └───────────────┬───────────────────────────────┬─────────────────┘
                   write task.json│                   jobs.run    │  ls / logs / diagnose
                                  ▼                               ▼
   ┌──────────── GCS runs bucket ───────────┐     ┌──── Cloud Run job fugaro-<repo>-<wf> ────┐
   │ runs/<repo>/<run-id>/{task,result,…}   │◄───►│  derived image                          │
   │ cache/<repo>/<wf>/<key>.tar.zst        │     │   └─ fugaro exec (runner, Go)           │
   │ locks/<repo>/<branch>                  │     │        ├─ claude -p  (stages)          │
   └────────────────────────────────────────┘     │        ├─ fugaro verify (build/test)    │
                                                  │        └─ Provider API (push, PR)       │
   Secret Manager ──(mounted as env/files)──────► │  runs as SA fugaro-<repo>-<wf>          │
   Cloud Logging  ◄──(stdout, structured JSON)─── └──────────────────────────────────────────┘
```

1. **`fugaro` CLI** (local). Commands: `init`, `image build`, `image check`, `image status`, `run`, `ls`, `logs`, `diagnose`, `cancel`, `secrets`, `validate`.
2. **Runner** (`fugaro exec`, in the container). Implements the lifecycle in §4.
3. **Base images**: `server-jvm` and `web-node`. They contain the toolchain, Claude Code (native installer), git, and the `fugaro` binary.
4. **Derived images**: one per (repo, workflow), built from a template Dockerfile.
5. **Terraform modules** (`deploy/terraform/gcp/{modules/{installation,repo,workflow},roots/{installation,repo}}`, embedded in the binary by `deploy/terraform/terraform.go`), with `fugaro init` wrapping them (§8). The Go side is `internal/infra` (names, tfvars, discovery, readiness, and `internal/infra/tf`, the Terraform wrapper) and `internal/imagecheck` (the image record and the daily check, §7.2).
6. **Claude Code plugin** (`plugin/`). This repo is also a plugin marketplace.
7. **Schemas**: JSON Schemas for `fugaro.yaml`, the task spec, and the run record.

### 3.2 Job model

**One Cloud Run job per (repo, workflow), and one execution per task.** The job definition fixes:

- the derived image
- the dedicated service account
- which secrets are mounted
- CPU, memory, and task timeout
- `maxRetries: 0`, because agent runs are not idempotent

Terraform creates the job. The CLI only calls `jobs.run` with an env override `FUGARO_RUN=<repo-slug>/<run-id>` and, when the run has a timeout override, the execution's task timeout (§4.5).

Job naming: `fugaro-<repo-slug>-<workflow>-<hash>`. `repo-slug` is the repository path (`owner/name`, ASCII lower-cased, without `.git`) with runs of other characters replaced by `-`, truncated to 46 characters, then `-` and 16 hex of SHA-256 over the git provider kind and the path. The kind is included because `git.provider` is per repository: a GitHub `acme/app` and a Bitbucket `acme/app` in one deployment get different slugs. The slug is at most 63 characters, so it fits a label value, and its bucket prefixes are the IAM boundary between repositories. Job, service account, secret and image names drop the slug's hash from their readable part, truncate to the resource's limit (49 for a job, 30 for a service account), and end in hex of the SHA-256 of (slug, workflow or secret name): 12 for a job, 8 for a service account, 16 for a secret or image. The hashes make names distinct against accident, not against a name chosen to collide; the control there is that onboarding (`fugaro init`, and the M4 bootstrap before it) verifies that an existing job, service account or secret belongs to the same repository and workflow before reusing or deleting it.

- **Three more names per repository,** each derived in a hash domain of its own, so none can collide with another kind of name, even one built from a workflow called `build` or `check`:
  - **The build service account,** `gcp.BuildServiceAccountID(slug)`, which Cloud Build runs as for that repository (§6.1, §7.2). Its hash is over `build\x00<slug>`.
  - **The image registry,** `gcp.RegistryRepoID(slug)`: an Artifact Registry repository `fugaro-<readable slug>-<12 hex>`, at most 63 characters, that holds only that repository's derived images (§6.1).
  - **The check job,** `gcp.CheckJobName(slug)`: the Cloud Run job that runs the daily image check (§7.2). Its prefix is `fugarochk-`, not `fugaro-`, so the `fugaro-` job listings that `ls` and the `max_parallel` check make never count it. It carries `fugaro_role=check` in place of `fugaro_workflow`.
- **Ownership marks.** Jobs carry the labels `fugaro=managed`, `fugaro_repo` and `fugaro_workflow`. Secrets carry `fugaro=managed`, `fugaro_repo` and `fugaro_secret` (the logical name). A repository's image registry carries `fugaro=managed` and `fugaro_repo`, and the runs bucket, the base registry and the legacy registry carry `fugaro=managed`. Service accounts can't carry labels, so one is recognized by its display name: `Fugaro job <slug> <workflow>` for a job's account, `Fugaro build <slug>` for a build account, and `Fugaro scheduler` for the scheduler's. The M4 form of a job account's name, `Fugaro M4 job <slug> <workflow>`, is accepted too, and kept as it is when `fugaro init` adopts the account, so the M4 bootstrap still recognizes it during a rollback. `fugaro_repo` is the slug with every character outside `[a-z0-9_-]` replaced by `_`, never truncated, since truncation would cut off the hash.
- **These marks are the control, and Terraform sets them too.** A resource without them is refused, not adopted: `fugaro secrets set` won't add a version to a secret whose labels don't match, the bootstrap won't reuse, grant or delete a job, account or secret that isn't marked as this repository's and workflow's, and `fugaro init` checks the marks before it imports, grants on or allows the deletion of anything (§8.2).
- **Terraform receives names; it never derives them.** Every job, account, secret, image and registry name, every label value, the bucket condition and its title, and the job env are computed in Go (`internal/infra`) and passed in `terraform.tfvars.json`. So are the installation's singletons: the scheduler account, the custom role IDs, the base registry, and the log bucket, sink, exclusion and view. The HCL only checks shapes. A golden test holds the sandbox fixture's names to what M4's `fugaro gcp job-spec` printed, byte for byte, apart from the image path, which moved to the repository's own registry.
- **One provider per owner/name in a project.** The local config's `repos` is keyed by `owner/name`, so one installation can't hold a GitHub `acme/app` and a Bitbucket `acme/app` side by side, even though their slugs differ.

### 3.3 State: GCS only

There is no database and no server. Everything a run produces lives in one bucket:

```
gs://<runs-bucket>/
  runs/<repo-slug>/<run-id>/
    task.json            # task spec (written by CLI, create-if-absent)
    launching            # the launch claim (create-if-absent; never deleted after a launch, §4.7)
    launch.json          # the started execution's name (written once, create-if-absent, §4.7)
    cancel               # cancel marker (written by fugaro cancel, §4.5)
    result.json          # run record (written by runner, updated per stage, always finalized)
    verify/<n>.json      # one record per `fugaro verify` invocation
    transcripts/<stage>-<n>.jsonl   # claude stream-json output per stage
    session/             # Claude Code session files, for follow-up resume
    report.md            # human-readable report, also posted to the PR
  cache/<repo-slug>/<workflow>/<key-hash>.tar.zst   # content-addressed dependency caches
  locks/<repo-slug>/<branch-hash>                   # one-run-per-branch lock
  builds/<repo-slug>/<workflow>/
    image.json           # the build record: what the current :latest was built from (§7.2)
    check.json           # the daily check's last decision and its last rebuild
```

- **Lock key:** `<branch-hash>` is the first 16 hex characters (8 bytes) of SHA-256 of the branch name.
- **Lifecycle rules** (set by the M4 bootstrap with these ages fixed in the script, and by the installation's Terraform since M5, where the ages are the variable `bucket_lifecycle`): delete `runs/` objects after 90 days, and `cache/` objects not read in 30 days. "Not read" is the object's GCS custom time, which the runner sets when it writes an archive and again on every restore, and the rule is `daysSinceCustomTime: 30`. An object without a custom time never matches that rule, so a second one deletes any `cache/` object 180 days after creation as a backstop. **No rule touches `builds/`**: a build record must outlive any age, since a missing record makes the daily check rebuild.
- **Run ID** format: `YYYYMMDD-HHMMSS-<4 hex>`, in UTC.
- **Lookup:** the CLI accepts either `<repo-slug>/<run-id>` or a bare `<run-id>`. For a bare ID it checks each `runs/<repo-slug>/` prefix, of which there are few.

### 3.4 Backend seam

The CLI talks to the cloud only through:

```go
type Backend interface {
    Launch(ctx context.Context, spec LaunchSpec) (ExecutionRef, error)          // LaunchSpec{Repo RepoRef, Workflow, RunID, Timeout}
    Execution(ctx context.Context, name string) (Execution, error)              // one execution by its full name
    List(ctx context.Context, f ListFilter) ([]Execution, error)                // ListFilter{Jobs, Since, ActiveOnly}
    Logs(ctx context.Context, q LogQuery, fn func(LogEntry) error) error        // LogQuery{Execution, Since, Follow, Poll}
    Cancel(ctx context.Context, name string) error
}
```

The interface lives in `internal/backend`. `ErrNotFound` means the execution or job does not exist. `ErrRejected` means the platform definitively refused a request (a 4xx other than 408, 429 and 499, the last being gRPC's CANCELLED over HTTP), so nothing was created; any other error from `Launch` is ambiguous, and callers must assume the execution may exist (§4.7).

- **Resource limits and prices are not part of the seam.** They live in the backend's own package: `internal/backend/gcp` holds `CheckResources` (Cloud Run's CPU and memory rules, §5.1) and `ListPrices` (its price table, §10.1). A Batch backend would bring its own of each.
- **Execution identity.** An execution is named everywhere it is stored (`launch.json`, `result.json`, the lock) by its full resource name, `projects/<project>/locations/<region>/jobs/<job>/executions/<name>`. On Cloud Run the runner builds it from `CLOUD_RUN_EXECUTION` (the short name) and `CLOUD_RUN_JOB`, which Cloud Run sets, and `FUGARO_PROJECT` and `FUGARO_REGION`, which the job sets. The API may spell the project as an ID or a number, so names are never compared as strings: everything compares them by (region, job, short name), through `backend.ParseExecution(…).Key()` or `backend.SameExecution`.
- **Per-run timeout.** `LaunchSpec.Timeout`, when it is not zero, is sent as the `jobs.run` override `timeout`: the run's `timeouts.total` plus the task timeout's 2-minute slack (§4.5). `Launch` derives it from the stored task spec, so `--retry` and a repeated `--run-id` launch with the same timeout.
- **Launch IAM.** `Launch` calls `jobs.run` with per-execution overrides (`FUGARO_RUN`, and the timeout), which needs the `run.jobs.runWithOverrides` permission. The installation's Terraform grants it through two custom roles, so no launcher needs a broad role:
  - **`fugaroLauncher`,** on the project: `run.jobs.get`, `run.jobs.list`, `run.executions.get`, `run.executions.list`, `run.executions.cancel` and `run.operations.get`, which is what `run`, `ls`, `logs`, `diagnose` and `cancel` need, plus `secretmanager.secrets.list` and `secretmanager.versions.list` for `fugaro secrets ls` (metadata only: reading a value needs `secretAccessor`, which neither launchers nor operators hold).
  - **`fugaroJobRunner`** (`run.jobs.run` and `run.jobs.runWithOverrides`), granted **on each workflow job** and not on the project, so a launcher can start Fugaro's jobs and nothing else.
  - A launcher also gets `roles/storage.objectAdmin` on the runs bucket and read access to the Fugaro log view (§6.1).

  Both member lists (`launchers` and `operators`, §6.1) are empty by default: an install where the owner is the only user needs neither.
- **Storage** goes through `gocloud.dev/blob`, which covers GCS and S3 with one API. `blobx.Bucket` wraps it and is the one place with GCS-specific precondition code: create-if-absent that returns the new generation, generation-matched replace and delete, and the custom-time update. On GCS these are atomic. On `file://` and `mem://` buckets (local runs and tests) replace and delete fall back to comparing the object's contents first, which is not atomic, and `fileblob`'s create-if-absent is not atomic either. Those buckets are for a single writer.
- **What the runner touches in the cloud:** it uses only the blob bucket. The platform injects secrets as env vars or files, logs go to stdout, and model auth is configured through env.
- **Only GCP is implemented** (`internal/backend/gcp`). An AWS backend (ECS/Batch, S3, CloudWatch, Secrets Manager, Bedrock) would be a sibling package plus `deploy/terraform/aws/`.

## 4. Runner lifecycle

`fugaro exec` runs a fixed stage machine. It records the current stage in `result.json` at each transition, so a crash at any point leaves an accurate "stage reached".

```
bootstrap ─► implement ─► review(1) ─► [fix ─► review(2)] … ─► finalize ─► writeback
```

### 4.1 Stages

**bootstrap**

1. **Read the task.** Read `FUGARO_RUN` and load `task.json`. Then note which image the run started from: the commit the baked checkout is at (its `HEAD`, read before anything is fetched, so it is what the image really holds) and the time the image was built, which the derived template wrote into `/etc/fugaro/image.json`. They go into the record's `image` block (§4.6). This is informational and never fatal: a missing file (a local run, or an image from before M5) leaves the block out, and an unreadable one is a warning.
2. **Write the first record, create-if-absent.** On Cloud Run the runner creates `result.json` (`status: running`, `stage: bootstrap`, its own `execution`) only if it doesn't exist. If it exists and names another execution, this is a duplicate execution of the run: it exits here, having written nothing, and never touches the owner's `result.json` or lock. If it names this same execution (compared with `backend.SameExecution`, so a project number and a project ID match), the execution restarted and carries on. A local run, with no execution, just writes the record.
3. **Sync code.** Open the checkout (or clone it), `git fetch` the ref, and force-check-out `fugaro/<run-id>` at it, removing untracked files. A follow-up run would check out the existing branch (§4.4); M4's runner refuses follow-up runs.
4. **Load `fugaro.yaml`** from the checked-out tree, select the workflow and apply the task's overrides. The record's `deadline` is set now.
5. **Acquire the branch lock.** It comes after the config, because its expiry needs `timeouts.total`, and before anything changes remote state (the clone and checkout are local, and the provider has only been asked for credentials). Create `locks/<repo-slug>/<branch-hash>` with create-if-absent (`ifGenerationMatch=0`). The body holds the run ID, the execution, and an expiry of `started_at + timeouts.total + 3m`: the Cloud Run task timeout (`total + 2m`) plus a minute, so a live run never loses its lock. An existing lock whose expiry has passed, or that can't be parsed, is taken over with a generation-matched overwrite. A live lock fails the run with `infra_error: branch busy`.
   - A lock held by the same run ID from another execution is also a duplicate. This check is defensive only: step 2 already stops a duplicate, and this one fires only if the owner's `result.json` vanished. The duplicate then has written just its own first record; it rewrites that record, generation-matched, to name the lock's holder and expiry, and stops.
6. **Restore caches.** For each cache entry, compute its key from the checked-out ref (§7.2) and extract the matching archive if one exists. Restore is bounded by `min(10m, timeouts.total / 6)`, and nothing in it fails the run: a missing archive is a miss, and a failed or refused one is a warning.
7. **Fetch the base branch.**
8. **Get a git token for the agent** (§6.2) and configure the git credential helper and `gh` auth with it.

**implement.** Runs `claude -p` in a new session S1 (`--session-id`). The prompt is:

- the task text, and for follow-up runs the PR comments
- Fugaro's appended system prompt, which explains the run contract: work on this branch, run build and test only through `fugaro verify`, commit your work, write the PR title and body to `$FUGARO_STATE_DIR/pr.md`, and note that a PR is only marked ready if the final commit has a passing recorded test run
- the repo's optional `agent.instructions` file

The state directory (`FUGARO_STATE_DIR`) lives outside the checkout, so files Fugaro and the agent write there never dirty the working tree.

**review(n).** Runs `claude -p` in a **fresh session**, using the configured review skill or prompt against the branch diff versus base. It must end with a structured verdict:

```json
{ "verdict": "ship" | "changes", "findings": [{ "severity": "...", "file": "...", "summary": "..." }] }
```

The runner passes the verdict schema with `--json-schema` and reads the `structured_output` field of Claude Code's result event. If that field is missing, it falls back to the last fenced JSON block in the result text. An unparseable verdict counts as `changes` with one finding: "review produced no parseable verdict".

**fix.** Resumes S1 (`--resume`) with the findings from the last review. It then goes back to `review(n+1)`, until the verdict is `ship` or `agent.review_rounds` is used up.

**finalize.** The runner, not the agent:

1. Commits any uncommitted changes as `fugaro: uncommitted work at finalize`.
2. If the branch has no commits ahead of base, adds an empty commit whose message is the failure summary, so a PR can exist.
3. Pushes the branch.
4. **Finds or creates the PR** for the branch. The title and body come from `$FUGARO_STATE_DIR/pr.md`, or are generated from the task if that file is missing.
5. Sets ready or draft (§4.2).
6. Posts `report.md` as a PR comment.

**writeback.** The runner records `stage: writeback`, then, for each cache entry, recomputes its key from the final tree (when the agent changed a lockfile, the new dependencies belong under the new key) and, if that archive does not exist yet, archives the paths with zstd and uploads it with create-if-absent. Because the archives are content-addressed and immutable, parallel runs never contend and no locking is needed. A cancelled run skips the cache write-back. Writeback's uploads run until `started_at + timeouts.total + 60s` (at least 20 seconds, however late they start). That leaves the rest of the task timeout's 2-minute slack for what follows, each on a bounded context of its own: the branch lock's release (up to 15 seconds), the final `result.json` (up to 30 seconds), and 15 seconds for the container's startup, since `started_at` comes after the task's clock starts. Nothing in writeback fails the run.

**Exit status.** `fugaro exec` exits 0 when the run reached an outcome it recorded: `succeeded`, `failed`, or `cancelled` after bootstrap. It exits 2 when the run ended in `infra_error` (a failure before the branch existed), was cancelled during bootstrap, turned out to be a duplicate execution of a run another execution owns (or couldn't tell whether it owns it, §4.7), or couldn't write its final record. Cloud Run shows those executions as failed.

**Caches and the base image.** The base image is part of every cache key, read from `FUGARO_BASE_IMAGE`, which the derived-image template sets from its `FUGARO_BASE` build argument (a digest on Cloud Build). A repository Dockerfile doesn't set it unless it does so itself, so its caches are keyed on `unpinned` instead of the base, and the runner warns that they may be stale after a base change.

### 4.2 PR outcome rule

A PR is **ready** if and only if both of these hold:

1. The run record contains a `fugaro verify test` whose `head_sha` equals the final pushed HEAD, with `clean_tree: true` and `passed: true`. A pass can include tests marked flaky, meaning they failed and then passed on `--rerun-failed`.
2. The last review verdict was `ship`.

Otherwise the PR is a **draft**. Its report states the reason, for example "no verified test run on final commit", "review round 2 still has 3 findings", or "stage `fix` timed out".

The engine never re-runs build or test itself.

### 4.3 `fugaro verify`

`fugaro verify build|test [--rerun-failed]` is on `PATH` inside the container. The agent calls it the way it would call `./gradlew test`. The wrapper:

- runs the configured command (`commands.build`, `commands.test`, or `commands.rerun_failed.command` followed by `commands.rerun_failed.each` once per failed test ID, with `{id}` replaced by the shell-quoted ID), and streams its output to the agent unchanged
- parses the configured `reports` globs (JUnit XML; Jest/Vitest JUnit output) into passed, failed, and skipped counts plus the failed test IDs
- with `--rerun-failed`, re-runs only the previously failed tests, and marks as `flaky` those that now pass. It refuses unless the previous test run was on the current commit with a clean tree, so a flaky pass can't vouch for code it didn't test.
- counts only report files modified after the command started, so stale reports from earlier runs are ignored
- writes `verify/<n>.json` (`kind`, `head_sha`, `clean_tree`, `exit_code`, `passed`, counts, `failed[]`, `flaky[]`, `duration`)
- runs its command in its own process group, and kills the whole group on completion or timeout, which also kills leaked Gradle daemons

### 4.4 Follow-up runs

`fugaro run --pr <n> ["extra instructions"]` works like this:

1. **Resolve the PR.** The CLI resolves the PR to its head branch. The branch must match `fugaro/<run-id>`, which also identifies the previous run. The task spec gets `branch`, `pr`, and `previous_run`.
2. **Load context.** The runner checks out the branch. It fetches the PR's unresolved review comments and general comments through the provider, and adds them to the implement prompt. If no task text is given, the default is "Address the unresolved review comments on this PR."
3. **Resume the session (best effort).** If `runs/<repo>/<previous_run>/session/` exists, the runner restores it into Claude Code's session directory. Implement then *resumes* the original session instead of starting S1 fresh. The image's workdir path is fixed, so session paths line up. If the session is missing or can't be restored, it starts a fresh session and says so in the report.
4. **Update the existing PR.** Finalize updates the existing PR rather than creating one, re-evaluates draft or ready, and posts a new report comment.

The branch lock prevents concurrent runs on the same PR.

### 4.5 Timeouts and failure handling

**Timeouts**

- **Stage timeouts** (`timeouts.stage`, and `timeouts.verify` for the wrapper). On expiry, the process group gets SIGTERM, then SIGKILL after 10 seconds.
- **Overall budget.** The runner tracks elapsed time against `timeouts.total` and keeps a reserve (`timeouts.finalize_reserve`, default the lesser of 5 minutes and a fifth of `timeouts.total`). When the reserve is reached, it abandons the current stage and goes to finalize. This does not rely on Cloud Run's SIGTERM grace period. Finalize itself runs within the reserve, with one bounded exception: if opening the PR gives up with a PR already created, the runner posts a "not ready" comment on a context of its own, which may run up to 30 seconds past the reserve.
- **Task timeout.** Terraform (the M4 bootstrap before it) sets the Cloud Run task timeout to `timeouts.total + 2m`.
- **Per-run override.** `fugaro run --total-timeout 45m` writes `overrides.total_timeout` into `task.json`, and the launcher sends `total + 2m` as the execution's task timeout (§3.4), so the runner's clock and Cloud Run's agree. The CLI checks it: a Go duration, longer than the checkout's `finalize_reserve` when the checkout is the run's repository, and at most 24 hours (`OverrideCap`); the runner checks again at bootstrap. `--retry` keeps it, since the stored task is launched as it is, and it can't be given again there.
- **Agent cost cap.** `agent.max_budget_usd` limits each stage's spend, through `claude --max-budget-usd`.

**Failure paths**

| Failure | Result |
|---|---|
| Failure after the branch exists (any stage) | Push, then a **draft PR** with the stage reached, the reason, and the log tail. `result.status = failed`. |
| Failure before the branch exists (auth, lock, fetch, config) | No PR is possible. `result.status = infra_error`, with `stage` and `reason` set. The write happens in a deferred finalizer that runs on every exit path, including panics. |
| Cancelled (`fugaro cancel`) | The CLI writes a `cancel` marker to the run prefix. The runner polls for it every 30 seconds. When it sees the marker, it kills the current stage's process group and goes to finalize, producing a draft PR marked cancelled. If the execution is still in a stage after a grace period, the CLI cancels it through Cloud Run, and `ls` shows `cancelled` based on the execution state. See below. |

**Cancel's grace is measured against the recorded stage.**

- **The grace** is `--grace` (default 3 minutes), but never less than a floor: the run's finalize reserve plus 40 seconds for the runner to notice the marker (one 30-second cancel poll and the stage's 10-second SIGTERM-to-SIGKILL grace), so finalize still gets its whole reserve. The reserve is `finalize_reserve_s` from `result.json` (§4.6), which the runner records at bootstrap; before that, the workflow's `timeouts.finalize_reserve` from the checkout's `fugaro.yaml` when it is the run's repository; else 5 minutes. A shorter `--grace` is raised to the floor, with a note.
- **"Finalized"** means the PR exists. The CLI counts a run as finalized as soon as `result.json` has a final status, or its stage is `writeback`, which runs after finalize.
- **A run in `finalize` or `writeback` is never hard-cancelled.** In `writeback` it is already finalized. In `finalize` the CLI waits up to 10 minutes past the grace, and if the run is still finalizing then, it exits 1 and leaves it to the task timeout.
- **`--now`** cancels the execution without waiting for the draft PR, but still not during `finalize`.
- **If the cancel marker can't be written**, the CLI doesn't touch the execution unless `--now` was given, since a hard cancel skips finalize and its draft PR.
- **What `cancel --json` reports** in `status`: `finalized` (with the PR URL when `result.json` names one), `cancelled` (the execution was cancelled through the backend; the message says the run may not have a draft PR), `ended-unfinalized` (the execution ended, or the backend forgot it, without a final record; never reported as finalized), `already-finished` (the execution had ended before the call; no marker is written), `not-launched` (the marker is written, so `fugaro run --retry` refuses the run; also reported when a launch was in flight and its launcher, seeing the marker, refused and released its claim), and `launching` (a launch is in flight, or its execution isn't listed yet; the marker is written, and the launcher's re-check after its claim, or the runner's check right after its first record, stops it).

### 4.6 Run record (`result.json`)

```json
{
  "version": 1,
  "run_id": "20260926-221530-a1b2",
  "repo": "acme/server",
  "workflow": "server",
  "execution": "projects/<project>/locations/<region>/jobs/<job>/executions/<name>",
  "status": "running | succeeded | failed | infra_error | cancelled",
  "stage": "bootstrap | implement | review | fix | finalize | writeback",
  "outcome": "ready | draft | none",
  "reason": "string, empty on success",
  "branch": "fugaro/20260926-221530-a1b2",
  "head_sha": "…",
  "pr": { "number": 123, "url": "…" },
  "reviews": [{ "round": 1, "verdict": "changes", "findings": 3 }],
  "verify": [{ "n": 1, "kind": "test", "head_sha": "…", "passed": true, "flaky": ["…"] }],
  "cost_usd": 4.12,
  "cost": { "model_usd": 4.12, "compute_usd": 0.38, "compute_estimated": true, "total_usd": 4.50, "estimate": true, "model_basis": "api-list" },
  "stages": [{ "name": "implement", "started_at": "…", "duration_s": 812 }],
  "started_at": "…",
  "deadline": "…",
  "finished_at": "…",
  "finalize_reserve_s": 300,
  "image": { "built_at": "2026-09-29T04:31:00Z", "baked_commit": "…" }
}
```

`succeeded` means the PR is ready. `failed` means a draft PR exists. The schema is `schemas/result.schema.json`.

- **`execution`** is the canonical full name of the execution that owns the run (§3.4), empty for local runs. Every view follows it over `launch.json`'s, because after a double launch `launch.json` may name the duplicate.
- **`deadline`** is the branch lock's expiry, `started_at + timeouts.total + 3m` (§4.1), set once the config is loaded. A `running` record whose execution the backend no longer knows is shown as `infra_error` once its deadline has passed, or at once if it has none.
- **`finalize_reserve_s`** is the workflow's `timeouts.finalize_reserve` at the task's ref, overrides applied, in seconds. The runner records it once bootstrap has read `fugaro.yaml`, and it is absent before that or when bootstrap failed first. `fugaro cancel` reads it for its grace floor (§4.5), since the ref the run uses may differ from the local checkout.
- **`image`** says which image the run started from: `baked_commit` is the commit the image's checkout was at when the run began, and `built_at` is when the image was built (absent for a local build, which has no build time). It is written at bootstrap, before the checkout is synced, and is never fatal: when the information is missing the block is left out, and when it is unreadable the runner logs a warning and carries on. `fugaro ls --json` turns it into `image_age_s`, the image's age when the run started (§9.1).
- **`cost`** is the breakdown of §10.1. `cost_usd` keeps the model figure for compatibility.
  - `compute_estimated` is the only signal that compute was estimated. When it is false (a local run, or unknown prices or resources), `compute_usd` is 0 and means "not estimated", not free.
  - `total_usd` counts only billed dollars, rounded to the cent. With `model_basis: subscription`, the model figure is notional, and `total_usd` leaves it out.
  - `estimate` is always true: storage, logging and image builds are left out.

### 4.7 Recovery after a local crash or restart

Nothing about a run lives only on the machine that launched it. A run is a cloud execution. All of its state is in the runs bucket (`task.json`, `result.json`, transcripts, verify records, the report) plus the execution's own state, and every run that gets past bootstrap leaves a PR. A laptop that crashes, reboots, or loses its Claude Code session changes nothing in the cloud. Recovery means rebuilding the local view from cloud state, never from local memory.

- **Launching is recorded, and can be repeated safely.**
  - `fugaro run` writes `task.json` first, create-if-absent. It then starts the execution and records the execution name in `runs/<repo>/<run-id>/launch.json`, also create-if-absent.
  - A run that has `task.json` but no `launch.json` never launched, for example because the CLI crashed in between. `fugaro ls` shows it as `unlaunched`, or `launching` while a fresh launch claim is held.
  - `fugaro run --retry <run-id>` launches an unlaunched run without creating a new one. It takes no task flags or text: the stored `task.json` is launched as it is.
  - If the CLI died after the execution started but before `launch.json`, `--retry` (like any later launch of the run) backfills `launch.json` from `result.json`'s `execution`, which the runner writes at bootstrap, and reports the run as already launched instead of starting another.
  - A run with a cancel marker is never launched: `--retry` refuses a cancelled run.
- **Launching is idempotent.**
  - `fugaro run --run-id <id>` accepts a run ID chosen by the caller. A second `run` with an ID that has already launched is a no-op that prints the existing run (`status: already-launched`).
  - A second `run --run-id` with a different task is an error (exit 1): `task.json` is never overwritten.
  - The local agent should choose the ID itself, so a retried launch after a crash can't start the same task twice.
- **The launch protocol.** Several CLIs may launch the same run ID at once, or one may crash between `jobs.run` and `launch.json`. There must still be at most one execution:
  - **The claim.** Before launching, the CLI creates `runs/<repo>/<run-id>/launching` (holder and time), create-if-absent. The claim is never deleted after a launch, so a later caller always finds it.
  - **Re-read whenever the claim is held or just won.** A caller that finds the claim held waits up to 30 seconds for the holder's `launch.json` and reports it as already launched; if none appears it exits 1, "still in flight". A caller that has just won the claim re-reads `launch.json` and `result.json` before launching, since an earlier holder may have launched just before its claim went stale.
  - **Stale claims.** A claim older than 10 minutes is stale, its holder presumably dead. It is read once, content and generation together, and taken over with an overwrite matched to that generation, never delete-then-create, so two takers can't both win. Everything done while holding the claim is bounded to 5 minutes, and the launch call itself to 2, well inside that window. Staleness is judged by comparing the reader's clock with the holder's timestamp in the claim, so the CLIs' clocks must agree to within 5 minutes (the TTL less the hold bound). A larger skew can let a live claim be taken over; the resulting double launch is contained by the runner's duplicate-execution check, which leaves the second execution writing nothing.
  - **Release only after a failed launch.** Only a definitive refusal (`backend.ErrRejected`) releases the caller's own claim, generation-matched, so a corrected retry can go at once. After an ambiguous error (a timeout, a 5xx, a dropped connection) the execution may exist, so the claim stays until it goes stale; by then the runner's `result.json` says whether it started, and `--retry` reads it.
  - **`file://` buckets are single-user.** `fileblob`'s create-if-absent is not atomic (§3.4), so this protocol holds only on GCS.
- **Runs can be found again without remembering their IDs.**
  - `fugaro ls --mine --since <duration>` filters on the task spec's `requested_by`.
  - `fugaro run --batch <name>` records a batch label in the task spec, and `fugaro ls --batch <name>` recovers a group of runs launched together as one unit.
- **Skills reconcile first.** `fugaro:status` and `fugaro:diagnose` start by listing recent runs (`ls --mine --since …` or `--batch …`) and reporting what finished, what's still running, and what failed. After a restart, the local agent picks up from the cloud state, not from its conversation.

## 5. Configuration

### 5.1 `fugaro.yaml` (repo root)

The runner reads it from the target ref, so config changes ship with the code. `fugaro init --repo` reads the same file to generate that repo's infrastructure, which keeps one source of truth.

```yaml
version: 1

git:
  provider: github            # github | bitbucket
  base_branch: main
  pr:
    labels: [fugaro]
    reviewers: []

agent:
  auth: vertex                # vertex | api-key | oauth
  model: claude-opus-5-5      # optional; Claude Code default otherwise
  review_rounds: 2
  max_budget_usd: 25          # per stage, passed to claude --max-budget-usd
  instructions: .fugaro/instructions.md   # optional, appended system prompt
  review: /review             # skill name or path to a prompt file

workflows:
  server:
    base: server-jvm          # server-jvm | web-node
    image:                    # optional; rendered into the engine's derived-image template (§7.2)
      jdk: "21"               # toolchain version override (jdk for server-jvm, node for web-node)
      apt: [libvips-dev]      # extra system packages
      setup: ["./gradlew --version"]   # extra RUN steps after the dependency warm-up, run as fugaro (sudo works during the build only)
    # dockerfile: .fugaro/server.Dockerfile   # escape hatch; replaces the template (mutually exclusive with image)
    commands:
      build: ./gradlew assemble
      test: ./gradlew test
      rerun_failed:           # optional; enables flaky proof
        command: ./gradlew test
        each: "--tests {id}"  # appended once per failed test ID
      reports: ["**/build/test-results/**/*.xml"]
    cache:                    # optional; per-base defaults below
      - key: [gradle/libs.versions.toml, gradle/wrapper/gradle-wrapper.properties]
        paths: [~/.gradle/caches, ~/.gradle/wrapper]
    secrets:                  # logical names; infra maps them to Secret Manager
      - { name: artifactory-token, env: ARTIFACTORY_TOKEN }
    resources: { cpu: 8, memory: 32Gi }
    timeouts: { total: 90m, stage: 40m, verify: 30m, finalize_reserve: 5m }
    rebuild:                  # optional; when the daily image check rebuilds this workflow's image (§7.2)
      check: daily            # daily | off
      max_age: 14d            # rebuild an image older than this
      lockfiles: true         # rebuild when a cache key file changed on the base branch
      base: true              # rebuild when the base image's digest moved
      paths: ["packages/**"]  # rebuild when a change under one of these globs reached the base branch
```

**Per-base defaults**

| Base | cache | reports | resources |
|---|---|---|---|
| `server-jvm` | Gradle caches and wrapper, keyed by `gradle/*.toml`, `**/*.gradle*`, and the wrapper properties | `**/build/test-results/**/*.xml` | 8 vCPU, 32Gi |
| `web-node` | pnpm store, Yarn cache (Berry or classic) or npm cache, detected from `packageManager` and the lockfile and keyed by the lockfile | `**/junit*.xml` | 4 vCPU, 8Gi |

**The `rebuild:` block** says when the daily image check (§7.2) rebuilds a workflow's image. Every field is optional:

| Field | Default | Meaning |
|---|---|---|
| `check` | `daily` | `daily` puts the workflow's repository on the daily check. `off` leaves the image to `fugaro image build`, and a repository whose workflows are all `off` gets no check job and no schedule (for a sandbox, say). Turning it off in a repository that already has them deletes a protected job, which takes a `--allow-job-delete` apply first ([gcp-setup.md](../gcp-setup.md)). There is no `weekly`: a daily check costs next to nothing, and `max_age` says "at least every so often". |
| `max_age` | `14d` | Rebuild an image older than this. It is `0` (the age trigger off) or between `1h` and `90d`, written as a Go duration or with whole days (`14d`, `1d12h`, `0d`). What follows the days is unsigned: `1d-5h` is refused, not read as 19 hours. Every duration in `fugaro.yaml` (`timeouts` too) takes days the same way. The default is 14 days until the base images are published (M7), because until then `base_image` is a tag that doesn't move (§7.2), so this is what bounds how long a security fix in the base waits; it goes back to 7 days then. |
| `lockfiles` | `true` | Rebuild when a file of the workflow's cache key (§7.2), including the per-base defaults, changed on the base branch since the build. |
| `base` | `true` | Rebuild when the base image's digest, or the base image itself, changed. |
| `paths` | none | Globs, relative to the repository (`doublestar` syntax, as the cache key files use). Rebuild when a change under one of them reached the base branch since the build. It is for a repository that bakes something other than dependencies into its image, such as its own built packages. |

A change to `image:`, `dockerfile:` (or the file it names), the `base` name or `image.setup` **always** rebuilds and can't be turned off, because it makes the image wrong, not just stale (§7.2). `fugaro validate` reports a problem at `workflows.<name>.rebuild.<field>`: `check` must be `daily` or `off`; `max_age` must be 0 or within 1 hour to 90 days; each `paths[i]` must be non-empty, relative (not starting with `/`), free of a `..` component, and a valid glob.

**Skipping install build scripts (`web-node`).** `image.skip_build_scripts: true` (default `false`) makes the dependency warm-up (§7.2) install without running package lifecycle or build scripts: `yarn install --immutable --mode=skip-build` for Yarn 2 and later, and `--ignore-scripts` added to the Yarn 1, npm and pnpm installs. It is for monorepos whose install would otherwise start dozens of build scripts at once, such as workspaces with `postinstall: yarn build`. Yarn runs them through its own task pool, which ignores the container's CPU and memory limits, so on a build machine the install can oversubscribe it and never finish. Since nothing is built during the warm-up, the workflow's `build` command must build whatever the tests need, for example serially. Leave it off when a dependency needs its install script, such as a native module that compiles or downloads a binary on install. `fugaro validate` accepts it only on `web-node`.

**What stays out of `fugaro.yaml`**

- Cloud resource paths, project IDs, and secret resource names. `secrets` lists logical names; the Terraform layer (`fugaro init`) binds each `name` to the Secret Manager secret `gcp.SecretID(slug, name)`.
- The git provider's long-lived credential.

**Reserved secret names.** The platform mounts four logical secrets of its own, so a workflow's `secrets` may not use their names:

| Logical name | Variable |
|---|---|
| `bitbucket-token` | `FUGARO_BITBUCKET_TOKEN` |
| `github-app-key` | `FUGARO_GITHUB_APP_PRIVATE_KEY` |
| `claude-oauth-token` | `CLAUDE_CODE_OAUTH_TOKEN` |
| `anthropic-api-key` | `ANTHROPIC_API_KEY` |

**Reserved secret variables.** A workflow secret's `env` is mounted into the runner's own environment on the job and into the image build step, so it may not be a variable Fugaro sets or one that changes how the runner, git, a shell, the build, a language runtime or the Google clients behave. `fugaro validate` refuses, ignoring case, these families (`config.ReservedEnvPrefixes`): `FUGARO_`, `ANTHROPIC_`, `CLAUDE_CODE_`, `GIT_`, `LD_`, `DYLD_`, `PYTHON`, `BASH`, `LC_`, `DOCKER_`, `BUILDKIT_`, `CLOUDSDK_`, `CLOUD_RUN_`, `VERTEX_REGION_`, `GOOGLE_`, `GCE_`, `GRPC_` and `STORAGE_EMULATOR_`. It also refuses these single variables (`config.ReservedEnvNames`):

- the Go runtime: `GODEBUG` (with `http2debug` it makes Go log bearer tokens), `GOFLAGS`, `GOTRACEBACK`, `GOMAXPROCS`, `GOMEMLIMIT`
- the proxies and CA bundles: `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY`, `ALL_PROXY`, `SSL_CERT_FILE`, `SSL_CERT_DIR`, `NODE_EXTRA_CA_CERTS`, `CURL_CA_BUNDLE`
- the process and the shell: `PATH`, `HOME`, `PWD`, `OLDPWD`, `SHELL`, `USER`, `LOGNAME`, `HOSTNAME`, `TMPDIR`, `IFS`, `LANG`, `TERM`, `TZ`, `ENV`, `CDPATH`, `GLOBIGNORE`, `PS4`, `SHELLOPTS`, `PROMPT_COMMAND`
- the language runtimes: `NODE_OPTIONS`, `NODE_PATH`, `PERL5LIB`, `PERL5OPT`, `RUBYOPT`, `RUBYLIB`, `JAVA_TOOL_OPTIONS`, `_JAVA_OPTIONS`, `JDK_JAVA_OPTIONS`
- the Google clients: `GOOGLE_APPLICATION_CREDENTIALS`, `GOOGLE_CLOUD_PROJECT`, `GOOGLE_SDK_GO_LOGGING_LEVEL`, `CLOUD_ML_REGION`, `GCE_METADATA_HOST`, `GCE_METADATA_IP` (the metadata server, which the token fetch uses)
- the image build step's own variables: `IMAGE`, `SECRET_ENVS`, `WORKFLOW`, `REPO_URL`, `BASE_BRANCH`

`schemas/fugaro.schema.json` mirrors both lists.

**Resources.** The core schema requires only that `resources.cpu` is a positive integer and `resources.memory` a quantity such as `512Mi` or `8Gi`. The compute backend checks its own limits (`gcp.CheckResources` for Cloud Run): 1, 2, 4, 6 or 8 CPUs; 512Mi to 32Gi; more than 4Gi needs at least 2 CPUs, more than 8Gi 4, more than 16Gi 6, and more than 24Gi 8; and 4 CPUs need at least 2Gi, 6 or 8 CPUs at least 4Gi (checked against Cloud Run's documentation 2026-09-27). `fugaro validate` reports both kinds of problem, each at its `workflows.<name>.resources.<field>` path.

**Validation.** `fugaro validate` checks the file against `schemas/fugaro.schema.json` and verifies that the declared commands and key files exist in the tree. When `dockerfile` is set, it also checks that the file exists, builds `FROM` a Fugaro base image, and does not replace `/work/repo`. Concretely, the Dockerfile's final stage, followed back through the stages it builds on, must start `FROM ${FUGARO_BASE}` (declared with `ARG FUGARO_BASE`) or `ghcr.io/dimipaun/fugaro-<base>`, and must write the checkout to `/work/repo`. It must not move `WORKDIR`, end as a user other than `fugaro`, replace `ENTRYPOINT`, or declare a `VOLUME` under `/work`. `fugaro image build --local` checks the rest when it smoke-tests the image (§7.2). `image` and `dockerfile` cannot both be set. Each `image.setup` step becomes one `RUN` instruction, so a step must be a single line with no `<<` and no trailing backslash, and must not start with `-` or `[` (which would read as a `RUN` flag or the exec form). `git.base_branch` must be a plain branch name (letters, digits, `.`, `_`, `-` and `/`, within git's ref-name rules, and not starting with `-`), because it reaches git, Docker build arguments and Cloud Build, and git itself accepts shell metacharacters in ref names.

### 5.2 Creating `fugaro.yaml`

The file is written by the **`fugaro:onboard` skill**, not by engine code. Working out the right config means reading the repo: what CI actually runs, which secrets the build needs, where test reports land, and whether the repo holds both a server and a web app. An agent does that well; file-pattern detectors in Go would not, and would be code to maintain for a weaker result. Fugaro already requires Claude Code, so the skill doesn't narrow who can use it.

1. **`fugaro:onboard`** starts from `fugaro config example`, an annotated template embedded in the binary. It fills the template in from:
   - the build files: `gradlew`/`settings.gradle*` → `server-jvm`; `package.json` plus a lockfile → `web-node`; both → two workflows
   - the CI config (`.github/workflows/*`, `bitbucket-pipelines.yml`), for the real build and test invocations, the secrets they need, and the report paths
   - `git remote` and the provider, for `git.provider` and `base_branch`

   It runs `fugaro validate --json` and fixes what comes back until the file passes. It then lists the logical secrets the user needs to store, as `fugaro secrets set <name> --repo <owner/name>` commands, which label each secret so Fugaro accepts it (§6.1).

   **Image setup is part of onboarding.** Working out what the image needs uses the same inputs: CI `apt-get install` lines, `setup-node`/`setup-java` versions, `.nvmrc`, `.tool-versions`, `packageManager`, and steps like `playwright install --with-deps`. The skill puts what it finds into `image:`. It writes a repo Dockerfile (`.fugaro/<workflow>.Dockerfile`, `FROM` the Fugaro base) and sets `dockerfile:` only when `image:` can't express the need. Then it runs `fugaro image build --local` and iterates until that passes.
2. **Without the skill,** a user runs `fugaro config example > fugaro.yaml` and edits it by hand, with `fugaro validate` as the check.
3. The user commits the file through a normal PR. Then `fugaro init --repo` provisions the repo's jobs and secret bindings from the committed file.

### 5.3 Task spec (`runs/<repo>/<run-id>/task.json`)

```json
{
  "version": 1,
  "run_id": "20260926-221530-a1b2",
  "repo": "acme/server",
  "ref": "main",
  "workflow": "server",
  "task": "markdown task text…",
  "branch": "fugaro/20260926-101010-9f3c",
  "pr": 123,
  "previous_run": "20260926-101010-9f3c",
  "overrides": { "review_rounds": 3 },
  "requested_by": "someone@example.com",
  "batch": "tuesday-cleanup"
}
```

- **Field rules:**
  - `workflow` is optional when the repo defines exactly one workflow.
  - `batch` is an optional label that groups runs launched together, so they can be found again after a restart (§4.7). It matches `^[a-z0-9][a-z0-9._-]{0,62}$`: 1 to 63 lower-case letters, digits, `.`, `_` or `-`, starting with a letter or digit.
  - `branch`, `pr`, and `previous_run` are set only for follow-up runs.
  - `overrides` accepts only `review_rounds`, `max_budget_usd`, `model`, and `total_timeout`.
- **Task text** comes from an argument, `--task-file <path>`, or `--task-file -` (stdin), which is how the local agent hands it off.
- **Schema:** `schemas/task.schema.json`.

### 5.4 Local CLI config (`~/.config/fugaro/config.yaml`)

This holds the installation settings plus the list of onboarded repos. It lives at `$FUGARO_CONFIG`, else `$XDG_CONFIG_HOME/fugaro/config.yaml`, else `~/.config/fugaro/config.yaml`, and every cloud command also takes `--config`. `fugaro init` writes it, and rewrites it from the installation's outputs each time it runs, showing the diff first and backing the old file up (§8.2; [gcp-setup.md](../gcp-setup.md)). M4's throwaway bootstrap, `deploy/bootstrap/gcp-m4.sh config` ([gcp-bootstrap.md](../gcp-bootstrap.md)), wrote the first ones, which still load. Every cloud command (`run`, `ls`, `logs`, `diagnose`, `cancel`, `secrets`, and `image build` without `--local`) accepts `--project` and `--region` to override it.

```yaml
version: 1                            # the only version
project: my-project                   # GCP project ID
region: us-central1                   # where the jobs run; also the price region (§10.1)
runs_bucket: fugaro-runs-my-project   # bucket name; the CLI and the jobs use gs://<runs_bucket>
bucket_url: ""                        # optional override of the bucket URL, such as file:///tmp/runs, for tests
registry: us-central1-docker.pkg.dev/my-project/fugaro   # LEGACY: M4's registry; only a rollback reads it
registry_host: us-central1-docker.pkg.dev/my-project       # where the per-repository and base registries are
base_image: ""                        # the base for image builds and the image check (in the base registry)
build:
  service_account: ""                 # DEPRECATED: accepted and ignored, with a warning; each repository has its own build account
  machine_type: E2_HIGHCPU_8          # default
  region: ""                          # where Cloud Build runs; default: region
terraform:                            # written by fugaro init
  state_bucket: fugaro-tfstate-my-project
  alert_email: ""                     # where failed image checks and rebuilds are reported
  launchers: []                       # IAM members (user:, group:, serviceAccount:, domain:) who launch and watch runs
  operators: []                       # the same, who also onboard repositories
scheduler_region: us-central1         # Cloud Scheduler's region for the daily checks (default: region, or the nearest one Scheduler offers)
log_view: projects/my-project/locations/global/buckets/fugaro/views/fugaro-runs   # where logs and diagnose read (§6.1)
compute_prices:                       # optional overrides of the list prices, by region (§10.1)
  us-central1: { vcpu_second_usd: 0.000014, gib_second_usd: 0.0000016 }
user: ""                              # requested_by for run and ls --mine; default: git config user.email
max_parallel: 20                      # default; run refuses a new launch at this many active executions
endpoints:                            # optional API root overrides, for fakes and emulators only
  run: ""
  logging: ""
  secret_manager: ""
  cloud_build: ""
  storage: ""
  iam: ""
  artifact_registry: ""
  resource_manager: ""
  cloud_scheduler: ""
  no_auth: false                      # send no credentials (fakes only)
repos:                                # onboarded repositories, keyed by owner/name
  acme/web:
    provider: bitbucket               # github | bitbucket; optional, but without it commands must run from the repo's checkout
    base_branch: main                 # run's default --ref
    workflows: [web]                  # run's default --workflow when there is exactly one
    github_app_id: ""                 # a GitHub repository's App ID (not a secret); set by fugaro init --repo --github-app-id
    vertex: false                     # set by fugaro init --repo when a workflow has agent.auth: vertex; fugaro init then enables Vertex AI
```

- The file is decoded strictly: an unknown field is an error.
- `project`, `region`, the bucket name (unless `bucket_url` is set), `max_parallel` (at least 1), each repository's `owner/name`, its `provider` and its workflow names are validated. `--project` and `--region` are validated the same way after they are applied, since both go into resource paths.
- Each `endpoints.*` URL must be `https`, or plain `http` only to `127.0.0.1`, `localhost` or `::1` (the fakes tests run), and must have a host and no userinfo: the operator's credentials are sent to it.
- `repos[].provider` is part of the repository's slug (§3.2). When it is unset, the checkout's `git.provider` decides, and a command run outside a checkout of the repository can't tell the slug and refuses. When both are set and disagree, the command refuses.
- **The M5 fields.**
  - `registry` is legacy: M4's single registry, kept for a rollback and read by nothing else. Derived images live in per-repository registries under `registry_host`, and base images in the installation's base registry (§6.1, §7.2). `registry_host` must be `<region>-docker.pkg.dev/<project>` of the config's own project.
  - `build.service_account` is deprecated. Every repository builds as its own build account (§6.1), so the field is accepted, ignored, and reported with a warning by the commands that print the config's warnings.
  - `terraform.state_bucket` (default `fugaro-tfstate-<project>`), `terraform.alert_email`, `terraform.launchers` and `terraform.operators` are what `fugaro init` keeps between runs. Members are `user:`, `group:`, `serviceAccount:` or `domain:` IAM members. `--launcher`, `--operator` and `--alert-email` override them for one run and are then stored. The budget is not stored: pass its flags again on every rerun, or the plan deletes it (the guard refuses that, and says which flags keep it).
  - `scheduler_region`: Cloud Scheduler isn't offered in every Cloud Run region, so the daily check's Scheduler job may live in another one (§7.2). `gcp.SchedulerRegion(region)` returns the region itself when Scheduler offers it and a fixed nearby one otherwise (`us-east5` gives `us-east4`); an unknown region needs `--scheduler-region`.
  - `log_view` is the Fugaro log view, which `fugaro logs` and `fugaro diagnose` read through. `fugaro init` writes it from the installation's output. With log isolation off it is absent and they read `_Default` as before.
  - `compute_prices` maps a region to `{vcpu_second_usd, gib_second_usd}`, each finite, greater than 0 and at most 0.001, for committed-use discounts and the like (§10.1).
  - `repos.<owner/name>.github_app_id` is a GitHub repository's App ID, 1 to 20 digits. It isn't a secret; it reaches the job as `FUGARO_GITHUB_APP_ID` and the image build as `_GITHUB_APP_ID`.
  - `repos.<owner/name>.vertex` is recorded by `fugaro init --repo` when any of the repository's workflows has `agent.auth: vertex`. `fugaro init` derives the installation's `enable_vertex` from it (§8.1), so the first Vertex repository needs one more `fugaro init`, and `init --repo` warns so.
  - `endpoints.cloud_scheduler` is the Cloud Scheduler API root, which `fugaro init --repo`'s discovery reads the check's Scheduler job through. With `no_auth` set, `fugaro init`'s discovery refuses to start while any endpoint it calls is unset, so a test can't reach Google through one left empty.

## 6. Security model

### 6.1 Trust boundary

**The trust boundary is the container, not the process.** The agent runs with permission prompts bypassed and shares the container with the runner. It can therefore use anything the job's service account can reach (through the metadata server) and anything mounted into the container. The design does not pretend otherwise; it scopes what the container can reach:

- **Service account.** Each job has its own service account (`gcp.ServiceAccountID(slug, workflow)`, §3.2). It can read only its own declared secrets. It can read and write objects under its own `runs/<repo-slug>/`, `cache/<repo-slug>/`, and `locks/<repo-slug>/` prefixes. With `auth: vertex` it also gets `roles/aiplatform.user`, on the project, and only then (Terraform grants it; the M4 bootstrap didn't). Nothing else. Its bucket condition names no `builds/` prefix, so a job account can't write a build record.
  - **The bucket binding** is `roles/storage.objectUser` on the runs bucket, with this IAM condition (from `fugaro gcp job-spec --field bucket-condition`):
    ```
    resource.name.startsWith("projects/_/buckets/<bucket>/objects/runs/<slug>/") ||
    resource.name.startsWith("projects/_/buckets/<bucket>/objects/cache/<slug>/") ||
    resource.name.startsWith("projects/_/buckets/<bucket>/objects/locks/<slug>/")
    ```
    The trailing slashes matter: without them, a slug would reach every slug it is a string prefix of. The condition names objects, so it also denies listing the bucket, which is checked against the bucket rather than an object. The runner never lists.
- **Each repository has its own build service account** (`gcp.BuildServiceAccountID(slug)`), and its own image registry (`gcp.RegistryRepoID(slug)`). `fugaro image build` and the daily check submit builds as that account, and the check job runs as it. Terraform gives it exactly this, and nothing at project level beyond the two roles named:
  - `secretmanager.secretAccessor`, on the repository's provider credential and workflow secrets only (§7.2), never on the project;
  - `artifactregistry.writer` on **the repository's own registry** only, so its token can write nobody else's images, and only `writer`: no `admin`, and so no `artifactregistry.tags.delete` (§7.2);
  - `artifactregistry.reader` on the base registry `fugaro-base` (below);
  - `logging.logWriter`, on the project;
  - the custom role `fugaroBuildSubmitter` (`cloudbuild.builds.create` and `cloudbuild.builds.get`), on the project, to submit builds and to read one;
  - `roles/iam.serviceAccountUser` on **itself only**, since a build submitted as an account needs `actAs` on it;
  - `roles/storage.objectUser` on the runs bucket, conditioned on `builds/<slug>/`, so it can write its repository's build record (§3.3) and nothing else in the bucket.

  This is what per-repository isolation means for builds: one repository's build token can't read another repository's secrets, and can't overwrite its images. **`fugaro-build`,** M4's single account for the whole installation, could do both, and is retired after migration (gcp-setup.md).
- **Base images live in their own registry, `fugaro-base`,** an installation-level registry that only operators (and owners) can write. Every build account can only read it. Otherwise a leaked build token could overwrite the base image that every repository's `credential` step and check job run while holding that repository's provider credential. The legacy `fugaro` registry, which holds M4's images, stays for a rollback, unwritten. A repository's derived images are in its own registry, and its job keeps running its M4 image until the new path has a `:latest`, so the switch never points a job at a missing image.
- **Secrets** are labelled `fugaro=managed`, `fugaro_repo=<repo label>` and `fugaro_secret=<logical name>` (§3.2). They are written only through `fugaro secrets set NAME`, which reads the value from stdin (a pipe, a redirect, or a hidden prompt at a terminal) and never from an argument, a flag or the environment.
  - `NAME` must be a reserved name (§5.1) or one some workflow of the checkout's `fugaro.yaml` declares, so a typo can't store an orphan, and a value typed in its place never becomes a secret ID. The messages refusing a `NAME` don't quote it.
  - An existing secret without the matching labels is refused, not given a new version.
  - One trailing newline is dropped. A value must be 4 bytes to 64 KiB. It must be on one line, except `github-app-key` (a PEM, redirected from a file), and a one-line value may not start or end with whitespace.
  - No command reads a secret value back. `fugaro secrets ls` shows IDs, logical names, labels and version counts, never values. The value is never printed, and any error that could echo it is redacted first.
- **Model credentials.** An API key or OAuth token is a per-repo secret, so it is visible to that repo's job only.
- **The git credential is scoped as narrowly as the provider allows**, because the agent can reach it:
  - **GitHub:** a GitHub App installed only on the repos Fugaro serves, with `contents:write`, `pull_requests:write`, `issues:read`, and `metadata:read`. A per-org App is the default; teams that want per-repo isolation can create one App per repo.
  - **Bitbucket Cloud:** one repository access token per repo, scoped to that repo by design.
- **Base branch protection is a documented prerequisite.** It is what actually prevents pushes to, or merges into, the base branch.
- **Egress is unrestricted in v1.** Prompt injection through repo content or dependencies could leak source code or the scoped token. The docs state this plainly. Restricting egress with a VPC and firewall is a later hardening option.
- **Secrets are never baked into images and never logged.** The runner redacts the values of all mounted secrets from its log output and from transcripts before uploading them. The job sets `FUGARO_SECRET_ENVS` to the comma-separated names of every secret variable it mounts: the platform's own, and the job's own workflow's secrets in the `fugaro.yaml` it was deployed from, and the runner registers their values with the redactor when it starts, before bootstrap. So even an early bootstrap failure is redacted, and so is a secret the task's ref no longer declares, whose value is in the environment all the same.
- **Log access is secret access, and log isolation enforces it.** Cloud Logging's audience is anyone with log-view access on the project, and the run log carries the agent's live output (§10). Redaction is best effort (below). In a shared project Fugaro can't take `roles/logging.viewer` away from anyone, so instead the installation's Terraform routes Fugaro's own logs somewhere else (`log_isolation`, on by default):
  - The logs of Fugaro's Cloud Run jobs, the workflow jobs and the check jobs (both labelled `fugaro=managed`), go through a sink to a dedicated log bucket, `fugaro` in location `global`, kept for 30 days.
  - A project-level exclusion keeps them out of `_Default`. It leaves two kinds of line in `_Default`, because log-based alerts don't operate on excluded logs: the check jobs' own decision lines (`event: image-check`) and Cloud Run's system log. Neither carries agent output. The other log the alert reads, the audit system events, is in `_Required`, which no exclusion applies to.
  - Readers need `roles/logging.viewAccessor` on the bucket's view, `fugaro-runs`, which the Logs Viewer role doesn't grant. The launchers get it from Terraform. Owners and editors can still read everything.
  - `fugaro logs` and `fugaro diagnose` read through the view named in the local config's `log_view`.
  - **Recorded exception:** Cloud Build logs (`resource.type="build"`) stay in `_Default`. They carry the repository's build output and, by design, never a secret value: secrets reach a build as file mounts, and the git credential never reaches a log. A filter on build tags may allow moving them under isolation later.
  - `fugaro init --no-log-isolation` leaves logs in `_Default`. `fugaro init --forget` turns isolation off first (§8.2).
- **What the redactor catches, and what it can't.** For each secret, it replaces the raw value, its JSON-escaped form, and, for a secret of at least 8 bytes, its base64 in the standard, raw-standard, URL and raw-URL alphabets (the whole encoding, plus the alignment-independent cores that catch a secret embedded at any offset in a longer encoded input), its percent-encoded forms, and the lines of its standard base64 wrapped at 76 and 64 columns when the secret starts the encoded input. It can't catch a secret split across two fields, content blocks or events; a secret the agent slices, truncates or otherwise transforms; hex, gzip or any other encoding; or a secret embedded mid-stream in wrapped base64, as in `echo KEY=$TOKEN | base64` or `env | base64`. Anything published from agent output is best-effort redacted, not guaranteed clean.
- **The CLI's own debug logging must not leak credentials.** Every cloud command (§5.4) refuses to run while `GODEBUG` contains `http2debug`, which would make Go print requests, bearer tokens and bodies to stderr. `GOOGLE_SDK_GO_LOGGING_LEVEL` is cleared at startup, because the storage client ignores Fugaro's discarding logger and would log every request.
- **The service account is per repository, not per run.** Every run of a repository's workflow runs as the same account, and the bucket condition grants the whole `runs/<slug>/`, `cache/<slug>/` and `locks/<slug>/` prefixes. So a run's agent can read and overwrite the records of the same repository's other runs (`task.json`, `launch.json`, `result.json`, cancel markers), take or break its branch locks, and poison its caches. A prompt-injected run can retask a queued run of the same repository or plant files a later run restores. The isolation is between repositories, not between runs of one; per-run credentials would need a service account (or a downscoped token) minted per execution, which v1 doesn't do. The CLI treats everything under a run's prefix as written by that repository's agent: it never follows a record to another repository's job.
- **Also by design, and not defended against:**
  - **The agent can reach the tokens it works with.** The provider token and the model credential reach it through the environment, the metadata server (as the job's account), Secret Manager and `/proc` of the runner, which runs as the same user; with egress unrestricted it can send them anywhere (§6.2).
  - **`actAs` on a build account amounts to that repository's secrets.** Anyone who holds `iam.serviceAccounts.actAs` on a repository's build account (for example to submit builds) can run a crafted build as it, and reach its provider credential and workflow secrets. That is why only operators get it. It spans one repository, no longer the installation. The account's isolation from repository code rests on the metadata boundary of §7.2.
- **A build token can still submit builds as the project's default build identity.** A build request that names no service account runs as the project's default build identity, which needs no `actAs`, and a build account holds `cloudbuild.builds.create`. So if that identity is powerful, a leaked build token is a path from one repository to the project. Fugaro's own requests always name the repository's account, and `gcp.BuildRequest` refuses any other, but a leaked token isn't bound by that. What that identity is depends on the project: `gcloud builds get-default-service-account --project <project>` names it, and `gcloud projects get-iam-policy` shows what it holds. If it is the legacy Cloud Build account (`<number>@cloudbuild.gserviceaccount.com`) or holds `roles/editor`, the path is real. The metadata boundary of §7.2, which keeps repository code from reaching any build token at all, is what keeps it closed, and gcp-setup.md tells the operator to read that identity before onboarding. The result for the installation Fugaro was first migrated in is recorded in docs/gcp-live-checklist.md.
  - **Name collisions are stopped by ownership checks, not by the hash.** The 8-hex hash in a service account ID resists accidental collisions, not chosen ones; the display name and the labels (§3.2) are what the bootstrap and `fugaro secrets set` check before reusing or deleting a resource.
  - **The redactor is best effort** (above).
  - **The bootstrap's `config` step** writes `REPOS` and `BASE_IMAGE` into the operator's own local config without a YAML serializer; a crafted value affects only that operator's file.
  - **The render step follows symlinks** in the clone: a symlinked `.fugaro/<wf>.Dockerfile` can read files in the render container, which holds no credential files (it runs as the repository's build account, whose metadata access is by design; §7.2).
- **Proxy variables reach the agent verbatim.** `HTTP_PROXY`, `HTTPS_PROXY` and `NO_PROXY` (in either case) are passed to the agent so it works on proxied networks. A proxy URL can embed `user:password@`, and the agent can read it like any other variable, so operators must not put credentials in proxy URLs; use a proxy that authenticates the job by network or identity instead.

**Who can do what.** The installation's Terraform takes two lists of IAM members, both empty by default, since an install where the owner is the only user needs neither (`fugaro init --launcher` and `--operator`, or the local config's `terraform.launchers` and `terraform.operators`).

- **Launchers** run and watch runs: `run`, `ls`, `logs`, `diagnose` and `cancel`. They get `fugaroLauncher` on the project, `fugaroJobRunner` on each workflow job (§3.4), `roles/storage.objectAdmin` on the runs bucket, and `roles/logging.viewAccessor` on the Fugaro log view. `fugaroLauncher` also holds `secretmanager.secrets.list` and `secretmanager.versions.list` on the project, for `fugaro secrets ls`, so launchers (and operators, who get what launchers get) can list every secret in the project, not only Fugaro's: each secret's name, labels and version states, never a value. In a shared project that metadata is visible to every launcher; a narrower operator-only role is possible if it matters.
- **Operators** also onboard repositories. They get everything launchers get, and on each repository's resources: `secretmanager.secretVersionAdder` and `secretmanager.viewer` on each of its secrets (so `fugaro secrets set` works), `roles/iam.serviceAccountUser` on its build account and each job account (creating a job needs `actAs` on its account), and `roles/artifactregistry.reader` on its registry (to pull its images and inspect or smoke them by hand; `fugaro image build` needs no grant to check that the registry exists, and warns and goes on if that check is refused). Installation-wide, they get `roles/iam.serviceAccountUser` on `fugaro-scheduler` (creating a Scheduler job needs `actAs` on it), the custom role `fugaroBuildSubmitter`, `roles/storage.objectAdmin` on the state bucket, and `roles/artifactregistry.writer` on `fugaro-base`, the only write access to base images.
- **The scheduler account** `fugaro-scheduler` (display name `Fugaro scheduler`) is the identity Cloud Scheduler starts the check jobs as. It holds `roles/run.invoker` on each check job and nothing else.
- **Who runs `fugaro init` for the installation.** Creating the service accounts, the custom roles and the project-level member bindings needs project-level IAM administration, so the person who runs `fugaro init` (without `--repo`) which is required. The three IAM administration roles (`roles/resourcemanager.projectIamAdmin`, `roles/iam.serviceAccountAdmin` and `roles/iam.roleAdmin`) are needed on top of the rights to create buckets, registries, secrets, jobs, log buckets and enable APIs (for example Editor, plus the Run, Secret Manager and Artifact Registry admin roles for their IAM), and are not enough alone. `fugaro init --repo` creates service accounts and project-level bindings too, so it needs the same rights; the operator role is what lets an operator work with resources that exist (store secret versions, act as the accounts, push base images), not what creates them.

**The state and runs buckets have no project-wide readers.** Cloud Storage gives a bucket convenience bindings for the project's Viewers. The runs bucket holds transcripts and caches, and the Terraform state bucket holds every name, account email, IAM condition and job env (never a secret value), so `fugaro init` removes the `projectViewer` bindings from both, each after its own confirmation (declining the runs bucket's is allowed and leaves a warning). On a fresh project the runs bucket is created by the apply, so `init` makes the confirmed removal after the apply when it has just created the bucket; a rerun is harmless. Owners and editors keep access through the same convenience bindings, which can't be removed. The state bucket is readable by operators only.

**The build credential stays out of repository code.** Each build has a `credential` step that runs the base image's `fugaro image git-credential`, which writes the git credential file into a Cloud Build volume, `fugaro-creds`, mounted at `/creds`. Only the `credential`, `source` and `build` steps mount it (a `prep` step first creates `/creds`, mode 0700, owned by uid 1000, since the base image runs as `fugaro`); `render` and the smoke don't. Nothing is written to `/workspace` or `/builder/home`. For Bitbucket the credential comes from the `bitbucket-token` secret, as before. For GitHub the step mints an installation token from the `github-app-key` secret and the App ID, with only `contents: read` and `metadata: read`, for the one repository, valid for at most an hour. `build` passes the file to BuildKit as the `git-credentials` secret, which no layer keeps.

**The smoke test runs repository code without network.** A repository's `dockerfile:` controls the whole image, its `fugaro` binary included, so the candidate image is smoke-tested by `docker run --network none`, never as a Cloud Build step: a step would run on the `cloudbuild` network, with the metadata server and the build account's token in reach (§7.2). The smoke is always the structural selftest, `basic`, and there is no `smoke:` setting.

**Terraform never holds a secret value.** No `google_secret_manager_secret_version`, resource or data source, exists anywhere under `deploy/terraform`, and the tfvars carry secret IDs only, so the state holds none. Secret containers are Terraform's; their versions are `fugaro secrets set`'s. Secrets, the runs bucket and every registry have `prevent_destroy`.

### 6.2 Agent git token

The agent's git token is a convenience, not a security boundary. At bootstrap, the runner gets a short-lived token for the agent:

- **GitHub:** an installation token for this repo only, valid for about an hour, minted from the App key. A token about to expire is refreshed between stages.
- **Bitbucket:** the repository access token itself.

The runner configures git and `gh` with the token, so the agent can push, edit the PR, and read issues and PRs as it would locally.

## 7. Images

### 7.1 Base images

Published to `ghcr.io/dimipaun/fugaro-<base>:<version>`, with a moving `:<major>` tag. They are rebuilt nightly for OS and toolchain patches.

| Base | Contents |
|---|---|
| `server-jvm` | Temurin JDK (LTS), git, zstd, Claude Code (native install), `fugaro`, and a non-root `fugaro` user with workdir `/work/repo` |
| `web-node` | Ubuntu 24.04, Node.js LTS (24, from nodejs.org into `/opt/node`) with corepack (pnpm/yarn), git, zstd, `tini` as PID 1, `sudo` with no rules, `gh` (GitHub CLI, pinned release tarball), Claude Code (native install, pinned), `fugaro`, and the same user and workdir |

The `fugaro` user's HOME holds no credentials. Model auth and the agent's git token reach the container through the environment and the runner (§6.2); `/work/creds` (mode 0700, outside HOME and the checkout) is reserved for a credential file the runner writes. The base images are built and checked with plain docker scripts, `images/build-base.sh`, `images/smoke.sh` and `images/scan.sh`, which CI runs unchanged.

### 7.2 Derived images

Every (repo, workflow) gets its own derived image. That image bakes in the checkout and the warm dependency caches, so a run only fetches the delta (§4.1) and never does a full clone.

**Default: generated, with no Dockerfile in the repo.** The engine ships `images/derived/Dockerfile.tmpl` and a Cloud Build config, and renders the template from the workflow's `image:` settings (§5.1). The derived image:

1. starts `FROM` the base image. Cloud Build pins it by digest: the render step's run pulls the base, and the build step resolves the digest of that same local image and builds `FROM` it. `fugaro image build --local` uses the reference as given, `--base` or the published base matching the fugaro version
2. applies the `image:` settings: the toolchain version override and extra `apt` packages
3. clones the repo at `base_branch` into `/work/repo`. Cloud Build clones the remote with the git credential as a BuildKit secret (`git-credentials`) that no layer keeps. `fugaro image build --local` instead puts a git bundle of the local checkout's `HEAD`, published as `base_branch`, in the build context, so it needs no credential. Either way the checkout's `origin` is the repository's https URL without credentials, which the runner adds credentials to at run time
4. runs a dependency warm-up with the workflow's declared secrets mounted as BuildKit secrets for private registries. Each is mounted as a file (`/run/secrets/<VAR>`, owned by `fugaro`, mode 0400, `required=false`), and the RUN's own shell reads it into `<VAR>` and exports it for that one command, so the value is on no command line and in no layer, `ENV`, build argument or log; a secret the build lacks leaves its variable unset. The `image.setup` steps get the same. BuildKit's `env=` secret mounts would be simpler, but Cloud Build's docker refuses them (`exec.secretenv is not supported by build server`). For Node it chooses, from `packageManager` and the lockfile, `pnpm fetch` plus an offline `pnpm install`, `yarn install --immutable` for Yarn 2 and later, `yarn install --frozen-lockfile` for Yarn 1, or `npm ci`. With `image.skip_build_scripts` (§5.1) the install runs no package lifecycle or build scripts (`--mode=skip-build` for Yarn 2 and later, `--ignore-scripts` for the others), so it only fetches and links the dependencies, and the workflow's `build` command builds what the repository needs; a repository whose dependencies need their install scripts, such as native modules, leaves it off. For Gradle it runs `./gradlew dependencies --no-daemon`
5. runs the `image.setup` steps as `fugaro`, with passwordless `sudo` granted for those steps only, which is what `playwright install --with-deps` needs
6. removes that sudo rule, strips the setuid bits of sudo and su (unconditionally, even when the workflow sets no `image.setup`), and runs `finalize-checkout`, which strips git credential config and fails the build if the origin isn't a plain https URL

**Escape hatch: a repo Dockerfile.** When `image:` can't express what the build needs, the repo commits `.fugaro/<workflow>.Dockerfile` and points `dockerfile:` at it. It replaces the template. It must build `FROM` a Fugaro base and keep `/work/repo` with the baked checkout, and `fugaro validate` checks both. The `fugaro:onboard` skill writes it only when needed (§5.2). A repository Dockerfile gets the same build arguments (`FUGARO_BASE`, `REPO_URL`, `REPO_ORIGIN`, `BASE_BRANCH`, and in Cloud Build `FUGARO_COMMIT` and `FUGARO_BUILT_AT`) and secrets as the template. `FUGARO_COMMIT` is the commit the build's `render` step read, which the smoke test and the build record expect: the template resets its clone to it, so a push to the branch during the build changes nothing, and a repository Dockerfile should do the same. `fugaro image render` prints the generated Dockerfile to start from.

**Local check.** `fugaro image build --local` builds the derived image with the developer's Docker, whether it comes from the template or the repo's Dockerfile. It then runs `fugaro image selftest` inside the image. The selftest checks that the user is not root and has no passwordless sudo, and that PID 1 is `tini`. A second container, run as root so no unreadable directory can hide a file, checks that there is no unexpected setuid or setgid binary and no file capability. It checks that `claude --version` and `node -v` work, with Node matching `image.node`. It checks that `/work/repo` is at the built commit, with an https `origin` and no credentials in any git config scope or in HOME. Last, it checks that `fugaro verify build` passes. The report comes back as JSON (`--json`) for the onboard skill, or a human, before anything goes to Cloud Build.

Builds:

- **Daily check:** one Cloud Run job per repository looks at every workflow once a day and rebuilds an image only when a trigger says to (below).
- **On demand:** `fugaro image build`.
- **Destination:** the repository's own Artifact Registry repository (`gcp.RegistryRepoID(slug)`, §6.1). The job references the `:latest` tag, and a build moves it, by digest, only after the new image passes its smoke test (below).

**Cloud Build.** `fugaro image build` without `--local`, run from the repository's checkout, submits `images/derived/cloudbuild.yaml` through `gcp.BuildRequest`, which fills in its substitutions and secrets, as the repository's own build account (§6.1). The daily check submits the same request, generated by the current code at check time, so nothing stale sits in Cloud Scheduler.

- **The steps.** `prep`, `credential`, `source`, `render`, `build`, `smoke`, `gate`, `promote`, `record` and `untag`, in that order.
  - `prep` creates the credential volume's mount point (§6.1). `credential` writes the git credential into the `fugaro-creds` volume, and `source` makes a shallow clone of `base_branch` with it.
  - **One base.** `render` runs the base image's own `fugaro image render` on the clone, so Cloud Build pulls `_FUGARO_BASE` once, for this step. `build` doesn't pull again: it pins the digest of that same local image (logging `base <image>@sha256:…`) and builds `FROM` it, so a tag republished between the steps can't give them different bases. The base is `--base`, else the local config's `base_image`, else the published base matching the fugaro version.
  - **A candidate first.** `build` pushes only `<image>:candidate-<build id>`, with the OCI labels `org.opencontainers.image.revision`, `org.opencontainers.image.created` and `dev.fugaro.base.digest` (for people and the registry console), and reads back the pushed digest. Nothing touches `:latest` yet.
  - **The smoke** (`fugaro image build --no-smoke` skips it) runs the candidate, by digest, in two containers with `docker run --network none` (§6.1): the structural selftest of the local check above, without `fugaro verify build`, and a scan as root for setuid and setgid binaries and file capabilities. It fails the build on a non-zero exit or a report that isn't `passed`.
  - **The gate** (`fugaro image gate`) reads the workflow's current record, `builds/<slug>/<workflow>/image.json` (§3.3). If that record is **newer** than the one this build would write, the build has been superseded (an older commit built more slowly than a newer one), and `promote`, `record` and `untag` do nothing. Newer means a later committer time on the source commit, or the same commit built later. It has limits: committer times need not follow history (clock skew, a rebase that keeps an old time), so the order can be wrong. The check corrects that, since a record whose source commit is no longer on the branch counts as changed. Otherwise the gate keeps the generation of the record it read.
  - **Promote by digest.** `gcloud artifacts docker tags add <image>@<digest> <image>:latest` points `latest` at exactly the image the smoke tested, so the tag can't move between the smoke and the promotion.
  - **The record** (`fugaro image record`) writes `image.json` with a generation-matched write against the generation the gate read (or create-if-absent when there was no record), as the build account, whose bucket condition covers `builds/<slug>/` and nothing else. The record holds the source commit and its time, the blob IDs of the workflow's cache key files, the hash of its image config, the template salt (the embedded `cloudbuild.yaml` and the fugaro version), the base reference and digest, `built_at`, the image digest, the build ID and the fugaro version. A record that changed since the gate read it fails the build (exit 2). Since `latest` has moved by then, the check's `latest` drift trigger sees a `latest` that doesn't match the record and rebuilds.
  - **Untag, best effort.** The build then tries to delete the candidate tag. The build account holds `artifactregistry.writer` and no more, and `writer` lacks `artifactregistry.tags.delete`, so this normally fails with a logged warning, and the step still succeeds. That is intended: `admin` would let a leaked build token delete any image in the repository, including `latest`. A leftover candidate tag is harmless, because the registry's cleanup policies handle it (below).
  - **Why a record in the bucket, and not just image labels.** A bucket object is one authenticated read through the blob code the CLI already has, it can sit next to the check's decisions, and its schema can change without a rebuild. Labels would need a registry manifest and a config blob, and new fields would appear only after a rebuild.
- **Registry cleanup.** Artifact Registry's cleanup policies delete *versions*, not tags, so a rule that matched the `candidate-` tag would delete the promoted version, which carries `latest` too. So every image registry has `KEEP` policies, and a keep rule wins over a delete rule:
  - versions tagged `latest` (and, on the base registry `fugaro-base`, `dev-`), and the 3 most recent versions;
  - delete: untagged versions older than 14 days, and, on a repository's registry, versions tagged `candidate-` older than 2 days (a version still among the 3 newest, or still `latest`, is kept by the rules above).

  The legacy `fugaro` registry has no policy. Cleanup starts in **dry run** (`--registry-cleanup dry-run`, the default): Artifact Registry only logs what it would delete, an operator checks that the log never names a version tagged `latest` or `dev-` (docs/gcp-live-checklist.md, check 17), and only then turns deletion on (`--registry-cleanup on`).
- **The git credential** is the `credential` step's, in the `fugaro-creds` volume (§6.1). For Bitbucket it is the repository's `bitbucket-token` secret, which fugaro writes into the build's `availableSecrets` directly (Cloud Build rejects a substitution the template doesn't reference), with `_GIT_USER` naming its https username (`x-token-auth`). For GitHub, `_GITHUB_APP_ID` and the `github-app-key` secret let the step mint a read-only installation token (§6.1). Only `credential` sees the secret, as `GIT_TOKEN` or `GITHUB_APP_KEY`. Go writes the credential line, percent-encoded, mode 0600, and refuses a URL that isn't the provider's own https host. The `source` step reads it from the volume, and `build` removes it on exit after passing it to BuildKit as the `git-credentials` secret; nothing goes to `/workspace` or `/builder/home`, so `render` never sees a credential.
- **GitHub repositories build in the cloud** the same way. The check job and `fugaro image build` both need the App ID (`repos.<r>.github_app_id`, set with `fugaro init --repo --github-app-id`), and the job carries it as `FUGARO_GITHUB_APP_ID`.
- **Workflow secrets.** `_SECRET_ENVS` lists the workflow's secret variables. `gcp.BuildRequest` adds each one to `availableSecrets` and to the build step's `secretEnv`, and the step writes each, with `umask 077` and `printf`, into its `mktemp` credential directory (removed on exit) and passes it as a file BuildKit secret (`--secret id=<VAR>,src=<file>`), since Cloud Build's docker doesn't support `env=` secrets. `fugaro image build --local` passes them as `--secret id=<VAR>,env=<VAR>`, which Docker Desktop supports; the Dockerfile mounts them as files either way. `cloudbuild.yaml` declares none of them itself, so a build's request is always made by `gcp.BuildRequest`, as the check makes it, and never by running the file as is. A workflow secret may not reuse a variable the build step sets or relies on, or one of the credential step's.
- **Repository code has no metadata server.** The `docker build` runs without `--network=cloudbuild`, so the `RUN` steps, where the repository's own code runs, can't reach the metadata server and the build service account's credentials. The `render` step does run on the `cloudbuild` network as the build service account, but it runs only the base image's `fugaro`, never repository code. The smoke runs the image, which is repository code, so it does so with no network at all.
  - **This is the boundary a build account's isolation hangs on** (§6.1). A repository controls its Dockerfile completely (`dockerfile:` or `image.setup`), and a Dockerfile can ask for `RUN --network=host`. A token reachable from any `RUN` would let repository code use its build account: read the repository's secrets, overwrite its images, and, through `cloudbuild.builds.create`, submit builds as the project's default build identity.
  - **It is checked live, not assumed.** The live Cloud Build check (`TestLiveCloudBuildSecretAndDigest`, docs/gcp-live-checklist.md, check 11b) probes the token endpoint, by name (`metadata.google.internal`) and by address (`169.254.169.254`), from a `RUN` on BuildKit's default network and from a `RUN --network=host`, and requires both to fail. It also probes from `docker run --network none` and from a `docker run` on the default network (the smoke's path), and requires both to be blocked. A control probe from a Cloud Build step on the `cloudbuild` network must succeed, so a probe that can't reach anything proves nothing. The result is recorded as a `FACT`.
  - **If the check fails,** the boundary doesn't hold: builds must move to a BuildKit builder that denies the `network.host` entitlement (`docker buildx create --driver docker-container` without `--allow network.host`), with `fugaro validate` refusing `--network` in a repository Dockerfile as a partial guard. Until then a failed check blocks onboarding an untrusted repository.
- **Injection.** Substitutions reach the step scripts only through `env:`, read as quoted `"$VAR"`, never spliced into a script: a branch named `x$(…)` is a valid git ref.
- **From the local config:** the machine type (`build.machine_type`, default `E2_HIGHCPU_8`), the region (`build.region`, default `region`) and the base image (`base_image`). The build account, the registry and the provider secret come from the repository's names (§3.2), not from the config. Without `--no-wait` the CLI waits for the build and prints the pushed digest, or says the build was superseded; `--no-wait` returns once it is submitted. A missing registry is a clear error before the build is submitted (a 403 on that check is only a warning, since an operator needs no grant on it).
- **`--no-smoke` can record a wrong commit.** The record's commit comes from the `source` step's clone, while the Dockerfile clones the branch head again during `build`. If a push lands between them, the smoke's checkout check fails the build, so nothing wrong is promoted. Without the smoke, nothing does, and the record can then name a commit the image doesn't hold. That is a limitation of `--no-smoke`; passing the commit into the build as an argument would fix it.

**The daily image check.** For each repository whose workflows aren't all `check: off`, Terraform creates a Cloud Run job, `gcp.CheckJobName(slug)`, and a Cloud Scheduler job that starts it once a day (`jobs.run`, as `fugaro-scheduler`, at a minute between 05:00 and 06:59 UTC derived from the repository, so repositories don't all build together). The job runs `fugaro image check --job` from `base_image`, as the repository's build account, in the installation's region.

- **Why the check exists.** A derived image bakes in the checkout and its dependencies. Correctness never depends on the image being fresh: at bootstrap the runner fetches the ref and force-checks it out (§4.1), and whatever the agent or `fugaro verify` runs installs what changed. A stale image costs three things, none of them a wrong result: run time and compute (a bigger fetch, more dependencies to install; the GCS caches soften it, but a warm image starts cheapest), security fixes in the base and toolchain that reach an image only when it is rebuilt, and, when `image:`, a `.fugaro/*.Dockerfile` or the setup steps change, an image that no longer matches the config the runner reads, which makes runs fail in confusing ways (a missing apt package). That last trigger isn't optional.
- **What it costs.** One rebuild is a 12-minute build plus a minute of smoke and promotion on `E2_HIGHCPU_8`, at about $0.016 a minute: about **$0.21**. A check is a 1 to 3 minute run of a 1 vCPU, 2 GiB job, about $0.004 (30 a month is about $0.12, likely inside the free tier), and Cloud Scheduler adds $0.10 a month per job beyond the billing account's free ones. Registry storage for the versions cleanup keeps besides `latest` is about $0.20 to $0.30 a month. So a daily check that rebuilds on a trigger costs about $1 to $3 a month per active repository, against $6.30 for rebuilding every night and up to 7 days of staleness, even right after a lockfile change, for rebuilding weekly. The ceiling is the nightly rate, reached only if a trigger fired every day, and a failing rebuild backs off (below).
- **What it reads.** The workflow's record (`image.json`), a blobless, no-checkout clone of the base branch (its tree and the few blobs the evaluation reads), and the base image's current digest, through a registry manifest `HEAD` (as the build account, which has read access to the base registry). It also compares the registry's `:latest` digest with the record's.
- **Triggers,** evaluated per workflow, and every one that fires is recorded: `no-record`, `image-config` (`image:`, `dockerfile:`, the Dockerfile's blob, the `base` name and `setup`, plus the template salt, so a new fugaro or `cloudbuild.yaml` rebuilds), `lockfiles` (the blob IDs of every file the workflow's cache key globs match, including the per-base defaults), `base`, `paths`, `max-age`, `built-commit-gone` (the recorded commit is no longer on the branch, after a force-push) and `latest-drift` (`latest` doesn't match the record, or is missing). An unreadable base or `latest` digest is a note, never a rebuild by itself. `image-config` and `no-record` can't be switched off (§5.1).
- **When one fires,** the job submits the build. Before it does, it asserts that the request has a `smoke` step, so the check never rebuilds with `--no-smoke`. It logs one JSON line per workflow (`event: image-check`, `decision`, `reasons`), and writes `builds/<slug>/<workflow>/check.json`. When the check itself fails, it logs `decision: check-failed` at ERROR before exiting 2.
- **Back-off.** A rebuild whose inputs (source commit, image config, key files and base digest) are the same as the last submitted build's, where that build ended in any final state, is not submitted again: the decision is `rebuild-failed-last` and the line is ERROR, so a broken build, or one that ended without fixing the image, doesn't burn a build every night. A build still running gives `skip` (`build-running`). A new commit, changed inputs or `--force` rebuild. A failed rebuild reaches `fugaro ls` (below), `fugaro image status` and the optional alert.
- **Paused until a record exists.** The schedule is created paused, and stays paused until `builds/<slug>/<workflow>/image.json` exists for every workflow it covers. An adopted M4 image has no record, so an unpaused first check would decide `no-record` and start a billable build that moves a live `:latest`, with nobody asked. `fugaro init --repo` decides this from what it finds, and offers the first build; the next `fugaro init --repo` unpauses the schedule.
- **The Scheduler region.** Cloud Scheduler isn't offered in every Cloud Run region, so the Scheduler job runs in `scheduler_region` (§5.4) and names the check job's own location in its URI, so a cross-region start works. The check job stays in the installation's region.
- **Locally,** `fugaro image check` runs the same evaluation with the operator's own git access and ADC, and only prints each workflow's decision (`--dry-run` is accepted and is what it always does; `--force` prints `rebuild`); it never submits a build or writes `check.json`, since that is the job's. `fugaro image status` prints each workflow's record and last check. Both need `base_image` in the local config.
- **Why not the alternatives.** Cloud Scheduler calling the Cloud Build API directly with a static body can't check anything, and goes stale when fugaro changes. A Cloud Build trigger can't hold each workflow's secrets without an inline copy of the request, and needs a repository connection. A check inside Cloud Build pays for a build machine every night.
- **Security.** The check needs the provider credential, which the build account already reads. What it adds is `cloudbuild.builds.create` on the project, which is not "nothing new": see the project's default build identity in §6.1.

**Base images live in `fugaro-base`.** Until the base images are published (M7), `base_image` in the local config is a dev tag in the installation's base registry, `<region>-docker.pkg.dev/<project>/fugaro-base/fugaro-web-node:dev-<commit>`, pushed by an operator (gcp-setup.md). The render step, the credential step, the check job and the `base` trigger all use it, and the credential, gate, record and check commands live in the base image's own `fugaro`, so the base must be rebuilt from a version that has them. A dev tag doesn't move, so the `base` trigger fires only when `base_image` itself changes (run `fugaro init --repo` after changing it, which updates the check job) or when the tag is pushed again, and `max_age` (14 days) is what bounds how long a security fix waits. From M7, `base_image` is unset, the published tag is refreshed nightly, the trigger does its job, and `max_age` can go back to 7 days.

**Dependency caches** (§4.1) are `cache/<repo-slug>/<workflow>/<key>.tar.zst`, written once with create-if-absent and never changed.

- **The key** is the SHA-256 of the key files' contents, the cached paths, the base image (a digest when the build pinned one, §4.1), and a toolchain hash of the workflow's `image:` settings (`node`, `jdk`, `apt` sorted, `setup` in order). A toolchain change such as a Node bump invalidates caches holding native binaries built for the old one. An entry with none of its key files is not cached.
- **Paths.** `~/<dir>` is under the home directory; anything else is inside the checkout. Absolute paths, `..`, any `.git` component, and paths that repeat or nest inside one another are refused. So are paths that are, contain, or are inside a credential location, since every cache is uploaded to the runs bucket: `~/.ssh`, `~/.claude*`, `~/.config/gcloud`, `~/.config/gh`, `~/.aws`, `~/.kube`, `~/.gnupg`, `~/.git-credentials`, `~/.npmrc`, `~/.netrc` and `~/.docker` (so `~/.config` itself is refused too). Any other path under `~/.config` is allowed, with a warning. A cache root that is a symlink, or lies under one below its base (home or the checkout), is never restored or saved, with a warning: a committed link, or one the agent made, could point a cache at a credential location or `.git` past every check above. The runner checks at restore and again before each save, and the save walks and opens everything through an `os.Root` of the root, so a link swapped in during the walk can't lead it outside.
- **What a save leaves out.** `~/.npm/_logs` (npm's debug logs quote the commands it ran), `~/.m2/settings.xml` and `~/.gradle/gradle.properties` (they often hold repository credentials). Symlinks that resolve outside their root are left out too, with a warning. An archive over the size cap (8 GiB uncompressed) is not written, and neither is one with no files.
- **Restore is hostile-archive safe.** It writes only inside the declared roots, through `os.Root`: no `..`, no absolute names, no symlink or hardlink escape, no write through a symlink already in a root, no setuid bits, nothing past the size cap. An archive that is corrupt or refused, including one that conflicts structurally with what is already at its paths, is a bad archive: the restore is a warning, not a failed run, and the object is deleted (generation-matched, so a replacement written since is kept) so it doesn't block its key until the lifecycle rule expires it.

**Staleness policy** (resolves SPEC §9). The baked checkout and dependencies are as old as the image, which the daily check (§7.2) rebuilds a day after a lockfile or config change and at least every `max_age`; the run's `image_age_s` (§9.1) shows how old. Correctness never depends on it. The startup delta fetch covers the code. The content-addressed GCS caches cover dependency changes between rebuilds, because a changed lockfile gives a new key that the first run writes back.

## 8. Infrastructure

### 8.1 Terraform modules (`deploy/terraform/gcp/`)

```
deploy/terraform/
  terraform.go                 # package terraform: //go:embed gcp
  gcp/
    modules/installation/      # shared: APIs, runs bucket, base registry, custom roles, scheduler account,
                               #   log bucket/view/exclusion, optional budget and alert
    modules/repo/              # one repository: secret containers, its image registry, build account
                               #   and its IAM, check job and schedule, module "workflow" for each workflow
    modules/workflow/          # one (repository, workflow): job account, bucket condition,
                               #   secret accessors, aiplatform.user, Cloud Run job, launcher IAM
    roots/installation/        # backend "gcs" {}, provider, module call, outputs, lock file, tests/
    roots/repo/                # the same; the installation's outputs arrive as tfvars
    .tflint.hcl
```

**Installation-level resources** (`modules/installation`):

- the enabled APIs: Run, Storage, Secret Manager, Artifact Registry, Cloud Build, Cloud Scheduler, Logging, Monitoring, IAM and Cloud Resource Manager, plus Vertex AI when it is used. The installation root can't read the workflows, so "used" comes from the local config: `fugaro init --repo` records `repos.<r>.vertex` when any workflow has `agent.auth: vertex`, and `fugaro init` sets `enable_vertex` when any recorded repository has it. For the first such repository `init --repo` warns that the installation must be rerun, and the API then stays enabled while any recorded repository has the flag. Always with `disable_on_destroy = false`, so removing Fugaro never disables an API something else uses
- the runs bucket with its lifecycle rules (§3.3)
- the base registry `fugaro-base`, with its cleanup policies (§7.2), and the legacy `fugaro` registry when `fugaro init` adopts one (`adopt_legacy_registry`, set from discovery, so a fresh project never gets an empty one)
- the custom roles `fugaroLauncher`, `fugaroJobRunner` and `fugaroBuildSubmitter`, the scheduler account, and the launchers' and operators' installation-level grants (§3.4, §6.1)
- log isolation: the log bucket, sink, exclusion and view (§6.1)
- an optional billing budget with 50%, 90% and 100% alerts (`--budget`, `--budget-currency`, `--billing-account`), and an optional alert that emails `alert_email` about failed image checks and rebuilds: one notification channel and two alert policies, one per log-match condition (the check's `image-check` line at `ERROR`, and a check job execution's failure at ERROR in either the audit log's system events, where a failure at container start such as an unreadable secret appears, or the Cloud Run system log, where a later one does), since Cloud Monitoring allows a log-match condition only alone in its policy. The budget needs billing-account permissions; a budget made by hand stays unmanaged

**Per-repository resources** (`modules/repo`, input: the repository's rendered settings, not a map of every repository):

- the secret containers (never their values: Terraform never holds a secret value), labelled as §3.2 says
- the repository's image registry, with its cleanup policies, and the build account with its IAM (§6.1)
- the check job, its Scheduler job (created paused, §7.2) and the scheduler account's `roles/run.invoker` on it
- for each workflow (`modules/workflow`): the job account and its IAM (§6.1), the Cloud Run job (image, resources, timeout, `maxRetries 0`, one task, mounted secrets, `deletion_protection`), and the launchers' `fugaroJobRunner` on it

Every IAM grant is a `*_iam_member` resource, never a binding or policy, so nothing is authoritative over a resource shared with someone else. Secrets, the runs bucket and every registry have `prevent_destroy`, and jobs have `deletion_protection`, which only an explicit apply lowers (`--allow-job-delete`), before offboarding or before a change that removes a job (all checks off, or a workflow removed).

**State: one per repository.** The installation has a state (`fugaro/installation`) and each repository its own (`fugaro/repos/<slug>`), in a GCS bucket, `fugaro-tfstate-<project>` by default. So an operator who onboards a repository plans and applies that repository alone, can't omit another repository and so plan its deletion, and every apply's blast radius is one repository. The repository root is self-contained: `fugaro init --repo` reads the installation root's outputs and passes the values it needs (the runs bucket, the base registry, the scheduler account, the role IDs, the launchers and operators) in `terraform.tfvars.json`, with no `terraform_remote_state`. So the tfvars describe the whole input, and a team that runs its own Terraform doesn't depend on our state layout. The state holds no secret value, but it holds every name, account email, IAM condition and job env, so it is operator-only (§6.1). Terraform never manages the state bucket itself: `fugaro init` creates it through the storage API, in the installation's region, with versioning on, uniform bucket-level access, public access prevention enforced, the label `fugaro=tfstate`, a rule that keeps the 20 newest noncurrent versions, and no `projectViewer` bindings. The GCS backend locks the state.

### 8.2 `fugaro init`

`fugaro init` wraps Terraform. It runs the `terraform` binary on `PATH` (1.7 or newer, before 2.0) through `os/exec`, with nothing but `version -json`, `init`, `plan -out`, `show -json`, `apply <planfile>`, `output -json` and `state rm`, so the argv and environment are exact and tests can substitute a fake. It embeds the modules and writes the root into a disposable working directory (`$XDG_STATE_HOME/fugaro/terraform/<project>/…`), so the binary and its module always match.

**Commands**

| Command | What it does |
|---|---|
| `fugaro init` | The installation: the shared resources of §8.1. |
| `fugaro init --repo [PATH]` | One repository, from its checkout (default: the current directory), whose committed `fugaro.yaml` says what it needs. Without a `fugaro.yaml` it exits pointing to `/fugaro:onboard` and `fugaro config example` (§5.2). The installation must have been initialized first. |
| `--plan-only` | Stop after showing the plan. |
| `--print-vars` | Print the Terraform variables as JSON and exit, with no cloud calls and no Terraform. With `--repo` the values are ungated, and a warning on stderr says so: no discovery or readiness gate ran, so every job (the check job too) is deployed, on the new image path, and every account gets the new display name. Without `--repo` they are ungated too, with the same kind of warning: no discovery ran, so `adopt_legacy_registry` is `false`. |
| `--config-only` | Write the local config from the installation's outputs (or the flags, when there is no state), with no plan. This is for teams that run Terraform themselves. |
| `--forget` | The rollback, below. |

Other flags: `--project` and `--region`; `--runs-bucket`, `--state-bucket`, `--base-image` and `--scheduler-region`; `--launcher` and `--operator` (repeatable) and `--alert-email`; `--budget`, `--budget-currency` and `--billing-account`; `--registry-cleanup dry-run|on|off` (default `dry-run`); `--no-log-isolation`; `--allow-delete <address>` (repeatable); `--yes`; `--json`; and, with `--repo`, `--github-app-id`, `--no-build` and `--allow-job-delete`. Teams that manage Terraform themselves use `roots/*` as examples and `github.com/dimipaun/fugaro//deploy/terraform/gcp/modules/repo?ref=vX.Y.Z` as the module source, with the inputs from `--print-vars`.

**What `init` does,** in order: it checks its environment (below), writes nothing yet, and computes every name and the tfvars; it runs the read-only discovery and ownership checks, including the live IAM bindings, and generates `imports.tf.json`; it decides the readiness gates and the schedule's paused state; it creates the state bucket if it is missing, and removes the `projectViewer` bindings from the runs and state buckets (each behind its own confirmation); it runs `terraform init`, `plan` and `show -json`; it prints a summary and applies the guard; it asks; it applies **the saved plan file it showed and nothing else**; and it writes the local config, showing the diff and keeping the old file as `config.yaml.bak-<UTC time>`. With `--repo` it then offers each workflow's first image build (its own confirmation, billable), applies again to deploy the built image and unpause the check, and prints the `fugaro secrets set` commands still needed (a secret made with `gcloud secrets create` lacks the labels, and Fugaro refuses it).

**What `init` never does:** read or write a secret value; apply without a confirmation; apply anything but the plan it showed; let a plan delete or replace a resource the user didn't name with `--allow-delete`; enable billing; edit project-wide IAM authoritatively; or start a billable build unattended.

- **Discovery adopts what the bootstrap made, and refuses what isn't ours.** A resource under one of our names that exists **and** carries our mark (§3.2) gets an import block, so Terraform adopts it in place. One without the mark, or marked for another repository or workflow, or a bucket that belongs to another project, is refused: `init` exits 1 and names it, and generates nothing for it. For an existing job account, discovery also reads the bucket's and each secret's live IAM policy, and requires exactly one conditional bucket binding with the spec's title and expression, or refuses with the diff, since a condition that differs by a byte would be a second binding next to the bootstrap's. The summary says `IAM: n bindings match the live ones (adopted), m new`.
- **Readiness gates.** A workflow's job is deployed when its image exists and every secret it mounts has an enabled version, or when the job already exists. An adopted job keeps its M4 image path until the new registry has a `:latest`, so the switch never points a job at a missing image. The check job, with its invoker grant and Scheduler job, is deployed when the provider credential it mounts has an enabled version, or when the check job already exists: Cloud Run checks a job's secrets when it creates it, and a fresh repository's first `init --repo` creates the credential's secret empty. The check's schedule stays paused until every workflow it covers has a record (§7.2). What is still missing is printed, with the command that fixes each.
- **The guard.** Any plan that would delete or replace a resource is refused (exit 1) unless `--allow-delete` names its address, and any action the guard doesn't know is refused too. A refused delete of something only a flag declares (the budget, the alert, the launcher and operator grants) comes with a hint naming the flags to pass again. The summary lists risky in-place updates first, with the changed attribute names and never values: a job's `service_account`, `image`, `env` or `max_retries`, a bucket's `lifecycle_rule`, a registry's `cleanup_policies`, the schedule's `paused`.
- **The confirmation.** `init` prints `⚠ CONFIRM (project <p>): …` and asks for the project ID to be typed, unless `--yes` is given. Without a terminal it refuses and does nothing, unless `--yes` is given. The same applies to creating the state bucket, removing the `projectViewer` bindings and submitting an image build. `--plan-only` changes no IAM and creates nothing but the state bucket.
- **The environment is an allowlist.** The wrapper builds Terraform's environment from scratch. It copies only `PATH`, `HOME`, `USER`, `LOGNAME`, `LANG`, `LC_ALL`, `TZ`, `TMPDIR`, the `XDG_*` variables, the proxy variables, `SSL_CERT_FILE` and `SSL_CERT_DIR`, `CLOUDSDK_CONFIG` and `GOOGLE_APPLICATION_CREDENTIALS`, and sets `TF_IN_AUTOMATION`, `TF_INPUT=0`, `CHECKPOINT_DISABLE`, its own `TF_DATA_DIR` and its own `TF_CLI_CONFIG_FILE` (holding only a plugin cache directory and `provider_installation { direct {} }`, so a user's `~/.terraformrc` is never read). Everything else is dropped, including every `TF_*` (`TF_LOG` at trace level would log bearer tokens; `TF_CLI_ARGS` could add `-lock=false` or `-auto-approve`; `dev_overrides` or `TF_REATTACH_PROVIDERS` would swap in a provider the lock file never checked) and the provider's own credential variables. `GOOGLE_IMPERSONATE_SERVICE_ACCOUNT` is refused, not dropped, so the user knows the apply would run as someone else. `init` also refuses to run while `GODEBUG` contains `http2debug`, or while `GOOGLE_PROJECT`, `GOOGLE_CLOUD_PROJECT` or `CLOUDSDK_CORE_PROJECT` names another project. The generated provider always sets `project`, `region`, `billing_project` and `user_project_override`, so gcloud's active project never matters.
- **`--forget` is the rollback,** at any point before `fugaro-build` is retired. It undoes what M5 added, not only the state. For the installation, its first phase is a normal guarded, confirmed apply with log isolation and registry cleanup turned off, which deletes the `_Default` exclusion, the sink, the view, the log bucket and `fugaro-base`'s cleanup policies (the repositories' registries keep theirs, which M4 never reads); `--forget` allows exactly those deletions and no others (and refuses a plan that creates anything). A deleted log bucket stays pending deletion for 7 days and its ID can't be reused meanwhile: `--forget` prints that, with the undelete command (`gcloud logging buckets undelete <bucket> --location=global --project <p>`), which a migration retried within the week runs first. Its second phase, after a second confirmation, is `terraform state rm` of everything left, which destroys nothing. It refuses while any repository's state exists. Its state keeps the root's outputs, so `init --repo` checks that the installation's state still manages resources, and until `fugaro init` has run again it refuses (exit 1) and says so. `init --repo --forget` does only the second phase, and also deletes the repository's now-empty state object (the bucket is versioned, so it stays recoverable). The runbook then restores the backed-up local config and redeploys each job with the M4 binary's `gcp-m4.sh --apply job`, always ([gcp-setup.md](../gcp-setup.md)). A later `fugaro init` imports again what `--forget` left and still carries our mark (the runs bucket, the registries, the log bucket once undeleted, the custom roles, the scheduler account, and each repository's accounts, secrets, jobs and Scheduler job). The custom roles are matched by title and `fugaro-scheduler` by display name; a deleted role isn't imported, since the plan's create restores it. The log bucket can carry no labels, so its description, which Go sets through the tfvars, is its mark: a `fugaro` log bucket without it is refused (exit 1), since the plan would set its retention and the rollback would delete it, and ours still pending deletion is refused (exit 1) with the undelete command. The summary lists any change of the bucket's retention under "⚠ Review these first". A Scheduler job is ours only when it targets the repository's check job and runs as `fugaro-scheduler`. Each lookup treats a 404 as "create" and any other error as a remote error with no imports. The sink and the `_Default` exclusion were deleted by the first phase, so the retry creates them again. It doesn't adopt the alert's notification channel and two policies ("Fugaro image check failed" and "Fugaro image check job failed") or the budget, which have no name to find them by: a retry duplicates them unless they are deleted by hand first (`gcloud alpha monitoring policies delete` for each of the two policies, `gcloud alpha monitoring channels delete`, `gcloud billing budgets delete`; the runbook lists them).
- **Exit codes:** 0 ok, 1 a user error or refusal (a guard, an ownership check, a missing confirmation), 2 a remote failure (a GCP API error, or a Terraform plan or apply that failed). `--json` prints one result document on stdout, with the human-readable text on stderr.

**Offboarding** isn't a command yet. Only its first step is implemented: `fugaro init --repo --allow-job-delete` lowers the repository's jobs' `deletion_protection`. Removing the repository's secrets from state and destroying the rest is an unsupported outline (gcp-setup.md) that means running `terraform` by hand in the workdir, outside the guard and the environment allowlist, and that also needs the registry's `prevent_destroy` handled, which today means editing the module.

## 9. CLI and plugin

### 9.1 Commands

Every command that reports something supports `--json`: `run`, `ls`, `logs`, `diagnose`, `cancel`, `secrets set`, `secrets ls`, `validate`, `init`, `image build`, `image check` and `image status`. The exceptions print a fixed kind of output or run inside a job: `config example` (the template), `image render` (the Dockerfile), `version`, `verify` and `exec`. Exit codes are stable: 0 for ok, 1 for a user error, 2 for a remote failure.

| Command | Behavior |
|---|---|
| `fugaro run [--repo R] [--ref REF] [--workflow W] [--run-id ID] [--batch NAME] [--total-timeout D] [--task-file F \| TEXT]` | Writes `task.json`, launches, and records `launch.json` (§4.7). `--repo` defaults to the checkout's origin. The workflow is `--workflow`, else the local config's single workflow for the repository, else the checkout's single workflow. The ref is `--ref`, else the local config's `base_branch`, else the checkout's `git.base_branch`. `--run-id` makes the launch idempotent (§4.7). `--total-timeout` (a Go duration, at most 24 hours) overrides the workflow's `timeouts.total` for this run (§4.5). A new launch checks the `max_parallel` soft limit (local config, default 20) against active executions of every `fugaro-` job (the check jobs, `fugarochk-`, don't count). The `jobs/-` listing is newest first across jobs (confirmed live), so it stops at the first execution older than a horizon: the longest task timeout among the region's `fugaro-` jobs (one `jobs.list` call) or the 24-hour override cap, whichever is longer, plus the 2-minute task slack and an hour for queueing. That is about 25 hours for a 92-minute workflow, usually one page. The limit is soft: an execution older than the horizon that is still running goes uncounted, which needs an override longer than the cap allows. Prints the run, the future branch name and a Cloud Logging URL (a Logs Explorer query on the Fugaro log view, when log isolation is on); `--json` gives `run`, `repo`, `run_id`, `branch`, `execution`, `log_url` and `status` (`launched` or `already-launched`). |
| `fugaro run --retry RUN` | Launches a run that has `task.json` but was never launched, and takes no task flags or text (§4.7), so the stored `--total-timeout` is kept. It backfills `launch.json` from `result.json` for a run whose CLI died after the launch, refuses a cancelled run, and exits 1 while another launch may still be in flight. |
| `fugaro run --pr N [TEXT]` | Launches a follow-up run (§4.4). In M4 the flag exists, hidden, and exits 1 pointing to M6. |
| `fugaro ls [--repo R \| --all] [--mine] [--since D] [--batch NAME] [--watch]` | Joins the runs bucket (`task.json`, `launch.json`, `result.json`, the claim and the cancel marker) with the backend's executions. Shows run, status, stage, age, cost and the PR URL, newest first, then a totals line (§10.1). By default it lists the local config's repositories (every repository in the bucket when the config lists none); `--all` lists every repository in the bucket. `--since` defaults to `7d` (days, or a Go duration such as `36h`; `0` for no bound). Statuses: `launching`, `unlaunched`, `pending`, `running`, `succeeded`, `failed`, `infra_error`, `cancelled` and `error`. `succeeded` comes only from `result.json`; an execution that ended without a final record is `infra_error` ("execution ended without finalizing"), and so is a `running` record whose execution the backend no longer knows, once past its `deadline`. A launched run with no record whose execution the backend doesn't know is `infra_error` ("no execution found and the runner never recorded the run") once 10 minutes (the claim TTL) have passed since its launch; before that it is `pending`. `error` is a run whose objects can't be trusted or read: a corrupt or oversized `launch.json`, `result.json` or claim, or an execution that isn't one of the run's own job in this region (§6.1); its reason says which, with a warning on stderr, nothing about its progress is guessed, and it counts as settled. The totals line and `--json`'s `totals` are §10.1's. Each `--json` row has `image_age_s`, the age of the image the run started from (its `started_at` less the record's `image.built_at`, §4.6), absent when unknown. **Image warnings.** For each workflow of the local config's repositories, `ls` reads its image record and last check (§7.2) and prints a `warning:` line before the table (in `--json`, the always-present top-level `warnings` array, empty when there are none): the image rebuild failed (`the image rebuild of <date> failed (FAILURE); runs still use the image built <date>`), the daily check failed (`the daily image check failed on <date>: <error>`), the check hasn't run for 48 hours, or an image status object can't be read. Whether a workflow is on the daily check comes from the checkout's `fugaro.yaml` when `ls` runs in one, else from the installed check job's list of workflows (no check job: none), so a workflow whose check is off never warns that it hasn't run. A failure a newer record has since superseded is not reported. `--watch` redraws every 10 seconds until every run has settled; with `--json` it prints one JSON document (`runs` and `totals`) per redraw. |
| `fugaro logs RUN [-f]` | Cloud Logging entries of the run's execution (by region, job name and the `run.googleapis.com/execution_name` label), oldest first, from a minute before the launch. `-f` keeps printing until the execution ends and its logs settle. `--json` is NDJSON, one object per entry with `time`, `severity`, `stage`, `stream`, `event` and `message`. Every line is also redacted of the platform credentials in the CLI's own environment. |
| `fugaro diagnose RUN` | Shows the stage reached, the reason, the last verify records (failed and flaky tests), the last review findings, a log tail, the agent's final message, the cost, and the PR URL. `--json` fields: `row` (the `ls` row), `verify`, `failed`, `flaky`, `findings`, `agent_message` (clipped to 4 KiB), `log_tail` (the newest 30 lines) and `report_path`. Everything is redacted like `logs`; a failed log read is a warning, not a failure. |
| `fugaro cancel RUN [--grace D \| --now]` | Writes the cancel marker, then cancels the execution after a grace period (§4.5). `--grace` defaults to 3 minutes and is never less than the run's finalize reserve plus 40 seconds. It reports `finalized` as soon as `result.json` is final or the run is at `writeback`, and never hard-cancels during `finalize` or `writeback`. `--now` cancels at once, still not during `finalize`, and can't be combined with `--grace` (exit 1). `--json` gives `run`, `status` (§4.5), `marker` (the cancel marker was written), `hard` (the execution was cancelled through the backend) and `pr` (the PR URL, when `result.json` names one). |
| `fugaro secrets set NAME [--repo R]` | Stores a new version of the repository's secret `NAME` in Secret Manager, creating it (labelled, §6.1) if needed. The value comes only from stdin: a pipe, a redirect, or a hidden prompt at a terminal. `NAME` must be reserved (§5.1) or declared by a workflow of the checkout's `fugaro.yaml`. Prints the secret ID and version, never the value. |
| `fugaro secrets ls [--repo R]` | Lists the repository's secrets (by the `fugaro_repo` label): logical name, secret ID, latest version, version count, creation time and labels. It never reads a value. |
| `fugaro validate [path]` | Validates `fugaro.yaml` against the schema and checks the declared files and commands. With `--json`, it emits one problem per entry, each with a path and a message, for the onboard skill to act on. |
| `fugaro config example` | Prints the annotated `fugaro.yaml` template. |
| `fugaro init [--repo [PATH]] [flags]` | Provisions the installation, or with `--repo` one repository, with Terraform, and writes the local config (§8.2, [gcp-setup.md](../gcp-setup.md)). `--plan-only`, `--print-vars`, `--config-only` and `--forget` are its modes; nothing is applied without a confirmation. |
| `fugaro version` | Prints the fugaro version, which picks the matching published base images and which the onboard skill checks. |
| `fugaro image build [--workflow W] [--base IMAGE] [--repo R] [--no-wait] [--local]` | Without `--local`, submits the derived-image build to Cloud Build from the repository's base branch and waits for it (§7.2); run it from the repository's checkout, whose `fugaro.yaml` and origin say what to build (`--repo`, if given, must match the origin). `--no-wait` returns once the build is submitted. `--local` builds it with local Docker from the checkout you are in (§7.2), then smoke-tests it by running `fugaro image selftest` inside the image, which checks the user, sudo, the toolchain, the baked checkout and its origin, credentials, setuid and setgid binaries, file capabilities and sudoers, and runs `fugaro verify build`. `--base` names the base image (default: the local config's `base_image` for a cloud build, else the published base matching the fugaro version), `--tag` the locally built image (default `fugaro-<dir>-<workflow>:local`), `--platform` the platform (default `linux/amd64`), `--no-smoke` skips the smoke test (on Cloud Build, `latest` is then promoted unsmoked, and the record can name the wrong commit, §7.2), and `--json` prints the result as JSON. On Cloud Build it reports a superseded build (§7.2) as such. |
| `fugaro image check [--workflow W] [--force] [--dry-run] [--job]` | Evaluates the rebuild triggers of the repository's workflows against the head of its base branch (§7.2): a blobless clone, the build record in the runs bucket, and the base image's digest. | `fugaro image status [--repo R]` | For each workflow of the local config's repositories (or `--repo`'s), prints what the runs bucket records: the image's build time and age, source commit and base digest (`image.json`), and the last daily check's time, decision and reasons and the last rebuild's status (`check.json`). |

## 10. Observability and guardrails

**Observability**

- **Logs:** the runner writes JSON logs to stdout with fields `run_id`, `repo`, `workflow`, `stage`, and `severity`. The agent's and verify's output is relayed with `stream: agent|verify`.
- **The agent-event relay.** While a stage runs, the runner relays a concise, live view of Claude Code's `stream-json` output as `stream: agent` entries, each with an `event` field: `init` (session and model), `text` (the agent's text), `tool` (a tool call and a summary of its input), `tool_error` (the first line of a failed tool result), and `result` (with `cost_usd` and `is_error`). It sits behind the transcript's redactor, and each message is redacted again, then clipped: 2000 bytes for `text`, 300 for the others. A `stream-json` line over 4 MiB (in practice a tool result carrying a large file) is dropped from the relay whole; it is still in the transcript. `fugaro logs -f` shows these events as they happen.
- **Cost:** the per-stage cost reported by Claude Code (`--output-format stream-json` result events) is added up into `result.cost_usd`.
- **Durable record:** the PR plus `runs/<repo>/<run-id>/`.

**Guardrails**

- stage and overall timeouts, including the finalize reserve (§4.5)
- the Cloud Run task timeout
- `agent.max_budget_usd` per stage
- the `max_parallel` soft limit in the CLI
- the GCP billing budget alert
- `maxRetries 0`

### 10.1 Cost reporting

Every run reports what it cost, split into model and compute. The report goes in `result.json` (`cost`, §4.6), the PR report, `fugaro ls` and `fugaro diagnose`.

- **Model cost:** the per-stage `total_cost_usd` from Claude Code's result events, added up. `cost_usd` keeps this figure for compatibility. `model_basis` says how far to trust it:
  - `api-list`: the auth is `vertex` or `api-key`, and the figure matches list-price billing.
  - `subscription`: the auth is `oauth`. The figure is notional, because usage counts against plan limits, not dollars, so `total_usd` leaves it out and `ls` shows it separately.
- **Compute cost:** billed duration × (vCPU × price per vCPU-second + GiB × price per GiB-second).
  - Prices belong to the backend. Each backend (Cloud Run now, a Docker-capable backend in M8) ships published list prices as defaults, keyed by region: `gcp.ListPrices(region)` for Cloud Run. The engine holds no company-specific rates.
  - **Local overrides,** for example to reflect committed-use discounts: the local config's `compute_prices` (§5.4) gives a region's vCPU-second and GiB-second prices, which replace the list prices in `ls` and `diagnose`, with the `Source` field of the price set to `local override`. So the runner's PR report agrees with `ls`, the same values reach the jobs as `FUGARO_COMPUTE_PRICES=<vcpu>,<gib>` (the tfvars carry them), and the runner reads that variable; a malformed value logs a warning and falls back to the list price. Without an override, everything uses list prices.
  - Smaller costs are left out: storage, logging, and image builds. That's why every figure is marked as an estimate. The free tier is ignored too, so figures are an upper bound.
- **Cloud Run jobs list prices** (no committed-use discount; from `https://cloud.google.com/run/pricing`, checked 2026-09-27):

  | Tier | Per vCPU-second | Per GiB-second |
  |---|---|---|
  | 1 | $0.000018 | $0.000002 |
  | 2 | $0.0000216 | $0.0000024 |

  Tier 1 is the regions the pricing page lists as "Subject to Tier 1 pricing", copied into `internal/backend/gcp/prices.go`. **An unknown region gets tier 2**, the higher price, so an estimate errs high rather than low.
- **Where it's computed:**
  - The runner records the model cost and its basis as it goes. At finalize it writes its own compute estimate into the PR report: elapsed time since `started_at` at the list price of `FUGARO_REGION`, with the workflow's `resources`. The final `result.json` repeats that estimate, up to the end of the run.
  - `fugaro ls` and `diagnose` compute it from the backend's execution record instead: the execution's billed duration (start to completion, or to now while it runs) with the task's CPU and memory limits, at the list price of the execution's own region (the local config's region, after `--region`, when that isn't known). When the execution isn't known, they fall back to the record's estimate, or report compute as not estimated.
  - `compute_estimated` says whether a compute figure exists; nothing reads a zero `compute_usd` as "free".
- **Totals across runs:** `fugaro ls` ends with a totals line summing the listed runs, for example with `--batch`, `--since`, or `--mine`. Each run's `total_usd` is rounded to the cent, and totals sum those, so totals are compared and shown to the cent.
- **Report lines.** The PR report's line depends on the basis and on whether compute was estimated:
  - `**Cost:** ≈ $4.50 (model $4.12 + compute $0.38, estimate)`
  - `**Cost:** ≈ $0.38 compute (estimate); model $4.12 notional, counted against the Claude subscription`
  - `**Cost:** model $4.12 (compute not estimated)`
  - `**Cost:** model $4.12 notional, counted against the Claude subscription (compute not estimated)`
  - `**Cost:** $4.12`, the model figure alone, for a record with no `cost` breakdown (the runner computes one only once it has read `fugaro.yaml`)

  `fugaro ls` prints each run's `total_usd` as `$0.38`, with a trailing `~` when a notional subscription figure was left out, and a totals line such as `3 runs · ≈ $1.14 billed (model $0.00 + compute $1.14) · $12.36 model notional (subscription)`. The notional part appears only when there is one. A run whose compute was not estimated shows `, compute not estimated` after its cost instead of reading as free, and the totals line adds `compute not estimated for N runs`; `--json` counts them in `totals.compute_not_estimated`, which means the compute sum is a lower bound. A run that never launched has no compute at all, which is known, and isn't counted.

## 13. Testing strategy

The runner depends only on the interfaces `Agent`, `Provider`, `blob.Bucket`, `Shell`, and `Clock`, so nearly everything is testable without the cloud or a model.

- **Unit tests (CI, every push):**
  - config and task parsing against the schemas, with golden files; `validate` problem reporting; the embedded example must itself pass `validate`
  - the stage machine as table-driven transitions with fakes: review asks for changes → fix → next round; review rounds used up → draft; budget reaching the finalize reserve → finalize; bootstrap failure → `infra_error`; follow-up run with a missing session → fresh session; cancel marker; lock busy or expired
  - the PR outcome rule
  - cache key computation and restore/writeback against `memblob`/`fileblob`
  - lock semantics
  - JUnit parsing and flaky detection
  - secret redaction
- **Adapter tests:**
  - GitHub and Bitbucket against recorded `httptest` fixtures: find-or-create PR, draft toggling, comment retrieval, App JWT and installation-token minting
  - the agent adapter against a scriptable **fake `claude`** binary that emits canned `stream-json`, checking flags, session resume, env scrubbing, cost aggregation, and a process-group kill that includes a daemon-like child
- **Hermetic end-to-end test (`go test -tags docker`):** `fugaro exec` inside a derived image built by `fugaro image build --local` from each real base image. It uses a local bare git remote mounted at its host path, `fileblob`, a fake provider, the fake `claude`, and a tiny npm fixture (a Gradle fixture arrives with the `server-jvm` base). It asserts on the resulting branch, including a commit pushed after the image was built and a file only the image's warm state holds, and on the run record and the provider calls. Without the `docker` tag, `go test ./...` never needs Docker.
- **Real end-to-end test (nightly and manual, budget-capped):** fixture repos on GitHub, a sandbox GCP project, real Cloud Run, and real Claude on a trivial task. It asserts a ready PR, then a failure-injected draft PR, then a follow-up run on that PR, and closes the PRs afterward. Bitbucket end-to-end is a manual pre-release checklist item.
- **Infrastructure and images:** `terraform validate` and `tflint` in CI. Images are built and smoke-tested (`fugaro version`, `claude --version`, `java -version`, `node -v`, the non-root user, `tini` as PID 1, no passwordless sudo), then scanned with Trivy. The checks are plain docker scripts (`images/build-base.sh`, `images/smoke.sh`, `images/scan.sh`) that CI runs unchanged, so they also run locally.

## 14. Delivery order

The detailed task breakdown lives in each milestone's implementation plan.

**Sequencing decision (2026-09-27): web first, Docker later.** Cloud Run jobs can't run Docker, so a test suite that needs Docker can't run on it. v1 therefore ships first for workflows whose tests don't need Docker, starting with the web repo. Support for Docker-dependent workflows comes afterwards, as a second compute backend. This works because the runner (the container, `fugaro exec`, verify, finalize) is compute-agnostic. Only the CLI's `Backend` (§3.4) and the Terraform module are Cloud Run-specific.

To keep that later step cheap:

- **Per-workflow compute is reserved.** A future `workflows.<name>.compute` field (`cloud-run` | `batch`) selects the backend per workflow. Omitting it means `cloud-run`, so existing `fugaro.yaml` files stay valid.
- **Resource limits belong to the backend.** `resources` stays `{cpu, memory}` in the core schema. Cloud Run's rules (the 1/2/4/6/8 CPU set, the 32 GiB cap) move out of `config.Validate` and into the Cloud Run backend in M4. A Batch backend brings its own limits.
- **Cloud Run specifics stay under `internal/backend/gcp`.** Runner code never assumes Cloud Run.

The milestone order is:

- **M0 — Feasibility checks, split in two.**
  - **Now, before M3:** run the Docker-dependency check (Step 0 of the M0 runbook) against the **web** repo. Web suites can depend on Docker too, for example Playwright or Cypress end-to-end tests that start a backend with docker-compose, or Testcontainers-based integration tests. Headless Chromium itself runs fine on Cloud Run if the image carries its libraries.
  - **Before server work:** run the full spike against the server repo: the Docker check, peak memory against the per-task ceiling, and warm-run timing. Its outcome decides whether the server workflow needs the Docker-capable backend (M8).
- **M1 — Runner core, local.** Config and schemas, the stage machine, the agent adapter, `fugaro verify`, the run record, `exec --local`, and the fake `claude`.
- **M2 — Git providers.** GitHub (including the App token) and Bitbucket Cloud; the finalize step. The web repo's host comes first.
- **M3 — Images.** The `web-node` base image; the derived template rendered from `image:` settings; the `dockerfile` escape hatch and its validation; `fugaro image build --local`; CI publishing. `fugaro:onboard` moves here from M7, so the web repo can be onboarded as soon as its image exists. `server-jvm` waits for the server spike.
- **M4 — GCP backend and CLI. Delivered** ([implementation plan](../plans/2026-09-27-m4-gcp-backend.md)). `run`, `ls`, `logs`, `diagnose`, `cancel`, `secrets set`/`secrets ls`, and cloud `image build`; cache restore/writeback; locks; protection against duplicate executions; the live agent-event relay (§10). Cloud Run's resource rules moved into the backend. Recovery (§4.7): `launch.json`, the launch claim, `--retry`, idempotent `--run-id`, `--batch`, and `ls --mine/--since/--batch`. Cost reporting (§10.1): the backend price table, compute cost, the `cost` breakdown in `result.json` and the PR report, and `ls` totals.
  - **The GCP resources come from a throwaway bootstrap**, `deploy/bootstrap/gcp-m4.sh`, run one confirmed step at a time ([gcp-bootstrap.md](../gcp-bootstrap.md)). It writes the local config and creates the APIs, the bucket and its lifecycle rules, the registry, `fugaro-build`, and each repository's job service account, secret bindings and job, all with the names `fugaro gcp job-spec` computes. M5's Terraform replaced it, adopting what it made; the script stays only as M5's rollback path, until it is retired.

  - **Deferred:** one-command offboarding (§8.2 describes the manual steps); `smoke: full` (the smoke is always the structural selftest, run without network), which would need the live network probe extended to `docker run`; Cloud Build logs under log isolation; an egress-restricted VPC; importing the hand-made budget; and, with the published base images (M7), an unset `base_image`, the `base` trigger doing its job, and `max_age` back at 7 days.

  - **The server spike.** Run the full M0 runbook against the server repo: the Docker-dependency check, peak memory against the per-task ceiling, and warm-run timing against an unloaded laptop. Record the results in `docs/design/m0-results.md`. The go/no-go outcome decides whether the server workflow needs the Docker-capable backend at all, or can run on Cloud Run with its Docker-dependent tests split out.
  - **A second `Backend`**, most likely Cloud Batch: Compute Engine VMs, where Docker works and larger machines are available. The alternatives, weighed with the spike's numbers, are GKE Autopilot jobs, or keeping Cloud Run and splitting out the Docker-dependent tests. It runs the same runner image with Docker available, behind the same `Backend` seam, so `run`, `ls`, `logs`, `diagnose`, `cancel`, recovery and cost reporting work unchanged. Its price table joins the §10.1 cost reporting.
  - **Its Terraform module**, alongside M5's Cloud Run module: the VM templates or node pools, service accounts and IAM with the same per-repo prefix conditions, and networking.
  - **The `server-jvm` base image:** a JDK (the `image.jdk` setting), Gradle warm-up in the derived template (the template's jdk branch is written but unreachable until this image exists), the Docker client, and a Gradle fixture for the hermetic image tests. It is published by the same `images` workflow, with the same pinning, signature checks and Trivy gate as `web-node`.
  - **Backlog.** Small items found along the way, with no earlier milestone. Each can move into an earlier milestone if it starts to matter:
    - **A pnpm Docker test.** pnpm's warm-up is covered only by the render test; add a derived-image Docker test like the npm and Yarn ones.
    - **Nightly refresh for older release lines.** The nightly `images` rebuild refreshes only the newest release tag, so an older major's `:<major>` tag stops getting patch refreshes once a second major ships. Rebuild the newest tag of each supported major.
    - **A Bitbucket CLI for the agent (optional).** On Bitbucket the runner owns PR creation and updates, and M6 puts review comments into the agent's prompt, so the agent has no `gh` equivalent. If it turns out to need one, build a small `bb` into the `fugaro` binary on top of the Bitbucket adapter, mirroring `gh`'s command shapes. Don't install a third-party CLI (supply-chain risk). Any `pr ready` it offers must not decide the run's outcome: finalize has the last word (§4.2).
    - **Self-hosted Bitbucket Data Center.** `HTTPSOrigin` keeps an SSH port when converting an origin (`ssh://host:7999` becomes `https://host:7999`), which is wrong for Data Center. v1 targets bitbucket.org and github.com only.
    - **Follow-ups from M5's reviews and live run.** None blocks M5; each can move into an earlier milestone.
      - **The pinned commit on Bitbucket:** the image template fetches the pinned commit by SHA when it has left the branch. GitHub and git's local protocol serve that; whether Bitbucket Cloud does is unverified (live check 18). If it refuses, a force-push during a build fails the build at the clone step, visibly.
      - **A persistently broken build on an active repository** is resubmitted about once a day, because the back-off counts the branch head as an input (about $0.2 a day, alerted). Consider backing off on the failed inputs only after two days.
      - **The promote race:** two builds that both pass the gate can leave `latest` on the build whose `record` write failed; if that was the check's build, the next check waits for a person.
      - **Cost provenance:** a compute-price override is validated and applied, but the cost line doesn't say the figure came from an override; add a `compute_basis` to the cost record and show it in `ls`, `diagnose` and the PR report. The runner also imports `localcfg` for the price bounds; move them next to `backend.Prices`.
      - **`fugaro init` details:** it forgets nothing about the alert channel, alert policies and budget after a `--forget` (delete them by hand, §8.2), nor the budget, log-isolation and registry-cleanup flags between runs (the guard refuses the resulting deletes, with hints); `init --repo` offers to enable Resource Manager and then stops when there is no installation; concurrent `init --repo` runs share one outputs directory and the loser fails closed; `init --repo --forget` needs a valid `fugaro.yaml` and an https origin; the disabled-API check for two repository lookups matches any `projects/` consumer instead of the target project; the readiness decisions under a disabled API are not pinned by tests; `Apply` could record a hash of the plan it showed.
      - **Operators and launchers** can list every secret's name, labels and version states in the project (no values), because `secrets ls` needs project-level list permissions; a smaller operator-only role would narrow it.
      - **Rotating a repository token** leaves the old value in any local token file; the runbook should say to update or delete local copies when a token is revoked.

## 15. Resolved and remaining questions

| SPEC §9 item | Resolution |
|---|---|
| Cloud Run resource ceilings | Checked by the server spike before server work (§14). Web workflows start on Cloud Run without it. |
| Cache invalidation policy | A daily image check that rebuilds on a trigger (§7.2), plus content-addressed GCS caches keyed on lockfiles and the base image digest. |
| Per-repo config schema | §5.1, published as a JSON Schema. |
| Bitbucket/company specifics | Confined to the `bitbucket` provider adapter and each repo's `fugaro.yaml` and secrets. |

**Resolved in M2:**

- **Bitbucket draft PRs.** The Bitbucket Cloud REST API documents a `draft` boolean on the pull request object, set on create (`POST …/pullrequests`) and update (`PUT …/pullrequests/{id}`). Both need the `pullrequest:write` scope, which a repository access token can hold. The adapter sends `draft`, checks the response, and falls back to a `[DRAFT] ` title prefix if Bitbucket ignored it. **Confirmed live (2026-09-27)** against a sandbox repository with a repository access token: `draft: true` on create gives a real draft, and `PUT {title, draft}` moves an existing PR from draft to ready and back, keeping its description and reviewers. A `PUT` is a partial update: omitted fields, `draft` included, are kept. So Bitbucket runs get real draft PRs, and the title fallback remains only as a guard for a workspace or plan that ignores `draft` ([git-providers.md](../git-providers.md#live-check-against-a-sandbox-repository)).

**Resolved in M4:**

- **Cloud Run's resource rules live in the backend.** The core schema asks only for a positive CPU count and a memory quantity. `gcp.CheckResources` applies Cloud Run's rules (§5.1), and `fugaro validate`, `fugaro image build --local` and the bootstrap's job spec report them. A second backend brings its own.
- **Cost basis semantics.** `total_usd` counts billed dollars only. A subscription (`oauth`) run's model figure is notional: it is recorded and shown, but never added to `total_usd` or to the billed part of the `ls` totals. `compute_estimated` distinguishes "not estimated" from a zero. M4 uses list prices throughout, and an unknown region prices at tier 2 so estimates err high (§10.1).
- **Duplicate executions are safe.** Cloud Run, or a double launch that slipped past the launch claim, may start two executions of one run. The first record is created with create-if-absent before the lock, so the second execution finds it, exits and writes nothing: it never overwrites `result.json` or takes the lock. The same execution spelled with a project number instead of an ID is not a duplicate, because executions are compared by (region, job, short name). The lock-held-by-the-same-run check is a defensive second line (§4.1). If a double launch does happen, every view follows `result.json`'s execution, the owner, not `launch.json`'s.

**Resolved in M5:**

- **The image rebuild policy** (SPEC §9's staleness question). Not every night, not weekly: a daily check that rebuilds when a trigger fires, with `max_age` (14 days until the base images are published) as the floor. The rationale, cost and back-off are in §7.2, and the triggers in §5.1. The default costs about $1 to $3 a month per active repository, against $6.30 for a nightly rebuild.
- **State layout.** One Terraform state per repository and one for the installation, in a GCS bucket `fugaro-tfstate-<project>` that `fugaro init` creates and Terraform never manages. The repository root takes the installation's outputs as variables, with no remote-state coupling (§8.1).
- **Registries.** One registry per repository for derived images, written only by that repository's build account, and a separate base registry, `fugaro-base`, that only operators write. A leaked build token can neither overwrite another repository's `:latest` nor the base image every repository's `credential` step runs (§6.1). The legacy `fugaro` registry stays, unwritten, for the rollback.
- **Log access.** Fugaro's job logs go to their own log bucket through a sink and are excluded from `_Default`; readers need `roles/logging.viewAccessor` on its view. In a shared project Fugaro can't take the Logs Viewer role away from anyone, so this is the enforceable form of "log access is secret access". Cloud Build logs stay in `_Default`, a recorded exception (§6.1).
