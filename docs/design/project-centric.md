## 1. Summary and recommendation

The spec asks that the **project**, not the repository, be the unit of configuration, policy, credentials and setup, and that adding a repository be lightweight: no Terraform, no confirmations. The code agrees that this is possible, and shows that **most of the weight is one mechanism**: `fugaro init --repo` copies project policy into each repository's Cloud Run job and builds per-repository cloud resources around it, so every policy change and every new teammate means re-running per-repository Terraform. The budget counters, the launch path and most of the runner are already more project-centric than the provisioning around them. Two things the first draft got wrong are corrected here and drive the shape: **sharing a job is not free of runner changes** (the runner takes its repository, slug and remote from the job's environment, not from `task.json`, §4.1) and **moving policy to the database needs a rules change, a fail-closed rule and an explicit Firebase requirement** (§5).

Recommendation, in the order that delivers value soonest:

1. **Small independent fixes first**: the four wrong flag names in budget refusals and the Anthropic key made optional (§6.1, phase 0).
2. **Take policy out of the job definition** into one project policy object read by the runner at start, with a fail-closed rule, an RTDB rules change (an owner-run rules deploy) and an enrollment allow-list that ships with it (§5, §4.3, phase 1). This ends re-running `init --repo` for changes to policy **values** (mode, caps, allowed models, prices, routing among keys already mounted). Changes to what a job **mounts** (a secret, a provider key, a named account, a launcher or operator grant) still need per-repository Terraform until phase 3 (§11).
3. **Decouple model choice from key routing** with one explicit project switch whose default stays `direct` (§6.2, phase 1).
4. **Project-scope keys by default**, a decision that reverses a ruling of the project-secrets design and so is the owner's (§6.3, phase 2).
5. **Shared project jobs** for `checkout: clone` workflows on GitHub: one Cloud Run job and one job service account per (profile, account), the runner binding its slug to the repository it clones (§4, phase 3).
6. **Enrollment as data**, migration of the owner's two installations (§4.3, §4.4, phase 4).
7. **Person-owned OAuth tokens** shared by reference, with failover in the CLI (§7, phase 5).
8. **A backing Git repository** fed by `fugaro project export`, secrets excluded (§8, phase 6).

Baked-image workflows (a repository's checkout inside its image) are inherently per repository and are the one thing the spec's hard requirement forces a ruling on (§4.4, D3). Bitbucket is first-class in phase 3 (D5): the owner's production repositories are Bitbucket, so shared jobs use a project-wide access token, after a verification task (§4.5).

## 2. What the code does today (verified)

### 2.1 The weight is in `init --repo`

- Three Terraform roots exist: installation (`fugaro init`), firebase, and **repo** (`fugaro init --repo`), state at `fugaro/repos/<slug>` (`internal/infra/workdir.go:19-23`, `repo.go:38-40`).
- Per repository the repo root creates: one Secret Manager container per logical secret with `prevent_destroy` and two operator grants each (`modules/repo/secrets.tf:4-42`); an Artifact Registry repository (`registry.tf:10-72`); a **build service account** with registry, secret, bucket and project grants (`build.tf:5-91`); a daily **check job** with an invoker grant and a paused scheduler when any workflow is baked (`check.tf:16-142`); and per workflow variant a **job service account**, bucket conditions on `runs/`, `cache/` and `locks/` **per slug**, secret grants, the **Cloud Run job** (deletion protection) and `job_runner` for every launcher (`modules/workflow/sa.tf`, `job.tf`). The golden plan for 2 workflows is **39 resources** (confirmed). Under oauth there is one variant per (workflow, named account) (`spec.go:808-821`).
- It is re-run for every repository when a launcher or operator is added (grants are per job, secret, service account and registry) and when the budget mode, per-run cap, allowed models, prices or providers change, because they are copied into each job's env (`budgetEnv`, `spec.go:659-673`, `713-752`; `upgrade` only reports the drift, `upgrade_cloud.go:162-174`).
- Confirmations: the unknown-repository gate (type `owner/name`, never satisfied by `--yes`), a prompt per missing secret, one or two Terraform applies each confirmed, `--allow-delete` for deletes and replaces, a typed project name per billable first build, and a refusal inside a coding agent (`init_repo_gate.go`, `init_review.go`). A first onboarding is roughly 15 to 30 minutes and 3 to 5 interactions (estimate).
- `image refresh` and `upgrade` already update jobs **through the Cloud Run API without Terraform** (`image_refresh_steps.go:226-260`), a precedent for API-driven job changes.

### 2.2 What the runner takes from where (the part that decides sharing)

- **Everything the repository-specific job env carries today:** `FUGARO_REMOTE` (the clone URL, computed at **deploy time** by `infra.repoURL`, `spec.go:435-441`, written to the env at `spec.go:650`), `FUGARO_GITHUB_APP_ID` (a per-repository `github_app_id`, `localcfg.go` `Repo.GitHubAppID`, `spec.go:112-113`, `656-657`), the git-secret mount, `FUGARO_MODEL_PROVIDERS` (cut down per repository, `runner/providers.go`), `FUGARO_SECRET_ENVS`, and the budget and policy variables. The runner clones from `r.d.Remote` (`cli/exec.go:67`, `runner.go:789-794`, `provision.go:30-44`).
- **The slug comes from the `FUGARO_RUN` override** (`exec.go:157`, `168`, `runstore.ParseRef`), not from `task.json`. Locks (`lockcache.go:76`), cache (`lockcache.go:188`) and the budget session (`budget_session.go:128`, `180`) key off that slug. **Nothing checks that `task.Slug(provider, spec.Repo)` equals it.** Today the per-repository job's bucket condition is what makes a mismatch fail: the job cannot read another slug's `task.json`. Repository, ref, task, workflow, account and layer do come from `task.json` (`runner.go:797-803`), and the git token is minted for `spec.Repo` (`runner.go:586`; GitHub App tokens are scoped to that repository, `gitprov/github/apptoken.go:169-192`).
- **Launchers can override any job's env today.** Every launcher holds `run.jobs.runWithOverrides` on every job (`installation/iam.tf:26-31`, `modules/workflow/job.tf:93-101`); the Cloud Run v2 API merges override env into the job's (`run-gen.go:769-778`; `args` replace, and `delayExecution` and `taskCount` are also overridable) and the runner reads nothing about the execution's overrides. By the code a launcher can launch with `FUGARO_BUDGET_MODE=off` today (no gateway, no cap). This is a **current gap**, not an inference; it is a property of the launcher role, which is a trusted role (§4.2).

### 2.3 What is already project-level

- **Budget caps.** Global caps, `--defaults` and per-repository nodes are RTDB nodes read live (`internal/budget/model.go:149-167`, `188-226`; `rules.go:341-345`). A repository with no node uses the defaults; nothing copies caps into repositories; there is no per-repository registration. The M9a policy (`per_run_usd`, `mode`, `allowed_models`, `max_run_tokens`) is the per-repository snapshot (`spec.go:713-737`); with api-key and enforce but no copied cap the run halts "set budget.per_run_usd ... and run fugaro init --repo" (`runner/gateway.go:322-327`).
- **The RTDB is optional.** `FUGARO_RTDB_URL` and `FUGARO_FIREBASE_API_KEY` are set in the job env only when the budget mode is not off (`budgetEnv`, `spec.go:713-752`; `budget_session.go:27-52`: without them "the runner is M9a's"); SECURITY.md says the mode defaults to off.
- **Tying a repository to a project.** `project:` in the default-branch `fugaro.yaml` is required and enforced by the runner (`runner/project.go:20-43`). The local config's `repos:` is a **map keyed by `owner/name`** with per-repository fields (`provider`, `base_branch`, `workflows`, `github_app_id`, `vertex`: `localcfg.go:96`, `378-395`), published into the operator-only bucket `fugaro/config.yaml`. **Job service accounts have no access to `fugaro/`** (`bucket-iam.md` §3; `names.go:363`: job prefixes are `runs`, `cache`, `locks`). Launchers are RTDB **viewers** only (`firebase/iam.tf:43-49`).

### 2.4 What is repository-bound and should not be

- **Keys.** Secret containers are per repository (`names.go:140-145`). The **Anthropic key is mandatory for every api-key run**, even when every model routes through OpenRouter, in five places: `spec.go:571-572` (mounted unconditionally; deploy blocked without a version, `readiness.go:100-107`), `agent/env.go:97-103`, `runner/gateway.go:74-76`, `internal/gateway/gateway.go:269-272` and `internal/gateway/route.go:95-97`. That is the "dummy Anthropic key". `providers` and `claude_accounts` exist **only in the owner's local config** (`localcfg.go:78-84`), are refused in the shared config (`sharedcfg.go:146-155`, for the stated reason that launchers could write the bucket) and are copied into each job.
- **Routing.** The model ID alone decides the route (`providers.go:92-99`, `route.go:142-151`); Claude is forced direct (`ClaudePatterns`, `providers.go:203-219`; `pricing.IsAlias`, `alias.go:30-43`); a Claude model has a different ID per route (`claude-sonnet-5-5` versus `anthropic/claude-sonnet-5.5`) and nothing translates between them. Routing exists only with the gateway: `stagePins` returns nil when it is off (`agentenv.go:54-57`).
- **OAuth tokens.** One secret per (repository, account), one job and service account per (repository, workflow, account), no notion of a person (`claude_accounts.go:63-85`, `spec.go:800-821`); failover only in the skill (`plugin/skills/working/reference/diagnose.md:79-97`). Per-person tokens were ruled out of scope in 0.6.5 (`named-oauth-tokens.md:15`).
- **Policy has no history and one author.** It is authoritative in RTDB, the bucket `fugaro/*`, and **a file on one laptop** (`~/.config/fugaro/projects/<name>.yaml`) holding providers, claude accounts, the budget ceiling, prices and project secrets.

### 2.5 Two budget findings

- Four refusal messages name flags that do not exist (`evaluate.go:190`, `247`; `session.go:501`, `511`: `--repo-daily`, `--repo-per-run`); the real ones are `budget set --defaults --daily` and `--defaults --per-run` (`cli/budget.go:687-691`). A plain fix.
- The global per-run cap is **not** the fallback when a repository and the defaults have none (`model.go:210-215`), although `m9-budget-and-dashboard.md:271` says it is. This is **deliberate and mirrored in the RTDB rules** (`rules.go:341-345` `fallback()` returns null so every comparison is false and the rules deny; `REPOPERRUN` at `rules.go:310-311`; the `reserved` validator, `rules.json.tmpl:28`). Changing only `model.go` breaks the rules parity test and still leaves the rules denying; making the global cap the fallback is a **fail-open-direction change to security rules** (template, emulator tests, parity test, an owner-run rules deploy). The conservative reading is that the m9 document is wrong. **Owner decision D6 (2026-10-14): change the rules and the code** so the global per-run cap is the fallback. That is a fail-open-direction change to security rules and ships as an owner-run step in phase 0: the rules template, the emulator and parity tests, then a rules deploy; the m9 design doc then says what the code does. **Implemented (2026-10-15, phase 0 item D6)**: `Caps.PerRun` is `min(repo or defaults, global)` with a side that is not set simply not bounding the run and `ok` false only when no per-run cap is set anywhere; the rules' `PERRUNOK` macro is one boolean with the same three sides, and the both-unset branch is `false`, so a database with no per-run cap at all still denies (fail closed); `Evaluate`'s refusal and `fugaro budget show` name the scope that binds (repo, default or global); the golden file is regenerated, the emulator rows are updated and the parity test's directed cases cover the fallback (the emulator half needs a JRE and runs in CI, not in the container that wrote this). The rules reach a database only through the owner's deploy (`fugaro init --firebase`, the order and a read-only verification in `docs/gcp-setup.md`, "Deploying the rules is an owner step"), which had not been run at the time of writing. **The owner ruled on 2026-10-15 to keep the both-sides form** (the review asked whether an enforcing project should instead be required to hold a global per-run cap): a repository with its own (or the default) per-run cap and no global per-run cap is bounded by its own cap alone — it used to be refused — and that is documented, accepted behavior (`docs/gcp-setup.md`, "What this deploy widens").

## 3. Principles

1. **The project is the unit.** A repository is a row: a name, an allow-list match and a slug. In the default model it carries no cloud resources of its own.
2. **Policy is data, read at start, and fails closed.** The runner reads the project policy from the database. It does **not** remove the launcher's ability to override the job env (§2.2): launchers remain trusted principals (§4.2), and the design states that plainly instead of claiming a fix.
3. **Overrides survive only if they cost nothing.** A per-repository cap is an RTDB node and survives. Anything needing per-repository infrastructure is dropped.
4. **Reuse what exists**: the budget counters, #343's project secrets, #344's retirement engine for migration, the price catalog, `report.Build` for the export, `fugaro watch --json` for a console.
5. **State the isolation actually kept.** Sharing a job removes boundaries; each is named in §4.1 and in SECURITY.md rather than argued away.

## 4. Jobs, enrollment and migration

### 4.1 One job and one job service account per (profile, account), for clone workflows

Cloud Run cannot vary the image, service account, CPU or memory per execution, so the shareable unit is "a job with these properties". A **profile** is defined at the project level: `{cpu, memory, task timeout class, secrets, allowed repositories}` on the one Fugaro base image. The installation root creates one job **and one job service account** per (profile, account). A repository's workflow selects a profile by name (`workflows.<name>.job_profile`, default `standard`; this document and the plan write `profile`, and the key that ships is `job_profile`, because `profile` already names the *project layer's* workflow template in `fugaro.yaml` — one key cannot be both selections).

**Isolation granularity is the profile.** Inside one project job every run can read every secret that job mounts, through the environment, `/proc` or the metadata server. There is **no IAM boundary between repositories sharing a job**, and no allow-list can create one: an allow-list on a project secret is only meaningful as "which profiles mount it" and "which repositories the launch check lets onto those profiles". A secret that must stay away from some repositories lives on a profile those repositories are not allowed on. **The runner enforces profile admission, not only the launch check**: before it clones or mints a token the runner reads the profile's `allow_repos` from the policy and refuses to run a repository the profile does not admit, for the (profile, account) it is actually running on (the repository picks its profile in `fugaro.yaml`, and the launch check is advisory, §4.3). The same admission is what gives §7's per-reference repository lists their effect. (This is also why §7 gives each account its own job service account: runtime fetching of any shareable token by one shared service account is rejected for the same reason.)

**`checkout: clone` is the prerequisite** (the 0.7.5 mode, gated by `cloneShipped`; the job runs `fugaro-base`, the runner clones and installs the tools `mise.toml` names). **New runner behavior is required**, not just a shared job:

1. The runner computes the clone URL from `task.json`'s repository, the provider and the project policy (a custom clone URL lives in the policy), instead of `FUGARO_REMOTE` from the job env. The provider comes from `task.json`'s repository reference, the way `task.Slug(provider, repo)` takes it (the plan confirms where it is carried).
2. **The slug is bound:** the runner refuses to start unless `slug == task.Slug(provider, spec.Repo)` and the repository is enrolled (§4.3). The check runs **before** it mints a git token, takes the budget lease or reads anything. Today only the per-repository bucket condition stands in for this.
3. The GitHub App ID and key become project policy (one App per project, §4.5); `FUGARO_MODEL_PROVIDERS` and `FUGARO_SECRET_ENVS` per repository disappear in favor of the policy and the profile's mounts; the job's `workflows.<n>.secrets` per repository (§6.3) are not supported on shared jobs.

What this changes, honestly:

| Today | Project-centric | What is lost |
|---|---|---|
| Job and job service account per (repo, workflow, account) | Job and service account per (profile, account) | Per-repository service accounts and per-repository GitHub Apps: a project with several Apps cannot share jobs (SECURITY.md tells users to use one App per repository if that matters; D5). |
| Bucket conditions per slug on `runs/`, `cache/`, `locks/` | One condition on each prefix | **A regression of a documented 0.7.0 property.** SECURITY.md lists "poison `cache/`; forge or steal `locks/`" among what 0.7.0 removed. A run, which is an untrusted agent unlike a launcher, could poison another repository's cache (cross-repository code execution on its next run), forge or steal locks, and rewrite another repository's queued `task.json`. With one GitHub App this is not worse than the App key's reach, but it is not "launchers can already write `runs/`": launchers are people, runs are not (D4). |
| Secret containers and grants per repository | Project secrets granted to the project's job service accounts | Per-repository secret access (§6.3). |
| Registry, build service account, check job and scheduler per repository | None for clone repositories (`spec.go:822-829`: clone repositories need no check); one project-level base-image check | Nothing. Clone repositories get an inert registry today (`checkout.md:81`). |
| Launcher and operator grants per job, secret and registry | Per project job | Nothing: every launcher already holds every job. |
| Policy in each job's env | Policy read at start | The env-copy snapshot; see §5 for what replaces it. |

Unchanged and safe to share: the history job reads the whole bucket (`history.tf:160-169`), logs are selected by job and execution name (`logs.go:193-194`), `max_parallel` counts `fugaro-` jobs (`run.go:222`). **Every caller of the job naming changes**: `Launch` (`run.go:107`), logs, cancel and `CheckRunExecution` (`run.go:92-101`), which must compare the execution's own `FUGARO_RUN` (already read from the execution at `run.go:389-390`) with the run.

**Update 2026-10-16 — what "unchanged and safe to share" means once a job is shared (plan Task 3.4).** The two counts above are unchanged *in what they read*, and neither may be read as "the job names the run" any more. `fugaro logs` still filters by the job **and** the execution name, and both clauses are needed: the job clause is what keeps one execution's read from scanning every run of the profile, and the execution name (`labels."run.googleapis.com/execution_name"`, the name `launch.json` records) is what separates the several repositories' runs that one project job now has. `max_parallel` still lists `fugaro-` jobs at the same horizon, but its count is of **executions, not jobs** — `internal/backend/gcp`'s `List` appends one `Execution` per execution and `checkMaxParallelFor` counts those, so a shared job's ten active runs count as ten, exactly as ten per-repository jobs' would; the horizon's `LongestTaskTimeout` likewise takes the longest timeout among the region's `fugaro-` jobs, which includes every project job (`fugaro-p-…` carries the same `fugaro-` prefix). And the run's own `FUGARO_RUN` — not the job name — is what `CheckRunExecution` compares, because on a shared job the name says nothing about whose execution it is. An execution Cloud Run no longer has reports no `FUGARO_RUN` at all, so the views that read logs (`fugaro logs`, `fugaro diagnose`) refuse to follow it rather than trust the run's own objects for it (its logs can outlive it, and may be another repository's); only `cancel` still tolerates it, having nothing to act on. Cloud Run and the Fugaro log bucket both keep 30 days, so a run that has lost its execution has lost its logs too.

**What Task 3.2 builds, and what it defers (its review, 2026-10-16).** `fugaro init` deploys one job and one job service account per profile from the local config (`internal/infra/projectjobs.go`, `deploy/terraform/gcp/modules/project/`), with three limits the code enforces:

- **GitHub only.** No shared job serves a `provider: bitbucket` profile, and no shared job mounts `bitbucket-token`: the owner ruled on 2026-10-15 that a Bitbucket credential cannot be scoped to one project's repositories, so Bitbucket stays per-repository (D5 as amended). A Bitbucket profile is **not** refused — the policy admits one and a Bitbucket repository's workflow may select it, and the runner only requires a selected profile to be defined — `fugaro init` simply deploys no job for it (`internal/infra`'s `SharedJobProvider`), and a launch of a repository selecting it keeps the per-repository job it has always had (`internal/cli`'s `launchProjectJobFor` asks the same predicate, so the job a launch computes is always a job that was deployed).
- **No Claude OAuth token on a shared job.** `claude-oauth-token` and every named account's token are refused (D2: person-owned, not swept into project scope; a shared job cannot honour an account's `allow_data_to`). The account axis of a job's name is therefore empty until phase 5 decides how an account reaches a shared job; an installation on `auth: oauth` has no usable shared job until then.
- **No retirement of a project job.** The job has deletion protection and the module has no `allow_job_delete` (unlike `modules/workflow/job.tf`). A removed profile, or one whose provider or secrets change its job name, plans the old job's delete, and `fugaro init` refuses that plan whatever `--allow-delete` names (`infra.RefuseProjectJobDeletes`), because an apply would remove the launchers' grants and then fail on the protection. Restore the profile; retirement is deferred to a later task.

**Service-account count (Check 52 U4, run by the owner on 2026-10-16).** The sandbox project held 10 service accounts; Cloud Quotas reported `ServiceAccountsPerProject` as `-1` (read as "no limit", UNVERIFIED) and a creation rate of 30 per minute. A project job adds one account per profile, so neither number constrains it; Fugaro neither reads nor enforces either one, and an `init` that creates more than 30 accounts at once would meet the rate limit as an apply error to rerun.

### 4.2 Launchers are trusted; the override surface

A shared job cannot carry per-repository policy in its env, and **launchers can override any job's env** (§2.2). The design does not claim to close that. It states the boundary: a launcher is a trusted principal who can already start any run and spend the budget; the money and data limits that matter are enforced in the gateway and the rules against the run's own token. The budget token deliberately does not travel as an override (`m9-budget-and-dashboard.md:582`). **What stays in env after §5**: `FUGARO_RUN`, the timeout, and the pointer to the policy (`FUGARO_RTDB_URL`, `FUGARO_PROJECT`, `FUGARO_BUCKET`), all overridable by a launcher. Owner decision **D10**: (a) accept it and document it in SECURITY.md (recommended for now), or (b) narrow the launcher role to `run.jobs.run` and carry `FUGARO_RUN` through a claim object found by execution name, plus a runner check of the execution's own overrides (a larger change, UNVERIFIED: whether Cloud Run exposes an execution's overrides to the container; `run.go:385-390` already reads the execution's own environment to find `FUGARO_RUN`, and whether that exposes the overrides is part of the check). One live check should confirm the current gap before SECURITY.md states it.

### 4.3 Enrollment (open question 2): an allow-list in the policy, checked by the runner

**Decision.** A repository is tied to a project by three things, all data:

1. Its default-branch `fugaro.yaml` names the project (`project:`), already enforced by the runner.
2. The project's **allow-list**, a new policy key `allow_repos` (globs such as `acme/*`, `acme/service-*`; **not** the existing `repos:` map, which is keyed by exact name with per-repository fields). It lives in the policy object the runner can read (§5), **not** in the bucket (job accounts cannot read `fugaro/`). **Default empty means no repository is enrolled**; `["*"]` is an explicit choice. It is checked by the runner before it mints a token or takes a lease (§4.1) and by `fugaro run` before launch; the CLI check is **advisory**, because a launcher can call `jobs.run` directly (§4.2).
3. Provider-side access: the GitHub App installed on the repository.

**No registration record.** The first draft proposed an RTDB registration written at first use; no principal can write it (launchers are viewers, run tokens write only their own `runs/`, `spend/` and `agents/` nodes). The set of repositories that have run is already derivable from the nodes the runner writes (the bucket's `runs/<slug>/` prefix and Firestore `spendDaily` are the durable sources; the RTDB run ledger, `agents/` registry and counters are pruned after about 8 days), so **`fugaro project repos` lists them from there** with the allow-list. **Discovery is optional and explicit**: `fugaro project sync` lists the GitHub App's installed repositories and offers to add the missing ones to the allow-list (a data write by an operator, confirmed once per batch); `fugaro project add-repo owner/name` adds one.

**Ordering.** The allow-list and the runner's checks ship in **phase 1** with the policy object and are required by phase 3's shared jobs from the first day. There is never a state in which a shared job serves a repository that has not been allowed.

### 4.4 Baked workflows (the hard requirement) and migration (open question 3)

A **baked** workflow puts the repository's checkout and warmed dependencies into the job image and cannot be shared. The spec's hard requirement says to drop per-repository overrides rather than keep per-repository Terraform. Recommendation: phases 3 and 4 support clone workflows only; baked workflows stay on the existing per-repository path, unchanged, until phase 4 ends, and are then **dropped** (the base image carries every runtime, and `checkout: clone` plus `mise install` costs seconds: Check 41 measured a 10.5 s median cold start) or **re-implemented as per-repository jobs created through the Cloud Run API**, adopted by labels, with no Terraform (the `image refresh` precedent). Owner decision D3.

**Migration with the no-backward-compat rule.** Until release only the owner's **two installations** exist: `fugaro` and `belong`. Installation `fugaro` holds `dimipaun/fugaro` (GitHub, baked, with a check job), `edgeappinc/fugarosandbox` (Bitbucket, baked, no check job) and `dimipaun/fugarosandbox` (Bitbucket, listed in the local config with no workdir on this machine: stale or onboarded elsewhere, UNVERIFIED). Installation `belong` holds the production repositories `edgeappinc/edgeserver` and `edgeappinc/edgeweb` (both Bitbucket, baked). **No agent ever touches `belong`**: every live step of this design is owner-run on `fugaro` and a sandbox repository, and moving `belong` is the owner's own work after the model is proven on `fugaro` (D2 changes `secrets set` there too, and D3 drops baked workflows, which both production repositories use). Migration is "re-run init under the new model": deploy the project jobs, switch launches, then retire each repository's root. [config-transitions.md](config-transitions.md)'s retirement engine covers a changed `fugaro.yaml`, **not the retirement of a whole repository root** with `prevent_destroy` secret containers and a registry (its plan Tasks 1 to 5 do not cover full offboarding); the plan adds a "retire a repository root" task on top of it (state removal, then the label-driven delete of the old jobs, service accounts, grants and registries). **Secret values cannot be carried over**: no person can read them (`secrets.tf:31-42`), so the project-scope secrets are re-entered. With Bitbucket first-class in phase 3 (D5), the Bitbucket sandbox (`edgeappinc/fugarosandbox`) is the live-check repository for phases 3 and 4; a GitHub-specific check also needs a GitHub repository, and `dimipaun/fugarosandbox` is Bitbucket, so one would have to be created.

### 4.5 Providers

**GitHub:** one App, one App ID and key as project policy, a token minted per repository by the runner. A project that uses several Apps cannot share jobs. **Bitbucket (D5: in phase 3):** today each repository has its own access token (`bitbucket-token`, shared across repositories by #343's project scope where the owner chooses, and never by D2's default: the owner ruled on 2026-10-15 that a Bitbucket credential stays per repository, §6.3). Shared jobs need a project-wide credential: a Bitbucket workspace or project access token, whose scoping is UNVERIFIED and is the **first task of phase 3** (verify it can read and push to exactly the project's repositories, and what it can be used for besides). A runtime fetch by secret-name prefix with an IAM condition (UNVERIFIED) is the fallback and reintroduces the shared-service-account exposure of §4.1. If the verification fails, Bitbucket projects stay on the per-repository path and the owner is told before phase 3 starts.

## 5. Policy as data (phase 1)

**Decision.** One **project policy object** in RTDB, `config/policy`, readable by run tokens and writable only by admins (IAM-only writes, as for the caps: the rules grant no client write to `config/*`, `rules.json.tmpl:3-21`, `firebase/iam.tf`). Three corrections to the first draft:

1. **Firebase becomes mandatory in project-centric mode** (D11). Today the runner talks to RTDB only when the budget mode is not off (§2.3), and the mode is itself part of the policy being moved, which is circular. In project-centric mode every installation has Firebase and the budget backend on; an installation that wants budget mode off stays on the per-repository path, which makes **a permanent second code path** for budget-off installations. This is a decision, not a detail.
2. **The RTDB rules need a read rule**: `config/policy` is not readable by a run token under the current rules (child reads exist only for `caps/global`, `caps/defaults`, `caps/repos/$slug`, `limits`, `mode`, `kill/*`). **RTDB read grants cascade to children**, so a `TOKEN` read on `config/policy` itself would make every child readable by every run token and defeat the narrowing below; the rule must be per child, the way `config/caps` works: `config/policy/shared` readable by a run token, `config/policy/repos/$slug` readable only for the token's own slug, and an admin-only `config/admin`. The new nodes need emulator and parity tests and an **owner-run rules deploy**. Because every run token can read it (and a prompt-injected agent can take the token through `/proc`), **the readable node holds only what the runner needs and nothing personal**: no emails, no account owners; repository-specific parts sit under `$slug` nodes the way `caps/repos/$slug` does. Admin-only metadata (owners, who set what) lives in an admin-only `config/admin` node and in the export.
3. **The runner fails closed.** `resolvePolicy` (`runner/policy.go:63-107`) treats the ceiling as optional today: an empty mode, nil `AllowedModels` and no cap constrain nothing. In project-centric mode a **missing or unreadable policy halts the run** with a message that says which node it could not read; it never falls back to an empty ceiling (which would be less constrained than today's env copy).

**What "project-centric mode" is, and how existing runs keep working.** The mode is **the existence of `config/policy/shared`** (`fugaro project policy publish` creates it; the runner tests that child, because a read of the parent is denied under the per-child rules), not a flag in the job env that a launcher could clear. **The RTDB URL must reach every job**: `budgetEnv` (`spec.go:736-750`) writes `FUGARO_RTDB_URL` only when the **deploy-time** budget mode is not off, so a job deployed with the mode off never reads the policy. Phase 1 changes `budgetEnv` to write the RTDB URL whenever Firebase is configured; adopting it costs one `init --repo` per repository plus a runner image rollout, in the order **rules deploy, runner rollout, `policy publish`**. This is D11's mechanism. When RTDB is configured and the node is **absent**, the runner behaves exactly as today (policy from the job env, the per-repository path), so nothing changes for an installation that has not published a policy; when the node **exists**, it governs, and a node that exists but cannot be read or parsed halts the run. `policy publish` **seeds `allow_repos` from the local config's `repos:` map (exact names) by default**, so publishing a policy never un-enrolls a repository that runs today; globs are added explicitly.

**Content.** What is copied into jobs and the local file today: the M9a policy (`mode`, `per_run_usd`, `allowed_models`, `max_run_tokens`), providers (name, base URL, auth style, the **secret name, never a value**, models, `allow_data_to`, `route_fee_pct`, and from the price catalog `require_zdr` and `price_policy`), price overrides (**the history job reads them from env today and moves with them**, `m9-budget-and-dashboard.md:315`), routing (§6.2), the claude-account definitions without owner identity, profiles (§4.1) and `allow_repos` (§4.3). **Two per-run caps exist** (the M9a `per_run_usd` and the RTDB `config/caps/*` per-run); the policy keeps `per_run_usd` as a ceiling the caps can only tighten, and the plan consolidates the messages so a user sees one. The shared-config restriction on `providers` and `claude_accounts` (§2.4) is **not lifted**: policy goes to RTDB, and a second carrier would drift; that restriction's current validity after 0.7.0 is for the owner to revisit separately.

`fugaro project policy publish` writes the policy from the operator's file (and `fugaro project show` prints the effective project: caps, defaults, policy, allow-list, repositories seen); the local operator file shrinks toward identity, endpoints and caches. Policy gets history through the export (§8).

**Budget, as the spec asks, with the commands that already exist.** `budget set --global` is the overall project cap; `--defaults` is the default per-repository cap, applying to every repository including ones never configured; `--repo` is a per-repository override, kept because it is an RTDB node and costs nothing. **Open question 1 resolved: the only per-repository overrides that survive are the cap and the kill switches**; everything needing per-repository infrastructure is dropped.

## 6. Keys and routing

### 6.1 Neither key mandatory (phase 0)

Mount `anthropic-api-key` whenever the secret has a version (a fact at init time about data, not about policy, so flipping the routing switch never needs Terraform); make the gateway's Anthropic upstream optional and refuse a direct Claude call with a clear message when there is no key; drop the demands at the five sites in §2.4 and the readiness block. Independent of everything else.

### 6.2 Model choice decoupled from key routing (phase 1)

The model and the route become two settings. A route entry in the project policy lists the models it serves, and a stage's pin names a model; the route is resolved from policy, not from the ID alone. The spec's default (Anthropic models go direct when an Anthropic key exists, else through OpenRouter; or one OpenRouter key for everything) is expressed as a project setting **`routing.claude: direct | openrouter | auto`**. Two decisions, split because the first draft hid the bigger one inside the smaller:

- **D1a.** The merged ruling ([mixed-credentials.md](mixed-credentials.md) §4, §8) requires **one explicit `anthropic/<id>` per route entry, never a pattern**, in the local operator config or the shared project layer, never in a repository's `fugaro.yaml`. A switch that covers every Claude model is pattern-like, and delivering it through the RTDB policy changes where it lives. This design keeps both properties: the switch carries an **explicit list of Claude IDs** (`routing.claude: {via: openrouter, models: [claude-sonnet-5-5, ...]}`), written by the operator in the local operator config or the project layer and only **delivered** to the runner through the policy; a repository can never write it. Do you accept the policy object as the delivery path and the explicit list as the opt-in? Recommendation: yes. **The switch supersedes the layer's key when it ships:** `claude_models` (the senior-reviewer plan's Task 7, PR #397) is the interim path — the same explicit list, written as a top-level key of the shared project layer and merged into the run's own route table on every launch — and nothing in that plan removes it; when D1a's phase 1b lands, the list lives in the policy object instead.
- **D1b.** What does an **absent** switch mean? Recommendation: **`direct`, today's behavior**; `openrouter` and `auto` must be written. The spec's "sensible default" (key-presence driven) conflicts with the merged ruling that "with no such entry ... everything is refused"; the owner rules once. Safeguard that is real, not nominal: `openrouter` and `auto` resolve to a provider **only when its `allow_data_to` is written**, as a list or the explicit `["*"]`. Under #343's rule an absent `allow_data_to` already means every repository, so the safeguard must require it to be written; `fugaro validate` prints the resolution (or says it cannot resolve it offline, §11), and a project with no Anthropic key and Claude pinned fails validation with a message that names `routing.claude: openrouter`.

Routing exists only with the gateway (`agentenv.go:54-57`), so the switch means nothing with the budget off; D11 makes that the mode of project-centric installations. **IDs need a map**: a canonical Claude ID has a different ID per route, the gateway never rewrites bodies (`provider-price-catalog.md:14`), so the translation is applied where pins are rendered (`agentenv.go:54-77`), in prices and in records: a canonical-to-route map carried by the price catalog rows. This is the one new piece with no existing code, and the cache-marker behavior of Claude through OpenRouter is unmeasured and stays a live-check item. PR #359's phase 2 (the `anthropic/<id>` claim) is the mechanism; extend it with the switch rather than replace it. **Corrected 2026-10-15: that parenthetical used to say `IsAlias(model, claimed)`, which is the mechanism #359's plan vetoed.** `IsAlias` keeps its signature and the price package stays claim-blind: it accepts a well-formed `anthropic/<id>` as a real model ID (`internal/pricing/alias.go`, where `IsProviderModelID` exports the grammar), and the gate on **pinning** is `internal/config`'s (`CheckClaudeClaim` next to `CheckModelPattern`, and `CheckProviderPolicy`, which asks its own providers map whether a route claims the ID). No claimed set is computed, stored or passed, so no `IsAlias` call site changed — the five a claimed-set parameter would have threaded (`internal/config/pins.go:42`, `internal/config/providers.go:559`, `internal/config/validate.go:534`, `internal/localcfg/localcfg.go:222`, `internal/pricing/overrides.go:245`) stay exactly as they are, as do `Table.With` and `ParseOverrides`, and so do the three other non-test callers, which price the catalog rather than a pin and had no claimed set to take: `internal/pricing/catalog_apply.go:111` and `:131` (the built-in catalog's own keys), and `internal/pricing/catalog/gencatalog/main.go:360` (the generator's allowlist).

**The switch supersedes the interim path when it ships.** D1a's `routing.claude` carries an explicit list of Claude IDs, operator-written and never writable by a repository: that is the same shape as the claim PR #387 ships now (one explicit `anthropic/<id>` per route entry in the operator config, the entry itself the whole permission, `config.CheckClaudeClaim`), delivered a different way — through the policy rather than through the route's `models`. So the route entry is the interim path, the switch is where it goes, and nothing in #359's plan removes the route entry: the switch is **phase 1b of [§11 (Phases)](#11-phases)**, the line inside phase 1's bullet; the two things it was to land after have since merged — the price catalog (#361) and #359's phase 2, the opt-in (its claim rule and price half in #387, its end-to-end run in #394) — and the last thing it waited on, the plan's layer half (Task 7, #397), is the PR this text arrives with, so the wait is over.

### 6.3 Project-scope keys (phase 2)

[project-secrets.md](project-secrets.md) (PR #343) is the foundation: an installation-level container, `fugaro secrets set --project-wide`, a repository copy that wins over the project copy, and the §3a rule for provider keys. What #343 allows today: the four reserved names (`anthropic-api-key` and the git credential among them) can be project-scoped through `project_secrets:` **with an explicit, non-empty `allow_data_to`**; what it forbids is a reserved secret **reaching a repository the owner did not opt in** ("the DEFAULT must be safe: nothing shared until the owner says so", §3(b)).

**Decision D2 reverses that ruling, and says so**: the spec wants inheritance by default, so `fugaro secrets set` without `--repo` stores at project scope and a project-scope key reaches every enrolled repository on the profiles that mount it, including the reserved names, with no per-name allow-list. The owner stated the default-safe rule; D2 is a change of it, not an extension. With §4.1 in mind the doc says plainly: **inside a shared job a project secret has no IAM boundary between repositories** (the profile is the boundary, §4.1), and `workflows.<n>.secrets` (repository-specific application secrets) cannot be shared across a job's mounts: they become named project secrets mounted on a profile, or stay on the per-repository path. The data-policy gate for providers (`allow_data_to`, enforced by the gateway at runtime) is unaffected and stays a real control: it decides which repositories' code the gateway may route to a provider, and it does **not** keep the key out of a shared job's environment. D2 covers API keys and the git credential; `claude-oauth-token` secrets are person-owned (§7) and are not swept into project scope.

**The owner ruled on 2026-10-15 that the sweep stops at the Bitbucket credential** (Task 2.1's implementation, round 2): `bitbucket-token` is a repository access token, issued for one repository and usable for no other (docs/git-providers.md), so a project-wide copy hands every repository the first one's token, which authenticates none of them — the first repository's `init --repo` stored it project-wide, later ones read the name as covered and were never asked, and their runs failed. `fugaro secrets set bitbucket-token` and init's secrets stage therefore always store the repository's own copy, and the project-wide store is refused for it unless the owner's local config carries an explicit `project_secrets.bitbucket-token` allow-list, which is only right for a credential that really does serve several repositories (§4.5's phase 3 verification is what would establish one). The GitHub App key stays swept in: one App serves a team's repositories by design.

## 7. OAuth tokens (phase 5)

Today tokens are per (repository, account) with a job per (repository, workflow, account) and failover only in the skill. The spec asks for personal ownership, individual or project registration, never repository level, with a project-level token as a reference to an individual's token, and failover.

**Decision.**

- **Storage.** One Secret Manager secret per (person, account) in the project's GCP project (flat IDs and per-secret grants work regardless of the Terraform root, `project-secrets.md:18`). The owner is granted `secretVersionAdder` and `viewer` on that secret only, never `setIamPolicy`. **Granting the project's job service account `secretAccessor` on a person's secret needs `setIamPolicy`, so it is an operator step**, performed when the reference is accepted.
- **Reference.** A record `{account, owner, secret ID, allowed profiles/repositories}` in the policy, writable only by operators; the owner's identity sits in the admin-only node, not the run-readable one (§5). It holds no value. `fugaro accounts share <name>` proposes it after the owner confirms; an operator accepts it; the owner can retire it.
- **Mounting.** A secret env var is fixed in the job definition, so a shared account means one project job and **one job service account per (profile, account)**, which keeps each person's token readable only by the runs that use that account. A new shared account therefore means a new job per profile: an installation apply, or an API-created job (the `image refresh` precedent); the plan picks one given the "no Terraform per addition" goal. The alternative (the runner fetches the token by name at boot with one shared service account) is rejected for the §4.1 reason.
- **Failover.** Move the skill's logic into `fugaro run`: when a run ends on a usage limit, retry on the next account, the launcher's own accounts first then shared ones, with the tried-list of the existing design. The launcher's identity is already recorded (`runstore/launch.go:12-29`, the registry's `requestedBy`). Claude Code's usage-limit text is UNVERIFIED (U4 of the named-accounts design).
- **Scope of "individual level".** The spec may mean tokens an individual registers once across projects; this design scopes a person's secret to one GCP project. Cross-project sharing is out of scope and flagged for the owner (D12).
- **No repository level.** The per-repository copies, `secrets set claude-oauth-token-* --repo` and the init prompts go away with the per-repository path; `agent.oauth_token` stays as a preference.

Residual risks stated: a project job that mounts several people's tokens widens the `/proc` and metadata-server exposure of [mixed-credentials.md](mixed-credentials.md) §6 to every repository sharing that job; OAuth spend is notional and no per-person budget exists (`runstore/cost.go:62-70`). PR #363 (the OAuth reviewer stage) multiplies per-repository variant jobs and should wait for this phase (D9).

## 8. The backing Git repository (phase 6; open questions 4 and 5)

A project may name a **backing location**: a Git repository, a **folder inside one**, and a branch. It is a record, not a unit of execution (it is not enrolled and never runs). The folder case is the owner's own requirement (2026-10-15): *"we may not necessarily want a repository dedicated to that information. Maybe somebody has a mono repo and would like to save that information under a folder in that repository, called maybe fugaro-project."* The location is therefore **three settings, not one** — the shape `routing.claude` already has (D1a: a thing that is not a scalar is not a scalar) — carried as one **`backing` object** in the policy:

| Setting | Default | Meaning |
|---|---|---|
| `repo` | absent — the feature is off | the repository: canonical `provider/owner/name` (the same spelling `allow_repos` and the runner's slug use), **or** an absolute `file://` URL naming a repository on the operator's own machine. The second form exists for exactly one purpose — a rehearsal or a live check with no host, no account and no workspace to write in (Check 61) — and the export says in its own output that a `file://` location is local and not shareable |
| `path` | `fugaro-project/` | the folder **inside** that repository — the owner's own name for it. The **repository root** is the dedicated-repository case, written `""` or `"."` |
| `branch` | `fugaro-project` | the branch the export commits to: **never the monorepo's own `main`** unless the owner writes it there, because a monorepo's `main` is usually protected and reviewed, and an export that lands on it puts a machine's commit in front of a reviewer |

`fugaro project export [--push]` writes, reusing `report.Build` and the existing readers. **Every item below lands under `path`**:

- `README.md`: what this folder is, who writes it (`fugaro project export [--push]`), what it deliberately does not hold (no secret value, and no person's address unless `--with-people`), and the repository and branch it belongs to. In a monorepo the folder sits in the middle of someone else's code, and the file that says what it is travels with it;
- `policy/`: RTDB `config/*` (caps, defaults, mode, limits, kill switches with when and why) and the policy object;
- `config/`: the bucket's shared config, project layer and recipes verbatim;
- `config/operator.yaml`: the operator's local config without identity and endpoints, secrets by **name** only. The most valuable item, because it exists nowhere else today;
- `inventory/`: secrets metadata (Secret Manager list; launchers already hold it, `iam.tf:15-19`), enrolled repositories and project jobs;
- `spend/`: Firestore `spendDaily` (final days only, so history is never rewritten) and per-run CSVs from `result.json`. **People's emails** (`byPerson` spend, who set a kill switch) are committed to a git repository: they are omitted by default (a hash is reversible with a dictionary of the team's addresses), with an opt-in to keep them.

Not exported: Terraform state (rebuildable, may hold sensitive values) and transcripts (large, may hold code). **What the export lets you reconstruct** is the project's configuration and policy, and an account of spend over time; it does **not** make the project reconstructable end to end: secret values must be re-entered (no person can read them), and Firestore history, run records, the GitHub App and the Firebase project itself are not in it.

**Everything else in the repository is somebody else's.** An export writes only under `path` and stages only `path`: no other file is rewritten, reformatted, re-sorted or tidied, and the phase's own test fails if a single file outside the folder changes or is staged (plan Task 6.2, and Check 61 in Task 6.5). In the dedicated-repository case the folder *is* the root and the two statements are the same one; in the monorepo case the difference is the whole point, because the tree beside the folder is another team's product and the export is not a migration of it.

**What `path` may be — the grammar, written once, in two halves.** The string half is a rule about the setting; the filesystem half is a rule about what the fetched tree may contain. Both are refusals at write time, never sanitisation: an export never "cleans up" a `path` and then uses it, because a normalised path the owner did not write is a folder the owner did not name. **An earlier revision of §8 said "no path that does not end in `/`" while also allowing `""` and `"."` as the root, which is a contradiction rather than a rule** — so the grammar is stated here once and the plan and the code both point at it.

*The string half* — a `path` is accepted only if it is one of exactly two shapes. Either it is the **repository root**, written exactly `""` or `"."` (the dedicated-repository case), or it is a **folder path** that satisfies all of these, in order:

1. **relative** — no leading `/`, no drive letter, no UNC prefix, no `~`;
2. **`/` is the only separator** — never `\`, on any platform;
3. **no empty segment** — never `//`, and never a trailing double slash;
4. **no `.` segment and no `..` segment**, as a whole segment anywhere (`./a/`, `a/./`, `a/../b/`, `../`): the path is already normalised or it is refused;
5. **ends in `/`** — a folder path names a folder, and the trailing slash is the whole difference between the folder `a/b/` and a file called `b`;
6. **valid UTF-8, no NUL and no newline**;
7. **no `.git` segment in any case** — `.git/`, `a/.git/`, `a/.GIT/` and `a/.Git/` are all refused, because an export whose own folder is a repository's object store is a way to corrupt that repository, and on a case-insensitive filesystem the case is not a difference at all.

| written | accepted? | why |
|---|---|---|
| `fugaro-project/` | yes | the default |
| `""`, `"."` | yes | the repository root — the dedicated-repository case, and the only two spellings of it |
| `engineering/fugaro-project/` | yes | any depth, as long as the seven rules hold |
| `fugaro-project` | no | rule 5 — without the slash, the setting may name a file |
| `/fugaro-project/`, `~/fugaro-project/` | no | rule 1 |
| `fugaro-project//`, `a//b/` | no | rule 3 |
| `./fugaro-project/`, `a/../fugaro-project/`, `../fugaro-project/` | no | rule 4 — refused, not normalised |
| `fugaro-project\.git\` | no | rule 2 |
| `.git/`, `fugaro-project/.git/`, `fugaro-project/.GIT/` | no | rule 7 |

*The filesystem half* — the string half cannot see the tree, so the push re-checks `path` against what it fetched, and refuses in two more cases: a segment of `path` that resolves through a **symlink** (a committed symlink where the export expects a folder, or one that points out of the working tree — the export writes through the working tree and never follows a link out of it), and a **case-variant collision** on the fetched tree (two entries under `path` that differ only in case, which cannot both be checked out on macOS, and a `.git` entry spelled differently from the one `path` names). The first half lives beside `validRouting` in `internal/projectpolicy` and is what the CLI refuses at publish time; the second lives in the export and is what `--push` refuses after the fetch. **`TestBackingPathGrammar` carries one row per line of the table above and the plan lists the three filesystem cases as their own tests** (Task 6.2) — the reason both halves are tested rather than argued is that the string half is the one a reader assumes is sufficient.

**Concurrency: fetch, commit on the fetched tip, push plainly — never force.** Every push starts by fetching `branch`. The export keeps no local history of its own, so "rebase onto the branch" and "create the commit" are the same operation: the tree is written and committed on the fetched tip, as one commit. If someone else changed a file **under `path`** since the last export, the branch cannot be moved forward without overwriting them and the export **fails loudly, naming the paths**, rather than resolving it by force. The push itself is a plain `git push` — no `--force`, no `--force-with-lease`, no `+` refspec: a branch that moves between the fetch and the push makes the push be *rejected*, and the export reports the divergence and stops. **`gitops.Repo.Push` must not be reused for this**: it is forced **under a lease** by design because a run's own branch may be amended and rebased (`gitops.go:594-598`), and it refuses every branch outside `fugaro/` (`checkRunBranch`, `:664-672`) — which is itself the reason the default branch is *not* inside the runner's own prefix. What is reused from `internal/gitops` is `noHooks` (`:179`, so a cloned repository's own hooks never run) and the fixed identity below. **The credential is the operator's own, never the runner's.** `fugaro project export --push` is an operator action run from the operator's machine, and it authenticates with the local git credentials that machine already holds for the repository's host — the SSH agent, the credential helper, or `gh auth` — exactly as a `git push` typed in that shell would. It does **not** read the runner's git secret: that secret is minted for a run and **no person can read it**, so a manual export could not use it even if it wanted to — and it is the wrong shape anyway, because the export's authority should be the operator's own, inspectable credential rather than a cloud credential the operator cannot see (the same reason `config/operator.yaml` is exported without identity and endpoints). The push goes to the host the `repo` setting names (`provider/owner/name`, the spelling `allow_repos` and `task.Slug` already use; the supported providers are the ones `docs/git-providers.md` lists), and nothing is inferred from a URL — the provider is the one the setting writes, and `file://` is the one non-provider form, which needs no credential at all. The **scheduled** export is the one that will need a machine credential — a deploy key or App token stored as a project secret — and that is the deferred half of D7, not this one.

**The detector: how "somebody changed a file under `path`" is actually *known*.** The paragraph above states the rule — an export fails loudly rather than overwriting somebody's edit — and an earlier revision of this design stated the rule with **no way to detect it**, which would have made the plan's conflict test unwritable: an export that regenerates the whole folder and keeps no history of its own cannot ask the branch, because a folder the last export wrote and a folder a person edited look identical to a fetch, and "diff the folder against the last export" needs a last export that does not exist. So the export writes its own record, **inside the folder it owns**: a **marker file**, `<path>.fugaro-export.json` (`.fugaro-export.json` in the repository-root case), holding the export's `checked_at` and the **git tree hash of everything the export wrote under `path`, the marker itself excluded** — the exclusion is not a detail, since a file cannot hash itself, and the marker is the one path under `path` the export rewrites unconditionally. The push then runs as: fetch `branch` → read `path` from the fetched tip → compute that same tree hash from the fetched commit → compare. **The recipe is written once, here, and both sides use it**, because the obvious one is wrong: `git rev-parse <tip>:<path>` names the folder's tree *as committed*, which **contains the marker**, so it could never equal a value that excludes the marker — every export would refuse, forever, and the refusal would look like somebody else's edit. The folder's hash, marker excluded, is the tree built from the folder's entries without the marker's:

```sh
# <tree>:<path> is the folder at the fetched tip (or at the export's own commit)
git ls-tree <tip>:<path> | sed -e '/[[:space:]]\.fugaro-export\.json$/d' | git mktree
```

`git ls-tree` prints one entry per line (`<mode> <type> <sha>\t<name>`), the `sed` drops the marker's own line, and `git mktree` builds the tree object from the rest — normalising the entry order, so the hash depends on the entries and not on how they were listed. The export's own side is the same object built the other way: it writes the folder, stages it, and takes `git rev-parse "$(git write-tree):<path>"` **before the marker exists in the index**, then writes the marker with that value and stages it; `git mktree` over the same entries produces the same tree object, so the two values are comparable by construction rather than by convention. (At the repository root, where `path` is `""` or `"."`, the same recipe run against `<tip>^{tree}` and the root's entries gives the same answer.) **Equal** means nothing has been written under `path` since the last export: the folder is replaced, the marker is rewritten, the export commits. **Different — or a non-empty `path` with no marker at all** — means someone else wrote there: the export **refuses, names the paths it would overwrite, prints both hashes and stops without committing and without pushing**. This is the detector Check 61 step 8 produces on purpose, and it is deliberately not "does the parent commit's subtree match": the rule is about the folder's *content*, not about who committed last, and a person's edit that was already committed to `branch` must be refused exactly like one that was not.

Two overrides get past that refusal, and they are two different questions rather than two names for one flag:

- **`--adopt`** answers *"whose folder is this?"* — it is for a `path` that already holds something the export did not write (a hand-made folder, or the first export into a repository that already has one). The export writes its tree over it and records a fresh marker: the operator's statement that the folder is the export's to own from here on. Without it, the first export into a non-empty folder the export did not write **fails**, which is the safe direction — the alternative is an export that silently eats a directory nobody meant to give it.
- **`--force-regenerate`** answers *"may I discard this edit?"* — it is for a folder whose marker **does** exist and whose tree differs from it. Somebody edited the exported record; the operator says the export's version wins. The export overwrites, records a fresh marker, and names in its own output the paths it replaced.

Neither is available to a scheduled or agent-run export: when D7's scheduled half is built it **refuses and reports**, because the operator is not there to answer either question, and it never passes a flag on someone's behalf. There is no third way past the refusal — no `--yes`, no interactive prompt, no quiet adoption of a folder whose marker is missing.

**The branch is bootstrapped from the default branch, not created orphan.** When `branch` does not exist on the remote, the export creates it **at the default branch's current tip** and puts its single commit on top; it does **not** create an orphan branch. The tradeoff, stated rather than assumed: an **orphan** branch keeps the folder's history out of the monorepo's history and makes the export's commits the only ones on it, which is tidy — and that is all it buys, while it costs the things reviewers actually use. `git log` from the default branch never reaches it; `git diff <default>..<branch>` — the command Check 61's fence is written with, and the one a reviewer runs to see what changed — reports the whole folder as *added* rather than as this cadence's change; a host cannot offer "compare against `main`" as a base for anything; and a repository owner who opens the branch sees a tree with no stated relationship to the code beside it. Branching from the default branch's tip costs one shared ancestor, which the export never writes to again — the folder's determinism does not depend on the history beneath it, and the detector above is what actually answers "has anyone written here" — and it makes the branch an ordinary branch on the repository: protection rules, diffs and review tooling work unchanged, and a person can merge the folder into the default branch by hand if the owner wants it there. **The default branch is read from the remote** (`git ls-remote --symref <url> HEAD`), never from the operator's own checkout's `HEAD`, because that checkout is a different repository and its `HEAD` is a different branch — which is also why `branch` has no "empty means the default branch" spelling in the table above: the value is always written out, so a repository whose default branch moves does not silently move the export with it.

**What a monorepo costs, and why the clone is shallow, blobless and sparse.** A monorepo is not a small clone, the export runs on the operator's own machine and network, and it only ever needs one folder. So the fetch is **shallow** (`--depth 1`: one commit of `branch`, or of the default branch when `branch` is being bootstrapped), **blobless** (`--filter=blob:none` — a mechanism this repository already has for exactly this reason, `gitops.CloneBlobless`), and **sparse** (`git sparse-checkout set <path>`, so only the folder's own blobs are materialised; anything else arrives on demand from the same remote, and nothing outside the folder is ever written to disk). The tree hash the detector compares is read from the fetched commit rather than from a working tree (the `git ls-tree … | git mktree` recipe above, which reads tree objects and no blobs), so the comparison needs no content at all, and the push carries only the folder's objects because the export's commit differs from its parent in that subtree and nowhere else. The dedicated-repository case costs the same as before and stays trivial; the reason it is written down is the monorepo case, where "clone the repository to export one folder" reads like something an operator ought to be warned about and is not.

**CI and history noise.** A monorepo builds on every push, so an export's commit carries a **skip-CI marker** in its subject (`[skip ci]` — the marker GitHub Actions, GitLab and Bitbucket Pipelines all honour) and a subject that names the export's own `checked_at`; an export that starts a whole monorepo's build is a tax on everyone who works in it. The author and committer are **fixed, never the operator's own**: `Fugaro <fugaro@users.noreply.invalid>`, `internal/gitops`' identity (`gitops.go:62-78`), so the person who ran the export is not written into a repository other people read — the same principle that omits `byPerson` spend. And the output is **sorted and stable** (fixed names, sorted keys and rows, byte-identical for the same input), so a diff is the policy change and not a map iteration or a renamed CSV.

**Who can read it — and why the defaults matter more in a monorepo.** In a monorepo the folder is readable by **everyone who can read that repository**, which is usually more people than can read the Firebase project. That is the intended, stated consequence, and it is what decides what goes in: the folder holds the *shareable* part of the record — the policy, the caps, and an account of spend over time, by name and by number. It is not a place for anything that should stay narrow, so **people are omitted by default** (P10: no `byPerson` spend, no kill-switch author), a default that matters more here than in a dedicated repository because the readership is wider; `--with-people` is the operator's explicit choice and its help text says the addresses are committed to a repository other people can read. **Secrets are excluded, never encrypted in place**: no value is ever written, and the inventory is metadata only.

**A PR instead of a direct commit (D14 — answered 2026-10-15).** A monorepo may protect `branch`, require every change to go through review, or run rules that a machine's commit should not bypass. So the export has an **optional PR mode**: it would push the export's own branch and open a pull request instead of committing to the branch the policy names. **The owner ruled on 2026-10-15, and the ruling is: a dedicated branch by default — the branch `fugaro-project`, writing only under the `fugaro-project/` folder — never the monorepo's `main` by default; and the PR mode is a documented opt-in, not built in the first slice.** That is the one wording this design, D14 and the plan all use. The PR mode is an opt-in rather than the default because it needs a credential that can open a pull request on the repository's host, and because an export that waits on a human every cadence stops being an export at all (the deferred half of D7) — while "not built in the first slice" is the honest description of its status: Task 6.2 ships the dedicated branch, pushed directly, and `docs/project-layer.md` documents the PR mode as an opt-in the CLI does not have yet, with its reason.

**The live check is a folder check (Check 61) — and the scratch repository is the owner's own, not the sandbox's.** The phase's own check, Check 56, asserts the export's *content* (no secret value, no per-person spend, a deterministic tree) against the configured backing location. The folder case is a different assertion and gets its own number: **Check 61** exports into a scratch repository that also carries unrelated files and asserts they are **untouched**, then makes the branch move under a second export and asserts the export follows it without forcing, and finally edits the folder out of band and asserts the detector refuses (plan Task 6.5).

**Where that scratch repository lives is a correction, and it is written here so the check is runnable.** An earlier revision said "a scratch repository on the sandbox's own host", which would have meant creating a repository in the `edgeappinc` Bitbucket workspace — the workspace that holds `edgeappinc/fugarosandbox` and also `edgeappinc/edgeserver` and `edgeappinc/edgeweb` (`belong`). **That workspace is not this check's to write in:** the rule that no agent touches `belong` generalises to "the check adds nothing to somebody else's workspace", and a scratch repository is not an exception to it. So the check has two acceptable homes, and both avoid the workspace entirely: a **local bare repository** the check itself creates (`git init --bare` under a temporary directory, pushed to over a `file://` remote — no host, no account, no network, and the default, because it costs nothing and touches nothing), or a throwaway repository the owner creates under **their own personal account** on the host they already use for their own work. Either way the check's own step names the push target explicitly. **Check 43's guard stays verbatim and is not weakened by this**: its third hard stop pins *the checkout the `fugaro` commands run from* to `edgeappinc/fugarosandbox`, which is correct and must remain so — the guard is about which installation and which checkout the commands act on, and a push target is a different object, which is why the step that introduces it says what it is rather than leaving a reader to infer it from the guard.

**Cadence (question 4): both.** A manual `fugaro project export` ships first (it needs the operator's local file and git credentials). A scheduled entry on the history job (sweep every 15 minutes, rollover daily: `history.tf:174-260`; its service account already has RTDB admin) is later, needing a deploy key or App token stored as a project secret (UNVERIFIED that the existing App can push to the backing repository); a hook in `init` and `budget set` captures local policy changes.

**Secrets (question 5): excluded, with an inventory.** No value is ever written, and no person holds secret-read today (`secrets.tf:31-42`). If encryption is ever wanted: SOPS with GCP KMS (operators decrypt with their own gcloud credentials) plus an offline age recipient as break-glass, because the KMS key dies with the GCP project. Nothing in the repository uses KMS, SOPS or age yet; an opt-in for later.
