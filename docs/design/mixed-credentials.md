# Mixed credentials and a stronger senior reviewer in a cheap-coder loop

Status: draft for the owner's review, 2026-10-14, corrected after an independent review against the code; **§11 records the owner's B0 ruling of 2026-11-04**, which reverses the "a run does not mix credentials" rule for one stage credential, and the ruling shipped as the tasks B1–B6 in 0.19.0 (the config rule and the launch, B1 and B1b; the account's own job and the token it mounts, B2; the per-stage environment, B3; the account stage's notional accounting and its bound, B4; the failure text a stage reports, B5; and these documents, the repository's own `fugaro.yaml` comment and **Check 290** of [gcp-live-checklist.md](../gcp-live-checklist.md), the owner-run smoke test, B6). §5, §9 and §10 say per area what shipped and what did not; the one thing that did not is §6.4's optional separate job execution for the review stage, which §11 keeps unbuilt on purpose. Related: [m10-multi-model.md](m10-multi-model.md) (provider routes, §7 auth modes, §11a two-tier review), [named-oauth-tokens.md](named-oauth-tokens.md), [recipes.md](recipes.md), [m9-budget-and-dashboard.md](m9-budget-and-dashboard.md) (D2).

## 1. Summary and recommendation

The cloud loop runs a cheap coder (DeepSeek through OpenRouter). The senior review stays outside it today, because the in-loop DeepSeek reviewer's "ship" is weak. This design asks how to put a stronger senior reviewer **inside** the loop. Three ways:

- **Path A: Claude through an Anthropic API key, behind the gateway.** Works today with the code as it is. Real dollars, capped by the gateway, no new trust exposure. Needs an Anthropic API key, docs and a live check.
- **Path C: a stronger model through OpenRouter.** Any model OpenRouter serves as the senior reviewer, behind the same route table and gateway as the coder. One provider key for both roles. **Not possible today**: the config refuses it for Claude models (§4), so it needs a small change to an M10 invariant, which the owner has approved as an explicit opt-in. For a non-Claude senior (GPT, Gemini) it needs no such change.
- **Path B: the subscription OAuth token for the reviewer stage only.** Needs infra and runner changes (§5). No dollar cost, but the gateway cannot cap it and the token shares a job with a cheap model that reads untrusted repository content.

Owner rulings (2026-10-14): B is worth its residual risk because Fugaro will work mostly with trusted repositories, and an explicit opt-in is enough (no separate reviewer job). The senior reviewer is built through whichever of A and C the owner has a credential for; the owner has an OpenRouter key and subscription OAuth tokens, no Anthropic API key. This design recommends: (1) a **non-Claude senior through OpenRouter first**, because it needs no code change and is the cheapest test of the idea; (2) **C for Claude models**, now that the owner has ruled the M10 invariant is relaxed by an explicit opt-in (§4); (3) **A** only if the owner gets an Anthropic key; (4) **B** as the separate, larger piece of work, behind its opt-in.

## 2. What exists today (verified in the code)

- `agent.auth` is **one value per workflow**: `oauth`, `api-key` or `vertex`. A provider-routed model (DeepSeek) needs `api-key`; `oauth` or `vertex` with a provider pin is refused at config time (`internal/config/providers.go`, `CheckProviderAuth`).
- With `api-key`, the runner starts the gateway with the **Anthropic upstream** and the repository's `ANTHROPIC_API_KEY` (`internal/runner/gateway.go`, `startGateway`), plus **provider routes** for the providers the pinned models name. The real key is not put in the agent's environment (`internal/agent/env.go`). `internal/infra/spec.go` writes the `anthropic-api-key` mount into the spec for **every** `api-key` workflow. *(2026-10-15: PR #371 changed what happens to it — `internal/infra/readiness.go` drops the mount when the secret has no enabled version (`OptionalSecret`, `:74`), `internal/agent/env.go:92-105` wants the key only with the gateway off, and `fugaro init --repo` asks for one only when a call of the run reaches Anthropic. So the key is optional and no placeholder is needed; the one refusal left is a key that is present and shorter than 4 bytes.)* The repository's current all-DeepSeek `fugaro.yaml` works because that secret exists.
- `oauth` is never proxied; the token secret is mounted, and per-account workflow variant jobs are built, when `agent.auth` is `oauth` — **and, since B2 (2026-11-05), for an `api-key` workflow that declares a stage account**: `mixedStageAccounts` (`internal/infra/spec.go`) puts that account beside the default, so the run's own job mounts its token next to the provider key the gateway reads, and every other auth, and an `api-key` workflow naming no stage account, are unchanged. The key that names the account is `agent.oauth_token` (repository and override scope, 0.6.5 or later), checked against `claude_accounts.<name>.allow_data_to`.
- The runner writes a managed settings file that points every Claude Code process at the gateway and refuses settings that route around it (`internal/runner/agentenv.go`, `writeManagedSettings`, `checkSettingsRouting`). *(2026-11-05: this bullet read "**one** managed settings file" for the whole run; since B3 the file follows the stage — the gateway's routing for a stage the run's own credential serves, neither its URL nor its token for a stage a Claude OAuth account serves (`TestMixedRunManagedSettingsFollowTheStage`).)*
- **Claude goes direct, by rule.** `ClaudePatterns` (`claude-*` and `anthropic/*`) are refused as provider model patterns (`CheckModelPattern`). *(2026-10-15: this bullet read "`pricing.IsAlias` treats the `anthropic/` prefix as an alias, so `model_prices` and pins reject an `anthropic/<id>` key". The pricing half of §4's opt-in is now built: `IsAlias` accepts a well-formed `anthropic/<id>` (`internal/pricing/alias.go`), so a pin and a `model_prices` key may name one exact ID; a route entry may claim that same ID, and an `anthropic/<id>` no route names is refused by the config gate rather than by the alias rule (`CheckProviderPolicy`, `internal/config/providers.go`). Every pattern spelling — `claude-*`, `anthropic/*`, `anthropic/claude-*` — is still refused.)* M10's reason (decision 2, spec §5.2): Claude's prompt-cache markers are handled on the direct path.
- The stage split exists: `agent.models.coder` and `.reviewer`, the `standard` recipe (a cheap loop, then the senior review, with bounce-back), and `first_line_review: auto`, which runs the cheap first-line review when a provider serves the coder and none serves the reviewer.

## 3. Path A: Claude through an Anthropic API key

```yaml
agent:
  auth: api-key
  models:
    coder: deepseek/deepseek-v4.1-flash
    reviewer: claude-sonnet-5-5
```

with `agent.recipe: standard`. DeepSeek implements, a first-line DeepSeek review and fix loop runs, then the Sonnet senior review decides readiness; a rejection bounces back to the cheap loop. Verified against the code: `CheckProviderAuth` passes for `api-key`, `first_line_review: auto` fires for a provider coder with a Claude reviewer, and `claude-sonnet-5-5` is in the embedded price table ($2 input, $10 output per million tokens; verify against the list price at build time).

**Prerequisites (all existing behavior, to document):**

1. `budget.mode: enforce` with a per-run cap (`CheckProviderGateway`).
2. If `budget.allowed_models` is set, it lists both models.
3. `agent.models.background` defaults to the provider coder, so Claude Code's background requests during the reviewer stage still go to DeepSeek through the gateway; the doc says so and how to pin it.
4. A real Anthropic API key in the repository's `anthropic-api-key` secret, which the owner types.

**Missing:** the user docs, the cost guidance (Sonnet reads the diff at list rates in real dollars, bounded by the per-run cap; a ceiling is `review_rounds` times the diff size at those rates), a gateway test with both upstreams in one run (check `internal/runner` and `internal/gateway` provider tests first), and one sandbox live check. No new trust exposure: the gateway holds the key; the D2 residual is unchanged.

## 4. Path C: a stronger model through OpenRouter

```yaml
# local operator config
providers:
  openrouter:
    models: ["deepseek/*", "openai/gpt-5*"]   # a non-Claude senior: valid today
model_prices:
  openai/gpt-5.5: { input_per_m: ..., output_per_m: ... }   # cache_read is a multiplier of input_per_m (default 0.1), not a price
# fugaro.yaml
agent:
  auth: api-key
  models: { coder: deepseek/deepseek-v4.1-flash, reviewer: openai/gpt-5.5 }
```

**A non-Claude senior (GPT, Gemini, a larger DeepSeek or Qwen) works with the existing rules**: the route table, pins, prices and gateway need nothing new, and a different model family reviewing a DeepSeek diff is a better second opinion than the same family. Two things still apply: an existing, at least 4-byte `ANTHROPIC_API_KEY` secret (§2: a placeholder the owner types is enough when no `claude-*` model is pinned, since the gateway sends it upstream only for a Claude model), and `allow_data_to` listing the repository for the provider.

**A Claude senior through OpenRouter (`anthropic/claude-sonnet-5.5`) was refused before the opt-in**, in three places: `ClaudePatterns` rejected a provider claiming `anthropic/*`, `IsAlias` rejected the key in `model_prices`, and the pin checks rejected the ID as an alias. The owner ruled on 2026-10-14 that the rule is relaxed with an explicit opt-in in config. The change is: an opt-in route entry that claims one explicit `anthropic/<id>` (not a pattern), with the pin checks accepting exactly the IDs a route claims, and the alias tests changed on purpose. (It is built in a narrower shape than this paragraph proposed — the price package stayed claim-blind, so `IsAlias` itself knows nothing about claims: see "What shipped" below.) **Where the entry lives** (owner ruling, 2026-10-14): in the local operator config or in the shared project layer, so a project lead can enable it without editing local config **both halves are built**: the operator-config half (PR #387, #394) and the layer half (Task 7, PR #397 — a claim written in the shared project layer is merged into the run's own route table on every launch); a repository's own `fugaro.yaml` can choose the model (`agent.models.reviewer`) but cannot add or enable a route, and `allow_data_to` on the provider still decides which repositories may send code. The plumbing is narrower than this paragraph first assumed: the gateway's `validateRoutes` shares the rule by calling `config.CheckModelPattern`, so a claim is judged in one place, and **nothing has to reach the pricing package** — `IsAlias(model string)` (`internal/pricing/alias.go:49`) accepts a well-formed `anthropic/<id>` as the model ID it is, with no knowledge of claims; `CheckPins(a Agent, prices *pricing.Table)` (`internal/config/pins.go:34`) takes no providers map and needs none, because the pin that no route claims is refused elsewhere; and `CheckProviderPolicy` (`internal/config/providers.go:559`) is `internal/config`'s, asking the providers map it already holds. Those three are the claimed-set threading the plan vetoed (P4), and none of it shipped. With a provider-served senior, `first_line_review: auto` turns the first-line review **off** (it is on only when the coder is provider-served and the reviewer is not), so a Path C senior runs without the cheap first line unless `first_line_review: on` is set. The cache-marker reasoning (M10 decision 2) is the open technical question: OpenRouter forwards Anthropic's `cache_control`, but whether Claude Code's cache markers survive the Anthropic-compatible endpoint is to be measured, not assumed; **Check 46** of [gcp-live-checklist.md](../gcp-live-checklist.md) is the live check that compares `cache_read` (and `cache_write_5m`) tokens and the charge between a direct and an OpenRouter run, and it has not been run, so the question stays open until it has.

**What shipped (2026-10-15, PR #387), and in what shape.** The ruling above is built, and not in the shape the paragraph above describes: **the claim is one literal `anthropic/<id>` route entry, and the entry itself is the whole permission** (`config.CheckClaudeClaim`, `internal/config/providers.go` — one explicit provider model ID under the prefix, no wildcard, no separate claimed-ID list and no switch). **The pricing package stayed claim-blind**: `IsAlias` keeps its signature and accepts a well-formed `anthropic/<id>` as a real model ID (`internal/pricing/alias.go`, with `IsProviderModelID` exporting the grammar so the claim rule and the price grammar cannot drift), so `model_prices` may key one and `CheckPins` needs no providers argument; the gate on **pinning** is `internal/config`'s, in `CheckProviderPolicy`, which asks its own providers map whether a route claims the ID. `anthropic/*`, `anthropic/claude-*`, a bare `claude-*`, a `:` variant, a `[1m]` spelling and an over-length ID are refused exactly as before, and an ID no route claims is refused at bootstrap on every launch — and by `fugaro validate` when the local config it finds is the repository's own project's, which is the only case in which it judges pins and providers at all. The implementation plan is [2026-10-14-openrouter-senior-reviewer.md](../plans/2026-10-14-openrouter-senior-reviewer.md), and its tasks divide like this: **Tasks 4, 5 and 6 are merged** (PR #387 — the price half, `IsAlias`/`IsProviderModelID`, and the config half, the claim rule and the refusals; PR #394 — the claimed senior end to end and the four refusals it must not erode: unclaimed, `allow_data_to`, oauth, observe); **Task 7** (the claim in the shared project layer, PR #397) and **Task 8** (these docs, PR #398) are the other two, both shipped; **Task 2 shipped** (the two tests Phase 1 is for — the mixed-stage charge at each model's own rate, and the `auto` run whose reviewer is provider-served — PR #413) and **Task 1 is in review** (the user-doc section for a non-Claude senior, [multi-model.md](../multi-model.md)'s "The senior reviewer on a provider route", PR #408); and **Tasks 3 and 9 *are* Checks 45 and 46** — owner-run, sandbox only, and not yet run — whose sections are already written in [gcp-live-checklist.md](../gcp-live-checklist.md), each task being that check's maintenance rule rather than new text. Both halves of the place ruling in §8 are shipped: the operator names the ID in a route's `models` of the local operator config, or in the shared project layer's `claude_models`, and a repository's own `fugaro.yaml` can still choose the model but never enable a route.

Facts from OpenRouter's public API, 2026-10-14 (to re-verify at build time; the lists change): `anthropic/claude-sonnet-5.5` $2/$10 per million tokens, `anthropic/claude-opus-5.5` $4/$20, `anthropic/claude-fable-5.1` $10/$50; Anthropic models are served by Amazon Bedrock and Google on the zero-data-retention endpoint list. The route fee (`route_fee_pct`) is added to every charge; the code default is 0, and 5.5 is the value in the owner's operator config. A route that reports no cache fields is charged at the full input rate, so a senior with worse caching costs more as well as risking different behavior; `fugaro budget preview` (#351) gives a ceiling.

**Owner ruling (2026-11-04): B is approved in one shape, and it is not this section's** (task B0). **Built (B1–B6), and in §11's shape rather than this section's.** The proposal below is kept as the shape the build answered to, one line at a time, and it is not a list of work outstanding: the infra mount and the per-account variant jobs (B2, `internal/infra/spec.go`), the per-stage runner spec — the token and no gateway URL for the stage the account serves, the reverse for every other stage, and the managed settings file following both (B3, `internal/runner/agentenv.go`, `writeManagedSettings`), the validation §11's rule asks for (B1, `config.CheckStageAccountMix`) and the notional record (B4, `result.json`'s stage `credential`, `model_usd` and `model_notional_usd`). Two lines of it are deliberately not built and §11 says so: **the gateway still cannot cap it** — the stage's calls go direct to Anthropic, out of the gateway's ledger entirely — and §6.4's separate job execution for the reviewer is the optional hardening it was. The sandbox run this section asks for at the end is **Check 290** ([gcp-live-checklist.md](../gcp-live-checklist.md)): owner-run, sandbox only, never `belong`, one trivial task, and **NOT RUN**.

**Proposed shape (names tentative):**

```yaml
agent:
  auth: api-key
  models: { coder: deepseek/deepseek-v4.1-flash, reviewer: claude-sonnet-5-5 }
  stage_auth: { reviewer: oauth }   # new; only "reviewer" and only "oauth" in the first slice
  oauth_token: bmb                  # the existing key, now naming the reviewer's account
```

**What it takes (larger than a flag):**

- **Infra:** mount the OAuth token secret for an `api-key` workflow that sets `stage_auth`, and build the per-account variant jobs for it (today both happen only for `agent.auth: oauth`); `fugaro init --repo` re-run and an upgrade note for deployed jobs.
- **Runner:** one gateway, one managed settings file and one `spec.Auth` switch exist today. The reviewer stage needs its own spec: Claude Code started without the gateway base URL and with the token, the managed settings file absent or rewritten for that stage, restored at stage end, and a Claude-only model set for it (the background and haiku pins are DeepSeek ids with no meaning on a direct stage). The gateway sees no call from the stage, so the stage is recorded as notional dollars with `credential: oauth` in `result.json`.
- **Validation:** `CheckProviderAuth` accepts exactly `api-key` plus `stage_auth.reviewer: oauth`; `reviewer: coder` and `coder: reviewer` recipes are refused with it (the coder would need the token); `claude_accounts.<name>.allow_data_to` is checked at launch.
- **Budget:** uncapped by the gateway; the stage is bounded only by `agent.max_budget_usd`, which is **Claude Code's own estimate** (accurate for a Claude model, unlike for DeepSeek, where it is about 25 times too high).

## 6. Security: the residual risk, stated plainly

In Path B the subscription token and a cheap model that reads untrusted repository text share one job for the whole run. The token reaches the runner as a mounted secret in the runner's environment, and the coder runs as the same OS user, so a prompt-injected coder can read it from `/proc/<runner>/environ`; the job's service account also keeps `secretAccessor` on the secret, and the metadata server is reachable. This is the accepted D2 residual. What B adds: the stolen credential is an **account-wide subscription token usable anywhere**, with no spend cap and shared rate limits with the owner's interactive use, not a key held in the gateway.

Mitigations, honestly:

1. **Opt-in, trusted repositories only.** Enforced by validation as far as config can: `claude_accounts.allow_data_to`, and refusing `stage_auth` where the workflow takes follow-ups from public-repository comments (`followup.allow_public`), together with review mode's trusted-author rule and SECURITY.md's fork handling. `allow_public` does not gate the first run on a public repository, so the gate is only as strong as who can push branches and comment.
2. **Stage-scoped environment** keeps the token out of the coder's own environment and logs. It does **not** narrow the `/proc` attack above.
3. **Fetching the token at stage start** shortens the window but does not close it: the service account keeps access.
4. **A separate job execution for the reviewer**, with its own container and service account, is the only mitigation that closes the gap. Not required by the owner's ruling; an optional hardening for repositories with outside contributors.

The SECURITY.md known-gaps list gets one line for B if it ships. Path A needs none. Path C changes the data-flow scope: `allow_data_to` on the provider decides which repositories may send code to it.

## 11. The B0 ruling (2026-11-04): the one credential a run may mix

**A ruling recorded, and built: the tasks B1–B6 shipped in 0.19.0.** The owner ruled on 2026-11-04 that the rule §5 was parked behind — *a run does not mix credentials* — is **reversed for exactly one case**, so that a run keeps its cheap coder on a provider route **and** runs its in-job reviews on an Opus model through the owner's own Claude subscription account. The rest of the requirement (the senior review at level 2, the adversarial review at level 3, both inside the job) is the in-job review work's; this section is the one rule that work needs from this document, and the tasks **B1–B6** built against it. When this section was written it allocated no D-number and no check number and changed no behaviour on its own; the build is what changed the behaviour, and **Check 290** of [gcp-live-checklist.md](../gcp-live-checklist.md) — owner-run, sandbox only, never `belong`, **NOT RUN** — is the one number the work took afterwards, above the register's own top. What follows is the rule, the threat model it is accepted under, what a failure does, and the decisions the six tasks followed.

### The rule

A run whose own credential is a provider key — `agent.auth` is `api-key`, the only value a provider pin is admitted under (`CheckProviderAuth`, [internal/config/providers.go](../../internal/config/providers.go)) — may declare **exactly one stage-scoped Claude OAuth account**, and use it for two stages and no others: the senior `review` (review level 2) and the adversarial/security `adversarial` (level 3, `recipe.StepAdversarial`). The account is a name of the owner's local `claude_accounts`, held to this repository by that account's `allow_data_to` (`claudeAccountAllowed`, `config.AllowedClaudeAccounts`), and chosen by the accounts design's chain ([accounts-add](../accounts-add/spec.md) §11.1–§11.2): `stages.<stage>.claude_account` on `review` or `adversarial` — rung 2 of that spec's §11.2 chain — **or the project's `default_claude_account` (rung 4), which opts such a run in too under the owner's ruling of 2026-11-05, amending the conservative reading this section recorded on 2026-11-04**: *IF `default_claude_account` is set AND we have an Anthropic model for senior review and/or security review, then we get mixed runs.* Rung 2 wins where the two name different accounts, and rung 4 reaches the two stages of the allow-list and no others, and only where that stage's own model is an Anthropic one: where it is not, nothing changes and nothing is refused — `default_claude_account` is the account *every* stage of an `oauth` run uses when nothing more specific does ([internal/localcfg](../../internal/localcfg/localcfg.go), spec §11.1, D873), and a project that sets it and reviews on another vendor has not asked for a mix. Rung 2 is a declaration about the stage it is written on and is served as written, whatever that stage's model: the condition the ruling attaches is the *default*'s, because a default is what a project has for every stage it has by writing one key. A project that spells the key `default_claude_account: default` declares **no mix at all**: `default` is the unsuffixed default account — the sentinel `spec.OAuthToken`'s own rule reads as "no token of the run's own", and a value a local config may write for either account-choice key — and an `api-key` run's job carries no OAuth token for the default account, so the key names nothing, is not refused under a mode that could not carry a mix, and is not a second credential beside the other stage's own.

The 2026-11-04 reading held the opposite — that reading the default here would turn every `api-key` repository an account's `allow_data_to` already covers into a mixed run off a key nobody set for one, with no per-stage declaration at all. The owner ruled that the key *is* the act where the reviews are Claude's: a project that sets the default and reviews on an Anthropic model is asking for the mix.

**The mix applies only where the run can carry it.** It is a second credential beside the provider key the gateway holds, so it needs the run that has one: the coder's pin must be a pin a provider route this repository may use claims, under `budget.mode: enforce` — the only mode that routes a call to a provider at all (`CheckProviderGateway`, [internal/config/providers.go](../../internal/config/providers.go)). A configuration that declares a mix under `off` or `observe` declares a key that could never apply, and the launch refuses it (`config.CheckMixBudget`) rather than carrying it to a run that halts for the pin.

| | The run's own credential | The stage's |
| --- | --- | --- |
| `implement`, `review_first` | the provider key, through the gateway | — |
| `review`, `adversarial` | — | the one Claude OAuth account, direct to Anthropic |
| anything else | the provider key, through the gateway | — |

**An allow-list, not a denylist: in such a run the account serves `review` and `adversarial` and no other stage.** The account on any stage other than those two — `implement`, `review_first`, `fix`, `plan`, and any stage a later recipe adds — is refused, so a stage the tree does not have yet starts refused rather than permitted. Five refusals carry the rule: never `implement`, never `review_first`, never a second provider's key, never under `oauth`, `vertex` or `cascade`, and never without the gateway that holds the provider key. Each is a decision B1 implements rather than an accident of the code today:

- **Never `implement`.** The coding stage is the coder's, and the coder's credential is the provider key the gateway holds. A stage-scoped account on the coder's own stage is refused, not ignored.
- **Never `review_first`.** Level 1 is the cheap first line, pinned to the coder's role (`reviewStages`, [internal/runner/routing.go](../../internal/runner/routing.go)) and served by the coder's model: it is a coder stage that happens to be a review, and the same refusal applies.
- **Never a second provider's key.** The mix is exactly one provider key plus one Claude subscription account. No run holds two provider keys, and no run holds two Claude accounts for this purpose: where the project default and the other mixed stage's own key name different accounts, the launch is refused (`mixedStageAccount`, [internal/cli/run.go](../../internal/cli/run.go)) rather than the default being honoured as a second credential — naming one account in both keys is the fix, and a project whose `default_claude_account` is the account its `oauth` runs use keeps it.
- **Never without the gateway.** The account is a second credential *beside* the provider key the gateway holds, and only `budget.mode: enforce` routes a call to a provider at all: under `off` and `observe` the coder's calls go direct to Anthropic and there is no provider key to mix, so a config that declares a mix there is refused (`config.CheckMixBudget`) rather than admitted as a mix that could never be one.
- **Never under another auth.** `oauth`, `vertex` and `cascade` are unchanged: a provider pin under any of them is refused as it is today, and the stage account exists only to give an `api-key` run a Claude review credential it otherwise has none of. What this refusal must not do is take `stages.<stage>.claude_account` away from an `oauth` run: there the keys keep the meaning the accounts design already gives them — a run may name one account for a stage and another for the rest, and B1 must not refuse that. What B0 admits is one thing only, the stage-scoped account *alongside a provider key*, and an `oauth` run has no provider key to mix.

Two things are **not** bent by the reversal. An OAuth token is still only ever sent to Anthropic's own endpoint — that invariant is checked on the route and on the destination ([SECURITY.md](../../SECURITY.md), "The invariant") — and the stage that uses it goes **direct to Anthropic**, so the invariant holds rather than being relaxed: what the reversal changes is *how many credentials one run holds*, not where any of them may be sent. And every name is still held to `claude_accounts`'s allow-list for the repository before any launch, wherever a rung of the run can hand it to something — the stage key here, the mix's default at the launch, an `oauth` run's own default when the walk picks it — while a name *no* rung of that run can reach is not the launch's to refuse (the first cut checked the project default unconditionally and refused a repository the key names only for other projects).

### The threat model

**Who holds the token, and when.** The job mounts the account's token into the **runner's** environment, where it is present for the whole run — the runner is what builds each stage's environment, so it is the process that has to hold the credential the `review` and `adversarial` stages are given. The **coder's own environment is an allow-list** and carries no model credential at all: `BuildEnv` ([internal/agent/env.go](../../internal/agent/env.go)) keeps `baseEnv`, the auth variables and the workflow's declared secrets, the provider key stays in the runner where the gateway reads it, and the review account's token is added for the review stage's own process and no other (B4). The token is registered with the redactor **from bootstrap, for every stage**, rather than by the stage that happens to use it: the registration does not ride on a stage's environment, so there is no stage — the coder's, a review's, or one a later recipe adds — whose transcript or log line could carry the token because the redactor did not know it yet. That is the treatment the provider key already gets, registered where `BuildEnv` keeps it out of the agent's environment ([internal/agent/env.go](../../internal/agent/env.go)), and it builds on a refusal the tree already has, applied per stage: an environment whose auth is `oauth` is refused a gateway in both places one is built — `BuildEnv` and `GatewayVars` return `auth: oauth never goes through the gateway` ([internal/agent/env.go](../../internal/agent/env.go)) — so the stage that carries the token is exactly the stage whose environment is built with no gateway URL, and the coder's stages are the reverse ([internal/runner/runner.go](../../internal/runner/runner.go), the per-stage `BuildEnv` call B4 adds to).

**What a hostile coder can reach.** Everything it can reach today, and the token with it. The agent runs as the same OS user in the same container as the runner, so a prompt-injected coder reads the runner's environment through `/proc` (`/proc/<pid>/environ`) and finds the account's token exactly where it already finds the OpenRouter key, the git token, the gateway token and every declared secret. **That is the accepted residual, and the whole of the owner's argument for accepting it: the token is the same exposure class as the provider key the loop already carries.** Nothing in this rule narrows it, and the allow-listed coder environment must not be read as narrowing it — it keeps the token out of the coder's *own* environment and out of what Fugaro publishes, not out of the process tree. The job's service account also holds `secretAccessor` on that account's secret and the metadata server stays reachable, so the credential is reachable by two routes and not one. §6.4's separate execution for the reviewer — its own container and service account — is the only mitigation that closes the `/proc` read, and **it is not built**: the owner's ruling does not require it.

**What the token's own blast radius is.** A subscription credential, not a scoped key: usable anywhere Anthropic accepts it, with shared rate limits against the owner's own interactive use, and revocable at the account. **The gateway does not bound it.** The stage's calls go direct to Anthropic and never through the gateway, so they are neither priced nor refused by the run's cap; the stage is bounded only by `agent.max_budget_usd`, which is Claude Code's own estimate — accurate for a Claude model, unlike for a provider-served coder (§7's table records the comparison). What bounds *which repositories* may put code where that token is: the account's own `allow_data_to`, the same list every named account stands on.

### A review stage that fails

A stage whose account the launch refuses — a name that is not in `claude_accounts`, one whose `allow_data_to` does not list this repository, or, on a project job, an account the job does not carry — is refused **before any model call**: there is no silent fallback. It is never quietly run on the coder's credential, and never on another account: the coder's credential is the provider key the gateway holds, and a review that silently ran on the model it was meant to be independent of would be worse than one that did not run at all.

**A stage that starts and fails ends as a failed stage.** An expired or revoked token, a rate limit, a provider error, or an agent that reports an error (`res.IsError`, [internal/runner/runner.go](../../internal/runner/runner.go)) takes the runner's ordinary failure path (`r.fail`): the stage is recorded as failed, no verdict is recorded for it, and the run cannot come back ready for review on a review that never ran. There is no new failure mode here — the same path a review stage takes today when its model call fails.

**Failover is a decision the owner makes, not a default.** With `claude_account_auto` on, A7's dormant failover walks to the next **review-class** account ([accounts-add](../accounts-add/spec.md) §11.3) — never mid-stage, always logged, and writing the account that took over into the record's `stage_accounts` map, which is on `main` and read by nothing ([internal/runstore/runstore.go](../../internal/runstore/runstore.go)). With the switch off — which is its default — a rate limit ends the stage as the paragraph above says. The record's own limit stands either way: `oauth_account` is one scalar and names the account the run used *last*, so `stage_accounts` is what says which account served which stage.

### The decisions the tasks B1-B6 follow

One per area, each with the thing that was missing on `main` when the ruling was recorded and the task that shipped it; the tasks' own split across B1–B6 was the plan's to make.

1. **Config: admit exactly one mix, refuse every other.** `agent.auth` is one value per run ([internal/config/config.go](../../internal/config/config.go)), and a provider pin is admitted only under `api-key` (`CheckProviderAuth`). The permitted combination is `api-key` plus one stage account, **declared by that stage's own key** (`stages.review.claude_account` or `stages.adversarial.claude_account`) **or named by the project's `default_claude_account` where that stage's own model is an Anthropic one** (owner ruling 2026-11-05, amending the reading recorded here on 2026-11-04); refused are the account on any other stage — `implement`, `review_first`, `fix`, `plan`, any stage a later recipe adds — a second account, a second provider's key, the account under `off` or `observe` where a provider route serves the coder (`config.CheckMixBudget`), the stage account under `oauth`, `vertex` or `cascade`. No compat shim: the rule is the rule at every layer that judges it, and `fugaro validate` says the same as the run — `config.CheckStageAccountMix` for the mix and the auth, and its own provider-pin rule (`CheckProviderGateway`, which refuses a provider model in any mode but `enforce`) for the mode the launch's own clause reads. **Shipped (B1, B1b):** `CheckStageAccountMix` refuses every case the sentence above lists on every launch and in `fugaro validate`, `CheckMixBudget` is the mode clause, and the stage rung and the widened rung 4 are the launch's; `fugaro run` and `fugaro validate` read the same rule out of the same two functions, so a config cannot be legal to one and refused by the other.
2. **Infra: mount the account's token for such a workflow.** Today the mount and the per-account variant jobs exist only for `agent.auth: oauth` (`WorkflowAccounts`, [internal/infra/spec.go](../../internal/infra/spec.go)), and a job mounts **one** account's token — so a workflow that declares a stage account has to be given that account's secret, and the job that serves it has to be the one built for it. `fugaro update` carries the migration in the same release (CLAUDE.md's hard rule: no operator step, no second command). **Shipped (B2):** `mixedStageAccounts` is the workflow's own list beside the default, so an `api-key` job whose repository declares a stage account mounts that account's secret and gets its per-account variant job, and `fugaro update` — the one command — is still the whole of the operator's side.
3. **Launch: resolve the account through the accounts design's chain.** `claudeAccountFor` ([internal/cli/run.go](../../internal/cli/run.go)) walks rung 1 (the flag), rung 2 (the stage's own key, for the two stages of the allow-list on an `api-key` run), rung 3 and rung 4, and every rung ends in the allow-list — `claudeAccountAllowed` for the run's own rungs, `claudeAccountMembership` inside `mixedStageAccount` for the mix's — so a key can only name an account the owner already admitted for the repository, and only where the run would use it. Rung 4 is a rung for a *stage* only under the ruling of 2026-11-05 — the stage is one of the mix's two, its own model is an Anthropic one, the coder is served by a provider route this repository may use and the mode the run resolves is `enforce` (`mixedStageAccount`) — and it is never the run's own credential: an `api-key` run's own account stays the unsuffixed default, while B3 wires rung 4 for an `oauth` run's own default as the accounts design says. **Shipped (B1, B1b):** `claudeAccountFor` walks the four rungs and `mixedStageAccount` holds the mix's two, both on every launch (and `fugaro validate` reads the same walk), with the tests in `internal/cli/run_stage_account_test.go`.
4. **Runner: give the review stage its own environment.** One gateway, one managed settings file and one `spec.Auth` switch serve the whole run; `stagePins` ([internal/runner/agentenv.go](../../internal/runner/agentenv.go)) reads the gateway's routing, and returns nothing when the gateway is off. The review stage's process needs the token and no gateway URL, the coder's the reverse, and the managed settings file — which points Claude Code at the gateway — has to be right for each. The token is registered for redaction at bootstrap, once for the whole run, not per stage: the stage that holds it is not the stage that has to know it for the redactor's sake. The stage's calls are outside the gateway's ledger by construction, which is exactly why §7's table and SECURITY.md's residual both say the cap does not bound them. **Shipped (B3):** the per-stage environment is `stageEnv`/`stagePins` and the managed settings file is written per stage — the coder's stages carrying the gateway's routing and no token, the account's two carrying the token and none of the gateway — which `internal/runner/agentenv_internal_test.go`'s mixed-run tests pin half by half. **Shipped (B4):** the accounting, where the stage's figure is Claude Code's own, all of it notional, with `credential: oauth` beside it and its only ceiling `agent.max_budget_usd` next to `timeouts.stage`.
5. **Record: write what happened per stage.** `stage_accounts` in the run record ([internal/runstore/runstore.go](../../internal/runstore/runstore.go), on `main` since A2) is where a stage's account is recorded, and the `res.IsError` path in [internal/runner/runner.go](../../internal/runner/runner.go) is what keeps a stage that reported an error from being read as a review that ran. The field is record-only: nothing reads it until a later task surfaces it, and `oauth_account` keeps the meaning it has. **Shipped (B3):** a run that serves a stage from the account writes `stage_accounts[<stage>]` and writes no entry for a stage it served, which `internal/runner/agentenv_internal_test.go`'s `TestMixedRunRecordsTheStagesAccount` pins, and the `res.IsError` path is the one that keeps a stage which reported an error from being read as a review that ran. Nothing outside the record reads the map yet, so the field still means what it meant when it was reserved.
