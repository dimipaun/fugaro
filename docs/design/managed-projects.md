Status: **nothing here is approved and nothing is built.** This document reconciles the owner's draft ([managed-projects-spec.md](managed-projects-spec.md), kept verbatim) against the code on `main`, resolves what it can, and lists the decisions that are the owner's. ## 1. Summary and recommendation

The spec asks for autonomy: in a project **Fugaro created**, the agent runs Terraform and other cloud operations end to end, with the agent reviewing each plan in place of a human, and with the plan and its review kept for audit. It justifies this with "a managed project is disposable" and with the observation that **humans rarely read Terraform plan output**.

The observation is true and the conclusion does not follow from it. The code already contains the machinery the spec is reaching for, and it already contains the control the spec would remove:

1. **The plan gate already exists, and it is deterministic.** `internal/infra/tf/guard.go` refuses any plan that deletes or replaces anything unless the exact address is named with `--allow-delete` (`Guard`, `guard.go:19-45`), and `internal/infra/tf/cover.go` decides whether a plan may share a confirmation at all — an allowlist of resource types (`allowedTypes`, `cover.go:15-46`), of the roles each `*_iam_member` type may grant and to whom (`grantRules`, `cover.go:63-113`), of every custom role's exact permission set (`RolePermissions`, `cover.go:169-182`), plus attribute checks: images in this run's registry, schedulers calling this run's jobs, a sink to this project, a private bucket, **the billing account the review showed**, and the project each resource lives in (`Cover.Projects`, `cover.go:127-143`; `attributes`, `cover.go:609-728`). This is exactly the "machine-checkable plan rules" the spec's step 3 wants, built for a different purpose and already wired into the apply path.
2. **The control the spec removes is the strongest one the program has.** `internal/initflow/stage.go`'s `CanConfirm` returns `false` for **every** step when a coding agent's environment marker is present (`stage.go:334-343`), `AgentRefusal` explains why (`stage.go:298-305`), and `fugaro init`'s own help says it plainly: "Under a coding agent's environment variable (`CLAUDECODE` and the like) init applies nothing, `--yes` included … that is a mitigation, not a barrier: an agent that unsets its own variables is not stopped, and **the real controls are the typed confirmations** and the skills' lint" (`internal/cli/init.go:376`). The markers are `CLAUDECODE, CLAUDE_CODE_ENTRYPOINT, CLAUDE_CODE_SSE_PORT, CLAUDE_CODE_REMOTE, CURSOR_AGENT, AI_AGENT` (`internal/cli/initsecrets.go:132`).
3. **"An agent that checks every resource change is the better reviewer" is not what the reviewer is.** The review stage is a model call (`internal/runner/runner.go:1559`, `r.stage(ctx, "review", …)`) whose verdict is a two-valued string from a JSON schema (`internal/runner/verdict.go:13`), run in the run's own container, as the same user and the same process as the coder. **By default it is the same model as the coder** — the recipe maps reviewer to coder and the configured reviewer model is explicitly ignored (`runner.go:1038-1040`). A control that cannot be independent of the thing it checks is not a control, however good the model is; and the text it reads (resource names, descriptions, the plan's own strings) is written by whoever wrote the configuration the plan applies. SECURITY.md already says of the same agent in review mode: a trusted author's own prompt injection "is still code execution under `--dangerously-skip-permissions`" (`SECURITY.md:70`).
4. **A managed project is not disposable in the way the spec means.** It holds the GCP billing budget's state and Fugaro's **spend history and kill-switch state in RTDB** (`internal/budget/model.go:30-38`, `:57-72`), the runs bucket (`runs/` records expire at 90 days and the bucket is **unversioned**, `deploy/terraform/gcp/modules/installation/bucket.tf:16-24`), and the **Terraform state bucket** — which by default lives *in the installation's own project* (`fugaro-tfstate-<gcp-project>`, `internal/cli/init.go:348`; `CreateStateBucket(ctx, c, spec.Project, …)`, `internal/cli/init.go:1198`). If the project dies, its Terraform state dies with it. "Deleting the whole project loses almost nothing" is wrong for the state, the spend history and the kill-switch state; and it is wrong for anything shared with a repository outside the project, which is precisely what the spec's non-goals exclude and what the `belong` installation *is*.

**Recommendation, in the order that delivers the spec's value safely.**

1. **The marker first, and the cloud is the authority** (§5, D22–D24). Make "Fugaro created this project" a fact recorded *at creation*, in the installation's own Terraform state and in a labelled marker object the run's credentials cannot write — not a project label alone (a project label is writable by any project editor, and this feature is about to hand the run more capability, not less), and not a project config in the repository (the agent writes to that repository).
2. **Keep the plan gate, and make it the gate** (§4, D26–D28). Managed mode replaces *the human's typed confirmation* with `tf.Guard` + a managed-project instantiation of `tf.Cover` — not with a model's verdict. That is the deliverable the spec's steps 2 to 4 are asking for, and it is the only version of it that can be tested without a live cloud.
3. **The model's review becomes advisory, recorded, and never the gate** (§4, D26). It still runs, it is still stored for audit, and the deterministic checks decide. A model that says `ship` about an out-of-scope plan must not apply it, and a model that says `changes` must not be the only thing that stops a plan the checks allow.
4. **Do not remove the coding-agent refusal; narrow it instead** (§3, **D21, the central decision**). The spec's autonomy is "an agent applies", and the program's one mechanical control is "an agent applies nothing". The honest version of managed mode is that the *apply* moves out of the agent's session: the run's agent proposes (writes the Terraform, opens the pull request), and a step that is not a coding agent — the runner's own privileged apply path, or an owner-run command at a terminal — performs the apply of a saved plan that passed the deterministic gate. That keeps the spec's "no prompts for cloud operations" for everything the gate covers and keeps the boundary the whole SECURITY.md threat model rests on.
5. **The hard stop needs a decision, not a design** (§4, D29). Disabling billing needs the Cloud Billing Budgets API, a Pub/Sub topic and a function that holds billing-admin. Fugaro's GCP budget today only emails (`budget.tf:11-36`), and there is no Budgets-API client in the tree. The alternative — no hard stop, alerts plus a spend cap — costs less privilege and is already built.
6. **Release after 0.8.0, as its own release, and never as a 0.8.0 task** (§7, D35). 0.8.0 is the compute-instance backend (`docs/design/generic-tool.md:312`; Check 57), and this design also depends on project-centric phases 1 and 3 for the project/repo boundary it presumes.

## 2. How this reconciliation was done, and what it refuses to accept

Two misreadings are worth naming before the findings, because the spec makes both.

- **"Humans rarely read plans, therefore a model review is a control."** The premise is about *attention*, and the conclusion is about *authority*. A model review is a second opinion from a system that shares a container, a user, a model and a context window with the thing it reviews (`runner.go:1559`, `:1038-1040`), and that reads attacker-writable text. The repo already reached the right conclusion about attention — that is why `tf.Cover` and `tf.Guard` exist: they are the checks nobody has to read. The reconciliation therefore **does not** treat the model review as a control anywhere, and §4 says what it should be instead.
- **"'Disposable' therefore 'safe to lose'."** Disposable is a property of the *compute*; the spec's own Disaster recovery and Secrets sections list what is not restorable (state, live counters, third-party keys). The reconciliation takes the spec's own list at its word and treats the loss surface as the finding (§6).

**The `belong` installation is never touched, and this design cannot touch it.** `belong` holds the owner's production-adjacent repositories `edgeappinc/edgeserver` and `edgeappinc/edgeweb` (`docs/design/project-centric.md:111`). The rule is already written into the design and the checklist: "**No agent ever touches `belong`**: every live step of this design is owner-run on `fugaro` and a sandbox repository" (`project-centric.md:111`), and every check from 48 onward carries Check 43's guard block with `--project fugaro` on every `fugaro` command (`docs/plans/2026-10-14-project-centric.md:63`, `:228`). **How this feature cannot touch it**, stated mechanically rather than as a promise:

1. `belong` predates the marker: it was created by hand, not by `fugaro init --create-project`, so a rule of the form "only a project whose creation this installation recorded is managed" (D24) gives it no marker and therefore **keeps today's confirmations there in full**. A managed mode that could be turned on for an existing project by editing a config file is the version of this design that is dangerous, and the reconciliation rejects it.
2. The detection is a read of the installation's own state and buckets (`infra.ReadProjectMarker`, `internal/infra/project.go:42-56`), which is scoped to the project named by the local config (`internal/localcfg`), and every live step of the plan is run with `--project fugaro` in a sandbox checkout under Check 43's guard.
3. Nothing in the plan adds a bulk or fleet-wide operation: every task touches one named project, and no task enumerates projects.

## 6. What the reconciliation refuses to accept from the spec

Three claims in the spec are not adopted, and this is the plain statement of each.

1. **"An agent that checks every resource change is the better reviewer."** Better than an *inattentive* human, perhaps; but the agent in question is the same model, in the same container, as the same user, as the coder that wrote the change (finding 8), and it reads text the configuration's author controls (finding 9). It is adopted as an **advisory, recorded** step (D26), never as the gate. The gate is deterministic (D27).
2. **"This is safe because a managed project is disposable … Even deleting the whole project loses almost nothing."** True of the compute and of the resources Terraform can re-create; false for the Terraform state bucket, which lives in that project (finding 31), for the spend history and kill-switch state in RTDB (finding 26), for anything older than the runs bucket's 90-day retention (finding 29), and for anything the project shares with a repository outside it — the case the spec's own non-goals carve out, and which is what `belong` is.
3. **"The prompts protect little, because humans rarely read Terraform plan output."** The premise is not contested. It is the reason `tf.Guard` and `tf.Cover` exist — checks nobody has to read. It is not a reason to replace the *authority* to apply, because attention and authority are different things; the fix for inattentive confirmation is a better gate, which is what §3 findings 5 and 6 already are.

## 7. Where this feature sits

- **Project-centric** ([project-centric.md](project-centric.md)): managed mode is a property of a **Fugaro project** (one GCP project, its Firebase project, its repositories, its people lists; `docs/design/v1.md` §1), and its marker is read with the same cloud-side, project-number-checked discipline the marker read already uses. It presumes project-centric phase 1's project-scope configuration and, for shared jobs, phase 3. It adds no RTDB node and no new layer (D37).
- **Compute backend** ([compute-backend.md](compute-backend.md), Check 57, release 0.8.0): nothing here depends on which backend runs a job; a managed apply is a step of the work, not of the execution environment.
- **The console** ([desktop-console.md](desktop-console.md)): unchanged and unchanged *by design* — read-only by allow-list, no credential, no backend (`:92-94`, `:139`). A managed project gives it nothing to write.
- **Release**: its own release, after 0.8.0 (D35).

## 8. Rules that bind every task in the plan

1. **Docs and code only; no live action.** No task applies anything to any cloud, and no task contacts a real project.
2. **Never handle a secret.** No task reads, writes, prints or transmits a secret value; secret *names* and metadata only.
3. **Never touch `belong`.** No task names `belong` as a target, and every check-shaped step runs with `--project fugaro` in a sandbox checkout under Check 43's guard (`docs/plans/2026-10-14-project-centric.md:228`).
4. **Fail closed.** A marker that cannot be read means "not managed", and a check that cannot run means "ask for confirmation" (`internal/infra/project.go:42-56` is the model).
5. **Nothing is approved.** Answering a D-number is not approving a task, and no task starts until the plan's OWNER APPROVAL GATE is passed.
