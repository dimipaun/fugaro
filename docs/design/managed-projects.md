## 1. Summary and recommendation

The spec asks for autonomy: in a project **Fugaro created**, the agent runs Terraform and other cloud operations end to end, with the agent reviewing each plan in place of a human, and with the plan and its review kept for audit. It justifies this with "a managed project is disposable" and with the observation that **humans rarely read Terraform plan output**.

The observation is true and the conclusion does not follow from it. The code already contains the machinery the spec is reaching for, and it already contains the control the spec would remove:

1. **The plan gate already exists, and it is deterministic.** `internal/infra/tf/guard.go` refuses any plan that deletes or replaces anything unless the exact address is named with `--allow-delete` (`Guard`, `guard.go:16-44`), and `internal/infra/tf/cover.go` decides whether a plan may share a confirmation at all — an allowlist of resource types (`allowedTypes`, `cover.go:15-47`), of the roles each `*_iam_member` type may grant and to whom (`grantRules`, `cover.go:63-112`), of every custom role's exact permission set (`RolePermissions`, `cover.go:169-182`), plus attribute checks: images in this run's registry, schedulers calling this run's jobs, a sink to this project, a private bucket, **the billing account the review showed**, and the project each resource lives in (`Cover.Projects`, `cover.go:127-154`; `attributes`, `cover.go:609-728`). This is exactly the "machine-checkable plan rules" the spec's step 3 wants, built for a different purpose and already wired into the apply path.
2. **The control the spec removes is real, and it is narrower than it looks — six environment variables, read at every CLI path that writes to the cloud.** Exactly: `internal/initflow/stage.go`'s `CanConfirm` returns `false` for **every** class when a coding agent's environment marker is present (`stage.go:334-342`), `AgentRefusal` names the marker and never offers `--yes` (`stage.go:298-304`), and `fugaro init`'s own help states both the control and its limit: "Under a coding agent's environment variable (`CLAUDECODE` and the like) init applies nothing, `--yes` included (**except `init --anchor`**, which only edits the checkout's `fugaro.yaml` and honours `--yes` there); that is a mitigation, not a barrier: an agent that unsets its own variables is not stopped, and **the real controls are the typed confirmations** and the skills' lint" (`internal/cli/init.go:376`); its own comment on `AgentAdvice` says it "stops the accident, not the adversary" (`stage.go:275-278`). The markers are `CLAUDECODE, CLAUDE_CODE_ENTRYPOINT, CLAUDE_CODE_SSE_PORT, CLAUDE_CODE_REMOTE, CURSOR_AGENT, AI_AGENT` (`internal/cli/initsecrets.go:132`). It is **not confined to `init`, and the list below is a grep rather than a sample**: `grep -rn 'agentMarker(\|agentEnv(' internal/cli --include='*.go'`, minus the two definitions at `internal/cli/initsecrets.go:136` and `:146`, finds **24 call sites in 15 files** — 17 through `agentMarker(os.Getenv)`, six through `agentEnv(os.Getenv)` and one through `agentEnv(getenv)`, the injectable form (`internal/cli/githubapp.go:63`, inside the `--check-github-app` helper the `getenv` parameter exists for) — and they do three different things, which is why “the refusal” has to be stated carefully. Every site is named below; a reviewer re-running the grep should get the same 24. **They refuse the command outright, before anything runs** (a `userErr`, or an `initflow.AgentError` the caller turns into one): `fugaro image build` (`internal/cli/image.go:169-171` builds the `Conditions`, the refusal is `:354-356`), `fugaro image refresh` (`image_refresh.go:382-384`, and again per billable build at `image_refresh_steps.go:215-217`), `fugaro image check --job` (`imagecheck.go:545-546`), `fugaro config publish` (`config_publish.go:36-38`), `fugaro recipes publish` (`recipes.go:332-334`), `fugaro init --retire` (`init_retire.go:568-570`), `fugaro init --publish-config` (`init.go:537-539`), `fugaro init --onboard-repo` (`init.go:702-704`), `init`'s own apply path (`init.go:1012-1014`, `ask`, and `init_review.go:143-145`, `askOrdinary`), and `--check-github-app` (`githubapp.go:60-67`, called from `init.go:499`, `:1896` and `doctor.go:208` — a secret *read*, refused before the value is touched). **They skip a cloud step and say why, without failing the command**: `fugaro upgrade` reads the marker at `internal/cli/upgrade.go:156` and passes it into the checkout, where the cloud step returns a *skipped* result naming the marker (`upgrade_cloud.go:463-470`); and `init`'s shared-config publish returns early with a note rather than an error (`init.go:1538`, called from `init.go:1530` and `:2786`, telling the reader to run `fugaro init --publish-config` in their own terminal — the first group's refusal, one command later). **And they suppress a confirmation rather than refuse anything**: `initflow.Conditions` is built with `Agent` at `init.go:972`, `init_stages.go:112` and `image.go:169` (the same read whose refusal is the one named in the first group, so it is one call site doing both); `runCovers` (`init_review.go:79`), `canType` (`init_project.go:263-266`), `canPrompt` (`initsecrets.go:200`) and `canConfirmRepo` (`init_repo_gate.go:105`) all return false under a marker; and four sites only reword what the user is told, refusing nothing and skipping nothing (`init_repo_gate.go:49`, `:113`, `initsecrets.go:467` — the secrets stage's own `canPrompt` fallback — and `initsecrets.go:514`). **The spec's “no prompts for cloud operations” removes the first group and the third**, which is why D55 is the central decision rather than a detail. What it still does not reach: **it does not stop an agent that runs `terraform` or `gcloud` directly with the operator's credentials**, and it is not the program's only control — the typed confirmations are the other, and `tf.Guard` and `tf.Cover` (finding 5 and finding 6) are the mechanical ones. **The owner answered D55 on 2026-10-16: the refusal is removed for a managed project. The consequence is recommendation 4 below, D55's row, and §6 item 4.**
3. **"An agent that checks every resource change is the better reviewer" is not what the reviewer is.** The review stage is a model call (`internal/runner/runner.go:1559`, `r.stage(ctx, "review", …)`) whose verdict is a two-valued string from a JSON schema (`internal/runner/verdict.go:13`), run in the run's own container, as the same user and the same process as the coder. **By default it is the same model as the coder**, and not through the recipe: `ModelFor` returns `agent.model` whenever `models.reviewer` is not set (`internal/config/config.go:216-225`), which is the default. Two recipes go further and *force* it — `roles: reviewer: coder` in `solo` and `lint-fix` (`internal/recipe/catalog/solo.yaml:5-6`, `lint-fix.yaml:5-6`), where a configured reviewer model is discarded, and `runner.go:1038-1040` logs exactly that. Of the other six catalog recipes, five carry no `roles:` block at all and **`premium` carries the inverse** — `roles: coder: reviewer` (`internal/recipe/catalog/premium.yaml:5-6`), which maps the *coder* to the reviewer rather than the reverse, a different direction this finding does not rely on. A control that cannot be independent of the thing it checks is not a control, however good the model is; and the text it reads (resource names, descriptions, the plan's own strings) is written by whoever wrote the configuration the plan applies. SECURITY.md already says of the same agent in review mode: a trusted author's own prompt injection "is still code execution under `--dangerously-skip-permissions`" (`SECURITY.md:70`).
4. **A managed project is not disposable in the way the spec means.** It holds the GCP billing budget's state and Fugaro's **spend history and kill-switch state in RTDB** (`internal/budget/model.go:30-38`, `:57-72`), the runs bucket (`runs/` records expire at 90 days and the bucket is **unversioned**, `deploy/terraform/gcp/modules/installation/bucket.tf:16-24`), and the **Terraform state bucket** — which by default lives *in the installation's own project* (`fugaro-tfstate-<gcp-project>`, `internal/cli/init.go:348`; `CreateStateBucket(ctx, c, spec.Project, …)`, `internal/cli/init.go:1198`). If the project dies, its Terraform state dies with it. "Deleting the whole project loses almost nothing" is wrong for the state, the spend history and the kill-switch state, for **the Firestore and RTDB application data** (a from-zero apply re-creates the databases, not their contents), and for **the Firestore database's permanent location** (`internal/cli/init_firebase.go:525-544`: it "can NEVER be changed"); and it is wrong for anything shared with a repository outside the project, which is precisely what the spec's non-goals exclude and what the `belong` installation *is*.

**Recommendation, in the order that delivers the spec's value safely.**

1. **The marker first, and the cloud is the authority** (§5, D56–D58). Make "Fugaro created this project" a fact recorded *at creation*, in the installation's own Terraform state and in a labelled marker object no credential a run holds can write (and, per finding 16, none a project-level storage role holds either — that is an IAM constraint the plan's Task 0.1 has to state and test, not an assumption) — not a project label alone (a project label is writable by any project editor, and this feature is about to hand the run more capability, not less), and not a project config in the repository (the agent writes to that repository).
2. **Keep the plan gate, and make it the gate** (§4, D60–D62). Managed mode replaces *the human's typed confirmation* with `tf.Guard` + a managed-project instantiation of `tf.Cover` — not with a model's verdict. That is the deliverable the spec's steps 2 to 4 are asking for, and it is the only version of it that can be tested without a live cloud.
3. **The model's review becomes advisory, recorded, and never the gate** (§4, D60). It still runs, it is still stored for audit, and the deterministic checks decide. A model that says `ship` about an out-of-scope plan must not apply it, and a model that says `changes` must not be the only thing that stops a plan the checks allow.
4. **The owner has removed the coding-agent refusal for a managed project, and the deterministic gate is what has to carry it** (§3, **D55, the central decision**). The owner answered D55 on 2026-10-16: **remove it for managed**. The managed apply therefore happens inside the agent's session and the human's typed confirmation is replaced by the gate, so this design's job changes from arguing against that to saying exactly what is left holding the line: **the plan gate** — `tf.Guard` refusing every delete or replace unless the exact address is named, on a list the **owner** writes and an agent cannot (`internal/infra/tf/guard.go:16-44`; a refused plan falls back to a confirmation, which in an agent's session means it does not proceed) — in a managed project that list is an object in the project's own runs bucket, written only by an owner-run command and read fail-closed, never the applying command's own `--allow-delete` (**D74**) — and the managed `Cover` refusing anything outside its allowlists (finding 6, D61); **the cloud marker**, the authority for *whether* managed mode applies, written only by an owner-run path that no credential a run holds can write (D56, D57 — answered the same day, the same way); **per-address owner approval for every delete and replace** (D72; where each approval lives, in what format, and who may write it is D74); **the budget** — an amount required at creation, no silent default, the existing alerts (D63, D64 — both answered); and **the scope rules** — never another project, never org-level IAM, never the billing link, never a secret value, never a billing-admin credential, never `belong` (D72). **The model's review is not one of them**: it stays advisory and recorded (D60, finding 8). **What makes the gate hold, and what does not**: it holds because it is a program in the apply path rather than a promise — it runs on the plan JSON before the apply, the apply requires the saved plan file, and the marker read fails closed — and it does **not** hold against an agent that uses the credentials it already shares with the runner. §6 item 4 states that residual risk plainly and is the paragraph to read before approving this. The shape this design recommended before the answer — keep the refusal, and make the separation real: the agent proposes, and the apply runs where no agent is, at an owner-run terminal or in a separate job with its own service account and no shared container — is D55's alternative column now, with its cost.
5. **The hard stop needs a decision, not a design** (§4, D63). Disabling billing needs the Cloud Billing Budgets API, a Pub/Sub topic and a function that holds billing-admin. Fugaro's GCP budget today only emails (`budget.tf:11-36`), and there is no Budgets-API client in the tree. The alternative — no hard stop, alerts plus a spend cap — costs less privilege and is already built.
6. **Release after 0.8.0, as its own release, and never as a 0.8.0 task** (§7, D69). 0.8.0 is the compute-instance backend (`docs/design/generic-tool.md:312`; Check 57), and this design also depends on project-centric phases 1 and 3 for the project/repo boundary it presumes.

## 2. How this reconciliation was done, and what it refuses to accept

Two misreadings are worth naming before the findings, because the spec makes both.

- **"Humans rarely read plans, therefore a model review is a control."** The premise is about *attention*, and the conclusion is about *authority*. A model review is a second opinion from a system that shares a container, a user, a model and a context window with the thing it reviews (`runner.go:1559`, `internal/config/config.go:216-225`), and that reads attacker-writable text. The repo already reached the right conclusion about attention — that is why `tf.Cover` and `tf.Guard` exist: they are the checks nobody has to read. The reconciliation therefore **does not** treat the model review as a control anywhere, and §4 says what it should be instead.
- **"'Disposable' therefore 'safe to lose'."** Disposable is a property of the *compute*; the spec's own Disaster recovery and Secrets sections list what is not restorable (state, live counters, third-party keys). The reconciliation takes the spec's own list at its word and treats the loss surface as the finding (§6).
- **"The runner can apply it instead of the agent, so the agent is out of the loop."** This is the one correction the design has to make against itself, and the owner's answer to D55 changes what it is used for. It is **not** a separation, because **the agent shares the container and the user with the runner**: it reads the runner's environment through `/proc` and the job's service account through the metadata server (`SECURITY.md:47-53`), so any credential an in-container apply path holds, the agent holds and can use directly, skipping whatever gate the apply path would have enforced. Before the answer, this design used that to argue that the apply must run **where no agent is** — an owner-run terminal, or a separate job with its own service account and no shared container, environment or filesystem. **The owner ruled on 2026-10-16 that the refusal is removed for a managed project (D55), so the managed apply *is* in the agent's session and that shape is now the alternative rather than the recommendation.** What survives is the consequence, and it is why the gate has to be mechanical rather than a promise: the runner is not a boundary the agent cannot cross, so nothing only the runner decides is safe to rely on. §6 item 4 states plainly what is protected and what is not.

**The `belong` installation is never touched, and this design cannot touch it.** `belong` holds the owner's production-adjacent repositories `edgeappinc/edgeserver` and `edgeappinc/edgeweb` (`docs/design/project-centric.md:111`). The rule is already written into the design and the checklist: "**No agent ever touches `belong`**: every live step of this design is owner-run on `fugaro` and a sandbox repository" (`project-centric.md:111`), and every check from 48 onward carries Check 43's guard block with `--project fugaro` on every `fugaro` command (`docs/plans/2026-10-14-project-centric.md:228`). **How this feature cannot touch it**, stated mechanically rather than as a promise:

1. `belong` predates the marker: it was created by hand, not by `fugaro init --create-project`, so a rule of the form "only a project whose creation this installation recorded is managed" (D58) gives it no marker and therefore **keeps today's confirmations there in full**. A managed mode that could be turned on for an existing project by editing a config file is the version of this design that is dangerous, and the reconciliation rejects it.
2. The detection is a read of the installation's own state and buckets (`infra.ReadProjectMarker`, `internal/infra/project.go:51-84`), which is scoped to the project named by the local config (`internal/localcfg`), and every live step of the plan is run with `--project fugaro` in a sandbox checkout under Check 43's guard.
3. Nothing in the plan adds a bulk or fleet-wide operation: every task touches one named project, and no task enumerates projects.

## 6. What the reconciliation refuses to accept from the spec

Three claims in the spec are not adopted, and this is the plain statement of each. **Item 4 is different in kind: it is not a claim the reconciliation refuses, it is the risk the owner's D55 answer accepts, stated so that nobody has to infer it.**

1. **"An agent that checks every resource change is the better reviewer."** Better than an *inattentive* human, perhaps; but the agent in question is the same model, in the same container, as the same user, as the coder that wrote the change (finding 8), and it reads text the configuration's author controls (finding 9). It is adopted as an **advisory, recorded** step (D60), never as the gate. The gate is deterministic (D61).
2. **"This is safe because a managed project is disposable … Even deleting the whole project loses almost nothing."** True of the compute and of the resources Terraform can re-create; false for the Terraform state bucket, which lives in that project (finding 31), for the spend history and kill-switch state in RTDB (finding 26), for **the application data itself — the Firestore and RTDB records a managed project exists to hold** (the budget ledger, the caps and the kill switches, `internal/budget/model.go:30-38`, `:57-72`, `internal/budget/kill.go:16-27`), which a from-zero apply re-creates the *database* for but not its *contents*, for **the Firestore database's location, which is permanent and can never be changed** (`internal/cli/init_firebase.go:525-544`: "a database's location can NEVER be changed", so a recreated project in another region is not the same installation and no restore can make it one), for anything older than the runs bucket's 90-day retention (finding 29), and for anything the project shares with a repository outside it — the case the spec's own non-goals carve out, and which is what `belong` is.
3. **"The prompts protect little, because humans rarely read Terraform plan output."** The premise is not contested. It is the reason `tf.Guard` and `tf.Cover` exist — checks nobody has to read. It is not a reason to replace the *authority* to apply, because attention and authority are different things; the fix for inattentive confirmation is a better gate, which is what §3 findings 5 and 6 already are.

4. **The risk D55 accepts, stated rather than argued away.** The owner removed the coding-agent refusal for managed projects on 2026-10-16, so in a managed project a coding agent's session applies cloud changes with no human prompt. The controls are the deterministic gate (`tf.Guard`, `tf.Cover` — never the model), the cloud marker, the per-address approval for deletes and replaces (an owner-written object in the project's own runs bucket, D74), the budget and D72's rules — and **not one of them is a boundary against an agent that does not go through the program**: the agent shares the container, the user, `/proc` and the metadata server with the runner (`SECURITY.md:47-53`), so it holds whatever the apply path holds, can run `terraform` or `gcloud` directly, and can call the apply path with a plan it wrote. **What the design does make hold**: the gate is mechanical and runs before the apply, so an agent driving `fugaro` cannot get an out-of-scope, delete-bearing or unallowlisted plan applied, and cannot authorize a delete of its own — what it may not remove comes from the owner's list, not from the command it runs (D74); the marker read fails closed, so an unreadable marker or one naming another project means “not managed”; and a refused plan falls back to a confirmation, which in an agent's session does not proceed. **What is not protected**: the plan is written by the agent (finding 22), so the gate is only as good as its allowlists — which is why D61 closes the checkable set and D62 blocks on names rather than on estimates; the marker lives in the bucket of the very project the agent is being given broad rights in, where any identity holding a project-level storage role can rewrite it (`SECURITY.md:36`, finding 16); and the refusal's own documented limit, “stops the accident, not the adversary” (finding 11), is the measure of what removing it gives up. **The narrower truth, stated last because it is the one that matters**: what the removal gives up is not a barrier that was working — it is the accident, an agent (or a person's agent) innocently driving `init` into an apply it did not mean to make. In a managed project that accident is now a designed outcome, and the gate is what has to make it a safe one.

## 7. Where this feature sits

- **Project-centric** ([project-centric.md](project-centric.md)): managed mode is a property of a **Fugaro project** (one GCP project, its Firebase project, its repositories, its people lists; `docs/design/v1.md` §1), and its marker is read with the same cloud-side, project-number-checked discipline the marker read already uses. It presumes project-centric phase 1's project-scope configuration and, for shared jobs, phase 3. It adds no RTDB node and no new layer (D71).
- **Compute backend** ([compute-backend.md](compute-backend.md), Check 57, release 0.8.0): nothing here depends on which backend runs a job; a managed apply is a step of the work, not of the execution environment.
- **The console** ([desktop-console.md](desktop-console.md)): unchanged and unchanged *by design* — read-only by allow-list, no credential, no backend (`:92-94`, `:139`). A managed project gives it nothing to write.
- **Release**: its own release, after 0.8.0 (D69).

## 8. Rules that bind every task in the plan

1. **Docs and code only; no live action.** No task applies anything to any cloud, and no task contacts a real project.
2. **Never handle a secret.** No task reads, writes, prints or transmits a secret value; secret *names* and metadata only.
3. **Never touch `belong`.** No task names `belong` as a target, and every check-shaped step runs with `--project fugaro` in a sandbox checkout under Check 43's guard (`docs/plans/2026-10-14-project-centric.md:228`).
4. **Fail closed.** A marker that cannot be read means "not managed", and a check that cannot run means "ask for confirmation" (`internal/infra/project.go:51-84` is the model).
5. **Nothing is approved.** Answering a D-number is not approving a task, and no task starts until the plan's OWNER APPROVAL GATE is passed.
