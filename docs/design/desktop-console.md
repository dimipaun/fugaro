## 1. Summary and recommendation

The console is **a graphical `fugaro watch` that adds spending graphs and project views, and it gets every byte of its data from the CLI it already has.** It has no backend, no service account, no database client and no credential of its own. It spawns the installed `fugaro` binary as a child process, reads that process's JSON output, and draws it. Nothing in the console may write to the cloud: the writes an operator wants (kill, resume, cancel) are the CLI's own commands, with the CLI's own ETag-guarded compare-and-set and its own typed confirmations.

That single decision — **the CLI is the data plane** — answers most of the questions the spec's section 6 leaves open, and it is the reason the console can be built at all without a new backend:

1. **It reuses exactly what `fugaro watch` and the budget dashboard read.** The four RTDB event streams, the Firestore `spendDaily` documents and the runs bucket are read by the CLI, under the operator's own identity, through the code `watch`, `budget` and `report` already ship. The console adds no path, no field and no reader (§2).
2. **It never sees a secret.** No command the console invokes copies a secret value to the machine (`SECURITY.md`, "Cloud keys stay in the cloud": "No command copies a secret value back to your machine, and `fugaro secrets` never prints one"). The allow-list is by **exact argument list**, and that is what makes this true rather than approximately true: it admits `secrets ls --json` — metadata only, "it has no access call at all" — and excludes every command that can read or write a *value*, including `doctor --check-github-app`, which reads the App's private key out of Secret Manager with the operator's own credentials (§5.1's two tables).
3. **Its access is exactly `fugaro watch`'s access**, because it *is* `fugaro watch`, one layer up: the same operator, the same gcloud/Firebase identity, the same roles — `roles/firebasedatabase.viewer` and `roles/datastore.viewer` for launchers and operators, and `roles/firebasedatabase.admin` for the project's owners, editors and budget admins, all granted by `deploy/terraform/gcp/modules/firebase/iam.tf` (§3). **That last one is a write-capable identity, and the design says so** (§3.4 rule 6, **D14**): what keeps the console read-only is the allow-list and the absence of a write path, not the credential.

The one place this design disagrees with the repo's own instincts is worth stating up front. **tmog.org markets itself on not being Electron** — its own "why" page says, in its list of facts, "No Electron, no web view, no embedded browser", and its three hosts are Swift/AppKit, C++/Win32 and C++/Qt 6 over one shared C++20 core. The owner's spec asks for Electron and names tmog.org as the *visual* inspiration, so this design takes the information design and the engineering honesty from tmog.org and none of its technology — and it takes one of its principles as a hard requirement of our own (§6.1). If the owner wants tmog.org's actual posture (native shells over a shared core), that is a different, much larger design, and it is decision **D8**.

## 2. Data sources: exactly what the CLI already reads

The console reads **no cloud service directly**. Its inputs are the JSON of the CLI's own read-only commands. What follows is therefore (a) the commands the console consumes, and (b) — because the owner asked for it — the underlying RTDB/Firestore/bucket paths those commands read, with who may read each under the rules.

**Two shapes, not one, and the console must handle both.** The live document is `JSONDoc` (`internal/watch/json.go`, built by `BuildJSON`). **The no-Firebase mode emits an entirely different document**: `watchDegradedDoc` in `internal/cli/watch.go` is `lsDoc` (`{project, runs, totals, warnings}`, from `internal/cli/runs.go`) **embedded and flagged** — `{"degraded": true, "notice": "…"}`. Nothing in it has a cap, a burn rate, a kill state or a repository block, because none of those exist without the database. **A screen that expects `JSONDoc` and receives `watchDegradedDoc` must not render zeros for the missing half**; the two are distinguished by the `degraded` flag, and the design's §6.3 table is what each becomes on screen.

**`--repo` narrows the JSON too.** An earlier draft of this design said `--json` is "always unfiltered"; that is wrong. The flag reaches `watch.FilterRepo(v View, key string)` (`internal/watch/json.go`), called from `internal/cli/watch.go` when the repository key is set, so `watch --json --repo R` emits only `R`'s runs and repository block. What *is* always unfiltered is the other axis — the finished-run and ready-for-review lists ignore `--all`/`--keep`/`--keep-count`. The console therefore passes `--repo` **only** when the operator has filtered the Live screen, and remembers that the result is narrowed.

**And there is a line of the live feed that is not JSON at all.** In the degraded mode, `runWatchDegraded` handles a transient read failure by printing a plain sentence to **stdout**, on the same stream as the documents: `"%s\nrun records unavailable (retrying): %s\n"` (`internal/cli/watch.go`). A consumer that decodes stdout line by line as NDJSON will choke on it — so the console's reader must **skip any line that is not a JSON object** and surface it as a warning in the header rather than as a parse error or a crash. This is also one of the CLI changes v1 truly wants (§4.3): that message belongs on stderr.

**`watch` is not only a database reader.** Besides the four RTDB streams it scans the **runs bucket** for the two lists a live view needs and no database has: the runs that are queued or claiming and the runs that have finished in the last 24 hours. `internal/cli/watch_queued.go` (`openQueueBucket`, `scan`, `scanRepo`, `scanRun`) lists `runs/<slug>/<run>/` through `blobx.Open(lc.BucketURL())` and reads `task.json`, the `launching` claim, `launch.json` and `result.json` (plus the `cancel` marker), folding them into `watch.QueuedRun`, `watch.FinishedRun`; **the per-run reader it calls, `readRun`, is not in that file — it is `internal/cli/runs.go`, shared with `fugaro runs ls`**, which an earlier revision of this sentence got wrong. Those become `queued`/`stuck` on a run row and the `finished[]` and `ready[]` arrays of the JSON document. **That means the console inherits a bucket dependency as well as a database one** — and it is the reason the console's run list can show "queued but not started" and "ready for your review" at all, two rows the RTDB alone cannot produce. It also explains a fact the console's install story must state: a `fugaro` that can read the database but not the bucket shows a live view with those sections empty rather than wrong.

The JSON shapes are a real contract, not an accident: `internal/watch/json.go` declares them as named types — `JSONDoc`, `JSONTotal`, `JSONRepo`, `JSONRun`, `JSONKill`, `JSONBurn`, `JSONConn`, `JSONFinished` — and `BuildJSON` is their single constructor. **What proves `--json` exists is not a repo-wide test but the cobra command itself**: each command above declares its own `--json` flag, and the design names the flag and the document type for each (the table in §2.1, §12 item 1). `internal/cli/json_everywhere_test.go` is much narrower than an earlier revision of this paragraph claimed — it holds **three** tests, covering `init` twice and `doctor` once (`TestInitJSONOnARefusalBeforeAnyStage`, `TestInitJSONPrintsOneObject`, `TestDoctorJSONWithAnInvalidLocalConfig`) — so it is evidence of a convention, not of coverage, and it is worth having for the shape of the assertion rather than its breadth. **The console pins the schema version it was built against and refuses to guess** (§7.1): a field it does not know is ignored, a field it needs and does not find is `unavailable`, never a zero (the same rule tmog.org states and `watch` already follows — the registry's live shape has no `round` or `spent` until a run reports them, and `watch` shows `-` for an absent field, `m9-budget-and-dashboard.md` §7).

### 2.2 The RTDB paths behind `watch`, and who may read them

The tree, its fields and the rule that governs each node, from `m9-budget-and-dashboard.md` §6.2 and §6.4, whose generator is `internal/budget/rules/rules.go` over the template `internal/budget/rules/rules.json.tmpl` (golden file `internal/budget/rules/testdata/rules.golden.json`; parity in `internal/budget/rules/parity_test.go`; emulator cases in `emulator_test.go`, `lease_emulator_test.go`, `harness_test.go`).

**Two different notions of "who may read", and the console must not confuse them.** A **run token** is what a run holds (`auth.token.fs`/`fr`/`fx`, minted by the launcher, `m9-budget-and-dashboard.md` §6.4); the rules bound it per node as the table shows. A **launcher or operator** holds no run token at all: they hold IAM, and for anyone who is not a budget admin its whole extent is four grants — `roles/firebasedatabase.viewer` (`google_project_iam_member.viewer`), `roles/datastore.viewer` (`google_project_iam_member.datastore_viewer`) and `roles/serviceusage.serviceUsageConsumer` (`google_project_iam_member.usage_consumer`, `for_each = setunion(local.people, local.admins)`, whose comment explains it is the quota project the Firestore client sends as `X-Goog-User-Project`) on the Firebase project, plus the custom role **`fugaroTokenMinter`** (`google_project_iam_custom_role.token_minter`, `iam.serviceAccounts.signJwt` and nothing else) **on the signer account**, not at project level. **A budget admin holds a fifth**: `roles/firebasedatabase.admin` (`google_project_iam_member.admin`, `for_each = local.admins`) is granted to `local.admins`, the set `(var.admins, var.budget_admins)` — which is the whole reason the admin can write `/config` at all (D14), and why the console treats every identity as a possible admin rather than trying to tell them apart. All of them are in `deploy/terraform/gcp/modules/firebase/iam.tf`; the grant table is `m9-budget-and-dashboard.md` §6.1. The third one is not incidental to this console — it is a role `report` needs, and its absence is one of the remedies the CLI's own permission error prints (§6.3). **IAM is not subject to the database rules**, so a viewer sees every node the table's third column marks "yes" — including every repository's counters and registry entries, which is exactly what `fugaro watch` shows today. The console inherits that reach and nothing more.

The console must also be honest about what a launcher can reach *besides* the database, because the projects screen shows inventory: `SECURITY.md` records that the `fugaroLauncher` custom role "additionally lets any launcher list every secret in the project (names, labels and version counts; reading a value still needs `secretAccessor`, which only the job and build accounts hold)". A names-only inventory is therefore something the operator can already obtain; **the console shows secret names, scope and version counts and never a value.** Its one source is `fugaro secrets ls`, whose own doc comment is the guarantee — it "reads metadata only: it has no access call, so it can't print a value" — and whose allow-list entry is `secrets ls --json` with **`--repo R` or `--project-wide` always passed explicitly** — with neither, the command resolves "this checkout's origin", which a Finder-launched app does not have (§3.4 rule 3, §5.1's authoritative table; an earlier revision of this sentence wrote the argv without them and contradicted that table). Every other `secrets` subcommand (`get`, `set`, `rm`, `copy`, `check`) is unreachable, by name and by argument list.

### 2.3 Firestore, the runs bucket and what `report` reads

- **Firestore `(default)` database, collection `spendDaily`**, documents `<YYYY-MM-DD>_<slug>`: `repo`, `slug`, `date`, `spentMicros`, `notionalMicros`, `computeMicros`, `unreconciledMicros`, `overrunMicros`, `runHours`, `calls`, `runs`, `outcomes{succeeded,failed,halted,cancelled,infra_error}`, `byModel{<model>:{micros,in,out,cr,cw}}`, `byPerson{<requested_by>:{micros,notionalMicros,runs}}`, `capDailyMicros`, `final`, `version`, `archivedAt`, `writtenAt`, and the mark document `meta/installation` (`m9-budget-and-dashboard.md` §6.2). **Read by the operator's IAM** (`roles/datastore.viewer`) — the Firestore rules deny everything and only IAM principals read or write. This is the console's spend history, reached through `fugaro report --json`.
- **The runs bucket** (`fugaro/` objects, `runs/<slug>/…`): `task.json`, `result.json`, `launch.json`, the log references, `check.json`. Launchers hold `roles/storage.objectViewer` on the whole bucket (and a `roles/storage.objectUser` conditioned on `runs/` since the 0.7.0 hardening, and on `runs/` and `tokens/` since 0.9.0's sealed budget token, `SECURITY.md` and [bucket-iam.md](bucket-iam.md) §10). The console reaches this through `fugaro runs ls --json` and `fugaro logs`, not directly.
- **`byPerson` and identity.** Firestore keeps the requesters' addresses indefinitely and only IAM viewers can read them; `report --by person` shows them. This is the one place the console displays something personal, so it is the one place with a switch — and it is decision **D15**: the person view is off by default in the console even though the CLI prints it, because a shared screen is not the same as a terminal.
- **Live logs: bounded lines in, transcript linked out.** These are two different things and an earlier revision of this design ran them together. The run-detail screen's log panel reads **`logs RUN --json`** — one JSON object per line — under a **hard console-side line cap and a timeout** (§5.1), so what is on screen is a capped window of structured lines (`time`, `severity`, `stage`, `stream`, `event`, `message`) and not a body. The **full log view is linked, never embedded**: `logs RUN --url` (its own argv, never combined with `--json`) opens the execution's Cloud console page, and the console never spawns `--follow`. Logs are per-run, large, and redaction is best effort — which is why the cap exists and why the transcript stays in the browser.

## 3. Authentication: three options, priced

The requirement is that the app acts **as the signed-in operator, with the same read-only access `fugaro watch` has**, that it **never reads or stores a secret**, and that it **never writes**.

### 3.1 Option A — the CLI as a sidecar (recommended)

The Electron main process spawns the installed `fugaro` binary and reads its JSON. The child runs with the **fixed, minimal environment of rule 5 below** — not the app's environment wholesale — and uses whatever identity `fugaro` already uses for that project, the same path `fugaro watch` takes to `roles/firebasedatabase.viewer`: the cloud SDK finds the operator's credentials in their home directory exactly as it does in a terminal, and the app never hands it a credential variable. Which project "that project" means is not left to the environment either — the app passes `--project` explicitly (rule 3, **D13**).

- **Credential story:** the console holds none. The CLI holds none either — it presents the operator's ambient cloud identity, and no Fugaro command copies a secret to the machine. Nothing about the operator's identity is stored in the app: no token, no key, no config copy.
- **Read surface:** identical to `fugaro watch` by construction, because it *is* `fugaro watch` — with the three things the app must add to reproduce a terminal: an explicit `--project` **on every command that takes one** (all of them but the `version` handshake, which takes no flags at all), an explicit working directory, and an explicitly resolved binary path (§3.4 rules 3 to 5).
- **Write surface:** none. The allow-list is an explicit list of exact argument lists, all read-only (§3.4, §5.1) — and it is the *only* thing that makes the console read-only when the operator is an admin, because that identity holds `roles/firebasedatabase.admin` and IAM bypasses the rules (§3.4 rule 6).
- **Cost:** the console must resolve the binary itself; the JSON schema becomes a compatibility contract (§7.1); a child process per data source is more overhead than one HTTP client; and the console's release train must stay near the CLI's.
- **Why it wins:** it is the only option that satisfies "reuse exactly what `fugaro watch` and the budget dashboard read, no new backend" literally rather than approximately. Every future improvement to a data source (the phase-1 policy object, the compute-backend cost rows, the `budget show` cap source) reaches the console with a CLI release, and **no reader is written twice**.

### 3.2 Option B — direct RTDB/Firestore from the app (rejected)

The app embeds the operator's credentials (Application Default Credentials, or a Firebase token) and speaks to RTDB's REST API and Firestore itself.

- **Cost:** the app must reimplement the RTDB REST client with its streaming and its ETag semantics, the Firestore query, the burn-rate computation, and — critically — the **sanitization of job-written text** (`watch`'s rule that every job-written field is stripped of control and escape characters and clipped, `m9-budget-and-dashboard.md` §7). A missed sanitization in a *renderer* is a script-injection, not a mangled terminal line.
- **The disqualifier:** it puts a cloud credential inside a Chromium process whose entire purpose is to render untrusted, job-written strings. That contradicts this design's own hard rule (§5.1), contradicts the "never read or store a secret" requirement in spirit (an OAuth token in an app's userData *is* stored material), and buys only latency.
- **Verdict:** rejected. If it is ever revisited it would have to be as Option C, not as this.

### 3.3 Option C — a local read-only API served by the CLI (the designed evolution)

`fugaro console serve --listen 127.0.0.1:<port>` serves the same JSON over loopback, and the app is a thin client. It is Option A generalised: the same reader, the same identity, one process instead of one per screen.

- **What it must have to be safe:** loopback-only binding; a per-launch bearer token the CLI prints and the app must present; `Origin`/`Host` checks; no CORS; and the same read-only surface — the exact-argv table of §5.1, which is the authoritative one, with §3.4's rules unchanged.
- **Why it is not v1:** it adds a listening socket to the CLI, which is a new attack surface for a program that today only makes outbound calls. That is a real cost for a benefit (less spawn churn) that v1 does not need.
- **Why it is designed now:** so that v1 puts its data access behind one interface (§8.2) and C can replace A without touching a single screen.

### 3.4 The recommendation

**Option A for v1, behind an interface that makes Option C a drop-in replacement; Option B never (D1).** Concretely, and enforceable in review:

1. The console spawns **one** binary, from a **fixed list of read-only command lines**, with `shell: false` and arguments passed as an array — never a shell string, never a command built from a job-written field.
2. **The allow-list is by exact argument list, not by command name** (§5.1). A name is not enough: `doctor` is read-only with no flags and reads a private key out of Secret Manager with `--check-github-app`, `logs` is a bounded read and a tail with `--follow`, and `watch` is a stream and a server-side narrowing with `--repo`. §5.1 is the table; this section only fixes the principle.
3. **The project is passed explicitly, and the earlier ban on `--project` was wrong** — but "on every spawn" was wrong too, and this is the correction: **`--project` goes on every allow-listed argv that has a project to name, which is every entry in §5.1's allow-list except two: `version`, which takes no flags at all, and the picker's own read, `config list --json`, which lists this machine's installations and needs no project selected to do it.** The CLI does not discover the project from the environment alone: `internal/cli/project.go`'s `selectWith` builds a `localcfg.SelectInput` from the `--config`/`--project` flags, `$FUGARO_CONFIG`/`$FUGARO_PROJECT`, and the **working directory's checkout** (`checkoutProject`), falling back to the shared config when `sharedOK`. An app launched from Finder has none of those: its working directory is `/`, which is nobody's checkout; it inherits launchd's environment, not the shell's, so `FUGARO_PROJECT` and the cloud SDK's variables are absent; and its `PATH` is the system's. With the owner's two installations, "the only config" does not select the sandbox — or selects the wrong one. **So the console passes `--project <name>` (the installation's project name, from its own local config) and `--config <path>` (when the installation is not the one the ambient environment would pick) on every allow-listed command that accepts them: `watch`, `budget show`, `report`, `runs ls`, `diagnose`, `logs`, `secrets ls`, `accounts ls`, `doctor` and `plan status`.** The picker's `config list --json` is the second exception and needs no argument at all: the read is the *list of installations*, so there is no installation to name yet, and `newConfigListCmd` is `cobra.NoArgs` with one flag of its own (`--json`); it opens no bucket and works with no config at all (§2.1, §5.1 rule 6). `version` is the other exception and is not a special case invented here: `newVersionCmd` is `cobra.NoArgs` with no `Flags()` at all (`internal/cli/root.go`), so `fugaro version --project X` is an unknown-flag error and a handshake that passed it would fail on every machine. That is the same fact `docs/gcp-live-checklist.md`'s Check 43 guard already states — "**`fugaro version` is the one exception** — it takes no flags at all" — which is where the console's spawn table gets it from. An earlier revision of this rule said "on every spawn" and made the handshake impossible; §5.1's table is the authority and its `version` row carries the same note, as does the picker's row. That is not a credential — a project name is a name — and it is the only way the console can be sure which installation it is showing. See **D13**.
4. **The binary is resolved explicitly, never through the app's `PATH`.** The console looks, in order, at **the optional override a store already carries** — the `binaryPath` field of an existing `installations.json` entry (`INSTALLATION_KEYS` in `console/src/main/installations.ts`), kept working and never asked for (§5.1 rule 10) — then at the well-known install locations (`/opt/homebrew/bin`, `/usr/local/bin`, `~/.local/bin`, `/usr/bin`), **and nowhere else: the app's own inherited `PATH` is not searched at all** (owner's ruling of 2026-10-20; the parameter was removed from `binDirectories`, so the step cannot come back without changing every caller). It shows the absolute path it resolved and the version it got, and refuses to run a binary it cannot identify. A Finder-launched app's `PATH` is not the shell's, so a console that resolved through it would run whatever the app happened to be launched with — which is nothing the operator chose, and not a place anything is *installed*. The override is a candidate and not a pin: an entry whose stored path has gone falls through to the well-known locations rather than refusing, because **the console resolves the `fugaro` that is installed**. The first run asks the operator for no path at all: when none of the locations holds a `fugaro`, the screen that follows is §4.4's absent-binary screen. **Amended 2026-10-20 by the owner's ruling (D10, §7.6): Linux resolves against its own well-known locations, in this order — `/usr/local/bin`, `/usr/bin`, `~/.local/bin`, `/home/linuxbrew/.linuxbrew/bin`, `~/.linuxbrew/bin` — and `/opt/homebrew/bin` is not among them.** It is the macOS Homebrew prefix, Linux's equivalent installations are Linuxbrew's two directories, and a directory that does not exist on the machine is not a place to look for a binary. Both platforms' lists are one table in the app (`PLATFORM_LOCATIONS` in `console/src/main/spawn.ts`, read through `locationsFor`), so a third platform is a row rather than an edit in each place that needs one, and neither platform can take the other's per-user Homebrew prefix.
5. **The sidecar's environment and working directory are stated, not inherited.** The console passes a **fixed, minimal environment** — `PATH`, `HOME`, `TMPDIR`, the `XDG_*` variables, `LANG`/`LC_ALL`, and the chosen installation's `FUGARO_PROJECT` — and passes nothing else from the app's own environment. **The `PATH` is stated exactly, because "the resolved prefix" alone was wrong** (round 4): it is the resolved binary's own directory **first**, then the well-known tool prefixes the console resolves against in rule 4 — `/opt/homebrew/bin`, `/usr/local/bin`, `/usr/bin`, `/bin`, `/usr/sbin`, `/sbin` — and it is never the app's inherited `PATH`. The reason the extra prefixes are there is that **the CLI looks up external tools itself**: `doctor` resolves the SDK tools its checks need with `exec.LookPath` (`internal/cli/doctor.go:147`, used by its terraform check and its cosign problems), and `terraform`, `cosign` and the rest do not live in the same directory as the `fugaro` binary even under Homebrew. A child given only the resolved binary's directory would make `fugaro doctor --json` report those tools as missing on a machine that has them, and **the environment view would be a false description of the environment** — the one thing a screen built on `doctor` must not be. So the child's `PATH` is a fixed list that contains every prefix the console itself would accept a tool from, and **what is outside that list really is invisible to the child**: the environment view renders such a problem in exactly those terms — *not on the PATH the console gives the CLI*, listing the prefixes and the remedy (install it under one of them, or link it there) — and never as "not installed", because the console cannot know what the operator's shell has. A tool the operator has on a path none of those cover is the same class of gap as an installation outside the well-known prefixes in rule 4, and the design treats it the same way: named, with the remedy, rather than papered over. It adds no credential variable of any kind, and in particular never sets `GOOGLE_APPLICATION_CREDENTIALS`. The cloud SDK finds the operator's identity the way it does in a terminal, from their home directory. **The child's working directory is set explicitly as well, and the earlier silence on it was a real defect**: a GUI app's default cwd is `/`, which is nobody's checkout, and commands that resolve something *relative to the checkout* then answer from nowhere. `secrets ls` and `accounts ls` are already pinned to a repository by `--repo` (rule 3), but **`doctor` is not**: its `--dir` flag defaults to `.` and a directory outside a checkout makes it emit a `plugin-pin` warning — "`<dir>` is not in a checkout (no `.git` above it), so the Fugaro plugin wiring cannot be checked" (`internal/cli/doctor.go`), which `--strict` turns into a failure. So the installation triple of D13 optionally carries **the checkout directory** — the sandbox checkout, for the owner — the child is spawned with that `cwd`, and `doctor` is called with `--dir <that directory>`. **An installation with no directory is a supported state, not an error**: the console spawns from a private, empty directory it owns (never `/`, never the app bundle, never the operator's home) and renders `doctor`'s plugin check as the informational *no checkout* state it is — which is also why the console calls `doctor --json` and never `--strict`, whose exit code is about a checkout's plugin wiring rather than about the environment the console draws. **Amended 2026-10-20 by the same ruling (D10, §7.6): on Linux the child's `PATH` is the resolved binary's own directory first, then `/usr/local/bin`, `/usr/bin`, `/bin`, `/usr/sbin`, `/sbin`, `/home/linuxbrew/.linuxbrew/bin`** — Linuxbrew's system directory in place of the macOS `/opt/homebrew/bin`, which is not on a Linux child's `PATH` at all — and `~/.linuxbrew/bin` is a candidate for rule 4 rather than an entry here, because nothing expands a `~` inside a `PATH` and the per-user case is already covered by the resolved binary's own directory, which the child's `PATH` always puts first.
6. **The identity is not read-only, and the console cannot tell whether it is — two separate facts, and an earlier revision of this rule ran them together.** `deploy/terraform/gcp/modules/firebase/iam.tf` grants `roles/firebasedatabase.admin` (`google_project_iam_member.admin`) to `local.admins` — project owners, editors and budget admins — and **IAM bypasses the RTDB rules**, so for those people the CLI can write caps, kill switches and the `runs/` ledger. What *prevents* a write is not the identity; it is the allow-list in §5.1 and the absence of a write path in the app. **But no read-only command reports the caller's role, so the console must not claim to know it.** An earlier revision said the CLI already distinguishes the case; it does not: the one admin-related sentence — `AdminDeniedText`, "you are not a budget admin for project X: only the GCP project's owners and editors and terraform.budget_admins may change caps and kill switches…" (`internal/budget/kill.go`) — is produced **only as the refusal of a write**, which the console never issues, and `budget show --json`'s `mode` is `/config/mode` (`observe` or `enforce`), a property of the *project*, not of the credential (`internal/cli/budget.go`). So **D14**'s recommendation is now the opposite of the one this rule first carried: treat every identity as potentially an admin, show no role in the header, and rest the read-only guarantee on the allow-list alone. A read-only "am I an admin?" check would be a new CLI command with a new IAM read and is not needed for v1 — the console behaves identically either way — so it is not one of §4.3's gaps.
7. The console never stores a credential, never reads `~/.config/fugaro` itself, and never passes a flag the renderer chose. **The installation list is read from the CLI, never from the config directory** — the console runs `fugaro config list --json`, a read-only, offline document of every project config on the machine with its GCP project, its region, whether a shared config was merged and when the shared copy was last checked, and its `checkouts`: one entry per path this machine remembers for the project's repositories, each carrying the repository identity, the path, whether the project's own config enrolls that repository, whether it is still a checkout of that project and that repository, and a reason code when it is not (`internal/cli/config_list.go`, the read D13 names; the console v2 plan's V2.1.1 is where it was settled and §4.3 gap 5 records it as closed). The command is the only thing that reads `~/.config/fugaro`, and the app still never opens it — this rule is unchanged in what it forbids. The paths in that document are local state and are re-validated on the read: a path that has moved, is no longer a checkout, or whose `fugaro.yaml` names another project is reported with `valid: false` and a reason code rather than dropped. **And nothing in that document is a path the console acts on — with one exception, stated exactly, added 2026-10-20.** A directory the app **opens, reads, writes, executes or hands to a command other than the allow-listed reads** is one the operator typed or chose (D13's form), never one that arrived in a JSON field, so a stale or hostile entry in the machine's own state file cannot redirect a spawn. The exception is the one the console v2 plan's V2.1.1 needs and the JSON contract's §6.8 states in the same words: **a row carrying `valid: true` may be used as the child's working directory for a command from §5.1's exact-argv allow-list, and for nothing else.** Such a row is an absolute path the CLI has just re-validated as a git checkout of that installation's project and of a repository that project enrolls, so it is a directory the CLI itself would have resolved; a row with `valid: false` — whatever its reason, including one whose path had to be escaped or truncated for printing, which is `not_representable` — is never used for anything, not even as a working directory, and the operator's stored directory stands instead. **Which of those rows the console *offers* the operator is a narrower question than which it may use, and the answer was narrowed again on 2026-10-31** (the owner's ask: "an installation can have multiple repos, I should be able to pick one with a dropdown"). The chooser offers **one entry per repository** whose row is `valid: true` **and** `enrolled: true` — a row the CLI did not re-validate, or that this installation's own config does not enroll, is never offered and never used — labelled with the repository identity and a short directory, and the directory it sends is written by the same `installation.checkout` operation the picker's own control uses, so it is re-validated on use by the pairing check below like every other one. `enrolled` is read as a second half of the verdict rather than assumed from `valid`, even though the CLI's own `valid` already implies it, because the two are separate fields of the document (§6.8) and a reader that leaned on one implying the other would offer a row the day they diverge. The prohibition this rule was written for is intact: **the app never opens, joins, stats, copies or deletes anything at a path from this document**, and it never passes one as a flag or an argument to a command the allow-list does not carry. The form-based add-an-installation screen of D13 stood until the console task landed; the picker now carries the row for `fugaro config list` in §5.1's spawn table (the amendment below). **And the pairing is checked before an installation is stored**, because the CLI would otherwise refuse every command for it: with a checkout directory chosen, the add-an-installation screen runs one allow-listed read against that installation — the checkout as the child's working directory, `--project` as typed — and if the checkout's `fugaro.yaml` names a different project the CLI refuses with `this checkout belongs to project %s; --project says %s` (`internal/localcfg/select.go`, reached from `checkoutProject`/`selectProject` in `internal/cli/project.go`); the screen shows that sentence verbatim and does not save the installation. The app still never reads the config itself (this rule); **the CLI is the one that reads it**, which is also why the check cannot be done in the renderer. **And this prohibition is a test rather than a sentence**, like every other rule on this list: the plan carries a named test over `console/src/` asserting that nothing there reads the operator's config — no `~/.config/fugaro`, no `FUGARO_CONFIG`-derived path, no `XDG_CONFIG_HOME` join, no `readFile` of any of them — with the one distinction the rule turns on: **the config's path may be a string the operator typed or the installation stored** (it is passed as `--config` and `FUGARO_PROJECT` to the child), but **the app itself never opens it**, because it is read in the main process, outside the IPC surface rule 5 covers, and reading it is precisely the shortcut D13 forbids (it would answer "where do the installations come from" the one way this design says it must not). **Amended 2026-10-20, by the owner's ruling, and the amendment supersedes the two clauses above that name a screen.** The console asks the operator for **nothing**: not the binary, not the config. So there is no add-an-installation screen, no file picker for a binary and no typed project name — the list the screen draws is `fugaro config list --json`, which is the CLI's own enumeration of the installations on this machine (`console/docs/json-contract.md` §6.8), and **one click opens a row**. The pairing check stays exactly as it is written here, and moves to where it now belongs: it runs when a **checkout directory is set for an installation** — the one place a repository is asked for, at the moment a screen genuinely needs one — and it is unchanged in every other respect (one allow-listed read, the checkout as the child's working directory, the installation's `--project`, the CLI's sentence shown verbatim and nothing stored) **except that it is asked of the installation's own CLI**: the same two facts a choose is probed with — the record's `binaryPath` as rule 4's first candidate, and its `configPath` as the `--config` — so a checkout is never validated by a `fugaro` the console would not drive, and an installation whose only `fugaro` is its own override is not refused. The form's channel rows are gone with the form: the picker's surface is `list`, `choose`, `checkout`, `remove` and the one link, and `test/unit/installations-view.test.ts` fails if a form control comes back.
8. `fugaro version` is the handshake (§7.1): the console knows which CLI it is driving, and says so in its header.

## 4. v1 scope

### 4.1 In

1. **Live runs** — the default screen: the project line, each repository's cap bar and burn rate, and each run's stage, round, models, spend and age, with `silent` (>60 s without a heartbeat) and `lost` (>3 min) flags, and the stage-deadline amber past 80%. This is `fugaro watch`'s live view, at a window size a terminal cannot have.
2. **Spend graphs** — over time (`day`/`week`/`month`), by repository, by model, and with `~$` kept visibly separate from real dollars and compute kept separate from both (the "one account of cost" rules, `m9-budget-and-dashboard.md` §10: the three never sum). Caps shown as a default-versus-override table with the binding scope named.
3. **Project views** — the project-centric screen: the project's caps and kill state; the enrolled repositories (the ones the operator has *seen* run are a run-list claim, and console 0.117.0 dropped the run list from this screen); the policy object and the routing switch **when they exist** (project-centric phases 1 and 1b; not built today); the job profiles; and a names-and-versions inventory of secrets and accounts.
4. **Degraded and offline modes** — the no-Firebase mode (`watch` polls `ls` every 10 s, runs grouped the same way, each run's cost from `result.json`, no caps and the kill keys disabled), the live-data-stale banner after 45 s without an event, and the CLI-absent/CLI-skew screens (§6.3).
5. **Packaging** — macOS, signed and notarised, with auto-update (§7); **and, since the owner's ruling of 2026-10-20, Linux as well** — an AppImage and a `.deb` for x86-64, from 0.10.0, unsigned (§7.6, **D10**).

### 4.2 Out, explicitly

- **Any write.** No kill, no resume, no cancel, no launch, in v1. The app may *show* the exact command (copy to clipboard), and §3.4's allow-list makes an accidental write unreachable. **D2** asks the owner whether v1.1 adds the three write buttons, and if so, always by invoking the CLI's own command so the confirmation, the admin check and the ETag compare-and-set stay where they are.
- **Secrets values, ever** — not in v1, not later. Names, labels and version counts only.
- **A new backend, a new service account, a new RTDB node, a rules change.** This design adds none. If a view needs data no command emits, the answer is a CLI `--json` field, not a console reader.
- **Streaming transcripts and log bodies inline.** The run-detail screen's log panel is a **capped window of `logs RUN --json`'s structured lines** and nothing more — a hard console-side line cap, a timeout, never `--follow` (§2.3, §5.1) — and the full log view is **linked out** through the validated `logs RUN --url` affordance. No transcript body is ever embedded, and no unbounded stream is ever spawned.
- **Multi-project aggregation.** The m9 design calls cross-project views "later, read-only" (`m9-budget-and-dashboard.md` §6.0); the console has one installation at a time in v1.
- **Windows as a *packaged* deliverable** — the code stays cross-platform and CI runs on Linux (§9.4), but signing and distributing Windows is still a later phase (**D10**, whose 2026-10-20 amendment takes Linux and leaves Windows where the recommendation put it). **Linux is no longer on this list**: its package ships from 0.10.0, unsigned (§7.6).
- **The backing-repository history view** (project-centric phase 6 — `fugaro project export` does not exist yet), **OAuth quota** (there is no per-person budget to show; OAuth spend is notional), **the recipe/config editors**, and **any telemetry** (tmog.org's own posture: "TMOG sends no usage statistics, hardware inventory, process information, or identifiers. Its only routine request is an update check"; ours mirrors it, §7.4).

## 5. Electron security posture

The console's threat is unusual and worth naming precisely: its renderer displays **strings written by a coding agent running with `--dangerously-skip-permissions` in a cloud container**, plus task text copied from issues and pull requests. `watch` already treats every job-written field as hostile and sanitizes it. In a browser engine, the same strings are a script-injection surface, so the posture below is not boilerplate — it is the load-bearing part of the design.

### 5.1 The hard rules

1. **The renderer is untrusted by construction.** `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`, `webviewTag: false`, `nodeIntegrationInWorker: false`, `allowRunningInsecureContent: false`, `experimentalFeatures: false`. The renderer gets no `require`, no `process`, no filesystem, no network.
2. **No remote content, ever.** The window loads the bundled document over a **custom `app://` scheme**, never a remote origin. `will-navigate` and `setWindowOpenHandler` **deny** every navigation and every window; an external link goes to the OS browser through a single `openExternal` path that validates the URL is `https:` and on an allow-list of hosts (the repository, the provider's console, the docs). No `loadURL` to a remote origin, no remote `<script>`, no remote font, no remote image. **A host check is the second gate, never the first, and the run's PR link is the case that shows why.** `pr_url` arrives inside `agents/<slug>/<run>`, written by the agent's own container — a hostile field like every other — so "github.com is an allowed host" is not the same statement as "this is *this run's* pull request". The link the console opens is **constructed** from facts about the run rather than taken from the feed — **and a construction needs to know which provider the repository is on, which no document on this tree says.** Fugaro opens pull requests on **GitHub and Bitbucket Cloud** (`docs/git-providers.md`: the provider comes from `git.provider` in the repository's `fugaro.yaml`, or from the origin URL's host, or from `fugaro exec --provider`; the provider kinds are `github`, `bitbucket` and `fake` — `internal/task/task.go`'s `Slug`, which hashes provider and repository together, **one way**, so a slug cannot be inverted into its provider). **No JSON shape the console reads carries it**: not `JSONRun` (`internal/watch/json.go:54`), not `JSONFinished` (`:83`), not `runview.Row` (`internal/runview/runview.go:57`) — and `doctor --json` does not report it either, so there is no read to fall back on. So **the console opens no PR link at all until gap 7 of §4.3 lands.** That is not caution for its own sake: a GitHub-shaped guess is *wrong* for every Bitbucket and GitHub Enterprise repository and **dangerous**, not merely useless. `edgeappinc/fugarosandbox` — the sandbox repository this repository's own live checks run against, Check 59's included — is on **Bitbucket** (`docs/gcp-live-checklist.md` talks to `api.bitbucket.org` for it), so on the very repository Check 59 runs against, a construction of `https://github.com/edgeappinc/fugarosandbox/pull/<n>` would pass this rule's own host allow-list while naming a repository the operator does not own, and it would be opened by design — link confusion pointed at whoever holds that name. It would also reject the real `pr_url`, which is the other half of the same defect. **Meanwhile the console shows the run's repository, its number and its `pr_url` as text, with the reason** — "this CLI does not say which provider this run's repository is on, so the console will not build a link from it" — copyable like the v1.1 write commands (D2) and never handed to `openExternal`. Once a shape carries the provider (gap 7), the rule is **one construction per provider** — `github` → `https://github.com/<repo>/pull/<n>`, `bitbucket` → `https://bitbucket.org/<workspace>/<name>/pull-requests/<n>` — each built from that document's own `repo` and its own number, with a `pr_url` opened only if it equals the construction for **the provider that document names**, and both providers' web hosts on the `openExternal` allow-list. The provider is a property of the document, never inferred from the `pr_url` it is meant to check: inferring it is the defect this paragraph exists to prevent.

**The fields are named, and an earlier revision of this rule named fields that do not exist.** Read off the code on `main`, the repository is **`repo`** on every shape that carries a run — `JSONRun` and `JSONFinished` (`internal/watch/json.go:54`, `:83`), and `runview.Row` (`internal/runview/runview.go:57`) behind `runs ls --json` and `diagnose --json` — and **there is no `repository` field anywhere**; and the number is **`pr_number`** on `JSONFinished` (`json.go:92`) but **`pr`** on `runview.Row` (`runview.go:109`), where `pr_url` sits beside it. So a rebuild would read a pair, and which pair depends on which document the run came from — and **every one of these documents is missing the provider as well, which is why none of them produces a link yet**:

| The run | The document | The pair a rebuild would use | The provider it names |
|---|---|---|---|
| finished, from the live feed | `watch --json`'s `finished[]`/`ready[]` | `repo` + `pr_number`, with `pr_url` as the string a construction would have to equal | **none — so no link (gap 7)** |
| any run on its detail screen | `diagnose RUN --json`'s `row` | `repo` + `pr`, with `pr_url` as the string | **none — so no link (gap 7)** |
| a **live** run in a list | `watch --json`'s `runs[]` | **no pair — the entry carries no `pr_url` and no `pr`** (`JSONRun`); its `pr_number` (2026-10-27, GV2.5) is a number to show, not a pair to build a link from | **none — the number is there and the provider is not, so no link (gap 7)** |

Two of the three rows are CLI gaps, and §4.3 names them: **gap 6** is the missing PR URL on `JSONRun` (its number half landed 2026-10-27, GV2.5 — a live run now has a number to show and still no pair to build a link from, so the console pays one extra `diagnose` read for the run whose detail screen is open), and **gap 7** is the missing provider on **all three** shapes, which is the one that stops any link from being built on this tree. Both are one small field each on the documents the CLI already emits, and neither blocks v1: the run's repository, number and `pr_url` are still shown, as text. The same rule covers the `logs RUN --url` link, whose value comes from the CLI rather than from a job and is still put through the `https:`-and-allow-list check before `openExternal` sees it.
3. **A deny-by-default CSP, delivered as a real response header — which is why the scheme is `app://`, not `file://`.** A `file://` document is not served over HTTP, so `session.webRequest.onHeadersReceived` never fires for it and a `Content-Security-Policy` header **cannot** be attached to it: only the `<meta http-equiv>` form works there, and the meta form is parsed late and is weaker than a header. The fix is the design's: register a standard, secure custom scheme with `protocol.handle('app', …)` and serve the bundled files through it, so the document has response headers and the CSP is a header — `default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'none'; form-action 'none'; base-uri 'none'; frame-ancestors 'none'; object-src 'none'` — with the `<meta>` copy kept as belt-and-braces. **`connect-src 'none'` is the important one**: the renderer never talks to the network, because every byte arrives over IPC. The console's only network traffic is the CLI child process's — an outbound call the CLI already makes and the app never sees.
4. **Electron Fuses are flipped at package time**, so the shipped binary is not a general-purpose Node interpreter. Through `@electron/fuses`: **`RunAsNode` disabled** (otherwise `ELECTRON_RUN_AS_NODE=1` turns the app into a Node runtime for anyone who can execute it), **`EnableNodeOptionsEnvironmentVariable` disabled** and **`EnableNodeCliInspectArguments` disabled** (otherwise `NODE_OPTIONS` or `--inspect` reach the app's own process), **`EnableEmbeddedAsarIntegrityValidation` enabled** and **`OnlyLoadAppFromAsar` enabled** (so a modified `app.asar` on disk is refused), and **`GrantFileProtocolExtraPrivileges` disabled**. These are build-time facts about the binary, not settings, so no runtime misconfiguration can undo them.
5. **An IPC allow-list, not an IPC bridge.** The preload exposes a small, frozen, versioned object of named operations (`subscribeLive`, `runReport`, `openExternal`, …). Each channel's handler validates its arguments against a closed schema, takes no path, takes no command, takes no URL other than the validated one, and returns already-rendered data. No generic `invoke(channel, …)`, no channel name from the renderer, no dynamic `require`. **The dashboard's surface is twenty-four operations** (`CONSOLE_OPERATIONS`, `src/main/ipc.ts`). The twenty-fourth is `run.launch` (added 2026-10-28 by the console v2 plan's V2.5.1a, the launch, rule 11): the console's **one write**, and the only operation here that is not a read. Its schema is the closed five-field set rule 11 writes, and its confirmation is **the modal window rule 11 writes** — `createConfirmWindow` (`console/src/main/confirm.ts`), which V2.5.1a's part 2b-3b-1 (2026-10-29) builds into the entry point in `main()`, once, over `session.defaultSession` — so the operation takes the surface to twenty-four and **the one `run` argv rule 11 writes is reachable, and spawned, only on a yes from that window's own top frame**: no other sender, no other frame, and no renderer's message on its own. Until that part landed the shipped app spawned no `run` child at all, because its `launchRunner` was over `DECLINING_CONFIRMER` (`console/src/main/launch.ts`), which refuses with `the launch confirmation window is not built yet`. The twenty-third is `coordinator.status` (added 2026-10-27, Bitbucket credentials T1.2): the project view, spawned as `coordinator status --from-store --all --json` (rule 6). Its document is every repository the installation's local config lists, read from the view the coordinator's sweep last stored, and it takes **no argument at all** — both extra words are fixed flags of its row, and the repository set is the CLI's own answer rather than a renderer's. The twenty-second is `plan.status` (added 2026-10-26, console v2 plan GV2.1): the graph screen's per-task state, spawned as `plan status --json` (rule 6). It takes at most the `all` boolean and **no path**, because the checkout reaches the CLI as the spawn's own working directory, from the installation's record and never from the renderer (§3.4 rule 5). The six before it are the installation rail's (owner's design ruling of 2026-10-25: the console never shows a picker screen, and every installation is a row in the rail): `installation.list` (the one that spawns: `config list --json`, below), `installation.choose`, `installation.checkout`, `installation.remove`, `installation.reveal` and `installation.open`. `installation.list` and `installation.open` take no argument; the other four take **a project name** the CLI printed, checked against the records and the list the main process holds. The one path-shaped argument on the surface is `installation.checkout`'s directory, which is accepted only when it is one the rail offers for that installation: a directory the CLI listed for it, or the console's own recorded checkout, and in either case **not** a temporary or tool-owned path, judged on the path as spelled and on where it resolves (a symlink into one is refused). So a renderer cannot name a directory of its own. `installation.reveal` takes the name and computes the folder itself, and `installation.open` opens the picker window.

10. **The app writes the spawn log, when asked, the installations file and `updates.json`, and nothing else.** *(Amended 2026-10-18 by the owner's C8 answer: the installation list is persisted, so this rule is no longer "the spawn log is the only thing the app ever writes". Amended 2026-10-30 by the owner's D768 and D770 answers: the update off switch is a third file, `updates.json`, and the two locations the updater itself writes are named under it.)* The app writes **nothing else** by default: no history, no cache of a document, no crash dump. **The spawn log** is opt-in, local and bounded. When **`FUGARO_CONSOLE_SPAWN_LOG` names a file path**, the main process appends one JSON object per line (JSONL) to that path, one line per child process it spawns, containing **exactly four fields** — `ts` (RFC 3339 UTC), `argv` (the full argument vector, the binary's absolute path first), `cwd` (absolute) and `project` (the installation's project name, the one passed as `--project`, so a spawn that carries no flag still records which installation it was for). It holds **no command output, no environment, no credential, no job-written text and no person**: the only installation-specific strings it can contain are the argv the app built, which is the point — it is an audit of the app's own spawn contract, and nothing else. It is **bounded** at 1000 records, after which the app appends one `{"truncated":true,"limit":1000}` line and stops. The app **never reads it back**, never rotates it, never deletes it and never transmits it: it is the operator's file at the operator's path, and §7.4's rule — nothing leaves the machine — is what makes writing it here acceptable at all. Unset (the default), the code path is not reached and no file exists. **D20** records the reasoning, and the two things that depend on it are Task 1.3's spawn-contract test and Check 59a's negative assertion, both of which read it as *evidence about the app*, never as application state. **A launch's line is the case rule 11 turns on, and it is where the two halves of that argv are visible:** it records the argv the app built — the `--title`, the `--plan-task` and the `--repo` included, because they are words of that argv — and it records **no task text**, which goes to the child on stdin and so is in neither the process table nor this file.

    **The installations file** is the second of the three things the app writes (C8, answered by the owner 2026-10-18; Task 3.4b builds it). One `installations.json` in Electron's `userData` directory, mode `0600`, schema-closed and bounded, holding **tuples only** — a project name, a config path, a binary path and an optional checkout directory — and **never a credential**. It is written only when the operator adds, chooses or removes an installation, and it is **never read from the operator's own CLI config**: §3.4 rule 7 stands, and this file is the app's own setting rather than a second reader of anyone's configuration. Together these three are the whole of what the app writes, and §7.4 says so in the same words. It lives under the app name `fugaro-console`, it is **schema-checked on read** (an unknown key refuses the whole file rather than being ignored), it is **bounded** at 16 installations and 64 KiB, and it is written **atomically** — a temporary file in the same directory, `0600` in a `0700` directory, renamed over the old one — so a crash mid-write leaves the previous list intact rather than a truncated one. The console refuses to keep it under any of the CLI's own configuration directories (`~/.config/fugaro`, `$XDG_CONFIG_HOME/fugaro`, the directory `$FUGARO_CONFIG` names): the two must not be able to be confused for one another.

    **`updates.json` is the third and last, and it is the update off switch's own file** (D768, answered by the owner 2026-10-30; U4 builds it). One boolean in Electron's `userData`, mode `0600`, holding **exactly one boolean and not an object** — there is one update setting, and a shape with room for a second field is a shape somebody has to version later. It is written **only when the switch changes**: a write whose value the file already holds is no write at all, so the file's inode and timestamp do not move for a checkbox clicked twice. It is read **fresh** every time the switch, the menu item or the policy asks, so a hand-edited file, or one another run wrote, is the answer the next ask gets; and the answer with no file, with a file that cannot be read, or with a file that is not a boolean is **on** — the default the console ships, the safe direction for a file nobody moved, reported with one constant line and never repaired or deleted. It is written atomically, exactly as `installations.json` is: a fresh temporary file in a `0700` directory, `0600`, renamed over the target.

    **The two locations the updater itself writes are not the app's, and they are named here rather than left for a reader to find** (D770, answered by the owner 2026-10-30). Both are written **only after an update was downloaded**, both are **removed or replaced by the install**, and **neither holds an identifier**: `electron-updater`'s download cache, `~/Library/Caches/fugaro-console-updater/` — the name `hardenUpdater` sets through `configOnDisk`, because the `app-update.yml` the library would read it from is a file this bundle does not ship — and **Squirrel.Mac's ShipIt staging directory**, where the OS-side installer stages the download it is about to run. The identifier this is all here to remove is the library's own: `hardenUpdater` keeps electron-updater from minting and writing `.updaterId` under `userData` and from sending `x-user-staging-id` on a request, and Check 59b reads both absences, and the two locations' state before and after a download, on a real Mac.

    - **The task text never reaches argv, which is what `--task-file -` is for.** **The task text goes to the child on stdin and never into the argv**, so it is in neither the process table nor the spawn log; the main process writes it, closes the stream, and the child is never left waiting on a terminal. The console's own bound is **at most 16 KiB of valid UTF-8 with no NUL byte**, refused above or outside it, and the bound is the console's because the CLI's is not: `internal/cli/run.go`'s `taskText` reads stdin to EOF and refuses only an empty task, with **no size cap of its own**. **16 KiB and not more, because the operator confirms by reading the task**: the whole of it is displayed in the launch window, so a task nobody could read in one sitting is not one this app asks anyone to confirm on the operator's behalf, and a larger bound would make the confirmation a formality over text nobody read. The text must be **valid UTF-8** and **must contain no NUL byte**; either failing is a refusal with the reason, never a truncation and never a replacement character. **The text is trimmed before it is shown, counted and handed over, because the CLI trims it**: `internal/cli/run.go`'s `taskText` calls `strings.TrimSpace` on what it reads and refuses a task that is empty afterwards ("the task is empty"), so surrounding whitespace — a trailing newline is the common case — is not part of the task the run stores, and **the bytes the window counts and the operator confirms are the bytes the run keeps**. **A task that is empty once trimmed is refused on this side**, with the CLI's own reason, rather than opening a window the CLI then refuses after the operator has confirmed — the same principle as the format characters below, where the console refuses rather than letting the CLI drop a character. Beyond that the text is shown as the operator typed it, except that the window **strips the format characters out of the displayed text** (below) and never renders any part of it as markup (rule 7).
    - **`--title` and `--plan-task` do reach argv, and are validated as values rather than trusted.** They are visible in the process table and in the spawn log (rule 10), which is acceptable because a title is not a secret — it is the run's own label, the one `fugaro runs ls` prints — and because the spawn log is the operator's own file at the operator's own path, written only when the operator asks for it. The main process validates each so a hostile string can neither add a word to the vector nor mislead what the vector is read as: the `=` form removes the leading-dash problem entirely (above), and besides it **no newline and no other control character**, because the argv is shown to the operator in the window and written to a file they read (rule 10), and a control character can rewrite the line a reader sees; **no Unicode format characters (`Cf`), the bidi overrides (U+202E and its family) and the zero-width joiners among them**, because those are not control characters and pass a control-character check while still reversing or corrupting the line the operator reads — the CLI's own sanitiser drops this class (`internal/safetext`'s `unicode.Is(unicode.Cf, r)`), and the console **refuses on this side rather than letting the CLI silently drop a character**, so the value in the window is the value in the argv; at most 100 runes for a title and 128 bytes for a plan task; and non-empty when present. Each is passed as its own word, in the `=` form. **The rule applies to the task text too, for the displayed copy**: the task is not validated as an argv word, but the window renders it with the format characters stripped, so no bidi override can reorder the paragraph a person is confirming. **A title and a plan task are not `value` arguments, and the console's own alphabet is why.** `isSafeArgumentValue`'s `ARGUMENT_RE` and its leading-`-` check (`console/src/main/spawn.ts`) are the guard on a **renderer** argument, and between them they refuse a space and a leading `-` — the first is something a title is allowed to have and the second is a value that would look like a flag — so neither of these two can ride the `value` kind. **V2.5.1a gives them argument kinds of their own** (`SpawnArgumentKind`), checked by exactly the rules above — the cap, one line, no control character, no format character, non-empty when present — while **`ARGUMENT_RE` stays unchanged for every other field**, which is the point: widening the alphabet for a title would widen it for `--repo`, for a `RUN` argument and for every other value the surface carries.
    - **stdin, and the one row that is allowed to write to a child.** Every other spawn's stdin is `'ignore'` — `SpawnOptionsLike.stdio` in `console/src/main/spawn.ts` pins it and says why (**the console never writes to a child**, the Windows work's Part E), and a child that reads its stdin sees it closed rather than hanging on a terminal nobody is at. **`run.launch` is the one row that gets `'pipe'` on stdin**, because handing the task over on stdin is the whole point of the row: the type widens by exactly one slot, from `readonly ['ignore', 'ignore' | 'pipe', 'ignore' | 'pipe']` to `readonly ['ignore' | 'pipe', 'ignore' | 'pipe', 'ignore' | 'pipe']`, so the stop child sent inside a distribution (`['ignore', 'ignore', 'ignore']`, T-F4) and every read still type-check, the argv builder for this row is the only caller that asks for `'pipe'`, and **a test pins `'ignore'` for every other row of the spawn table** (V2.5.1a's `console/test/unit/spawn.test.ts`), so the widening cannot quietly become a general permission to write into children. The main process writes the task and ends the stream; it never waits for the child to ask for it.
    - **The confirmation is a window the main process owns, not a native message box.** Before the spawn, the **main process** opens **a modal window of its own** — a second `BrowserWindow`, created for this one answer, loading a bundled document over the `app://` scheme (rule 3) with **its own preload**: two methods, `fields()` and `answer(true|false)`, and nothing else — no read, no spawn, no `openExternal`, no channel of the dashboard's. **`dialog.showMessageBox` is not used**: a native box cannot show a 16 KiB task scrollably, so the paragraph names the window rather than a dialog, and the reviewer's point that a native box is what the first revision recommended is what this sentence answers. The window shows these fields and no others, all of them the main process's own values: **the installation, the repository, the ref, the title, the plan task, the run id**, **the exact argv field by field**, the task's **byte size**, and **the whole task text, displayed in full and scrollable** — the operator reads it rather than the app summarising it. The window's document is untrusted-by-default like the dashboard's (rule 1's flags: context isolation, no node integration, a sandboxed renderer) and it renders every value as a text node (rule 7); it draws **no HTML, no link and no image from any of them**. **Cancel is the default button**, so Escape, Enter and closing the window all cancel, and confirming takes a deliberate click on the other button. **A yes is refused until the window has settled, and the measure is the main process's own** (amendment of 2026-10-29 by V2.5.1a part 2b-3b-2, from the independent review of 2b-3b-1): the spawn is built **before** the window opens, so the window can appear **under the pointer** a few hundred milliseconds after the click that asked for it — the time `build` takes, between the click and the window — and the second click of a double-click in the dashboard then lands on the confirming button of a window nobody has seen. The main process therefore refuses a yes for **`CONFIRM_READY_DELAY_MS` (500 ms) after the window's own `show` or `focus`, whichever of the two came last**, with both events read **in the main process** and never by a timer in the page — the page is the document whose late arrival is the hazard — and answers it with **`CONFIRM_NOT_YET` and decides nothing**: the window stays open on its frozen launch, and the click that comes after the delay is the one that confirms. A **re-focus** starts the delay over, because a window the operator comes back to is one they are looking at again, and **Cancel takes no delay at all**: the window's own way out is answered on the instant it is clicked, so an operator is never made to wait to decline a window that appeared under their pointer. **Focus is not required, and only ever extends the delay**: a window that is shown and never focused becomes answerable once the delay has run from its `show`, because requiring a focus would make a window Electron never focuses one **no launch can be confirmed from**, while a focus can only push answerability further out. **What the delay does not cover, and the quantity it is measured against.** What a yes has to wait out is the operator's own **double-click interval** (`I`) — a value the platform makes configurable, and one Windows' own slider puts as high as **900 ms** — and **not** the appearance gap, which is why a *slow* `build` is protective and a fast one is not: a window becomes answerable at `click + B + CONFIRM_READY_DELAY_MS`, where `B` is what `build` took, so the guard holds only while **`B + CONFIRM_READY_DELAY_MS > I`**, and a **fast** `build` (150 ms, a warm `config list --json`) with a slow double-click setting leaves a second click that still lands as an answer. **That case is recorded rather than claimed away**, and closing it is not a change part 2b-3b-2 makes: a delay measured from the click needs the click, which is the dashboard's, and `open` — called **after `build` resolves** — never sees it. It is the only confirmation in the chain (F8, above). **Declining spawns nothing**: no process, no run, no record — and the run id is not reused, so a second attempt is a new window with a new id. **What the renderer can do to this window is nothing**: it cannot open it, close it, re-focus it, re-open it, change a word in it, and it **cannot answer for the operator** — the two methods above exist on the window's own preload and are reachable from that document alone, and the main process spawns only on an answer that arrives on that path. **What the window shows is what is spawned.** The main process builds the whole spawn **once** — the binary path, the argv, the cwd, the environment and the trimmed task bytes — **before the window opens**, and freezes it under that window's run id; on a yes-answer it spawns **that frozen object verbatim**. It **never re-reads** the installation record, the renderer's fields or the current installation between the window and the spawn, so nothing an operator or a renderer does while a window is open can change what confirming it spawns. An installation **removed or re-chosen** while the window is open **closes the window as a cancel** — the answer becomes a decline, and declining spawns nothing (above) — and the held-id retry (below) spawns the same frozen object rather than rebuilding one from records that may have moved. *(Amendment of 2026-10-29 by V2.5.1a part 2b-3b-2: what "re-chosen" means, and the third way the window goes away.)* **Re-chosen means that same installation chosen again** — a launch names its own installation rather than the active one, so choosing *another* installation is not this sentence — and it reaches the window through `launchRunner.cancelFor(project)` in the picker's `onChosen`, **before `lifecycle.choose`**, which is what the entry pins. **A choose closes the dashboard window as well** — the new installation's window opens first and the one it replaces is closed after it (`chooseNow` in `console/src/main/window.ts`) — and that is the other way this one goes away: the confirmation is built **modal over the dashboard** (the `parent` above), so it is that window's child and no child outlives its parent. **The console does not close it there**: `cancelFor` closes the window the run id names and nothing else, so the closure is the parent's own and it is only true **when `dashboardWindow()` finds one**. A console with **no dashboard** — the refusal screen, a startup that has not opened the dashboard yet — passes no parent, and the confirmation window then **survives a switch to another installation**: it closes on its own answer, its own close box or its own load failure, and nothing else. **V2.5.1c must confirm on a real window that closing the parent closes the child** — Electron's documented behaviour for a child window, asserted here rather than observed, because no hermetic test can show it — **and that this window's own `show` and `focus` arrive at all**: a window for which Electron emitted neither would leave `readyAt` at infinity for good, so **every yes to it would be refused** and no launch could be confirmed from it. That dependency is the one whose failure mode is the safest kind — **fail-closed, a window nobody can confirm rather than a run nobody confirmed** — and it is asserted in the tests and observed on no real window, which is why it is named here beside the parent's.
    - **Idempotency, replay, and everything that can be repeated.** The **run id is generated once per confirmed window** by the main process, in `task.NewRunID`'s shape (`<UTC 20060102-150405>-<4 hex>`). That id, and not the click, is what makes a launch repeatable without spending twice, and **its two callers are both the window's own main-side `answer()` path**: the confirmation window's yes-answer, which a second click on its button and a re-sent IPC call reach, and nothing else does — the renderer asks for a window and **cannot answer for the operator** (above), so it never reaches this path at all. The two cases are different from each other: **a second answer for the same window's run id, while that launch is in flight, is attached to the launch in flight** — it waits on it and gets its answer, and no second child is started, which is the in-flight case; and **a second answer for the same window's run id, after the first was answered, is answered from the app's own record** of that answer — the decoded `launchResult` the first one produced, held **in memory only**, never written to disk, and **capped at `MAX_RECORDED_OUTCOMES` (256), oldest evicted first** (`console/src/main/launch.ts`'s `recordOutcome`) — which is the replay case. **An evicted id stays issued and answers `undefined` without spawning**: the id itself is this process's for the life of the process (`issuedRunIds`, so it is never drawn again for a later launch), the *record* of what it answered is not, and a second answer for an evicted id therefore produces **nothing at all** — no `launchResult`, no sentence, and nothing spawned — rather than a second child or a rebuild of a launch whose records may have moved. The cap is not a claim that 256 launches is enough for anyone: a replay is a repeat of a click, the record is an answer and not a promise about every id the process has ever used, and the bound is what keeps a day-long console from holding one decoded result per launch it has run. Neither of them reaches `spawn` a second time, and the two are not in tension: the first is a repeat *before* there is an answer, the second is a repeat *after* one, and the run id decides which. **No field of the schema names a run id** — the five fields above are the whole of it, and the id is main-process state — so no caller can propose one, and these two cases are everything that can repeat on a run id the app already knows. A launch whose id no record and no in-flight entry knows is a new launch and is checked against every rule here. **The one repeat that does reach `spawn` again is the killed launch's, and it is not a replay**: the unknown-outcome state below keeps the run id and offers the operator a retry — **how long that offer stands is open point 6**, left to the owner rather than decided here — and that retry **re-spawns with the run id the main process already holds — never a fresh window and a fresh id** — so the CLI's own claim answers `already-launched` and no second container starts — **where the first launch got as far as writing that claim**. The retry is safe because the run id is the app's own, not because a second attempt is free: **a child killed before it wrote a claim leaves nothing for the retry to find, and the CLI starts the container for that id**, and **a retry more than `ClaimTTL`'s ten minutes later finds a claim the CLI takes over as stale, which starts a second container for the same id**. The deadline bullet below carries the same qualifier in the same words — "when the first launch did start" — and it is what keeps this paragraph from promising an idempotence the retry path does not have. The CLI's answer sits behind all of this and is the truth for what the container did: the claim (`internal/runstore/launch.go`'s `Claim`, `ClaimKey`, `ClaimTTL`'s ten minutes) stays the CLI's, and the app's in-memory record is what keeps a replayed answer from asking twice.
    - **Rate: the windows, the cool-down, and the caps across installations.** Three bounds, because a launch screen is a surface a person can lean on: **windows are opened at most three times a minute per installation, and six times a minute across the whole app** — a rate limit on the **confirmation request**, not only on accepting one, because the request is what this process has to work for: the name the operator gave is read against the records before any window exists, so a request whose window is refused, and a request whose launch never builds at all, each count exactly as an opened window does, and a stream of them is a denial of service against the person at the keyboard rather than against the CLI (the two rate stamps are taken when the request arrives, and the limits themselves are elapsed-time bounds read off a **monotonic** clock rather than the wall clock, so a clock the machine moves cannot free a launch early or lock one out); an accepted launch starts **a ten-second cool-down** for that installation before the window will open again, longer than any double-submit a person can make and short enough that a deliberate second launch is paused rather than blocked; and **at most one launch is in flight per installation, and at most two launches in flight across the whole app** — a further `run.launch` while a launch is unsettled is refused rather than queued, which is D22's "no command queue" in the small, and the app-wide cap is what keeps ten installations from being ten times one installation's spend rate.
    - **The working directory and the environment.** The child's environment is §3.4 rule 5's, unchanged, with **no addition of any kind** (rule 8): no credential variable, no token in the argv, nothing a renderer chose. Its working directory is **always the app's own private, empty directory, never the operator's checkout** (`privateWorkingDirectory`, `console/src/main/spawn.ts`; §3.4 rule 5's supported "no directory" state) — the directory §3.4 rule 5 keeps for an installation with no checkout, which every other row of the spawn table reaches only in that case and this row uses **always**, the installation's recorded checkout included. **This is a security rule and not tidiness**: `newRunRef` cuts a run from **the branch the working directory's checkout is on** when that branch exists on origin, so a launch spawned inside the operator's checkout could take its ref from whatever the operator happens to have checked out — an uncommitted state choosing the branch a spend is cut from, and invisibly, since nothing in the window would show it. From the app's own empty directory there is no such checkout, the checkout fallbacks of the resolution above are unreachable, and the **recorded** base branch is the only answer left. The checkout is not passed, not read and not used as the cwd: **a launch does not need a checkout at all**, because `--repo` names the repository and the branch, the workflow and the repository's own settings are the CLI's answers from the installation's local config and the project layer.
    - **Windows, and the WSL route.** On the WSL route (`docs/console-windows/`) the CLI runs through `sh -c` inside a distribution, so the CLI's argv is handed to a shell there — and the wrapper **quotes every word of the CLI's argv with `shellQuoteWord`** (`console/src/main/spawn.ts`): a POSIX single-quoted string in which nothing is interpolated (no `$`, no backtick, no `*`), where the only character that needs anything at all is the single quote itself, and which refuses a NUL rather than dropping it. **A `--title=<T>` or `--plan-task=<P>` word therefore carries a space — or any other character a title's own rules admit — and reaches the CLI as the one word the host route would have delivered**, which is why this rule refuses no title on that route: the `=` form keeps the value *inside the flag's own word*, the wrapper's quoting is what makes that word inert, and `planFor`'s `distroShellUnsafe` refusal — which holds the non-flag, non-program words, the values the console passes as their own words, `--repo`'s and `--project`'s among them, and skips the program word and every `--` word — never inspects it. **The check that has to move is `assertArgvFlags`**, which refuses any argv element beginning `--` that is not on `SPAWN_FLAGS` and would refuse `--title=…` as a flag nobody allowed: it must **accept exactly the `--title=` and `--plan-task=` prefixes, for the `run.launch` row alone** — a bare `--title` or `--plan-task` word stays refused, the same prefix on any other row stays refused, and the value after the `=` is held to the value rules above (its cap, one line, no control character, no format character), which is where a value the quoting layer would otherwise have to carry is stopped instead. **The task itself is unaffected**: it still arrives **on the same stdin the cell pipe carries** — the console's `'pipe'` is the wrapper's stdin and reaches the distribution's shell as its own — and this is a requirement of that route rather than an observation about it (the WSL work's unbuilt parts must hold it): **a WSL-route launch either delivers the task on stdin or is refused with a named refusal; it never spawns with `'ignore'` and an empty task.**
    - **The deadline, and what a killed launch means.** **`LAUNCH_TIMEOUT_MS` is not `READ_TIMEOUT_MS`.** `READ_TIMEOUT_MS` (90 s, `console/src/main/spawn.ts`) is a read's deadline and this row is not a read: a launch runs the budget pre-check, writes the task, and starts a job, so it gets its own deadline, **`LAUNCH_TIMEOUT_MS` (120 s)**, under which a read's 90 s would kill a launch that is still working. It is stopped the way every child here is: **`SIGTERM`, then `SIGKILL` after `SHUTDOWN_GRACE_MS`** (2 s), and the same path is what a quitting app uses on its children. **A child killed mid-launch proves nothing about the run**: the CLI may have started the container before it died, so the app must not report "not launched" and must not retry on its own. What it does instead: it releases the in-flight entry, keeps the run id, and shows that **the launch's outcome is unknown**, naming the run id and the reads that settle it (`fugaro runs ls --json` and `fugaro diagnose <run> --json`, both allow-listed rows) — and the operator may ask again, which is safe **because the run id is the app's own**: the CLI's claim answers `already-launched` for it when the first launch did start. That is the "no way to know" D23 speaks about, reached by the console only here and by a launch that was killed rather than by one that failed.
    - **Results, and every refusal.** The reply is decoded by a **closed decoder** for `launchResult` (`internal/cli/run.go`). `status` is `launched` or `already-launched`, drawn **as a fact rather than as an error** (D23): the second means the CLI's claim already holds this run id. `run`, `repo`, `run_id`, `branch` and the execution are shown as the CLI's own values; a field the decoder does not know is **ignored** (the owner's ruling of 2026-10-30, §7.1, which replaced "refuses the whole reply": the reply arrives after the spend, and refusing it over a field a newer CLI added would report a launch that happened as one that did not), while a known field of the wrong type still refuses it. Every refusal is shown as the **CLI's own sanitised message, as text** — never as HTML, never as a rendered link, never re-worded by the console. The states this operation must draw, each with its own sentence: **a repository the installation's records do not carry** (refused by the app, before any window opens); **a repository identity the conversion refuses** (a provider that is not github or bitbucket, or a remainder that is not a canonical `owner/name`); **a repository the installation records no base branch for** (the refusal above, which names the repository and the setting); **a task that is empty once trimmed, over 16 KiB, not valid UTF-8, or carrying a NUL byte**; **a title or plan task that is empty, over its cap, multi-line, or carries a control or format character**; **the budget pre-check refused** (the CLI's own refusal, and the console has no `--no-budget-check` to get past it); **the claim held** by a launch already in flight; **the rate** (a window too soon, or a launch already in flight); **auth failure** (the CLI's sentence about the credential it could not use); and **a CLI too old for a flag of the row**. The last has a floor rather than a guess: `--plan-task` is the newest flag the row can carry, its release is `internal/cli/recipes_skew.go`'s **`planTaskSince = "0.11.2"`** (the title's is `titlesSince = "0.8.5"`; `--run-id` and `--task-file` are older), so **the operation is offered only to an installation whose CLI is at least that**, and that floor is **a version comparison and not membership in the console's supported range**: the handshake's version is compared against `planTaskSince` (`console/src/shared/version.ts`, `startup.compatibility`, §7.1), and the range cannot stand in for that comparison — it read `SUPPORTED_CLI_MINORS = ['0.7', '0.8']` against `CLI_VERSION_BUILT_AGAINST = '0.8.1'` when this rule was written, so **every CLI the console supported then was below the floor**, and it is minor-granular where the floor is a patch, which puts `0.11.0` and `0.11.1` inside "0.11" and still below `0.11.2`. So **V2.5.1a part 1 moved the supported range to include `0.11`** (2026-10-28, #1200), the owner's ruling of 2026-10-30 added `0.12` and `0.13` and made every plain release above the set `ok` (§7.1), and the launch form says so in words and never opens its window for a CLI below the floor.
    - **The spawn log, for this row.** Rule 10's opt-in log records a launch the same way it records every other spawn, with one thing it must not record: the line carries the argv the app built — `--repo`, `--title` and `--plan-task` included — and it **records no task text**, because the task went to the child on stdin and never through the argv (above).
    - **What a hostile renderer can do, as a threat and as tests.** A fully hostile renderer can, through this operation, at most **ask for a window**: it can propose a task, a title and a plan task, and it can name an installation and a repository **the main process's records already carry**. It **cannot choose a flag** (the argv is built from those five named fields, in a fixed order, under a closed exclusion list); it **cannot choose a path** (no field of the schema is a path, and the task goes over stdin); it **cannot choose the ref** (the recorded base branch does, and a repository without one is refused); it **cannot name a repository outside the installation's records**, or one whose identity the conversion refuses; it **cannot skip, fake or re-order the window**, which the main process creates, draws and answers, and it **cannot answer for the operator**; it **cannot open windows faster than the rate above**, and cannot turn its own refusals into a stream of windows aimed at the person at the keyboard; it **cannot pass a credential, a cloud project, a region or a recipe**; and it cannot make the app write anything beyond the spawn log and the installations file (rule 10). What proves each is V2.5.1a's headline test — the argv built from named fields only, every excluded flag unreachable, the task text in no argv and in no spawn-log line, `'ignore'` on every other row's stdin — together with V2.5.1c's e2e pair: a cancelled window that leaves no spawn, and an accepted one that spawns exactly this row, read back from the spawn log.

    **Open points, ruled.** The five points this paragraph first left open were answered by the owner on 2026-10-27, and this is what they were and what the answer was: **(1) the confirmation is drawn by the main process** — *ruled*, and not as a native message box: it is the modal window above, because it must show the whole task scrollably and because the renderer is untrusted by rule 1 and a confirmation the untrusted side could draw is one it could fake, skip or re-order; **(2) an operator-picked task file is out of scope** — *ruled*: a task is text, no field of the schema is a path, and a file, if it ever comes, comes through a main-process open dialog in its own task with its own review; **(3) the rate limits** — *ruled*: the ten-second cool-down **plus** the rate limit on confirmation requests (both above), because a limit only on accepted launches leaves the window itself unlimited; **(4) which surface carries the form** — *ruled*: **the Runs screen is the only place** a launch starts, so the graph screen does not launch and a graph node stays a read; and **(5) a follow-up launch (`run --pr`) is off this row** — *ruled*: it stays off the argv until the owner rules on it, beside D34's pair, since a follow-up launches a task that already has a run and D22's answer is about a first launch rather than about that. **The numbers, though, are this document's and not a ruling**: 16 KiB, ten seconds, three and six windows a minute, one and two launches in flight, and `LAUNCH_TIMEOUT_MS`'s 120 s are recommendations a review may move. And **one number here is not this document's to take**: the decision number for this paragraph. `D21`–`D38` are the console v2 reconciliation's (`docs/design/desktop-console-v2.md` §2) and `D39`–`D54b` are the voice work's (`docs/mobile/README.md`'s register, `docs/design/voice.md`'s "it is not D21"), so "the next free `D`" is not free — it is taken. The recommendation is that the owner either allocates this paragraph a number in the register or lets the console line carry its own prefix, the shape `docs/console-dependency-graph/README.md` already uses for `GD1`–`GD8`. **And one point is left open rather than ruled: (6) the held-id retry once the claim's ten minutes have passed.** This paragraph does not decide it, and it is the sixth point rather than a sixth ruling: **the recommendation is that the console refuses the retry once `ClaimTTL`'s ten minutes are gone**, and points the operator at `runs ls --json` and `diagnose RUN --json` — both allow-listed reads — instead of offering a second spawn, because after ten minutes the CLI takes the stale claim over and the retry really does start a second container for the same run id, which is a spend nobody asked for twice. **The owner should rule on it before V2.5.1a's retry path is written**, and that slice carries whichever answer he gives.
### 5.2 Supply chain and dependency pinning

The repo already has the right precedent, in the one Node dependency it ships: `internal/budget/rules/emulator/package.json` pins `firebase-tools` to an exact version (`15.19.0`), commits a `package-lock.json`, declares `"private": true` and `engines.node >= 20`, and says in its own description that it should be bumped "on purpose, with the rules tests". The console follows that rule, at a larger scale:

- **Exact versions only** — no `^`, no `~`, no `latest`, in `dependencies` and `devDependencies` alike; a committed lockfile; `npm ci` (never `npm install`) in CI, with `--ignore-scripts` on the install step and an allow-list for the few packages whose postinstall is genuinely required (Electron's own binary download being the one this design expects to need).
- **Electron pinned exactly**, with the version recorded in the design's implementation notes and bumped as a deliberate, reviewed change; Electron's release cadence means a floating pin is a monthly silent change to the most privileged dependency in the repo.
- **A small dependency tree is a feature, and exactly one entry of it is a runtime one.** `dependencies` holds **`electron-updater`, pinned to exactly `6.8.10`** — the console's **one runtime dependency**, and the component that downloads and installs code, which is why it is pinned on purpose — and `console/test/unit/pinning.test.ts`'s runtime allow-list is what keeps the set that one entry. Everything else the console pins is build and test tooling: `electron` itself, the TypeScript compiler, the test runners, the packer and the fuses writer. The renderer bundles TypeScript and no framework runtime beyond what the screens need (D9); the charts are drawn with the platform's own 2D canvas or SVG rather than pulled in.
- **The update feed is signed and verified** (§7.3), and the app refuses an update it cannot verify.
- **Reviewers get a "what changed in the tree" note**: any PR that touches the lockfile says which package moved and why.
- **The repo's own pinning regime is followed, not reinvented.** CI installs the rules emulator with `npm ci --ignore-scripts --no-audit --no-fund` (`ci.yml`'s `rules` job, over `internal/budget/rules/emulator/package-lock.json`); GitHub Actions are pinned to **full commit SHAs** with a `# vX.Y.Z` comment; and `.github/dependabot.yml` tracks **only `github-actions`**, weekly, from `/`. The console adds a second thing Dependabot should watch — and one it cannot see at all: **Electron's own binary is not an ordinary npm dependency** (its postinstall downloads a large prebuilt runtime), so the pin, the download and the checksum need the same hand-bumped, documented treatment the repo already gives the Trivy digest in `images/scan.sh` and the Dockerfile frontend digest.

## 6. The UI

### 6.1 What to take from tmog.org

tmog.org was read for this design (2026-10-15) and its own stated principles are the most useful part of it. Six transfers, concretely:

1. **"A measuring instrument should never make up an answer."** tmog.org: "TMOG distinguishes zero from unavailable and leaves gaps when samples stop. Every reading carries an explicit availability state, so a missing sensor cannot quietly become a plausible-looking value", and "A stopped measurement leaves a gap. A gap is the truth. Drawing a smooth line through missing samples would not be." **This becomes the console's first rule.** Every number on every screen carries one of: **measured**, **notional** (`~$`, for OAuth runs and any spend the gateway did not price), **estimated** (compute, which is an estimate by design), **unavailable** (`n/a` — never 0), or **gap** (the stream stopped; the graph breaks and the bar goes hollow). Fugaro hands us exactly these cases: compute is `n/a` when no run was estimated, `report` marks days with no final document `(partial)`, a crashed run's outstanding amount is `unreconciledMicros`, RTDB days older than 8 days are pruned, and `watch` already draws `-` for an absent registry field. The console must not smooth any of that away.
2. **Density as the default, not a setting.** tmog.org's screens are "Twelve destinations, one glance apiece". For us: a compact row (~24 px) with tabular figures in a monospaced numeral style, right-aligned numerics, no whitespace padding between related figures, and the project/repository/run hierarchy legible as *one* tree rather than three tables. tmog.org's "real screens, not simulated dashboards" is the standard: every screen must be readable at a glance and dense enough that scrolling is the exception.
3. **Live graphics that behave like instruments**: a rolling sparkline per repository (burn rate over a 5-minute window — `watch`'s own definition — because `counted` jumps by whole leases and its slope is lumpy), a stage-progress meter per run, and a cap bar that changes colour only at a defined threshold (tmog.org's amber/green discipline), never decoratively.
4. **"Replay the slow hour."** tmog.org's Flight Recorder records, saves, scrubs and replays the same telemetry panels in one interchangeable file. Ours is the same idea on the JSON feed: the console keeps a bounded in-memory ring of the last N minutes of the feed, can scrub back through it, and can export the window to a file. This is nearly free (the feed is already one JSON document per change), it is the single best debugging aid for "the run was slow at 14:20", and it doubles as the fixture format for tests (§9.2).
5. **Themes as a phosphor set, "Instrument, not ornament".** tmog.org offers Light, Dark and the classic phosphor palettes (green, amber, blue, mono) with a saturation control, and says the meters are drawn by the app so the chrome belongs to the product. Ours: a light, a dark, and a small set of low-saturation palettes, with all colour choices from a single token file — which is also what makes the screens readable for colour-blind users, a constraint tmog.org does not state and we should.
6. **One glance answers "what is responsible"**, not "here is a table of everything". tmog.org's sales line — "One glance at TMOG shows which process and which subsystem are responsible—right now" — is the console's top-level question restated: *which run, and which stage, is spending the money right now*. The default screen answers that before anything else is drawn.

**What we do not take:** the native-technology posture ("No Electron, no web view, no embedded browser"; three separate native hosts over a shared C++20 core). That is the owner's **D8**. We also do not take tmog.org's twelve equal destinations — Fugaro has four screens, and a fifth would be a concession, not a feature.

### 6.2 The screens

**A screen renders each part when its data arrives; independent reads run in parallel; no screen waits for all of them** (the owner's rule of 2026-10-31, and how the screens below are read): a screen that reads two things draws the one that answered, with its own busy state and its own refusal, rather than holding a spinner until the last read lands. The renderer’s half of that is `console/src/renderer/section.ts`, and the session cache beside it: a view the session already read is drawn instantly with an `as of HH:MM` stamp and a refresh control, and one older than five minutes is drawn **and** re-read at once.

1. **Live** (default). Header: project, installation, CLI version, connectivity (`live` / `stale` after 45 s / `polling` in the no-Firebase mode), and the global cap bar with today's `counted`. Body: one row per repository with its cap bar, burn sparkline and kill state (a killed repository shows `KILLED by <who> <time> "<reason>"`); under each, its runs with stage, round, verify step, coder/reviewer models, spend and age, flagged `silent`/`lost`/amber. A run with `auth: oauth` shows its spend as notional. **A run's row also names who started it** (`launched_by`, the owner's request of 2026-10-18): the CLI's own short form — the part before an address's first `@`, the whole value for anything else (`runview.LauncherShort`, the cut `fugaro runs ls`'s `BY` column makes) — and no cell at all for a run whose record carries none. **It is the one key drawn in a class other than the one `WIRE_TEXT_CLASSES` gives it**, recorded here rather than left as a surprise: the `person` class refuses a dotted local part, so the column would read `n/a` for most of the people who use it, while the short form has no address in it (`console/README.md`'s class table is the long form of the reason, and `console/src/shared/launcher.ts` is the module). This is not **D15**'s ground: that decision is the Spend screen's per-person breakdown, and this screen already names a person without a switch — the kill state above reads `KILLED by <who>`.
2. **Spend.** Time series with a range picker (`--since`/`--until`), a breakdown switch (`day|week|month|year|repo|model|person|mode`), three series that are **never summed** (model, `~$`, compute), and the caps panel: global, defaults, per-repository overrides, with the *binding scope* named for each effective per-run cap. Partial days are drawn hollow with a `(partial)` marker. The person breakdown is **off by default** (**D15**, §2.3) — an earlier revision of this sentence cited a "D6.4" that does not exist; the decisions are D1 to D20 and the per-person one is D15. **What the knob turns on is the by-person panel** (added 2026-10-23, L5b): one line per launcher from `runs stats --json` (§2.1), under the total the read itself reports and the window it read, drawn directly under the report's own totals, above the caps panel, and only while the knob is on. **The console does not decide who may be seen, and it cannot ask** (§5.1 rule 6): an operator of the installation sees every launcher, a plain launcher sees their own line alone, and the owner's ruling of 2026-10-22 is that the panel **fails private** — a read that does not say who it was resolved for, or that names a view or a breakdown word this console does not know (`userStatsViewOwn`; the unattributed key `unknown` is one of those identities), draws **no line at all**, because "nobody spent anything" and "this console will not show you whose money this was" are two different facts — and in the two of those states the CLI itself fills (its `you` empty, or the unattributed key `unknown`, which it deletes every run on before it aggregates, so it publishes `totals: []` as well as `rows: []`) there is no total to draw either, which the panel says in its own words rather than leaving a blank. The totals the panel does draw are the ones the read published and never a sum of this screen's: the CLI aggregates **after** it filters, so they are the window's under `all` and the caller's own runs alone under `own`, and the panel says which. The window is the picker's own, translated into `parseSince`'s grammar (`12w` is a `report` form this command refuses, so the screen asks for `84d`); a UTC day and any `--until` are refused in the console's own words rather than passed through, and nothing the console can send widens the view.
3. **Project.** The project-centric screen, and the one that grows as [project-centric.md](project-centric.md) ships. **Every panel names its source, and where there is no source the panel says so rather than drawing an empty box**: caps, kill switches and the enrolled repositories from `budget show --json` — **one read, and no run list** (console 0.117.0, the owner's report of 2026-10-31: `runs ls --json` is about 248 KB and six seconds for a day of runs, the screen started it before the caps could be drawn, and the tab took about twenty seconds with nothing on screen; the jobs table and the enrolled-versus-seen repository split went with it, because both are claims only a run list can make) — and the panel's own section carries the console's busy mark, its skeleton and its "still reading" word while that read is out, the frame being mounted in the tab's own first frame; the Claude accounts from `accounts ls --json` (the names are a local read that never calls Secret Manager; the states beside them are a bounded read of the project's `creds/marks` — five seconds for the whole read, one attempt per call, `accountsStateBudget` — so a database that never answers costs the screen seconds rather than the per-call timeout twice, and `states` absent with a `state_note` renders as unknown, never as available; a `complete: false` document renders as `unavailable`, never as an empty list); the secrets inventory from `secrets ls --json` with an explicit `--repo`/`--project-wide` — **name, scope and version count only**, never a value; the policy object with its version and the `routing.claude` switch **only when `fugaro project show --json` exists, which it does not on this tree** (project-centric phase 1, PR #390), so that panel is written from its first commit to render an explicit *not readable with this CLI* state; the profiles from the same sources. The job row that named who started a job beside who requested it (`launched_by` and `requested_by`, which are two different facts) went with the jobs table: the run list that fed it, and the short form and the class item 1 keeps for the Live row, belong to the screens that still read runs. **Every field on this screen must trace to a command line in §5.1's allow-list, or the screen does not show it** — that is the review criterion for this screen above all others, because it is the one that was designed to show an inventory.
4. **Run detail.** One run: its ledger, stage timeline with deadlines, models and per-stage spend, outcome, the pull request — **shown as text, with its repository and number, until §4.3's gap 7 gives the console a provider to build a link from** (§5.1 rule 2; the `logs` link it draws beside it comes from the CLI and is unaffected), the log panel and the `logs` link, and the diagnostic view (`fugaro diagnose`). **The PR link would be rebuilt from the run's repository and PR number rather than trusted from the feed — and until gap 7 it is not built at all** (§5.1 rule 2)**, and the log panel is a capped window of structured lines with the full log one `logs RUN --url` link away** (§2.3, §5.1 rules 2 and 6) — with §5.1 rule 2 naming which field carries each, since the repository is `repo` on every shape, the number is `pr_number` on a finished run's `watch --json` entry and `pr` on a `diagnose` row, and **a live run's entry carries neither**, so its number waits for the run to finish or for the detail screen's `diagnose` read (and its link waits for gap 7, like every other). **The header also names who started the run** (`launched_by`), and this is where the **whole** recorded identity is drawn rather than the short form the Live and Project columns draw: through the `person` class, so an address is the console's marker here as it is in the requester cell beside it, and a login or a CI identity is itself. That is the owner's "the full identity only in the expanded or run view and in JSON", and it is the one place the two forms of one key are visible side by side. This is where "replay" is most useful, so the scrubber lives here too.

### 6.3 How it degrades offline

There is no "online" mode in the ordinary sense, because the renderer never touches the network (§5.1). The console is always a client of a local process, so the degradations are:

| Condition | What the user sees |
|---|---|
| RTDB unreachable / no live events for 45 s | The `stale` banner in the header; graphs **break** rather than interpolate; the last-known values stay with their timestamps; nothing is silently zeroed |
| No Firebase configured (budget mode off, or never set up) | The `polling` indicator: `watch`'s no-Firebase mode — runs from `ls`, cost from `result.json`, **caps shown as `unavailable` and the kill/resume affordances absent** (as the CLI disables them) |
| A day older than 8 days, or a day with no final document | `(partial)`/hollow rendering; the range shows what Firestore has |
| No `fugaro` this console can use: none in any of rule 4's locations, a candidate that exists and does not answer `version`, or a `binaryPath` in the store that is not absolute | A single explanatory screen: what the console needs, **the resolution's own sentence** (the one line that names what actually happened — the fixed words must not claim a cause, since two of these three are not "nothing was found"), the one install command (`brew install dimipaun/tap/fugaro`), the places the resolution looked, and a link to the website's getting-started page — opened through the one validated external-link path. **No "choose the binary" affordance**: the console asks the operator for no path (owner's ruling of 2026-10-20). No partially drawn dashboard |
| A `fugaro`, and no installation the CLI can list | The second explanatory screen, in the same words and with the same link: "Set up your first installation", the one command that does it (`fugaro init`, in one constant — the setup-wizard plan in `docs/setup-wizard/` renames it), and the getting-started link. The console asks for no repository here: the checkout is optional and is asked for at the moment a screen needs one (rule 7's amendment). A store entry the CLI did not list is still drawn, so the screen is for a machine with nothing at all, and never for one whose installation the CLI merely cannot enumerate |
| CLI older than the console's supported set, or a version line that is not a plain release | A banner naming both versions and the fix, with the console running in the reduced mode it can support (**D7**). A CLI **newer** than the set is not skew (§7.1, owner 2026-10-30): the console draws what it can read, and a read that fails to decode is refused on its own screen |
| CLI refuses a read (permission, wrong project) | The CLI's own message, verbatim, plus the one-line remedy the CLI prints (for `report`, the permission error names `roles/datastore.viewer` and `roles/serviceusage.serviceUsageConsumer`; the console shows that text unedited) |

## 7. Packaging: macOS first

### 7.1 What ships, and what "alongside the CLI" means

**The repo's release rule is that one tag releases everything.** `docs/release.md` (its "Releasing Fugaro" section) states it as the single source of truth: a strict SemVer `vX.Y.Z` tag releases the binary, the base images, the Terraform modules at the tag, the schemas at the tag and the plugin. One `vX.Y.Z` push fires two independent workflows — `release.yml` (GoReleaser: the `fugaro` binaries for darwin/linux amd64+arm64, `checksums.txt`, per-archive syft SBOMs, a **keyless cosign** signature of `checksums.txt`, the GitHub Release and the Homebrew cask) and `images.yml` (build, scan, publish ghcr.io images, then `verify-public`) — and both run `scripts/release-gate.sh` first, which refuses unless the tag is on `origin/main` and the `test`, `terraform` and `rules` checks passed on it. Neither workflow runs the test suite; CI already did, on `main`.

Two consequences the console must live with, and they shape D11:

- **Today's macOS binaries are not Apple-signed or notarised.** `docs/release.md`'s "Verifying a release" section is explicit that the checksums are signed but the binaries are not, and the Homebrew cask works around Gatekeeper with a `postflight` hook that runs `xattr -dr com.apple.quarantine`. That workaround is tolerable for a `fugaro` you run in a terminal. **It is not tolerable for a GUI application** — an unsigned `.app` is quarantined and refused without a trip through System Settings, and an updater refuses an unsigned bundle. So for the console, signing and notarisation are not a nicety the CLI skipped; they are the first thing that has to exist, and they are a new capability for this repo (**D4**, Check 59a).
- **The signature mechanism the repo already has is keyless.** Every existing signature is cosign over GitHub OIDC — `id-token: write`, no stored private key anywhere in the tree, scripts or a run. The only signing-adjacent secret in the whole release path is `HOMEBREW_TAP_GITHUB_TOKEN` (a fine-grained PAT for `dimipaun/homebrew-tap`), and its absence merely skips the cask with a `::warning::`. **The console's Apple signing is the first time this repo would hold a private key**, which is precisely why §7.5 puts every step that touches it in the owner's hands.

So: the console is **its own artifact, published from the CLI's own `vX.Y.Z` tag rather than from a second tag stream** (D11) — one release train, two artifacts, which is what "one tag releases everything" means once a second deliverable exists. **One gate, the CLI's tag; its own release** (the owner's ruling of 2026-10-17, "Separate console release"): the console is published as its own GitHub release, `console-vX.Y.Z`, created by the console workflow from the CLI's `vX.Y.Z` tag push behind the same `scripts/release-gate.sh`, because with immutable releases on the CLI's GoReleaser release cannot take an asset once published; the console release is created as a draft, given every asset, and published in one job, and a re-run refuses rather than clobbering. The console's Homebrew cask, when it exists, points at that release. The console declares the CLI version it was built and tested against, and **the version-skew rule is the load-bearing part of this section**: the console's JSON inputs are a contract, so it carries a **supported CLI range** — an explicit, hand-written set of minors rather than a rule derived from the version it was built against (`SUPPORTED_CLI_MINORS`, `console/src/shared/version.ts`, which V2.5.1a part 1 read as `['0.7', '0.8', '0.11']`; it is deliberately not the launch's floor's minor, §5.1 rule 11) — and checks it at startup with `fugaro version` (the subcommand — the root command's own `--version`/`-v` prints the same line, but the handshake stays the subcommand, which every CLI in the console's supported range has; and `version` itself has no flags at all, so the handshake runs it bare — §3.4 rule 3, §5.1). Outside the range: a banner naming both versions and a reduced mode; below a hard floor the console refuses to draw a live dashboard rather than misreport spend (**D7**).

**The owner's ruling of 2026-10-30 (not the recommendation; recorded here as the ruling it is).** The owner, driving console 0.114.0 against CLI 0.13.0, found the console in the reduced mode (spend, caps and kill/resume withheld) because `0.12` and `0.13` were not in the set. The ruling: **a CLI at or above the supported set answers `ok`**, that is, any plain release newer than the newest member of `SUPPORTED_CLI_MINORS` (now `['0.7', '0.8', '0.11', '0.12', '0.13']`, built against `0.13.0`); the reduced mode is kept for (a) a CLI below the hard floor (refused) or in the unsupported gap below the set (`0.9`, `0.10`), and (b) a read that **fails to decode** (a field removed or retyped), which is refused on that read's own screen with the decoder's sentence naming the read and the field. Acceptance is open only to a well-formed `major.minor.patch` line (an optional `v`, no leading zero, no prerelease or build tail): `0.14.0-rc.1`, `0.14.0+x`, `00.14.0` and `0.14` are reduced, never `ok`. The launch and compute floors (`LAUNCH_CLI_FLOOR = 0.11.2`, `BUDGET_COMPUTE_CLI_FLOOR = 0.13.0`) gate features, not skew, and are unchanged. The console's decoders now **ignore an unknown key** on every CLI read shape (`console/src/shared/schema.ts`, and the launch reply in `console/src/main/launchrules.ts`) while still refusing a missing or retyped field.

**The compatibility contract** (owner, 2026-10-30): **fields never change meaning; if a field's semantics must change, it is renamed.** Adding a field is compatible; removing or retyping one is a format change and bumps the document's format version; changing meaning means a new field name (`console/docs/json-contract.md`, "Compatibility rule"). The risk the ruling accepts, a semantic change behind an unchanged field name drawing a wrong figure with no error, is mitigated by this rule, and a guard in `console/test/unit/version.test.ts` fails when the newest released CLI in `docs/release-streams.yaml` does not answer `ok` as a member of the set, so the next console release re-reads that minor.

### 7.2 macOS: signing and notarisation

1. **Certificate and identity.** A `Developer ID Application` certificate, in the owner's keychain and, for CI, in the signing machine's keychain only. The app is signed with the **hardened runtime** enabled, with the minimum entitlements: no `com.apple.security.cs.disable-library-validation` unless Electron's own signing story requires it (it must be justified in the entitlements file's comment if it is), no `get-task-allow` outside debug builds, and no entitlement the app does not demonstrably use.
2. **Notarisation.** `xcrun notarytool submit --wait` with an App Store Connect API key (or an app-specific password) held as a CI secret, then `xcrun stapler staple` on the `.app` and on the `.dmg`, then verification: `codesign --verify --deep --strict`, `spctl --assess --type execute`, and `stapler validate`. **These verification commands are the fact the release records**, the same way the CLI's release records its checksums.
3. **Gatekeeper's real constraint.** An unsigned or unstapled build does not run on a normal Mac without the user disabling Gatekeeper. That makes signing a *release blocker*, not a polish item: an unsigned console is not shippable to anyone but the owner.
4. **Distribution.** A direct download (`.dmg`/`.zip`) from the console's own GitHub release, `console-vX.Y.Z` (§7.1), plus a Homebrew cask mirroring the CLI's existing cask. **The Mac App Store is not the path** (**D4**): sandboxing an app whose job is to spawn another installed executable fights the platform, and it would put the console behind an App Review process the CLI does not have.

### 7.3 Auto-update

Electron's own `autoUpdater` — Squirrel.Mac — over a **signed** feed, driven by **`electron-updater`**, the `electron-builder` companion: `electron-updater` is what supplies the feed client and the `latest-mac.yml` manifest, and **that manifest format is electron-updater's, not Squirrel's** (Squirrel.Mac itself reads a JSON feed), so the design names the client rather than implying Electron ships a YAML feed reader. The `.dmg`/`.zip` and the manifest are published on the release, and the OS verifies the new bundle's signature before it is installed (an update the app cannot verify is refused). **What ships (U1 to U4 of the auto-update chain, 2026-10-30; this paragraph's recommendations made concrete).** The check runs **at launch and then every six hours**, and a download is **quiet** — the console keeps working while it happens. When a download is ready the console shows a **non-blocking** native notice that names the version on disk, with **`Restart to update`** and **`Later`**: nothing is installed until the operator presses the first, and **nothing is installed on quit** — the update installs only the download that notice named, and a press sent for one download cannot install another. A **downgrade** is refused, and so is any update whose signature the app cannot verify. The feature is **on by default** and its off switch is visible in the application menu — **`Check for Updates Automatically`**, and **`Check for Updates Now`** beside it, whose state is the one boolean `<userData>/updates.json` holds (§5.1 rule 10, D768) — and **`FUGARO_NO_UPDATE_CHECK=1`** turns the checks off as well. Those two are the whole of the opt-out: the console honours **neither** the CLI's `update_check` setting nor anything else in the operator's CLI config (**D769** of 2026-10-30), and §3.4 rule 7 stands. The one runtime dependency that does all of this is `electron-updater`, pinned exactly (§5.2).

**This would be the repo's first self-updater, and the CLI's existing machinery is deliberately not one.** `fugaro` never replaces its own binary: `docs/design/upgrade.md` and the `upgrade` skill make the sequence `brew upgrade dimipaun/tap/fugaro && fugaro upgrade`, where the package manager does the replacing and `fugaro upgrade` does the pinning, the plugin update and the image refresh. What the CLI *does* have is a **notice**: `internal/updatecheck/updatecheck.go` does one background `GET` a day to the GitHub `releases/latest` endpoint, caches under `$XDG_CACHE_HOME/fugaro`, and prints at most one nag a day (`WarnTTL`, `CheckTTL`, `FetchTimeout`), disabled by `FUGARO_NO_UPDATE_CHECK=1`, by `update_check: false` in the local config, and automatically in CI, under `exec`/`help`/`version`, on a non-terminal stderr and on Cloud Run; the fix line is the constant `updatecheck.BrewCommand`. So the design says: **the console's update check should read the same release metadata and honour the same opt-out** — with **D769**'s correction of 2026-10-30: the opt-out it actually honours is `FUGARO_NO_UPDATE_CHECK=1` and its own switch, and **not** the CLI's `update_check`, which the console never reads — and the *installation* of the new bundle is the one genuinely new mechanism — which is why it is `D5` (recommended: **on by default, with the toggle visible**) and why Check 59b exercises the round trip on a real Mac, **after** a published release exists to feed it.

### 7.4 "Your machine stays your business"

tmog.org's promise — no usage statistics, no hardware inventory, no process information, no identifiers, "its only routine request is an update check" — is the right default here for a stronger reason than taste: the console displays a team's work, spend and repository names. **No telemetry, no crash reporting to a third party, no analytics, and no update check that carries an identifier.** The only outbound requests are the CLI's own (to the cloud the operator already owns) and the update check. **The app writes three things to disk and nothing else (§5.1 rule 10, amended 2026-10-30 by the owner's D768 and D770 answers): the spawn log, which is off unless the operator names a path for it; the installations file, which holds the operator's own choices and no credential, and is written only when that list changes (C8); and `updates.json`, the update off switch's one boolean, written only when the switch changes (D768). Two locations under the machine's own caches are the updater's and not the app's — electron-updater's download cache `~/Library/Caches/fugaro-console-updater/` and Squirrel.Mac's ShipIt staging directory — and both are written only after an update was downloaded, are removed or replaced by the install, hold no identifier, and are named here rather than left to be inferred (D770).** In the default state — no log path, no installation added yet, no switch moved — this section's promise is literal: the app keeps no history, no cache and no record of anything, and a run of it leaves the machine exactly as it found it. When the log *is* on, it stays on that machine: it is written to a path the operator chose, read by no one but the operator and the owner-run check (59a and 59b), and sent nowhere (**D20**). That is also why it is safe for it to hold argv — a project name and a repository name — since those never leave the file's own directory.

**Note added 2026-10-19.** The mobile work's P5.3 design ([docs/mobile/design/voice-evaluation-switch.md](../mobile/design/voice-evaluation-switch.md)) gives the **phone** app an in-app switch between local and remote STT/TTS, for evaluation, and the owner answered its **Q0** on 2026-10-19 (option (a)) permitting that — with the never-send rules and the persistent indicator that design sets out. **This section's promise is about *this* app's outbound requests and is unchanged by it**: the console still makes no request of its own, the phone's switch is the phone artifact's path and not the console's, and no console feature, setting or phase changes. Recorded here because this is the section that owns the sentence, so that a reader of either document sees the same fact.

### 7.5 Which steps are owner-run, and why no agent does them

Signing and notarisation **cannot** be done by an agent, on this repo's existing terms and for a concrete reason: the certificate, the App Store Connect key and the notarisation credentials are secrets, and the rules under which this work is done are that no agent handles a secret and that releases are owner-gated. So:

| Step | Who |
|---|---|
| Writing the entitlements file, the builder configuration, the update-feed metadata, and the CI workflows' **text** | an agent may write the files, and **each workflow only as a staged change under `docs/pending-workflows/` for the owner to copy** — the repo already does exactly this (its README is the only thing in that directory today), and `docs/release.md`'s "Before you tag" names copying a staged workflow in as an owner step. **There are two, and they are deliberately separate files**: the tests workflow (staged with Task 1.4 and copied in as Task 1.5 — so the console's CI begins with that copy-in, one task after the shell's code lands, and Tasks 1.0 to 1.4 merge with no console workflow running at all: §9.4) and the signing workflow (§9.4, staged as Task 4.2 and copied in as Task 4.5) |
| Creating the protected GitHub environment that holds the signing secrets, and approving its deployments | **owner only** — the signing job reads them from an `environment:`, in a workflow that only ever runs on a tag (§9.4) |
| Creating the certificate, storing it, storing the API key as a CI secret | **owner only** |
| The first signed, notarised, stapled build and its verification | **owner only** (Check 59a) |
| Cutting the tag that publishes it | **owner only**, as with the CLI |
| The auto-update round trip on a real Mac | **owner only** (Check 59b, and only once a published release carries the console's feed — so it follows the first tag rather than the first signed build) |
| Windows signing | **owner only**, later (**D10**) — and **no Linux signing step exists at all**: the Linux package is unsigned by the owner's ruling of 2026-10-20, with no key, no certificate and nothing for an agent or the owner to handle (§7.6) |

### 7.6 Linux, unsigned (the owner's ruling of 2026-10-20)

**The owner ruled on 2026-10-20: Linux ships for 0.10.0, unsigned.** This section exists because that ruling is the one place where the console's packaging departs from §7.2's, and a departure a reader has to infer is a departure that gets re-litigated. What it is:

1. **What ships.** An **AppImage** and a **`.deb`**, for **x86-64 only**, built by `console/package.json`'s `build.linux` from the same source, the same `build.files`, the same asar rule and the same six fuses as the macOS bundles — the Linux executable gets the fuses through the same afterPack hook, with `context.electronPlatformName` — the platform the packer says it is packing, which is not the build host's own — deciding which executable is patched, so the two platforms cannot drift into different postures. The artifact names are `Fugaro.Console-X.Y.Z-linux-x86_64.AppImage` and `Fugaro.Console-X.Y.Z-linux-amd64.deb` — **the packer writes the target's own word for the architecture and not the build's `x64`** (the AppImage is `x86_64`, the `.deb` is `amd64`), which the release that published them corrected here on 2026-10-24: this sentence said `linux-x64`, a file no release holds (`console/README.md`'s artifact-name row, `docs/release.md`'s "Verifying the console's release"). The CLI binary the console spawns is resolved from Linux's own well-known locations (§3.4 rule 4), never from the inherited `PATH`.
2. **It is not code-signed, and nothing here claims otherwise.** An AppImage is a self-mounting archive: it carries no signature and there is no Linux equivalent of Apple's notarisation or of Gatekeeper's refusal to launch an unsigned bundle. So the ruling costs no key, no certificate and no owner-run signing step (§7.5), and **the release must not describe the Linux artifacts as signed** — the release notes, `docs/release.md` and `console/README.md` say unsigned in those words. What a reader verifies instead is the release's own machinery: the artifact's SHA-256 against `console-sha256sums.txt`, and that file against the **keyless cosign** signature the release already publishes as a Sigstore bundle (the mechanism §7.1 records as this repo's existing one — GitHub OIDC, no stored private key).
3. **Windows is untouched.** D10's recommendation was about two signing identities and a later phase; the ruling removes neither. The console's code stays cross-platform, and Windows packaging and signing remain the later phase the row above answers.
4. **What does not come with it.** **No Linux auto-update** (§7.3 is Squirrel.Mac and an `electron-updater` feed; the AppImage path has no such feed here), **no arm64 Linux build** until one can be built and verified on a runner that has it, **no Flatpak, snap or rpm**, **no Linux Homebrew cask**, and **no distribution channel beyond the release's own files**. Each is a later decision, not an oversight: this ruling is the smallest thing that makes "Linux is supported" true.
5. **Where the owner's own steps are.** None of them are signing steps. The owner's work is the same as any release — the tag, and approving the console release draft — and the Linux build job is a **build-only** job that runs on `ubuntu-latest`, takes no secret and uploads the two artifacts into that release. Its workflow text is staged under `docs/pending-workflows/` for the owner to copy, and the copy-in is the owner's step (§9.4).

## 8. Where it lives, and its interaction with the Go module and CI

### 8.1 Recommendation: this repo, under `console/` (**D3**)

Arguments for keeping it here, in order of weight:

1. **The contract lives here.** The JSON shapes the console consumes are `internal/watch/json.go`'s types and the CLI's `--json` output. A separate repository makes that contract cross-repo, which means it needs a published schema, a compatibility policy and its own versioning — all of which this repo already has in its `docs_*_test.go` presence tests and its `internal/watch/json_test.go` shape tests (the `--json` convention itself is per-command, not a single repo-wide test: §2.1).
2. **The rules the console must obey are enforced here.** The docs tests (`internal/cli/docs_*_test.go`), the release process and the owner-gated release rule are in this repo. A console in a second repo would have to be *told* about them.
3. **Version skew is easier to manage in one place.** The console's supported-CLI-range check (§7.1) is a fact about this repo's releases; keeping the two version streams in one git history makes the mapping checkable, not aspirational.
4. **The Go module is untouched.** `console/` contains no Go package, so `go build ./...`, `go vet ./...` and `gofmt -l .` take no notice of it; `go.mod` and `go.sum` do not change; no Go package may import anything from `console/`, and nothing under `console/` may be imported by the module. That is stated as a rule, not a hope: a Go test asserts it (§9.5).

The honest cost, which the design states rather than argues away: **the console brings a Node toolchain, a TypeScript build and by far the largest dependency tree in the repository.** There is precedent but no scale: the repo already has three small npm projects — `internal/budget/rules/emulator/` (the pinned `firebase-tools`, installed in CI with `npm ci --ignore-scripts`), `images/base/harnesses/` (the agent harnesses baked into the base image) and `deploy/sandbox/` (a zero-dependency sandbox helper) — and none of them has a runtime, a bundler or a lockfile measured in megabytes. The console has all three, plus CI time. Both are mitigations, not eliminations: exact pins and a lockfile (§5.2), `npm ci --ignore-scripts`, and a console job that is **cheap rather than filtered** — an earlier revision of this sentence offered "a path-filtered workflow so Go and console jobs do not run each other", which §9.4 shows would break the release gate, so the job runs unconditionally and pays for itself with a cached, minimal install.

A separate repository (**D3**'s alternative) is defensible if the owner wants the CLI's CI and supply chain untouched, and the design notes what it costs: a cross-repo contract, two release processes, and the console's rules restated somewhere they are not enforced.

### 8.3 The interface that makes Option C a drop-in

`FugaroSource` is the only thing the screens may talk to: it yields `JSONDoc`-shaped snapshots and emits change events, and it knows nothing about how they were produced. v1's implementation spawns the CLI. ## 9. Testing without a live cloud

The repo's existing discipline is the template: `watch`'s **golden frames** — `internal/watch/render_test.go`'s `golden(t, name, got)` helper comparing rendered output to `testdata/<name>.golden` files at fixed widths, rewritten deliberately with `-update` and reviewed in the diff, driven by a fake fixture rather than a terminal — then the in-process RTDB fake `internal/gcpfake`, the Firebase RTDB **emulator** behind the `firebase` build tag with a pinned `firebase-tools` (`internal/budget/rules/emulator/package.json`), and Terraform plans against a mock provider. The console follows it, with one addition — Playwright driving the real Electron binary.

**One correction to an earlier revision of this section, because the design's contract is that every code claim names a symbol that exists.** It said the golden frames come from **`teatest`**. They do not: `teatest` appears nowhere in `go.mod`, `go.sum` or any `.go` file in this repository, and it was **explicitly rejected** — "**No `teatest` (it lives in `x/exp` and moves): the model is driven directly, `m.Update(msg)` then compare `m.View()` to golden files**" (`docs/plans/2026-10-03-m9c-fugaro-watch.md`, work item W15). The mechanism the console copies is the one that is actually there: a direct call and a golden file. A design that cited a dependency the repo does not have would have been the exact failure this design's own §12 exists to prevent.

### 9.1 The fake data source is a recording, not an invention

The primary test double is a **recorded `fugaro watch --json` transcript**, replayed through the fixture `FugaroSource`. A hand-written fixture would only prove the app handles the shapes its author imagined; a recording proves it handles the shapes the CLI emits.

- **Where recordings come from.** The sandbox installation and the sandbox repository, never `belong` — the same rule every live check in this repo carries. The recorder (`console/tools/record-fixture/`) spawns the CLI, captures the NDJSON, and **redacts**: task titles clip and redact in `watch` already (`title` is "the run's own title, clipped to 80 characters and redacted", `m9-budget-and-dashboard.md` §6.2), and the recorder applies the same treatment to anything else repository-specific (repository names, PR URLs, requester addresses). A fixture that fails the redaction check is not committed.
- **What a fixture must contain to be worth having**: a normal run; a run that goes `silent` then `lost`; a kill switch flipping mid-feed; a repository at its cap; a run with `auth: oauth` (notional spend); an absent field (`round`/`spent` before the run reports them); a **gap** in the feed long enough to trip the 45 s stale banner; and a **hostile title** — the `watch` render tests already carry hostile-title cases, and the console's must too.
- **The recorder is console-side.** It adds no CLI command, no flag and no backend: the CLI gains nothing from this design.

### 9.2 Unit tests (no Electron)

The schema types, the availability-state rendering rules, the sanitization re-application, the burn-rate computation (checked against `watch`'s own 5-minute rolling window so the two cannot drift), the version-skew range check, and **the spawn allow-list** (a test that iterates the allow-list and asserts every entry is read-only, and that a table of write subcommands is *not* reachable — the mutation-proof form, so adding `budget kill` to the list fails a test rather than passing review by accident).

### 9.3 Playwright + Electron end-to-end

Playwright drives the packaged app (`electron.launch`) with the fixture source, and asserts:

- **Behaviour**: the Live screen renders the fixture's runs with the right flags; the Spend screen keeps model, `~$` and compute separate; a `(partial)` day is hollow; the Project screen shows what is not built as not built.
- **Screenshot goldens**, in `internal/watch/render_test.go`'s golden-frame tradition (a direct render call, a `testdata/` file, an explicit `-update` flag — **not `teatest`, which this repo does not use**): one per screen per theme, with a documented, deliberate update command. Golden images catch the density and layout regressions that DOM assertions cannot.
- **The security assertions, which are the ones that must not be allowed to rot** (§5.1): a remote navigation is refused; a `window.open` is refused and does not open an internal window; **any renderer-initiated network request fails** — enforced both by the CSP (`connect-src 'none'`) and by a Playwright route handler that fails every request, so a CSP regression is caught too; a hostile title renders as text; and the IPC surface rejects an unknown channel name and a malformed argument.

### 9.4 How this runs in CI

- **Two runners**: `macos-latest` (the platform we ship first, and the only one where the app's real packaging works) and `ubuntu-latest` with `xvfb-run` for the fast Linux pass. **Since the owner's ruling of 2026-10-20 the Linux runner also builds what it ships** (§7.6, D10): a second, **build-only** workflow — staged as `docs/pending-workflows/console-linux.yml` and, for the tag, the Linux job inside `console-release-linux.yml` — runs `electron-builder --linux`, asserts that exactly one AppImage and one `.deb` came out, and uploads them. It holds **no environment and no secret**, because there is nothing to sign with, and it is **not** in `scripts/release-gate.sh`'s required-check list: a red Linux pack is information rather than a blocked release, and adding it to the gate is the owner's decision and not a packaging change — the staged README sets out the three edits it would take, and why folding a second job into `console-tests.yml` silently would change which checks gate a tag. **Windows joins when D10 says so** — and the 2026-10-20 amendment did not say so.
- **The Node toolchain is installed only for the console jobs**: `actions/setup-node` with the version `console/package.json`'s `engines.node` names, `npm ci --ignore-scripts`, then the console's own test command. This mirrors how the rules tests gate the Firebase emulator behind a `firebase` build tag rather than making every job pay for it.
- **The console job runs unconditionally, and this is not a performance choice — it is what makes the job gate-able.** An earlier revision of this section proposed path filters "so the two halves do not run each other": the console job on `console/**`, the Go jobs on everything else. **That breaks the release gate.** `scripts/release-gate.sh` requires a named check on the tag's commit *and*, in its `identical_tree_checks` fallback, the same names on the pull request head whose tree matches; a check that does not exist is not a success, so a `console` job that a `paths:` filter skipped is a gate that exits 1 on **every** tag — the gate's `names` array would hold the console's check runs, and a name no run reports would refuse releases that never touched the console. Ordering the gate edit after the copy-in does not help: the filter, not the order, is the bug. So **the console job has no `paths:`/`paths-ignore:` filter and no `if:` guard**, and it is **keyed `console`** — the same one-word convention `test`, `terraform` and `rules` follow. (The check-run names the gate requires are the two matrix legs, `console (ubuntu-latest)` and `console (macos-latest)`: GitHub appends a matrix job's values to its job name, so there is no check run named exactly `console` to require. Task 4.6's gate edit and its test are written for the legs, and derive them from this job's key and matrix.) The trigger pattern to copy is `ci.yml`'s — `push: branches: [main]` plus `pull_request` — and the console job **takes its triggers and not its docs-only skip**: `ci.yml`'s `changes` job spares `test`, `rules` and `terraform` on a documentation-only pull request, and the console job does **not** join them, because the same fallback reads the pull request head and treats a *skipped* check as a non-success. (The Go jobs can keep that skip: the gate's fallback already has that behaviour today, and on `main` every job runs.) If the owner ever wants the console's CI time back, the safe levers are a conditional *inside* the job or a cached, incremental install — never a filter or a guard that removes the check. Task 1.4's staged-workflow test asserts the job name and the triggers precisely so this cannot regress silently — and the signing workflow (Task 4.2) carries its own test asserting it never gains a pull-request trigger.
- **Two workflows, not one, and the split is a security boundary rather than tidiness.** An earlier revision staged a single `console.yml` carrying both, which would have put the signing job — and the Apple secrets it reads — in the same file as a job that runs on **every pull request**: a branch pushed by anyone with write access would then execute next to the signing key, and the environment protections that exist to stop that were not in the picture at all. So:

  | Staged file | What it holds | Triggers | Secrets |
  |---|---|---|---|
  | `docs/pending-workflows/console-tests.yml` (Task 1.4, copied in as Task 1.5) | the `console` job: `actions/setup-node`, `npm ci --ignore-scripts --no-audit --no-fund`, the unit tests and the e2e pass | `pull_request` and `push` to `main`, unconditionally and with no `paths:` filter — the gate-ability rule above | **none at all**, and the staged file is asserted to contain no `secrets.` reference |
  | `docs/pending-workflows/console-release.yml` (Task 4.2, copied in as Task 4.5) | the signing, notarising and stapling job, and the verification that records `codesign --verify --deep --strict`, `spctl --assess` and `stapler validate` | **`push` of a `vX.Y.Z` tag, and nothing else** — never `pull_request`, never `pull_request_target`, never `workflow_run` | the certificate, its password and the App Store Connect key, read from a **protected GitHub environment** (`environment:`) whose deployment rules are the owner's, and named only as `secrets.NAME` |
  | `docs/pending-workflows/console-linux.yml` (2026-10-20; the Linux build check §7.6 rules in) | the `console-linux` job: the pinned toolchain, `npm run build`, `npm run package:linux`, an assertion that exactly one AppImage and one `.deb` came out, `upload-artifact` | `pull_request` and `push` to `main`, no `paths:` filter — the gate-ability reasoning above, even though this check is not in the gate | **none at all**, because there is nothing to sign with |
  | `docs/pending-workflows/console-release-linux.yml` (2026-10-20; **supersedes the row above's `console-release.yml`**, so it is copied over the staged copy *and* into the workflow) | that file **plus** a third, secret-less `linux` job that packs and then verifies **what ships** — the SHA-256 of both artifacts, the `.deb` through `dpkg-deb`, the AppImage through its own runtime's `--appimage-extract`, and the fuse wire read back out of the executable inside each artifact — handing both legs to one `publish` that merges them into a single `console-sha256sums.txt` and signs it keyless with cosign | identical to the row above: **`push` of a `vX.Y.Z` tag, and nothing else** | **the Linux job holds none**; the macOS job still reads the Apple secrets from the protected environment |

  The signing workflow publishes the console's **own release, `console-vX.Y.Z`** (D11: one gate, the CLI's tag; its own release), never an asset on the CLI's immutable release; the job that builds and signs holds a read-only token, and a separate `publish` job — no environment, no Apple secret, no packer — holds `contents: write`, re-checks the assets' SHA-256 sums and publishes. Every pack is stamped with the tag's X.Y.Z as the app's version. A tag push runs the workflow as the tagged commit holds it, so the environment's required reviewer and a tag ruleset are the real control, and the approver confirms the tag is on `main`; the job also checks the tagged commit is an ancestor of `origin/main` before anything else. The signing workflow runs **`scripts/release-gate.sh` first**, exactly as `release.yml` and `images.yml` do, so a console build is not signed for a tag the gate would refuse — and because the gate requires the console tests' check runs, the tests workflow's job must exist on `main` and on every pull-request head, which is the previous bullet's rule. **The two files are the reason the gate can require the tests check without ever running the signing one**: the gate lists check *names*, and the signing job's name is not among them, because a signing check that exists only on a tag is not a check the identical-tree fallback could ever find.
- **A workflow file is described, never written.** This repo refuses to let an agent create or edit anything under `.github/workflows/` (GitHub will not accept Fugaro's push of a workflow change at all, so a run that edits one cannot be delivered). So both workflows' text is written **in the plan and by the owner**, as `docs/pending-workflows/README.md` already does for another staged workflow. The plan's CI tasks say this explicitly.
- **And therefore: no CI runs a console test until the owner copies the staged tests file in — which the plan now puts in phase 1, not phase 4.** The tests workflow is staged with Task 1.4 and applied by the owner as Task 1.5. **The earlier claim that the console has CI "from its first pull request" is false and is withdrawn**: Tasks 1.0 to 1.4 — the pinned toolchain, the hardened window, the IPC allow-list, `FugaroSource` and the fixtures — merge **before** the copy-in, and no workflow runs a console test on those four tasks or on the pull requests that carry them. What is true is that the uncovered window is exactly those four tasks and nothing later: from Task 1.5 onward every pull request and every `main` push runs the `console` job. Before the correction the copy-in sat in phase 4, which meant phases 1 to 3 merged with **no workflow running a single console test at all**. The signing workflow is the one that lands late (staged as Task 4.2, applied as Task 4.5), and the release gate does not require its check at any point (**D18**): the gate's list carries the tests workflow's two check runs (`console (ubuntu-latest)`, `console (macos-latest)`), and making it require a job no workflow runs would refuse every tag on this repository — including the releases that ship none of this. The design says it here rather than leaving a reader to infer a green pipeline from a CI section.
- **No cloud credentials in these jobs.** Not one: they run against fixtures.

## 11. What is out of this design's remit

- **Any CLI change.** The console needs no new flag and no new command in v1. If a screen needs a field no `--json` emits, that is a CLI task in a CLI plan.
- **Any change to the RTDB rules or the Firebase IAM.** The console reads what launchers and operators already read.
- **Any change to `.github/workflows/`.** Described for the owner, never written by an agent.
- **The `belong` installation.** Never touched, by any step, agent-run or owner-run.
