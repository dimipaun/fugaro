# Releasing Fugaro

One SemVer tag `vX.Y.Z` releases everything (design section 12): the binary, the base images, the Terraform modules at the tag, the schemas at the tag, and the plugin. Before 1.0, minor versions may break.

## What a tag does

A push of a strict `vX.Y.Z` tag triggers two independent workflows:

- `release.yml` (this document): checks the tag, then runs GoReleaser, which builds `fugaro` for darwin and linux on amd64 and arm64, writes `checksums.txt`, an SBOM per archive (syft), a keyless cosign signature of `checksums.txt`, and the GitHub Release; it also pushes the Homebrew cask. **The release body** is, in order: the install header, `## Highlights` (the hand-written `docs/releases/vX.Y.Z.md`, below), `## Changelog` (generated from the commit titles since the previous tag, with no SHAs; `release:`, `docs:`, `test:`, `chore:`, `ci:`, `Design:` and merge commits are left out) and the base-images footer. **Pre-release marking:** v0.1.0 to v0.3.x are marked as pre-releases and stay so; from v0.4.0 on a release is a normal release (it can be "Latest"). GoReleaser's `prerelease: auto` only recognises `-rc1`-style suffixes, which the strict tag rule never produces, so the workflow's last step marks the old ones itself, asking `scripts/release-policy.sh prerelease X.Y.Z` (a numeric comparison, tested in `scripts/release_test.go`).
- `images.yml`: today builds, smoke tests, scans and publishes `ghcr.io/dimipaun/fugaro-web-node`, `fugaro-go`, `fugaro-java-services`, `fugaro-history` (`X.Y.Z` and a moving `:X` each, linux/amd64 only) and `fugaro-base` (per-architecture `X.Y.Z-amd64`/`X.Y.Z-arm64` plus the multi-platform index `X.Y.Z` and a moving `:X`, both linux/amd64 and linux/arm64). After publishing, the `verify-public` job pulls every reference with no login (`images/verify-public.sh`) and fails the release when one cannot be read or has no `linux/amd64` build (`linux/arm64` too, for `fugaro-base`); it lists each image's digest in the run summary. Pull requests build, smoke test and publish nothing; the nightly run scans. The 0.7.0 hard cut deleted `images/go/`, `images/web-node/` and `images/java-services/` from the tree, so the `base` job's three legacy legs now have nothing to build and skip (the version job's directory probe finds none); they are not yet removed from the workflow file itself.

  **Applied for 0.7.0:** the legacy per-kind `base` job is deleted from `images.yml` and `publish` and `verify-public` cover `history` (`fugaro-base` has its own `fugaro-base (amd64|arm64)` and `publish-base` jobs). The nightly workflow therefore no longer refreshes `fugaro-go`, `fugaro-web-node` and `fugaro-java-services` (design §10): their already-published tags stay on ghcr.io forever as immutable history, and no release after 0.6.x republishes a moving `:X` tag for any of the three. **Staged, and a release gate:** #318's Task 1 — signing the pushed base image by OCI digest and publishing the nightly-immune `-pinned` tag — is what the resolve step verifies. [PR #377](https://github.com/dimipaun/fugaro/pull/377) merged it as a **staged** file, `docs/pending-workflows/images.yml`, which only the owner can copy into `.github/workflows/images.yml`; the pre-tag checklist below gates the 0.7.5 tag on that copy being on `main`.

Neither workflow runs the test suite; CI already did on main. Both workflows run `scripts/release-gate.sh` first, so a tag on an off-main or red commit publishes nothing (no binaries, no images). It refuses unless the tagged commit is reachable from `origin/main` and the GitHub Actions checks `test`, `terraform`, `rules` and both of the console's (`console (ubuntu-latest)`, `console (macos-latest)`) all succeeded on it (a check of that name from another app does not count); if CI is still running, re-run the failed job once it is green. `release.yml` also requires the plugin version to equal the tag. **The console's two check runs exist on `main` only once the `console` branch has been merged into `main` and a push to `main` has run `.github/workflows/console-tests.yml`:** the requirement and the workflow arrive together, so do not run the gate (or `scripts/release.sh`) on a `main` commit before that, since a commit without them has the console checks missing and the gate refuses it.

## Making the image packages public (one time per package)

The mirror (below) reads the source with no credentials, and a plain `docker pull` has none either, so every published package must be public. **In practice a package a workflow publishes from this public repository is public from the start** (it inherits the repository's visibility): the v0.2.0 release published `fugaro-go`, `fugaro-java-services` and `fugaro-history` for the first time, `verify-public` passed with no manual step, and all four manifests answered 200 anonymously. `fugaro-base` is expected to behave the same once its own first publish happens (above; not yet). So after a release that publishes a new package, only check that it is public: the `verify-public` job passing is that check.

If a package ever turns out private (`verify-public` fails with "cannot be read without a login (is the package public?)"): GitHub has no API call for this with the workflow's token, so do it by hand:

1. Open `https://github.com/users/dimipaun/packages/container/fugaro-<name>/settings`.
2. Under "Danger Zone", "Change package visibility", choose Public and confirm.
3. Re-run the `verify-public` job of that release's `images` run (or `images/verify-public.sh ghcr.io/dimipaun/fugaro-<name>:X.Y.Z` on any machine, which uses no login).

Later releases of a public package stay public.

## How `fugaro init` uses the images (the mirror)

**The base image is not copied any more, and the reason this section used to give is gone.** The packages are public, and Artifact Registry **remote repositories** take `https://ghcr.io` as a Docker upstream — a documented feature, not a workaround (design [registry-remote-repository.md](design/registry-remote-repository.md) §1, §2.3). So the `images` stage of `fugaro init` resolves `ghcr.io/dimipaun/fugaro-base:X.Y.Z` (the running binary's version; `--image-source ghcr.io/<owner>` for a fork) at its nightly-immune `-pinned` tag, **verifies the cosign signature that release's tag push attached to that exact digest** — all four claims of that push: the certificate identity `https://github.com/dimipaun/fugaro/.github/workflows/images.yml@refs/tags/vX.Y.Z`, the issuer `https://token.actions.githubusercontent.com`, and the certificate's trigger (`push`) and repository (`dimipaun/fugaro`) extensions, the last two because a `workflow_dispatch` run against that same tag ref carries the same identity and is not a tag push — reads the digest back through the installation's own remote repository `<region>-docker.pkg.dev/<gcp-project>/fugaro-ghcr/` and records that path at that digest in `base_images`: nothing is pushed anywhere, nothing is copied, and the 1.2 GB the copy used to move through the operator's machine is gone. Cloud Build and Cloud Run Jobs pull the pinned digest through the project's own repository, so no job needs ghcr.io reachability and there is no copy to keep in step. **`--base base` has nothing to pin yet**, since no release has published `fugaro-base` (above): it fails with a clear error rather than falling back silently.

**The history image is still copied**, because it is not the base and this change leaves it alone: `--firebase` copies `ghcr.io/dimipaun/fugaro-history:X.Y.Z` into `<region>-docker.pkg.dev/<gcp-project>/fugaro-base/` as the user, where it lands as `history:latest`, which the history job runs. That copy is plain HTTP against the registry API: no Docker, only the `linux/amd64` image, each digest verified, nothing sent when the destination already has the same digest. A development build copies nothing and says how to build from a checkout.

What a release must therefore guarantee is what `verify-public` checks: every published reference is anonymously readable and has a `linux/amd64` build. Until a package is made public (above) a user's `init` is refused with the unreadable-source message. **What each path's trust rests on, now that they differ.** For a base kind the anchor is the signature, not the tag: the CLI verifies the release's cosign signature (identity, issuer, trigger and repository, above) and pins the digest, so a moved ghcr.io tag cannot change what a job pulls (design §4) — signing the pushed base image (the plan's F1, #318's Task 1, [PR #377](https://github.com/dimipaun/fugaro/pull/377) — merged as the staged `docs/pending-workflows/images.yml`, not yet copied into `.github/workflows/images.yml`) is what makes that possible, and until a release publishes a signed `-pinned` tag every base pin refuses, loudly, rather than falling back to a tag. For the history copy the anchor is still the tag as ghcr.io resolves it: pin the digest from the `verify-public` run summary with `--expect-digest history=sha256:<hex>` (KIND is `go`, `java-services`, `web-node` or `history`; a base kind refuses `--expect-digest` only as a cross-check of the verified digest). The release notes do not list the digests (GoReleaser runs in another workflow and cannot know them). **Which images exist when:** v0.1.0 published only `fugaro-web-node`; v0.2.0 was the first to publish `fugaro-go`, `fugaro-java-services` and `fugaro-history`; `fugaro-base`'s own first publish happens on the next release tag that runs `images.yml` (the `fugaro-base`/`publish-base` jobs are already live; above), not yet done as of this writing.

## Secrets

- `HOMEBREW_TAP_GITHUB_TOKEN`: a fine-grained personal access token with `Contents: Read and write` on the single repository `dimipaun/homebrew-tap`. Add it as a repository secret. If it is absent the release still succeeds and only the tap update is skipped, with a `::warning::` and a line in the run summary (add the secret and re-run the job, or copy the cask from a `dry-run` artifact's `homebrew/Casks/` by hand).
- Nothing else: the release uses the workflow's `GITHUB_TOKEN` (`contents: write`) and GitHub OIDC (`id-token: write`) for cosign.

## The cask's quarantine hook

The Homebrew cask runs a post-install step on macOS: `xattr -dr com.apple.quarantine` on the installed `fugaro`. The binaries are not signed or notarized by Apple, so without it Gatekeeper blocks the first run of a downloaded binary. The cost is that Gatekeeper's check is skipped for this binary; integrity rests on the sha256 in the cask, which comes from the release archives, and on the cosign-signed `checksums.txt`. Linux cask support was not tested; Linux users can use the archive or `go install`.

**`cosign` is not a cask dependency, and that is deliberate.** The cask installs the `fugaro` binary and nothing else: `fugaro` runs without `cosign` until the first base image is pinned, and `fugaro init --base`/`image refresh` **refuse** (naming `--base-image`) when it is missing rather than pinning a digest nothing verified (design [registry-remote-repository.md](design/registry-remote-repository.md) §9). Declaring `depends_on formula: "cosign"` would put sigstore's toolchain on every user's machine for a verification that runs when a base is pinned — an upgrade-time step, not a per-run one — so instead `fugaro doctor` reports it with the install link on every run, and the confirmation names the binary it used. Install it from your distribution or from Homebrew (`brew install cosign`); nothing in the release or the cask changes for it.

### The `postflight` deprecation warning

Homebrew warns that a cask using a `postflight` quarantine removal is deprecated (it is moving to refuse unsigned, un-notarized casks). That warning comes from Homebrew, not from GoReleaser: the `postflight` block is the one this repo's `hooks.post.install` asks for, GoReleaser v2.18.2 (the pinned version) emits `hooks.post.install` as `postflight` with no alternative stanza, and `.goreleaser.yaml` uses none of the config fields v2.18.2 flags as deprecated (`binary`, `manpage`, `url.verified`, `conflicts.formula`). So there is no supported config change to make offline, and none was made. What would remove it: sign and notarize the macOS binaries (GoReleaser's `notarize` support, which needs an Apple Developer ID certificate and API key as secrets), then delete `hooks` from the cask. Until then the hook stays; if Homebrew starts disabling such casks, `brew install` of the tap cask will fail and users fall back to the archive or `go install`.

## Cutting a release

**Before you tag (the checklist; each item has been missed or is easy to miss):**

- **Do not tag 0.7.5 until the signing workflow is on `main`.** #318's Task 1 — the `-pinned` tag and the `cosign sign` step in `images.yml` — is [merged as a staged file](https://github.com/dimipaun/fugaro/pull/377) (`docs/pending-workflows/images.yml`), and only the owner can copy it into `.github/workflows/images.yml`; that copy must be on `main` **before** the release's version-bump merge commit, so the tagged tree carries it: the 0.7.5 CLI resolves `fugaro-base:<version>-pinned`, verifies that digest's cosign signature and only then pins it, so a tag pushed by a workflow without those steps publishes no `-pinned` image and no signature — every `fugaro init --base`/`image refresh` on 0.7.5 refuses (fail closed) and no installation can migrate off the copied base. Same ordering as the plugin-version bump and the Highlights file: on `main` before the tag, never after.
- **Write `docs/releases/vX.Y.Z.md` (the Highlights) and merge it to `main` through a PR, from 0.4.0 on** ([docs/releases/README.md](releases/README.md) has the format: 3 to 6 user-facing bullets, then `### For operators` when a rollout order matters, then `### Known limits` with what this release does not do, does not stop or leaves to a later one — a release ships with its known limits in its notes, so that section goes in unless the release genuinely has none; take the content from the pull requests merged since the previous tag). GoReleaser reads it from the tag's tree through `readFile` in `release.header` (v2.18.2 has no `from_file` for the release header and `readFile` yields an empty string for a missing file, so nothing in GoReleaser enforces it). Two checks do: `scripts/release.sh` stops in its preconditions, naming the file, when it is missing or empty on `main`, and the release workflow's first step fails before building anything. Versions below 0.4.0 need no file.
- **Run `scripts/bump-plugin-version.sh X.Y.Z` and commit it** (through a PR to main). The release gate refuses a tag whose plugin version or any skill header differs from it, and a repository pinned to the tag would otherwise load a plugin that disagrees with the binary.
- **Check that each new ghcr.io package is public** (see "Making the image packages public"): a package published from this public repository inherits its visibility (it did for v0.2.0), so this is only a check; `verify-public` passing is the proof.
- **Turn on tag protection and immutable releases (the repository owner's setting; Fugaro does not change repository settings).** A git tag is mutable, and the plugin pin and the image tags are anchored to it, so: add a GitHub ruleset that restricts updates and deletions of `v*` tags (Settings, Rules, Rulesets, target tags `v*`, restrict updates and deletions), and enable immutable releases. Without them, anyone who can push tags can move `vX.Y.Z` after users pin to it.
- **The console is its own release, `console-vX.Y.Z`, never an asset of the CLI's** (the owner's ruling of 2026-10-17, "Separate console release"; once `docs/pending-workflows/console-release.yml` is applied as plan Task 4.5). With immutable releases on, GoReleaser's `vX.Y.Z` release cannot take an asset once published, so the console workflow, on the same tag and behind the same gate, builds and signs in a job holding only a read token and hands the assets to a separate `publish` job (the only one with `contents: write`), which re-checks their SHA-256 sums and creates `console-vX.Y.Z` as a draft, uploads the `.dmg`, the `.zip`, `console-verification.txt` and `console-sha256sums.txt`, and publishes it with `--latest=false`. Before tagging: the tag ruleset must let the workflow create `console-v*` tags, and no `console-vX.Y.Z` release or tag may exist yet (a re-run refuses rather than clobbering; delete a leftover draft first). The console's version is the tag's (`console/package.json` says `0.0.0`; every pack is stamped with `-c.extraMetadata.version=X.Y.Z`), so the `.dmg` and `.zip` names carry X.Y.Z. When approving the `console-release` deployment, confirm the tag's commit is on `main`: the workflow runs as the tagged commit holds it, so the environment's reviewer and the tag ruleset are the real control. The console's Homebrew cask, when it exists, points at the console release.
- **Verify `gcpProjectFieldSince`** (`internal/cli/init_fugaroyaml.go`, currently `"0.4.0"`, the release that ships the field) equals the release that ships the `gcp_project:` field. `fugaro init --anchor` (and plain `fugaro init`'s repository stage, in the checkout) compares each job image's build record and each copied base image with it, refusing (or warning about) images that predate the field; a wrong value warns too late or too early.
- **Verify `recipesSince`** (`internal/cli/recipes_skew.go`, currently `"0.5.0"`, the release that ships recipes) equals the release whose runner reads a task's `recipe` and `agent.recipe`. `fugaro run` compares each job image's build record `base_ref` with it before launching a run that names a recipe (or from a checkout whose `fugaro.yaml` sets `agent.recipe`), and refuses an older release base; a wrong value refuses too late (old runners fail the run) or too early.
- **Verify `layeredSince` in `internal/cli/recipes_skew.go`** equals the release that ships the project layer (0.6.0).
- **Verify `cloneSince` in `internal/cli/recipes_skew.go`** (currently `"0.7.5"`) equals the release whose runner reads `FUGARO_CHECKOUT` and makes a blobless clone at start (generic-tool plan Task 17). That release shipped, so this line's job is now the same as the other constants' above: verify it names the release that carries the runner support; a wrong value refuses too late (old runners start from an empty checkout with no idea why) or too early. **`cloneShipped`, next to it, is `true`** — the flip landed in 0.9.0, after the owner ran live Check 38 (`docs/gcp-live-checklist.md`) and it passed on 2026-10-17. Its one edit re-enabled everything at once:
  - `checkCloneImageSince` no longer says "checkout: clone's own runner side is not released yet" (for either a too-old release or a non-release ref); it gives the ordinary "upgrade your base image" refusal, or the ordinary warning for a ref whose release is unknown, the same as every other `*Since` gate;
  - `fugaro init --repo` (`planRepo`) and `fugaro image refresh` (`refreshCloneJobs`) deploy and move a `checkout: clone` workflow's job instead of refusing through `refuseClonesNotShipped`;
  - `fugaro validate` no longer warns that a `checkout: clone` workflow cannot run.

  **The check's own record was not edited by that PR, and still is not.** `docs/gcp-live-checklist.md`'s Check 38 row reads **USER-RUN, NOT RUN** and its section still describes step 0's hand-flipped build, because writing the run's FACT lines there is the owner's step: the flip's PR carries the constant, its tests and the docs above, not another owner's results. A release that reads the two together should know that the pass this bullet names lives in the owner's ruling, not in the checklist file (`TestChecklistHasCheck38` pins the row and the section as they are). `cloneSince` was not bumped by that PR: the check needed no runner fix, so the constant still names the release that shipped Task 17. **Nothing in a later release's commit may flip `cloneShipped` back**: it is what says the option is shipped, and a release that had to un-ship it would be its own PR, with the check's failure as its evidence (the flip's PR history — owner's ruling, 2026-10-14, generic-tool plan Task 18 — is why no release commit ever held this edit: Check 38 needs a binary built with the gate open, so the flip could not be the release commit's change).
- **Verify `namedTokensSince` in `internal/cli/recipes_skew.go`** (currently `"0.6.5"`) equals the release that ships `task.Spec.OAuthToken` (named Claude OAuth accounts). `fugaro run` gates it (`internal/cli/run.go`) before any launch that would set a non-default `OAuthToken` — first run, follow-up, `--workflow` and `--batch` all go through the same check; a wrong value refuses too late (old runners fail the run) or too early, the same risk `recipesSince`/`layeredSince` already carry.
- **Verify `policySince`** (`internal/cli/recipes_skew.go`) **and `VersionSince`** (`internal/projectpolicy/version.go`). `policySince` (currently `"0.8.0"`) is the release that ships the project-centric policy model: the published node `config/policy/shared`, its `version` and its `allow_repos`. It equals the release whose launcher reads that policy before a launch, and it is *not* the release a policy version arrived in: `projectpolicy.VersionSince` maps each policy version to the release that introduced it (1 is the model, `"0.8.0"`; 2 is the profile gate, `"0.8.5"`; 3 is the account axis — a profile's `claude_accounts` and the `accounts` block it is gated by — `"0.9.0"`), and **a release that raises `projectpolicy.Version` adds its row in the same change** — `TestVersionSinceCoversEveryVersion` fails until it does, so a bump cannot ship a refusal that sends an operator to a release they already run. `fugaro run` gates the launch (`launchPolicyGates`), refusing — before the execution is created — a policy whose `version` is above what the binary understands (that refusal — like every too-new refusal, the runner's and `fugaro project policy`'s included — names the release `VersionSince` holds for the version on the node, and only the upgrade, with no release, for a version above every row; a node *behind* the binary keeps `policySince`) and a launch whose repository the policy does not admit (that one is the run's own message, `projectpolicy.NotAdmitted`'s, with no release in it). The rules marker's `RulesVersion` is deliberately not part of the gate (an absent marker, or one below `PolicyRulesVersion` — the generation that carries the policy nodes — is the legacy path: no policy read, no refusal; a marker above it reads a policy whatever generation the deployed document is), so this line, like the ones above, verifies a release and nothing else; a wrong value refuses too late (an older launcher launches a run its own runner then refuses at bootstrap) or too early.
- **Verify `sealSince`** (`internal/cli/recipes_skew.go`, currently `"0.9.0"`, the release that ships both halves of the budget token's seal, [design/budget-token-channel.md](design/budget-token-channel.md)) equals the release whose runner reads a sealed token from `tokens/` with the seal key in `FUGARO_BUDGET_TOKEN`. `fugaro run` gates it (`sealGate`) before any launch that mints a budget token. **Refused:** a job image whose build record is missing, unreadable (not JSON, or no `version`) or has no `base_ref`; one built from a release base older than `sealSince`; one built from a non-release (development or hand-pushed) base whose record does not say `sealed_budget_token` and whose `built_at` is before `sealRunnerIntroduced` (2026-10-17T17:45:33Z); and, for a `checkout: clone` workflow, a `base_images.base` that is unset or a release older than `sealSince`. **Passes with no warning:** a release base at `sealSince` or later, or a non-release base whose record says `sealed_budget_token` (written by the base's own fugaro at render time). **Passes with only a warning** (the launch goes ahead, and a base that in fact predates the seal would echo the key into the run's record): a non-release base whose record has no `sealed_budget_token` and a `built_at` at or after `sealRunnerIntroduced`, or none — `built_at` is the job image's build time, not the base's — and a non-release `base_images.base` of a `checkout: clone` workflow. The record-based refusals refuse some legitimate launches, each cured by rebuilding the job image with `fugaro image build --repo <owner/name> --workflow <name>` (or `fugaro image refresh`): a job image older than build records, or whose record was deleted; one pushed by hand, adopted, or built outside `fugaro image build`; a record that is not valid JSON or has no version; a record with an empty `base_ref`. What the record shows is only what the base image's own build step recorded: `sealed_budget_token` and `base_ref` come from the base's fugaro during the image build, the launch runs the repository's `:latest` (never compared with the record's `image_digest`), and a `dockerfile:` workflow builds its own image, fugaro included — so a hand-pushed `:latest`, or a `dockerfile:` image shipping an older fugaro, still gets the key echoed into `result.json`, where peer runs of the repository can read it. An older runner would format the key into its bootstrap error and look for the token under `runs/`. A wrong value refuses too late (the key reaches an old runner's record) or too early.
- **Check the project-secrets release's plan shape** (this one is a plan-shape check, not a constant-equality one; the single `*Since` constant the feature does add, `gitSecretIDSince`, has its own bullet below). Confirm the release note for the shipping version names the owner's migration sequence ([design/project-secrets.md](design/project-secrets.md) §6), and that an installation applying the `installation` root for the first time after this feature ships sees the new `secrets.tf` resources as **creates only** — never an update or replace of an unrelated resource (a regression elsewhere in the module would show as an unexpected diff there).
- **Verify `gitSecretIDSince`** (`internal/cli/recipes_skew.go`, currently `"0.7.5"`) equals the release that ships `imagecheck.go`'s awareness of `CheckJobSpec.GitSecretID`. `fugaro init --repo` gates moving the git credential to project scope on it, parsing the check job's own base image ref the same way `gcpProjectFieldSince`'s own check already parses a base ref; a wrong value refuses too late (an old base image's daily rebuild still silently fails) or too early (a repository that could safely move stays blocked).
- **Check the config-transitions release's plan shape** (also a plan-shape check, not a constant-equality one: the design adds no `*Since` constant, because `--retire` is a flag and no `fugaro.yaml` key changes). Confirm the release note for the shipping version names the retirement sequence ([design/config-transitions.md](design/config-transitions.md) §4, and the "Changing auth, or removing a workflow, secret or provider" section of [gcp-setup.md](gcp-setup.md)), and that a repository applying the `repo` root for the first time after this ships sees no unexpected diff: the ordinary `fugaro init --repo` behaves as before, plus the retirement summary line, because the refusal gate is narrow (§3.3 — only a `prevent_destroy` plan abort, or a state-held job still protected after its variant left the configuration). The note must also state that Fugaro never deletes a secret or a secret version, so a retirement leaves a container and its value in Secret Manager — and it must not promise that re-mounting a container is by itself what brings one back: a live container carrying the repository's `fugaro` labels is adopted (imported) back into the plan by the next run, which is the same lookup that keeps it out of the retirement set, while a container the run reported as `KEPT` is one that lookup could not vouch for.
- **Regenerate the provider price catalog and read the diff** (`scripts/gen-price-catalog.sh`, which writes `internal/pricing/catalog/catalog.json`): it reads OpenRouter's public API (no credentials, no cloud call) and must be deterministic, so the diff is only what actually moved. Read it — a price that **rose** is invisible until someone regenerates, and the run only covers that gap by charging the dearest end of a tier's range once the file is 30 days old (`catalog.StaleAfter`; `fugaro budget prices` and `fugaro doctor` warn at the same threshold). Commit the result; nothing else in the release depends on it, and no release is blocked by a model appearing or disappearing. The shipped file's `checked_at` and the model and endpoint counts belong in the release notes ([price-catalog plan](plans/2026-10-14-provider-price-catalog.md), Task 1).
- **Verify `catalogSince` in `internal/cli/recipes_skew.go`** (currently `"0.7.5"`) equals the release whose runner reads a route's `require_zdr` and `price_policy` (price-catalog plan Task 4; design [provider-price-catalog.md](design/provider-price-catalog.md) D11). It names a release that **does not exist yet**, on purpose: those keys are written into the job's `FUGARO_MODEL_PROVIDERS`, which every older runner decodes with `DisallowUnknownFields`, so a job written by a newer CLI fails at bootstrap on a field nobody typed. Until the release that ships them is tagged, `catalogSwitchSkew` refuses **every** `fugaro init --repo` whose route sets either key, unconditionally and before any cloud effect (no base image can read them, so "upgrade your base image" would not fix anything). Once it is tagged, this line's job is the same as `recipesSince`'s: verify the constant equals the release that ships them, and **in the same commit flip `catalogShipped` (next to it) to `true`**, which turns that refusal back into the ordinary base-image age check (the installation's base image predating `catalogSince`) and is the one edit that re-enables the two keys.
Flipping it without that fix brings back an `init` that fails partway through its apply.
- **`batchProvisionShipped` in the same file is `true` as of 0.9.5, and that release is what took it off this checklist as something to verify.** `batchProvisionShipped` is `true` as of 0.9.5, the release that fixed the compute module the `fugaro init --provision-batch` stage applies: the reaper's role is the five permissions Google defines, so the role is creatable and the apply completes, and `deploy/terraform`'s `TestCustomRolePermissionsAreAllowedByGoogle` carries an **empty** `knownInvalid` map because the entry it held — `batch.jobs.cancel`, the permission that is not one Google has — went with it. That flip was the whole of 0.9.5's change here, and the names that made the gate re-openable (`batchProvisionOpen`, `batchProvisionDisabled`, `refuseBatchProvisionNotShipped`) went with it: an open gate nothing closes and a refusal nothing can reach are names a later reader re-opens. **The flip alone is not what un-refuses a stage for an installation that has not applied the module change** — the flag is a build constant, so an installation running the new binary against the old module gets the old apply failure, and the stage's own Terraform is what fixes it. **That flip is not a thing a later release re-does**, and the flip alone is not what un-refuses a stage for an installation that has not applied the module change.

- **Verify `artifactsSince` in `internal/cli/recipes_skew.go`** (currently `"0.8.0"`) equals the release whose runner implements a `mode: artifact` recipe: it reads a task's `mode` field, renders through `commands.render` and writes the run record's `render` object (artifact-runs plan Task 2; design [artifact-runs.md](design/artifact-runs.md) §3). `fugaro run` judges three things at it, all before anything is written: a recipe whose YAML the launcher embeds (a project or catalog one) through `checkRecipeImage`, a `checkout: clone` launch through its `checkCloneRecipeImage` twin, and a task carrying `mode` at all through the launcher's own gate — the last because `task.Parse` decodes with `DisallowUnknownFields`, so an older runner refuses the spec outright. A wrong value refuses too late (the run fails at bootstrap, or its task is unreadable) or too early (an image that would have worked stays blocked).
- **Verify `titlesSince` in `internal/cli/recipes_skew.go`** (currently `"0.8.5"`, the release that ships `task.Spec.Title` and `fugaro run --title`) equals the release whose runner reads a task's `title` field: without it the run's title is the task prompt's first line, and with it the launcher's own title, in `fugaro watch`, the registry entry, `fugaro runs ls --json` and the pull request the run opens when the agent wrote no `pr.md` of its own — there its title and its body's first heading (`task.Spec.TitleLine` is the one rule, and an agent that wrote a `pr.md` has named that pull request itself, as it always has). `fugaro run` gates it (`internal/cli/run.go`) before any launch whose spec carries a title — a first run, a `--batch`/`--attempts` launch (every attempt), and a `--pr` follow-up that inherits or overrides its run's title — through both halves of the check, `checkImageSince` for a built job image and `checkCloneImageSince` for a `checkout: clone` workflow. A launch with no `--title` is never gated: its spec is byte-identical to what the previous release wrote (the field is `omitempty`, and `task.Parse` decodes with `DisallowUnknownFields`, so an older runner refuses a task carrying one outright). A wrong value refuses too late (an older runner fails the run at bootstrap) or too early (an image that would have worked stays blocked).
- **Check the artifact-runs release's plan shape** (a plan-shape check, not a constant-equality one; the feature's own constant, `artifactsSince`, has its bullet above). Confirm the release note for the shipping version names three things: **the new recipe mode** (`mode: artifact`, with its `plan` and `render` steps and its `outputs` block, [artifact-runs.md](artifact-runs.md), [recipes.md](recipes.md)); **the new CLI surface** — `fugaro run --attach`, and `fugaro artifacts ls`/`fugaro artifacts get` — and **the fact that the caps count model dollars only**: a render is compute, bounded by `timeouts.total` and the workflow's `resources` and never by `budget.per_run_usd`, with `result.json`'s `cost.compute_usd` an estimate that is reported and never charged (design [artifact-runs.md](design/artifact-runs.md) §6, `SECURITY.md`'s "Known limits"). The note must also carry the boundary the design makes a precondition: an artifact-producing run stays on the plain per-repository Cloud Run backend, and is not enabled on project-centric phase 3's shared project jobs or the VM backend until a per-run prefix condition or a per-run account exists (design §8.5, D11).
- **Check that the Claude claim and the catalog's Claude rows ship in the same release** ([senior-reviewer plan](plans/2026-10-14-openrouter-senior-reviewer.md), P11): the mixed-credentials opt-in ([design/mixed-credentials.md](design/mixed-credentials.md) §4) lets one provider route name one explicit `anthropic/<id>` in its `models`, never a pattern, and the provider price catalog's three measured Claude rows — `anthropic/claude-sonnet-5.5`, `anthropic/claude-opus-5.5`, `anthropic/claude-fable-5.1`, the rows [provider-price-catalog.md](design/provider-price-catalog.md) §11's Phase 2 adds — are the pairing's other half. Nothing is threaded between the two, so either may merge first; they must meet in one release. A release that ships the claim without the rows still works, but a claimed ID is then priced only by an operator's own `model_prices` override, and an override row is thin: an image request on that model is refused and a PDF reserves the default context rather than the model's real one. Before tagging, confirm the release's `internal/pricing/catalog/catalog.json` carries the three rows (the regeneration bullet above produces the diff; add the IDs to the generator's allowlist if they are not on it — no Claude ID is on it as of 0.7.5) and that `fugaro budget prices` shows each of them a `CATALOG` column; if the rows are deliberately left for a later release, say in the release note that a claimed Claude model has to be priced under `model_prices` until they land.
- **Refresh `internal/pricing`'s `checkedAt` date** after checking the vendor's price page (`fugaro budget prices` warns that the table is older than 90 days: the table was last checked 2026-09-30, so it warns from 2026-12-29).
- **Check the layer slice's release shape** ([senior-reviewer plan](plans/2026-10-14-openrouter-senior-reviewer.md), Task 7 step 5): a claim reaches a run by two paths, and only one of them is free. Written in the **operator config** it is an entry in a route's `models`, which `fugaro init --repo` writes into the job's `FUGARO_MODEL_PROVIDERS` — a shape every older runner already decodes, so a job deployed before this release needs no re-`init` to keep working. Written in the **project layer** it is a top-level key of `fugaro/project-layer.yaml`, which the **runner** parses on every launch with `KnownFields` (`config.ParseProjectLayer`), as the daily image check and the Cloud Build copy of the layer parse it too — so a job whose image predates this release refuses the layer file and fails at bootstrap. Before an operator publishes a layer carrying `claude_models`, every repository of that project must therefore have been re-`init`ed against this release (its job running a base image built from the new binary), and the claimed ID's `model_prices` entry must be in the local config and deployed by that same `fugaro init --repo`: the layer cannot carry a price, and the run's route table never carries the claim, so the built-in catalog cannot price it ([project-layer.md](project-layer.md) §6).
- The binary prints the commit it was built from (`fugaro doctor --plugin`, `fugaro update-skills`) with the one line that checks the tag: `git ls-remote https://github.com/dimipaun/fugaro 'refs/tags/vX.Y.Z^{}' 'refs/tags/vX.Y.Z'` must print that commit: on the `^{}` line for an annotated tag, on the only line for a lightweight tag (the `^{}` pattern alone prints nothing for one, which is why both are given). Run it once after tagging.

`scripts/release.sh X.Y.Z` does the whole thing from a clean `main`: it checks every precondition below, bumps the plugin through a PR, waits for it to merge, verifies the merge commit, waits for the release gate on it, then tags and pushes (there is no prompt). It needs `gh` installed and authenticated (`gh auth login`) and nothing else; it never force-pushes, never pushes to `main` directly, and never deletes or re-tags a release.

1. Preconditions, checked in order and stopping at the first failure: `X.Y.Z` is strict SemVer (no `v`, no pre-release suffix, no leading zeros); the working tree is clean (**untracked files count: a stray file blocks the release**, so commit, remove or ignore it first); the current branch is `main` and equals `origin/main` after a fetch; for `X.Y.Z` of 0.4.0 or later, `docs/releases/vX.Y.Z.md` exists and is not empty on `origin/main` (so before any branch, PR or tag); `gh` is installed and authenticated and targets the repository `origin` points at; the tag `vX.Y.Z` doesn't already exist on origin (a release is never re-tagged, see "Rolling back" below; a tag that exists only locally is handled at step 5); `X.Y.Z` is greater than the latest released tag (only strict `vX.Y.Z` tags count, so `-rc` and four-part tags are ignored); and `test`, `terraform`, `rules` and both console checks all succeeded on the tip of `main` (reusing `scripts/release-gate.sh`). Checks that are still running on `main` (for example a just-merged PR) are waited for, polling and naming the pending check, up to `--timeout-minutes`; a failed check fails at once, and one still pending at the timeout fails with a clear message.
2. It creates `release/vX.Y.Z` from `main`, runs `scripts/bump-plugin-version.sh X.Y.Z` (below), commits and pushes it, opens a PR to `main` and turns on squash auto-merge. If auto-merge is unavailable (it is off for the repository), it says so and stops: merge the PR yourself, then re-run.
3. It polls (every 30s, 45 minutes by default; `--timeout-minutes N`, a whole number of at least 1, to change it) until that PR merges, stopping immediately if it's closed unmerged or one of its checks fails. A cancelled check gets one more poll before counting as a failure.
4. Once merged, it pulls `main`, requires `HEAD` to be the PR's merge commit (if anything else landed on `main` first it stops, inspect before tagging), re-checks the plugin version, and then **waits for the release gate on the merge commit**: CI starts on that commit only now, so its `test`, `terraform`, `rules` and both console checks are first missing, then running. It polls (same interval, up to `--timeout-minutes` again), printing which check is still pending, and fails at once on a conclusive failure; a check that is still pending or cancelled when the wait ends fails the release. **Identical-tree shortcut.** A squash merge creates a new commit, so CI starts from nothing on it even though a version bump changes no code and the PR head already passed. While `test`, `terraform`, `rules` or a console leg is missing, running or cancelled on the merge commit (and none failed on it), the gate accepts the checks of the pull request's head instead, and prints `using the checks of <sha> (identical tree)`; the wait ends at once. The candidate counts only if all of these hold, each read from the GitHub API rather than assumed: it is the head of a pull request that is merged and whose `merge_commit_sha` is exactly the commit being gated (so an unrelated commit with the same tree on another branch, or an open or closed-unmerged PR, cannot vouch); its tree id equals the commit's tree id (identical content to the commit being gated; the PR's checks ran on its head merged with the base of that moment, since `pull_request` jobs check out the merge ref, and that is accepted because the tree equals the merged result that became the commit); and `test`, `terraform`, `rules` and both console checks are all `success` on it from the GitHub Actions app, as strict as on the commit itself (failed, cancelled, running or missing never counts). A conclusive failure on the commit's own runs is never overridden, and a commit with its own complete green checks never triggers the lookup. The lookup needs no token on a public repository, so the tag workflows (`release.yml`, `images.yml`) may use the shortcut too, under the same rules; if the repository ever goes private it fails with a one-line `identical-tree lookup unavailable (...)` note on stderr and the gate falls back to waiting for the commit's own checks. Only the first 100 pull requests associated with the commit are read. It then prints a summary (tag, commit, checks) and the standard reminder that a pushed tag is permanent. There is no confirmation prompt: the green release gate on the verified merge commit is the safeguard (`--yes` is still accepted and does nothing).
5. It creates the annotated tag and pushes it (`git push origin refs/tags/vX.Y.Z`) and prints the two workflow run URLs to watch, plus this page's post-release checklist (verify-public, making a new image package public once, verifying the release). If the push fails the tag stays local, the script prints the exact command to run by hand, and a re-run pushes it: a local-only tag is accepted only if the release PR is merged and the tag is on the verified merge commit; any other local tag is refused. If origin turns out to already have the tag at that commit, it says so instead of reporting a push.

`--dry-run` stops after printing the plan for step 2, changing nothing. However it ends (an error, Ctrl-C, SIGTERM, SIGHUP) the script switches the checkout back to `main`, and re-running is safe: it finds the state from git and `gh` rather than keeping any of its own. An existing `release/vX.Y.Z` branch with no PR is reused (rebuilt from `main` if `main` has moved on), an open PR is picked up at step 3, and a merged PR goes straight to step 4.

**Recovering from a closed release PR.** If the PR for `release/vX.Y.Z` was closed without merging, the script stops before attempting a merge and prints the recovery: delete the branch (`git push origin --delete release/vX.Y.Z`, plus `git branch -D release/vX.Y.Z` locally) and re-run, which opens a fresh PR; or reopen the PR on GitHub and re-run.

`scripts/release_test.go` covers this against a local bare repository and a fake `gh`: every precondition (including the Highlights file from 0.4.0 and the version policy of `scripts/release-policy.sh`), argument errors, `--dry-run`, the full happy path (exactly one branch, one commit, one PR, the tag, with no prompt and no stdin), `--yes` as a no-op, the post-merge wait (checks missing, pending, cancelled, red), `HEAD` not being the merge commit, a failed bump check, resuming a merged PR, an open PR, a pushed branch without a PR and a stale local branch, a closed PR, a failed push of the branch, the PR creation or the tag (each leaving the checkout on `main`), signals, and a local-only tag.

### Manual steps (fallback)

Only needed if `scripts/release.sh` can't run (no `gh`, or something it doesn't handle):

1. Main is green: `test`, `terraform`, `rules` and both console checks passed on the commit to be released (`gh run list --branch main`). From 0.4.0 on, `docs/releases/vX.Y.Z.md` (the Highlights, non-empty) is on `main` before the tag: both tag workflows refuse without it (`scripts/release-policy.sh check-highlights`).
2. Bump the plugin and commit it through a PR to main:

   ```sh
   scripts/bump-plugin-version.sh X.Y.Z   # plugin/.claude-plugin/plugin.json and the header of every file under plugin/skills; the marketplace entry carries no version and the plugin test rejects one
   ```

   The header is the two lines at the top of each skill file, the comment `<!-- fugaro-skill name=<dir> fugaro-version=X.Y.Z -->` and the sentence `(Fugaro X.Y.Z)` in the quoted notice; the script rewrites both everywhere and then runs its own check. `go test ./plugin/` only requires a non-empty `plugin.json` version and a header in every skill file equal to it; the release workflow enforces `version == tag` for both (`scripts/bump-plugin-version.sh --check X.Y.Z`), so a tag on a commit whose plugin version or any skill header differs publishes nothing.

   **The plugin is pinned to this tag (M11, [design §4.3](design/m11-setup-and-skills.md)).** `fugaro init` and `fugaro update-skills` write the release tag `vX.Y.Z` of the running binary as the `ref` of the Fugaro marketplace in a repository's `.claude/settings.json`, so the binary, the plugin and the pin agree only if the plugin at that tag has version `X.Y.Z`: that is what the gate above enforces, and why a published tag is never moved or re-cut (a pin to it would silently change). `bump-plugin-version.sh` rewrites, and `--check` verifies, the version in `plugin.json` and in each skill's do-not-edit header. A development build (`fugaro version` prints `dev`) writes no pin. A private fork hosts its own marketplace and plugin at its own tags (`--allow-fork` moves the ref of its entry to the running binary's tag), and its users pin to those. After a release a repository moves its pin with `fugaro update-skills` (or `fugaro init`), reviewed as one line in a PR; `fugaro doctor --plugin --strict` in its CI fails a pin that is older or newer than the binary, unpinned, foreign or not wired. Users move a checkout's pin, installed plugin and job images to a new release with one sequence: `brew upgrade dimipaun/tap/fugaro && fugaro upgrade` ([design/upgrade.md](design/upgrade.md)).
3. Rehearse if the pipeline changed: Actions, `release`, Run workflow (`workflow_dispatch`). It runs `goreleaser release --snapshot --skip=publish,sign` and uploads `dist/` as the `goreleaser-dist` artifact. Locally: `goreleaser release --snapshot --clean --skip=publish,sign` with `HOMEBREW_TAP_GITHUB_TOKEN=` set (empty), and syft on the PATH (or add `sbom` to `--skip`).
4. Tag the merged commit and push:

   ```sh
   git switch main && git pull --ff-only
   git tag -a vX.Y.Z -m "Fugaro vX.Y.Z"
   git push origin vX.Y.Z
   ```

5. Watch both workflows (`gh run watch`), then verify.

**If a workflow refuses after the tag was pushed because the Highlights file is missing or empty** (`release.yml` and `images.yml` both fail in their first steps, so nothing is published): the tag can never be moved or deleted by the release process, so leave it and cut `vX.Y.(Z+1)` with the file committed. Deleting the tag is the repository owner's rollback decision ("Rolling back"), not part of the routine.

Pull requests that touch `.goreleaser.yaml`, `release.yml` or the bump script run `goreleaser check` as the `check` job of `release.yml`. It is not a required check.

## Rolling out the shared installation config

The release that adds `gcp_project:` to `fugaro.yaml` needs an ordered rollout, because job images carry a baked-in `fugaro` binary that reads the repository's `fugaro.yaml` from the base branch (and the daily image check reads it too), and that parser refuses unknown keys. **Do not add `gcp_project:` to a repository's `fugaro.yaml` before its image is rebuilt with the new binary, and rebuild only after `fugaro init` has pinned the release's base image**: runs and the daily check refuse the file until it is. Put this order in that release's Highlights, under `### For operators` ([design/shared-config.md](design/shared-config.md) §9):

1. Merge and release the version that adds the field (check `gcpProjectFieldSince` above).
2. Upgrade the CLI and run `fugaro init` once per installation (default-named runs bucket only). It publishes the shared file and changes no repository.
3. For each repository, in its checkout, in your own terminal window, or with `--yes` from CI or a script: `fugaro upgrade` (its cloud step is `fugaro image refresh`). It pins the release's base image — signature-verified at the release's `-pinned` tag, by digest through the installation's remote repository — and records it, points the daily image check job at it (image and `FUGARO_CHECK_SPEC`, no Terraform), and rebuilds every workflow not yet built from it. A derived image takes the `fugaro` binary from the base image, which is why the order matters, and the command keeps it. If the local config sets `base_images.<kind>` to a development (`dev-<sha>`) or hand-pushed image, it stops and names the entry, with or without `--yes`, and refresh never replaces a custom base image: either remove the entry from the local config (keep a backup) and rerun, or keep your own base image and rebuild from it with `fugaro image build --repo <owner/name> --workflow <name>`. `--yes` confirms every step unattended, including each billable build, with no cap on how many run; it is still refused in a coding agent's session, and there is still no `--json` or `--plan-only`. Its cloud step handles one repository per checkout; `fugaro upgrade` tries every PATH in turn and never writes `fugaro.yaml`.
4. Every teammate's CLI and every CI job or pin that runs `fugaro` against the repository (validate, doctor --plugin --strict, run) must be on the new release BEFORE the gcp_project line is merged: older versions refuse the key as unknown.
5. In each checkout, run `fugaro init --anchor` to add the `gcp_project:` line, then commit and merge it. It runs no Terraform and publishes nothing; it first checks every workflow's build record and the local config's base images, and writes nothing (exit 1, one ordered fix per workflow: the base-image fix if needed, `fugaro image refresh` in the checkout, `fugaro init --anchor`) while an image was submitted by an older or development CLI, was built FROM an older, development or hand-pushed base image (the record's `base_ref`; a record that does not name it fails too), or a configured base image would bring one back. A record read that fails in the cloud (missing credentials included) exits 2. Then it shows the diff and asks `Write this to <path>? [y/N]`. Plain `fugaro init` in the checkout also writes the line as its last stage, with the same checks as warnings, after the full converge; `fugaro init --repo` does not write it.
6. Check it: in a fresh clone with an empty config and cache directory, `fugaro doctor` shows the `shared-config` line ([gcp-live-checklist.md](gcp-live-checklist.md) Check 28).

Until step 5 nothing changes for teammates: a checkout without the line gets the clear "add this line" error and can use `fugaro init` as today. Teammate-facing description: "Teammates: no setup" in [gcp-setup.md](gcp-setup.md).

## Rolling out the 0.7.0 bucket hardening

Release 0.7.0 gives launchers who are not operators `roles/storage.objectViewer` on the runs bucket and `roles/storage.objectUser` on its `runs/` only, instead of `objectAdmin` on the whole bucket ([design/bucket-iam.md](design/bucket-iam.md)). This is a separate rollout from "Rolling out the shared installation config" above (that one is pinned to the release that added `gcp_project:`, not 0.7.0). None of it is exercised against a real bucket in this project's own testing: the live check is [gcp-live-checklist.md](gcp-live-checklist.md) Check 32, reserved for the owner to run.

0.7.0's own rollout order ([design/bucket-iam.md](design/bucket-iam.md) §8, citing [design/base-image.md](design/base-image.md) §10) is the base-image consolidation's usual order — operators upgrade the CLI, each repository gets its pull request, each repository runs `fugaro image refresh`, doctor shows a clean result — with two steps the bucket hardening appends after those:

1. **One operator runs `fugaro init`** (the installation stage) in their own terminal, reads the plan and the `bucket access (0.7.0)` banner naming each launcher whose old grant is replaced, and types the project's name. **Apply it while nobody is launching** (design §5): Terraform may destroy a launcher's old `objectAdmin` grant before it creates their two new ones, so a launcher who writes `runs/` during the apply can get a 403 for a few seconds, or for as long as IAM propagation takes (unverified, V5). The fix is to retry; no data is at risk, since the claim protocol fails closed. On a one-person installation (the only user is both launcher and operator) the plan has no bucket change.
2. **Every operator and launcher runs `fugaro doctor`,** which reports `runs-bucket-iam` ok.

The bucket change does not depend on the base-image steps, and pre-0.7.0 CLIs keep launching after it: a 0.6.x launch writes only `runs/` already. **A pre-0.7.0 CLI's own stale-lock clear is different, though:** once the apply lands, an older binary's `locks/` delete (`cancel`, `run --pr`, on a holder confirmed over) is refused the same as a current CLI's, but it predates this release's classification of a refused write and has no "an operator must clear it" message to show — it surfaces whatever raw, unclassified error the refusal produces instead. Upgrade every machine's CLI at or before the apply if lock takeovers matter to you. Claude never applies this migration; the user reviews and applies the plan at their own terminal (no live cloud access in a Claude session).

## Verifying a release

```sh
V=X.Y.Z
gh release download v$V -R dimipaun/fugaro -p checksums.txt -p checksums.txt.sigstore.json -p "fugaro_${V}_$(uname -s | tr A-Z a-z)_*"

# The checksums are signed by the release workflow on that tag
cosign verify-blob checksums.txt \
  --bundle checksums.txt.sigstore.json \
  --certificate-identity "https://github.com/dimipaun/fugaro/.github/workflows/release.yml@refs/tags/v$V" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com

# The archives match the checksums
grep " fugaro_${V}_" checksums.txt | shasum -a 256 -c -      # macOS
grep " fugaro_${V}_" checksums.txt | sha256sum -c -         # Linux

# Each channel
brew install dimipaun/tap/fugaro && fugaro version
go install github.com/dimipaun/fugaro/cmd/fugaro@v$V
docker pull ghcr.io/dimipaun/fugaro-web-node:$V
docker pull ghcr.io/dimipaun/fugaro-go:$V
docker pull ghcr.io/dimipaun/fugaro-java-services:$V
docker pull ghcr.io/dimipaun/fugaro-history:$V
# Once a release has published fugaro-base (not yet true):
# docker pull --platform linux/amd64 ghcr.io/dimipaun/fugaro-base:$V
# docker pull --platform linux/arm64 ghcr.io/dimipaun/fugaro-base:$V
```

Also check on the release page: it is not a draft; for 0.4.0 and later it is not marked "Pre-release"; the body shows `## Highlights` above `## Changelog`.

`fugaro version` prints `X.Y.Z` (no `v`); a `go install` build prints `dev` because the version is injected only by GoReleaser's `-ldflags`. SBOMs are the `*.sbom.json` assets (SPDX/syft JSON, one per archive).

**Update checks.** Once a day, any command asks this same releases API (`/repos/dimipaun/fugaro/releases/latest`, which only ever returns a non-draft, non-prerelease release) whether a newer one exists, and nags once a day at most when it does ([gcp-setup.md](gcp-setup.md#staying-up-to-date) has the switches and `fugaro doctor`'s own check). Nothing in this repository's test suite or CI ever makes that call for real: it is exercised only against fake HTTP servers, never verified here against a live lookup.

## Rolling back

Rolling back a published release is the repository owner's decision, and the owner runs it; automation and the `/new-release` skill never delete or move a tag and supersede with the next patch release instead. Delete the GitHub Release and the tag (`gh release delete vX.Y.Z --cleanup-tag -R dimipaun/fugaro`), delete the images' `X.Y.Z` tag from the package page (and re-point `:X` at the previous release if it moved), and revert the cask commit in `dimipaun/homebrew-tap`. The Go module proxy caches `vX.Y.Z` forever, so `go install ...@vX.Y.Z` keeps working with the old content; never reuse a version. Ship the fix as `vX.Y.(Z+1)` and, if the bad version is dangerous, add a `retract` directive to `go.mod`.
