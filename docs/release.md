# Releasing Fugaro

One SemVer tag `vX.Y.Z` releases everything (design section 12): the binary, the base images, the Terraform modules at the tag, the schemas at the tag, and the plugin. Before 1.0, minor versions may break.

**There are three release streams, and each has its own tag.** `vX.Y.Z` is the CLI's (the paragraph above — the base images, the modules, the schemas and the plugin ride it too); the desktop console releases on `console-vX.Y.Z` (the owner's ruling of 2026-10-17, "Before you tag" below); and the mobile app releases on `mobile-vX.Y.Z` (the owner's ruling of 2026-10-22, [Mobile releases](#mobile-releases) below). A tag of one stream starts that stream's workflow and no other. Everything else in this document is the CLI's stream unless it says otherwise.

## What a tag does

A push of a strict `vX.Y.Z` tag triggers two independent workflows (the desktop console is not one of them: the owner's addendum of 2026-10-22 gives it its own stream and its own `console-vX.Y.Z` tag, below, "Console releases", applied on 2026-10-23 — a `vX.Y.Z` push starts these two and no console work):

- `release.yml` (this document): checks the tag, then runs GoReleaser, which builds `fugaro` for darwin and linux on amd64 and arm64, writes `checksums.txt`, an SBOM per archive (syft), a keyless cosign signature of `checksums.txt`, and the GitHub Release; it also pushes the Homebrew cask. **The release body** is, in order: the install header, `## Highlights` (the hand-written `docs/releases/vX.Y.Z.md`, below), `## Changelog` (generated from the commit titles since the previous tag, with no SHAs; `release:`, `docs:`, `test:`, `chore:`, `ci:`, `Design:` and merge commits are left out) and the base-images footer. **Pre-release marking:** v0.1.0 to v0.3.x are marked as pre-releases and stay so; from v0.4.0 on a release is a normal release (it can be "Latest"). GoReleaser's `prerelease: auto` only recognises `-rc1`-style suffixes, which the strict tag rule never produces, so the workflow's last step marks the old ones itself, asking `scripts/release-policy.sh prerelease X.Y.Z` (a numeric comparison, tested in `scripts/release_test.go`).
- `images.yml`: today builds, smoke tests, scans and publishes `ghcr.io/dimipaun/fugaro-web-node`, `fugaro-go`, `fugaro-java-services`, `fugaro-history` (`X.Y.Z` and a moving `:X` each, linux/amd64 only) and `fugaro-base` (per-architecture `X.Y.Z-amd64`/`X.Y.Z-arm64` plus the multi-platform index `X.Y.Z` and a moving `:X`, both linux/amd64 and linux/arm64). It also builds `ghcr.io/dimipaun/fugaro-credentials`, the credentials service's image (linux/amd64 only), and smoke tests, size-checks and secret-scans it on every run, pull requests included; a release tag publishes it with the others (`X.Y.Z` and a moving `:X`) and, the way `fugaro-base` is, signs the pushed digest keyless with cosign, verifies that signature and only then writes the nightly-immune `X.Y.Z-pinned` tag at it, which is the tag `fugaro update`'s credentials stage resolves and verifies before it pins the service to that digest. After publishing, the `verify-public` job pulls every reference (`fugaro-credentials` included) with no login (`images/verify-public.sh`) and fails the release when one cannot be read or has no `linux/amd64` build (`linux/arm64` too, for `fugaro-base`); it lists each image's digest in the run summary. Pull requests build, smoke test and publish nothing; the nightly run scans. The 0.7.0 hard cut deleted `images/go/`, `images/web-node/` and `images/java-services/` from the tree, so the `base` job's three legacy legs now have nothing to build and skip (the version job's directory probe finds none); they are not yet removed from the workflow file itself.

  **Applied for 0.7.0:** the legacy per-kind `base` job is deleted from `images.yml` and `publish` and `verify-public` cover `history` (`fugaro-base` has its own `fugaro-base (amd64|arm64)` and `publish-base` jobs). The nightly workflow therefore no longer refreshes `fugaro-go`, `fugaro-web-node` and `fugaro-java-services` (design §10): their already-published tags stay on ghcr.io forever as immutable history, and no release after 0.6.x republishes a moving `:X` tag for any of the three. **Staged, and a release gate:** #318's Task 1 — signing the pushed base image by OCI digest and publishing the nightly-immune `-pinned` tag — is what the resolve step verifies. [PR #377](https://github.com/dimipaun/fugaro/pull/377) merged it as a **staged** file, `docs/pending-workflows/images.yml`, which only the owner can copy into `.github/workflows/images.yml`; the pre-tag checklist below gates the 0.7.5 tag on that copy being on `main`.

Neither workflow runs the test suite; CI already did on main. Both workflows run `scripts/release-gate.sh` first, so a tag on an off-main or red commit publishes nothing (no binaries, no images). It refuses unless the tagged commit is reachable from `origin/main` and the GitHub Actions checks `test`, `terraform`, `rules` and both of the console's (`console (ubuntu-latest)`, `console (macos-latest)`) all succeeded on it (a check of that name from another app does not count); if CI is still running, re-run the failed job once it is green. `release.yml` also requires the plugin version to equal the tag. **The console's two check runs exist on `main` only once the `console` branch has been merged into `main` and a push to `main` has run `.github/workflows/console-tests.yml`:** the requirement and the workflow arrive together, so do not run the gate (or `scripts/release.sh`) on a `main` commit before that, since a commit without them has the console checks missing and the gate refuses it.

**The Linux build is deliberately not one of those checks.** Since the owner's ruling of 2026-10-20 ("yes, Linux for 0.10.0, unsigned") the console is packaged for Linux too, and the staged `docs/pending-workflows/console-linux.yml` builds and uploads the AppImage and the `.deb` on every pull request — but it is **not** added to `scripts/release-gate.sh`'s `names` array, and it must not be added without the three edits `docs/pending-workflows/README.md` sets out. The gate's list is derived from `.github/workflows/console-tests.yml`'s job set (`TestReleaseGateRequiresTheConsoleCheck` reads that workflow and refuses one with several jobs), so a second job is not a packaging change: it is a change to which checks gate every release tag, and a red Linux pack is information rather than a blocked release until the owner decides otherwise.

## Mobile releases

The mobile app is its own release stream, and since the owner's ruling of 2026-10-22 it has **its own tag**: `.github/workflows/mobile-release.yml` (applied on 2026-10-23, on the owner's approval) triggers on `mobile-v[0-9]+.[0-9]+.[0-9]+` and on a manual dispatch, **and on nothing else**. Until that ruling the app's workflow triggered on the CLI's `v[0-9]+.[0-9]+.[0-9]+` filter, so every CLI release built the app on EAS and submitted it to TestFlight's internal testers and to Play's internal-testing track whether or not the app had changed; the app is its own artifact with its own cadence (D125, [docs/mobile/reconciliation.md](mobile/reconciliation.md)), so it now releases when the app is released and only then. A `mobile-vX.Y.Z` tag starts this workflow and neither of the CLI's two, and a `vX.Y.Z` tag starts the CLI's workflows and not this one.

**The version comes from the tag, and the app's own version lines have to agree with it.** The tag's version is `X.Y.Z`, and the app's version lives in **two checked-in lines**: `mobile/app.json`'s **`expo.version`**, which is the line the app itself reports (EAS reports the config's version, not the tag), and `mobile/package.json`'s **`version`**, which the app's own test pins `expo.version` to (`mobile/src/app-config.test.js`, "the config and the manifest agree on the version"). So the release that cuts `mobile-vX.Y.Z` sets **both** to `X.Y.Z` in one commit **on `main` before the tag**, and each job of the workflow opens by holding the tag to a strict `mobile-vX.Y.Z` shape, taking `X.Y.Z` out of it and refusing to build when either line carries anything else — so a tag whose version differs from either line stops the run before EAS is called, rather than submitting a build that reports a version no tag names. **Both lines or neither**: a release that bumped only the config would build and submit, and the app's suite — which nothing this repository runs executes, because no workflow mentions `mobile/` — would be red on the tagged commit behind it, which is why the manifest is compared in the workflow's own step rather than left to that suite. Nothing stamps the version from the tag: `mobile/app.config.js` spreads the static config and writes only the two store identities on top of it, so the config line is the version, and the check is what keeps the three in step. (The console's packs are stamped from its tag with `-c.extraMetadata.version=X.Y.Z`, which is why `console/package.json` stays `0.0.0`; that is not available here without a change to `app.config.js`.)

**Cutting the tag.** There is no script for this stream (`scripts/release.sh` is the CLI's), so the owner creates and pushes the tag by hand, from a clean `main` that already carries the two version lines, the notes file and the summary (above):

```sh
git tag -a mobile-vX.Y.Z -m "Fugaro Mobile vX.Y.Z"
git push origin mobile-vX.Y.Z
```

An **annotated** tag is recommended, and it is what the CLI's own path creates (`scripts/release.sh`'s step 5, and the manual fallback's `git tag -a vX.Y.Z`): the object carries its own message and date, and `git push origin mobile-vX.Y.Z` pushes that object with it. A **lightweight** tag works too — the workflow matches the ref name, not the object's type — and it peels correctly: after the push, `git ls-remote https://github.com/dimipaun/fugaro 'refs/tags/mobile-vX.Y.Z^{}' 'refs/tags/mobile-vX.Y.Z'` prints the tagged commit on the `^{}` line for an annotated tag and on the only line for a lightweight one, the same command the CLI's post-release step runs for `vX.Y.Z` (below, "Before you tag"). Never move, delete or re-create the tag: the stores keep what was submitted from it, and the fix for a bad release is a new version (below).

**After each release, the website.** Once the build is submitted and verified, update the website wherever it names the app's latest version or links, run the website's tests (`npm run check` in `website/`, and `go test ./internal/cli -run Docs`), merge, then dispatch `website-preview`. The owner promotes: `website-promote` and the `website-live` approval click are the owner's.

**The app's own notes, and its own name.** Both are the stream's, and neither is the CLI's:

- **Highlights: `docs/releases/mobile/vX.Y.Z.md`**, in the same format as the CLI's `docs/releases/vX.Y.Z.md` ([docs/releases/README.md](releases/README.md); [docs/releases/mobile/README.md](releases/mobile/README.md) carries the app's own copy of the rule). The app's notes live in their own directory because the CLI's changelog reads `docs/releases/*.md` one level down and nothing else: an app note at the top level would enter the CLI's changelog, and the site's build refuses a top-level file that is not `vX.Y.Z.md`.
- **End-user summary: one line in `website/data/mobile-release-summaries.yaml`**, keyed by the tag (`mobile-vX.Y.Z: what this release gives a user.`) — the app's own file, beside the CLI's `website/data/release-summaries.yaml` rather than inside it, because the CLI's file is keyed `vX.Y.Z` and validated against the CLI's own release files. The app's stream keeps the same habit the CLI's has: a release ships with a sentence a user reads before the highlights, and neither is written inside the repository's code.
- **The name list: the app's releases are named after birds** — the **first is Falcon** (`0.200.0`), then **Pelican** (`0.201.0`), then **Robin** (`0.202.0`), in that order, one per release. **The three streams' name lists are the owner's ruling of 2026-10-22** (recorded in [docs/console-dependency-graph/reconciliation.md](console-dependency-graph/reconciliation.md) GD7 and [docs/console-dependency-graph/spec.md](console-dependency-graph/spec.md) §3, the table that lists them), one list each and used in order: **the CLI's are animals, with no bird among them** — **Badger** (`0.10`), **Camel** (`0.11`), then **Dolphin**, **Gecko**, **Hippo**, **Koala**, **Moose**; **the console's are fruits** — **Cherry** (`0.110.0`), **Mango**, **Melon**, with **Apple** and **Lemon** avoided ([Console releases](#console-releases) carries that list and the reason Apple is avoided); and **this stream's are the birds above** (Falcon moves here from the CLI's list, which contains no birds). The name is part of the release: put it in the notes' first bullet, in the summary sentence's own phrasing where it fits, and in the store listing's "what's new" text. There is no GitHub release to title on this stream — the workflow builds and submits and creates none, and the app's page and its store text are written by hand from the notes and the summary.

**The first mobile release is `mobile-v0.200.0`, "Falcon".** The app is not out yet: `mobile/app.json` carries `expo.version` `0.0.0`, which is a placeholder rather than a version anybody released, and the release that cuts `mobile-v0.200.0` sets it to `0.200.0` in a commit on `main` first (above). If you find another version in `mobile/app.json` when you read it, that line is the version being released and the tag is `mobile-v<that line>`: the config is the authority and the tag follows it, never the other way round. The birds are spent in order from Falcon, so the second app release is `mobile-v0.201.0`, "Pelican", whatever the version number turns out to be. The stream starts at `0.200.0` rather than `0.1.0` so that a mobile version is never mistaken for a CLI or console one ([Console releases](#console-releases) says why).

**The gate, and the environment.** `mobile-vX.Y.Z` is a tag like any other: each job runs `scripts/release-gate.sh` first — the gate accepts the app's stream by stripping its `mobile-` prefix and holding the version under it to the same strict `vX.Y.Z` shape, so the tagged commit must be reachable from `origin/main` and `test`, `terraform`, `rules` and both console checks must have succeeded on it (`scripts/release-gate.sh` says which) — and each job declares `environment: mobile-release`, whose only required reviewer is the owner, **whose deployment branches and tags must name `main` and tags `mobile-v*`** (a policy that still said `v*` admits no ref this workflow offers, and GitHub refuses the deployment rather than the tag), and whose one secret is the environment secret `EXPO_TOKEN`. Every step of that setup, and the check that has to precede it, is in [docs/pending-workflows/README.md](pending-workflows/README.md)'s `## mobile-release.yml` section and in [docs/mobile/eas-signing-runbook.md](mobile/eas-signing-runbook.md) §9 and §10.

**The copy-in is done: the workflow is applied.** The owner approved it on 2026-10-23, and `.github/workflows/mobile-release.yml` is the staged file copied in byte for byte, its staged copy removed (`docs/pending-workflows/README.md`'s `## mobile-release.yml` section is the record). The `mobile-release` environment was created **before** the copy-in, as it had to be — GitHub creates a missing environment on first use with **no required reviewer** — with the owner as its only reviewer and deployment policies for branch `main` and tags `mobile-v*`. `MOBILE_RELEASE_DISABLED_PLATFORMS` is deliberately left unset, so both platforms are enabled. **Two things stay the owner's before the first real run:** the environment secret `EXPO_TOKEN`, which the owner sets by hand (`gh secret set EXPO_TOKEN --repo dimipaun/fugaro --env mobile-release`, typed by the owner; no agent handles it), and a first **dry-run dispatch from `main`** (Actions, mobile-release, Run workflow, `dry_run` on), whose log must show the bundle id and the package name masked before any tag is pushed.

**Tag protection covers all three streams.** The ruleset **"protect release tags"** restricts updates and deletions of `v*`, `console-v*` and `mobile-v*` tags, so a pushed `mobile-vX.Y.Z` cannot be moved after a build was submitted from it, exactly as a CLI or console tag cannot.

**The two settings this stream rests on, by name.** The **ruleset** above is one repository ruleset — its three patterns are what make every stream's tags immutable, and the streams' prefixes are disjoint, so one ruleset covers all three. The **environment** is `mobile-release`: the owner is its only required reviewer, and its deployment policy has to admit branch `main` and tags `mobile-v*` (the paragraph above says why, and what happens when it does not). The console's stream uses the same pair under its own names — the ruleset's `console-v*` pattern and the `console-release` environment, whose policy admits `console-v*` tags ([Console releases](#console-releases)). Both are the owner's settings to create and to keep: Fugaro changes no repository setting, and neither is optional — without the ruleset a tag can move after something was built from it, and without the environment's policy naming this tag's ref the deployment is refused before any build runs.

**Rolling back an app release is not rolling back a tag.** A store submission cannot be unpublished the way a `vX.Y.Z` release can (D125): deleting `mobile-v0.200.0` leaves the build submitted to TestFlight and to Play, and the fix is a **new** version (`mobile-v0.200.1`) submitted behind it. Treat the tag as a record of what was submitted, not as a switch.

## Making the image packages public (one time per package)

The mirror (below) reads the source with no credentials, and a plain `docker pull` has none either, so every published package must be public. **In practice a package a workflow publishes from this public repository is public from the start** (it inherits the repository's visibility): the v0.2.0 release published `fugaro-go`, `fugaro-java-services` and `fugaro-history` for the first time, `verify-public` passed with no manual step, and all four manifests answered 200 anonymously. `fugaro-base` is expected to behave the same once its own first publish happens (above; not yet). So after a release that publishes a new package, only check that it is public: the `verify-public` job passing is that check.

If a package ever turns out private (`verify-public` fails with "cannot be read without a login (is the package public?)"): GitHub has no API call for this with the workflow's token, so do it by hand:

1. Open `https://github.com/users/dimipaun/packages/container/fugaro-<name>/settings`.
2. Under "Danger Zone", "Change package visibility", choose Public and confirm.
3. Re-run the `verify-public` job of that release's `images` run (or `images/verify-public.sh ghcr.io/dimipaun/fugaro-<name>:X.Y.Z` on any machine, which uses no login).

Later releases of a public package stay public.

## How `fugaro setup` uses the images (the mirror)

**The base image is not copied any more, and the reason this section used to give is gone.** The packages are public, and Artifact Registry **remote repositories** take `https://ghcr.io` as a Docker upstream — a documented feature, not a workaround (design [registry-remote-repository.md](design/registry-remote-repository.md) §1, §2.3). So the `images` stage of `fugaro setup` resolves `ghcr.io/dimipaun/fugaro-base:X.Y.Z` (the running binary's version; `--image-source ghcr.io/<owner>` for a fork) at its nightly-immune `-pinned` tag, **verifies the cosign signature that release's tag push attached to that exact digest** — all four claims of that push: the certificate identity `https://github.com/dimipaun/fugaro/.github/workflows/images.yml@refs/tags/vX.Y.Z`, the issuer `https://token.actions.githubusercontent.com`, and the certificate's trigger (`push`) and repository (`dimipaun/fugaro`) extensions, the last two because a `workflow_dispatch` run against that same tag ref carries the same identity and is not a tag push — reads the digest back through the installation's own remote repository `<region>-docker.pkg.dev/<gcp-project>/fugaro-ghcr/` and records that path at that digest in `base_images`: nothing is pushed anywhere, nothing is copied, and the 1.2 GB the copy used to move through the operator's machine is gone. Cloud Build and Cloud Run Jobs pull the pinned digest through the project's own repository, so no job needs ghcr.io reachability and there is no copy to keep in step. **`--base base` has nothing to pin yet**, since no release has published `fugaro-base` (above): it fails with a clear error rather than falling back silently.

**The history image is still copied**, because it is not the base and this change leaves it alone: `--firebase-project` copies `ghcr.io/dimipaun/fugaro-history:X.Y.Z` into `<region>-docker.pkg.dev/<gcp-project>/fugaro-base/` as the user, where it lands as `history:latest`, which the history job runs. That copy is plain HTTP against the registry API: no Docker, only the `linux/amd64` image, each digest verified, nothing sent when the destination already has the same digest. A development build copies nothing and says how to build from a checkout.

What a release must therefore guarantee is what `verify-public` checks: every published reference is anonymously readable and has a `linux/amd64` build. Until a package is made public (above) a user's `fugaro setup` is refused with the unreadable-source message. **What each path's trust rests on, now that they differ.** For a base kind the anchor is the signature, not the tag: the CLI verifies the release's cosign signature (identity, issuer, trigger and repository, above) and pins the digest, so a moved ghcr.io tag cannot change what a job pulls (design §4) — signing the pushed base image (the plan's F1, #318's Task 1, [PR #377](https://github.com/dimipaun/fugaro/pull/377) — merged as the staged `docs/pending-workflows/images.yml`, not yet copied into `.github/workflows/images.yml`) is what makes that possible, and until a release publishes a signed `-pinned` tag every base pin refuses, loudly, rather than falling back to a tag. For the history copy the anchor is still the tag as ghcr.io resolves it: pin the digest from the `verify-public` run summary with `--expect-digest history=sha256:<hex>` (KIND is `go`, `java-services`, `web-node` or `history`; a base kind refuses `--expect-digest` only as a cross-check of the verified digest). The release notes do not list the digests (GoReleaser runs in another workflow and cannot know them). **Which images exist when:** v0.1.0 published only `fugaro-web-node`; v0.2.0 was the first to publish `fugaro-go`, `fugaro-java-services` and `fugaro-history`; `fugaro-base`'s own first publish happens on the next release tag that runs `images.yml` (the `fugaro-base`/`publish-base` jobs are already live; above), not yet done as of this writing.

## Secrets

- `HOMEBREW_TAP_GITHUB_TOKEN`: a fine-grained personal access token with `Contents: Read and write` on the single repository `dimipaun/homebrew-tap`. Add it as a repository secret. If it is absent the release still succeeds and only the tap update is skipped, with a `::warning::` and a line in the run summary (add the secret and re-run the job, or copy the cask from a `dry-run` artifact's `homebrew/Casks/` by hand).
- Nothing else: the release uses the workflow's `GITHUB_TOKEN` (`contents: write`) and GitHub OIDC (`id-token: write`) for cosign.

## The cask's quarantine hook

The Homebrew cask runs a post-install step on macOS: `xattr -dr com.apple.quarantine` on the installed `fugaro`. The binaries are not signed or notarized by Apple, so without it Gatekeeper blocks the first run of a downloaded binary. The cost is that Gatekeeper's check is skipped for this binary; integrity rests on the sha256 in the cask, which comes from the release archives, and on the cosign-signed `checksums.txt`. Linux cask support was not tested; Linux users can use the archive or `go install`.

**`cosign` is not a cask dependency, and that is deliberate.** The cask installs the `fugaro` binary and nothing else: `fugaro` runs without `cosign` until the first base image is pinned, and `fugaro update --base`/`image refresh` **refuse** (naming `--base-image`) when it is missing rather than pinning a digest nothing verified (design [registry-remote-repository.md](design/registry-remote-repository.md) §9). Declaring `depends_on formula: "cosign"` would put sigstore's toolchain on every user's machine for a verification that runs when a base is pinned — an upgrade-time step, not a per-run one — so instead `fugaro doctor` reports it with the install link on every run, and the confirmation names the binary it used. Install it from your distribution or from Homebrew (`brew install cosign`); nothing in the release or the cask changes for it.

### The `postflight` deprecation warning

Homebrew warns that a cask using a `postflight` quarantine removal is deprecated (it is moving to refuse unsigned, un-notarized casks). That warning comes from Homebrew, not from GoReleaser: the `postflight` block is the one this repo's `hooks.post.install` asks for, GoReleaser v2.18.2 (the pinned version) emits `hooks.post.install` as `postflight` with no alternative stanza, and `.goreleaser.yaml` uses none of the config fields v2.18.2 flags as deprecated (`binary`, `manpage`, `url.verified`, `conflicts.formula`). So there is no supported config change to make offline, and none was made. What would remove it: sign and notarize the macOS binaries (GoReleaser's `notarize` support, which needs an Apple Developer ID certificate and API key as secrets), then delete `hooks` from the cask. Until then the hook stays; if Homebrew starts disabling such casks, `brew install` of the tap cask will fail and users fall back to the archive or `go install`.

## Cutting a release

**Before you tag (the checklist; each item has been missed or is easy to miss):**

- **`fugaro update` must be the whole upgrade (the owner's critical rule of 2026-10-30).** Before tagging, ask of every change in the release whether an installation at the PREVIOUS release reaches the new one with `fugaro update` alone: a policy or rules version bump ships its migrator in `update`, a changed image contract is rebuilt by it, nothing is a second command, a deletion or a hand repair. 0.14.0 broke this (policy v4 needed a delete-and-republish of the policy, an image refresh and a rules deploy); the release notes' `### For operators` section must read "run `fugaro update`" and say what it will ask, never a list of other commands. If a change cannot meet it, it does not ship in this release.

- **Every policy version bump ships its migrator.** A release that raises `projectpolicy.Version` (or `RulesVersion`) adds the step that carries an installation at the previous version over — `internal/projectpolicy`'s `migrators` chain, called by `fugaro update`'s policy stage and `fugaro upgrade`'s policy step ([docs/policy-migration.md](policy-migration.md)); a `RulesVersion` bump ships its deploy the same way, in `fugaro update`'s rules stage and `fugaro upgrade`'s rules step, which stand in front of the policy step because the policy write is gated on the deployed generation — and a migration step's only input is the node: a member the node cannot state is derived from the project's local config by the stage, never by the step, and never by asking the operator to delete the node and publish again. `TestEveryOlderVersionHasAMigratorOrARefusal` refuses a bump with neither a step nor a refusal row, and the stage's own tests (`internal/cli/init_policy_migrate_test.go`) are where "the node is carried over in place" is checked.

- **Do not tag 0.7.5 until the signing workflow is on `main`.** #318's Task 1 — the `-pinned` tag and the `cosign sign` step in `images.yml` — is [merged as a staged file](https://github.com/dimipaun/fugaro/pull/377) (`docs/pending-workflows/images.yml`), and only the owner can copy it into `.github/workflows/images.yml`; that copy must be on `main` **before** the release's version-bump merge commit, so the tagged tree carries it: the 0.7.5 CLI resolves `fugaro-base:<version>-pinned`, verifies that digest's cosign signature and only then pins it, so a tag pushed by a workflow without those steps publishes no `-pinned` image and no signature — every `fugaro update --base`/`image refresh` on 0.7.5 refuses (fail closed) and no installation can migrate off the copied base. Same ordering as the plugin-version bump and the Highlights file: on `main` before the tag, never after.
- **Write `docs/releases/vX.Y.Z.md` (the Highlights) and merge it to `main` through a PR, from 0.4.0 on** ([docs/releases/README.md](releases/README.md) has the format: 3 to 6 user-facing bullets, then `### For operators` when a rollout order matters, then `### Known limits` with what this release does not do, does not stop or leaves to a later one — a release ships with its known limits in its notes, so that section goes in unless the release genuinely has none; take the content from the pull requests merged since the previous tag). - The binary prints the commit it was built from (`fugaro doctor --plugin`, `fugaro update-skills`) with the one line that checks the tag: `git ls-remote https://github.com/dimipaun/fugaro 'refs/tags/vX.Y.Z^{}' 'refs/tags/vX.Y.Z'` must print that commit: on the `^{}` line for an annotated tag, on the only line for a lightweight tag (the `^{}` pattern alone prints nothing for one, which is why both are given). Run it once after tagging.

`scripts/release.sh X.Y.Z` does the whole thing from a clean `main`: it checks every precondition below, bumps the plugin through a PR, waits for it to merge, verifies the merge commit, waits for the release gate on it, then tags and pushes (there is no prompt). It needs `gh` installed and authenticated (`gh auth login`) and `go` on `PATH`, and nothing else: the release reads the CLI stream out of `docs/release-streams.yaml` through `go run ./internal/streams/cmd/streams` (`--dry-run`'s plugin-budget check needs `go` too), and it refuses at step 1 without it. It never force-pushes, never pushes to `main` directly, and never deletes or re-tags a release.

1. Preconditions, checked in order and stopping at the first failure: `X.Y.Z` is strict SemVer (no `v`, no pre-release suffix, no leading zeros); the working tree is clean (**untracked files count: a stray file blocks the release**, so commit, remove or ignore it first); the current branch is `main` and equals `origin/main` after a fetch; for `X.Y.Z` of 0.4.0 or later, `docs/releases/vX.Y.Z.md` exists and is not empty on `origin/main`, and `website/data/release-summaries.yaml` on `origin/main` carries a non-empty entry `  vX.Y.Z: …` (both are the release's own text and both ship in one PR, so both are refused before any branch, PR or tag); `gh` is installed and authenticated and targets the repository `origin` points at; the tag `vX.Y.Z` doesn't already exist on origin (a release is never re-tagged, see "Rolling back" below; a tag that exists only locally is handled at step 5); `X.Y.Z` is greater than the latest released tag (only strict `vX.Y.Z` tags count, so `-rc` and four-part tags are ignored); `docs/release-streams.yaml` can record `X.Y.Z` as the `cli` stream's `current` — step 2's write, computed in memory by `go run ./internal/streams/cmd/streams set --check cli X.Y.Z` (so `go` must be on `PATH`), which refuses a version below the stream's `current` (the version it is already at is allowed: that is an interrupted release being finished, and the tag check above refuses one that really did ship), one off the CLI's named line (a major bump, a minor below 0.10), one with no name left after it for `next`, and a file whose `current:` is not quoted; the two doc lines that name the released version (the checklist above) each read as the rewrite expects, once per file; and `test`, `terraform`, `rules` and both console checks all succeeded on the tip of `main` (reusing `scripts/release-gate.sh`). Checks that are still running on `main` (for example a just-merged PR) are waited for, polling and naming the pending check, up to `--timeout-minutes`; a failed check fails at once, and one still pending at the timeout fails with a clear message. The same read gives the release its spoken name (`Camel two` for 0.11.2); a version the check accepts always has one.
2. It creates `release/vX.Y.Z` from `main`, runs `scripts/bump-plugin-version.sh X.Y.Z` (below), records `X.Y.Z` as the `cli` stream's `current` in `docs/release-streams.yaml` (moving `next` on when the release opens a new minor, so the file the console's graph draws never describes a version that has shipped), rewrites the two doc lines that name the released version to `X.Y.Z` (the checklist above), commits and pushes it, opens a PR to `main` and turns on squash auto-merge. If auto-merge is unavailable (it is off for the repository), or GitHub refuses the request — `gh pr merge --auto` also fails on a pull request it reports as already mergeable, with `Pull request is in clean status` — it says so and stops, and auto-merge is then not on whatever the reason: merge the PR yourself, then re-run `scripts/release.sh X.Y.Z`, which picks the merged PR up at step 4.
3. It polls (every 30s, 45 minutes by default; `--timeout-minutes N`, a whole number of at least 1, to change it) until that PR merges, stopping immediately if it's closed unmerged or one of its checks fails. A cancelled check gets one more poll before counting as a failure.
4. Once merged, it pulls `main`, requires `HEAD` to be the PR's merge commit, and stops with `HEAD (<sha>) is not the release merge commit (<sha>)` when anything landed on `main` after it. **That refusal does not clear on a re-run** — the PR is merged, so step 4 finds the same mismatch every time — and it is what 0.10.0 hit: `v0.10.0`'s tag is on 072cbdff, the follow-up that shortened the setup skill the bump had pushed over its byte budget (#929), not on its release merge commit 40b1fdbc. Inspect what landed; when it is such a fix and the checks are green on the tip, tag the tip by hand ("Manual steps (fallback)", step 4), since the script will not: what the gate requires is a tag on a commit of `main` that passed it, and that commit is now the tip. It then re-checks the plugin version, and then **waits for the release gate on the merge commit**: CI starts on that commit only now, so its `test`, `terraform`, `rules` and both console checks are first missing, then running. It polls (same interval, up to `--timeout-minutes` again), printing which check is still pending, and fails at once on a conclusive failure; a check that is still pending or cancelled when the wait ends fails the release. **Identical-tree shortcut.** A squash merge creates a new commit, so CI starts from nothing on it even though a version bump changes no code and the PR head already passed. While `test`, `terraform`, `rules` or a console leg is missing, running or cancelled on the merge commit (and none failed on it), the gate accepts the checks of the pull request's head instead, and prints `using the checks of <sha> (identical tree)`; the wait ends at once. The candidate counts only if all of these hold, each read from the GitHub API rather than assumed: it is the head of a pull request that is merged and whose `merge_commit_sha` is exactly the commit being gated (so an unrelated commit with the same tree on another branch, or an open or closed-unmerged PR, cannot vouch); its tree id equals the commit's tree id (identical content to the commit being gated; the PR's checks ran on its head merged with the base of that moment, since `pull_request` jobs check out the merge ref, and that is accepted because the tree equals the merged result that became the commit); and `test`, `terraform`, `rules` and both console checks are all `success` on it from the GitHub Actions app, as strict as on the commit itself (failed, cancelled, running or missing never counts). A conclusive failure on the commit's own runs is never overridden, and a commit with its own complete green checks never triggers the lookup. The lookup needs no token on a public repository, so the tag workflows (`release.yml`, `images.yml`) may use the shortcut too, under the same rules; if the repository ever goes private it fails with a one-line `identical-tree lookup unavailable (...)` note on stderr and the gate falls back to waiting for the commit's own checks. Only the first 100 pull requests associated with the commit are read. It then prints a summary (tag, the release's spoken name when the catalogue names one, commit, checks) and the standard reminder that a pushed tag is permanent. There is no confirmation prompt: the green release gate on the verified merge commit is the safeguard (`--yes` is still accepted and does nothing).
5. It creates the annotated tag and pushes it (`git push origin refs/tags/vX.Y.Z`) and prints the two workflow run URLs to watch, plus this page's post-release checklist (verify-public, making a new image package public once, verifying the release). If the push fails the tag stays local, the script prints the exact command to run by hand, and a re-run pushes it: a local-only tag is accepted only if the release PR is merged and the tag is on the verified merge commit; any other local tag is refused. If origin turns out to already have the tag at that commit, it says so instead of reporting a push.

`--dry-run` runs one more check than the preconditions above — the plugin tests on a scratch worktree of the tree with `scripts/bump-plugin-version.sh X.Y.Z` applied, which is where a skill file the bump pushes over its byte budget fails (the checklist's plugin-budget step; the worktree is removed however the check ends, Ctrl-C and SIGTERM included) — and then stops after printing the plan for step 2, changing nothing else. The plan names the release — `vX.Y.Z` and, when the catalogue names one, its spoken name — and says what that check did, and says so when it did not run: a checkout with no `go.mod` skips it with a note, while `go` missing from `PATH` is a refusal — the check cannot run without it, and it is the check the dry run exists for. However it ends (an error, Ctrl-C, SIGTERM, SIGHUP) the script switches the checkout back to `main`, and re-running is safe: it finds the state from git and `gh` rather than keeping any of its own. An existing `release/vX.Y.Z` branch with no PR is reused (rebuilt from `main` if `main` has moved on), an open PR is picked up at step 3, and a merged PR goes straight to step 4.

**A dropped connection to GitHub does not end the release.** A TLS handshake timeout, an unexpected EOF, an i/o timeout, a reset connection or a `Recv failure` used to stop the script half-way through a wait. Read-only calls (`git fetch`, `git ls-remote`, `git pull --ff-only`, `gh auth status`, `gh repo view`, `gh pr list`, `gh pr view`, `gh pr checks`) and the release gate's polling of the check runs now go through `scripts/retry.sh`: up to 3 tries, waiting 5s and then 10s, and only on a failure that reads like a dropped connection (a refusal or a 404 is final at once; `gh auth status`, which reports a dropped API as not logged in, is retried on any failure). The calls that change something are never repeated blindly: a failed `gh pr merge --auto` is repeated only after the pull request has been read again and found neither merged nor closed, and a failed tag push only after `git ls-remote` has found origin without the tag. Three failures in a row still stop the script with the call's own message, and a re-run resumes as below.

**Recovering from a closed release PR.** If the PR for `release/vX.Y.Z` was closed without merging, the script stops before attempting a merge and prints the recovery: delete the branch (`git push origin --delete release/vX.Y.Z`, plus `git branch -D release/vX.Y.Z` locally) and re-run, which opens a fresh PR; or reopen the PR on GitHub and re-run.

`scripts/release_test.go` covers this against a local bare repository and a fake `gh`: every precondition (including the Highlights file from 0.4.0 and the version policy of `scripts/release-policy.sh`), argument errors, `--dry-run` (including its plugin-budget check: a passing and a failing plugin test command, each run inside the scratch worktree, which carries the bump and is removed either way), the full happy path (exactly one branch, one commit, one PR, the tag, with no prompt and no stdin), `--yes` as a no-op, the post-merge wait (checks missing, pending, cancelled, red), `HEAD` not being the merge commit, a failed bump check, resuming a merged PR, an open PR, a pushed branch without a PR and a stale local branch, a closed PR, a failed push of the branch, the PR creation or the tag (each leaving the checkout on `main`), signals, a local-only tag, the two doc lines rewritten in the release commit (and a reworded one refused), and the retries: `retry_read` against a stub that fails twice and then answers, bounded at three tries and never retrying a permanent error, and a whole release riding out transient failures of `gh repo view`, `gh pr view`, the gate's `gh api` polling, the auto-merge request and the tag push.

### Manual steps (fallback)

Only needed if `scripts/release.sh` can't run (no `gh`, or something it doesn't handle):

1. Main is green: `test`, `terraform`, `rules` and both console checks passed on the commit to be released (`gh run list --branch main`). From 0.4.0 on, `docs/releases/vX.Y.Z.md` (the Highlights, non-empty) is on `main` before the tag: both tag workflows refuse without it (`scripts/release-policy.sh check-highlights`).
2. Bump the plugin and commit it through a PR to main:

   ```sh
   scripts/bump-plugin-version.sh X.Y.Z   # plugin/.claude-plugin/plugin.json and the header of every file under plugin/skills; the marketplace entry carries no version and the plugin test rejects one
   go run ./internal/streams/cmd/streams set cli X.Y.Z   # docs/release-streams.yaml: the released version as the cli stream's current (and its next name moved on when the release opens a new minor)
   ```

   Both edits belong in the one release commit. The second is the step `scripts/release.sh` makes for you: `docs/release-streams.yaml` is the CLI stream's own record of where the line is at, so a release that does not write it back leaves the next release's floor and spoken name describing a version that has already shipped.

   The header is the two lines at the top of each skill file, the comment `<!-- fugaro-skill name=<dir> fugaro-version=X.Y.Z -->` and the sentence `(Fugaro X.Y.Z)` in the quoted notice; the script rewrites both everywhere and then runs its own check. `go test ./plugin/` only requires a non-empty `plugin.json` version and a header in every skill file equal to it; the release workflow enforces `version == tag` for both (`scripts/bump-plugin-version.sh --check X.Y.Z`), so a tag on a commit whose plugin version or any skill header differs publishes nothing. Run `GOFLAGS=-p=2 go test ./plugin/ -count=1` on the bumped tree before committing it, as in the checklist's plugin-budget step: the bump's own two bytes per skill file can be what pushes one over its budget.

   **The plugin is pinned to this tag (M11, [design §4.3](design/m11-setup-and-skills.md)).** `fugaro setup` and `fugaro update-skills` write the release tag `vX.Y.Z` of the running binary as the `ref` of the Fugaro marketplace in a repository's `.claude/settings.json`, so the binary, the plugin and the pin agree only if the plugin at that tag has version `X.Y.Z`: that is what the gate above enforces, and why a published tag is never moved or re-cut (a pin to it would silently change). `bump-plugin-version.sh` rewrites, and `--check` verifies, the version in `plugin.json` and in each skill's do-not-edit header. A development build (`fugaro version` prints `dev`) writes no pin. A private fork hosts its own marketplace and plugin at its own tags (`--allow-fork` moves the ref of its entry to the running binary's tag), and its users pin to those. After a release a repository moves its pin with `fugaro update-skills` (or `fugaro setup`), reviewed as one line in a PR; `fugaro doctor --plugin --strict` in its CI fails a pin that is older or newer than the binary, unpinned, foreign or not wired. Users move a checkout's pin, installed plugin and job images to a new release with one sequence: `brew upgrade dimipaun/tap/fugaro && fugaro upgrade` ([design/upgrade.md](design/upgrade.md)).
3. Rehearse if the pipeline changed: Actions, `release`, Run workflow (`workflow_dispatch`). It runs `goreleaser release --snapshot --skip=publish,sign` and uploads `dist/` as the `goreleaser-dist` artifact. Locally: `goreleaser release --snapshot --clean --skip=publish,sign` with `HOMEBREW_TAP_GITHUB_TOKEN=` set (empty), and syft on the PATH (or add `sbom` to `--skip`).
4. Tag the merged commit and push:

   ```sh
   git switch main && git pull --ff-only
   git tag -a vX.Y.Z -m "Fugaro vX.Y.Z"
   git push origin vX.Y.Z
   ```

   **This is also the path when the release PR merged and something landed on `main` after it** (0.10.0's case, step 4 above): `scripts/release.sh` refuses at step 4 and refuses on every re-run, so inspect the commits, check the gate on the tip (`GITHUB_SHA=<tip> GITHUB_REPOSITORY=dimipaun/fugaro scripts/release-gate.sh vX.Y.Z`), and tag the tip — it carries the bump and the fix, and the gate is what the tag workflows check.

5. Watch both workflows (`gh run watch`), then verify.

**If a workflow refuses after the tag was pushed because the Highlights file is missing or empty** (`release.yml` and `images.yml` both fail in their first steps, so nothing is published): the tag can never be moved or deleted by the release process, so leave it and cut `vX.Y.(Z+1)` with the file committed. Deleting the tag is the repository owner's rollback decision ("Rolling back"), not part of the routine.

Pull requests that touch `.goreleaser.yaml`, `release.yml` or the bump script run `goreleaser check` as the `check` job of `release.yml`. It is not a required check.

**After each release, the website (a standing step, the owner's rule of 2026-10-30).** Once the release is published and verified, update the website: downloads, checksums, versions and links, wherever the site names the latest release. Run the website's tests (`npm run check` in `website/`, and `go test ./internal/cli -run Docs`), merge, then dispatch `website-preview`. The owner promotes: `website-promote` and the `website-live` approval click are the owner's. For the CLI the changelog and the home page's latest-release line follow the release's own notes and summary, so the step is mostly confirming that nothing else on the site still names the previous version.

## Rolling out the shared installation config

The release that adds `gcp_project:` to `fugaro.yaml` needs an ordered rollout, because job images carry a baked-in `fugaro` binary that reads the repository's `fugaro.yaml` from the base branch (and the daily image check reads it too), and that parser refuses unknown keys. **Do not add `gcp_project:` to a repository's `fugaro.yaml` before its image is rebuilt with the new binary, and rebuild only after `fugaro setup` has pinned the release's base image**: runs and the daily check refuse the file until it is. Put this order in that release's Highlights, under `### For operators` ([design/shared-config.md](design/shared-config.md) §9):

1. Merge and release the version that adds the field (check `gcpProjectFieldSince` above).
2. Upgrade the CLI and run `fugaro update` once per installation (default-named runs bucket only). It publishes the shared file and changes no repository.
3. For each repository, in its checkout, in your own terminal window, or with `--yes` from CI or a script: `fugaro upgrade` (its cloud step is `fugaro image refresh`). It pins the release's base image — signature-verified at the release's `-pinned` tag, by digest through the installation's remote repository — and records it, points the daily image check job at it (image and `FUGARO_CHECK_SPEC`, no Terraform), and rebuilds every workflow not yet built from it. A derived image takes the `fugaro` binary from the base image, which is why the order matters, and the command keeps it. If the local config sets `base_images.<kind>` to a development (`dev-<sha>`) or hand-pushed image, it stops and names the entry, with or without `--yes`, and refresh never replaces a custom base image: either remove the entry from the local config (keep a backup) and rerun, or keep your own base image and rebuild from it with `fugaro image build --repo <owner/name> --workflow <name>`. `--yes` confirms every step unattended, including each billable build, with no cap on how many run; it is still refused in a coding agent's session, and there is still no `--json` or `--plan-only`. Its cloud step handles one repository per checkout; `fugaro upgrade` tries every PATH in turn and never writes `fugaro.yaml`.
4. Every teammate's CLI and every CI job or pin that runs `fugaro` against the repository (validate, doctor --plugin --strict, run) must be on the new release BEFORE the gcp_project line is merged: older versions refuse the key as unknown.
5. In each checkout, run `fugaro update --anchor` to add the `gcp_project:` line, then commit and merge it. It runs no Terraform and publishes nothing; it first checks every workflow's build record and the local config's base images, and writes nothing (exit 1, one ordered fix per workflow: the base-image fix if needed, `fugaro image refresh` in the checkout, `fugaro update --anchor`) while an image was submitted by an older or development CLI, was built FROM an older, development or hand-pushed base image (the record's `base_ref`; a record that does not name it fails too), or a configured base image would bring one back. A record read that fails in the cloud (missing credentials included) exits 2. Then it shows the diff and asks `Write this to <path>? [y/N]`. Plain `fugaro setup` in the checkout also writes the line as its last stage, with the same checks as warnings, after the full converge; `fugaro update --repo` does not write it.
6. Check it: in a fresh clone with an empty config and cache directory, `fugaro doctor` shows the `shared-config` line ([gcp-live-checklist.md](gcp-live-checklist.md) Check 28).

Until step 5 nothing changes for teammates: a checkout without the line gets the clear "add this line" error, and a machine can still write its own local config with `fugaro update --gcp-project <id> --region <region>`. Teammate-facing description: [README.md](README.md) — a teammate who is made a launcher needs the CLI and `gcloud auth application-default login`, no `fugaro setup`.

## Rolling out the 0.7.0 bucket hardening

Release 0.7.0 gives launchers who are not operators `roles/storage.objectViewer` on the runs bucket and `roles/storage.objectUser` on its `runs/`, instead of `objectAdmin` on the whole bucket ([design/bucket-iam.md](design/bucket-iam.md)). 0.9.0's sealed budget token widened that condition to `runs/` and `tokens/`, and an operator's `fugaro setup` replaces a runs/-only binding with the widened one, never deleting it. This is a separate rollout from "Rolling out the shared installation config" above (that one is pinned to the release that added `gcp_project:`, not 0.7.0). None of it is exercised against a real bucket in this project's own testing: the live check is [gcp-live-checklist.md](gcp-live-checklist.md) Check 32, reserved for the owner to run.

0.7.0's own rollout order ([design/bucket-iam.md](design/bucket-iam.md) §8, citing [design/base-image.md](design/base-image.md) §10) is the base-image consolidation's usual order — operators upgrade the CLI, each repository gets its pull request, each repository runs `fugaro image refresh`, doctor shows a clean result — with two steps the bucket hardening appends after those:

1. **One operator runs `fugaro setup`** (the installation stage) in their own terminal, reads the plan and the `bucket access (0.7.0)` banner naming each launcher whose old grant is replaced, and types the project's name. **Apply it while nobody is launching** (design §5): Terraform may destroy a launcher's old `objectAdmin` grant before it creates their two new ones, so a launcher who writes `runs/` during the apply can get a 403 for a few seconds, or for as long as IAM propagation takes (unverified, V5). The fix is to retry; no data is at risk, since the claim protocol fails closed. On a one-person installation (the only user is both launcher and operator) the plan has no bucket change.
2. **Every operator and launcher runs `fugaro doctor`,** which reports `runs-bucket-iam` ok.

The bucket change does not depend on the base-image steps, and pre-0.7.0 CLIs keep launching after it: a 0.6.x launch writes only `runs/` already. **A pre-0.7.0 CLI's own stale-lock clear is different, though:** once the apply lands, an older binary's `locks/` delete (`cancel`, `run --pr`, on a holder confirmed over) is refused the same as a current CLI's, but it predates this release's classification of a refused write and has no "an operator must clear it" message to show — it surfaces whatever raw, unclassified error the refusal produces instead. Upgrade every machine's CLI at or before the apply if lock takeovers matter to you. Claude never applies this migration; the user reviews and applies the plan at their own terminal (no live cloud access in a Claude session).

## Verifying a release

```sh
V=X.Y.Z
gh release download v$V -R dimipaun/fugaro -p checksums.txt -p checksums.txt.sigstore.json -p "fugaro_${V}_$(uname -s | tr A-Z a-z)_*"

# The checksums are signed by the release workflow on that tag
cosign verify-blob checksums.txt \
  --bundle checksums.txt.sigstore.json \
  --certificate-identity "https://github.com/dimipaun/fugaro/.github/workflows/release.yml@refs/tags/v$V" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com

# The archives match the checksums. The grep names this OS's entries, which are
# the ones the download line above fetched: checksums.txt covers every platform's
# archive and its SBOM, and sha256sum exits 1 with "FAILED open or read" for each
# entry whose file is not in the directory.
grep " fugaro_${V}_$(uname -s | tr A-Z a-z)_" checksums.txt | shasum -a 256 -c -      # macOS
grep " fugaro_${V}_$(uname -s | tr A-Z a-z)_" checksums.txt | sha256sum -c -         # Linux

# Each channel
brew install dimipaun/tap/fugaro && fugaro version
go install github.com/dimipaun/fugaro/cmd/fugaro@v$V
docker pull ghcr.io/dimipaun/fugaro-web-node:$V
docker pull ghcr.io/dimipaun/fugaro-go:$V
docker pull ghcr.io/dimipaun/fugaro-java-services:$V
docker pull ghcr.io/dimipaun/fugaro-history:$V
# Once a release has published fugaro-base (not yet true):
# docker pull --platform linux/amd64 ghcr.io/dimipaun/fugaro-base:$V
# docker pull --platform linux/arm64 ghcr.io/dimipaun/fugaro-base:$V
```

Each archive carries the binary, `LICENSE`, `LICENSES/LicenseRef-Fugaro-Subscription.txt` (the text of `ee/LICENSE`, which the tagged binary's `ee/` code is under), `README.md` and `THIRD_PARTY_NOTICES.md`, the licence and notice texts of every Go module the binary links, which `scripts/third-party-notices.sh` writes in GoReleaser's before hooks — one `go list -deps` per target of the build matrix, so a module only one target links is covered too, and the file is generated into the tree rather than committed.

Also check on the release page: it is not a draft; for 0.4.0 and later it is not marked "Pre-release"; the body shows `## Highlights` above `## Changelog`.

`fugaro version` prints `X.Y.Z` (no `v`); a `go install` build prints `dev` because the version is injected only by GoReleaser's `-ldflags`. SBOMs are the `*.sbom.json` assets (SPDX/syft JSON, one per archive).

**Update checks.** Once a day, any command asks this same releases API (`/repos/dimipaun/fugaro/releases/latest`, which only ever returns a non-draft, non-prerelease release) whether a newer one exists, and nags once a day at most when it does (the switches are `FUGARO_NO_UPDATE_CHECK=1` and a project config's `update_check: false`, and `fugaro doctor` reports the comparison itself, as its `cli-version` check). Nothing in this repository's test suite or CI ever makes that call for real: it is exercised only against fake HTTP servers, never verified here against a live lookup.

### Verifying the console's release

The console's own release, `console-vX.Y.Z`, carries the desktop app, not the CLI. **The macOS build is signed, notarised and stapled (D4); the Linux build is not signed at all (the owner's ruling of 2026-10-20, design D10 and §7.6), and an AppImage is not code-signed** — there is no signature inside the file, no notarisation step and no Linux signing key, so nothing about the AppImage or the `.deb` can be checked with `codesign`, `spctl` or `cosign verify-blob` against the file itself. What is verified is the release's own machinery: the artifact's SHA-256 against `console-sha256sums.txt`, and that file against its Sigstore bundle.

```sh
V=X.Y.Z
gh release download console-v$V -R dimipaun/fugaro \
  -p console-sha256sums.txt -p console-sha256sums.txt.sigstore.json \
  -p "Fugaro.Console-${V}-linux-*" -p console-linux-verification.txt

# The one sums file covers every asset of the release, macOS and Linux alike,
# and it is signed by the console workflow on that tag (keyless, via OIDC).
# The identity's ref segment is the CONSOLE tag: console-vX.Y.Z, never vX.Y.Z
cosign verify-blob console-sha256sums.txt \
  --bundle console-sha256sums.txt.sigstore.json \
  --certificate-identity "https://github.com/dimipaun/fugaro/.github/workflows/console-release.yml@refs/tags/console-v$V" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com

# The Linux artifacts match that signed list of hashes -- the signature is over
# the list, not over the AppImage, because an AppImage is not code-signed. The
# grep is not a shortcut around the check: the file covers the macOS assets too,
# which this download does not include. It matches on `linux-`, the one word both
# names carry: the packer writes the target's own word for the architecture, so
# the AppImage is `-linux-x86_64.AppImage` and the deb is `-linux-amd64.deb`, and
# a pattern spelled `linux-x64` matches neither
grep "linux-" console-sha256sums.txt | sha256sum -c -      # shasum -a 256 -c - on macOS

# What the workflow ran against those exact bytes: the .deb's control/metadata
# and contents, the AppImage's own unpacking, and the fuse wire read back out of
# the executable inside each artifact
less console-linux-verification.txt
```

**Two things a reader must not conclude.** That the Linux artifacts are signed in any sense — they are not, and a release note or a page that says so is wrong. And that the CLI's release carries any of this: the console's assets are on `console-vX.Y.Z` and on no other release, and a console release carries a Linux leg as well as the macOS pair, so the macOS names above are not the whole of what it ships (console/README.md, the Linux section).

## Console releases

The desktop console has **its own release stream**: its own tag, its own version line and its
own notes, independent of the CLI's. The three streams are the owner's (addendum of
2026-10-22): **CLI = animals** on `vX.Y.Z`, **Console = fruits** on `console-vX.Y.Z`, **Mobile
= birds**. `scripts/release.sh` and `scripts/release-gate.sh` are the CLI's and are unchanged
by this: a `vX.Y.Z` tag releases the CLI and starts no console work, and a `console-vX.Y.Z`
tag releases the console and no CLI work.

**Tag format.** `console-vX.Y.Z` — strictly `console-v`, then three dot-separated numbers with
no leading zeros. The workflow triggers on a push of a tag matching exactly that and on
nothing else (no pull request, no `pull_request_target`, no `workflow_run`, no manual
dispatch: the signing job reads the Apple certificate and the App Store Connect key from the
protected `console-release` environment, and a branch of this repository can open a pull
request). The tag step refuses anything else, **the CLI's own `vX.Y.Z` tags included**. The
version the release is stamped with is `X.Y.Z` after the `console-v` prefix.

**The version line.** `console/package.json`'s `version` is the console's own version. It is
set to `X.Y.Z`, on `main`, **in the same commit as the notes below and before the tag is
pushed** — the same ordering the plugin version and the Highlights file follow. Both build
legs refuse to run when the tag's `X.Y.Z` differs from that field (or when the field is absent:
a version line of `null` is not a version). This is the call `release.yml` already makes for
the plugin's version, one file over. It exists because a version that lives only in its tag is
one whose file names, update feed and own version line can disagree with the release they were
built for; and because the console's updater refuses a **downgrade** (Task 4.4 of
`docs/plans/2026-10-15-desktop-console.md`), a console stamped below the version its
installation already runs would refuse every update it was offered afterwards. So the version
line never goes backwards, and the first release on this stream is **`0.110.0` "Cherry"** — see
below.

**Why the console and the app start at `0.110.0` and `0.200.0`.** The console's and the
mobile app's version numbers are deliberately far from the CLI's, so that a version on its own
identifies its stream: the CLI has its own `0.11.0` ("Camel"), and a console `0.11.0` beside it
would be read as the same release (the owner's ruling of 2026-10-24, which renumbered the
console from `0.11.0` and the app from `0.1.0`).

**The notes file.** `docs/releases/console/vX.Y.Z.md`, written by hand and merged to `main`
before the tag, like `docs/releases/vX.Y.Z.md` for the CLI. [`docs/releases/console/README.md`](releases/console/README.md)
is the format and the naming list. It is the release's **body**: the release job refuses to
build when it is missing or empty, and the `publish` job — which has no checkout — reads it
from the tagged commit through the API and passes it as `--notes-file`, after the standing
sentence about what is and is not signed on each platform.

**The console's end-user summary is the opening sentence of that file**, and it is
deliberately *not* an entry in `website/data/release-summaries.yaml`: that file is keyed by the
CLI's `vX.Y.Z` tags and the site's changelog is the CLI's page, so a console release writes no
line there and appears nowhere on the site. `scripts/release.sh` does not check the console's
notes and never asks for a summary of them.

**The release names are fruits, used once each, in order.** The list starts **Cherry**
(`0.110.0`), then **Mango** (`0.111.0`), then **Melon** (`0.112.0`), then **Nectarine**
(`0.113.0`), then **Orange** (`0.114.0`), then **Papaya** (`0.115.0`), then **Peach** (`0.116.0`), then **Pear** (`0.117.0`); the name is the heading of
that version's notes file, and the list is extended by one when the next console release is
cut. **Apple is avoided** — in any spelling, including its varieties, and most visibly as
"Apple": the desktop app is not an Apple product and a console release titled after one would
say it is — and **Lemon is avoided** too, because it reads as a disclaimer on a release that
has not gone sour. `docs/releases/console/README.md` carries the table.

**What the release gate checks.** Both console legs run the CLI's own
`scripts/release-gate.sh`, handed **`v` + the version** rather than the console tag, because
that script is the CLI's and refuses anything that is not a strict `vX.Y.Z`; the console tag's
own shape was already checked strictly, by prefix, one step earlier. What the gate is asked
for is the part that is about the commit: the tagged commit **is an ancestor of `origin/main`**
(and the workflow refetches `main` to check it, with `fetch-depth: 0`), and the required check
runs on it — **`test`, `terraform`, `rules`, `console (ubuntu-latest)` and `console
(macos-latest)`** — have all succeeded (a cancelled run is ignored while another run of the
same name exists; a missing or still-running one makes the gate wait or refuse, and it may
accept the checks of a merged pull request whose tree is identical).

**To release the console**, in order:

1. Bump `console/package.json`'s `version` to `X.Y.Z` and write `docs/releases/console/vX.Y.Z.md`,
   in one PR to `main`.
2. Tag that commit **on `main`** and push the tag:

   ```sh
   git tag console-vX.Y.Z
   git push origin console-vX.Y.Z
   ```

3. Approve the `console-release` deployment when GitHub asks (the environment's required
   reviewer is the owner). **When approving, confirm the tagged commit is on `main`**: the
   workflow runs as the tagged commit holds it, so the environment's reviewer and the tag
   ruleset are the real control, not the file on `main` today.
4. The workflow builds, signs and notarises the macOS app in a job holding only a read token,
   builds and verifies the unsigned Linux artifacts beside it, and hands both legs to the
   `publish` job — the only one with `contents: write` — which re-checks the SHA-256 sums,
   merges them into one `console-sha256sums.txt`, signs that file keyless with cosign, creates
   `console-vX.Y.Z` as a draft with every asset, and publishes it with `--latest=false`. The
   CLI's release stays the repository's latest.
5. **A re-run never clobbers.** Releases here are immutable: if `console-vX.Y.Z` is already
   published, or a draft of it is left from an earlier attempt, the job stops rather than
   overwriting — and it checks, before publishing, that the tag **still resolves to the commit
   it built**: the tag is the owner's and this job never creates, moves or reuses it, so a tag
   that was force-pushed or re-pointed after the run started stops the publish rather than
   putting artifacts from one commit under a tag naming another. Delete a leftover draft
   (`gh release delete console-vX.Y.Z`) and re-run; a new build needs a new tag.
6. **Update the website** once the release is published and verified: `website/content/downloads.json`'s
   `release.version` and each entry's `sha256`, and `website/data/console-sha256sums.txt` copied byte
   for byte from the release's own `console-sha256sums.txt` after `cosign verify-blob` accepts it
   (the file also names the update feed, `latest-mac.yml`, which is not a download, and the site's
   checks pass over that one name). Run the website's tests (`npm run check` in `website/`, and
   `go test ./internal/cli -run Docs`), merge, then dispatch `website-preview`. The owner promotes:
   `website-promote` and the `website-live` approval click are the owner's.

`docs/pending-workflows/console-release-tag.yml` and has been applied: it superseded the staged

console work; the `console-release` environment's deployment policy and the tag ruleset name
`console-v*` for it.

## Rolling back

Rolling back a published release is the repository owner's decision, and the owner runs it; automation and the `/new-release` skill never delete or move a tag and supersede with the next patch release instead. Delete the GitHub Release and the tag (`gh release delete vX.Y.Z --cleanup-tag -R dimipaun/fugaro`), delete the images' `X.Y.Z` tag from the package page (and re-point `:X` at the previous release if it moved), and revert the cask commit in `dimipaun/homebrew-tap`. The Go module proxy caches `vX.Y.Z` forever, so `go install ...@vX.Y.Z` keeps working with the old content; never reuse a version. Ship the fix as `vX.Y.(Z+1)` and, if the bad version is dangerous, add a `retract` directive to `go.mod`.
