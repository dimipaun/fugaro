# Phase 2 hosting: the always-on orchestrator

**Status: design only; nothing is implemented — and this is the design of record.** This document is the design Task **P5.1** of [the mobile plan](../implementation-plan.md) asks for. **The owner approved P5.1 on 2026-11-14 and the plan split it into eight tasks, P5.1a–P5.1h**; this document is **P5.1a**'s deliverable. It writes no code, no Terraform, no workflow file and no rules change, it approves nothing, and it allocates no decision number. The draft of it was written in **PR #632, which is closed and was never merged**, against a tree that has since moved; **this revision is that draft's text, re-grounded against the tree of 2026-11-16**, with a dated note on every sentence the tree has made false ([§0.2](#02-corrections-to-the-draft-dated-2026-11-16)) rather than a silent edit. *(The draft's status block read "**P5.1 stays unscheduled**", which was true on 2026-10-19: the owner had answered **D115** on 2026-10-17 with "decide phase 2 later" ([reconciliation.md](../reconciliation.md) §3), and answering a decision is not approving a task. The approval of 2026-11-14 is the owner's own act and it is recorded in the plan, not here; **what it does not do is build anything** — the seven tasks that would are approved and unbuilt.)*

**The one-paragraph answer to the owner.** The phone's tasks should keep running while the laptop sleeps, and they can — but not by putting the laptop's job into one always-on cloud process. Split the thing the task entry calls "the always-on orchestrator" into the two functions it conflates: **the mailbox's other side** (a small consumer that polls the inbox, verifies the tag, holds the lease, writes the outbox and the heartbeat, and launches runs) and **the agent work** (which already runs as a Cloud Run **Job** execution, one container per run, discarded at the end — the boundary `SECURITY.md` relies on). The resident part runs as **one Cloud Run service per installation, in the installation's own GCP project**, `min-instances = 0`, woken by a Cloud Scheduler tick, with a dedicated service account that holds the **launcher's** grants and **no model credential of its own**; the model credential stays where it is today — in the job that needs it, per-repository, per-secret — and the [credentials service](../../credentials-service/README.md) **has since landed and every `fugaro update` deploys it**, so the jobs move to it per repository rather than all at once ([§3.5](#35-the-credentials-service-which-has-landed)). That split is what makes the envelope answerable: a stolen phone can ask, a stolen account cannot sign, a poisoned message cannot verify, and nothing any of them sends can move money past the caps and the kill switch, which the database — not the resident orchestrator — enforces. **Two things this document must not oversell, and §4.5 states as its own attackers:** the resident orchestrator holds a **copy of the pairing key** (the tag is a symmetric HMAC, so a verifier must hold it — a third copy the owner ruled on 2026-10-19, taking [Q8](#10-answered-by-the-owner-on-2026-10-19)'s recommended option), and it held **`signJwt`**, so a compromise of it could mint any identity in the installation, the phone's included. It is the strongest attacker this design has, and it is written down as **E4** rather than argued away. **Re-grounded 2026-11-27: the signing row is the credentials service's alone** (D3121, LM14 of [docs/launcher-does-not-mint/](../../launcher-does-not-mint/implementation-plan.md)), so a compromised orchestrator reaches the launch path — a ticket for a run the issuer admits — and not the signing key; §4.5's E4 and §4.3's table carry the change.

### 1.2 The direction-bound MAC exists, in JavaScript and in Go — the consumer that would verify it does not

This one is real, and it is the strongest thing the mailbox has. `shared/mailbox-schema/mac.js` exports `macOf(record, key, direction)` and `verifyMac(record, key, direction)` — HMAC-SHA-256 over `canonicalBytes(record, direction)`, timing-safe on verify, over every field except `mac` itself and the phone-written `acked`. `shared/mailbox-schema/index.js` exports `DIRECTIONS` (`inbox`, `outbox`, `heartbeat`) and injects the direction into the covered bytes, so a record reflected from the inbox into the outbox does not verify (the owner's ruling of 2026-10-18 on PR #579). The heartbeat is **signed too** ([§4.5](#45-the-hard-envelope-a-stolen-phone-a-stolen-account-a-poisoned-message-and-a-compromised-orchestrator) E2 and [Q8](#10-answered-by-the-owner-on-2026-10-19)); that is what makes this a custody question and not just a verification one.

**Re-grounded 2026-11-16: the Go half exists, and the draft said it did not.** The draft's sentence was "**no Go code verifies a MAC** … the rules' mailbox subtree does not require a `mac` field — `TestMailboxRulesAgreeWithTheSharedSchema` records that gap by name". Both halves are now false of this tree:

- **`internal/mailbox/mac.go`** carries **`VerifyMAC`** in Go, over the same canonical bytes and the same direction the JavaScript computes, with the same `false` for a mismatch — and `internal/mailbox/mac_test.go` and `mac_sign_test.go` read `shared/mailbox-schema/vectors.json` directly, which is the parity the mobile rule for JS-and-Go wire formats asks for.
- **The rules require the field.** `internal/budget/rules/rules.json.tmpl` carries `"mac": { ".validate": "MACOK" }` on the inbox, the outbox and the heartbeat, and `TestMailboxRulesAgreeWithTheSharedSchema` pins `required` to exactly `{id, sender, text, at, mac}` — the schema's own list, not a looser one.

**What is still unbuilt is the consumer, and that is the whole of the gap now.** `internal/cli/root.go` registers **no `mailbox` command**, and `internal/cli/mailbox.go` does not exist: the pass that would call `VerifyMAC` on a real inbox is plan **Task P4.1**, and its cloud half is what [§4.2](#42-what-it-is-made-of-a-consumer-a-launcher-and-jobs-that-are-the-agent) proposes to run as a service. The plan's P5.1 section records the same thing as the one wait left in phase 2: **P5.1f and P5.1g wait on P4.1**, and nothing else does.

**Consequence.** The resident orchestrator is the **first consumer that will exist**, and what it needs is a pass that does not exist rather than a verification primitive that does not. That is a smaller gap than the draft's, and it does not change the design: [§4.6](#46-how-it-authenticates-the-phone) still separates "what authenticates the phone today" (the rules' user claim, **now with the device node**) from "what authenticates the *message*" (the MAC, built on both sides and called by nobody), and [§9](#9-the-alternatives-priced) still prices a laptop-only phase 2 as a real alternative rather than as a fallback.

### 1.3 "The approval model" is not a mechanism in the tree

P5.1's own text says an always-on orchestrator inherits "the approval model (F17)". No mechanism by that name exists: `grep` over `internal/` finds no `approv*` machinery except `fugaro allow-delete` (`internal/cli/allow_delete.go`), which is an operator-recorded list of Terraform addresses approved for cloud deletes and has nothing to do with a run. "The approval model" is the mobile work's name for the console's confirmation-before-write rule (D22), the D128 amendment of 2026-10-17 (destructive voice commands allowed only with a read-back and an explicit "confirm") and managed-projects' plan-then-apply gate. *(Re-checked 2026-11-16 and unchanged: still no such mechanism.)*

**Consequence.** This design does not invent an approval service. It writes down what the existing pieces would enforce for a phone that is the only human ([§4.8](#48-approvals-when-the-phone-is-the-only-human)) and leaves the unbuilt pieces (the spoken-confirmation machine, Phase 6 P6.2) named as dependencies. **`shared/confirm/index.js` is merged on `main`, not a draft** — `shared/README.md` calls it "the spoken-confirmation state machine … with its own tests, its own mutation proof and `vectors.json` for P6.7's Go parity test" — but nothing in the tree imports it: no Go or JS consumer exists, and `vectors.json`'s own note names `TestConfirmParityWithShared`, **a test that still does not exist on `main`** *(re-checked 2026-11-16: the name appears in `shared/confirm/vectors.json` and in two plan documents, and in no `_test.go` file)*. Merged logic with no consumer is exactly what the mobile plan says it is: not evidence that a task is approved.

## 2. The problem

Phase 1 puts the operator's agent on the operator's laptop: the phone writes an inbox message, and a consumer running beside it on that machine reads it, acts, and writes the outbox and the heartbeat. The mailbox is designed for a consumer that is **sometimes absent** — at-least-once delivery, a lease with a TTL, dedupe, a replay window, a 72-hour TTL on stored messages — so nothing is lost when the laptop sleeps. But the phone's primary feature does not work when it does: a launch waits, a prompt waits, and the heartbeat D117 shows as presence goes stale, so the app honestly reports the installation **offline** while the owner is away from the laptop.

Phase 2 is the fix, and it is not a small one. The laptop's consumer runs under the **operator's own identity**: `internal/cli/cloud.go`'s `google.DefaultTokenSource` gives it the operator's application-default credential, and **D113b** records the honest consequence — that credential is an admin/editor on the database and **bypasses the RTDB rules** — so for the laptop "the outbox and the heartbeat and nothing else" is a rule in the consumer's code, not a fence the database enforces. A cloud consumer under a **narrow service account** is the first mailbox writer the rules can actually fence — and it is also the first one that needs a cloud identity, a cloud posture, a spend story **and a copy of the pairing key**. That is D115, and it is why the owner deferred it.

**Re-grounded 2026-11-16: phase 1 is still not built.** The paragraph above is written as if the laptop consumer existed; it does not. `internal/cli/mailbox.go` is not in the tree and `fugaro mailbox` is not a registered command, so **P4.1 is a prerequisite of both halves of this design** — the laptop pass and the cloud one are the same pass run by a different process ([§4.2](#42-what-it-is-made-of-a-consumer-a-launcher-and-jobs-that-are-the-agent)). Nothing else in this section has moved: D113b's honesty note, the 72-hour TTL and the presence staleness are as the draft states them.

| Confirmation | `shared/confirm/index.js` (merged; `shared/confirm/README.md`) | The read-back, the fixed phrase, the timeout, the replay ledger and D128's refusals — with tests and a mutation proof, and **no consumer anywhere in the tree**. |
| The database side | `internal/budget/rules/rules.json.tmpl`, `internal/budget/rules/rules.go` (`MAILBOX`, `CONSUMER`, `userClaim`, `USER`, `MACOK`, `PathDevices`) | `userClaim` is `auth.token.mu == auth.uid` **and the device node's existence** (`root.child('config/admin/devices').child(auth.uid).exists()`); **`USER` expands to `userClaim` unchanged** (its `case "USER"` returns it), so the device node is a conjunct of the phone's own reader claim; `MAILBOX` is `userClaim && $mb == auth.uid`; `CONSUMER` is `auth.token.mc == $mb`; the phone writes its own inbox and the `acked` child of an outbox message it has spoken (`TestMailboxWritesAreExactlyTheFour`). |
| Rules generation | `internal/projectpolicy/version.go` (`RulesVersion = 6`) | **Generation 3 is the mailbox's message fields, the device node and the pairing nodes; 4 is the coordinator's grant; 5 is the voice policy node; 6 is the registration kind's fields on a mailbox message.** *(The draft's row read "`RulesVersion = 2` — Generation 2 is the mailbox. There is no generation 3"; the file is cited by symbol, so the row moves with it rather than being edited to a number that will move again.)* |

Two properties matter for everything below. **Delivery is at-least-once, so acting exactly once is the consumer's problem**, not the phone's; and **the tag is over the message and its direction**, so an attacker who can *write* a node the phone or the consumer reads still cannot make either of them act without the pairing key — which is a statement about the key's secrecy, and [§4.5](#45-the-hard-envelope-a-stolen-phone-a-stolen-account-a-poisoned-message-and-a-compromised-orchestrator) E4 is where that secrecy stops holding.

### 3.2 The launch path and the launch claim

A run today is launched by the CLI on the operator's machine:

1. **The claim.** `internal/runstore/launch.go`'s `Claim`/`ClaimKey`/`ClaimTTL`/`ReadClaim` — a GCS object under the run's prefix, created **if absent** (`launching`), taken in `internal/cli/run.go`'s `takeClaim`, and readable only after a win. `ClaimTTL` is 10 minutes, and a stale or unreadable claim can be taken over by a `ReplaceIf` on the generation read. F4 and `desktop-console-v2.md` F11 record this as **the tree's only "two actors cannot do the same thing twice" mechanism** — "the **only** reason two launchers cannot start the same run twice".
2. **The mint.** Only a CLI holding the claim mints: `internal/cli/launch_budget.go`'s `mintBudgetToken` signs a custom token through `token.IAMSigner` (`iam.serviceAccounts.signJwt`, the `token_minter` custom role in `deploy/terraform/gcp/modules/firebase/iam.tf` — "signJwt and nothing else"), and `internal/budget/token/object.go`'s `PutObject` writes it create-if-absent to `runs/<slug>/<run>/budget-token`, with a bucket lifecycle rule deleting an untaken one after a day. **"May mint" is exactly "may launch".** **Re-grounded 2026-11-27: this is the bridge now, not the path.** Where the installation's credentials service serves the ticket route the launcher asks it for the run's identity, puts the ticket on the execution and signs nothing and writes no object (LM6, LM7 of [docs/launcher-does-not-mint/](../../launcher-does-not-mint/implementation-plan.md)); the mint above is what a launch does where the service answers "not served", or is not configured, or is a release behind (R7), and the signing row this step needs is one `fugaro update` has taken away from every launcher and operator (D3121). **So the step that made "may mint" "may launch" is the step the issuer absorbed**: a launcher may launch the repositories its scope admits and may not mint.
3. **The take.** The container takes it once — `internal/runner/projectpolicy.go`'s `takeBudgetToken` reads and deletes, and `internal/budget/token/object.go`'s `checkNames` refuses a token whose own `uid`/`fs`/`fr` claims are not the names used (`ErrTokenMismatch`). A launcher's marker with no token in the bucket is a refusal and never "this project published no policy" (`internal/runner/budget_session.go`'s `TokenMarked`, which `strayTokenNoBackend` is the refusal for); and an environment that *names* a backend it cannot parse does not take the legacy path either (`MalformedEnv`, whose own comment calls it "the one place the marker did not fail closed"), so it stops the run at the backend or the policy read instead of falling back to the environment ceiling.
4. **The launch.** `internal/backend/backend.go`'s `LaunchSpec` carries one environment marker into the Cloud Run Job execution override; the job's own service account runs the container.

None of this needs a laptop. All of it needs an identity that may **sign, write the bucket, and run the job** — which is exactly what a service account in the installation's own project can be given. **And `signJwt` is not a narrow power**: the signer account's role is `signJwt` and nothing else, and a principal holding it can sign **any claim set for any uid**, which the rules' own `userClaim` doc-comment in `rules.go` states in so many words — *"any claim they read (an fp, an expiry) is one the minter writes too"*. That is the fact [§4.5](#45-the-hard-envelope-a-stolen-phone-a-stolen-account-a-poisoned-message-and-a-compromised-orchestrator) E4 is built on, and it is why 0.30.0 takes the row away from this actor (D3121, D3125): the resident orchestrator's row is removed once the resident service runs that release's image, and what it keeps is the launcher's other grants — so it launches through the issuer like every other launcher, and its asks are narrowed to a recorded, unstarted attempt of a repository (D3136). The steps above stay as the design reached them, with §4.5's E4 re-grounded beside them.

**Re-grounded 2026-11-16: a second launcher and a second lease are in the tree, and this design must say which one it is.** `internal/orchestrator/` — the stateless-orchestrator work's package, `docs/stateless-orchestrator/` O0–O18 — holds `launch.go` (a `Spec` and a `SpecOf`/`SpecDigest` over a work item), `lease.go` (a **daemon lease** per orchestrator id, O3/D1232, built on `internal/rtdb`'s `ServerNow` and an ETag fence) and its own `ClaimTTL` of ten minutes, which its own comment says is *"the same ten minutes `internal/runstore` gives a launch claim, and the window O8's launcher takes a stale claim over after"*. **It is not a rival to the four steps above — it is a launcher over a different state, and the plan's P5.1-Q10 rules that phase 2 reuses it** rather than writing a third one ([§4.2](#42-what-it-is-made-of-a-consumer-a-launcher-and-jobs-that-are-the-agent)).

### 3.3 The budget envelope

The caps are enforced **twice, and the second time is by the database**:

- **Per-run cap:** `internal/budget/evaluate.go`'s `Evaluate` compares `Outstanding()+Amount` against `caps.PerRun()`, and `internal/budget/lease.go`'s `leaseSize` clamps the lease to it — under `if sn.Caps.Enforcing()`, so the clamp is itself conditional on the mode (this section's closing paragraph) — *and* `internal/budget/rules/rules.go`'s `perRunOK` generates the rules' own comparison into the `reserved` leaf's `.validate`. The effective cap is the **minimum** of the repository's own/default and the global one, fail-closed.
- **Daily caps:** the same shape, `REPODAILY`/`GLOBALDAILY` in the rules and `ReasonRepoDailyCap` in `Evaluate`.
- **The kill switch:** `config/kill/global` and `config/kill/repos/<slug>` (`internal/budget/model.go`'s `PathKillGlobal` and `PathKillRepo` — the repository one is `"config/kill/repos/" + seg("slug", slug)`, and `internal/budget/rules/rules.go`'s `KILLS_OFF` macro reads `root.child('config/kill/repos').child($slug).child('on')`, so the `repos/` segment is the tree's, not a convenience — written by `internal/budget/kill.go`'s `SetKill`), and `KILLS_OFF` refuses a lease while either is on.
- **The seal:** `docs/budget-token-channel/spec.md` §7 — the token object is sealed AES-256-GCM under a per-launch key that travels in the existing marker, so a run that steals a peer's object cannot use it ("a capability, not a boundary"). That design's D14–D19 are answered and **both halves shipped in 0.9.0** — Slice A, the runner side and the token package (PR #417), and Slice B, the launcher's seal, the retry re-seal and the `tokens/` move with its grants — and the tree carries the result as `SealedBudgetToken` in the image record and in `internal/cli/launch_budget.go`. *(The draft's sentence was "its implementation rides 0.9.0", which was a promise on 2026-10-19 and is a fact now; Check 60 is written in the register and has not run.)*

A compliant-but-hostile client therefore cannot write an over-cap ledger; the caps are not a promise the launcher makes, they are a rule the database applies. **That is the load-bearing fact for [§4.5](#45-the-hard-envelope-a-stolen-phone-a-stolen-account-a-poisoned-message-and-a-compromised-orchestrator)**: the resident orchestrator inherits exactly these caps and cannot loosen any of them, because loosening one is a `config/caps/**` write, which is owner-run.

**And the whole envelope is conditional on the budget being on, which it is not by default.** `SECURITY.md`, "What is not on by default": *"**Budget mode defaults to off.** With no `budget:` block in the installation's own config … there is no gateway and no per-call cap: the real model key sits in the agent's environment like any other secret, and the only limits are the provider account's own limit and the token cap, if you set one (0 is none)."* The code agrees: `internal/runner/spend.go`'s `Spend.Mode` is `off | observe | enforce` and `Spend.On()` is false for `off`; `internal/cli/launch_budget.go`'s `budgetBackendOn` returns false for `BudgetOff`, an absent `budget:` block or an empty RTDB URL, so **no cap node is read at all**; and even with the budget on, `Evaluate` in **observe** mode returns a refusal as `Decision.Advisory` on an allowed decision. **On an installation with the budget off, or in observe, the sentences below that say "the caps bound it" are empty** — nothing in this design changes that, and [Q9](#10-answered-by-the-owner-on-2026-10-19) asks the owner whether a phone-launchable installation must be one with caps set. **The plan answers that for phase 2**: its **P5.1-Q3** recommends that a phone-launchable installation must have the budget published, **on and enforcing**, with the module and `doctor` refusing a launch otherwise — recorded in [§10.1](#101-answered-by-the-owner-on-2026-11-14--the-plans-eleven-questions).

### 3.4 Where a model credential lives today

`agent.auth` in a repository's `fugaro.yaml` is one of `vertex`, `oauth` or `api-key`. `internal/infra/spec.go`'s `SecretMounts` is "the one place that decides" what a job mounts: the git secret always; for `oauth`, `config.ClaudeAccountSecret(...)` → `CLAUDE_CODE_OAUTH_TOKEN`; for `api-key`, `anthropic-api-key` → `ANTHROPIC_API_KEY` plus each allowed provider key; for `vertex`, **nothing** — the job's service account gets `roles/aiplatform.user` and the SDK uses the metadata server. `deploy/terraform/gcp/modules/workflow/job.tf` builds the Cloud Run Job with a static `secret_env` → `secret_key_ref`, and `deploy/terraform/gcp/modules/workflow/sa.tf` grants `roles/secretmanager.secretAccessor` **per secret, to that job's service account**.

Two limits follow, and both are recorded in the tree: a job-level mount is **per job, not per execution** (Cloud Run execution overrides cannot carry a secret reference — `docs/named-oauth-tokens/spec.md` U1), so every execution of one job sees the same value; and the agent shares the container with the runner, so it can read the value from the runner's `/proc`, which `SECURITY.md` lists among the known limits along with "the GitHub App's private key".

**A third limit is what [§4.4](#44-how-it-holds-a-model-credential-three-candidates-priced) has to be honest about**: `SECURITY.md` records, of the launcher's reach, that *"This is an accepted decision, not an oversight: the launcher holds the job's own credentials"*, and that *"A launcher can override a job's environment"* — including the two variables the run reads the project's policy from. So "the credential is in the job, not in the launcher" bounds **where the secret is stored**, not **what a launcher can reach through a job**. An identity that may `runWithOverrides` and write `runs/` can start a run whose agent reads the mount. That is B3 of this round's review, and [§4.4](#44-how-it-holds-a-model-credential-three-candidates-priced) now says it in its own words.

**Re-grounded 2026-11-16: the credentials service changes the shape of this section, and only for the repositories that have switched.** The arrangement above is still the default and still what a repository mounts; what has changed is that the service that exists to replace it **is deployed** ([§3.5](#35-the-credentials-service-which-has-landed)) and a repository switches to it one at a time. So "a job mounts its model key" is true of a repository the switch has not reached, and false of one it has — which is the state [§4.4](#44-how-it-holds-a-model-credential-three-candidates-priced) (A) and (B) have to be read against.

### 3.5 The credentials service, which has landed

`docs/credentials-service/reconciliation.md` (D130–D154) designs the opposite arrangement: a **standalone Cloud Run service per project** whose service account is the only identity holding `secretAccessor` on model keys; jobs keep `run.invoker` and **no** `secretAccessor` on those secrets, and reach it through the in-runner gateway with a short-lived per-job token that **is** the run's existing budget identity (D134). The service never returns the real credential to the job — it swaps the header and forwards. Its bounds are its own decisions: D143 accepts the single point with bounds and a fail-closed halt (an unreachable service halts the run, never falls back in-job), D146/D147 make it per-installation and owner-applied from the installation's Terraform root, and **the boundary this design has to respect is `docs/credentials-service/spec.md`'s "Boundary" bullet, recorded by `docs/credentials-service/reconciliation.md`'s F36**: the service "stays secrets-only", and other always-on features — *"the phone client backend"* is named explicitly — go in **sibling services that call it**. (The quotation is the spec's; F36 is the finding that classifies it **Exists**, and its `Consequence` is that "no mobile function goes in this service".)

**Re-grounded 2026-11-16: "plan-only, unscheduled, gated on the budget-token seal" is no longer true, and the correction matters more than any other in this list.** What the tree holds:

- **The service is built.** `internal/credsvc/` is a real package — `auth.go` (the caller's Google ID token verified against the keys Google publishes, and the `email` claim against the installation's job service accounts), the wire contract, the answer-header swap, the audit, the Bitbucket proxy and the cascade's own accounting — with its tests.
- **It is deployed for every installation, automatically, by `fugaro update`.** The owner's ruling of **2026-11-05** is "DEPLOY NOW, SWITCH LATER": `fugaro update` deploys the service, and **the jobs switch to it later, per repository, and only where the service can serve that job** — the repository root's `credentials_service` input and the run's `FUGARO_CREDENTIALS_SERVICE_URL` stay off until the bundle holds what that job's auth mode needs. The switch is `fugaro update`'s own act and there is no second command, which is the HARD RULE holding.
- **Check 90 has run and passed.** The register's `## Check 90` section records **RUN 2026-10-21: PASSED — TIER A VIABLE**, one informational FAIL, `stream`.
- **The register's 90–99 block is no longer empty.** `docs/gcp-live-checklist.md` now carries **`## Check 90`, 91, 92, 94, 95, 96 and 99** (93, 97 and 98 are not written). *(The draft said "on `main` the register carries no Check 90–99 section for it yet"; that was true on 2026-10-19 and is the first item of [§12](#12-the-hygiene-list-what-goes-stale-on-merge-and-what-collides) that has since been settled.)*

**Consequence for this design: the credentials service is no longer the target this design can only point at.** [§4.4](#44-how-it-holds-a-model-credential-three-candidates-priced) (A) is a built, deployed, owner-run service that a repository opts into, and (B) — a Secret Manager secret mounted into one job — is what every repository that has not opted in still does. The F36 boundary is unchanged and still binding: **this design's service is a sibling that calls it, never a tenant inside it.**

### 3.6 The managed-projects gate

D115 is answered as "decide phase 2 later, after managed-projects' D55–D78 gate", so those decisions bind this design even though none of them is about a mobile feature:

- **D75** — the identity that applies a managed plan is a **dedicated deployer service account**, impersonated per apply, with **no project-level `setIamPolicy`** and no `iam.roles.*`, and resource-level `setIamPolicy`/`actAs` only on resources and accounts it created (the reserved-name-prefix condition), fail-closed, and **nothing on the runs bucket**.
- **D56/D57/D58** — the "this project is managed" authority is a runs-bucket-root marker written **only by an owner-run command**; the bucket root sits outside the jobs' prefix-conditioned grants, and no run-held credential has a write path to it.
- **D72/D74** — what a managed apply may never do (delete or replace without a per-address owner approval recorded at the bucket root, touch another project, org IAM or the billing link, write a secret value, create a billing-admin credential, touch `belong`).
- **D63** — **no hard billing stop**, deliberately, because one "would need an always-on billing-admin credential (finding 25)". Managed projects adopted **no always-on component**, and D71 adds no RTDB node.
- **D78** — the monitoring types are dropped from the managed allowlist and are owner-run.

**Consequence for this design: managed projects deliberately introduced no always-on identity, and this design must not be read as the one it refused.** The `orch` account is not the deployer and cannot impersonate it; it does not hold `setIamPolicy`; it is not a billing identity. Where D63 refused an always-on credential with money-adjacent power, this design keeps that refusal and gets its spend bound from the caps and the kill switch instead — subject to [§3.3](#33-the-budget-envelope)'s condition that the budget is on, and to the plan's **P5.1-Q3**, which makes that condition a requirement for a phone-launchable installation. *(Re-checked 2026-11-16: D55–D78 are as quoted and the deployer's fence is unchanged in `deploy/terraform/gcp/modules/installation/deployer.tf`.)*

## 4. The proposal

### 4.1 Where it runs

**One Cloud Run service per installation, in the installation's own GCP project, `min-instances = 0`, request-based billing, woken by a Cloud Scheduler tick.**

- **Per installation, not shared.** An account is an installation (D114), one Firebase project per installation is the standing rule, `belong` is never touched (F31), and the credentials service took the same shape for the same reasons (D146/D147). A Fugaro-hosted service holding every customer's model credentials and every phone's pairing keys would be the single largest blast radius in the project, and would make "the operator's own project" — the property the whole budget and rules design rests on — meaningless. [Q3](#10-answered-by-the-owner-on-2026-10-19) put the alternative in front of the owner with its cost, and the owner answered it on 2026-10-19 as recommended — **per installation**.
- **A service, because the consumer is event-shaped, not job-shaped** — it holds a lease, answers a prompt, writes a heartbeat. A Cloud Run **Job** on a schedule can do exactly the same work (see [§9](#9-the-alternatives-priced), alternative A3) and is *cheaper*; the service is chosen because it can also answer a request, which is what a synchronous "what is pending?" would need and what the phone's own presence view may eventually want. If the mailbox stays the only path, A3 is the better build and the owner should take it.
- **Scale-to-zero, because "always on" means available, not busy.** The laptop is asleep; the mailbox already tolerates an absent consumer for the whole 72-hour TTL (D118/O5). A scheduler tick gives availability at no idle cost. **What a tick really costs in latency is not a second**: Cloud Scheduler's shortest interval is one minute and it may fire up to that late, so the phone's worst-case wait is a tick plus a cold start, not a cold start alone — [§11](#11-unverified) U1 now says so, and [Q1](#10-answered-by-the-owner-on-2026-10-19) asks for the cadence rather than for the choice, and the owner answered it on 2026-10-19 as recommended — **this service**, with the cadence Q4's answer sets. `min-instances = 1` buys sub-tick latency and a permanently listening socket for a fixed monthly cost per installation; this design does not take it.
- **Cloud Scheduler, because the installation already has the module.** `deploy/terraform/gcp/modules/installation/scheduler.tf` creates the scheduler service account and each repository module grants it run access on that repository's check job — the same shape a tick on the resident orchestrator takes. **The documented free allowance is per billing account, not per installation**, which an owner with several installations has to price ([§11](#11-unverified) U8).
- **The same `fugaro` binary.** The resident orchestrator is the CLI run with flags, not a terminal: `internal/cli/cloud.go`'s `google.DefaultTokenSource` resolves the service account from the metadata server, so the launch path is unchanged and the "one container per run, discarded at the end" boundary `SECURITY.md` relies on is preserved.
- **A new, owner-applied resource.** Following D146's pattern for the credentials service: a new module in the **installation** Terraform root, applied by the owner with the installation's own tooling — never by `fugaro managed apply`, never by an agent, never in a test. [§6](#6-what-it-must-never-do) rule 2 makes that explicit, and [Q7](#10-answered-by-the-owner-on-2026-10-19) asked who deploys it; the owner answered on 2026-10-19 as recommended — **owner-run**, never self-deployed.
- **It is not the only phone-facing service a plan in flight proposes.** The credentials service's F36 boundary — "secrets-only; other always-on features go in sibling services that call it" — is the rule a second phone-facing service would have to sit beside rather than inside; [§12](#12-the-hygiene-list-what-goes-stale-on-merge-and-what-collides) records the proposal that is not in this tree.

**Re-grounded 2026-11-16: the HARD RULE is that `fugaro update` is the whole upgrade, and the plan applies it here.** The bullet above says the module is "applied by the owner with the installation's own tooling", which is what D146's pattern for the credentials service said in 2026-10-19 terms; the owner's requirement is stricter and simpler — **no release may ship an operator step that is another command**. The plan's **P5.1-Q8** therefore recommends that **the module ships in the installation root and `fugaro update` applies it**, with the service created only when the installation opts in, and **P5.1b**'s own text says so: *"The module ships in the installation root, so `fugaro update` applies it: the HARD RULE holds, no second operator command is added, and no installation is asked to run anything twice."* That is the shape the credentials service already took ([§3.5](#35-the-credentials-service-which-has-landed)) and the shape this design is built to.

**Re-grounded 2026-11-22: the writer is plain `fugaro update`, and the opt-in is gone.** The installation root's `orchestrator` variable is written by `fugaro update` with no flag (the owner's ruling of 2026-11-20; `internal/cli`'s `ensureOrchestratorBlock` through `internal/infra`'s `Orchestrator`, in the credentials-service stage, which already moves the service's image onto the release's pin), and the block is the installation's own record that the update wrote it: the account (`fugaro-orch`), the service and the tick are the release's fixed names, the signer is the Firebase root's own account ID, the database is the installation's `budget` block, and the image is the digest pin the credentials service now runs, because `fugaro orchestrator serve` is a subcommand of that same released binary. Nothing is an operator-supplied value and no one types a digest. **The writer runs after the Firebase root**, which is what the token-minter row's ordering needs, and only for an installation whose config records the Firebase backend, the credentials service being the account's caller class: an installation with no credentials service, no Firebase backend or no pinned image is left off with one printed line naming why, and is never an error. **What default-on does about §4.3's signJwt row.** The earlier opt-in's gate (a real terminal, no `--yes`, no coding agent's session) was a confirmation, and Fugaro asks for nothing, so it is not carried over as a gate; what stands in its place is that the grant is still seen and classified. The update's apply is an ordinary apply of the installation root: planned, held to `internal/infra/tf`'s cover (the `fugaroTokenMinter` row on the signer is `orchestratorMinterGrant`'s, narrowed to the budget signer account of this run, and any other target is named), confirmed or gated like every plan of that root, and announced in the line the step prints before it applies (the account, the service, the tick and `iam.serviceAccounts.signJwt` on the budget signer). A coding agent's session never reaches it: the stage is skipped there, as every cloud write is. **The same apply also grants the installation's operators `roles/iam.serviceAccountTokenCreator` on `fugaro-orch`** (orchestrator.tf's `fugaro_orchestrator_token_creator`, the verifier's and the deployer's shape): the daemon runs on an operator's own machine and presents the credentials service with an ID token it mints *as* that account, which only a holder of that role can do, and without the grant the owner would have to make it by hand, a second step. It means an operator can act as `fugaro-orch`, which holds the launcher's grants; **until 0.30.0 the account also held `signJwt` on the budget signer and so did the operators themselves (the token-minter row on the people list), and since 0.30.0 neither does (D3121, LM14)** — so what the grant adds now is the account's other reaches and the pairing key's accessor. It is made to operators and to nobody else, and `internal/infra/tf`'s `deployerTokenCreator` admits it on that account of this run alone. The cost is the one E4 prices, now carried by every installation that updates rather than by those who asked: the always-on account with the launcher's grants exists wherever the update ran — **and since 0.30.0 (D3121) that account no longer holds `signJwt`, so what it may mint is nothing: the cost is a launch button, the pairing key's accessor and the `/proc` reach of [§4.4](#44-how-it-holds-a-model-credential-three-candidates-priced), not the signing key of every identity in the installation** ([§4.5](#45-the-hard-envelope-a-stolen-phone-a-stolen-account-a-poisoned-message-and-a-compromised-orchestrator)'s re-grounding). Once written the block is state: later runs carry it untouched and move only its image onto the release's pin.

### 4.2 What it is made of: a consumer, a launcher, and jobs that are the agent

The resident orchestrator is **two functions and no more**:

1. **The consumer** — reads the inbox, verifies the tag, holds the lease, acts, writes the outbox and the heartbeat. This is the phase-1 consumer of Task P4.1 (`fugaro mailbox`, D113c's answer), running in the cloud instead of on the laptop. **Verifying the tag means holding the key**: `verifyMac` computes the same HMAC the phone computed, and the heartbeat it writes is signed the same way. So the resident orchestrator holds a **third copy of the per-pairing key** — a change to D111/D113b's custody, written out in [§4.5](#45-the-hard-envelope-a-stolen-phone-a-stolen-account-a-poisoned-message-and-a-compromised-orchestrator) E2 and [Q8](#10-answered-by-the-owner-on-2026-10-19) — **answered by the owner on 2026-10-19 as recommended**: the per-installation Secret Manager copy, with [§4.7](#47-revocation) step 2b as its revocation. **The note that records the widening is P5.1e's, not this document's** — D111 and Global Constraint 4 both fix the key in exactly two places, and the change that writes the copy is the change that writes the note ([§10.1](#101-answered-by-the-owner-on-2026-11-14--the-plans-eleven-questions), P5.1-Q2).
2. **The launcher** — for a launch request, takes the launch claim, mints the budget token, and starts the job execution. That is `fugaro run`'s existing path with a service account behind it.

**The agent does not run in the resident service.** A task is a Cloud Run **Job execution** — the container that already exists, with the credential mount it already has, discarded when the run ends. This is the design's central decision, and it is what keeps the credential out of a long-lived process. **It is not, by itself, an exposure bound**, and [§4.4](#44-how-it-holds-a-model-credential-three-candidates-priced) says why.

**Re-grounded 2026-11-16: the launcher is not a thing this design gets to invent.** `internal/orchestrator/` is in the tree ([§3.2](#32-the-launch-path-and-the-launch-claim)) with a **launcher** (`launch.go`'s `Spec`, `SpecOf`, `SpecDigest` and the escalation that follows a launch), a **lease** (`lease.go`, O3/D1232, one daemon per orchestrator id, fenced on an ETag and stamped from `internal/rtdb`'s server clock) and a **state** (`decide/`, `caps.go`, `list.go`). The plan's **P5.1-Q10** rules on the collision: *"the resident orchestrator is its own service (the design's §4.1), **it reuses** `internal/orchestrator/`'s launcher, lease and state rather than rebuilding them, and `docs/central-orchestrator/`'s D1–D26 stay open and unabsorbed — nothing here rules on them."* **So "two functions" is two functions and not two new packages**: the consumer is P4.1's pass run elsewhere, and the launcher is the package that already exists, with `internal/runstore`'s claim and `internal/cli/launch_budget.go`'s mint behind it. What this design adds is the **service** around them, not a third launcher.

**The identity.** One dedicated service account per installation (the `orch` account), created by the installation module in the owner's apply. Its grants are the **launcher's** grants, assembled from resources that already exist, plus the three the design's own functions add — the pairing key's cloud copy ([Q8](#10-answered-by-the-owner-on-2026-10-19)), the consumer's two mailbox writes, and the database read the tick needs — and nothing else:

**Who can read a secret *value* in this installation — the true set, because "the `orch` account alone" is not one.** `secretAccessor` is not the only way to a value, and the row above is a statement about **this account**, not about the installation. The principals that can read the payload of a secret in the installation's project are:

| Principal | How | Can it read the pairing key's cloud copy? |
|---|---|---|

| Any principal holding `secretAccessor` **on that secret** | `deploy/terraform/gcp/modules/workflow/sa.tf` grants it per secret to a job's account; `modules/repo/build.tf` to the build account (the git secret; F3) | Yes, on that secret — so the grant this design proposes for `orch`, and any later grant, each add a reader |
| Anyone who can `setIamPolicy` **on the secret** or on the project | They can grant themselves the accessor role and then read | Yes — **but not `fugaroDeployer`**: `modules/installation/deployer.tf` holds `secretmanager.secrets.setIamPolicy` only under the `fmgd-` **name-prefix condition**, and says of its own role list, on `secretmanager.secrets.update`, "no versions.access, so no value is ever readable" |
| A **launcher** (`fugaroLauncher`) | Names, labels and version counts only | **No** — and `SECURITY.md` says so in the same sentence: "reading a value still needs `secretAccessor`, which only the job and build accounts hold". `roles/secretmanager.viewer` likewise lists versions and never their payload |
| The **`orch` account** | The grant this design proposes | Yes, under [Q8](#10-answered-by-the-owner-on-2026-10-19) — answered by the owner on 2026-10-19 as recommended, the per-installation Secret Manager copy — and this is the only row the earlier draft of this document counted |

**Two things follow, and both are now part of the threat model rather than a footnote.** (1) **Fugaro's own plans never grant a secret's value to a person, and never at project scope except to the credentials service's own account.** `internal/infra/tf/cover.go`'s `grantRules` carries **two** rows for `roles/secretmanager.secretAccessor`, and they say different things: the **project** row (`google_project_iam_member`) is **`toCredentials`** — the credentials service's account alone — and `dynamicSecretsGrant` is the refusal that enforces it, in the file's own words: *"grants a project-wide roles/secretmanager.secretAccessor … which is not the credentials service's own account"* (and even for that account the grant must carry the dynamic secret names condition byte for byte, `gcp.DynamicSecretNamesCondition()`); the **secret** row (`google_secret_manager_secret_iam_member`) is **`toAccounts | toCredentials | toCoordinator`** — job accounts, the credentials account and the installation's coordinator, on a named secret. So **a person is refused on both rows**, **the project as a scope is refused for every principal except the credentials account**, and **the grant this design's `orch` account takes is the secret row, not the project row**. `internal/infra/tf/cover_grants_test.go` pins the negative shapes: a project-wide accessor to a job account, a secret accessor to a person, and a secret accessor to the deployer account. That is a real narrowing, and it is **not** the same claim as "only the orchestrator can read the copy": the basic roles sit above the whole mechanism. (2) **Every principal in the first and third rows can forge what the phone speaks**, because the key is all a forger needs ([§4.5](#45-the-hard-envelope-a-stolen-phone-a-stolen-account-a-poisoned-message-and-a-compromised-orchestrator) E2, E4). In phase 1 the key has exactly two readers (the unlocked phone; any process running as the operator, which is assumption 7 below); **the answer to [Q8](#10-answered-by-the-owner-on-2026-10-19) — the per-installation Secret Manager copy, taken by the owner on 2026-10-19 as recommended — widens that to the installation's Owners and Editors and to every principal the operator later grants `secretAccessor` on that secret**, which is why the option was written that way, and why (b) and (c) were on the table rather than being formalities.

**What it may never do.** The never-list is [§6](#6-what-it-must-never-do); the three that cost the most to get wrong are here:

1. **No IAM.** The account holds no `setIamPolicy` anywhere and no `iam.roles.*` — the D75 fence for the deployer, applied to the resident orchestrator for a different reason: an orchestrator that could grant itself a role could widen its own envelope, and then none of [§4.5](#45-the-hard-envelope-a-stolen-phone-a-stolen-account-a-poisoned-message-and-a-compromised-orchestrator) is true. It also cannot impersonate the deployer, so it cannot reach managed applies indirectly.
2. **No managed applies.** `fugaro managed apply` is the deployer's path (D75/D76), the marker that permits it is written only by an owner-run command (D56/D57), and the bucket root is outside this account's object **write** condition (it may read it, and reading a marker permits nothing). The resident orchestrator cannot become the thing that creates and deletes cloud resources.
3. **No model credential of its own.** Never a mounted model key, never a provider key, never `secretAccessor` on one — see [§4.4](#44-how-it-holds-a-model-credential-three-candidates-priced) for what that does and does not buy.

### 4.4 How it holds a model credential: three candidates, priced

D115's own sentence is "the model credential lives in a secret manager **in the installation's own project**, the service runs as a dedicated identity with a narrow IAM role". The candidates below are what that sentence could mean.

**(A) The credentials service.** The resident orchestrator holds **no** model credential; the runs it launches present their budget identity as a per-job token to a sibling service that swaps in the real credential and forwards. *For:* it is the design that exists for exactly this problem — `docs/credentials-service/reconciliation.md` has thought about the identity (D143), the accounting (D140), the fail-closed halt, and the customer boundary (its F36, off `docs/credentials-service/spec.md`'s "Boundary"); it removes the credential from the container the agent shares, which closes the `/proc` gap `SECURITY.md` lists; and D134 makes the per-job token something the launcher already has. *Against:* it does not hold a `vertex` credential at all (F1), so a Vertex installation is unchanged; and a repository reaches it only where the service can serve that job's auth mode, so the switch is per repository and partial for as long as the bundle does not cover a mode. **Re-grounded 2026-11-16: the draft's first two objections — "plan-only, unscheduled, gated on the budget-token seal; nothing here can depend on it shipping" — are gone.** The service is built, every `fugaro update` deploys it, Check 90 has passed, and a repository opts in through its own root ([§3.5](#35-the-credentials-service-which-has-landed)). What is left of the objection is the Vertex case and the per-repository switch, not the existence of the service.

**(B) A Secret Manager secret mounted into one job.** The mechanism that exists **today**: `infra.SecretMounts` + `modules/workflow/job.tf`'s `secret_env` + `modules/workflow/sa.tf`'s per-secret `secretAccessor`. *For:* shipped, per-job, per-secret, nothing new to invent; the credential never reaches the resident service, because the resident service is not the job. *Against:* the value is in the container the agent shares; Cloud Run mounts it **per job, not per execution** ([U7](#11-unverified)), so one value serves every run of that job; and it is the exact arrangement the credentials service exists to replace. **It is the acceptable interim**, stated as such and with the honesty below, not as a bound. **And it is what every repository the switch has not reached still does** — so (B) is not "the old way" but "the way most installations are on, today".

**(C) Named OAuth tokens per project, one chosen per run.** This is where the brief's own framing needed correcting, and it is worth stating exactly. Today's shipped design is narrow: `docs/named-oauth-tokens/spec.md`'s T1 keeps account names and their allow-lists in the **operator's local config only** (`internal/config/claude_accounts.go`'s `ClaudeAccountNameRE`, `claude_accounts:`, which `Shared()` strips), and since Cloud Run cannot carry a secret reference in an execution override (`named-oauth-tokens.md`'s own U1) the account is really selected by choosing a **job variant at deploy time** — `fugaro run --token NAME` resolves a name at launch against a fixed set of variants. **That is not the end of the story, and describing it as "disqualifying" was wrong.** `docs/project-centric/spec.md` **§7, "OAuth tokens (phase 5)"** designs project-level registration of person-owned tokens — the spec asks for *"personal ownership, individual or project registration, **never repository level**"*, with a project-level token as a reference to an individual's own — and the owner's release ruling R6 of 2026-10-15 moved phases 3, 4, 5 and 6 to 0.9.0 (`docs/project-centric/implementation-plan.md`). **That is a design, not a ruling**: §7's scope question is **D12**'s — this design scopes a person's secret to one GCP project, and **cross-project sharing is out of scope and flagged for the owner** — so the shape is still §7's to settle.

**Where the names would be published is per repository, not project-wide.** The node is `config/policy/repos/$slug`: §7's account axis is an admission, §5 of the same design says "repository-specific parts sit under `$slug` nodes the way `caps/repos/$slug` does", and `docs/credentials-service/reconciliation.md`'s **O4**, which the owner confirmed on 2026-10-17, has `fugaro project policy publish` write each repository's admitted account **names** exactly there for the same reason. (`config/policy/shared` is the project-wide node `docs/project-layer.md` describes; the names are not project-wide, because the admissions are not.) A resident service with no operator-local config can read `config/policy/repos/$slug` with the run's own token — which is exactly what it needs. **Re-grounded 2026-11-16: "and what phase 5 has not yet built" is false.** The axis is built: `internal/projectpolicy/accounts.go` carries **`Account`** (`allow_repos` — the canonical repositories whose runs may use an account's token, derived from the account's own `allow_data_to` or from the profiles that name it), **`RepoAccount`** (the second source, for a repository whose runs are not on a profile job at all) and **`DeriveAccounts`**, and `internal/projectpolicy/version.go`'s Generation 3 comment names the node as *"the node that names Claude accounts"*. So (C) is no longer a future axis this design points at; **it is a shipped one**, and what remains open is the same thing §7 left open: the cross-project sharing question, which is D12's and not this design's. Under that scheme **(C) is not a rival to (B): it is (B) with an account axis** — a secret mounted into the job per name, plus a published mapping the launcher may choose from. What it does **not** solve is the execution-override limit (a per-task choice still needs a variant per name unless the override API changes) and it introduces a question of its own (whose headroom does each name draw on, and who may name one), which is a **new decision**, not a consequence of D115. **Conclusion, unchanged: (B) is the interim, (A) is the target, and (C) is an axis on (B) that is built and whose selection question is the owner's.**

**Recommendation: (B) today, (A) as the switch reaches each repository — and no model credential in the resident process.** Concretely: the resident service holds **no model credential**; the runs it launches take theirs exactly as laptop-launched runs do; as the credentials service's switch reaches a repository, the mount disappears from that repository's job without this design changing. **What that buys, stated precisely, because the earlier draft of this document overstated it:** it buys *where the secret is stored* and *how long a compromise of it lives* — a compromise of the resident process yields no credential that outlives a run. **It does not buy a bound on what the resident orchestrator can reach.** `SECURITY.md` records that *"the launcher holds the job's own credentials"* and that *"A launcher can override a job's environment"*; the `orch` account holds `run.jobs.runWithOverrides` and writes `runs/`, so a compromise of it can launch a run whose agent reads the mounted key out of the runner's `/proc` — the container is disposable, but it does not need to live long. **The true statement, in place of the earlier falsifiable one:**

> **A compromise of the resident orchestrator does not hand the attacker a long-lived key; it hands them a launch button that produces one on demand.** What bounds that is not this design: it is the **caps and the kill switch** (money, through the gateway, when the budget is on — [§3.3](#33-the-budget-envelope)), the **per-key provider credit limit** `SECURITY.md` advises every operator to set, the **runner's admission check** on which repositories a run may touch, and the fact that a job is per-repository rather than per-installation. What does **not** bound it is the rules, the MAC or the launch claim — E4, below. [Q2](#10-answered-by-the-owner-on-2026-10-19) is what the owner answered on 2026-10-19 — **(a)**, no model credential in the resident process — and the argument for (a) is about *lifetime and blast radius per compromise*, not about an envelope.

### 4.5 The hard envelope: a stolen phone, a stolen account, a poisoned message, and a compromised orchestrator

**Four attackers now, not three.** Each is stated as **what it can do**, then **what stops it**, then **what is left**. E1–E3 are the phone-side attackers; **E4 is the cloud-side one this round's review found missing**, and it is the strongest.

**E1 — a stolen, unlocked phone.** It holds the two items D111 allows: the Firebase Auth ID token (`mu` claim) and the per-pairing MAC key.
*Can:* read the four granted families (`config/caps/**`, `spend/$day/**`, `config/kill/**`, its own mailbox — tension (b1)); write its own inbox messages, correctly signed; ack an outbox message it has spoken; **say "confirm"** — the read-back does not stop a thief; and **launch**, which takes **no** confirmation at all (D162, answered against the recommendation, whose own recorded cost is "a misheard sentence starts a paid run; the spend caps bound the damage but do not prevent it").
*Stopped by:* the spend caps and the kill switch, which the database enforces (when the budget is on — [§3.3](#33-the-budget-envelope)) and which no message can raise (`config/caps/**` is owner-run); the D128 amendment's closed verb list, which leaves every other destructive verb refused; the confirmation machine's one-confirmation-one-action rule, its timeout and its "the issuing utterance can never confirm" rule, so a thief cannot turn one "yes" into many actions; the runner's **admission check** (`internal/runner/project.go`'s `admissionCheck` → `internal/access`'s `AdmitRepo` on the project's `allow_repos`, enforced for per-repository jobs too and additionally through the profile for project jobs), so a launch outside the project's allow-list refuses in the runner; and the **time to revoke** — which, **since P6.4 landed, is the time it takes to delete a device node**, not the lifetime of an issued ID token ([§4.7](#47-revocation)).
*Left, honestly:* cancel and merge are not bounded by money — a thief can cancel a job and merge a PR, and the caps do not touch either; §3.5 of the functional-spec reconciliation accepts this as the residual risk D169 takes together with F38, and names the real bound: **the time to revoke.** **And the launch case is worse than the earlier draft of this document said.** A thief can start any task the installation admits; the agent in that run can read the mounted model credential from the runner's `/proc` or push a change to the repository ([§3.4](#34-where-a-model-credential-lives-today)); and then the thief can merge it after confirming his **own** read-back. The caps bound the *spend*; they do not bound what the run's agent can read or write, and they do not bound a merge. **Mitigations, priced as options in [Q9](#10-answered-by-the-owner-on-2026-10-19), answered by the owner on 2026-10-19 as recommended:** a per-device allow-list of repositories a phone may launch for, a rate and cost cap per device, and a restriction that an unconfirmed launch may only run a named safe recipe — with the human gate before a merge ([Q11](#10-answered-by-the-owner-on-2026-10-19)(c), also answered as recommended). **The plan turns Q9's answer into P5.1g's and P5.1-Q11's work, with the values the owner publishes** ([§10.1](#101-answered-by-the-owner-on-2026-11-14--the-plans-eleven-questions)).
*Also, for the phone that is the only human:* [§4.7](#47-revocation) — the owner-run steps that revoke and that set the kill switch need credentials the phone does not have.

**E2 — a stolen phone account** (the Auth uid, without the device: an exfiltrated refresh token, a shared login, a deleted-but-unexpired ID token).
*Can:* read the four families; write inbox messages to its own mailbox, because the rules' `MAILBOX` conjunct is `userClaim && $mb == auth.uid`.
*Stopped by:* it **cannot sign**. Signing needs the pairing key, which an Auth account does not carry: it lives in the phone's platform secure storage (D111, and the laptop's OS keychain for the laptop's side), and — under [Q8](#10-answered-by-the-owner-on-2026-10-19), answered 2026-10-19 — in the cloud copy, whose readers are [§4.3](#43-its-identity-and-what-it-may-never-do)'s table and never an Auth account. An exfiltrated refresh token, a shared login, or a deleted-but-unexpired ID token gives the account the rules' user claim and nothing else. So the consumer refuses every unsigned or mis-signed inbox message before acting (the MAC covers every field and the direction). It cannot write the outbox or the heartbeat — those are `CONSUMER`, not `MAILBOX`. And an outbox message it could inject would not be spoken, because the phone verifies the tag before it speaks a word.
*Left, honestly:* **reads.** A stolen account reads caps, spend and kill state until its Auth user is deleted; the deletion is immediate for new tokens, and an already-issued ID token's remaining lifetime is [U3](#11-unverified) — **and check 101, which measures it, is written in the register now** (it was "proposed, P6.11" when the draft was written). Tension (b1) already shrank what that exposes to numbers and states with no run titles and no repositories.
**And the sentence this document used to get wrong:** *"the key never left the device" is true of the phone and the laptop, and false the day a cloud consumer exists.* `macOf` and `verifyMac` are one symmetric HMAC — the verifier holds what the signer holds — and the heartbeat the consumer writes carries a `mac` too (`HEARTBEAT_REQUIRED`), so a cloud consumer must hold the key. **D111 and D113b/tension (b2) fix the key in exactly two places** — "the phone's platform secure storage … and the laptop's OS keychain, with the consumer's settings holding only the keychain item's name". Phase 2 needs a **third copy in the cloud**. **The owner answered [Q8](#10-answered-by-the-owner-on-2026-10-19) on 2026-10-19 as recommended: the copy goes in Secret Manager, so the key now exists in three places**, and [§4.7](#47-revocation) says what revocation then has to reach. **The note D111 and Global Constraint 4 are owed for that widening is P5.1e's to write, not this document's** — the design states the widening and the task that records it.

**E3 — a poisoned mailbox message** (an attacker who can *write* a node the consumer reads: a project owner/editor, an admin service account, or any launcher holding a minted token — `TestMailboxResidualMintedTokenNeedsTheDeviceNode` records that the rules cannot tell a minted `mc` token from the real consumer; what the device node does now is deny a token whose `mu` names a device that has been deleted).
*Can:* write into the mailbox nodes the rules cannot distinguish; today it can even write as the consumer.
*Stopped by:* the pairing MAC, verified **before anything else and before any action** (P6.7's rule), over every field including the direction — so a message reflected from the outbox into the inbox, or re-targeted at another run or PR, fails; the replay windows (6 hours for commands, 72 hours for prompt answers) and the ledger keyed `(sender, id)`; the action-id and confirmation-id dedupe, which survives a restart, so a signed record re-sent under a new message id is refused; and D169's rule that a destructive prompt is answered only by a MAC-verified **action record**, never by free text and never by a plain `answer`.
*Left, honestly:* **the rules now require the field** — `"mac": { ".validate": "MACOK" }` on the inbox, the outbox and the heartbeat, with `TestMailboxRulesAgreeWithTheSharedSchema` pinning the schema's own five required fields — **and Go verifies it** (`internal/mailbox/mac.go`'s `VerifyMAC`). What is still missing is the **consumer that calls it**: `internal/cli/mailbox.go` does not exist and `fugaro mailbox` is not a registered command (P4.1). **So E3's window is now "until P4.1 and P6.7 ship", not "until P6.4/P6.7 ship"** — and that is still the strongest reason this design does not recommend a phase 2 before phase 1's consumer exists. **An attacker with the key is no longer E3 but E4.**

**E4 — a compromised resident orchestrator.** *This attacker is new in this revision, and it is the one the design has to be honest about.* The `orch` account holds `signJwt` on the signer ([§4.3](#43-its-identity-and-what-it-may-never-do)), so a compromise of the process — a dependency, an injected error path, a stolen service-account token from the metadata server — reaches the **signing key for every identity in the installation**.
*Can:* mint a custom token for **any uid**: as `mc == $mb`, it is the consumer and may write the outbox and the heartbeat; as `mu == <a paired uid>`, it is the phone and passes `USER` and `MAILBOX` — **and, since P6.4, passing `USER` needs the device node for that uid to exist, which the same process can mint a token for but cannot create, because writing `config/admin/devices/**` is `roles/firebasedatabase.admin` and not this account's** — so it may write the phone's own inbox and read the four families; with `fp`/`fx`/`fs`/`fr` set, it is any repository's run. **And per [Q8](#10-answered-by-the-owner-on-2026-10-19), answered 2026-10-19, it also holds the pairing key** (whose other readers are [§4.3](#43-its-identity-and-what-it-may-never-do)'s table: any project Owner or Editor reaches the copy too, and reaches it without compromising this process at all), so what it forges is not merely *accepted* by the rules, it is **MAC-valid**: forged action records with confirmations (cancel, merge, confirm), and forged outbox text the phone will speak aloud. On top of that, if it was added through `var.launchers` it holds `roles/firebasedatabase.viewer` and reads **every mailbox in the installation** past the rules ([§4.3](#43-its-identity-and-what-it-may-never-do)); and through `runWithOverrides` it can launch a job that reads a model credential out of `/proc` ([§4.4](#44-how-it-holds-a-model-credential-three-candidates-priced)).
*Stopped by:* **the caps and the kill switch, and only for money.** Every token it mints is still subject to the rules, so a run it launches cannot write an over-cap ledger and the kill switch refuses the next lease — *when the budget is on and enforcing* ([§3.3](#33-the-budget-envelope)), which the plan's **P5.1-Q3** makes a requirement of a phone-launchable installation. The **confirmation machine's** one-action-per-confirmation and its target resolution still apply to the records it forges, but it can forge the confirmation too. Nothing else in this design stops it: **the MAC does not** (it holds the key), **the rules do not** (it can be the consumer and the phone), **the launch claim does not** (it holds the launcher's grants), and **D169's "typed action records executed by the consumer" does not** (it *is* the consumer). `SECURITY.md` already records this shape for every launcher — *"Any launcher can mint a budget identity for any repository … a launcher credential is budget write access up to the caps for every repository"* — and D169's own row names the phone case: a launcher *"could sign in as a paired `m~` uid, pass the device-node conjunct, and write an action record with an invented confirmation that the consumer would run under the operator's `gh` login"* — with the MAC as the defence. **Phase 2 is the design that puts a launcher's grants and the MAC key in one process.** That is the price of the mailbox's other side living in the cloud, it is not a defect of this document, and it is the strongest argument for the option [Q8](#10-answered-by-the-owner-on-2026-10-19) did **not** take — (b), an asymmetric tag, a verifier that holds no signing key — and for [Q3](#10-answered-by-the-owner-on-2026-10-19)'s "bring phase 1's consumer to the cloud at all". *(Re-grounded 2026-11-16: the device node narrows E4 by one step and does not bound it — a compromised orchestrator can mint a `mu` token for a uid whose device node exists, but it cannot create the node, and it cannot stop the owner deleting one. That is a real narrowing and it is the only one the tree has added.)*
*Left, honestly:* a compromise of the resident orchestrator is **the compromise of the installation's phase-2 control plane**, bounded in money and in time-to-revoke-the-service-account, and not bounded in what it can ask the phone or the operator to believe. The mitigations that help are the ones that shrink what it holds: no model credential ([§4.4](#44-how-it-holds-a-model-credential-three-candidates-priced)), **never `var.launchers`** ([§4.3](#43-its-identity-and-what-it-may-never-do)), the fewest possible grants, an asymmetric tag, which is the option [Q8](#10-answered-by-the-owner-on-2026-10-19) did not take, and the same service-account hygiene as any always-on identity.

**Re-grounded 2026-11-27 (LM16, D3121/D3125, O14).** The row E4 is built on is gone: since 0.30.0 the credentials service is the only principal holding `iam.serviceAccounts.signJwt` on the runs' signer account, and every launcher — this account included — asks the issuer for a one-time ticket instead ([§4.3](#43-its-identity-and-what-it-may-never-do)). What that leaves of E4 is smaller and precisely statable: the orchestrator can no longer mint `mc` or `mu`, so the whole "it *is* the consumer and the phone" arm of *Can* is closed, and what remains is a compromised process with the launcher's other grants — a launch button, `runWithOverrides` and its `/proc` reach, the pairing key under [Q8](#10-answered-by-the-owner-on-2026-10-19) and the MAC-valid forgeries that follow — plus, since 0.30.0, one more: **the ticket it holds for a launch it recorded but never started**. Its asks are narrowed to a recorded, unstarted attempt of a repository and carry no context repos (D3136), on the design's own §3.2 path. **And the residual this record adds, which no route can close today (O14):** §4.2's consumer and §4.6's third question are satisfied by a minted `mc` claim, and the resident orchestrator's copy of that claim is one **it would have minted through its own `signJwt`** — no code mints `mc` the way this design assumed, and after D3125 no route can, so a design that still wants the resident orchestrator to *be* the consumer needs a route the plan has not written. Whether this design needs one is `docs/launcher-does-not-mint/`'s to answer, not this document's.

**What bounds all four, and is worth saying once: the envelope is not the MAC.** The MAC decides **who may ask**; the caps and the kill switch decide **how much can be spent**; and the confirmation machine decides **which changes are allowed at all**. A design that relied on the MAC for spend would be relying on the phone's own key custody; this one does not — and E4 is the case where the MAC's custody is the cloud's and the caps are the only thing left.

**Two things the attacker list does not cover, said here rather than implied.** **(i) A free-text message.** D169's residual risk is that "a free-text message still reaches an orchestrator that can run `gh pr merge` or `fugaro cancel` … itself (Voice F38)", and the owner **accepted** it. In phase 1 that orchestrator is the operator's agent on the operator's machine; in phase 2 there is no operator's machine, so a free-text inbox message has to be handed to **a launched run's agent**, which is a departure from D115's framing and is written down here rather than discovered later ([§4.8](#48-approvals-when-the-phone-is-the-only-human)). **The plan's P5.1-Q4 closes it for the first release: free text is refused** ([§10.1](#101-answered-by-the-owner-on-2026-11-14--the-plans-eleven-questions)). **(ii) An installation with the budget off.** [§3.3](#33-the-budget-envelope) — on such an installation the caps are not read at all, so every sentence above that leans on them is conditional, and the only remaining bound is the provider account's own credit limit. **P5.1-Q3 makes "the budget is on and enforcing" a precondition of a phone-launchable installation**, so this case is refused rather than accepted.

### 4.6 How it authenticates the phone

Two questions are answered by two different mechanisms, and conflating them is the common mistake.

**"Is this phone a paired device of this installation?"** — the **rules**, through the user claim **and the device node**. `internal/budget/rules/rules.go`'s `userClaim` is `auth != null && auth.token.mu != null && auth.token.mu == auth.uid && root.child('config/admin/devices').child(auth.uid).exists()` — **the device node is a conjunct of `userClaim` itself since generation 3 (P6.4, merged as #601)**, and `USER`'s `case` returns `userClaim` unchanged, so it is a conjunct of `USER` too; that is the whole point of the node. The mailbox's own nodes use `MAILBOX` (`userClaim && $mb == auth.uid`), and `USER` carries **three** of tension (b1)'s four families — `config/caps/**`, `spend/$day/**` and `config/kill/**` — because it takes no `$mb`: its own comment in `rules.go` says it "names no mailbox, so it cannot be used to reach one". The fourth family, the phone's own mailbox, is the separate `.read: "MAILBOX"` the mailbox nodes carry. The phone signs in with a custom token minted at pairing (D165's two tokens, T5's "no public sign-in provider"), so the `mu` claim is carried in its ID token. **This is what fences reads and the ack, and it is the only part of the fence the database enforces** — and it fences nothing against the `orch` account itself, which can mint `mu` for any uid (E4).

**"Is this *message* really from that phone?"** — the **MAC**, verified by the consumer (and by the phone for the outbox and the heartbeat). `shared/mailbox-schema/mac.js` over `canonicalBytes(record, direction)`, one per-pairing key, **symmetric** — the consumer holds the same key, which is the custody change [Q8](#10-answered-by-the-owner-on-2026-10-19) settled on 2026-10-19. **The Go half is built** (`internal/mailbox/mac.go`'s `VerifyMAC`, [§1.2](#12-the-direction-bound-mac-exists-in-javascript-and-in-go--the-consumer-that-would-verify-it-does-not)); what does not exist is the pass that calls it (P4.1), which is why verification is still "in the consumer" and the consumer is still a task.

**The device node is now in this tree, and it answers a third question.** `config/admin/devices/$uid` is **P6.4's node and it is merged** ([§1.1](#11-the-draft-said-this-tree-had-no-rules-generation-3-and-no-device-node--re-grounded-2026-11-16)); the draft said "the device node … is **P6.4's proposal, not in this tree** … Until it lands, 'is this phone still allowed?' is answered by the Auth user's existence and the pairing key's existence, not by a node the rules consult." **It has landed, so it is consulted**: deleting the node denies the next read that carries `USER`, immediately, which is [§4.7](#47-revocation)'s step 1. What it does not do is bound E4 ([§4.5](#45-the-hard-envelope-a-stolen-phone-a-stolen-account-a-poisoned-message-and-a-compromised-orchestrator)), because the account that can mint a `mu` token cannot write the node and cannot keep a deleted one alive.

**The cloud consumer's own identity is fenced, and that is new — with a limit.** The laptop consumer writes as the operator's admin credential, which bypasses the rules (D113b's honesty note). The resident orchestrator writes as a service account, so it must satisfy `CONSUMER` (`auth.token.mc == $mb`) to write the outbox and the heartbeat at all: **the phase-2 consumer is the first mailbox writer the rules can hold to "the outbox and the heartbeat and nothing else"** — a property worth naming, because it is the one place where moving to the cloud *strengthens* the fence rather than widening it. **The limit, which the earlier draft of this document omitted:** what the rules fence is *that identity's* writes, not its ability to *be* another one. Holding `signJwt`, the same process could mint `mc` for any mailbox and `mu` for any paired uid, so the fence constrained a **stolen token**, not a **compromised process** (E4). **Re-grounded 2026-11-27 (LM16, D3121):** the row is the credentials service's alone since 0.30.0, so a compromised resident orchestrator can no longer mint either claim — see [§4.5](#45-the-hard-envelope-a-stolen-phone-a-stolen-account-a-poisoned-message-and-a-compromised-orchestrator)'s re-grounding for what the `mc` claim it would need now costs (O14).

### 4.7 Revocation

**Today (generation 3 and up: the device node is in the tree).** Four steps, in order, and **the owner's ruling is that the owner runs them** (D166):

1. **Delete the device node** `config/admin/devices/$uid`. **This is the immediate half**, and it is the mechanism P6.4 built: `USER` carries the node as a conjunct, so the next read that carries the user claim is denied, and `fugaro pair revoke` is the command that deletes it (`internal/cli/pair.go`'s `newPairRevokeCmd`, with `internal/budget/token/device.go`). It needs `roles/firebasedatabase.admin`, which is `admins` and `budget_admins` — **not the phone**.
2. **Delete the Firebase Auth user** for the pairing. Immediate for new sign-ins; an already-issued ID token remains valid until its `exp`, which is [U3](#11-unverified) here and **live check 101, which is written in the register and not run**. Step 1 is what covers that window for reads and writes; step 2 is what stops the account signing in again.
3. **Delete the laptop keychain item** for the pairing's key. The consumer is configured with the item's **name**, so this is what makes every message the phone signs stop verifying.
4. **The consumer drops the pairing's pending prompts**, delivering each one's safe answer once, and deletes its outbox messages.
5. **Re-pair** if the phone is replaced: **`fugaro pair`** — **built, merged as #2572**: `internal/cli/pair.go` registers `newPairCmd`, `newPairLsCmd` and `newPairRevokeCmd` in `internal/cli/root.go`, and `internal/budget/token/device.go` writes the device node — issues a new device uid and a new key, and the old pairing is revoked. *(The draft's step 4 read "`fugaro pair` — planned, not built: `internal/cli/root.go` registers no such command, and Task P6.6 is where it is proposed". That was true on 2026-10-19 and is the correction [§0.2](#02-corrections-to-the-draft-dated-2026-11-16) lists; the plan's P5.1 section records the same correction, and says **P5.1e's copy is written by a command that exists**.)*

**Phase 2 adds a step, and it is not optional:** with a cloud consumer, **step 3 no longer reaches the secret**. The laptop's keychain item and the cloud copy are two copies, and deleting one leaves the other verifying perfectly. Revocation therefore gains

> **2b. Delete the cloud copy of the pairing key** — the Secret Manager version the resident orchestrator reads, so that the pairing's messages stop verifying **in the cloud** as well as on the laptop. Rotating the value is not enough unless the old version is destroyed; disabling the version is not enough if the service is granted `versions.access` on the parent. **And deleting it un-reads nothing**: every principal in [§4.3](#43-its-identity-and-what-it-may-never-do)'s reader set who held the value keeps it — the step ends the *service's* ability to verify and to forge, not a reader's.

This is what [Q8](#10-answered-by-the-owner-on-2026-10-19) settled — where the copy lives, who may read it, and what the revocation step is — answered by the owner on 2026-10-19 as recommended, and it is the direct answer to the earlier draft's sentence *"the pairing key is held by the phone and the keychain — not by the service"*, which was **false for any design with a cloud consumer**. **The step is written as a command's behaviour by P5.1e** (`fugaro pair revoke` deleting the copy, the plan's own Files list for it), and **the note D111 and Global Constraint 4 are owed for the third copy is P5.1e's too** ([§10.1](#101-answered-by-the-owner-on-2026-11-14--the-plans-eleven-questions), P5.1-Q2): this design says the copy exists and says who writes the note; it does not write it.

**What the device node does to revocation, since it landed.** The draft's paragraph here read "*After P6.4 lands* (proposed), step 1 becomes 'delete the device node', which the rules consult — immediate for **reads and writes** alike, rather than only for new sign-ins." **That is now the state, not a forecast**: the node is step 1 above, and the Auth user's deletion is the step that covers what the node does not.

**What revocation cannot do, stated plainly.** A launch already claimed continues: the budget token was minted and the job started before the phone was revoked, and the caps — not the revocation — bound what that run spends.

**And the phone is usually not the one who can do any of this.** Steps 1, 2, 2b and the kill switch need credentials the phone does not hold: deleting the device node needs `roles/firebasedatabase.admin`, granted to `admins` and `budget_admins` only; deleting an Auth user needs `roles/firebaseauth.admin`, whose only Terraform-granted holder is the history job's account (`deploy/terraform/gcp/modules/firebase/iam.tf`'s `history_auth`, as G13 records); and `config/kill/**` and `config/caps/**` are owner-run writes, by ruling. **So when the phone is the only human and the laptop is asleep, the phone cannot revoke a pairing, cannot set the kill switch and cannot raise or lower a cap.** That is not a gap this document can close by making the phone an admin — it is the design question [Q10](#10-answered-by-the-owner-on-2026-10-19), which the owner answered on 2026-10-19 as recommended: a phone-side **request** that raises a prompt, not a phone-writable kill switch.

**What the resident orchestrator's death changes about revocation: nothing about the credentials, and something about the copy.** Revoking the key works whether or not the service is running, and the service cannot resurrect a revoked pairing by redeploying itself — but a copy it still holds is a copy until step 2b is run, which is exactly why 2b is written down.

### 4.8 Approvals when the phone is the only human

Phase 1's model assumes a human at a laptop for the things the phone will not do: writes to `config/caps/**` and `config/kill/**`, rules deploys, secret changes, managed applies, and revoking a pairing ([§4.7](#47-revocation)). **When the phone is the only human, "someone at the laptop" is not a control — it is a latency.** So the envelope has to be mechanical, and the pieces are these:

- **The spoken-confirmation machine** (Phase 6 P6.2, approved and unbuilt; `shared/confirm/index.js` is merged with tests and no consumer): a read-back of the **resolved target**, the fixed short phrase of Voice D47's reading, a timeout on an **injected** clock, one confirmation authorises **exactly one** action, and the utterance that issues a command can never confirm it.
- **Confirm targets, and why they are the whole argument.** A target is a run id, or a repository and a pull-request number, or — for a merge — that plus the PR head SHA (§3.5 of the functional-spec reconciliation). **An ambiguous target cannot be read back and therefore cannot be confirmed.** That is what stops a mishearing from becoming a merge: the machine has nothing to read back, so it refuses rather than guesses.
- **The consumer re-validates.** The phone's read-back is what the human heard; the consumer's own check is what actually runs — a MAC-verified **action record**, inside the command window, against a target that still exists, once per action id. The confirmation **timeout** is checked on the phone, where the pending state lives; the **windows** are checked on the consumer, where they can be enforced (commands 6 hours, prompt answers at the TTL).
- **The only-human rules this design adds.** (1) The resident orchestrator **never** synthesizes an owner confirmation and never treats its own prompt as answered — an unanswered prompt expires at the TTL and takes the **non-destructive** answer (D168 as amended). This is a **rule in the service's own code, not a mechanism** — E4 is the attacker for whom it does not hold, and the document says so rather than listing it as a fence. (2) It never escalates its own authority: no IAM, no caps, no kill, no self-deploy ([§6](#6-what-it-must-never-do)). (3) Launches take **no** confirmation (D162, answered against the recommendation) but do take the command window and **are** bounded by the caps — a launch is the one action the phone can take that spends money, and money is the one thing the caps bound mechanically, **when the budget is on**.
- **What happens to free text, which nothing above says.** D169's answer — typed action records executed by the consumer, with the agent told never to cancel or merge on voice-originated text, and the residual risk accepted (Voice F38) — was written for a consumer **beside the operator's agent**. With the agent in a launched container and no operator's machine, a free-text inbox message has to be passed to that run's agent, whose "never cancel or merge on voice-originated text" is a system prompt and not a fence. **This design adopts D169's shape unchanged and flags the departure**; **the plan closes it for the first phase-2 release: P5.1-Q4 recommends that the release carries launch, cancel, prompt answers and the merge-as-a-prompt and refuses free text**, with the app saying so ([§10.1](#101-answered-by-the-owner-on-2026-11-14--the-plans-eleven-questions)). [Q9](#10-answered-by-the-owner-on-2026-10-19), answered by the owner on 2026-10-19 as recommended, is what bounds the rest: a per-device allow-list, a per-device rate and cost cap, and a named safe recipe for an unconfirmed launch.
- **What merges, in the cloud.** D169's merge is *"`gh pr merge <n> --repo <owner/name>` by the consumer under the operator's own `gh` login"* — an identity that does not exist on a Cloud Run service. A resident orchestrator has no operator's `gh` login, so "a merge in phase 2" needs an identity of its own (a GitHub App installation, or a token in Secret Manager, or no merge at all). **The owner answered [Q11](#10-answered-by-the-owner-on-2026-10-19) on 2026-10-19 as recommended: no merge in the cloud for the first phase-2 release** — the merge record becomes a prompt the phone raises and a human merges, so phase 2 is read-only on every repository until a later ruling adds the App. **The plan's P5.1-Q5 records the same answer for the build**: ship (c), and take (a) as its own decision when the owner wants merges from the phone.
- **What is not solvable here.** If the phone is the only human and the phone is stolen, the thief is the human ([§4.5](#45-the-hard-envelope-a-stolen-phone-a-stolen-account-a-poisoned-message-and-a-compromised-orchestrator) E1). This design does not pretend otherwise; it bounds it by time-to-revoke, by the caps, and — on [Q9](#10-answered-by-the-owner-on-2026-10-19)'s answer — by what a phone is allowed to launch and what a merge still requires.

### 4.9 Failure modes

| Failure | What happens | What bounds it |
|---|---|---|
| **The resident orchestrator is down** | Nothing is lost. Messages sit in the mailbox for the whole TTL (72 hours, D118/O5); the phone's presence view shows offline from the heartbeat's age (`shared/presence`); a prompt waits. The laptop's `fugaro mailbox` can consume in the meantime. | The TTL, the lease, and the phone's honest "offline" state. |
| **Two consumers act on one message** (the laptop wakes while the resident orchestrator ticks) | At most one acts. Three fences, in order: the mailbox's ledger keyed `(sender, id)` (`shared/mailbox`'s `step`); the consumer lease (10-minute TTL, `already-claimed`, `shared/lease` and `internal/mailbox/lease.go`); and — for a launch — the launch claim itself. | The lease is the mailbox's fence; the launch claim is the run's. |
| **A duplicated launch** | One execution. `internal/runstore/launch.go`'s `Claim` is a create-if-absent object under the run's prefix; only the holder mints (`mintBudgetToken` runs after the claim loop in `internal/cli/run.go`); a second launcher's mint either fails the claim or, at worst, writes a token no execution will take, which `dropBudgetToken` removes and the lifecycle rule deletes within a day. | F4's claim, and the mint-after-claim ordering. |
| **A replayed message** | Refused. Commands older than 6 hours are `REPLAY`; prompt answers past the TTL are `EXPIRED`; a signed record re-sent under a **new** id is refused by action-id dedupe; the ledger survives a restart and is retained at least the TTL plus one sweep interval. The id is inside the MAC, so it cannot be changed without the key. | The windows, the ledger, and the tag. |
| **The resident orchestrator dies between the claim and the job start** | The claim goes stale after 10 minutes and a later tick takes it over by `ReplaceIf` on the read generation; an untaken budget token object is removed by `dropBudgetToken` or by the bucket's one-day lifecycle rule. | `ClaimTTL`, the generation precondition, the lifecycle rule. |
| **The clock differs** | A phone more than 5 minutes ahead of the consumer is refused (`DEFAULT_FUTURE_TOLERANCE_MS`, `MAX_CLOCK_SKEW`); windows are computed on the consumer's clock, so a phone ahead extends a window by the skew and a phone behind gets refusals early. | The tolerance band, and **check 84**, which measures the real skew — **it is one of the ten numbers this plan reserved (80–89) and it is written in the plan's own check table, not in the register** ([§7](#7-the-checks-it-would-need)). |
| **The service is older than the deployed rules** | It refuses rather than misreading — **at the deploy and in the run, not in `doctor`**. The rules marker carries the generation (`internal/projectpolicy/version.go`'s `RulesVersion`, `PathRulesMarker`), and the two places that see the skew refuse it: `internal/infra/firebasedb.go`'s `Check` refuses a marker **above** the binary's version outright — *"the deployed security rules are generation %d … and this Fugaro's are generation %d … Upgrade Fugaro first ('brew upgrade dimipaun/tap/fugaro'), then run 'fugaro update --firebase-project %s' again with the newer binary; 'fugaro doctor' reports this as policy-rules-skew"* — and its own comment says why the refusal is there and not in doctor: *"A warning the deploy path then ignores is not a boundary, so the deploy path refuses"*. | **The service is deployed but the module is wrong** (no signJwt, no job_runner on a job) | Launches fail at the claim or the mint, and **no run starts** — the failure is before any spend. ### 4.10 Cost model

**Idle cost.** With `min-instances = 0` and request-based billing, the service bills nothing between ticks. The idle cost is therefore the tick's own work plus the fixed pieces: **Cloud Scheduler** (a handful of jobs — **and the free allowance is per billing account, not per installation**, [U8](#11-unverified)), **RTDB** reads and the heartbeat writes whose volume D117 asks to measure (check 84's interval), **the runs bucket** and its lifecycle rules, **Artifact Registry** storage for the image, **Secret Manager** versions — including the pairing-key copy [Q8](#10-answered-by-the-owner-on-2026-10-19) adds — and **Cloud Run Jobs**, which cost nothing while not running. `min-instances = 1` would replace "nothing" with a fixed monthly charge per installation — the price of sub-tick latency — and is not taken here.

**Per-task cost.** Three parts: (1) **the run's compute**, a Cloud Run Job execution billed per vCPU-second and GiB-second (the tree's one measured figure is a different backend — check 57a-5 records a 143-second `e2-standard-4` window at about $0.0053 on the VM backend, and it is cited as an order of magnitude, not as a price for this); (2) **the model spend**, which is bounded by the per-run and daily caps and by the kill switch **when the budget is on** ([§3.3](#33-the-budget-envelope)), and by the provider account's own limit — `SECURITY.md`'s standing advice; (3) **the resident orchestrator's own request time**, a few hundred milliseconds of a 1-vCPU instance per tick, plus the launch.

**Prices are not in this document, deliberately.** The repository's own precedent is to fetch them when a plan commits (`docs/plans/2026-09-27-m4-gcp-backend.md` fetches the Cloud Run pricing page before committing), and a number invented here would be a number a later reader would trust. [§11](#11-unverified) lists the figures a plan must measure.

## 5. The threat model, stated once

**What is assumed.** The attacker model is `SECURITY.md`'s, plus the mailbox's:

1. **The repository and the task text are trusted**, and anyone who can push to the repository, launch a run, or is listed in `followup.trusted` can steer an agent that holds the credentials that job's service account may hold (`SECURITY.md`, "The assumption"). Fugaro remains not a sandbox for code you would not run on a developer's laptop.
2. **An agent inside a run is hostile-capable**: it writes code, reads the job's environment, reaches the metadata server, and shares the container and user with the runner, so it can read the runner's `/proc` — including a mounted model credential and the GitHub App private key (`SECURITY.md`, "Known limits").
3. **A launcher is trusted to launch, and that is already a wide power**: a launcher may launch the repositories its launch scope admits, override a job's environment, and write `runs/` for every repository (`SECURITY.md`, "What is not on by default" and "Known limits"). **Re-grounded 2026-11-27 (LM16, D3121): what a launcher may no longer do is mint** — "any launcher can mint a budget identity for any repository" is the pre-0.30.0 state this document was written against, and since 0.30.0 the credentials service holds the signing row alone while a launch asks the issuer for a one-time ticket ([§4.3](#43-its-identity-and-what-it-may-never-do)). This design does not narrow the rest of it; it inherits it, and [§4.5](#45-the-hard-envelope-a-stolen-phone-a-stolen-account-a-poisoned-message-and-a-compromised-orchestrator) E4 is what inheriting it costs when the launcher is an always-on process.
4. **Network egress is unrestricted** and the caps bound only traffic that goes through the gateway (`SECURITY.md`).
5. **The phone is an untrusted holder of exactly two items** (D111): an Auth ID token and a per-pairing MAC key. Anyone with the unlocked device has them; anyone with the Auth account has the first.
6. **Any project owner/editor or admin service account can write the mailbox nodes**, and a minted `mc` token is indistinguishable from the real consumer today (`TestMailboxResidualMintedTokenNeedsTheDeviceNode`) — and a launcher could mint one, G13 and D169's shape, which held until 0.30.0 took the row off launchers (D3121). **The device node denies a token whose uid has been revoked; it does not distinguish a minted `mc` from the real consumer** ([§1.1](#11-the-draft-said-this-tree-had-no-rules-generation-3-and-no-device-node--re-grounded-2026-11-16)).
7. **The operator's own machine is not a boundary**: the agent a message eventually reaches runs with the operator's identity on the operator's machine (Voice F38's accepted risk), and the keychain item is readable by any process running as that operator — that agent included.
8. **The budget may be off.** `SECURITY.md`: budget mode defaults to off; with it off there is no gateway, no cap node is read, and the only limit is the provider account's own ([§3.3](#33-the-budget-envelope)). **A phone-launchable installation is the exception this design asks for: P5.1-Q3 requires the budget published, on and enforcing, before a phone may launch.**
9. **A resident orchestrator, if built, holds the launcher's grants, the pairing key, and (until 0.30.0 took the row: D3121) `signJwt`** — the combination E4 prices, with [§4.5](#45-the-hard-envelope-a-stolen-phone-a-stolen-account-a-poisoned-message-and-a-compromised-orchestrator)'s re-grounding for what is left of it — and while it held the row it was the only actor in this design whose compromise reached every identity in the installation at once. **The key itself has more readers than that actor**: under [Q8](#10-answered-by-the-owner-on-2026-10-19)'s answer its cloud copy sits in the installation's project, where the basic Owner and Editor roles read any secret's value past the secret's own policy, so a project Owner can forge a MAC-valid message **without** compromising the orchestrator at all ([§4.3](#43-its-identity-and-what-it-may-never-do)).
10. **No live cloud was read for this document** and no `belong` installation was looked up (F31).

**What this design does not defend against, and says so.** A project-level owner credential (out of `SECURITY.md`'s scope entirely); an agent spending outside the gateway with a real key it read from `/proc` (the standing OEM limit — set a credit limit on every key); a launcher's existing write reach over `runs/`; a compromise of the owner's laptop that reads the pairing key out of the OS keychain; a compromised GCP project itself. **And the two this design newly owns, both written as attackers rather than as asides:** a compromised resident orchestrator (E4), which the MAC does not stop and the rules do not stop, and an installation with the budget off, on which no cap sentence in this document is true.

## 6. What it must never do

1. **No IAM.** Never `setIamPolicy` on the project or on any resource; never `iam.roles.*`; never an `actAs` on the deployer service account; never a new service account, key or binding. Its grants arrive with the owner's apply and change only with another owner's apply.
2. **No managed applies.** Never `fugaro managed apply`, never import the deployer, never write the runs-bucket-root marker that permits one (D56/D57), never write `fugaro/allow-delete.json` (D74) — the bucket root is outside its object **write** condition.
3. **No destructive commands.** Never delete a branch, close a PR, run `fugaro allow-delete`, write `config/kill/**` or `config/caps/**`, run `fugaro budget`'s writes, `fugaro secrets set`/`rm`, `fugaro init --firebase` (a rules deploy), or `fugaro restore`. The D128 amendment's three verbs are allowed **only** through the spoken confirmation, and this list is not widened. **And never write `config/admin/devices/**`**: the device node is the revocation mechanism, and an account that could create one could un-revoke itself ([§4.5](#45-the-hard-envelope-a-stolen-phone-a-stolen-account-a-poisoned-message-and-a-compromised-orchestrator) E4).
4. **No model credential of its own, ever.** It launches runs; the runs hold the credential, in the container that dies with them, until the credentials service takes it away from them too. **This bounds the secret's lifetime, not the orchestrator's reach** — [§4.4](#44-how-it-holds-a-model-credential-three-candidates-priced).
5. **Never read a secret value, and never hold the pairing key but the one copy the tag forces.** `secretmanager.secrets.list`/`versions.list` and nothing more — no `secretAccessor` on model, git or App secrets. The pairing key is the exception the tag forces, and it was **not** this design's to grant: **the owner answered [Q8](#10-answered-by-the-owner-on-2026-10-19) on 2026-10-19 as recommended** — a cloud consumer needs the key, the copy lives in Secret Manager, and [§4.7](#47-revocation) 2b is its revocation. **And "the orchestrator holds it" is never the whole reader set** — a Secret Manager value is readable by the project's Owners and Editors whatever its own policy says, so [§4.3](#43-its-identity-and-what-it-may-never-do) lists every principal, not this account alone.
6. **Never `belong`.** Not a target, not a fixture, not a name in a test (F31).
7. **Never act on an unverified message.** No MAC, no action: not for a `message`, not for an `answer`, not for an action record, and never for free text aimed at a destructive prompt. **This is a rule in the consumer's own code**: against E4, which holds the key, it is not a fence — which is why it is paired with the never-list's least-privilege rules rather than trusted alone.
8. **Never answer its own prompt, and never synthesize a confirmation.** Also a code promise, not a mechanism: an attacker who *is* the process can do both, and [§4.5](#45-the-hard-envelope-a-stolen-phone-a-stolen-account-a-poisoned-message-and-a-compromised-orchestrator) E4 says so.
9. **Never widen itself.** No self-deploy, no new revision from a phone request, no Terraform, no workflow file, no rules change from the mailbox. Every deploy is the owner's.
10. **Never a second installation's nodes.** One service account, one installation's project, one mailbox.
11. **Never joined to `var.launchers`.** The installation module grants the rows of [§4.3](#43-its-identity-and-what-it-may-never-do) **one binding at a time**; being listed in `var.launchers` would additionally hand it `roles/firebasedatabase.viewer` — a rules-bypassing read of every mailbox in the installation — plus `roles/datastore.viewer` and `roles/serviceusage.serviceUsageConsumer`.

## 9. The alternatives, priced

**A1 — stay laptop-only, with a wake helper.** The phone's message wakes the laptop (Wake-on-LAN on the local network, or a small always-on helper at home that receives and then starts the work), and phase 1's consumer does the rest. *For:* no new cloud identity, no new credential in the cloud, **no cloud copy of the pairing key** (B1/Q8), no E4, no new service to audit, D115's own recommendation ("decide phase 2 later") stays intact, and the operator's machine is where the operator already is. *Cost, stated plainly:* the phone's primary feature then depends on a home network, a laptop that can be woken, and a helper that is itself always-on and must be patched; "the laptop is asleep" becomes "the laptop must be wakable", which is a different product claim; and the failure is silent to the phone, which will show stale presence with no explanation. **This is the only alternative whose key stays in two places — the one [Q8](#10-answered-by-the-owner-on-2026-10-19) did not take.**

**A2 — a user-scoped orchestrator in the owner's own cloud project, against a Fugaro-shared service.** *User-scoped, per installation (recommended):* one service per installation, in the installation's project, with the installation's own service account — the shape the credentials service took (D146/D147), required by the account model (D114) and by F31. *Fugaro-shared:* one service holding many installations' model credentials **and many installations' pairing keys**. Cost: it is the single largest blast radius in the project; it makes "the operator's own project" — the property the caps, the rules and the token channel all rest on — meaningless; it puts `belong` and every other installation behind one credential; it makes E4 an attack on **every customer at once**; and it makes the F36 boundary ("secrets-only, sibling services") impossible to keep. Its only advantage is operational simplicity for the owner, which the opt-in module already provides.

**A3 — a scheduled job, not a service.** The same consumer code as a Cloud Run **Job** started by Cloud Scheduler, with no service at all. *For:* a smaller surface (nothing listens), a cheaper tick, and no ingress configuration; the lease's 10-minute TTL comfortably exceeds a per-minute tick, so the lease can simply expire. *Against:* no request path — the phone's every interaction must go through the mailbox (which is D112/D124's model anyway), and the job's cold start is paid per tick. **It still needs the pairing key** (a Job consumer verifies and signs exactly as a service does), so A3 is a deployment shape, not an answer to [Q8](#10-answered-by-the-owner-on-2026-10-19). **It would be the cheaper build if the mailbox were the only path, but [Q1](#10-answered-by-the-owner-on-2026-10-19)'s answer of 2026-10-19 took [§4.1](#41-where-it-runs)'s service**; this stays the build to prefer if a later phase drops the request path.

**A4 — no phase 2: the phone is a companion, not a remote.** The owner keeps phase 1 and the app does what phase 1 supports when the laptop is up. *For:* every attacker in [§4.5](#45-the-hard-envelope-a-stolen-phone-a-stolen-account-a-poisoned-message-and-a-compromised-orchestrator) is bounded exactly as the mobile reconciliation bounded it, and none of Q8–Q13 exists — which is why Q1's answer, taken on 2026-10-19, leaves it the honest alternative to the whole document rather than a rejected one. *Cost:* the feature the owner asked for — the phone's tasks running while the laptop sleeps — is not delivered, and D115's "decide later" becomes "decided no" for as long as the cloud has no consumer. **Listed because it is the honest alternative to the whole document**, and because [Q1](#10-answered-by-the-owner-on-2026-10-19)(c) is exactly this.

**The recommendation.** **A1 or A4 until P5.1 is built; then A2's user-scoped shape — one service per installation, [§4.1](#41-where-it-runs)'s service — with the key's custody fixed by [Q8](#10-answered-by-the-owner-on-2026-10-19)'s answer of 2026-10-19.** *(The draft read "A1 or A4 until P5.1 is scheduled"; **P5.1 is approved and split**, so the first clause is now about the build rather than about the plan.)* The one thing this design argues against outright is a shared, credential-holding service, and the one thing it argues against inside a user-scoped build is a model credential in the resident process — with [§4.4](#44-how-it-holds-a-model-credential-three-candidates-priced)'s correction about what that does and does not buy.

**Every question below was answered by the owner on 2026-10-19, each taking the option this design recommended.** The options, the recommendation and the why are kept exactly as they were written, and the answer is recorded in place, with its one-line consequence. **An answer is not an approval**: it approves no task, schedules nothing, allocates no decision number and writes no check — and **the approval this design now stands under is the owner's of 2026-11-14**, which is Task P5.1's and is recorded in [§8](#8-what-this-adds-to-the-plan-phase-5-approved-and-split). Where an answer names work (Q9's allow-list and caps, Q11's later GitHub App ruling), it names work a **later** task would carry — **and it is now the plan's P5.1g and P5.1-Q11 that carry Q9's, with the values the owner publishes**. **Q8–Q13 are new in the 2026-10-19 revision**, and each maps to a finding of that day's review.

**Q1 — Does phase 2 ship at all, and as what?** *(a)* A resident Cloud Run service, scale-to-zero, one per installation, woken by a scheduler tick (§4.1) — **recommended if a synchronous phone path is wanted**; *(b)* the same consumer as a **scheduled Cloud Run Job** (A3) — **recommended if the mailbox stays the only path**, which is the smaller surface and the cheaper tick; *(c)* no phase 2: stay laptop-only (A1) or give the app no remote at all (A4). *Why the recommendation is conditional:* everything the phone does today is a mailbox message, so (b) is enough; the service earns its extra surface only if the phone gets a request path, and that is a product question, not a hosting one. **Answered 2026-10-19: the recommended option** — **(a)**, the resident Cloud Run service, scale-to-zero, one per installation ([§4.1](#41-where-it-runs)) — the branch of the conditional recommendation this document is built on; the cadence is Q4's answer. *Consequence:* phase 2 is a service, and [§9](#9-the-alternatives-priced) A3 stays the build to prefer only if a later phase drops the request path.

**Q2 — Does the resident orchestrator hold a model credential, or only launch runs that do?** *(a)* **No credential in the resident process** (recommended): the agent runs in a job, with the credential it has today, moving to the credentials service when it lands; *(b)* a model credential mounted into the resident service itself, so it can run an agent in-process. *Why (a):* a compromise that holds no key must fetch one through a job, which is a launch, a claim and a budget token — three things the caps and the audit can see — where a resident key is simply there. **This is a smaller argument than the earlier draft made** ([§4.4](#44-how-it-holds-a-model-credential-three-candidates-priced)): (a) bounds the secret's lifetime, not the orchestrator's reach, because `SECURITY.md` records that a launcher holds the job's own credentials. **Answered 2026-10-19: the recommended option** — **(a)**: no model credential in the resident process; the runs it launches hold the credential they hold today. *Consequence:* a compromise of the orchestrator buys a launch button, not a key — a bound on the secret's **lifetime**, not on the orchestrator's reach ([§4.4](#44-how-it-holds-a-model-credential-three-candidates-priced)).

**Q3 — Per installation, or one Fugaro-shared service?** *(a)* **Per installation, in the installation's own project** (recommended); *(b)* a shared multi-tenant service. *Why (a):* D114's account model, F31's `belong` rule, the credentials service's own D146/D147 shape, and the F36 boundary — a shared service holds every customer's keys **and, per Q8, every customer's pairing key**, which makes E4 a single-point attack on all of them. **Answered 2026-10-19: the recommended option** — **(a)**: one service per installation, in the installation's own project. *Consequence:* E4 stays an attack on one installation, never on every customer at once.

**Q4 — May the tick be the only writer of the heartbeat, and at what cadence?** *(a)* One write per tick, cadence chosen with check 84's measurement (recommended); *(b)* a separate higher-frequency tick just for presence. *Why (a):* D117 asks for the write-cost measurement before the interval is fixed; a second tick is a second scheduled job for a number nobody has measured yet — and Cloud Scheduler's interval is at best one minute, which is the floor for either. **Answered 2026-10-19: the recommended option** — **(a)**: the tick is the heartbeat's only writer, one write per tick, at whatever cadence check 84's measurement supports. *Consequence:* presence is a measured cost rather than a guessed one, and no second scheduled job is added.

**Q5 — Who holds the check number?** *(a)* **Whatever is free at merge time** (recommended): this document claims no number; *(b)* the owner reserves a block for phase 2 now, which the other claimants would have to respect. *Why (a):* all ten of 80–89 are already named for other things, 90–99 and 100–109 are taken, and a number claimed by several documents at once is a number several documents have to renumber. **Answered 2026-10-19: the recommended option** — **(a)**: whatever number is free at merge time. *Consequence:* this document still **claims no number** and writes no check ([§7](#7-the-checks-it-would-need)), and **the plan's P5.1-Q7 says the same**: P5.1h takes the first number free past every claim when it merges.

**Q6 — May P5.1 ship before the device node (P6.4, proposed)?** *(a)* **No** (recommended): revocation is the envelope's only time bound, and without the device node it is owner-run steps with an ID-token window ([U3](#11-unverified)) **and, in phase 2, a cloud key copy that step 2 does not reach** ([§4.7](#47-revocation)); *(b)* yes, accepting "delete the Auth user and rotate the key" as the revocation story. *Why (a):* the mobile reconciliation already accepts time-to-revoke as E1's residual risk; shipping without the mechanism that makes it short would make that acceptance much larger than the owner agreed to. **Answered 2026-10-19: the recommended option** — **(a)**: **no**, P5.1 does not ship before the device node. *Consequence:* revocation stays short and mechanical, and the cloud key copy [§4.7](#47-revocation) step 2b removes is not the only bound on it. **Re-grounded 2026-11-16: the condition is met** — P6.4 is merged (#601) and the device node is `USER`'s conjunct ([§1.1](#11-the-draft-said-this-tree-had-no-rules-generation-3-and-no-device-node--re-grounded-2026-11-16)) — which is why P5.1 could be approved on 2026-11-14 at all.

**Q7 — Who deploys it, and may it deploy itself?** *(a)* **Owner-run, from the installation's Terraform root, following D146's pattern for the credentials service** (recommended); *(b)* an agent-run apply. *Why (a):* it is the first always-on identity this work introduces, and D63 refused an always-on credential for a weaker reason than this one has. **Answered 2026-10-19: the recommended option** — **(a)**: the owner deploys it, from the installation's Terraform root, following D146's pattern. *Consequence:* no agent applies it and no `fugaro managed apply` reaches it ([§6](#6-what-it-must-never-do) rule 2). **Re-grounded 2026-11-16:** "owner-run" here means **the owner's `fugaro update`**, not a second command — the module ships in the installation root and `update` applies it ([§4.1](#41-where-it-runs), [P5.1-Q8](#101-answered-by-the-owner-on-2026-11-14--the-plans-eleven-questions)), which is how the credentials service's own module works today ([§3.5](#35-the-credentials-service-which-has-landed)).

**Q8 — Where does the cloud consumer's copy of the pairing key live, and who may read it?** *(New, from B1.)* The tag is a symmetric HMAC (`shared/mailbox-schema/mac.js`'s `macOf`/`verifyMac`) and the heartbeat is signed too, so **any cloud consumer holds the key**; D111 and D113b/tension (b2) fix it in exactly two places today. The options: **(a) a per-installation key in Secret Manager, `secretAccessor` on the `orch` account alone** — with [§4.7](#47-revocation)'s step 2b as its revocation and a rotation story. **"Alone" is the grant and not the reader set, and this is the part the earlier draft got wrong:** the installation's **Owners and Editors read any secret's value whatever its own policy says** (their basic role carries `secretmanager.versions.access` — `docs/credentials-service/reconciliation.md` F3, and `docs/gcp-setup.md` has the installation run **as an Owner**), and so does any principal later granted `secretAccessor` on that secret, or anyone who can `setIamPolicy` and grant themselves it. So (a) means the key is readable by **the orchestrator, the operator, and anyone else with Owner/Editor on the installation's project** — every one of whom can then forge a MAC-valid outbox message the phone will speak aloud. [§4.3](#43-its-identity-and-what-it-may-never-do) now states the full set. Fugaro's own plans do narrow it: `internal/infra/tf/cover.go`'s `grantRules` allows `secretAccessor` on a **named secret** to job accounts, the credentials account and the coordinator (`toAccounts | toCredentials | toCoordinator`), and at **project** scope to the credentials service's own account **alone** (`toCredentials`; `dynamicSecretsGrant` refuses every other member, *"grants a project-wide roles/secretmanager.secretAccessor … which is not the credentials service's own account"*), so `init` will never hand a person the value and never hands any other principal the project scope — the basic roles are above that mechanism, not below it; **(b) an asymmetric tag** — the phone signs with a private key, the cloud verifies with a public one, so a compromised verifier learns nothing that lets it forge — which `shared/` does **not** support today (mac.js is HMAC only, and the merged schema, vectors and mutation proofs are built on it), so it is a change to merged code and to the phone's key custody, and probably to D171's delivery; **(c) no cloud consumer** (A1/A3 dropped, A4 taken), which keeps the two-place custody intact. **Recommendation: (b) if the owner is willing to reopen the merged schema; otherwise (a) with (2b) written into revocation — and never (a) without a decision, because it silently widens D111.** *Why:* the difference is what a compromise of the resident orchestrator means (E4): under (a) it can forge what the phone speaks aloud; under (b) it cannot, and E4 shrinks to "it can mint identities and launch runs", which the caps and the owner's kill switch still bound. **Answered 2026-10-19: the recommended option** — **(a)**: a per-installation key in Secret Manager, `secretAccessor` on the `orch` account alone, with [§4.7](#47-revocation) step 2b as its revocation and rotation story. It is the recommendation's second branch: (b), the asymmetric tag, was recommended only if the owner would reopen the merged `shared/` schema, and **it is not taken**, so the HMAC custody stands as merged. *Consequence:* the key exists in a **third place**, and its reader set is [§4.3](#43-its-identity-and-what-it-may-never-do)'s — the orchestrator, the operator, and any project Owner or Editor — so E4 keeps the power to forge what the phone speaks. **Re-grounded 2026-11-16: the note this answer owes is owed in D111, in Global Constraint 4 and in `SECURITY.md`, and it is [P5.1e](../implementation-plan.md)'s to write** — the plan's **P5.1-Q2** states it, and **this design says so rather than writing it**: [§4.2](#42-what-it-is-made-of-a-consumer-a-launcher-and-jobs-that-are-the-agent), [§4.5](#45-the-hard-envelope-a-stolen-phone-a-stolen-account-a-poisoned-message-and-a-compromised-orchestrator) E2 and [§4.7](#47-revocation) each name the task.

**Q9 — What may a phone launch, and how much?** *(New, from B4 and M2.)* Today a launch needs no confirmation (D162) and is bounded only by the caps ([§3.3](#33-the-budget-envelope)) and the runner's `allow_repos` admission check; there is no **per-device** limit, and a thief can launch anything the installation admits and read the run's environment. Options: **(a)** a per-device allow-list of repositories a phone may launch for; **(b)** a rate and cost cap per device (N launches per hour, a daily ceiling of its own); **(c)** an unconfirmed launch may run only a **named safe recipe** — everything else needs the spoken confirmation D162 removed; **(d)** a human gate before a merge can be confirmed (the merge record's target and head SHA pinned, and a cooldown); **(e)** all of the above for a phone-only installation only. **Recommendation: (a) and (b) together, plus (c) if the owner wants a launch to stay confirmation-free.** *Why:* the caps bound money and nothing else, so the launch case has to be bounded by *what* and *how often*; and (a) is nearly free, because `allow_repos` already exists and this only narrows it per device. **Answered 2026-10-19: the recommended option** — **(a) and (b) together, plus (c)**: a per-device allow-list narrowed from `allow_repos`, a per-device rate and cost cap, and an unconfirmed launch limited to a named safe recipe (D162 keeps launches confirmation-free). *Consequence:* the launch case is bounded by **what** and **how often** as well as by money — real work in the consumer, and none of it exists today. **Re-grounded 2026-11-16: it is [P5.1g](../implementation-plan.md)'s, and its values are [P5.1-Q11](#101-answered-by-the-owner-on-2026-11-14--the-plans-eleven-questions)'s** — the recipe is one of the repository's own recipes, named per installation, and the allow-list and the caps are published by `fugaro project policy publish` from the operator's local config, **with no new node**.

**Q10 — Is there a phone-side kill switch?** *(New, from M1.)* When the phone is the only human, the phone **cannot** delete the Auth user (`roles/firebaseauth.admin` is the history account's), cannot write a device node (`roles/firebasedatabase.admin` is `admins`/`budget_admins`'), and cannot write `config/kill/**` (owner-run). Options: **(a)** no phone-side kill — the phone can cancel a run and nothing more, and revocation waits for a laptop; **(b)** a narrow phone-side "stop everything" that writes one path the rules give the phone and the consumer honours (a new node, a new ruling, and a new rule in the consumer that E4 can bypass); **(c)** a phone-side request that raises a **prompt** on the laptop/console rather than acting. **Recommendation: (c) now, and (b) only with a ruling**, because (b) is a new write path into the enforcement side and E4 makes "the consumer honours it" a weaker promise than "the rules enforce it". *Why:* M1 is a real hole — the only human may be unable to stop the thing they are looking at — but the fix must not be a phone-writable kill switch the rules cannot enforce. **Answered 2026-10-19: the recommended option** — **(c)**: a phone-side request that raises a prompt on the laptop or the console, not a phone-writable kill switch. *Consequence:* a phone-only installation still cannot stop the thing it is looking at by itself, but nothing new is written into the enforcement side, and (b) needs a further ruling. **Re-grounded 2026-11-16: the plan's P5.1-Q6 records the same answer and says (c) stands.**

**Q11 — What executes a merge in the cloud, and what identity does it have?** *(New, from M5.)* D169's merge is `gh pr merge` under the **operator's own `gh` login** — an identity a Cloud Run service does not have. Options: **(a)** a **GitHub App** installation with `pull_requests: write`, creating the merge as the App, with its own audit trail; **(b)** a token in Secret Manager for a machine user, which is the operator's login in a vault and inherits its scope; **(c)** **no merge in the cloud**: the merge record becomes a prompt the phone raises and a human merges on the laptop, so phase 2 is read-only on every repository. **Recommendation: (c) for the first phase-2 release and (a) after a ruling.** *Why:* (c) removes the sharpest edge of E1 (a stolen phone merging) and of E4 (a compromised orchestrator merging) at the cost of one action that already has a confirmation machine in front of it; (a) is the right long-run answer and is a new decision in its own right, with its own App, key and revocation. **Answered 2026-10-19: the recommended option** — **(c) for the first phase-2 release, (a) after a ruling**: no merge in the cloud. *Consequence:* phase 2 is **read-only** on every repository, the merge record becomes a prompt a human acts on, and the GitHub App is a later decision with its own App, key and revocation. **Re-grounded 2026-11-16: the plan's P5.1-Q5 says "ship (c)" and takes (a) as its own decision when the owner wants merges from the phone.**

**Q12 — Does a pairing expire, and is there a biometric re-authentication on the phone?** *(New, from M6.)* D165 gives the *pairing token* an `exp` of five minutes and CLI-only pairing, but **the pairing itself has no lifetime**, and nothing in the mobile work discusses a biometric gate (Face ID / fingerprint) before the app will sign a message or a confirmation. Options: **(a)** a pairing lives until revoked, plus an app-side biometric re-authentication before a **destructive** action (cancel, merge, confirm) and before the app releases the MAC key from secure storage; **(b)** a pairing lifetime (re-pair every N days), which is a second custody problem and a second revocation story; **(c)** both. **Recommendation: (a).** *Why:* the key is the app's to guard and the phone's secure storage already has the biometric API; a lifetime adds a re-pairing path without shrinking the window a thief has while the phone is unlocked; and (a) is the mitigation that makes E1's "the read-back does not stop a thief" less true than it is today. **Answered 2026-10-19: the recommended option** — **(a)**: a pairing lives until revoked, with an app-side biometric re-authentication before a destructive action and before the app releases the MAC key. *Consequence:* no re-pairing path is needed, and the unlocked-phone window is the one this narrows. **Re-grounded 2026-11-16: the draft's parenthetical "(P6.6, unbuilt)" is spent — `fugaro pair` is built (#2572)** ([§4.7](#47-revocation)) — so re-pairing exists even though this answer does not require it.

**Q13 — May the resident orchestrator hold `run.invoker` on the credentials service?** *(New, from the review's finding (e).)* `docs/credentials-service/reconciliation.md`'s D135 grants that role **to job and Batch accounts only**. The table in [§4.3](#43-its-identity-and-what-it-may-never-do) lists it so the launcher can reach the service; giving it to a resident orchestrator is a widening of an answered decision and needs the owner's word. Options: **(a)** no — the orchestrator never calls the credentials service, and only jobs do (probably sufficient: the swap happens inside the run); **(b)** yes, with the service's own bounds (D143). **Recommendation: (a)**, and remove the row, unless a later phase-2 feature needs the orchestrator to call the service on a run's behalf. *Why:* the run presents its own job token (D134), so the orchestrator has no reason to hold the role today, and an unused grant on a service that holds every model key is exactly the kind of reach this design's identity table exists to keep out. **Answered 2026-10-19: the recommended option** — **(a)**: **no**; the orchestrator never calls the credentials service, and [§4.3](#43-its-identity-and-what-it-may-never-do)'s `run.invoker` row is removed. *Consequence:* the credentials service keeps D135's "job and Batch accounts only", and the orchestrator holds no reach it has no use for. **Re-grounded 2026-11-16: the service has since landed and every `fugaro update` deploys it** ([§3.5](#35-the-credentials-service-which-has-landed)), **which changes nothing about this answer** — the run still presents its own job token (D134) — and [§4.3](#43-its-identity-and-what-it-may-never-do) states it as the row that is not in the table.

## 12. The hygiene list: what goes stale on merge, and what collides

This document is written against a tree with other work in flight. Five things here will be **wrong the day something else merges**, and they are listed rather than left to be discovered. **Items 1–4 are the draft's, re-grounded 2026-11-16 — three of them have already gone stale, and each is corrected in place rather than deleted** ([§0.2](#02-corrections-to-the-draft-dated-2026-11-16)).

1. **The check number.** [§7](#7-the-checks-it-would-need) claims no number on purpose. **110** read as free on 2026-10-19; the register's own reading, pinned to the commit it was taken at, records that **110 is claimed by an open pull request** and takes **111** on that basis; the plan records 110 as **free and unclaimed** and hands it to nobody; [voice-evaluation-switch.md](voice-evaluation-switch.md)'s §13 records "110 upward — nothing is claimed"; and PR #632, closed and never merged, named 110 too. **This revision names 110 and claims nothing**; [P5.1h](../implementation-plan.md) takes the first number free past every claim at the time it merges. **Nothing in this document should be edited to a hard number.**
2. **The register's 90–99 block.** *Re-grounded: the sentence this item carried — "the register carries no Check 90–99 section as of the date checked" — is now false and is corrected rather than deleted.* The register carries **90** (RUN 2026-10-21, PASSED), **91**, **92**, **94**, **95**, **96** and **99** as `## Check` sections, and **100–104** beside them. What is still not written is the check this work would need, and **P5.1h writes it**.
3. **Phase 6's status, and a test's name.** *Re-grounded: this item read "an open pull request (#601) is reported both to move Phase 6 from proposed to approved and to rename it".* **#601 is merged**: Phase 6 is approved (2026-10-18), the device node and the rules generation 3 are in the tree, and the test is **`TestMailboxResidualMintedTokenNeedsTheDeviceNode`** (`internal/budget/rules/emulator_mailbox_test.go`) — the rename the draft predicted, with the citation-by-symbol that made it a one-line fix. The draft's own `TestMailboxResidualMintedTokenPassesUntilPhase6` no longer exists.
4. **A second phone-facing service.** *Re-grounded: this item read "an open pull request is reported to propose exactly such a sibling … and neither design mentions the other".* **The sibling has landed**: [voice-evaluation-switch.md](voice-evaluation-switch.md) (P5.3, approved 2026-11-14 and split into P5.3.1–P5.3.7) proposes a **new minimal service** — its own Q2, answered (a) on 2026-10-19 — which holds a provider key for the voice evaluation. The credentials service's boundary (`docs/credentials-service/spec.md`'s "Boundary", `docs/credentials-service/reconciliation.md`'s F36) is that it "stays secrets-only" and other always-on features go in **sibling services that call it**. **The collision the draft flagged is still there and is now between two landed documents**: `docs/mobile/design/voice-evaluation-switch.md` **does not contain the word "orchestrator" anywhere**, and this document is the one that has to say so. If both services are built they should share the installation module's shape (one service account per service, never `var.launchers`, [§4.3](#43-its-identity-and-what-it-may-never-do)) — and the plan's P5.3.3 already reaches the same conclusion for the hop, deploying it through `fugaro update` the way the credentials service is.
5. **`internal/orchestrator/`.** *New in this revision.* The stateless-orchestrator work (O0–O18) is merged, and its package holds a launcher, a daemon lease and state ([§3.2](#32-the-launch-path-and-the-launch-claim)). [P5.1-Q10](#101-answered-by-the-owner-on-2026-11-14--the-plans-eleven-questions) rules that this design **reuses** it rather than rebuilding it, so a later change to `internal/orchestrator/launch.go`, `lease.go` or `decide/` is a change under [P5.1d](../implementation-plan.md), and this document's [§4.2](#42-what-it-is-made-of-a-consumer-a-launcher-and-jobs-that-are-the-agent) describes a shape rather than a package it owns.

**Not a hygiene item, but the same kind of thing:** the word "orchestrator" itself ([§0.1](#01-glossary-which-orchestrator-this-document-means)) is used in this tree for the operator's own session by at least three other documents, **and — since the stateless-orchestrator work merged — for a Go package**, `internal/orchestrator/`, whose orchestrator is neither the operator's session nor this resident service. This document uses **the resident orchestrator** for the cloud process and **the operator's agent** for that session, and a later document that wants the short word should pick one and say which.
