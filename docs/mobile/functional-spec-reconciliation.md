## 2. Findings

Classes as in [reconciliation.md](reconciliation.md) §0: **Wrong** (contradicts the code), **Exists**, **Gap**, **Rule** (conflicts with a recorded ruling), **Open**. Numbered **G1–G22** to keep them apart from the earlier F1–F37.

### Relationship to existing plans

**G1 — The functional spec is the same app as [spec.md](spec.md), reframed around voice. Exists.** Its §1 purpose, §3.1 summaries and interrupt switch, §3.3 multiple installations and §4.2 Firebase Auth are spec.md's Feature 2, "Presence", "Auth & access" and the closing line on multiple accounts. **Consequence:** this is a second spec for one plan, not a new plan. Every answer D110–D129 and the tension rulings keep applying; this document only adds what v0.1 introduces (wake word, app commands, prompts and their queue, multi-agent, QR pairing, allowlist management, offline, text fallback, the front agent).

**G2 — "The voice module is first built inside the console, then reused by the phone" is the pre-D119 order. Rule.** Evidence: [reconciliation.md](reconciliation.md) D119 (answered: a top-level pure-logic package, amending Voice D50); `shared/` exists on `main` with five built modules; `console/` holds only `README.md` and `docs/json-contract.md` (`internal/cli/docs_console_boundary_test.go`'s `TestConsoleIsOutsideTheGoModule`). **Consequence:** the phone does not wait for the console; the shared logic is already landing first. The spec sentence is read as intent ("one module, two consumers"), which D119 already delivers. Recorded as tension **T1** because it contradicts an answered row's wording, not because the design is in doubt.

**G3 — The orchestrator the app talks to is the laptop's `fugaro mailbox` consumer beside a Claude session, not Voice D40's helper. Exists / Rule.** Evidence: D113c (answered option (ii)), tension (c) (`fugaro mailbox`), plan P4.1. **Consequence:** "other agents" (§1, §3.3) are other conversational endpoints behind the consumer, not Fugaro runs; see G6.

**G4 — The "sibling service next to the per-project Cloud Run security service" is a recorded direction with two gates in front of it. Exists.** Evidence: [credentials-service/spec.md](../credentials-service/spec.md) ("Boundary: … other always-on features (e.g. the phone client backend) go in sibling services"), its reconciliation F36 and D147 (the service is opt-in per installation), and its plan, which puts the service after the seal (D137, O1); mobile D115 (phase 2 decided later, after managed projects' D55–D78 gate) and D121 (no push in v1). **Consequence:** nothing in v1 depends on it; the conversational front agent (§3.1 "future option") and any push land there or nowhere (D172).

### Interactions

**G5 — "The wake word is predictable and never misroutes" is not true of a transcript. Gap.** Routing is a prefix test on what on-device STT returns (D44, D46, D123: local engines only). "Fugaro" is not a dictionary word; a general model will often hear "Figaro", "Fugar oh", or drop it. A missed wake word sends an app command to the agent as text; a false one intercepts agent speech. **Consequence:** the router is a **pure function with a closed alias set and a closed command grammar** in `shared/` (proposed P6.1), and the measured recognition rate is an owner-run check (proposed check 102). The bake-off of D123 must include the wake word in its vocabulary. Decision **D164**.

**G6 — "Talk to *agent*" has nothing to address. Gap.** Evidence: draft #532's `mailbox/$mb` subtree, one consumer per mailbox (`CONSUMER` = `auth.token.mc == $mb`); `shared/mailbox-schema`'s `FIELDS` has no `agent`; the template's `"$other": { ".validate": false }` refuses an unknown field. And the RTDB's `agents/$slug/$run` (`internal/budget/model.go`'s `PathAgent`) are **Fugaro runs**, which tension (b1) denies the phone. **Consequence:** "list agents" cannot come from the database the phone may read; it has to come from the consumer (for instance a list in its heartbeat), and routing needs either an `agent` field (schema + rules change) or one mailbox per agent. Decisions **D161** (the model) and **D163** (default agent).

**G7 — Agent prompts have no producer and no shape. Gap.** Evidence: Voice D48 dropped "awaiting user input" because nothing in the tree produces it; Voice D41 made the hooks bridge output-only in v1; the outbox schema carries `id, sender, text, at` and nothing that says "this is a question with options", nor an inbox field saying "this answers message X". **Consequence:** a prompt is a new message kind with options, a reply link and an expiry, produced by the consumer from the orchestrator session. That is a schema change to merged P0.2 and a rules change to in-flight P2.1 (proposed P6.3, P6.4). Decisions **D161** (the `agent` field) and **D168** (expiry).

**G8 — "Only the job waiting on the answer pauses" is wrong about Fugaro jobs. Wrong.** Fugaro runs are headless (`internal/agent/agent.go`'s `Args`) and never wait for input; a cap does not pause a run, it **halts** it, terminally (`internal/runstore/runstore.go`'s `StatusHalted`: "a budget or token limit stopped the run"). What can wait is the **orchestrator session** on the laptop, and a Claude Code session waiting on a question waits as a whole. **Consequence:** "the job" in §3.2 means the orchestrator's conversation, not a run; the queue holds prompts while runs continue because runs never asked. Prompt expiry (D168) is about what the orchestrator does with no answer.

**G9 — The interrupt ladder exists; "spending cap hit" is not on it, and the phone cannot see a halted run. Gap.** Evidence: `shared/digest/severity.js`'s `SEVERITY_ORDER` (`kill` > `failed` > `fast_burn` > `info`) reads **feed documents**; `FINISH_STATUS` counts `halted` as a failure, but finished and halted runs live in the runs bucket and `outcomes/**`, which tension (b1) leaves unreadable to the phone (reconciliation F13, F14). What the phone may read is `config/kill/**`, `config/caps/**` and `spend/$day/**`. **Consequence:** on the phone "a cap was hit" is **computed** (today's spend ≥ the cap, or the kill node set), not observed per run. The interrupt set is decision **D160**.

**G10 — "Yes, merge it" fails the confirmation rule Voice D47 wrote for exactly this case. Rule.** Voice D47's cell: "the confirmation must be a different act from the command, and the same misrecognition must not satisfy both … the read-back names the argv or the exact run id … the confirming utterance is a fixed, short, low-confusability phrase rather than 'yes' … recognised by a second, independent pass with its own confidence floor". **Consequence:** the owner's ruling of 2026-10-17 (an explicit "confirm" after a read-back, §3.1) satisfies that rule; the spec's example "yes, merge it" does not, and the app must not accept it as a confirmation.

**G11 — "Cancel" has no CLI confirmation to inherit, and "merge" is not a Fugaro verb. Rule / Gap.** Evidence: `internal/cli/cancel.go` (`Use: "cancel RUN"`) has no prompt, no `--yes`, no stdin read (Voice F22); `merge` is `gh pr merge`, not a `fugaro` command (Voice D47). And Voice **F38**: the orchestrator is an agent with a Bash tool and the operator's identity, and no argv table fences it. **Consequence (load-bearing for the D128 amendment):** a confirmation enforced only in the app or only in prose protects nothing, because a free-text message reaching the orchestrator can make it cancel or merge without any record. The only enforceable shape is a **typed action record** that the consumer itself executes after re-validating its confirmation record, plus a standing refusal for destructive free text — and the residual risk (the agent acting on its own on free text) is stated, not designed away. Decision **D169**, plan P6.2, P6.7.

### Pairing and access

**G12 — "Anyone can authenticate with Firebase" is false for a Fugaro installation. Wrong.** Evidence: `internal/cli/init_firebase.go`'s `identityPlatform` / `refusePublicSignUp` and `internal/infra/identityplatform.go`'s `PublicSignUp` refuse any configuration that enables email, anonymous, phone-number or any default/OAuth IdP sign-in ("the web API key is public, so only custom tokens signed by our signer may work"); `deploy/terraform/gcp/modules/firebase/firebase.tf`'s `google_apikeys_key.web` is restricted to `identitytoolkit` and `securetoken`. **Consequence:** the phone signs in with a **custom token** — the same mechanism every run uses (`internal/budget/token`'s `Mint`, exchanged by `exchange.go`'s `signInWithCustomToken`). Enabling a public provider (Google sign-in, say) would be refused by `fugaro init --firebase` and would reopen exactly what that check closes. The QR pairing token is therefore naturally a **short-lived custom token carrying the `mu` claim**, and "the allowlist" is the set of Auth users holding a valid claim (D165).

**G13 — Who may generate a pairing code already has a precise answer. Exists.** `iam.tf`'s `token_minter` custom role (`iam.serviceAccounts.signJwt` only) is bound to `var.launchers` and `var.operators` on the signer account (`google_service_account_iam_member.minter`). **Consequence:** whoever can launch can mint a phone token. That matches §4.1's sentence for the token, but **not for the rest of pairing**: writing `config/admin/devices/$uid` (D166) needs `roles/firebasedatabase.admin`, which `iam.tf` grants only to `admins` and `budget_admins` ("Budget admins (D6) write /config over IAM"), and deleting an Auth user needs `roles/firebaseauth.admin`, whose only Terraform-granted holder is the history job's account (`iam.tf`'s `history_auth`); an installation's owners or editors may hold Auth permissions through basic roles outside Terraform. So, under D165/D166, **pairing and revoking are admin acts in effect, and no person holds a Terraform-granted role to delete a phone's Auth user** (D166 says what follows). It also means **any launcher can mint a token for any `mu` or `mc`** — the per-pairing MAC key (tension (b2)) remains the only thing that tells the phone its own consumer from another launcher. (The same IAM file gives those people `roles/firebasedatabase.viewer`, an IAM read that bypasses the rules — so mailboxes are readable by every launcher, as `projectpolicy.PathAdmin`'s comment says of `config/admin`.)

**G14 — A claim-only allowlist revokes slowly. Gap.** A Firebase ID token lives an hour and the custom-token claims persist into refreshed ID tokens (UNVERIFIED U2). Deleting the Auth user stops refreshes, but an issued ID token keeps passing `USER` until it expires. **Consequence:** immediate revocation needs the rules to consult something the operator can delete. `config/admin` (`projectpolicy.PathAdmin()`) is already client-denied by the template and is written over IAM by admins; rules can still **read** it in a predicate. Adding `root.child('config/admin/devices/' + auth.uid).exists()` to `USER` makes "delete the node" an immediate revoke. That changes in-flight P2.1's macro. Decision **D166**.

**G15 — A custom token is not one-time. Gap.** A custom token can be exchanged repeatedly until its `exp` (`internal/budget/token`'s `Lifetime` is one hour for runs). "One-time" has to be built: a short lifetime **and** activation that only the pairing's own completion grants. **Consequence:** a confirmation code alone does **not** make it one-time: the QR's token names one uid, so anyone who photographs it signs in **as the same uid**, and once the operator confirms the real phone's code the copy is admitted too (and, if the QR carried the MAC key, holds that as well). One-time pairing needs a binding the copy cannot share: the phone generates its own key pair, publishes the public key in a one-shot pairing node, shows a short code that is a **fingerprint of that public key**, and the CLI — after the operator types the code — delivers the **final** credentials (a custom token for a fresh device uid, and the MAC key) **encrypted to that public key**. A copy of the QR can read the ciphertext but not open it. Decision **D165**, with D171.

**G16 — The QR is the only channel for the per-pairing MAC key. Gap / Rule.** Tension (b2) confirmed a per-pairing key, held in the phone's secure storage and the laptop's OS keychain, "established when the account is added by hand". The functional spec's QR carries "the Firebase configuration and a pairing token" — not a key. Any other channel (the database) is readable by every launcher (G13). **Consequence:** either the QR carries the key (a secret on screen for the seconds the QR is shown), or the two ends agree a key by key exchange through the database with a short code compared by the operator. Decision **D171**.

**G17 — Phone users must never be swept as run users. Gap.** `internal/budget/sweep.go`'s `deleteUsers` deletes Auth users whose uid starts with `uidPrefix` (`r~`, `internal/budget/token`'s `UID`) and are older than the history window. **Consequence:** a phone uid must use a different prefix (for example `m~<random>`) and a test must pin that the sweeper never deletes it. Part of proposed P6.6.

**G18 — The Firebase configuration in the QR is already non-secret and already recorded. Exists.** `internal/cli/init_firebase.go` records `FirebaseProject`, `RTDBURL` and `FirebaseAPIKey` from the Terraform outputs (`firebase_project`, `rtdb_url`, `firebase_api_key`, the last marked "isn't a secret: it names no one"). **Consequence:** the QR payload needs no new config source; `fugaro pair` reads what `init` wrote.

**G19 — The console cannot generate a pairing code under its recorded rules. Rule.** The console is read-only by an exact-argv allow-list (desktop-console D2, D14, §5.1 rule 6); console v2 D22 admits exactly one write, a launch. Minting a credential for a phone is a write of a different kind. **Consequence:** v1 pairing is **CLI only**; a console button is a new decision against D2/D14/D22. Recorded as tension **T3**.

**G20 — Cross-installation overview inherits console v2 D32. Rule.** [desktop-console-v2.md](../design/desktop-console-v2.md) D32, as answered: one figure per installation, each labelled with its installation and its freshness, and **never a grand total** across installations. **Consequence:** the phone's overview is a list of per-installation tiles, each from the four granted families (tension (b1)), never a sum. Decision **D170** (recommended: inherit).

### Offline and fallback

**G21 — The Firebase SDK queues writes while offline, which is "accepting messages into the void". Gap.** The RTDB client keeps pending writes and sends them on reconnect (UNVERIFIED U3 for the Expo/React Native SDK's defaults). A command spoken offline would be delivered hours later. **Consequence:** the app gates sending on the SDK's connection state and the presence rule (`shared/presence`'s `STATE`), says "no connection" instead, and the consumer's replay window (P1.1) refuses any stale write that still arrives. A destructive action record must never be queued at all. Decision **D167**.

**G22 — The text fallback is wider than D122's "tap to speak". Gap.** D122 gives a visible control when the OS refuses background audio or the microphone; it does not give a screen of pending prompts, summaries or typed input. **Consequence:** a text screen is new app work (proposed P6.9); it is also where a typed confirmation (the original D128 alternative) can live for people who prefer it.

## 3. Decisions

### 3.1 The owner ruling of 2026-10-17 that amends D128

> **Owner ruling, 2026-10-17 (relayed by the coordinating session during this reconciliation):** destructive or changing voice commands — **cancel a job, approve/merge, confirm an action** — **are allowed in v1, but only with a spoken confirmation**: a read-back of exactly what will happen, then an explicit "confirm". This **supersedes D128** ("no destructive voice commands in v1") **for the phone app's voice commands**.

What this document does with it, and nothing more:

- D128's cell in [reconciliation.md](reconciliation.md) gains a dated amendment note; **its original text is kept**.
- The consequences are **proposed** tasks (P6.2, P6.7, and test lists), **not approved**.
- **Voice D47** (the console's voice) was not amended by this ruling as given; **the owner then settled O1 (2026-10-17): the console follows the same ruling**, and D47 carries a dated note.
- The ruling names the verbs **cancel**, **merge/approve** and **confirm an action**; every other destructive verb (the kill switch, `fugaro budget` writes, deletes) **stays refused** by voice. **Launch** ("kick off …") is neither destructive in D47's sense nor named by the ruling: **D162, answered 2026-10-17: launches need no confirmation** (the caps apply).
- The ruling's "explicit 'confirm'" is read as Voice D47's "fixed, short, low-confusability phrase", so "yes", "yes, merge it" and "sure" are **not** confirmations (G10).

**What has to be enforced, and where (G11):**

1. **In the app (`shared/confirm`, proposed P6.2, pure):** the read-back is built from the command's **resolved target** (a run id, or a repository and PR number) — an ambiguous target cannot be read back and so cannot be confirmed; a confirmation has a timeout on an injected clock; one confirmation authorises exactly one action; the utterance that issues a command can never also confirm it; a confirm must be a separate utterance recognised as the fixed phrase.
2. **On the wire:** a destructive action travels as a **typed action record** (verb, resolved target, action id, confirmation id, confirmation time, for a merge the PR **head SHA** read back at confirmation, and a **`mac`** from the per-pairing key over all of them, §3.5) — never as free text (proposed P6.3, P6.4). Every other inbox message carries a `mac` too.
3. **In `fugaro mailbox` (proposed P6.7, an extension of P4.1):** the consumer re-validates every action record and **refuses a destructive command that arrives without a valid confirmation record** (missing or bad **MAC**, missing, expired or replayed confirmation, a different target, or for a merge a **head SHA** that no longer matches the PR), refuses a plain-text or plain-`answer` reply to a destructive prompt, and executes the two verbs itself — `fugaro cancel RUN` through the CLI's own code path, and the merge per D169 — rather than handing text to the orchestrator.
4. **Residual risk, stated:** a free-text message still reaches an orchestrator that can run `gh pr merge` or `fugaro cancel`, or confirm an action, itself (Voice F38). The consumer refuses destructive free text it recognises, but it cannot fence an agent's own choices. D169 asks the owner to accept or narrow that.

### 3.4 D168 answered "never expire": the consequences, for the owner's awareness

> **Moot since 2026-10-17, kept as background:** the owner amended D168 — **prompts expire at D118's mailbox TTL**; at expiry the sweeper deletes the unanswered prompt and the waiting conversation takes the non-destructive answer (or stops if there is none). The owner chose that a queued prompt waits indefinitely. What that holds or costs while it waits, stated from the tree and the plan:

- **No Fugaro run waits** (G8): a cloud run never pauses for an answer, so no Cloud Run or Batch job, no budget lease (`internal/budget/lease.go`, per run) and no launch claim (`runstore.Claim`) is held by a waiting prompt.
- **What does wait is the orchestrator's conversation** on the laptop: a Claude Code session blocked on a question waits **as a whole**, so every later request to that agent queues behind it. While idle it spends no model tokens; the `fugaro mailbox` process stays up, keeps its **consumer lease** (P1.2's shape, renewed within its TTL) and keeps writing the **heartbeat** (D117), each write billed by RTDB at no less than the floor interval (`shared/presence`'s `MIN_INTERVAL_MS`).
- **The prompt stays in the database**, and that **conflicts with D118** (a TTL on the mailbox node plus a sweeper): either an unanswered prompt is exempt from the TTL — so the retention bound no longer holds for prompts — or the sweeper deletes it, which is an expiry by another name. **O4, settled 2026-10-17: they are not exempt** — the TTL holds and D168 is amended. - **A bounded alternative that is not an expiry (proposed in P6.5, NOT APPROVED):** reminder escalation — re-announce a waiting prompt at the next natural pause after 1 hour, then once a day, and list it first in "what's pending"; nothing is decided or dropped by a timer. **It bounds attention, not storage**: the storage bound is the pending-prompt cap above.

### 3.5 The MAC, the action ledger and a stolen phone (specified after review round 2, 2026-10-17)

This section specifies what D169 (answered) and D171 (answered) require; it decides nothing new except where marked, and the marked items are listed under Open items.

- **Every inbox message carries a MAC — every kind** (`message`, `answer`, `action`), not only action records; every outbox message carries one too (tension (b2)). Without it, a launcher who mints a token for a paired `m~` uid (G13) could send a plain `message` or an `answer` saying "merge" to the orchestrator's own "approve the merge?" prompt.
- **An answer to a destructive prompt is accepted only as a MAC-verified action record carrying a confirmation** — never as free text and never as a plain `answer`. The consumer refuses a plain `answer` or `message` to a prompt whose effect is destructive.
- **The key:** the per-pairing key of D171, held in the phone's secure storage and the laptop's OS keychain (the consumer's settings hold only the item's name). **Custody, stated:** the keychain item is readable by any process running as the operator — the orchestrator agent included — so an agent that reads it can sign; that folds into the **accepted F38 risk** (the agent already holds the operator's identity) and is not a new boundary.
- **What is covered: every field of the message except `mac` itself** — `id`, `at`, `sender`, `agent`, `kind`, `text`, `options`, `reply_to`, the chosen answer, `acked` is excluded only because the phone writes it after the fact on the outbox, and for an action record the verb, target (run id, or repository and PR number), action id, confirmation id, confirmation time and, for a merge, the PR head SHA. A field added later is covered by default. **Canonical serialisation:** the message without `mac` (and without `acked`) as JSON with keys sorted by code point, no insignificant whitespace, absent fields omitted (never `null`), strings as UTF-8 with JSON's own escaping only, numbers as integers (milliseconds); HMAC-SHA-256 over those bytes, hex-encoded in `mac`. The serialisation is one pure function in `shared/mailbox-schema` (P6.3) with a vectors file; the Go consumer reimplements it and tests against the same vectors. **P6.3's vectors include a valid MAC with `text`, `options`, `reply_to` or the answer swapped, each refused.** *(Owner ruling 2026-10-18, on PR #579: the **direction** is covered too — one field beyond the list above. `canonicalBytes(record, direction)` adds `"direction"` (`inbox`, `outbox` or `heartbeat`) to the covered bytes; it is not stored in the record, the reader supplies it from the node it read, and a record carrying its own is refused. One per-pairing key signs all three nodes, so without it a message reflected from the inbox into the outbox, or back, would verify. The vectors carry pairs that differ only in direction and refused reflections.)*
- **Who signs:** the **phone** signs every inbox message it writes (P3.6, using P6.3's serialisation and the key from secure storage); the **consumer** signs every outbox message and the heartbeat (below).
- **Where it is verified:** in the consumer, `fugaro mailbox`, before anything else and before any action (P6.7), and on the phone for the outbox and heartbeat (P3.6). The rules (P6.4) only require the field to be present; they cannot verify an HMAC.
- **The heartbeat is signed too (added on review round 3; see Open items).** A minted `mc` token could otherwise fake liveness and the advertised `agents` list, which feeds D163's default agent. Recommendation, taken into P6.3/P6.4: a `mac` on the heartbeat over `at`, `boot` and `agents`; the phone treats an unsigned or wrongly signed heartbeat as **offline** and ignores its agent list.
- **Timeout and windows.** The confirmation **timeout is checked on the phone** (P6.2), where the pending state lives; the consumer checks only the **command window** (6 hours from the confirmation time) and the prompt window (72 hours). *Why the first:* the pending time is phone-local state, and putting it under the MAC would only prove what the phone already asserts; the 6-hour window is what the consumer can enforce.
- **Clock trust.** `at` and the confirmation time are set by the phone; windows and expiry are computed on the consumer's clock. A phone **ahead** makes a message look fresher (a window is extended by the skew); a phone **behind** gets messages refused early. The consumer refuses any `at` or confirmation time more than **5 minutes in the future** of its own clock and computes every window from the phone's time with that tolerance; the skew is measured live in **check 84** (presence and clocks).
- **The ledger:** the consumer records every used **message id, action id and confirmation id**, and every prompt it has expired or answered, in a ledger that **survives a consumer restart** and keeps each entry for **at least the 72-hour TTL plus one sweep interval, or until the stored message is gone, whichever is later**, so a restart can re-deliver neither an answer nor an expired prompt's safe answer, and a signed record re-sent under a new message id is refused by action-id dedupe. **P1.1's dedupe retention is tied to the 72-hour acceptance window** (it must not forget an id while a message bearing it can still be accepted).
- **Pending prompts survive the sweep:** the consumer keeps its pending prompts **locally** (id, `at`, safe answer) so that when the owner-run sweeper deletes the stored prompt it can still expire it and deliver the safe answer exactly once.
- **A stolen phone:** revocation is **(1) delete the device node** (`fugaro pair revoke`, D166 — immediate for reads and writes), then **(2) delete the laptop's keychain item** for that pairing's key, so nothing the phone signs verifies afterwards. Before revocation, whoever holds the unlocked phone can do what its owner can, **including saying "confirm"** — the read-back does not stop a thief, and the spend caps do not bound a cancel or a merge. **The real bound is the time to revoke.** That is the residual risk D169's answer accepts together with F38.
- **Re-pairing and rotation:** a key is rotated by pairing again (`fugaro pair` issues a new device uid and a new key) and revoking the old pairing. After a revoke, the consumer drops that pairing's pending prompts, delivering each one's safe answer once, and deletes its outbox messages; a message signed with a revoked key is refused.
- **Tests (P6.7, P3.6, P6.3):** a valid MAC over a message with a tampered target, head SHA, `text`, `options`, `reply_to` or answer is refused; a signed record re-sent under a new message id is refused (action-id dedupe); an unsigned `message`, an unsigned `answer`, and a plain-text answer to a destructive prompt are each refused and nothing runs; the ledger refuses a reused id after a restart and does not re-deliver an expired prompt's safe answer after a restart; an `at` more than 5 minutes ahead is refused; an unsigned heartbeat is shown as offline.

### 3.6 D173's open question, and how the windows ship (2026-10-17)

- **The kinds and their windows.** *Confirmed by the owner 2026-10-17 (O6):* an **answer to a destructive prompt is a confirmation** and takes the **command window** (6 hours); an **answer to a non-destructive prompt is a prompt answer** and takes the **prompt's TTL** (D118). It follows from D169 (a destructive answer is an action record) and from D173 (commands 6 h, prompts TTL).
- **Ordering, stated honestly.** PR #537 (P1.1, `shared/mailbox`) implements **one** window (`DEFAULT_WINDOW_MS` 6 h, `MAX_WINDOW_MS` 7 days), and the schema has **no `kind`** until P6.3. So: P1.1 (in its fix round) ships a **kind-parameterised window API** — the caller passes the kind or the TTL — and implements per-kind windows over the kinds that exist; **P6.3 adds the `kind` field**; P6.5 and P6.7 call the API per kind.
- **The cap must cover the TTL.** `MAX_WINDOW_MS` must be at least D118's TTL. **D118's original answer stated no TTL value** (the plan's C5 left the retention window to the owner); until the owner set one, the cap and the TTL were tied by a rule: **the TTL may not exceed `MAX_WINDOW_MS` (7 days) unless P1.1's cap is raised with it**. **The owner set the TTL on 2026-10-17 (O5): 72 hours** — D118's mailbox TTL and the unanswered-prompt TTL alike. P1.1's cap (7 days) already covers it, so no cap change is needed; the consumer passes **`promptTtlMs` = 259 200 000** (72 × 3 600 000 ms) to P1.1's window API for prompt answers, and the 6-hour default for commands and for answers to destructive prompts.
