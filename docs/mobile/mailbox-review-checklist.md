# `fugaro mailbox` — the review checklist (mobile P4.1, T1–T8)

**Status: shipped with T8's parity corpus. Every line below is either proved by a named test on
this branch or marked as a line no test in this repository can prove — and the second kind is
written down rather than left out, because a claim nobody can check is exactly the one a reviewer
has to check by hand.**

This is the checklist `docs/mobile/mailbox-consumer-plan.md`'s T8 names. It is not a summary of the
plan: it is the list of claims a reviewer of T1–T7 must confirm, each with the test that proves it,
so a review can be a reading of this file plus the tests it names rather than a re-derivation of the
whole design. Run the named tests with `GOFLAGS=-p=2 go test <package> -run '<filter>' -count=1`
from the repository root; every test here is hermetic (no network, no cloud, no clock — `internal/gcpfake`,
fakes and `t.TempDir()`).

## The lines no test in this repository can prove

| Confirm | Why nothing can |
| --- | --- |
| **T5 — the `fugaro mailbox` row in `docs/design/v1.md` §9.1**, and its prose list of `--json` commands. | **Not test-enforced, and T5's own section says so.** Nothing in this repository reads that table and compares it with `NewRootCmd`; the pins that exist are for `website/content/cli-reference.md` and for `docs/project-layer.md` §7's flag table, which this change does not touch. Keeping the row is a duty of the commit and a line here, not a red test — and claiming it was enforced would be the same false guarantee as any other test that does not exist. |
| **T5 — no IAM sentence was added anywhere near the bucket.** | The guard that scans for IAM claims (`docs_bucket_iam_test.go`) reads `docs/*.md`, `docs/design/*.md`, `README.md`, `SECURITY.md` and the plugin skills: its globs do not descend into `docs/mobile/`, so **nothing would go red if a sentence appeared here**. The absence is a duty and a review line; no test looks for an IAM claim in this plan's directory, for its presence or for its absence. |
| **T7 — the `m~…` sweep rule.** | It is **P6.6's** (`internal/budget/sweep.go`, approved and not built). At P4.1 the sweeper's delete set cannot contain an `m~…` — or an `r~…` — user, and the sweep asserts that it refuses and reports rather than performing one (`TestSweepDeletesNoUser`). What the rule itself should be is P6.6's, and nothing here can prove it. |
| **T7 — the store-side deletion of a stored prompt.** | It is **P6.13's** half and has landed elsewhere (the pairing plan's T7); T7 asserts only that its **own** delete set holds no store path and that the sweeper never answers. Whether the store-side half is right is that task's tests' business, not this plan's, and neither half reaches the other's. |
| **T2 — the parked unverifiable message, and its cost.** | The **behaviour** is asserted: a message the gate refuses stays in the inbox, is refused again on the next pass with its code, and nothing this command can do retires it (`TestARefusedMessageIsRefusedAgainOnTheNextPass`, `TestUnverifiableIsRefused`). Whether the cost is acceptable — one inbox read and one `refused[]` entry per pass, forever, from one bad message, retired only by an operator with their own credential, out of band — is an **operator's decision to accept**, not something a test can settle. The design decision is stated in the plan's §7 ordering 2 and §16; this line is where a reviewer is asked to accept it. |
| **T8 — the corpus's drift gap.** | `TestParityCorpusIsCurrent` regenerates and diffs **only where `node` is on `PATH`**; CI's `test` job has none, so there a `shared/mailbox` change under an unregenerated corpus is caught by no test in this repository until the owner copies the staged `docs/pending-workflows/shared-tests.yml` in. The hash catches a **hand edit** everywhere; only regeneration catches a **changed module**. Where a Node exists — the owner's machine, a Fugaro run that has set one up with mise, and the P4.3 job once it runs — the check is live. |

## Two things a reviewer should know about T8 itself

- **The plan names `shared/mailbox/parity.test.js` as "the generator"; the writer is
  `shared/mailbox/parity.generate.mjs`, and `parity.test.js` is the reader that re-derives every
  answer by calling the live module.** The split is deliberate and the reason is
  `shared/mailbox/mutation-proof.sh`: it applies a mutation to `index.js` and restores `index.js`
  and nothing else, so a test file that regenerated the corpus would leave the mutated module's
  answers in the working tree. To change the corpus, change the `.mjs` and run
  `node shared/mailbox/parity.generate.mjs`.
- **The corpus carries what no vector file does: the module's outcomes and codes.** The committed
  vectors M9 leans on are `shared/mailbox-schema/vectors.json` (T1) and `shared/confirm/vectors.json`
  (P6.7's); `shared/mailbox` has none, which is why its state machine is held to this corpus instead.
