- The installation's base image is no longer copied into your registry: `fugaro init --base base`, `fugaro image refresh` — and `fugaro upgrade`, whose cloud step is refresh — resolve the release's nightly-immune `-pinned` tag, verify the cosign signature that release's tag push attached to that exact digest (by the release workflow's identity and issuer, mandatory), read the digest back through the installation's own Artifact Registry **remote repository** over ghcr.io, and record that remote path at that digest in `base_images`, refusing to pin anything that does not verify; `cosign` must be on your `PATH` (a missing binary refuses rather than warns, and `fugaro doctor` reports it on every run).
- `fugaro init --repo --retire` is the one-command form of the transition that used to be hand-run `terraform state rm`: an ordinary `fugaro init --repo` now predicts what a change to `fugaro.yaml` retires (a workflow variant, a named Claude account, a secret no longer mounted) and refuses when Terraform's `prevent_destroy` blocks the plan, while `--retire` removes those protected addresses from the state (destroying nothing in GCP), plans and shows the plan's own delete list, applies, and deletes the orphaned Cloud Run jobs through the API — with the project's name typed twice at a real terminal, never by `--yes`, a pipe or an agent session, and never deleting a secret or a secret version, so a released container stays in Secret Manager with its value and is re-adopted by its labels if that mount comes back.
- One global per-run cap now bounds every repository: `fugaro budget set --global --per-run P` is the effective per-run cap of any repository that has none of its own and no `--defaults --per-run`, where before such a repository halted in enforce while the global cap was only a ceiling on top of a repository's own; `fugaro budget show` prints the effective cap and where it came from (`repo`, `default`, `global`), and the refusals for a repository with no cap anywhere now name flags that exist (`--defaults --per-run`, `--global --per-run`) instead of the never-existing `--repo-per-run`. This rule lives in the budget database's rules, so it reaches a project only through `fugaro init --firebase <firebase-project-id>` run with the new CLI — CLI first, then the rules, then the runner images (below).
- Provider-routed models are now priced from a provider price catalog built into the binary: 5 models across 91 endpoints, checked 2026-10-14, charged at the ZDR tier's cheapest end by default with each tier's real range gathered from OpenRouter's endpoints, printed offline by `fugaro budget prices`, and falling back to the dearest end of the range once the file is 30 days old (`fugaro doctor` warns at the same threshold), while `model_prices` in the project config still replaces a catalog row; the two route keys that pick a tier, `require_zdr` and `price_policy`, are **refused** by `fugaro init --repo` in this release — no released runner reads them yet — so their defaults apply but you cannot set them until a later release flips that.
- A secret can now be stored once for the whole Fugaro project instead of once per repository: `fugaro secrets set NAME --project-wide` writes the project's own container, which the installation's Terraform creates, and every repository the name is allow-listed for mounts that copy, except a repository that keeps its own copy of the name, which still wins; a provider key with no `allow_data_to`, or one written as `["*"]`, is available to every repository — `fugaro validate`, `fugaro init` and `fugaro doctor` now name every provider open that way, an `allow_data_to` written with nothing under it is refused as ambiguous instead, and `SECURITY.md` warns that a project-wide git credential reaches every repository allow-listed for it; `anthropic-api-key` also became optional: a repository whose `agent.auth: api-key` runs under an enforcing budget and whose coder, reviewer and background models are all served by a provider allow-listed for it needs no Anthropic key, and the gateway's refusal and `fugaro validate`'s offline note name the fix — `fugaro secrets set anthropic-api-key`, or route the model through a provider — when one is still needed.
- The smaller changes you will notice: `result.json` records each stage's model cost (`model_usd`, and the stage's `model`, with spend settling after a stage ends under `model_by.unattributed`); `fugaro budget preview --recipe NAME --runs N` answers "could this batch blow my budget?" with a rough worst-case ceiling and, once the repository has five priced runs in the last 30 days, a `typical:` line from its own recorded costs (only real dollars count, so oauth runs are excluded and counted); the base image creates `~/.cache/mise` owned by `fugaro`, so derived builds stop printing mise's `Permission denied` cache warning; and the hidden `fugaro ls` pointer is gone for good — `fugaro ls` is an ordinary unknown command (exit 1) now, while `fugaro runs ls` is unchanged.

### For operators

1. Upgrade the CLI (`brew upgrade dimipaun/tap/fugaro`, or this release's archive with its cosign check), and install `cosign` on your `PATH` (`brew install cosign`, or your distribution's package): `fugaro init --base` and `fugaro image refresh` refuse without it, and `fugaro doctor` names it on every run.
2. If you use the budget backend, deploy its rules **before** any runner image moves: with the new CLI, `fugaro init --firebase <firebase-project-id>` (add `--print-vars` first to see what it writes; `docs/gcp-setup.md`'s "Turning the shared budget on" section has the read-only check of what landed) writes the new per-run-cap rules as the last write of its database step. Also point Application Default Credentials at your installation's project — `gcloud auth application-default set-quota-project <gcp-project>`, with the Cloud Billing API enabled there — because `init` and `doctor` read billing through that quota project and name it when the API is off.
3. Then `fugaro upgrade` in each checkout (its cloud step is `fugaro image refresh`): it now pins the release's base image through the installation's registry remote repository at the digest whose signature it verified, and rebuilds each workflow that is not yet on it. It asks before every billable build, and the base image must move before any repository's image does, which that command keeps in order.
4. For project-wide secrets, in this order: (a) in the installation root, `fugaro init` with no `--repo` plans the project's secret containers as creates only — one per eligible name, no destroys, no replacements and no update to an unrelated resource — and applying it is your step, not something a repository's job can do; (b) then `fugaro secrets set NAME --project-wide` for each name stored once for the project (the value is read from stdin, and it takes no `--repo`; a value stored before (a) is adopted by that apply rather than conflicting); (c) for a repository that adopts a project-wide name while its own copy still has a version, that copy must be disabled before the repository uses the project's — `gcloud secrets versions disable` needs `secretmanager.versions.disable`, which is project-owner-only; (d) then `fugaro init --repo` in its checkout plans replacements of the per-repository IAM addresses, which Terraform's guard refuses until each removal is named with `--allow-delete`.
5. If a plan ever tells you it would retire resources, use a binary built from this release: `fugaro init --repo --plan-only` first (it prints the predicted retirements and, when Terraform's `prevent_destroy` blocks the plan, refuses with "Rerun with --retire"), then `fugaro init --repo --retire`, as `docs/gcp-setup.md`'s "Changing auth, or removing a workflow, secret or provider" section describes. An older binary keeps failing on `prevent_destroy` the way it does today and needs that page's manual `terraform state rm` route.

Two notes. `checkout: clone` is **not** usable in this release: the runner side is in the tree (the blobless `--filter=blob:none` clone, the `mise install` provision stage, the prefetch), but the switch that turns it on has not been flipped, so its job cannot exist at all — `fugaro init --repo` and `fugaro image refresh` refuse to deploy or move a clone workflow's job, and `fugaro run` refuses a clone launch on any job image, a known release or a development one, telling you to use `checkout: baked`. `checkout: baked` workflows are unchanged, and the flip lands after its own live check. And the two items 0.7.0's notes left unverified have since been checked live on the sandbox installation: the runs bucket's launcher grants (Check 32) and the one base image's cold start (Check 41, ~10.5 s median against the old image's ~11.7 s).
