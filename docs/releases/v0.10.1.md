- **The credentials service is wired end to end.** An installation that opted in with `fugaro update --provision-credentials` now has the service's address recorded in its project config and put on every per-repository job it launches, so a `cascade` run asks the service for its model credential and a GitHub run asks it for its installation token instead of minting in the job. The service itself stays dormant: it is off until an owner opts in, and an installation that has not opted in gets nothing new.
- **The service can read the installation's database.** The installation root now creates the service account's own database role, `fugaroCredentialsDatabase` (`firebasedatabase.instances.get` and `.update`, the database's two data permissions, and no instance lifecycle), and binds it to that account alone, so once applied a call's reads — the run's outcome, the stop switches, the policy and the credential state — are admitted rather than refused `state_unavailable`.
- **A shared project job is deliberately left alone.** The service refuses a caller whose account belongs to one, so the launch does not tell such a job the service's address; it keeps its own credentials and mints in the job as before.
- **An installation that has not opted in is byte for byte what it was.** No job of one carries the service's address, and nothing about its runs changes.
- **A teammate's machine needs `fugaro update` after the opt-in if it has its own local config.** The address travels in the published shared config, but a machine whose own local config lacks it launches with no address — a `cascade` run then fails closed at bootstrap — until it runs `fugaro update`.

### For operators

1. **Per machine** — upgrade the CLI on every machine that runs Fugaro: `brew upgrade dimipaun/tap/fugaro`.
2. **Per repo checkout** — run `fugaro upgrade`, which pins the plugin to this release and refreshes the repository's job images.
3. **Per installation, only if you mean to turn the service on** — `fugaro update --provision-credentials` deploys it, its database role and that role's binding, and records its address; before you expect a GitHub run to work, write the App's key into the service's bundle with `fugaro creds set github-app-key`, because a mint that finds no key is a refusal and never a fall back to the job's own copy. Nothing in your cloud project changes by upgrading alone.

### Known limits

- **The service is wired for `cascade` workflows, and the other auth modes are not.** The opt-in removes a per-repository job's own model credentials whatever its `agent.auth`, while only a `cascade` run's calls go through the service, so an `oauth` or `api-key` workflow of a repository that has opted in has no model credential of its own and nothing yet to replace it: run such a project's workflows with `agent.auth: cascade`.
- **The GitHub App key does not leave the job in this release.** A job of an opted-in installation still mounts `github-app-key` and still holds its accessor on it, while the runner no longer reads the key and mints at the service instead; the grant and the mount are taken away in the release after the owner's live check proves the deployed service mints.
- **The service issues only what its bundle holds.** No Terraform fills the bundle; `fugaro creds set` is its only writer, so a call against an empty bundle is refused, never served from the job's own copy.
- **None of this has been proven live yet.** The owner-run Checks 94, 95, 96 and 99 are not run.
- **The service ships with its own known limits, stated in SECURITY.md:** a refusal answered before the caller's identity is verified carries no audit line, and a model call's issuance line is written before the answer streams, with a second line when the stream then fails.
- **A `cascade` launch is legal on the published policy switch, not on the service:** a project that publishes `routing.claude: {via: cascade}` without a service launches a run that fails at bootstrap rather than one refused at launch. `agent.auth: cascade` also needs a published `budget.allowed_models`.
