- An installation's database rules now carry the orchestrator's own state subtree, closed to every identity the rules evaluate, and the person's own credential is what writes a state node.
- `fugaro update` deploys that document and records its generation in the same run, so one command is still the whole upgrade; a database whose rules came from a newer Fugaro is refused rather than overwritten with an older document.
- **`fugaro security paths` prints what a repository's runs treat as security-sensitive** — one named row per tree, file or file class, each with the category it is labelled — so the rule can be read instead of guessed at. `--check <path>` answers a path against the list, and `--json` prints the document a tool reads.
- **The list is read at the base branch, never from the working copy**, so a change cannot carry the rule that governs its own review; a path the command cannot place at all is answered sensitive rather than routine.
- **An upgrade that is given the budget once flags an installation that is not managed itself.** `fugaro update --budget <amount> --budget-currency <code> --billing-account <account>` writes both marks of a managed project as it converges — the creation fact in the runs bucket and the `fugaro_managed=true` label on the GCP project — so from the next run on that project's applies no longer stop for the typed confirmation and no `fugaro managed flag` has to follow. `fugaro update --help` says so on `--budget` itself, and the run prints what it is about to write before it writes it. A coding agent's session and a Fugaro run's own process are refused that write.
- **A launcher's cloud access now reaches the installation's shared issue store as well**, ahead of the commands that will file and read issues there: the grant on the runs bucket gains the `issues/` prefix, so an issue is written with the credential of the person who files it and no run's own account can write one. Nothing files an issue yet — this release grants the access the issue commands need when they arrive.
- **`planning.decoupling` turns the dependency-breaking planning pass off for one repository, or for every repository of a project through the layer's `defaults.planning`.** It is a preference and not a bound, so the narrowest layer that writes it wins: a repository settles it for itself even where the project set it, the other way round from a guardrail that only tightens. Both files are decoded with unknown fields refused, so a job image older than this release reads the key as an error and refuses the file at bootstrap: `fugaro update` gates the repository's `fugaro.yaml` and the project layer against the installation's base image before it writes anything — a base image that is not a release ref warns rather than refuses, since such a runner refuses the key itself — and the same run moves every job image of the repository onto this release.
- **A published policy's pools now name their owner and the people they are served to.** `craft_pools` entries carry `owner` and `allowed_users`, both spelled by email, and `fugaro project policy publish` refuses a pool that names no owner — a pool with no owner serves nobody. This is policy version 5, and `fugaro update` migrates the node in place rather than asking you to publish again: every pool that names no owner comes out carrying `legacy_open`, the marker that says the pool predates owners, so the upgrade serves exactly whom the installation served before it. Nothing else of the node is touched — the fields you edited into it by hand are carried over rather than published again.

### For operators

1. Run `fugaro update` once per installation, on your own machine. It is the whole upgrade: it deploys the new rules and records the generation they belong to, and no second command is needed. On an installation that is not managed, giving that run `--budget <amount> --budget-currency <code> --billing-account <account>` flags it as managed in the same run, so no `fugaro managed flag` follows it.
2. The same `fugaro update` replaces each launcher's bucket grant with the one that also covers `issues/`, the prefix the shared issue store lives under. It names the launchers whose grant it replaces and needs no `--allow-delete`: the grant is the launcher's own, and removing it would take that launcher's `runs/` writes with it.
3. Nothing to run for the security list, and nothing in your cloud project changes for it: `fugaro security paths` is a reader, and no run's cost moves in this release.
4. The same `fugaro update` raises the project-wide budget mode to `enforce` on a managed project wherever no person chose the mode, so an installation from before this release — whose converge seeded `observe` — enforces its project-wide caps from this run on. A mode you set yourself (`fugaro budget set --global --mode observe`) is recorded as yours, and no later update touches it. A coding agent's session may not record that choice for a mode below `enforce` — it is refused the way a raise is — so a session cannot put the mode out of the update's reach. Where a cap `enforce` compares every lease against is not set — the project-wide daily and per-run pair, or the default daily cap a repository without one of its own is compared against — the mode stays `observe` and `fugaro doctor` names them: `fugaro budget set --global --daily <usd> --per-run <usd>` and `fugaro budget set --defaults --daily <usd>` set them, and the next `fugaro update` raises the mode itself.
5. Nothing to run for `planning:` beyond the `fugaro update` above: the key is decoded, validated and resolved by this release, and the same run moves every job image onto it, so a repository may write it as soon as the update has converged. The pass the switch turns off is not in this release — the planning skill that reads the switch ships in a later one — so a file that sets it plans exactly as before, and no run's cost moves.
6. The same `fugaro update` rewrites the published policy node in its last stage, from version 4 to version 5: it prints the migration's diff and asks for the project's own name before it writes, with `--yes` answering for it (the migration only adds a marker, so it widens no ceiling). The migration's whole change is `legacy_open` on every pool that names no owner; nothing else of the node is rewritten, so the entries you edited into it by hand survive it. It is safe while runs are in flight and asks no run to finish: when runs are running it says so in one line and proceeds, and a run that bootstrapped under the release behind keeps its records and its ledger. Upgrade every machine that runs Fugaro before it reads or publishes the policy again (see Known limits).

### Known limits

- **An older Fugaro can take this release's rules away.** `fugaro update --firebase-project` run from a binary older than this one reads the policy marker at its own generation, so nothing stops it deploying its older document — the one without the `/orchestrator` node — while the generation marker this release writes stays where it is. The state the person's own credential then writes lands over IAM, which no rule binds, under rules no client may read back, and nothing names the divergence. Upgrade that machine's Fugaro and run `fugaro update` again: it puts this release's document and marker back.
- **The subtree's live check has never been run.** Check 300 of `docs/gcp-live-checklist.md` — the person's own credential writing a state node on a real installation, and no token identity admitted to that subtree — is **NOT RUN**, and so are Checks 301 to 305 written alongside it. Until you run them, the emulator tests are the only evidence for that fence.
- **The two security keys ship, and nothing reads them yet.** `security:` — a project's rows in the layer file it publishes, a repository's own in `fugaro.yaml` — is decoded and validated by this release, and a job image older than this one decodes both files strictly and refuses the key whole at bootstrap: writing the layer's key therefore needs every job image of the project on 0.22.0. No run resolves a list from either key yet, though: the list in force is still the engine's own floor of 43 rows, `fugaro security paths` prints that floor, and `fugaro doctor`'s finding about a written row that matches nothing cannot fire until a run reads the layers. `always_level_3`, and the per-run request that goes with it, are validated here and enforced in a later release.
- **A policy node migrated to version 5 is refused by 0.21.** Once the `fugaro update` above has rewritten it, a 0.21 CLI and a 0.21 job image read it as "the project policy is version 5; this Fugaro understands version 4" and refuse it — the node's pools carry members that reader decodes strictly, so it is unreadable there rather than tolerated as an unknown key. A repository whose job images have not moved therefore refuses at bootstrap, which is what the same `fugaro update` prevents by moving every job image of the repository onto this release; a machine still running 0.21 must be upgraded before it reads or publishes the policy, and the remedy it prints instead — `fugaro project policy publish --delete` and a fresh publish — loses what the node carries, so upgrade rather than take it. The credentials service is the one reader that carries on across the gap: a service on this release that meets a node the update has not reached yet reads it as this one would after migrating it, in memory, and writes nothing back to the database.
- **`planning:` ships, and the pass that honours it does not.** A job image older than this release decodes the repository's `fugaro.yaml` and the project layer it resolves over strictly and refuses the key whole at bootstrap, so writing it needs every job image of the project on 0.22.0. No run reads the switch yet, either: the dependency-breaking pass belongs to the planning skill, which reads `planning.decoupling` from a later release, so a file that sets it plans exactly as it did before this one.
