- **A run pushes the commit its suite tested.** A run no longer ends by writing the findings it left open into `docs/backlog/` in a commit made after the suite's last run: what it left open is in its record and in the pull request's status section, so the branch it pushes is exactly the commit the suite passed on.
- **A run refuses to commit an artifact.** Finalize lists what a commit would add that no commit holds — an untracked file, a staged one, a path added with the intent to add — and refuses by name every one that is executable or whose first bytes read as binary: the path is held out of the commit and the run opens as a draft whose reason says which file was refused and why.
- **A review that answers nothing leaves a draft, after one retry.** A senior review round that returns no readable verdict is asked once more, in a session of its own, and a round that still has nothing to read opens the pull request as a draft with the reason recorded, rather than shipping work nobody read.
- **`fugaro doctor` looks at the credential side of an installation.** Its default screen now counts the checks for the credentials service and its callers' invoker grants, the bundle's Bitbucket token (behind `--check-bitbucket-token`, sent only to an https root the installation lists and that passes the same validation the policy publish applies), stored credentials past the rotation period or expiry your config records, and a model credential that reaches a workflow's agent — and no line prints the token's own value.
- **Project answers outside a checkout.** `fugaro config layer` works from outside a checkout, taking `project:` and `gcp_project:` from the selected project config and saying which of the two answered; `fugaro run --repo X` from outside X's checkout refuses and names both causes instead of silently targeting the repository's own job; and two `rigor.areas` rules that carry the same glob in one layer are refused where they are written.
- **Smaller fixes.** `fugaro watch --json`'s total block carries `max_parallel`, the cap a launch is checked against, so a console's concurrent-runs bar draws the real value; every message that sent an owner to `fugaro upgrade --local` now says `fugaro update`; and the policy read that concurrent launches share is race-free.

### For operators

Run `fugaro update`.

- A config or project layer that repeats a `rigor.areas` glob now fails validation: remove the duplicate.
- On an installation that has published profiles, a launch from outside the repository's checkout is refused — `fugaro run --repo X`, the `--retry` and `--pr` follow-ups, and with them a console launch of a repository other than the installation's recorded checkout. Launch from the repository's checkout until the follow-up that reads the checkout kind from the deployed job lands.

### Known limits

- The authorship a launcher names and the trailers a run writes are a record and not proof: nothing verifies a `Fugaro-Run` trailer, no account owns the author a launcher claims, and a commit can be amended after a run pushes it. A repository whose `fugaro.yaml` sets `git.author` is refused at launch against a job image older than 0.14.0, which names the upgrade instead. Nothing a run commits is signed. The stamp hooks the runner writes live in temporary directories the run's agent can also write, since the agent and the runner share one user, as `SECURITY.md` says of everything that user can reach.
- A launch from outside the repository's checkout is refused once the project has published profiles: `fugaro run` reads a workflow's `checkout:` kind and its profile from the `fugaro.yaml` of the checkout it runs in, the job it is about to run being no source for either, so from elsewhere it cannot tell a clone workflow's shared job from a baked one's own and will not guess. An installation that has published no profiles is untouched, the per-repository job being the only job there is. `--retry` and `--pr` are refused the same way, and so is a console launch of a repository other than the installation's recorded checkout.
- A run writes no backlog item: what it left open is in its record, which says which review round produced it and what the run tolerated, and in the pull request's status section. A Hotfix run's deferral of the proper fix was expressed only as an item, so it is no longer written down — `fugaro backlog add` is the command that files one.
- Pairing completes only with the phone app's later release: 0.14.0 wrote the device node and the delivery, and nothing on the phone reads them yet.
- The laptop's copy of a pairing's MAC key is stored through `security -i` in the macOS keychain or through `secret-tool` (libsecret) on Linux; Windows has no keychain writer in this release, so `fugaro pair` there stops at the keychain step and removes the device node it wrote.
- `fugaro user` changes the local configuration's launcher and operator lists, which the next `fugaro update` applies. No cloud-side role enforcement ships with it: a launcher and an operator still differ only by the IAM roles the installation grants them.
- Shared images arrive in 0.15.0: a `fugaro.yaml` whose workflow says `checkout: shared` is refused (`fugaro validate` says "shared images arrive in 0.15.0") and its launches fail, so a repository that wrote it uses `checkout: baked` or `checkout: clone` meanwhile. The installation's shared image registry is created by `fugaro update` and stays unused until then.
- Bitbucket brokering is not in this release: the proxy arrives in 0.15.0 and the flip in 0.16.0, so until then a Bitbucket run's job holds its own token and reads it as it always has, and `proxy: true` in the published block changes nothing such a run does. What 0.14.0 pinned is where the token may be sent, and `fugaro creds set` can already hold the token in the credentials service's bundle for that proxy, which stays dormant; because the bundle's git credential is named `bitbucket-token`, a model-credential account of that name is refused in the config.
- Model A/B testing is inert in this release: a challenger run publishes nothing, a run is a challenger only when a task hands it that role by hand, and no command samples a run, launches a pair or reads one back yet.
