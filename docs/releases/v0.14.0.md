- **Your commits can carry your name, and a run's commits carry the run.** A repository that opts in with `git.author: launcher` has its runs' commits authored by the person who launched them (a `commit_email` that is neither that person's own address nor a forge noreply address is refused at launch), and every commit a run pushes is born carrying `Fugaro-Run`, `Fugaro-Rigor` and `Fugaro-Model` trailers (the last where the stage pinned a model), so your history names the run, the rigor mode and the model behind a commit, and the runner's own commits run none of the repository's git hooks.
- **A phone can be paired with your installation, and unpaired again.** `fugaro pair` shows a QR code, waits for the phone's key, checks the code you type against it, and then sends the phone its configuration, its device token and the pairing's MAC key sealed to the phone's own key, while keeping this laptop's copy of that MAC key in the OS keychain; `fugaro pair ls` lists the paired devices and `fugaro pair revoke` removes one, and all three take `--json`.
- **The installation's people are editable one at a time.** `fugaro user ls` lists the installation's launchers and operators, and `fugaro user add MEMBER --role launcher|operator` and `fugaro user rm MEMBER --role launcher|operator` change one member of one list without restating the others, and `fugaro user rm` refuses to remove yourself from the operators or to leave the installation with none.
- **A Bitbucket token goes only where you allow it.** Policy version 4 carries the Bitbucket token's block — the repositories the project's credential may reach — together with the API roots you allow-list, and a cloud run refuses a Bitbucket API root that is neither Bitbucket's own nor one you listed.
- **Dependencies are installed apart from the source.** A repository's image now installs its dependencies on a layer that holds only the files the install reads, with the source in a layer above it, `image.key_files` adds files of your own that install reads (a patch a postinstall applies, a vendored toolchain) so a change to one rebuilds the image as a lockfile change does, and a launch warns when a job's image digest is not the one its build record holds.

### For operators

1. **Per installation, before upgrading:** keep the enrolled list: run `fugaro project policy show` and keep what it prints, because the republish below rebuilds `allow_repos`.
2. **Per machine:** upgrade the CLI on every machine that launches. The policy version moves to 4, and the two versions refuse each other: a 0.14.0 CLI refuses a launch against a published version-3 node until step 4 republishes it, and a 0.13.0-or-older CLI refuses a launch against a version-4 node with "upgrade Fugaro (fugaro upgrade)".
3. **Per onboarded repository:** refresh the image: `fugaro image refresh` in the repository's checkout (or `fugaro update --base base`). A job image built from 0.13.0 or older is not caught at launch: the run starts and its runner halts at bootstrap with "refresh the runner image". `fugaro image build` alone is not enough: it builds on the base image the local config already pins, whose runner is still the older release's.
4. **Per installation, in your own terminal outside any repository checkout:** republish the project policy. The order is the lockstep, because `fugaro project policy publish` refuses to overwrite a node written in another version: run `fugaro project policy publish --delete` to remove the version-3 node, then `fugaro project policy publish` to write the version-4 node. Read the diff the publish prints and repair the list against what step 1 kept, with `fugaro project repos add <owner/name>` and `fugaro project repos rm <owner/name>`: the delete removes the whole node, so entries added or removed by hand do not survive it.
5. **Per installation, if a Bitbucket profile mounts the token:** check the republish succeeded: the node now requires a profile that mounts `bitbucket-token` to write its own exact `allow_repos`, a subset of the block's, and to not be a GitHub profile. A node that breaks either rule is refused where it is published, and the fix is the local config and a publish, not the node by hand.
6. **Per installation, then per repository checkout:** run `fugaro update` once for the installation **before** `fugaro update --repo` in any repository's checkout, so the installation's shared image registry exists before a repository's re-converge grants its accounts on it; the registry is for 0.15.0 and nothing in this release writes to it.

### Known limits

- The authorship a launcher names and the trailers a run writes are a record and not proof: nothing verifies a `Fugaro-Run` trailer, no account owns the author a launcher claims, and a commit can be amended after a run pushes it. A repository whose `fugaro.yaml` sets `git.author` is refused at launch against a job image older than this release, which names the upgrade instead. Nothing a run commits is signed. The stamp hooks the runner writes live in temporary directories the run's agent can also write, since the agent and the runner share one user, as `SECURITY.md` says of everything that user can reach.
- Pairing completes only with the phone app's later release: this release writes the device node and the delivery, and nothing on the phone reads them yet.
- The laptop's copy of a pairing's MAC key is stored through `security -i` in the macOS keychain or through `secret-tool` (libsecret) on Linux; Windows has no keychain writer in this release, so `fugaro pair` there stops at the keychain step and removes the device node it wrote.
- `fugaro user` changes the local configuration's launcher and operator lists, which the next `fugaro update` applies. No cloud-side role enforcement ships with it: a launcher and an operator still differ only by the IAM roles the installation grants them.
- Shared images arrive in 0.15.0: a `fugaro.yaml` whose workflow says `checkout: shared` is refused (`fugaro validate` says "shared images arrive in 0.15.0") and its launches fail, so a repository that wrote it uses `checkout: baked` or `checkout: clone` meanwhile. The installation's shared image registry is created by `fugaro update` and stays unused until then.
- Bitbucket brokering is not in this release: the proxy arrives in 0.15.0 and the flip in 0.16.0, so until then a Bitbucket run's job holds its own token and reads it as it always has, and `proxy: true` in the published block changes nothing such a run does. What this release pins is where the token may be sent, and `fugaro creds set` can already hold the token in the credentials service's bundle for that proxy, which stays dormant; because the bundle's git credential is named `bitbucket-token`, a model-credential account of that name is now refused in the config.
- Model A/B testing is inert in this release: a challenger run publishes nothing, a run is a challenger only when a task hands it that role by hand, and no command samples a run, launches a pair or reads one back yet.
