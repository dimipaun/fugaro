- **Your commits can carry your name, and a run's commits carry the run.** A repository that opts in with `git.author: launcher` has its runs' commits authored by the person who launched them (a `commit_email` that is neither that person's own address nor a forge noreply address is refused at launch), and every commit a run pushes is born carrying `Fugaro-Run`, `Fugaro-Rigor` and `Fugaro-Model` trailers (the last where the stage pinned a model), so your history names the run, the rigor mode and the model behind a commit.
- **A phone can be paired with your installation, and unpaired again.** `fugaro pair` shows a QR code, waits for the phone's key, checks the code you type against it, and then sends the phone its configuration, its device token and the pairing's MAC key sealed to the phone's own key, while keeping this laptop's copy of that MAC key in the OS keychain; `fugaro pair ls` lists the paired devices and `fugaro pair revoke` removes one, and all three take `--json`.
- **The installation's people are editable one at a time.** `fugaro user ls` lists the installation's launchers and operators, and `fugaro user add MEMBER --role launcher|operator` and `fugaro user rm MEMBER --role launcher|operator` change one member of one list without restating the others, and `fugaro user rm` refuses to remove yourself from the operators or to leave the installation with none.
- **A Bitbucket token goes only where you allow it.** Policy version 4 carries the Bitbucket token's block — the repositories the project's credential may reach — together with the API roots you allow-list, and a cloud run refuses a Bitbucket API root that is neither Bitbucket's own nor one you listed.
- **Smaller changes.** A workflow's dependency key files are now copied before the source layer, so a change to one of them rebuilds an image exactly as a lockfile change does, and a launch warns when a job's image digest is not the one its build record holds.

### For operators

1. **Per installation:** before upgrading, keep the enrolled list: run `fugaro project policy show` and keep what it prints, because the republish below rebuilds `allow_repos`.
2. **Per machine, then per installation, then per repo checkout:** upgrade the CLI on every machine, then run `fugaro update` once per installation, then `fugaro update --repo` in each repository's checkout, so the shared image registry and its grants exist before the first shared refresh; the registry is for 0.15.0 and is unused until then, so nothing in this release builds a shared image.
3. **Per repo checkout:** refresh the images. The policy version moves to 4, and the two versions refuse each other: a 0.14.0 CLI refuses a launch against a published version-3 node, and a 0.13.0-or-older CLI refuses a launch against a version-4 node. A job image built from 0.13.0 or older is not caught at launch: the run starts and its runner halts at bootstrap with "refresh the runner image". Refresh each repository's image: `fugaro image refresh` in the checkout of each onboarded repository (or `fugaro image build --repo <owner/name> --workflow <name>`).
4. **Per installation, in your own terminal outside any repository checkout:** republish the project policy. The order is the lockstep, because `fugaro project policy publish` refuses to overwrite a node written in another version: run `fugaro project policy publish --delete` to remove the version-3 node, then `fugaro project policy publish` to write the version-4 node. Read the diff the publish prints and repair the list against what step 1 kept, with `fugaro project repos add <owner/name>` and `fugaro project repos rm <owner/name>`: the delete removes the whole node, so entries added or removed by hand do not survive it.
5. **Per installation:** if a Bitbucket profile mounts the token, check the republish succeeded: the node now requires a profile that mounts `bitbucket-token` to write its own exact `allow_repos`, a subset of the block's, and to not be a GitHub profile. A node that breaks either rule is refused where it is published, and the fix is the local config and a publish, not the node by hand.

### Known limits

- The authorship a launcher names and the trailers a run writes are a record and not proof: nothing verifies a `Fugaro-Run` trailer, no account owns the author a launcher claims, and a commit can be amended after a run pushes it. A repository whose `fugaro.yaml` sets `git.author` is refused at launch against a job image older than this release, which names the upgrade instead.
- Pairing completes only with the phone app's later release: this release writes the device node and the delivery, and nothing on the phone reads them yet.
- The macOS keychain writer stores the pairing key through `security -i`, and that writer is not live-checked by the release; the check is the owner's.
- `fugaro user` changes the local configuration's launcher and operator lists, which the next `fugaro update` applies. No cloud-side role enforcement ships with it: a launcher and an operator still differ only by the IAM roles the installation grants them.
- Shared images arrive in 0.15.0: nothing builds a shared dependency-layer image in this release, and the listing, the clean-up and the image-count warning are 0.15.0's too. A workflow that says `checkout: shared` validates and runs — its job is the one that clones the source at launch — but the image it runs is the repository's own derived image, not one shared with the other repositories on the same dependencies. The installation's shared image registry is created by `fugaro update` and stays unused until then.
- The Bitbucket proxy is not in this release either: a Bitbucket run's job still mounts its own token, and the brokering that moves that token into the credentials service arrives in 0.15.0. What this release pins is where the token may be sent.
- The model A/B shadow arm is merged and inert: a run is a challenger only when a task hands it one by hand, and nothing samples a run, launches a pair or reads one back yet.
