- **A person's own Claude subscription token is served at the workspace.** A person on a workspace's roster stores theirs once — `fugaro secrets user set claude-oauth-token --project <the workspace's project>`, from their own terminal, naming the workspace's own project rather than resolving a workspace name — and every run they launch in a member whose model route is the workspace draws on it ahead of the workspace's shared entries. The member's own admins turn the half on (`fugaro settings set personal_workspace_tokens true`, then their `fugaro update`): off is what every member is until then, and a workspace whose members leave it off serves exactly what it served before.
- **The token follows the model route, and only its owner's runs are served it.** A member whose runs still call a model credential of its own keeps using it, so the personal half reaches that member only once that credential is gone, and `fugaro doctor` says so for the caller's own project. The workspace's service admits a roster person on two routes of its own — the grant route, and the calls of a run under the slip it granted — and a person is served their own token and never another's.
- **`fugaro run` says which token the run draws on.** A launch in a workspace prints one line naming the caller's own token at the workspace's project, or a warning naming why this run spends the shared entries instead; `fugaro run --no-personal-token` launches one that never asks for a token. A grant the workspace's service cannot answer does not stop the launch: that run starts on the shared entries.
- **Being taken off the roster ends it within a minute.** A person removed from a workspace's roster is refused at their next grant and at the calls of a run already in flight, which halts with a reason naming the removal; a token they store in the window before the workspace owner's next `fugaro update` is served to nobody.
- **`fugaro doctor` reports the personal half**: whether the caller's own token is served at the workspace their project is a member of, and that a member's own model credential shadows it.

### For operators

**Run `fugaro update`.** It is the whole upgrade, on every machine, and nothing below is a second command. No run in flight is waited for or touched: the update reaches an installation whose runs are going exactly as it reaches an idle one, and it names the steps that can reach one.

**Turning the personal half on is configuration**, and nothing else is owed. For an installation that does not use the feature, the first `fugaro update` is the whole of it: nothing it holds changes, and a workspace whose members leave the switch off serves exactly what it served before.

1. **The workspace owner, once per installation.** Run `fugaro update`: it binds the invoke grant for each person on the workspace's roster. A person added to the roster later needs the next one.
2. **Each member's admin, per member.** Run `fugaro settings set personal_workspace_tokens true` and then `fugaro update` on the member's own machine: the update publishes the switch on the member's policy node, and the workspace's service — the only enforcer — reads it there. Until that run the member's half is off.
3. **Each person, once.** Store the token in the workspace's own project from your own terminal — `fugaro secrets user set claude-oauth-token --project <the workspace's project>`, the value on stdin or at the hidden prompt — and launch a run in a member. The launch prints one line naming the token it drew on.
4. **Upgrade the member's CLI before the `fugaro update` that publishes the switch.** A CLI of an earlier release refuses a policy node carrying the key it does not know, and says so; the key moves no policy version, so the upgrade is the whole fix.

### Known limits

- **Every workspace admin can read every person's token, and a token read is a bearer at Anthropic.** The personal containers sit in one project that the workspace's admins hold owner on, and nothing here revokes a value copied out of it. What bounds the reach is not technical: the workspace owner's choice of its admins, Google's own account protection, and the person rotating their token.
- **A member's admins can spend a person's subscription in that member**, for a slip claim taken while the person launched there — the claim deadline counted from the grant, plus 24 hours from the claim — and a grant replayed inside the hour a launch's identity token lives reaches only the members that person is a launcher of. Both bounds were accepted by the owner in words; the switch that exposes the subscription is set by the member's admins, the party that can then spend it.
- **A person's runs draw on their own subscription by default.** Whoever stores a token spends it unless they pass `--no-personal-token` for one run, and the single line the launch prints is the whole of the notice.
- **A run whose grant fails spends the workspace's shared entries**, which is the workspace's money through the member's allow-list and the meter. The alternative — refusing the launch — would let an outage of the workspace's service block every person who holds a token.
- **One subscription, more runs.** A token served to several members reaches its rate window sooner, and a personal token is never lent and never a pool's, so there is no workspace-wide pool to fail over within.
- **Whoever holds the intake's account, and every workspace admin, can replace or delete any person's token in one place** — one container per person and name in the workspace's project — and a deletion is not loud at the person's next launch: the grant answers that no token is held, and the run starts on the shared entries.
- **A roster person who holds a token learns whether a job account and a repository are a member's**, because the grant route answers a grant or a refusal for a named pair before the node is read. It is the workspace's own membership table, every refusal names nothing, and every answer is one audit line in the workspace's own record.
