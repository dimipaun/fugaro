- **A workspace can serve a person's own Claude token.** A person on the workspace's roster stores their token once at the workspace (`fugaro secrets user set claude-oauth-token --project <the workspace's project>`), and every run they launch in a member whose admins turned the personal half on is handed it: the launch prints one line naming the workspace, and `--no-personal-token` skips it for one run, which draws on the shared entries as every run did before (D3142). A person who holds no token launches exactly as before and sees nothing new, and where the repository's model route is the member's own credential, that credential is what the run uses (D3141).
- **The personal half is one switch per member.** `personal_workspace_tokens` is off until a member's admin writes it, so a member that leaves it off serves what it served before, and the setting reaches the workspace's service through the same `fugaro update` every other setting does.
- **A launch is never blocked by the personal half.** A grant that is refused, a workspace that cannot be reached, a container that is missing and a token that was deleted all start the run on the workspace's shared entries, and say so.
- **Offboarding follows the roster.** `fugaro workspace user rm` sweeps what that person stored at the workspace, and a run whose person has left the roster halts within about a minute instead of continuing (D3146).
- **A workspace can be offered a provider key.** `fugaro workspace share` accepts a provider key the workspace's bundle holds — the project's own or a named entry — and serves it to the members its allow-list names as a model entry; a repository credential is still refused, with a reason.

### For operators

`fugaro update` is the whole upgrade. **An installation that does not use this feature needs that one command and nothing else**: a workspace whose members leave the switch off serves exactly what it served before, and nothing an installation holds changes.

Turning the personal half on is configuration, in this order:

1. The workspace owner runs `fugaro update`, which binds the grants for the people on the roster. A person added later needs the next run (D2971).
2. Each member's admin sets the switch (`fugaro settings set personal_workspace_tokens true`) and runs `fugaro update`, which publishes it to the node the workspace's service reads.
3. Each person stores their token once, naming the workspace's own project: `fugaro secrets user set claude-oauth-token --project <the workspace's project>`.

### Known limits

- **A workspace admin reads every person's token, and a read token is a bearer at Anthropic.** Every workspace admin holds the workspace project's owner role, so each of them reads, replaces and deletes every personal token in one place, and a value one of them read spends that person's subscription from anywhere, with nothing here to revoke it. Fugaro's own commands never read a personal token under a person's prefix (D2825) — a rule about this CLI, not about IAM — and what bounds the reach is the workspace owner's choice of admins, `fugaro workspace user rm --admin`, Google's own account protection, and the person rotating their token.
- **A member's admins can spend a person's subscription for up to 24 hours from a slip's claim.** The claim is held to the member's own identity and job account, so those admins can take and claim a slip and spend it until it expires; the claim itself is bounded by a deadline counted from the grant.
- **A member's admin can act as a person who launched there for about an hour**, at every Cloud Run service the person can invoke and with or without a false address. A grant taken in that hour reaches only the members the person is a launcher of, which this release binds (D3145); the replay can ask for grants as the person and replace or delete that person's secrets at any intake that admits them, and can never read a token.
- **A person's runs draw on their own subscription by default**, and one subscription serves more runs as its rate window is reached sooner: there is no workspace-wide pool to fail over within. The one line `fugaro run` prints is the whole notice, and `--no-personal-token` is per run.
- **Whoever holds the intake's account, and every workspace admin, can replace or delete any person's token in one place.** A token someone else replaced is one the person did not write, the next run draws on it, and the launch does not say so.
- **A person removed from the roster stays admitted at the workspace's intake until the workspace owner's next `fugaro update`**, and anything they store there in that window is served to nobody.
- **A refused or failed grant starts the run on the workspace's shared entries**, which the workspace owner pays for rather than the person.
- **A roster person who holds a token learns whether a job account and a repository are a member's**, from the grant route's answer for a named pair. Every refusal names nothing, and only a token-holder learns it.
- **Every roster person sends their gcloud token to the workspace's service and its intake**, which the workspace's admins deploy and can replay for about an hour after each launch, reaching the person's projects outside the workspace: forge read mints, pairing, slips and intake writes, `fugaro_p_` secrets included where the person is an admin of that project.
- **Publishing the switch makes an older CLI in that project refuse to launch** until it is upgraded: upgrade the installation (`brew upgrade` or its own installer) and run `fugaro update`.
