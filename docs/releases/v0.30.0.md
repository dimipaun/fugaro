- **Shared, project-level jobs are the default job model, for GitHub and Bitbucket alike.** `fugaro update` gives a project the default shared-job profile it has none of, deploys its job and writes the project's catalog image, and a repository that profile admits applies no Terraform of its own from then on: adding or removing one is a config change, and the per-repository jobs an earlier release created are retired by `fugaro update` — for a Bitbucket repository on the update after the one that turns its proxy on. The image is the project's too, and a repository baked into it is a cache that saves the clone: what a job may reach is not decided by what the image holds.
- **What a run may touch is decided per run, by the credentials service.** A Bitbucket run's clone, fetch, push, submodules and LFS all travel through the project's proxy, which mints a token narrowed to the repositories the task names and swaps the workspace token in on each request; a GitHub run's access is a GitHub app installation token narrowed the same way, and the job holds no Bitbucket token at all.
- **A workflow's own `secrets:` is stored once for the project, and served to the runs allowed to read it.** `fugaro secrets set NAME` keeps the value in the project's own container, `fugaro secrets allow NAME PATTERN...` names the repositories whose runs may read it, and a run fetches the value at its start instead of mounting it, so a name like `db-password` is one value for every repository the entry admits rather than one copy per repository. An entry with `file: true` writes the value to a `0400` file and sets the variable to its path, and no such file is written in an independent review run. Nothing in a repository's own `fugaro.yaml` grants anything: a repository-level copy is accepted and ignored, as it has been since 0.19.0.
- **A person's own Claude subscription token is served at the workspace.** A person on a workspace's roster stores theirs once — `fugaro secrets user set claude-oauth-token --config <the workspace project's config file, which its owner hands them>`, from their own terminal, naming that project's own config rather than resolving a workspace name — and every run they launch in a member whose model route is the workspace draws on it ahead of the workspace's shared entries. The member's own admins turn the half on (`fugaro settings set personal_workspace_tokens true`, then their `fugaro update`): off is what every member is until then, and a workspace whose members leave it off serves exactly what it served before.
- **The token follows the model route, and only its owner's runs are served it.** A member whose runs still call a model credential of its own keeps using it, so the personal half reaches that member only once that credential is gone. The workspace's service admits a roster person on two routes of its own — the grant route, and the calls of a run under the slip it granted — and a person is served their own token and never another's.
- **`fugaro run` says which token the run draws on.** A launch in a workspace prints one line naming the caller's own token at the workspace's project, or a warning naming why this run spends the shared entries instead; `fugaro run --no-personal-token` launches one that never asks for a token. A grant the workspace's service cannot answer does not stop the launch: that run starts on the shared entries.
- **Being taken off the roster ends it within a minute.** A person removed from a workspace's roster is refused at their next grant and at the calls of a run already in flight, which halts with a reason naming the removal; a token they store in the window before the workspace owner's next `fugaro update` is served to nobody.

### For operators

**Run `fugaro update`.** It is the whole upgrade, on every machine, and nothing below is a second command. No run in flight is waited for or touched: the update reaches an installation whose runs are going exactly as it reaches an idle one, and it names the steps that can reach one.

**Shared dependency-layer images need no step of yours, and none ships here.** The registry they live in and the grants around it are the installation's one shared registry and the grants the project's catalog images already use, which `fugaro update` has created; a refresh can adopt a shared image the lock already holds. `checkout: shared` stays refused until a release ships the images themselves, so no repository is on one yet.

**On a project whose repositories still run per-repository jobs, the same update retires them, and asks you nothing: nothing here is a second command.** It creates the project's default shared-job profile where it has none, deploys its job, writes the project's catalog image and turns the Bitbucket proxy on, and it retires each migrated repository's whole root — its jobs, its registry, its build account and its check job — on the update that finds the facts it needs in place. For a GitHub repository that is this one; **for a Bitbucket repository it is the next one**: the proxy switch is published after the stage that would retire the root, so this update turns the switch on and the following one retires it — and if the credentials service's bundle holds no workspace token, the switch stays off and the retirement waits for the update after you store one. The retirement is confirmed at your own terminal, where being there is the confirmation: a pipe, `--json` and a coding agent's session confirm none of it and leave it, named in one line, for a later update you run at a terminal. A job with a run still going is left for a later update too, as is a repository whose profile, image or proxy is not in place yet — each with one line saying what retires it, and the repository keeping the jobs it has until then. A first shared run that fails is repaired by the same command: run `fugaro update` again and relaunch. Two things it prints rather than waits on: one line per repository still running its workflows on a per-repository job, naming the shared project job that replaces it, and one naming the command that stores the Bitbucket workspace token where the credentials service's bundle holds none — `fugaro creds set bitbucket-token--<workspace>` — with the proxy switch left off for that project until one is there.

**Turning the personal half on is configuration**, and nothing else is owed. For an installation that does not use the feature, the first `fugaro update` is the whole of it: nothing it holds changes, and a workspace whose members leave the switch off serves exactly what it served before.

1. **The workspace owner, once per installation.** Run `fugaro update`: it binds the invoke grant for each person on the workspace's roster. A person added to the roster later needs the next one.
2. **The workspace owner, per person.** Hand each person on the roster the workspace project's config file your own `fugaro update` wrote (`$XDG_CONFIG_HOME/fugaro/projects/<the workspace's project>.yaml`). A person who is not a launcher of that project has no other way to reach it: the address a token is sent to is read out of that file, and the one published to the runs bucket is refused.
3. **Each member's admin, per member.** Run `fugaro settings set personal_workspace_tokens true` and then `fugaro update` on the member's own machine: the update publishes the switch on the member's policy node, and the workspace's service — the only enforcer — reads it there. Until that run the member's half is off.
4. **Each person, once.** Store the token from outside any project's checkout — a selection naming another project than the checkout's is refused, and no flag recovers it — with the file the workspace's owner sent selected, from your own terminal — `fugaro secrets user set claude-oauth-token --config <that file>`, the value on stdin or at the hidden prompt — and launch a run in a member. The launch prints one line naming the token it drew on.
5. **Upgrade the member's CLI before the `fugaro update` that publishes the switch.** A CLI of an earlier release refuses a policy node carrying the key it does not know, and says so; the key moves no policy version, so the upgrade is the whole fix.
6. **The project's Owner, once per installation.** Run `fugaro update`: it copies each workflow secret's value into the project's own container and records which repositories may read it, which needs your own read on those copies — an operator without it is stopped with the fix. Nothing else is owed.

### Known limits

- **The Bitbucket shared job is not proven live yet, and the retirement does not wait for it.** The check that measures one end to end (Check 580, `docs/gcp-live-checklist.md`) failed on 2026-11-26 at the run and owes a rerun; the per-repository jobs go with this release's code rather than after it passes. Every retirement still holds on its structural precondition — the repository admitted by a deployed profile, the project image resolving, the proxy on for a Bitbucket repository — and on no execution running on the job, so a job a run is going on is left to a later update.
- **A repository's own copy of a secret is accepted and ignored.** A workflow's own `secrets:` is stored once for the project instead (`fugaro secrets set NAME`), and the repositories whose runs may read it are named by `fugaro secrets allow NAME PATTERN...` or by the operator-local `workflow_secrets` block; `fugaro validate` and `fugaro update` print one warning per repository that declares one, and the repository-scope `fugaro secrets` commands answer a notice and change nothing.
- **A shared project job's run carries no workflow secret.** The fetch turns the shared class away whole: the value reaches a per-repository coding job's run alone.
- **A workflow secret is served only to a repository an entry admits.** With no `workflow_secrets` entry, or one that lists nothing, no repository may read the project copy; a run left with no value stops at its start rather than starting without one.
- **Every workspace admin can read every person's token, and a token read is a bearer at Anthropic.** The personal containers sit in one project that the workspace's admins hold owner on, and nothing here revokes a value copied out of it. What bounds the reach is not technical: the workspace owner's choice of its admins, Google's own account protection, and the person rotating their token.
- **A member's admins can spend a person's subscription in that member**, for a slip claim taken while the person launched there — the claim deadline counted from the grant, plus 24 hours from the claim — and a grant replayed inside the hour a launch's identity token lives reaches only the members that person is a launcher of. Both bounds were accepted by the owner in words; the switch that exposes the subscription is set by the member's admins, the party that can then spend it.
- **A person's runs draw on their own subscription by default.** Whoever stores a token spends it unless they pass `--no-personal-token` for one run, and the single line the launch prints is the whole of the notice.
- **A run whose grant fails spends the workspace's shared entries**, which is the workspace's money through the member's allow-list and the meter. The alternative — refusing the launch — would let an outage of the workspace's service block every person who holds a token.
- **One subscription, more runs.** A token served to several members reaches its rate window sooner, and a personal token is never lent and never a pool's, so there is no workspace-wide pool to fail over within.
- **Whoever holds the intake's account, and every workspace admin, can replace or delete any person's token in one place** — one container per person and name in the workspace's project — and a deletion is not loud at the person's next launch: the grant answers that no token is held, and the run starts on the shared entries.
- **A roster person who holds a token learns whether a job account and a repository are a member's**, because the grant route answers a grant or a refusal for a named pair before the node is read. It is the workspace's own membership table, every refusal names nothing, and every answer is one audit line in the workspace's own record.
- **Every roster person's own gcloud token goes to the workspace's service and its intake, and the workspace's admins can replay it.** The token arrives at services those admins deploy on each launch and at the intake, and they — or a workspace service that has been compromised — can replay it for about an hour to reach that person's projects outside the workspace: forge read mints, pairing, slips and intake writes, `fugaro_p_` secrets included where the person is an admin of that project. It is accepted with the rest of this half, and nothing here revokes a replayed token.
