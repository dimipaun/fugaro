- **A managed project asks you nothing, at a terminal or through your coding agent.** In a project Fugaro created, `fugaro update`, `config publish`, `project policy publish`, `image refresh`, `accounts add` and `settings set`/`unset` no longer prompt for a typed confirmation; the gate still judges every plan and still refuses a loosening in its own words. If you would rather be asked, `--ask` puts a managed project's confirmations back for one run; it loosens nothing and changes nothing in a project that is not managed.
- **A run can code on a cheap provider model and review on your Claude subscription.** An `api-key` run whose coder is routed to a provider through the budget gateway can now run its senior review, and its adversarial review, directly on one Claude OAuth account on an Opus model. Name the account with `stages.review.claude_account` or the project's `default_claude_account` (a review on an Anthropic model picks the default up on its own); the token is mounted only on that run's job, given to the review stages alone and never to the coder's environment, and the review's dollars are recorded as notional and stay out of the budget's cap. `fugaro update` publishes the two keys to the project's policy node behind the typed project name.
- **A project's workflow secrets reach exactly the repositories you list.** The new `workflow_secrets` block names a secret a workflow needs and the repositories (a pattern like `acme/*` covers every repository it matches, now and later) that may use it; `fugaro secrets set NAME` stores one value for all of them and the init secrets stage no longer asks each repository for its own copy.
- **`fugaro secrets rm NAME` withdraws a project secret in one step**, deleting its container and its config entry behind one diff and one confirmation, and `fugaro secrets set NAME --allow-data-to OWNER/NAME` and `--proxy` write the policy keys without hand edits.
- **An OAuth account's spent allowance is now named and can move the run on.** A run that hits a subscription's usage limit says so in its reason instead of a generic agent error, and the dormant ordered failover between accounts advances on that signal.
- **A review can be launched as its own read-only job.** The review-only job variant, with its own service account and no push or secret access, and `fugaro run --pr N --review-run ID` (a fix round's brief carries an independent review's findings as bounded, quoted data) are in place; launching a review job stays refused until a later release admits it.

### For operators

1. Upgrade the CLI and run `fugaro update` in each checkout: it brings the installation, the published policy and the checkout to this release.
2. If a project sets `default_claude_account` (or `stages.<stage>.claude_account`) and a repository's review model is a Claude model, `fugaro update` creates one more job for that repository and mounts that account's token on it, and publishes the two keys after you type the project's name. A project that sets neither is unchanged.
3. The managed gate no longer asks anything of a managed project; pass `--ask` to a command to be asked once.

### Known limits

- The mixed run is covered by tests and has not been run live: the owner-run Check 290 needs this release's runner image, so it runs after the release, on an installation that has run `fugaro update`. Until it has, a mix is built and not yet seen end to end.
- A review's Claude subscription dollars are not capped by anything in Fugaro; the gateway caps the coder only.
- `fugaro review` is not registered in the CLI yet and its launch is refused until the credentials service admits a review job.
- A workflow secret's own removal and the rest of the config-management tasks (G3 to G13) are not in this release; repository-image removal is planned for 0.20.0.
