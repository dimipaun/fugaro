- **`fugaro rigor floor` is the command for a project's review floor, and these notes are its first announcement: it landed in 0.23.0, whose notes did not carry it.** The floor is the review levels a run of each rigor mode must run whatever a repository or a layer asks for: `fugaro rigor floor show` prints the floor this machine's config sets and `--json` prints the same answer as a document, `fugaro rigor floor set MODE LEVELS` writes one mode's floor from a comma-separated list of `l1`, `l2` and `l3` — the floor is the whole list, so a level it drops stops being required — and `fugaro rigor floor unset MODE` removes one mode's entry.
- **A floor reaches runs through the policy node your update publishes, and the read tells apart the two ways your file can name none.** `fugaro project policy publish` copies `review_floor` into the policy node a run fails closed on, so a change here is live at your next `fugaro update`, and `fugaro rigor floor show` says which of the two silences you have: a file that says nothing about the key keeps the published floor standing, while a written `review_floor: {}` is a floor of nothing, which is what takes the published one away — which is why removing a mode's last entry leaves the empty mapping rather than deleting the key.
- **The mode itself is one command too, and both of this family's writes are yours to run.** `fugaro rigor set MODE` writes the project layer's `defaults.rigor.default` and `fugaro rigor set MODE --area GLOB --name NAME` writes one area rule of `defaults.rigor.areas`, both into the one local layer file `fugaro update` publishes; both that command and `fugaro rigor floor` landed in 0.23.0, and the file they write has been published by update's `Layer` stage since 0.15.0, so this release adds no command here — what it adds is the floor's first mention in any release's notes. Both writes are refused in a coding agent's session, in every direction, and each ends by naming `fugaro update`.
- **A pull request of a run the installation's orchestrator launched can carry `fugaro:running`, `fugaro:failed` and a `spec:<name>` label, and the credentials service is what writes them.** `POST /v1/github/labels` performs each read and each write for the installation's daemon, minting its own installation token for that one act — scoped to the one repository and to `pull_requests: write` and `metadata: read` — so no credential leaves it, and a pull request the daemon does not own cannot be relabelled: every write is corroborated against the run id the daemon sends, and only the two status names and a `spec:` name of the allowed shape are accepted. It is GitHub only, since Bitbucket Cloud has no pull request labels; the `git.pr.labels` list you already set is unchanged, and a plain `fugaro run` is not labelled. The labels are created by the service on first use, so no command pre-creates them.

### For operators

1. **Per installation** — run `fugaro update` once, at your own terminal. It is the whole upgrade: nothing runs after it, and no repository's root has to be re-applied. Where your project publishes a project layer, the `Layer` stage this command already runs is where a rigor edit lands: it **seeds** your one local layer file (`~/.config/fugaro/projects/<project>.layer.yaml`) from the published object when the file is absent, and when the file is there and **`unpublished`** — its bytes differ from the published object — it prints the diff and rewrites the published layer from your file after your confirmation, so the one command both seeds and publishes. **Nothing is typed**: a confirmation is answered by being at your own terminal, a project whose marks say it is managed asks nothing, and declining leaves both your file and the published object exactly as they are. A file written from a published generation that has since moved is refused with the three-way state and offered a re-seed, rather than published over someone else's change.
2. **Per person, when you change a rigor mode or the review floor** — `fugaro rigor set` and `fugaro rigor floor` write this machine's own files and nothing else, and each ends by naming `fugaro update`, which is what publishes them; run them at your own terminal, because both are refused in a coding agent's session in every direction. Nothing else is required of you for these writes: no repository's root has to be re-applied, and there is no second command.
3. **Per installation, before a typed Bitbucket token's coverage is published** — upgrade the CLI **before** the `fugaro update` that publishes it. The policy node gains `bitbucket_tokens`, a new top-level member, and a CLI of the release behind refuses a top-level key it does not know and cannot launch against the project until it is upgraded: v0.25.0's notes recorded that limit, and its own `fugaro update` cannot write the key — the publisher lands here. Nothing else is asked of you here: a token stored with `fugaro creds set bitbucket-token--<name>` is in the bundle and in your config and serves no request until the `fugaro update` after the store, and an installation holding only the legacy `bitbucket-token` converges with the one command above and no read of the credential state store.
4. **Per installation, when a pool of yours names members of both halves of a run** — run `fugaro update`, and it asks nothing else. A pool is served by one half from this release: the credentials service selects among its members by tier and only breaks a tie by the listed order, while a run's own gateway holds one upstream per stage and never retries a call across a secret, so a pool naming a member of each can serve an order that means nothing. The update shows the diff and applies it: a pool that crosses becomes two, one per half, each keeping its own members in the order it listed them and the pool's strategy and owner, and each craft that named the pool is repointed to the half its own model routes to. It does the same to the published node, whose policy version moves to 9 — which is why the same update redeploys the credentials service in the stage that follows. A run in flight is not asked to finish first: its record, its ledger and its counters stay exactly as they are. Nothing else is asked of you, and there is nothing to delete or republish.
5. **Per installation, for the status labels** — run `fugaro update` once, at your own terminal. It redeploys the credentials service, which is the identity that performs every label read and write, and that is the whole of the step: the labels are created by the service on first use, so nothing pre-creates them, no repository's root has to be re-applied for this, and there is no second command.

### Known limits

- **The daemon's half of the status labels is not in this release.** The capability, the service's `POST /v1/github/labels` route and the syncer are here; the client the daemon would ask the route with and the tick that computes the difference are not, so no pull request carries `fugaro:running`, `fugaro:failed` or a `spec:` label yet. What this release gives an installation is the route, deployed by the `fugaro update` above.
