- **A craft's model is what its stages run, and the resolved model is the one every reader names.** A run's five crafts — coder, first-line review, senior review, security review and the merge judge — each carry a model and an **access**, and the model half reaches a run in this release: a stage's model is the first rung that answers, most specific first — a task's model grade, a review level's own model (`agent.levels.l1/l2/l3.model`), **the craft's model**, `agent.models.<role>`, `agent.model` — and the resolved model is written where the run's own readers already read a stage's model, so the pin the agent is given, the gateway's allow-list, the price row `cost.go` charges and the record's `stages[].model` name one answer. A craft that names no model changes nothing at all: `agent.models` and `agent.model` keep every meaning they have for it, and a craft naming a model no route claims or no price covers is refused where your own pins are judged, never at the provider with a billable failure.
- **Your publish is what puts a craft's credential in front of a call.** `fugaro project policy publish` copies this installation's `crafts`, `craft_credentials` and `craft_pools` onto the policy node (`config/policy/shared`) where an earlier release kept the node's own, and a run is served from the node: the credentials service reads a pool's members there on every call and the run's own gateway reads the craft whose stages it runs, so the node's own member order — not your local file alone — is what serves a pool's calls. A project whose config states none publishes none, so its node is byte for byte what it was; the node has carried these three members since 0.24.0, so it is the pool rule below and not them that moves its `version`.
- **A key is a credential you can declare, and the half its type names is what serves it.** `fugaro accounts add <name> --type anthropic` and `--type openrouter` are this release's two new types: the value is read **only** from stdin or, at your own terminal, a hidden prompt — never from an argument, a flag or the environment, and never echoed back — and it is stored project-wide under the credential's own derived name, `credential-<name>-key`, rather than the account's `claude-oauth-token-<name>`. An `anthropic` key is served by the credentials service and an `openrouter` key by the run's own gateway, whose provider entry of the same name gives it its base URL, its prices and its `allow_data_to`; **neither is served by the `add` alone** — the service reads only the bundle `fugaro creds set credential-<name>-key` writes at your own terminal, so the `anthropic` key authenticates nothing until that command has run, and the gateway's job mounts the `openrouter` key once a `providers.<name>` entry exists; `fugaro accounts ls` names each credential's serving path, and `fugaro accounts rm` clears the crafts whose access named it while refusing a name a pool still lists, naming the `fugaro accounts pool rm` to run first. A key credential rides no job of its own, so `--profile` is refused with either type, and so is a name a profile already lists; `vertex` stays built in and `openai` and `codex-oauth` keep refusing as not yet.
- **A pool stays on one half of a run, and `fugaro update` splits one of yours that crosses.** A pool's members are all served by the same half from this release — the credentials service selects among them by tier and only breaks a tie by the listed order, while a run's own gateway holds one upstream per stage and never retries a call across a secret — so a pool naming a member of each half is refused where it is written (`fugaro accounts pool add`) and where the node is read (`config.ValidatePublishedPools`, which the runner, the credentials service, `fugaro doctor` and `fugaro update` itself all meet). A pool an earlier release wrote is repaired rather than refused, in your config and on the published node, by the `fugaro update` of step 7 below.
- An installation that runs the coordinator's job now keeps its licence up to date on its own: `fugaro update` creates the renewal job and a daily schedule for it, so a licence does not lapse between visits.
- The renewal job runs as an account of its own that can read the key, write the key back, read and add the renewal secret, and read the two objects that tell it which installation it is renewing for — the project marker and the published config, the way any machine with no checkout finds them. Nothing else of your project.
- The job is created on every installation that deploys the coordinator's job, whether or not a licence was bought: with no key it does nothing and says nothing, and `fugaro licence set` is what gives it one.
- **`fugaro rigor floor` is the command for a project's review floor, and these notes are its first announcement: it landed in 0.23.0, whose notes did not carry it.** The floor is the review levels a run of each rigor mode must run whatever a repository or a layer asks for: `fugaro rigor floor show` prints the floor this machine's config sets and `--json` prints the same answer as a document, `fugaro rigor floor set MODE LEVELS` writes one mode's floor from a comma-separated list of `l1`, `l2` and `l3` — the floor is the whole list, so a level it drops stops being required — and `fugaro rigor floor unset MODE` removes one mode's entry.
- **A floor reaches runs through the policy node your update publishes, and the read tells apart the two ways your file can name none.** `fugaro project policy publish` copies `review_floor` into the policy node a run fails closed on, so a change here is live at your next `fugaro update`, and `fugaro rigor floor show` says which of the two silences you have: a file that says nothing about the key keeps the published floor standing, while a written `review_floor: {}` is a floor of nothing, which is what takes the published one away — which is why removing a mode's last entry leaves the empty mapping rather than deleting the key.
- **`fugaro update` says what it is doing while it looks for runs in flight, and its note about them is short.** The check names itself on the screen (`Checking for runs in flight`) rather than leaving you at a blank one, and the note under it is the count — the update waits for none of them and changes nothing they hold — followed by one short line per step that can still reach a run, instead of the paragraph it used to be. Nothing else changes: the update waits for none of them, asks none of them to finish, and never stops over one.
- **The mode itself is one command too, and both of this family's writes are yours to run.** `fugaro rigor set MODE` writes the project layer's `defaults.rigor.default` and `fugaro rigor set MODE --area GLOB --name NAME` writes one area rule of `defaults.rigor.areas`, both into the one local layer file `fugaro update` publishes; both that command and `fugaro rigor floor` landed in 0.23.0, and the file they write has been published by update's `Layer` stage since 0.15.0, so this release adds no command here — what it adds is the floor's first mention in any release's notes. Both writes are refused in a coding agent's session, in every direction, and each ends by naming `fugaro update`.
- **A pull request of a run the installation's orchestrator launched can carry `fugaro:running`, `fugaro:failed` and a `spec:<name>` label, and the credentials service is what writes them.** `POST /v1/github/labels` performs each read and each write for the installation's daemon, minting its own installation token for that one act — scoped to the one repository and to `pull_requests: write` and `metadata: read` — so no credential leaves it, and a pull request the daemon does not own cannot be relabelled: every write is corroborated against the run id the daemon sends, and only the two status names and a `spec:` name of the allowed shape are accepted. It is GitHub only, since Bitbucket Cloud has no pull request labels; the `git.pr.labels` list you already set is unchanged, and a plain `fugaro run` is not labelled. The labels are created by the service on first use, so no command pre-creates them.
- **A Bitbucket repository your published policy proxies carries no Bitbucket token in its run's container any more.** Where the policy admits the repository with `proxy: true` and the repository runs through the credentials service, `fugaro update --repo` in that checkout gives the job up both the container's mount of `bitbucket-token` and its account's access to it, so the copy an agent used to read out of the runner's `/proc` is not there to read. Every git and Bitbucket API call of such a run is served by the service instead, which puts the token on the wire for that one repository and that one branch.
- **The drop is per repository**: a project may proxy one Bitbucket repository and leave the rest alone, because the flip follows the published node's block for that repository and never a switch of the installation's. Every Bitbucket repository the policy does not admit with `proxy: true` keeps its mount, its accessor and its own token, whichever installation it belongs to.
- **The build account keeps its own copy until S4**: a build's Dockerfile can still reach the token and a rotation still writes both copies, so rotating one is still two writes.
- **`fugaro update` will not drop the mount of a proxied repository whose bundle holds no token.** It refuses that one repository's drop and names the one command that stores the token, so a proxied run is never left with nothing to fetch a credential from; `fugaro doctor --check-bitbucket-token` reads what the bundle holds today and names the same command.
- **A catalog entry's Dockerfile can build with the repository's own files, so a `COPY` finds them exactly as it does in CI.** A `dockerfile` entry's `source` may name a `context:` — a directory of the entry's own repository — and the entry's build hands that directory to Docker as the build context, which is what a Dockerfile that copies anything out of the repository needs. The Dockerfile and its context are **one checkout at one commit**: the copy is read at the commit the entry's branch resolves to, the two are staged together before anything is built, and the entry's record — the commit the image's revision label names, and the commit the nightly check rebuilds it at — names that one commit and never a branch head. The nightly check follows the directory as well: what moves the entry's rebuild is the staged context's own digest, the rebuild runs at the commit that copy staged, and the check job therefore still reads no repository and holds no repository credential. **An entry that names no `context:` is built byte for byte as it was**, and a job image older than this release stops a run at bootstrap rather than meeting the member as a key it would silently ignore (the operator note below is the whole of what that costs you).

- **`fugaro review --pr N` works on a project that publishes no profiles, and the job it runs on is one `fugaro update` deploys.** The review used to run only on the review-only variant of a shared project job, so a repository whose workflow resolves none — a baked workflow, or a project with no `profiles:` block — had nothing to run on and the launch was refused. The installation now carries its own implicit default review-only job, one per provider, deployed by the update below exactly as every other job is, and `fugaro review` resolves a review onto it: no profile to declare, and no profile is written into your config for it. It is the same isolated container it always was — it mounts no credential at all, its read-only git token and its model calls both come from the credentials service, and a review never runs in the repository's coding job. Three things about it stay as they were: it serves the **default** account alone (a review that names another with `--token` is refused, because the service pairs a caller with the account its job was deployed for), the run places itself in it by the project's **published policy** (so a project that has published none is still refused, naming `fugaro project policy publish`), and a **Bitbucket** repository is served by it only where the published policy brokers that repository's access (`proxy: true` on its `project_secrets.bitbucket-token` entry).

- **`fugaro escalation ls` and `fugaro escalation show ITEM` read the ladder a stalled pull request is walked up, and the whole of what wrote it is one state node.** A pull request that stops converging has rungs above it — a rebase and re-test, a resume, one stronger single pass, a merge with follow-ups under a gate, and a split as the last resort — and each move the ladder makes is written to the orchestrator's ledger with the rung, the reason it entered it, the head it was decided at and the runs it spent. `fugaro escalation ls` lists every pull request the ladder has acted on with that rung, the reason, how long it has been going, how many of the ladder's own runs it has spent and what its own runs have cost; `fugaro escalation show ITEM` prints one in full, its transitions oldest first. Both only read — no command moves a rung, readies a draft or merges — `--json` prints a versioned document, and an item whose runs this machine cannot read shows its age and its cost as unknown rather than as a smaller figure. The machine's own `escalation.*` keys set the rungs' thresholds, the cost ceiling and the two model grades the upper rungs run on (`strong` and `strongest`, which stay project-layer keys).
- **A rung 3 merge is decided before any token is asked for, and everything it cannot read refuses it.** The one merge in Fugaro that would not be a person's is the orchestrator daemon's, and it is the last rung rather than a mode: a stalled pull request whose run is over, whose commits are pushed with a changed-path set that is neither empty nor truncated, whose CI is green, whose whole changed-path set is `Routine` and which has no blocking finding is merged with the findings it left open filed as follow-ups — every one of those readings made at **one** head SHA, which the merge call names again, so a push in between refuses the merge, and any input the gate cannot read refuses it too. The mode decides only **who is told**: a ceiling that is not a merge, every Critical item and every refusal raise the question for a person instead. A pull request that is still a **draft** is readied and merged at the head it readied unless the machine turns `escalation.ready_drafts` off (`fugaro settings set escalation.ready_drafts false`), which ships **on**.

- **`fugaro project repos status` now says when a repository's credential has no version, and names the command that stores one.** It is the doctor for a repository's enrolment in a project: one row per fact that decides whether a run of it can start — the App installation, the credential container's enabled version, the account tokens, the image map entry, the admission, the credentials service, the job and its `run.invoker` grant, this machine's config entry and the last run — each failing row naming the one command that puts it right, read-only on every path and nonzero when something blocks a launch. `fugaro project repos add` does the whole enrolment behind one typed confirmation, `rm` is its inverse and says what it removes, what it keeps (the repository's Terraform state and its root's own IAM members) and what it deliberately leaves, and `ls --json` and `status --json` are the two reads of the group a desktop console may make. **No operator step**: an installation that never runs `add` converges through `fugaro update` exactly as it does today, one that runs `add` converges to the same tree, and nothing here needs a backfill, a secret change or a rollout order.

- **`fugaro followups` works in a coding agent's session, the way `fugaro run` does.** It finds its git credential where the installation keeps it, the credentials service's read mint or the App key at your own terminal, so filing a merged pull request's follow-ups from an agent no longer stops on a missing GitHub App ID.

- **`fugaro update` finishes when the Bitbucket proxy switch meets a moved node, and keeps a project's proxy when this machine's config has no bitbucket-token entry.** In the first case the switch waits for the next update; in the second the node's proxy block stays as published, so proxied runs in flight are not stranded.

### For operators

1. **Per installation** — run `fugaro update` once, at your own terminal. It is the whole upgrade: nothing runs after it, and the one per-repository `fugaro update --repo` of step 3 is the same command run from a checkout. Where your project publishes a project layer, the `Layer` stage this command already runs is where a rigor edit lands: it **seeds** your one local layer file (`~/.config/fugaro/projects/<project>.layer.yaml`) from the published object when the file is absent, and when the file is there and **`unpublished`** — its bytes differ from the published object — it prints the diff and rewrites the published layer from your file after your confirmation, so the one command both seeds and publishes. **Nothing is typed**: a confirmation is answered by being at your own terminal, a project whose marks say it is managed asks nothing, and declining leaves both your file and the published object exactly as they are. A file written from a published generation that has since moved is refused with the three-way state and offered a re-seed, rather than published over someone else's change.
2. **Per person, when you change a rigor mode or the review floor** — `fugaro rigor set` and `fugaro rigor floor` write this machine's own files and nothing else, and each ends by naming `fugaro update`, which is what publishes them; run them at your own terminal, because both are refused in a coding agent's session in every direction. Nothing else is required of you for these writes: no repository's root has to be re-applied, and there is no second command.
3. **Per installation, before a typed Bitbucket token's coverage is published** — upgrade the CLI **before** the `fugaro update` that publishes it. The policy node gains `bitbucket_tokens`, a new top-level member, and a CLI of the release behind refuses a top-level key it does not know and cannot launch against the project until it is upgraded: v0.25.0's notes recorded that limit, and its own `fugaro update` cannot write the key — the publisher lands here. Nothing else is asked of you here: a token stored with `fugaro creds set bitbucket-token--<name>` is in the bundle and in your config and serves no request until the `fugaro update` after the store, and an installation holding only the legacy `bitbucket-token` converges with the one command above and no read of the credential state store.
4. **Per context repository a run should read** — install the installation's GitHub App on it. This release's runner clones the repositories a task names with `--context` (C5c), and the token it clones them with is a read-only installation token: one per App installation, naming exactly the repositories that installation covers. A repository the App is not installed on is one no run can be given a read-only token for, so the run ends at bootstrap naming it — the install is a GitHub-side step, once per repository, and nothing in Fugaro does it for you.
5. **Per installation whose repositories run with the credentials service** — redeploy that service, and it is the `fugaro update` above: the service is a resource of the installation's own Terraform root, which that command applies (`deploy/terraform/gcp/modules/installation/credentials.tf`), and the read this release adds is a route of it, so an installation that redeploys nothing serves no context token. What a run needs besides is the switch the service is reached through, which is per repository — and the launch is where it is judged: a launch naming `--context` on a repository whose job carries no service address is refused before any execution exists, naming `fugaro update` and the `agent.auth: cascade` setting that puts one there, so a repository the service does not serve is one you read context repositories from nowhere today.
6. **Per installation, for the status labels** — run `fugaro update` once, at your own terminal. It redeploys the credentials service, which is the identity that performs every label read and write, and that is the whole of the step: the labels are created by the service on first use, so nothing pre-creates them, no repository's root has to be re-applied for this, and there is no second command.
7. **Per installation, when a pool of yours names members of both halves of a run** — run `fugaro update`, and it asks nothing else. A pool is served by one half from this release: the credentials service selects among its members by tier and only breaks a tie by the listed order, while a run's own gateway holds one upstream per stage and never retries a call across a secret, so a pool naming a member of each can serve an order that means nothing. The update shows the diff and applies it: a pool that crosses becomes two, one per half, each keeping its own members in the order it listed them and the pool's strategy and owner, and each craft that named the pool is repointed to the half its own model routes to. It does the same to the published node, whose policy version moves to 9 — which is why the same update redeploys the credentials service in the stage that follows. A run in flight is not asked to finish first: its record, its ledger and its counters stay exactly as they are. Nothing else is asked of you, and there is nothing to delete or republish.

8. **Per machine, for the orchestrator daemon** — run `fugaro update` at your terminal; it installs the orchestrator daemon on this machine if it is not there, and one machine per project drives runs. The install asks nothing: the unit and the path it is written at are one line of the plan that same `fugaro update` shows you before it applies anything, and the file it writes is your own, under your home — no system path, no root, no `sudo`, no network. A run with no terminal on it, or one in a coding agent's session, writes no unit and says so in one line, and your own next terminal `fugaro update` installs it; a machine with neither launchd nor a systemd user session gets one line too and the update still succeeds. Every machine may carry one: the project's lease keeps exactly one of those daemons live and the others on standby, so a second machine needs nothing more than this command, and a machine that already has the unit gets its unit file rewritten to this release's version, exactly as before.

9. **Bitbucket repositories your published policy proxies** — run `fugaro update --repo` from the checkout of each one. That run is what takes the token's mount and the job account's accessor away, and it is one command like any other update: the delete is fugaro's own decision, so the run needs no flag for it and asks nothing beyond what every update asks at your own terminal. Where the bundle holds no token yet, the update refuses that repository's drop and prints the command that stores it, which is yours to run at your own terminal; there is no step before this one.
10. Nothing to run for a Bitbucket repository your policy does not proxy: it keeps its mount, its accessor and its own token, before and after this update.
11. **Per repository of an `api-key` or `oauth` workflow whose policy is switched on** — run `fugaro update --repo` from its checkout, and it is the same one command. That run is what takes the Anthropic key's and the Claude OAuth token's mounts, and the job account's accessors on them, away (B2.7, D2072), and it fires only where the repository's own root is re-applied with the credentials service switch on **and** the project's published budget mode is `observe` or `enforce`: **a repository that is not switched keeps every mount, before and after this update**, and so does a `vertex` repository, which the switch never admits. A run of a switched repository needs a job image whose runner reads its model credential from the service — the 0.25.0 base image or newer — and a launch on an older one is refused before any execution exists, naming that release and `fugaro update`. A provider key (`FUGARO_PROVIDER_KEY_*`) stays mounted either way: the service serves the Anthropic key and the account's token, never a provider's own key. And `fugaro project policy publish` refuses to lower the project's budget mode to `off` while such a repository is switched, because its job would then hold no mount and every run of it would halt until `fugaro update --repo`.

12. **Per installation whose local config prices a cache dimension** — run `fugaro update` once, at your own terminal, and it is the same command: it renames the old cache-price keys (`cache_read`, `cache_write_5m`, `cache_write_1h`) to `cache_read_mult`, `cache_write_5m_mult` and `cache_write_1h_mult` in your own config file, in place, keeping every price you set, and it asks nothing. A comment you wrote on one of those three keys goes with the old key — the rename is a key-line splice, and the file this command replaced is kept beside it, so nothing you wrote is lost. The old names keep their meaning, so a file this command cannot rewrite is left as it is with one warning naming the keys rather than stopping the upgrade — there is no second command either way. That command and `fugaro validate` also print one warning per price below the cheapest endpoint the built-in catalog prices that model's dimension at, naming both figures: nothing is refused, and the price you wrote stays the price.
13. **Per installation, when the governance defaults are too tight for a repository** — the guardrails a repository can write already bound a stage's own time, and from this release the rest of the `governance:` block stops a run: a stage that spends its share of the run's per-run cap or passes its stage token ceiling, a review that spends more calls on the implementation than the ratio allows, a stage that starts more distinct sub-agents than its maximum, and a review round whose range has moved off the run's own commits each end the run at once, with a checkpoint report on the record and the draft pull request that carries it — never a silent kill. The defaults that bound them are Fugaro's own and are shares of the cap you already set: the implementation gets 0.7 of the run's per-run cap, review 0.5, the fix rounds 0.5 of the implementation's own share, review may spend at most `max(20, 5 × the implementation's calls)`, and a stage may start 5 sub-agents, or 3 for a run a plan graph dispatched at `trivial` or `small`. None of them moves the per-run cap, which stays the ceiling they all sit under, and a run with no per-run cap is bounded by none of the four, because a fraction of nothing is not a budget. Where a default is too tight, loosen it in the project layer — the one layer that may, and the block a run starts under — by writing the key in your local layer file and running `fugaro config publish FILE`, at your own terminal and per installation; a repository's own `fugaro.yaml` and the branch a run checks out may only tighten, and a looser value there is dropped with a warning that names the key. The defaults that stop runs are in the business-licensed part of the binary, so a job image built without it warns once and ignores the block; an `oauth` run makes its calls outside the gateway and is not stopped live by any of these, its stage figures being what its reports say afterwards.
14. **Per installation whose job image is older than this release, for a project whose catalog carries a `context:`** — run `fugaro update`, at your own terminal, and it asks **nothing else**. The member reaches a run inside the project's policy node, and this release publishes that node at policy version 9 (step 7 above is where the version moves): a job image older than 0.26.0 — a 0.25.0 image understands version 7 — refuses the node at bootstrap with the version sentence: `the project policy is version 9; this Fugaro understands version 7; refresh the runner image (fugaro update)`, followed by `policy version 9 arrived in fugaro 0.26.0`. The same command is the whole of the fix, and it needs no flag of yours: it moves the installation's base image to this release, and it rebuilds the catalog images of the checkout it runs in whose recorded base predates this release — one `rebuilt N catalog image(s) FROM this release's base image: …` line — which is what gives a `context:` entry a job image that reads the member. An entry whose build belongs to another repository's checkout is named with the `fugaro image build <entry>` to run there, because such a build runs as that repository's build account with its own credential and secrets; a workflow's own derived image — one a repository's CI builds — is moved by `fugaro image refresh`. Nothing is deleted, no node is republished by hand, and an installation whose job image is this release's or newer reads a `context:` entry exactly as it reads any other entry.
15. Upgrade the CLI and run `fugaro update` once per installation. It applies the licence job, its schedule, its account and the empty container the renewal secret is written into — with no question on a managed project, and everywhere else inside the confirmation `update` already asks for a plan that creates something.
16. Nothing else. An installation with no licence bought yet needs no step: the job runs daily, finds no key and stops.
17. **Per installation, for the credentials service's issue route** — grant the GitHub App the **Issues read-and-write** permission and accept it on each installation. The service reads a repository's open issues and opens new ones with an installation token it mints itself, so no token leaves it and no run holds the write — but the installation must grant it, and that is a GitHub-side step `fugaro update` cannot take: the update deploys the route, and nothing in Fugaro changes the App's permissions for you. Until it is granted, `fugaro doctor` fails its `github-app` check per repository, naming the grant and the exact fix ("change Issues to Read and write, then accept the new permission on the installation"), and `fugaro setup` holds the first billable image build of a GitHub repository with the same fix rather than billing it. A run's own token still asks for the read alone, so nothing else about the installation changes.
18. **Per installation, so `fugaro review --pr N` works on a repository with no profile** — run `fugaro update` once, at your own terminal, and it is the whole step. That run deploys the installation's implicit default review-only job — one per provider, named from the default profile, the provider and the default account (the review variant the `standard` profile would have if your project declared one, so its name is the job name you already know with the review suffix on the account), with its own service account and the row of the credentials service's review table that admits a review caller, so a project that has published no profiles gets a job a review can run on from this one update: nothing is typed, no profile is written into your config, and no repository's root has to be re-applied. What the job is composed behind is the same state the rest of the credentials-service work needs — the service opted in, a repository of that provider recorded, exactly one GitHub App ID recorded for the GitHub job, and no profile's own review variant already holding the name — and an installation whose config can no longer compose it keeps the job its record holds rather than losing it. Where you read it is `fugaro update --print-vars`, whose `project_review_jobs` is the set of the jobs this command hands Terraform — not `fugaro doctor`, whose job census is the jobs your own `profiles:` declare and so names the review variant of a profile you wrote, not this one.

19. **Per installation, for the escalation ladder** — run `fugaro update` once, at your own terminal, and it asks nothing new: no flag, no question and no second command. The daemon raises its own state node on the first read after the update — a node written by an earlier release is migrated up to this release's schema version in memory and the next save writes it there — so nothing is typed and no node is edited or republished by hand. One thing stays as it is, and one thing is on: `escalation.ready_drafts` ships **on**, so a daemon that meets a stalled **draft** pull request whose gate passes readies it and merges it at the next tick (a machine that wants the question instead runs `fugaro settings set escalation.ready_drafts false`), and the App's **merge** permission is yours to grant per repository on GitHub — a step no Fugaro command can take (D2048, Check 542). Neither is needed for this release to be installed, because the ladder is not switched on in it (the known limit below).

19. **Per checkout whose `docs/backlog/` folder still holds items** — run `fugaro update` in it, at your own terminal, and it is the whole step: that run moves the folder's open items into the project's backlog, one item per file under the file's own id, and prints one line with the count. Each folded item is queued and unapproved, so it runs once a person approves it (`fugaro orchestrator patch`) and not before. A second update over the same checkout folds nothing while the backlog knows the id it wrote — in its work list, and afterwards in the ids it has archived, which is where a folded item goes once it has finished — and the folder is left exactly where it is: it is history from this release, `fugaro backlog add` files into the backlog instead, and there is nothing to delete or run afterwards. Outside a checkout, and in a coding agent's session, the update folds nothing. That memory is bounded, and one item is the exception: one folded, finished and since aged out of the archive is filed again by a much later update in that checkout — queued and unapproved like the first, so nothing runs before you see it.

20. **Per installation whose daemon presents itself at the credentials service** — run `fugaro update` at your own terminal, and it asks nothing new. That one command renders the daemon's account into the service's caller class and grants it `roles/run.invoker` on the service, both from the installation's own `orchestrator` block, so an installation that runs a daemon is one where the daemon is admitted, and an installation that runs none plans exactly what it planned before. **What that command cannot write is the right to mint the daemon's token**: the installation grants nobody `actAs` on that account, so a machine whose own credential cannot already impersonate it needs `roles/iam.serviceAccountTokenCreator` on the daemon's account — `gcloud iam service-accounts add-iam-policy-binding <the daemon's account> --member=user:<you> --role=roles/iam.serviceAccountTokenCreator`, once per machine — and a daemon that cannot mint prints one line naming that grant and that command rather than labelling nothing quietly. Nothing else is asked of you, and there is no second command.

### Known limits
- **The escalation ladder is built and the daemon does not walk it yet.** The rungs, the deterministic merge gate, the ledger every rung transition is written to, `fugaro escalation ls` and `fugaro escalation show ITEM`, the machine's own `escalation.*` keys and the daily digest's Escalation section are all in this release; the daemon's own cycle is built without the ladder's seam, so no rung is walked, `fugaro escalation ls` answers an empty list, no report prints the digest's section, and **Fugaro merges nothing today** — a person merges every pull request, and the App's merge permission above is not needed yet.
- **The daemon's half of the status labels is wired in this release, and no installation has proven it live.** The capability, the service's `POST /v1/github/labels` route, the syncer, the client the daemon asks the route with and the daemon's own identity at the service are all here, so a daemon on an installation that holds the orchestrator block asks the route for every label read and write; what is not is the live proof — the check that would show a labelled pull request is owner-run and not written yet, and the machine that runs the daemon needs `roles/iam.serviceAccountTokenCreator` on the daemon's account (step 19) before its token can be minted — so no pull request carries `fugaro:running`, `fugaro:failed` or a `spec:` label yet. What this release gives an installation is the route and the daemon's identity to it, both from the `fugaro update` above.
- An installation that has not turned the coordinator's job on gets no renewal job — the job runs the coordinator's image, which such an installation does not have. `fugaro licence status` says renewal is by hand there.
- The job renews a licence whose renewal secret the installation holds. A key that arrived without one is renewed by hand, by pasting the next key with `fugaro licence set`.
- **A plan graph that carries the graph's new `tier` field is refused by a CLI of the release behind.** The field is the expectation a task is run at, one of `trivial`, `small`, `medium` and `large`; the graph's reader decodes a document strictly, so an earlier CLI meets the key as an unknown field and refuses the artifact rather than drawing it. Upgrade the CLI before reading a plan graph written by a newer one; a graph written before this release reads unchanged, because the field is additive.
- **No Fugaro command writes the `context:` member yet.** `fugaro image add` has no `--context` flag, so a `context:` is written by editing this machine's project config — the file the image catalog commands read and `fugaro update` publishes — and an entry that arrives that way is built and checked like any other. Reading a catalog back, promoting an entry and adding one all keep a `context:` an entry already carries: they edit the entry's own members and never the source's.
