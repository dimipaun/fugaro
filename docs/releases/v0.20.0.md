- **A workflow that runs a catalog image builds nothing of its own.** A workflow that names a catalog entry no longer gets a per-repository build or a confirmation for one, a nightly rebuild leaves a base that did not change where it is, and `fugaro image add --image REF` writes a prebuilt-image entry without hand-editing the config.
- **The cloud senior review is built, and not yet switched on.** A review runs in its own read-only job variant with its own service account; `fugaro review` is registered; a fix round's brief carries a review's findings only after the credentials service has verified the verdict's signature against the pull request's current head; a review run's model path is its class and not `agent.auth`; and the installation creates a dedicated verifier service account that the launcher impersonates for that check.
- **`fugaro update` names the verifier account for you.** On an installation with the credentials service on, one `fugaro update` creates the verifier service account and publishes it in the policy, with no extra step.
- **A typed confirmation works from an IDE terminal.** A terminal whose only agent marker is the IDE's own `CLAUDE_CODE_SSE_PORT` is a person's terminal and accepts the typed project name.
- **The hosted MCP server's foundations are in, dormant:** the limits vocabulary, the authorize endpoint's Firebase sign-in, the store the tokens live in (hashes only, a store of its own) and the database rules that refuse the new subtree to every client. Nothing in this release starts the server.

### For operators

1. Upgrade the CLI and run `fugaro update` in each checkout: it brings the installation (including the verifier service account where the credentials service is on), the published policy and the checkout to this release.
2. The first `fugaro update` after the upgrade asks one policy-publish confirmation, because the policy now carries the verifier account's address.

### Known limits

- The cloud review is built and not admitted: `fugaro review` and the fix round that reads a review stay refused until the owner-run live checks (C3.9 and Check 125's steps 6 and 7) pass and the admission flip follows in a later release.
- A launcher who is not one of the installation's operators cannot verify a review's verdict: the verifier account's token-creator grant is the operators', and the refusal says so.
- Repository-image removal (the per-repository `image:`, `dockerfile:` and `rebuild.*` keys) and the rest of the config-management tasks (G3 to G13) are not in this release; the per-repository keys still work.
- The credentials service is still opt-in; deploying it for every installation by `fugaro update` is planned, not shipped.
- The deployer fence's per-service condition checks (Check 68) and Check 290 have not been measured live.
