- A project can now be **managed**: `fugaro init --create-project --gcp-project ID --managed --budget N --budget-currency CCC --billing-account ID` creates one in which a coding agent's Terraform is applied by `fugaro managed apply` with no prompt, because a deterministic gate over the saved plan (a resource-type allowlist, the plan's cost-bearing attributes, the exact delete list you write with `fugaro allow-delete`, and a recorded budget) decides what may change, and the apply runs as a dedicated deployer account, never as you.
- `fugaro restore NEW_PROJECT_ID ROOT` rebuilds a lost managed project from zero into a fresh project ID through the same gate; it is owner-run, asks for the project name at a terminal, and refuses a coding agent's session.
- A managed project's budget (1 to 10,000,000 whole units in a three-letter currency) is recorded in a marker that no credential a run or the deployer holds can write, and its billing-account budget sends 50%, 90% and 100% alerts that only notify.
- A project's policy can define job profiles, `fugaro init` deploys one shared Cloud Run job per profile and provider (GitHub only: a Bitbucket profile gets no job), and a workflow selects one with `job_profile:` (`fugaro validate` checks the name's form), but `checkout: clone` stays refused, so no run completes on a shared job yet.
- `fugaro run --title TEXT` names a run in `fugaro watch`, `fugaro runs ls` and the pull request it opens (unless the agent writes its own `pr.md`), where the first line of the task named it before.
- The desktop console ships as its own signed, notarised macOS release, `console-vX.Y.Z`: it reads an installed `fugaro`, opens on the installation you pick, shows a reduced view with a banner when that `fugaro` is outside the 0.7 and 0.8 minors it was built for, refuses to draw its dashboard below 0.6.0, is read-only, and does not update itself; the CLI also gains `fugaro config list`, `fugaro plan graph` and a files-changed record per run in `fugaro runs ls`.

Terraform 1.9 or newer is now required, and `fugaro init` and `fugaro managed apply` check for it (see the first operator step).

### For operators

1. Upgrade Terraform to 1.9 or newer wherever `fugaro init` runs (`terraform version`). The floor is new in this release: the project module this release adds validates one variable against another, which Terraform allows only from 1.9, while 0.8.0 and 0.8.1 declared `>= 1.7.0` with no such validation, so an installation on 1.7 or 1.8 first meets the requirement here.
2. Upgrade the CLI everywhere (`brew upgrade dimipaun/tap/fugaro`, or this release's archive with its cosign check), including CI pins and teammates.
3. Run `fugaro init` once per installation, in your own terminal. Its plan adds the managed-project pieces to every installation, managed or not: the `fugaro-deployer` account with its two custom roles, a custom Cloud Asset reader role, and the Cloud Asset API. Read the plan and type the project name.
4. In each checkout run `fugaro upgrade` (its cloud step is `fugaro image refresh`) so each job runs a runner image built from 0.8.5; this also pins the plugin, which carries the updated setup skill.
5. Run `fugaro doctor`. An installation that published a project policy under 0.8.0 or 0.8.1 gets `policy-older-than-binary`, and until it is fixed `fugaro run` refuses that project's launches: run `fugaro project policy publish --delete`, then `fugaro project policy publish`, after step 4 (an older runner refuses a version-2 policy).
6. Run the owner-run live checks for managed projects (67 and 68) against a real sandbox project, after the release: neither has been run before the tag, and neither has its steps in `docs/gcp-live-checklist.md` yet (what each must assert is in `docs/plans/2026-10-16-managed-projects.md`), so writing them comes first.

`fugaro init --firebase` is **not** needed for 0.8.5: no managed or project-policy change touches the database rules. The rules on `main` also carry a mailbox for the mobile app, as generation 2, still undeployed. Installations whose marker is generation 1 get a `policy-rules-skew` warning from `fugaro doctor` in the meantime; it is not a failure: a generation-1 installation still reads and enforces its published policy and can still publish another. Run `fugaro init --firebase` only when you want that warning to go away, or the mailbox, with a 0.8.5 binary and in your own terminal.

The console's own owner steps — the first signed build and its Gatekeeper verification (Check 59a) — belong to the console's release, `console-vX.Y.Z`, and not to this one. The console has no auto-update, and the round trip that would check one (Check 59b) needs a published update feed, so it is a later task and not a step of this release.

### Known limits

- **An existing project cannot be made managed.** There is no command for it in this release (planned for 0.9.0): a managed project is created fresh with `--create-project --gcp-project ID --managed --budget N --budget-currency CCC --billing-account ID`, and `init` on a project that already exists warns that the flag was not applied.
- **The project inventory and the created-resources fallback are not wired into `managed apply`.** The inventory is built and tested, but the apply takes no inventory, so a resource created outside Fugaro in a managed project is not detected, and in a coding agent's session a plan the allowlist admits applies without a confirmation. The plan gate, the exact delete list, the budget gate and the plan-hash re-check still apply; wiring the inventory is unscheduled, with flagging existing projects in 0.9.0.
- **The marker and the delete list stop the accident, not an agent that goes around the program.** A coding agent shares the session's user and its credentials, so it can write `fugaro/managed.json` or the delete list itself, or apply directly; what the marker, the delete list and the gate stop is a session that goes through `fugaro managed apply`.
- **There is no billing hard stop.** The budget alerts only notify, the marker's amount is the alert amount, and nothing stops spending.
- **The delete list holds resource addresses, not identities.** An address stays approved after the delete it approved has been applied: nothing prunes the list (unscheduled).
- **A shared project job cannot run a clone checkout.** `checkout: clone` is refused for it in this release.
- **Compute-module IAM grants stay refused,** and compute network types are excluded from managed plans.
- **The Cloud Batch job-name check is a latent fail-safe** in this release, since the Compute Engine/Cloud Batch backend is not shipped.
