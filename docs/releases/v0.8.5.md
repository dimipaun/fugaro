- A project can now be **managed**: `fugaro init --create-project --managed --budget N --budget-currency CCC --billing-account ID` creates one in which a coding agent's Terraform is applied by `fugaro managed apply` with no prompt, because a deterministic gate over the saved plan decides what may change (an allowlist of resource types, the exact delete list you write with `fugaro allow-delete`, and an apply-time read of the recorded budget) and the apply runs as a dedicated deployer account holding two custom roles, never as you; `fugaro restore NEW_PROJECT_ID ROOT` rebuilds a lost managed project from zero into a fresh project ID and applies the root through the same gate, owner-run, taking the project name typed at a terminal and refusing a coding agent's session.
- A managed project's monthly budget amount and currency are recorded in an owner-written marker an agent cannot write — 1 to 10,000,000 whole units in a three-letter currency code — and the project's billing-account budget sends 50%, 90% and 100% alerts that only notify.
- A project's policy can now define job profiles, and `fugaro init` deploys one shared Cloud Run job per profile and provider (a profile may not mount a Claude OAuth token yet); a workflow selects a profile with `job_profile:`, `fugaro validate` checks the name, and a run on one is admitted only when the profile's own `allow_repos` admits the repository, its git remote names exactly the provider's host, and it refuses a checkout it did not make — but `checkout: clone` stays refused in this release, so no run completes on a shared job end to end.
- The desktop console is published as its own release, `console-vX.Y.Z`, from the same tag as the CLI: a signed and notarised macOS app that reads a `fugaro` you installed, opens on the installation you pick, and refuses to draw its dashboard when that binary is older than the version range it supports (above the range it draws a reduced mode and names both versions); it is read-only, has none of the console's v2 work, and does not update itself.
- `fugaro run --title TEXT` gives a run a name of its own where it was named by the first line of its task — in `fugaro watch`, in the registry entry that `fugaro budget ls` and the console list a run by, and in the pull request a run opens when the agent writes no `pr.md`. *(Pending: the pull request adding this is still open against the 0.8.5 line — drop this bullet if it does not merge before the tag.)*
- Terraform 1.9 or newer is now required, and `fugaro init` and `fugaro managed apply` check for it.

### For operators

1. Upgrade Terraform to 1.9 or newer wherever `fugaro init` runs (`terraform version`). The project module's variable validation reads another variable, which Terraform allows only from 1.9; that code shipped in 0.8.0 and 0.8.1, so `terraform validate` already failed on 1.7 and 1.8.
2. Upgrade the CLI everywhere (`brew upgrade dimipaun/tap/fugaro`, or this release's archive with its cosign check), including CI pins and teammates, before anything else.
3. Run `fugaro init` once per installation, in your own terminal. Its plan adds the managed-project pieces to every installation, managed or not: the `fugaro-deployer` account with its two custom roles, a custom Cloud Asset reader role, and the Cloud Asset API. Read the plan and type the project name.
4. In each checkout run `fugaro upgrade` (its cloud step is `fugaro image refresh`) so each job runs a runner image built from 0.8.5; this also pins the plugin, which carries the updated setup skill.
5. Run `fugaro doctor`. An installation that published a project policy under 0.8.0 or 0.8.1 gets `policy-older-than-binary`, and until it is fixed `fugaro run` refuses that project's launches: run `fugaro project policy publish --delete`, then `fugaro project policy publish`, after step 4 (an older runner refuses a version-2 policy).
6. Run the owner-run live checks for managed projects (67 and 68) against a real sandbox project, after the release: neither has been run before the tag.

`fugaro init --firebase` is **not** needed for 0.8.5: no managed or project-policy change touches the database rules. The rules on `main` also carry a mailbox for the mobile app, as generation 2, still undeployed. Installations whose marker is generation 1 get a `policy-rules-skew` warning from `fugaro doctor` in the meantime; it is not a failure: a generation-1 installation still reads and enforces its published policy and can still publish another. Run `fugaro init --firebase` only when you want that warning to go away, or the mailbox, with a 0.8.5 binary and in your own terminal.

The console's own owner steps — the first signed build and its Gatekeeper verification (Check 59a) and the auto-update round trip (Check 59b) — belong to the console's release, `console-vX.Y.Z`, and not to this one.

## Known limits

- **An existing project cannot be made managed.** There is no command for it in this release (planned for 0.9.0): a managed project is created fresh with `--create-project --managed --budget N --budget-currency CCC --billing-account ID`, and `init` on a project that already exists warns that the flag was not applied.
- **The project inventory and the created-resources fallback are not wired into `managed apply`.** The inventory is built and tested, but the apply takes no inventory, so a resource created outside Fugaro in a managed project is not detected, and in a coding agent's session a plan the allowlist admits applies without a confirmation. The plan gate, the exact delete list, the budget gate and the plan-hash re-check still apply; wiring the inventory is unscheduled, with flagging existing projects in 0.9.0.
- **There is no billing hard stop.** The budget alerts only notify, the marker's amount is the alert amount, and nothing stops spending.
- **The delete list holds resource addresses, not identities.** An address stays approved after the delete it approved has been applied: nothing prunes the list (unscheduled).
- **Compute-module IAM grants stay refused,** and compute network types are excluded from managed plans.
- **The Cloud Batch job-name check is a latent fail-safe** in this release, since the Compute Engine/Cloud Batch backend is not shipped.
