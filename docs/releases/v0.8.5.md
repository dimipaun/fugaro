- A project can now be **managed**: `fugaro init --create-project --managed --budget N --budget-currency CCC --billing-account ID` creates a project in which a coding agent's Terraform is applied by `fugaro managed apply` with no prompt, because a deterministic gate over the saved plan decides what may change (an allowlist of resource types, the exact delete list you write with `fugaro allow-delete`, an apply-time read of the recorded budget) and the apply runs as a dedicated deployer account holding two custom roles, never as you.
- A managed project records its monthly budget amount and currency in an owner-written marker that an agent cannot write, and the project gets a billing-account budget whose 50%, 90% and 100% alerts only notify.
- `fugaro restore NEW_PROJECT_ID ROOT` rebuilds a lost managed project from zero into a fresh project ID, then applies the root through the same gate; it is owner-run, takes the project name typed at a terminal and refuses a coding agent's session.
- A project's policy can now define job profiles, and `fugaro init` deploys one shared Cloud Run job per profile, provider and Claude account; a workflow selects a profile with `job_profile:`, `fugaro validate` checks the name, and a run on a project job is admitted only when the profile's own `allow_repos` admits the repository, its git remote names exactly the provider's host, and it refuses a checkout it did not make. Runs on these shared jobs are **not enabled yet**: `checkout: clone` stays refused in this release, so nothing completes on one end to end.
- The project policy is now version 2, so an older runner image refuses it ("refresh the runner image") and `fugaro doctor` reports a version-1 policy as `policy-older-than-binary` with the fix.
- Terraform 1.9 or newer is now required, and `fugaro init` and `fugaro doctor` check for it.

### Known limits of managed projects in 0.8.5

- **An existing project cannot be made managed.** There is no command for it in this release (planned for 0.9.0): a managed project is created fresh with `--create-project --managed --budget N --budget-currency CCC --billing-account ID`, and `init` on a project that already exists warns that the flag was not applied.
- **The project inventory and the created-resources fallback are not wired into `managed apply`.** A resource created outside Fugaro in a managed project is not detected by the apply, and in a coding agent's session a plan the allowlist admits applies without a confirmation. The plan gate, the exact delete list, the budget gate and the plan-hash re-check still apply. Wiring the inventory is planned for 0.9.0, with flagging existing projects.
- **There is no billing hard stop.** The budget alerts only notify, the marker's amount is the alert amount, and nothing stops spending.
- **The delete list holds resource addresses, not identities.** An address stays approved after the delete it approved has been applied: nothing prunes the list (unscheduled).
- **Compute-module IAM grants stay refused,** and compute network types are excluded from managed plans.
- **The Cloud Batch job-name check is a latent fail-safe** in this release, since the Compute Engine/Cloud Batch backend is not shipped.
- **Everything about creating, restoring and applying is owner-run, and its live checks (67 and 68) are the owner's, after the release:** no live check has been run against a real project before the tag.

### For operators

1. Upgrade Terraform to 1.9 or newer wherever `fugaro init` runs (`terraform version`). The project module's variable validation reads another variable, which Terraform allows only from 1.9; that code shipped in 0.8.0 and 0.8.1, so `terraform validate` already failed on 1.7 and 1.8.
2. Upgrade the CLI everywhere (`brew upgrade dimipaun/tap/fugaro`, or this release's archive with its cosign check), including CI pins and teammates, before anything else.
3. Run `fugaro init` once per installation, in your own terminal. Its plan adds the managed-project pieces to every installation, managed or not: the `fugaro-deployer` account with its two custom roles, a custom Cloud Asset reader role, and the Cloud Asset API. Read the plan and type the project name.
4. In each checkout run `fugaro upgrade` (its cloud step is `fugaro image refresh`) so each job runs a runner image built from 0.8.5; this also pins the plugin, which carries the updated setup skill.
5. Run `fugaro doctor`. If an installation published a project policy under 0.8.0 or 0.8.1, it reports `policy-older-than-binary`, and until you fix it `fugaro run` refuses that project's launches: run `fugaro project policy publish --delete`, then `fugaro project policy publish`, after step 4 (an older runner refuses a version-2 policy).
6. `fugaro init --firebase` is **not** needed for 0.8.5: no managed or project-policy change touches the database rules. The rules on `main` also carry a mailbox for the mobile app, as generation 2, still undeployed. Installations whose marker is generation 1 get a `policy-rules-skew` warning from `fugaro doctor` in the meantime; it is not a failure: a generation-1 installation still reads and enforces its published policy and can still publish another. Run `fugaro init --firebase` only when you want that warning to go away, or the mailbox, with a 0.8.5 binary and in your own terminal.
