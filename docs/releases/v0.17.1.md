- **A repository's job can now run on a project catalog image.** 0.17.0 published the image catalog but held back every job a catalog entry gives its image to, because the release gate was left off; 0.17.1 turns it on, so `fugaro update --repo` deploys a workflow that names an entry (`image_name:`), lists the tags it needs (`needs:`) or takes the default.
- **A prebuilt catalog entry deploys as written.** An entry whose source is an image you build and push yourself (`source: { kind: image, image: <ref> }`) is no longer refused with "is not <registry>/<package>:latest in the repository's registry": the job runs the entry's own reference, with no Fugaro build record or tag to look for.

### For operators

1. Upgrade the CLI, then run `fugaro update --repo` in each checkout whose workflow runs a catalog entry: that is the run that deploys its job on the entry's image. An installation with no `image_catalog` plans exactly as before.

### Known limits

- A prebuilt entry's image is not checked before the job is deployed: Fugaro does not read the registry for it, so a reference that was never pushed (or that the job's account cannot pull) fails when the job is created or first run, not at the review screen.
- A prebuilt entry is never rebuilt by Fugaro: after a Fugaro upgrade, rebuild it from the new release's base image and push it, or its runner is the older release's.
- Moving an existing job from one prebuilt entry to another through the image refresh path is still refused; `fugaro update --repo` deploys the job with the image the catalog now names.
- `fugaro validate`, `fugaro image render`, `fugaro image build --local` and `fugaro update --repo` still assume a per-repository image in places for a catalog workflow (a runtime warning, a rendered Dockerfile the job does not run, and a recorded base image required for the daily check).
