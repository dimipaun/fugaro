- **A review can run in the cloud on its own job.** `fugaro review` launches a read-only review job that reads the project's review account from the credentials service, which `fugaro update` now deploys on every installation, and the launcher refuses an installation that predates the feature before any spend.
- **A run's default time budget is now three hours, up from ninety minutes, and a stage gets one hour instead of forty.** A security-reviewed task with three review levels fits the default stage window, so a long task no longer has to be relaunched with a longer limit; `fugaro.yaml` and `fugaro run --total-timeout` still override it, and the engine refuses a value above 24 hours.
- **A run says why it failed and what it ran on.** The record carries a failure class for each stage's error, and each stage names the credential it ran on, so a report or a console reads them instead of parsing text.
- **A review finding that needs your decision stops the loop** and is handed to you, instead of burning fix rounds on a question only the owner can answer.
- **Fugaro asks nothing of a person on a managed project:** the policy node, the image build and the setup steps no longer prompt, `--repo` takes a checkout path everywhere, and `fugaro setup` and `fugaro update` print one line per step with the full output in a log.
- **New read-only commands and lines:** `fugaro accounts rm`, `fugaro seats` (an advisory seat estimate), `fugaro runs digest --due`, `fugaro managed status --json`, and `fugaro doctor` now reports the security patterns in force, the reviews due and the credentials service's state, and stays clean after an update.

### For operators

1. Run `fugaro update`; it deploys the credentials service, re-renders the review accounts, takes the new default budget and asks what it asks today (a rebuild of the job images behind its own confirmation).

### Known limits

- The review launch is admitted, but the owner's live checks of it (C3.9, Check 125, the flip check and Check 290) have not been run, so no live installation has been observed admitting the review job.
- A run already in flight keeps the budget it started with; the new default reaches runs launched after the update.
- A repository whose `fugaro.yaml` writes its own `timeouts` keeps them, including one that pins the old ninety minutes on purpose.
- A repository that runs on a **shared project-profile job** takes that job's Cloud Run task timeout from its profile's `timeout_class` plus two minutes, not from its workflow's `timeouts.total`. A class sized for the old ninety-minute default is shorter than the new one, and it is the class that decides: the run holds its own budget to its job's class and finalizes inside it, so it still ends with a result and its pull request, but with the class's budget rather than the new three hours. (A run launched with `--total-timeout` keeps the limit it was launched with, because that limit is the execution's own.) A profile that should give its runs the full default needs `timeout_class` of at least 3 hours.
- A stage that runs longer than about 50 minutes outlives the run's git credential. The runner refreshes a GitHub installation token before each stage but never asks for more than 50 minutes, which is all GitHub will give, so the agent's `git` and `gh` calls late in a longer stage fail until the next stage's refresh. The new 60-minute default stage is past that limit — a stage that runs to its end has no working `git` or `gh` credential for its last ten minutes. A workflow that must not have it sets `timeouts.stage` to 45 minutes or less. Runs on Bitbucket are unaffected, and the previous 40-minute default stage was below it.
