- **`fugaro issue mine` shows what happened to the issues you reported.** It lists the issues this user created and the ones their report was merged into as an occurrence of somebody else's, each with its number and summary, where it stands (`local`, `pending`, `submitted`, `resolved`, `dismissed`, or `regression` — a failure that came back after the release that fixed it), when it was hit, submitted, resolved and dismissed, the link to the GitHub issue, and how many other people hit it. Other reporters are counted, never named. `fugaro issue list --mine` prints the same listing from the same read.
- **A resolved issue names the release that fixed it, and whether this machine is on it.** Where the CLI or the installation is older than that release the row says `fugaro update`, the one command that closes the gap; where the installation's own record could not be read the row says the installation was not checked, and a build that is not a release says it has nothing to compare. A row this machine is already covered for also offers the command this machine's own issue file recorded for the failure — never the shared record's — and nothing is run for you.
- **It works offline.** The last successful read is kept per project under the user's cache directory, so a listing with no network shows those rows beside this machine's own local issues and says which of the two it is showing and as of when; with nothing cached it shows the local issues alone and says so. A coding agent's session reads only those two and uploads nothing, and it asks the credential nothing at all: it takes who "me" is from the cached verified address, which is also what an offline run falls back to when the lookup cannot be made. The verified address is cached after each success, for display reads alone.
- **It reads no GitHub issue state.** What says an issue is fixed is the release the shared record carries, compared against this machine's own version, so no token is needed and no rate limit is involved — see the known limit below for what that costs.
- **`--all` shows the rows the 30-day rule hides, and `--json` prints a versioned document** (`schemas/issue-mine.schema.json`): the rows, the source they came from (`shared`, `snapshot` or `local`), the time that state was known, and counts — counts only, never another reporter's name or digest.
- **A published policy's pools now name their owner and the people they are served to.** `craft_pools` entries carry `owner` and `allowed_users`, both spelled by email, and `fugaro project policy publish` refuses a pool that names no owner. This is policy version 5, and `fugaro update` migrates the node in place rather than asking you to publish again: every pool that names no owner comes out carrying `legacy_open`, the marker that says the pool predates owners, so a reader can tell it from one whose owner is still to be named. Nothing else of the node is touched — the fields you edited into it by hand are carried over rather than published again.

### For operators

1. Run `fugaro update` once per installation, on your own machine. It is the whole upgrade for this release: nothing here runs after a deploy, and no record needs a backfill — the shared issue store and the times `mine` prints are written by the CLIs that ship it.
2. The same `fugaro update` rewrites the published policy node in its last stage, from version 4 to version 5: it prints the migration's diff and the write carries the same confirmation every other stage write does — `--yes` answers it, a person at the terminal confirms it by being there, and a session nobody is at is refused without `--yes` (a managed project with a person at the terminal is told what is written and asked nothing). The migration only adds a marker, so it widens no ceiling and asks for no typed name. Its whole change is `legacy_open` on every pool that names no owner; nothing else of the node is rewritten, so the entries you edited into it by hand survive it. It is safe while runs are in flight and asks no run to finish: when runs are running it says so in one line and proceeds, and a run that bootstrapped under the release behind keeps its records and its ledger. Upgrade every machine that runs Fugaro before it reads or publishes the policy again (see Known limits).

### Known limits

- **A resolved issue can lag.** `mine` reads the shared store and never GitHub (the owner's ruling of 2026-11-08, D1784), so an issue closed as completed on GitHub stays `submitted` here until the record is marked resolved. The pass that marks it is the resolve pass, which runs from the daily report — `fugaro runs digest`, in a person's own terminal, asks GitHub what became of the project's filed issues and writes the ones its release fixes back. A reporter who looks before that pass runs therefore sees `submitted` for an issue that is already closed; the listing is as current as the last read of the shared store, which its own `as of` line and its `source` name.
- **A pool's owner and its roster ship, and nothing reads them yet.** `craft_pools` entries carry `owner` and `allowed_users`, and a published pool must name its owner — but the two are decoded, validated and published by this release and read by no run of it. A `fugaro_p_` name is still granted to any launcher that asks for it, and `config.Pool.Serves`, the function that answers whether a pool is served to a person, has no caller: whether a pool admits the person asking for one of its credentials is DS3.2's check, made where the credential is resolved. Until that ships the owner and the roster are a declaration of intent and not a gate, and the migration's `legacy_open` marker changes nothing about who is served today. Write the owner anyway: a pool that names none is refused at publish, and the node is what the release that reads it will answer from.
- **A policy node migrated to version 5 is refused by 0.22.** Once the `fugaro update` above has rewritten it, a 0.22 CLI and a 0.22 job image read it as "the project policy is version 5; this Fugaro understands version 4" and refuse it — the node's pools carry members that reader decodes strictly, so it is unreadable there rather than tolerated as an unknown key. A repository whose job images have not moved therefore refuses at bootstrap, which is what the same `fugaro update` prevents by moving every job image of the repository onto this release. A machine still running 0.22 must be upgraded before it reads or publishes the policy, and what its own readers print for this node is the upgrade — `upgrade Fugaro (brew upgrade dimipaun/tap/fugaro), then fugaro update` from a 0.22 CLI, `refresh the runner image (fugaro upgrade)` from a 0.22 image — while a 0.22 publish refuses to write over or delete a node of another version at all. The delete advice is **not** 0.22's, and it is not this release's for a version-4 node either: `fugaro project policy publish --delete` is what this release's readers name for a node below the migration chain's first step (versions 1 and 2, which 0.8.0 and 0.8.5 wrote and no step reaches), and a version-4 node — what an installation holds between the upgrade and the `fugaro update` above — is answered with `fugaro update` itself, which rewrites it in place rather than costing what only the node carries. The credentials service is the one reader that carries on across the gap, and only from version 4 up: a service on this release that meets a node the update has not reached yet reads it as this one would after migrating it, in memory, and writes nothing back to the database — while a version-3 node it refuses, because the 3 → 4 step is the one whose node needs a republish (the Bitbucket token block is derived at publish from the project's local config, so a carry in memory would state an enforcement the operator never published).
