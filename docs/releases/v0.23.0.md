- **`fugaro issue mine` shows what happened to the issues you reported.** It lists the issues this user created and the ones their report was merged into as an occurrence of somebody else's, each with its number and summary, where it stands (`local`, `pending`, `submitted`, `resolved`, `dismissed`, or `regression` — a failure that came back after the release that fixed it), when it was hit, submitted, resolved and dismissed, the link to the GitHub issue, and how many other people hit it. Other reporters are counted, never named. `fugaro issue list --mine` prints the same listing from the same read.
- **A resolved issue names the release that fixed it, and whether this machine is on it.** Where the CLI or the installation is older than that release the row says `fugaro update`, the one command that closes the gap; where the installation's own record could not be read the row says the installation was not checked, and a build that is not a release says it has nothing to compare. A row this machine is already covered for also offers the command this machine's own issue file recorded for the failure — never the shared record's — and nothing is run for you.
- **It works offline.** The last successful read is kept per project under the user's cache directory, so a listing with no network shows those rows beside this machine's own local issues and says which of the two it is showing and as of when; with nothing cached it shows the local issues alone and says so. A coding agent's session reads only those two and uploads nothing, and it asks the credential nothing at all: it takes who "me" is from the cached verified address, which is also what an offline run falls back to when the lookup cannot be made. The verified address is cached after each success, for display reads alone.
- **It reads no GitHub issue state.** What says an issue is fixed is the release the shared record carries, compared against this machine's own version, so no token is needed and no rate limit is involved — see the known limit below for what that costs.
- **`--all` shows the rows the 30-day rule hides, and `--json` prints a versioned document** (`schemas/issue-mine.schema.json`): the rows, the source they came from (`shared`, `snapshot` or `local`), the time that state was known, and counts — counts only, never another reporter's name or digest.
- **A Bitbucket repository your published policy proxies carries no Bitbucket token in its run's container any more.** Where the policy admits the repository with `proxy: true` and the repository runs through the credentials service, `fugaro update --repo` in that checkout gives the job up both the container's mount of `bitbucket-token` and its account's access to it, so the copy an agent used to read out of the runner's `/proc` is not there to read. Every git and Bitbucket API call of such a run is served by the service instead, which puts the token on the wire for that one repository and that one branch.
- **The drop is per repository**: a project may proxy one Bitbucket repository and leave the rest alone, because the flip follows the published node's block for that repository and never a switch of the installation's. Every Bitbucket repository the policy does not admit with `proxy: true` keeps its mount, its accessor and its own token, whichever installation it belongs to.
- **The build account keeps its own copy until S4**: a build's Dockerfile can still reach the token and a rotation still writes both copies, so rotating one is still two writes.
- **`fugaro doctor --check-bitbucket-token` is where an installation reads what its bundle holds** — the credential the service serves a proxied run with — and it warns when a proxied repository has nowhere to fetch one from.

### For operators
1. Run `fugaro update` once per installation, on your own machine. It is the whole upgrade — it deploys the credentials service this release's flip needs and everything else the release carries — and no second command is owed for it. Nothing in the issue listing needs a backfill: the shared issue store and the times `fugaro issue mine` prints are written by the CLIs that ship it.
2. **Before the re-applies below, the bundle has to hold the token.** From your own terminal, `fugaro creds set bitbucket-token < token-file` stores the copy the service serves a proxied run with — the order this flip needs, the credential in the bundle **before** the job gives up its mount. `fugaro doctor --check-bitbucket-token` reads what the bundle holds today and names this command when it holds none; the write is refused from a coding agent's session and from a run, and no flag covers it, so this step is yours alone.
3. Run the same `fugaro update --repo <owner/name>` from the checkout of each Bitbucket repository your published policy admits with `proxy: true`. That run is what takes the token's mount and the job account's accessor away, and it is one command like any other update: on a managed project the accessor's removal is a delete the run retires by itself. On an installation whose project is not managed the run stops where it has always stopped and prints what would go away with the command that retires it (`fugaro update --repo . --retire`, which asks its own confirmations at a terminal); `--allow-delete <address>` on the same command is the other route the guard accepts.
4. Nothing to run for a Bitbucket repository your policy does not proxy: it keeps its mount, its accessor and its own token, before and after this update.

### Known limits

- **A resolved issue can lag.** `mine` reads the shared store and never GitHub (the owner's ruling of 2026-11-08, D1784), so an issue closed as completed on GitHub stays `submitted` here until the record is marked resolved. The pass that marks it is the resolve pass, which runs from the daily report — `fugaro runs digest`, in a person's own terminal, asks GitHub what became of the project's filed issues and writes the ones its release fixes back. A reporter who looks before that pass runs therefore sees `submitted` for an issue that is already closed; the listing is as current as the last read of the shared store, which its own `as of` line and its `source` name.
- **The bundle is not written for you, and the flip does not read it.** `fugaro update` neither reads nor writes the credentials service's bundle, and the Terraform it applies is the same whether or not that bundle holds a token: a repository whose bundle holds no `bitbucket-token` credential still gives up its mount and its accessor, and its runs are then refused when they ask the service for their git credential — nothing is left in the container to fall back on. `fugaro creds set bitbucket-token`, run by a person in their own terminal (a coding agent's session is refused it), is the bundle's only writer. The order this flip is meant to keep — the token in the bundle **before** the job gives up its mount — is kept by hand, as step 2 above; no command enforces it, so the flip does not.
- **This release accepts that window on purpose, rather than refusing the drop.** The credential is the operator's: `fugaro update` cannot write it, and the only other fix — `fugaro update --repo` refusing to apply the drop while the bundle holds no `bitbucket-token` — is a readiness gate the design left open and the owner has not answered (`docs/secrets-brokering/reconciliation.md`, **O8**). So the drop stays unconditional on the bundle, the order is an operator step plus a `fugaro doctor --check-bitbucket-token` warning, and a proxied repository whose bundle holds no token is refused at its first git call rather than quietly falling back: there is nothing to fall back to.
- **The flip is held behind the owner's live Check 191.** The proxy chain end to end on a released build — the service serving a run's clone, push and pull request, and refusing the attempts it must — has not been run or reported passed, and this flip ships only behind it: until then these notes are the draft of the release that carries it. It is the release **after** the chain's, and the chain's own is 0.22.0 — the first release whose runner can serve a proxied run; 0.21.0 was tagged without that half. Nothing gates the drop by version, so the fill must not reach a tag before 0.22.0 is out and Check 191 has passed on it: it has not, so these notes wait for the release they name rather than for the next one cut from the tree carrying them.
