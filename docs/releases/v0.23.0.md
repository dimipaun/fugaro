- **`fugaro issue mine` shows what happened to the issues you reported.** It lists the issues this user created and the ones their report was merged into as an occurrence of somebody else's, each with its number and summary, where it stands (`local`, `pending`, `submitted`, `resolved`, `dismissed`, or `regression` — a failure that came back after the release that fixed it), when it was hit, submitted, resolved and dismissed, the link to the GitHub issue, and how many other people hit it. Other reporters are counted, never named. `fugaro issue list --mine` prints the same listing from the same read.
- **A resolved issue names the release that fixed it, and whether this machine is on it.** Where the CLI or the installation is older than that release the row says `fugaro update`, the one command that closes the gap; where the installation's own record could not be read the row says the installation was not checked, and a build that is not a release says it has nothing to compare. A row this machine is already covered for also offers the command this machine's own issue file recorded for the failure — never the shared record's — and nothing is run for you.
- **`mine` works offline, reads no GitHub issue state, and has two switches.** The last successful read is kept per project, so a listing with no network shows those rows beside this machine's own local issues and says which it is showing and as of when; what says an issue is fixed is the release the shared record carries, so no token is needed and no rate limit is involved; `--all` shows the rows the 30-day rule hides and `--json` prints a versioned document (`schemas/issue-mine.schema.json`) of rows, source and counts, never another reporter's name.
- **A launch can continue a run that opened no pull request, and carry its limits with it.** `fugaro run --continues RUN-ID` joins the named run's chain, `--used-usd`, `--used-tokens`, `--used-time` and `--used-review-rounds` charge the chain for spend its own runs do not hold, and `--max-usd`, `--max-tokens`, `--max-time` and `--max-review-rounds` bound the chain, tighten-only, refused with both figures and the layer named when a request is above what remains.
- **The plugin lives at user scope, and `fugaro update` takes an older release's pin out of a repository.** `fugaro update` no longer writes the Fugaro plugin into a checkout's `.claude/settings.json`; where an older release left its `fugaro@fugaro` pin there it shows the two entries as a diff and, at a terminal or with `--yes`, removes them and nothing else, committing nothing.
- **More of a project's settings have a command.** `fugaro settings` reads the published policy and the project's database as layers and `--why` names the level that won each key, and the writes the layer file and the repository config lacked are commands: `fugaro rigor set`, `fugaro project profile`, `fugaro project routing`, `fugaro project clone-url`, `fugaro project repos set` and `fugaro accounts allow` and `deny`, each showing its diff and refused in a coding agent's session where it widens what a run may reach.
- **`fugaro troubleshoot [ID]` explains a failed command.** Given a run ID or, with none, the newest logged command that failed, it hands the evidence and the source of the installed version to a read-only agent capped at 30 turns and one dollar, prints the one line saying what leaves the machine before the call, and marks a printed `fugaro` command the CLI's own tree does not have as not to be run blindly.

### For operators

1. Run `fugaro update` once per installation, on your own machine. It is the whole upgrade for this release: nothing here runs after a deploy, and no record needs a backfill — the shared issue store and the times `mine` prints are written by the CLIs that ship it.
2. In a checkout an older release pinned the plugin into, the same `fugaro update` offers to remove the `fugaro@fugaro` entries from `.claude/settings.json`: it shows them as a diff and asks at a terminal (`--yes` answers it); in a coding agent's session it prints the diff and writes nothing, so run it at your own terminal. Nothing is committed: review the change with `git diff`.

### Known limits

- **A resolved issue can lag.** `mine` reads the shared store and never GitHub (the owner's ruling of 2026-11-08, D1784), so an issue closed as completed on GitHub stays `submitted` here until the record is marked resolved. The pass that marks it is the resolve pass, which runs from the daily report — `fugaro runs digest`, in a person's own terminal, asks GitHub what became of the project's filed issues and writes the ones its release fixes back. A reporter who looks before that pass runs therefore sees `submitted` for an issue that is already closed; the listing is as current as the last read of the shared store, which its own `as of` line and its `source` name.

- **The Bitbucket proxy is opt-in, and it has not been proven live.** `proxy: true` on `project_secrets.bitbucket-token` has an effect only for a repository that is also on the credentials-service switch (`agent.auth: cascade`) and admitted in the published policy; every other repository keeps mounting its own token. The flip that takes the token away from a proxied repository's job (#2166) is held and is not in this release: `config.ProxiedGitSecretNames` is still empty, so no job loses its mount or its accessor. Checks 191 and 192 of `docs/gcp-live-checklist.md`, the proxy end to end and the flip, are NOT RUN.
- **The cascade has not been exercised live.** A repository on `agent.auth: cascade` reaches the credentials service, but Checks 95 and 99, a run through the service and the cascade across accounts, are NOT RUN, so the unit and emulator tests are the only evidence that the account walk, the wait and the probe behave as written.
- **A chain with the budget off is a report, not a stop.** The chain's dollars and tokens are read off the budget database's ledgers; with the budget off the dollar figure comes from the run records, the chain is unenforced and says so with a warning, and a dimension the chain cannot measure keeps only its own limit. A ledger that cannot be read is charged that run's whole per-run cap, never zero.
