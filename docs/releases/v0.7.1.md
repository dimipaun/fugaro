- New `fugaro budget preview --recipe NAME --runs N [--repo R] [--json]` answers "could this batch blow my budget?" before you launch it — a read-only, rough worst-case ceiling for the N runs (N × the smaller of the per-run cap and the recipe's stage bound × `agent.max_budget_usd`) set against the repository's headroom under the caps today, with a warning when the ceiling could exceed it, one verdict line, and a `typical:` line from the repository's own recorded runs (the mean cost per stage and model over the last 30 days, once at least five runs have a price to average) so the ceiling can be checked against what this repository actually spends — a ceiling, not a forecast: an unset cap is reported as unbounded rather than guessed at, and only real dollars count, so oauth runs, whose cost is notional, are excluded and counted rather than folded in.
- `result.json` now records the model cost of every stage (`model_usd`, and the stage's `model`), so a run's bill can be read stage by stage instead of as one figure; the per-stage figures add up to the run's `cost.model_usd` except for spend that settles after its stage ended, which appears as `model_by.unattributed`; old records still parse.
- A secret can now be stored once for the whole Fugaro project instead of once per repository: `fugaro secrets set NAME --project-wide` writes the project's own container, which the installation's Terraform creates, and every repository the name is allow-listed for mounts that copy, except a repository that keeps its own copy of the name, which still wins; a provider key with no `allow_data_to`, or one written as `["*"]`, is available to every repository — `fugaro validate`, `fugaro init` and `fugaro doctor` now name every provider open that way, an `allow_data_to` written with nothing under it is refused as ambiguous instead, and `SECURITY.md` warns that a project-wide git credential reaches every repository allow-listed for it.
- `fugaro ls` is gone for good: after 0.7.0 kept it as a hidden pointer to `fugaro runs ls`, it is now an ordinary unknown command — cobra's `unknown command "ls"`, exit 1 — so a script that still calls it fails instead of being pointed at the new name. `fugaro runs ls` is unchanged.
- The base image creates `~/.cache/mise` as the `fugaro` user, so the mise cache a derived image's build mounts there stays writable by the user a run runs as: runs stop printing mise's `failed to write cache file … Permission denied` warning on every command that reads its cache. The image's runtime selftest now checks that directory exists, is a real directory owned by `fugaro` and is writable.
- Fugaro's own repository no longer names a base: its `go` workflow runs on the one Fugaro base image, with its runtimes from `mise.toml` instead, and its cloud loop on `agent.auth: api-key` with a DeepSeek coder and reviewer through OpenRouter (`docs/dogfooding.md` is the worked example, including the two secrets it needs). One lesson from that is worth copying if you run a provider model: Claude Code applies `--max-budget-usd` against its own cost estimate, and for a non-Anthropic model that estimate is Sonnet-like, about 25 times what the gateway charges for DeepSeek, so a per-stage `agent.max_budget_usd` that looks enormous in real dollars still ended two runs at $0.13 and $0.22 of actual spend — the gateway's per-run and daily caps remain the hard stop.

### For operators

1. Upgrade the CLI (`brew upgrade dimipaun/tap/fugaro`, the release archive, or `go install github.com/dimipaun/fugaro/cmd/fugaro@v0.7.1`).
2. Then run `fugaro upgrade` in each checkout (its cloud step is `fugaro image refresh`): the mise-cache fix, the `typical:` line and the per-stage cost in `result.json` all live in the job image, so a run only gets them from an image rebuilt from this release's base image. It asks before every billable build, writes no `fugaro.yaml`, and leaves a custom or development base image alone.
3. Project-wide secrets are an ordered rollout, and its first step is yours alone: in the installation root, `fugaro init` (with no `--repo`) plans the project's secret containers — one create per eligible name, no destroys and no replacements — and applying that plan is an operator action, not something a repository's job can do.
4. Then `fugaro secrets set NAME --project-wide` for each name you want stored once for the project (the value is read from stdin and it takes no `--repo`); it writes the project's own container, and a value stored before step 3's apply is adopted by that apply rather than conflicting with it.
5. For each repository that adopts a project-wide name while its own copy still has a version, that copy must be disabled before the repository will use the project's — `gcloud secrets versions disable` needs `secretmanager.versions.disable`, which is project-owner-only — and then `fugaro init --repo` in its checkout plans replacements of the per-repository IAM addresses, which Terraform's guard refuses until each removal is named with `--allow-delete`.
6. `fugaro doctor` should show its usual clean lines, and its new project-secrets check plus the `fugaro validate` and `fugaro init` mentions are how a provider key open to every repository is surfaced — look at them before adding a provider, since an absent `allow_data_to` now means every repository rather than nobody.

Two notes. `checkout: clone` is **not** usable in this release: its runner side has merged since the last draft of these notes (generic-tool plan Task 17, PR #342 — the runner's blobless `--filter=blob:none` clone, a `mise install` provision stage and the prefetch all exist on main), but the switch that turns it on (Task 18) is still off (`cloneShipped` is false), so `fugaro init --repo` and `fugaro image refresh` refuse to deploy or move a clone workflow's job and `fugaro run` refuses a clone launch.
