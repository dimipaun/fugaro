- **One `fugaro update` is the whole upgrade.** After `brew upgrade`, a single `fugaro update` brings the installation, the checkout's plugin pin and installed plugin, the deployed security rules generation and the published policy node up to this version, the node migrated in place after a diff of what changes and what is kept, so the delete-and-publish-again step of 0.14.0 is gone and no separate `fugaro upgrade --local` or `fugaro image refresh` is needed either.
- **Stale security rules are deployed before the policy that needs them.** An installation whose deployed rules predate the policy model no longer stops at the policy step and leaves you a second command: the rules generation is deployed in its own stage first, so the policy migration that follows has the rules it is read under.
- **A database your installation does not own is left alone.** `fugaro update` writes its mark, its project name and its security rules only into the database your installation adopted; a database in another Firebase project, or one that holds data with no Fugaro mark, is refused rather than written into, so a mistyped `budget.firebase_project` marks nothing.
- **`fugaro doctor` answers on one screen.** The default view is a verdict, one line saying what an error and a warning mean, and then one sentence with the fix for each item; the audits stay behind `--all` and `--security`, and one pointer line says so when they have findings.
- **`fugaro report` and `fugaro runs ls` are much faster.** Run records are read 32 at a time instead of one at a time, so `fugaro report` on a project with a few hundred runs drops from about 26 seconds to about 3, with the same days, the same runs on each and the same order.
- **The coordinator's GitHub App token goes only to GitHub.** Its API root is pinned to `api.github.com` and the environment variable that used to move it is ignored, so nothing that can set a variable in the coordinator's process can have the App's token sent to a host of its choosing.

### For operators

Run `fugaro update`. It brings the installation, the checkout's plugin pin and installed plugin, the deployed security rules generation and the published policy node up to this version, the node migrated in place after a diff of what changes and what is kept: no other command, and nothing deleted and published again. Expect its confirmations — the plan, the typed project name (or `--yes`) before the steps that write to your cloud project, the rules deploy, the policy migration, and the checkout's images — and these notes:

1. `fugaro update --yes` now also approves billable rebuilds of the checkout's job images.
2. On rules generation 1 or 2, `fugaro update` deploys the device binding, which locks out every phone account without a `config/admin/devices/<uid>` node.
3. An installation whose Firebase project differs from its GCP project and whose database carries no Fugaro mark: drop `budget.firebase_project` and `budget.rtdb_url` from the project config and run `fugaro update --firebase-project <gcp-project-id>`; one that already carries the mark converges as before.
4. In a coding agent's session `fugaro update` writes nothing and exits 1 (it does not move the plugin pin there): run it in a normal terminal.

### Known limits

- The authorship a launcher names and the trailers a run writes are a record and not proof: nothing verifies a `Fugaro-Run` trailer, no account owns the author a launcher claims, and a commit can be amended after a run pushes it. A repository whose `fugaro.yaml` sets `git.author` is refused at launch against a job image older than 0.14.0, which names the upgrade instead. Nothing a run commits is signed. The stamp hooks the runner writes live in temporary directories the run's agent can also write, since the agent and the runner share one user, as `SECURITY.md` says of everything that user can reach.
- Pairing completes only with the phone app's later release: 0.14.0 wrote the device node and the delivery, and nothing on the phone reads them yet.
- The laptop's copy of a pairing's MAC key is stored through `security -i` in the macOS keychain or through `secret-tool` (libsecret) on Linux; Windows has no keychain writer in this release, so `fugaro pair` there stops at the keychain step and removes the device node it wrote.
- `fugaro user` changes the local configuration's launcher and operator lists, which the next `fugaro update` applies. No cloud-side role enforcement ships with it: a launcher and an operator still differ only by the IAM roles the installation grants them.
- Shared images arrive in 0.15.0: a `fugaro.yaml` whose workflow says `checkout: shared` is refused (`fugaro validate` says "shared images arrive in 0.15.0") and its launches fail, so a repository that wrote it uses `checkout: baked` or `checkout: clone` meanwhile. The installation's shared image registry is created by `fugaro update` and stays unused until then.
- Bitbucket brokering is not in this release: the proxy arrives in 0.15.0 and the flip in 0.16.0, so until then a Bitbucket run's job holds its own token and reads it as it always has, and `proxy: true` in the published block changes nothing such a run does. What 0.14.0 pinned is where the token may be sent, and `fugaro creds set` can already hold the token in the credentials service's bundle for that proxy, which stays dormant; because the bundle's git credential is named `bitbucket-token`, a model-credential account of that name is now refused in the config.
- Model A/B testing is inert in this release: a challenger run publishes nothing, a run is a challenger only when a task hands it that role by hand, and no command samples a run, launches a pair or reads one back yet.
