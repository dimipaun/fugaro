- **`fugaro troubleshoot` diagnoses a failure on a machine with no Claude login.** The command's third tier sends the same redacted evidence the local diagnosis would have sent — the log, `fugaro doctor`'s output, the effective configuration with secrets removed and a reference to the Fugaro source at the version that failed — to your own Cloud project, where one bounded diagnosis job reads it and answers; the answer is checked against the CLI's own command tree exactly as a local one is, so a command it prints is shown as runnable or as unchecked either way, and the run it came from is printed beside it.
- **The tier that spends is asked for last, and it prints what it cost.** The rules tier and the local login still answer first, so a broken cloud is explained rather than met with a second failure, and the pre-flight asks the launch path's own gates before anything is uploaded: a job image older than 0.26.0 and a credentials service that is off each end with the reason and `fugaro update` as the fix, and a budget that is spent ends with the launch path's own refusal, printed as it stands — it names the launch flag that skips the check, and a diagnosis takes none. A cloud answer prints the figure the diagnosis run's record holds.
- **A cloud diagnosis never runs on the person's own credential.** The job is the review-only variant `fugaro review --pr N` already uses, which mounts no credential of its own: the model call is signed for the project by its credentials service, the person's login never enters the container, and no installation secret is read into the CLI.
- **Upgrading is `fugaro update`, as it always is.** The cloud tier starts the job image this release builds, and until that has run the command's own pre-flight refuses a diagnosis against the older image, naming the release and the fix.
- A workflow's own `secrets:` are no longer mounted in the job that runs it on a repository whose credentials-service switch is on: the run fetches each declared value from the installation's credentials service at bootstrap, so the value is not in the container the agent runs in.
- A repository you do not switch keeps every mount, before and after this release: the drop follows the repository's own root being re-applied with the switch on, and a repository the switch holds off reads its secrets exactly as it does today.
- `fugaro update` and `fugaro update --repo` are the two commands that move an installation and a repository onto the fetch, and a run launched on a job image older than 0.26.0 is refused before any execution exists, naming that release and `fugaro update`.
- A switched repository's **builds** read their credentials at the credentials service too: the build account holds no `secretAccessor` on the git credential or on any of the workflows' build secrets, the build request carries no `availableSecrets`, and the daily image-check job mounts none of them. What a build clones with is the credential the service answers, so what the build reaches is unchanged: the same repository, the same token, and on Bitbucket the same token as before.
- **A shared project job gives up its model credentials where the credentials service serves its profile.** The profile's shared jobs — one per provider and Claude account — mount none of the model credentials any more: not the Claude account token each job's own name carries, not the Anthropic key, and not a provider's key. Their accounts keep no accessor on them either, so a run of such a profile calls the model with the credential the service answers rather than one its container holds. A profile no repository of yours is switched for keeps every mount and every accessor, before and after this update.
- **`fugaro runs ls` answers the two questions you ask most without reading your whole history.** `--pr N` and `--state running` read a small index of a pull request's runs and the executions the cloud is still running, where before they read every run of the window — 23 s for one row and 20 s for none on a project with a history. A pull request with no index entry yet is read the old way, with one line on stderr saying so; the rows and `--json` are unchanged.

### For operators

1. **Per installation** — run `fugaro update` once, at your own terminal, and it is the same one command. It deploys the installation's credentials service if it is not deployed yet and writes each repository's workflow-secrets record (B3.1) — the record a run's fetch is served from. It takes no mount away from any repository: that is the next step, and a repository keeps every mount until its own root is re-applied.
2. **Per repo checkout** — run `fugaro update --repo <owner/name>` from the checkout of each repository whose workflow secrets you want brokered. That run is what applies the flip (B3.8): the repository's job account gives up its accessor on each of the workflow's own secrets, the job mounts none of them, and the run fetches each declared value from the installation's credentials service at bootstrap instead. **A repository you do not run it in keeps every mount, before and after this update**, and so does a repository whose root is re-applied with the credentials-service switch off. A run that started before the re-apply of its repository is unaffected: it keeps the mounts it bootstrapped with, and the re-apply neither ends it nor changes what it reads. A run of a switched repository needs a job image whose runner fetches a workflow secret from the service — the 0.26.0 base image or newer — and a launch on an older one is refused before any execution exists, naming that release and `fugaro update`.
3. **Per installation** — nothing beyond step 1, but `fugaro update` shows one more planned change this release, and it is the only one on the runs bucket: a new lifecycle rule deleting a message object under `tokens/` whose name ends `.msg.json` — a message a launcher sends a run that is going — 7 days after it is written, where before this release it was kept for ever. Nothing else under `tokens/` is touched, and the rule is planned whether or not the budget is enabled.
4. **Per installation** — nothing beyond step 1, but `fugaro update` writes the pull-request index for the last 90 days of runs: one entry per run whose own records say it opened, followed or reviewed a pull request, under the run's own prefix, created only where one is missing, so a second update writes nothing. It waits for no run — the entries go beside what a run in flight holds and nothing it holds is rewritten — and until it has run, `--pr N` reads a pull request the old way.

5. **Per repo checkout, the build half** — the same `fugaro update --repo <owner/name>` run applies the build flip (B4.9) as well: the repository's build account gives up its accessor on the git credential and on each of the workflows' build secrets, the build request names none of them, and the daily image-check job mounts none of them — the build and the check ask the installation's credentials service instead. **A repository you do not run it in keeps every accessor and every mount, before and after this update.** The build's credential step runs on the installation's base image, and only one carrying this release's `fugaro` reads the service: that image is what step 1's own image stage moves (behind its own confirmation), so a repository is switched only after it has run — a build on an older base image finds the mounts this flip has taken away and fails its credential step rather than reading them.

6. **Per installation, the shared-job half** — the same `fugaro update` applies the shared-job flip (B5.7), and it is done when it returns: a profile the credentials service serves has no model credential on any of its shared jobs afterwards — none mounted, and none readable by their accounts — while a profile no repository of yours is switched for keeps every mount and every accessor, before and after. The drop is the **profile's** and not one repository's: a shared job is one job per profile, provider and Claude account, so one repository of that profile switched takes the mount off every repository sharing the job, and a repository you have not switched shares the switch of the ones you have. Its runs are served by the address their own launch is handed, which is what step 2's `fugaro update --repo` in its checkout is for; a repository of a switched profile whose own launch is handed no address has no model credential left to fall back on.

### Known limits

- On a switched repository the launch is judged on the workflow as the document declares it, so a workflow that declares a repository-level secret your project's published policy does not admit — a name the flip never mounts and the service never has a value for — still needs the 0.26.0 base image or newer, even though nothing was taken from that job.
- Workflow secrets are fetched by a run of the repository's own job. A review run mounts no secret of its own and is untouched by the flip, and a run on a shared project job reads the secrets its profile mounts: the model credentials are no longer among them once the shared-job flip has run, and the GitHub App's key stays.
- A cloud diagnosis runs inside a repository checkout, scoped to that repository; run from outside one, the command prints the evidence with that reason rather than a diagnosis.
