- **The resident orchestrator daemon now has an identity of its own, so the labels it keeps on its runs' pull requests really land.** The daemon presents a Google ID token minted as an account your installation created for it — the credentials service admits that account as its orchestrator class and nothing else — where before this release the service admitted no daemon at all: the `fugaro:running`, `fugaro:failed` and `spec:<name>` labels the daemon computes were refused by the service, and a pull request carried none of them.
- **Your installation's operators can obtain that identity, and nothing has to be typed.** The one command that upgrades you creates the daemon's account, points the credentials service at it and lets each operator impersonate it, so a daemon running on an operator's own machine mints its own token on demand, per call, and never caches one.
- **A daemon that cannot mint its identity says so in one line and names what to run, instead of labelling nothing quietly.** There is no fallback credential and no silent skip: the daemon's tick goes on without labels and the line it writes tells you which command to run at your own terminal.

### For operators

Run `fugaro update` once per installation, at your own terminal. That is the whole step, and it is the command you already run: it applies the installation's own Terraform — creating the account the daemon runs as, granting it the invoker bit on the credentials service and rendering its address into the class that service admits — and it binds `roles/iam.serviceAccountTokenCreator` on that account for every operator of the installation, which is what lets a daemon on any operator's machine mint its own identity. No repository's root has to be re-applied for this, no credential is typed, and there is no second command.

What that update will ask and change, so nothing is a surprise: it redeploys the credentials service, whose container gains `FUGARO_ORCHESTRATOR_ACCOUNTS` (an installation that never opted into a resident orchestrator gets the empty list and behaves exactly as it did), and the two rows above are shown on the run's own review screen and admitted as the design's own table rather than as a new question. Runs in flight are not asked to finish first: the update changes nothing a run holds, and the daemon meets its new identity at its next call.

### Known limits

- **No daemon merges a pull request in this release.** The merge credential's route is reachable by the daemon's class now, but nothing in the tree asks it for a token, so a person still merges every pull request, exactly as before.
- **A coding-agent session on an operator's machine can present the daemon's identity**, because the daemon runs as that operator — `SECURITY.md` states it for this class in the words it uses for the installation's other identities of the same kind: what that identity can then do is what the credentials service's label route accepts, which is the status and spec labels of this installation's own pull requests.
- **Labels are the daemon's alone.** A plain `fugaro run` with no daemon watching it still opens its pull request unlabelled, and a repository whose host has no pull request labels (Bitbucket) gets none.
