- The desktop console has its new look: one dark stylesheet bundled into the app, a two-column layout with an installation rail beside the screens, styled Live, Spend, Projects and Run screens, keyboard navigation (the arrow keys through the navigation and the rail, Command+digit on macOS or Control+digit elsewhere for a rail row) and the website's mark as its icon; it stays read only and is published for this release as its own download, `console-v0.9.5`.
- `fugaro budget set`, `fugaro budget kill` and `fugaro budget resume` take `--repo` with no value to mean the repository this checkout belongs to, so `fugaro budget set --repo --daily 150` sets the caps of the repository you are standing in, and the bare form is refused outside a checkout whose origin names a repository rather than guessed.
- `fugaro project repos ls` lists the project's allow-list against the repositories that have actually run there (read from the runs bucket and the daily spend records rather than from the runs in flight), marks each one admitted or not, and says so plainly when a repository's name cannot be recovered.
- `fugaro project sync` is new: it asks GitHub which repositories the project's GitHub App is installed on and offers the ones the allow-list does not admit yet as one list confirmed once, only ever adding names (reading the App's private key needs `--github-app-key`, which is refused in a coding agent's session).
- `fugaro init --provision-batch` is turned back on, with the reaper's role reduced to the five permissions Google defines (`batch.jobs.cancel`, which is not a permission Google has, is gone, so the role can be created), and `fugaro backends ls` lists the compute backends a project config may name and which one it uses; both are groundwork, since no run can use the Batch backend yet.

### For operators

Only the database rules move in this release, so the order is short: upgrade the CLIs first, because a 0.9.0 `fugaro doctor` reads this release's rules as a skew and prescribes the redeploy that would undo them.

1. **Per machine** — upgrade the CLI on every machine that runs `fugaro doctor` or `fugaro init` against the installation: `brew upgrade dimipaun/tap/fugaro`.
2. **Per repo checkout** — run `fugaro upgrade --local`, so the plugin pin follows the CLI (the setup and working skills changed) without a cloud call.
3. **Per installation, in your own terminal, outside any repository checkout** — run `fugaro init --firebase <gcp-project>`. It deploys this release's database rules (the credentials service's groundwork: the `creds/` node denied to every run token, and new optional children only a credentials-cascade run writes) and records their generation at `config/limits/credsRules`; it prints what it changes before it applies anything. Until it runs, this release's `fugaro doctor` reports `policy-rules-skew` as a warning, and nothing else behaves differently. In a checkout it would also pin this release's base image and move the shared jobs onto it, which this release does not need.

Nothing else is required: no policy republish, no `fugaro init --repo` and no image rebuild. The runner's changes are the wording of one error and fields only a credentials-cascade run writes, and no launch check asks for a 0.9.5 base image. When you do move a repository's images with `fugaro upgrade` (its cloud step) or `fugaro image refresh`, the shared jobs follow only on a later `fugaro init --firebase <gcp-project>`, per installation, run on that machine, as in 0.9.0.

### Known limits

- **The Batch backend is still disabled.** `backend: cloud-batch` is refused by this build, so no run can use it, and once it is enabled a run with a sealed budget token will be refused on it by design (the seal's key cannot be kept out of a Batch job's definition). `fugaro init --provision-batch` creates billable, lasting resources (a Cloud NAT and router, a boot image rebuilt on a schedule) that nothing uses yet, and its apply has not been run against a live project: the owner-run Check 57b of `docs/gcp-live-checklist.md` is **NOT RUN**. Run it only to try the groundwork.
- **The credentials service is not usable.** This release carries only its groundwork (the database rules above, the policy's `credentials` block and per-repository admissions); there is no service to deploy. `routing.claude.via: cascade` is accepted in a routing block but changes nothing yet (a Claude call still goes direct), and publishing it with `fugaro project policy publish` makes every older CLI refuse each launch and publish of the project and every older runner halt its runs, which the publish's own diff warns about, so do not publish it.
- **An older CLI can undo this release's rules.** Once step 3 has run, a 0.9.0 `fugaro doctor` reports `policy-rules-skew` and prescribes `fugaro init --firebase`; run with that older CLI, it redeploys the older document and takes the credentials children away. Upgrade that machine's CLI instead: this release's `fugaro doctor` then reports the older document as `policy-rules-skew` in its turn, and its `fugaro init --firebase` puts this release's rules back.
- **Managed projects stay disabled, exactly as in 0.9.0.** Every command that would create a managed project or act as its deployer still refuses before any cloud call, and the deployer's redesign is not in this release.
- **The console still asks for each installation by hand.** Its installations window takes a project name you type and a `fugaro` binary, a config file and a checkout you choose; finding them by itself is planned for 0.9.6.
- **The live checks have not been run, and only you can run them.** Every owner-run, sandbox-only check in `docs/gcp-live-checklist.md` that this release's changes touch is still **NOT RUN**, Check 57b among them, and `fugaro project sync` has not been run against a live GitHub App.
