- **`fugaro setup` uses a GCP project you already made, when it holds nothing of Fugaro's.** An ID named by `--gcp-project` (or typed at the wizard's question) that is already there, is ACTIVE and carries no installation, no installation state and no label a run of `fugaro setup` writes is adopted: setup uses it as if the run had created it, marks it Fugaro-managed in the same step a creation is marked, and says so in one line. A project that holds anything of Fugaro's is refused exactly as before, one that is being deleted says so, a billing account already linked is never relinked (and no question about it is asked), and Firebase is added only when the project has none.
- **One command is enough, and `--no-apply` is how you stop it.** A management command — `fugaro image add`, `fugaro settings set`, `fugaro accounts rm`, `fugaro project repos add`, `fugaro models add` and the rest of that family — now runs the steps that make its change live instead of leaving them to you: `fugaro image add` alone builds the entry, redeploys the checkout's repository and publishes the catalog, `--no-apply` saves the change and stops, and `fugaro apply` runs whatever is still owed — one entry per step name, so three changes that owe the `policy` stage run it once.
- **A step that does not run costs you the run, not the work.** A step that cannot run — a coding agent's session may not publish your policy, a build that fails — leaves the change saved and the step owed, says so in one line naming `fugaro apply`, and exits non-zero, so nothing is half-applied and nothing has to be written again.
- **`fugaro update` moves what a repository's own file decided into the project.** A repository's model, rigor, A/B rate, recipe name and cap are written to the project's layer, each change printed first as one line per repository, and the repository's `.fugaro/recipes/` is published flat under the project; the runner no longer reads that folder, and `fugaro doctor` offers its removal as a diff.
- **The project says the oldest CLI that may act on it.** `fugaro update` raises that stamp to the release it ran from and prints `required CLI: 0.28.0 → 0.29.0`; a CLI below it is refused before any write and told to upgrade, `fugaro doctor` reports it, and the resident orchestrator holds below it.
- **A workflow secret is stored once for the project.** `fugaro secrets allow` and `deny` record which repositories may use it, the intake writes it, `fugaro doctor` lists any deployed job that still mounts one, and `fugaro update` redeploys every repository's job when the image map changes.

### For operators

1. Run `fugaro update` once per installation. An installation whose run index is not built, or has stopped being built, is marked for a rebuild and gets one execution of the history job in its reindex mode, printing `run index: marked incomplete and reindexing now as <execution>`; an index that is already complete is left alone, so an upgrade does not walk an index that has nothing to repair. No other command is needed.
2. Nothing else is asked of you, and no run in flight is waited for or touched: the update reaches an installation whose runs are going exactly as it reaches an idle one. The walk resumes from its own cursor until it reaches the end of history; until then `fugaro runs ls` is short and `fugaro doctor` reports `index_complete: false`. An installation that could not start the execution is marked all the same, and `fugaro runs reindex` starts it again.
3. The same `fugaro update` creates the run index's eleven composite indexes — the ones its `runs ls`, `runs stats`, `plan status` and `graph` reads are served by — in the installation's Firestore database when the credential it runs with may make that Firebase project's IAM changes, which a project owner's does. An update that may not (an operator's, typically) converges without touching the project and prints one line saying the indexes wait for an update by a project owner.
4. Every member upgrades the CLI with `brew upgrade`: after the update a CLI below 0.29.0 is refused, and so is any CI pin that selects the project. It prints first one line per repository whose model, rigor, A/B rate, recipe name or cap changes, and each recipe it renamed.

### Known limits

- **A repository `update` cannot list or cannot read is not migrated.** One admitted only by a pattern such as `*` drops its lifted values, and a recipe name it uses resolves to what a listed repository published, or to the catalog's.
- **CLIs released before 0.29.0 are not fenced.** The stamp stops this release and later ones; an older CLI is not refused.
- **The stamp fails open.** A read of it that fails lets the command go on, because it stops honest drift and IAM stays the boundary.
