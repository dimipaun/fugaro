- **`fugaro setup` uses a GCP project you already made, when it holds nothing of Fugaro's.** An ID named by `--gcp-project` (or typed at the wizard's question) that is already there, is ACTIVE and carries no installation, no installation state and no label a run of `fugaro setup` writes is adopted: setup uses it as if the run had created it, marks it Fugaro-managed in the same step a creation is marked, and says so in one line. A project that holds anything of Fugaro's is refused exactly as before, one that is being deleted says so, a billing account already linked is never relinked (and no question about it is asked), and Firebase is added only when the project has none.
- **One command is enough, and `--no-apply` is how you stop it.** A management command — `fugaro image add`, `fugaro settings set`, `fugaro accounts rm`, `fugaro project repos add`, `fugaro models add` and the rest of that family — now runs the steps that make its change live instead of leaving them to you: `fugaro image add` alone builds the entry, redeploys the checkout's repository and publishes the catalog, `--no-apply` saves the change and stops, and `fugaro apply` runs whatever is still owed — one entry per step name, so three changes that owe the `policy` stage run it once. A step that does not run costs you the run, not the work: a step that cannot run — a coding agent's session may not publish your policy, a build that fails — leaves the change saved and the step owed, says so in one line naming `fugaro apply`, and exits non-zero, so nothing is half-applied and nothing has to be written again.
- **`fugaro update` moves what a repository's own file decided into the project, and says the oldest CLI that may act on it.** A repository's model, rigor, A/B rate, recipe name and cap are written to the project's layer, each change printed first as one line per repository, and the repository's `.fugaro/recipes/` is published flat under the project; the runner no longer reads that folder, and `fugaro doctor` offers its removal as a diff. The same run raises that stamp to the release it ran from and prints `required CLI: 0.28.0 → 0.29.0`; a CLI below it is refused before any write and told to upgrade, `fugaro doctor` reports it, and the resident orchestrator holds below it.
- **A workflow secret is stored once for the project.** `fugaro secrets allow` and `deny` record which repositories may use it, the intake writes it, `fugaro doctor` lists any deployed job that still mounts one, and `fugaro update` redeploys every repository's job when the image map changes.
- **A workspace shares model credentials across its projects, and its own spend ceiling binds.** The workspace owner declares each member with `fugaro workspace project add <project> --workspace <name>` (its job service accounts, its Firebase project, its `fp`, its exchange endpoint, its database region and the repositories each account is a job of) and offers a credential to some of them or to all with `fugaro workspace share <credential> --workspace <name> --projects a,b` (or `--all-members`); a member joins with `fugaro workspace add <name>` and pins what it trusts. Runs then call the workspace's own credentials service for those credits, so the key never leaves the machine that holds it, and a member's own credential of the same kind still wins for that project. `fugaro workspace cap set --workspace <name> --monthly <amount>` records the group's ceiling; the workspace's service reserves each paid call against it before the call and settles on the answer's usage, refuses a call at the ceiling, and reports what room is left on every answer it gives. `fugaro budget kill` takes a workspace scope: it stops the workspace's service serving any shared-credential call, so every member's run that reaches one halts at once, while a member's runs on its own credentials keep going — that member's own `fugaro budget kill --all` is what stops those.
- **`fugaro update` is the whole of it, on both sides.** The workspace owner's run stands the workspace's service up, deploys the security rules the workspace's database is read under, publishes the node the service reads (from the member table and the shared list the owner's own config now holds) and grants each member's job accounts the right to call the service; on each member's machine the same `fugaro update` binds the workspace's account to that member's database and publishes where each of its repositories is served, with no flag and no second command. Both converge an installation at the previous release, and neither deletes anything.

### For operators

`fugaro update` is the whole upgrade, and nothing below is a second command. No run in flight is waited for or touched: the update reaches an installation whose runs are going exactly as it reaches an idle one.

1. Run `fugaro update` once per installation. An installation whose run index is not built, or has stopped being built, is marked for a rebuild and gets one execution of the history job in its reindex mode, printing `run index: marked incomplete and reindexing now as <execution>`; an index that is already complete is left alone, so an upgrade does not walk an index that has nothing to repair.
2. The walk resumes from its own cursor until it reaches the end of history; until then `fugaro runs ls` is short and `fugaro doctor` reports `index_complete: false`. An installation that could not start the execution is marked all the same, and `fugaro runs reindex` starts it again.
3. The same `fugaro update` creates the run index's eleven composite indexes — the ones its `runs ls`, `runs stats`, `plan status` and `graph` reads are served by — in the installation's Firestore database when the credential it runs with may make that Firebase project's IAM changes, which a project owner's does. An update that may not (an operator's, typically) converges without touching the project and prints one line saying the indexes wait for an update by a project owner.
4. Every member upgrades the CLI with `brew upgrade`: after the update a CLI below 0.29.0 is refused, and so is any CI pin that selects the project. It prints first one line per repository whose model, rigor, A/B rate, recipe name or cap changes, and each recipe it renamed.
5. **A workspace is set up by the same `fugaro update`, run by the workspace owner and then by each member.** On the workspace owner's machine: declare each member (`fugaro workspace project add <project> --workspace <name>`, with the member's job accounts, its Firebase project, its `fp`, its exchange endpoint, its database region and the repositories each account is a job of), decide what the workspace offers (`fugaro workspace share <credential> --workspace <name> …`) and record the ceiling (`fugaro workspace cap set --workspace <name> --monthly <amount>`), then run `fugaro update`. That run deploys the workspace's credentials service and its rules, publishes the node the service reads, and grants the members' job accounts their invoke right. On each member's machine: `fugaro workspace add <name>` pins the workspace's Firebase project, its issuer, its assertion key and the service account, and `fugaro update` does the rest — it binds the workspace's account to that member's database and publishes where each of its repositories is served. A member's owner consents to the workspace's authority over the project with `fugaro workspace project link`.
6. The order matters when a member adds a repository later: **the member that adds a repository needs the workspace owner's `fugaro update` before that repository's runs reach the service**, because the invoke grant is bound from the owner's member table. Until that run, such a run halts with a reason naming this step.

### Known limits

- **A member that uses an orchestrator, a coordinator or image builds keeps its own forge credential.** A shared entry of the workspace's pool carries a forge credential too (its own kind, which is what a run's forge routes are served by), but the workspace's service admits a member's job account and the workspace owner's people and no other caller class, so the member's orchestrator, coordinator and image builds — different callers on different routes — keep calling their own project's service, and a member's forge token is never shared through the workspace for them.
- The workspace cap is metered at the workspace's own service, and the reconciliation between its count and a member's ledger **runs nowhere in this release**: the alarm needs a ledger record no member writes and is deferred to its own work. The cap itself binds without it.
- One member can use the workspace's ceiling up for the others: the cap is the group's, and no per-member share of it ships here.
- **A workspace whose own installation is split gets no credentials service rather than a half-serving one.** Where the workspace's own project records a `budget.firebase_project` that is not itself, the database the service would read is another project's, so `fugaro update` creates no service account, makes no grant and deploys no credentials service for it, and the step says why and how to adopt the project as its own Firebase one. A member's own Firebase project is not this: a member may sit in whatever Firebase project it has.
- **A repository `update` cannot list or cannot read is not migrated.** One admitted only by a pattern such as `*` drops its lifted values, and a recipe name it uses resolves to what a listed repository published, or to the catalog's.
- **CLIs released before 0.29.0 are not fenced.** The stamp stops this release and later ones; an older CLI is not refused.
- **The stamp fails open.** A read of it that fails lets the command go on, because it stops honest drift and IAM stays the boundary.
