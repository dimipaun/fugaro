- **`fugaro setup` uses a GCP project you already made, when it holds nothing of Fugaro's.** An ID named by `--gcp-project` (or typed at the wizard's question) that is already there, is ACTIVE and carries no installation, no installation state and no label a run of `fugaro setup` writes is adopted: setup uses it as if the run had created it, marks it Fugaro-managed in the same step a creation is marked, and says so in one line. A project that holds anything of Fugaro's is refused exactly as before, one that is being deleted says so, a billing account already linked is never relinked (and no question about it is asked), and Firebase is added only when the project has none.
- **A workspace shares model credentials across its projects.** The workspace owner declares each member with `fugaro workspace project add <project> --workspace <name>` (its job service accounts, its Firebase project, its `fp`, its exchange endpoint, its database region and the repositories each account is a job of) and offers a credential to some of them or to all with `fugaro workspace share <credential> --workspace <name> --projects a,b` (or `--all-members`); a member joins with `fugaro workspace add <name>` and pins what it trusts. Runs then call the workspace's own credentials service for those credits, so the key never leaves the machine that holds it, and a member's own credential of the same kind still wins for that project.
- **A workspace has its own spend ceiling, and it binds.** `fugaro workspace cap set --workspace <name> --monthly <amount>` records the group's ceiling; the workspace's service reserves each paid call against it before the call and settles on the answer's usage, refuses a call at the ceiling, and reports what room is left on every answer it gives. `fugaro budget kill` takes a workspace scope, and it stops the runs of every member at once.
- **`fugaro update` is the whole of it, on both sides.** The workspace owner's plain run stands the workspace's service up, deploys the security rules the workspace's database is read under, publishes the node the service reads (from the member table and the shared list the owner's own config now holds) and grants each member's job accounts the right to call the service; on each member's machine `fugaro update --firebase-project <the member's own Firebase project>` binds the workspace's account to that member's database — the Firebase flag is what carries the root with the grant, so a plain run publishes the rest and binds nothing — and both converge an installation at the previous release. Neither deletes anything.

### For operators

**A workspace is set up by `fugaro update`, run by the workspace owner and then by each member.** Nothing below is a second command: every step is `fugaro update` at the machine that made the change.

1. On the workspace owner's machine: declare each member (`fugaro workspace project add <project> --workspace <name>`, with the member's job accounts, its Firebase project, its `fp`, its exchange endpoint, its database region and the repositories each account is a job of), decide what the workspace offers (`fugaro workspace share <credential> --workspace <name> …`) and record the ceiling (`fugaro workspace cap set --workspace <name> --monthly <amount>`), then run `fugaro update`. That run deploys the workspace's credentials service and its rules, publishes the node the service reads, and grants the members' job accounts their invoke right.
2. On each member's machine: `fugaro workspace add <name>` pins the workspace's Firebase project, its issuer, its assertion key and the service account, and `fugaro update --firebase-project <the member's own Firebase project>` binds the workspace's account to its database and publishes where each of its repositories is served. **The flag is not optional here**: the binding is made by the converge's Firebase root, whose stage skips when the member's config already records its database and no `--firebase-project` is given, so a plain `fugaro update` leaves the workspace's service unable to read that member's record and its workspace-served runs fail. A member's owner consents to the workspace's authority over the project with `fugaro workspace project link`.
3. The order matters when a member adds a repository later: **the member that adds a repository needs the workspace owner's `fugaro update` before that repository's runs reach the service**, because the invoke grant is bound from the owner's member table. Until that run, such a run halts with a reason naming this step.

### Known limits

- **A member that uses an orchestrator, a coordinator or image builds keeps its own forge credential.** A shared entry of the workspace's pool carries a forge credential too (its own kind, which is what a run's forge routes are served by), but the workspace's service admits a member's job account and the workspace owner's people and no other caller class, so the member's orchestrator, coordinator and image builds — different callers on different routes — keep calling their own project's service, and a member's forge token is never shared through the workspace for them.
- The workspace cap is metered at the workspace's own service, and the reconciliation between its count and a member's ledger **runs nowhere in this release**: the alarm needs a ledger record no member writes and is deferred to its own work. The cap itself binds without it.
- One member can use the workspace's ceiling up for the others: the cap is the group's, and no per-member share of it ships here.
- **A workspace whose own installation is split gets no credentials service rather than a half-serving one.** Where the workspace's own project records a `budget.firebase_project` that is not itself, the database the service would read is another project's, so `fugaro update` creates no service account, makes no grant and deploys no credentials service for it, and the step says why and how to adopt the project as its own Firebase one. A member's own Firebase project is not this: a member may sit in whatever Firebase project it has.
