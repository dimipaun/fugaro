- **`fugaro setup` uses a GCP project you already made, when it holds nothing of Fugaro's.** An ID named by `--gcp-project` (or typed at the wizard's question) that is already there, is ACTIVE and carries no installation, no installation state and no label a run of `fugaro setup` writes is adopted: setup uses it as if the run had created it, marks it Fugaro-managed in the same step a creation is marked, and says so in one line. A project that holds anything of Fugaro's is refused exactly as before, one that is being deleted says so, a billing account already linked is never relinked (and no question about it is asked), and Firebase is added only when the project has none.

### Known limits

- **A CLI of an earlier release refuses a policy node that carries the new `personal_workspace_tokens` key.** Upgrade the CLI (`brew upgrade dimipaun/tap/fugaro`, then `fugaro update`) before the `fugaro update` that publishes the member's switch for the personal half of a workspace's credentials: the key is a top-level one, and while the runner of an earlier release reads the node past it and warns once, the readers that decide something by the node — the launch gate above all — refuse it and name the upgrade, so a project that publishes the switch loses launches from an unupgraded CLI until it moves. The key moves no policy version, so the upgrade is the whole of the fix: no republish, no migration and no hand edit is needed.
