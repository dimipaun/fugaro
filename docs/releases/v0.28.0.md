- **You can store a credential of your own, and a run is served it.** `fugaro secrets user set NAME` stores a value under your own Google account — the value comes from stdin or a hidden prompt, and no flag or argument takes it — and `fugaro secrets user ls` and `fugaro secrets user rm NAME` list and remove what you own; `fugaro secrets shared set NAME` is the same three verbs for a credential the project shares, which only an address on the installation's admin list may write. The credentials service resolves such a name by its own container first and by the installation's bundle second, so a credential you rotate this way is served from your container and the bundle's entry is what an installation that has rotated nothing keeps reading.
- **The intake writes, and it can never read back.** The secrets intake is a Cloud Run service of the installation's own: it creates a container, adds a version to one, lists the caller's own names and dates, and deletes — and it holds no grant that reads a version's payload, so a value a person wrote is not one it can answer. The name prefix it writes under comes from the caller's verified Google account and from no field of a request, its write grant is bound to the two name prefixes and to nothing else, and it writes into an existing container only when that container's shape is exactly its own, so a container some other deployer pre-created is refused rather than trusted.
- **A run is served its own credentials under a slip, and a slip is bound to that one run.** `fugaro run` asks the service for a slip before the job is started and puts its id on the job's environment; the run claims it once at its start-up and is answered a claim secret it keeps in memory, and every call it makes after that presents the slip's id and that secret together. A call that presents one of the two without the other, or a slip that is unknown or has run past its own maximum runtime, is refused rather than served; a call that presents neither header is the slip-less path — what the service served before slips existed, and what it goes on serving from the bundle, as an older CLI's run is. The slip records the repository, the run and the job account the run is served at, and the credential set it permits is decided once, when it is issued.
- **`fugaro doctor` reports the intake and the names it may not read.** It names an installation where the intake's account holds a grant that reads a secret's value, or a write grant that is not bound under the two name prefixes, and it warns about a container whose name carries one of those prefixes and no grammar admits — a container the intake may version and delete and nothing can ever resolve.

### For operators

1. **Per installation** — run `fugaro update` once, at your own terminal. It is the whole upgrade and it asks nothing beyond the confirmation it already asks ahead of rebuilding the job images: it deploys the secrets intake (or re-pins the one already deployed to this release's image) and writes the intake's address back into the installation root, applies the credentials service's accessor over the per-user and project-shared name prefixes, and publishes the policy migration. Nothing else is needed, and there is no second command.
2. It waits for no run, and it says so in one line when runs are running: the count, and that it waits for none of them and changes nothing they hold.

### Known limits

- **A database admin can forge a slip.** Realtime Database IAM has no path-level scope, so an admin's bypass of the database's rules reaches the nodes where slips are recorded; what a forged slip still has to name is a real run identity and the account that run is served at.
- **A person's Google ID token carries gcloud's audience, so a token sent to the intake is replayable there for about an hour**, and the same token is replayable at the grant route. A replayed admin token therefore reaches write and rotate of the holder's own containers, write of the project-shared `fugaro_p_<name>`, the delete sweep of another member's whole prefix, and a slip at the grant route; it reaches no other member's own containers, because the two routes that write one carry no owner at all and take the prefix from the token's verified account. The intake reads no value and a slip is bound to a run and to a claim secret; the window is not narrowed by this release.
- **An older CLI that predates the slip path is served the bundle's entry after a rotation.** The service resolves a user-supplied credential by its container first and by the bundle second, so a run of a CLI below the release that claims a slip is served the value the bundle holds after a rotation has written the container; `fugaro update` prompts the CLI upgrade, and the value is the one the operator meant to retire.
- **Cloud Run grants the invoker per service and not per route**, so every account that may invoke the credentials service passes IAM on every route of it. The class check inside the process is the fence that decides who is served, and it is the finer of the two.
- **A slip is not a secret from the agent.** The agent shares the container with the runner and can read the runner's environment and its memory, so it can read a slip's id — and, before the run has claimed it, claim it, which is why the runner claims at its start-up rather than at its first model call. What a slip rests on is its binding to one run and its claim secret, and not its secrecy.
