- A project's limits and its allow-list are now the project's own data instead of each job's environment: `fugaro project policy publish` writes the ceiling, the prices and the repositories that may run (`allow_repos`), `fugaro project show` and `fugaro project repos ls|add|rm` read and edit them, and a run reads the policy before it starts — one it cannot read halts the run rather than falling back to the job's own ceiling, for an installation whose rules and marker are in place (see the operator steps below). The policy's `providers` block is carried but not applied yet, and an installation that publishes nothing behaves exactly as it does today.
- The operator can now **write down** where Claude goes: `routing.claude` in your own config takes an explicit list of Claude model IDs and `via: direct | openrouter | auto` (an absent switch means `direct`), and `fugaro project policy publish` copies it into the published policy, which is how a run receives it. Your config is its only definition site — a repository's `fugaro.yaml` has no `routing` key, and a project layer that writes one fails to load rather than half-applying it. A run resolves each named ID to the route's own ID (read by the pins, the price lookup and the recorded `serving_model`/`priced_as`), `fugaro validate` prints that resolution or says it is unresolved offline (and checks a routed pin with the same price, variant and alias rules the run applies), and `fugaro doctor` reports the same resolution; a Claude pin with no Anthropic key and no switch is a note from `validate`, never a refusal, since only the cloud knows which keys exist.
- `fugaro secrets set NAME` now stores the project's copy by default for a name that has a project-wide meaning (a reserved secret such as `anthropic-api-key`, a provider key, a named Claude account), with `--repo` for a repository's own copy and `--project-wide` still accepted as a synonym; a repository copy still wins over the project's, and `secrets ls` follows the same default. A project-scope key mounts on the repository's job without an extra opt-in, and `fugaro doctor` gains a `secret-scope` check that lists which names are project-scope and warns when a repository copy shadows one.
- A route may claim **one exact** `anthropic/<id>`, which is the operator's opt-in to have that one Claude model served through the provider route — from your project config or from the project layer's `claude_models`, never from a repository's `fugaro.yaml`. That stage needs `agent.auth: api-key`, `budget.mode: enforce`, the repository inside the route's `allow_data_to` and a price for the claimed ID (your own `model_prices` when the claim comes from the layer), and a routed Claude that reports no cache reads is charged at the full input rate.
- A recipe can be `mode: artifact` — a run whose deliverable is a file rather than a pull request: it declares its `outputs`, runs the optional `plan` stage and then the repository's own `commands.render` command, ends with `outcome: artifacts` and neither pushes a branch nor opens a pull request. `fugaro budget preview` prints that run's compute ceiling beside the model ceiling and says it is **not capped** — the compute is bounded by `timeouts.total`, not by `budget.per_run_usd`. The outputs are selected, capped, hashed and uploaded to `runs/<slug>/<run>/artifacts/` and recorded in `result.json`; the optional `commands.probe` runs over the staged set before the upload and fails closed; `fugaro run --attach` uploads files in with the launch; `fugaro artifacts ls|get` takes the files back, with `runs ls` and `diagnose` showing them; the user guide is `docs/artifact-runs.md`.

### For operators

1. Upgrade the CLI (`brew upgrade dimipaun/tap/fugaro`, or this release's archive with its cosign check).
2. If your installation has a database, deploy the rules **first**: `fugaro init --firebase <firebase-project-id>` in the installation root writes the rules a policy is read under and the marker that records them. `fugaro project policy publish` refuses to publish without that marker, and an older CLI's `init --firebase` is exactly what redeploys the older rules under an unchanged marker — so use a 0.8.0 binary for this step. `fugaro doctor` reports the two skews separately, and only one of them halts: a marker whose generation is below this Fugaro's leaves **no** run reading a published policy — every run keeps the ceiling from its own job's environment, silently, and `publish` refuses until the marker is brought up — while deployed rules older than the marker make the policy node unreadable, so every budget-on run halts.
3. Roll the runner out in this order, because neither `fugaro upgrade` nor `fugaro image refresh` writes a job's **environment** and only `fugaro init --repo` does: (a) build and publish each workflow's image from this release, (b) `fugaro init --repo` in each checkout to write `FUGARO_RTDB_URL` and `FUGARO_FIREBASE_API_KEY` into each job, (c) `fugaro upgrade` (its cloud step is `fugaro image refresh`) so the jobs point at the new image. A rollout that skips (b) leaves every run reading its ceiling from the job's environment and never seeing the policy, and no check reports that state — `fugaro doctor`'s `policy-vs-jobs` reports the neighbouring one, jobs still on a runner image that predates this Fugaro, which is what skipping (c) leaves. **Step 2 must come before (b)**: an `init --repo` planned from a local config with no `budget.rtdb_url` removes the backend from the jobs that have it, and the plan says so — pass the installation's `--budget-mode` (and `--firebase`) again if you use them.
4. Then adopt the model, once per installation: `fugaro project policy publish` writes the policy (the ceiling, the prices and `allow_repos`) and `fugaro project repos add|rm` edits the allow-list afterwards. The first publish seeds `allow_repos` from your config's `repos:` map and the shared config's repository list, and a later publish keeps the node's own list — so removing an entry is how you un-enroll a repository. A published policy with an **empty** `allow_repos` admits no repository at all, which is not the same as an installation that has published nothing: `fugaro run` makes the same check before it creates an execution.

Nothing changes until step 4: an installation with no published policy spends and is capped exactly as it does today. The one change that lands earlier is step 2's: an installation whose local config has `budget.rtdb_url` now depends on Firebase and Cloud Storage at launch and at run start — every job carries the backend's address and key whatever the mode, the launch reads the policy and leaves a token object in the runs bucket, and each run reads it before it starts — so either service being down **fails closed** (the launch is refused, or the run halts) instead of running on the environment ceiling. `--budget-mode off` still stops only the cap session, and an installation that never configured a database keeps today's behaviour exactly.

Not in this release: project-centric phases 3 to 6 (shared project jobs, enrollment as data, the OAuth pool and the backing Git repository, including the monorepo-folder export), the Compute Engine/Cloud Batch execution backend (the code is inert and `backend: cloud-batch` is refused by the config), the desktop console, and `checkout: clone` — still not usable, exactly as 0.7.5's notes said: `fugaro init --repo` and `fugaro image refresh` refuse to deploy or move a clone workflow's job, and the flip belongs to the shared project jobs this release does not ship. Checks 44 to 46 — the price catalog and the two senior-reviewer checks — had **not** been run when this release was cut: they are run against the sandbox installation after the tag, and anything they find becomes a 0.8.0.x patch release, never a moved tag. Policy as data, the routing switch, project scope by default and artifact runs have no live check written yet, so they are not covered by one before the tag.
