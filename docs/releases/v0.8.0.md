### For operators

1. Upgrade the CLI (`brew upgrade dimipaun/tap/fugaro`, or this release's archive with its cosign check).
2. If your installation has a database, deploy the rules **first**: `fugaro init --firebase <firebase-project-id>` in the installation root writes the rules a policy is read under and the marker that records them. `fugaro project policy publish` refuses to publish without that marker, `fugaro doctor` reports the skew (a marker whose generation is below this Fugaro's, or deployed rules older than the marker, means no run reads a published policy and every budget-on run halts), and an older CLI's `init --firebase` is exactly what redeploys the older rules under an unchanged marker — so use a 0.8.0 binary for this step.
3. Roll the runner out in this order, because neither `fugaro upgrade` nor `fugaro image refresh` writes a job's **environment** and only `fugaro init --repo` does: (a) build and publish each workflow's image from this release, (b) `fugaro init --repo` in each checkout to write `FUGARO_RTDB_URL` and `FUGARO_FIREBASE_API_KEY` into each job, (c) `fugaro upgrade` (its cloud step is `fugaro image refresh`) so the jobs point at the new image. A rollout that skips (b) leaves every run reading its ceiling from the job's environment and never seeing the policy, which `fugaro doctor` will tell you. **Step 2 must come before (b)**: an `init --repo` planned from a local config with no `budget.rtdb_url` removes the backend from the jobs that have it, and the plan says so — pass the installation's `--budget-mode` (and `--firebase`) again if you use them.
4. Then adopt the model, once per installation: `fugaro project policy publish` writes the policy (the ceiling, the prices and `allow_repos`) and `fugaro project repos add|rm` edits the allow-list afterwards. The first publish seeds `allow_repos` from your config's `repos:` map and the shared config's repository list, and a later publish keeps the node's own list — so removing an entry is how you un-enroll a repository. A published policy with an **empty** `allow_repos` admits no repository at all, which is not the same as an installation that has published nothing: `fugaro run` makes the same check before it creates an execution.
Nothing changes until step 4: an installation with no published policy spends and is capped exactly as it does today. The one change that lands earlier is step 2's: an installation whose local config has `budget.rtdb_url` now depends on Firebase and Cloud Storage at launch and at run start — every job carries the backend's address and key whatever the mode, the launch reads the policy and leaves a token object in the runs bucket, and each run reads it before it starts — so either service being down **fails closed** (the launch is refused, or the run halts) instead of running on the environment ceiling. `--budget-mode off` still stops only the cap session, and an installation that never configured a database keeps today's behaviour exactly.

Not in this release: project-centric phases 3 to 6 (shared project jobs, enrollment as data, the OAuth pool and the backing Git repository, including the monorepo-folder export), the Compute Engine/Cloud Batch execution backend (the code is inert and `backend: cloud-batch` is refused by the config), the desktop console, and `checkout: clone` — still not usable, exactly as 0.7.5's notes said: `fugaro init --repo` and `fugaro image refresh` refuse to deploy or move a clone workflow's job, and the flip belongs to the shared project jobs this release does not ship. The live checks for this release's new surfaces — 44 to 46 (the price catalog and the two senior-reviewer checks), 49 to 51 (policy as data, the routing switch, project scope by default) and 58 (artifact runs) — had **not** been run when this release was cut: they are run against the sandbox installation after the tag, and anything they find becomes a 0.8.0.x patch release, never a moved tag.
