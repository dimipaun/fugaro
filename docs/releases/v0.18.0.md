- **A managed project lets your coding agent manage it, behind a fixed gate.** In a project Fugaro created (both marks present: the runs-bucket marker and the GCP label), an agent session can now run `fugaro update`, `config publish`, `project policy publish`, `image refresh`, `accounts add` and `settings set`/`unset` without asking you to type a confirmation, but only for changes the gate judges safe: a step that loosens anything (raises a ceiling, widens an allow-list, lowers a review floor, adds an executable key) is still refused and stays yours to run at your own terminal. `fugaro doctor` shows the last managed apply, and `fugaro managed unflag` takes a project back out.
- **A project's catalog images are rebuilt on a schedule.** One project-level job checks the catalog every night under its own narrowly granted account and rebuilds entries whose definition or base moved; the job ships paused until you enable it, and `fugaro update` plans it as soon as a catalog exists.
- **A first catalog publishes itself.** `fugaro update` now makes a project's first policy publish when only the published node can carry the local config (the catalog case that 0.17.0 silently skipped), behind a typed confirmation; an empty allow-list needs its own confirmation that names the consequence.
- **Configuration without hand edits.** `fugaro settings set` has `--add-entry` and `--remove-entry` for maps and lists; the diff of `fugaro project policy publish` lists the image catalog and folds empty members; and an unconfigured checkout gets a guided sentence naming `/fugaro:setup` instead of a filesystem error.
- **A person can read pull requests and files through the credentials service.** The person class accepts the ID token a user account can mint with plain `gcloud` login, and Bitbucket repositories gain a contents reader, so a dockerfile source on a provider that cannot read a file is refused early.
- **`fugaro image build` needs no environment.** A catalog entry's Dockerfile is read with the repository's own GitHub App: the App ID comes from the project config and the key from the repository's secret in Secret Manager, read with your own credentials and never in a coding agent's session; and the build now records its result, which 0.17.0's did not.

### For operators

1. Upgrade the CLI and run `fugaro update` in each checkout: it brings the installation (Terraform, rules, the catalog check job and its account), the published policy and the checkout to this release. It asks for the typed project name where it plans the catalog-check grants.
2. If you publish an `image_catalog`, run `fugaro image build <entry>` once per entry after the update; a build from a 0.17.0 CLI never recorded itself, so an entry built then shows "not built yet" until it is built again.
3. The catalog check job is created paused. Enable its schedule when you want nightly rebuilds.

### Known limits

- Per-repository image settings (`image:`, `dockerfile:`, `rebuild.*`) still work in this release; the catalog is the new path, and their removal is planned for 0.19.0.
- The managed gate's allowlist of settings keys (the two round-count floors) is recorded as pending your confirmation (D1027); `fugaro rigor` and `accounts rm` under the gate are not built yet.
- The deployer fence's per-service condition checks (Check 68) have not been measured live: the fence applies and holds no drift, and the remaining measurements are an owner-run check after this release.
- The end-to-end catalog build on the dogfood installation is verified after this release rather than before it.
- A catalog of only prebuilt entries, with no base image recorded, makes `fugaro user` and `fugaro update` refuse until `base_images.base` is set.
