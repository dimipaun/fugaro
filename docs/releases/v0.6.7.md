- Provider-model runs (a non-Anthropic model through OpenRouter on `agent.auth: api-key` with the budget gateway on) now report what they really cost: the gateway used to settle every streamed OpenRouter call at its worst-case reservation, so a $0.01 DeepSeek run showed as $1.19 and a per-run cap would have tripped on estimates. It now reads the usage OpenRouter reports in the stream's final events; a call whose usage it cannot trust still settles at the reservation, never lower than before, and the run's log says why (`usage_unparsed` with a reason).
- The first complete provider-model run works end to end: DeepSeek (`deepseek/deepseek-v4.1-flash`) coded and reviewed a change through OpenRouter on the sandbox. Two things to know before you try it: OpenRouter refuses a route whose providers may train on your prompts when your account setting forbids it (the error is "Paid model training violation"; allow only zero-data-retention providers in your OpenRouter provider settings), and a model that is not in `model_prices` is priced at the table maximum, so add an entry for the model you route (`docs/multi-model.md` §6).
- `fugaro upgrade` now tells you when the cloud job still carries an old copy of your project config (providers, model prices, budget settings) and names the one command that fixes it, `fugaro init --repo .`; it never runs it, and `--yes` does not cover it.

### For operators

1. Upgrade the CLI (`brew upgrade dimipaun/tap/fugaro`), then run `fugaro upgrade` in each checkout: the gateway ships inside the job image, so the usage fix only takes effect on an image built from 0.6.7, which `fugaro upgrade` rebuilds when it finds it stale.
2. If `fugaro upgrade` prints the stale-config note, run `fugaro init --repo .` in your own terminal and read its plan before confirming.
3. For provider models, add a `model_prices` entry for the exact model id you route and check your OpenRouter provider and data-policy settings (see `docs/multi-model.md`).
4. Repositories that use only Claude models see no change except one stricter rule: a negative usage count in a late or duplicate `message_start`, or a bad `message_delta` after `message_stop`, now settles the call at its reservation.
