- **A teammate's access is now a role held at a scope.** `fugaro user grant MEMBER --role viewer|operator|admin --scope project|all-repos|<patterns>` records one role and scope pair in the installation's own grants node, `fugaro user revoke` takes it away, `fugaro user ls --repo owner/name` (or `--json`) says who holds what and the role each person holds in a repository, and a repository-scoped pair limits what the CLI and the console let that teammate act on, to the repositories it names. It grants no cloud access of its own and is a check rather than a barrier: a teammate who already holds the project's IAM still reaches every repository through the cloud, and one who holds none is refused everywhere.
- **The installation's two IAM lists are derived from that record.** `fugaro update` migrates an installation still holding `launchers` and `operators` into grants in place — `launchers` become operator at the project, `operators` become admin at the project, and the project's owners, editors and `budget_admins` stay implicit admins — and for a pure rename the plan it shows is empty. `fugaro user add` and `fugaro user rm` keep editing the two lists in your own config file alone, and the next `fugaro update` re-derives them from the grants, so a member written that way is dropped.
- **The commands that spend, cancel or read a run, and the settings, policy, images, budget, accounts, secrets and repository writes this release gates, ask the caller's role and scope before they act** and refuse with the role and the scope they needed rather than with a cloud error: a repo-scoped operator is refused on another repository, and a repo-scoped admin is refused on the project's own guardrails. The check reaches the commands this work gates and not yet every writer of the same files, which a limit below states.
- **The viewer role ships.** `fugaro user grant MEMBER --role viewer --scope project` records a viewer, and the commands that read a run, its logs or the project's spend accept one while a launch or a cancel is refused. **Roles are granted at a terminal.** `fugaro user grant` and `fugaro user revoke` are refused in a coding agent's session, which prints the command for the person to run.
- **A launch of a repository from outside its checkout has worked since 0.23.0, where the installation has a credentials service and has redeployed it: these notes are its first announcement, because 0.23.0's and 0.24.0's did not carry it.** `fugaro run --repo owner/name`, and the console's launches, which always run in the app's own empty directory, read the repository's `fugaro.yaml` at the ref the run checks out through that service, as you, and decide from it which job the run belongs on: the token is the service's, minted for that one repository, and the CLI holds no App key. A launch from the repository's own checkout reads the same file out of the checkout, with no credential at all.
- **That read is refused in a coding agent's session, with the same refusal every other read made with your own credential gets.** Run the launch in your own terminal window, or from the repository's checkout, where nothing is read at all. **Where the installation has no credentials service there is nothing to make the read with, so a launch from outside the checkout whose job can only be decided from the document — a provider a shared job serves, on a project that has published a profile — refuses exactly as it does today and names the checkout as the way out.** The launcher holds no provider credential of its own, so that installation's checkout stays the way to launch such a repository. Every other launch from outside the checkout is untouched: a repository no shared job serves (every Bitbucket one) and a project that has published no profile keep the per-repository job, and read nothing.

### For operators

1. **Per installation** — run `fugaro update` once, at your own terminal. It migrates the `launchers` and `operators` lists into the grants node under `config/admin/access`, derives both IAM lists from it, and retires the old keys in the same run: there is no second command, nothing to delete and nothing to repair. An installation whose lists were only renamed shows an empty plan.
2. Per installation, on your own machine, run `fugaro update` unless it has already been run on 0.23.0 or later. The permission set the read asks for arrived with **0.23.0**, and every `fugaro update` re-pins the credentials service's image to the release's own, so an installation already updated since then already mints it and needs nothing here, while one last updated before 0.23.0 gets it from this update as from any other since. Nothing else is required of you, and no repository's own root has to be re-applied for this.

### Known limits

- **A scoped role is a policy check, not a cloud barrier.** A role held at all-repos or at a list of repository patterns is judged by the CLI and the console, and the cloud keeps its project-wide IAM: per-repository cloud enforcement is a later slice, and a scoped pair grants no cloud access of its own.
- **The check on settings writes is partial: some writers of the same files ask no role yet.** `fugaro rigor set` writes the project layer file, `fugaro workflow add|rm` and `fugaro models use` write a repository's own `fugaro.yaml`, and `models add|rm`, `project repos set`, `project profile set|add|rm` and `project routing set` write this machine's own project config — each through the same write the gated commands use, and none of them asks who is calling. Nor do `fugaro update`'s own publishes of the layer and the policy: a caller the gate refuses in front of the publish still reaches both writes by running `fugaro update`. Until those writers are gated, what bounds each is the cloud permission the file or the node itself needs — not the roles.
- **A repository-scoped teammate holds nothing in the cloud.** The IAM lists are derived from project-scope pairs, so a scoped operator or admin works through the checks over the grants their own account already holds; where they hold none they are refused everywhere, which the refusals say.
- **Anyone given the write the grants node needs is effectively a project admin.** `roles/firebasedatabase.admin` writes every node under `config/`, the grants node included, so the write stays with the project's owners, editors and `budget_admins`; an admin stored in the node holds no database write of its own, and the command refuses for them and names `budget_admins`.
- **A grant or a revoke refused in a coding agent's session is a courtesy, not a barrier.** Sessions are detected by environment variables an agent can unset, so the refusal is there to stop an accident rather than an agent that means it.
- **The viewer's read-only cloud grants are not filled in yet.** The installation's Terraform carries a viewer list with the read-only role and grants of this design, and no command of this release populates it: a viewer added now reaches what the CLI and the console check, and the list's cloud grants land once a run derives it. The live check that a viewer cannot launch or cancel has not been run.
- **The read's token reaches the whole repository, not the one file.** The mint the service serves carries `contents`, `pull_requests` and `metadata`, all read and no write, and it is a person route: every person on the installation's people list can mint a full-tree read of any repository the installation serves, from their own terminal. One file is how the launcher uses the token, not a limit on it.
- **A read that fails is a refusal, never a fallback to the per-repository job.** A repository the installation does not hold, an identity that is not one of its people, no network, a forge that answers 5xx, a ref the repository does not have, and a document that does not resolve all refuse, naming the cause and the checkout as the way out — a run placed on a job the project's policy did not choose is worse than a refusal.
- **No live check has been run for this path.** The read outside a checkout is proved by tests that replay the forge's answers and by the unit tests; nothing in `docs/gcp-live-checklist.md` covers a launch from outside a checkout, so what a real installation's service mints and a real forge answers is unverified until you run one.
