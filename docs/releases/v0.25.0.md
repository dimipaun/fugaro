- **A launch of a repository from outside its checkout works again where the installation has a credentials service and has redeployed it.** `fugaro run --repo owner/name`, and the console's launches, which always run in the app's own empty directory, read the repository's `fugaro.yaml` at the ref the run checks out through that service, as you, and decide from it which job the run belongs on: the token is the service's, minted for that one repository, and the CLI holds no App key. A launch from the repository's own checkout reads the same file out of the checkout, with no credential at all.
- **That read is refused in a coding agent's session, with the same refusal every other read made with your own credential gets.** Run the launch in your own terminal window, or from the repository's checkout, where nothing is read at all.
- **Where the installation has no credentials service there is nothing to make the read with, so a launch from outside the checkout whose job can only be decided from the document — a provider a shared job serves, on a project that has published a profile — refuses exactly as it does today and names the checkout as the way out.** The launcher holds no provider credential of its own, so that installation's checkout stays the way to launch such a repository. Every other launch from outside the checkout is untouched: a repository no shared job serves (every Bitbucket one) and a project that has published no profile keep the per-repository job, and read nothing.

### For operators

1. Per installation, on your own machine, run `fugaro update` unless it has already been run on 0.23.0 or later. The permission set the read asks for arrived with **0.23.0**, and every `fugaro update` re-pins the credentials service's image to the release's own, so an installation already updated since then already mints it and needs nothing here, while one last updated before 0.23.0 gets it from this update as from any other since. Nothing else is required of you, and no repository's own root has to be re-applied for this.

### Known limits

- **The read's token reaches the whole repository, not the one file.** The mint the service serves carries `contents`, `pull_requests` and `metadata`, all read and no write, and it is a person route: every person on the installation's people list can mint a full-tree read of any repository the installation serves, from their own terminal. One file is how the launcher uses the token, not a limit on it.
- **A read that fails is a refusal, never a fallback to the per-repository job.** A repository the installation does not hold, an identity that is not one of its people, no network, a forge that answers 5xx, a ref the repository does not have, and a document that does not resolve all refuse, naming the cause and the checkout as the way out — a run placed on a job the project's policy did not choose is worse than a refusal.
- **No live check has been run for this path.** The read outside a checkout is proved by tests that replay the forge's answers and by the unit tests; nothing in `docs/gcp-live-checklist.md` covers a launch from outside a checkout, so what a real installation's service mints and a real forge answers is unverified until you run one.
