- **A teammate's access is now a role held at a scope.** `fugaro user grant MEMBER --role viewer|operator|admin --scope project|all-repos|<patterns>` records one role and scope pair in the installation's own grants node, `fugaro user revoke` takes it away, `fugaro user ls --repo owner/name` (or `--json`) says who holds what and the role each person holds in a repository, and a repository-scoped pair is what lets a teammate work one repository without the rest.
- **The installation's two IAM lists are derived from that record.** `fugaro update` migrates an installation still holding `launchers` and `operators` into grants in place — `launchers` become operator at the project, `operators` become admin at the project, and the project's owners, editors and `budget_admins` stay implicit admins — and for a pure rename the plan it shows is empty. `fugaro user add` and `fugaro user rm` keep editing the two lists in your own config file alone, and the next `fugaro update` re-derives them from the grants, so a member written that way is dropped.
- **The commands that spend, cancel or read a run, and the settings, policy, images, budget, accounts, secrets and repository writes this release gates, ask the caller's role and scope before they act** and refuse with the role and the scope they needed rather than with a cloud error: a repo-scoped operator is refused on another repository, and a repo-scoped admin is refused on the project's own guardrails. The check reaches the commands this work gates and not yet every writer of the same files, which a limit below states.
- **The viewer role ships.** `fugaro user grant MEMBER --role viewer --scope project` records a viewer, and the commands that read a run, its logs or the project's spend accept one while a launch or a cancel is refused.
- **Roles are granted at a terminal.** `fugaro user grant` and `fugaro user revoke` are refused in a coding agent's session, which prints the command for the person to run.

### For operators

1. **Per installation** — run `fugaro update` once, at your own terminal. It migrates the `launchers` and `operators` lists into the grants node under `config/admin/access`, derives both IAM lists from it, and retires the old keys in the same run: there is no second command, nothing to delete and nothing to repair. An installation whose lists were only renamed shows an empty plan.

### Known limits

- **A scoped role is a policy check, not a cloud barrier.** A role held at all-repos or at a list of repository patterns is judged by the CLI and the console, and the cloud keeps its project-wide IAM: per-repository cloud enforcement is a later slice, and a scoped pair grants no cloud access of its own.
- **The check on settings writes is partial: some writers of the same files ask no role yet.** `fugaro rigor set` writes the project layer file, `fugaro workflow add|rm` and `fugaro models use` write a repository's own `fugaro.yaml`, and `models add|rm`, `project repos set`, `project profile set|add|rm` and `project routing set` write this machine's own project config — each through the same write the gated commands use, and none of them asks who is calling. Nor do `fugaro update`'s own publishes of the layer and the policy: a caller the gate refuses in front of the publish still reaches both writes by running `fugaro update`. Until those writers are gated, what bounds each is the cloud permission the file or the node itself needs — not the roles.
- **A repository-scoped teammate holds nothing in the cloud.** The IAM lists are derived from project-scope pairs, so a scoped operator or admin works through the checks over the grants their own account already holds; where they hold none they are refused everywhere, which the refusals say.
- **Anyone given the write the grants node needs is effectively a project admin.** `roles/firebasedatabase.admin` writes every node under `config/`, the grants node included, so the write stays with the project's owners, editors and `budget_admins`; an admin stored in the node holds no database write of its own, and the command refuses for them and names `budget_admins`.
- **A grant or a revoke refused in a coding agent's session is a courtesy, not a barrier.** Sessions are detected by environment variables an agent can unset, so the refusal is there to stop an accident rather than an agent that means it.
- **The viewer's read-only cloud grants are not filled in yet.** The installation's Terraform carries a viewer list with the read-only role and grants of this design, and no command of this release populates it: a viewer added now reaches what the CLI and the console check, and the list's cloud grants land once a run derives it. The live check that a viewer cannot launch or cancel has not been run.
