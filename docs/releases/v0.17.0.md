- **A project can keep a catalog of named images, and a run picks from it.** An operator lists named images with tags (a Dockerfile in one of the project's repositories or written out in the catalog) under `image_catalog` in the project policy, `fugaro image ls`, `add`, `rm`, `build` and `promote` manage the entries, and the cloud build copies each Dockerfile, mounts the workflow's build secrets, runs the smoke and records the result. A run's image is chosen by the tags it needs: the entry that covers every needed tag wins, a task that needs `docker` runs on a VM or Batch only, and a repository that pins an image by hand keeps it, with a warning at deploy time, instead of being overridden.
- **The smoke asserts the runtime contract on any base image.** Whatever base a catalog entry builds from, the smoke checks that the critical tools and the shell are present and fails the build when the tools table cannot be read, so a catalog image never reaches a run unverified.
- **The independent review's mutation check runs after the review stage,** so the review judges the head as pushed and the check that breaks and restores a guard no longer sits before it; and each review level's own focus prompt (levels 1 and 2) now reaches its reviewer.
- **`fugaro settings set` and `unset` classify an edit before writing it.** The dry run says whether an edit widens a ceiling, names the layer it would write and the value the winning layer would keep, and writes nothing; a no-op is no longer reported as a widening. The read behind it carries which settings are writable, who owns them and which layer a write targets.
- **Bitbucket repositories can be read through a read-scoped consumer.** The credentials service's read mint has a person caller class and a coordinator caller class, `fugaro coordinator show` prints a Bitbucket pull request, the coordinator's sweep and `coordinator status` read Bitbucket through the service (an installation whose repositories are all on Bitbucket needs no GitHub App), and `scripts/live-checks/check145.sh` lets an owner measure the consumer's facts (token lifetime, reach, refusal of a write) on a sandbox workspace without ever printing the credential.

### For operators

1. Upgrade the CLI and run `fugaro update` in each checkout. An installation that has no `image_catalog` plans exactly as before; one that publishes a catalog gets one new IAM grant per repository root, which lets the build account move tags on the shared registry.
2. A catalog entry is built with `fugaro image build`, then pointed at by a repository with `fugaro image promote`; an older job image refuses a catalog and names `fugaro update`.
3. To use the Bitbucket read mint, store the read consumer with `fugaro creds set bitbucket-read-consumer`, redirecting a small YAML file of `key`, `secret` and `workspace` into it (the value is read from stdin only and never printed), after running Check 145 on a sandbox workspace. The same `fugaro update` grants the coordinator's job its invoker role on the service.

### Known limits

- A catalog entry's Dockerfile source is not checked to belong to this project's repositories: the catalog is operator-owned, and an operator can publish an entry that points at any repository the installation's forge access reaches.
- `fugaro image add` writes a Dockerfile source only; a prebuilt-image entry is written by hand in the project config, where `validate` accepts it.
- A catalog build mounts the repository's own workflow secrets for every entry it builds, because an entry names no secrets of its own yet; an entry whose Dockerfile lives in another repository is refused.
- Scheduled rebuilds of a catalog's images are not part of this release.
- `fugaro coordinator show` for a GitHub pull request still needs the GitHub App's ID and key in the environment of the person who runs it (and is refused where the credentials service holds the key), so the console's pull-request detail draws the CLI's refusal there; reading GitHub through the service for a person comes in a later release.
- The Bitbucket consumer's refresh token, single-token revocation, IP allowlist and scope listing are not measurable on the sandbox plan, and the check reports them as unverified.
