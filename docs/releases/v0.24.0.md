- **A run can end ready with a reviewer's smaller findings written down instead of fixed.** A new step between the review and the fix weighs every finding the mode's table would have blocked — against the task the run was given, and in `startup` and `pro` only — and either keeps it for the fixer or records it as a follow-up. A security or data-loss finding, an impact of 5 outside `hotfix`, a finding the reviewer left unscored, and one only the owner can settle are never deferred, and a triage call that fails or cannot be read blocks everything the table blocks. A repository switches the step off with `agent.triage: false` in its own `fugaro.yaml`, and the owner's switch for the whole project merges tighter-only, so off wins wherever it is written.
- **The deferrals are in the pull request and in the run's report, and `fugaro followups RUN` files them once the pull request is merged.** The status section carries a **Deferred (follow-ups)** list with the one-line reason each finding was left, and a run that reaches its review cap finalizes ready with the leftovers deferred in `startup` and POC, and stays a draft in `pro`. `fugaro runs ls --debt` lists the work a review left behind; `fugaro followups` prints the plan and writes nothing by default, `--launch` files one task per group, at most `--max` of them (10 by default), it refuses while the pull request is still open, and `fugaro runs ls --json` carries `follow_up_of` on each of those runs.
- A repository no longer needs its own `image:` block: the project's catalog decides the image its jobs run, and a repository that still carries the old key is told once that the key is ignored rather than being refused. A run on a catalog image carries the repository inside the image, so the job starts on the code it was asked to work on instead of cloning it first. A skill builds the project's images for you: it surveys the repositories, proposes at most four that cover them, and generates each Dockerfile from what the code actually needs. Every proposed image is built by the cloud, never on your machine, and the build is checked against the runtime contract before a run can use it; a rerun proposes only what changed.
- **A project can name its own credentials, group them into ordered pools and give each of a run's four crafts the model and the credential or pool its calls go out on.** `fugaro accounts add --type claude-oauth` declares a typed credential, `fugaro accounts pool add|rm|ls` manages the ordered pools, and `fugaro craft ls` shows, per craft, what it resolves to and the layer each half came from, offline and by name, never by value; a pool spreads across its members, a pool of subscriptions stays inert until the owner's subscription-spread switch is on, and a repository selects among the project's credentials and can never add one.
- **A project can sample its runs and give each one a shadow challenger.** With `rate` in the project layer's `ab:` block, a share of eligible runs is launched beside a second run on another coder model — the same task, at the same commit, from the same recipe, mode and tier. The challenger is a shadow: it pushes nothing, opens no pull request, comments on nothing and holds no git write credential, so a sampled task still leaves one branch and one pull request, and both arms carry the pair and the same batch label — `ab-pair-<the champion's run ID>`, or the launch's own `--batch` label where it passed one — so `fugaro runs ls --batch <label>` shows the two. A/B is off until the layer turns it on, and no model is switched for you: this is a report.
- **`fugaro ab` scores the pairs, and they are judged blind by a run of their own.** One row per rigor mode, tier and model pair, with the challenger's wins, losses and ties, the interval around its win share, the median pair cost ratio, each arm's halt count, the champion's follow-ups, and a recommendation at the mode's exchange rate; it reads the run records alone, so the same records always give the same table, and a row with fewer than 20 decisive pairs says it has no conclusion rather than approximating one. `judge_model` in the same block names the model the `ab-judge` recipe calls, one judge run per repository at a time, over each pair's two patches shown as A and B with no run, branch, model or commit in them; the order is swapped on the second pass, and only an arm both passes agree on is decided — anything else is a tie.

### For operators

1. Once per installation, on your own machine, run `fugaro update`. It is the whole upgrade for this release: the published policy learns the `triage` stage name and `agent.triage` as it normally converges, and the job images and the base-derived images the catalog uses are rebuilt, each behind its own confirmation. It also reads an existing installation's `claude_accounts` and per-stage account keys as the new typed credentials and crafts, in place, on the installation's own config, with nothing to type and nothing to delete; where `fugaro creds set` refuses a bundle because the deployed credentials service cannot read it, the answer is this same `fugaro update`, which redeploys the service. It also asks for the review of the steps it will apply, and nothing here runs after a deploy or needs a backfill.
2. Point the `fugaro:images` skill at a repository you want on the catalog. The skill proposes, you confirm, and the images it proposes are built by the cloud.
3. **Per installation, and only if you want A/B at all.** Nothing is required: a project that publishes no `ab:` block samples nothing, and every repository of it keeps running as it does today. To turn it on, add the `ab:` block (`rate`, `challengers`, `max_pairs_per_day`, `judge_model` and any `exchange_rate` a mode should have) to the project's layer file and publish it with `fugaro config publish` at your own terminal; `fugaro update` publishes the same file, so an installation that is already being updated needs no second command. Nothing samples a launch until the layer is published.
4. **Per installation, and only where the coordinator's front door is on.** Nothing is required: no released `fugaro update` turns that door on — its opt-in is the installation's `mcp_server` setting and the flag that writes it is a later release's (D934) — so an installation that never turned it on plans exactly what it planned before. Where it is on, this release adds the front door's read of the orchestrator's node: one custom role in the installation's Firebase project (`fugaroStateRead`, carrying `firebasedatabase.instances.get` and nothing else, because a Realtime Database grant has no path-level scope and `get` is the only read there is) and its one binding to the front door's own account (`fugaro-mcp`). Both are Terraform this same `fugaro update` applies: no second command, no `gcloud` line, nothing to delete and nothing to repair. That plan carries project-level IAM, which the managed plan gate admits none of (its type list refuses `google_project_iam_custom_role` and `google_project_iam_member` outright), so on a managed project the installation stage is not applied under the gate: it keeps its own typed confirmation, which you give at your own terminal — a coding agent's session cannot give it, by design and not as a limitation, and `docs/workspaces/implementation-plan.md`'s W7 records the same mechanism for a member's binding.

### Known limits

- **The floor rests on the reviewer's own labels.** What makes a finding undeferrable is the class and the impact the reviewer wrote, so a coder that can steer a reviewer's wording can have a real correctness finding deferred where the mode's table blocks it today. The owner accepted that for this release; a bound on the judge's reach is a later change and no wire format moves for it.
- **Nothing wires the follow-ups to a scheduler.** `fugaro followups` is a command a person runs after the merge: a deferred finding does not queue work by itself, and a pull request waiting on one is not unblocked by anything here.
- **No run merges.** A ready pull request is the end of the run's part of the work, and a merge is a person's — or the coordinator's, under its own gate — step, exactly as it is for a run that ends ready with no deferrals at all.
- The image skill's behaviour is pinned by two owner-run checks, **Check 500** and **Check 501**, and neither has been run: they are written as scripts and their rows in the live checklist still read NOT RUN. What the skill does end to end on a project that is not the author's, and what an installation really starts a run on after this release's upgrade, are unverified until you run them.
- The cap of four images is the skill's own rule. Nothing in the CLI enforces it, so a project whose catalog grows past four keeps working and is never told.
- **Nothing here has been proven live, and no live check covers it yet.** The three that will — a sampled run leaving one branch and one pull request, what the judge's stored input shows, and a provider challenger end to end — are still plan tasks (A2.2, A5.3 and A6.2): `docs/gcp-live-checklist.md` holds no Check 210, 211 or 212, and none of the three has been run. The unit and emulator tests are the only evidence that the sampler, the pair launch and the judge behave as written.
- **A row advises nothing until it has 20 decisive pairs.** A project that samples a tenth of its runs reaches that in weeks, not days, and each row is counted per rigor mode and tier, so small groups stay at `no conclusion` for a long time. That is the rule working, not a fault: a conclusion drawn from three pairs is a guess.
- **A challenger must be a model the project already reaches.** It has to differ from the champion's coder and pass every check a run's own model passes — the run's allow-list, a route that claims it and names the repository, a price, an API-key credential and a provider gateway in enforce mode. A Bitbucket repository, and a GitHub repository whose App key the credentials service holds, are never sampled at all. A launch that is skipped says so in one line with the reason.
- **No run starts a judge by itself.** The judge run is launched by hand with `fugaro run --recipe ab-judge`, one per repository at a time, and it is refused while one has not finished and when the project publishes no `judge_model`; a project that wants it regularly schedules the launch itself.
- **A craft's model half is written, validated and shown, and it is not yet what a run runs.** `fugaro craft ls` prints the model each craft resolves to, while a run still takes its models from `agent.models` and `agent.levels`; a craft's access is the half a run resolves today.
- **A pool's members are served by the two halves of a run, and one pool cannot cross them.** An OpenRouter or Vertex member is served by the run's own gateway and a Claude OAuth or Anthropic-key member by the credentials service, so a pool that mixes the two can fail over only at a stage boundary.
- **A credential whose type authenticates with a key is not declarable by a command yet.** `fugaro accounts add --type` serves `claude-oauth`; an OpenRouter or Anthropic-key credential is written in the config's own `credentials:` block.
- **A run is served from the published node's own craft blocks.** No command of this release writes the crafts, credentials and pools from your config into the published policy, so what a pool changes today is `fugaro craft ls` and the launch, rather than which member serves a call.
- **No live check has been run on credentials, pools and crafts.** A pool's failover on a real installation, the spread of round-robin over several runs and the convergence of `fugaro update` on an installation at the previous version are owner-run checks that have not been run.
- **Where the front door is on, its read of the orchestrator is a read of the whole database.** Realtime Database IAM has no path-level scope, so the one role the state group reads through reaches every top-level node the rules keep — `pairing/`, `mailbox/`, `config/`, `spend/`, `runs/` and the rest — and a compromised front door reads all of it. The owner chose that over serving no orchestrator state through MCP; what it exposes node by node is unread, **Check 305** in `docs/gcp-live-checklist.md` is written and has not been run, and the front door itself is off on every installation until you turn it on.
