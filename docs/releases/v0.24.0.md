- A repository no longer needs its own `image:` block: the project's catalog decides the image its jobs run, and a repository that still carries the old key is told once that the key is ignored rather than being refused.
- A skill builds the project's images for you: it surveys the repositories, proposes at most four that cover them, and generates each Dockerfile from what the code actually needs.
- Every proposed image is built by the cloud, never on your machine, and the build is checked against the runtime contract before a run can use it.
- A run on a catalog image carries the repository inside the image, so the job starts on the code it was asked to work on instead of cloning it first.
- A catalog rerun proposes only what changed, so a second pass over a project that is already covered is a short list rather than the same five images again.

### For operators

1. In each installation, run `fugaro update`. It is the whole upgrade, and it asks for the things only you can answer: the review of the steps it will apply, and the rebuild of the base-derived images, each behind its own confirmation.
2. Point the `fugaro:images` skill at a repository you want on the catalog. The skill proposes, you confirm, and the images it proposes are built by the cloud.

### Known limits

- The skill's behaviour is pinned by two owner-run checks, **Check 500** and **Check 501**, and neither has been run: they are written as scripts and their rows in the live checklist still read NOT RUN. What the skill does end to end on a project that is not the author's, and what an installation really starts a run on after this release's upgrade, are unverified until you run them.
- The cap of four images is the skill's own rule. Nothing in the CLI enforces it, so a project whose catalog grows past four keeps working and is never told.
