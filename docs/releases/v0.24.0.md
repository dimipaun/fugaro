- **A project can sample its runs and give each one a shadow challenger.** With `rate` in the project layer's `ab:` block, a share of eligible runs is launched beside a second run on another coder model — the same task, at the same commit, from the same recipe, mode and tier — and `fugaro ab` reports what the two arms did. A/B is off until the layer turns it on, and no model is switched for you: this is a report.
- **A challenger run is a shadow.** It pushes nothing, opens no pull request, comments on nothing and holds no git write credential, so a sampled task still leaves exactly one branch and one pull request, and the run the developer follows up is always the champion. Both arms store the patch they produced, and both carry the pair and a shared batch label, so `fugaro runs ls --batch ab-pair-<id>` shows the two.
- **`fugaro ab` scores the pairs from the run records alone.** One row per rigor mode, tier and model pair, with the challenger's wins, losses and ties, the interval around its win share, the median pair cost ratio, each arm's halt count, the champion's follow-ups, and a recommendation at the mode's exchange rate — better within the rate, cheaper and not worse, or keep the champion. No model call and no judgement is involved, so the same records always give the same table, and a row with fewer than 20 decisive pairs says it has no conclusion rather than approximating one.
- **Pairs are judged blind, by a run of their own.** `judge_model` in the same block names the model the `ab-judge` recipe calls, one judge run per repository at a time, over each pair's two patches shown as A and B with no run, branch, model or commit in them. The order is swapped on the second pass, and only an arm both passes agree on is decided — anything else is a tie.

### For operators

1. **Per installation, and only if you want A/B at all.** Nothing is required: a project that publishes no `ab:` block samples nothing, and every repository of it keeps running as it does today. To turn it on, add the `ab:` block (`rate`, `challengers`, `max_pairs_per_day`, `judge_model` and any `exchange_rate` a mode should have) to the project's layer file and publish it with `fugaro config publish` at your own terminal; `fugaro update` publishes the same file, so an installation that is already being updated needs no second command. Nothing samples a launch until the layer is published.

### Known limits

- **Nothing here has been proven live.** Checks 210, 211 and 212 of the live checklist — a sampled run leaving one branch and one pull request, what the judge's stored input shows, and a provider challenger end to end — are written and NOT RUN, so the unit and emulator tests are the only evidence that the sampler, the pair launch and the judge behave as written.
- **A row advises nothing until it has 20 decisive pairs.** A project that samples a tenth of its runs reaches that in weeks, not days, and each row is counted per rigor mode and tier, so small groups stay at `no conclusion` for a long time. That is the rule working, not a fault: a conclusion drawn from three pairs is a guess.
- **A challenger must be a model the project already reaches.** It has to differ from the champion's coder and pass every check a run's own model passes — the run's allow-list, a route that claims it and names the repository, a price, an API-key credential and a provider gateway in enforce mode. A Bitbucket repository, and a GitHub repository whose App key the credentials service holds, are never sampled at all. A launch that is skipped says so in one line with the reason.
- **No run starts a judge by itself.** The judge run is launched by hand with `fugaro run --recipe ab-judge`, one per repository at a time, and it is refused while one has not finished and when the project publishes no `judge_model`; a project that wants it regularly schedules the launch itself.
