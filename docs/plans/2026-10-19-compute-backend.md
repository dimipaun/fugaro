## Global Constraints

These hold for every task below, and the plan's own review checks them:

1. **`backend: cloud-batch` stays refused until Task 10's commit, and no task before it lifts the refusal.** The refusal is `internal/localcfg/localcfg.go`'s `backend` validation and it is pinned by `TestCloudBatchIsRefused`; **Task 10 is the only task that may change it**, and it may only change it together with the `doctor` gate the design's §4.4 requires, because a Batch run without log routing leaves its output in `_Default` where every project viewer reads it (§1.5) and a Batch run without a reaper leaks VMs (§3.4). **A task that finds it needs the refusal lifted early says so rather than lifting it.**
2. **No task adds a second way to select a backend.** The registry is `internal/backend/registry.go`'s `Open` over the opener map `internal/cli/cloud.go`'s `openCloudFor` builds, and the name comes from `localcfg.Config.Backend()`; a task that adds a name checks it against `internal/backend/backend.go`'s constants rather than inventing a string.

## Review Focus

What a reviewer of each phase should attack, in the design's own terms:

- **Phase A, the wiring (Task 8)**: **does the Batch backend's configuration come from the installation, or from a default nobody chose?** The socket gid, the machine type, the boot image, the network and the subnetwork, the run account and the secrets map are all per-installation facts the Terraform root already produces (`internal/infra/compute.go`'s `ComputeOutputs`), and a `batch.Options` built from constants would launch a job on a VM that cannot open the socket. **Then**: do the three seam call sites actually use the selected backend's codec, or do they still reach for Cloud Run's — a `Launch` record that says `cloud-run` for a Batch run is a run `fugaro logs`, `fugaro cancel` and the reaper all misread. And: does the opener fail **closed** for a name with no opener (`backend.Open`'s contract) rather than falling back to Cloud Run?
- **Phase A, the provisioning (Task 9)**: **the permission question first, because it is the one that has already failed once.** The role's list is a security surface *and* a correctness one: a permission GCP does not have makes the apply impossible, and a permission wider than the code's use makes a second launcher. Ask what each remaining permission is for, whether the code path that needs it can be reached by anything but the scheduled sweeper, and whether dropping `cancel` **widens** anything (it does not: `jobs.delete` is strictly the more destructive of the two, and the code already holds it). **Then**: the gid. A recorded gid that is not re-read on a rebuild is a stale gid, and a stale gid is a Docker run whose socket mount comes up unable to open the socket — the failure 57b-1 exists to catch. And: does flipping `batchProvisionShipped` un-refuse the flag for installations that have not applied Task 9's module change? (It does — the flag is a build constant, not a per-installation fact — which is why Task 9's commit order matters and the release note says so.)
- **Phase B, the reaper's invocation (Task 11)**: **this is the task that turns a tested library into a process with `compute.instances.delete` on a schedule.** The three questions: **what does it refuse to delete** (a job whose labels it cannot read, a VM whose `fugaro_run` label it cannot match, anything on a network or project it was not pointed at), **what happens when it is wrong** (it deletes a VM of a run that was still starting — the queue-deadline slack is the whole defence, and a reviewer should compute it), and **what stops it running twice at once** (Cloud Run jobs do not, by default). **And the honest limit the design's §3.7 states**: IAM cannot scope these permissions by label, so the account can reach every job and every VM in the project — which is why it is a separate account, why it holds nothing that can create, and why 57b-10 and 57b-11 exist.
- **Phase B, the enable (Task 10)**: **is the gate the gate?** `doctor` is what refuses an installation until the provisioning, IAM, logs, cost and reaper checks pass, so the question is whether each of those checks can answer "yes" for an installation where the thing is absent — the IAM propagation delay 57a measured is the live hazard (a binding that is not readable yet must say "propagating", not send the operator to re-provision), and a check that reads a fresh account's bindings must not read the propagation gap as a missing grant. **And the second attack, which is the one this task can get wrong by omission**: does the enable also enable something it was not asked to? The Batch backend's account is not per-repository, so `docs/design/artifact-runs.md` §8.5 and D11 keep an artifact-producing run on Cloud Run until a per-run boundary exists — **this task must leave that refusal standing**, and a reviewer should check that the artifact refusal survives the commit rather than reading it as a leftover of the refusal this task removed (Global Constraint 13).
- **Phase C, the check (Task 12)**: **does the check measure the thing the plan claims?** 57b's steps are written to fail loudly: a run that never started, a log line that never arrived, a cost that does not match the bill, a reaper that swept nothing. A step whose assertion is "the command exited 0" measures nothing — the register's own convention is a FACT line per step and a closing assertion whose every line reads `0`.
- **Phase C, the seal (Task 14)**: **what is the carrier's audience, and is that audience already trusted?** The refusal exists because a Batch job's `variables` are the job's *definition*, readable by every launcher the IAM Condition admits and by the reaper. A reviewer should ask for the audience of any proposed carrier in one sentence before accepting it, and should treat "it is only in the VM" as false unless the design's rejected C2 is being reopened.
- **Every phase**: the refusal stays until Task 10; no task handles a secret value; no task's command needs a live cloud; `belong` is untouched; and nothing under `.github/workflows/` is edited.

## Phase A — The backend an installation can select

### Task 8: The backend the installation selects — the opener, its configuration, and the seam's call sites — SECURITY-SENSITIVE, independent opus review

**Files:** `internal/cli/cloud.go`, `internal/cli/run.go`, `internal/cli/validate.go`, `internal/cli/doctor.go`, `internal/cli/backends.go`, `internal/cli/backends_test.go`, `internal/localcfg/localcfg.go`, `internal/localcfg/localcfg_test.go`, `internal/cli/root.go`, `plugin/skills/setup/SKILL.md`; and the tests of every file above. **And `internal/cli/docs_compute_backend_test.go`, this plan's own pin test, because two of its assertions are about exactly what this task changes**: its comment-marker table counts the three `TODO(compute-backend Task 8)` markers this task removes at each call site, so the counts go to zero and the assertion becomes the markers' absence; and its `internal/cli/run.go` symbol entry asserts `Backend: backend.CloudRun`, which is the constant step 6 replaces. **A task that leaves its own pin red is a task whose commit does not stand.**

**Steps:**

1. **The opener.** `openCloudFor` (`internal/cli/cloud.go`) builds a one-entry opener map — `map[string]backend.Opener{backend.CloudRun: …}` — and passes it to `backend.Open` with `lc.Backend()`. It gains `backend.CloudBatch`, whose opener constructs `batch.New(ctx, batch.Options{…})` from the local config. **`backend.Open`'s contract is kept**: an unset name resolves to Cloud Run (`localcfg.Config.Backend()`), and a name with no opener fails closed rather than falling back.
2. **The configuration.** `internal/localcfg` gains the section the Batch backend reads, and its validation. Every field is an installation fact the Terraform root already produces and `internal/infra/compute.go`'s `ComputeOutputs` already decodes: **the recorded socket gid** (`batch.Docker.SocketGID` — `Options.Docker` has no producer today, so this is the field that makes a Docker run possible at all), the machine type, the preloaded boot image, the network and subnetwork (57a found Batch refuses `noExternalIpAddress: true` without both named explicitly), the run account, and the secrets map. **A Docker workflow on an installation whose gid is unrecorded is refused** — `internal/backend/batch/batch.go`'s `checkDocker` already does this, and this task is what makes the refusal reachable rather than theoretical.
3. **`fugaro backends ls`** (design §4.4): a new command that lists the names `internal/backend/backend.go` defines and which one the project uses. It reads `localcfg` and `internal/backend`, and it calls no cloud API.
4. **`fugaro validate`** (design §4.4): the offline checks, each a refusal with a message naming what to do — the backend name is known; `docker: true` requires a Docker-capable backend, so `docker: true` with `backend: cloud-run` is an error naming `cloud-batch`; the resources fit the VM backend (`internal/backend/batch`'s own resource check, not Cloud Run's `internal/backend/gcp/limits.go`); the workflow's timeout fits Batch's `maxRunDuration` and sits well inside the 14-day `RUNNING` limit; and **Spot combined with a workflow whose outcome rules require a finalize/PR is a warning, not an error** (C5, and the design's §4.5 item 5), because the brief's preemption result is exactly that case. **And the artifact boundary (Global Constraint 13): `artifacts:` with `backend: cloud-batch` is an error**, naming `docs/design/artifact-runs.md` §8.5 and D11 and saying what it waits for — a per-run prefix condition or a per-run account.
