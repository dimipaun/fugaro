## 2. What was done

**Nothing was built, and no code was touched.** The plan's own precedent settles what to do with an approval that is not in the record: when Task 4.1's review found it being built while the OWNER APPROVAL GATE still named it unapproved, the fix was not to proceed — it was to record the go in the plan first (`6c5ad4e`). A project label is a write to the privilege boundary the whole feature rests on (`resourcemanager.projects.update`, design finding 14), so it is not a change to make while the authority documents say the opposite of the instruction.

This file is the deliverable: the disagreement above, and below it exactly what is missing to build Task 3.0 safely and a recommendation for each point. If the owner confirms the 2026-10-17 ruling, this addendum is the whole of the work and Task 3.0 stays struck. If the label is wanted, the points below are the answers a build needs.

**It is a separate file rather than an edit to the plan** for the plan's own reason: `docs/plans/2026-10-16-managed-projects.md` is written by **Task 5.4 alone** (`:179`), the plan is single-writer so that the parallel tasks cannot collide in it, and this run is not that pass. ## 3. What is missing, and what to do about each

1. **The reversal, recorded.** Nothing else on this list can be built safely first. **Recommendation:** if the label is wanted, the owner records it as a dated ruling in the same shape §5.1 uses — a fourth item there, or a §5.2 — and the plan's Task 3.0 heading, its C3 row (`:915`), the parallel-execution table (`:219`) and the approval-gate line (`:938`) are rewritten to it. The plan file is **Task 5.4's alone** (`:179`, "Task 5.4 only, if an answer changes a task's shape"), so that pass is Task 5.4's or a small docs task of its own, and no code task may edit the plan file to make room for itself. If the 2026-10-17 ruling stands, nothing is needed and this addendum is the record.

2. **The label's name, which is permanent.** Task 3.0's Steps say `fugaro_managed=true` (`:551`); the owner's spec says `fugaro-managed=true` (`docs/design/managed-projects-spec.md:30`); and `internal/backend/gcp/names.go:56-57` already owns `LabelManaged = "fugaro"` / `ManagedValue = "managed"` for *resources* — a different key on a different kind of object, and not this. A GCP project label key lives for the life of the project, is visible to everyone who can read it, and `fugaro_managed` and `fugaro-managed` are two different keys. **Recommendation:** `fugaro_managed` with the value `"true"` — the plan's own text, which is the more recent of the two — declared as a constant beside the marker's in `internal/infra/managed`, and the spec's `fugaro-managed` recorded as the name not taken.

3. **Where it is written.** The Files list names `internal/cli/init_project.go` (`:162`, "Task 3.0: the label write"), but the Steps name "the same operator-run path that writes the marker object (Task 0.1)" — which is `internal/cli/init.go`'s `markCreated` (`:709`), and it has to be: the project stage runs first and the runs bucket does not exist until the installation stage has applied, which is the whole reason `markCreated` sits where it does (`:670-680`). A creation-time write is a third thing again: `internal/infra/projectcreate.go`'s `CreateProject` builds only `ProjectId`, `DisplayName` and `Parent` (design finding 14) and is not in the Files list at all. **Recommendation:** the marker object's writer and nothing else — one operator-run step writes both marks, so the two cannot disagree about whether the run tried, and a failure is reported once, as `markCreated`'s warning rather than as a failed `init` (`:689-696`). `init_project.go`'s line in the Files list is then wrong and should be corrected with the rest of point 1's pass.

4. **What "agree" means on every answer, and which direction fails closed.** The plan gives the two disagreement cases — either mark alone refuses — and not the rest. **Recommendation:** state it as one rule, **the label can only narrow, never widen**: managed requires the object's read to answer managed *and* the project's label to be present and exactly `"true"`; an absent label, a label with another value, and a project the read cannot fetch at all are all **not managed**, each with a reason a person can act on, in `Status.Detail`'s one-line shape; and a test asserts the label alone never makes a project managed. **This costs no new privilege and no new call**, which is worth writing down because it is the first thing a reviewer will check: `readFact` already fetches the project object for its number check — `gcpProjectNumber`, `internal/infra/managed/read.go:392-398`, is `c.Projects.Get(gcpProject)` — and throws away the `Labels` that answer carries. The label is one field off an object the read already holds, read by the identity the read already uses, under a permission it already needs. What is genuinely new is only that a second condition can now turn managed mode off.

5. **What happens to a project that is already marked.** Every managed project in existence today has the object and no label, because nothing writes one. Adding the agreement condition turns all of them **not managed**: `fugaro managed apply` and `fugaro restore` then refuse, and the coding-agent refusal comes back. That is fail-closed and therefore safe, but it is a functional regression the plan does not mention, and it is not hypothetical — the sandbox installation's managed project is one. **Recommendation:** say so in the task, and give the owner a one-line, owner-run backfill recorded in `docs/gcp-setup.md` beside the managed creation. The refusal may name it: it *tightens* the mark rather than getting around it, which is the line Task 3.2 draws ("no refusal ever names a way around the marker", `:601`). A test asserts that a project whose object is there and whose label is absent is refused, with that reason.

6. **The job-account test, and the case where it cannot be written.** Task 3.0's third test asserts the run's job account holds no permission that can set the label, and the plan's Open item 2 (`:927`) says that if the fixture cannot be written, **the label is refused instead**. It can be written: `internal/infra/managed/marker_test.go` already scans the installation module's grants for exactly this kind of property — the refused-grant mutations (`TestTheModuleScanCatchesTheMutations`, `:514`, and `projectGrantToJob`, `:922`) and the fenced-write scan above them — so this is an extension of an existing fixture, not a new one. **Recommendation:** extend that scan with `resourcemanager.projects.update` (and `resourcemanager.projects.setIamPolicy`) as permissions no run account may hold, asserted from the same fixture, and record in the task that Open item 2's conditional is answered by it rather than left standing.

7. **Where the label lands relative to what has already shipped.** Task 3.1 has merged (`6aa3ecc`, #527), so the plan's edge "3.1 ← 3.0 if a label is wanted" (`:208`) is already violated by merge order: the label would arrive as a **narrowing change to a shipped apply path**, not before it. **Recommendation:** state that plainly in the task and let its review read it that way. The label can only remove managed mode, so the change is fail-closed, but a new condition on a shipped read is still a new way for an apply to refuse and a new sentence a person reads, and the task's own review is where that is weighed.

8. **The documents that follow.** `docs/gcp-setup.md` (the managed creation, and the backfill of point 5), `plugin/skills/setup/SKILL.md` (Global Constraint 13), the design's C3 discussion and §5.1, and the plan's Task 3.0 heading, C3 row, parallel-execution table and approval-gate line. **Recommendation:** Task 5.4's pass for the plan file, which is its single writer, and a small docs task of its own for the other two, so no code task has to reach into documents the plan gives to someone else.
