# The OAuth token for the senior-reviewer stage: implementation plan

> **STATUS: HELD until phase 5 of [docs/design/project-centric.md](../design/project-centric.md); to be rebased onto the person-owned OAuth pool; not scheduled.**
>
> The owner decided this on 2026-10-14 (**D9**, `docs/design/project-centric.md:241`, merged to `main` as PR #364): "#363 OAuth reviewer stage — Multiplies per-repository variant jobs; widens token blast radius under sharing — **Hold** until phase 5". Phase 5 (§7, "OAuth pool") replaces the per-repository `claude-oauth-token` secrets, the `secrets set claude-oauth-token-* --repo` path and the init prompts with **person-owned** secrets behind a project-level reference, and replaces the per-repository variant jobs with **one project job per (profile, account)**. **Goal:** let one workflow run its **coder** through the budget gateway on a cheap provider model (`agent.auth: api-key`) while its **senior reviewer** runs Claude Code directly on a Claude subscription OAuth token, behind an explicit per-repository opt-in (`agent.stage_auth: {reviewer: oauth}`), so the strongest available reviewer costs no dollars per run and is bounded only by `agent.max_budget_usd`. ## What survives phase 5, and what is replaced

**Everything that is about a *run's* two credentials survives unchanged** — it never reads a secret name, a job name or a repository path:

- **P1 to P6** (the `stage_auth` key and its `reviewer: oauth` value; `agent.auth` staying the run's auth; the one permitted mix in `CheckProviderAuth`; the Claude-and-unclaimed reviewer model; the role-swap refusal with review mode permitted; the `followup.allow_public` refusal), **P9** (the version-skew constant), **P10 to P15** (the second `agent.EnvSpec`, `stageDirect`, the per-stage notional record and its display, the routing-key check and its widened gate, `max_budget_usd`) and **P17** (the temporary refusal that keeps the key inert).
- **Tasks 1, 2, 3, 4, 5 and 9** as written, and **Task 7**'s runner/record/display half.
- **`agent.oauth_token` itself.** Phase 5 keeps it: "the per-repository copies, `secrets set claude-oauth-token-* --repo` and the init prompts go away with the per-repository path; **`agent.oauth_token` stays as a preference**" (§7). So P7's key keeps its meaning even though the account it names is resolved differently, and P7's rule that the **default account needs no `allow_data_to`** survives as the failover list's first entry.

**The four things phase 5 replaces, and what each becomes:**

| This plan, today | After phase 5 |
|---|---|
| **Task 6 / P8:** the per-account **workflow variant job** per (repository, workflow, account) and its `SecretMounts` entry for `claude-oauth-token-<name>` (`internal/infra/spec.go`, `internal/backend/gcp/names.go`'s `WorkflowVariant`) | One **project job per (profile, account)**, mounting a person-owned secret by reference; the runner binds the job the way the clone workflows already do (`slug == task.Slug(...)`, design §7 "Mounting"). The per-repository variant mechanism goes away with the path it belongs to, so Task 6 is **deleted rather than rewritten**, and its remaining obligations (the mount, the upgrade note, the SECURITY.md gap line) move into phase 5's own plan. |
| **Task 6:** the `fugaro init --repo` re-run and the upgrade note, which create the variant jobs and the mount | `init --repo` is retired for clone repositories in phase 4. The account's job comes from an installation apply or an API call (the `image refresh` precedent), and granting a job service account `secretAccessor` on a **person's** secret needs `setIamPolicy`, so it is an **operator step** performed when the reference is accepted (§7). |
| **P7:** a named account must be listed in that account's `allow_data_to` for the repository | The reference record's own `allowed profiles/repositories` field, accepted by an operator, plus `fugaro run`'s failover order (the launcher's own accounts first, then shared ones — §7). The **default needs nothing** half survives as written. |
| **P16:** `agent.stage_auth` is `InRepo` scope only | Person-owned tokens are project-level, so the token is no longer repository-scoped and the scope question changes shape. The **key** stays repository config (it is a per-workflow preference), so the scope table row is rewritten, not removed. |

**Check 47** keeps steps 1, 3, 4, 5, 7 and 8 as written and rewrites **step 2** (store the person's token once and share it by reference, instead of storing it per repository) and **step 6** (the launch gate becomes the reference's allowed-list and the failover order, instead of `--token <name>` against `allow_data_to`). Its section carries the same banner as this plan.

**If the owner lifts the hold early**, the table above is the list to rewrite and nothing else in this plan touches the per-repository path. **If phase 5 lands first**, this plan is rebased onto it, Task 6 is deleted, and P7, P8 and P16 are restated against person-owned references.

## Decisions (veto any before execution starts)

- **P1. `agent.stage_auth` is a pointer to a struct with exactly one field, `reviewer`, whose only accepted value is `oauth`.** `StageAuth *StageAuth` (`yaml:"stage_auth,omitempty"`) holding `Reviewer string` (`yaml:"reviewer,omitempty"`), with `func (a Agent) ReviewerOnOAuth() bool`. A pointer, not a value, because the config is decoded with `dec.KnownFields(true)` (`internal/config/config.go:485`): the pointer is the only way to tell `stage_auth: {}` (present, sets nothing — refused, because a silent no-op that looks like an opt-in is the worst of both) from an absent key. The struct is what makes `stage_auth: {coder: oauth}` an unknown-field **parse** error rather than a validation rule, so the "only `reviewer` in this slice" limit is enforced by the decoder, before any check runs. *Veto alternative:* `agent.reviewer_auth: oauth` (a scalar) — rejected: the design names `stage_auth`, and a scalar key would have to be renamed if it ever generalizes (design §8 open question 2 recommends it never does, which is why `coder` is refused rather than ignored).
- **P2. `agent.auth` stays the run's auth; `stage_auth` is an override for exactly one stage, never a second auth mode.** Everything that reads `cfg.Agent.Auth` today — `gatewayOn()` (`internal/runner/gateway.go:46`), the budget registry entry (`Auth: r.cfg.Agent.Auth`, `internal/runner/budget_session.go:265`), `runstore.ModelBasis` (`internal/runstore/cost.go:41`), `watch`'s `Notional: e.Auth == "oauth"` (`internal/watch/build.go:393`) — keeps reading it, and the sites that must become per-stage change **at that site** (P11), not by redefining the key. A `stage_auth` run is still an api-key run: api-key job, api-key budget identity, gateway for every stage but one. *Veto alternative:* make `agent.auth` a list or a map — rejected: it changes every existing consumer and every existing `fugaro.yaml` for one stage of one role.
- **P3. The permitted mix is exactly `agent.auth: api-key` plus `stage_auth.reviewer: oauth`; every other combination is refused, and the rule lives in `config.CheckProviderAuth`.** That function (`internal/config/providers.go:390`) is already the auth/model consistency rule and is already called from both surfaces that matter: `fugaro validate` (`internal/cli/validate.go:203`) and the runner's bootstrap (`internal/runner/gateway.go:392`, `checkProviderModels`), each **after** `runner.ApplyRoles` has rewritten the role models (`internal/cli/validate_recipes.go:136` `withRecipeRoles`; `internal/runner/recipe.go:115`), so the checks see the models the run really uses. The refusals, each naming the key and the reason: `stage_auth` with `auth: oauth` ("the whole run already uses the subscription token; `stage_auth` would say nothing"), with `auth: vertex` (same shape), `stage_auth.reviewer` holding anything but `oauth`, and `stage_auth` present with no `reviewer`. **The `stage_auth` rules go above `CheckProviderAuth`'s early `if a.Auth == "api-key" { return nil }`, or they never run for the one auth they are written for.** *Veto alternative:* a new `CheckStageAuth` called from the same two places — rejected as a second place to keep in step with `CheckProviderAuth` for no gain; the one rule that genuinely needs config `CheckProviderAuth` does not receive is P6's, and that gets its own small function for that reason.
- **P4. The reviewer's model must be a Claude model that Anthropic serves directly, and no provider route may claim it.** On the direct stage the model ID goes to Anthropic, so it must match `config.ClaudePatterns` (`claude-*` or `anthropic/*`, `internal/config/providers.go:333`) **and** `config.ProviderFor(providers, model)` must not find a route for it. Both clauses are needed and neither is redundant: a DeepSeek reviewer would send a DeepSeek ID to Anthropic, and a provider-claimed `anthropic/claude-sonnet-5-5` (the §4 opt-in's spelling) is OpenRouter's ID, not Anthropic's — a Path C senior, not a Path B one. The refusal names `agent.models.reviewer`, the model and `agent.stage_auth`. **The empty case is defined, not left to `ModelFor`:** `Agent.ModelFor(RoleReviewer)` falls back to `agent.model` when `agent.models.reviewer` is empty (`internal/config/config.go:216-225`), so a `stage_auth` workflow that sets no reviewer model is refused on the model it would really use, with a message that says the reviewer's model is unset, that it falls back to `agent.model`, and that a Claude model must be named in `agent.models.reviewer` (pinned by `TestStageAuthReviewerModelUnsetRefused`). **This is also what catches `roles: {reviewer: coder}` for free**: `ApplyRoles` copies the coder's model onto `Models.Reviewer` before any check runs, so a DeepSeek coder becomes the reviewer's model and the Claude clause refuses it — pinned by a test that asserts the refusal for a `reviewer: coder` recipe, not merely for an explicit DeepSeek `agent.models.reviewer`.
- **P5. A recipe that swaps roles is refused with `stage_auth`; a review-mode recipe is permitted, and review mode's existing trusted-author gate is the mitigation for it. The runner is the authority, `validate` is best-effort.** A role swap makes one role's model run in the other's stage, so the slice's contract ("exactly the `review` stage runs direct, with exactly `agent.models.reviewer`") becomes a coincidence of the recipe: `reviewer: coder` puts a non-Claude model on the direct stage (P4 catches it, but the message should name the recipe), and `coder: reviewer` runs the reviewer's Claude model on the **gateway** stage while the reviewer runs it direct — the same model on two credentials, which is not a mix this slice defines. The check is `runner.StageAuthRoleProblems(a config.Agent, rcp *recipe.Recipe) []config.Problem` (new, in `internal/runner/recipe.go`, next to `ApplyRoles`), called from the runner's bootstrap and from `internal/cli/validate_recipes.go`. A **project** recipe is not readable from a checkout, so `validate` cannot always decide: `annotateProjectRecipe` (`internal/cli/validate_recipes.go:150`) gains the same note it already adds for the role-mapped model keys, and the runner — which reads the recipe at the task's ref and always has it — refuses at bootstrap. **Review mode (`recipe.Mode == ModeReview`) is deliberately NOT refused.** Review mode is already trusted-author-only: `checkReviewAuthor` (`internal/runner/reviewmode.go:125-152`) refuses any pull request whose live `author_association` is not OWNER, MEMBER or COLLABORATOR, refuses a fork unless the fork's owner is that same trusted author, and fails closed on Bitbucket (every fork refused, and a same-repository pull request needs no author check because pushing a branch there already needs write access); the owner ruled this on 2026-10-13. Design §6 mitigation 1 lists that rule as one of the mitigations the opt-in **relies on** ("together with review mode's trusted-author rule"), not as a case to refuse, and refusing review mode would remove the senior reviewer's most useful configuration. A fork's head is not "code the repository did not write" in review mode: a fork is only ever reviewed when its owner is the trusted author GitHub reports right now, so refusing review mode would refuse the case the rule already covers. What this plan owes the design instead is a statement of the reliance (Review Focus 3) and a test that the reliance is real (`TestReviewModeStillGatedByTrustedAuthor`, the existing reviewmode tests, plus `TestStageAuthPermitsReviewMode`). If the design wants review mode refused after all, that is a design change and this plan stops for it. *Veto alternative:* refuse `stage_auth` whenever `agent.recipe` names anything at all — rejected: it would refuse the ordinary `standard` recipe, which is the one the opt-in is for.
- **P6. `followup.allow_public: true` is refused with `stage_auth`.** `AllowPublic` lets a follow-up run on a public repository (`internal/config/config.go:80-82`, read at `internal/runner/followup.go:195`), where a commenter who can push branches can steer a run whose job holds the subscription token. It does not gate the **first** run on a public repository (design §6 mitigation 1 says so plainly), so this refusal is only one of the two gates the config can express; the other is `claude_accounts.<name>.allow_data_to`, which is owner-controlled and checked at launch (P7). New `config.CheckStageAuth(a Agent, f Followup) []Problem`, called from `internal/cli/validate.go` and from the runner's `checkProviderModels` (which can read `r.cfg.Followup`), so both surfaces refuse it. The message says what to do: remove `stage_auth`, or remove `followup.allow_public` and run on a private repository. *Veto alternative:* warn instead of refuse — rejected: the whole point of an opt-in for a residual risk this size is that the dangerous combinations are hard refusals, and a warning on a public repository is a warning nobody reads.
- **P7. `agent.oauth_token` is optional and names the reviewer's account when set; the launch gate is relaxed by exactly one clause.** **The account rule, stated once and used everywhere:** with `stage_auth` and no `agent.oauth_token`, the reviewer runs on the **default** account — the `claude-oauth-token` secret, which `config.AllowedClaudeAccounts` always includes (`internal/config/claude_accounts.go:107-115`) and which no `allow_data_to` gates, because it is the owner's own unnamed token and the one every plain oauth workflow already uses. With `agent.oauth_token: <name>`, the reviewer runs on that named account, and the name must be in `AllowedClaudeAccounts(claudeAccounts, repo)` — that is, the account's `allow_data_to` must list the repository. So a `stage_auth` workflow needs no named account at all, and a named one it names must be allow-listed for it; nothing anywhere may say "a named, allow-listed account is required". `claudeAccountAllowed` (`internal/cli/run.go:874`) today refuses a named account outright when `co.Agent.Auth != "oauth"`, because no secret would ever be mounted for it. With `stage_auth` a secret **is** mounted (P8), so the clause becomes `co.Agent.Auth != "oauth" && !co.Agent.ReviewerOnOAuth()` and nothing else changes: the allow-list membership check, the `--token` resolution order (`claudeAccountFor`, `:850`), the follow-up inheritance rule and the job-variant-must-exist backstop (`internal/backend/gcp/run.go:146`'s "job %s does not exist; create it with fugaro init --repo") all stay as they are. `fugaro doctor`'s `oauth-token-allowed` check (`internal/cli/doctor.go:991-1016`) reports the account for a `stage_auth` workflow too, and its `claude-accounts-stored` sibling (`:920`) expects the secret to exist for it — the default secret when no account is named. *Veto alternative:* a separate `agent.stage_oauth_token` key — rejected: the account is a property of the workflow's identity, not of which stage uses it, and two keys naming accounts could disagree.
- **P8. Infra mounts the token and builds the account variants for an api-key workflow that sets `stage_auth`, through one shared predicate.** Three sites gate on `cfg.Agent.Auth == "oauth"` today and all three must ask the same question: `infra.SecretMounts`'s switch (`internal/infra/spec.go:585-590`, which mounts `config.ClaudeAccountSecret(token)`), the per-account variant loop in `BuildRepoSpec` (`:822-836`, which decides the token set `{"default"} ∪ config.AllowedClaudeAccounts(...)`), and `fugaro init --repo`'s secrets stage (`internal/cli/initsecrets.go:315`, which prompts for every allowed account's own token). One new predicate — `config.Agent.UsesClaudeToken() bool` = `Auth == "oauth" || ReviewerOnOAuth()` — is what all three call, so a fourth caller cannot get it subtly different, and the variant job names stay `gcp.WorkflowVariant(name, token)` (`internal/backend/gcp/names.go:296`) unchanged. The default variant is the workflow's own job, so a `stage_auth` workflow with no `agent.oauth_token` needs no new job at all; a named account gets its variant exactly as an oauth workflow's does. *Veto alternative:* let `init --repo` mount the token on the default job only and refuse `--token NAME` for a `stage_auth` workflow — rejected: the whole reason named accounts exist is that the owner's subscription is not the repository's, and a `stage_auth` reviewer is exactly the case where an owner wants to choose which account pays.
- **P9. A new key in a strictly-decoded config is a version-skew break, so `fugaro init --repo` refuses `stage_auth` against a base image that predates the release reading it, and the upgrade note is extended.** `config.Parse` decodes with `dec.KnownFields(true)` (`internal/config/config.go:485`), so a base image older than the release that knows `stage_auth` fails at bootstrap with an unknown-field error naming a key the owner did type — a repository that merges `stage_auth` would start failing every run until its image is rebuilt. The mitigation is the `cloneSince`/`imagePredates` shape (`internal/cli/recipes_skew.go:44`, `internal/cli/init_fugaroyaml.go:133`): a `stageAuthSince` constant, unshipped at first, with a release-checklist line, refusing `init --repo` with a message naming the release. **Separately, the existing deployed-job note does not cover this change and must be extended:** `jobConfigCopyNote`'s diff loop (`internal/cli/upgrade_cloud.go:249-266`) walks each workflow's **default** job through `infra.Workflow` and compares `spec.Env` only, so it never sees a `SecretEnv` mount and never sees a variant job. The task's first step is to verify what `JobFullEnv` returns for a secret-backed env entry before writing the test; the note then reports, in names and never values, a workflow whose deployed job lacks a secret env name the spec now declares, and a workflow whose spec declares a variant job that does not exist. *Veto alternative:* change only the note's wording — rejected: the owner reading it would be told to re-run `init --repo` for a reason the tool cannot actually see, which is how a note stops being trusted.
- **P10. The reviewer stage gets its own `agent.EnvSpec`, built once at bootstrap, and every stage's start writes the managed settings file it needs.** `r.env` is built by one `agent.BuildEnv` call with the gateway (`internal/runner/runner.go:1151`); the direct stage needs the other branch of the same function (`auth: oauth`, `Gateway: nil`, which prepends `CLAUDE_CODE_OAUTH_TOKEN` and refuses a gateway, `internal/agent/env.go`'s `case "oauth"`). Building it at bootstrap — not at stage start — means a missing or too-short token is an `infra_error` before the first stage instead of a failure mid-run, and it is what makes the design's mitigation 3 ("fetching the token at stage start shortens the window but does not close it") explicitly **not** in this slice: the token is a mounted secret in the runner's environment for the whole job either way. **The managed settings file is written per stage and the write is authoritative, which replaces the design's "rewrite and restore" — the one design amendment in this plan, made explicit in Task 7.** The runner's `writeManagedSettings` (`internal/runner/agentenv.go:85-105` — which builds the variable map and calls the lower-level `agent.WriteManagedSettings` at `internal/agent/settings.go:44`) writes the gateway's variables plus the pins plus the web-tool denial, and returns without writing anything when there is no gateway. The rule becomes: at each stage's start, a **direct** stage writes the pins and `denyWeb: true` with **no** `agent.GatewayVars` (whether or not the gateway is on); every **other** stage writes the gateway's file when the gateway is on, and **removes** the file when it is not (`r.removeManagedSettings()`, which is a no-op for every existing run, since a budget-off run never writes one). Nothing is left to a stage-end `defer`, because a `defer` cannot be observed between two stages and, worse, a stage-end restore leaves the reviewer's file in place for a following stage whenever the gateway is off — a budget-off `stage_auth` run's coder stage would have started with the reviewer's model pinned. The observation point the test uses is the fake agent's run hook, once per stage. The reviewer's model set is **Claude-only**: `agent.PinVars(reviewerModel, "", maxOutput)` — no `ANTHROPIC_DEFAULT_HAIKU_MODEL` (the run's background model is the DeepSeek coder, an ID with no meaning on a direct stage) and no `agent.ProviderRouteVars()` (design §5). The pins for a direct stage are computed even when the gateway is off, because they are what make Claude Code run the configured model — that is the one place where a direct stage sets a variable a budget-off run does not set today, and it is the point of the opt-in. *Veto alternative:* remove the managed settings file for the direct stage instead of writing it — rejected: the web-tool denial and the model pin are exactly what the file is for, and removing it would also drop `CLAUDE_CODE_MAX_OUTPUT_TOKENS`.
- **P11. Every reader that asks "does this run have a gateway?" about a **stage** must ask "does this stage use the gateway?" instead.** One predicate, `func (r *run) stageDirect(name string) bool { return r.cfg.Agent.ReviewerOnOAuth() && config.StageRole(name) == config.RoleReviewer }`, threaded through the stage path. The sites that decide by the **run** rather than by the stage are, each with what it really reads today: `stagePins` (`internal/runner/agentenv.go:54-65`, which gates on `r.gatewayOn()` — true for a `stage_auth` run — and would add the DeepSeek background pin and the provider-route vars to the direct stage), `writeManagedSettings` (`internal/runner/runner.go:1600`), the `beginGatewayStage`/`watchHalt` block (`internal/runner/runner.go:1671`), `crossCheckCost` (`:1722`, which compares Claude Code's own figure against `r.lastStage`'s gateway figure and would WARN spuriously against the **previous** stage's), `r.rec.CostUSD = r.gwUsed.USD()` (`:1724`, which would overwrite the run's billed figure from the ledger and drop the direct stage's entirely), `stageTiming` (`internal/runner/cost.go:33-50`, `gateway := r.gw != nil`), and `reportNotional` (P13). The direct stage also clears `r.lastStage` so nothing stale is read. `r.gw != nil` and `r.gatewayOn()` are not interchangeable here: the first is true only once the gateway is actually running, the second says whether it will be — and for a stage_auth run both are true, which is why a stage-scoped predicate is needed rather than either of them. *Veto alternative:* give the direct stage its own tiny "gateway" object that reports zero — rejected: it would make the ledger look like it saw a stage it never saw, and `cost.model_by`'s `unattributed` accounting would absorb the difference.
- **P12. The reviewer stage's dollars are notional, recorded per stage and per run, and `cost.model_usd` keeps its sum invariant.** `runstore.StageTiming` gains `Credential string` (`json:"credential,omitempty"`), `"oauth"` for the direct stage and empty everywhere else; `runstore.Cost` gains `ModelNotionalUSD float64` (`json:"model_notional_usd,omitempty"`), and the cost constructors (`runstore.NewCost`, `ModelOnlyCost`, `newCost`, `internal/runstore/cost.go:52-71`) take the notional part and subtract it from `TotalUSD` (a run with `basis == api-list` must not bill the subscription stage). `ModelUSD` keeps its meaning — every stage's model dollars at list rates — so the documented invariant `sum(stages[].model_usd) + model_by["unattributed"] == cost.model_usd` still holds exactly, and `model_notional_usd` says how much of it was notional. `model_basis` stays `api-list` (the run's billed part is the gateway's) and `model_source` stays `"gateway"`; the stage's own `credential: oauth` is what says its `model_usd` is Claude Code's own figure. **Every reader of the run's dollars must split on the new field rather than on `ModelBasis`**, because a mixed run's `ModelBasis` is `api-list` for the whole run: `internal/cli/report.go`'s `recordOfRun` (`:407-430`), `fugaro runs ls` (`internal/cli/runs.go:547`), and `internal/runview`'s `Sum` (`internal/runview/runview.go:384-395`, whose `ModelBasis == BasisSubscription` branch is the split `fugaro runs ls` (`internal/cli/runs.go:521`) and `fugaro watch` (`internal/cli/watch.go:454`) total — and only those two call it). `fugaro budget show` needs nothing: it renders the registry's counted/spent/notional counters (`internal/cli/budget.go:442-522`), which `AddNotional` already feeds correctly (P13). `budget preview`'s typical line **has** landed (PR #357, merged) and **does** read per-stage figures, through the same wrong key: its means builder skips a whole run whose `rec.Cost.ModelBasis == BasisSubscription` and otherwise averages in every stage's `ModelUSD` (`internal/cli/budget_preview.go:495-514`), so a mixed run's reviewer stage would be averaged in as billed dollars; Task 5 moves it onto the same field as `Sum`. `budget.AgentEntry` gains nothing: the live registry describes the run, whose auth is api-key and whose counted spend is the gateway's, and the notional part already reaches the backend through `AddNotional` (P13). *Veto alternative:* `cost.model_usd` = billed only and the sum invariant restated — rejected: it would make one documented invariant false for exactly one kind of run, and a reader comparing a stage's figure with the run's would find a gap nothing explains.
- **P13. `reportNotional` fires per stage, not per run.** Its gate is `if sess == nil || r.gatewayOn() { return }` (`internal/runner/budget_session.go:352`), which for a mixed run is true and silently drops the direct stage's notional dollars from the counters the dashboard and `fugaro report` read. The signature grows the stage name — `reportNotional(ctx, name, res)` (`internal/runner/runner.go:1686`) — and the gate becomes the stage's own, **inverted**: `if sess == nil || !r.stageDirect(name) { return }`, against today's `if sess == nil || r.gatewayOn() { return }`. A gateway stage's dollars are the ledger's to report and a direct stage's are nobody else's, so the guard must return for the gateway stages and fall through for the direct one; written without the negation it would return early for exactly the stage that must report, which is the failure Review Focus 9 and `TestNotionalLandsOnTheRunLedgerAndCounters` exist to prevent. The by-model split it writes prices the reviewer's usage against `r.spend.Prices`, which for an enforcing run is the embedded Claude table plus the owner's overrides, so a Claude model is priced and the notional figure is at list rates, as the field means. **What `AddNotional` does with it is verified, not assumed** (`internal/budget/lease.go:308-324` and its flush at `:461-481`): the figure is added to the run's own ledger leaf (`/spend/<day>/runs/<slug>/<run>/notional`) and to the repository's and the project's notional counters — which is why a mixed run's reviewer stage shows up in the notional column of `fugaro watch` and `budget show` while the run's own row shows only the gateway's counted spend (`budget.AgentEntry`, `internal/budget/model.go:307-336`, carries `Spent` and no notional field at all). Task 5 pins that with a test and Task 7 says it in the docs; **this plan does not add a notional field to the live registry**, because a new registry field is a backend rules deployment and a version skew of its own for a display the stored record already gives. *Veto alternative:* report the whole run's notional part once at the end — rejected: the counters are per stage so a kill mid-run keeps what completed, and the stage's model usage is only in that stage's result event.
- **P14. `checkSettingsRouting`'s refused-key set gains `CLAUDE_CODE_OAUTH_TOKEN`, and the check's gate grows the direct stage.** `agent.RoutingKeys` (`internal/agent/settings.go:108`) lists the settings `env` keys that would send Claude Code's calls or its credentials somewhere other than Fugaro's gateway, reading the `routingEnvKeys` list at `:98-101` — `ANTHROPIC_BASE_URL`, `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, the `CLAUDE_CODE_USE_*` prefix, the proxies. `CLAUDE_CODE_OAUTH_TOKEN` is not on it, and on the direct stage that variable **is** the credential: a committed `.claude/settings.json` setting it would replace the account the run resolved with one the repository names. **What is and is not tightened, precisely:** `checkSettingsRouting` has exactly two call sites and both are behind `gatewayOn()` — `stage()`'s (`internal/runner/runner.go:1593`, under the `if r.gatewayOn()` at `:1593`) and `checkBudget`'s (`internal/runner/gateway.go:359`, after the `if !r.gatewayOn() { return nil }` at `:343`) — so (a) a plain `auth: oauth` run never reaches it, so adding the key changes **nothing** for existing oauth runs; (b) the tightening lands on every run that **does** reach it, which today means every `api-key` and `vertex` run with the budget on: a repository whose `.claude/settings.json` sets `CLAUDE_CODE_OAUTH_TOKEN` is now refused there too, where before it was allowed and meaningless. That is a strictness increase for existing api-key and vertex runs, deliberately, and it is the fail-closed direction. **It is a strictness increase for repositories that never opt in, so it is announced rather than discovered:** Task 6 adds it to `docs/release.md` next to the `stageAuthSince` line (D4), in the words "a repository whose committed `.claude/settings.json` sets `CLAUDE_CODE_OAUTH_TOKEN` is now refused on any budget-on run; remove the key, which the runner sets for the account you chose". And (c) because a `stage_auth` run with the budget **off** has no gateway, the check would never run for the one stage whose credential it is there to protect, so **both** call sites' gates become `r.gatewayOn() || r.cfg.Agent.ReviewerOnOAuth()` — the runner's at `:1593` and `checkBudget`'s at `:343`, which is the one a bootstrap-time refusal comes from. The remaining hole is named rather than closed: a plain `auth: oauth` run's settings file is still never checked at all, which is a pre-existing gap this plan writes down (Review Focus 12) and does not fix, since closing it would start refusing settings files for existing oauth workflows and is a decision of its own. *Veto alternative:* add the key only for runs with `stage_auth` — rejected: the hijack is equally possible for a plain `auth: oauth` run, and a per-run key set would be a second list to keep in step.
- **P15. `agent.max_budget_usd` is the reviewer stage's only bound, and it is Claude Code's own estimate — stated, not changed.** The gateway does not see the stage's calls, so no per-run cap binds it; `req.MaxBudgetUSD` (`internal/runner/runner.go:1642`) is passed to Claude Code as `--max-budget-usd` exactly as it is today, and for a Claude model that estimate is accurate (design §5's budget bullet: unlike DeepSeek, where it is about 25 times too high). No new cap, no new key: `fugaro validate` adds one note for a `stage_auth` workflow naming the stage, the bound and the fact that the run's `budget.per_run_usd` does not bind it, and `docs/multi-model.md` §5 says the same in the owner's words. **The budget-off case is defined, not left to be discovered.** With `budget.mode: off` (or no budget block) `spend.On()` is false, so `gatewayOn()` is false for every stage and there is no gateway at all: the coder stage runs api-key direct with the real Anthropic key, exactly as a budget-off api-key run does today, and the reviewer stage runs oauth direct. The direct stage still gets its Claude pins and `--max-budget-usd` (P10), and `fugaro validate`'s note says so. Nothing is refused, because nothing about it is unsafe — but it is also not the design's shape, so the note says the run has no gateway and both stages are direct. A provider coder model cannot appear in that configuration anyway: `config.CheckProviderGateway` (`internal/config/providers.go:421-424`) already refuses a provider-served model unless the budget is `enforce`, from both `validate` and the runner's bootstrap, so a budget-off `stage_auth` run has a Claude coder or no provider route. *Veto alternative:* require a separate `agent.stage_auth.max_budget_usd` — rejected: a second budget knob for one stage, defaulting to the first one anyway, is a knob nobody sets correctly.
- **P16. `agent.stage_auth` may be set in the repository's own `fugaro.yaml` only — not in the project layer, not in an override.** The scope row is `{Key: "agent.stage_auth", In: InRepo, Why: "it turns on a subscription credential for one stage, which only the repository's own, PR-reviewed fugaro.yaml may opt into; a project-wide or launcher-written opt-in would enable it for repositories the owner never vetted"}`. The project layer is written by a project lead (a bucket writer) and an override is written by a launcher; both are outside the PR review that makes the opt-in meaningful, and both are already refused the credential identity itself (`agent.oauth_token` is `InRepo | InOverride` precisely because a launcher may **switch** accounts, never **enable** the token). `docs/project-layer.md`'s marked table gets the row in the same commit, and `TestScopeTableMatchesDocs` is the test. *Veto alternative:* `InProject | InRepo`, matching `agent.auth` — rejected: `agent.auth` chooses among credentials the owner already runs, while `stage_auth` adds the subscription token's `/proc` exposure (Review Focus 1 and 2) to a repository the project lead may never have seen.
- **P17. `stage_auth` is refused as not yet implemented from Task 1 until the task that makes the runner honour it, and that refusal is the only thing that makes the intermediate commits safe.** Without it, `stage_auth` decodes from Task 1 onward and is ignored by the runner until the runner's task lands: every run of an opted-in repository would go through the gateway on the api-key credential, silently doing the opposite of what the owner asked and billing the model the owner meant to take off the meter. So Task 1 adds one clause to `CheckProviderAuth` — any non-nil `StageAuth` is a problem, `agent.stage_auth is not implemented in this release: ...` — placed **after** the mix and model rules of P3 and P4 and **before** `CheckProviderAuth`'s early api-key return, so that every specific refusal still fires with its own message while a config that would be permitted is refused for exactly this reason. Both surfaces that already call `CheckProviderAuth` (`fugaro validate`, the runner's `checkProviderModels`) refuse it, so no run of an opted-in repository can start. Task 4 deletes that clause in the same commit that makes the runner build the direct stage, and the test that pins it (`TestStageAuthRefusedUntilImplemented`) is replaced by Task 4's `TestStageAuthReviewerStageIsDirect`. From Task 4 until Task 6 the token is not yet mounted, so an opted-in run fails at bootstrap on the missing secret (P10's `infra_error`, whose message names the secret and the two commands that mount it) — a visible, fail-closed failure, which is why Tasks 4 and 6 ship in the same release. *Veto alternative:* land the runner before the config key — rejected: the runner cannot read a key the decoder refuses as unknown.

## Review Focus (mutation-proof notes)

**The residual risk, stated in the plan because the code cannot close it:**

1. **The token is readable by the coder through `/proc`.** The runner holds `CLAUDE_CODE_OAUTH_TOKEN` in its own environment for the whole job, and the agent runs as the same OS user in the same container, so a prompt-injected coder can read `/proc/<runner pid>/environ`. The stage-scoped environment (P10) keeps the token out of the coder's **own** environment and out of logs and transcripts; it does **not** narrow this. Pinned by nothing in this repository: the mitigation is the opt-in and SECURITY.md's known-gaps line (Task 6), and Task 8's live check must not claim otherwise.
2. **The metadata server.** The job's service account keeps `secretAccessor` on the token's secret, and the metadata server is reachable from the container, so an injected coder can read the token from Secret Manager even if `/proc` were closed. Design §6 mitigation 3 says fetching the token at stage start does not close it, and P10 does not fetch it at all. Same status as item 1: documentation, not code, and the honest sentence is "a separate job execution for the reviewer is the only mitigation that closes the gap".

**Mutation-proof notes (each names the test that pins it):**

3. **Review mode's trusted-author gate is what makes a review-mode opt-in acceptable, and this plan relies on it rather than refusing review mode (P5).** Pinned by the existing reviewmode tests — `checkReviewAuthor` refusing an untrusted author and a trusted author's foreign fork, and Bitbucket's fork refusal — plus `TestStageAuthPermitsReviewMode`, which asserts that `stage_auth` adds no refusal of its own to a review-mode recipe. The mutation that matters is the review-mode refusal coming back on the rationale this plan retracted, or the trusted-author gate being relaxed while `stage_auth` is set.
