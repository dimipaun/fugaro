# The OAuth token for the senior-reviewer stage: implementation plan

**Goal:** let one workflow run its **coder** through the budget gateway on a cheap provider model (`agent.auth: api-key`) while its **senior reviewer** runs Claude Code directly on a Claude subscription OAuth token, behind an explicit per-repository opt-in (`agent.stage_auth: {reviewer: oauth}`), so the strongest available reviewer costs no dollars per run and is bounded only by `agent.max_budget_usd`. This is Path B of [docs/design/mixed-credentials.md](../design/mixed-credentials.md) §5, which the owner ruled on 2026-10-14 is worth its residual risk with an opt-in and no separate reviewer job. No code in this plan has been written or run; this is a design-to-code plan, the same status `docs/plans/2026-10-14-*` had before its Task 1 started. **This PR (the one that adds this plan) is docs-only: no Go, Terraform or product-behavior file under this plan's "Files" lists is touched by it — the one exception is `docs/gcp-live-checklist.md`, Task 7's own file, which IS one of the two files this PR itself edits, since reserving Check 45's number and writing its not-yet-run steps is itself a docs-only act. Tasks 1 onward are future work, gated on the owner approving this plan's decisions.**

**Spec:** [docs/design/mixed-credentials.md](../design/mixed-credentials.md) §5 (the shape and the four bullets), §6 (the residual risk and the four mitigations), §7 (the comparison table), §9 (the tests for B). Its §8 records the owner's rulings: B is worth the residual risk, an opt-in is enough, the separate reviewer job is **not** required, and the M10 "Claude goes direct" rule is relaxed only by an explicit opt-in in config. This plan's own decisions continue as P1 onward, each independently vetoable.

**Depends on:** release 0.7.x on `main` — the M10 budget gateway and provider routes (`internal/gateway`, `internal/runner/gateway.go`, `internal/config/providers.go`), the named Claude accounts and their per-account job variants (`internal/infra/spec.go`, `internal/cli/run.go`'s `claudeAccountFor`, `docs/design/named-oauth-tokens.md`), the recipe role mapping (`internal/recipe`, `internal/runner/recipe.go`'s `ApplyRoles`), and the per-stage cost fields of `result.json` (generic-tool plan Task 24, `internal/runstore.StageTiming`). It does **not** depend on the §4 opt-in that lets a provider route claim an `anthropic/<id>` (a Path C senior): P4 is written to stay correct when that lands, and nothing here needs it.

**Checked before this plan was written:** every claim about existing code below was read on this branch's base — `internal/config/{config.go,providers.go,validate.go,scope.go,example.yaml,docs_scope_test.go,corpus_test.go}`, `internal/infra/spec.go`, `internal/backend/gcp/{names.go,run.go}`, `internal/cli/{run.go,initsecrets.go,validate.go,validate_recipes.go,upgrade_cloud.go,doctor.go,runs.go,report.go}`, `internal/recipe/recipe.go`, `internal/runner/{runner.go,recipe.go,gateway.go,agentenv.go,cost.go,budget_session.go,spend.go}`, `internal/agent/{env.go,settings.go}`, `internal/runstore/{runstore.go,cost.go}`, `internal/gitops/gitops.go`, `internal/watch/build.go`, `internal/budget/model.go`, `schemas/{fugaro,result}.schema.json`, `docs/{multi-model.md,project-layer.md,gcp-live-checklist.md}`, `SECURITY.md`. If the merged code differs when a task starts, that task's implementer adapts its edits to the then-current file, not the other way round (the rule `docs/plans/2026-10-08-upgrade.md` and `docs/plans/2026-10-13-project-secrets.md` use).

## Decisions (veto any before execution starts)

- **P1. `agent.stage_auth` is a pointer to a struct with exactly one field, `reviewer`, whose only accepted value is `oauth`.** `StageAuth *StageAuth` (`yaml:"stage_auth,omitempty"`) holding `Reviewer string` (`yaml:"reviewer,omitempty"`), with `func (a Agent) ReviewerOnOAuth() bool`. A pointer, not a value, because the config is decoded with `dec.KnownFields(true)` (`internal/config/config.go:485`): the pointer is the only way to tell `stage_auth: {}` (present, sets nothing — refused, because a silent no-op that looks like an opt-in is the worst of both) from an absent key. The struct is what makes `stage_auth: {coder: oauth}` an unknown-field **parse** error rather than a validation rule, so the "only `reviewer` in this slice" limit is enforced by the decoder, before any check runs. *Veto alternative:* `agent.reviewer_auth: oauth` (a scalar) — rejected: the design names `stage_auth`, and a scalar key would have to be renamed if it ever generalizes (design §8 open question 2 recommends it never does, which is why `coder` is refused rather than ignored).
- **P2. `agent.auth` stays the run's auth; `stage_auth` is an override for exactly one stage, never a second auth mode.** Everything that reads `cfg.Agent.Auth` today — `gatewayOn()` (`internal/runner/gateway.go:46`), the budget registry entry (`Auth: r.cfg.Agent.Auth`, `internal/runner/budget_session.go:265`), `runstore.ModelBasis` (`internal/runstore/cost.go:41`), `watch`'s `Notional: e.Auth == "oauth"` (`internal/watch/build.go:393`) — keeps reading it, and the sites that must become per-stage change **at that site** (P11), not by redefining the key. A `stage_auth` run is still an api-key run: api-key job, api-key budget identity, gateway for every stage but one. *Veto alternative:* make `agent.auth` a list or a map — rejected: it changes every existing consumer and every existing `fugaro.yaml` for one stage of one role.
- **P3. The permitted mix is exactly `agent.auth: api-key` plus `stage_auth.reviewer: oauth`; every other combination is refused, and the rule lives in `config.CheckProviderAuth`.** That function (`internal/config/providers.go:262`) is already the auth/model consistency rule and is already called from both surfaces that matter: `fugaro validate` (`internal/cli/validate.go:194`) and the runner's bootstrap (`internal/runner/gateway.go:402`, `checkProviderModels`), each **after** `runner.ApplyRoles` has rewritten the role models (`internal/cli/validate_recipes.go:132` `withRecipeRoles`; `internal/runner/recipe.go:107`), so the checks see the models the run really uses. The refusals, each naming the key and the reason: `stage_auth` with `auth: oauth` ("the whole run already uses the subscription token; `stage_auth` would say nothing"), with `auth: vertex` (same shape), `stage_auth.reviewer` holding anything but `oauth`, and `stage_auth` present with no `reviewer`. *Veto alternative:* a new `CheckStageAuth` called from the same two places — rejected as a second place to keep in step with `CheckProviderAuth` for no gain; the one rule that genuinely needs config `CheckProviderAuth` does not receive is P6's, and that gets its own small function for that reason.
- **P4. The reviewer's model must be a Claude model that Anthropic serves directly, and no provider route may claim it.** On the direct stage the model ID goes to Anthropic, so it must match `config.ClaudePatterns` (`claude-*` or `anthropic/*`, `internal/config/providers.go:205`) **and** `config.ProviderFor(providers, model)` must not find a route for it. Both clauses are needed and neither is redundant: a DeepSeek reviewer would send a DeepSeek ID to Anthropic, and a provider-claimed `anthropic/claude-sonnet-5-5` (the §4 opt-in's spelling) is OpenRouter's ID, not Anthropic's — a Path C senior, not a Path B one. The refusal names `agent.models.reviewer`, the model and `agent.stage_auth`. **This is also what catches `roles: {reviewer: coder}` for free**: `ApplyRoles` copies the coder's model onto `Models.Reviewer` before any check runs, so a DeepSeek coder becomes the reviewer's model and the Claude clause refuses it — pinned by a test that asserts the refusal for a `reviewer: coder` recipe, not merely for an explicit DeepSeek `agent.models.reviewer`.
- **P5. A recipe that swaps roles, and any review-mode recipe, is refused with `stage_auth`; the runner is the authority, `validate` is best-effort.** A role swap makes one role's model run in the other's stage, so the slice's contract ("exactly the `review` stage runs direct, with exactly `agent.models.reviewer`") becomes a coincidence of the recipe: `reviewer: coder` puts a non-Claude model on the direct stage (P4 catches it, but the message should name the recipe), and `coder: reviewer` runs the reviewer's Claude model on the **gateway** stage while the reviewer runs it direct — the same model on two credentials, which is not a mix this slice defines. Review mode (`recipe.Mode == ModeReview`, `internal/recipe/recipe.go:38-41`) is refused because it reviews a pull request's head, which for a fork is code the repository did not write — exactly the case design §6 mitigation 1 excludes. The check is `runner.StageAuthRoleProblems(a config.Agent, rcp *recipe.Recipe) []config.Problem` (new, in `internal/runner/recipe.go`, next to `ApplyRoles`), called from the runner's bootstrap and from `internal/cli/validate_recipes.go`. A **project** recipe is not readable from a checkout, so `validate` cannot always decide: `annotateProjectRecipe` (`internal/cli/validate_recipes.go:148`) gains the same note it already adds for the role-mapped model keys, and the runner — which reads the recipe at the task's ref and always has it — refuses at bootstrap. *Veto alternative:* refuse `stage_auth` whenever `agent.recipe` names anything at all — rejected: it would refuse the ordinary `standard` recipe, which is the one the opt-in is for.
- **P6. `followup.allow_public: true` is refused with `stage_auth`.** `AllowPublic` lets a follow-up run on a public repository (`internal/config/config.go:80-82`, read at `internal/runner/followup.go:195`), where a commenter who can push branches can steer a run whose job holds the subscription token. It does not gate the **first** run on a public repository (design §6 mitigation 1 says so plainly), so this refusal is only one of the two gates the config can express; the other is `claude_accounts.<name>.allow_data_to`, which is owner-controlled and checked at launch (P7). New `config.CheckStageAuth(a Agent, f Followup) []Problem`, called from `internal/cli/validate.go` and from the runner's `checkProviderModels` (which can read `r.cfg.Followup`), so both surfaces refuse it. The message says what to do: remove `stage_auth`, or remove `followup.allow_public` and run on a private repository. *Veto alternative:* warn instead of refuse — rejected: the whole point of an opt-in for a residual risk this size is that the dangerous combinations are hard refusals, and a warning on a public repository is a warning nobody reads.
- **P7. `agent.oauth_token` names the reviewer's account; the launch gate is relaxed by exactly one clause.** `claudeAccountAllowed` (`internal/cli/run.go:867`) today refuses a named account outright when `co.Agent.Auth != "oauth"`, because no secret would ever be mounted for it. With `stage_auth` a secret **is** mounted (P8), so the clause becomes `co.Agent.Auth != "oauth" && !co.Agent.ReviewerOnOAuth()` and nothing else changes: the allow-list membership check, the `--token` resolution order (`claudeAccountFor`, `:851`), the follow-up inheritance rule and the job-variant-must-exist backstop (`internal/backend/gcp/run.go:145`'s "job %s does not exist; create it with fugaro init --repo") all stay as they are. `fugaro doctor`'s `oauth-token-allowed` check (`internal/cli/doctor.go:582-611`) reports the account for a `stage_auth` workflow too, and its `claude-accounts-stored` sibling (`:525`) expects the named secret to exist for it. *Veto alternative:* a separate `agent.stage_oauth_token` key — rejected: the account is a property of the workflow's identity, not of which stage uses it, and two keys naming accounts could disagree.
- **P8. Infra mounts the token and builds the account variants for an api-key workflow that sets `stage_auth`, through one shared predicate.** Three sites gate on `cfg.Agent.Auth == "oauth"` today and all three must ask the same question: `infra.SecretMounts`'s switch (`internal/infra/spec.go:561-563`, which mounts `config.ClaudeAccountSecret(token)`), the per-account variant loop in `BuildRepoSpec` (`:797-800`, which decides the token set `{"default"} ∪ config.AllowedClaudeAccounts(...)`), and `fugaro init --repo`'s secrets stage (`internal/cli/initsecrets.go:315`, which prompts for every allowed account's own token). One new predicate — `config.Agent.UsesClaudeToken() bool` = `Auth == "oauth" || ReviewerOnOAuth()` — is what all three call, so a fourth caller cannot get it subtly different, and the variant job names stay `gcp.WorkflowVariant(name, token)` (`internal/backend/gcp/names.go:285`) unchanged. *Veto alternative:* let `init --repo` mount the token on the default job only and refuse `--token NAME` for a `stage_auth` workflow — rejected: the whole reason named accounts exist is that the owner's subscription is not the repository's, and a `stage_auth` reviewer is exactly the case where an owner wants to choose which account pays.
- **P9. A new key in a strictly-decoded config is a version-skew break, so `fugaro init --repo` refuses `stage_auth` against a base image that predates the release reading it, and the upgrade note is extended.** `config.Parse` decodes with `dec.KnownFields(true)` (`internal/config/config.go:485`), so a base image older than the release that knows `stage_auth` fails at bootstrap with an unknown-field error naming a key the owner did type — a repository that merges `stage_auth` would start failing every run until its image is rebuilt. The mitigation is the `cloneSince`/`imagePredates` shape (`internal/cli/recipes_skew.go:43`, `internal/cli/init_fugaroyaml.go:133`): a `stageAuthSince` constant, unshipped at first, with a release-checklist line, refusing `init --repo` with a message naming the release. **Separately, the existing deployed-job note does not cover this change and must be extended:** `jobConfigCopyNote`'s diff loop (`internal/cli/upgrade_cloud.go:239-266`) walks each workflow's **default** job through `infra.Workflow` and compares `spec.Env` only, so it never sees a `SecretEnv` mount and never sees a variant job. The task's first step is to verify what `JobFullEnv` returns for a secret-backed env entry before writing the test; the note then reports, in names and never values, a workflow whose deployed job lacks a secret env name the spec now declares, and a workflow whose spec declares a variant job that does not exist. *Veto alternative:* change only the note's wording — rejected: the owner reading it would be told to re-run `init --repo` for a reason the tool cannot actually see, which is how a note stops being trusted.
- **P10. The reviewer stage gets its own `agent.EnvSpec`, built once at bootstrap, and the managed settings file is rewritten for it and restored at stage end.** `r.env` is built by one `agent.BuildEnv` call with the gateway (`internal/runner/runner.go:1084`); the direct stage needs the other branch of the same function (`auth: oauth`, `Gateway: nil`, which prepends `CLAUDE_CODE_OAUTH_TOKEN` and refuses a gateway, `internal/agent/env.go`'s `case "oauth"`). Building it at bootstrap — not at stage start — means a missing or too-short token is an `infra_error` before the first stage instead of a failure mid-run, and it is what makes the design's mitigation 3 ("fetching the token at stage start shortens the window but does not close it") explicitly **not** in this slice: the token is a mounted secret in the runner's environment for the whole job either way. The managed settings file (`agent.WriteManagedSettings`, `internal/runner/agentenv.go`) carries `ANTHROPIC_BASE_URL` and the gateway's token under api-key; for the direct stage it is rewritten with the pins and the web-tool denial only, and rewritten back at stage end, so a stage that follows the reviewer's (a `fix` after a rejected review) never starts under the reviewer's routing. The reviewer's model set is **Claude-only**: `agent.PinVars(reviewerModel, "", maxOutput)` — no `ANTHROPIC_DEFAULT_HAIKU_MODEL` (the run's background model is the DeepSeek coder, an ID with no meaning on a direct stage) and no `agent.ProviderRouteVars()` (design §5). *Veto alternative:* remove the managed settings file for the direct stage instead of rewriting it — rejected: the web-tool denial and the model pin are exactly what the file is for, and removing it would also drop `CLAUDE_CODE_MAX_OUTPUT_TOKENS`.
- **P11. Every reader that asks "does this run have a gateway?" about a **stage** must ask "does this stage use the gateway?" instead.** One predicate, `func (r *run) stageDirect(name string) bool { return r.cfg.Agent.ReviewerOnOAuth() && config.StageRole(name) == config.RoleReviewer }`, threaded through the stage path, because `r.gw != nil` is true for a `stage_auth` run and wrong at each of these sites: `stagePins` (`internal/runner/agentenv.go`, which would add the DeepSeek background pin and the provider-route vars), `writeManagedSettings` (`:1533`), the `beginGatewayStage`/`watchHalt` block (`internal/runner/runner.go:1604`), `crossCheckCost` (`:1655`, which compares Claude Code's own figure against `r.lastStage`'s gateway figure and would WARN spuriously against the **previous** stage's), `r.rec.CostUSD = r.gwUsed.USD()` (`:1657`, which would overwrite the run's billed figure from the ledger and drop the direct stage's entirely), `stageTiming` (`internal/runner/cost.go`, `gateway := r.gw != nil`), and `reportNotional` (P13). The direct stage also clears `r.lastStage` so nothing stale is read. *Veto alternative:* give the direct stage its own tiny "gateway" object that reports zero — rejected: it would make the ledger look like it saw a stage it never saw, and `cost.model_by`'s `unattributed` accounting would absorb the difference.
- **P12. The reviewer stage's dollars are notional, recorded per stage and per run, and `cost.model_usd` keeps its sum invariant.** `runstore.StageTiming` gains `Credential string` (`json:"credential,omitempty"`), `"oauth"` for the direct stage and empty everywhere else; `runstore.Cost` gains `ModelNotionalUSD float64` (`json:"model_notional_usd,omitempty"`), and the cost constructors (`runstore.NewCost`, `ModelOnlyCost`, `newCost`, `internal/runstore/cost.go:52-71`) take the notional part and subtract it from `TotalUSD` (a run with `basis == api-list` must not bill the subscription stage). `ModelUSD` keeps its meaning — every stage's model dollars at list rates — so the documented invariant `sum(stages[].model_usd) + model_by["unattributed"] == cost.model_usd` still holds exactly, and `model_notional_usd` says how much of it was notional. `model_basis` stays `api-list` (the run's billed part is the gateway's) and `model_source` stays `"gateway"`; the stage's own `credential: oauth` is what says its `model_usd` is Claude Code's own figure. `internal/cli/report.go`'s `recordOfRun` (`:406-430`) splits `ModelUSD - ModelNotionalUSD` into counted and `ModelNotionalUSD` into notional instead of keying off `ModelBasis`, and `fugaro runs ls` (`internal/cli/runs.go:547`) appends the notional part beside the total for a mixed run rather than adding `~` to a total that is real. `budget.AgentEntry` gains nothing: the live registry describes the run, whose auth is api-key and whose counted spend is the gateway's, and the notional part already reaches the backend through `AddNotional` (P13). *Veto alternative:* `cost.model_usd` = billed only and the sum invariant restated — rejected: it would make one documented invariant false for exactly one kind of run, and a reader comparing a stage's figure with the run's would find a gap nothing explains.
- **P13. `reportNotional` fires per stage, not per run.** Its gate is `if sess == nil || r.gatewayOn() { return }` (`internal/runner/budget_session.go:352`), which for a mixed run is true and silently drops the direct stage's notional dollars from the counters the dashboard and `fugaro report` read. The signature grows the stage name — `reportNotional(ctx, name, res)` (`internal/runner/runner.go:1619`) — and the gate becomes the stage's own (`stageDirect`). The by-model split it writes prices the reviewer's usage against `r.spend.Prices`, which for an enforcing run is the embedded Claude table plus the owner's overrides, so a Claude model is priced and the notional figure is at list rates, as the field means. *Veto alternative:* report the whole run's notional part once at the end — rejected: the counters are per stage so a kill mid-run keeps what completed, and the stage's model usage is only in that stage's result event.
- **P14. `checkSettingsRouting`'s refused-key set gains `CLAUDE_CODE_OAUTH_TOKEN`.** `agent.RoutingKeys` (`internal/agent/settings.go:95-102`) lists the settings `env` keys that would send Claude Code's calls or its credentials somewhere other than Fugaro's gateway — `ANTHROPIC_BASE_URL`, `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, the `CLAUDE_CODE_USE_*` prefix, the proxies. `CLAUDE_CODE_OAUTH_TOKEN` is not on it, and on the direct stage that variable **is** the credential: a committed `.claude/settings.json` setting it would replace the account the run resolved with one the repository names. Adding it makes the check refuse such a file on every run, which is a strictness increase for existing oauth runs too — deliberately, and it is the fail-closed direction. *Veto alternative:* add the key only for runs with `stage_auth` — rejected: the hijack is equally possible for a plain `auth: oauth` run today, and a per-run key set would be a second list to keep in step.
- **P15. `agent.max_budget_usd` is the reviewer stage's only bound, and it is Claude Code's own estimate — stated, not changed.** The gateway does not see the stage's calls, so no per-run cap binds it; `req.MaxBudgetUSD` (`internal/runner/runner.go:1575`) is passed to Claude Code as `--max-budget-usd` exactly as it is today, and for a Claude model that estimate is accurate (design §5's budget bullet: unlike DeepSeek, where it is about 25 times too high). No new cap, no new key: `fugaro validate` adds one note for a `stage_auth` workflow naming the stage, the bound and the fact that the run's `budget.per_run_usd` does not bind it, and `docs/multi-model.md` §5 says the same in the owner's words. *Veto alternative:* require a separate `agent.stage_auth.max_budget_usd` — rejected: a second budget knob for one stage, defaulting to the first one anyway, is a knob nobody sets correctly.
- **P16. `agent.stage_auth` may be set in the repository's own `fugaro.yaml` only — not in the project layer, not in an override.** The scope row is `{Key: "agent.stage_auth", In: InRepo, Why: "it turns on a subscription credential for one stage, which only the repository's own, PR-reviewed fugaro.yaml may opt into; a project-wide or launcher-written opt-in would enable it for repositories the owner never vetted"}`. The project layer is written by a project lead (a bucket writer) and an override is written by a launcher; both are outside the PR review that makes the opt-in meaningful, and both are already refused the credential identity itself (`agent.oauth_token` is `InRepo | InOverride` precisely because a launcher may **switch** accounts, never **enable** the token). `docs/project-layer.md`'s marked table gets the row in the same commit, and `TestScopeTableMatchesDocs` is the test. *Veto alternative:* `InProject | InRepo`, matching `agent.auth` — rejected: `agent.auth` chooses among credentials the owner already runs, while `stage_auth` adds the subscription token's `/proc` exposure (Review Focus 1 and 2) to a repository the project lead may never have seen.

## Global Constraints

From the design:
- Only `stage_auth.reviewer: oauth` exists in this slice; `coder` and every value but `oauth` are refused (P1, P3).
- Only `agent.auth: api-key` may combine with `stage_auth`; every other mix is refused (P3).
- The reviewer's model must be Claude served by Anthropic directly, unclaimed by any provider route (P4).
- The run's auth, job, budget identity and gateway stay api-key; one stage only is direct (P2, P11).
- The token is a mounted secret in the runner's environment for the whole job, and the job's service account keeps `secretAccessor` on it (design §6). Nothing in this plan narrows that; the mitigations are the opt-in (P3, P5, P6, P7) and the documentation (Task 6).
- The subscription stage's dollars are notional and never enter `TotalUSD` or a cap (P12, P13).
- `cost.model_usd`'s documented sum invariant stays true for every run (P12).

Project rules (carried over from this repository's existing plans):
- Every task's own test run is in the foreground, `-count=1`, and `-race` where the package's existing tests use it.
- Fakes only in tests: no real Anthropic call, no real subscription token, no real Cloud Run job.
- Docs must match behavior: `GOFLAGS=-p=2 go test ./internal/cli -run 'Docs|Lint' -count=1` stays green throughout. This plan adds a `fugaro.yaml` key, so the schema, the scope table and the corpus **do** change, in Task 1, and the lint is the test that says so.
- `fugaro verify build` / `fugaro verify test` are the only build and test entry points for this repository's own conventions; a task runs them before it is considered done.
- Check 45 (Task 7) is the owner's own task, run once, **sandbox installation and sandbox repository only, never the `belong` project, and never applied by an agent**; the owner types their own token, and no agent ever sees it.

## Review Focus (mutation-proof notes)

**The residual risk, stated in the plan because the code cannot close it:**

1. **The token is readable by the coder through `/proc`.** The runner holds `CLAUDE_CODE_OAUTH_TOKEN` in its own environment for the whole job, and the agent runs as the same OS user in the same container, so a prompt-injected coder can read `/proc/<runner pid>/environ`. The stage-scoped environment (P10) keeps the token out of the coder's **own** environment and out of logs and transcripts; it does **not** narrow this. Pinned by nothing in this repository: the mitigation is the opt-in and SECURITY.md's known-gaps line (Task 6), and Task 7's live check must not claim otherwise.
2. **The metadata server.** The job's service account keeps `secretAccessor` on the token's secret, and the metadata server is reachable from the container, so an injected coder can read the token from Secret Manager even if `/proc` were closed. Design §6 mitigation 3 says fetching the token at stage start does not close it, and P10 does not fetch it at all. Same status as item 1: documentation, not code, and the honest sentence is "a separate job execution for the reviewer is the only mitigation that closes the gap".

**Mutation-proof notes (each names the test that pins it):**

3. **The reviewer stage silently gets the gateway's base URL.** Pinned by a runner test that inspects `req.Env` for the `review` stage: it contains `CLAUDE_CODE_OAUTH_TOKEN`, and contains neither `ANTHROPIC_BASE_URL` nor `ANTHROPIC_API_KEY`; and the coder stage's `req.Env` is the exact reverse (Task 4).
4. **The managed settings file still carries the gateway during the reviewer stage, or is left rewritten after it.** Pinned by a runner test that reads the file from inside the fake agent's run hook (no `ANTHROPIC_BASE_URL`, no `ANTHROPIC_DEFAULT_HAIKU_MODEL`, the reviewer's model pinned) and again after the stage returns (the gateway's variables are back), with a following coder stage asserted to start under the restored file (Task 4).
5. **The DeepSeek background model is pinned onto the direct stage.** Pinned by the same two tests asserting no `ANTHROPIC_DEFAULT_HAIKU_MODEL` and no `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS`/`MAX_THINKING_TOKENS` anywhere in the reviewer stage's env or settings (P10).
6. **The reviewer stage's cost is billed into `TotalUSD`.** Pinned by a `runstore` test on the cost constructors and by a runner test on a one-run record: `model_notional_usd` equals the direct stage's `model_usd`, `total_usd` excludes it, and `sum(stages[].model_usd) + model_by["unattributed"] == model_usd` still holds (P12, Task 5).
7. **`stageTiming` attributes the previous stage's gateway figure to the direct stage, or `r.rec.CostUSD` drops the direct stage's.** Pinned by one runner test with both stages in one run: the `review` stage's `model_usd` is Claude Code's own number for it (not the coder stage's gateway figure), and the run's `cost.model_usd` is the two stages' sum (P11, Task 5). The same test asserts no `cost cross-check` WARN for the direct stage.
8. **The direct stage's notional dollars never reach the counters.** Pinned by a budget-session test asserting `AddNotional` is called for the `review` stage of a run whose gateway is on (P13, Task 5). The mutation that matters is the `r.gatewayOn()` early return coming back.
9. **A repository's settings file replaces the account the run resolved.** Pinned by an `internal/agent` test on `RoutingKeys` with `CLAUDE_CODE_OAUTH_TOKEN` set, and a runner test that `checkSettingsRouting` refuses a checkout whose `.claude/settings.json` sets it (P14, Task 4).
