## 1. What this plan is

The spec asks for eight components (its §4, plus the mobile relay of §9). Read against the tree (design §1), they fall into four groups, and the plan's ordering follows from that:

1. **The conversation half is one spawn and one parser** (design F1, D40). The bridge comes **first** (phase V1) and it comes **without audio** — text in, text out, on screen — because a bridge built after the audio would be shaped by it, and because everything in phase V1 is testable with a fake child and a scripted transcript.
2. **The event half is a classification layer over a document that already exists** (design F2, F3, D48). It comes second (phase V2) because it depends on nothing else and because it is the cheapest part of the spec: `fugaro watch --json` already computes the burn rate, the cap fractions and the kill state, and the console already reads them through `FugaroSource`.
3. **The audio is where the credentials, the permissions and the provider choice live** (design F15, F18, F19, F22; D43–D46). It comes third, behind its own decisions, and behind interfaces with fakes so that four of the spec's six acceptance criteria are asserted in CI without a microphone and without a provider.
4. **Everything that writes, everything that leaves the machine, and everything that needs a new artifact comes last and separately** (phases V7–V10): the cloud providers, the packaged permission ask, the standalone entry point, and — if ever — the phone relay, which is a rules change and a design of its own.

**Releases.** The console is its own artifact published from the CLI's own `vX.Y.Z` tag (console D11), and this module ships inside that artifact rather than as a second one (design D50). **This plan adds no release and is not scheduled against one** (design D53). The release train this repository records is **R4 of [2026-10-14-project-centric.md](2026-10-14-project-centric.md)**: project-centric phase 0 on `main`, phases 1–6 on `next`, released together as **0.8.0**; the highest release in `docs/releases/` is `v0.7.5.md`.

**Global constraints.** The console plan's Global Constraints **1–10** apply to every task here, verbatim and without restatement: no new backend ever; no credential read, held or stored by the app; the app never writes; the renderer is untrusted and gets no network; every number carries an availability state; `belong` is never touched; no `.github/workflows/` edit by an agent (stage under `docs/pending-workflows/`); the Go module is untouched; SECURITY-SENSITIVE tasks are not merged on a self-review; docs-only tasks keep the docs suite green with `GOFLAGS=-p=2 go test ./internal/cli -run 'Docs|Lint' -count=1`. Four more are this plan's own:

11. **A credential value exists in exactly two places and no others**: the store that owns it on the operator's machine (their keychain, or Claude Code's own login store for the Claude credential of D42's recommendation) and the memory of the child process that resolves it, for as long as that child runs. Nowhere else: not this repository, not `fugaro.yaml`, not a published shared config, not the console's settings document, not the app, not a log, not a fixture, not a test.
12. **Nothing recorded from a person is committed.** Not a voice, not a transcript of a real conversation. Audio fixtures are **synthesised** (Task V4.3) and transcripts come from fixtures that pass D6's redaction check. This is tighter than the console plan's rule 6 and it is deliberate: design F32.
13. **Every audible claim is traceable to a document or a fake.** A spoken sentence may state a fact only if that fact is a field of a `watch --json` document, a field of an agent message, or a value the summarizer was given — and the digest may never invent a state (`important`'s "awaiting user input" is dropped until something defines it: design F3, D48). This is the console's §6.1 availability rule with a microphone in front of it, and it is a review criterion, not a nicety.
14. **The two-binary spawn table is as mutation-proof as the one-binary table.** Console §5.1 rule 6's mechanism (a test that fails when a command or an argument is added) applies to the second table verbatim, and the `claude` table carries its own never-list — including `--dangerously-skip-permissions`, which the runner passes in a disposable container (`internal/agent/agent.go`'s `Args`) and which is a different proposition on the operator's own checkout (design D40, U5).

**Numbering, so nothing here collides.** These tasks are **V0.1 onward** and they are this document's own namespace. Two other namespaces exist and neither is touched: the console plan's tasks (0.1–5.x) and the console v2 plan's (V2.0.1 onward, on PR #426). Design decisions continue from **D39** and the reason is stated in [voice.md](../design/voice.md) §2 — D1–D20 are answered on `main`, D21–D38 are PR #426's, and the tree's own rule for a collision is "whichever merges second renumbers".

### Phase V1 — the bridge, with no audio

**V1.1 — the bridge interface, and the spawned-`claude` implementation. (needs D40) — SECURITY-SENSITIVE**
The `AgentBridge` interface exactly as the spec's §4.1 declares it — `send(text)`, `onMessage(cb)`, `onAwaitingInput(cb)` returning an unsubscribe, and the three `AgentMessage` kinds — with one implementation in this phase: a child process spawned the way the console spawns `fugaro`, with `shell: false`, an argv array, an explicitly resolved binary and the fixed minimal environment of console §3.4 rule 5. The argv is built in Go-shaped named fields on the app side from the same precedent the runner uses (`internal/agent/agent.go`'s `Args`), plus `--input-format stream-json`; the output is parsed with the shape this tree already understands (`internal/agent/stream.go`'s `ParseStream`). **No audio in this task and no summarizer.** The screen shows what came out, verbatim.
*Why security-sensitive:* **this is the task that widens console §3.4 rule 1 from one binary to two, and it is the first entry in the app's spawn story that is not read-only.** The reviewer's questions are: what is the second binary's exact argv table, what is in its never-list (`--dangerously-skip-permissions` first), can any field of any document or any transcribed text reach the argv, what happens when the binary is absent or is the wrong `claude`, and does the spawn log (console D20, `FUGARO_CONSOLE_SPAWN_LOG`) now cover both binaries.
*Files:* `console/` (the bridge, the second spawn table, the never-list test, the screen), `internal/cli/docs_console_boundary_test.go` if the boundary allow-list must grow (it must **not** — design F30), `docs/design/voice.md`.
*Verification:* the console's own test command, plus a mutation-proof test in console §5.1 rule 6's shape asserting that adding an argument to either table fails, plus `GOFLAGS=-p=2 go test ./internal/cli -run 'ConsoleBoundary' -count=1`.
*Independent merge:* yes, and it is the first code task in this plan.

**V1.2 — what to do with a child that dies, and with a second one. (needs V1.1)**
The bridge's failure story, which the console's own long-lived-reader contract already solves for the other child: a supervised child (console `docs/json-contract.md` §10.11 — "Does option A need a supervisor process? Yes"), a re-spawn that is **visible** rather than silent, and a rule that there is exactly one bridge child at a time. A bridge that dies mid-turn must not lose the screen's history, and must not respawn into a loop.
*Files:* `console/` (the supervisor, the tests), `docs/design/voice.md`.
*Verification:* the console's own test command, with a fixture child that exits on start, one that exits mid-stream, one that exits cleanly, and one that never exits.
*Independent merge:* yes.

**V1.3 — the producer check: is the operator's `claude` the one the parser knows? (needs V1.1) — SECURITY-SENSITIVE**
The design's U6: the stream shape this tree parses was read from a container's invocation of a **pinned** Claude Code, and the operator's PATH may hold a different version. This task asserts the parsed events match against a recorded transcript and **refuses a producer the parser does not know** — the same shape as the console's version-skew handshake (console plan phase 3), applied to a second child. The refusal is visible and non-destructive: it stops the bridge, it does not guess.
*Why security-sensitive:* a parser that accepts an unknown producer is a parser that will happily mis-report what it did not understand, and here the misunderstanding is spoken aloud (constraint 13).
*Files:* `console/` (the version probe, the recorded transcript, the refusal), `internal/agent/stream.go` if a shape is genuinely missing (a CLI-side change, in a CLI-shaped PR — and if it is, it says so rather than smuggling it in).
*Verification:* the console's own test command, plus a fixture stream in an unknown shape that must be **refused**, not rendered.
*Independent merge:* yes.

**V1.4 — the injection probe. (needs U1 settled; **OWNER-RUN**)**
Design F33 and U1: whether a Claude Code hook can inject a user turn into an already-running interactive session is a question about Claude Code, not about this repository, and nothing in this tree answers it — no hook is registered anywhere, and the tree's posture is that hooks are a hazard it warns about (`internal/pluginwire/notices.go`'s `settingsNotices`, and `plugin/skills_lint_test.go`'s rejection of a `hooks:` key). **This task is a probe, not an implementation**: the owner registers a `UserPromptSubmit` hook in their own settings on their own machine, runs an interactive session, and reports whether the hook can supply input. The result is written into [voice.md](../design/voice.md) §6 as a settled fact either way.
*Files:* `docs/design/voice.md` (U1's row, answered).
*Verification:* the docs suite (`GOFLAGS=-p=2 go test ./internal/cli -run 'Docs|Lint' -count=1`) — and the *evidence* is the owner's report; **no agent runs an interactive Claude Code session.**
*Independent merge:* yes.
*Why this is a task and not a question:* nothing in phase V1's other tasks or in phase V9 may depend on it until it is settled, and building a socket and a protocol for a capability that may not exist is the worst kind of work.

### Phase V2 — the digest

**V2.1 — `EventDigester` over `FugaroSource`. (needs D39, D48)**
Findings F2, F3 and F11: the digester is a **classification layer over `fugaro watch --json` documents**, behind the console's existing `FugaroSource`, and it must not recompute what the CLI computes (the burn rate is `watch`'s own five-minute window: `internal/watch/json.go`'s `JSONBurn.USDPerMin`). Grouping by project, a rolling window since the last digest, and a severity classification from the fields that exist — `JSONKill{By, At, Reason}`, `JSONFinished{Failed, Status, Outcome}`, `JSONTotal.Percent`/`JSONRepo.Percent`, `JSONBurn.FastAlert`, and `JSONConn` for a feed that is down.
*Files:* `console/` (the digester, its fixture, its table-driven test), `console/docs/json-contract.md` if a field is genuinely missing (and then the fix is a CLI task, console Global Constraint 1).
*Verification:* the console's own test command, table-driven over the console's own **eight named fixture cases** (console design §9.1) — the kill-flip and at-cap cases are this feature's severity table.
*Independent merge:* yes.

**V2.2 — the interrupt policy, as a pure function. (needs V2.1, D48)**
The three modes (`quiet`, `important`, `all`), the 60-second batch floor, the "never interrupt while the user is speaking — wait for a gap" rule, and the one-line headline. It is a **pure function from a digest and a clock to a decision**, which is what makes the spec's first acceptance criterion ("no task-status message is ever spoken inline unless the interrupt policy allows it") an assertion rather than an opinion. **`important`'s "anything awaiting user input" trigger is not implemented** (design F3: no state in this tree carries it) and the task says so in the code's own comment, so the omission is visible rather than forgotten.
*Files:* `console/` (the policy, its tests), `docs/design/voice.md` if the trigger is later defined.
*Verification:* the console's own test command, including the negative case: a `quiet` mode that speaks **nothing** over a fixture containing a failure and a kill.
*Independent merge:* yes.

**V2.3 — the cap-near threshold, as a local setting. (needs D48) — SECURITY-SENSITIVE**
The console v2 reconciliation's D35, unchanged: a read-side computation over figures the CLI already prints (`internal/watch/json.go`'s `JSONTotal.Percent`, `JSONRepo.Percent`), with the threshold a **local setting of the app**, and the existing rate alert (`internal/localcfg/localcfg.go`'s `BurnAlert()` into `internal/cli/watch.go`'s `watch.Config{BurnAlertPerHour: …}`) left exactly as it is. It never sums across installations and it says how fresh the figure is.
*Why security-sensitive:* an alert is a claim about money, and a spoken one is a claim nobody can re-read before acting on it.
*Files:* `console/`, `docs/design/voice.md`.
*Verification:* the console's own test command, plus a fixture with two installations whose figures must appear as two rows and never as one total.
*Independent merge:* yes.

### Phase V3 — the summary

**V3.1 — the `Summarizer`, with a fake model. (needs D45)**
The spec's §6 output rules (1–3 short spoken sentences, no code/paths/URLs/hashes/tables read aloud, numbers spoken naturally, end with the question if there is one, never invent anything not in the reply) as a system prompt and a post-check, with a **fake model** in tests and the real call behind an interface. The post-check is the part worth reviewing: "never invent anything not in the reply" is not enforceable by a prompt alone, so the task states exactly what is checked (the identifiers, numbers and proper nouns in the output must appear in the input, with the rounding rules applied first) **and what is not** — a mechanism that catches the understandable failure, not a claim that it catches every one.
*Files:* `console/` (the summarizer, the fake, the tests), `docs/design/voice.md`.
*Verification:* the console's own test command, with a fixture reply containing a diff, a path, a URL and a table, and a golden assertion on the spoken text.
*Independent merge:* yes.

**V3.2 — the headless implementation, and what it costs. (needs V3.1, D45, D42) — SECURITY-SENSITIVE**
The real summarizer runs as **a second headless child under the operator's own login** (design D45's recommendation), so there is no new key and no new credential anywhere — and the app states on screen and in `console/README.md` that **this call is not charged against any Fugaro cap and will not appear in `fugaro budget show`**. The disclosure is the task, not a footnote to it: `SECURITY.md`'s posture is "the backstop is the provider account's own limit", and a spend that escapes the caps silently is the thing to refuse.
*Why security-sensitive:* it is a second model call with a real cost, under an identity the app does not own, whose output is spoken aloud (constraint 13).
*Files:* `console/`, `console/README.md`, `docs/design/voice.md`.
*Verification:* the console's own test command, plus a test that the disclosure string is present **and that no provider key is read on this path** (a fake that fails the test if any environment variable matching a key-shaped name is touched).
*Independent merge:* yes.

**V3.3 — "more detail" and "read it". (needs V3.1)**
The two follow-up commands of the spec's §6: re-summarize the same reply at ~3× length, and read the reply's prose skipping code blocks. Both are properties of text the app already holds — no new call for "read it" — and "read it" needs a code-block splitter that is tested against fenced blocks, indented blocks and a block with a language tag.
*Files:* `console/` (the splitter, the re-summarize path, the tests).
*Verification:* the console's own test command, with a fixture reply whose code blocks must not reach the speaker.
*Independent merge:* yes.

### Phase V4 — ears

**V4.1 — `AudioIn`, `SpeechToText` and the fakes. (needs D46)**
The two interfaces exactly as the spec's §4 declares them, with **fake implementations from this task** so that everything downstream is testable before a device is opened: `AudioIn` (capture, VAD, end-of-turn, a barge-in signal) driven by synthesisable sample frames, and `SpeechToText` (streaming transcription) driven by a scripted transcript. That is a §5.1 hard-rule change and is written as a **new** decision row beside the old rule, not as an edit to a merged document.
*Why security-sensitive:* it is the first permission the app has ever asked for, and the renderer's two properties — no network, no permission — are what §5 exists to hold.
*Files:* `console/`, `docs/design/desktop-console.md` (a new row; the merged text is not edited), `docs/design/voice.md`.
*Verification:* the console's own test command, plus a test that `connect-src 'none'` is still in the CSP and that the permission handler grants nothing else, plus `GOFLAGS=-p=2 go test ./internal/cli -run 'ConsoleBoundary' -count=1`.

### Phase V5 — a mouth

**V5.1 — `TextToSpeech` and `AudioOut`. (needs V4.1, D46)**
The two remaining interfaces, behind fakes in tests. Streaming, **cancellable mid-utterance** (the spec's §4 requires it and the barge-in budget depends on it), with the ~300-millisecond stop budget asserted **in CI against the fakes** — constraints 13's rule that a spoken claim is traceable applies to the cancellation too: a cancelled utterance must not be reported as spoken.
*Files:* `console/` (the interfaces, the fakes, the implementation, the tests), `docs/design/voice.md`.
*Verification:* the console's own test command, with a stop-during-utterance fixture whose measured cancellation latency must be under budget, and a test that a cancelled utterance is not recorded as delivered.
*Independent merge:* yes.

**V5.2 — echo cancellation, or an honest statement that there is none. (needs V5.1) — SECURITY-SENSITIVE**
The spec's §5 asks for "echo cancellation so the assistant's own speech isn't transcribed". Whether that is the platform's, the provider's or ours is a property of the choice made in V4.4, and the failure mode is specific: without it, the assistant's own speech becomes a user turn, which becomes an agent turn, which is a loop that costs money and says nothing. The task implements whichever mechanism the local choice offers and, if there is none, **suppresses capture while playing and says so** — a barge-in that requires the user to speak slightly louder than the machine is a worse experience than a documented half-duplex turn, and it is the honest one.
*Why security-sensitive:* the loop's blast radius is spend.
*Files:* `console/`, `docs/design/voice.md`.
*Verification:* the console's own test command, with a fixture in which the assistant's own output is fed back into `AudioIn` and must **not** produce a user turn.
*Independent merge:* yes.

### Phase V6 — the controller

**V6.1 — the state machine. (needs V1.2, V2.2, V3.2, V4.1, V5.1)**
The `VoiceController` of the spec's §4: one state machine tying the seven components together, owning the interrupt policy and the voice commands. Written as an explicit state machine with an explicit table of transitions, because the interesting failures are all transitions: speech during playback, a digest arriving mid-turn, a child dying mid-turn, a turn cancelled during transcription.
*Files:* `console/` (the controller, its transition table, its tests), `docs/design/voice.md`.
*Verification:* the console's own test command, table-driven over the transition table, with every illegal transition asserted to be a **refusal**.
*Independent merge:* yes.

**V6.2 — the voice commands that are not writes. (needs V6.1)**
`status`, `repeat`, `more detail`, `read it`, `stop`, `mute`, and the interrupt-mode switches — all local, none sent to the agent, and each a **fixed, low-confusability phrase** with its own confidence floor, because a misheard `mute` is an annoyance and a misheard `stop` is a privacy event (the microphone stays open). `mute` is by button and by global shortcut as well as by voice, and unmuting by voice is **not** implemented (the spec defers it to wake-phrase support, which is a non-goal for v1).
*Files:* `console/` (the command table, the tests), `docs/design/voice.md`.
*Verification:* the console's own test command, with near-miss transcripts (`stats`, `muted`, `stops`) that must **not** fire a command, and a test that `mute` takes effect before the next capture frame is consumed.
*Independent merge:* yes.

**V6.3 — destructive commands: the design, and the refusal to ship them here. (needs D47) — SECURITY-SENSITIVE**
Design D47's recommendation, made concrete and made **a refusal**: v1 ships the shape D2 already chose for its deferred writes — the console shows the **exact command**, copyable, and the operator runs it, with the CLI's typed confirmation and its admin check (`internal/budget/kill.go`'s `AdminDeniedText`) intact. **No voice path to a kill switch, a cancel or a merge exists in this plan.** If the owner later wants one, this task's document is the design it must satisfy, and the rule is stated so it cannot be designed away: **the confirmation must be a different act from the command, and the same misrecognition must not satisfy both** — the read-back names the run id or the argv rather than a paraphrase; the confirming utterance is a fixed short phrase rather than "yes"; it is recognised by a second independent pass with its own confidence floor; and the thing that executes is the CLI's own command, so the CLI's confirmation and admin check stay in the path.
*Why security-sensitive:* every alternative here ends in a merge or in a repository's spend being killed by a misrecognition.
*Files:* `console/` (the command display, the tests), `docs/design/voice.md`.
*Verification:* the console's own test command, plus a test that **no** spawn of `fugaro cancel`, `fugaro budget kill` or any merge verb exists in the app's tables — the same mutation-proof shape as V1.1's never-list.
*Independent merge:* yes.

### Phase V7 — cloud providers, only if the owner says yes

**V7.1 — the provider clients and the egress policy. (needs D44 and an owner answer beyond it) — SECURITY-SENSITIVE**
The cloud STT/TTS paths, behind the same interfaces, plus the policy that governs them: a **console-local list whose semantics are copied verbatim from `config.ModelProvider.AllowDataTo`** (absent or `["*"]` means every project, `[]` is refused as ambiguous, a real list is the opt-in), with the unit being **the project** rather than the repository, because what leaves the machine is the operator's own speech and the agent's replies about a project — and because `allow_data_to` does **not** cover this today (design F23). The task says that in `console/README.md` in as many words, so no reader assumes the existing key covers it.
*Why security-sensitive:* this is the only task in the plan that sends a person's voice off the machine, and the promise it breaks by accident is console §7.4's "your machine stays your business".
*Files:* `console/` (the clients, the policy, its tests), `console/README.md`, `docs/design/voice.md`.
*Verification:* the console's own test command, with the policy's four states (absent, `["*"]`, `[]`, a list) each asserted, and a test that with an empty or `[]` policy **no client is constructed at all**.
*Independent merge:* yes, and it is the only task in this phase.

**V7.2 — the privacy write-up, and the provider's own policy. (needs V7.1)**
Design F37 and `docs/multi-model.md`'s rule for the one provider case this tree already has: *"`require_zdr` is a price, not an enforcement — Fugaro cannot read your account's data policy."* The same will be true here, and the console cannot verify what a provider retains. This task writes down, for each configured provider, **what is sent, who sees it, what the provider's own policy says and that Fugaro cannot check it** — the honest form of the sentence, in the document the operator reads, rather than a claim the code cannot support.
*Files:* `console/README.md`, `docs/design/voice.md`.
*Verification:* the docs suite plus the console's own test command; and a review criterion: every claim in the write-up names its source or is marked unverifiable.
*Independent merge:* yes.

### Phase V8 — the packaged ask

**V8.1 — the microphone entitlement and the prompt. (needs V4.2, D51) — SECURITY-SENSITIVE — OWNER-RUN (the signing steps)**
Design D51: `NSMicrophoneUsageDescription` in `Info.plist` is mandatory (without it the process is terminated on first capture), and `com.apple.security.device.audio-input` is added **only if** the chosen packaging (console D4's hardened runtime and plan Task 4.1's entitlements file) needs it for the chosen mechanism. Both are "an entitlement the app demonstrably uses", so console D4's rule is satisfied rather than bent — and the app's first run stops being "a read-only dashboard with no permission dialog", which is the thing worth stating in the PR. The prompt is tied to a visible session start, never to launch. **The agent writes the files; the owner runs every signing and notarisation step** (console D4: the owner holds the certificate).
*Why security-sensitive:* this changes what the app is, on the platform where the app is distributed, with a key the owner holds.
*Files:* `console/` (the entitlements, the `Info.plist` fragment, the builder configuration), and the workflow text **staged under `docs/pending-workflows/`** for the owner to copy — never a file under `.github/workflows/`.
*Verification:* the console's own test command plus the packaged-build test the console plan already defines; the signed build itself is the owner's step and Check 61.
*Independent merge:* no — it depends on the console plan's phase 4 packaging existing.

**V10.1 — a design of its own, not a task. (needs D49)**

## 4. The owner-run check: Check 61

**Check 61 (OWNER-RUN, NOT RUN)**, in [docs/gcp-live-checklist.md](../gcp-live-checklist.md), on the **sandbox installation** (`fugaro`) and the sandbox repository only — **never the `belong` installation**. Written with FACT lines, a restore step and **Check 43's full guard verbatim** (three hard stops, `--project fugaro` on every `fugaro` command, `--project "${P:?}"` on every `gcloud` command, the block re-run from a fresh shell before every step).

**In outline**, and only for the phases built by then:

1. **the bridge**: start a session in the console, send one turn, and read back from the spawn log (`FUGARO_CONSOLE_SPAWN_LOG`, console D20) the exact argv of the `claude` child and of the `fugaro` child — both tables, and neither carrying an argument outside its table;
2. **the digest**: with the kill switch flipped and a repository at its cap in the sandbox, the digest names both from the documents the CLI printed, and a `quiet` session speaks neither;
3. **the ears and the mouth**: a short hands-free exchange — one turn spoken, one reply summarized and spoken, one barge-in — with the measured latency numbers written into the check's FACT lines (this is the half that **cannot** be tested in CI: design D52);
4. **the permission**: on a freshly installed signed build, the microphone prompt appears **on session start and not on launch**, and refusing it leaves the app fully functional and silent;
5. **the restore step** removes every object and every local file the check created, deletes the spawn log it asked for, and leaves the sandbox installation as it found it.

**This check cannot be written until the tasks it exercises are approved and built** — which is what the owner approval gate at the top of this document means. Its number is reserved now so that the reservation is not a decision taken in a hurry later; §2 says what to do if the number has moved.

## 6. Cross-task dependencies

Stated so a reviewer can check the claim that each task is independently mergeable:

- **V1.1 → everything in V1, V2, V3, V6.** The bridge is the conversation half; nothing speaks an agent reply before there is a bridge that produced one.
- **V1.4 → V9.1's hooks half, and nothing else.** The probe's result decides whether a second `AgentBridge` implementation is buildable at all; no other task may depend on it (design F33, U1).
- **V2.1 → V2.2 → V2.3.** The policy and the threshold are functions of the digest's classification.
- **V3.1 → V3.2, V3.3.** The post-check and the output rules come before the real call and before the follow-ups.
- **V4.1 → V4.2, V4.3, V4.4, V5.1.** The fakes are what makes the permission task, the fixtures and the mouth testable.
- **V5.1 → V5.2, V6.1.** There is no echo to cancel and no playback to barge into until something speaks.
- **V4.2 → V8.1.** The entitlement is the packaged form of the permission the capture path needed; which entitlement, exactly, is V4.2's finding (design U2, D51).
- **V6.1 → V6.2, V6.3.** The commands are transitions in the state machine.
- **V7.1 → V7.2.** The write-up describes the clients that exist.
- **V8.2 → V8.1 and the phases it exercises.** The check cannot be written before there is something to check.
- **Everything → the owner approval gate, and D39/D40/D41/D42 first.** This is the dependency that matters and it is the first one, not the last.

## 7. What this plan does not do

- **It does not reopen the console.** Phases 0–5 of [2026-10-15-desktop-console.md](2026-10-15-desktop-console.md) and decisions D1–D20 of [desktop-console.md](../design/desktop-console.md) stand as they are. Where this work moves one of their invariants — §3.4 rule 1 (V1.1), §5.1 rule 9 (V4.2) — it writes a **new** sentence or decision row beside the old one, in this plan's or the design's own document, and says so.
- **It does not depend on PR #426.** The console v2 plan is open and unmerged; nothing here needs it, and if its own numbering (D21–D38, Check 60) changes on merge, only §2's ruling and [voice.md](../design/voice.md) §2's paragraph are affected.
- **It does not ship a write.** The only writing process in the whole plan is the spawned `claude` child, decided explicitly in D40; every destructive act is deferred to the CLI and its own confirmations (V6.3).
- **It does not ship a credential.** No key, no token, no account: with D40's and D45's recommendations the app holds nothing and the child resolves the operator's own login, exactly as `fugaro` resolves their ambient gcloud identity.
- **It does not touch the realtime database, its rules, or the mobile relay.** No rules change, no new node, no new backend, no service account (console Global Constraint 1). The one phase that would is V10, and V10 is a design with six questions, not a task.
- **It does not add a workflow file.** Any workflow a later phase needs is staged under `docs/pending-workflows/` and applied by the owner.
- **It does not run anything live, and no agent-run step in it touches a secret.** The sandbox installation is the only one any of it runs against, and `belong` is never touched.
