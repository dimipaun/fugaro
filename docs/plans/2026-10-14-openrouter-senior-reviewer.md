# A senior reviewer through OpenRouter: implementation plan

**Goal:** put a **stronger senior reviewer inside the cheap-coder loop**, served by a provider route rather than by Anthropic directly, in the two phases the design's §10 sets: **Phase 1**, a non-Claude senior (GPT, Gemini, a larger DeepSeek or Qwen) — which works with the code as it is, so it is documentation, two missing tests and one live check; and **Phase 2**, the owner's approved opt-in that lets a provider route claim **one explicit `anthropic/<id>`**, which is the small change to M10's "Claude goes direct" rule that the design's §4 rules in and §9 lists the tests for. No code in this plan has been written or run; this is a design-to-code plan. **This PR (the one that adds this plan) is docs-only: no Go, Terraform or product-behavior file in this plan's "Files" lists is touched by it. The one exception is `docs/gcp-live-checklist.md`, which this PR itself edits, because reserving Checks 45 and 46 and writing their not-yet-run steps is a docs-only act; Tasks 3 and 9 are the tasks that maintain that file.**

**Gating, said once (P1, D6):** **Phase 1 is gated on nothing** — it is two documents, two tests and a check, and it must not wait for any answer. **Phase 2 is gated on the owner's ruling, which is given** (2026-10-14) and which this plan implements. The design's §8 open questions gate **conclusions, not work**: question 1 (`docs/design/mixed-credentials.md:118`: *is a non-Claude senior acceptable as the first step, before any Claude senior?*) is what Check 45's by-hand comparison supplies evidence for — the owner rules it, the check does not — and the §4 cache-marker question is what Check 46 measures. Nothing in this plan waits on either answer, and no task may be deferred for want of one.

**Spec:** [docs/design/mixed-credentials.md](../design/mixed-credentials.md). Its owner rulings of 2026-10-14 (§1, §4, §8) are settled: an explicit opt-in is enough, the claim lives in the local operator config or the shared project layer, a repository may choose the model but never add or enable a route, and `allow_data_to` still decides which repositories may send code. Its Path A (Claude behind the gateway with an Anthropic key) is **not** in this plan: the owner has no Anthropic key, so §10 puts it behind whichever credential exists. This plan is §10's Phase 1 (non-Claude senior) and Phase 2 (the opt-in); Path B (the OAuth reviewer stage, §5 and §10 phase 3) is deliberately absent.

**Depends on:** release 0.7.x on `main` (the M10 route table, the budget gateway, `internal/pricing`, the first-line review and the project layer are all merged). [docs/design/provider-price-catalog.md](../design/provider-price-catalog.md) is **not** a prerequisite but is coupled on two points, both stated at the task that touches them: its D8 generator check and its §11 Phase 2 add the three `anthropic/<id>` catalog rows, which can only pass its own `IsAlias` guard once this plan's Task 4 has relaxed it (P11), and under P4 that is the **only** coupling — no claimed-set argument ever reaches the generator.

## Decisions (veto any before execution starts)

- **P1. Phase 1 ships no product code, and a task that finds itself editing Go outside `_test.go` stops and reports.** Everything a non-Claude senior needs exists and was verified above: the route table, `CheckProviderPolicy`, the pins, the price table, the gateway, `allow_data_to`, the ≥4-byte placeholder key, and `auto` turning the cheap first line off for the derived recipe. Phase 1's deliverables are one user-doc section (Task 1), the two tests nothing covers (Task 2) and Check 45 (Task 3). Gating is settled once in the header: Phase 1 waits for nothing.
- **P2. Phase 1's test work is exactly two tests, and this plan names the four that already cover the rest so a task does not write them again.** (a) `internal/gateway`: one stage, one Claude call and one routed call, asserting `rep.ByModel` for **both** models and `rep.Used` as their sum at their own rates, with **different** usage so a swapped rate shows in the per-model numbers. The smallest honest way to do it is to extend `TestRouteRecordedPerCall` (`provider_settle_test.go:373`) — same shape, same stage, both calls — rather than to build a fifth fixture. Do not re-assert what `TestRouteByModel`, `TestNoFeeOnClaudeCalls` and the existing `ByRoute` assertions already cover. (b) `internal/runner`: an `auto` run with the provider on **both** the coder and the reviewer — the case nothing covers — asserting `implement, review` with no `review_first`, `tier: senior` on every review, and the reviewer stage's `ProviderRouteVars`. **Both roles must be provider-served**: `FirstLineOn` is `claimed(coder) && !claimed(reviewer)`, so a Claude coder turns the line off for the coder's own sake and the fixture would stay green if the reviewer clause were deleted. No **runner-level** test has a provider reviewer today (the config-level table does have the predicate: `TestFirstLineReviewAutoOnlyForProviderCoder`, `internal/config/firstline_test.go:42`, whose `auto, provider reviewer too` row at `:53` is the reviewer clause).
- **P3. The opt-in is one literal `anthropic/<id>` entry in a route's `models`, and the entry itself is the whole permission.** `CheckModelPattern` accepts an entry overlapping `anthropic/*` only when it contains no `*` and is a plain provider model ID under that prefix; `anthropic/*`, `anthropic/claude-*` and every bare `claude-*` entry stay refused, with today's message verbatim. *Veto alternative:* a boolean on the provider — rejected by the owner's ruling (one explicit ID, not a class).
- **P4. The pricing package stays claim-blind; the opt-in changes what an alias *is*, not who may pin what.** `IsAlias` keeps its signature and every rule except one: an `anthropic/`-prefixed value that is a well-formed provider model ID (`providerIDRE`) is **no longer an alias**, because under the opt-in it is a real model ID — and a price table that refuses to key it would make a claimed ID unpriceable in the very path the opt-in needs. The gate on *pinning* moves nowhere near pricing: it lives where the routes are (P5). This is the decision that makes the phase small, and it is why there is no claimed-set parameter, no `Table.With(o, claimed)`, no `ParseOverrides(s, claimed)`, no reordering of `internal/cli/exec.go:95-96`, no `validateBudget` signature change, and no change to `internal/cli/upgrade_cloud.go:377-378`, whose two `ParseOverrides` calls diff two deployed price maps and care about keys, not about who may route them. *Vetoed alternative (the previous draft of this plan):* `IsAlias(model, claimed []string)`, with the claimed set threaded through five call sites, `Table.With`, `ParseOverrides`, `Env`, `localcfg.Overrides`, `SpendFromEnv`, `CheckPins` and `CheckModelID`. It was rejected on evidence: the price and allow-list environment is parsed in `internal/cli/exec.go:95-96` **before** the runner ever sees the task spec's project layer, `internal/localcfg` and `init --repo` have no layer concept at all, and `internal/pricing` cannot ask `internal/config` — so a layer-only claim could not be priced or validated without inventing a second source of truth for the claim. The claim-blind design has none of those problems and is strictly narrower in code.
- **P5. The claim gate is `internal/config`'s, in the three places that already hold the providers map:** `CheckModelPattern` (a route entry, P3), `ProviderFor` (routing, unchanged — a model no route claims is not routed), and `CheckProviderPolicy` (every pinned role, `agent.model`, and every `budget.allowed_models` entry). No claimed-ID list is computed, stored or passed: `CheckProviderPolicy` asks `claimed(providers, model)` directly. The runner runs it on **every** launch, before the gateway starts and before any call (`internal/runner/gateway.go:401`), and `fugaro validate` runs it too (`internal/cli/validate.go:182,184`), so an unclaimed `anthropic/<id>` is refused at both surfaces with **no new plumbing**.
- **P6. `CheckPins` does not change at all.** Under P4 its alias branch simply stops firing for `anthropic/<id>`, and the refusal is `CheckProviderPolicy`'s, which is the better home for two reasons: it can tell a claimed ID from an unclaimed one (the pins cannot without a providers parameter), and a provider-less project still gets the refusal (the branch is not conditional on there being providers). The price half of `CheckPins` still does its job: a claimed ID with no price anywhere is refused with "has no price: add it under model_prices in the project config". *Veto alternative:* give `CheckPins` the providers map so the pin surface refuses too — rejected as a second refusal of the same thing, in the surface that cannot name the fix. `fugaro validate` still prints the `CheckProviderPolicy` problem at the pin's own path, so an owner sees `agent.models.reviewer` either way.
- **P7. The first slice is the **operator config**; the shared project layer is a separate task (Task 7), staged honestly and not pretended.** The owner's ruling allows either place, so the ruling is satisfied in two slices, in this order, and **both documents say which slice they describe** (Task 8). Why the layer cannot ride along: the layer arrives in the runner's *task spec*, while the CLI's own surfaces (`fugaro validate`, `config show`) and the environment paths resolve from the operator config only, so the layer needs (a) the runner merge in `(*run).resolveConfig` (`internal/runner/runner.go:1242`) with every `r.d.Providers` reader switched to the merged map, (b) the CLI's existing checkout-layer resolution (`resolveFugaroYAML`, `internal/cli/layer_resolve.go:285`) taught to apply the claim where it feeds the provider checks, and (c) a decision that the claim is **never** written into `FUGARO_MODEL_PROVIDERS` — see Task 7, which lists all three with their evidence. Nothing in Tasks 4-6 depends on Task 7, and Task 7's tests are the only ones that may touch the layer.
- **P8. The layer may only add explicit entries to a route the local config already defines; it can never create one.** `base_url`, `auth`, `secret` and `allow_data_to` stay with the operator, so a layer cannot make a route appear, point one at another host, or widen who may send code; a name the local config does not define is refused, naming it. A repository's `fugaro.yaml` cannot carry the key at all (P7's structural reason: a top-level layer key is not a `Config` field, and `Resolve` decodes into `Config` with `KnownFields`).
- **P9. `auto` turns the cheap first line off for the **derived** recipe only, and every document says exactly that — naming the recipe, not only the setting.** `planOf` skips the step when `derived && !FirstLineOn(providers)` (`internal/runner/plan.go:35`), and `derived` is narrower than "the default recipe": it is `rrec.Name == recipe.DefaultName && rrec.Source == string(recipe.SourceCatalog)` (`internal/runner/runner.go:940`), the catalog's `default` and nothing else. So with a provider-served senior under `first_line_review: auto` the **derived** run is `implement, review`, while **every other recipe keeps its own steps whatever `auto` says** — the catalog's `standard` (`internal/recipe/catalog/standard.yaml`) carries both `first_line: {}` and `review: {bounce: first_line}`, so it still runs a cheap line and its bounce is reachable (`internal/runner/runner.go:1448`). Because that is a property of the **recipe** and not of a setting, `first_line_review: on` on a `default` run is **not** its witness: that is the setting path, it turns the derived step back on, and it would stay green if `plan.go`'s `derived &&` were dropped or widened. So each document says its half in its own terms: Task 1 step 2 for the owner (the default recipe loses the line; a recipe that names its own keeps it), Task 2 step 2 for the code (`auto`, derived), and **Check 45 with a named recipe** — step 4 runs the catalog `default`, step 6 runs a catalog recipe that is not the default (`standard`). *Veto alternative:* make the derived rule apply to explicit recipes too — rejected: it would silently drop a step the owner wrote.
- **P10. A claimed Claude model is a provider model in every respect, and nothing is special-cased for it.** Its stage gets `ProviderRouteVars` (thinking and the experimental betas off), its background requests follow `EffectiveBackground` (the coder's model when `agent.models.background` is unset), it is charged at the route's price with `route_fee_pct`, it needs `agent.auth: api-key` (`CheckProviderAuth`: an oauth token is never sent to another provider) and `budget.mode: enforce` (`CheckProviderGateway`), and it is subject to `allow_data_to`. Note the background nuance: `stageOnProviderRoute` looks at the role's model **and** the background (`internal/runner/agentenv.go:71-78`), so a Claude role on a provider-coder run gets the variables too when the background is routed or unset. *Veto alternative:* exempt a claimed Claude model from the provider-stage variables so it keeps thinking — rejected: the fields Claude Code adds when thinking is on are the ones the route's field allowlist refuses (Check 25 step 4), so the exemption would trade a working call for a 400.
- **P11. The catalog's `anthropic/<id>` rows and this plan's Task 4 land in the same release, in either order, and nothing is threaded between them.** What the owner gets meanwhile, and what it costs: the claimed ID lives as a `model_prices` **override** row only, so every field the catalog would carry and the override cannot is at its zero value — an **image** request on that model is refused (`ImageTokens <= 0` means "this model takes no images") and a **PDF** reserves the default context rather than the model's real one. That is the right trade for an opt-in senior reading diffs, and Task 8 step 1 says it in one sentence so the owner is not surprised by it.
 Its D8 generator check refuses an allowlisted ID `IsAlias` rejects; under P4 the relaxation is inside `IsAlias` itself, so the generator needs **no** argument and its `TestGeneratorRefusesIsAliasKey` keeps refusing everything else. `internal/pricing/table_test.go:24` stays green either way, and a folded `anthropic/<id>` row passes its provider-ID expectations (`ImageTokens <= 0` is allowed because the ID contains `/`). Until the row lands, the owner prices the claimed ID under `model_prices` — accepted claim-blind (P4) in the operator config, from `localcfg` through to the runner's env parse.
- **P12. Check 46 leads with the refusal and ends with the `cache_read` comparison, because that comparison is the only open technical question this phase has.** M10 decision 2's reason for the direct rule is the prompt-cache markers; whether Claude Code's markers survive the Anthropic-compatible endpoint is unmeasured (design §4). A routed Claude senior that never reports a cache read is charged at the full input rate, so this is the difference between list price and several times list price. *Veto alternative:* judge the phase by review quality alone — rejected: the quality question is the owner's to answer, but the caching one has a **number**, and a number is what a live check is for.

## Global Constraints

From the design:
- One explicit `anthropic/<id>` per route entry, never a pattern (P3); with no such entry the "Claude goes direct" rule is unchanged and everything is refused exactly as today.
- A repository's own `fugaro.yaml` may choose the model (`agent.models.reviewer`) and can never add or enable a route (P5, P7, P8).
- `allow_data_to` still decides which repositories may send code: the opt-in changes which host sees the code, not who may send it.
- The claim lives in the local operator config (Tasks 4-6) or the shared project layer (Task 7), and in no other place.
- No new secret: the existing `anthropic-api-key` secret keeps its ≥4-byte placeholder role, and the provider's own key is the only one that reaches OpenRouter.

Project rules (carried over from this repository's existing plans):
- **One task, one commit.** Every task is a reviewable slice: its own Files, its own failing test first, its own command, and a commit that leaves the tree green. A step's test is written and watched **fail** before the code that makes it pass; where a step's test cannot be red first (a pure message change), the task says so at the step.
- Every task's test run is in the foreground, `-count=1`, with `-race` where the package's existing tests use it.
- Fakes only in tests: no real OpenRouter call, no real key; the hermetic fake upstreams in `internal/gateway/anthropicfake` are the pattern.
- Docs must match behaviour: `GOFLAGS=-p=2 go test ./internal/cli -run 'Docs|Lint' -count=1` stays green throughout. Phase 2 adds no `fugaro.yaml` key (the claim is a route entry and, later, a *layer* key), so `config.Scopes` and §5's table are not touched — but `docs/project-layer.md` is read from **two packages**, and a task editing it runs both: `internal/cli` (`TestDocsProjectLayerCommandsExist`, `internal/cli/docs_project_layer_test.go:34`, selected by the command above) and `internal/config` (`TestScopeTableMatchesDocs` and `TestExecutableKeysMatchDocs`, `internal/config/docs_scope_test.go:14,38`, which the `./internal/cli` command **does not select** — a task that edits §5's table runs `GOFLAGS=-p=2 go test ./internal/config -run 'ScopeTable|ExecutableKeys' -count=1` as well).
- `fugaro verify build` / `fugaro verify test` are the only build and test entry points for this repository's own conventions; a task runs them before it is considered done.
- Checks 45 and 46 are the owner's own tasks, run once each, **sandbox project and sandbox repository only, never the `belong` project, and no agent runs any step of either**.

## Review Focus (mutation-proof notes)

1. **An `anthropic/<id>` a route does not claim becomes pinnable.** Pinned by `TestUnclaimedClaudeIDStillRefused` (Task 5, config) plus its run-level twin (Task 6, a run refused before any call, the shape `TestNoCallBeforeRefusal` uses, `internal/runner/provider_policy_test.go:76`), and by the unchanged `want true` entries of `alias_test.go` other than the two the opt-in moves.

The rule reuses `providerIDRE` through an exported helper, so a spelling the pricing grammar rejects cannot be a claim.
