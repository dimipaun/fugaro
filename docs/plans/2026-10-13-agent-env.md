# Agent env: implementation plan

**Goal:** Let a repository's `fugaro.yaml` set a small, allow-listed set of
environment variables on the Claude Code process itself (`agent.env`), and
let the owner set the same kind of variable, scoped to a model provider's
own stages, in the local config (`providers.<name>.agent_env`), with
built-in defaults for the provider-routing quirk that motivated this design
— without adding a single new way to redirect model traffic, proxy it,
preload code, or touch anything `ReservedEnvPrefixes`/`ReservedEnvNames`
already protect. No code in this plan has been written or run. **This PR
(the one that adds this plan and its design doc) is docs-only: no file
under this plan's "Files" lists is touched by it.** Tasks 1 onward are
future work, gated on the owner ruling on the design doc's §7 open
decisions (D1-D5) before any task starts.

**Spec:** [docs/design/agent-env.md](../design/agent-env.md). Its decisions
(§2's scope and allow-list shape, §3's provider-scoped mechanism and
precedence order, §4's surface boundaries) are settled there; this plan's
own decisions continue the same letter, E1 onward, each independently
vetoable.

**Depends on:** nothing from the 0.7.0 bucket-IAM or base-image work
(design §8); only ordinary merge-conflict hygiene with whichever other
change to `internal/config/config.go`, `validate.go` or `scope.go` lands
first. **Not gated on any live check before it ships**: §2's v1 scope sets
process environment variables Claude Code already documents reading, and
§3's built-in defaults are a cited, already-observed fix (design's origin
story), not a speculative one. Design §6's live checks confirm the shipped
feature; none of them block the PR that ships it.

## Decisions (veto any before execution starts)

Continuing the design doc's D1-D5:

- **E1. One shared validation function, `validateAgentEnvMap`
  (`internal/config/validate.go`), used by both `agent.env`'s `Validate`
  call site and `ModelProvider.AgentEnv`'s `ValidateModelProviders` call
  site.** *Veto alternative:* duplicate the check in `providers.go`;
  rejected because the allow-list and shape rules must stay identical by
  construction (design §3: "a provider cannot set anything a repository
  couldn't set either") and a single function is the only way a future
  edit to one can't silently diverge from the other.
- **E2. `agent.env`'s values enter `BuildEnv` as a new `EnvSpec.AgentEnv
  map[string]string` field, copied into `out` immediately after `baseEnv`
  and before `spec.Secrets`, `spec.Set` and the gateway's own vars** (not
  as a change to `spec.Set` itself). *Veto alternative:* have the runner
  fold `cfg.Agent.Env` into the same `set` map it already builds at
  `runner.go:966-973` before calling `BuildEnv`; rejected because that map
  also carries git identity and Fugaro's own `FUGARO_STATE_DIR`/timeout
  variables, and mixing a repository-controlled map into it makes the "is
  this value repository-controlled or Fugaro's own" question harder to
  answer at a glance in `BuildEnv` itself — keeping it a distinct `EnvSpec`
  field keeps `BuildEnv`'s own ordering comment (`env.go:133-141`) honest
  about what each line is.
- **E3. The provider-scoped variant's managed-settings merge lives in
  `writeManagedSettings` (`internal/runner/agentenv.go`), reading a new
  per-stage argument, not a new standalone function.** *Veto alternative:*
  compute the provider's `agent_env` in a separate helper and have
  `beginGatewayStage`/`endGatewayStage` apply it directly to the gateway's
  own state; rejected because `writeManagedSettings` is already the one
  place that assembles "everything this stage's managed-settings file
  should contain" (gateway vars + pins today), and a second assembly point
  would need to agree with it on ordering by convention instead of by
  reading one function.
- **E4. `DefaultProviderAgentEnv` applies only to providers of kind
  `config.ModelProviderKind` ("anthropic-compat") — the only kind that
  exists (design §3) — keyed by provider kind, not hard-coded to "every
  provider," so a second kind added later does not inherit it by
  accident.** *Veto alternative:* key it to nothing (apply to every
  provider regardless of kind); rejected as a trap for a future kind this
  plan cannot foresee the needs of.

## Task 1: the Go struct, `Validate`, the schema, the scope row

**Files:** `internal/config/config.go`, `internal/config/validate.go`,
`internal/config/scope.go`, `schemas/fugaro.schema.json`,
`docs/project-layer.md` (scope table), `internal/config/testdata/config/`
(a new corpus fixture), `schemas/schemas_test.go`.

**TDD steps:**

1. Write failing tests first:
   - `internal/config/validate_test.go`:
     `TestAgentEnvAcceptsAllowedNames` (each name in `AgentEnvAllowed`
     parses clean with a valid value) and
     `TestAgentEnvRefusesUnknownName` (`agent.env: { ANTHROPIC_BASE_URL:
     "x" }` fails `Validate`, naming `agent.env.ANTHROPIC_BASE_URL`, not a
     generic "unknown key" message — the message must say *why*, per
     `validate.go`'s existing style for `agent.oauth_token`).
   - `internal/config/validate_test.go`:
     `TestAgentEnvRefusesBadValueShape` (a value with a newline, a value
     over 128 bytes, an empty value is **not** refused — "" clearing a
     default-ish entry mirrors the rest of `fugaro.yaml`'s "null/empty
     means not set" convention, but only matters once §3's defaults exist;
     for v1, document that an empty string is a valid, if useless, value
     rather than special-casing it).
   - `internal/config/reservedenv_test.go`-style new test,
     `TestAgentEnvAllowListNeverRoutes` (**flag for an opus-level review**:
     this test is the one piece of code that encodes §1's core safety
     claim, and a mistake here is a silent security regression, not a
     build failure): for every name in `AgentEnvAllowed`, assert it is
     never a routing key. `routingEnvKeys` and the `CLAUDE_CODE_USE_`
     prefix check live in `internal/agent/settings.go` today, but
     `internal/agent` already imports `internal/config` (`env.go:11`), so
     `internal/config` cannot import `internal/agent` back — an import
     cycle, not a style choice. Move the canonical list into
     `internal/config` instead (`config.RoutingEnvKeys` and
     `config.IsRoutingEnvKey(name string) bool`, beside
     `ReservedEnvPrefixes`/`ReservedEnvNames`, which already live there for
     the same reason: `internal/config` is the leaf package other packages
     read reserved/routing names from), and change
     `internal/agent/settings.go`'s `RoutingKeys` to call
     `config.IsRoutingEnvKey` instead of keeping its own copy — a
     refactor, not a behavior change; `internal/agent/settings_test.go`'s
     existing `RoutingKeys` tests must keep passing unmodified. Then
     `TestAgentEnvAllowListNeverRoutes` asserts
     `!config.IsRoutingEnvKey(name)` for every `AgentEnvAllowed` entry,
     with no cycle. **Do not** assert `AgentEnvAllowed` and `ReservedEnv`
     (`validate.go:84-87`) are disjoint — they are expected to overlap:
     `ReservedEnv` is the *secrets* deny-list (`CLAUDE_CODE_*` is reserved
     there for a different reason, design §0), not the routing list this
     test checks.
   - `schemas/schemas_test.go`: `TestFugaroSchemaReservesTheSameAgentEnvAllowList`,
     mirroring `TestFugaroSchemaReservesTheSameEnv`
     (`schemas_test.go:292-313`): walk the schema's `agent.env.properties`
     keys and assert they equal `config.AgentEnvAllowed` (as a set, order
     irrelevant, both sorted before comparing).
   - `internal/config/docs_scope_test.go`'s existing
     `TestScopeTableMatchesDocs` will fail once `scope.go` gets the new row
     and `docs/project-layer.md` doesn't yet — confirm this failure mode
     before fixing both together.
2. Make them pass:
   - `config.go`: add `Env map[string]string \`yaml:"env,omitempty"\`` to
     `Agent`.
   - `validate.go`: add `AgentEnvAllowed []string` (the design §2 list;
     owner rules on exact contents per D2 before this task starts) and
     `validateAgentEnvMap(path string, env map[string]string) []Problem`
     (E1), called from `Validate` for `agent.env` and, in Task 5, from
     `ValidateModelProviders` for `providers.<name>.agent_env`. Shape rule:
     `agentEnvValueRE` (printable, no control chars, no whitespace) and a
     128-byte length cap, mirrored from `validateAgentModels`'s pattern
     (`validate.go:442-456`).
   - `schemas/fugaro.schema.json`: `agent.env`, `additionalProperties:
     false`, one named property per allow-listed name with a matching
     `pattern`/`maxLength`.
   - `scope.go`: the new `ScopeRow` (design §2's exact `Why` text).
   - `docs/project-layer.md`: the matching table row, in `Scopes`'s order.
   - A `testdata/config` corpus fixture exercising `agent.env` (valid and,
     per `TestFugaroSchemaCorpus`'s existing shape, a refused case too).
3. Run: `go test ./internal/config/... ./schemas/... -run 'AgentEnv|Scope|Fugaro' -count=1`.

**Interfaces:**

```go
// internal/config/config.go, on Agent:
Env map[string]string `yaml:"env,omitempty"`

// internal/config/validate.go
var AgentEnvAllowed = []string{ /* design §2's list, owner-ruled */ }
func validateAgentEnvMap(path string, env map[string]string) []Problem
```

## Task 2: `BuildEnv` wiring and ordering

**Files:** `internal/agent/env.go`, `internal/agent/env_test.go`,
`internal/runner/runner.go` (the `EnvSpec{...}` construction at
`runner.go:992-994`).

**Flag for opus review**: this task edits the exact function (`BuildEnv`)
whose comment ("last, so nothing declared or inherited can override the
routing") is the load-bearing security guarantee of the whole agent
environment; an ordering mistake here is silent until a live run leaks a
routing override.

**TDD steps:**

1. Write failing tests first, in `internal/agent/env_test.go`:
   - `TestBuildEnvAppliesAgentEnv` — an `EnvSpec.AgentEnv` entry appears in
     the result.
   - `TestBuildEnvAgentEnvCannotOverrideSet` — `EnvSpec.AgentEnv` and
     `EnvSpec.Set` both name the same key; `Set`'s value wins (Fugaro's own
     values, e.g. `FUGARO_STATE_DIR`, always beat a repository's).
   - `TestBuildEnvAgentEnvCannotOverrideGateway` — `EnvSpec.AgentEnv`
     contains a `routingEnvKeys` name (even though `Validate` would already
     refuse this at the config layer, `BuildEnv` is the last line of
     defense per the design's "defense in depth" stance) and `EnvSpec.Gateway`
     is set; the gateway's own value wins. This test calls `BuildEnv`
     directly with a hand-built `EnvSpec`, bypassing `Validate` entirely,
     precisely to prove `BuildEnv` does not *rely* on `Validate` having run.
   - `TestBuildEnvAgentEnvCannotOverrideSecrets` — a declared secret and an
     `AgentEnv` entry share a name; confirm which wins and that the choice
     is deliberate (recommend: a secret's value wins, since secrets are
     narrower-scoped and more specifically declared; document whichever
     the implementer picks in `BuildEnv`'s own comment, since the design
     doc does not prescribe this exact sub-case).
2. Make them pass: add `AgentEnv map[string]string` to `EnvSpec`
   (`env.go:37-46`); in `BuildEnv`, after the `baseEnv` loop and before the
   `spec.Secrets` provider-key check (`env.go:58-78`), copy
   `spec.AgentEnv` into `out` — before secrets, before `spec.Set`, before
   the gateway vars, exactly mirroring the existing ordering comment's
   intent. Update the function's doc comment to describe the new
   precedence explicitly (don't just add code silently to a function whose
   whole value is that its comment is trustworthy).
3. Wire the runner: `runner.go:992-994`'s `agent.EnvSpec{...}` gains
   `AgentEnv: cfg.Agent.Env`.
4. Run: `go test ./internal/agent/... ./internal/runner/... -run
   'BuildEnv|AgentEnv' -count=1`.

**Interfaces:**

```go
// internal/agent/env.go, on EnvSpec:
AgentEnv map[string]string // fugaro.yaml's agent.env, allow-listed by config.Validate
```

## Task 5: the provider-scoped variant

**Files:** `internal/config/providers.go` (`ModelProvider.AgentEnv`,
`ValidateModelProviders`), `internal/config/providers_test.go`,
`internal/runner/agentenv.go` (`writeManagedSettings`),
`internal/runner/gateway.go` (`stagePins`/`beginGatewayStage`'s
neighborhood — wherever the stage's role model is already resolved, reuse
it rather than resolving it twice), `internal/runner/providers_test.go` (or
wherever `agentenv.go`'s tests live), `docs/multi-model.md`.

**Flag for opus review**: this task implements §3's precedence claim (owner
`agent_env` beats a repository's `agent.env`, by construction, because it
lives in a different, higher-precedence channel) and the kind-gating of
`DefaultProviderAgentEnv` (E4); a mistake either silently defeats the
origin bug's own fix for a repository that didn't ask for provider models
at all.

**TDD steps:**

1. Write failing tests first:
   - `internal/config/providers_test.go`: `ModelProvider.AgentEnv`
     round-trips through `ValidateModelProviders` using the same
     `validateAgentEnvMap` as `agent.env` (Task 1, E1) — a bad name or
     value under `providers.<name>.agent_env` is refused with the same
     message shape as `agent.env`'s.
   - `internal/runner`: `TestWriteManagedSettingsIncludesProviderAgentEnv`
     — a stage whose role model `config.ProviderFor` resolves to a
     provider with `AgentEnv` set gets those keys in the written managed
     settings; a stage whose role model is Claude (no provider) does not.
   - `TestWriteManagedSettingsAppliesDefaultProviderAgentEnv` — a provider
     of kind `anthropic-compat` with **no** `AgentEnv` set still gets
     `DefaultProviderAgentEnv`'s two keys; a provider's own `AgentEnv`
     entry for the same key overrides the default's value, not merges with
     it.
   - `TestWriteManagedSettingsProviderAgentEnvNeverAppliesToClaude` — the
     reviewer's stage, pinned to a Claude model while the coder's is
     provider-routed, gets **no** provider `agent_env` keys — proof the
     per-stage, per-role scoping (not "the whole run") actually holds; this
     is the test most likely to catch E4/the stage-scoping mistake the
     opus review should specifically look for.
2. Make them pass: add `AgentEnv map[string]string` to `ModelProvider`
   (`providers.go:29-47`); call `validateAgentEnvMap` from
   `ValidateModelProviders` (`providers.go:103-165`); add
   `DefaultProviderAgentEnv` keyed by `config.ModelProviderKind` (E4); in
   `writeManagedSettings` (`agentenv.go:65-84`), for each role actually
   pinned this stage, resolve its provider (reusing whatever
   `stagePins`/`beginGatewayStage` already computed, not a fresh lookup)
   and merge `DefaultProviderAgentEnv` then that provider's own `AgentEnv`
   into `vars` before the final `WriteManagedSettings` call — ordering
   matters: defaults first, provider's own overrides second, both before
   the function's existing gateway vars and pins so those still win if
   they ever collide (they shouldn't, by name, but the ordering should not
   depend on that).
3. Update `docs/multi-model.md` §5 ("What is refused, and why" /
   nearby): note that `context_management`/extended-thinking requests are
   now suppressed by default for a provider-routed stage rather than
   merely refused at the gateway if sent — cross-reference
   `docs/design/agent-env.md` §3 as the mechanism, and soften or remove the
   "assumed until Check 25" framing for the specific thinking/beta-header
   failure mode this closes (leave every other "assumed until Check 25"
   claim in that document untouched; this task narrows exactly one of
   them).
4. Run: `go test ./internal/config/... ./internal/runner/... -run
   'ProviderAgentEnv|ManagedSettings' -count=1`.
