**Architecture — what the seven phases build, in one paragraph (Phase 0 to Phase 6).** Phase 0 makes "Fugaro created this project" a fact the program can read after the run that created it has ended, and makes the read **fail closed** — a marker that cannot be checked means *not managed*, exactly as `infra.ReadProjectMarker` already behaves for the runs bucket. Phase 1 turns the two deterministic gates that exist for Fugaro's own embedded modules (`internal/infra/tf/guard.go`'s `Guard` and `internal/infra/tf/cover.go`'s `Cover`) into the gate a managed project's applies run behind: `Guard` unchanged, `Cover` re-derived as a managed-project allowlist whose widest entries are decided rather than inherited, **and `Guard`'s allow-list read from a place the applying command cannot write** — an owner-written object at the root of the managed project's runs bucket, absent or empty meaning every delete and replace is refused (Task 1.4, D74) — **and it builds the account the gate's applies run as**: a dedicated deployer service account whose two custom roles admit exactly what the managed allowlist admits and nothing on the runs bucket (Task 1.5, D75). Phase 2 makes the model's review **advisory and recorded** — it runs, its output is stored, its verdict can only *add* a refusal, and it is never the reason a plan is applied — and puts the redaction rule in place so no plan file ever reaches a repository. Phase 3 is the apply path, and it is where D55's answer lands: **the coding-agent refusal is removed for a managed project and the apply happens inside the agent's session**, on a saved plan that passed the deterministic gate, with the cloud marker, the owner-written delete list (Task 1.4's object, which this apply reads and whose own command-line flags it refuses) and the budget as what replace the refusal; it ships **inert until phase 4's inventory and required budget land**, and the shape the design used to recommend — keep the refusal, and apply where no agent is — is a task of its own, kept as the alternative. Phase 4 builds the two things the spec's Cost safeguards and "single purpose" need that do not exist: a whole-project inventory read, and the budget's **required** amount with the existing alerts. Phase 5 is secrets and disaster recovery: one new column on `fugaro secrets ls`, and a restore that promises a **from-zero apply**, not a state restore, because the state bucket lives in the project that was lost. Phase 6 is deliberately empty of work in the first release: it lists the two things a reader will otherwise look for (the billing hard stop, and moving an existing project into managed mode) and says which decision each waits on, plus **Task 6.2**, which is scheduled rather than decided — the re-run of phase 0's and Task 1.4's negative write tests against the run credential the **compute backend (excluded from 0.9.0, so a later release)** creates.

**What this plan does not do, stated once so it is not read as an omission.** It removes `CanConfirm`'s agent-marker refusal **for a managed project only** (D55's answer of 2026-10-16) — the one place where a refusal is deleted rather than narrowed, and the task that does it (3.1) is SECURITY-SENSITIVE, carries the design's residual-risk paragraph in its PR description, and is unapproved until the owner passes the gate for it **— the approvals of 2026-10-16 reach Phases 0 and 1 and not this task**; it does not put a plan file in the repository; it does not introduce a Cloud Billing Budgets API client, a Pub/Sub topic or a billing-admin function (D63); it does not add a credential anywhere the console, the launcher or the agent can read one; and it does not touch `belong`.

## Global Constraints

These hold for every task below, and the plan's own review checks them:

1. **The coding-agent refusal is removed for a managed project and for nothing else — and the marker, the gate and the delete rule are what replace it.** D55's answer of 2026-10-16 is this plan's shape: in a **managed** project `initflow.CanConfirm` stops returning `false` for a marker on the apply classes the gate covered, so the agent's session applies; in **every other** project the refusal stays exactly as it is today (`internal/initflow/stage.go:334-342`, `AgentRefusal` at `:298-304`), and no task here adds a path around it. Three things replace the refusal and each is a task rather than a sentence: **the gate** — no apply without a `tf.Guard`/managed-`Cover` verdict, the caller's only permitted action on a refusal being to fall back to a confirmation (Tasks 1.0, 1.1, 1.2); **the delete rule** — a managed apply takes no `--allow-delete` of its own: the addresses come from an **owner-written** list an agent cannot write, so an agent can never authorize its own delete or replace — an object at the root of the managed project's runs bucket, written only by an owner-run command, read with the marker's own project-number check, and absent, empty or unreadable meaning every delete and replace is refused (**Task 1.4** builds and defines it; Task 3.1 reads it and refuses the flag; D74); and **the marker** — the read that decides whether managed mode applies at all, writable by no credential a run holds (Tasks 0.1, 0.2). **The residual risk is part of this constraint, not a footnote**: the agent shares the container and the user with the runner and reads the runner's environment through `/proc` and the job's service account through the metadata server (`SECURITY.md:67-70`), so none of the three is a boundary against an agent that goes around the program — the design's §6 item 4 says what holds and what does not, and Task 3.1's PR description carries that paragraph because Task 3.1 is the change it is about.
2. **The cloud marker is the authority and every config may only narrow.** No task lets a repository's `fugaro.yaml`, the local project config, or any agent-written file turn managed mode **on**. Reading one may turn it **off**.
3. **A marker that cannot be read means "not managed".** Every read fails closed, in the shape `infra.ReadProjectMarker` already has (`internal/infra/project.go:51-84`: the bucket must be the expected project's, proved by its own project number, before its contents are believed).
4. **No credential a run holds, and no credential the apply identity holds, may be able to write the marker — or the delete list a managed apply reads (Task 1.4, D74)** — or, in the full version of this feature, to widen its own cloud permissions. A task that changes what a run's identity can do carries a test asserting what it can no longer do. **The limit is the IAM, not the marker**: `SECURITY.md:56` records that Project Owners, Editors and anyone with a project-level storage role bypass the bucket's own policy regardless, so the apply identity's roles are part of the task, not an assumption (Task 0.1). **And the identity that applies a managed plan is now decided: the deployer service account of D75** (the owner's answer of 2026-10-16, and this plan's C7) — an account the managed apply **impersonates**, whose **custom role** Task 1.5 enumerates, and whose reach the design's D75 row states exactly: **no project-level IAM permission at all** (so no `resourcemanager.projects.setIamPolicy`), **no `iam.roles.*`** (an account that can update its own custom role can widen itself), **resource-level `setIamPolicy` and `actAs` only through a binding whose IAM condition admits the managed name prefix and never project-wide — the owner's amended D75 answer of 2026-10-16, fail-closed: a type GCP cannot honour the condition for is dropped** (a permission in a project-bound role reaches every resource of its kind — every service account, the project's default compute account included; D75 (iii), Task 1.5), and **nothing at all on the runs bucket** — no object writes and no bucket-IAM admin — so this constraint is true of the identity that applies and not only of the job account. **The correction that made this statement buildable, and the one line to keep**: the first form said "no role on the marker bucket's root objects", which no account that applies the installation root can have, because that root's plan contains the marker object (`deploy/terraform/gcp/modules/installation/bucket.tf:78`). **The deployer therefore does not apply that root**: a managed apply applies **the agent-authored root in the project repository** — through **`fugaro managed apply`** (D76), with its state in a **dedicated state bucket** (D77), both answered 2026-10-16 — Fugaro's own embedded roots keep their typed confirmations because their plans carry project-level IAM the account cannot make, and the gate refuses any plan that writes an object under the runs bucket's root prefix or binds IAM on the runs bucket (Task 1.1). **The operator's own identity remains the wider one** — `fugaro init` run by a person, typically a project Owner, can still write `fugaro/managed.json` and `fugaro/allow-delete.json` directly with `gcloud storage cp`, and can unset the agent marker in its own environment and run the owner-run `fugaro allow-delete` itself (its only guard is the env-marker check — `agentMarker`, `internal/cli/initsecrets.go:136`, over the marker list at `:132`); ## Review Focus

What a reviewer of each phase should attack, in the design's own terms:

- **Phase 0**: **can the marker be made true by anything the agent can do?** Two questions, and both must be answered from the code rather than from the prose: what identity writes it, and what reads it. A read that trusts a string, or that treats "cannot read" as "managed", is the defect that turns this whole feature into a privilege escalation.
- **Phase 1**: **is the gate the gate?** `Cover.NotCovered`'s managed-project allowlist is the widest entry in the design — a plan the agent wrote, judged by a list someone chose. A reviewer should ask which type on the list is there because the embedded modules use it and which is there because a managed project might legitimately need it, and treat an unexplained second category as a finding. Then: does every refusal actually stop the apply, or merely return an error someone ignores? **And, for Task 1.4: is the delete allow-list's provenance anything more than a sentence?** The two failures to look for are a `Guard` call fed from the apply's own flag in a managed project, and a read that treats an absent or unreadable list as "nothing to check" instead of "refuse every delete".
- **Phase 2**: **can a job-written string become a decision, and can a plan secret become a repository file?** Look for a verdict interpolated into a refusal list as though it were a rule, and for any path that writes a plan rather than a summary.
- **Phase 3**: **is the removal narrow?** D55's answer removes the refusal **for a managed project only**, so the first attack is the other direction: can a **non-managed** project — or a marker that is absent, unreadable or names another project — reach an apply while a marker is set? Then: can an agent authorize its own delete or replace, by passing `--allow-delete` from its own command line rather than from the owner-written list — which Task 1.4's object defines, and which a managed apply must **refuse** the flag for rather than silently ignore? And does every refusal fall back to a confirmation rather than applying? **The phase has failed if a marker plus a non-managed project reaches an apply, or if the delete allow-list is anything an agent can write** — the second is asserted in Task 1.4 and read in Task 3.1.
- **Phase 4**: **does the inventory check fail in the safe direction?** A false positive must fall back to confirmations, never halt; a false negative must not be reachable by a resource the installation's state does not know about. And: does the budget amount come from the operator, or from a default nobody chose?
- **Phase 5**: **what does restore actually promise, and is it true?** The state bucket lives in the project that was lost; a restore that reads it is a restore that will fail exactly when it is needed. Check whether the plan's promise is "from-zero apply" and whether anything in it quietly assumes the old state.
- **Every phase**: the refusal stays **for every project that is not managed** — D55's answer narrows it and does not delete it — the marker fails closed, no plan file is committed, `belong` is untouched, and no task's command needs a live cloud.

## Phase 0 — The fact

**Why this is first.** Everything else in this feature is downstream of one question: **how does the program know, in a run that did not create the project, that Fugaro created the project?** Today it does not. `fugaro init --create-project` creates the GCP project and adds Firebase (`internal/cli/init_project.go:412-444`, `internal/infra/projectcreate.go:374-418`), the fact lives in the run's memory for the length of that run, and nothing persists it (design finding 19). The nearest durable ownership mark is the runs bucket's `fugaro/project.json`, and it is read with a project-number check precisely because a bucket name proves nothing on its own (`internal/infra/project.go:16-84`). Phase 0 makes the creation fact durable, in that shape, and writes the one property test whose failure would be silent. **Phase 0 is approved: the owner approved Tasks 0.1, 0.2 and 0.3 on 2026-10-16, with Phase 1's gate, because Phase 1 depends on them.**

### Task 0.1: The creation fact, recorded where a run cannot write it — SECURITY-SENSITIVE, independent opus review — D56, D57, D58 AND D73 ANSWERED 2026-10-16 ("cloud marker, owner-run"; existing projects MAY be flagged after the fact, owner-run and per project); the applying identity is D75, answered the same day and built by Task 1.5

**Files:** `internal/infra/managed/marker.go`, `internal/infra/managed/marker_test.go`, `internal/cli/init.go`, `internal/infra/projectcreate.go` — **and nothing under `deploy/terraform/` at all**: the shape is resolved and it is a Go-written object (step 1 below), so this task adds no Terraform resource, no variable and no `count`. `internal/cli/init_project.go` is **not** in this task's file list either — the created flag is read from the run's own result where the write happens, and there is no Terraform input to pass it to.

**Steps.** The fact is "**this run created this project**", and it has to be written where the thing that holds it exists. Three corrections to the shape this task is written in, all read from the code rather than assumed:

1. **The write is a Go call at the end of the run that created the project, and it is not a Terraform resource — this is C2, and this plan resolves it as (i).** Two shapes were possible and only one survives the code: **(i) the creating run writes `fugaro/managed.json` itself, after the `Installation` stage has created the runs bucket** — the same shape Task 1.4's delete list has, written by a CLI-written object rather than a Terraform-managed one; or **(ii) a second `google_storage_bucket_object` beside the one that already writes `fugaro/project.json` (`bucket.tf:78`, `google_storage_bucket_object.project_marker`), with its `count` driven by a variable the creating run sets.** **(ii) is rejected on the same ground D74 rejects a Terraform variable for the delete list**: `fugaro init` rewrites the installation's `terraform.tfvars.json` from its own flags on **every** run (`internal/cli/init.go:1137-1142`, and again at `:2492`), so the next `init` — by the same owner, on a machine with no memory of the first — writes tfvars without that variable, Terraform reads the default, and **the plan is to destroy the marker**: the authority D57's answer rests on, deleted by an ordinary `fugaro init`, silently, with the apply that follows reading "not managed". A `lifecycle { prevent_destroy = true }` does not fix it either; it turns a silent loss into a blocked `init`. So the marker is written the way the delete list is: **an object at the root of the runs bucket, written by the owner-run creating command once the bucket exists, and never a Terraform variable.** The timing is the whole difficulty and the code settles it: the project stage runs first and the runs bucket does not exist while it runs — the bucket is created by the **installation** module (`deploy/terraform/gcp/modules/installation/bucket.tf`, `google_storage_bucket.runs`) at the `Installation` stage, later in the same `init` — so the write belongs **after** that stage, in the same run, from the one place that knows the fact.
2. **The creation signal is `r.res.Created`, not `AddFirebase` returning.** `AddFirebase` runs on **existing** projects too: `internal/cli/init_project.go`'s `Apply` sets `r.res.Created = s.id` and `created = true` only inside the `if s.create` branch (`:393-425`), and the `else if s.addFirebase` branch (`:426-444`) is a project this run did **not** create, where Firebase was merely missing. `AddFirebase` is then called once, for both (`:435-444`). A marker keyed on "Firebase was added" would mark the owner's pre-existing projects — the `belong`-shaped case the whole design excludes — and **D73's answer of 2026-10-16 is that the addendum covers only a project Fugaro created or one the owner has flagged under D58, so adding Firebase is never by itself what makes a project managed**. The write is therefore gated on `r.res.Created` being set, and on nothing else.

**The writer's IAM is part of the task, not an assumption about it, and the check for it is Check 68 rather than a test.** `internal/infra/project.go:20-22` says "no job account can write it, and since 0.7.0 no launcher", and that is the property this task needs — but `SECURITY.md:56` records how narrow it is: "Project Owners, Editors and anyone with a project-level storage role bypass the bucket's own policy regardless, hardened or not". **Two identities are in play and only one of them is testable**: the **job account** a run holds, whose grant set this task asserts from a fixture (it holds no role with a write path to the bucket's root prefix — the assertion Global Constraint 4 asks for); and the **deployer service account D75 defines**, which is the identity that actually applies a managed plan — created by the owner-run creating apply (Task 1.5), so its **live bindings cannot be asserted in a test at all**, because Global Constraint 12 forbids a live IAM read and no fixture can know what the owner created. That second one is **Check 68**, an owner-run live check on the sandbox installation measuring **the deployer account's IAM — not the operator's own identity** (an earlier revision of this task named the operator's, which is the identity the deployer is impersonated *from*, not the one that applies), and the design decision it belongs to is **D75** (this plan's **C7**) — **answered by the owner on 2026-10-16 as recommended: option (a), the managed apply impersonates a dedicated deployer service account holding no role on the marker bucket's root objects and no `setIamPolicy`** — the owner's first words; **the owner AMENDED them on 2026-10-16 to "allow conditioned resource-level `setIamPolicy`/`actAs`"**, and that is the answer that stands: **no project-level `setIamPolicy`, no `iam.roles.*`, no write path to the runs bucket, and resource-level `setIamPolicy` and `actAs` only on the accounts and resources the deployer created, through the reserved-name-prefix IAM condition, a type dropped where GCP cannot honour it** (D75 (iii), Task 1.5) — so D56/D57's test is about **that** account as well as about the job account. Option (b) — the operator's own identity applies, and its ability to write the marker and the delete list is carried as residual risk rather than closed — is D75's alternative column, kept so its cost can be read beside the answer. (**C7, not D57: D57's answer of 2026-10-16 — "cloud marker, owner-run" — is about the marker's form and its writer.** The identity that applies is the separate question D75 settles.) **What the answer adds to this task**: the apply path carries the impersonation (Task 3.1), the account and its one-time impersonation grant are the owner's to create, and this task's fixture half (the job account) is written the same way it would have been — the deployer account's own grants are Check 68's, not a fixture's.

## Phase 1 — The gate

**Why this is second.** The spec asks for a plan gate (its steps 2 to 4) and treats the model's review as it. The reconciliation's finding is that the gate already exists — `tf.Guard` refuses every delete and replace unless the exact address is allow-listed (`internal/infra/tf/guard.go:16-44`) and `tf.Cover` decides what may share a confirmation at all (`internal/infra/tf/cover.go:20-46`, `:63-112`, `:169-182`, `:198-266`, `:614-728`) — and that it was built for Fugaro's own embedded modules, whose resource-type allowlist is tested against them. Reusing it for an agent-authored plan means **a new allowlist, and choosing it is a decision, not a copy** (design finding 22). Phase 1 builds the gate and the choice — the delete/replace rule inherited unchanged, and the one thing it has never had written down: **where `Guard`'s allow-list comes from** once the applying command's own `--allow-delete` is no longer allowed to be it (Task 1.4, D74) — **plus the identity the gate's applies run as, which D75's answer of 2026-10-16 made part of this phase rather than an assumption about it (Task 1.5)**: a deployer service account whose two custom roles admit what the allowlist admits and nothing on the runs bucket. **This is the phase the owner approved on 2026-10-16 ("Approve the gate for phase 1"), so Tasks 1.0 to 1.5 are the plan's approved work** — and the parallel-execution levels show it is also the critical path's middle.

### Task 1.0: The plan's path through the gate, and what a refusal does

### Task 1.3: The cost attributes, flagged and blocked

**Files:** `internal/infra/tf/managed_cost.go`, `internal/infra/tf/managed_cost_test.go`

**Steps.** The spec's step 4 asks the agent to flag "new or upsized resources that bill continuously, such as Cloud Run min instances, Cloud SQL tiers, GPUs and large VMs" — the Gap finding 27 records ("nothing blocks a plan on an estimated cost"), and the one the Spec paragraph above sends here.
