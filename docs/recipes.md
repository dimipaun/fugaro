# Recipes: choose the task loop

Recipes need fugaro 0.5.0 or later; the format this document describes (`use_when`, `mode`, `roles: { coder: reviewer }`, the `check` step and `bounce: first_line`) needs 0.7.0 or later, the `adversarial` step (review level 3) needs 0.16.0 or later, the `hand_over` review flag and the `rebase` step (the escalation ladder's own two, section 2) need 0.23.0 or later, and the `by_level` block (the recipe's one conditional, section 1) needs 0.27.0 or later. Design: [recipes/spec.md](recipes/spec.md), [generic-tool/spec.md](generic-tool/spec.md) (§3).

A Fugaro run implements the task, then loops: an optional first-line review by the coder's model, then the senior review, each followed by a fix when the review asks for changes, and optionally a harder review after the senior one. A **recipe** names that loop after `implement` so you can pick it per run, per repository or per project. A repository that names no recipe runs the `default` recipe, which is that whole loop: up to three review levels, each one running only where its own condition holds (section 4).

## 1. What a recipe is

A recipe is a small YAML file. This is the catalog's `standard` exactly as `fugaro recipes show standard` prints it (without the header):

```yaml
version: 1
name: standard
description: The cheap coder loops review and fix, then the senior reviews; a rejection goes back to the cheap loop.
use_when: Typical feature or bug-fix work that needs a real review. Choose it when nothing more specific fits.
steps:
  - first_line: {}
  - review:
      bounce: first_line
```

The keys are `version` (must be 1), `name`, `description` (optional, at most 200 bytes), `use_when` (optional, at most 300 bytes: see section 2), `roles` (optional, see below) and `steps`. `version`, `name` and `steps` are required. The catalog's `solo` shows `roles`:

```yaml
version: 1
name: solo
description: One model codes and reviews its own work in a fresh session.
use_when: Small, low-risk changes confined to one or two files, where a second model's review would cost more than it finds.
roles:
  reviewer: coder
steps:
  - review: {}
```

- `implement` always runs first, unless `mode: review` (section 3) says there is no `implement` at all, or the first step is `digest`, which is the run's own deterministic first stage instead (see below). `steps` lists what follows it, in order.
- `digest: {}` is the report run's step (the catalog's `run-digest`, section 2): the run writes the run reports the repository is missing and commits them itself, so no model writes a figure. It takes no options, and it may appear only once, only as the first step, and only in a `mode: implement` recipe — the shape is exactly `digest` and then `review`, so the one senior review judges the pull request the digest wrote and no other step runs over it. The step is the runner's own work, and the first release whose runner does it is 0.13.0: `fugaro run` refuses a launch of a recipe holding one against a job image built from an older release, naming that release and `fugaro image refresh` (section 9). A base image that is not a release only warns there, which is safe either way, because the refusal is the image's own runner's rather than a silent skip of the step: a 0.12.1 runner knows the step kind and refuses the recipe at bootstrap (`does not execute yet`) instead of skipping the step and opening an ordinary pull request in its place, a runner older than 0.12.1 — a release or a non-release image — has no `digest` in its version 1 step list at all and refuses the recipe as `is not a step type`, and a runner that does execute the step runs it. A runner older than 0.13.0 does not know the `digest_runs` manifest a report run carries either: its task decode is strict, so it refuses the field as unknown. A `task.json` written by hand never passes that gate at all, and reaches the step, which refuses a task carrying no `digest_runs` manifest before any model call.
- `commit_reports: {}` is the commit run's step (the catalog's `commit-reports`, section 2): the launcher hands in the stored run reports the runs bucket holds, and the step is the runner's own — it refuses an object whose bytes do not match the sha256 it was handed, refuses a name that is not a report of the mirror's own shape (`<slug>/<YYYY>/<key>.md` for a repository's report, `<YYYY>/<key>.md` for the project's aggregate), writes each one into the folder the project designates, regenerates the folder's index over every report in it and commits them, so no model writes a byte of them. It takes no options, like `digest`, and it may appear only once, only as the first step, and only in a `mode: implement` recipe — the shape is exactly `commit_reports` and then `review`, so the one senior review judges the pull request the step wrote and no other step runs over it. The step is the runner's own work, and the first release whose runner does it is 0.26.0: a runner older than that has no `commit_reports` in its version 1 step list at all, so a job image built from an older release refuses the recipe as `is not a step type` rather than skipping the step and opening an ordinary pull request in its place.
- `plan` and `render` are the two step kinds of `mode: artifact` (section 3): `plan` is an agent stage and `render` is deterministic, running the workflow's `commands.render`. An artifact recipe's `steps` is exactly those two, in that order, `render` alone — a `render`-only recipe calls no model at all — or the `diagnose` shape below.
- `diagnose: {}` is the step the cloud diagnosis runs (the catalog's `troubleshoot`, section 2): one model stage reads the evidence a launcher left under the run's own prefix and writes the answer's two files, `diagnosis.md` for a person and `diagnosis.json` for the offline path and the run record, which the recipe's `outputs` block is what names. It takes no options, like `plan` and `digest`: what the stage reads and what it writes are the runner's own contract rather than an author's choice. It is a step of `mode: artifact` alone (section 3), standing exactly where `render` stands — alone, or after one `plan` — so it may appear at most once, never beside a `render`, and in no other mode. The stage runs under the recipe's own per-call output bound rather than the loop knobs: 10000 tokens — $0.20 of the tier's own $0.25 cap at the reviewer model's $20/M output rate, the rest being what that call's input may reserve, and far below any run's. D2407's turn bound, 8, is written down in `recipe.TroubleshootMaxTurns` and read by nothing yet: the stage's own call has no turn knob, so a cloud diagnosis is bounded by that reservation, the run's lease and the stage's timeout. And the stage is the runner's own: a run of a recipe holding one whose job image does not execute the stage is refused at bootstrap, before any model call, instead of dropping the step and ending as an artifact run with nothing in it. The step is the runner's own, and the first release whose runner executes the step is 0.26.0: the cloud tier meets that gate at your terminal rather than inside a job, its pre-flight refusing a diagnosis against a job image built from an older release, naming that release and `fugaro update` (section 9). A base image that is not a release only warns there, which is safe either way, because the refusal is the image's own runner's rather than a silent skip of the step: a 0.25.0 runner has no `diagnose` in its version 1 step list at all and refuses the recipe as `is not a step type`.
- `outputs` is a top-level block, legal only on `mode: artifact` (section 3): `globs` (required: the artifact paths, relative to the checkout), `max_files`, `max_bytes` (each artifact) and `max_total_bytes` (the whole set), and `probe`, which is `probe` or `none` and names the workflow's `commands.probe`. `outputs` on any other mode is refused outright (section 8), and `mode: artifact` without it is too.
- `check` may appear at most once, and only before `first_line` and `review`: `check: { command: build | test | lint, autofix: true }`. `command` names a `commands.*` key of the `fugaro.yaml` the run reads at its ref (never a command of its own: a recipe never names a command). `autofix` is allowed only with `command: lint`, and needs `commands.fix` next to `commands.lint`. `commands.fix` is trusted only when it exits 0, does not time out, and leaves the branch's history exactly where it found it: a timeout, a non-zero exit, or a commit it made on its own, are all discarded (reset to the commit read before the fix ran, untracked files removed) rather than committed under the runner's identity, and the check step ends red with a plain explanation of why. A follow-up (`fugaro run --pr N`) keeps its recipe, so its check still runs; a clean or fixed check never ends or shortens a follow-up the way it does a first run — the launcher asked for something specific (replying to comments, applying instructions), and the gate passing does not mean that work is done.
- `first_line` may appear at most once, with `max_rounds` 1 to 3. It is a review by the coder's model in a fresh session, followed by a fix when it asks for changes. It never decides readiness.
- `review` is required in every recipe: exactly once, with `max_rounds` 1 to 10 (1 only, under `mode: review`). A recipe cannot produce a ready pull request without a senior review. It is the last step unless the recipe has an `adversarial` step after it.
- `adversarial` is review level 3: a second, harder review after the senior one, in its own fresh session. It may appear at most once, only after `review`, and last. Its `max_rounds` is 1 to 10 (the `review` step's own range; a step that writes none runs the rigor mode's senior row, section 4), and `bounce: first_line` is its only bounce target, needing a `first_line` step before it exactly as `review`'s bounce does: a rejection runs the fix, then another first-line loop, then the next adversarial round. It is the newest construct a recipe can carry, and the first release whose runner acts on it is 0.16.0 (0.15.0 shipped with the step parsing but no runner running it, so L4.2 missed that tag): `fugaro run` refuses a launch of a recipe holding one against a job image built from an older release, naming that release and `fugaro image refresh` (section 9). A base image that is not a release only warns there, which is safe either way, because the refusal is the image's own runner's rather than a silent skip of the step: a runner that predates the step has no `adversarial` in its version 1 step list at all and refuses the recipe as `is not a step type`. Section 4 has the stage bound it adds.
- `hand_over: true` on a `review` step ends the run at that review: its verdict and findings are recorded, and no fix follows them, whatever the review asked for. The round's `max_rounds` still bounds how many rounds run (each of them the review alone, since none of them buys a fix), and what the run leaves is decided exactly as it is for any run whose last review asked for changes — a `ship` verdict with the verified passing test is a ready pull request, a `changes` verdict leaves it a draft with the findings in `result.json` — which is what the catalog's `escalate` asks for (section 2). It is refused beside `bounce: first_line` (a review that bounces asks for the fix `hand_over` refuses), in a recipe with an `adversarial` step after that review (nothing runs after the run has ended), and in a `mode: review` recipe (which has no fix round to skip). A run inserts no step of its own for a review level either: level 3's `adversarial` after such a review would have nothing to run after the run has ended, and level 1's `first_line` before it would be the cheap review-and-fix pass this recipe is defined without. `escalate` is one coding pass and one review pass, of the model the recipe names, on every mode — Critical included, where level 3's step is otherwise inserted by default — and with `agent.first_line_review` on, where level 1's is. Like the `adversarial` step it is a construct of one release, 0.23.0: a runner that predates it has no `hand_over` key on a review step at all and refuses the recipe as an unknown key.
- `rebase` is one step and the whole run: the job fetches the base, puts the pull request's branch on it, and where the replay conflicts asks the coder's model to resolve them, then re-runs the tests and force-pushes the branch with a lease. It has no `implement`, no review and no further step — the recipe holds it alone — and it ends the run itself: a run that resolved the conflicts pushes the rebased branch and records the head it pushed, one that could not ends refused with the reason and the conflicted paths, having pushed nothing and left the branch where it was. It needs `commands.test` in the workflow's `fugaro.yaml`, and it is launched as a follow-up on an existing pull request (`--recipe rebase --pr N`): with no pull request to put back on its base, the run has no branch to rebase and is refused at bootstrap. It is the escalation ladder's rung 0 and one of the 0.23.0 constructs above.
- A `first_line` or `review` step without `max_rounds` takes `agent.first_line_rounds` or `agent.review_rounds` from `fugaro.yaml` (section 4). A recipe's own `max_rounds` wins over those keys. A per-task `review_rounds` override (the task's `overrides`) wins over a recipe's `max_rounds` for the `review` step.
- `roles: { reviewer: coder }` makes the reviewer run on the coder's model, in a fresh session, with the reviewer's prompt. "Solo" means exactly this: the same model reviews, in a new session that has not seen the coder's reasoning. `roles: { coder: reviewer }` is the other direction: the coder (the `implement` stage, and any `fix`) runs on the reviewer's model instead, with the reviewer's per-call output limit; `agent.models.coder` is ignored if it is set (the run logs that), the same way `reviewer: coder` ignores `agent.models.reviewer`. The two exclude each other: a recipe cannot set both.
- `by_level` is the recipe's one conditional: a mapping from a rigor level — `poc`, `startup`, `pro`, `critical` or `hotfix`, the levels `fugaro rigor` names — to the `roles` mapping the recipe resolves at that level, which replaces the recipe's own `roles` there. Each entry holds exactly one key, `roles`, with one of the three spellings the top-level key takes, `roles: {}` included: `roles: { reviewer: coder }` beside `by_level: { critical: { roles: {} } }` is a recipe that reviews on the coder's model everywhere but Critical, where it reviews on the repository's own reviewer. `roles: {}` is a level that resolves no mapping at all (the models `agent.models` names), and a level the block does not name keeps the recipe's own `roles`. Nothing else is conditioned: the per-run cap a run gets is its level's own share of the deployed cap, whatever the recipe says ([rigor-modes.md](rigor-modes.md)), and the steps — the `check` gate, the loop's shape and its rounds — are the recipe's, so a level branch picks models and the reviewer, and nothing more. A key other than `roles` inside an entry is refused with that reason rather than read as a bound or an unknown key (section 8), and `by_level` is refused wherever `roles` is (an `artifact` or `evaluate` recipe has no agent steps to map roles onto). **No run applies the block yet**: the parser accepts and checks it and resolves it per level, and the runner and the level resolver both apply the recipe's own top-level `roles` once, at bootstrap, before the run's level is known — so a recipe that writes `by_level` today runs on its top-level `roles` at every level, whatever the block says. A launch of one still needs a runner that can read the key, which is what the gate below is for. The first release whose reader knows the key is 0.27.0: a runner older than that has no `by_level` key at all and refuses the whole recipe as `is not a recipe key`, which is why `fugaro run` refuses such a launch against a job image built from an older release, naming that release (section 9). The gate judges the key's presence and never what its entries hold, so an older reader refuses `by_level: {}` all the same, and a recipe that does not write the key loads unchanged on every release, `default` included.
- Models are never named in a recipe. They come from `agent.models` in `fugaro.yaml`, as they always did.
- Readiness is unchanged and not configurable: a pull request is ready only if the final commit has a verified passing test and the review's verdict is `ship` — or the run reached its **stop** in a mode whose stop rule accepts what the round left, which is Startup's and POC's "merge as-is, follow up the rest" (the owner's ruling of 2026-11-08, section 4) — or every finding the deciding round left is one the triage stage **deferred**, which is Startup's and Pro's and no other mode ([triage.md](triage.md)). A ready pull request loses its draft state and nothing else: **no run makes a merge call**, so a person, or the coordinator, merges it, and anything else is a draft. The one other thing that may merge is a project's **orchestrator daemon**, at the top of its escalation ladder (rung 3): it lands a stalled pull request only under the deterministic gate a run's own triage already uses — green CI, the whole changed-path set `Routine`, no blocking finding, all read at **one** head SHA, so a push after the gate refuses the merge — and the mode decides only who is told, because Critical waits for a person in every case. A pull request that is still a **draft** is readied first and merged at the head it readied, and that readying happens only where the machine sets `escalation.ready_drafts`, which is **off** by default, so a daemon nobody switched on merges no draft and raises the question for a person instead; the whole of it is [outer-loop-escalation/README.md](outer-loop-escalation/README.md). The ladder's executor is built and the daemon does not walk it yet, so today no merge call is made by anything but a person. A `check` step that passes ends the run with no pull request at all (section 5); `mode: review` never changes a pull request's draft state.
- Under `reviewer: coder`, the reviewer's model and its per-call output limit are the coder's, and `agent.models.reviewer` is ignored (the run logs that). The output limit is applied before the project's policy: if the default branch's `fugaro.yaml` sets a tighter `agent.max_output_tokens.reviewer`, the aliased reviewer limit ends up tighter than the coder's, and the run's report notes that the looser value was ignored. Limits from policy can only tighten. `coder: reviewer` is the mirror image: the coder's (and `fix`'s) model and per-call output limit are the reviewer's, `agent.models.coder` is ignored if set (the run logs that), and the same policy rule applies to the coder's output limit.
- `review: { bounce: first_line }` needs a `first_line` step before the `review` step. When the senior review asks for changes, the usual `fix` still runs, but it is then followed by another `first_line` round (bounded by `agent.first_line_rounds`, or the `first_line` step's own `max_rounds`) before the next senior round, instead of going straight back to the senior reviewer. This repeats on every senior rejection, up to `agent.review_rounds` (or the `review` step's `max_rounds`) senior rounds in total; the last round never bounces, since there is no further round to use it. `result.json`'s `reviews` array records which cheap loop (if any) a first-line review followed: `bounce: 1` on the first one that followed a senior rejection, `2` on the second, and so on; the field is omitted (0) on every senior review and on a first-line review that ran before any rejection.
- A recipe file is at most 16 KiB and is strictly parsed: unknown keys, duplicate keys, YAML anchors, aliases, tags and extra documents are refused. A recipe older than 0.7.0 never used `use_when`, `mode`, `roles.coder`, a `check` step or `bounce`; a recipe that does is refused outright by a CLI or runner older than 0.7.0 (section 6).
- `name`, `description` and `use_when` are refused if they hold a C0 or C1 control character, DEL, a Unicode format character (bidi overrides, zero-width characters and the like) or a line or paragraph separator (U+2028, U+2029): a project recipe is anyone-with-bucket-write's text, shown verbatim by `recipes ls` and read by the routing skill, so none of those three fields can carry a character that would corrupt a terminal or make the same bytes read differently to a human and a skill.

## 2. The catalog

| Name | Behaviour | Use when |
|---|---|---|
| `default` | The whole loop, up to three review levels (0.16.0): a first-line review only when `agent.first_line_review` turns it on (`auto`, the default for that key, turns it on when a provider serves the coder and none serves the reviewer), then the senior review, then the adversarial review (level 3) only where the run's review levels run it, which is Critical by default today: `agent.levels.l3`, the task's `review_levels` and the owner's floor can turn it on at any mode. | The implicit choice: what runs when nothing else names a recipe. Its rounds are not fixed: a repository that sets neither round knob runs the rigor mode's own row (section 4), so an unconfigured repository, which resolves `pro`, runs 3/3 where it used to run 1/2, and the same recipe takes more stages. |
| `solo` | `roles: { reviewer: coder }`; `review: {}`. | Small, low-risk changes confined to one or two files, where a second model's review would cost more than it finds. |
| `standard` | `first_line: {}`; `review: { bounce: first_line }`. | Typical feature or bug-fix work that needs a real review. Choose it when nothing more specific fits. |
| `premium` | `roles: { coder: reviewer } `; `review: {}`. No cheap stage. | High-stakes or subtle work (concurrency, security, data migrations) where a cheap model's attempt is likely to waste the review. |
| `review-only` | `mode: review`; `review: { max_rounds: 1 }`. No coding. | Reviewing a human-written or external pull request. Launch with `--recipe review-only --pr N`, or as the independent cloud senior review with `fugaro review --pr N` (0.19.0, the release that registers it), which runs this same recipe on the review-only job variant. The review is judged against the task of the run that opened the pull request by default; `--code-only` asks for the code alone, with no task, and `--spec FILE` judges it against the task in that file, which is how a pull request no run produced is reviewed against something. The two flags are refused together, and the key `agent.review_against_task` (a repository's, and the project's published policy) is what switches the default off. |
| `pick` | `mode: review`; `review: { max_rounds: 1 }`. No coding. | Comparing several pull requests for the same task to decide which to keep, once every attempt has settled. Launch with `--recipe pick --pr A --pr B [--pr C]` (2 to 4 pull requests). |
| `test-and-fix` | `check: { command: test }`; `first_line: {}`; `review: { bounce: first_line }`. | Keeping a branch green, chasing a failing or flaky test, CI babysitting. A green run ends with no pull request. |
| `lint-fix` | `roles: { reviewer: coder }`; `check: { command: lint, autofix: true }`; `review: {}`. | Routine mechanical cleanup (formatting, lint and type-check errors) in a repository with `commands.lint` and `commands.fix`. |
| `run-digest` | `digest: {}`; `review: { max_rounds: 1 }`. The report run: the runner's own step writes the reports this repository's tree is missing — every closed day it has no file for, up to the last seven, plus the week, month or year that just closed — and commits them, then one senior review judges the pull request. A run whose periods are all already in the tree writes nothing, calls no model and opens no pull request, and the pull request's diff against its base is the generated files byte for byte whatever a review or a fix round wrote beside them. The step is the runner's own, so the job image must be 0.13.0 or later. Its one review is also the one stage a catalog recipe bounds for itself (0.24.1): `agent.max_output_tokens.reviewer` is capped at 32000 tokens for this recipe alone, because a call reserves its whole output allowance at the gateway before it spends anything, and no bound at all reserves the reviewer model's own maximum — 128k on `claude-opus-5-5`, $2.56 plus the input, more than a small repository's per-run cap holds, which halted a report run with `run_cap` having spent nothing. A repository or a project whose reviewer bound is smaller keeps its own; the run logs the cap where the figure it drops is larger. It stays MIT: the digest is part of the MIT core, so every build runs it, tagged or not. | Scheduled run reviews only, launched by your own routine (`fugaro run --recipe run-digest "periodic run review"`), one repository per launch. Never the recipe for a task. Ask any checkout whether its reports are due with `fugaro runs digest --due`, which reads that checkout's committed report folder and nothing else: offline, no project config and no credentials. The project's reports job stores the reports it writes in the runs bucket, under `reports/`, one repository and one period each: read one back with `fugaro runs digest --stored <period>` (`2026-10-25`, `2026-W43`, `2026-10` or `2026`), which prints this repository's stored report of that period and writes nothing — a launcher reads the runs bucket and writes only `runs/`, `tokens/` and `issues/`, so `reports/` has one writer and it is the job (section 7) — and `fugaro runs digest --dir FOLDER` writes one into a checkout instead. |
| `commit-reports` | `commit_reports: {}`; `review: { max_rounds: 1 }`. The commit run: the step is the runner's own and writes no figure — the launcher hands in the stored run reports, and the step refuses a name that is not a report of the mirror's own shape or a byte whose sha256 disagrees with the one handed in, writes each report into the folder the project designates (a repository's at `<dir>/<slug>/<YYYY>/<key>.md`, the project's aggregate at `<dir>/<YYYY>/<key>.md`), regenerates `<dir>/README.md` over the whole folder with the repository named on a row that belongs to one, and commits them; then one senior review judges the pull request. A report the store overwrote replaces the folder's copy, and a file the folder holds and the store does not is **left alone** and named in the run's record — a run never takes a report away. When every stored report is already in the folder with the same bytes the run ends without a pull request rather than opening an empty one. The step is the runner's own, so the job image must be 0.26.0 or later (section 1). | Committing this project's stored reports into the repository the owner designates (D2750), from that repository's own checkout, one run per launch (`fugaro run --recipe commit-reports`). Never the recipe for a task: it commits records rather than code, and a run whose project designates no repository — or one other than the repository the run stands in — is refused before its first stage. The owner sets the designation (`reports_commit.repo`, and `reports_commit.dir` for the folder, `docs/fugaro-reviews-mirror`, a folder `run-digest` never writes, unless the project says otherwise) in the owner's own local project config and publishes it with `fugaro project policy publish`: a repository's own `fugaro.yaml` cannot carry it, because the run's own agent writes that file. **A committed report is the stored document and nothing else:** the period's figures and the runs behind them, the failing tests' names and the findings' text a review wrote, the run ids a flagged row is actionable by, the stage and recipe names, and the cost — and **no person, no address, no task text, no log line and no credential**. That list is closed, so designating a public repository is a choice you can weigh rather than a risk this page leaves to a guess. |
| `troubleshoot` | `mode: artifact`; `diagnose: {}`; `outputs: { globs: ["out/diagnosis.md", "out/diagnosis.json"] }`. One model stage reads the evidence a failed command left and writes the answer's two files (section 1). No coder pass, no review and no pull request, and the stage's own per-call output bound — 10000 tokens — is the recipe's rather than the knobs'. | The cloud tier of `fugaro troubleshoot` launches it, on this machine's own project, when the machine has no login of its own. Never the recipe for a task: it diagnoses one failure and delivers the answer as a file. |
| `escalate` | `review: { max_rounds: 1, hand_over: true }`. One `implement` pass and one review, with no fix (section 1). | A pull request that needs one stronger single pass rather than another fix loop: the review's verdict is the run's own, and the findings it left are for whoever reads it rather than handed back to the coder. The escalation ladder's rung 1 launches it, and it is one of the 0.23.0 constructs (section 9). |
| `rebase` | `rebase: {}`. The step is the whole run: the job fetches the base, puts the pull request's branch on it, resolves the conflicts with the coder's model, re-runs the tests and pushes the branch. No coder pass and no review (section 1). | Rung 0 of the ladder: a pull request that has fallen behind its base and needs nothing else. Launch it as a follow-up on the pull request (`--recipe rebase --pr N`), in a repository whose workflow has `commands.test`; a conflict no stage resolves ends the run refused, with the reason and the conflicted paths, having pushed nothing. One of the 0.23.0 constructs (section 9). |
| `merge-judge` | `mode: evaluate`; `merge_judge: {}`. The step is the whole run: a read-only stage that reads the head's diff, the findings the ladder still has open there and the fundamentals checklist, and answers `merge_with_follow_ups` — naming the leftovers, each with its importance — or `blocked`, naming the fundamental issue in the way. The stage runs with no tool and no setting source at all, over a brief its launcher left under the run's own prefix; the run has no checkout, no repository command, no push credential and no pull request of its own. | Rung 3 of the ladder: a pull request no further round will move, at a head a scored review verdict already covers. The escalation ladder's launcher starts the judge run and leaves the brief it reads, so a launch that left no brief — any launch that is not the ladder's own — is refused at bootstrap, naming the brief. The judge is advisory in one direction only: its verdict can veto a merge and can never cause one — the deterministic gate is what merges — so an absent, failed, timed-out, budget-exhausted or unreadable verdict is itself the veto, and a head the judge never answered for is a head rung 3 did not clear. Its `mode: evaluate` is the 0.24.0 construct and its `merge_judge` step the 0.25.0 one (section 9). |

Only the catalog's own `default` follows `agent.first_line_review`. Every other recipe, including a `default` you define yourself in the repository or the project, is taken as written: a `first_line` step in it always runs.

`use_when` is required for every catalog recipe but `default`. A repository or project recipe without one gets a `fugaro recipes ls` note ("the routing skill matches on use_when, add one"): the routing skill falls back to `description`, but a good `use_when` is what it actually matches the task against.

Every catalog recipe is launchable. `commands.lint` and `commands.fix` exist in `fugaro.yaml` (validated, schema'd); a `check` step is executed by the runner as a gate before `implement` (so `test-and-fix` and `lint-fix` run), and `mode: review` is executed directly, in place of `implement` (so `review-only` and `pick` run) — section 3. `run-digest` is the one whose job image has to be new enough for the step it starts with: the `digest` step is the runner's own, so a launch of it against a job image older than 0.13.0 is refused at your terminal, naming that release, before anything runs. The digest is not one of the business-licensed parts: it is part of the MIT core, so a job image built without the `ee` tag runs this recipe all the same, and the only gate over it is the version above. It is also the one recipe a follow-up never runs: `--pr` and `--retry` are refused for it, before any cloud work (section 8). `escalate`, `rebase` and `merge-judge` are the three whose job image has to be new enough for what they carry (`hand_over` and the `rebase` step, 0.23.0; the `merge_judge` step, 0.25.0; section 9): a launch of any of them against an older image is refused at your terminal, naming that release, before anything runs. The judge's step and its `mode: evaluate` are a release apart, and the newer of the two is the step: 0.24.0's runner reads the mode the judge's task carries and has no `merge_judge` step, so an image at that release would start the run and refuse the recipe at bootstrap. `troubleshoot` is the fourth: its `diagnose` step is the runner's own, so the cloud tier's pre-flight refuses a diagnosis against a job image older than 0.26.0, naming that release and `fugaro update`, before the evidence is uploaded and before any job exists (section 9) — and it is the one recipe no person launches by hand, so the gate a hand launch meets is the runner's own at bootstrap, not this one. `commit-reports` is the one catalog recipe whose launch stands in a particular checkout: the designated repository is the only place a report may be committed, so the recipe is launched on that repository's own checkout (`fugaro run --recipe commit-reports`), the reports are committed under the identity and branch that repository's runs already use, and a run in another repository is refused before its first stage, naming the designation. Its step is the runner's own too, so its job image has to be 0.26.0 or later: an older image's runner has no `commit_reports` in its version 1 step list and refuses the recipe as `is not a step type`. `rebase` is the one catalog recipe that is only a follow-up: it has a pull request's branch to put on its base, so a first run of it is refused at bootstrap, and it is launched with `--recipe rebase --pr N`. `merge-judge` is the one only the ladder can launch: the brief it judges is left under the run's own prefix by the escalation ladder's launcher, and a launch that left none is refused at bootstrap, naming that brief — so until the ladder ships, a hand launch of it is refused rather than run against nothing (section 9).

## 3. Review mode, pick, and artifact mode

`mode: review` (default `mode: implement`) means the recipe has no `implement` and no `fix`: exactly one `review` step, `max_rounds: 1`, and no `roles` (there is no coder step to map them onto). `review-only` and `pick` are both `mode: review`; the difference is how they are launched, not the format.

`fugaro review --pr N` is `review-only`'s second spelling, and the one the independent cloud senior review is launched by: it resolves the same catalog recipe and builds the same task, and runs it on a review-only job **variant** — the sibling job `fugaro update` deploys beside the repository's coding job, and, where its workflow resolves no shared project job (a baked workflow, or a project that publishes no `profiles:`), the installation's implicit default review-only job, which the same command deploys for the project so that a review needs no profile: either carries the `-review` suffix in its account segment and mounts no credential of its own, its verdict being signed by the installation's credentials service rather than by a key in the container. It takes exactly one `--pr`, and the account it runs as is the repository's own (`agent.oauth_token`, else the project's `default_claude_account`); `fugaro review show RUN` prints the verdict artifact and its markdown back, since the review posts nothing on the pull request itself. It is **in the command tree**, and since 2026-11-08 the launch is admitted with it: what a launch still checks is that the installation's credentials service is enabled — an installation without one is refused with a sentence naming the two commands that supply it — and that the installation is one whose service admits the review job's own caller (E7's second half): the binary carries the class as a constant that was flipped once the service read `FUGARO_REVIEW_JOB_ACCOUNTS` and every `fugaro update` deployed it, and the installation's own release is judged from the image its own `fugaro update` pinned for the credentials service — the record that command writes on every run, rather than a base image an update outside a checkout never moves — so an installation whose service predates 0.21.0 is refused with a sentence naming `fugaro update` (`docs/cloud-senior-review` §6's CSR11; the owner's live checks are still unrun, so the release that carries the flip is the one whose notes say the launch is admitted rather than that the check passed). A job image built from a release older than 0.20.0 is refused too, naming that release and `fugaro image refresh`, since the variant and the marker a review launch sets are what the image's runner has to know; `fugaro validate` notes E7's missing halves on an installation that has named a Claude account.

A `mode: review` recipe always needs `--pr` (`fugaro run --recipe NAME --pr N`, repeatable): it reviews **any open pull request of the repository, not only Fugaro's own**, and is never a follow-up (`--pr` without a mode: review recipe keeps its older, follow-up meaning — section 5). `review-only` needs exactly one `--pr`; `pick` needs 2 to 4 (it has nothing to compare one pull request against); either count is refused, by name, before any checkout — a custom `mode: review` recipe under any other name is unconstrained beyond `--pr`'s own 1-to-4 range. TEXT, or `--task-file`, is optional then too, the same "adds instructions" rule a follow-up's own `--pr` already follows: it is appended to the review's prompt, trusted launcher text rather than anything read from the reviewed checkout. The runner:

- checks out each pull request's head read-only (fetched by commit, never a branch of its own) and reads `fugaro.yaml` from the base branch, like a follow-up does — never from the pull request's own tree, which a follow-up doesn't trust either. On GitHub this works for a fork too, since GitHub keeps `refs/pull/N/head` on the base repository whether or not the head is in a fork; Bitbucket's pull-request API gives only an abbreviated (12-hex) commit hash, which `git fetch` cannot resolve on its own, so it is resolved to the full hash with one more call to Bitbucket's own commit endpoint first — **unverified** against a real Bitbucket repository (only the fake's), and worth checking by hand before relying on it, same as the rest of this provider's support;
- refuses a pull request that is closed or merged, and is **trusted-author-only** (owner ruling 2026-10-13): it reviews a pull request only when the author's LIVE `author_association` (GitHub's own, read fresh on every run) is owner, member or collaborator, or the author is Fugaro's own identity on a pull request it opened itself — fork or not; an outside contributor's pull request is refused outright, with no flag to let one through. The base branch's `followup.trusted` (the account-ID list a follow-up's own comment trust also consults) is **not** one of these signals: a follow-up's trust is that list AND a live collaborator check together, but review mode's is the live association ALONE — a name on the list with no current association (a removed collaborator, say) is still refused. A **trusted** author's own fork is reviewed only when the fork repository's owner is that same trusted author, so a shared or organizational fork can't carry someone else's commits under a name the trust check never sees. Bitbucket has no `author_association` at all: review mode accepts only a same-repository branch there (pushing one already needs write access) and refuses every fork. The refusal is reported on the pull request itself (a comment naming the reason), not only in Fugaro's own run record;
- runs the one `review` step with no git credentials, no `GH_TOKEN` and none of the workflow's `secrets:` in the agent's environment at all (the same rule a follow-up's agent already follows for git): it only ever reads the checkout;
- deletes every `.claude` and `.claude-plugin` directory, at any depth, whole (`.claude/commands` included, not only `settings.json`, `settings.local.json`, `agents` and `skills`; `.claude-plugin/plugin.json` is the same mechanism, this repository's own plugin included), plus `.mcp.json`, `CLAUDE.local.md` and `CLAUDE.md` at any depth, from every checkout it makes (the single pull request, or each of `pick`'s worktrees) before the review stage starts: a fork's own hooks, subagents, skills, slash commands, MCP servers or plugin manifest are configuration the headless agent would otherwise run, not text it merely reads, and `CLAUDE.md` is instructions the session loads rather than text it merely reads either. The reviewer is given the base branch's own instructions in their place, read read-only out of the base ref — its `CLAUDE.md` at any depth, and the root `.claude/rules/` — never anything out of the reviewed checkout, and never the head's copies as a fallback when the base has none;
- runs the review stage with a `HOME` of its own — an empty directory under the run's state, so a user-level settings file baked into the job image contributes no rule to the session either — while the toolchains keep the paths they have in the image: mise's installs, config and cache, and the Go and npm caches beside them, are named explicitly in the stage's environment, because the shims on `PATH` resolve their installs through `HOME` and find none under a fresh one;
- restores no build or test cache into the checkout and writes none back (a fork's dependency lockfile, or anything it plants under a cached path, must never be saved under the key it computes, which a later trusted run on the same repository would then restore and execute);
- posts one comment per pull request (`Provider.Comment`, redacted, capped at 60 KiB) naming the recipe and the verdict (`Fugaro review (review-only): ship`, or `changes` with the findings); a `pick` run's comment also names which pull request to keep (`keep #N`) and is posted, identical, on every one it compared;
- never pushes, and never opens, updates or changes the draft state of any pull request;
- ends the run with a new outcome, `reviewed` (`result.json`'s `reviewed` array names each pull request, its commit and the verdict).

**Trusted-author-only is not a sandbox. Read this before relying on it.** The checks above (closed/merged refused, the trusted-author gate, no git token, no workflow secrets in the agent's own environment, the settings/agents/skills/MCP strip) narrow who can reach the agent and what it can do; they do not sandbox it. The agent that reviews a trusted author's pull request is the same process, as the same user, in the same container as the runner itself — exactly what every first run and follow-up already is, with none of the extra scoping a real sandbox would need. Concretely:

- the agent runs with every permission prompt turned off (Claude Code's own "dangerously skip permissions" mode, like every other run) and reads text the pull request's author fully controls (`CLAUDE.md`, the diff, code comments, commit messages): **one line of prompt injection is code execution**, not a theoretical risk needing a separate vulnerability — trusted-author-only narrows *who* can place that line, not what it can do once it's there;
- that code runs as the runner's own user, which can read the runner's environment through `/proc` (SECURITY.md): every workflow secret, the GitHub App's private key (which can mint a token for **every repository the App is installed on**, not only this one), the real model and provider keys, and the job's service account through the metadata server are all reachable this way, whether or not any of them is in the agent's own environment;
- **network egress is open**, so code running under that identity can send any of the above anywhere it likes. Redaction (the posted comment, the report, transcripts, logs) only masks what Fugaro itself publishes; it is not a network exfiltration barrier, and does nothing once the secret has left the container on its own;
- with the job's service account token, that code can also write directly to the runs bucket's cache prefix for this repository, bypassing the runner's own code entirely — the cache-read/write guard above stops the *runner* from restoring or saving a poisoned cache, but it cannot stop a trusted author's code that is already running from writing the cache object itself.

**"Member" and "collaborator" are GitHub's own categories, and are broader than they sound.** A MEMBER is any member of the organization that owns the repository, even one with no access to this particular repository at all; a COLLABORATOR can be a read-only one. A follow-up's own comment trust also uses these, but ANDs them with `followup.trusted`'s own account-ID list; review mode's trust is the live association ALONE, with no list at all — simpler, and never stale, but also never narrower than "whatever GitHub currently says this account is". A stricter check — the collaborator's actual permission level (`GET /repos/{owner}/{repo}/collaborators/{username}/permission`) — is possible future hardening; the App permission it would need is unverified, so it is not done.

**Trusting a person also trusts what they, in turn, let happen to their own pull request or fork.** Review mode's check is "is the fork's owner a trusted author", not "is every commit on it theirs":
- a trusted author's own fork can have OTHER collaborators pushing to it (a fork is a repository of its own, with its own collaborator list, independent of the one above); review mode has no way to tell their commits apart from the trusted owner's;
- GitHub's "allow edits by maintainers" on a pull request lets the base repository's maintainers push to the fork branch directly — again, commits review mode cannot tell apart from the trusted author's own;
- a trusted author's own BRANCH (same-repository case, no fork involved at all) can have someone else's commits merged into it before review mode ever reads it; the branch's owner being trusted says nothing about who authored every commit reachable from its tip.

None of this is checked today: trusting an author's PR trusts everything reachable from its head commit, not only commits that account itself wrote.

Do not run Fugaro's review mode against a repository whose GitHub/Bitbucket App installation or job holds secrets worth protecting, for anyone whose trust you would not extend to the repository's own secrets — the App's private key, provider keys, or anything else you would not hand to that person directly — until Fugaro has real process isolation for reviewed code (a separate, unprivileged user with no inherited environment, no metadata-server route and no open egress; none of that exists today).

The model credential reaching the agent (`cfg.Agent.auth`, needed for the stage to run at all) and a pull request's own text being untrusted prompt injection (`CLAUDE.md` included: a first run or follow-up loads it as instructions, review mode strips it and shows it as diff content) are not special to review mode: they are true of every run. What review mode's trusted-author gate narrows is *who* can trigger that exposure at all — an outside, untrusted pull request is refused before any of it, fork or not.

`review-only` reviews one pull request, checked out in place. `pick` compares 2 to 4: each head gets its own directory (a git worktree), and the prompt lists them so the agent reads every one before naming which to keep. `fugaro run --attempts N` (2 to 4) launches that many independent runs of the same task, under one batch label, so `pick` has something to compare once they have all opened a pull request; `pick` itself only ever needs the pull requests its own `--pr` already names.

A follow-up (`fugaro run --pr N` with no `--recipe`, or one naming an ordinary recipe) never runs a `mode: review` recipe, even one it would otherwise inherit from the pull request's own history (a prior run's recipe, or the one the runner chose for it): `fugaro run` refuses it before any cloud work, since a follow-up only ever continues a pull request Fugaro itself opened, which `mode: review` never does.

A report recipe is refused for the same two shapes of launch, and before any cloud work: a follow-up never inherits the `digest` step (section 2) from the pull request's history, and `--retry` refuses a run whose recipe holds it. A report run opens on its own — the launch lists the records it may read and refuses it while another report run of the repository is going — and a follow-up carries no such listing at all, while a retry carries the one its *first* launch listed, stale by however long the retry took. Either would write the reports of a repository whose records it never read, beside a report run already going. The fix is the launch a report run is meant to be: `fugaro run --recipe run-digest "TEXT"`.

**`mode: artifact` is the other mode with no pull request**: the run's deliverable is a file it uploads to the runs bucket instead of a branch and a PR, and you fetch it back with `fugaro artifacts get`. The recipe names the agent stage, the render step and the deliverable's own `outputs` block, and the workflow's `fugaro.yaml` carries the commands it runs:

```yaml
version: 1
name: sizzle
description: Render a short video from attached screenshots with ffmpeg.
use_when: You have screenshots (or frames) and want a video file back, not a pull request.
mode: artifact
steps:
  - plan: {}       # the agent writes the render plan; no push, no git token
  - render: {}     # deterministic: runs the workflow's commands.render
outputs:
  globs: ["out/*.mp4"]
  max_files: 8
  max_bytes: 268435456        # each artifact
  max_total_bytes: 2147483648 # the whole set
  probe: probe                # names the workflow's commands.probe
```

Launch it with `fugaro run --recipe sizzle --attach screenshot.png`, which uploads the file to the run's own `inputs/` and is refused unless the recipe really is `mode: artifact`. `plan`, `render` and `diagnose` are the only step kinds it may use: `plan` and `render` are the render shape, with `render` last, and a recipe that names `diagnose` instead of `render` is the diagnosis shape (the catalog's `troubleshoot`, section 1) — one model stage that writes the files `outputs` names, alone or after one `plan` — and `steps: [render: {}]` alone is legal, a recipe that calls no model at all. `implement`, `first_line`, `bounce`, `roles` and a carry-over of the ordinary loop are refused: there is no PR to loop around. Neither command comes from the recipe (a recipe never names a command): the render runs the workflow's `commands.render` and the optional probe runs its `commands.probe`, both read from `fugaro.yaml` at the task's ref, and a render step with no `commands.render` — or `probe: probe` with no `commands.probe` — is refused before the first step. Write `commands.render` as the script itself, an inline `|` block: a command that names a file in the checkout runs that file's working-tree bytes, which the plan stage could have rewritten. The rest — the caps, the probe's interface, `--attach` and where the files go — is [artifact-runs.md](artifact-runs.md).

## 4. Loop knobs stay outside the recipe

`agent.first_line_rounds` (1 to 3, the cheap rounds) and `agent.review_rounds` (1 to 10, the senior rounds; with `bounce`, the number of bounce-backs is `review_rounds - 1`) are the knobs a recipe's own `max_rounds` overrides, never the other way around (section 1). Leaving one out, or writing 0, runs the rigor mode's own row instead of a fixed pair (0.15.0): poc 1/1, startup 2/2, pro 3/3, critical 3/5, hotfix 1/1. A repository that sets neither knob and configures no mode therefore runs pro's 3/3, where it ran 1/2 before — set both keys, or a `defaults.rigor.default` in the project layer, to pin what a repository runs. The catalog recipes above set no `max_rounds` (`review-only` and `pick` excepted, which `mode: review` pins to 1, and `run-digest` and `commit-reports`, whose one review round is the report run's own shape rather than a knob), so tuning the loop in `fugaro.yaml` or the project layer keeps you on a built-in recipe. A custom recipe can still pin its own rounds.

`agent.review_stop_fraction` (0 to 1, 0.8 when unset) is the share of the run's total time budget after which the loop starts no new review or fix round and goes to finalize — the *time* half of the stop, whose other half is the mode's review rounds being spent (section 1). It is where a run's remaining findings are left to the mode's stop rule rather than bought another round for, so it is a repository or project layer key like the two round knobs above, never a recipe's. It needs fugaro 0.22.0 or later in the job image that runs it: both files are decoded strictly, so the key alone refuses an older runner at bootstrap, whatever it says (`review_stop_fraction: 0` included), and `fugaro run` refuses such a launch naming the image to move.

The most model stages a run of a recipe can start is `implement + 2·f + n·(2 + 2·f) + n₃·(2 + 2·f)`, where `f` is the first-line rounds, `n` the senior rounds and `n₃` the adversarial rounds — the step's own `max_rounds`, or the rigor mode's senior row where it writes none, which is the same number that mode's senior loop starts from (1 at poc and hotfix, 2 at startup, 3 at pro, 5 at critical); the last term is `n₃·2` for an `adversarial` step with no `bounce`. Each term is one review and its fix, plus the cheap loop a bounce inserts. A `check` step and an artifact recipe's `render` are runner commands with their own timeout, so they are not model stages and do not count, and a `digest` or `commit_reports` recipe starts no `implement` stage at all. Today's `standard` with `agent.first_line_rounds: 1` and `agent.review_rounds: 2` — the pair every mode ran at before 0.15.0 — bounds a run at 11 stages, and the same recipe with `adversarial: { max_rounds: 2, bounce: first_line }` at 19. Leave the knobs unset and the mode's row sets `f`, `n` and `n₃` together, so `standard` is 31 stages at an unconfigured repository's pro and 55 with the step at pro's senior row. `fugaro budget preview` quotes this number.

## 5. Choosing a recipe

The first of these wins:

1. `fugaro run --recipe NAME`
2. `agent.recipe: NAME` in `fugaro.yaml`
3. `default`

`agent.recipe` applies to first runs only. A follow-up (`fugaro run --pr N`, one PR, no `mode: review` recipe named) keeps the recipe of the run it continues unless `--recipe` names another — never one that is `mode: review` (section 3). `--recipe NAME --pr N` where NAME is `mode: review` is not a follow-up at all: `--pr` then means which pull request(s) to review (section 3), and is repeatable.

`fugaro run` prints one line to stderr before it launches: `recipe: <name> (<source>)` when the CLI resolved the recipe; `recipe: default (catalog)` when it resolved the catalog `default`; and `recipe: chosen by the runner (agent.recipe in fugaro.yaml at <ref>, else default)` when you launch with no `--recipe`, there is no local checkout of the repository, and the project has no recipe named `default`. In that case the CLI validates nothing about `agent.recipe` locally: the runner reads it at the ref, so a malformed or unknown recipe fails in the run, not at your terminal, and a project recipe other than `default` is not found there (name it with `--recipe` instead). If the project has a `default`, the CLI embeds it and the line reads `recipe: default (project)`.

## 6. Where a recipe comes from

For a name, the first match wins:

1. The project's copy of the repository's own recipe: `fugaro/recipes/<name>.<readable>-<8 hex>.yaml` in the runs bucket, the name the repository's `.fugaro/recipes/<name>.yaml` took when `fugaro update` published it and the name clashed. A name nothing else answered is published flat, under rule 2. A run never reads a checkout's `.fugaro/recipes/`: the copy is what every run of that repository gets, in a checkout or not, and it is listed under its own name.
2. The project's flat store: `fugaro/recipes/<name>.yaml` in the runs bucket `fugaro-runs-<gcp_project>`, for every repository of the project.
3. The catalog.

A repository that still holds `.fugaro/recipes/<name>.yaml` on its default branch and has no migration record — `fugaro update` never ran over it, so the copy above was never published — is refused at the launch, naming the repository, the recipe and the fix: list the repository in the project, then run `fugaro update` in your own terminal. That is the one case where a run would otherwise change silently under a repository the update could not list. A repository with a record launches as before, and so does one whose default branch holds no such file.

A name another repository of the project already resolves to different text — another repository's file, an existing project recipe, or a catalog recipe — is a **clash**, and `fugaro update` never lets one repository's copy change another's runs: each clashing copy is renamed `<name>.<readable>-<8 hex>` (the readable half of the repository's slug and eight hex of its hash), which is the name rule 1 above looks up for the repository that wrote it. A name nothing else answers is published flat. `fugaro update` prints one line per rename; no admin step follows it.

A name the 0.7.0 catalog retired (`cheap-loop-senior` -> `standard`, `claude-solo` -> `solo`) is refused with its replacement ("`cheap-loop-senior` was renamed in 0.7.0: use `standard`") once the project defines no recipe of that exact name; a project recipe of the old name still wins, exactly as any other name would.

A project recipe named `default` replaces the catalog's `default` for the whole project. It is then an ordinary recipe-carrying launch: it is embedded in every task, so every launch needs 0.5.0 job images, or 0.7.0 if its text uses a construct from section 1 (section 8). The file name must equal the recipe's `name:`. A name is 1 to 40 of `a-z`, `0-9` and `-`.

When the CLI resolves the recipe (`--recipe`, or a local checkout), it does so before any cloud work, so a malformed, unknown or renamed recipe fails at your terminal with the path of the problem. A project recipe — a repository's own copy included — is embedded in the task with its sha256, and the run record (`result.json`) records its name, source and sha256; the catalog `default` is deliberately not embedded (so a default run needs no 0.5.0 runner), except when `--recipe default` must override an `agent.recipe` that could apply. A task that carries a repository recipe by name alone (`source: repo`) is a follow-up keeping the recipe of a run launched before that repository's recipes were published as the project's copies: the runner refuses it at bootstrap, with the upgrade and `fugaro update` as the fix, and it never falls back to `default`. Repository defaults and workflow profiles use the same publishing model: see [project-layer.md](project-layer.md).

## 7. Commands

- `fugaro recipes ls` lists the project's recipes and the catalog, and which one wins for each name. It does not read a checkout's `.fugaro/recipes/`, and says so when you run it in one: a repository's own recipe is the project's copy of it, published by `fugaro update`, and the copy is listed here under its own name. `--verbose` also prints each recipe's `use_when` and `steps`; `--json` always carries both, plus `launchable` (a boolean, `false` only for a recipe with a parse problem, which `problem` then names): the routing skill reads it so it never picks a recipe only to have `fugaro run` refuse it.
- `fugaro recipes show NAME` prints the recipe a run would get, the layer it comes from and its sha256.
- `fugaro recipes validate FILE` checks a recipe file; it needs no cloud access.
- `ls`, `show` and `validate` take `--json` for machine-readable output.
- `fugaro recipes publish FILE` writes the file to the project as `fugaro/recipes/<name>.yaml`. It shows what it replaces and refuses to overwrite a concurrent change. A coding agent's session runs it like any other command. It is an operator command: once an operator has applied the 0.7.0 bucket hardening ([bucket-iam/spec.md](bucket-iam/spec.md)), launchers read the runs bucket but write only `runs/`, `tokens/` and `issues/` (the sealed budget token and a launcher's own issue, neither of them a publish), so a launcher's publish is refused with the operator-role message and nothing is written. Project recipes need the default-named runs bucket (`fugaro-runs-<gcp_project>`); with a custom-named bucket, `publish` is refused with a note that gives the required name, and `ls` and name lookups skip the project layer and print the same note.
- `fugaro recipes rm NAME` removes one of the project's recipes. A repository's own recipe is the project's copy of it, so this is how a migrated copy is removed; publishing a file of the same name is how it is replaced. Like `publish` it is an operator command and a coding agent's session runs it too, and it refuses to remove an object another publisher changed while it ran. Removing a name the catalog also has is not an error: it then resolves to the catalog's recipe again.
- `fugaro validate` also checks the repository's `.fugaro/recipes/` and warns when `agent.recipe` is set, including when it names a renamed catalog name (see section 8).

A published project recipe is cached on each machine for 24 hours (up to 7 days when the bucket cannot be reached, with a note), so another machine's `fugaro run` may launch the old text for up to 24 hours. `ls` and `show` refresh the cache; `fugaro run` does not.

`fugaro watch` shows the recipe name of a run that does not use `default` beside its models, in that run's expanded detail (space on the row): the run table itself has no MODELS column, and `fugaro watch --json` carries the recipe too. `fugaro runs ls` adds a RECIPE column once any listed run is not `default`; the column then has a value on every row, `default` included.

## 8. What is refused

A recipe that uses a reserved key is refused with a message that says so:

- `checks` as a step name: the step type is `check`, not `checks`.
- `goto` and `on_reject`: no general jumps between steps. (`review: { bounce: first_line }`, section 1, is the one bounce the format allows, and only back to a `first_line` step already in the recipe.)
- `extends`: copy the recipe instead.
- `on_pass` and `on_fail`: outcome rules are not configurable.
- `model` and `models`: a recipe never names a model; models come from `agent.models`.
- any role other than `reviewer` or `coder`; any `reviewer` value other than `coder`; any `coder` value other than `reviewer`; and both mapped at once (`reviewer: coder` and `coder: reviewer` exclude each other).
- `by_level` that is not a mapping ("must be a mapping such as {poc: {roles: {coder: reviewer}}}"), a key inside it that is not a level ("must be a rigor level: poc, startup, pro, critical, hotfix"), an entry that is not a mapping ("must be a mapping holding roles"), an entry with no `roles` key ("must set roles: a by_level entry is the level's role mapping"), or any key inside an entry but `roles` — the cap and the loop's shape are not the level's to change, so a budget word written there is refused for what it is rather than read as a bound ("a by_level entry can set roles only: the cap a run gets is its level's own, and the loop's shape is the recipe's"). An entry's own `roles` is checked exactly as the top-level key is, for the same reasons and with the same messages, and `by_level` is refused where `roles` is: `mode: artifact` and `mode: evaluate` have no agent steps to map roles onto ("remove by_level").
- `check.command` other than `build`, `test` or `lint`; `autofix` on anything but `command: lint`.
- `outputs` on a recipe that is not `mode: artifact` ("is only for `mode: artifact`"), and `mode: artifact` with no `outputs` at all ("is required for `mode: artifact`").
- `roles` on a `mode: artifact` recipe: it has no agent steps to map them onto.
- `plan`, `render` or `diagnose` in a recipe of any other mode ("is only for `mode: artifact`"), and `check`, `first_line`, `digest`, `review` or `adversarial` in a `mode: artifact` one ("is not a step of `mode: artifact`") — an artifact recipe takes one `render` or one `diagnose`, optionally after one `plan`, and nothing else.
- `diagnose` twice ("diagnose may appear at most once"), or beside a `render` ("mode: artifact takes one render or diagnose step, optionally after one plan step"): one diagnosis to a run, and the outputs block names the one deliverable it delivers.
- `adversarial` anywhere but after `review` ("adversarial must come after review"), twice ("adversarial may appear at most once"), in a `mode: review` recipe (which allows exactly one `review` step and nothing else), or before a step that is not the last one ("review must be the last step, or the adversarial step after it"). Its `bounce` may only be `first_line` ("bounce can only be first_line"), and needs a `first_line` step before it ("bounce: first_line needs a first_line step before the adversarial step").
- `digest` anywhere but first ("digest must be the first step"), twice ("digest may appear at most once"), in a `mode: review` recipe ("digest is only for `mode: implement`"), or followed by anything but the one `review` step ("digest must be followed by one review step") — an `adversarial` step after the review included, since the report run's shape is exactly those two steps.
- `hand_over` on anything but `true` ("hand_over can only be true"), beside `bounce: first_line` ("hand_over and bounce: first_line exclude each other"), on a review an `adversarial` step follows ("hand_over ends the run at the review: no adversarial step may follow it"), or in a `mode: review` recipe ("mode: review has no fix round to skip: remove hand_over").
- `rebase` twice ("rebase may appear at most once"), beside any other step ("a recipe with the rebase step holds it alone: the step is the whole run"), or in a recipe that is not `mode: implement` ("rebase is only for `mode: implement`"). A `rebase` recipe also needs `commands.test` in the workflow's `fugaro.yaml`: the step re-runs the tests before it pushes, and a repository that has none is refused rather than pushed on a guess. A first run of it is refused at bootstrap, since there is no pull request's branch to rebase.

There are no task-shaped catalog recipes (fix a bug, add a feature) yet.

`fugaro run` also refuses, separately from the parser, two launch-shaped mismatches between `--pr` and the recipe (section 3): a `mode: review` recipe with no `--pr` at all ("recipe NAME is mode: review, which only reviews pull requests; launch it with --recipe NAME --pr N"), and a follow-up (`--pr` naming no `mode: review` recipe of its own) that would inherit one from the pull request's history ("recipe NAME is mode: review, which only reviews an existing pull request and cannot continue one"). The third is the report recipe's (section 2), and it has a second message for `--retry`: a follow-up (`--pr` continuing a pull request whose recipe holds the `digest` step) is refused with "recipe NAME writes this repository's run reports, and a repository has one report run at a time; a follow-up carries no manifest of the records it may read and skips the in-flight check a fresh launch makes, so it cannot use it — schedule a report run of its own with fugaro run --recipe NAME", and `fugaro run --retry RUN` on a report run with "run REPO/RUN is a report run, and --retry launches the task of its first launch as it stands: its manifest is stale by now, and a repository has one report run at a time, because both would write the same reports — launch a new report run with fugaro run --recipe NAME". A follow-up carries no listing at all and a retry carries the first launch's, so neither has the records a report run writes its reports from. Several `--pr` (`pick`'s case) need an explicit `mode: review` recipe too, and at most 4.

## 9. Rolling out 0.5.0, 0.7.0, the `adversarial` step and the escalation recipes

Order matters:

1. Upgrade every CLI, every CI pin and every workflow's job image to 0.5.0 **before** you merge `agent.recipe` into `fugaro.yaml` or launch a non-default recipe; to 0.7.0 **before** you launch a recipe that uses `use_when`, `mode`, `roles.coder`, a `check` step or `bounce` (every catalog recipe but `default` does); to 0.16.0 **before** you launch a recipe with an `adversarial` step; to 0.23.0 **before** you launch `escalate`, `rebase` or any other recipe that hands a review over or holds the `rebase` step, and to 0.25.0 **before** you launch `merge-judge`, whose `merge_judge` step is a kind no older runner's step list knows — its `mode: evaluate` alone is 0.24.0's, and a 0.24.0 runner reads the mode, admits the launch and then refuses the step — and to 0.27.0 **before** you launch a recipe with a `by_level` block, whose key no older recipe reader knows. A binary older than the one you need refuses the new keys as unknown, and an older runner rejects a task that carries a recipe using them. `fugaro validate` warns when `agent.recipe` is set.
2. `fugaro run` checks the workflow's build record and refuses a recipe run (or a checkout that sets `agent.recipe`) on a job image too old for what it carries. The fix is `fugaro update` in the repository's checkout, in your own terminal window (a non-terminal session — a pipe, `--json`, a coding agent's session — is refused, and there is still no `--json` or `--plan-only`). Then use the recipe. A launch of the catalog `default` carries no recipe and needs no job-image gate, unless `--recipe default` must override an `agent.recipe` that could apply; a project or repository recipe named `default` is a recipe-carrying launch and does need it.
3. `cheap-loop-senior` and `claude-solo`, the 0.6 catalog's two non-default recipes, are gone from the 0.7.0 catalog: `agent.recipe` or `--recipe` naming either is refused with its replacement (`standard`, `solo`), unless a repository or project recipe of that exact name still exists, which wins as it always did.
4. Deployed Firebase rules are updated only by `fugaro update --firebase-project <gcp-project-id>` (its Firebase stage). Until you rerun it, the dashboard shows no recipe name; the runs still work, and the run logs a warning that names that command.
5. `review-only` and `pick` are launchable, with `--pr` (section 3), like every other catalog recipe; `test-and-fix` and `lint-fix` are too, with their `check` step run as a gate.

## 10. Safety

A recipe can only choose among the existing stages within their limits. It cannot name a model, change policy or loosen a cap, so it cannot get past the model allow-list, the price table or the token and dollar caps. Budgets are not a recipe key either: the governance block (`governance.*`, which bounds a stage's own share of the run) is written in `fugaro.yaml` and in the project layer, and a recipe that writes it is refused for the unknown key it is rather than read as a bound on the run. A repository recipe is repository data, like `fugaro.yaml`: the agent could edit it during a run, but only a later run reads it. A project recipe is bucket text that anyone with write access to the bucket can change, so it is parsed strictly, size-limited and validated, and its sha256 is recorded with each run. A recipe holds no secrets. A `check` step names no command of its own (section 1): it can only point at a `commands.*` key of the `fugaro.yaml` the run already read at its ref, so a project recipe cannot make a job run anything the repository itself did not already say.
