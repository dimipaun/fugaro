# GCP setup with `fugaro init`

`fugaro init` sets up one Fugaro project's installation in a Google Cloud project with Terraform. Two names appear throughout: the **Fugaro project's name** (`<project>`, such as `aurora`: a short permanent name that every repository of the project carries in its `fugaro.yaml`) and the **GCP project ID** (`<gcp-project>`, such as `my-fugaro-dev`). It plans, shows you the plan, and applies exactly that plan once you confirm. This runbook takes a fresh project from nothing to a repository's first run, one confirmed step at a time. It also covers adopting what M4's bootstrap made, rolling back, offboarding a repository, retiring `fugaro-build`, and pushing a base image.

Design §8 says how `init` works and why (the state layout, the guard, the environment allowlist); §6.1 has the IAM it creates. This page says what to run.

**What you end up with:**

- **The installation** (`fugaro init`, once per project): the enabled APIs, the runs bucket, the base registry `fugaro-base`, the custom roles, the scheduler account, log isolation, and optionally a budget and an alert.
- **Each repository** (`fugaro init --repo`, from its checkout): its secret containers, its image registry, its build account, one job and job account per workflow, and a daily image check (a Cloud Run job and a Scheduler job).
- **The project's local config** (`~/.config/fugaro/projects/<project>.yaml`), written from the installation's outputs, with the diff shown first and the old file kept as `<project>.yaml.bak-<time>`. It also holds the project's model-spend budget and prices ("Turning the model budget on").

## The short path: `fugaro init`, then `/fugaro:setup`

In the repository's checkout, run `fugaro init` in your own terminal, then open your coding agent and run `/fugaro:setup`.

- **`fugaro init`** converges the installation (a first run names it: `--name`, `--gcp-project`, `--region`; `--create-project` and `--link-billing` create the project and link billing, each behind a confirmation you type), pins the release's base images by digest through your registry's remote repository, asks for secrets at hidden prompts in your own terminal, and wires the Fugaro plugin into the repository's `.claude/settings.json`, pinned to the release. "How every step behaves", below, says what each stage does and what it never does without you.
- **`/fugaro:setup`** reads the repository, writes `fugaro.yaml` with you (and a Dockerfile only when `image:` can't express the build), loops on `fugaro validate` and `fugaro image build --local` (Docker; without it the first cloud build is the test), and opens a pull request. Merge it, then run `fugaro init` again: that adds the repository's job, its first image build and its daily check.
- **The plugin** gives your agent five skills: `setup`, `working` (run, watch, diagnose, follow up), `routing` (cloud or local), `parallelism` (how wide to fan out) and `upgrade` (bring a checkout up to the installed `fugaro`). Commit the `.claude/settings.json` change; Claude Code installs the plugin when you open the folder in a new session and trust it. If the /fugaro: skills are not listed (for example the folder was already trusted), run `fugaro upgrade --local` in the checkout, then restart the session; `fugaro doctor` then shows the plugin as installed. (see the `plugin` stage below, and Troubleshooting at the end of this page). `fugaro doctor` checks the pin and the rest of the setup; `fugaro upgrade` moves the pin to your binary's release and updates the installed plugin (`fugaro update-skills` moves the pin alone).
- **A release binary is needed for the short path.** `go install` builds report the version `dev`: `init` then copies no release image and wires no plugin pin, and prints the build-from-checkout commands instead ("The base image, in `fugaro-base`"). Use the Homebrew cask or a release archive ([release.md](release.md#verifying-a-release)).
- **Teammates** of an onboarded repository need no setup at all ("Teammates: no setup", below).

## Manual setup

The steps `fugaro init` and `/fugaro:setup` do for you, one by one, and what comes after. Each points to the section with the detail.

### Stand up the installation (once per project)

```bash
fugaro init --name <project> --gcp-project <gcp-project> --region <region>
```

Read "Preconditions" first, then "The steps", 1 to 3. `--plan-only` shows the plan and applies nothing; `--json` prints each stage and what is left for you; exit 0 is done, 1 refused or left for you, 2 a cloud failure.

### Set up a repository by hand

Write `fugaro.yaml` yourself, starting from `fugaro config example`, check it with `fugaro validate` (and `fugaro image build --local` when you have Docker), and merge it. Then, from the checkout, in your own terminal:

```bash
fugaro init --repo                    # its secrets, registry, job and daily image check
fugaro init                           # asks, hidden, for the secrets the repository's jobs mount
fugaro secrets set anthropic-api-key  # or one secret by hand: from stdin or a hidden prompt; only needed when a call goes direct to Anthropic (below)
```

For a GitHub repository pass `--github-app-id <id>` the first time; the App and its four permissions are precondition 10. Step 4 ("A repository") is the full sequence, the first billable build included.

### Run, watch, diagnose

```bash
fugaro run "add a --verbose flag to the export command"
fugaro runs ls                      # runs, newest first; --watch redraws until they settle
fugaro logs -f <run>           # <repo-slug>/<run-id>, or a bare run ID
fugaro diagnose <run>          # status, failed tests, review findings, last message, cost, PR
fugaro cancel <run>            # the runner finalizes first; the draft PR stays
```

Every run that pushed ends in a pull request, a draft one if it failed. The draft appears at the run's first checkpoint push (within about a minute of its first commit), marked not verified, and shows the run's progress ([git-providers.md](git-providers.md#checkpoint-pushes-gitprcheckpoints)); the configured reviewers are requested only when it becomes ready (`git.pr.early_draft`, [git-providers.md](git-providers.md#early-draft-prs-gitprearly_draft)), so a failed, halted or cancelled run notifies no reviewer: watch `fugaro runs ls` for those. Checkpoints need 0.5.1 everywhere: older CLIs and job images reject or ignore `git.pr.checkpoints` (`fugaro image refresh` updates the image); on a host without draft PRs set `git.pr.early_draft: false`. To act on review comments, continue the PR with `fugaro run --pr N` (optionally with extra instructions as TEXT); it reads only the comments of the accounts that `fugaro.yaml`'s `followup.trusted` lists ([git-providers.md](git-providers.md#follow-up-runs-design-44)). Logs are in Cloud Logging, in Fugaro's own log bucket when log isolation is on (design §6.1, §10).

### Optional: the shared budget

With a Firebase project linked to billing, runs share project-wide caps and kill switches:

```bash
fugaro init --firebase <firebase-project-id>
fugaro budget show             # caps, today's counters, kill switches
fugaro budget set ...          # after a while in observe mode; see --help
fugaro watch                   # live dashboard
fugaro report --by week        # spend history: by day, week, month, year, repo, model or person
```

"Turning the model budget on", "Turning the shared budget on (M9b)" and "Spend history and reports (M9d)", below, are the detail.

## How every step behaves

- **Nothing is applied unseen.** `init` prints a summary of the plan (risky in-place updates first) and a `⚠ CONFIRM (project <project>, GCP project <gcp-project>): …` banner, then asks you to type the **project name** (not the GCP ID). `--yes` answers for you, and should be used only after you have read what that exact step does. Without a terminal, `init` refuses and does nothing unless `--yes` is given. **One confirmation per run in a project Fugaro owns:** when this run created the project (`--create-project`) or the runs bucket, which must be the default `fugaro-runs-<gcp project>` and belong to that project (its own project number is checked), carries a `fugaro/project.json` naming this Fugaro project and this GCP project (a read-only check; a custom runs bucket never qualifies), the ordinary steps (the Terraform applies of the installation, the Firebase root, the history job and the repository; the state bucket; the Cloud Resource Manager API; the removal of project Viewers' read access to the runs bucket; image copies that only add tags; the Firestore marks, rules and Identity Platform; the local config) share one review screen and **one** typed project name, asked when the first of them has something to change (a rerun with nothing to do asks nothing). Each step still prints its own exact plan and says it was covered. It never covers creating the project, linking billing, the Firestore database's permanent location, a Cloud Build, replacing an image tag, an unlisted repository or a secret: each is typed on its own as before. The review prints the effective launchers, operators, budget admins and viewers and the alert email, each marked as from a flag, the local config or the default, before the typed name. The state bucket and the Cloud Resource Manager API are fixed, announced and free; every Terraform plan is shown as it runs and is covered only if it consists of creates and in-place updates of the installation's own resource kinds, granting only the roles the modules use to the listed members or to Fugaro's own service accounts. The attributes are checked too: a job's image must be in this project's registry (so is a `base_images` entry that flows into a job: the review lists them and flags any outside), a scheduler must call a job of this project as a Fugaro service account, a log sink must go to this project, buckets must be private, and a budget must name the billing account the review showed. A custom role is covered only with exactly the permissions the modules give it, under the role IDs they use, in this run's projects (on a create as well as an update; the permissions are pinned in `tf/cover.go`, and a test fails when a module's list and the pin differ). A job's `FUGARO_CHECK_SPEC` must name a registry of this project and only base images in it. Anything Terraform will know only after apply (a project, a container command or args, the spec, a role's ID, project or permissions) is never covered, whatever it will turn out to be. A Firebase project other than the installation's is verified separately (its own runs bucket must carry this project's mark); if it is not, its Terraform apply and database writes ask their own typed names, and the review says which. **A separate Firebase project that has no runs bucket of its own (the usual case: nothing of Fugaro's lives there but the budget backend) can never be verified, so it always takes its own typed names**; only the installation's own project, or a Firebase project holding its own marked runs bucket, shares the run's one confirmation. Any other plan (a destroy or replace, an IAM binding or policy, a service account key, an unlisted member, a widened custom role, an unreadable plan) stops that step with its plan shown, and it asks its own typed name. A wrong name applies nothing in this or any later step; the confirmation is per run and never stored. A project that is neither created by this run nor marked (adopting an existing GCP project, a first run in an unmarked one) keeps a typed name at each step. **What `--yes` covers, and what it never does:** it covers the ordinary steps (the Terraform applies of the installation and the Firebase root, the image copy, the local config, the plugin wiring, a known repository's steps). It **never** covers creating a project or linking billing, a secret, a repository the project does not list, the Firestore database's permanent location, a billable first image build, or replacing an image tag in your registry: each of those is typed at a real terminal, and with `--yes`, `--non-interactive`, `--json` or a pipe it is left for you with the one line to run. **Under a coding agent's environment (`CLAUDECODE`, `CLAUDE_CODE_ENTRYPOINT`, `CLAUDE_CODE_SSE_PORT`, `CLAUDE_CODE_REMOTE`, `CURSOR_AGENT`, `AI_AGENT`) `init` applies nothing at all, `--yes` included**; `--plan-only` and the read-only checks still work. That is a mitigation, not a barrier: an agent that unsets its own variables is not stopped, and your own IDE terminal may set one (`CLAUDE_CODE_SSE_PORT`; the refusal tells a person what to do about that). The real controls are the typed confirmations at a real terminal for money and permanent steps, and the plugin's skills lint; the rule is to run `init` in your own terminal window. **Typed confirmations need a real terminal:** a coding agent's shell, a `!`-prefixed command in Claude Code, a pipe and most CI steps are not one, and a secret is never taken from them (see the `secrets` stage). Run `init` in your own terminal. Every command this page and `init` print is one line, so pasting it works: if a command wraps in your terminal, it is still one line.
- **`init` is a converge of stages, and a rerun is the resume.** The stages, in order, are `preflight`, `project` (only with `--create-project`), `installation`, `firebase` (with `--firebase`, else skipped), `images` (the history image with `--firebase`, the base kinds named by `--base` or by the checkout's `fugaro.yaml`; else skipped), `installation-2` (the history job, once its image exists; only with `--firebase`), `secrets`, `plugin` (the Claude Code plugin wiring) and `repository` (`init --repo` for the checkout). It prints each stage's state (`done`, `changed`, `will-do`, `blocked`, `needs-you`, `skipped`, `failed`), applies them in order with each stage's own confirmation, and stops at the first that fails or needs you: nothing after it runs. A rerun with nothing to do says `No changes` and exits 0. `--json` prints `stages`, `left_for_you` (what only you can do: `{stage, kind, text}`) and `failed` on every outcome. A stage that needs a person says what to do in one line, and `init` ends with the list. Run it from a **fresh clone of the real remote**: the plugin and repository stages act only on a repository the project's local config lists, or one you opt in (type its `owner/name` at your own terminal, or `--onboard-repo owner/name`, which must equal the origin; `--yes` and `--non-interactive` never cover it), so a cloned third-party repository cannot onboard itself.
- **The `plugin` stage** merges the Fugaro marketplace and `enabledPlugins` into the checkout's `.claude/settings.json`, pinned to the tag of the binary that ran it (a development build has no tag, so nothing is wired), after showing the diff and asking (`--yes` confirms it). It never commits: review it with `git diff`. The diff screen also lists, as `heads-up` lines, what else the file already holds that every teammate's agent will obey (hooks, `permissions.allow`, `apiKeyHelper`, `enableAllProjectMcpServers`, `env`, other marketplaces or plugins, and repository-local skills or commands named `fugaro...`); `doctor` shows them as informational lines and `doctor --strict` does not fail on them. Claude Code installs the plugin when a teammate opens the folder in a new session and trusts it (observed with Claude Code 2.1.289 on 2026-10-04: no install prompt, and the trust dialog does not mention the plugin). **Observed 2026-10-07:** in a checkout that `fugaro init` had just wired, opening Claude Code did not list the `/fugaro:` skills and `fugaro doctor` kept saying `plugin-install: not installed` until the plugin was installed by hand; the cause is not verified. If the folder was already trusted, or for any other reason Claude Code did not install it, run `fugaro upgrade --local` in the checkout (it installs the plugin through the `claude` CLI, or prints the slash commands without one), then restart the session. A repository's settings can install a plugin from the marketplace they name, so only trust folders you trust. After the pin changes, `fugaro upgrade --local` updates the installed plugin (until then the plugin shows "not cached" and its skills are gone); `fugaro update-skills` moves the pin alone after upgrading the binary, and `fugaro doctor --plugin --strict` is what a repository's CI runs to fail a stale, unpinned or foreign pin. A marketplace entry that names another repository (a fork you host) is kept and flagged; only `--allow-fork` moves its ref.
- **The `repository` stage** runs `init --repo` for the checkout when its origin's default branch (as last fetched) has a `fugaro.yaml` naming this project, else it is skipped and says why: that is the state of a first `fugaro init`, before `/fugaro:setup`. It asks once for the GitHub App's ID of a GitHub repository (or take `--github-app-id`) and keeps its own confirmations, the first image build's included. **Before the first billable build it asks GitHub whether the App is ready** (the same check as `doctor --check-github-app`): as the App, with its ID and its private key, it reads `GET /repos/<owner>/<repo>/installation` and compares what the installation grants with what runs ask for (Contents: Write, Pull requests: Write, Issues: Read, Metadata: Read, derived from the code that mints the tokens). The key is used only from memory: the one you typed at this run's `secrets` stage, or, only with `--check-github-app` (one-line notice first, your own credentials, owners only, refused in a coding agent's session), read from Secret Manager; only its PEM byte copy is cleared afterwards (the encoded payload and the parsed key live until garbage collection) and it is never printed; GODEBUG=http2debug in your own environment would print the JWT's Authorization header (it lives 9 minutes), so unset it. A key stored in an earlier run, without the flag, is not read: the check says `not checked: rerun with --check-github-app ... or run fugaro doctor --check-github-app in your own terminal` and the build is offered as before. An App that is not installed on the repository, or lacks a permission, leaves the build as `needs-you` with each missing permission and its exact fix (`add Issues: Read, then accept the new permission on the installation`) and nothing is billed; an App that holds Workflows: Write is warned about (Fugaro must never have it), as is any other permission Fugaro never asks for. A check that cannot be made (no key in memory and no flag, none stored, you may not read secret values, GitHub unreachable) is a warning that does not claim the App is fine, and the build is offered as before. The unlisted-repository question (its own typed name) is asked **first**, at the start of the run, before any Terraform plan, not after them.
- **A teammate (adopt mode).** Where the installation exists and this machine has no local config for it, `fugaro init --gcp-project <id>` writes the config from the installation and changes nothing in the cloud (the plugin wiring, a local `.claude/settings.json` edit with its own confirmation, still runs in a checkout); it says which roles to ask an owner for. The name is asked after the GCP project and the region, and its suggestion is the installation's own name (read from the runs bucket's `fugaro/project.json`, only from a bucket of that GCP project that carries Fugaro's label), not the directory's; a `--name` that is not the installation's is refused as always. When the installation has a Firebase backend, the adopted config's `budget` section (`rtdb_url`, `firebase_project`, `firebase_api_key`, `token_signer`) is filled from the Firebase root's Terraform outputs, read-only (`terraform init` and `output` in the Firebase root, nothing applied), so your `fugaro watch` and runs find the budget backend; none of the four is a secret (the web API key is restricted to Identity Toolkit and Secure Token by design), nothing the outputs do not hold is written (not the mode, not a cap), and when the state cannot be read the section stays empty and the run says why.
- **`fugaro doctor`** reads and changes nothing: the environment, Terraform, billing and the project's IAM, the local config, a checkout's `fugaro.yaml`, the stored secrets by name and the plugin wiring; with `--check-github-app`, in your own terminal (refused in a coding agent's session), it also asks GitHub, as each recorded GitHub App, whether it is installed on its repository with the permissions Fugaro's tokens request (see the `repository` stage; this is the one thing that reads a secret's value, the App's key, in memory only); without it, doctor never reads one; with a budget backend it also runs the `token-signers` check, below; it exits 1 with a one-line fix per failure. Run it first when something is off.
- **The `secrets` stage** runs in a checkout of a repository of this project (the local config knows it, or its `fugaro.yaml` names this project; another project's checkout is skipped). It asks, at hidden prompts, for the secrets the repository's jobs mount: the git credential (`github-app-key`, pasted as a PEM until its `-----END` line, or `bitbucket-token`), the Claude credential `agent.auth` names (`claude-oauth-token`: run `claude setup-token` in your own terminal first; `vertex` needs none; with `api-key`, `anthropic-api-key` **whenever a call actually goes direct to Anthropic** — under an enforcing budget that is a pin no provider allowed to see the repository serves (a Claude model above all), and without one nothing routes a call to a provider (observing only accounts for the spend), so every call goes to Anthropic and the key is always needed whatever the pins are; a run whose pins are all served by providers holds no Anthropic key, the job mounts it whenever the secret has a version, and a call that needs one without it is refused at run time with the `fugaro secrets set anthropic-api-key` command, never silently sent elsewhere), the keys of the model providers allowed to see the repository (only with `api-key`) and the workflows' own `secrets:`. Without a `fugaro.yaml` it asks only for the git credential and says so. A secret that already has a version is skipped and never read or rotated (`fugaro secrets set` rotates). It creates each secret's container itself, before the repository stage, with the same labels Terraform gives (`fugaro` and `fugaro_repo`, or `fugaro_project` when the value is stored project-wide — the prompt says which, and `--repo` is how you keep a value to this repository instead), which `init --repo` then adopts. It prompts only in **your own terminal**: `--yes`, `--non-interactive` and `--json` never prompt for it (`--json` never prompts, a hard rule; the stage is `needs-you`, exit 1, with one-line `fugaro secrets set` commands), a stdin that is not a terminal is never read (a pipe included: pipe values with `fugaro secrets set NAME < file`), stdout and stderr must be terminals too, and it refuses when a coding agent's environment is present (`CLAUDECODE`, `CLAUDE_CODE_ENTRYPOINT`, and the like): run it yourself, not through an agent. `CLAUDE_CODE_SSE_PORT` is also set by the Claude Code IDE extension in the integrated terminals of VS Code and JetBrains, so your own IDE terminal can be refused: for that variable only, the message tells a person they can unset it themselves; run `fugaro secrets set` in your own terminal window either way. A pasted PEM may have at most 120 lines (a 4096-bit key has about 52); longer is refused with nothing stored. That last rule is a mitigation, not a barrier: an agent that already holds a secret's bytes, or drives a terminal itself, can get around any gate in the program. The real controls are that the plugin's skills never ask for, read or print a value (the forbidden-instruction lint) and that you type the secrets yourself. Without Secret Manager permission (`roles/secretmanager.viewer` to list, `secretmanager.secrets.create` to create a secret's container, which `roles/secretmanager.admin` or a custom role has, and `roles/secretmanager.secretVersionAdder` to store) or with the API off, the stage is `needs-you` with that one-line cause, not a failure.
- A checkout's `Dockerfile`, `package.json` and `.yarnrc.yml` are read only when they are regular files (not symlinks) of at most 1 MiB; a symlinked one fails `validate` and the image render.
- **`--non-interactive`** never prompts and never reads stdin. Without `--yes` the run only plans; with it, it applies. `--yes` never covers creating a project, linking billing, a secret, an unlisted repository, the Firestore location, a billable build or replacing an image tag (see the first bullet), and does nothing in a coding agent's environment (a mitigation, not a barrier: an agent that unsets its own variables is not stopped; see the first bullet). `--plan-only` shows the review screen of a project Fugaro owns and applies nothing, and never takes `--yes` and creates nothing on its word: a plan that needs the state bucket (or the Cloud Resource Manager API) made first takes the project's name typed at a terminal, or stops with the route, so a first `--non-interactive` plan exits 1 and says so. With `--forget` and `--config-only` it only stops them prompting: their confirmations then need `--yes`.
- **Exit codes.** 0: done, or only planned. 1: a refusal (a flag, the environment, a missing confirmation, a plan the guard refuses) or a step left for you. 2: a cloud or Terraform failure.
- **It applies the plan it showed, and only that.** It saves the plan to a file and applies the file.
- **It never deletes.** A plan that would delete or replace anything is refused (exit 1) unless `--allow-delete <address>` names that resource.
- **`--plan-only`** stops after the plan. It can still create the state bucket, behind its own confirmation, because the plan needs it.
- **`--print-vars`** prints the Terraform variables and exits, with no cloud calls, so you can read what would be sent. With `--repo` the values are **ungated**: no discovery or readiness check ran, so every workflow has `deploy_job = true` (and so does the check), its job uses the new image path (which may not be built yet), and its account gets the new display name (an adopted bootstrap account would be renamed). It says so on stderr. Adopt a repository through `fugaro init --repo`, not by applying these values. The installation's values are ungated too, and say so on stderr: no discovery ran, so `adopt_legacy_registry` is `false` even when the bootstrap's legacy registry is there and ours.
- **It never touches a secret value.** Secret containers are Terraform's; their values are `fugaro secrets set`'s.
- **Exit codes:** 0 ok, 1 a user error or refusal, 2 a remote failure.
- **Reruns are safe.** Running a step again with the same inputs plans no change. Flags are not remembered, except the ones the local config stores (see "Flags to pass again").

## Preconditions

These are read-only checks, and yours to run and fix.

0. **The project's name.** Choose it once: 1 to 40 of `a-z`, `0-9` and `-`, starting and ending with a letter or digit. **It is permanent.** `fugaro init --name` stamps it on the runs bucket (the label `fugaro_project`) and in the marker object `fugaro/project.json`, and every job carries it as `FUGARO_PROJECT`; a later `init` with another name is refused, and a bucket labelled for another project is never adopted. Every repository of the project then names it as `project:` at the top of its `fugaro.yaml` (`fugaro config example` prints the template, with it filled in once the project is selected).
1. **Your account.** `gcloud auth list` shows it, and `gcloud auth application-default login` has been done: `fugaro` and Terraform both use Application Default Credentials.
2. **ADC's quota project** (a GCP project). `gcloud auth application-default set-quota-project <gcp-project>`. The generated provider sets `user_project_override`, so this is the project that is billed for API calls. **The Cloud Billing API must be enabled on that quota project** (a quota project that doesn't have it makes the billing reads fail with a message that looks like missing permissions): `gcloud services enable cloudbilling.googleapis.com --project <quota-project>`. `fugaro doctor` and `init`'s preflight name the API and the project and print that line. When `init` creates the project (`--create-project`), the quota project is an existing project of yours, not the new one: the billing reads and links of `init` and `doctor` use the credentials' own quota project (never the project being set up, where the API cannot be enabled yet), and when the API is off there the message names the project to enable it in.
3. **No overriding environment.** `GOOGLE_IMPERSONATE_SERVICE_ACCOUNT` is unset (`init` refuses to run with it, rather than apply as someone else), and `GOOGLE_PROJECT`, `GOOGLE_CLOUD_PROJECT` and `CLOUDSDK_CORE_PROJECT` are unset or name `<gcp-project>`. `GODEBUG` doesn't contain `http2debug`.
4. **Billing** is linked: `gcloud billing projects describe <gcp-project>` shows `billingEnabled: true`. Terraform doesn't link billing.
5. **`serviceusage.googleapis.com`** is enabled: `gcloud services list --enabled --project <gcp-project>`. Terraform needs it to enable the other APIs, and can't enable it itself.
6. **Terraform** 1.9 or newer (before 2.0) is on `PATH`: `terraform version`.
7. **Your role.** For the installation step you must be an Owner. The three IAM administration roles (`roles/resourcemanager.projectIamAdmin`, `roles/iam.serviceAccountAdmin` and `roles/iam.roleAdmin`) are needed on top of the rights to create buckets, registries, secrets, jobs, log buckets and Scheduler jobs and to enable APIs (for example Editor, plus the Run, Secret Manager and Artifact Registry admin roles for their IAM), and are not enough alone. `fugaro init --repo` creates service accounts and project-level bindings as well, so run it as an Owner too. The operator role that the installation step grants (design §6.1) lets people work with what exists (store secrets, act as the accounts, push base images); it doesn't let them create it.
8. **Who else needs access.** On the first run of a **new** project config (no config file yet), both lists default to you, the person running `init`, as `user:<your Google account's email>` (read from your Application Default Credentials; the review screen and the output say so: `launchers: user:x (you); operators: user:x (you); change with --launcher/--operator`), and are written to the config's `terraform.launchers` and `terraform.operators`: without them nobody holds the launcher or token-minter role and the first `fugaro run` fails with "not allowed to sign as the token signer". Passing `--launcher` or `--operator` replaces that default entirely (it adds nothing for you); an existing config, and a config adopted from an installation, are never changed implicitly; and with a service account's credentials, or none, there is no default and `init` stops with the one line naming `--launcher` and `--operator`. Decide whether anyone besides you launches runs (`--launcher user:you@example.com --launcher user:a@example.com`) or onboards repositories (`--operator …`): the flags replace the whole list, so name yourself and every current member too. Members are `user:`, `group:`, `serviceAccount:` or `domain:` IAM members.
9. **The project's default build identity.** A build request that names no service account runs as it, and a leaked build token could submit one (design §6.1). Read it, and what it holds, before you onboard anything:

   ```bash
   gcloud builds get-default-service-account --project <gcp-project>
   gcloud projects get-iam-policy <gcp-project> --flatten='bindings[].members' --filter='bindings.members:<that account>' --format='table(bindings.role)'
   ```

   If it is the legacy `<number>@cloudbuild.gserviceaccount.com` or holds `roles/editor`, that path is real in your project: weigh that before you onboard a repository whose code you don't trust. In the **same-project layout** (Firebase in the installation's own project) the same applies to the default Compute Engine, Cloud Build and App Engine accounts, which Google may create holding `roles/editor` on a project that has Compute enabled: `fugaro doctor` and `init` list the ones that hold a primitive role (check `default-service-accounts`) with the line that removes it, `gcloud projects remove-iam-policy-binding <gcp-project> --member=serviceAccount:<account> --role=roles/editor`. Fugaro never runs it for a project it did not create. A project that `init --create-project` made has no default Compute account yet, and init does not enable Compute.

   <a id="token-signers"></a>**Who can sign run tokens: `fugaro doctor`'s `token-signers` check.** Firebase accepts a custom sign-in token signed by **any** service account of the Firebase project, not only by `fugaro-token-signer` (live Check 26 saw it accept one signed by `fugaro-scheduler`). So the real boundary of the budget database's identity is **who can sign as a service account of that project**, and the signer's minter role is only the designed, narrow path. With a budget backend (`budget.firebase_project` in the local config), `doctor` reads, read-only, the Firebase project's IAM policy and the policy of each of its service accounts, **resolves every role in them through the IAM API** (predefined, primitive and custom alike, so nothing rests on a list of role names), and lists every principal whose role includes a permission that signs as an account (`iam.serviceAccounts.signJwt`, `signBlob`, `getAccessToken`, `implicitDelegation`, `iam.serviceAccountKeys.create`) or lets it grant itself that (`iam.serviceAccounts.setIamPolicy`, `resourcemanager.projects.setIamPolicy`), at project level or on a single account. It prints the resolved fact (which permissions of the role matched) and claims nothing more about a role than the API returns. Three kinds of principal are shown as **info** and never fail `doctor --strict`, and none is ever given a remove command. (1) **Designed**: the Firebase Admin SDK account (`firebase-adminsdk-<4 to 6 letters>@<project>.iam.gserviceaccount.com`, for signing only) and `fugaroTokenMinter` on the signer account alone, for users, groups and service accounts only (never `allUsers` or a domain), while that role is still `signJwt` and nothing else; both are part of the summary line. (2) **Google-operated service agents of this project** (`token-signers-google-agents`, one line listing each with its roles): the IAM API resolves roles such as `roles/cloudbuild.serviceAgent`, `roles/cloudscheduler.serviceAgent`, `roles/firebase.managementServiceAgent` and `roles/run.serviceAgent` to include `getAccessToken`, `signBlob` or `setIamPolicy`, which is true, but Google operates these accounts and Cloud Build, Scheduler, Run and Firebase break without them, so the trust is the same as trusting Google and there is no action. A principal counts as one only if it is a service account whose email is **exactly** `service-<this project's number>@<agent domain>` (`gcp-sa-<service>.iam.gserviceaccount.com`, `serverless-robot-prod`, `containerregistry`, `compute-system`, `container-engine-robot`, `gcf-admin-robot`, `firebase-rules`, `dataflow-service-producer-prod` and a few other pinned Google domains) or `<this project's number>@cloudservices.gserviceaccount.com` / `@cloudbuild.gserviceaccount.com`, bound at project level, and the number equals the project number doctor reads from the project. Another project's agent, a look-alike domain, a `user:` or `group:` member with such an email, an account of the project named like an agent, and the default Compute account (`<number>-compute@developer.gserviceaccount.com`, a plain account people grant roles to) do not qualify. If the project number cannot be read, nothing is recognised as a service agent (they are warnings, and the summary says why). (3) **Project owners** (`token-signers-owners`): users, groups and service accounts holding `roles/owner` on the project can create service-account keys and so sign tokens; they are the trust root, so this is one line counting and naming them ("keep this list short"), with no remove command (it would remove the owner's own ownership). `roles/editor` is **not** in this class: the primitive editor role resolves to key creation too, and that is unexpected power. **Every other principal is a warning** (`token-signers-N`; it fails `doctor --strict`, not plain `doctor`) that names the principal, the role, where it is held and the consequence ("can sign sign-in tokens with any claims, i.e. act as any run against the budget database"), with the one-line command that removes the binding, prefixed `review before running:` because removing a binding can break whatever relied on it, for example `gcloud projects remove-iam-policy-binding <project> --member=user:<who> --role=roles/iam.serviceAccountTokenCreator` (or `gcloud iam service-accounts remove-iam-policy-binding <account> --project <project> --member=... --role=...` for a binding on one account). **The result is partial, and the check says so even when it finds nothing:** it did not read folder- or organization-inherited bindings or deny policies. A role or policy it cannot read is a warning (unknown, never safe), and a Firebase project it cannot read at all is a warning too, so `doctor --strict` does not go green when nothing could be read. In the same-project layout this is the installation's own project.
10. **Provider credentials.** Each repository's Bitbucket repository access token, or GitHub App (its ID and a private key file), exists. The App has exactly four repository permissions, Contents Read & write, Pull requests Read & write, Issues Read and Metadata Read, never Workflows, is installed on the repository, and any later permission change is accepted on the installation. Name it when you create it: the name is shown as the author of the pull requests and comments Fugaro creates, and is not something to change later. **A GitHub App's name is unique across GitHub, so the bare `Fugaro` is taken: use `<yourname>-fugaro`** (git-providers.md). `init` and `fugaro doctor` check the installation against this and name each missing permission.
11. **On an installation that ran the M4 bootstrap:** `fugaro runs ls --since 1d` shows no active run, and you have a snapshot to roll back to (see "Adopting an M4 installation").

## The steps

### 1. The installation, planned

```bash
fugaro init --name <project> --gcp-project <gcp-project> --region <region> --plan-only
```

Add `--launcher`, `--operator`, `--alert-email`, `--budget`, `--budget-currency` and `--billing-account` as you need them (see "Optional pieces").

- **It enables the Cloud Resource Manager API, after its own confirmation,** when it is disabled (as on a fresh project): `init` reads the project's number through it before Terraform's apply could enable it. It enables it through Service Usage (precondition 5), then waits up to a few minutes for the enable to propagate. It is free, and Terraform later manages it with the other APIs without ever disabling it. Under `--plan-only` it does this only on the project's name typed at a terminal, never on `--yes`. Without a terminal and without `--yes` (or with `--plan-only`), `init` enables nothing and exits 1 with the command to run yourself: `gcloud services enable cloudresourcemanager.googleapis.com --project <gcp-project>`. Any other API that is still disabled (Cloud Scheduler, Cloud Logging, and so on) holds nothing yet, so the plan simply creates its resources; a 403 for a missing permission still stops `init`, and so does a disabled Cloud Storage API, which the Terraform state bucket needs.
- **It creates, after its own confirmation:** the Terraform state bucket `gs://fugaro-tfstate-<gcp-project>` (`--state-bucket` overrides the name), in `<region>`, with versioning, uniform bucket-level access, public access prevention, the label `fugaro=tfstate`, and no project-Viewer read access.
- **It offers to remove project Viewers' read access to the runs bucket,** if that bucket already exists (on a fresh project it does this after the apply, step 2), after another confirmation. Declining is allowed and leaves a warning; `--plan-only` never removes it.
- **Cost:** the state bucket is cents a month.
- **Undo:** delete the bucket (`gcloud storage rm -r gs://<bucket>`), once nothing is in it you need. The Viewer removal is undone by granting the bucket's `roles/storage.legacyBucketReader` and `roles/storage.legacyObjectReader` back to `projectViewer:<gcp-project>`.
- **The plan shows:** the APIs, the runs bucket (an import if it exists), `fugaro-base` with its cleanup policies in **dry run**, the custom roles, `fugaro-scheduler`, the log bucket, sink, exclusion and view, and the member bindings. Read it. On a fresh project it is all creates and no deletes.

### 2. The installation, applied

```bash
fugaro init --name <project> --gcp-project <gcp-project> --region <region>
```

Give it the same flags as step 1. It asks for the project name once more, applies the saved plan, and writes the local config.

- **Creates** what step 1's plan showed.
- **The log sink and its `_Default` exclusion carry one arm per platform.** `fugaro-jobs` routes a Fugaro-managed job's lines into the installation's log bucket and `fugaro-jobs-from-default` keeps them out of `_Default`; the filters name the resource type the platform gives an entry, so they carry both `cloud_run_job` and `batch.googleapis.com/Job` (the VM backend's jobs, [compute-backend.md](design/compute-backend.md) §1.5). The Batch arm is **additive and inert** on a project with no Batch jobs: nothing carries that resource type, so nothing moves, and who can read a line is unchanged (the `fugaro-runs` view has no filter of its own and its IAM member still names exactly the launchers and operators). **This is installation Terraform, so it reaches a project only when this apply runs there** — no other command applies it, and an installation from before the arm keeps routing only Cloud Run's lines until the owner reruns `fugaro init`.
- **Cost:**
  - The APIs are free to enable.
  - Service accounts, custom roles and IAM bindings are free.
  - The base registry is storage, about $0.10 per GB-month.
  - The log bucket is Cloud Logging's usual ingestion and retention charge beyond its free allotment (30-day retention).
  - The runs bucket is storage.
  - A budget and the alert's notification channel and policies add nothing.
- **Undo:** `fugaro init --forget` stops Terraform managing all of it and turns log isolation and cleanup off first (see "Rolling back"). It destroys nothing else. Deleting the resources is a manual `gcloud` job, since the runs bucket and every registry are protected on purpose.
- **The runs bucket's Viewer access.** On a fresh project the apply creates the runs bucket, so `init` then makes the confirmed removal of project Viewers' read access after the apply. If you declined it or it was interrupted, rerun `fugaro init`: a rerun is harmless.
- **`--name` and `--gcp-project`** are what create `projects/<project>.yaml` the first time; later commands select the project from the checkout's `project:`, `--project <project>`, `FUGARO_PROJECT` or the only project config there is, in that order (design §5.4), and print `project: <project> (GCP <gcp-project>)` first. With two project configs and nothing to choose by, a command refuses, lists them and names the one-line fix (`export FUGARO_PROJECT=<name>` or `--project <name>`); when the checkout's origin repository is listed by exactly one project's `repos`, that project is selected without it. `fugaro init --name <new name>`, with one config or several and no config of that name, is a first run of that name (a first run does not need `--project`; it needs `--gcp-project` and `--region`).
- **Check:** `fugaro runs ls` works, `gsutil cat gs://<runs bucket>/fugaro/project.json` (read-only) shows the name and the GCP project, and the local config has `runs_bucket`, `registry_host`, `log_view`, `scheduler_region` and a `terraform:` block. **Rerun it whenever you change `--launcher`, `--operator` or `--alert-email`** (or the flags in "Flags to pass again").

### 3. The base image, in `fugaro-base`

**0.7.0:** `base_images` holds one key, `base`; [base-image-migration.md](base-image-migration.md) says how to move.

**Not published yet.** `ghcr.io/dimipaun/fugaro-base` has not been published by any release so far: the `images.yml` workflow's `fugaro-base`/`publish-base` jobs exist and are live, but no release has triggered them yet. Until a release tag runs them, every `--base base` below finds no released image to resolve and `fugaro init`/`fugaro image refresh` refuse with a clear error, same as a typo'd kind would. `go`, `java-services` and `web-node` are refused everywhere in this release (the 0.7.0 cut; see [base-image-migration.md](base-image-migration.md)): their already-published tags stay on ghcr.io as immutable history, but no fugaro command accepts those kinds any more.

**Release images: `fugaro init` verifies them and pins them for you.** `fugaro init --base base` (and the base kind your checkout's `fugaro.yaml` implies; `--firebase` also copies the history image) resolves `ghcr.io/dimipaun/fugaro-base:<version>` for the CLI's own release version at its nightly-immune `-pinned` tag, **verifies the cosign signature the release attached to that exact digest**, reads that digest back through the installation's own Artifact Registry **remote repository** (`fugaro-ghcr`, a pull-through proxy over `https://ghcr.io`) and records the remote path at that digest in `base_images`: nothing is copied and nothing is pushed. It shows the digest it verified and asks for its own confirmation; a rerun whose entry is already this release's pin says "No changes". **`cosign` must be on your `PATH`** ([install](https://docs.sigstore.dev/cosign/installation/)): it is the verifier, `fugaro doctor` reports it with its fix line, and a missing binary refuses the pin rather than warning past it — name your own base with `--base-image KIND=IMAGE` if you would rather not have it. `--image-source ghcr.io/<owner>` is for a fork; `--expect-digest base=sha256:<hex>` **cross-checks** the digest the signature was verified for — the pin comes from the release's signed `-pinned` tag, and the run refuses if the two disagree (an out-of-band value comes from the `verify-public` run summary, which lists each image's digest); a tag already in your registry that names another image (a release tag, or a hand-pushed `history:latest`) is never replaced unless you name its kind with `--replace-image history` (repeatable) **and** type the project's name at a real terminal, in a confirmation that names both digests; `--yes` never replaces one. A base kind has nothing to replace any more: `--replace-image base` is refused and says why. **The anchor is the signature, not the tag:** a git tag is mutable, but what `base_images` records is a **digest** whose cosign signature was verified, before anything was written, against all four claims of a tag push of this repository: the certificate identity `https://github.com/dimipaun/fugaro/.github/workflows/images.yml@refs/tags/v<version>`, the issuer `https://token.actions.githubusercontent.com`, and the certificate's trigger (`push`) and repository (`dimipaun/fugaro`) extensions — the last two because a `workflow_dispatch` run against that same tag ref carries the same identity and is not a tag push. So whoever can write the ghcr.io tag cannot change what your cloud runs — the pin they would have to move is content-addressed (design [registry-remote-repository.md](design/registry-remote-repository.md) §4). `fugaro doctor --plugin` prints the commit your binary was built from and the one `git ls-remote` line that checks the tag still names it. A development build copies nothing and prints the build-from-checkout commands below.

**Upgrading: `fugaro upgrade`.** After `brew upgrade dimipaun/tap/fugaro`, run `fugaro upgrade` in each checkout, in your own terminal window (several checkouts: `fugaro upgrade PATH...`). It pins the plugin (as `fugaro update-skills` does), installs or updates it in Claude Code through the `claude` CLI, then runs the cloud step for the checkout's repository. The cloud step is `fugaro image refresh` for that repository. `--yes` confirms every cloud step, each billable build included; `--local` skips the cloud step; `--check` writes nothing and exits 1 when something is stale. A coding agent's session never runs the cloud step: it prints the command for your terminal instead. A teammate without a local project config gets the local steps only. After a real cloud step it also compares the deployed job's whole copy of the local project config (`providers`, `model_prices` ([multi-model.md](multi-model.md)), budget settings, the region's compute price override and the GitHub App ID) with what the local config would write now, and, if they differ, prints the fields and the one command that refreshes it, `fugaro init --repo .` (run in your own terminal; `fugaro upgrade` never runs it for you). `--check` makes no cloud call, so it says it cannot tell instead. It checks each workflow's default-account job; a named-account job ([design/named-oauth-tokens.md](design/named-oauth-tokens.md)) is updated by the same `fugaro init --repo .`, not checked separately.

**Moving a repository to a new release: `fugaro image refresh`.** In the repository's checkout, in your own terminal window (or unattended with `--yes`: see below), `fugaro image refresh` (optionally `--repo <owner/name>`, which must be the checkout's origin, and `--workflow <name>`, repeatable) does the whole move for ONE repository per invocation. It is refused in a coding agent's session, `--yes` included, and there is no `--json` or `--plan-only`. It prints its whole plan first. Every step asks its own confirmation, the project's name typed at a real terminal or, with `--yes`, none: (2) The base step resolves and verifies this release's base image of each selected workflow's kind as `init --base` does, shows the digest it verified before pinning it, and asks that step's own confirmation. (3) The check-job step points the repository's daily image check job at it, both its image and `FUGARO_CHECK_SPEC`'s base images, through the Cloud Run Admin API, without Terraform, after a typed confirmation. Before you type (or before `--yes` confirms it), it shows the old and the new image and a per-kind diff of `base_images` (an unselected kind that also moves to the local config's value is listed and flagged); it guarantees that no other field of the job or its spec changes and that the job's execution tokens (`startExecutionToken`, `runExecutionToken`) are not sent back. It is designed to write exactly what `init --repo` would render, so that the next `fugaro init --repo` plans no change (unverified until the sandbox live check, see Status). A check job that is missing (404) is reported with `run fugaro init --repo` and the run continues to the builds. (4) The build step rebuilds each selected workflow whose build record says it was built from another base (or has none), each build billable, confirmed the same way as the other steps (typed, or `--yes`, with no cap on how many builds run in one invocation). **Ctrl-C during a build's wait does not cancel it:** the submitted Cloud Build keeps running and billing, the stop message names the build ID and a `gcloud builds describe` command, and an immediate rerun may find no build record yet and offer a duplicate build, so wait for it to finish first. It ends by naming `fugaro init --anchor` when `fugaro.yaml` lacks `gcp_project:`; it NEVER writes `fugaro.yaml` and never onboards a repository. A declined confirmation (or a failure, under `--yes`) stops every later step (and build) and prints what finished and the exact rerun command (with `--yes` in it, if it was given); a rerun skips what is done. **A custom base image.** A `base_images` entry that is not a release image `fugaro init` pinned (a `dev-<sha>` or hand-pushed image) stops it before anything changes, with or without `--yes`, because refresh never replaces a custom, dev or hand-pushed base image. Two ways on: remove the entry from the local config (keep a backup) and rerun `fugaro image refresh`; or keep your own base image and rebuild from it with `fugaro image build --repo <owner/name> --workflow <name>`. The old steps still apply to a custom base: refresh will not pin, record or build from it, so the check job and the images are yours to keep in step by hand. **Unattended use.** `fugaro image refresh --yes` (add `--repo <owner/name>` and `--workflow <name>` as usual) runs it from CI or a script, with no terminal needed. It still refuses in a coding agent's session and never replaces a custom, dev or hand-pushed base image; and it can start many billable Cloud Build builds in one run, with no cap, so read the printed plan's build count first. **Status:** the direct Cloud Run job update (step 3) is UNVERIFIED against the real API: that Cloud Run accepts the read-back job including its output-only fields, enforces the body's etag, and starts no execution; likewise that the next `fugaro init --repo` plans no change is unverified until the operator's sandbox-only live check after release ([gcp-live-checklist.md](gcp-live-checklist.md) Check 30). Every other step reuses `init`'s own tested code paths.

Until you use a release build (or for a development build), an operator builds the base from a Fugaro checkout and pushes it to `fugaro-base`. Only operators can write there, and build accounts only read it, so a leaked build token can't replace the image every repository's `credential` step and check job run. The `credential`, `gate`, `record` and `check` commands live in the base image's own `fugaro`, so build it from a version that has them.

```bash
gcloud auth configure-docker <region>-docker.pkg.dev            # edits ~/.docker/config.json
commit=$(git -C <fugaro checkout> rev-parse --short HEAD)
tag=<region>-docker.pkg.dev/<gcp-project>/fugaro-base/fugaro-base:dev-$commit
sh <fugaro checkout>/images/build-base.sh base "$tag"
docker push "$tag"                                   # ⚠ CONFIRM: about 1.5 GB of billable registry storage
fugaro init --base-image "$tag"
```

- **The push** needs `roles/artifactregistry.writer` on `fugaro-base`, which the operator role gives.
- **`init --base-image`** is a plan with no resource change: it rewrites the `base` entry of `base_images` in the local config: `--base-image base=IMAGE` (or an image named `fugaro-base`, whose kind init reads from the name). A project needs the one entry `base`, built and pushed the same way with `build-base.sh base`. Rerun `fugaro init --repo` in each repository afterwards, so the check job's image follows it.
- **Cost:** about 1.5 GB of registry storage per base image.
- **Undo:** delete the image (`gcloud artifacts docker images delete <tag> --delete-tags`), and remove the `credHelpers` entry from `~/.docker/config.json`.
- **A dev tag doesn't move,** so the `base` rebuild trigger fires only when the kind's `base_images` entry itself changes or the tag is pushed again. `rebuild.max_age` (14 days) bounds how long a base security fix waits.

### 4. A repository

1. **Write and commit its `fugaro.yaml`,** whose first lines are `version: 1` and `project: <project>`. Use the `/fugaro:setup` skill, or `fugaro config example > fugaro.yaml` and edit it, then `fugaro validate` and `fugaro image build --local`. Merge it. For a sandbox that should never rebuild by itself, set `rebuild: { check: off }` on its workflows before its first `init --repo`: it then gets no check job and no schedule. Turning the checks off later deletes a protected job: see "Turning checks off, or removing a workflow". If the project publishes a project layer, `fugaro config init --yes` writes the minimal `fugaro.yaml`; publish or update the layer with `fugaro config publish FILE` (after every teammate's CLI and every job image is on 0.6.0: see [project-layer.md](project-layer.md#9-rollout-060)).
2. **Plan it, from the repository's checkout:**

   ```bash
   fugaro init --repo --plan-only
   ```

   For a GitHub repository add `--github-app-id <id>` (not a secret; it is recorded in the local config). The plan shows the registry, the build account, and per workflow the job account, the secret containers and the job (created only once its image exists and its secrets have a version), plus the check job and a **paused** Scheduler job. Discovery refuses first if anything under our names isn't marked as ours, and prints warnings for what it leaves alone.
3. **Apply it:**

   ```bash
   fugaro init --repo
   ```

   It applies the plan and prints the `fugaro secrets set` commands still needed. For a repository with no image yet, the job isn't deployed until the image and secrets exist.
4. **Store the secrets,** each with its own command, in your own terminal (design §6.1). Project scope is the default for a name that has one: `fugaro secrets set anthropic-api-key < <key file>` and `fugaro secrets set github-app-key < <key.pem>` each store one credential for the whole installation, and `--repo acme/webapp` stores one repository's own copy instead (which then overrides the project copy for that repository). `bitbucket-token` is the exception, and has no project-wide default at all: a Bitbucket credential is a repository access token, issued for one repository and usable for no other, so `fugaro secrets set bitbucket-token < <token file>` run in a checkout of that repository always writes its own copy, and every repository needs its own token (docs/git-providers.md). `claude setup-token` then `fugaro secrets set claude-oauth-token --repo acme/webapp` at the hidden prompt stores the default account's token in this repository's own copy; a bare `fugaro secrets set claude-oauth-token` stores this checkout's own copy the same way, and the project-wide copy only when `project_secrets.claude-oauth-token` allow-lists the repository you run it from — with no checkout, and no entry, there is no repository whose copy it could mean and the command is refused, so name the scope (`--repo`, or `--project-wide` with the entry) ([project-claude-accounts.md](project-claude-accounts.md)) — and a workflow's own `secrets:` are per repository too. Never put a value in a conversation with an agent. **A project-wide git credential reaches other repositories:** `fugaro secrets set bitbucket-token --project-wide` (or `github-app-key`) stores one workspace token, or one App key, for the whole installation — and, since project scope is the default for the App key, `github-app-key` does so with no flag at all (`bitbucket-token` needs an explicit `project_secrets.bitbucket-token` allow-list, or the command is refused: its repository access token serves one repository) — the token reaches every repository that workspace token covers, and the App key mints tokens for every repository the App is installed on, so a job in one repository you allowed holds a credential that opens the others too (design §3, plan follow-up 1). Store the git credential with `--repo acme/webapp` unless that is the reach you mean, and give each repository its own App if it matters: installations of one App share its key, so a second installation of the same App changes nothing about that reach.
5. **Rerun `fugaro init --repo`.** Now it offers each workflow's **first image build**, behind its own confirmation. It is billable: a 13-minute build on `E2_HIGHCPU_8` is about $0.21. It runs as the repository's build account into its own registry, and proves the credential volume, the candidate, the smoke test without network, the gate, promotion and the record. `--yes`, `--non-interactive`, `--json`, a pipe and a coding agent never confirm it; declining it, or not being able to, prints the one-line `fugaro image build --repo <owner/name> --workflow <name>` to run in your own terminal, which asks for the project's name too (**`fugaro image build` without `--local` is billable and is typed the same way**; `--json` is for `--local` only; `image build --local` builds with your Docker and costs nothing in the cloud).
6. **The second apply** switches the job to the new image and, once every workflow has a record, **unpauses the daily check**. It has its own confirmation, and the summary highlights the job's `image` and the schedule's `paused`.

- **Cost:**
  - Each build is billed per build-minute.
  - A job costs nothing until it runs.
  - A check is about $0.004 a run, about $0.12 a month.
  - Cloud Scheduler is $0.10 a month per job beyond its free ones.
  - A repository's registry is storage. An active repository costs about $1 to $3 a month all told (design §7.2).
- **Vertex AI:** when any workflow has `agent.auth: vertex`, `init --repo` records `vertex: true` for the repository in the local config. `fugaro init` enables the Vertex AI API whenever a recorded repository has it. So for the first such repository, `init --repo` warns that the installation hasn't enabled Vertex AI yet: **rerun `fugaro init`** afterwards. The API stays enabled while any recorded repository has the flag.
- **Undo:** `fugaro init --repo --forget` (state only), or offboarding, below.
- **Check:**
  - `fugaro image status --repo acme/webapp` shows the record.
  - From the checkout, `fugaro image check --dry-run` prints `skip` for a current image (locally it only prints, and needs `base_images` entries for the kinds of the repository's workflows).
  - `fugaro run …` launches a run.

### 5. Turning registry cleanup on

Cleanup starts in **dry run**: Artifact Registry logs what it would delete and deletes nothing. A day or more after the first images exist, audit the log for `fugaro-base` and each repository's registry (docs/gcp-live-checklist.md, check 17). It must never list a version tagged `latest` or `dev-`. If one appears, stop: the keep rules are wrong, and it is a bug to report. If not:

```bash
fugaro init --registry-cleanup on          # only fugaro-base's dry-run flag changes in the plan
fugaro init --repo                         # in each repository's checkout, no flag needed
```

The repository step copies the installation's setting (its `registry_cleanup_dry_run` output) into that repository's registry, so it takes no flag of its own; both registries and `fugaro-base` end with dry run off. Keep rules always win over delete rules: versions tagged `latest` (and `dev-` in `fugaro-base`) and the 3 newest are never deleted. Cost: none; it lowers registry storage. Undo: `--registry-cleanup dry-run`.

## Optional pieces

- **A budget:** `--budget 100 --budget-currency USD --billing-account <id>` creates one with 50%, 90% and 100% alerts. It needs billing-account permissions. **Pass the same three flags on every later `fugaro init`**: the budget isn't stored, and a plan without them would delete it (the guard refuses that and names the flags). A budget made by hand stays unmanaged.
- **An alert:** `--alert-email <address>` emails a failed image check or rebuild (and stores the address in the local config). It is one notification channel, "Fugaro alerts", and two alert policies, since Cloud Monitoring allows a log-match condition only alone in its policy: "Fugaro image check failed" (the check logged a failed check or rebuild) and "Fugaro image check job failed" (a check job execution failed before it could log: an ERROR in the audit log's system events, such as a failure at container start on an unreadable secret, or in the Cloud Run system log). Without it, failures still show in `fugaro runs ls`, `fugaro image status` and the check job's `ERROR` log line.
- **Launchers and operators:** `--launcher` and `--operator`, repeatable, stored in the local config (a new config starts with you in both, see precondition 8); rerun `fugaro init` and `fugaro init --repo` to change who has what. Passing either flag replaces that whole list, so repeat it for every current member, yourself included. The installation step grants project-level and bucket-level roles, and each repository step the per-repository ones. Since 0.7.0 launchers and operators no longer get the same bucket-level role (see "The runs bucket" below).
- **The Scheduler region:** Cloud Scheduler isn't offered in every Cloud Run region, so the daily check's Scheduler job may run elsewhere (`us-east5` uses `us-east4`). `--scheduler-region` overrides it; the check job stays in `<region>`.
- **Log isolation off:** `--no-log-isolation` leaves job logs in `_Default`.
- **Named Claude accounts on a shared job (0.9.0):** a profile serves the Claude accounts its `claude_accounts:` list names, one Cloud Run job per (profile, provider, account), each holding that account's token. It needs the tokens stored project-wide, the accounts declared in the project's local config and the policy published from 0.9.0. See [project-claude-accounts.md](project-claude-accounts.md), and "Claude accounts a project job serves (0.9.0)" below for the rollout.
- **Running Terraform yourself:** use `deploy/terraform/gcp/roots/*` as examples, and `github.com/dimipaun/fugaro//deploy/terraform/gcp/modules/repo?ref=vX.Y.Z` as the module source, with the inputs from `fugaro init --print-vars` (for a repository these are ungated, see above: set `deploy_job` and the image yourself until the image exists, and the check's `deploy_job` until the provider credential has a version). Then `fugaro init --config-only` writes the local config from the installation's outputs.

## The runs bucket: who reads and writes what (0.7.0)

Since 0.7.0 ([design/bucket-iam.md](design/bucket-iam.md)) launchers and operators no longer hold the same bucket-level role on the runs bucket. **This end state takes effect only once an operator applies it:** it is Terraform, not a toggle, so an installation stays on the pre-0.7.0 grants (every launcher holds `objectAdmin` on the whole bucket) until an operator runs 0.7.0's `fugaro init` and the plan's bucket change is applied (see "Rolling out the 0.7.0 bucket hardening" in [release.md](release.md)). None of this has been exercised against a real bucket in this project's own testing; the live check is [gcp-live-checklist.md](gcp-live-checklist.md) Check 32, reserved for the owner to run.

| Principal | `fugaro/` | `builds/<slug>/` | `runs/` | `cache/`, `locks/` | How |
|---|---|---|---|---|---|
| Operator | read, write | read, write | read, write | read, write | `roles/storage.objectAdmin`, no condition |
| Launcher (not an operator) | read | read | read, write | read | `roles/storage.objectViewer` (no condition) plus `roles/storage.objectUser` conditioned on `resource.name.startsWith("projects/_/buckets/<bucket>/objects/runs/") \|\| resource.name.startsWith("projects/_/buckets/<bucket>/objects/tokens/")` (`gcp.LauncherBucketCondition`; `tokens/` holds the sealed budget token, [design/budget-token-channel.md](design/budget-token-channel.md) §7.2) |
| Job account | none | none | its slug only | its slug only | unchanged, conditioned on its own slug; plus **read only** on `tokens/<its slug>/` (`roles/storage.objectViewer` conditioned by `gcp.TokenBucketCondition`), so a run reads its sealed budget token and cannot delete or replace a queued run's |
| Build account | none | its slug only | none | none | unchanged, conditioned on its own slug |
| History account | read | read | read | read | `roles/storage.objectViewer`, unconditioned |

So a launcher who is not an operator reads the whole bucket and can write only `runs/` and `tokens/` (the one object a launch writes under `tokens/` is its own sealed budget token, `tokens/<slug>/<run>/budget-token`): `fugaro run`, `ls`, `logs`, `diagnose` and `watch` keep working, and so does a stale lock's takeover by the CLI itself (`cancel`, `run --pr`, on a holder confirmed over) — but when that delete is refused (the lock is still live, or a previous launcher's grant hasn't migrated yet), only an operator can clear it: the CLI prints the `gcloud storage rm` command for them instead of clearing it itself. Every other write — outside `runs/` and `tokens/` — fails, but not all the same way:

- **Exit 1, "nothing was published."** `fugaro recipes publish` and `fugaro config publish` (the project layer object itself) fail with `nothing was published: writing <key> in gs://<bucket> needs the operator role …`, and nothing is written. `fugaro init --publish-config` fails the same way.
- **Exit 1, a different lead-in.** `fugaro config publish`'s own per-repository `builds/<slug>/project-layer.yaml` fan-out copy is attempted only after the layer itself already published, so a launcher's copy is refused with `the layer was published, but this repository's copy was not written (or removed): … needs the operator role …` instead of "nothing was published".
- **A warning, not a failure.** The shared-config publish every ordinary `fugaro init` stage runs as a side effect (as opposed to `--publish-config` itself) does not fail the stage for a launcher: it only warns, `could not publish the shared config: …`, and the stage goes on.
- **Exit 2, a different cause.** `fugaro image check --job` without `--dry-run` writes `check.json` as the repository's own build service account, not as the caller, so a refusal there means that account's own `builds/<slug>/` grant is missing or broken (`writing … was refused: the repository's build service account may be missing its builds/ write grant …`), not a launcher-versus-operator question. Plain `fugaro image check` (no `--job`) never writes `check.json` at all, with or without `--dry-run`: it only prints the decision.

A member on both lists gets the operator grant only. **What a launcher can still do, even once the hardening is applied (design §10, item L3):** `runs/` is writable for every repository, not only the ones a launcher was onboarded to, so a launcher can overwrite another launcher's queued `task.json`, forge `result.json` or `launch.json`, set the `cancel` marker on anyone's run, or plant a `session/` file or `followup.md` that a later follow-up of that repository restores ([SECURITY.md](../SECURITY.md) has the full threat model).

**Project-level writers.** Project Owners and Editors (`roles/editor` carries `storage.objects.*`, plus the `legacyBucketOwner` convenience binding) and anyone holding `roles/storage.admin` or an object-level storage role on the *project* can write the bucket whatever its own policy says; the bucket hardening cannot stop them. Treat them as operators, and list them as such.

**`fugaro doctor`'s `runs-bucket-iam` check** is read-only and never fails doctor outright (a warning needs `--strict` to fail the exit code). When it can read the bucket's policy it reports, as `runs-bucket-iam-N` lines under the `runs-bucket-iam` summary: any non-operator member holding an unconditioned write-capable role (fix: `fugaro init`, 0.7.0 or later, for a launcher; otherwise the `gcloud storage buckets remove-iam-policy-binding` command for that member and role), any conditional write grant to a person or account that isn't a recognized condition, any launcher missing a grant, a custom role (flagged "cannot tell" rather than judged, since doctor can't read what it grants), and an unrecognized service account (a warning, not info, once `terraform.launchers`/`operators` are known). With no `terraform.launchers`/`operators` configured at all (a teammate on the shared config, say, with no local lists to compare against), an unconditioned writer is reported only as info, since doctor cannot tell a launcher from a stranger. **Only when the bucket policy read succeeds and `terraform.launchers` is non-empty** does doctor also read the project's IAM policy and report (as a warning) any launcher holding a project-level role that bypasses the bucket's policy entirely (see "Project-level writers" above); when that policy read fails, the gap itself is reported as a warning, since a launcher's project role would otherwise go unnoticed silently. **When the bucket policy itself can't be read — the common case for a launcher, since doctor usually can't either** — it falls back to `testIamPermissions` and reports only what the caller's own credentials can do (held or not): there is no project-level check in this path at all.

**`fugaro doctor`'s `job-token-grant` check** comes from the same bucket policy read (so it runs only when that read succeeds, typically for an operator): for each job account holding its `runs/`, `cache/` and `locks/` grant, it warns (as `job-token-grant-N` lines) when the account lacks the read-only `roles/storage.objectViewer` grant on its repository's `tokens/<slug>/` — a repository not re-applied since the sealed budget token moved there (0.9.0). Such a job's budget runs stop at bootstrap saying the token could not be read, because GCS answers its refused read like a missing object. Fix: an operator runs `fugaro init --repo` in that repository's checkout. It is never silently green: when the bucket policy cannot be read (a launcher's usual case, or a server error) it is an info line saying it is unchecked, and a job account whose `runs/` grant is not in the exact shape this fugaro writes is an info line saying its `tokens/` grant was not checked.

**Rollback (H10).** There is no toggle; to restore one member's old access by hand, outside Terraform:

```
gcloud storage buckets add-iam-policy-binding gs://fugaro-runs-<gcp-project> --member=user:<member> --role=roles/storage.objectAdmin
```

The grant is non-authoritative, so later Terraform applies leave it, and `fugaro doctor` flags it.

**Optional: `DATA_WRITE` audit logs.** To log every object write in the runs bucket (the volume and the cost of doing so can be significant): `gcloud projects get-iam-policy <gcp-project> --format=json > policy.json`, add an `auditConfigs` entry for `storage.googleapis.com` with a `DATA_WRITE` log type, then `gcloud projects set-iam-policy <gcp-project> policy.json`. This is not applied by Fugaro's Terraform.

## Turning the model budget on

The model budget is a guard on what one **run** may spend on the model, for `agent.auth: api-key` runs (and, in `observe` only, `vertex`). It is separate from the billing-account budget of `--budget` above, which only alerts. It works through a gateway inside the runner (design §6.1), so the repository never holds the real key. It is off until you turn it on. With it off a run is what it was before: no gateway starts, and neither the model pins (`ANTHROPIC_DEFAULT_*_MODEL`, `CLAUDE_CODE_SUBAGENT_MODEL`, the output limit) nor the managed settings file is set or written, whatever `agent.model` says. A task's `overrides.model` keeps its reach (coder and reviewer) unless `agent.models` names a role.

1. **Pin the models.** In each repository's `fugaro.yaml` name an explicit model ID for each role (`agent.models.coder`, `reviewer` and `background`), and limit the output of a call (`agent.max_output_tokens`) and, optionally, a run's tokens (`agent.max_run_tokens`; it can only tighten the project's `budget.max_run_tokens`). Aliases such as `sonnet` are refused with a budget on. A model the embedded price table lacks needs a `model_prices` entry in the project config first. `fugaro validate` checks all of this once the budget is on.
2. **Observe first.** In `~/.config/fugaro/projects/<project>.yaml` set `budget: { mode: observe }`, then run `fugaro init --repo` in each repository (the jobs then carry `FUGARO_BUDGET_MODE`). Runs account their spend and **refuse nothing**; a call the cap would have refused is only logged (`budget: calls the cap would have refused`). The runner's log has a `model call` line for each call with its reservation and its settled charge; **a week of `observe` is what calibrates the cap**.
3. **Enforce.** In the project config (`~/.config/fugaro/projects/<project>.yaml`, not the repository's `fugaro.yaml`) set `mode: enforce` and `per_run_usd` (more than 0, at most 100000), and rerun `fugaro init --repo` in each repository. A run halts when its next call's worst case would pass the cap (design §4.5): it pushes what it has, opens a draft PR and ends `halted`. Raise the cap (in the project config and `init --repo`, or by merging a change to the default branch's `fugaro.yaml` when that is what set it) and use `fugaro run --pr N` to continue. An `enforce` budget with no cap halts every run at bootstrap. **A halted run exits 0**, so Cloud Run shows its execution as succeeded and the "execution failed" alert never fires for it: look at `fugaro runs ls` (status `halted`) or the draft PR's report, not at the alert.
4. **Turn it off:** `mode: off` (or remove the block) and rerun `fugaro init --repo`. The gateway doesn't start.

**Who sets what (M9a.1).** The project config is the **ceiling**: `budget.mode`, `per_run_usd`, `max_run_tokens`, `allowed_models` and `model_prices`, which reach the jobs through `fugaro init --repo`. A repository can commit a `budget:` block (`mode`, `per_run_usd`, `per_day_usd`, `allowed_models`) and `agent.max_run_tokens` in `fugaro.yaml`; the runner reads it from the **default branch** (`refs/remotes/origin/<default>`) at bootstrap, never from the run's branch, and the **tightest of three layers wins**: ceiling, default branch, the run's branch. Each layer can only tighten (lowest positive cap, strictest mode, intersection of allow-lists); a looser value on a branch is ignored with a warning and recorded in `result.json` `policy.ignored`. The ceiling holds whatever its mode (cap, prices, tokens, allow-list), and a committed `enforce` can switch the gateway on under an `off` ceiling for `api-key` (not `oauth`, not Vertex). An invalid default-branch policy (a misspelt key, an empty `allowed_models`) blocks runs until fixed, and a follow-up needs a valid default-branch `fugaro.yaml` too. A role that names no model is refused when an allow-list applies. The policy is read once at bootstrap. `agent.max_output_tokens` (per role) is bounded the same way: a branch can't raise the default branch's value. `allowed_models` bounds the models `fugaro.yaml` may choose and is enforced on every model call only while the gateway runs (`api-key` or `vertex` with the budget on); with `oauth`, or with the budget off, a branch-controlled means (a subagent's `model:` frontmatter, `/model`, `.claude/settings.json`) can use other models, so there it is a configuration check only (accepted risk). Prices are owner-only; `budget.per_day_usd` is the repository's own day cap: committed, tightening-only like the others, and enforced by the runner (client-side, against the repository's day counter) rather than the database; a lower cap the owner sets in the database (`fugaro budget set`, see "Turning the shared budget on") wins over it. To change a committed limit merge to the default branch; to raise the ceiling edit the project config and rerun `fugaro init --repo`. `fugaro validate` warns about keys the ceiling would clamp (stderr `warning:` lines, `warnings` in `--json`), and `init --repo` prints the ceiling and the clamps. Claude Code's own cost estimate is not the arbiter; the gateway's ledger is.

What the budget does and doesn't give you:

- **The managed settings file guards against committed configuration only.** It is how the gateway outvotes a repository's own `.claude/settings.json`, but it is writable by the agent's own user and is rewritten before every stage, so **a compromised agent can still route around the gateway**. Treat the budget as a guard against mistakes and expensive tasks, not as a boundary against a hostile agent (design §6.1).
- **`oauth` has no gateway.** Its token cap rests on the result event's `usage` and `modelUsage` alone, checked at stage boundaries. The token cap is the lowest of the project config's `budget.max_run_tokens` (the ceiling) and `agent.max_run_tokens` in `fugaro.yaml` on the default branch; a run's own branch can only tighten it, so a repository writer cannot lift it without a merge to the default branch.
- **The effective dollar cap is lower than the nominal one** by up to one worst-case call, because a call is halted when its worst case would not fit beside what is already spent. While other calls are still in flight their reservations (which over-count) are held too: a call that would fit but for them gets a retryable 429, Claude Code backs off and asks again, and the run is not halted unless a call cannot fit even with nothing else running. A stream that drops after it started is charged its full reserved output. Both err on the safe side; calibrate the cap with a week of `observe`. As a size guide, one call with a 150 KB request body and a 1-hour cache write reserves about $0.60 at $2 per million input tokens, and a long conversation reserves several times that, so a cap below a few dollars halts a normal run at its first calls.
- **Vertex budgets in `enforce` are refused** (by `init --repo`, `validate` and the runner) until the Vertex facts of live check 20 are recorded ([gcp-live-checklist.md](gcp-live-checklist.md)). Embedded prices are the global endpoint's; Vertex's regional endpoints cost about 10% more, so set `model_prices` for them. On Vertex only the basic web search exists, and there is no web fetch.
- **Requests the gateway refuses,** failing the stage with a configuration error (not a halt): fast mode, `inference_geo`, `service_tier` other than `auto` or `standard_only`, every server tool and typed tool, MCP servers, `fallbacks`, `context_management` other than the `clear_thinking_*` and `clear_tool_uses_*` edits (compaction adds a model pass the call's bound doesn't cover), `file` and `url` sources, and images for a model with no known image ceiling. They are refused because the request does not bound their cost or the gateway cannot price them. **`WebSearch` and `WebFetch` are denied to the agent while the gateway is on** (both are server tools). If Claude Code's tool search is on for a repository with many MCP tools it sends a server tool too: set `ENABLE_TOOL_SEARCH=false` in the agent's environment. The gateway forwards the agent's request headers except credentials and hop-by-hop ones (an allow-list is a possible follow-up), and does not pass the upstream's organization ID or cookies back.
- **Priority Tier organizations:** a response whose `service_tier` is `priority` fails the stage. Pin models that Priority Tier excludes, or keep the budget off.
- **Models served but not in the embedded table** (older Opus and Sonnet versions, for example) need a `model_prices` entry before they can be pinned with the budget on. Image ceilings in the table are conservative guesses no billed image has confirmed yet, and each request is reserved with a fixed 4,096-token allowance for what its body does not show.
- **The base image must be from M9a or later** (it creates `/etc/claude-code` for the managed settings); a run on an older base with the budget on ends `infra_error` saying so. Rebuild the base and each repository's image (step 3 and `fugaro image build`).

## Turning the shared budget on (M9b)

The model budget above caps one run in memory. The **shared budget** adds what no single run can know: a daily cap per repository and per project, kill switches, a live list of runs in flight, and the notional spend of `oauth` runs. It lives in a Realtime Database in the project's **Firebase project** (one per Fugaro project), reached by the runner with a per-run identity.

**One project or two: either is supported.** The Firebase project can be the installation's own GCP project (`fugaro init --firebase <the same project id as --gcp-project>`, the simplest: nothing to create or link beyond what the installation already has), or a project of its own. With one project the backend sits next to the jobs, so its protection rests on IAM and the database rules, not on a project boundary: Fugaro's Terraform grants no job, build or scheduler account any role on the backend, but anyone who is a project Owner or Editor can already read and write it, a role you add by hand to a job account can reach it, and so can anything that runs as one of the project's default service accounts when they hold `roles/editor`: an image build's step can submit a Cloud Build build without a `serviceAccount`, which runs as the default Cloud Build or Compute Engine account. **If you use one project, remove `roles/editor` from the default Compute Engine, Cloud Build and App Engine service accounts and set the organization policy `iam.automaticIamGrantsForDefaultServiceAccounts`** (`fugaro init --firebase` warns when one of them holds a primitive role). Any account of the project with `signJwt` can also sign a token the database accepts. With two projects a role like that would have had to be added in the Firebase project as well. Pick two projects if several people hold broad roles in the installation's project; see design `m9-budget-and-dashboard.md` §6.0 for the residual risk. It is off until you do this, and a project without it behaves as M9a.1.

1. **Choose the Firebase project, and link billing.** To use the installation's own project, skip to the next step: it exists and has billing already. By default `init` neither creates a project nor links billing. `--create-project --gcp-project <id>` creates that GCP project and adds Firebase to it (`--parent organizations/<n>` or `folders/<n>`, `--display-name`), as you, after you type its ID at a terminal; `--link-billing <account>` then links that billing account after you type the account's ID (it may incur charges). Each is its own typed confirmation that `--yes`, `--non-interactive` and `--json` never give; without `--link-billing` init prints the one `gcloud billing projects link` line and stops. An existing project you can read is adopted, one held by someone else or pending deletion is refused, and an existing billing link is never changed. Not run against a real organization yet (Check 27). Otherwise create a project (suggested id `<project>-fp`, in the same organization or folder as the GCP project), add Firebase to it, and link a billing account (the Blaze plan: a Realtime Database in a non-default location and Identity Toolkit need it). You need `resourcemanager.projects.create` and Billing Account User. The cost at the design's scale is small (the database, the history job and its Scheduler job; expect under about $10 a month); add a billing budget alert on it in the Console.
2. **Give your own credentials the Firebase scopes.** `gcloud auth application-default login --scopes=https://www.googleapis.com/auth/cloud-platform,https://www.googleapis.com/auth/firebase.database,https://www.googleapis.com/auth/userinfo.email`. `fugaro budget` and `init --firebase` read the database as you, and minting a run's token calls `signJwt` with the `cloud-platform` scope.
3. **`fugaro init --firebase <firebase-project-id> --budget-mode observe`.** Add `--print-vars` first to see what it will do (read-only). It checks that the project exists and has billing, refuses a project whose database already holds data without a Fugaro mark, then runs **three applies**, each showing its plan and asking you to type the project's name (or `--yes`): the installation (the history account), the Firebase root (the database, a restricted sign-in web API key, the token-signer account and its minter role, the budget admins: the GCP project's owners and editors who are users or groups, plus each `--budget-admin`), and the installation again (the history job and its Scheduler job, once the history image exists; **nothing builds that image for you**, see "The history image" below). Between the last two it ensures **Identity Platform is initialized** (without it Identity Toolkit answers CONFIGURATION_NOT_FOUND) and deploys the database's **rules**, the Fugaro mark, the project name, the mode and the largest lease, after a confirmation of its own that lists each write, and writes the local config. Identity Platform is ensured over REST, not by Terraform (the provider's resource fails on a project where it is already initialized): if it is not initialized, init initializes it with no sign-in provider once you confirm; if it is, init leaves it exactly as it is. It **refuses** (and writes nothing) a configuration with a public sign-up path enabled (email, anonymous, phone or any identity provider): the web API key is public, and only custom tokens signed by Fugaro's signer may work. It never changes an existing configuration, it reports what to disable (`budget.rtdb_url`, `budget.token_signer`, and so on). The Firebase root is operator-only with its own state (`fugaro/firebase`); `--budget-mode off` later stops the jobs opening a budget session and keeps the data — it no longer takes the backend's address and key out of the jobs, which every job keeps whatever the mode so a run can read a project policy (`FUGARO_RTDB_URL` and `FUGARO_FIREBASE_API_KEY`; the mode decides only whether a session opens).
4. **Rebuild the base image and run `fugaro init --repo` in each repository.** The runner reads the backend from its job's environment (`FUGARO_RTDB_URL`, `FUGARO_FIREBASE_API_KEY`), which only `init --repo` sets; the base image must contain this milestone's runner. A run launched meanwhile is refused or halts; freeze launches between the base image rebuild and each repository's `init --repo`.
5. **Observe first, then caps, then enforce.**
   - **Observe** (the default): runs lease and release, would-be cap refusals are only logged, and **kill switches, `maxReserve` and the grace still apply**. Let it run for a week; `fugaro budget show` prints today's counted, spent and notional dollars and the runs in flight.
   - **Set caps** from what you saw: `fugaro budget set --global --daily 150 --per-run 20`, `fugaro budget set --defaults --daily 60`, and `--repo owner/name` for an exception. Setting a cap that was unset, or raising one, asks you to type the project's name; it shows the old and the new value. A per-run cap may not exceed the daily cap of the same scope.
   - **Enforce:** `fugaro budget set --global --mode enforce`. The mode is **project-wide**: it is one value in the database, and a repository's `fugaro.yaml` can only tighten it. `init --firebase --budget-mode enforce` is refused unless the global daily and per-run caps already exist, because an enforcing budget with no global caps would refuse every lease.
   - **One global per-run cap bounds every repository.** `fugaro budget set --global --per-run P` is now the per-run cap of every repository that has no per-run cap of its own and no `--defaults --per-run` cap. Before, a repository with no per-run cap of its own **halted** in enforce even when the global cap was set: the global cap was only a ceiling on top of a repository's own. The effective cap is the smaller of the repository's side (its own node, else the defaults) and the global one, and a side that is not set does not bound the run; with no per-run cap on any of the three the rules still deny every lease (fail closed), so an enforcing project should set the one global cap. `fugaro budget show` prints the effective cap and where it comes from: `repo`, `default`, `global`, or "no per-run cap anywhere". **This lives in the database's rules, not only in the CLI** (see the next bullet).
   - **Deploying the rules is an owner step, and it comes after the CLI.** The rules are generated by the CLI you are running and reach the database only through `fugaro init --firebase <firebase-project-id>`, in its database step. The writes for whatever is absent go first (the mark, the project's name, the mode, the largest lease), then the rules, and **then the generation marker** — `config/limits/policyRules`, which records which generation of the document the database runs under; the marker is written **after** the rules and never before, so it is a statement about the document underneath it rather than a claim made before that document lands (`internal/infra`'s `DB.Plan` appends the rules action (`Path: "rules"`) and then plans the marker with its `d.put(projectpolicy.PathRulesMarker(), …)` call, and `Apply` writes them in that order). A rules deploy that fails therefore leaves the marker as it was — absent on a first deploy (generation 0, the legacy path: no policy is read and none can be published), or the previous generation on an upgrade, which is what the document still deployed carries — where a marker written first would have recorded this generation over rules that never landed. The whole step is behind its own confirmation, which lists each write. The order, after upgrading the CLI: **(1)** `fugaro init --firebase <fp> --print-vars`, read-only, shows the variables and writes nothing; **(2)** `fugaro init --firebase <fp>`, and confirm the database step when it lists "deploys the security rules (… bytes, generated)". A database whose rules already match prints **no rules line** for that step, but it still plans the **marker** write whenever the marker is absent or holds another generation — a database whose document was deployed before this code existed still has to record which generation it runs under — so only a step with nothing at all pending prints "The database already has the rules, mark, project name and mode." and asks for no confirmation (`No changes` is `fugaro init`'s line for a stage with nothing to do, not this step's); **(3)** verify read-only, with the `firebase.database` scope of step 2 above and no writes:
     ```
     # <db> is the host of budget.rtdb_url: that local-config value is already
     # the database's whole address, so strip its scheme and any trailing
     # slash and add nothing (aurora-fp-default-rtdb.firebaseio.com, or
     # <name>.<region>.firebasedatabase.app for a regional database). Do not
     # append a domain to it: it is the whole host.
     db=$(sed -n 's|^ *rtdb_url: *||p' ~/.config/fugaro/projects/<project>.yaml \
       | tr -d "\"'" | sed -e 's|^https://||' -e 's|/*$||')
     test -n "$db" || { echo "the local config has no budget.rtdb_url"; exit 1; }
     curl -fsS -H "Authorization: Bearer $(gcloud auth print-access-token)" \
       "https://$db/.settings/rules.json" \
       | jq -r '.rules.runs["$slug"]["$run"].reserved[".validate"]' > /tmp/live-perrun.txt
     test -s /tmp/live-perrun.txt || { echo "the read returned nothing: check <db> and the token, do not read on"; exit 1; }
     grep -o "config/caps/defaults/repoPerRunMicros').exists()" /tmp/live-perrun.txt | wc -l  # 1: the repo-else-default side is live
     grep -o "config/caps/global/perRunMicros').exists()" /tmp/live-perrun.txt | wc -l       # 2: the global fallback side is live
     ```
     The whole validator is one line, so `grep -c` counts it once however many times the expression occurs: `grep -o … | wc -l` counts occurrences, which is what these two numbers are. The old rules never called `.exists()` on the defaults per-run node and ended the per-run comparison with `&& … <= root.child('config/caps/global/perRunMicros').val()`; the new ones read all three sides and end with `: false)` (nothing set anywhere denies). If the file still holds the old expression, both counts are 0 (and the `: false)` tail is absent) — but an **empty** file (a bad `<db>`, a token without the `firebase.database` scope) is not that: it means the read failed, and the two `test` lines above **exit** before the greps run (each guard ends in `exit 1`, so a paste of the whole block stops there) rather than let 0 read as "the old rules are live". **The order is: the operator's CLI, then this deploy, then the runner images.** The rules are generated by the CLI you run `init --firebase` with, so upgrade the operator's CLI before step (2): an old CLI deploys the old rules, whatever this page says. And the base image (and each repository's image) goes **after** this deploy, never before: a runner built from the new CLI asks the backend for a lease past the cap the old rules compare against, that write is refused, and the gateway reads a refused write with no cap reason as the backend being unavailable rather than a halt — the call waits as a retryable 503 and the run halts once the session's grace period is up. Nothing needs the two closer in step than that order: the new rules accept every lease the old runner asks for.
   - **What this deploy widens.** It is a change in the fail-open direction, and only this far: a repository with no per-run cap of its own and no default used to be refused, and is now bounded by the project's global per-run cap. **A second shape widens with it, and the owner ruled on 2026-10-15 to keep it:** a repository that has its own per-run cap (or the default) in a project with **no** global per-run cap used to be refused as well — the old expression compared against the global node whether or not it existed — and is now bounded by the repository's own cap alone. That is D6's rule ("a side that is not set does not bound the run") applied to both sides, it is what the code and the rules do, and it is **documented, accepted behavior**: an enforcing project may hold per-repository per-run caps and no project-wide one. It is reachable on purpose, not only by accident: the `--mode enforce` check that refuses a project without global caps runs only when `--mode enforce` is being set, so `fugaro budget set --global --clear` followed by `--global --daily X` leaves an enforcing project with repository caps and no global per-run cap. The daily caps, the kill switches and `maxReserve` are unchanged, and a database with no per-run cap anywhere still refuses every lease. Nothing else deploys rules: `fugaro budget set`, `init --repo` and `upgrade` never touch them, and rolling back is the same command from a checkout of the older version.
6. **Day to day.** `fugaro budget show [--repo R | --all] [--json]`, `fugaro budget preview --recipe R --runs N [--repo R] [--json]` (a ceiling, not a forecast: N runs × the smaller of the per-run cap and the recipe's most stages times `agent.max_budget_usd`, against today's remaining daily caps, ending in one verdict line; that figure is model dollars and nothing else, so for every workflow the checkout defines it also prints a `compute ceiling` line — that workflow's own `resources` over its own `timeouts.total` at this installation's compute prices, labelled NOT CAPPED because no budget key bounds compute at all (the run's own timeout is the cap) — which is the one figure sitting outside the model ceiling above it, and for a recipe whose expensive half is a render on a big machine, rather than the plan stage, it is the half that decides the bill; a region with no compute price table leaves that line naming what is missing instead of printing `$0.00`; with at least 5 of the repository's runs of the last 30 days that recorded a real-dollar cost it also prints a `typical:` line — the mean recorded cost of each stage kind, on the model the checkout pins for it (a kind the window has no cost for on that model leaves the line out and names the model rather than borrowing another model's mean), at the recipe's typical stage count of one round of each loop the recipe and its round knobs leave in (the two `fix` stages share one mean), over every run of the window whatever it ended as; a run on a subscription (`agent.auth oauth`), whose `model_usd` is notional rather than charged, a `result.json` that is missing or unreadable, and a record with no per-stage cost at all, are each named in a note and left out, never counted as runs that cost nothing; it writes nothing, and when the recipe is not in the checkout it reads the project's recipes from the runs bucket, like `fugaro recipes ls`), `fugaro budget kill --repo R` or `--all` (running runs halt within seconds, in the last stage after pushing; new launches refuse; `--all` asks for the project's name), `fugaro budget resume`, `fugaro budget prices` (offline). `show` and `preview` need the Viewer role on the Firebase project — plus, for `preview`, read access to the runs bucket, which `init` deliberately takes away from a plain project Viewer (§6.1), so a Viewer-only identity gets a bucket error when the recipe is not in the checkout, and no `typical:` line for a recipe or a repository whose runs bucket it cannot read; `set`, `kill` and `resume` need a budget admin. Roles are granted by Terraform from `terraform.budget_admins`; change the list and rerun `init --firebase`.

What to know:

- **Who can raise a cap.** A budget admin, in the database. A repository's committed `budget.per_day_usd` can only tighten the repository's day cap and is enforced by the runner against that repository's day counter, not by the database, and only while the project has the shared budget (on a project without it the key enforces nothing): a compromised agent can ignore it, where it cannot ignore the database's caps. The project's day cap is the database's alone.
- **A run needs the backend.** With the shared budget on, a run halts (`budget_unavailable`, outcome `none` at bootstrap) when it cannot reach the database or Firebase Auth for 3 minutes, **`oauth` runs included**; `budget_token_expired` means the run queued for over an hour: launch it again. `fugaro run` pre-checks the kill switches and caps and refuses a launch the budget would refuse; `--no-budget-check` skips only that check.
- **The token's window and `rb`.** A run's identity expires at launch + the target workflow job's task timeout (or the override) + 1 h queueing + 5 m. Its `rb` claim is the launcher's own name from the local config (`user`, else `git config user.email`): self-asserted, for attribution in the registry and outcomes only, and nothing in the rules trusts it.
- **`--retry` after an ambiguous launch.** If the first launch's outcome was unknown and `--retry` runs after the claim's TTL while that execution is still queued and has written no record yet, a second execution may start (a hazard from before M9b). One of the two takes the single-use token and the other halts for want of one; nothing is stolen or corrupted.
- **Known limits.** A run's identity (its Firebase token) is valid until `fx`, launch + the job's timeout + 1 h + 5 min, not until the run ends. Every launcher can mint a token with any repository, run id and `rb` through `signJwt` on the signer (R5), so a launcher credential equals budget write access up to the caps; `rb` is attribution only. When lease denials come with healthy reads, a run neither spends nor halts until its stage deadline (idle compute, no money; a wall-clock task timeout is a v3 open item). A compromised agent can take the token object of a queued sibling run of the same repository before it starts (that run then halts for want of a token); the caps bound what it can spend. A calendar day can overshoot its cap by the leases alive across midnight (at most one per-run cap per live run).
- **The history image.** The sweeper's job runs the image `<region>-docker.pkg.dev/<project>/fugaro-base/history:latest`. With a release binary, `init --firebase` copies it from `ghcr.io/dimipaun/fugaro-history` (published from the first release tag after the one that adds it, so v0.1.0 has none) and deploys the job. Until then, and with a development build, **you build and push it once, by hand**, from a checkout of this repository: `sh images/build-base.sh history <region>-docker.pkg.dev/<project>/fugaro-base/history:latest`, then `gcloud auth configure-docker <region>-docker.pkg.dev` and `docker push <region>-docker.pkg.dev/<project>/fugaro-base/history:latest`; then run `fugaro init --firebase <id>` again, which deploys the history job and its Scheduler job. `init --firebase` prints these exact commands (with your registry path) while the image is missing. CI builds, smoke-tests and scans the image, and publishes it as `ghcr.io/dimipaun/fugaro-history:X.Y.Z` on a release tag (`fugaro init --firebase` copies it into your registry for a release build, see "Release images" above; a development build still builds it by hand). Without it the sweeper does not run: crashed runs' registry entries stay and old run users are not deleted. The image's base (`distroless/static-debian12:nonroot`) is pinned by tag, not by digest.
- **Who runs the third apply.** The history job runs as the history account and nobody is granted `actAs` on it by design, so the person running `init --firebase` must be able to act as it by other means (the project's owner or editor role, or Service Account User they already hold).
- **Mode skew.** A job whose env mode is `observe` under a database `enforce` halts on cap refusals; `budget show` prints both modes.
- **The history job.** Once a day (00:30 UTC) it also moves finished days to Firestore ("Spend history and reports (M9d)" below). Every 15 minutes the sweeper removes the registry entries of runs that ended without cleaning up, marks their reservation `crashed` (it stays counted, which errs high), and deletes old run users. It runs as its own account with its own image, holds the database admin role and no model credential, and never writes the caps.
- **Watching it.** `fugaro watch` shows the caps, the spend, the burn rate, the live runs and the kill switches as they change (it needs only the Viewer role on the Firebase project, like `budget show`); `fugaro budget show` is the one-shot version. The optional `watch: { burn_alert_usd_per_hour: N }` in the project config sets the burn-rate alert (default: the daily cap over 8 hours). In `watch`, `k`/`r` act on the selected repository and `K`/`R` on the whole project, `k` asks for `y` or Enter; `r`, `K` and `R` ask for a typed word (the repository's or the project's name). `--plain`, `--json` and `--once` print instead of drawing a screen. `fugaro runs ls --watch` stays for "did my runs finish" and needs no Firebase. **Queued runs** (claimed or launched, no registry entry yet: they haven't started) show as a `queued` row, aged since the claim or launch, with a "not started after N min" warning once one has gone more than 10 minutes without starting; stuck rows stay listed until 30 minutes after the launch. Queued rows refresh about once a minute; a `fugaro run --retry` of an old stored task is not shown queued (its run ID is old), only once it starts (`fugaro runs ls` shows it pending). This reads the runs bucket the same way `fugaro runs ls` does, so only a launcher or an operator sees queued rows: a plain Firebase Viewer without bucket access never does, and always gets a one-line "queued runs unavailable" note instead (everything else stays live), since `init` deliberately removes the runs bucket's project-Viewer read access (§6.1).
- **Rollback.** `fugaro init --firebase … --budget-mode off` then `fugaro init --repo` (the jobs stop opening a budget session; they keep the backend's address and key, which every job carries whatever the mode so a run can read a published project policy); the data stays. `fugaro budget kill --all` is the emergency stop.
- **A budget-off installation with a database still depends on Firebase and Cloud Storage.** Turning the mode off stops the cap session, not the policy read: a job of an installation whose local config has `budget.rtdb_url` carries the backend's address and key whatever the mode, the **launch** reads the project's policy with the operator's credentials and leaves a token object in the runs bucket (Cloud Storage), and every run takes that object and reads `config/policy/shared` (Firebase Auth, then Realtime Database) before it starts. Either service being down therefore **fails closed** — the launch is refused, or the run halts — instead of running on the environment ceiling with a published policy unenforced. An installation that never configured a database keeps today's behaviour exactly: no backend in the jobs, no dependency, no read — and a config that names a budget mode but no `budget.rtdb_url` is not refused for the mode alone either. The mode is the operator's claim about the budget, never a policy. What refuses a *launch* is a policy the launcher can see and cannot honour — an `allow_repos` that does not admit the repository, or a node it cannot read — and the readiness gate above blocks a *deploy* only where the config making the plan can see a policy, because that config is what it reads the node through. It fires for a job this apply would deploy without the backend while a policy is published — a job carries the backend through both `budget.rtdb_url` and `budget.firebase_api_key`, so the reachable case is a config that names the URL and not the key. A config that names **no** `budget.rtdb_url` sees no policy at all, so the gate never fires for it, whatever the project has published: nothing refuses that deploy, and the job goes out unable to read a policy that may well exist. That is a gap in the gate, accepted by the owner on purpose, not a rule a policy would close. What the policy then enforces is [docs/project-layer.md](project-layer.md) §5's table: the budget ceiling the node names and its prices, and, in this release, `allow_repos`. A run refuses a repository its project's published `allow_repos` does not admit (and a run whose `FUGARO_RUN` is not the slug of the repository its task names), before any git credential exists and before anything is cloned; a published policy with an empty `allow_repos` admits no repository at all, which is not the same as a project that has published nothing. `fugaro run` makes the same check before it creates an execution, and refuses a policy whose `version` is newer than the binary the same way: nothing is launched, and the fix is to upgrade Fugaro. `providers` and `routing` are still decoded and accepted but not applied.
- **Verification.** Firebase and Realtime Database behaviour that cannot be checked offline is recorded by live check 21 in [gcp-live-checklist.md](gcp-live-checklist.md).
- **Backstop at the vendor.** Set a spend limit on the Anthropic Console workspace the key belongs to; Fugaro's caps are a guard, not a replacement.

## `init --firebase` on a project that already has the Firebase resources

When the Firebase root's state is lost (a new state bucket, a recreated installation, a second machine on another bucket) while the Firebase project still holds what an earlier apply created, `fugaro init --firebase <fp>` adopts those resources instead of failing on four creates. Before it plans the Firebase root it reads the root's state, then reads the project (read-only, as you, with the Firebase project as the quota project), checks each singleton the state does not already manage, and writes an import block for each one that is ours. The design is [design/adopt-firebase-root.md](design/adopt-firebase-root.md).

**What is adopted** (only at these four addresses, under `module.firebase.`):

| Resource | Name | Address |
|---|---|---|
| The default Realtime Database instance | `<fp>-default-rtdb`, in `us-central1`, `ACTIVE` | `google_firebase_database_instance.this` |
| The web API key | `fugaro-web`, display name `Fugaro run sign-in` | `google_apikeys_key.web` |
| The token signer account | `fugaro-token-signer@<fp>.iam.gserviceaccount.com` | `google_service_account.signer` |
| The token minter role | `fugaroTokenMinter` | `google_project_iam_custom_role.token_minter` |

An empty default instance that carries no Fugaro mark is adopted too (the database step writes the mark right after the apply); one that holds data without our mark is refused by the database check, as before. IAM members are **not** imported: they are non-authoritative and creating one that exists changes nothing, so the plan shows them as creates. The project services and `google_firebase_project.this` are not imported either; creating them when they exist is accepted.

**What is refused, and why.** Names and descriptions are public, so a look-alike can carry them; the checks that matter are on shape. Every refusal is printed together with what was found and what was expected, and the run stops before the Firebase root is planned or applied and before its `imports.tf.json` is written (its tfvars and backend are written and `terraform init` and the state read have run: they read the installation's state bucket and, on a first run, may create an empty state object there, but write nothing to the Firebase project; the installation root has already been planned, and applied if it needed it). Nothing is ever imported and then changed, or deleted.

- **The signer**, because its signature admits a run to the database: another display name or description (the description names this Fugaro project); disabled; any user-managed key (whoever holds one signs tokens without IAM; the message gives the `gcloud iam service-accounts keys delete` command); any grant on it but the minter role to this run's launchers and operators (see below).
- **The minter role**: its permissions must be exactly `iam.serviceAccounts.signJwt`, and its title `Fugaro token minter`. A wider role would make every grant of it reach further. The message gives the `gcloud iam roles update` command that sets it back. A deleted role is not imported; a note says the plan's create restores it.
- **The web key**: its restrictions must be exactly the two API targets `identitytoolkit.googleapis.com` and `securetoken.googleapis.com`, no methods, no browser, server, Android or iOS restriction, and it must not be bound to a service account. A deleted key is refused with the `gcloud services api-keys undelete` command.
- **The instance**: it must be the project's `DEFAULT_DATABASE`, named `<fp>-default-rtdb`, in `us-central1` and `ACTIVE`. A default instance in another region cannot be moved or renamed, so that Firebase project cannot host the backend: use another one. `DISABLED` or `DELETED` instances are refused with the step to take.

**A foreign minter on the signer.** If `fugaroTokenMinter` (or any other role) is granted on the signer to someone who is not one of this run's launchers or operators, the run is refused and names each one, for example:

```
token signer fugaro-token-signer@<fp>.iam.gserviceaccount.com grants fugaroTokenMinter to members who are not this installation's launchers or operators:
  user:old@example.com
Each could mint run tokens. Remove them, then rerun fugaro init --firebase <fp>:
  gcloud iam service-accounts remove-iam-policy-binding fugaro-token-signer@<fp>.iam.gserviceaccount.com --project <fp> --member=user:old@example.com --role=projects/<fp>/roles/fugaroTokenMinter
Or add them as launchers or operators if they should keep it.
```

Run the printed command for each member, or add the member as a launcher or operator, then rerun. A grant under a condition is marked `(under a condition)` and its command ends with `--all`. Member emails compare case-insensitively over ASCII (IAM stores them lower-cased); the type prefix must match exactly.

**What to expect.** The run prints the plan before it asks: `Plan: 4 to import, ...` and one line `import <address> (id <id>)` per import. The confirmation names what is adopted (`adopting the existing Realtime Database <fp>-default-rtdb, web API key fugaro-web, token signer and fugaroTokenMinter role; ...`). Type the project's name as for any apply (`--yes` answers it too, as for any plan the review did not announce). A rerun imports nothing and ends with `No changes`. If an apply fails half-way, rerun: what landed in the state is skipped and the rest is imported again.

**What the state already manages is not checked again.** A singleton the Firebase root's state already manages is Terraform's: discovery skips it (no read, no check, no note), and the plan, the guard and the stage's typed confirmation handle it as on any rerun. So on an installation that drops a launcher, the plan deletes that member's `module.firebase.google_service_account_iam_member.minter["<member>"]` and the guard stops it until you pass `--allow-delete 'module.firebase.google_service_account_iam_member.minter["<member>"]'` (or remove the grant with the `gcloud iam service-accounts remove-iam-policy-binding` line yourself); a managed role, key or signer that drifted is restored by the plan behind the confirmation. Only what the state does not manage is checked, so a partly managed state never lets a look-alike through, and a state that cannot be read stops the run. A token-minter grant added out of band to a signer the state already manages is therefore not refused by `fugaro init` (the IAM-member resources are non-authoritative, so the plan shows nothing), and `fugaro doctor`'s `token-signers` check lists its holder as "can sign as designed" without comparing it with the launchers and operators: after offboarding someone, review the signer's policy by hand (`gcloud iam service-accounts get-iam-policy fugaro-token-signer@<fp>.iam.gserviceaccount.com --project <fp>`). A doctor check comparing the holders with the launchers and operators is a possible follow-up.

**The installation's GCP project must be unchanged.** Adoption works when the installation keeps its GCP project (a new state bucket, a lost state, a second machine). Moving the installation to a **new** GCP project is refused before adoption is reached, by the database checks: the Realtime Database's `fugaro/mark` and the Firestore database's mark name the old GCP project, and one Firebase project serves one installation. `init` has no remedy for that today: the marks must be dealt with first, which means emptying the Realtime Database (and handling the Firestore mark), as the move of the `belong` installation did.

**`--plan-only` does not show this.** With `--firebase`, `--plan-only` plans the installation root and stops there; the Firebase root, its discovery and the imports are only reached by a real run, which shows them before the confirmation.

**What discovery does not see.** It checks the signer's own policy. A role on the project (or inherited from a folder or the organization) that lets someone sign as the signer is not visible to it; run `fugaro doctor` after adopting, whose `token-signers` check lists the project-level grants (it needs the budget backend in the local config; inherited bindings are not checked at all). The run prints a note saying so when it adopts (imports) the signer; a rerun whose state already manages the signer prints none.

**The manual fallback.** If you cannot use the discovery (an older `fugaro`, or you prefer to see each command), import by hand. This is outside fugaro's guard: check each resource yourself against the list above. Every fugaro run deletes the root's files (`backend.hcl`, `terraform.tfvars.json`, `imports.tf.json`) and rebuilds them, so supply the backend and variables yourself, with the data directory fugaro uses:

```sh
W="${XDG_STATE_HOME:-$HOME/.local/state}/fugaro/terraform/<gcp-project>/firebase"
cd "$W/gcp/roots/firebase"      # exists once a fugaro run reached the Firebase root
export TF_DATA_DIR="$W/.terraform" TF_CLI_CONFIG_FILE="$W/terraformrc"
terraform init -input=false -lockfile=readonly -backend-config=bucket=fugaro-tfstate-<gcp-project> -backend-config=prefix=fugaro/firebase
fugaro init --firebase <fp> --print-vars | jq .firebase > terraform.tfvars.json    # import needs the root's variables
terraform import 'module.firebase.google_firebase_database_instance.this' 'projects/<fp>/locations/us-central1/instances/<fp>-default-rtdb'
terraform import 'module.firebase.google_apikeys_key.web' 'projects/<fp>/locations/global/keys/fugaro-web'
terraform import 'module.firebase.google_service_account.signer' 'projects/<fp>/serviceAccounts/fugaro-token-signer@<fp>.iam.gserviceaccount.com'
terraform import 'module.firebase.google_project_iam_custom_role.token_minter' 'projects/<fp>/roles/fugaroTokenMinter'
```

Use your own state bucket name if `--state-bucket` was set. `--print-vars` prints the installation's and the Firebase root's variables as one JSON object (`firebase` is the root's) and makes no cloud call, so its admins list is not the one a real run reads; the imports do not depend on it. The next `fugaro init --firebase <fp>` rebuilds the directory and should show `No changes`.

## Spend history and reports (M9d)

With the shared budget on, finished days move from the Realtime Database to **Firestore** and `fugaro report` reads them. Until [check 23](gcp-live-checklist.md#check-23-spend-history-and-fugaro-report) has been run against a real project, treat the Firestore calls as unverified.

**What it needs**

1. **A Firestore database in `us-east5`, which is permanent.** (Right after the database is created, the Firestore API can answer 403 "API has not been used ... or it is disabled" for a minute while its enablement propagates: the read-back is retried with a pause, not failed.) `fugaro init --firebase <id>` creates it over REST (not Terraform: its location can never change and Terraform does not adopt an existing database), with delete protection on, deny-all rules (only IAM principals read or write) and a Fugaro mark. When it would create the database it says so and you must **type `us-east5`** at a real terminal (`--yes`, `--non-interactive`, `--json` and a pipe never confirm it: the step is then left for you); a project that already has a Fugaro-marked database in `us-east5` is adopted without asking, and one in another location, of another type, with another owner's mark or with data and no mark is refused with nothing written. `--plan-only` shows the step. There is no `nam5` fallback: if `us-east5` is refused, the run stops with the API's error and choosing another location is your decision. Cost: within the free tier at expected scale.
2. **Rebuild and push the history image.** The history job now also runs `budget history --rollover`, a subcommand the image from M9b does not have. Build and push it as in "The history image" above (`sh images/build-base.sh history <region>-docker.pkg.dev/<project>/fugaro-base/history:latest`, `docker push`), then deploy it by rerunning `fugaro init --firebase <id>`. Rebuild the base image too if you want `fugaro` in the jobs to be the same version.
3. **Rerun `fugaro init --firebase <id>`.** Terraform adds the `firestore` and `firebaserules` APIs, `roles/datastore.user` and `roles/serviceusage.serviceUsageConsumer` for the history account on the Firebase project, `roles/storage.objectViewer` on the runs bucket for it (for `compute_usd`), the job's `FUGARO_RUNS_BUCKET` and `FUGARO_FIRESTORE_DB=(default)` environment, and the Scheduler job `fugaro-history-rollover` (`30 0 * * *`, UTC). Read the plan: it creates these, plus one in-place update (the history job's two new environment variables). The rollover Scheduler job is created **paused** and Terraform never resumes it: run the rollover once by hand and resume it as the live checklist (Check 23) says; until then nothing is pruned. Nothing changes for an installation with the budget off.
4. **Viewers.** Reading history needs `roles/datastore.viewer` **and** `roles/serviceusage.serviceUsageConsumer` on the Firebase project (the client sends `X-Goog-User-Project`). Terraform grants both to the launchers, operators and budget admins (people only); give them to anyone else by hand.

**The rollover** runs at 00:30 UTC. A day is written **provisional** once it has ended and becomes **final at 00:00 UTC of the day after next (D+2)**, because a run can still write to the previous day until then. A final document is never rewritten unless you run `fugaro budget history --rollover --day D --force` (a backfill: run it as the history account's job, or with credentials that may write Firestore). The database's day nodes are deleted only when a day is older than 8 days, final, equal to its documents and read back; anything else refuses (exit 1) and keeps the data. A rerun changes nothing. The history keeps requesters' addresses (`byPerson`) and the repositories' names, readable only through IAM.

**Reports**

```bash
fugaro report                                  # the last 30 days by day
fugaro report --by week --since 12w
fugaro report --by month --since 2026-01-01 --until 2026-09-30
fugaro report --by repo --since 7d
fugaro report --by model --since 7d
fugaro report --by person --since 30d --repo owner/name
fugaro report --since 90d --csv > spend.csv    # spreadsheet-safe cells
fugaro report --since 7d --json                # exact decimal *_usd strings
```

Model dollars, `NOTIONAL~` (a subscription's list-price figure, never billed) and compute dollars are separate columns and are never summed. Compute is an estimate and reads `n/a` when no run's was estimated. Days that are not final yet (the last day or two, and any the rollover has not reached) are computed live from the budget database and marked `(partial)`.

**Degraded mode.** With no `firebase_project`, no Firestore database or no mark, `fugaro report` says history is not enabled and prints run-record totals from the runs bucket, labelled "run records, not budget history" (a subscription's model spend shows as notional). A permission error (exit 1) names the two viewer roles. If Firestore is down the job exits 2 and the next night covers every day still in the database.

**Attribution.** A run's compute, hours and count belong to its start day. A run that crashed before writing a `result.json` has none of these (compute is `n/a`) and its outcome counts on the day the outcome was recorded, which can be the day after it started: a known, small difference.

**Retention.** Firestore documents are kept forever. The budget database keeps each day for at least 8 days and until it is final and archived.

**Rolling back.** Pause the Scheduler job (`gcloud scheduler jobs pause fugaro-history-rollover --location <scheduler region>`) or remove it with Terraform and the rollover stops; the budget database is then not pruned and nothing is lost. There is nothing to undo in Firestore except deleting the `spendDaily` documents (and `meta/installation`) yourself in the Console or with `gcloud firestore`; the database has delete protection, and **its location can never change**: a different location needs a different Firebase project. `fugaro report` falls back to run records meanwhile.

## Claude accounts a project job serves (0.9.0)

0.9.0 lets a profile serve more than the one Claude credential, by naming accounts: each name gets a Cloud Run job of its own, holding that account's token, and the policy bounds which repositories may use it. **It is in the released CLI since 0.9.0 — 0.8.x does not read any of it** — and the operator guide, with the refusal texts and the doctor lines, is [project-claude-accounts.md](project-claude-accounts.md).

**The profile field.** `profiles.<profile>.claude_accounts` in the project's local config is the list of accounts that profile's jobs serve; `default` is the unsuffixed `claude-oauth-token`, and every other name is a `claude_accounts.<name>` entry of the same file. A profile that lists accounts must also write its own exact `allow_repos` (no wildcard), every account it lists must cover every repository on it, and no Anthropic API key may sit beside them — publish and `fugaro init` refuse otherwise, naming the field. One job per (profile, provider, account) is what `fugaro init` deploys.

**The project-wide storage step.** Each account's token is a secret of its own, `claude-oauth-token-<name>`, and the job mounts the **project-wide** copy: a repository copy does not reach a shared job. In your own terminal, per installation:

```bash
claude setup-token
fugaro secrets set claude-oauth-token-<name>   # project-wide; --project-wide is the synonym
```

The bare `claude-oauth-token` follows the same rule — project-wide only when `project_secrets.claude-oauth-token` allow-lists the repository you run it from (at least one repository, where there is no checkout) — and with no such entry it is **not** refused: `--project-wide` is refused, naming `project_secrets`, while a bare `fugaro secrets set claude-oauth-token` run in a checkout quietly stores **that repository's own copy**, which a shared job does not mount. Store the default account's token from a checkout the entry lists. Rotation is another `fugaro secrets set` under the same name: the job mounts `version = "latest"`, so nothing is redeployed. Nothing is ever deleted — disable a version to revoke a token reversibly.

**The Version 3 rollout.** The published policy carries the account axis, and an older runner or CLI cannot read it (the node is refused, naming both versions). In order:

1. Upgrade the CLI, **per installation machine**: `brew upgrade dimipaun/tap/fugaro && fugaro upgrade`.
2. Republish the policy, **per installation**: `fugaro project policy show` first and keep its output, then `fugaro project policy publish --delete`, then `fugaro project policy publish`, then read the diff the publish prints. A publish refuses to overwrite a node written in another version, so the older node goes first; with no node to replace, the publish that follows rebuilds `allow_repos` from that installation's config (a repository removed with `fugaro project repos rm` comes back, one added with `repos add` is dropped), and the node's `clone_urls` and any hand-written `routing` block go with it — repair the list with `fugaro project repos add` / `rm`, and expect a shared job's runs to halt in between. `init --firebase` is not a remedy (it deploys the rules and marker and never writes `config/policy/shared`).
3. Refresh the runner image, **per repository checkout**: `fugaro image refresh` — it re-pins `base_images` and moves each repository's own jobs, but not a project job.
4. Move the shared jobs, **per installation**, on a machine where step 3 ran: `fugaro init --firebase <gcp-project>` — a project job runs the installation's base image, and only this re-apply of the installation moves it onto the pin step 3 recorded; until then it keeps the older runner, which refuses the version-3 node, and neither the launch check nor `fugaro doctor` (both read the pin, not the deployed job) says so.

## Installations from before M9a

M9a renamed what `project` means (design §1) and added the project name to the cloud. A pre-M9a installation (one GCP project, a single `config.yaml`, jobs with `FUGARO_PROJECT=<gcp id>`) is migrated once, by hand, in this order. Its jobs refuse to run in between (a new runner meets an old job environment and ends at once as `infra_error`, pointing at `init --repo`), so launch nothing meanwhile:

1. **Snapshot** `config.yaml`, each job's `gcloud run jobs describe --format json`, and the Scheduler job list; with the old binary check that `fugaro runs ls --since 1d` shows nothing running. **Pause every repository's `fugarochk-` Scheduler job**, so no check rebuilds on the new base or moves `:latest` meanwhile.
2. **The local config, by hand.** Choose the project's name. `mkdir -p ~/.config/fugaro/projects`, copy `config.yaml` to `projects/<project>.yaml`, rename its `project:` key to `gcp_project:`, add `name: <project>`, and move `config.yaml` to `config.yaml.bak`.
3. **`project: <project>` in each repository's `fugaro.yaml`,** merged to the repository's **default branch** (it is required: the runner refuses a repository that names none). The runner reads `project:` from the default branch (what `origin`'s HEAD names) even when `git.base_branch` is another branch, so with a base such as `develop` put it on both.
4. **A base image from M9a** (step 3 above), then `fugaro init --name <project> --base-image <tag>`: the plan stamps the bucket label, writes the marker object and rewrites `base_images`.
5. **Each repository, from its checkout:** `fugaro image build`, then `fugaro init --repo` (its jobs now carry `FUGARO_PROJECT=<project>` and `FUGARO_GCP_PROJECT=<gcp-project>`), then resume its Scheduler job.

A checkout whose `fugaro.yaml` has no `project:` yet is refused by every fugaro command run inside it (the repository decides the project), including `fugaro init --name`: add `project: <project>` first (step 3), or run the operator commands from another directory.

`fugaro init --json` changed shape: its `project` is now the project name and the new `gcp_project` is the ID.

## Turning checks off, or removing a workflow

Setting every workflow of an onboarded repository to `check: off` makes the plan delete its check job, its Scheduler job and the scheduler's invoker grant. Removing a workflow from `fugaro.yaml` makes it delete that workflow's job, its account and grants, and any secret only it used. Neither works in one run:

- the guard refuses every delete until `--allow-delete <address>` names it
- a job keeps `deletion_protection = true` in the state, and once it has left the configuration `--allow-job-delete` can no longer lower it, so the apply fails
- a secret has `prevent_destroy`, so the plan fails before the guard sees it

So do it in this order:

1. **Before changing `fugaro.yaml`,** run `fugaro init --repo --allow-job-delete` from the checkout. Its only change is `deletion_protection = false` on the repository's jobs.
2. **A secret only the removed workflow used:** Terraform must forget it rather than delete it. Take it out of the state with `terraform state rm '<address>'`, run by hand in the repository's working directory, outside fugaro's guard — or let `fugaro init --repo --retire` do it (see "Changing auth, or removing a workflow, secret or provider"), which is the one-command form of this whole order. Do **not** hand-write a `removed { from = … lifecycle { destroy = false } }` block into the working directory: `PrepareWorkdir` wipes and rewrites that directory, and whether `removed.from` accepts an instance-key address of a still-declared resource is unverified. Either way the secret and its value stay in Secret Manager, and `gcloud secrets delete` removes it if you want it gone. Skip this when no secret is used by that workflow alone.
3. **Change `fugaro.yaml`,** merge it, and run `fugaro init --repo --allow-delete <address> …`, naming each address the guard listed (the refusal prints them). Read the plan: it must delete only what you removed. The remaining jobs get their protection back in the same apply.

The same transition has a one-command form since 0.7.5, and it is the one to reach for: `fugaro init --repo --retire`, below. It also covers the cases this section's manual order does not — a job whose `deletion_protection` can no longer be lowered because its variant has already left the configuration, and a secret container Terraform refuses to destroy.

## Changing auth, or removing a workflow, secret or provider

`fugaro init --repo` reads the repository's Terraform state and the labels on its jobs and secrets before it plans, and prints what the change retires:

```
note: claude-oauth-token (fugaro-aurora-claude-oauth-token), claude-oauth-token-bmb (fugaro-aurora-claude-oauth-token-bmb) are no longer mounted by any job fugaro.yaml deploys; what is in Secret Manager stays there, and this is not a retirement: nothing is removed from Terraform's state and nothing is deleted
⚠ This change retires 8 addresses (project aurora, GCP project proj-1234, repository acme/webapp).
  8 go away.

Why: agent.auth no longer mounts claude-oauth-token; the named Claude account bmb is no longer a variant this repository deploys.

Going away (8, predicted from the state and the labels) — 7 the plan will delete, 1 deleted through the Cloud Run API after it:
  module.repo.module.workflow["go"].google_secret_manager_secret_iam_member.job["claude-oauth-token"] secret accessor: agent.auth no longer mounts claude-oauth-token
  module.repo.module.workflow["go_bmb"].google_cloud_run_v2_job_iam_member.launcher["user:owner@example.com"] IAM member: the named Claude account bmb is no longer a variant this repository deploys
  module.repo.module.workflow["go_bmb"].google_secret_manager_secret_iam_member.job["claude-oauth-token-bmb"] secret accessor: the named Claude account bmb is no longer a variant this repository deploys
  module.repo.module.workflow["go_bmb"].google_secret_manager_secret_iam_member.job["github-app-key"] secret accessor: the named Claude account bmb is no longer a variant this repository deploys
  module.repo.module.workflow["go_bmb"].google_service_account.job         service account: the named Claude account bmb is no longer a variant this repository deploys
  module.repo.module.workflow["go_bmb"].google_service_account_iam_member.operator["user:owner@example.com"] IAM member: the named Claude account bmb is no longer a variant this repository deploys
  module.repo.module.workflow["go_bmb"].google_storage_bucket_iam_member.job bucket grant: the named Claude account bmb is no longer a variant this repository deploys
  module.repo.module.workflow["go_bmb"].google_cloud_run_v2_job.this[0]    workflow job: the named Claude account bmb is no longer a variant this repository deploys

Order of operations:
  1. remove 1 address from Terraform's state without destroying it: the addresses no apply can delete (a secret container's prevent_destroy, a job whose deletion_protection the state says is on). Nothing in the cloud is deleted by this step.
  2. plan, show the plan's own counts and its full delete list, and ask again — the project's name typed at a real terminal, never --yes.
  3. apply, then delete the 1 orphaned Cloud Run job through the API.

Next command:
  fugaro init --repo . --retire
```

A retirement the run only *predicts* is a warning, not a refusal: an ordinary `fugaro init --repo` goes on to plan, and exits 1 only in the two cases below. A retirement an ordinary run cannot finish is one of:

- **A plan Terraform refuses on a `prevent_destroy` resource.** A secret container keeps `prevent_destroy` in the configuration, so a plan that would destroy one fails before the guard sees it. The run re-frames that failure in its own words — the summary above, and `Rerun with --retire` — and prints no Terraform text of its own; Terraform's stderr still goes to your terminal, and the workdir keeps it.
- **A job whose `deletion_protection` the state says is on, after its variant left `fugaro.yaml`.** No apply can lower it any more (`--allow-job-delete` reaches only the jobs the configuration still declares), so the run refuses (exit 1) and names `fugaro init --repo . --retire`.

`fugaro init --repo --retire` is the whole transition, in the order the design fixes:

1. **Remove the protected addresses from Terraform's state**, with `terraform state rm` (which destroys nothing in GCP): a secret container, and a job the state holds with its protection still on. This runs *before* the plan, because no plan exists until it has.
2. **Plan, print the plan's own counts and its full delete list, and confirm again** — the project's name typed at a real terminal. `--yes`, `--json`, `--non-interactive` and a pipe cannot take this confirmation; a coding agent's session cannot either.
3. **Apply**, then **delete the orphaned Cloud Run jobs through the Cloud Run API** — and only jobs carrying this repository's own labels, of a variant the configuration no longer builds. A job that is not ours, or another variant's, is refused, with the `gcloud run jobs delete` command to run by hand.
4. **Say what is left** if it stops in the middle: the addresses that left the state (alive in GCP, with nothing managing them until the delete runs) and the `gcloud` command that finishes it. Rerunning `fugaro init --repo --retire` is safe: an address the state no longer holds is not removed again, and the orphaned jobs are found by their labels.

**Fugaro never deletes a secret or a secret version.** When a retirement does release a container it is taken out of Terraform's state and stays in Secret Manager with its value: nothing in the flow calls `secrets delete`, `versions delete` or `versions destroy`, and `gcloud secrets delete` is what removes one if you want it gone. Which containers a run reports under `KEPT` is the label list's answer, not the state's: before it plans, the run lists the secrets carrying this repository's `fugaro` labels, and every live, correctly-labelled container goes back into the plan — so the same run adopts it (Readiness puts it in the spec's secrets and the plan imports it at its live ID, without which the apply would try to create a container that already exists) and prints it as one `note:` line ("no longer mounted by any job fugaro.yaml deploys") rather than as a retirement. That is the ordinary case, and it is why the 2026-10-14 retirement below kept nothing. `KEPT` is what is left for the containers the label list could not vouch for — the labels missing or wrong, or the `secrets list` call refused, which the run says in a warning. Re-adding a mount is therefore not on its own what brings a container back: the label lookup is, and it is the same lookup that keeps a correctly-labelled container out of the retirement set in the first place. A container a previous retirement already released is reported the same way, as a note. Neither path re-opens the gate: nothing is left to do about them, and the summary and the `--retire` suggestion do not recur.

`--retire` excludes `--plan-only`, `--print-vars` and `--forget` (each is refused: they print or forget rather than apply). `--allow-delete <address>` may be passed with it and can only narrow what the guard allows: the retirement's own allow-list already covers exactly the addresses its summary named.

**Worked example (2026-10-14).** Repository `acme/webapp` had deployed the named Claude account `bmb` as the variant `go_bmb`, and its owner moved back to the default account. `fugaro.yaml` lost the account; the state still held the variant's addresses, and the two OAuth containers were live in Secret Manager carrying the repository's labels. In order: the `agent.auth` edit in the checkout, merge; `fugaro init --repo` (the summary above, and the refusal — the state said `deletion_protection = true` on `go_bmb`'s job, so no apply could finish it); `fugaro init --repo --retire`, confirming the project name twice. The run reported the 8 addresses above: the two containers came back as the `note:` line (they were live and correctly labelled, so the plan adopted them and never retired them), the job's address left Terraform's state before the plan, the plan deleted the variant's other 7 addresses, and the job itself was deleted through the Cloud Run API after the apply. Both containers and their values are still in Secret Manager.

**Binaries older than 0.7.5.** Do it by hand in the repository's working directory, and in this order:

1. `fugaro init --repo --allow-job-delete` (only reaches jobs the configuration still declares).
2. `terraform state rm '<address>'` for each secret container and each protected job, with the addresses from `terraform state list` — this destroys nothing, and it is what makes the next plan possible.
3. `fugaro init --repo --allow-delete <address> …`, naming each address the guard lists, then `gcloud run jobs delete <name> --region <region>` for each orphaned job. **Do not hand-write a `removed { … }` block into the working directory** (`$XDG_STATE_HOME/fugaro/terraform/<gcp-project>/repos/<slug>`): `PrepareWorkdir` wipes and rewrites that directory on the next run, so the file does not survive to the plan it was meant for. `terraform state rm` is the mechanic that does.

## Flags to pass again

`init` doesn't remember every flag. The local config keeps the state bucket, launchers, operators, alert email, base image and scheduler region. It also keeps the shared budget: `init --firebase` records `budget.firebase_project`, so a plain `fugaro init` or `init --repo` afterwards keeps the backend, and `--budget-admin` entries are remembered in `terraform.budget_admins` when passed. `--firebase <id>` and `--budget-mode` themselves are not remembered: pass them again for `init --firebase` and to change the mode (`--budget-mode off` stops the jobs opening a budget session; the backend's address and key stay in every job, so a run can still read a published project policy). The budget flags (`--budget`, `--budget-currency`, `--billing-account`), `--registry-cleanup` and `--no-log-isolation` are not kept: leave one out and the plan removes or resets what it set. The guard refuses a plan that deletes the budget, alert channel or member grants, with a hint naming the flags that keep them. `fugaro init --repo` needs `--github-app-id` only the first time (it is stored), and records whether the repository uses Vertex AI, which `fugaro init` reads. Read the plan every time.

## Installations from before the tag mover role

A repository's build account needs `artifactregistry.tags.delete` on its own registry to move an existing `:latest`: `gcloud artifacts docker tags add` deletes the old tag first, and `artifactregistry.writer` lacks that permission. Without it, a repository's first build succeeds (there is no `latest` yet) and every later one, the daily check's included, fails at the `promote` step with `PERMISSION_DENIED: Permission 'artifactregistry.tags.delete' denied`, leaving `latest` where it was. The installation now has a custom role for this, `fugaroTagMover` (that permission alone), which each repository grants its build account on its own registry only, never on `fugaro-base` or the project. An installation applied before it existed gets it in two steps:

1. **`fugaro init`.** The plan's only change is one create, the role `fugaroTagMover`.
2. **`fugaro init --repo`, in each onboarded repository.** The plan's only change is one create, the build account's grant of that role on the repository's registry (`google_artifact_registry_repository_iam_member.build_tag_mover`). Until step 1 is applied, `init --repo` refuses, saying the installation's outputs have no `role_ids.tag_mover` and to run `fugaro init` first.

The next build then moves `latest` and removes its `candidate-` tag. A new IAM grant can take a few minutes to take effect; if that build still fails at `promote` with a permission error right after the apply, wait and run it again.

## Adopting an M4 installation

`fugaro init` adopts what M4's bootstrap script (`deploy/bootstrap/gcp-m4.sh`, removed from the tree after commit `0828eaa`) made, under the same names, and changes nothing you didn't ask for. Do it in this order, each its own plan and confirmation, with **zero deletes** in every plan: the installation, then a sandbox repository, then the others.

1. **Snapshot for rollback**, into a directory only you can read (mode 700): `gcloud run jobs describe <job> --region <region> --format=export` for each job; `gcloud storage buckets get-iam-policy` and `describe` for the runs bucket; `gcloud secrets get-iam-policy` for each secret; `gcloud artifacts repositories get-iam-policy fugaro`; the project's IAM policy filtered to `fugaro`; and a copy of `~/.config/fugaro/config.yaml`.
2. **The installation:** steps 1 and 2 above. The plan should import the runs bucket and the legacy `fugaro` registry, create the rest, and update in place only labels. The three lifecycle rules equal the bootstrap's, so the bucket's `lifecycle_rule` shouldn't change, and the legacy registry gets no cleanup policy.
3. **The base image:** step 3. The M4 dev tag in `fugaro` stays for a rollback.
4. **The sandbox, then each repository:** step 4. Discovery imports the job, the job account and the secrets, after checking that each carries our mark and that the live bucket and secret bindings equal the spec's byte for byte. The summary says `IAM: n bindings match the live ones (adopted), m new`. Acceptable in-place updates on an adopted job are the env's order, the CPU's form (`"1"` against `"1000m"`), client annotations and template labels, and `deletion_protection`, which lives only in state. The job keeps its **M4 image path and its legacy service account display name** (`Fugaro M4 job …`, so the account is never renamed and M4's tooling still recognizes it in a rollback), and the highlighted section must show no `image` or `service_account` change until the new registry has an image. If it shows a delete, stop.
5. **The first build, then the switch:** as in step 4.5 and 4.6. An adopted image has no record, so its schedule stays paused until the first build writes one; an unpaused first check would start a billable build that moves a live `:latest`.
6. **Retire `fugaro-build`** once the new build accounts have built successfully, below.

## Rolling back

At any point before `fugaro-build` is retired:

0. **First,** pause every Fugaro Scheduler job so no check submits a billable build during the rollback: `gcloud scheduler jobs pause <name> --location <scheduler region> --project <gcp-project>` (the names are in `fugaro init --repo --print-vars`, or `gcloud scheduler jobs list --location <scheduler region>`).
1. `fugaro init --repo --forget` in each onboarded repository. It removes the repository from Terraform's state and deletes its now-empty state object (the state bucket is versioned, so it stays recoverable); it destroys nothing.
2. `fugaro init --forget`. Its first phase is a normal guarded, confirmed apply with log isolation and registry cleanup turned off, which **deletes the `_Default` exclusion** (so M4's `fugaro logs` finds new lines in `_Default` again), the sink, the view, the log bucket and `fugaro-base`'s cleanup policies (the repositories' registries keep theirs, which M4 never reads), and nothing else. On an installation from before the tag mover role, it also creates that role, the one create the rollback allows (see "Installations from before the tag mover role"). **A deleted log bucket stays pending deletion for 7 days and its ID can't be reused meanwhile.** To retry the migration within the week, first run `gcloud logging buckets undelete fugaro --location=global --project <gcp-project>` (confirmed); `fugaro init` then imports it, and refuses to plan while it is still pending deletion. Its second phase, after another confirmation, runs `terraform state rm` for everything left.
3. **Restore** the backed-up config. The M4 tooling reads the old single `config.yaml` with its `project:` key (the GCP ID), so restore that file, not a project config.
4. **Always,** redeploy each job from the M4 spec: it puts back the M4 image path, env and order, and drops `FUGARO_COMPUTE_PRICES`. The M4 tooling is no longer in the tree. Check out `0828eaa`, the last commit that has it, build its `fugaro`, and run that commit's `deploy/bootstrap/gcp-m4.sh --apply job` for each repository with `FUGARO` pointing at that binary (its runbook is that commit's `docs/gcp-bootstrap.md`). The legacy display names were kept, so its ownership checks pass. The snapshot from "Adopting an M4 installation", step 1, is the reference to compare the result with.
5. Check `fugaro logs` on a new run, and `gcloud run jobs describe` for `maxRetries: 0`.
6. What `--forget` leaves is additive and doesn't affect M4: the build accounts, the new registries, `fugaro-base`, the scheduler account and its (paused) Scheduler jobs, the custom roles and the state bucket. Remove them with `gcloud` from the snapshot's diff, each confirmed.
7. **Retrying the migration later:** `fugaro init` and `fugaro init --repo` import again what `--forget` left behind and still carries our mark:
   - the runs bucket and the registries
   - the four custom roles, matched by title (a role with another title is refused; a deleted one is not imported, and the plan's create restores it)
   - `fugaro-scheduler`, matched by its display name
   - the log bucket, while log isolation is on. Log buckets carry no labels, so its description is the mark: a `fugaro` log bucket whose description isn't Fugaro's is refused (exit 1), with the `gcloud logging buckets update` command that marks it if it is Fugaro's, or `--no-log-isolation` if it isn't (a log bucket can't be renamed). Ours still pending deletion is refused (exit 1) with the `gcloud logging buckets undelete` command to run first. A change of its retention is listed under "⚠ Review these first".
   - each repository's accounts, secrets and jobs, and its Scheduler check job, which must target that repository's check job and run as `fugaro-scheduler` (anything else is refused)

   The `_Default` exclusion and the sink aren't imported: the rollback's apply deleted them, so the plan creates them again. **Not** the alert's notification channel and two policies, or the budget: they have no name Fugaro can find them by, so a retry creates a second of each. Delete them by hand before retrying, each confirmed, or accept the duplicates:
   - both policies, "Fugaro image check failed" and "Fugaro image check job failed": `gcloud alpha monitoring policies list --project <gcp-project> --filter='displayName:"Fugaro image check"' --format='value(name,displayName)'`, then `gcloud alpha monitoring policies delete <name>` for each;
   - the channel, "Fugaro alerts": `gcloud alpha monitoring channels list --project <gcp-project> --filter='displayName="Fugaro alerts"' --format='value(name)'`, then `gcloud alpha monitoring channels delete <name>`;
   - the budget, "Fugaro": `gcloud billing budgets list --billing-account <id>`, then `gcloud billing budgets delete <name>`.
8. If you removed the runs bucket's project-Viewer bindings, M4 doesn't need them; restore them from the snapshot if you want them back.

After `fugaro-build` is retired, a rollback also needs it re-enabled (`gcloud iam service-accounts enable`) and its bindings restored from the snapshot.

## What makes a project managed: two marks, not one

A project is managed when **both** of these are true, and it is not managed when either is not: its runs bucket holds Fugaro's creation fact (`fugaro/managed.json`) — the creation fact of the run that created the project, or the version-2 marker `fugaro managed flag` writes — **and the GCP project itself carries the label `fugaro_managed=true`**. Both marks are written by the same operator-run step, in your own terminal: `fugaro init --create-project --managed` for a project the run creates, and `fugaro managed flag <gcp-project-id> --budget N --budget-currency CCC` for one that already exists, each after you type the project's ID and state the budget amount — in a release that has managed mode on; in 0.9.0 both refuse (below). A plain `fugaro init --create-project` (no `--managed`) writes the label as well once a release turns managed mode on, and that is deliberate: the two marks go together with the creation fact whatever version it records, so a project a run created without `--managed` reads as managed exactly as it did before the label existed, and nothing else changes — the apply gate needs a version-2 fact that records an amount (Task 4.4), which such a project does not have, so it is refused however the label reads. **In 0.9.0, with managed mode off, a plain `fugaro init --create-project` writes the creation fact alone and no label**, says so, and the project it creates is not managed: init's own guard refusals for it keep their `--allow-delete` advice. Nothing else writes them: `fugaro managed apply` only reads them, and a coding agent's session can reach neither. **The label can only narrow:** a project with no label, with `fugaro_managed` set to anything but `true`, or that cannot be read at all is not managed whatever its creation fact says, and its runs keep the ordinary typed confirmations; a label alone never makes a project managed, because the creation fact is what records that Fugaro created the project and what the budget is read from. The label needs `resourcemanager.projects.update`, which is a write on the project and not on the runs bucket — no bucket condition and no deployer prefix fence bounds it (design/managed-projects.md, finding 14), which is why the owner-run steps write it rather than anything a run reaches. A project that already carries the key with another value is refused rather than overwritten, and a creating run or a flag that cannot write the label says so and names this section: the object written first is not taken back, so that project is one owner-run write away from complete.

**Which release writes the label, and what a project marked by 0.8.5 looks like.** The label is not part of 0.8.5's managed mode: that release's creating run wrote the creation fact alone. And 0.8.5's managed path does not carry over: **managed mode is turned off from 0.8.6 on, and 0.9.0 still ships with it off**: every way into it refuses — `fugaro init --create-project --managed`, `fugaro managed flag`, `fugaro managed apply` and `fugaro restore`, each before it reads or writes anything — so a project marked by 0.8.5 is not a managed project of the path below, and the two are not one mode. The label ships with the redesigned managed path, which the owner's ruling of 2026-10-19 moved to **0.9.5**, together with `fugaro managed flag` (Task 6.1): the 0.9.0 binary carries that command, and it refuses with `managed projects are disabled in this release` until then. What **is** in 0.9.0 is the inventory-aware apply: `fugaro managed apply` reads the whole-project inventory before it plans (the managed-projects plan's Task 4.5, on this branch), while the managed deployer's scoped role stays gated off, so no project is managed in 0.9.0 and the label is written by nothing. **A project marked by 0.8.5 therefore holds the object and no label**, which is also the state a creating run or a flag that could not write the label leaves behind (both need `resourcemanager.projects.update` on the project, which the credentials they run with need not hold): it is not managed until the line below is run, and the apply and the restore say so in one line.

**A project marked before this label existed is not managed until the label is written.** Write it once, in your own terminal, on the account that owns the project — and only where the creation fact is already right, because the label records the same fact and does not replace it. **UNVERIFIED until it is run live**: this is the one step of the label's life no test can make, because it is a write to a real project with the owner's own credential, so it is marked here until an operator has run it against a sandbox project and pasted the result back:

```bash
gcloud projects update <gcp-project> --update-labels fugaro_managed=true
gcloud projects describe <gcp-project>          # read the labels back
```

**Removing the label takes the project out of managed mode** — the read is fail-closed, so it is enough to unset it (`gcloud projects update <gcp-project> --remove-labels=fugaro_managed`), and the runs bucket's creation fact and its recorded budget stay where they are. **UNVERIFIED until it is run live**, for the same reason as the line above — it is a write to a real project with the owner's own credential, so it is marked here until an operator has run it and pasted the result back. It is the removal `fugaro managed flag` prints, beside the object to delete, as the undo of what that command wrote.

## Restoring a managed project

> **Disabled since 0.8.6, and still off in 0.9.0.** `fugaro restore`, `fugaro managed apply` and `fugaro init --create-project --managed` refuse before any cloud call ("managed projects are disabled in this release"): the deployer's scoped role is not created, because its `fmgd-` prefix fence is not an IAM condition GCP accepts yet. Managed projects are planned for a later release (0.9.5), by the owner's ruling of 2026-10-19, after the fence is redesigned. What follows describes them as they will work then.

`fugaro restore NEW_PROJECT_ID ROOT` rebuilds a lost managed project from zero into a **new** GCP project ID (a deleted project's ID stays reserved for about thirty days). The managed apply consults the whole-project inventory (a Cloud Asset read of the project, made with the operator's own credential, against what the installation's Terraform states account for): a resource created outside Fugaro in a managed project, or an inventory that cannot be read, keeps that run's confirmations, so a coding agent's session is refused and a person is asked; nothing is halted or deleted. It ends in `fugaro managed apply`, which is refused unless the project's creation fact (`fugaro/managed.json`, version 2) records a valid budget: an amount of 1 to 10,000,000 whole units and a three-letter uppercase currency code. That amount is the budget **alert** amount only; nothing compares it with Fugaro's recorded model spend. A project with no budget recorded (version 1, every `--create-project` without `--managed`) is refused, and the owner adds a budget to one with `fugaro managed flag <gcp-project-id> --budget N --budget-currency CCC`, run at their own terminal, which replaces that version-1 creation fact with the version that records the amount (the managed-projects plan's Task 6.1; the flag is refused from a coding agent's session, and its confirmation is the exact GCP project ID typed and nothing else); a managed project is created with `fugaro init --create-project --managed --budget N --budget-currency CCC --billing-account ID`. The restore refuses a coding agent's session first, before any cloud call; a coding agent reads that refusal to the user and stops, and never assembles the same sequence by hand. It takes the project's name typed at a real terminal and has no `--yes`. What it does, in order:

- **The old project must have been managed.** Whenever the old project can still be read (it answers, is `ACTIVE`, and its runs bucket answers), its creation fact is read and a project that is not managed is refused, whatever flags are given; a managed one gives the monthly amount unless `--budget` and `--budget-currency` are passed. When it cannot be read (deleted, closed, not yours to read) the restore proceeds only on `--budget` and `--budget-currency`. `--billing-account` is always required: the creation fact records no account.
- **Everything is checked before anything changes:** the agent and terminal rules, the selection, the root and the checkout's `gcp_project:` line, the old project's managed status, and the budget (whether from the flags or the old fact, it must pass the same shape check as a managed creation: 1 to 10,000,000 whole units of a three-letter uppercase currency code).
- **The new ID must not exist, and is never adopted.** A project that already exists is refused before anything is asked or changed; the creating path is also told to refuse one that exists by the time it reads it (where `init --create-project` alone would adopt it and write no creation fact).
- **The creation goes through `fugaro init --create-project --managed`**, with its own typed confirmations; the local project config moves to the new ID first (init installs into it). The creating run itself must then report that it created the new project and wrote its creation fact (a create-only write, so a fact planted beforehand is never taken as this run's) **and the project's `fugaro_managed=true` label** — the two halves of the mark (above) — and the new project's fact must open the managed apply's budget gate (version 2 with a valid budget), before the checkout's line moves. **A creation whose fact is written and whose label is not** (the label needs `resourcemanager.projects.update`, which the credentials the creating run uses need not hold) is the same project one owner-run write away from complete, so the config keeps pointing at it and the refusal names the missing label and the line in this document that writes it; the creating run's warning says the same thing at the time it happens. If that gate refuses after the creation was proved to be this run's, the new project exists and is a complete managed project except for the apply: the project config stays pointed at it (its previous content is in the backup), the checkout does not move, and the message says how to finish by hand (`fugaro managed apply ROOT` once the marker read works) or, when the marker records no valid budget, to shut the project down and retry with another ID. If the creation fails, panics, or ends with no creation fact written at all, **only the local project config file** is put back to its original bytes and the checkout is untouched, so the restore can be run again — with another ID if the project was created. (The half-marked case above is the one that does not go back: its project is this run's and is complete except for the label.) The backup of the config file stays, and **nothing the creating path did in the cloud is undone**: the project, its billing link, its Terraform state bucket, the installation's resources and any Secret Manager values it stored stay where they are (shut the project down with `gcloud projects delete` if it is unwanted).
- **Then** the checkout's `gcp_project:` line moves (shown as a diff, written on a yes), and the root is applied from zero through `fugaro managed apply`'s own path. No prior state is read.

Nothing is carried across: the runs in flight and their counters, the spend history, the kill switch, the Firestore and RTDB data, the Firestore database's location, the secrets, the plan files and the owner's delete list (`fugaro allow-delete` again; until then every delete and replace is refused) are not restored, and the project layer and the project's recipes are not re-published. The command prints that list at the end.

M4's single build account, `fugaro-build`, could read every repository's secrets and write every registry. After steps 4.5 and 4.6 have built successfully with per-repository accounts, retire it:

## Teammates: no setup

A launcher or operator in a checkout of an onboarded repository can run `fugaro run`, `ls`, `diagnose` and the other cloud commands on a fresh machine with no local config and no `fugaro init`. Design: [design/shared-config.md](design/shared-config.md).

**The shared file.** `fugaro/config.yaml` in the runs bucket (`gs://fugaro-runs-<gcp-project>`) holds the project config except what is owner-only, personal or derived: the budget block (mode, caps, allowed models, database URL, Firebase project, API key, token signer), `backend`, prices, `watch`, `max_parallel`, the repositories and the rest. Launchers and operators can read it (launchers read the whole runs bucket, and write only `runs/` and `tokens/`, the latter for the sealed budget token); only operators can write it. It never holds the `terraform:` section, `user:`, `endpoints:`, `providers:`, `project_secrets:`, a repository's `base_branch` (the checkout's `fugaro.yaml` names it) or any secret.

**Who publishes it.** An operator: `fugaro init` publishes it after it writes the local config (so do `init --repo` and `init --base`), and `fugaro init --publish-config` publishes it and stops. It merges into what is published (one that fails validation, or is another installation's, is replaced with a warning), so a machine that lacks another's repositories does not erase them. To republish after changing the local config or adding a repository, run `fugaro init --publish-config`; to remove an entry (an offboarded repository, a price) or clear a value, edit `fugaro/config.yaml` by hand (`gcloud storage cp` it down, edit, copy it up). Only installations whose runs bucket is the default name `fugaro-runs-<gcp-project>` publish; others get a warning.

**The `gcp_project:` line.** The checkout's `fugaro.yaml` carries `gcp_project: <id>` next to `project:`. It is the trust anchor: the GCP project is never guessed. A job image built before the field existed refuses a `fugaro.yaml` that has it, so the image comes first ("Rolling out", [release.md](release.md)). Per repository:

1. **The base image and the job images.** `fugaro image refresh` in the checkout, in your own terminal window or with `--yes` from CI or a script (see "Moving a repository to a new release" above). It pins this release's base image — signature-verified at the release's `-pinned` tag, by digest through the installation's remote repository — and records it, points the daily image check job at it, and rebuilds every workflow not yet built from it. If the local config sets `base_images.<kind>` to anything but this release's pin through the remote repository or a release image an earlier `fugaro init` copied (a `dev-<sha>` tag, a hand-pushed image), it stops and names the entry, and refresh never replaces such an image: either remove the entry from the local config (keep a backup) and rerun, or keep your own base image and rebuild from it with `fugaro image build --repo <owner/name> --workflow <name>`.
2. **The line.** `fugaro init --anchor` in the checkout. It runs no Terraform, publishes nothing and copies no image: it reads the local config and each workflow's build record, and refuses to write (exit 1, one line per workflow with its reasons and its fix in order: remove a custom `base_images` entry, `fugaro image refresh --repo <owner/name> --workflow <name>` in the checkout, `fugaro init --anchor`) while an image has no record, was submitted by a fugaro older than the field or by a development CLI, or was built FROM an older, development or hand-pushed base image (the record's `base_ref`: the image holds that base's `fugaro` binary, whatever CLI submitted the build; a record too old to say which base fails too), or while a base image the local config sets is a development or older one (the next build would start from it). A build record it cannot read from the cloud, missing credentials included, exits 2. The checks trust the build records (written by the builds and unsigned: the same trust as the shared config), and a hand-pushed image under a release-looking tag passes them. Then the diff; `--yes` writes, a terminal asks `Write this to <path>? [y/N]`, otherwise it prints the line to add by hand. A line that is already there with an image still unsafe exits 1 too. Commit it like any change.

Plain `fugaro init`, run in the checkout, also writes the line as its last stage (the repository stage, with the same diff and question, and the same checks as warnings), but only after the full converge; `fugaro init --repo` does not write it. Without the line, or `--gcp-project <id>`, the error says which line to add.

**The cache.** The first command reads the marker and the file and caches the validated config under `$XDG_CACHE_HOME/fugaro/shared-config/<project>.json` (else `~/.cache`). It is used as is for 24 hours; after that the bucket is read again. If the bucket cannot be reached at all, a cache up to 7 days old is used with a warning that says how old it is, and after that the command fails. Any answer from the server, a refused access above all, never falls back to the cache. The shared-config readers use a strict read for this; ordinary reads keep the driver's 403-as-absent mapping because the job and build accounts hold prefix-conditioned grants.

**A local config wins.** `--config`, `$FUGARO_CONFIG` and `~/.config/fugaro/projects/<project>.yaml` always take precedence, and nothing is fetched then. `validate`, `config example` and `init` never fetch. A command that would write the project config refuses when it is the shared one: run `fugaro init` to make your own.

**`fugaro doctor`** prints a `shared-config` line when the config came from the shared file (generation and age of the cache entry), or a `shared-config-differs` line when you have a local config and the published one differs, naming the fields.

**When it refuses.** Every refusal names the field. None is repaired.

| Message says | What it means, and what to do |
|---|---|
| add `gcp_project: <id>` next to `project:` | the checkout has no anchor: add the line, or ask whoever onboarded the repository to run `fugaro init --anchor` in the checkout |
| no Fugaro installation at gs://... / the installation ... is project X, not Y | `gcp_project:` is wrong, or names another project's installation: fix the line |
| has not published a shared config | an operator runs `fugaro init --publish-config` |
| no access to gs://... | you hold neither the launcher nor the operator role: ask an operator |
| needs the operator role | a launcher ran a publish (`fugaro init --publish-config`, `fugaro recipes publish`, `fugaro config publish`); an operator runs it, or adds you with `fugaro init --operator` |
| the shared config has a bad `<field>` / carries `<section>:` / is not valid | the object was tampered with, edited wrongly or written by another fugaro version: ask an operator to run `fugaro init` again (it replaces a refused object, with a warning); update `fugaro` if versions differ |
| `budget.firebase_project` is not `gcp_project` | a separate Firebase project: run `fugaro init` (adopt) for your own local config |
| over the 64 KiB limit | an operator runs `fugaro init` again, or edits the object |
| `--gcp-project` contradicts this checkout | the flag and `fugaro.yaml` disagree: drop the flag or fix the line |

## Offboarding a repository

There is no offboarding command. **Only step 1 is implemented.** Steps 2 and 3 are an unsupported outline: no fugaro command produces a removal or destroy plan (`init --repo` always plans the whole `fugaro.yaml`), so they mean running `terraform` by hand in the workdir, outside fugaro's guard and environment allowlist, and `PrepareWorkdir` overwrites hand edits the next time `init --repo` runs. Every resource that could lose data is protected on purpose: jobs by `deletion_protection`, and secrets, the runs bucket and every registry by `prevent_destroy`, which makes a destroy plan fail at plan time until you edit the module.

1. **Lower the jobs' protection:** `fugaro init --repo --allow-job-delete`, an apply whose only change is `deletion_protection = false` on the repository's jobs (workflow jobs and the check job). The flag is a variable of that apply, and the next run without it puts the protection back.
2. **Keep the secrets.** They hold values Terraform never saw, and `prevent_destroy` would refuse to delete them. Take them out of the repository's state first, so that Terraform forgets them and leaves them and their values in Secret Manager: `fugaro init --repo --retire` does exactly that (see "Changing auth, or removing a workflow, secret or provider"), and `terraform state rm '<address>'` run by hand in the repository's working directory is the fallback for a binary older than 0.7.5. Do **not** hand-write a `removed { from = … lifecycle { destroy = false } }` block into the working directory (`$XDG_STATE_HOME/fugaro/terraform/<gcp-project>/repos/<slug>`): `PrepareWorkdir` wipes and rewrites that directory, so the file does not survive to the run it was meant for, and whether `removed.from` accepts an instance-key address of a still-declared resource is unverified. Delete the secrets yourself later with `gcloud secrets delete` if you want them gone.
3. **Destroy the rest, by hand.** The repository's registry has `prevent_destroy`, so this needs the module edited first, and nothing checks the plan for you: read it line by line. The registry, its images, the job accounts, the build account and the check job and schedule go with it, and the runs bucket keeps the repository's `runs/`, `cache/` and `builds/` objects until their lifecycle rules delete them (`builds/` never expires: delete it by hand).

Finish with `fugaro init --repo --forget` if any state remains, and remove the repository from the local config's `repos`. The repository stays in the published shared config until you edit `fugaro/config.yaml` by hand (a later `init --publish-config` merges, so it does not remove it). Steps 2 and 3 haven't been exercised live.

## Staying up to date

Once a day, a command run at a real terminal (an actual tty — a real terminal check, not merely "stderr is some character device": stderr redirected to `/dev/null`, which is exactly what a shell's generated completion script does, never counts, so pressing Tab never starts it; also never in CI, never `exec` — the in-container runner — or `doctor`, which does its own check instead) makes one bounded, anonymous GET to GitHub's "latest release" API for `dimipaun/fugaro` (no token, no identifying data, no redirect ever followed, pre-releases and drafts never returned, a ~1 second timeout) in the background, and caches the answer under `$XDG_CACHE_HOME/fugaro` (`~/.cache` by default; a corrupt or unreadable cache is treated as no cache, never an error). It never changes a command's exit code, and it never makes the command itself wait on the network: at most it gives the check a short window (about 200ms) to finish before moving on, abandoning it (that day's check is simply lost, tried again next time) rather than ever visibly holding up an otherwise-fast command. When the cached answer names a stable release newer than this binary, the next command run at a real terminal (never under `--json`, `--plain`, inside a Cloud Run job, for a `dev` build, for `version` and `help` themselves, or for the completion machinery — `completion` and its generated shell subcommands, and the hidden `__complete`/`__completeNoDesc` commands a shell's completion script runs on every Tab press) prints one line on stderr, after the command's own output, at most once a day per release:

```
fugaro 0.6.2 is available (you have 0.6.1): brew upgrade dimipaun/tap/fugaro
```

Two independent switches turn off both the daily check and the line: the environment variable `FUGARO_NO_UPDATE_CHECK=1`, and the local config key `update_check: false` (`~/.config/fugaro/projects/<project>.yaml`, operator-only like `claude_accounts`: never published to the runs bucket). The config key only takes effect when the project is the one the current directory resolves to (a checkout's `fugaro.yaml`, `$FUGARO_PROJECT`, or the only project config there is); it is not read when a command only selects its project through `--project` or `--config` from a different directory. `fugaro doctor` always reports the comparison itself, as its `cli-version` check, regardless of either switch (a diagnostic is not a nag): ok when this binary is current, or when its version can't be told at all (a `dev` build); an informational line, never a failing one, when the lookup itself can't produce an answer (no network, nothing cached yet); a warning naming the brew command when it is behind (never an ordinary, always-failing check; like a stale plugin pin, `--strict` is what turns it into a failing exit code). Nothing here is verified against a live GitHub release lookup: no test, in this repository's own suite or CI, ever reaches the real network for it.

## Troubleshooting

### The /fugaro: skills are not listed

Claude Code installs the plugin when you open the folder in a new session and trust it; that did not happen (for example the folder was already trusted before `fugaro init` wired `.claude/settings.json`, or for another reason). In the checkout, in your own terminal, run:

```
fugaro upgrade --local
```

It installs or updates the plugin through the `claude` CLI and prints each command it runs; without `claude` on your `PATH` it prints the slash commands to type in Claude Code instead. Then restart the session. `fugaro doctor` reports the result as `plugin-install` (informational: `not installed` until the plugin is there, never a failure). Only trust folders you trust: a repository's settings can install a plugin from the marketplace they name.
