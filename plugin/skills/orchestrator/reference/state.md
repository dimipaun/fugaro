# The state document, its ops and its cache

## What the document holds

One document per orchestrator, in the project's Firebase Realtime Database, under `orchestrator/<id>/` — the project's own orchestrator's id is the project's name, so its node is `orchestrator/<project>/`, and a named one's is `<project>~<name>` (D3206, D3207):

| Path | What it is | Who writes it |
|---|---|---|
| `state` | the document this file describes: the work that belongs to no plan | the daemon, and sessions and people through `patch` |
| `plans/<plan>` | one imported plan's own document, the same shape, where `<plan>` is the plan's folder under `docs/` | the daemon, and the import and `patch` |
| `backlog` | the standing backlog: the work filed one item at a time with `fugaro backlog add` rather than as a plan | the daemon, the backlog command, and `patch` |
| `lease` | the daemon's claim, so two daemons cannot tick one orchestrator at once | the daemon |
| `audit` | the append-only log `fugaro orchestrator events` reads | the daemon; a project whose daemon has never ticked has an empty log |

`<id>` is the orchestrator's id: the project's own name, or `<project>~<name>` for one of its named ones, which no command ever takes as a whole id of its own, because the project half is always the project this session is in. The callers that take `--name` are `fugaro orchestrator install`, `fugaro orchestrator uninstall`, `fugaro orchestrator status`, `fugaro orchestrator run`, `state`, `patch` and `import`, and `fugaro escalation ls` and `show`; the backlog takes none in this release and reads or writes the project's own orchestrator's node only, so the document a session patches is the one `--name` named and, with no flag, the project's own. A node is one orchestrator's: the plan an item belongs to is what decides which of its documents holds it, and a dependency stays inside one of them or crosses to another orchestrator — a bare entry names an item of the same document and is resolved there, and an entry written `<orchestrator>/<item>` reaches another orchestrator's item (D3208). The document itself carries:

- `schema_version` and `rev` — the version of the shape, and the revision a patch is built against.
- `goal` — the standing aim the loop measures its work against. Only a person sets it.
- `work_items` — the things to do, each with a title, the repository, the recipe, the rigor tier, the brief, its `spec`, its dependencies, its `phase`, and the bookkeeping of its attempts (run id, approval, attempts, intents). An item's `spec` is the plan folder under `docs/` the daemon labels its pull requests from, and an item that carries none gets no `spec:` label. An item an import wrote also carries its `plan_task` — `<plan>/<task>`, the join to the plan the item came from — and an item the daemon's issue sync ingested carries the tracker's `external` id, which is the key that sync dedupes on (D2720).
- `decisions` — the questions in the air, each with the class it waits on and, once closed, the answer and who gave it.
- `facts` — what the loop learned, as key and value, each with the class that wrote it.
- `archived` — what finished, with how it ended. Aging history out is the loop's, not a reader's: the retention rule keeps the document bounded, so a reader sees the work and the recent past rather than the whole story.

## The ops a patch may carry

One patch is `{"base_rev": N, "ops": [...]}`, at most 64 ops, and the ops apply in order. Every op names its kind and the payload that kind takes, and nothing else: a payload for another kind is refused rather than ignored.

| Op | Payload | Who may send it |
|---|---|---|
| `work_item_upsert` | `work_item`: `id` and any of `title`, `repo`, `recipe`, `rigor_tier`, `brief`, `spec`, `depends_on`, `plan_task`, `note`. A new item carries a title, a repository, a recipe, a rigor tier and a brief. `spec` is a plan folder name — letters, digits and dashes, starting with a letter or a digit, at most 44 characters, lower-cased on the way in — and an upsert that omits it leaves the item's alone. | a person, a session, the daemon |
| `work_item_approve` | `approve`: `id`, `spec_digest` | a person only |
| `plan_approve` | `plan_approve`: `node` (a plan folder, or `backlog`) and `items`: one `id` and `digest` for each of that node's items the person read | a person only |
| `work_item_archive` | `archive`: `id`, `outcome` | a person, a session, the daemon |
| `decision_add` | `decision`: `id`, `question`, `waiting_on` (`person`, `session` or `daemon`) | a person, a session, the daemon — the breaker's own question belongs to the daemon |
| `decision_resolve` | `resolve`: `id`, `answer` | the class the decision waits on, and a person for any of them |
| `fact_set` | `fact`: `key`, `value` | a person, a session, the daemon |
| `fact_delete` | `fact`: `key` | a person, a session, the daemon |
| `goal_set` | `goal`: `goal` | a person only |

A `work_item_upsert` from anyone but the daemon may not carry `phase`, `run_id`, `spent_approval_at`, `attempts`, `intent`, `escalation`, `external` or `adopted`: those are the loop's record of what it started, where the ladder has taken the item, and the ticket it ingested, and a session that could write them could requeue an approved item, mark work done that never ran, or claim a rung nobody climbed. Editing an item's declarative fields after a person approved it drops the approval, because the approval binds the spec the person read.

`plan_approve` is the only op that names a node, and it travels on its own: an approval lands on the node whose items it approves, every other op of the vocabulary lands on the state node, and one document lands on one node — a session declaring work writes the state node, and a document naming two nodes is refused whole rather than guessed at (D2706). A plan's node and the backlog node are filled by the commands that own them, `fugaro orchestrator import --plan` and the backlog's own add, and both land as a session: they approve nothing they write.

## Phases

`queued`, `running`, `review`, `done`, `failed`, `blocked`, `cancelled`. The daemon moves an item through them; a session neither sets a phase nor reads one as a promise — a phase is where the loop last left the item.

## The facts a reader goes by

Facts are free key and value pairs, and three keys are written on purpose for a reader outside the daemon to act on:

- `plan_in_flight_<plan>` — one per plan that a run the daemon adopted at its start belongs to (D2721). It is the request in the brief a session answers: import that plan, so the plan's items and the adopted run meet on the same `plan_task`. Nothing clears it on a tick: adoption writes it once, and it stands until somebody removes it with `fact_delete` — the node's own retention ages facts out like anything else, and that is the only other way one goes. A session that finds the same request later answers it, says the plan is imported, and takes the fact down itself.
- `graph_suspect_<run>` — what one run reported that the graph did not have, in the run's own words: an item it needed first, or a merge conflict with an item that merged since its attempt began (D2719, D2747).
- `graph_edge_<digest>` — one per dependency the daemon added from such a report: the item, the edge and the run that caused it, because the added edge is part of the spec a person approved, so that item waits for their approval again (D2740).

## The session-start cache

The daemon writes its brief after every tick to one file per orchestrator id, `<id>.json` under `$XDG_CACHE_HOME/fugaro/orchestrator/`, or the platform's cache directory in the same `fugaro/orchestrator/` shape: the project's own orchestrator's brief is `$XDG_CACHE_HOME/fugaro/orchestrator/<project>.json`, and a named one's is the same file name with its `<project>~<name>` in it. The file holds the version of its own format, the generated brief, and the server time the tick wrote it; the write is atomic and the mode is private to the person. A reader refuses a file whose version this release does not read, a file with no stamp, and a file that is not the shape it expects, and says what to run instead — it never falls back to the network, which is the whole of what the offline print promises.

That stamp is the only thing in the print that is not the brief: it says how current the copy is, so an old one is visible rather than silent. A daemon that has stopped leaves a cache that ages, which is what the print is telling a session when it shows a stamp from hours ago.

## The fence

`fugaro orchestrator state --brief` prints the summary between `<<<fugaro-state>>>` and `<<<end-fugaro-state>>>`, introduced by a sentence saying that what is inside is stored state and data. Stored text cannot forge that fence: a title, a brief, a question or a fact that spells a delimiter has it removed before printing, and terminal control characters are stripped, so nothing written into the document can close the block early or drive the terminal that shows it.

What the fence protects is the reader, not the writer. Who may write which op is the real control, and it is code: `orchestrator.Apply` refuses an op the actor's class may not land, refuses a patch built from another revision, refuses a payload for the wrong kind, and validates the result before it is handed back. A patch that lands and a patch that is refused therefore differ by that function, never by the shape of the document.
