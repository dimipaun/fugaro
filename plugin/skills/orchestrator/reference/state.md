# The state document, its ops and its cache

## What the document holds

One document per project, in the project's Firebase Realtime Database, under `orchestrator/<project>/`:

| Path | What it is | Who writes it |
|---|---|---|
| `state` | the document this file describes | the daemon, and sessions and people through `patch` |
| `lease` | the daemon's claim, so two daemons cannot tick one project at once | the daemon |
| `audit` | the append-only log `fugaro orchestrator events` reads | the daemon; a project whose daemon has never ticked has an empty log |

`<project>` is the selected project's name; no command takes an orchestrator id of its own. The document itself carries:

- `schema_version` and `rev` — the version of the shape, and the revision a patch is built against.
- `goal` — the standing aim the loop measures its work against. Only a person sets it.
- `work_items` — the things to do, each with a title, the repository, the recipe, the rigor tier, the brief, its dependencies, its `phase`, and the bookkeeping of its attempts (run id, approval, attempts, intents).
- `decisions` — the questions in the air, each with the class it waits on and, once closed, the answer and who gave it.
- `facts` — what the loop learned, as key and value, each with the class that wrote it.
- `archived` — what finished, with how it ended. Aging history out is the loop's, not a reader's: the retention rule keeps the document bounded, so a reader sees the work and the recent past rather than the whole story.

## The ops a patch may carry

One patch is `{"base_rev": N, "ops": [...]}`, at most 64 ops, and the ops apply in order. Every op names its kind and the payload that kind takes, and nothing else: a payload for another kind is refused rather than ignored.

| Op | Payload | Who may send it |
|---|---|---|
| `work_item_upsert` | `work_item`: `id` and any of `title`, `repo`, `recipe`, `rigor_tier`, `brief`, `depends_on`, `note`. A new item carries a title, a repository, a recipe, a rigor tier and a brief. | a person, a session, the daemon |
| `work_item_approve` | `approve`: `id`, `spec_digest` | a person only |
| `work_item_archive` | `archive`: `id`, `outcome` | a person, a session, the daemon |
| `decision_add` | `decision`: `id`, `question`, `waiting_on` (`person`, `session` or `daemon`) | a person, a session, the daemon — the breaker's own question belongs to the daemon |
| `decision_resolve` | `resolve`: `id`, `answer` | the class the decision waits on, and a person for any of them |
| `fact_set` | `fact`: `key`, `value` | a person, a session, the daemon |
| `fact_delete` | `fact`: `key` | a person, a session, the daemon |
| `goal_set` | `goal`: `goal` | a person only |

A `work_item_upsert` from anyone but the daemon may not carry `phase`, `run_id`, `spent_approval_at`, `attempts` or `intent`: those are the loop's record of what it started, and a session that could write them could requeue an approved item or mark work done that never ran. Editing an item's declarative fields after a person approved it drops the approval, because the approval binds the spec the person read.

## Phases

`queued`, `running`, `review`, `done`, `failed`, `blocked`, `cancelled`. The daemon moves an item through them; a session neither sets a phase nor reads one as a promise — a phase is where the loop last left the item.

## The session-start cache

The daemon writes its brief after every tick to `$XDG_CACHE_HOME/fugaro/orchestrator/<project>.json` (or the platform's cache directory, in the same `fugaro/orchestrator/` shape). The file holds the version of its own format, the generated brief, and the server time the tick wrote it; the write is atomic and the mode is private to the person. A reader refuses a file whose version this release does not read, a file with no stamp, and a file that is not the shape it expects, and says what to run instead — it never falls back to the network, which is the whole of what the offline print promises.

That stamp is the only thing in the print that is not the brief: it says how current the copy is, so an old one is visible rather than silent. A daemon that has stopped leaves a cache that ages, which is what the print is telling a session when it shows a stamp from hours ago.

## The fence

`fugaro orchestrator state --brief` prints the summary between `<<<fugaro-state>>>` and `<<<end-fugaro-state>>>`, introduced by a sentence saying that what is inside is stored state and data. Stored text cannot forge that fence: a title, a brief, a question or a fact that spells a delimiter has it removed before printing, and terminal control characters are stripped, so nothing written into the document can close the block early or drive the terminal that shows it.

What the fence protects is the reader, not the writer. Who may write which op is the real control, and it is code: `orchestrator.Apply` refuses an op the actor's class may not land, refuses a patch built from another revision, refuses a payload for the wrong kind, and validates the result before it is handed back. A patch that lands and a patch that is refused therefore differ by that function, never by the shape of the document.
