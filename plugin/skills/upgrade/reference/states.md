# What an update prints

A run starts with a line `== ` and the checkout's directory, then one line per step: the step (`plugin:`, `cloud:`, `rules:` or `policy:`), its state and a reason. A `checkout:` line means the path itself was refused (not a checkout, not a Fugaro checkout).

## States

| State | Meaning | What you tell the user |
|---|---|---|
| `current` | nothing to do | that it is up to date |
| `done` | the step changed something | what changed (the reason says) |
| `stale` | only with `--check`: the step would change something | what would change and why |
| `skipped` | not run here, by rule; the reason names the rule | the reason, in plain words |
| `failed` | the step stopped, and this checkout's later steps did not run | the reason, and the rerun line in the summary |
| `not run` | a step after a failed one | nothing: it runs on the rerun |

## plugin

- `installed X.Y.Z` (`current` or `done`): the version Claude Code has installed at user scope on this machine — the one `fugaro update-skills` maintains, and not what a checkout's own settings may have installed there. After `done`, running sessions need a restart.
- `installed X.Y.Z` (`stale`), the reason also naming this fugaro's own version: Claude Code has an older plugin than the binary.
- `not installed on this machine` (`skipped`, with `--check`): `fugaro update-skills` installs it.
- `newer than this fugaro`: the marketplace on this machine is pinned to a newer release than this binary (a newer `fugaro` pinned it, and the pin is never moved down), so the plugin comes from there; the user upgrades the binary.
- `would not declare the marketplace at vX.Y.Z` (`skipped`): Claude Code refused to declare the `fugaro` marketplace at this release's tag, because the name is declared for it in settings this `fugaro` does not own (an organization's, say) and that declaration names another source. The plugin cannot be had on this machine; the reason names the slash commands that do it by hand, and the update's other steps need nothing from it. Only that refusal is read this way: any other failure — a clone that failed, a network that is down — fails the step, and what the step's clear removed — the marketplace declaration, and the plugin install Claude Code took with it — is put back first, so neither outcome leaves the machine without the marketplace and the plugin it had.
- `claude is not on PATH` (`skipped`): the user types the printed slash commands in Claude Code.
- `never replaces it` (`failed`): Claude Code on this machine has a `fugaro` marketplace from another source; the user decides whether to remove it.
- `cannot tell` (`skipped`): Claude Code's record could not be read; `fugaro update-skills` finds out.

## cloud

- `base images to move` (`stale`): the local project config records an older base image, or none, for a kind the workflows use. The user runs the command in SKILL.md step 4.
- a custom base image (`stale` with `--check`, `failed` without): a development or hand-pushed base image stops the refresh; the fix it printed comes first.
- `records this release's base image` (`current`): nothing to move. `--check` reads no build record, so a build that failed after the base moved does not show here.
- `a coding agent's session` (`skipped`): always, in this session; hand the user the command in SKILL.md step 4.
- `no local project config selects this checkout` (`skipped`): this machine is a teammate's; there is nothing to do here.
- `not onboarded` or `no fugaro.yaml` (`skipped`): the repository has no job image yet; setting it up is a separate task (the `setup` skill).
- `on this release's base image` (`done`) or `no base image to copy and no image to rebuild` (`current`): only when the user ran it in their own terminal.
- `stopped at step N` (`failed`): the refresh stopped; its reason names the steps that finished and the rerun line.
- a `note:` on the deployed job's whole copy of the local project config (multi-model `providers`, `model_prices`, budget settings, the region's custom compute price, the GitHub App ID): printed after a real cloud step, alongside any of the states above, whenever the copy no longer matches the local config, whatever the local config currently holds (removing every provider locally still leaves the job's old copy to find); names the fields and the one command that refreshes it, for the user to run themselves (SKILL.md step 4). Under `--check` it instead always says `--check` cannot tell, because `--check` makes no cloud call.

## rules

- `the deployed security rules are generation N, this Fugaro's own` (`current`): the project's database already carries the rules generation a project policy is read under, and this Fugaro's document. Nothing was written.
- `deployed the security rules (generation N) and recorded it` (`done` without `--check`): the plan was printed above `== ` for the checkout and the confirmation under it read nothing — a person at the terminal by being there, or `--yes` — and the generation was deployed and recorded. It ran before the policy step, whose write is gated on that generation.
- `a coding agent's session` (`skipped`): always, in this session; the user runs the upgrade in their own terminal window.
- `--check` (`skipped`, with a `note:`): `--check` makes no cloud call, so it cannot tell which generation is deployed; the upgrade without `--check` deploys it.
- `no local project config selects this checkout`, `not onboarded`, `no fugaro.yaml` (`skipped`): the same verdicts the cloud step's own line gives, and nothing here is the machine's to deploy.
- `names no shared Firebase budget backend` (`skipped`): there is no database to read the deployed rules in.
- a skip naming the config's `budget.firebase_project` or the database's mark (`skipped`): the database is one this installation may not write — another installation marked it, it holds data and no mark, or the config's project is not the installation's own and nothing adopted it. The reason names the one move that adopts it — the update door's `--firebase-project <gcp-project-id>`, which the user runs in their own terminal — and nothing was written.
- `could not be read` (`skipped`): the deployed rules or their generation marker could not be read, so whether this Fugaro's generation is deployed is unknown. Nothing was written.
- a reason naming a marker this Fugaro did not write — newer than this binary, or hand edited (`skipped`): the deployed rules are not this binary's to replace; a newer binary, or the hand edit, is what puts it right. Nothing was written.
- a refusal from the database (`failed`): the read or the write itself failed, and this checkout's later steps did not run.

## policy

- `the published policy is version Y` (`current`): the project's published policy node is already the version this `fugaro` writes. Asked nothing.
- `no policy is published at ...` (`current`): the project has a budget backend and no node in it; every run falls back to the ceiling its job's environment carries. Not the same line as the one above, and not something to go looking for.
- a reason naming the version the node carries and the one this `fugaro` writes (`done` without `--check`): the node is rewritten in place, after the diff printed above `== ` for the checkout and a confirmation that read nothing (a person at the terminal by being there, or `--yes` where the flag reaches the step). Nothing is deleted, and the fields the owner edited into the node by hand are kept.
- `a coding agent's session` (`skipped`): always, in this session; the user runs the upgrade in their own terminal window.
- `--check` (`skipped`, with a `note:`): `--check` makes no cloud call, so it cannot tell whether the node is current; the upgrade without `--check` migrates it.
- `no local project config selects this checkout`, `not onboarded` (`skipped`): the same verdicts the cloud step's own line gives, and nothing here is the machine's to migrate.
- `names no Firebase budget backend` (`skipped`): the node lives in that database, so there is none to read.
- `the published policy is version N and this step holds it there` (`skipped`): the installation runs the credentials service, and the image its tfvars record is not this release's, so raising the node would leave a service that refuses every cascade and Bitbucket-proxied call of the project. An update replaces no service — its cloud step refreshes job images only, and the service's image is the installation root's — so the node is held where it is, and the reason hands the user the command that migrates the node and replaces the service in one run (SKILL.md step 4).
- a refusal (`failed`): the node is one this `fugaro` must not rewrite — written by a newer `fugaro` (the reason names the versions and the upgrade), a version below the migration chain's first step (the reason names the removal and republish that are the way through), or carrying keys this `fugaro` does not know (the reason names their count, never their values). Nothing was written; the node is as it was.
