# An independent review of a pull request

`fugaro review --pr N` reviews a pull request that already exists, in a job of its own rather than the run's: a review needs no profile, and with no shared project job `fugaro update` deploys an implicit review-only job. The account is the repository's own — `agent.oauth_token` in `fugaro.yaml`, else the project's `default_claude_account` — and which credential serves its model calls is the project's routing table (`fugaro routing ls`). `--mutate <file>:<test>` asks for one mutation check of the reviewed head.

## What the review is judged against

By default a review judges the pull request against the task of the run that opened it, found through the runs bucket alone rather than the branch the forge reports — so a pull request no run produced, or one whose runs are older than the follow-up lookback, is reviewed against nothing, and says so. Two flags ask for something else, and both are on `fugaro run --recipe review-only --pr N` as well, with the same default:

- `--code-only` asks for the code alone, with no task at all.
- `--spec FILE` judges the diff against the task in FILE instead, which is how a pull request no run produced is reviewed against something. FILE's text is redacted like every other text a launcher adds, and a file over 16 KiB is refused with its size.

The two are refused together, and either is refused on a launch that is not a review — an ordinary recipe or a follow-up.

`fugaro review show RUN` prints the verdict the job wrote, its markdown, and one `against:` line saying what the review was checked against: the run whose stored task was quoted, the digest of a hand-supplied FILE, or none with the reason there was nothing. `--json` prints the artifact's own bytes alone. Where the job's image predates the release that reads a review's spec, the review is launched code-only instead and the launch's own JSON document carries the reason: read it out, and the upgrade below moves the installation onto a base image that can read a spec.

## What a review needs from the installation

A review needs the installation's credentials service — the reviewer's read-only git credential and its model calls come from there — so an installation without one refuses the launch, and so does a service predating the release that admits the review job's own caller. Both refusals name the upgrade that fixes them: read either out, never work around it, and leave the upgrade to the user, who runs it in their own terminal, not through the agent:

```bash user-runs
fugaro update
```

A newer service that does not admit the caller is the one shape this cannot see: the launch starts and the review fails — read the run's own failure.
