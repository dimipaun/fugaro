# The escalation ladder

You are reading what a project's orchestrator has done, or is doing, to a pull request that stopped converging, and reporting it without promising a merge.

A run's own recipe loop is not the last word. A pull request that stalls in a project whose orchestrator runs is picked up by that project's **orchestrator daemon** — one machine per project — which walks it up a ladder of rungs. Each rung is one step:

- **R0 — the cheap first step.** The branch is put back on its base, the conflicts resolved and the tests re-run. It is spent once per head and at most twice per pull request, because a rebase run pushes a new head and without the cap an item could rebase forever.
- **R1 — the floor, and today's behaviour rather than a step.** The item goes back to its own recipe loop. The ladder starts no run of its own for it.
- **R2 — one stronger single pass.** The `escalate` recipe runs once for the item, on a model grade above the item's own: `strong`, or `strongest` for a mode whose threshold row names it. Both grades are project-layer keys, so no repository can set them.
- **R3 — the pull request itself.** The ladder stops spending runs of the item's recipe and reads the pull request instead: the head it will judge is reviewed by a run whose own work is reading it, then an advisory merge judge reads the same head and may only veto, and then the ladder may merge and file the findings it left open as follow-ups.
- **R4 — the last resort.** A change that will not converge is split into sub-tasks scoped to the blocker the judge named. The same task is never relaunched.

## The merge, and why it is rare

The gate is a property of the code and not of anyone's judgement. The run behind the pull request is over, its commits are pushed with a changed-path set that is neither empty nor truncated, the host's own CI read is green, every changed path is `Routine` and no finding blocks — no critical one, and none high in a security path. Every reading is made at **one** head SHA and the merge names that same SHA, so a push in between refuses the merge; anything the gate cannot read at all refuses it too, the same way.

The mode the project runs decides only **who is told**, never whether the gate applies. A mode whose ceiling is not a merge, every item in the Critical mode, and everything the gate refused all end by asking the user instead. A pull request that is still a **draft** is readied and then merged at the head it readied unless the machine has turned `escalation.ready_drafts` off, and that key ships **on**. So the outcome of a stall on a machine that wrote `false` is a question for the user, not a merge, and no merge is ever a run's or yours.

Two bounds stop the ladder itself: a ceiling on how many of its own runs one item may spend, and the item's own cost ceiling, past which the decision stops spending and goes to rung 3 whatever rung the item is at. Every run the ladder starts is covered by the item's own standing approval, and an item nobody approved is one the ladder leaves exactly where it is.

Every move it makes posts one comment on the pull request and one line in the project's audit log, so what the ladder did is readable on the pull request itself.

## The commands

- `fugaro escalation ls` lists every pull request the ladder has acted on: the rung it is at, the reason it entered it, how long it has been going, how many of the ladder's own runs it has spent and what its own runs have cost. `--json` prints the same as a versioned document, and a figure this machine cannot read is written as unknown rather than as a smaller one.
- `fugaro escalation show <item>` prints one item in full: the same row plus every rung transition, oldest first, with the head each one was decided at. `<item>` is the id `fugaro orchestrator state` prints the work item under, and one work item is one pull request.
- Both commands only read. The ledger is the daemon's to write: nothing here moves a rung, readies a draft or merges, and none of that is yours to do for the user.
- A run's own side of the same picture is `fugaro runs ls` and the digest of the runs (`reference/status.md`, `reference/periodic-reviews.md`).

## What to say

Read the list before you say anything about a stalled pull request, and never tell the user a pull request is being climbed unless it is in that list: a project whose daemon does not walk the ladder has no items there, and its pull requests move only when a person moves them. Then say which rung the item is at, what its last transition was and why, what it has cost, and what is waiting on the user — never that Fugaro will merge it.
