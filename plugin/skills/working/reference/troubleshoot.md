# A failed Fugaro command, explained

`fugaro troubleshoot [ID]` explains one Fugaro command that failed on this machine — the newest one, or the ID you pass — from the log, the effective configuration and `fugaro doctor`'s output that failure left behind. Read its answer out to the user, with the one command that fixes it when it printed one, and never run that fix yourself: the command explains, it applies nothing, and a refusal it printed is a reason to say what would fix it rather than to look for a way around it.

A `fugaro` command the answer prints is checked against the CLI's own command tree before it is shown as runnable, and anything else is marked as not checked, so neither is something to run blindly.

## The four tiers, in order

It answers in one of four tiers, and it tries them in this order: the first tier that can answer does, and the ones after it are never reached. The order is the design — the tiers that cost nothing run first, so a failure the cloud itself caused is explained rather than met with a second failure.

1. **The rules, with no model.** The log or the run record already names the cause, and the command prints it as `cause` and `fix` with the log line it was read from. Nothing is sent anywhere, and the exit is zero because it explained something.
2. **The local diagnosis**, on this machine's own credential: the `claude` login already here, or `CLAUDE_CODE_OAUTH_TOKEN` or `ANTHROPIC_API_KEY` when the environment sets one. It reads no secret of the installation's and needs no gcloud, so it still answers when the cloud is what is broken. A `claude` that is present but not logged in is refused in one sentence naming `/login`, with no evidence printed.
3. **The cloud diagnosis job**, asked for last of the tiers that call a model, and reached only when this machine holds no login of its own — no `claude` to run and neither variable set. One bounded job in the user's own project reads the same redacted evidence the local tier would have sent — the log, `fugaro doctor`'s output, the effective configuration with secrets removed, and a reference to the Fugaro source at the version that failed — and writes the answer, which the command reads back out of the run's own prefix. It says what it cost: the figure the diagnosis run's record holds, printed beside the answer with the run it came from.
4. **Evidence only.** The evidence is printed where it already is, with the reason nothing diagnosed it, and the command exits non-zero.

## The cloud tier

It never runs on the user's own credential. The job is the review-only variant `fugaro review --pr N` uses, which mounts no credential of its own: the model call is signed for the project by its credentials service, the user's login never enters the container, and the CLI reads no secret of the installation's into itself. What leaves the machine is what the local tier would have sent, and the one line printed before anything is uploaded names both places the evidence goes, the user's own project first.

It is the only tier the project's own state can refuse, and every one of these is asked before anything is uploaded, so the person gets the reason rather than a second failure: a job image older than the release that carries this tier; a credentials service that is not deployed; a budget that is spent; and a repository the launch's roles gate does not admit, refused before a task, a token or an execution exists. The image and the credentials service name the fix, and it is the user's to run in their own terminal, not through the agent:

```bash user-runs
fugaro update
```

The budget's refusal is the launch path's own sentence, read out as it stands: it names the launch flag that skips the check, and this tier takes no such flag — a pre-flight that skipped the budget would vouch for a launch the backend refuses when it starts. Say the budget is what refuses, quote the sentence, and do not tell the user the flag is theirs to run.

Two limits are the tier's own, and neither is a fault to report: it needs a repository checkout, because a run is scoped to a repository and a failure that happened outside one has none, and it declines there with that reason; and its run is bounded far below a task run's — a per-run cap of $0.25 and a fifteen-minute timeout, spent on the project's credential rather than the user's, launched once with no retry.

The run is the catalog recipe `troubleshoot`, embedded in the task rather than named for the runner to resolve: a `mode: artifact` recipe whose one step is `diagnose`, delivering `out/diagnosis.md` and `out/diagnosis.json` and opening no pull request. It is never the recipe for a task, and it is the recipe's own `diagnose` step that ties the tier to a job image new enough to run it.

## What the answer is

The answer is the same shape a local diagnosis gives: the outcome (one of `configuration`, `bug`, `fixed_in_newer_release` or `unclear`), the cause in plain language, the evidence it was read from, what could not be checked, and the fix or the issue report. A `bug` or an `unclear` answer carries an issue report the user may post; posting it is theirs, not this session's.

`fugaro troubleshoot --json` carries the same answer as data, with which tier answered as `tier` (`rules`, `local`, `cloud` or `evidence`), the diagnosis run the cloud tier launched as `cloud_run`, and its cost as `cloud_cost_usd`. A cloud answer costs the user money: read its cost line out with the answer, and never launch the command again to "confirm" one — a second diagnosis is a second question.
