# The decisions, one topic at a time

Ask **one topic at a time**: say what the topic is, what you found, your recommendation and why, then wait. Apply the answer to `fugaro.yaml` before the next topic. A choice the user has already made in the conversation or in an existing `fugaro.yaml` is confirmed, not asked again. Never fill a topic in silently, and never write a value the user didn't give for the topics marked "from the user".

## 1. The GitHub App (GitHub repositories only)

Ask this first, because the final plan (`fugaro update --repo --plan-only --github-app-id <id>`) needs the App's ID, and it must not surface only at the end. Ask: "What is the GitHub App ID (a number on the App's settings page, not a secret)?" Take it from the user; don't look for it in files. If `fugaro doctor --json` or an earlier plan already shows an App ID for this installation, say so and ask only for a confirmation. If there is no App yet, tell the user how to create one and wait:
- **Name:** `<yourname>-fugaro`, for example `acme-fugaro`. App names are unique across all of GitHub and the bare `Fugaro` is taken. The name is shown as the author of every pull request and can't be changed, so use one App for all of the team's repositories.
- **Repository permissions, four:** Contents Read & write, Pull requests Read & write, Issues Read, Metadata Read. **Never Workflows**: a run able to edit `.github/workflows/*` could weaken the merge gates or reach the repository's secrets.
- **Install it on this repository.** When the permissions of an installed App change, accept the change on the installation (GitHub requires it; until then the old permissions apply).
- A client secret is not needed. The private key (PEM) goes in the `github-app-key` secret (step 8), never into this conversation.

Full text: [docs/git-providers.md](https://github.com/dimipaun/fugaro/blob/main/docs/git-providers.md).

## 2. `agent.auth`

What credential the remote agent uses to call a model.

| Value | Secret | Recommend when |
|---|---|---|
| `oauth` | `claude-oauth-token` (the user makes it with `claude setup-token` and stores it) | the user says they have a Claude subscription and want no per-token bill. There is no gateway: model pins, prices and dollar caps don't apply. The only token cap is `agent.max_run_tokens` (below). Say so |
| `api-key` | `anthropic-api-key` | the team pays per token and wants budget caps to apply |
| `vertex` | none (the job's own account) | Claude on Vertex AI is verified usable in the installation's cloud project (below) |
| `cascade` | none: the installation's credentials service attaches its own | the project's published policy turns it on (`routing.claude: {via: cascade}`), publishes `budget.allowed_models` (required: without it the service refuses every call and the launch refuses the run) and the budget mode is `observe` or `enforce`: the gateway carries the calls and the caps apply. Never with `followup.allow_public` (topic 6) |

With `api-key` the Anthropic key is needed whenever a call goes direct to Anthropic, which depends on the budget mode: under an enforcing budget, a pin no provider allowed to see the repository serves (a Claude model above all), and a run whose pins are all served holds no key at all; with the budget off or observing nothing routes a call to a provider (observing only accounts for the spend), so every call goes to Anthropic and the key is needed whatever the pins are — the mode to expect, since a budget is usually adopted after setup. The setup prompts for one either way. A call that needs one without it is refused at run time, by name, with the one-line command that stores it, never silently sent elsewhere.

**Verify before you recommend.** No command you may run shows whether Claude on Vertex AI is enabled and has quota in the installation's project (`fugaro doctor --json`'s `project` names it). So never mark `vertex` recommended on a guess: say you could not verify it, and offer it only as an option the user may confirm in their cloud console. Recommend the credential the evidence supports: `oauth` when the user says they have a subscription (the evidence is their statement, so ask), `api-key` when the team wants pay-per-token dollar caps, and say which evidence led there.

If `fugaro.yaml` exists, keep its value. If the project's other repositories already chose one, recommend the same.

With `oauth`, if the operator has configured more than one named Claude account (`fugaro doctor --json`'s `secrets` field lists more than one `claude-oauth-token-*` name), ask which one this repository should use by default and set `agent.oauth_token` to the chosen name (the part after `claude-oauth-token-`), or confirm the existing default account is fine and leave the key out.

## 3. `agent.models`

`coder` implements and fixes, `reviewer` reviews, `background` is Claude Code's small background requests. A role left out uses `agent.model`, else Claude Code's default. Read the current model IDs and prices from `fugaro budget prices` (offline); never write an ID from memory. With a budget on and `api-key`, `vertex` or `cascade`, every model must be an explicit ID with a price (no aliases) and `background` is required. With `oauth` the pins and prices don't apply, but explicit IDs are still the clearer choice. Recommend, and give the reason for each role: a strong, capable model for `coder` because it writes the change the review has to catch mistakes in; at least as strong for `reviewer`, because a weaker reviewer misses what the coder got wrong; the small, cheap one for `background`, because those requests are minor and frequent. Ask first, open-ended, which models the user wants for `coder` and `reviewer` (explain the three roles in a sentence each); recommend only when they ask or have no preference, and never from the repository's domain. Quote the prices you read so the user sees the cost, never recommend a model only because it is the biggest or the first listed, and let the user choose.

## 4. `budget` (from the user)

Optional. `mode` is `off`, `observe` (record, don't stop) or `enforce`; `per_run_usd` and `per_day_usd` are dollar caps; `allowed_models` is a list of explicit IDs. The block can only tighten the project's ceiling (set by the owner): a value above it is clamped with a warning, and the file is read from the default branch, so it takes effect once merged. Don't invent numbers: ask what the team will spend, and propose `observe` first when there is none. Model pins, prices and dollar caps apply only to `api-key`, `vertex` and `cascade`, which go through the gateway. With `oauth` the only token cap is `agent.max_run_tokens` (a run's total tokens, 0 is none; it can only tighten the project's ceiling): recommend asking the user for a number and setting it. `observe` records usage for the shared budget only. `vertex` supports `observe` only: `enforce` is refused until the Vertex facts are verified; there is no per-token price to cap. Also explain `agent.max_budget_usd` (default 25 per stage, Claude Code's own limit): keep it unless the user wants otherwise. Project-wide caps and kill switches belong to the owner (the budget commands); you never run them. In a project that has published a policy, the project's ceiling is that node: `mode`, `per_run_usd`, `allowed_models` and `max_run_tokens` there govern every run of every enrolled repository, a change to them is the owner's, in their own terminal, never by you (the budget rule), not an `update --repo` per repository. `fugaro doctor --all` reports whether a policy is published, and `fugaro project policy show` prints it.

## 5. `git.pr.reviewers` and `labels` (from the user)

Who is requested on the pull request and which labels it gets. Only the people the user names. GitHub takes logins. Bitbucket needs account UUIDs (`{...}`), not usernames. Looking one up needs the repository's access token, which you never hold: the user runs the lookup in their own terminal, from [Finding a Bitbucket reviewer's UUID](https://github.com/dimipaun/fugaro/blob/main/docs/git-providers.md#finding-a-bitbucket-reviewers-uuid), and tells you only the UUIDs (not the token or the command's output). The same goes for a Bitbucket `account_id` for `followup.trusted` ([Finding an account ID](https://github.com/dimipaun/fugaro/blob/main/docs/git-providers.md#finding-an-account-id-for-followuptrusted)). Labels default to `fugaro`.

## 6. `followup.trusted` and `followup.allow_public` (security)

A follow-up run (`fugaro run --pr N`) continues a Fugaro pull request and acts on the PR comments of **trusted** accounts. It holds the workflow's secrets and the model credential, so whoever is trusted steers an agent that holds them.

- `followup.trusted`: account IDs, not names. The people come only from the user, never from CODEOWNERS, `git log` or a README. For a numeric GitHub user ID run `gh api users/<login> --jq .id` (read-only) with a login the user gave, and show the user the result, or a Bitbucket `account_id`. Empty by default, so a follow-up acts only on the launcher's instructions. Recommend leaving it empty unless the team wants reviewers to steer follow-ups, then list only the people the user names. It is read from the base branch, so a PR can't widen its own list.
- `followup.allow_public`: on a **public** repository anyone can comment, and a follow-up run would act on comments from trusted accounts with the secrets in hand while untrusted comments are dropped; `allow_public: true` lets follow-ups run on such a repository at all. Without it they are refused, which is the safe default. **Explain this risk to the user and never set `allow_public` without their explicit decision** (a clear yes to the question, not silence and not a guess from the repository). Ask the user whether the repository is public; don't infer it from anything. If it is private, don't raise `allow_public`.

## 7. `resources` (machine size)

Its own topic, never combined with the review rounds. Evidence: the CI configuration's runner or `size:` and any memory flags (`machine size` in `discovery.md`), the test footprint (the parallel workers, a heap setting, services started in the same container, a browser), and the language's defaults. State the evidence with its file and line, the recommended CPUs and memory and why, and what you could not tell. Ask only this.

## 8. `agent.review_rounds` (and `timeouts`)

Its own topic. `agent.review_rounds` (1 to 10, or left out): rounds before the PR. **Recommend leaving it out**: unwritten (or 0) it follows the rigor mode (poc 1, startup 2, pro 3, critical 5, hotfix 1), so a mode set later moves the loop with it, while a written number pins it. If the user wants one anyway, evidence is how risky the repository is (money, authentication, data migrations, production data) and what the code and its tests guard. Each extra round costs time and tokens. Ask only this. `timeouts`: the defaults (`total` 90m, `stage` 40m, `verify` 30m); the verify command should finish well inside `verify`.

## 9. `agent.recipe`

Its own topic, after 3 and 8. Say first, before suggesting anything: setting `agent.recipe` writes a key that fugaro older than 0.5.0 refuses, in every teammate's CLI, every CI pin and every workflow's job image, so the user must hear this before it goes into the file and decide whether everything is on 0.5.0 or later (`fugaro validate` warns about it). `standard` and `solo` need 0.7.0 or later, not just 0.5.0: both use `use_when`, a 0.7.0 recipe-format key.

Then recommend `default`: leave `agent.recipe` out and say so. Never write `agent.recipe` without the user's explicit decision, and never guess a recipe from the repository's domain or language. Offer the others only if the user asks for them or says what they want. The recipe is the loop after implement: `default` is today's (a first-line review when `agent.first_line_review` turns it on, where `auto` turns it on for a provider coder with a non-provider reviewer, then `agent.review_rounds` senior rounds); `standard` is a first-line loop by the coder's model, then one senior round that can bounce back to the first-line loop on rejection; `solo` makes the coder's model also review, in a fresh session. A repository or project can define its own (`fugaro recipes ls` lists what exists).

## 10. `rebuild`

Almost always the defaults: leave it out and say so. Propose `rebuild.paths` only with evidence (`services-and-images.md`); `rebuild.check: off` only when the user wants a hand-rebuilt image.

## 11. Workflow names and anything to keep off Fugaro

With several workflows, confirm the names (`fugaro run --workflow` selects one). Ask whether any task type must stay off Fugaro (money, security, production data): if so, write it in the file `agent.instructions` points to (a repository-relative path to a text file that must exist; it is appended to the agent's prompt, so it is shown to the user like any executed text and goes in the PR) or in the team's own routing notes, never in a secret.

## 12. `checkout` (the workflow's job image)

Its own topic, only for a workflow that needs nothing a build gives it. `checkout: baked` builds a per-repository image with the repository baked in, rebuilt by the daily image check; `checkout: clone` runs the installation's own base image instead, so there is no image build and no daily check, and the run pays a blobless clone plus `mise install` at start-up (bounded at ten minutes). Leave the key out: the default is `baked`. Offer `checkout: clone` only when the workflow needs no system package and no Dockerfile and no service, so none of `image.apt`, `image.tools`, `image.setup`, `image.skip_build_scripts`, `image.key_files` and `dockerfile:`, the exact keys `fugaro validate` refuses under clone (a service is one of those in practice: it arrives through `image.apt` or `image.setup`; `docs/checkout.md`, "What `clone` refuses") — a plain Node, Go or Python workflow whose only requirement is what `mise.toml` declares. Say what clone trades away (the warm caches a build leaves behind: a private repository pays the clone and the tool install at every start-up), say that **it is the user's decision**, and let the user choose. **`checkout: clone` is shipped** (0.9.0): the `cloneShipped` gate (`internal/cli/recipes_skew.go`) is open, so deploying or moving its job goes through. A launch still checks the job image's release: fugaro 0.7.5 or later (`cloneSince`, the runner that makes the blobless clone) — older is refused, a dev build only warns. [docs/checkout.md](https://github.com/dimipaun/fugaro/blob/main/docs/checkout.md) is the full text.

## What scope a secret's value goes to

Init's own prompts (skill step 9) have no `--repo` to pass: a name this repository may mount project-wide goes to the project's Secret Manager; a per-repository name does not (`bitbucket-token` reaches project scope only through an explicit `project_secrets` entry; one workspace or project token may serve many repositories). A project-scope name's reach is its entry's `allow_data_to` — which may use `*` inside a segment (`myworkspace/*`, never across `/`), reaching every repository it matches, now and later — or the provider's for a provider key: say which repositories it reaches. A covered name is not asked for; a prompt that skips one works as intended.

For this repository's own copy instead, the user runs it in their own terminal window, not through the agent, and starts setup again:

```bash user-runs
fugaro secrets set <name> --repo <owner/name>
```

A repository copy with an enabled version wins over the project's, so this is how a covered name gets its own value; disabling it falls back to the project's at the next setup.

## Minimal file or full file?

With a project layer and a fitting profile, the minimal file keeps the repository on the project's settings: a profile change reaches it without a pull request. A full file is for a repository whose build or image is its own. Never copy a profile's values into `fugaro.yaml`; that would stop it from following the profile.
