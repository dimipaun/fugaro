# Validation loop and failures

## Validate

`fugaro validate --json` prints `{"valid": ..., "problems": [{"path": ..., "message": ...}]}`. It may also print `"warnings"` in the same shape (a value the project's ceiling would clamp): warnings don't make the file invalid, but tell the user. A third array, `"notes"` (also the same shape, omitted when empty), is neither: something the run will need that only the cloud can settle — today, a stored Anthropic API key when a call will go to Anthropic, and, for a file that writes `governance:`, the edition of the job images. `--offline` leaves the edition unresolved, and so does a reason the records could not be read at all — no project config selected for the file's project, a directory that is no checkout of the repository, or a runs bucket this machine cannot open — so whether their runners read the block is not known here. Each such note names the fix that would let the read happen (drop `--offline`, set `$FUGARO_PROJECT` or `$FUGARO_CONFIG` or run `fugaro setup`, run from the checkout, or check the bucket's credentials), the same way the other notes say what to do. Pass a note on to the user as information (its message says the fix), never as a problem, and never change the file to silence it: `valid` stays true with notes. Fix each problem at its `path` and run it again until `valid` is true. Don't silence a problem by deleting something the build needs.

## Check the image

A repository whose project gives its jobs a catalog image has nothing of its own to build: the check is `fugaro image ls --json` — the entry listed, its tags covering the workflow's `needs:` (step 7 of the skill). Where the project gives the workflow no catalog image, the repository's own image is what its job runs, and it is built by Cloud Build, never on anyone's machine. That build is the one setup submits from the merged checkout (steps 9 and 10 of the skill), because it reads the repository's base branch and pushes to a registry `fugaro update --repo` creates. It is billable, and it asks nothing in any session (its estimated cost is reserved against the project's budget caps before it is submitted, and a build no cap has room for is refused by name, with the cap and the command that raises it). Its log goes to stderr as text, one line per step, and a failed smoke names each check. You read the record back with `fugaro image status --json`: per workflow, the image's build time and age, its source commit and base digest, and the last daily check's time, decision and reasons. The user runs the next build in their own terminal window, not through the agent, with `fugaro image build --workflow <name>`. Before reading failures:
- **This build runs the repository's code** (install scripts, `image.setup`, the build command) in Cloud Build, as the repository's build account and with the workflow's `secrets:` mounted as file secrets, which is why the lines are shown and approved first (step 6 of the skill). A registry token arrives that way and never as a build argument or a copied file.
- `--base <image>` overrides the image the build starts from: a development build of `fugaro` has no published base image, so name one the build can pull.
- It builds the repository's **base branch** as it stands on the provider, not your working tree: an uncommitted `fugaro.yaml`, `.fugaro/<workflow>.Dockerfile` or lockfile is not in the image, which is why the file is merged first.
- `Dockerfile`, `package.json` and `.yarnrc.yml` must be regular files, not symlinks, of at most 1 MiB: a symlinked one fails `validate` and the image render.

When it fails, read the build log's failing step and the smoke's named check, then fix `fugaro.yaml` or the Dockerfile:

| Failure | Likely fix |
|---|---|
| apt: "Unable to locate package" | Fix the name in `image.apt`. The base is Debian 13 (trixie). |
| The dependency install fails with 401 or 403 | A registry token is missing. Declare it in the workflow's `secrets` and have the user store it (step 8 of the skill). The build mounts the workflow's `secrets:` as file secrets, so the Dockerfile reads the value from the mount and no layer keeps it: an `ARG`, an `ENV` or a `COPY` of a registry dotfile would put it in the image. Don't have the token put into your own environment: the value is then visible to the repository's code in the build and to every command your agent runs, and the mount is what the build reads. |
| The install hangs, runs out of memory or ends in an internal error while many packages build at once | Set `image.skip_build_scripts: true` and have `commands.build` build the packages. |
| `--immutable` or `--frozen-lockfile` refuses a lockfile change | The lockfile is out of date in the repository. Tell the user. |
| A `setup` step fails | Fix the step. Its own output is in the build's log, one line per step. |
| The origin is missing or not https | The clone needs an `origin` remote on the provider host. Tell the user. |
| Smoke `mise-tools` fails | A declared tool did not install: check its name and version in `mise.toml` (`mise ls-remote <tool>` lists versions), and that nothing removed the `mise install` step. |
| Smoke `tool:<name>` fails | The image lost a base tool or harness: restore the Dockerfile's contract. |
| Smoke `verify-build` fails | `commands.build` is wrong for the image, or needs a tool, variable or secret. |
| Smoke `origin`, `git-credentials` or `home-credentials` fails | Something wrote credentials into the image or changed the origin. Remove that step. |
| Smoke `user`, `init` or `no-sudo` fails | The Dockerfile changed `USER`, `ENTRYPOINT` or the sudo rules. Restore the contract. |
| Smoke `checkout` fails | `/work/repo` is not at the built commit. Remove the setup step or Dockerfile line that checks out, resets or pulls. |
| Smoke `claude`, `no-setuid`, `no-setgid`, `no-file-caps` or `sudoers` fails | The Dockerfile or a setup step removed Claude Code, added setuid or setgid binaries or file capabilities, or left sudo rules. Restore the contract. |
| Smoke `root-scan` fails | The filesystem scans must run as root (uid 0). Something changed the image's user or the scan's access. Restore the contract. |
| Smoke `managed-settings-dir` fails | Something baked files into the directory the runner writes Claude Code's managed settings to at run time. Remove that step. |
| Smoke `mise-cache-dir` fails | Something removed, replaced or changed the owner of `~/.cache/mise`, the mise download cache the base image creates for the run. Remove that step. |

If the same failure survives three different fixes, stop and ask the user. Then the loop is over only when both checks pass for every workflow.
