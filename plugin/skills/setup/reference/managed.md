# Managed projects: what makes one, the flag for an existing one, and creation

**Open as of 0.10.0, with the fence not yet measured live.** The `managedDeployerShipped` gate (`internal/cli/recipes_skew.go`) is true as of 0.10.0 (the owner's ruling of 2026-10-22), so the entry points below are available: creating one (`--create-project`), flagging an existing one, `fugaro managed apply` and `fugaro restore` — a creating run writes the label too. Before that release, 0.8.6 through 0.9.5 refused every one of them with `managed projects are disabled in this release` before any cloud call, so a user on one of those releases reads that refusal and stops. The deployer's scoped roles are created for an installation that uses managed projects — the creating run writes the installation module's `managed_deployer_scoped` from the project's own creation fact — and **the fence they are has not been measured live**: the redesign the 0.8.6 note asked for is in the tree (seven roles, one per service, each bound exactly once under its own `fmgd-` prefix condition), and what is unproven is whether GCP honours the `resource.name` reading it rests on. Check 68 in `docs/gcp-live-checklist.md` measures that; it is written, owner-run **after** the release, and **NOT RUN**. So a refusal the fence produces, and an apply that fails at a binding, are read to the user as what they are — never as a fence known to hold.

**What makes a project managed.** Two marks, and both are required: its runs bucket holds Fugaro's marker (`fugaro/managed.json`) — the creation fact of a project Fugaro created, or the flag its owner put on one that already existed — **and the GCP project carries the label `fugaro_managed=true`**. Both marks are the user's, written in their own terminal, not through the agent, and by nothing else: **never write that label yourself**, with `gcloud` or any other tool, and never remove it — it is a write on the project, and putting a project into managed mode or taking it out is the user's decision, not yours. The label can only narrow: a project missing it, carrying another value, or that cannot be read at all is not managed whatever its marker says — and a label alone never makes a project managed either. **Fugaro deals only with managed projects.** Every command that writes into a project reads both marks first, whatever the terminal and whoever reads the output, and on a project that is not one it refuses before it writes and names the single command that flags a project — the flagging command below, which only the owner runs at their own terminal. If a command refuses a project that way, read the refusal to the user and stop; `docs/managed-projects/spec.md` has the one line that writes the label, for the user to run.

**What your session may run in a managed project.** A managed project's plan-changing commands are judged by a deterministic gate over the plan they have already produced, and no model is asked whether the change is acceptable; `fugaro accounts add` is the one whose two halves have two doors (the owner's ruling of 2026-11-09). The declaration it writes — the account's name, the repositories the token may be sent to (`allow_data_to`) and the profile that serves it — is a document the gate reads, so **a session may add a bounded account and write that document**. The token that follows is not: a secret is the one class no plan gate admits, so on a managed project the command writes it for the person at their own terminal and for nobody else — a real terminal on both streams, no marker — and before the prompt it prints those repositories and says a job on them can read this token, asking nothing. **Only a person at a real terminal gets that token**: a pipe and a run with no terminal are refused in two lines before a byte is written, and an agent's session is refused the token in two lines after it has written the declaration: read the refusal to the user, verbatim, and stop — no flag, variable or marker reaches past it. On a project that is not managed the whole command is refused before it writes, and its owner flags the project managed first. **The typed entry and the pools are the operator's own writes, refused to an agent's session**: `--type claude-oauth|anthropic|openrouter` is what makes a name one a pool may list, and `fugaro accounts pool add|rm` declares or removes a pool, whose members decide where a project's calls may be spent. A session never writes either, and neither is a step of this skill: `fugaro craft ls` is the read that says what the credentials and pools resolve to.

**The deletes the owner approves.** A managed project records, in one object at its runs bucket's root, the addresses whose deletes and replacements its owner approves. Its writer is the owner's command, run in their own terminal, not through the agent; it refuses an agent's session. That is a speed bump, not a boundary: your session holds the owner's credentials, so never write that object yourself:

```bash user-runs
# one address, copied whole
fugaro allow-delete '<address>=type=<type> project=<project> name=<name> id=<id>'
# add instance=<value> if the type has one
```

**Applying one (0.10.0 and later — see the note at the top).** A managed project's agent-authored root is applied by `fugaro managed apply <root>` — a directory of this checkout, applied as the project's deployer account — and **it is refused when the project's recorded budget cannot be read**, which no flag reaches past: read that refusal to the user, then stop. A refused delete in a managed project names no flag: say which address is refused to the owner, and stop; a managed apply's refusal prints the identity the owner's list records: every part the plan's `before` view carries, in the order the list holds them — `type`, `project`, `name`, `id`, and the per-instance value where that type has one (a bucket's `time_created`, a Cloud Run job's `uid`, a secret's `create_time`) — and the owner's command compares it byte for byte with what the plan shows, so copy the identity out of the refusal whole, and never retype it from the address: a part left out, added or reordered matches no removal and the delete stays refused. The address beside it is printed as the plan carries it only up to 512 characters: an address shown with a `…` at the end was cut for the refusal, no entry written from that text matches the plan, and the same delete is refused again — tell the user the address is longer than the refusal prints and that the exact address comes from the plan, not from the refusal.

**Flagging a project that already exists.** A project Fugaro did not create, or one it created before every creation carried the marks, becomes managed by the same marker, and for such a project the writer of it is the owner's own command, run in their own terminal window, not through the agent: the flagging command below. It refuses an agent's session and a Fugaro run's own process, and it is the one way an existing project becomes managed — an update never flags one: on an installation that is not managed it stops, at the head of its engine, and names this command. The project it flags is the selected installation's own GCP project: the optional argument, when given, must be that project's exact ID, and omitted, the project is the installation's own; the statement it prints before either mark is written names the project either way, so the invocation is always about a project the owner can see it is about, and nothing is typed at a prompt. It records the monthly budget alert amount and currency the owner means: `--budget` and `--budget-currency` default to 100 USD, so the command with no flags records a figure rather than asking for one. An amount the project already records is its owner's own figure, and a default never replaces it: run with no `--budget` over such a marker it is left alone, and an explicit `--budget` replaces it — keeping the recorded currency unless `--budget-currency` is given too — printing the old figure and the new. It writes the label `fugaro_managed=true` on the project as well, in the same command and the same moment, so a flagged project is managed at once. Never run it yourself, and never write that marker any other way:

```bash user-runs
# flag the selected installation's own project as managed
fugaro managed flag
# or name that project's exact GCP project ID; --budget and --budget-currency default to 100 USD
fugaro managed flag <gcp-project-id> --budget <amount> --budget-currency <code>
```

**Creating a managed project (0.10.0 and later — see the note at the top).** A creating run (`--create-project`) is the one writer of a project the fence exempts, because it is what creates a managed project: it records the monthly budget amount in the project's creation fact — `--budget` and `--budget-currency` where the user states them, 100 USD where nobody chose — and writes the label too. Never state an amount for the user. `--billing-account` is the account charged, and it defaults to the one the run links; alerts fire at 50%, 90%, 100%. On a project that already exists, flag it instead, above, and a run that converges an installation that is already there is refused on one that is not managed. `fugaro restore` refuses an agent session: say so, stop, never rebuild it by hand ([docs/gcp-setup.md](https://github.com/dimipaun/fugaro/blob/main/docs/gcp-setup.md)).
