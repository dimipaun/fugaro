# Managed projects: what makes one, the flag for an existing one, and creation

**Open as of 0.10.0, with the fence not yet measured live.** The `managedDeployerShipped` gate (`internal/cli/recipes_skew.go`) is true as of 0.10.0 (the owner's ruling of 2026-10-22), so the entry points below are available: creating one (`--create-project --managed`), flagging an existing one, `fugaro managed apply` and `fugaro restore`; a plain `--create-project` writes the label too. Before that release, 0.8.6 through 0.9.5 refused every one of them with `managed projects are disabled in this release` before any cloud call, so a user on one of those releases reads that refusal and stops. The deployer's scoped roles are created for an installation that uses managed projects — the creating run writes the installation module's `managed_deployer_scoped` from the project's own creation fact — and **the fence they are has not been measured live**: the redesign the 0.8.6 note asked for is in the tree (seven roles, one per service, each bound exactly once under its own `fmgd-` prefix condition), and what is unproven is whether GCP honours the `resource.name` reading it rests on. Check 68 in `docs/gcp-live-checklist.md` measures that; it is written, owner-run **after** the release, and **NOT RUN**. So a refusal the fence produces, and an apply that fails at a binding, are read to the user as what they are — never as a fence known to hold.

**What makes a project managed.** Two marks, and both are required: its runs bucket holds Fugaro's marker (`fugaro/managed.json`) — the creation fact of a project Fugaro created, or the flag its owner put on one that already existed — **and the GCP project carries the label `fugaro_managed=true`**. Both marks are the user's, written in their own terminal, not through the agent, and by nothing else: **never write that label yourself**, with `gcloud` or any other tool, and never remove it — it is a write on the project, and putting a project into managed mode or taking it out is the user's decision, not yours. The label can only narrow: a project missing it, carrying another value, or that cannot be read at all is not managed whatever its marker says, so its runs keep the ordinary typed confirmations — and a label alone never makes a project managed either. If a command refuses a project that way, read the refusal to the user and stop; `docs/design/managed-projects.md` has the one line that writes the label, for the user to run.

**Applying one (0.10.0 and later — see the note at the top).** A managed project's agent-authored root is applied by `fugaro managed apply <root>` — a directory of this checkout, applied as the project's deployer account — and **it is refused when the project's recorded budget cannot be read**, which no flag reaches past: read that refusal to the user, then stop. A refused delete in a managed project names no flag: say which address is refused to the owner, and stop; a managed apply's refusal prints the identity the owner's list records: every part the plan's `before` view carries, in the order the list holds them — `type`, `project`, `name`, `id`, and the per-instance value where that type has one (a bucket's `time_created`, a Cloud Run job's `uid`, a secret's `create_time`) — and the owner's command compares it byte for byte with what the plan shows, so copy the identity out of the refusal whole, and never retype it from the address: a part left out, added or reordered matches no removal and the delete stays refused. The address beside it is printed as the plan carries it only up to 512 characters: an address shown with a `…` at the end was cut for the refusal, no entry written from that text matches the plan, and the same delete is refused again — tell the user the address is longer than the refusal prints and that the exact address comes from the plan, not from the refusal.

**Flagging a project that already exists.** A project Fugaro did not create, or one it created without `--managed`, becomes managed by the same marker, and for such a project the only writer of it is the owner's flagging command, run in their own terminal window, not through the agent; it refuses an agent's session, and its confirmation is that project's exact GCP project ID typed by hand, which no flag stands in for. It records the monthly budget alert amount the owner states, and the amount and the currency are the user's decision: ask, never pick. It writes the label `fugaro_managed=true` on the project as well, in the same command and the same moment, so a flagged project is managed at once. Never run it yourself, and never write that marker any other way:

```bash user-runs
# flag an existing project as managed, recording its monthly budget alert amount
fugaro managed flag <gcp-project-id> --budget <amount> --budget-currency <code>
```

**Creating a managed project (0.10.0 and later — see the note at the top).** With setup's `--create-project --managed`, the monthly budget amount is required: no default; without one nothing is created. Amount and currency are the user's decision, in their own terminal window, not through the agent: ask, never pick. `--billing-account` is the account charged; alerts fire at 50%, 90%, 100%. Both are recorded in its creation fact, and the creating run writes the label too. On an existing project setup will warn `--managed` was not applied: flag that project instead, above. Without `--managed` the budget is optional and nothing is recorded. `fugaro restore` refuses an agent session: say so, stop, never rebuild it by hand ([docs/gcp-setup.md](https://github.com/dimipaun/fugaro/blob/main/docs/gcp-setup.md)).
