# Parallel runs

Each Fugaro run has its own worker and its own branch and pull request, so independent work can run side by side. The cost is the same per run; the saving is time. The cap on spend and on simultaneous runs still applies.

## Go wide for independent work

Split when the pieces touch different files, need no result from each other, and can each be reviewed and merged alone: the same change in several services, a test file per module, unrelated bugs. One run per piece, each with a self-contained task (see `working`).

Give the runs a shared name so they can be followed together, and a run ID of their own each (see `working`'s launch reference), so a repeated launch cannot start a piece twice:

```bash
fugaro run --batch <name> --run-id <id> --task-file - <<'TASK'
<one piece of the work>
TASK
```

`fugaro runs ls --batch <name>` lists the batch, and `fugaro runs ls --watch --batch <name>` follows it. Tell the user each run by its short ID (`working`'s ground rules), and a batch's pull requests by the four words that skill's own paragraph defines: **live** while a run is going on one, **ready** when the last run that opened or followed it ended with the outcome `ready` (a review job's own outcome `reviewed` changes nothing), **stalled** when a run has been on it and it is not ready (`[DRAFT]`-titled ordinary pull requests on a host with no drafts included), **orphan** when no run produced or follows it.

## Stay narrow for coupled work

Keep it in one run when pieces edit the same files, share a new interface, or the second needs the first's result. Parallel runs on coupled work produce pull requests that conflict. When there is an order, launch the first, have the user merge it, and launch the next from the updated base branch.

## Job max

Job max is the aim: **the most completed, reviewed runs in parallel, not tokens spent; only real dependencies order runs**. What counts is runs that reach a reviewed pull request, so a graph that launches many and leaves them waiting or conflicting is slower than a smaller one that finishes; the caps bound the spend, not the ambition.

Three planning techniques get a graph there: **contracts first** (the bullet below says what to settle before a task is written); **stubs and fakes** so neither side waits — a task that consumes another's work is written against a stub and lands without the edge; and a graph **kept wide and shallow** — many independent tasks and few edges, because a chain finishes no sooner than its length however many runs it holds.

## How to split so pull requests do not conflict

- One owner for each file: no two tasks edit the same file.
- **Contracts first**: settle shared decisions (names, an interface, a schema) before writing a task, and put them in every task's text.
- Prefer slices that merge in any order. If one must come first, say so and launch it first.
- Keep each task small enough to review in one sitting.

## Write the plan's graph beside it

A plan you write as a file can carry its tasks as a graph the CLI reads. Write it beside the plan: `docs/plans/foo.md` is described by `docs/plans/foo.graph.json`, and `fugaro plan graph --plan docs/plans/foo.md --json` prints that document — a person can read the same file.

The example below is a plan that broke one edge with a contract: T1 to T2, with C1 the contract that settled the shape, I1 the task that re-joins them, and R1 a change request later raised against C1. C1 waits for nothing, which is what makes the break real: a contract written from T1's own types would leave T2 waiting on T1 through it, and `fugaro plan graph` would report that break as no gain — a break to undo rather than to write down.

```json
{
  "schema_version": 3,
  "plan": "docs/plans/foo.md",
  "stream": "cli",
  "nodes": [
    {"id": "T1", "title": "the parser", "run": null, "version": null, "size": 3,
     "footprint": {"prediction": true, "paths": ["internal/parse/**"]}
    },
    {"id": "T2", "title": "the read", "run": null, "version": null, "size": 2,
     "footprint": {"prediction": true, "paths": ["internal/cli/read.go"]}
    },
    {"id": "C1", "title": "the record's shape", "kind": "contract", "run": null, "version": null, "size": 0.5,
     "stubs": ["internal/record/record_stub.go"],
     "footprint": {"prediction": true, "paths": ["internal/record/record.go", "internal/record/record_stub.go"]}
    },
    {"id": "I1", "title": "wire the record in", "kind": "integration", "run": null, "version": null, "size": 0.5,
     "footprint": {"prediction": true, "paths": ["internal/record/record_stub.go"]}
    },
    {"id": "R1", "title": "the record's shape, amended", "kind": "contract_change", "run": null, "version": null,
     "footprint": {"prediction": true, "paths": ["internal/record/record.go"]}
    }
  ],
  "edges": [
    {"task": "T2", "needs": "C1", "reason": "the read is built against the record's shape"},
    {"task": "I1", "needs": "T1", "reason": "the integration runs both sides"},
    {"task": "I1", "needs": "T2", "reason": "the integration runs both sides"}
  ],
  "decoupling": [
    {"contract": "C1", "was": {"task": "T2", "needs": "T1"}, "integration": "I1",
     "reason": "T2 needed the parser's interface only, and not its behaviour"}
  ],
  "contract_changes": [
    {"change": "R1", "contract": "C1", "raised_by": "T2", "reason": "the read needs one more field in the record",
     "affects": ["T2"]}
  ]
}
```

- **Depends-on** is an edge: `task` waits for `needs`, and `reason` says why. Both must name a node in the document, and a cycle is refused rather than drawn.
- **Files footprint** is the node's `footprint.paths`: the paths you expect the task to touch, as doublestar globs (`internal/**`, `docs/*.md`), the same semantics this repository's own checks use. `[]` means the task predicts it touches nothing — not the same as not saying.
- The footprint is a **prediction** and `prediction` is always `true`: what a run really changed is the run's own record, never this. Two tasks whose paths can match the same file are the conflict to split apart before launching.
- **`kind`** is what the node is, and a node carrying none is an ordinary task. The decoupling pass adds the other three: `contract`, `integration` and `contract_change` — the nodes the section below and `reference/decoupling.md` are about.
- **`size`** is the node's weight against the others, absent meaning 1. It is what the gain is weighed in: a stub-only contract task is small against the pair it separates, and a task that reworks a service is large. Zero or less is refused rather than read as free work.
- **`stubs`** is a contract node's own list: the whole files it leaves for its dependents to compile against, each one named literally in that node's `footprint.paths` too, because the integration task deletes exactly the files this list names. A contract's footprint names its files one by one and never a pattern, and a contract whose footprint names no file at all is refused.
- **`decoupling`** is the pass's record, one entry per edge it broke: the `contract`, the `was` edge as it stood (`task` and `needs`), the `integration` node covering it, and the `reason` the break was right. That edge is gone from `edges` — an edge is broken or it is there, never both — and the `integration` node depends on both of its endpoints.
- **`contract_changes`** records a change request against a contract that has already merged: the `change` node, the `contract`, the `raised_by` task that found it, the `reason`, and the tasks the change `affects`.
- `run` is the run the task belongs to once one is launched, `null` before that; `version` is the release it ships in as `MAJOR.MINOR` or `MAJOR.MINOR.PATCH` (`0.10`, or the patch box `0.10.1`), and `null` when the plan does not say — anything else, `v0.10` or a fourth number, is refused.
- **The stream** is the release stream the plan ships in — `cli`, `console` or `mobile` — written as the document's own `stream`. `null`, or the key left out, is a plan that does not say, which is not the same as naming a stream nothing knows: that one is refused. It is what puts the plan in the right column of a graph drawn per stream, and it is a display input, so which release a task actually ships in comes from the project record rather than from this file.

`fugaro plan graph --json` prints the document back, validated; without `--json` it prints a table of ID, TITLE, LEVEL, STATE, VERSION, RUN, NEEDS and FOOTPRINT, every footprint labelled `predicted:`, and, when the plan broke an edge, a `DECOUPLING` block under it: the edge with its contract and integration node, the gain measured in tasks and weight before and after, and the contract stubs still in the checkout. Name the plan with `--plan` wherever `docs/plans/` holds more than one graph: with none the read takes the one artifact it finds there, and several are a refusal rather than a pick. A refused graph — another schema version, an unknown field, an unknown stream, a missing reason, a malformed glob, a cycle, a contract with no file of its own, a stub its own footprint does not name — exits non-zero and prints nothing.

## Break dependencies with a contract first

An edge that carries nothing but an order is one the plan did not have to accept. Read the pass's switch before you run it: `fugaro settings planning.decoupling --json`, with `--repo <owner/name>` naming the repository whose plan you are planning, because the value a repository's own `fugaro.yaml` sets is the one its runs resolve. When the pass is off, skip it and say so in the plan: a pass switched off and a plan in which no edge could be broken are different facts, and only the text tells a reader which one it is.

For each edge A to B, ask **does B need A's interface or A's behaviour?** Where it is the interface, write a small contract task that settles it and let both sides run at once; keep the edge where B needs A's real behaviour or data. The contract and the integration task that removes the stubs are nodes of the graph, named `C-...` and `I-...`, each edge carrying its reason — the "contracts first" and "stubs and fakes" techniques of job max, applied edge by edge.

Give the nodes the pass adds their relative `size`, record the break in the graph's `decoupling` block, and break an edge only when the weighted path shrinks. Do not work that out yourself: `fugaro plan graph` reports the edges broken and the edges kept and the gain — the tasks and the weighted path before and after, and whether the break improves the plan — and a break it reports as no gain is one to undo. The pass proposes and never launches: every contract task, integration task, independent review and follow-up it calls for goes to the user with the run count and the worst case, and none of them starts until the user says yes. `reference/decoupling.md` has the per-edge test, the contract task's contents, the integration task, what to do when a contract turns out wrong, the rigor table and what the plan says afterwards. Read the graph with `fugaro plan graph` — the CLI validates it, and never parse the graph yourself.

## A batch onto one long-lived branch

When the pieces all land on one integration branch whose own `fugaro.yaml` still names main, every run's review pays for that branch's divergence from main, so a batch of fifteen onto a branch far ahead of main reads that distance fifteen times. Merge main into the branch before the batch so it starts from as little divergence as possible, and launch each run with `--ref BRANCH` (the `working` skill's long-lived-branch section; a branch whose file names itself gets its pull requests against the branch, and its reviews read only the change itself).

## Redundant attempts for a hard task

For one hard task where the approach is uncertain, the user may choose two to four runs of the same task (a shared `--batch` name, a distinct `--run-id` each), then once every one has opened a pull request, compare them with `fugaro run --recipe pick --pr A --pr B [--pr C] [--pr D]` and keep the best. It multiplies the cost by the number of runs, so offer it only for work where a wrong first attempt would cost more, and only with the user's go-ahead.

## Mind the limits

- `max_parallel` (default 20 in the project's config) refuses a new launch at that many active runs. Launch fewer, or wait.
- Run `fugaro budget show` before a wide launch: it shows the caps and the headroom. A batch that exceeds the day's headroom will halt, with draft pull requests holding the work done so far.
- Tell the user the number of runs and the worst-case cost before launching a batch, and get their yes for the whole batch. The only exception is `/jobmax`, which launches the tasks whose dependencies are all merged, and only where the owner has turned on the project's opt-in; with the opt-in off, this rule stands.
- After the batch, the dearest runs are worth reading: the `working` skill's daily inspection.
- Changes to `.github/workflows/*` cannot be done by a run on GitHub; leave them out of every task.
