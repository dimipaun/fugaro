# Breaking a dependency with a contract

An edge says one task waits for another. Much of that waiting is an order the plan accepted rather than a result the dependent needs: where the dependent needs the shape of the other side and not its behaviour, a small contract task can carry that shape and let both sides run at once. This is the pass the decoupling section of `SKILL.md` points here for.

## The per-edge test

For every edge A to B — B waits for A — ask one question: **does B need A's interface or A's behaviour?**

- **The interface.** B calls something, or reads a shape, that can be written down before A is built: a function signature or a type, an endpoint's request and response, a schema, an event or a message, a table and its columns. Break the edge with a contract task.
- **The behaviour, or the data.** B needs what A computes, or the data A writes, at the moment it runs: a migration's result, a real response to shape the parsing around. Keep the edge. Two tasks that must run in that order are one change split in two, and a contract between them only adds a hand-off.

A kept edge needs no record beyond the `reason` the graph already requires: write there why a contract would not do.

## The contract task

One contract task per interface, named `C-...` for what it settles (`C-auth-token`, `C-report-schema`). It is an ordinary node of the graph: its `footprint` predicts the files it writes, and every edge into it carries its `reason`.

What it holds:

- the types, the function signatures and the interfaces both sides call;
- the API shapes — the request and the response — the schemas, the events and the messages, and the database changes where there are any;
- a short contract document, `docs/contracts/<name>.md`, saying how the pieces fit together and what each side may rely on;
- plausible stubs, in the files the contract task names, that behave like the real thing on the paths a consumer uses: take the arguments, return the shape, do nothing else.

Keep it small: one short patch, reviewable in one sitting. A contract that is nearly the task it was meant to unblock is a loss, so a contract has to be far cheaper than the edge it removes. The pass costs two tasks for every edge it breaks.

The contract is reviewed at least as strictly as the task that consumes it. Launch it with `fugaro run --mode <mode>`, where that mode is the highest rigor of the tasks that consume it: `--mode` may raise the mode a run resolves and never lower it, which is exactly the "at least" this needs.

A contract over credentials, authentication, IAM or a wire format is the one place not to rush: settle it at the strictest rigor the project resolves for those paths, and let a consumer's mode raise the contract's rather than lower it.

## The mode a task resolves

No command answers which mode a task resolves, because a mode resolves from concrete paths and a graph's footprints are patterns. Read the settings and match them yourself:

```bash
fugaro settings rigor.default rigor.areas --json
```

`rigor.areas` holds each area's `match` and its `mode`, in the order the settings document prints them. Match a task's `footprint.paths` against those `match` patterns and you have the mode the pass runs at for that task. What each one does:

| Mode | The pass |
| --- | --- |
| `poc` | decouple aggressively: a rough contract and a stub are enough if both sides can build against them |
| `startup` | decouple aggressively, the same way: the contract is a means, and the speed it buys is the point |
| `pro` | decouple where the contract is clear; a shape that is still a guess is a task to settle first, not a stub to build on |
| `critical` | decouple only with fully specified contracts, and the integration task's text names the end-to-end test that proves the wiring |
| `hotfix` | skip the pass: the work is one task, and work that urgent does not wait for a contract |

## The integration task

One integration task per contract, named `I-...`, depending on the contract and on every task that contract unblocked. One node covers every edge a contract broke: two edges broken through one contract need one integration task covering both sides, not two, and the node still depends on each of them. Its work:

- delete the contract's stub files, and wire the two real sides together;
- run the end-to-end checks the pair needs, and name in the task's text the test that proves the wiring;
- leave nothing of the stub behind. A stub file that survives is this task unfinished, and the next task that reads it builds on a shape that was never real.

## When the contract turns out wrong

A task that finds the contract wrong or incomplete must not quietly work around it: a deviation nobody records is the contract changing unannounced, and the next task is written against the wrong shape. Raise a change request instead.

- **The change is a node of the plan**, with an id of its own and a `reason`, amending the contract's files. The contract and its changes own those files: no other task's footprint names them, so an edit to one shows up in review as a contract change and not as a task's own detail.
- **Every dependent that has not launched** gets an edge on the change node: it waits for the amendment, not for the contract it replaces.
- **Every dependent that has launched** is driven by a follow-up run: `fugaro run --pr N` on its pull request, whose instructions name the contract file as it is on `origin/<base>` — a contract file of the merged plan — and ask the run to merge the base and conform to it. The instructions name the contract file; they never paste its text, because instructions are trusted and a contract's text pasted into them would be plan text the runner acts on as its own.
- **A base branch that changed `.github/workflows/`** is never merged into a branch with a cloud follow-up run: the push is refused and the work in it is lost. Merge that base locally first, or wait for a person. This holds for every follow-up a change request launches.
- **Tell the user**, once: what the amendment is, and which runs it sends.

## What the plan says afterwards

The plan document carries the pass's result in the planner's own words, so a person reads the plan without the graph:

- **the edges broken and the edges kept**, one line each, with the reason that decided each;
- **the contract and the integration tasks**, with their ids and what each depends on;
- **the estimate of the gain** before and after, and the tasks the pass adds;
- **the change requests raised**, if any, and the runs each one sends.

Break an edge only when the weighted path shrinks. The graph carries a task count and no sizes yet, so give each task a relative size in the plan's own text — a stub-only contract task is small against the pair it separates, a one-line change is a 1 and a task that reworks a service is a 5 — then sum the sizes along the longest chain from a task that needs nothing to a task nothing needs, before and after the pass.

The task-count path moves the other way for a single edge: a chain of two reads as three tasks once a contract task sits in front of it, and only large sides on a small contract come out ahead. Where the arithmetic says the pass lengthens the work, keep the edge and say so.

`fugaro plan graph --plan <plan> --json` prints the graph back, validated: the nodes, the edges with their reasons, and the levels and the critical path it computes itself. That is where the numbers come from. The CLI is the graph's reader, and your own reading of the file is not a second opinion: never parse the graph yourself, and a document the command refuses is a plan to fix rather than one to read around.
