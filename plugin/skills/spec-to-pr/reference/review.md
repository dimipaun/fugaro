# The review and fix loop

Each round is a **fresh, independent** full review of the documents as they now stand: never a diff against the last round, and never by the agent that wrote them. Use a stronger model for a plan that touches credentials, a write guard, IAM, an agent's prompt or a CI file, and for any contract over those.

## The brief

Give the reviewer the paths of the documents and tell it:

- Verify every claim about the code against `origin/<default>` (a graph query or `git grep`, then the lines located).
- Check every answer cell against the user's actual answers.
- Check that every decision and every finding lands in a task.
- Check every edge of the plan: where the dependent needs only an interface, is there a contract task and an integration task, and where an edge was kept, does its reason say why a contract would not do?
- Check the graph against the plan: the same tasks, the same edges, a footprint for each, and `fugaro plan graph` reads it.
- Probe each new trust boundary as an attacker would.

It reports ranked findings, each with its location in the documents and its evidence, in these buckets:

| Bucket | Meaning |
| --- | --- |
| Wrong claim | A document contradicts the code |
| Missing | A spec requirement with no plan part, or a decision with no consequence in the plan |
| Unordered | A task needs something a later task builds, or a level holds two writers of one file, or a contract waits on one of the sides it separates |
| Untestable | A task with no acceptance line or no runnable verification |
| Convention | The plan violates a rules file or a ruling of the user |

## Then fix

Verify each reported finding yourself before acting: a reviewer is wrong sometimes. Dismiss one with a one-line reason; defer one by design with a note in the commit body. One fix commit per round. A round of fixes adds no scope: a finding that needs a new behaviour or a product decision is reported to the user, not fixed.

**A confirmed finding can contradict a decision the user already made.** That happens when the decision rested on a wrong fact about the code. Do not keep the decision and ship a wrong plan, and do not change it silently. Amend it:

- Mark it `amended after review` in `reconciliation.md`, state the code fact that contradicts the premise and say what changed and why. Keep the user's intent; change only what the fact forces.
- Add it to the open items as a request to confirm the amended text.
- Say so in the pull request description under Decisions, so the reader sees it is not the original answer.
- When the contradiction is so severe that no amendment keeps the intent, stop the loop and ask with `AskUserQuestion`.

## Exit

Stop when a round returns no Wrong, Missing or Unordered finding, or after round three. Whatever is still open goes in the pull request description under **Open items**. Do not start a fourth round.
