# Reconciling a spec against the code

## Say what you assume first

Before checking anything, list what you take the spec to mean where it is silent or ambiguous, as numbered assumptions (`A1`...) at the top of `reconciliation.md`:

```
A1. "Users" means the project's people, not end customers of the product.
A2. The new endpoint extends the existing service; it is not a second one.
A3. The default branch is the release branch.
```

An assumption that no finding contradicts and no decision rests on stays in the list. One that a finding contradicts is a finding. One that the design turns on becomes a decision. Do not fill a gap silently: a wrong assumption is the most expensive kind of misunderstanding, and the point of this document is to surface it before a run builds on it.

## Check every concrete claim

Check each named class, table, endpoint, enum, flow and number in the spec, and each claim about what the user's own earlier rulings say. When the repository has a code graph (its `CLAUDE.md` says so), query it before grepping and read only the lines it locates; otherwise `git grep`. Read the `CLAUDE.md` and rules files the touched areas load, and every document on the same subject, **including plans and designs the spec supersedes or that may have moved on**: a branch or plan the spec names may no longer exist, and the reconciliation says so.

Classify each finding:

- **Wrong**: the spec contradicts the code.
- **Exists**: the spec proposes what is already there, perhaps under another name.
- **Gap**: the code forces a case the spec is silent on or ambiguous about.
- **Rule**: the spec conflicts with a rules file, a recorded ruling of the user or an existing document.
- **Open**: a question the spec raises and does not answer.

Number each `F1`..., cite the path and the symbol (never line numbers: they drift), and state what it means for the design. Where the spec's concepts overlap what the repository has, open with a table of "spec concept, what the repository already has". Re-check that every path and symbol you cite still exists on the default branch before you write it down.

## Check the spec is complete

A spec that cannot be built from is a finding, not a plan input. Read it against these areas and turn each hole into a Gap or an Open item:

1. **Objective and success criteria**: who it is for and what done looks like, as criteria a test can fail. "Fast" and "intuitive" are not criteria; each one the spec leaves vague is an Open item asking for a number or an observable.
2. **Commands**: the full build, test and check commands, with flags. The repository's own rules files usually answer this: cite them rather than ask.
3. **Where things live**: the source, test and document folders the work belongs in.
4. **Style**: an existing file the new code should look like, so the plan can name it.
5. **Testing strategy**: which test level proves which part, and the targeted command for each.
6. **Boundaries**, in three tiers: what a run always does (tests before commits, the naming convention), what it asks first (a schema change, a new dependency, a CI change), and what it never does (commit a secret, edit a vendored folder, delete a failing test). Most come from the repository's rules; the spec's own go in the plan's conventions.

## Look for the hard questions

The factual mismatches are the easy part. Look for what the spec leaves open:

- The new trust boundary or single point of compromise a proposal creates: who mints, what binds, how it is revoked, and what a hostile agent can do with it.
- What the existing code's invariants forbid.
- Limits of the platform the spec assumes away (timeouts, size limits, quotas), stated as known or UNVERIFIED.
- Legal or policy exposure, stated neutrally as the user's to confirm.
- Migration of what exists, and what an installation at the previous version needs to converge.
- Which parts can ship first, and the smallest useful first slice.
- **Where two parts meet.** Every interface between parts the spec describes loosely is a candidate contract: note it here as an open item so the plan can settle it first.

## UNVERIFIED

Anything you could not check goes in an `## UNVERIFIED` section, numbered `U1`..., each saying what would settle it and who can. Never state one as a finding.
