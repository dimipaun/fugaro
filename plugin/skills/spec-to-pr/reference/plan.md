# Writing the plan

The plan is built for parallelism: a plan that reads as one chain is a defect. Draw the edges first, break the ones that carry only an interface, and write down what is left.

## What the plan holds, in this order

- **Opening and Status.** What it builds (`spec.md` as amended by `reconciliation.md`), that nothing is implemented, that **no task is approved** and each needs the user's explicit go, and every answer that shaped the plan.
- **Conventions every part follows**: only those the plan's areas trigger, pointing at the rules files and `CLAUDE.md` rather than restating them. Include the boundaries of the spec in three tiers (always, ask first, never) and the standing safety rules that apply: no secret-shaped literal in a test, no live cloud action by an agent, live checks run by the user, the size limits of the files the plan edits.
- **Global constraints and review focus**: the inputs and failure modes the spec implies but no task tests, each with the task that pins it.
- **Slices, then tasks.** A slice ships something inert or useful alone. A task is the smallest unit that carries its own test cycle and its own review gate, completable in one focused run and touching about five files or fewer; a task past that is two tasks.
- **Parallel execution**: the edges, the levels, the critical path and the shared-files table.
- **The dependencies the plan broke and kept** (below).
- **Checks the plan takes** (from its reserved block): what each measures and who runs it.
- **After-deploy steps** (a backfill, a configuration or secret change, a rollout order), each as a release-actions entry in that part's own pull request, as the repository's convention says.

Decisions are referenced by `D#`, findings by `F#`, modules by their id.

## The task template

```markdown
### T4: the read command
- Acceptance: what must be true when it is done, as a statement a test can fail.
- Files: exact paths; a new file marked (new).
- Interfaces: what it consumes (task and contract) and what it produces.
- Tests: named and targeted, never a whole suite.
- Command: the one command that runs them.
- Red step: the test that must fail first, and how.
- Depends on: task ids, each with a reason, or none.
- Commit: the message.
- Reviewer tier: standard, or opus with a mandatory independent review for anything touching credentials, a write guard, IAM, an agent's prompt, a recipe or a CI file.
- Owner-run: only for live checks, store or signing steps and copying a workflow file; say exactly what the user types. No agent performs any step of it.
```

## The contract-first pass

An edge A to B says B waits for A. Much of that waiting is an order the plan accepted rather than a result B needs. For every edge ask one question: **does B need A's interface or A's behaviour?** The interface is a signature, a type, an API shape, a schema, an event or a table that can be written down before A is built. The behaviour is what A computes or the data it writes at the moment B runs.

- **Interface only: break the edge.** Add a small contract task `C-<name>` that settles the shape. It depends on neither side of the edge it breaks, nor on anything behind them: a contract written from A's own types leaves B waiting on A through it, which breaks nothing. Then A and B both depend on the contract and run side by side, and an integration task `I-<name>` depends on A, B and the contract.
- **Behaviour or data: keep the edge**, and write its reason. Two tasks that must run in that order are one change split in two.
- **The contract task holds**: the types, signatures and interfaces both sides call; the request and response shapes, schemas and events; the database changes; a short contract document in the repository saying what each side may rely on; and plausible stubs, in files it names, that take the arguments and return the shape and do nothing else. Small: one short patch, far cheaper than the edge it removes. A contract that is nearly the task it unblocks is a loss.
- **The integration task** deletes the stub files, wires the real sides together and names the end-to-end test that proves the wiring. A stub that survives is the task unfinished. One integration task covers every edge one contract broke.
- **Own the contract's files.** The contract and its changes own them: no other task's Files names one. A task that finds the contract wrong raises a **contract change request**, a small task `R-<name>` that amends it, and never works around it; the plan names the dependents each change would reach, and the launched ones are reached by a follow-up run on their pull request that names the contract file by path and never pastes its text.
- **Review it harder.** A contract is reviewed at least at the rigor of its strictest consumer, and launched at that mode. A contract over credentials, authentication, IAM or a wire format gets the strictest rigor and an independent review (`fugaro review --pr N`) before either side is written against it, since both sides build on that mistake.
- **Plan, never launch.** The contract, integration and review runs are proposed with their count and worst-case cost, and none starts until the user says yes.

Weigh the break before you keep it: the pass adds two tasks, so break an edge only when the weighted path shrinks. Give each node a `size` (a stub-only contract is small against the pair it separates), then let the CLI work out the gain rather than guessing it.

**By the mode each task resolves.** Read the settings for the repository and match the tasks' paths against the area patterns:

```bash
fugaro settings rigor.default rigor.areas --repo <owner/name> --json
```

| Mode | The pass |
| --- | --- |
| `poc`, `startup` | decouple aggressively; a rough contract and a stub are enough |
| `pro` | decouple where the contract is clear; a shape that is still a guess is a task to settle first |
| `critical` | decouple only with a fully specified contract, and name the end-to-end test in the integration task |
| `hotfix` | skip the pass: the work is one task |

Read the pass's switch first: `fugaro settings planning.decoupling --json`, with `--repo` naming the repository. When it is off, say so in the plan.

## The graph, written beside the plan

Write `implementation-plan.graph.json` in the same folder, in schema 3 (`parallelism` shows a full example): the nodes with their kind (contract, integration or contract change; an ordinary task carries none), size and footprint paths; the `edges` that remain with a `reason` each; one `decoupling` entry per broken edge (`contract`, `was`, `integration`, `reason`); and the contract changes the plan anticipates. A contract names its stubs one by one in `stubs` and in its own footprint; a footprint is a prediction of the files a task touches, in glob form, and never a permission. Then read it back:

```bash
fugaro plan graph --plan docs/<slug>/implementation-plan.md
```

A refusal (a cycle, a missing reason, a contract with no file of its own) is a plan to fix. The read prints the edges broken, the stubs left and the gain in tasks and weight; a break it reports as no gain is one to undo.

## What the plan says in its own words

So a person reads the plan without the graph:

- **The edges broken and the edges kept**, one line each, with the reason that decided it.
- **The gain**: the critical path before and after, as the read reports it.
- **Levels and the critical path**: tasks in one level run at once. Say what must be sequential and why (a build dependency, an interface, one file).
- **A shared-files table** proving no level holds two writers of one file; a change to any task's Files re-checks it.
- **The contract changes anticipated**, and which dependents each would reach.

## When the plan changes later

A later ruling can reshape the plan, for example "skip the interim slice". Re-slice cleanly: keep a short "considered and declined, and why" note, renumber without reusing a reserved number, and update the edges, levels, graph, shared-files table, critical path and every answer cell the ruling touches, keeping the original answer visible beside a dated amendment.

The spec and plan stay alive after the pull request merges. A run that finds the reconciliation wrong amends it in a documents pull request first, then builds; a task's pull request names the `T#` and `D#` it implements.
