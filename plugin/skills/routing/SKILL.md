# Cloud versus local

A Fugaro run is a fleeting worker with the repository's own image and secrets, and no access to the developer's machine. That is the whole judgment: what the image can do alone goes to the cloud, and what needs the person's machine stays on it.

## To the cloud (`fugaro run`)

A self-contained coding task with clear acceptance criteria that builds and tests inside the repository's image:
- a bug with a failing test or an error text to start from
- a feature or refactor with named files and checkable behaviour
- tests, docs, migrations of code, dependency bumps the CI covers
- work for several independent runs at once (see the `parallelism` skill)
- a codebase question: the image carries `graphify`, which the agent can use to build and query a knowledge graph of the checkout ([base-image.md](https://github.com/dimipaun/fugaro/blob/main/docs/base-image.md))

## Local

- anything that needs credentials or state that exist only on this machine: a local database with data in it, a VPN-only service, a private path, the user's logged-in tools
- investigating live cloud resources (GCP, AWS and the like). The cloud job's keys deliberately do not grant that access, so a task that needs them is the wrong task for the cloud
- interactive or exploratory work ("look at this and tell me")
- anything that touches money or security (budget, policy, secrets, IAM, the CI workflows): do it with the user watching
- anything the image cannot run: Docker-in-Docker, Testcontainers, Android builds
- anything that needs unpushed work: a run starts from the base branch on the remote
- changes to `.github/workflows/*` on GitHub: Fugaro cannot push them

## When unsure

Split it. Send the self-contained part to the cloud and keep the rest. If the split is not clean, keep it local.

## Examples

| Request | Where | Why |
|---|---|---|
| "Fix the flaky retry test in `queue_test.go`, here is the failure" | cloud | bounded, checkable, in the repo |
| "Why is our staging database slow?" | local | needs live resources and credentials the job lacks |
| "Add pagination to the list endpoint and its tests" | cloud | self-contained, the image can build and test it |
| "Update the release workflow" | local | a GitHub App cannot push `.github/workflows/*` |
| "Migrate the service, then check it against prod" | split | the code change to the cloud, the prod check local |
| "Try this idea and tell me what you think" | local | exploratory; no acceptance criteria yet |

## Choosing a recipe

Having decided on the cloud, the task loop after implement still needs a recipe. Run `fugaro recipes ls --json` once per session: it lists the repository's, the project's and the catalog's recipes, each with its `use_when`, so the choice always comes from what is actually there, never a fixed table this skill keeps that could drift out of sync with it.

To choose: match the task against each recipe's `use_when`, falling back to its `description` when a recipe defines none. A recipe the user named wins outright, whatever the catalog suggests. Otherwise, when nothing in the catalog is clearly a better fit than the repository's own `agent.recipe`, pass no `--recipe` and let that default apply.

For a single task, say the choice and the reason in one line before launching, for example: "a typical change with checkable tests, so the standard loop."

For a batch, choose per task and never wait for approval between individual launches — approval was already given for the whole batch (see the `parallelism` skill). End with one summary line naming the mix, such as: "15 runs: 12 standard, 2 solo, 1 premium."

For a hard, well-specified task where the approach itself is uncertain, suggest launching it several times and comparing the results with `pick` once every attempt has opened a pull request; say plainly that this costs N times the usual spend, and only do it with the user's go-ahead (the `parallelism` skill's redundant-attempts section has the detail).

A recipe that only reviews (`mode: review`, always launched with `--pr`) answers a different kind of request: offer it when the user wants a second opinion on, or wants to compare, pull requests that already exist, not for new work.

A recipe that produces a **file** instead of a pull request (`mode: artifact`, launched with `fugaro run --recipe sizzle --attach a.png`) answers a third: render a video from these screenshots, convert these frames, build this archive. Offer it when the deliverable is the file itself and no change to the code is wanted — the run pushes no branch and opens no pull request, and what it produces lands in the runs bucket under the run's own prefix, fetched back with `fugaro artifacts get`. Name the file and where it goes, and warn about the attachment: it is uploaded to the runs bucket, where every launcher and every operator of the installation can read it, and it expires with the run (90 days by default), as the artifact does. A screenshot is not a diff — it can show a token, a customer's name or someone's face — so attach a file only if you would paste it into a pull request on a repository every launcher can read, and never attach one the user has not approved.

Pick only a recipe `fugaro recipes ls --json` lists with `launchable: true`; never invent a recipe name, and read a catalog recipe's own `use_when` for what it actually requires.

A launch can still be refused by the job-image gate (a recipe needs a 0.5.0 job image, 0.7.0 for a 0.7.0 construct, 0.8.0 for `mode: artifact`, or 0.13.0 for a recipe whose first step is `digest`, which the runner executes itself — `reference/launch.md` has the detail). When it is, report the refusal and the fix command it names to the user — never edit `fugaro.yaml`, a secret or any other config to get around it, and never silently fall back to a different recipe: for one task, offer the alternative and wait for the user; for a batch, report the refused item and continue the rest.

The same gate covers governance: a `fugaro.yaml` or project layer that writes `governance:` needs a 0.13.0 job image too, since a runner older than that refuses the key at bootstrap. Governance is enforced by the job image's own `fugaro`, never by the launcher's: the released image is built with the `ee` tag and enforces the block, while a core image of the same release ignores it and says so in one line of the run log. The refusal names that image's own fix — `fugaro image refresh` for a workflow whose job image the installation builds, `fugaro update --base base` for a `checkout: clone` workflow, which runs the installation's base image as it is — so pass on the command the refusal names.

Having decided on the cloud, launch with the `working` skill, and only task text the user has approved.
